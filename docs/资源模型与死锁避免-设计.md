# 资源模型与死锁避免 — 设计

> 目标：**多流程并行时理论上不死锁**。
> 代价：单次分配要做安全检测（微秒级，**常开，不做开关**——见 R6 修正）。

---

## 一、为什么现在的设计不够

### 缺陷 1：锁的粒度错在"设备"

**场景**：B 只有一个出入口，但内部有多个位置。

```
B（3 个内部位置）
流程1：板1 进 B 位置1
流程2：板2 进 B 位置2      ← 应该能并行！
```

**如果锁"B 这台设备"，流程2 进不去** —— 这是错的。

**正确**：B 的**出入口**是共享的，**内部位置**是独立的。

### 缺陷 2：`returnTo` 只解决单链路

**场景**：A→B→C→A 环，3 个流程。

```
流程1 占 A，等 B
流程2 占 B，等 C
流程3 占 C，等 A
→ 循环等待，必死锁
```

**2 个流程能交错，3 个不行。** `returnTo` 双锁解决不了环。

---

## 二、资源模型：三层

| 层 | 资源 | 数量 | 共享性 | 举例 |
|---|---|---|---|---|
| **L1 位置** | 每个层位 | 每设备 N 个 | **独立** | `ID1183-L1`、`ID1183-L2` |
| **L2 出入口** | 设备的进/出通道 | 1 个/设备 | **共享** | `ID1183-PORT` |
| **L3 机械臂** | 搬运用机器人 | 1 个/岛 | **共享** | `ID1731` |

### 用三层解释你的场景 1

```
流程1 要往 B 送板：
  抢 L2（B 的出入口）  ← 独占，一次进一块
  抢 L1（B 的某个位置）← 选一个空位置
  释放 L2              ← 送完就放开，别人才好送

流程2 同时也想送：
  L2 被占 → 等（几秒）
  L2 释放 → 抢到 → 抢 B 的另一个位置（L1）→ 成功

结果：两块板都在 B 里，各占各的位置 ✅
```

### ⚠ 必须补的 invariant（评审 R3 指出）

**一次 Transfer 要同时持有 5 种资源**（机械臂 + 源口 + 源位 + 目标口 + 目标位 + 回程位），
原文没规定**跨资源类型的获取顺序**。

**如果实现成"先抓板、后申请目标位、被等待图拒绝"** ——
板已经在机械臂上，**没法"返回失败重试"**。

#### 强制顺序：所有申请完成前，板不离开源位

```
① 申请源口 (L2)
② 申请源位 (L1)     ← 确认板在
③ 申请目标口 (L2)
④ 申请目标位 (L1)
⑤ 申请回程位 (L1)   ← D105 要求
⑥ 申请机械臂 (L3)
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   **到此为止，所有资源到手；板还在源位，随时可以安全放弃**
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⑦ 抓板（板离开源位）  ← 这是不可逆点
⑧ 移动到目标、放下
⑨ 释放机械臂、源口、目标口
⑩ 回程位保持（直到板回去，见 D105）
```

**任何一步申请失败**：

```
→ 释放已申请的全部资源
→ 板还在源位，状态不变
→ 安全重试
```

**这个 invariant 是"拒绝"语义能成立的前提**。
没有它，等待图的"拒绝"在物理世界无法执行。

#### 顺序为什么是"口 → 位 → 臂"

| 约束 | 理由 |
|---|---|
| **源口先于源位** | 口是通道，位是目的地；先通道后目的符合物理 |
| **目标口先于目标位** | 同上 |
| **机械臂最后** | 臂是最贵的资源，最后申请能减少持有时间 |

**全序**：`源口 → 源位 → 目标口 → 目标位 → 回程位 → 机械臂`

**固定全序消除循环等待**——这是比"按 id 升序"更细的规则
（id 升序只在同类资源内有效，跨类型需要显式规定）。

### 关键：入口是"动作级"的，不是"任务级"的

**入口只在"板子穿过"的那几秒被占**，不是整个任务全程。

这和机械臂一样 —— 都是**瞬时资源**。

## 三、死锁避免：等待图 + 环检测

### 为什么不用完整银行家算法

**银行家算法要求预知"最大需求"**，但：

- 流程有**分支**，未来不确定
- 时长**不准**，无法精确算安全序列
- 每次分配算 O(n²)，开销大

### 实际方案：等待图（Wait-For Graph）

**只记录"谁在等谁"，检测环**。

```
流程1 要 B，B 被流程2 占  →  边：流程1 → 流程2
流程2 要 C，C 被流程3 占  →  边：流程2 → 流程3
流程3 要 A，A 被流程1 占  →  边：流程3 → 流程1
                            ↑ 检测到环！
```

**检测到环 → 拒绝这次申请**（让最后一个申请者等，而不是盲抢）。

### 为什么这个方案可行

| 对比 | 银行家 | 等待图 |
|---|---|---|
| 需要预知最大需求 | ✅ 必须 | ❌ 不需要 |
| 分支变化时 | 要重算 | 动态演进 |
| 计算量 | O(n²) 每次 | O(E) 检测环 |
| 能否 100% 避免 | 理论上能 | **能**（只拒绝成环的申请） |

**等待图能保证不死锁**——因为任何可能成环的申请都被拒了。

**代价**：某些"本来能过"的申请会被误拒（保守）。

### 算法

```
tryAcquire(资源 R, 执行 P):
  ① 能直接抢到？→ 抢，返回成功
  ② 抢不到，找到持有者 Q
  ③ 在等待图里加边 P → Q
  ④ DFS 检测从 P 出发能否回到 P
     - 有环 → 撤销边，返回"会死锁，拒绝"
     - 无环 → 返回"等待中"
  ⑤ 被释放时，唤醒等待者
```

---

### ⚠ R5 修正：`returnTo` 必须显式配置，不给默认

**评审意见**：默认等于 `source` 会**静默出错**。

**场景**：

```
流程：从 A 出板 → 到 B 执行 → 放到 C（不回 A）
不配 returnTo → 默认 = A → 错误地预留 A 的位置
  → 浪费一个位置，且 C 那边可能抢不到
```

**规范**：**`returnTo` 为必填**，不配就报错（编排时校验）。

**校验位置**：保存流程时检查所有 `Transfer` 节点，
缺 `returnTo` 直接拒绝保存，并提示"必须声明板最终位置"。

**代价**：编排时多填一个字段。
**收益**：不会因为默认值静默出错——这类 bug 最难查（系统"正常"运行，只是位置错了）。

## 四、你的场景 2 推演：A→B→C→A，3 个流程

### 初始

```
流程1 占 A
流程2 占 B
流程3 占 C
```

### 流程1 要 B

```
B 被流程2 占
等待图加边：流程1 → 流程2
从流程1 出发 DFS：流程1→流程2，流程2 没在等谁 → 无环
结论：允许等待
```

### 流程2 要 C

```
C 被流程3 占
加边：流程2 → 流程3
DFS：流程2→流程3，流程3 没在等 → 无环
结论：允许等待
```

### 流程3 要 A

```
A 被流程1 占
加边：流程3 → 流程1
DFS：流程3→流程1→流程2→流程3  ← **成环！**
结论：**拒绝**，流程3 必须等（不加入等待图，直接失败重试）
```

**结果**：流程1、2 继续等，流程3 退出等待。
当流程1 拿到 B、完成、释放 A 后，流程3 才能要 A。

**不死锁 ✅**

### 2 个流程的情况

```
流程1 占 A，要 B（B 被流程2 占）→ 加边 1→2，无环，等待
流程2 占 B，要...（不需要 A）→ 完成，释放 B
流程1 拿到 B → 完成
```

**2 个能过，3 个被拒 —— 符合你的判断。**

## 五、检测常开，不做开关（R6 修正）

**原设计想做 `LABOS_DEADLOCK_GUARD=auto/on/off` 开关，评审后取消。**

### 取消的理由

| 问题 | 说明 |
|---|---|
| **开销本来就小** | 等待图检测是内存 DFS，微秒级 |
| **COUNT 有竞态** | 两个执行同时启动，都查到自己"是唯一" → 都不检测 → 漏检 |
| **单 run 并行漏检** | 一个实验内部有 `parallelGateway`，`running = 1` 但确实有并发争用 |

### 开销算清楚

```
资源数 n ≤ 10，边数 E ≤ 20
一次 DFS < 10 微秒
一次 Transfer 涉及 6 次资源申请 → 60 微秒
```

**对比一次设备动作（150ms 到 30 分钟）**，60 微秒可以忽略。

**为了省 60 微秒引入竞态和漏检，不划算。**

### 如果将来确实需要降级

**不做环境变量开关**，而是**在代码里保留一个 `DeadlockGuard` 接口**，
默认实现是"完整检测"，测试时可以注入"空实现"。

**这样有测试灵活性，又不引入运行时的竞态。**

## 六、实现分批

### 第一批：资源模型（1 周）

| 任务 | 产出 |
|---|---|
| L1/L2/L3 三层建模 | `resource_booking` 的 `source_type` 区分 `position`/`port`/`robot` |
| 出入口的"动作级"锁 | 搬运前后抢/放，不全程占 |
| 位置选择（自动选空位） | 复用 `position_state` |
| 保留 `returnTo` | 回程位置预留 |

**验收**：你的场景 1 —— 两块板同时进 B（不同位置）。

### 第二批：死锁检测（1 周）

| 任务 | 产出 |
|---|---|
| 等待图数据结构 | 内存 `Map<Long, Set<Long>>` |
| 环检测（DFS） | `wouldDeadlock(P, Q)` |
| 拒绝 + 重试 | 被拒后等 200ms 重试，最多 N 次 |
| 开关 | `LABOS_DEADLOCK_GUARD` |

**验收**：你的场景 2 —— 3 个流程走 A→B→C→A，**不成死锁**（第三个被拒，前两个能完成）。

### 第三批：兜底与可观测（3 天）

| 任务 | 产出 |
|---|---|
| 等待图快照接口 | `GET /api/deadlock/graph` |
| 超时强制释放 | 超过 2 小时清锁（已有） |

## 七、代价与取舍

### 明确接受的代价

| 代价 | 说明 | 为什么接受 |
|---|---|---|
| **误拒** | 某些本可过的申请被拒（保守） | 死锁的代价更大 |
| **复杂度** | 三层资源 + 等待图 | 生产级并行必须付 |
| **调试难** | 出问题要查等待图 | 提供快照接口 |

### 明确不做的

| 不做 | 为什么 |
|---|---|
| 完整银行家算法 | 需要预知最大需求，流程有分支做不到 |
| 抢占（强制夺资源） | 板子可能真在机械臂上，抢占会砸板。<br>**注意**：这不是"银行家算法要求抢占"——银行家本身就是为不可抢占资源设计的，<br>不采用它的原因是"预知不了最大需求"（见 R1 修正） |
| 自动释放死锁 | 同上，只告警不自动处理 |

---

## 八、一句话总结

**资源要分三层**：位置（独立）、出入口（动作级共享）、机械臂（动作级共享）。

**死锁用等待图检测环**：只记录"谁在等谁"，成环的申请拒绝。

**单实验时开关关掉**：没有并发就不会死锁，不付这个开销。

**先做资源模型，再做检测** —— 资源粒度错了，检测算法救不回来。
