## 2. 相同点（三份一致，可以当作已定）

### S1 ⭐ 都否决"分支 runner + allOf"

| 评审 | 说法 |
|---|---|
| A | 不采用分支 runner + done/visits 隔离合并，改成单线程 GraphCoordinator 维护图状态 |
| B | 分支 runner + allOf 有线程池饥饿死锁风险 |
| C | 不推荐；嵌套时 4 个外层线程占满池，内层任务排队等不到 |

**理由一致**：`allOf().join()` 在嵌套并行时是**递归阻塞**——外层任务占着线程等内层，内层排队等线程。这不是性能问题，是**死锁**。

我方案里 D7 说"内层不额外申请信号量"，三份都指出**这只能解决信号量，解决不了线程占用**。

### S2 ⭐ 都指出：6 个容器改线程安全 ≠ 具备并发安全性

| 评审 | 补充的缺口 |
|---|---|
| A | `RunProgress` / `RunStateMachine.seq` |
| B | 事件链、`StepCollector`、`RunMonitor`、`loopIndexSupplier` |
| C | **11 处**完整清单（见 §4） |

`ConcurrentHashMap` 解决不了：图执行语义、复合操作原子性、DB 事务边界、**实例字段传递上下文**。

### S3 ⭐ 都发现 `loopIndexSupplier` 比 `seq` 更危险

```java
stateMachine.withLoopIndexSupplier(() -> round);   // 实例字段
NodeStatus st = stateMachine.executeNode(...);
// 完成处理器里再读 loopIndexSupplier.getAsInt()
```

并行后 A 设 round=2、B 设 round=5、A 的完成处理器读到 5 ⇒ **物料记录到错误圈次**。

**这条我完全没发现**，三份里至少 C 和 B 明确点了。

### S4 ⭐ 都不接受"停止等待超限强制 UNKNOWN"

```
超限 ≠ 设备已停 ≠ 可以释放租约
```

正确处置：超限进入 `QUARANTINED`（隔离待确认），**不自动结束物理执行、不释放设备**。

这条直接修正我方案的 D3。

### S5 都主张"协调等待阈值"不是"分支超时"

| 概念 | 归属 |
|---|---|
| 节点执行超时 | 业务配置 |
| 分支执行超时 | **不设** |
| **停止/暂停协调等待** | 只设运维告警阈值，不强制终止 |

### S6 都同意 D6：全局固定池 + Run 级额度

- 不推荐每 Run 独立池（线程数爆炸）
- 不推荐 `commonPool`（被其他任务影响）
- Run 级额度由 **Coordinator 维护 in-flight 计数**，不由 worker 递归拿信号量

### S7 都同意 D2 方向对，但要补读写冲突

不只查 WAW（两分支都写），还要查 **RAW / WAR**（一个写一个读）。

业务真需要累加 ⇒ **分支独立输出 + JOIN 后聚合**，不提供原子自增。

### S8 都主张：先做"线程安全 + 抽执行器"，验证串行等价，再上并发

| 评审 | 表述 |
|---|---|
| A | S0（补线程安全）→ S1（抽 NodeExecutor，串行等价） |
| B | V1（重构不改行为）→ V2（真并发）→ V3（可恢复） |
| C | 先做 S0、S1，通过后再进线程池 |

**这是三份唯一的交集，也是无争议的最小第一步。**

## 3. 不同点（必须拍板）

### D-A ⭐ 最关键：JOIN 用 `pending` 计数，还是 `SplitActivation`（激活身份）？

| 评审 | 主张 | 理由 |
|---|---|---|
| **A（Trae）** | **用现有 `pending`** | 入边计数已能表达"等齐"，V1 够用 |
| **B（MiniMax）** | **必须 `SplitActivation`** | 同一 JOIN 被不同圈次再次触发时，`pending` 复位时机难保证；可恢复性要求激活身份可持久化 |
| **C（ChatGPT）** | **两阶段**：简单图 `pending` 够；嵌套/循环需要 `splitActivationId` | 更细分 |

**技术后果**：

```
如果 V1 不支持"并行分支内有循环"  → pending 够用，省一大块
如果要支持                          → 必须 SplitActivation，工作量 +50%
```

**这直接决定 V1 的范围**。

### D-B ⭐ 第二关键：设备节点是"同步阻塞 worker"还是"SUSPENDED"？

| 评审 | 主张 |
|---|---|
| **B（MiniMax）** | **必须 SUSPENDED**：设备命令派发后释放 worker，等事件到达再恢复；否则 4 个 worker 等 4 个 30 分钟孵育，池废了 |
| **A / C** | 未明确（模型里节点提交 worker 后同步执行） |

**现状事实**：`executor.execute()` 是**阻塞**的，同步等设备回包。

**技术后果**：

| 选择 | 后果 |
|---|---|
| **同步阻塞**（V1/V2） | 并行度受 worker 数限制（4 worker = 最多 4 节点并行）。**不会死锁**，但等长设备时 worker 被占 |
| **SUSPENDED**（V3） | worker 可复用，但要把整个等待机制改成事件驱动 + 可恢复 —— **这是又一次大重构** |

**我的判断**：V2 阶段同步阻塞**够用**——因为并行度本来就受设备数限制（瓶颈是机械臂/设备，不是 worker）。SUSPENDED 留 V3。

### D-C 改造范围

| 评审 | 范围 | 工作量估计 |
|---|---|---|
| **A（Trae）** | 6 阶段，不引入 Token，不重构 GraphPlan | **1–2 周** |
| **C（ChatGPT）** | 先出"逐段职责映射表"，再定接口 | **3–5 天做映射 + 按映射实施** |
| **B（MiniMax）** | 完整 Runtime 重构：Compiler/GraphPlan/Token/SplitActivation/NodeHandler/EventDispatcher，V1–V3 | **1–2 个月** |

**B 的方案技术上是自洽的**（"可恢复的运行时不能依赖线程栈"这句话是对的），但**远超"尽快把并发做好"的诉求**。

### D-D 是否引入 Token

| 评审 | 主张 |
|---|---|
| B | 必须：`ExecutionToken{tokenId, branchId, splitActivationId, currentNodeKey, loopIndex}` |
| A | 不需要：`pending` + 分支局部状态够 |
| C | 只提 `splitActivationId`（图调度内部概念），不提完整 Token |

### D-E 共享汇合节点是否合法

**C 独家指出**：两条分支可以合法汇合到**同一个普通节点**（不是 gateway），`WorkflowGraphParser.Graph` 允许多入边，现有 `pending` 能处理（等齐后只执行一次）。

⇒ **不能要求"分支子图必须完全不相交"**，否则会错误拒绝合法图。

**这条我方案里写错了**（我写了"分支子图必须互不相交"作为硬校验）。

## 6. 推荐路线

### 第一步：S0 —— 按 §4 的 17 项清单补齐线程安全

不做这一步，后面所有并发都是空的。

其中 **#10 `loopIndexSupplier`** 和 **#11 `events`** 是必须的（会直接出错），其余按清单推进。

### 第二步：S1 —— 抽 `NodeExecutor`，串行等价验证

- 只抽"执行一个节点"的入口，**不动图推进**
- 用**三层验证的第一层**：改造前后同一批流程的执行 trace 对比（节点顺序、次数、变量值、圈次、台账）
- 这一步不引入线程池

### 第三步：S2 —— 建 `GraphCoordinator`，仍串行

把 `ready`/`pending`/`done`/`visits`/tracker 收进 Coordinator，**只有它能改**。

### 第四步：S3 —— 节点提交有界 WorkerPool

- Coordinator 继续单线程
- 节点执行交给池
- 完成结果回传 Coordinator
- **JOIN 仍用 `pending`**（D-A 选 A1）

### 第五步：S4 —— 停止/暂停协调

`STOP_REQUESTED → DRAINING → FAILED/QUARANTINED`，**超限只告警不强制终止**。

### 第六步：S5 —— 三层验收

Fake Executor → 模拟器 → 真实设备。

## 7. 与"尽快做好"的张力

**诚实的评估**：

| 路线 | 时间 | 能拿到什么 |
|---|---|---|
| 只做 S0+S1 | 2–3 天 | 代码结构变对，**仍然串行** |
| S0+S1+S2+S3 | **1–2 周** | **真并发**（这个流程的两个分支会重叠） |
| 加 S4 | +3 天 | 失败/暂停在并发下正确 |
| MiniMax 完整方案 | 1–2 月 | 可恢复的 Runtime |

**用户要的"并行同时执行"，最短路径是 S0→S3，1–2 周。**

中间任何一步跳过都会出问题：
- 跳 S0 ⇒ 并发下丢数据/串圈次
- 跳 S1 ⇒ 没有并发插入点
- 跳 S2 ⇒ 图状态被多线程改，出现第二个并发 bug 源

---

## 8. 我的建议

1. **接受三份的一致结论**：放弃"分支 runner"，改单线程 Coordinator + 并发节点
2. **D-A 选 A1、D-B 选 B1**（先做出来，V2 再升级），把"分支内循环 + 设备挂起"明确列为**当前不支持**
3. **S0 按 17 项清单做**，不要只做我原来列的 2 处
4. **C 的"共享汇合节点合法"要吸收**——删掉我方案里"分支子图必须互不相交"的硬校验，改成"共享节点由 Coordinator 负责，不进任何分支"
5. **MiniMax 的完整重构不现在做**，但把它的 `ExecutionToken`/`SplitActivation` 记为 V2 候选
