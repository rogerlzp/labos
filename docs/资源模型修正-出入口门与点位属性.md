# 资源模型修正：出入口、门、点位属性

> **L2「每设备一个出入口」是错的**。
> 实际有三类出入口形态 + 一个我漏掉的资源：**门**。

---

## 一、用户指出的四个事实

| # | 事实 | 对设计的影响 |
|---|---|---|
| 1 | 出入口有三种形态：分离 / 多进多出 / 单一 | L2 不能是"1 个/设备" |
| 2 | 机械臂只有一个爪子，抓起→搬运→放下**不可中断** | ✅ L3 的"动作级"定义正确 |
| 3 | **门没开，机械臂伸进去会撞机** | **漏了一个资源：门** |
| 4 | 点位需要额外属性才能做动态规划 | `robot_point` 字段不够 |

---

## 二、修正后的资源模型（四层）

| 层 | 资源 | 粒度 | 数量 | 占用 |
|---|---|---|---|---|
| **L1 位置** | `position_state` | 一个层位 | 每设备 N 个 | 任务全程 |
| **L2 通道** | `device_port` | 一个进/出口 | **每设备 1~N 个** | 动作级 |
| **L3 门/闸** | `device_access` | 一个可开合部件 | 每设备 0~N 个 | **动作级（开合期间）** |
| **L4 机械臂** | `device_state` | 一台机器人 | 每岛 1 个 | 动作级 |

### 2.1 L2：通道（三种形态）

```sql
CREATE TABLE device_port (
    id            bigserial PRIMARY KEY,
    tenant_id     bigint NOT NULL,
    resource_id   bigint NOT NULL REFERENCES resource_node(id),
    code          varchar(32) NOT NULL,       -- 'IN-1' / 'OUT-1' / 'BOTH'
    direction     varchar(8)  NOT NULL,       -- 'in' | 'out' | 'both'
    port_type     varchar(16) NOT NULL,       -- 'slot' | 'tray' | 'drawer' | 'conveyor'
    capacity      smallint NOT NULL DEFAULT 1,-- 同时能过几块板
    position_id   bigint,                     -- 关联的 position_state（如果有）
    UNIQUE (tenant_id, resource_id, code)
);

COMMENT ON COLUMN device_port.direction IS
    'in=只进 out=只出 both=进出共用（一次只能过一块）';
COMMENT ON COLUMN device_port.capacity IS
    '同时能过几块板。1=串行，>1=可并行（比如宽传送带）';
```

**三种形态怎么配**：

| 形态 | 配置 |
|---|---|
| **分离** | `IN-1`(in) + `OUT-1`(out) → **两把独立的锁** |
| **多进多出** | `IN-1`(in) `IN-2`(in) `OUT-1`(out) `OUT-2`(out) → 四把锁，可并行 |
| **单一** | `BOTH`(both, capacity=1) → **一把锁，进和出互斥** |

**关键**：**锁的数量由配置决定，代码不用改**。

### ⚠ capacity > 1 时锁是"信号量"不是"互斥"（已与用户确认）

**用户明确**：capacity > 1 的通道**物理上常见**（宽传送带、多层托盘），
**必须支持 1 / 2 / N**。

**所以通道锁不能是"有没有被占"，而是"还能进几个"**：

```sql
-- 不是 status='active' 互斥，而是计数
CREATE TABLE device_port_usage (
    tenant_id   bigint NOT NULL,
    port_id     bigint NOT NULL REFERENCES device_port(id),
    in_use      smallint NOT NULL DEFAULT 0,
    max_capacity smallint NOT NULL,
    updated_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, port_id),
    CONSTRAINT ck_port_capacity CHECK (in_use >= 0 AND in_use <= max_capacity)
);

-- 抢通道：原子地 +1（未满才成功）
UPDATE device_port_usage
SET in_use = in_use + 1, updated_at = now()
WHERE tenant_id = ? AND port_id = ? AND in_use < max_capacity
RETURNING in_use;
-- 返回行 = 抢到；无返回 = 满了

-- 释放：-1
UPDATE device_port_usage
SET in_use = in_use - 1, updated_at = now()
WHERE tenant_id = ? AND port_id = ? AND in_use > 0;
```

**三种情况的对照**：

| capacity | 语义 | 用哪张表 |
|---|---|---|
| **1** | 互斥（一次一块） | `device_port_usage`（`in_use < 1` 等价互斥） |
| **2** | 信号量（同时两块） | 同上 |
| **N** | 信号量 | 同上 |

**统一用 `device_port_usage`**——capacity=1 只是 `max_capacity=1` 的特例，
不用两套代码。

**注意**：**位置锁（L1）仍然是互斥**——一个位置只能放一块板。
只有**通道**支持计数。

### 2.2 L3：门（我漏掉的资源）

**为什么门是资源**：

```
离心机门关着
  → 机械臂伸进去 → **撞机**
  → 必须先调 OpenDoor，确认开了，才能进去
```

**门的开合本身是一个动作**（几秒），**这期间也占资源**。

```sql
CREATE TABLE device_access (
    id              bigserial PRIMARY KEY,
    tenant_id       bigint NOT NULL,
    resource_id     bigint NOT NULL REFERENCES resource_node(id),
    code            varchar(32) NOT NULL,     -- 'DOOR' / 'LID' / 'DRAWER'
    access_type     varchar(16) NOT NULL,     -- 'door' | 'lid' | 'drawer' | 'gate'
    state           varchar(16) NOT NULL DEFAULT 'unknown',
                                              -- closed|open|opening|closing|unknown
    open_method     varchar(64),              -- 'OpenDoor'（可空=手动门）
    close_method    varchar(64),              -- 'CloseDoor'
    open_timeout_ms integer NOT NULL DEFAULT 30000,
    state_checked_at timestamptz,
    UNIQUE (tenant_id, resource_id, code)
);

COMMENT ON COLUMN device_access.state IS
    '当前开合状态。unknown 表示不确定，必须先查询或强制关闭';
COMMENT ON COLUMN device_access.open_method IS
    '打开的门控方法名。为 NULL 说明是手动门，需要人工打开后确认';
```

**门的三种情况**：

| 情况 | `open_method` | 处理 |
|---|---|---|
| **电动门** | `'OpenDoor'` | 系统调方法打开，等状态变 open |
| **手动门** | `NULL` | **必须人工打开 + 确认**（系统没法开） |
| **常开（无门）** | 无记录 | 不需要处理 |

**门的状态怎么来：靠动作，不查询**（已与用户确认）

**设备不提供"查询门状态"的接口，也不需要**：

```
① 系统默认认为门是关的（初始状态 closed）
② 流程里有"开门动作"（方法 OpenDoor）
③ **动作成功返回 = 门开了** → state = 'open'
④ 反之"闭门动作"成功 = 门关了 → state = 'closed'
```

```java
// 进入设备前
if (access != null && !"open".equals(access.state())) {
    if (access.openMethod() == null) {
        throw new NeedsHuman("手动门，请人工打开后确认");
    }
    Result r = callMethod(access.openMethod());
    if (!r.ok()) {
        throw new DeviceFault("开门动作失败：" + r.errorCode());
    }
    // **不查询，直接信动作结果**
    access.setState("open");
    access.setStateCheckedAt(now());
}
```

**为什么这样可行**：

| 条件 | 说明 |
|---|---|
| **门只有系统能开关** | 人工不会去动（或者动了要通知系统） |
| **动作有明确的成功/失败** | 驱动返回 `method_status=2` 就是成功 |
| **流程保证成对** | 开了必关（`finally` 里补关） |

**风险与缓解**：

| 风险 | 缓解 |
|---|---|
| **人工手动关了门，系统不知道** | 要约束：人工动门必须在中控点"已手动关闭" |
| **动作成功但门实际没开**（机械卡住） | 靠后续动作失败暴露（伸不进去会报错） |
| **开门后执行崩溃，门一直开着** | 恢复时**强制先关门再开门**（幂等） |

**门必须成对开关**（已与用户确认）

```
有开门动作 → 必须有闭门动作
```

**实现约束**：

| 约束 | 做法 |
|---|---|
| **成对** | 开门的代码路径，`finally` 里必须有关门 |
| **关门失败要报错** | 不能吞掉，要标 `state='unknown'` 并告警（门可能半开） |
| **异常路径也要关** | 抓板失败、超时、暂停——所有路径都要走关门 |

```java
boolean opened = false;
try {
    openDoor(access);  opened = true;
    // ... 取放板 ...
} finally {
    if (opened) {
        Result r = closeDoor(access);
        if (!r.ok()) {
            access.setState("unknown");
            alert("门关闭失败：" + r.errorCode() + "，可能半开，需人工确认");
        }
    }
}
```

**恢复时的幂等处理**：

```
重启/恢复后，所有门状态视为 unknown
  → 第一次要操作某设备时，先调 CloseDoor（不管当前状态）
  → 成功 → state = 'closed'
  → 再调 OpenDoor → state = 'open'
```

**宁可多关一次，不要假设门是开的。**

### 2.3 L1 位置要关联到通道

**一个位置可能在哪个通道后面**：

```
离心机有 4 个层位，1 个门
  → 4 个位置都在这个门后面
  → 要拿第 2 层的板，必须先开门
```

**已经有 `device_port.position_id`**，但更准确的是**反向关联**：

```sql
ALTER TABLE position_state ADD COLUMN IF NOT EXISTS
    port_id bigint REFERENCES device_port(id);
-- 这个位置通过哪个通道可达
```

## 三、修正后的资源获取顺序

### 3.1 完整序列（含门）

```
【源设备侧】
① 源设备的门（开）           ← 新增
② 源通道（in/out/both）
③ 源位置

【目标设备侧】
④ 目标设备的门（开）         ← 新增
⑤ 目标通道
⑥ 目标位置

【收尾】
⑦ 回程位置（position-return）
⑧ 机械臂
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   全部就绪；板仍在源位，可安全放弃
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⑨ 抓板                      ← 不可逆点
⑩ 移动（走安全高度 safe_z）
⑪ 放下
⑫ 关两边的门（可选，按配置）
⑬ 释放：机械臂、两个通道
⑭ 回程位置保持
```

### 3.2 为什么门排在最前

| 顺序 | 理由 |
|---|---|
| **门先于通道** | 门是"总闸"，没开门进不去 |
| **门先于位置** | 同上 |
| **门在机械臂之前** | 门开了但机械臂没抢到 → 可以关门放弃，代价小 |
| **如果门在机械臂之后** | 抢了机械臂才发现门打不开 → **板已经在爪子上了**，没法放回去 |

**这就是"所有申请完成前板不离开源位"的延伸**：门也是"申请"，必须在抓板前完成。

### 3.3 门的开合也是"动作"

**开门要 3-30 秒**（电动门），这期间：

- 门资源被占（别人不能同时开同一个门）
- **机械臂不占**（等门的时候不用握着爪子）

**所以门和机械臂是两把独立的锁，可以交错**：

```
流程1：开门 A（3秒）→ 抢机械臂 → 抓板 → ...
流程2：开门 B（3秒，和流程1 并行）→ 等机械臂
```

## 四、点位属性（问题 4，动态规划的基础）

### 4.1 现有 `robot_point` 的不足

```sql
-- 现在只有这些
(id, tenant_id, island_id, robot_resource_id, code, name,
 x, y, z, device_resource_id, action, synced_at, ...)
```

**不够的地方**：

| 缺什么 | 后果 |
|---|---|
| 不知道这个点是"进"还是"出" | 抓取时选错点 |
| 不知道对应哪个层位 | 不知道板放在哪一层 |
| 不知道要不要先开门 | **会撞机** |
| 不知道安全高度 | 横移时撞架子 |
| 不知道接近方向 | 从错误方向伸进去会撞 |

### 4.2 补充字段

```sql
ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    point_type      varchar(16) DEFAULT 'generic',
    -- 'pick' 抓取点 | 'place' 放置点 | 'generic' 通用
    -- 'dock' 停靠点 | 'safe_z' 安全高度点

ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    port_id         bigint REFERENCES device_port(id),
    -- 这个点对应哪个通道

ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    position_id     bigint REFERENCES position_state(id);
    -- 这个点对应哪个层位（多板位设备必需）

ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    access_id       bigint REFERENCES device_access(id);
    -- 到访这个点之前必须先打开哪个门（NULL=无门）

ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    approach_axis   varchar(8) DEFAULT 'front',
    -- 接近方向：front|left|right|top|bottom
    -- 从错误方向伸进去会撞

ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    safe_z_offset   numeric(10,3) DEFAULT 50;
    -- 安全高度偏移：横移前先抬到 z + 这个值

ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    max_stack       smallint DEFAULT 1;
    -- 这个位置最多叠几块板

ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    height_mm       numeric(8,2);
    -- 这个点的板堆高度（叠放时用于算 Z）

ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    order_in_device smallint;
    -- 同一设备多个点的顺序（先取外层再取内层）
```

### 4.3 每个属性的作用

| 属性 | 动态规划怎么用 |
|---|---|
| `point_type` | 只在 `pick`/`place` 里选，跳过 `safe_z`/`dock` |
| `port_id` | 申请通道锁时知道用哪个口 |
| `position_id` | **选空位时只看这个点对应的层位** |
| `access_id` | **抓板前知道要开哪个门** |
| `approach_axis` | 生成机械臂路径时的进给方向 |
| `safe_z_offset` | 横移前抬到这个高度再动 |
| `max_stack` | 叠放时判断能不能再放 |
| `height_mm` | 叠放时算 Z 偏移 |
| `order_in_device` | 多板位时决定先取哪个（先外层） |

### 4.4 属性怎么来：模板自动带出 + 人工补填 + 核验（已与用户确认）

**用户说明的现状**：

```
机械臂做完 → 中控有"同步动作" → 点位同步到中控系统
```

**在此基础上加三步**：

| 步骤 | 做法 |
|---|---|
| **① 同步时自动带出模板** | 按 `device.model` 匹配设备类型模板，填默认属性 |
| **② 缺失的人工补填** | 模板没有的属性，提示人工填 |
| **③ 下次同步时核验** | 对比模板值，不一致就告警 |

**设备类型模板表**：

```sql
CREATE TABLE device_point_template (
    tenant_id     bigint NOT NULL,
    device_model  varchar(64) NOT NULL,      -- 按设备型号匹配
    point_type    varchar(16) DEFAULT 'generic',
    approach_axis varchar(8)  DEFAULT 'front',
    safe_z_offset numeric(10,3) DEFAULT 50,
    max_stack     smallint DEFAULT 1,
    height_mm     numeric(8,2),
    requires_door boolean DEFAULT false,
    port_direction varchar(8) DEFAULT 'both',
    notes         text,
    PRIMARY KEY (tenant_id, device_model)
);
```

**同步时的流程**：

```
机械臂同步点位（已有能力）
  ↓
对每个点位：
  ① 查 device.model → 查模板
  ② 有模板 → 填 approach_axis / safe_z_offset / max_stack / height_mm
  ③ 查 device_access → 有门就填 access_id
  ④ 查 device_port → 按方向填 port_id
  ⑤ 缺的字段（如 position_id 对应哪层）→ **标记"待补填"**
  ↓
前端显示"3 个点位待补填" → 人工补
  ↓
补完才能用于动态规划
```

**核验机制**：

```java
// 下次同步时
if (existing.safeZOffset() != template.safeZOffset()) {
    // 可能有人手工改过，或者模板更新了
    alert("点位 " + code + " 的 safe_z_offset 与模板不一致："
        + "现有 " + existing.safeZOffset() + " 模板 " + template.safeZOffset());
    // 不自动覆盖，让人确认
}
```

**为什么不自动覆盖**：**人工改过可能是有原因的**（比如那台设备位置偏了），
自动覆盖会把人的修正冲掉。

**补填状态的可见性**：

```sql
ALTER TABLE robot_point ADD COLUMN IF NOT EXISTS
    fill_status varchar(16) DEFAULT 'ok';
-- 'ok' 完整 | 'pending' 待补填 | 'verified' 已核验
```

**动态规划时**：`fill_status != 'ok'` 的点位**不使用**（跳过并在日志里说明）。

### 4.5 点位怎么选：**流程里用循环+变量硬编码**（主），自动选位是可选增强

**已与用户确认的设计取向**：

> **先采用在流程上硬编码的方式**——比如通过**循环 + 变量**得到一个动态的点位，
> 然后传给机械臂。这样机械臂就能拿到动态位置来处理。
>
> **这也是为什么需要有条件、计算等来修改变量**，从而达到更好的处理流程和点位的目的。

#### 为什么不是"调度器自动选空位"

| 自动选位 | 流程硬编码 |
|---|---|
| 需要设备**实时提供占用状态** | 不依赖设备配合 |
| 设备不一定支持 | **一定能用** |
| 调度器复杂 | 编排时就想清楚 |

**用户判断**："这个需要另外的设备也跟着来获得我们的信息，有的时候不一定那么好处理。"

**所以主路径是流程层指定，不是调度器猜。**

#### 实现：点位 code 支持变量

**流程配置**（循环节点 + 变量）：

```json
{
  "nodeType": "loop",
  "varName": "i",
  "from": 1,
  "to": 8,
  "body": [
    {
      "method": "Transfer",
      "params": {
        "source": "STACKER",
        "target": "ID1183-L${i}"      // ← 点位 code 用变量拼
      }
    }
  ]
}
```

**执行时展开成 8 步**：

```
Transfer(source=STACKER, target=ID1183-L1)
Transfer(source=STACKER, target=ID1183-L2)
...
Transfer(source=STACKER, target=ID1183-L8)
```

**每步的 `target` 是一个点位 code**，机械臂按 code 查 `robot_point` 拿坐标。

#### 这就要求三件事

| # | 要求 | 现状 |
|---|---|---|
| 1 | **变量替换能用在 `target`/`source` 上** | ✅ 已有（`substVars`） |
| 2 | **循环节点能展开成多步，每步变量不同** | ✅ 画布有循环列 |
| 3 | **点位 code 支持变量拼**（`ID1183-L${i}`） | ⚠ **要确认**：查 `robot_point` 前先替换变量 |

**第 3 点是 M1 要补的**：

```java
// 查点位前先替换变量
String targetCode = substVars(params.get("target"));   // ID1183-L3
RobotPoint p = robotPointByCode(targetCode);           // 查坐标
if (p == null) {
    throw new IllegalStateException("点位不存在：" + targetCode
        + "（可能是变量拼错了，或者点位没同步）");
}
```

#### 条件 + 计算 怎么配合

**用户提到"有条件、计算等来修改变量"**：

```json
// 条件：板上有样本才进孵箱
{
  "nodeType": "exclusiveGateway",
  "condition": "${plateCount} > 0",
  "then": [...],
  "else": [...]
}

// 计算：下一个空位的编号
{
  "nodeType": "compute",
  "set": { "nextSlot": "${usedSlots} + 1" }
}
```

**这些在流程层做**，不是调度器做。

**调度器只负责**：给我 `target=ID1183-L3`，我就去抢 L3、开 L3 的门、搬过去。

#### 自动选位作为"可选增强"（不是必须）

**如果设备确实提供了占用状态**，可以开启：

```json
{
  "target": "ID1183",              // 只写设备，不写层位
  "autoPickSlot": true             // 让系统选空位
}
```

**系统才去查 `position_state` 选空位**。

**默认关闭**——因为依赖设备配合，不一定可靠。

### 4.6 一个具体例子

**离心机有 4 个层位、1 个门**：

```sql
-- 门
INSERT INTO device_access (resource_id, code, access_type, open_method, close_method)
VALUES (<离心机>, 'DOOR', 'door', 'OpenDoor', 'CloseDoor');

-- 4 个层位
INSERT INTO position_state (resource_id, code, ...) VALUES
  (<离心机>, 'L1', ...), (<离心机>, 'L2', ...),
  (<离心机>, 'L3', ...), (<离心机>, 'L4', ...);

-- 4 个点位，都关联到同一个门
INSERT INTO robot_point
  (island_id, robot_resource_id, code, x, y, z,
   device_resource_id, point_type, access_id, position_id,
   approach_axis, safe_z_offset, order_in_device)
VALUES
  (..., 'CENT-L1', 320, 180, 45, <离心机>, 'pick', <门>, <L1>, 'front', 80, 1),
  (..., 'CENT-L2', 320, 180, 95, <离心机>, 'pick', <门>, <L2>, 'front', 80, 2),
  (..., 'CENT-L3', 320, 180, 145, <离心机>, 'pick', <门>, <L3>, 'front', 80, 3),
  (..., 'CENT-L4', 320, 180, 195, <离心机>, 'pick', <门>, <L4>, 'front', 80, 4);
```

**动态规划时**：

```
要放一块板到离心机
  → 查离心机的空位：L2 空着
  → 找到 L2 的点位 CENT-L2
  → 读到 access_id = 门 → 申请门（开）
  → 读到 port_id / 或直接用点位
  → 申请通道
  → 读到 safe_z_offset = 80 → 路径先抬到 z=175
  → 抢机械臂 → 移动 → 放下
```

**全部由数据驱动，不用改代码。**

### 5.1 M1 要改

## 七、还有三个问题要确认

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | **门的状态能不能查到？** 有些设备只能"开"，不能"查询状态" | 那就要靠"上次操作的时间"推断，风险高 |
| 2 | **同时能过几块板的通道**（`capacity > 1`）在物理上常见吗？ | 如果常见，锁的设计要支持"计数"而非"互斥" |
| 3 | **点位示教时怎么知道 `access_id`？** 手工填还是自动推断？ | 人工填 9 个属性太累，能不能从设备类型自动带出模板 |

## 八、一句话

**原来以为"出入口 = 每设备 1 个"，实际是"1~N 个，有方向"；**
**原来完全漏了"门"——它没开，机械臂伸进去会撞机；**
**点位不只是坐标，还要有"进哪个口、开哪个门、从哪个方向、抬多高"。**

**这三样不做，动态规划就是瞎猜。**
