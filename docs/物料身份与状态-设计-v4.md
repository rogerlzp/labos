## 0. 怎么用这份文档

### 0.1 一句话方案

**第一版只做一件事：设备执行完一个节点后，系统能「可恢复地」把这块板的板级工艺阶段/膜状态从 A 改成 B，并留下可重放的事件与可追责的动作审计；做不到时宁可按「待核对」停住，也不猜、不重跑设备。**

### 0.2 本版的三个硬决定

| # | 决定 | 理由 | 代价（明确接受） |
|---|---|---|---|
| **H1 范围裁剪** | 第一版：**一个节点、一圈执行最多一个物料 Effect**（`effect_index` 固定 0）；子过程逐轮参数绑定、扫码晚绑定、多 Effect/SPLIT/MERGE、分支级闸门全部**后置**（§9） | 先把「单板、单效果、可恢复」这条主链做到可验收；复杂能力在没有真实载体时先不做 | 多效果/扫码场景第一版不支持，预检必须明确拒绝并给出提示 |
| **H2 数据库约束策略** | 新表/新列**只建 UNIQUE 键与 CHECK**；**不建任何外键（FK）**；跨表引用一致性由**业务层**在写入事务内维护，并用巡检 SQL + 集成测试兜底（§5） | 用户明确要求：UNIQUE 管唯一性，FK 尽量不用；大量 FK 会让迁移、清库、并发和分库变重 | 引用完整性不是数据库强制的，必须靠代码纪律 + 巡检 + 测试；本稿把每条引用关系和检查点写死 |
| **H3 声明快照独立载体** | run 启动时的物料声明快照写入**独立追加表** `run_material_effect_declaration`（UNIQUE 定位，只 INSERT），**不再把 `run_node.input` 当权威快照** | 现有 `updateNodeStateLive/updateNodeResult/整单 flush` 会覆盖 `run_node.input`，不可变事实不能放在会被覆盖的列里（第 7 轮 openai P0-01） | 多一张小表；S1 迁移与 S2 写入点各加一处 |

### 0.3 阅读顺序（评审/实施都按这个顺序看）

1. §1 范围：先确认**第一版不做什么**；
2. §2 模型与不变量：确认我们建的是什么；
3. §3 执行/效果/恢复：最关键的事务与恢复语义；
4. §4 数据库设计 + §5 约束与引用完整性策略（**本版与 v3.3 最大差别**）；
5. §8 S0 冻结条件 + §9 后置清单 + §10 对第 7 轮 openai 评审的逐条处置。

### 0.4 第一版与 v3.3 的核心差异（先看这 6 条）

| 主题 | v3.3 | v4 第一版 |
|---|---|---|
| 数据库外键 | 14 条复合/引用约束（含跨租户 FK） | **全部不建 FK**；UNIQUE 键 + CHECK 保留；引用完整性进 §5 业务层策略 |

### 1.3 第一版的三个硬简化（与 v3.3 的差别，必须在评审中确认）

1. **单 Effect**：一个节点一圈只有 1 个 Effect ⇒ 节点级 `material_sync_status` 与 Effect 状态是**一一映射**，不需要多 Effect 聚合真值表（第 7 轮 openai P1-04 用范围裁剪解决，多效果后置 D3）。
2. **闸门命中即整 run 暂停**：不做「只扣相关分支」（第 7 轮 08-deepseek V7-06 指出与 GraphRunner 单队列不兼容；第一版明确接受整 run 暂停，见 D4）。
3. **不建 FK**：新表之间的引用（effect↔event↔action↔declaration、plate/run 引用）全部由业务层维护（§5）。

## 2. 领域模型（第一版）

### 2.1 四类事实分开，各有一个权威来源

| 事实 | 唯一权威来源 | 第一版是否修改 |
|---|---|---|
| 板是谁、孔里有什么 | `plate` / `plate_well` / `sample_aliquot` | 只给 `plate` 加板级工艺阶段/膜/版本列，不动孔级模型 |
| 板在哪里、被哪个 run 占用 | `position_state`（`plate_id` 存条码、`occupied_by_run`） | **不改**；`plate.location_id` 视为只读冗余（D11） |
| 设备/节点物理上是否完成 | 命令事实（`command_ledger`/`run_command`）+ `run_node` 执行确认四态 | 新增四态列与证据字段（§3.2） |
| 板级工艺状态如何变化 | **声明快照 → Effect → Event → 当前投影** | 新增（本稿主体） |

### 2.2 板级工艺阶段与膜

- `plate.process_state` 表达**整块板**在工艺中的阶段/处置状态；默认整板同质；**不表达**孔级内容（那是 `plate_well` 的职责）；
- 字典 `plate_process_state (tenant_id, code, display_name, sort_order, enabled)`，租户级；`code` 创建后不可改；停用用 `enabled=false`；
- `plate.seal_state`：`none`=确认无膜、`sealed`=确认封膜、**NULL=未知**；
- 空板统计按 `plate_well` 判定，**不新增空的板级状态**。

### 2.3 归属三个概念（不加列）

| 概念 | 落点 | 说明 |
|---|---|---|
| 当前占用 | `position_state.occupied_by_run` | 现有唯一真源；本稿不新增 `plate.current_run_id` |
| 生产来源 / 加工历史 | `plate_material_event`（`source_run_id`/`source_node_key`/`source_loop_index`） | 事件只追加；首条事件 = 最早可追溯来源（不伪造上线前历史） |
| 跨流程持有权移交 | 第一版不做 | 需要时另立显式 handoff 模型（D1 之后的阶段 3） |

### 2.4 核心不变量（第一版，I1-I10）

| # | 不变量 | 强制方式 |
|---|---|---|
| I1 | 位置变化不自动改工艺状态；工艺状态变化不自动改位置 | 应用层（两套服务分开）【S2 待实现】 |
| I2 | 自动迁移只能来自 run 启动时冻结的声明快照；运行期不按方法名/位置猜状态 | `run_material_effect_declaration` + 完成处理器【S2 待实现】 |
| I3 | 每个 Effect 最多一条自动 Event；`from=to` 的状态确认事件允许存在 | UNIQUE（`tenant_id, effect_id`）【设计】 |
| I4 | Event 与 `plate` 投影在同一事务写入；Event 的 before/after 等于本次实际值 | T2 单事务【S2 待实现】 |
| I5 | 同一板的所有投影通过行锁 + `state_version` 串行化，禁止最后写入者无声覆盖 | `SELECT ... FOR UPDATE` + CAS【S2 待实现】 |

| I9 | 执行结果分级：设备回包 ≠ 物理确认；超时/未知不得当确定失败或直接重跑 | `execution_resolution_status` + 证据等级【S2 待实现】 |

## 3. 执行、效果与恢复（第一版核心）

### 3.1 完成处理器：唯一注入点 + 明确的 S2 改造面

**唯一注入点**：共享的 `RunStateMachine` 实例（`WorkflowService` 构造一份 `sm`，图执行与顺序执行共用）。
在每个设备 TASK 节点的**执行结果边界**（成功、确认失败、超时/未知都算）调用 `materialEffectHandler`，由 boot 层 `MaterialEffectService` 实现。

handler 返回：

| 返回 | 含义 | 调用方动作 |
|---|---|---|
| `CONTINUE` | 无效果 或 效果已 APPLIED | 节点可完成，后继进入闸门检查 |
| `HOLD` | 效果 PENDING/FAILED/REJECTED/NEEDS_RECONCILIATION（物理完成、物料未闭环） | 节点保持物理完成终态；**run 进 `paused(material_sync)`**（第一版整 run 暂停，D4）；不伪造设备失败 |
| 抛持久化异常 | T1 连执行确认/效果意图都写不进去 | 立即中止 ⇒ run 隔离（§3.6）；**禁止续跑重放设备动作** |

**【S2 待实现】明确改造面（第一版设计必须承认这不是现成挂点）**：

1. `RunStateMachine.executeNode` 目前只有 `(RecoverableNode, RunProgress, StepExecutor)` 入参、6 个返回点、成功路径无证据对象 ⇒ 需要：
   - 扩展返回/上下文：携带 `runId / runNodeId / nodeKey / loopIndex(visit 或 0) / effectIndex(固定 0) / 命令证据引用`；
   - 在 6 个返回点统一映射为 `CONTINUE / HOLD / 抛异常` 三态（执行确认四态的判定见 §3.2）。
2. `GraphRunner` / `RunStateMachine.executeAll` 的**派发前**闸门 predicate 注入（仿现有 `withPauseChecker`；`GraphRunner` 不直接访问数据库）。
3. `executeAll` 目前无逐节点钩子 ⇒ 新增注入通道（顺序路径也要过闸门与完成处理器）。
4. 圈次行时序：现有 `roundRecorder` 在 `executeNode` 返回**之后**才 plain INSERT 圈次行 ⇒ T1 若"定位或创建"会撞 `uk_run_node`。**S2 改为：进入 `executeNode` 前先创建/挂起本圈 run_node 行**（或把 `insertNodeRound` 改 upsert），T1 只更新该行；具体方案在 S2 设计评审中定，但**时序必须先于 T1**。
5. 人工确认权限：新增 `material:reconcile / material:retry / material:cancel / material:write` 权限码（现有 RBAC 只有 admin/operator/viewer）。
6. `run.pause_kind` 词表新增 `material_sync`（S2 契约改动，需同步 UI/i18n 码表）。

> 以上 6 条属于 **S2 改造清单**；第一版设计承认它们是"要做的新东西"，不写成"已有能力"（第 7 轮 08-deepseek V7-05/V7-06/V7-20 教训）。

### 3.2 执行确认状态（run_node，四态）

`run_node.execution_resolution_status`：`unresolved / completed / failed_confirmed / reconciliation_required`，与既有 `node_status`、`material_sync_status` 分开。

| 状态 | 含义 | 写点 | 续跑语义 |
|---|---|---|---|
| `unresolved` | 尚未形成最终执行结论（含未开始/执行中/老数据） | 创建 run_node 外壳时默认 | 只有**没有任何派发证据**时才允许按未开始节点处理 |
| `completed` | 已确认目标物理动作完成 | 执行结果边界（成功且证据满足快照策略） | 只补执行/物料记录，**禁止重新执行设备动作** |
| `failed_confirmed` | 已确认目标物理动作未发生 | 明确失败且证据充分 | 才可进入现有安全重试策略 |
| `reconciliation_required` | 有派发/执行迹象，但最终物理结果未知 | 超时、连接中断、`command_ledger=UNKNOWN/DISPATCH_STARTED`、证据不足 | **禁止删除重建、普通 resume、自动重试**；先对账（§3.6） |

- `completed` 同时写 `physical_completed_at + physical_evidence_level + physical_evidence`（三者在同一事务）；**老数据 `status=completed` 只能以 `legacy` 兼容，不伪造精确时间**；
- `none / legacy_unspecified / transition` **三种声明模式共用**本守卫（无物料效果的节点也可能有物理不确定性）；
- 超时/未知**一律** `reconciliation_required`，不得按 `node_status` 直接当失败重跑。

### 3.3 T1：执行确认 + 声明快照 + 效果意图

**声明快照（H3）**：run 启动时，对每个 `mode=transition` 节点：把 `workflow_node.material_effect` 解析后的声明（含 `mode / target / set / acceptedEvidenceLevels`、声明哈希、workflow 版本）INSERT 到 `run_material_effect_declaration`；**只 INSERT，无 UPDATE/DELETE 业务路径**。

**T1（设备回包后、节点标 completed 前）**，尽量单事务：

1. 更新 `run_node.execution_resolution_status = completed` + 物理证据三件套；
2. 解析目标板（§3.4）：解析成功 ⇒ 写 `plate_material_effect(PENDING)`（含 `plate_id / declaration 快照副本 / target_snapshot / expected_state_version / payload_hash`）；确定性冲突 ⇒ `REJECTED`；证据不足/冲突 ⇒ `NEEDS_RECONCILIATION`；
3. 追加 `plate_material_effect_action(DECLARE)`；
4. 更新 `run_node.material_sync_status`（第一版单 Effect：与 effect 状态一一映射；§3.5）。

**T1 失败**（执行确认或效果意图写不进） ⇒ 抛异常 ⇒ run 隔离（§3.6）；恢复时先按命令账本对账，**禁止直接重跑设备**。

`mode=none / legacy_unspecified`：只写执行确认与物理证据，不创建 effect/action（`material_sync_status=not_required`）。

### 3.4 T2：物料投影（单事务）

对 `PENDING` 效果（当前线程立即尝试；失败后由 Worker 补偿）：

1. `SELECT effect ... FOR UPDATE`（状态仍 PENDING，否则按当前状态返回）；
2. 校验 `declaration_hash` 与目标（同键不同义 ⇒ `FAILED(DECLARATION_SOURCE_CONFLICT)`，不覆盖）；
3. `SELECT plate ... FOR UPDATE`；校验 `state_version = expected_state_version`（不符 ⇒ `FAILED(MAT_STATE_CONFLICT)`，不写事件）；
4. 写**恰好一条** `plate_material_event`（完整 before/after + `changed_fields` + `from/to_state_version`）；
5. 更新 `plate.process_state/seal_state/state_version`；
6. effect → `APPLIED` + `applied_at`；追加 `APPLY` action；更新节点 `material_sync_status`；
7. 提交。

业务校验失败：在同一事务只提交失败记录（effect `FAILED/REJECTED` + action + 节点状态），不写事件、不改板；提交后返回 HOLD。
数据库临时异常：整个 T2 回滚，effect 保持 PENDING；**失败计数与退避在独立短事务写**（§3.5，openai P1-02）。

### 3.5 节点级投影与 Worker（第一版简化）

**单 Effect 一一映射**（H1）：节点 `material_sync_status` ∈ {`not_required, pending, applied, failed, rejected, needs_reconciliation, cancelled`}，与 Effect 状态一一对应；**它是可重建投影**，权威仍是 Effect 行。写入者：T1/T2/Worker 在改 Effect 的同一事务内更新；闸门只读它（并允许用巡检 SQL 从 Effect 重建核对）。

**Worker**（第一版）：

- 只扫描 `status='PENDING' AND (next_retry_at IS NULL OR next_retry_at <= now())`；
- 单效果短事务，`SELECT ... FOR UPDATE SKIP LOCKED` 领取；不引入持久 PROCESSING 状态；
- **失败计数独立事务**：T2 回滚后，另起短事务写 `apply_attempt_count + 1 / last_error_code / last_attempt_at / next_retry_at`（独立事务失败 ⇒ 记日志 + 巡检/人工，最多重试 N 次后转 FAILED 人工）；
- 有界指数退避 + 最大次数；超限 ⇒ `FAILED` + 告警 + 转人工；
- 同键同负载重复回调可跳过；同键不同负载/声明 hash 变化必须报错。

### 3.6 隔离、恢复与人工闭环

**T1 失败 ⇒ 隔离 run**：`quarantined` + experiment 级 `runtime_hold`（复用 `StartupRecovery.quarantineUncertainRuns` 先例）。

**现有缺口与第一版必需的改造（【S2 待实现】）**：现有 resume 入口只接受 `paused` 或 `failed+recoverable`；隔离写 `quarantined+recoverable=false` ⇒ **当前没有 quarantined→可续跑通道**（第 7 轮 08-deepseek V7-04）。第一版要求新增业务流：
1. 运维/授权人员在隔离清单确认：命令账本已闭环、Effect 已处理完 ⇒ 调用「确认隔离」把 run 转为 `paused(manual_window)`；
2. 人工选择 CONTINUE（继续未完成节点）或 ABORT；
3. **在 1 完成前，resume 一律 409**；放行后也不允许重派已确认完成的物理动作。

**续跑删除守卫（比现有 `deleteIncompleteTopNodes` 更早）**：resume 前先跑守卫查询，存在下列任一情况 ⇒ 拒绝删除并转隔离：
- `execution_resolution_status IN (reconciliation_required)`，或 `completed` 但 Effect 未闭环；
- 有 `command_ledger` `DISPATCH_STARTED/UNKNOWN` 或 `run_command` 证据但 T1 未完成；
- Effect/Event 已引用该节点。
只有「无派发证据的未开始节点」与「已完成且记录完整」的节点可安全续跑；`failed_confirmed` 才走显式安全重试。

**效果状态机（六态）**：

| 当前 | 触发 | 下一个 | 谁 | 记什么 |
|---|---|---|---|---|
| `PENDING` | T2 成功 | `APPLIED` | AUTO | action APPLY + 恰好一条 Event |
| `PENDING` | 确定性声明/配置错误 | `REJECTED` | AUTO | action APPLY + error_code；无 Event |
| `PENDING` | 身份/物理证据冲突 | `NEEDS_RECONCILIATION` | AUTO | action APPLY + 证据；无 Event |
| `PENDING` | 可恢复失败超限 | `FAILED` | AUTO | action + error_code |
| `PENDING/FAILED/NEEDS_RECONCILIATION` | run 终止/授权取消 | `CANCELLED` | AUTO/MANUAL | action CANCEL |
| `FAILED` | 授权重试 | `PENDING` | 需 `material:retry` | action RETRY + 原因 |
| `NEEDS_RECONCILIATION` | 对账 completed | `PENDING`（随后走 T2） | 需 `material:reconcile` | action RECONCILE + evidenceSnapshot |
| `NEEDS_RECONCILIATION` | 对账 not_completed | `CANCELLED` | 同上 | action RECONCILE + 证据 |
| `APPLIED/REJECTED/CANCELLED` | 终态 | — | — | 不自动重试 |

**人工确认的授权边界（openai P1-05）**：节点声明**只能要求更高证据等级，不能授权人工确认**；`manual_confirmed` 必须由独立权限 + 操作者身份 + 原因 + 证据 + action 审计共同授权。

### 3.7 派发闸门（第一版：整 run 暂停）

- 闸门 predicate 注入 `GraphRunner` / `executeAll` 派发前：检查全部直接前置节点的 `material_sync_status` + `execution_resolution_status`；只有前置为 `not_required/applied` 且执行确认 `completed`（或 `not_required` 语义）才放行；
- 命中 ⇒ 该节点不启动，**run 进 `paused(material_sync)`**（第一版不做分支级，D4）；记 experiment 级 `runtime_hold` 告警；
- 对账/确认完成且人工确认后，通过 resume（CONTINUE）从停机点继续；**恢复只补投影，不重派设备**；
- 第一版**不新增 `node_status` 枚举值**，不伪造设备失败。

### 3.8 循环与幂等（第一版）

- 循环沿用现有图循环：`source_node_key` = 图节点 key（varchar(64)），`source_loop_index` = 执行上下文 `visit`（1..N；无环/顺序 = 0）；**不引入 call-path 键**（D1 后置）；
- 效果唯一键：`UNIQUE (tenant_id, source_run_id, source_node_key, source_loop_index, effect_index)`，`effect_index=0`；`attempt` 不入键；
- **循环恢复以命令账本为物理锚点**（openai P1-03）：恢复扫描联合 `command_ledger` / `run_command` / Effect / 声明快照，识别「未派发 / 已派发未回包 / 已回包未落效果」三种窗口；无法确定物理结果 ⇒ `reconciliation_required`，**不得根据当前循环计数推测原始轮次**；
- 命令层现状（【已有源码事实】）：`command_ledger.idempotency_key` 由 `DriverStepExecutor` 构造，含 run/nodeId/attempt/step/device/method/进程内 opSeq，**不含 loop_index** ⇒ 循环多轮的命令层幂等**不完整**；第一版要求 S2 修复（命令账本增加 loop 维度或明确 fail-closed 边界），并写入 §8.2 改造清单。

## 5. 约束与引用完整性策略（H2：UNIQUE 在库层，引用在业务层）

### 5.1 原则（本版最重要的工程决定）

1. **唯一性用数据库 UNIQUE 键保证**：幂等键、事件版本、Effect→Event 一对一、run 声明快照定位等，全部落 UNIQUE 索引；**不允许用应用层去重替代唯一键**。
2. **新约束一律不建 FOREIGN KEY**：跨表引用（→ run / plate / run_node / effect / 字典）只在**业务层**的写入事务内校验，并配巡检 SQL 与集成测试。
3. **既有表已有的 FK 不动**：本版不改既有 schema；新表不引用它们建立 FK。
4. **CHECK 保留**：枚举、状态组合、版本步进、changed_fields 一致性等**单行内可判定**的规则，全部用 CHECK；跨行/跨表规则才交给业务层。
5. **风险与缓解**：引用完整性不是数据库强制的 ⇒ 必须同时具备 ①写入事务内的校验函数（统一入口，不允许各处手写）②每日/每批次巡检 SQL（返回 0 行才算通过）③§7 的负向集成测试。三者缺一不可。

| # | 引用关系 | 数据库约束 | 业务层维护点 | 巡检/测试 |
|---|---|---|---|---|

### 5.3 巡检 SQL（S1 后纳入每日任务或发布前检查；全部必须返回 0 行）

```sql
-- Q1 effect → run 同租户
SELECT e.id FROM plate_material_effect e
 WHERE NOT EXISTS (SELECT 1 FROM run r WHERE r.tenant_id = e.tenant_id AND r.id = e.source_run_id);
-- Q2 effect.plate_id → plate 同租户
SELECT e.id FROM plate_material_effect e
 WHERE e.plate_id IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM plate p WHERE p.tenant_id = e.tenant_id AND p.id = e.plate_id);
-- Q3 effect → 本 run 的 run_node（node_key + 圈次）
SELECT e.id FROM plate_material_effect e
 WHERE NOT EXISTS (SELECT 1 FROM run_node n
                    WHERE n.tenant_id = e.tenant_id AND n.run_id = e.source_run_id
                      AND n.node_key = e.source_node_key AND n.loop_index = e.source_loop_index);
-- Q4 声明快照 → run
SELECT d.id FROM run_material_effect_declaration d
 WHERE NOT EXISTS (SELECT 1 FROM run r WHERE r.tenant_id = d.tenant_id AND r.id = d.run_id);
-- Q5 action → effect 同租户
SELECT a.id FROM plate_material_effect_action a
 WHERE NOT EXISTS (SELECT 1 FROM plate_material_effect e
                    WHERE e.tenant_id = a.tenant_id AND e.id = a.effect_id);
-- Q6 event → effect 的租户/run/plate 必须一致（openai P0-02 的业务层替代）
SELECT v.id FROM plate_material_event v
  JOIN plate_material_effect e ON e.tenant_id = v.tenant_id AND e.id = v.effect_id
 WHERE v.effect_id IS NOT NULL
   AND (v.plate_id <> e.plate_id OR v.source_run_id <> e.source_run_id);
-- Q7 event.plate_id → plate 同租户
SELECT v.id FROM plate_material_event v
 WHERE NOT EXISTS (SELECT 1 FROM plate p WHERE p.tenant_id = v.tenant_id AND p.id = v.plate_id);
-- Q8/Q9 字典引用
SELECT v.id FROM plate_material_event v
 WHERE (v.from_process_state IS NOT NULL AND NOT EXISTS
          (SELECT 1 FROM plate_process_state s WHERE s.tenant_id = v.tenant_id AND s.code = v.from_process_state))
    OR (v.to_process_state IS NOT NULL AND NOT EXISTS
          (SELECT 1 FROM plate_process_state s WHERE s.tenant_id = v.tenant_id AND s.code = v.to_process_state));
SELECT p.id FROM plate p
 WHERE p.process_state IS NOT NULL AND NOT EXISTS
   (SELECT 1 FROM plate_process_state s WHERE s.tenant_id = p.tenant_id AND s.code = p.process_state);
```

### 5.4 append-only 的实施要求（D5，S1 运维）

- 应用库角色对 `plate_material_event` / `plate_material_effect_action` / `run_material_effect_declaration` **只授 SELECT / INSERT**（REVOKE UPDATE, DELETE）；
- 迁移/运维使用独立高权限角色，操作纳入审计；
- 可选纵深防御：拒绝 UPDATE/DELETE 的触发器（第一版不强制，D5）；
- **代码层面也不提供 update/delete 这些表的入口**；如发现需要更正，只能追加新记录。

### 5.5 为什么不建 FK（决策记录）

| 理由 | 说明 |
|---|---|
| 用户明确的工程口径 | 「UNIQUE 管唯一性，尽量不用 FK，业务层维护」——本版按此执行 |
| 迁移/清库/在线 DDL 成本 | 本仓库已有 `pg_rebuild` 全量重建 + 90_all_in_one 同源机制，FK 会增加重建顺序与数据清理的耦合 |
| 并发/锁与分库演进 | FK 会在跨表写入时引入额外锁与顺序约束，后续拆库/分片时更难 |
| 本版引用都由单一服务写入 | 物料效果/事件/动作/声明四个入口都在 `MaterialEffectService` 内，业务层校验可以集中实现，不易绕过 |

**缓解（必须全部做到）**：§5.2 的写入校验统一入口 + §5.3 巡检 + §7 负向测试 + §5.4 权限。若未来需要 FK 化，按「先做数据预检（孤儿/跨租户/跨板应为 0）→ 补 (tenant_id,id) 唯一键 → 加 FK → 双跑验证」的迁移步骤单独评审。
