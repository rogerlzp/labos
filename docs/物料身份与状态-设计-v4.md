## 0. 怎么用这份文档

### 0.1 一句话方案

**第一版只做一件事：设备执行完一个节点后，系统能「可恢复地」把这块板的板级工艺阶段/膜状态从 A 改成 B，并留下可重放的事件与可追责的动作审计；做不到时宁可按「待核对」停住，也不猜、不重跑设备。**

### 0.2 本版的三个硬决定

| # | 决定 | 理由 | 代价（明确接受） |
|---|---|---|---|
| **H1 范围裁剪** | 第一版：**一个节点、一圈执行最多一个物料 Effect**（`effect_index` 固定 0）；子过程逐轮参数绑定、扫码晚绑定、多 Effect/SPLIT/MERGE、分支级闸门全部**后置**（§9） | 先把「单板、单效果、可恢复」这条主链做到可验收；复杂能力在没有真实载体时先不做 | 多效果/扫码场景第一版不支持，预检必须明确拒绝并给出提示 |
| **H2 数据库约束策略** | 新表/新列**只建 UNIQUE 键与 CHECK**；**不建任何外键（FK）**；跨表引用一致性由**业务层**在写入事务内维护，并用巡检 SQL + 集成测试兜底（§5） | 用户明确要求：UNIQUE 管唯一性，FK 尽量不用；大量 FK 会让迁移、清库、并发和分库变重 | 引用完整性不是数据库强制的，必须靠代码纪律 + 巡检 + 测试；本稿把每条引用关系和检查点写死 |
| **H3 声明快照独立载体** | run 启动时的物料声明快照写入**独立追加表** `run_material_effect_declaration`（UNIQUE 定位，只 INSERT），**不再把 `run_node.input` 当权威快照** | 【已有源码事实】`updateNodeResult`（`RunMapper.xml:575-582`）把结果 jsonb **合并写回** `run_node.input`（`input = COALESCE(input,'{}') || #{param8}`，同 key 会被覆盖），`insertNodeRound`（`:584-590`）同样写 `input`；且续跑会删除未完成的 run_node 行 ⇒ 放在 `input` 里的快照既可能被覆盖也会随行消失。（注：`updateNodeStateLive`（`:555-563`）**不**写 `input`）（第 7 轮 openai P0-01） | 多一张小表；S1 迁移与 S2 写入点各加一处 |

### 1.3 第一版的三个硬简化（与 v3.3 的差别，必须在评审中确认）

1. **单 Effect**：一个节点一圈只有 1 个 Effect ⇒ 节点级 `material_sync_status` 与 Effect 状态是**一一映射**，不需要多 Effect 聚合真值表（第 7 轮 openai P1-04 用范围裁剪解决，多效果后置 D3）。
2. **闸门命中即整 run 暂停**：不做「只扣相关分支」（第 7 轮 08-deepseek V7-06 指出与 GraphRunner 单队列不兼容；第一版明确接受整 run 暂停，见 D4）。
3. **不建 FK**：新表之间的引用（effect↔event↔action↔declaration、plate/run 引用）全部由业务层维护（§5）。

## 2. 领域模型（第一版）

### 2.1 四类事实分开，各有一个权威来源

| 事实 | 唯一权威来源 | 第一版是否修改 |
|---|---|---|
| 板是谁、孔里有什么 | `plate` / `plate_well` / `sample_aliquot` | 只给 `plate` 加板级工艺阶段/膜/版本列，不动孔级模型 |
| 板在哪里、被哪个 run 占用 | `position_state`（`plate_id` 存条码、`occupied_by_run`） | **不改**；`plate.location_id` 视为只读冗余（D11） |
| 设备/节点物理上是否完成 | 命令事实（`command_ledger`/`run_command`）+ `run_node` 执行确认四态 | 新增四态列与证据字段（§3.2） |
| 板级工艺状态如何变化 | **声明快照 → Effect → Event → 当前投影** | 新增（本稿主体） |

### 2.2 板级工艺阶段与膜

- `plate.process_state` 表达**整块板**在工艺中的阶段/处置状态；默认整板同质；**不表达**孔级内容（那是 `plate_well` 的职责）；
- 字典 `plate_process_state (tenant_id, code, display_name, sort_order, enabled)`，租户级；`code` 创建后不可改；停用用 `enabled=false`；
- `plate.seal_state`：`none`=确认无膜、`sealed`=确认封膜、**NULL=未知**；
- 空板统计按 `plate_well` 判定，**不新增空的板级状态**。

### 2.3 归属三个概念（不加列）

| 概念 | 落点 | 说明 |
|---|---|---|
| 当前占用 | `position_state.occupied_by_run` | 现有唯一真源；本稿不新增 `plate.current_run_id` |
| 生产来源 / 加工历史 | `plate_material_event`（`source_run_id`/`source_node_key`/`source_loop_index`） | 事件只追加；首条事件 = 最早可追溯来源（不伪造上线前历史） |
| 跨流程持有权移交 | 第一版不做 | 需要时另立显式 handoff 模型（D1 之后的阶段 3） |

## 3. 执行、效果与恢复（第一版核心）

### 3.1 完成处理器：唯一注入点 + 明确的 S2 改造面

**注入点**：设备 TASK 节点的**执行结果边界**（成功、确认失败、超时/未知都算）调用 `materialEffectHandler`，由 boot 层 `MaterialEffectService` 实现。

> **【第 10 轮修正 · S10-04】原「唯一注入点 = 共享的 RunStateMachine 实例（`WorkflowService` 构造一份 `sm`）」与源码不符**：main 里 `new RunStateMachine` 有 **9 个构造点**（`WorkflowService` 构造一份、但图执行/顺序执行/演示/恢复等各自构造）。因此第一版的口径改为：
> 1. **注入点 = `RunStateMachine` 的执行结果边界**（语义唯一），**不是「一个实例」**；
> 2. **S2 必须把 9 个构造点全部接入**（统一构造工厂或共享注册表），**漏接的路径必须 fail-closed**（未接入完成处理器的执行路径不得产出「物理已完成」的结论，见 §3.2 守卫）；
> 3. §8.2 第 1 项已把「9 个构造点逐一接入 + 未接入即 fail-closed」列为 S2 必做，并要求 S2 交付一份构造点清单（新增/删除构造点必须同步该清单）。

handler 返回：

| 返回 | 含义 | 调用方动作 |
|---|---|---|
| `CONTINUE` | 无效果 或 效果已 APPLIED | 节点可完成，后继进入闸门检查 |
| `HOLD` | 效果 PENDING/FAILED/REJECTED/NEEDS_RECONCILIATION（物理完成、物料未闭环） | 节点保持物理完成终态；**run 进 `paused(material_sync)`**（第一版整 run 暂停，D4）；不伪造设备失败 |
| 抛持久化异常 | T1 连执行确认/效果意图都写不进去 | 立即中止 ⇒ run 隔离（§3.6）；**禁止续跑重放设备动作** |

**【S2 待实现】明确改造面（第一版设计必须承认这不是现成挂点）**：

1. `RunStateMachine.executeNode` 目前只有 `(RecoverableNode, RunProgress, StepExecutor)` 入参、**6 个正常返回点**、成功路径无证据对象 ⇒ 需要：
   - 扩展返回/上下文：携带 `runId / runNodeId / nodeKey / loopIndex(visit 或 0) / effectIndex(固定 0) / 命令证据引用`；

### 3.2 执行确认状态（run_node，四态）

`run_node.execution_resolution_status`：`unresolved / completed / failed_confirmed / reconciliation_required`，与既有 `node_status`、`material_sync_status` 分开。

| 状态 | 含义 | 写点 | 续跑语义 |
|---|---|---|---|
| `unresolved` | 尚未形成最终执行结论（含未开始/执行中/老数据） | 创建 run_node 外壳时默认 | 只有**没有任何派发证据**时才允许按未开始节点处理 |
| `completed` | 已确认目标物理动作完成 | 执行结果边界（成功且证据满足快照策略） | 只补执行/物料记录，**禁止重新执行设备动作** |
| `failed_confirmed` | 已确认目标物理动作未发生 | 明确失败且证据充分 | 才可进入现有安全重试策略 |
| `reconciliation_required` | 有派发/执行迹象，但最终物理结果未知 | 超时、连接中断、`command_ledger=UNKNOWN/DISPATCH_STARTED`、证据不足 | **禁止删除重建、普通 resume、自动重试**；先对账（§3.6） |

- `completed` 同时写 `physical_completed_at + physical_evidence_level + physical_evidence`（三者在同一事务）；
- **旧数据兼容（v4.1 明确）**：`run_node.status='completed' AND execution_resolution_status='unresolved'` 记为 **legacy_completed**；**S1 迁移显式回填**：`execution_resolution_status='completed'`、`physical_evidence_level='legacy'`、`physical_completed_at=COALESCE(actual_end, updated_at)`、`physical_evidence` 写 `{"source":"legacy status=completed","not_physical_time":true}`（明确是系统记录时间，不是物理发生时间，不伪造精确时刻）；迁移后新数据不得再产生该组合（巡检 Q18）。
- `none / legacy_unspecified / transition` **三种声明模式共用**本守卫（无物料效果的节点也可能有物理不确定性）；
- 超时/未知**一律** `reconciliation_required`，不得按 `node_status` 直接当失败重跑。

### 3.2.1 错误码/驱动状态 → 执行确认四态（第一版，S2 实现；§3.1 第 7 条）

| 信号 | 映射 |
|---|---|
| DriverResult.SUCCESS 且证据等级满足声明快照的 acceptedEvidenceLevels | `completed` |
| 明确业务拒绝/参数错误，设备确认「未执行」，且没有任何派发迹象 | `failed_confirmed` |
| 已下发且收到回包但无法确定最终物理结果；超时/连接中断；command_ledger=UNKNOWN/DISPATCH_STARTED；证据等级不足 | `reconciliation_required` |
| 未开始 / 正在执行 | `unresolved` |

规则：material-transition 节点**禁止**对「可能已发生」的错误码做 command 级自动重试（现有 EC-05-1006 超时策略默认 retry，需按此分类短路）；重试成功也不得把未知当 completed，除非有满足快照的证据。该表由 S2 在 executeNode 重试循环内实现（§3.1 第 7 条）。

### 3.3b 声明契约（第一版；S2 实现预检与校验）

> **【第 10 轮修正 · V9-04 / B4】** 原稿把 `material_effect` 当作**已有契约**使用，但全文只有一句字段列举，**无 schema、无 mode/target/set 形态、无预检错误码** ⇒ S2 无从实现、H1「单 Effect」无法被预检强制。v4.2 补齐契约本身。

**契约载体**：`workflow_node.material_effect`（jsonb）。**第一版只有三种 mode**，且**每节点每圈最多 1 个 Effect**（H1，`effect_index` 恒为 0）。

```json

  "target": {
    "plateId": 123,
    "barcode": "PLT-001",

  "set": {
    "processState": "sealed",

**字段规则与预检错误码（逐条可测）**：

| # | 规则 | 预检错误码 | 分级 |
|---|---|---|---|
| 1 | `mode ∈ {none, transition, legacy_unspecified}` | `ME_INVALID_MODE` | ERROR |
| 2 | `mode=transition` 时 `target` 必填，且 `plateId` / `barcode` **至少一项** | `ME_TARGET_MISSING` | ERROR |
| 3 | `set` 至少含 `processState` 或 `sealState` 一项 | `ME_SET_EMPTY` | ERROR |
| 4 | `set.processState` 必须是该租户**启用**的字典 `plate_process_state.code` | `ME_DICT_UNKNOWN` | ERROR |
| 5 | `set.sealState ∈ {none, sealed}` | `ME_SEAL_INVALID` | ERROR |
| 6 | **单 Effect**：`mode=transition` 只允许**一组** `set`（不得声明多组 outputs/operations） | `ME_MULTI_EFFECT` | ERROR |
| 7 | `acceptedEvidenceLevels ⊆ {device_ack, physical_confirmed, manual_confirmed, legacy}` | `ME_EVIDENCE_LEVEL_INVALID` | ERROR |

### 3.4 T2：物料投影（单事务）

对 `PENDING` 效果（当前线程立即尝试；失败后由 Worker 补偿）：

1. `SELECT effect ... FOR UPDATE`（状态仍 PENDING，否则按当前状态返回）；
2. 校验 `declaration_hash` 与目标（同键不同义 ⇒ `FAILED(DECLARATION_SOURCE_CONFLICT)`，不覆盖）；
3. `SELECT plate ... FOR UPDATE`；校验 `state_version = expected_state_version`（不符 ⇒ `FAILED(MAT_STATE_CONFLICT)`，不写事件）；
   - `MAT_STATE_CONFLICT` **不自动重试**：只能由授权人员 rebase（更新 expected_state_version + **action `REBASE`**）或转 `NEEDS_RECONCILIATION` 按 §3.6 对账；Worker 对该 error_code 不自动重试（避免同一版本冲突死循环）；
     - **【第 10 轮修正 · S10-01】** 原稿要求写 `action REBASE`，但 §4 的 `ck_action_type` 白名单里没有 `'REBASE'` ⇒ 设计与 DDL 自相矛盾、S2 实现必撞 CHECK。**v4.2 已把 `'REBASE'` 加入 `ck_action_type` 白名单**（§4 第 ⑦ 段），并已在临时 PG 复跑验证（§11.4）；
4. 写**恰好一条** `plate_material_event`（完整 before/after + `changed_fields` + `from/to_state_version`）；
5. 更新 `plate.process_state/seal_state/state_version`；
6. effect → `APPLIED` + `applied_at`；追加 `APPLY` action；更新节点 `material_sync_status`；
7. 提交。

业务校验失败：在同一事务只提交失败记录（effect `FAILED/REJECTED` + action + 节点状态），不写事件、不改板；提交后返回 HOLD。
数据库临时异常：整个 T2 回滚，effect 保持 PENDING；**失败计数与退避在独立短事务写**（§3.5，openai P1-02）。
⇒ **对账转 PENDING 的前置**：`NEEDS_RECONCILIATION → PENDING` 时必须在同一事务提交 `confirmedTarget(plate_id)` 与按当前 plate 读到的 `expected_state_version/expected_*`；否则保持 `NEEDS_RECONCILIATION`（否则违反 `ck_effect_applicable_target`）。

### 3.5 节点级投影与 Worker（第一版简化）

**单 Effect/圈 + 跨圈聚合**（v4.1 修正，H1 的准确表述）：一个节点每一圈最多 1 个 Effect；循环 N 圈产生 N 个 Effect。节点 `material_sync_status` 是**跨圈聚合投影**，不是与单个 Effect 一一对应；权威仍是 Effect 行，投影可完全重建：

| 聚合输入（本节点所有已执行圈的 Effect） | 节点 material_sync_status |
|---|---|
| 任一 Effect = NEEDS_RECONCILIATION | `needs_reconciliation` |
| 否则任一 = REJECTED | `rejected` |
| 否则任一 = FAILED | `failed` |
| 否则任一 = PENDING，或声明了但该圈没有 Effect（缺失，等待补） | `pending` |
| 否则任一 = CANCELLED | `cancelled` |
| 否则全部 APPLIED | `applied` |
| 无声明（none/legacy） | `not_required` |

聚合规则固定为「按上表优先级取最阻塞者」；每次 Effect 状态变化后在**同一事务**重算并写节点投影；巡检 Q15b 可从 Effect 集合重建核对（不一致即告警）。**预期圈数**在循环结束后由实际执行圈次（visit 1..N）确定；闸门只统计已执行圈次 + 声明缺失。写入者：T1/T2/Worker 在改 Effect 的同一事务内更新。

**Worker**（第一版）：

- 只扫描 `status='PENDING' AND (next_retry_at IS NULL OR next_retry_at <= now())`；
- 单效果短事务，`SELECT ... FOR UPDATE SKIP LOCKED` 领取；不引入持久 PROCESSING 状态；
- **失败计数独立事务**：T2 回滚后，另起短事务写 `apply_attempt_count + 1 / last_error_code / last_attempt_at / next_retry_at`（独立事务失败 ⇒ 记日志 + 巡检/人工，最多重试 N 次后转 FAILED 人工）；
- 有界指数退避 + 最大次数；超限 ⇒ `FAILED` + 告警 + 转人工；
- 同键同负载重复回调可跳过；同键不同负载/声明 hash 变化必须报错。

### 3.6 隔离、恢复与人工闭环

**T1 失败 ⇒ 隔离 run**：`quarantined` + experiment 级 `runtime_hold`（复用 `StartupRecovery.quarantineUncertainRuns` 先例）。

**现有缺口与第一版必需的改造（【S2 待实现】）**：现有 resume 入口只接受 `paused` 或 `failed+recoverable`；隔离写 `quarantined+recoverable=false` ⇒ **当前没有 quarantined→可续跑通道**（第 7 轮 08-deepseek V7-04）。第一版要求新增业务流：
1. 运维/授权人员在隔离清单确认：命令账本已闭环、Effect 已处理完 ⇒ 调用「确认隔离」把 run 转为 `paused(manual_window)`；
2. 人工选择 CONTINUE（继续未完成节点）或 ABORT；
3. **在 1 完成前，resume 一律 409**；放行后也不允许重派已确认完成的物理动作。
4. **接口（S2 新增）**：`POST /api/runs/{id}/material-safety/confirm`（隔离确认；权限 `material:reconcile` + 原因必填），返回未闭环清单；确认后才允许 resume。

**续跑删除守卫（比现有 `deleteIncompleteTopNodes` 更早）**：resume 前先跑守卫查询，存在下列任一情况 ⇒ 拒绝删除并转隔离：
- `execution_resolution_status IN (reconciliation_required)`，或 `completed` 但 Effect 未闭环；
- **【第 10 轮修正 · S10-10】该节点存在**任意 `command_ledger` 行（**不限 state**）或任意 `run_command` 行 ⇒ 一律不允许删除、必须先对账**。
  - 理由（源码事实）：回包后**先**写 `command_ledger=ACKED`（`DriverStepExecutor.java:723`），**后**写 `run_command`（`WorkflowService.java:2251-2257`）⇒ 崩在两者之间会留下「ACKED + 无 run_command」，该组合**不匹配**原先只查 `DISPATCH_STARTED/UNKNOWN` 的条件，却会被 `deleteIncompleteTopNodes`（`WorkflowService.java:718-719`）删掉证据 ⇒ 设备可能被重复驱动；
- Effect/Event 已引用该节点。
只有「无派发证据的未开始节点」与「已完成且记录完整」的节点可安全续跑；`failed_confirmed` 才走显式安全重试。

**效果状态机（六态）**：

| 当前 | 触发 | 下一个 | 谁 | 记什么 |
|---|---|---|---|---|
| `PENDING` | T2 成功 | `APPLIED` | AUTO | action APPLY + 恰好一条 Event |
| `PENDING` | 确定性声明/配置错误 | `REJECTED` | AUTO | action APPLY + error_code；无 Event |
| `PENDING` | 身份/物理证据冲突 | `NEEDS_RECONCILIATION` | AUTO | action APPLY + 证据；无 Event |
| `PENDING` | 可恢复失败超限 | `FAILED` | AUTO | action + error_code |
| `PENDING/FAILED/NEEDS_RECONCILIATION` | run 终止/授权取消 | `CANCELLED` | AUTO/MANUAL | action CANCEL |
| `FAILED` | 授权重试（`last_error_code ≠ MAT_STATE_CONFLICT`，**`expected_state_version` 不变**） | `PENDING` | 需 `material:retry` | action RETRY + 原因 |
| `FAILED` | **授权 rebase**（`last_error_code = MAT_STATE_CONFLICT`；把 `expected_state_version` **更新为板当前 `state_version`**） | `PENDING` | MANUAL，需 `material:reconcile` | action **REBASE** + reason（**不重跑设备**；改完期望值后由 T2 重走） |
| `NEEDS_RECONCILIATION` | 对账 completed | `PENDING`（随后走 T2） | 需 `material:reconcile` | action RECONCILE + evidenceSnapshot |
| `NEEDS_RECONCILIATION` | 对账 not_completed | `CANCELLED` | 同上 | action RECONCILE + 证据 |
| `APPLIED/REJECTED/CANCELLED` | 终态 | — | — | 不自动重试 |

> **【第 10 轮修正 · REBASE 口径】**（第 10 轮 DDL 复跑发现）：`§4` 已把 `'REBASE'` 加入 `ck_action_type`，但本表原本**没有 REBASE 行** ⇒ REBASE 动作的 `from_status`/`to_status`/`actor_type` 无真源，实测**三种互不兼容的编码 DDL 全部接受**（`FAILED→PENDING` / `FAILED→FAILED` / `FAILED→FAILED` + 另记 RETRY）。现明确口径：
> 1. **REBASE 行的 `from_status` 恒为 `FAILED`，`to_status` 恒为 `PENDING`，`actor_type` 恒为 `MANUAL`**；
> 2. **REBASE 与 RETRY 互斥**：按 `last_error_code` 判定 —— `MAT_STATE_CONFLICT` ⇒ 只能 REBASE；其余 ⇒ 走 RETRY。REBASE 行**自身**承载「期望值已更新」这一事实，**不再额外写一条 RETRY 行**；
> 3. 验收断言（§7.1 A9）：**REBASE 行的 `to_status='PENDING'` 且 `actor_type='MANUAL'` 且 `operator_user_id`/`reason` 非空**；同一 effect 的 REBASE 行与 RETRY 行不得同时出现。

**人工确认的授权边界（openai P1-05）**：节点声明**只能要求更高证据等级，不能授权人工确认**；`manual_confirmed` 必须由独立权限 + 操作者身份 + 原因 + 证据 + action 审计共同授权。

### 3.6a 人工改状态（第一版：与自动迁移同一条写入路径）

> **【第 10 轮修正 · V9-11 / B6】** 原稿只在 §6 暴露了 `PUT /api/plates/{barcode}/state`，**没有写事务顺序、版本校验、字典处理与仲裁规则**；而 §5.5「引用都由单一服务写入」的论证依赖于此 ⇒ 若人工路径绕过校验，§5 的无-FK 策略在人工路径上失效（Q13/Q12b 只能事后发现）。v4.2 明确如下。

**唯一写入路径**：人工改状态**必须复用 T2 的写入函数**（`MaterialEffectService`），**不允许**另开直写 `plate` 的代码路径。

**事务顺序（单事务，与 T2 同构）**：

1. `SELECT plate ... FOR UPDATE`（锁板）；
2. 校验 `expectedVersion` 与板当前 `state_version` 不一致 ⇒ **409**，不写任何东西；
3. 校验目标值域：`processState` 必须是该租户**启用**的字典 code（停用值不允许新写，历史值仍可读）；`sealState ∈ {none, sealed}`；
4. 写**恰好一条** `plate_material_event`：`operator_type='MANUAL'`、`evidence='MANUAL_CORRECTION'`（盘点场景用 `MANUAL_INVENTORY`）、`operator_user_id` 与 `note` 必填（DDL `ck_pme_manual_actor` 已强制）、`changed_fields` 与 before/after 严格一致、`to_state_version = from_state_version + 1`；
5. 更新 `plate.process_state / seal_state / state_version`（版本 +1）；
6. 若该板存在 `PENDING` 效果且其 `expected_state_version` 已过期 ⇒ **该效果转 `NEEDS_RECONCILIATION`**（**不静默改写它的期望值**），并追加 `RECONCILE` action；
7. 提交。

**权限与审计**：需 `material:write`；人工写事件遵守 §3.6 的授权边界（操作者身份 + 原因 + 证据 + 审计 action）。

**与自动迁移的仲裁**：同一块板被人工写与 T2 自动迁移并发时，**以 `FOR UPDATE` 锁顺序定序**，后到的一方按 `expected_state_version` 不符处理 —— T2 ⇒ `FAILED(MAT_STATE_CONFLICT)`（不自动重试，走 §3.4 的 rebase/对账）；人工 ⇒ **409**。

### 3.7 派发闸门（第一版：整 run 暂停）

- **前置域（v4.1 修正，P0）**：闸门只对**物料依赖**判定，不是「全部直接前置节点」：
  - 参与判定的前置 = 直接前置中的**设备 TASK 节点**（声明了 transition 效果的）；结构节点（START/END/网关/BUILTIN）**跳过**——它们没有执行确认语义（§3.1 handler 只覆盖 TASK）；BUILTIN 声明效果 = 预检 ERROR；
    - **【第 10 轮修正 · S10-09】节点种类的真源**：图解析 `Kind` 枚举 = `TASK / START / END / SPLIT_PARALLEL / JOIN_PARALLEL / SPLIT_XOR / JOIN_XOR / SPLIT_CONDITIONAL / JOIN_CONDITIONAL / BUILTIN`（`WorkflowGraphParser.java:42-57`）；**只有 `Kind.TASK` 走 `stateMachine.executeNode`**（`GraphRunner.java:633`），BUILTIN 走 `executeBuiltin`（`:571-632`，注释明写「不碰设备，直接算」）。但 DB 侧 `workflow_node.node_type` 词表是 `task / subprocess / wait / condition / parallel / join / script`（`20_kernel.sql:214`），**与 `Kind` 不对应** ⇒ 预检按映射规则判定：DB `node_type ∈ {task, script}` 视为 TASK 候选；`subprocess/wait/condition/parallel/join` 视为结构节点；**BUILTIN 由 `Kind` 解析阶段判定，不依赖 `node_type`**（预检须读图解析结果，不能只看 DB 列）；
  - 每个 material 前置必须满足 (a) 全部已执行圈次的 Effect 均为 APPLIED（或 not_required），且 (b) 执行确认 `completed`；若为 `reconciliation_required`，或 `unresolved` 且已有派发证据 ⇒ 阻断；`failed_confirmed` 走现有失败路径（run 不继续），不进闸门；
  - 无物料声明的前置（none/legacy）也必须**执行确认不是 reconciliation_required**（物理未知同样阻断下游）；`unresolved` 且无派发证据 = 未开始，按正常派发逻辑处理，不停机；
  - **旧数据**：S1 迁移把旧 `status=completed` 回填成 `completed`+legacy 证据（§3.2）；迁移完成前，`status=completed AND execution_resolution_status='unresolved'` 按 legacy_completed 放行（不阻断旧 run），迁移后由巡检 Q18 保证该组合只存在于迁移前数据；
- 闸门 predicate 注入 `GraphRunner` / `executeAll` 派发前；命中 ⇒ 该节点不启动，**run 进 `paused(material_sync)`**（第一版不做分支级，D4）；记 experiment 级 `runtime_hold` 告警；
- **收尾（S2 必改）**：`settleRun` 与 `markBypassedNodes` 必须识别被闸门挂起/待对账的状态——不得把被挂起的 run 标 completed，不得把被扣住的 pending 后继标 bypassed（§8.2 第 9 项）；这是验收 C3 的前提；
- 对账/确认完成且人工确认后，通过 resume（CONTINUE）从停机点继续；**恢复只补投影，不重派设备**；
- 第一版**不新增 `node_status` 枚举值**，不伪造设备失败。

### 3.8 循环与幂等（第一版）

- 循环沿用现有图循环：`source_node_key` = 图节点 key（varchar(64)），`source_loop_index` = 执行上下文 `visit`（1..N；无环/顺序 = 0）；**不引入 call-path 键**（D1 后置）；
- 效果唯一键：`UNIQUE (tenant_id, source_run_id, source_node_key, source_loop_index, effect_index)`，`effect_index=0`；`attempt` 不入键；
- **循环恢复以命令账本为物理锚点**（openai P1-03）：恢复扫描联合 `command_ledger` / `run_command` / Effect / 声明快照，识别「未派发 / 已派发未回包 / 已回包未落效果」三种窗口；无法确定物理结果 ⇒ `reconciliation_required`，**不得根据当前循环计数推测原始轮次**；
- 命令层现状（【已有源码事实】）：`command_ledger.idempotency_key` 由 `DriverStepExecutor` 构造，含 run/nodeId/attempt/step/device/method/进程内 opSeq，**不含 loop_index** ⇒ 循环多轮的命令层幂等**不完整**；第一版要求 S2 修复（命令账本增加 loop 维度或明确 fail-closed 边界），并写入 §8.2 改造清单。

CREATE INDEX ix_pme_run ON plate_material_event (tenant_id, source_run_id);
```

**与 v3.3 DDL 的差异（评审重点）**：

1. 全部 FOREIGN KEY 删除（含 v3.3 §7⑧ 的 14 条复合约束）——引用完整性见 §5；
2. 声明快照独立成表（H3）；
3. effect_index=0 与相关 CHECK 把「单 Effect」变成库层可拒绝的约束（越界声明直接失败）；
4. 事件 changed_fields / 版本区间 / 唯一键保留（可重放）；
5. 节点/效果状态投影 CHECK 保留，material_sync_status 与效果的一一映射由业务层写（第一版单 Effect）。

> 标注：上述 DDL 为【设计】；**已于 2026-11-12 在临时 PostgreSQL 17.11 真跑通过（21 条语句、0 ERROR；见 §11.4）**；CHECK 与旧数据兼容（旧行升级测试通过）。S1 正式迁移脚本仍需复跑（§8.3）。


## 5. 约束与引用完整性策略（H2：UNIQUE 在库层，引用在业务层）

### 5.1 原则（本版最重要的工程决定）

1. **唯一性用数据库 UNIQUE 键保证**：幂等键、事件版本、Effect→Event 一对一、run 声明快照定位等，全部落 UNIQUE 索引；**不允许用应用层去重替代唯一键**。
2. **新约束一律不建 FOREIGN KEY**：跨表引用（→ run / plate / run_node / effect / 字典）只在**业务层**的写入事务内校验，并配巡检 SQL 与集成测试。
3. **既有表已有的 FK 不动**：本版不改既有 schema；新表不引用它们建立 FK。
4. **CHECK 保留**：枚举、状态组合、版本步进、changed_fields 一致性等**单行内可判定**的规则，全部用 CHECK；跨行/跨表规则才交给业务层。
5. **风险与缓解**：引用完整性不是数据库强制的 ⇒ 必须同时具备 ①写入事务内的校验函数（统一入口，不允许各处手写）②每日/每批次巡检 SQL（返回 0 行才算通过）③§7 的负向集成测试。三者缺一不可。

### 5.3 巡检 SQL（S1 后纳入每日任务或发布前检查；全部必须返回 0 行）

```sql
-- Q1 effect → run 同租户
SELECT e.id FROM plate_material_effect e
 WHERE NOT EXISTS (SELECT 1 FROM run r WHERE r.tenant_id = e.tenant_id AND r.id = e.source_run_id);
-- Q2 effect.plate_id → plate 同租户
SELECT e.id FROM plate_material_effect e
 WHERE e.plate_id IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM plate p WHERE p.tenant_id = e.tenant_id AND p.id = e.plate_id);
-- Q3 effect → 本 run 的 run_node（node_key + 圈次）
SELECT e.id FROM plate_material_effect e
 WHERE NOT EXISTS (SELECT 1 FROM run_node n
                    WHERE n.tenant_id = e.tenant_id AND n.run_id = e.source_run_id
                      AND n.node_key = e.source_node_key AND n.loop_index = e.source_loop_index);
-- Q4 声明快照 → run
SELECT d.id FROM run_material_effect_declaration d
 WHERE NOT EXISTS (SELECT 1 FROM run r WHERE r.tenant_id = d.tenant_id AND r.id = d.run_id);
-- Q5 action → effect 同租户
SELECT a.id FROM plate_material_effect_action a
 WHERE NOT EXISTS (SELECT 1 FROM plate_material_effect e
                    WHERE e.tenant_id = a.tenant_id AND e.id = a.effect_id);
-- Q6 事件 → Effect：必须同租户 + 同 run + 同 plate（v4.1 修正）
-- 原 Q6 用 INNER JOIN + tenant 条件，实测漏判三类：孤儿 effect_id（JOIN 丢行）、
-- effect.plate_id 为 NULL（NULL 比较被过滤）、跨租户（join 条件掩盖）。改 NOT EXISTS 全捕获：
SELECT v.id FROM plate_material_event v
 WHERE v.effect_id IS NOT NULL
   AND NOT EXISTS (
     SELECT 1 FROM plate_material_effect e
      WHERE e.tenant_id = v.tenant_id
        AND e.id = v.effect_id
        AND e.plate_id IS NOT DISTINCT FROM v.plate_id
        AND e.source_run_id IS NOT DISTINCT FROM v.source_run_id);
-- Q7 event.plate_id → plate 同租户
SELECT v.id FROM plate_material_event v
 WHERE NOT EXISTS (SELECT 1 FROM plate p WHERE p.tenant_id = v.tenant_id AND p.id = v.plate_id);
-- Q8/Q9 字典引用
SELECT v.id FROM plate_material_event v
 WHERE (v.from_process_state IS NOT NULL AND NOT EXISTS
          (SELECT 1 FROM plate_process_state s WHERE s.tenant_id = v.tenant_id AND s.code = v.from_process_state))
    OR (v.to_process_state IS NOT NULL AND NOT EXISTS
          (SELECT 1 FROM plate_process_state s WHERE s.tenant_id = v.tenant_id AND s.code = v.to_process_state));
SELECT p.id FROM plate p
 WHERE p.process_state IS NOT NULL AND NOT EXISTS
   (SELECT 1 FROM plate_process_state s WHERE s.tenant_id = p.tenant_id AND s.code = p.process_state);
-- Q8b 膜状态值域（DB CHECK 已拦，巡检兜底）
SELECT p.id FROM plate p
 WHERE p.seal_state IS NOT NULL AND p.seal_state NOT IN ('none','sealed');
-- Q10 事件 source_run → run（同租户）
SELECT v.id FROM plate_material_event v
 WHERE v.source_run_id IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM run r WHERE r.tenant_id=v.tenant_id AND r.id=v.source_run_id);
-- Q11 事件 source_node → run_node（同 run + 圈次）
SELECT v.id FROM plate_material_event v
 WHERE v.source_run_id IS NOT NULL AND v.source_node_key IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM run_node n
                    WHERE n.tenant_id=v.tenant_id AND n.run_id=v.source_run_id
                      AND n.node_key=v.source_node_key AND n.loop_index=v.source_loop_index);
-- Q12 事件版本链：不连续
SELECT v.plate_id, v.to_state_version FROM plate_material_event v
 WHERE v.to_state_version > 1
   AND NOT EXISTS (SELECT 1 FROM plate_material_event p
                    WHERE p.tenant_id=v.tenant_id AND p.plate_id=v.plate_id
                      AND p.to_state_version = v.to_state_version - 1);
-- Q12b plate.state_version 必须等于该板最大事件版本（无事件=0）
SELECT p.id, p.state_version FROM plate p
 WHERE p.state_version <> COALESCE(
   (SELECT max(v.to_state_version) FROM plate_material_event v
     WHERE v.tenant_id=p.tenant_id AND v.plate_id=p.id), 0);
-- Q13 投影一致性：plate 当前值必须等于最后一条事件的 to 值
SELECT p.id FROM plate p
  LEFT JOIN LATERAL (
    SELECT v.to_process_state, v.to_seal_state
      FROM plate_material_event v
     WHERE v.tenant_id=p.tenant_id AND v.plate_id=p.id
     ORDER BY v.to_state_version DESC LIMIT 1
  ) last ON true
 WHERE p.state_version > 0
   AND (p.process_state IS DISTINCT FROM last.to_process_state
        OR p.seal_state IS DISTINCT FROM last.to_seal_state);
-- Q14 事件 seal 值域（DB CHECK 已拦，巡检兜底）
SELECT v.id FROM plate_material_event v
 WHERE (v.from_seal_state IS NOT NULL AND v.from_seal_state NOT IN ('none','sealed'))
    OR (v.to_seal_state IS NOT NULL AND v.to_seal_state NOT IN ('none','sealed'));
-- Q15 声明/哈希完整性
SELECT e.id FROM plate_material_effect e
 WHERE NOT (e.declaration ? 'mode') OR length(e.declaration_hash) <> 64 OR length(e.payload_hash) <> 64;
SELECT d.id FROM run_material_effect_declaration d
 WHERE NOT (d.declaration ? 'mode') OR length(d.declaration_hash) <> 64;
-- Q15b 节点聚合投影可从 Effect 集合重建核对（不一致即告警）
SELECT n.run_id, n.node_key, n.loop_index, n.material_sync_status
  FROM run_node n
 WHERE n.material_sync_status <> COALESCE((
        SELECT CASE
                 WHEN bool_or(e.status='NEEDS_RECONCILIATION') THEN 'needs_reconciliation'
                 WHEN bool_or(e.status='REJECTED') THEN 'rejected'
                 WHEN bool_or(e.status='FAILED') THEN 'failed'
                 WHEN bool_or(e.status='PENDING') THEN 'pending'
                 WHEN bool_or(e.status='CANCELLED') THEN 'cancelled'
                 ELSE 'applied' END
          FROM plate_material_effect e
         WHERE e.tenant_id=n.tenant_id AND e.source_run_id=n.run_id
           AND e.source_node_key=n.node_key AND e.source_loop_index=n.loop_index), 'not_required')
   AND EXISTS (SELECT 1 FROM plate_material_effect x
                WHERE x.tenant_id=n.tenant_id AND x.source_run_id=n.run_id
                  AND x.source_node_key=n.node_key AND x.source_loop_index=n.loop_index);
-- Q16 tenant 存在性
SELECT 'event' AS t, v.tenant_id FROM plate_material_event v
 WHERE NOT EXISTS (SELECT 1 FROM tenant t WHERE t.id=v.tenant_id)
UNION ALL
SELECT 'effect', e.tenant_id FROM plate_material_effect e
 WHERE NOT EXISTS (SELECT 1 FROM tenant t WHERE t.id=e.tenant_id)
UNION ALL
SELECT 'declaration', d.tenant_id FROM run_material_effect_declaration d
 WHERE NOT EXISTS (SELECT 1 FROM tenant t WHERE t.id=d.tenant_id);
-- Q17 effect 与声明快照一致（同 run/node/effect_index 的 declaration_hash 必须一致）
SELECT e.id FROM plate_material_effect e
 WHERE NOT EXISTS (SELECT 1 FROM run_material_effect_declaration d
                    WHERE d.tenant_id=e.tenant_id AND d.run_id=e.source_run_id
                      AND d.node_key=e.source_node_key AND d.effect_index=e.effect_index
                      AND d.declaration_hash=e.declaration_hash);
-- Q18 迁移后不应再出现的 legacy 组合（S1 迁移前会命中旧行，迁移后必须 0）
SELECT n.run_id, n.node_key, n.loop_index FROM run_node n
 WHERE n.status='completed' AND n.execution_resolution_status='unresolved';
```

### 5.4 append-only 的实施要求（D5，S1 运维）

- 应用库角色对 `plate_material_event` / `plate_material_effect_action` / `run_material_effect_declaration` **只授 SELECT / INSERT**（REVOKE UPDATE, DELETE）；
- 迁移/运维使用独立高权限角色，操作纳入审计；
- 可选纵深防御：拒绝 UPDATE/DELETE 的触发器（第一版不强制，D5）；
- **代码层面也不提供 update/delete 这些表的入口**；如发现需要更正，只能追加新记录。

### 5.5 为什么不建 FK（决策记录）

| 理由 | 说明 |
|---|---|
| 用户明确的工程口径 | 「UNIQUE 管唯一性，尽量不用 FK，业务层维护」——本版按此执行 |
| 迁移/清库/在线 DDL 成本 | 本仓库已有 `pg_rebuild` 全量重建 + 90_all_in_one 同源机制，FK 会增加重建顺序与数据清理的耦合 |
| 并发/锁与分库演进 | FK 会在跨表写入时引入额外锁与顺序约束，后续拆库/分片时更难 |
| 本版引用都由单一服务写入 | 物料效果/事件/动作/声明四个入口都在 `MaterialEffectService` 内，业务层校验可以集中实现，不易绕过。**【第 10 轮修正 · V9-11】本条成立的前提是「人工改状态也走同一条路径」** —— §3.6a 已强制：人工写必须复用 T2 的写入函数，不允许另开直写 `plate` 的入口；否则本条论证失效（人工路径将绕过 §5.2 全部校验，只能靠 Q13/Q12b 事后发现） |

**缓解（必须全部做到）**：§5.2 的写入校验统一入口 + §5.3 巡检 + §7 负向测试 + §5.4 权限。若未来需要 FK 化，按「先做数据预检（孤儿/跨租户/跨板应为 0）→ 补 (tenant_id,id) 唯一键 → 加 FK → 双跑验证」的迁移步骤单独评审。

3. **legacy 回填脚本（V9-02 / V9-10 · B5）**：幂等、可重复执行，把 `run_node.status='completed' AND execution_resolution_status='unresolved'` 的旧行回填为 `completed` + `physical_evidence_level='legacy'` + `physical_completed_at=COALESCE(actual_end, updated_at)` + `physical_evidence={"source":"legacy status=completed","not_physical_time":true}`（§3.2）。

   ```sql
   -- legacy 回填脚本（S1 迁移；幂等；对应 §3.2 的 legacy_completed 语义）
   -- 前置：§4 的 ALTER 已执行（run_node 有 execution_resolution_status / physical_* 四列）
   UPDATE run_node n
      SET execution_resolution_status = 'completed',
          physical_evidence_level    = 'legacy',
          physical_completed_at      = COALESCE(n.actual_end, n.updated_at),
          physical_evidence          = '{"source":"legacy status=completed","not_physical_time":true}'::jsonb
    WHERE n.status = 'completed'
      AND n.execution_resolution_status = 'unresolved';
   ```
   - **范围**：只回填 `status='completed'` 的旧行；`status` 非 `completed` 的行**不动**（未开始/失败的行保持 `unresolved`，由闸门按「无派发证据 = 未开始」处理）；
   - **幂等**：条件含 `execution_resolution_status='unresolved'`，重复执行不改变已回填行；
   - **不伪造物理时刻**：`physical_completed_at` 取 `actual_end`，缺失时退到 `updated_at`（系统记录时间），并在 `physical_evidence` 里以 `not_physical_time=true` 标明；
   - **验收**：执行后 **巡检 Q18 必须 0 行**（第 10 轮临时 PG 已实测：回填后 0 行、重复执行仍 0 行）。
   - **为什么必须有**：`execution_resolution_status` 的 DDL 默认值是 `'unresolved'`，而 §7.4 D6 要求「Q18 迁移后为 0 行」⇒ **只加列不回填，Q18 当场就会命中**（旧 completed 行 + 新跑完但未写执行确认的行）；
   - **回填范围只限旧行**：`status='completed'` 且 `execution_resolution_status='unresolved'`；`status` 不是 `completed` 的行**不动**（未开始/失败的行保持 `unresolved`，由闸门按「无派发证据 = 未开始」处理）；
   - **幂等**：重复执行不改变已回填行（条件里带 `execution_resolution_status='unresolved'`）；
   - **验收**：临时库执行回填后 **Q18 必须 0 行**（已随第 10 轮复跑验证，见 §11.4）。

> 4. **【方法学提醒】** catalog 签名的**字节级比对**对 `ALTER TYPE` 往返敏感（PostgreSQL 会重写并重新渲染受影响的 CHECK 定义，语义等价但文本不同）⇒ 跨轮次比对签名应记 **token 级归一化签名**，或禁止在采集签名前做 `ALTER TYPE` 往返，否则会产生假阳性 drift。

| 规则 | §3 执行/效果/恢复规则（§3.3a 目标解析、§3.3b 声明契约、§3.4 rebase、§3.5 跨圈聚合、§3.6 守卫、§3.6a 人工路径、§3.7 闸门前置域） | S2 的代码组织与实现细节 |
| 数据库 | §4 DDL 结构基线（**sha256 绑定，见 §11.4**）+ §5 约束策略（R1-R18 / Q1-Q18） | 正式迁移脚本编写（S1）、append-only 角色权限（D5） |
| 接口 | §6 最小接口集 + §3.6a 人工路径的写入规则 | 前端页面与英文镜像（D10） |
| 验收 | §7 的 A1-A10 / B1-B11 / C1-C3 / D1-D10 | — |
| 实施范围 | §8.2 的 **22 项** S2 改造（= S2 的工作清单） | 第 22 项之外的新改造 |
| 安全 | §8.4 S0-safety 处置（**6 条**物理通路，flow-run 下线为必做） | 网络层隔离（作纵深） |

**冻结的三个含义**：

1. **不改** —— 上述对象的内容不得在实施中「顺手调整」；实施中发现问题走 CR，不在代码里夹带设计变更。
2. **可验** —— 冻结对象的每一条都有可执行的验证方式（§7 的 A/B/C/D 条目 = S1/S2 的验收清单）。
3. **可解冻** —— §13.3 的触发条件出现时，本稿**自动回到候选态**，必须复审后才继续实施。

### 13.2 变更请求（CR）流程

| 步 | 动作 | 产物 |
|---|---|---|
| 1 | 提出 CR（编号 CR-001 起，全局不复用） | CR 条目：触发原因 / 影响的不变量与条款 / 需要的验证证据 / 复审方 |
| 2 | 影响评估 | 标出受影响的 §2 不变量、§3 规则、§4 DDL（**sha256 变更**）、§7 验收项、§8.2 改造项 |
| 3 | 独立复审 | 评审记录（按 `docs/评审规范.md` §八 编号）+ 逐条处置更新 |
| 4 | 处置 | 接受 / 部分 / 不接受 + 落点 + 验证证据（§四 规则） |
| 5 | 回填 | 本稿改版号 + §12 修订记录 + 评审记录处置更新；**三处必须一致** |

**不需要 CR 的改动**（但须在评审记录登记）：错别字、失效链接、补充引用、章节顺序调整。

### 13.3 解冻 / 复审触发条件（出现任一项即回到候选态）

1. S2 实施证明 §3 某条规则在现有引擎上**不可实现**（与第 10 轮 A 组的可实现性结论冲突）；
2. S1 前生产数据预检（§8.3）与设计假设不符（旧 run 分布、plate 脏数据、跨租户孤儿、字典非法值、`node_status` 枚举漂移）；
3. 任一 §9 后置项的**触发条件达成**（如 D2 扫码晚绑定被业务强需求激活、D5 append-only 缺口被审计点名）；
4. 安全事件：任一未纳管的物理直跑通路被触发，或 S0-safety 的处置被绕过（含 §8.4 新增的 sidecar/gateway 两条）；
5. S1 真跑出现设计未预期的失败（DDL sha256 与 §11.4 不一致 / 巡检在真实数据上大面积命中）；
6. §11.2 的任一 UNKNOWN 被证伪或被证实（尤其是设备证据等级 U1、目标解析可用性 U6、逐 attempt 载体选型 U10、MANUAL 事件口径 U11）；
7. §8.2 的 22 项在实施中被证明**不可行或需扩范围**。

### 13.4 冻结后仍然「必须做」的三件事（不因冻结而免除）

| # | 事 | 归属 | 未做的后果 |
|---|---|---|---|
| 1 | **6 条物理通路的 S0-safety 处置**（flow-run 下线 + shadow 三条默认拒绝 + **sidecar TCP 收口** + **gateway Redis 写权收口**） | S0-safety | **不得进入 S1** |
| 2 | **旧数据 legacy 回填脚本**（§3.2 映射 + Q18 归零） | S1 迁移 | 旧 run 闸门语义与 D6 验收不成立（且 Q18 巡检会持续命中） |
| 3 | **§8.2 的 22 项 S2 改造 + §7.2 故障注入** | S2 | 第一版能力不成立（这是「数据库不拦」之外唯一能守住引用完整性的地方） |

> 理由：冻结的是**规格**，不是**事实**。上述三件事分别对应「还有没纳管的物理通路」「旧数据没有统一语义」「引擎还没改」，都属于**实施事实**，必须由实施阶段用证据关闭（§12.2）。
