## 0. 总体结论

**设计方向有条件通过；不批准据此直接开放并行度 2，也不批准把设计结论表述为现有能力。**

本版相较上一轮已有明显收敛：复用 `ExperimentScheduler` 而非新建调度器；承认事件归属不能简单依赖设备锁；区分命令身份、设备事件序号和恢复过程；明确设备协议准入条件；声明设计尚未实施。

但仍有四项 P0 设计缺口：

1. **E3 自发事件只按当前设备占用者归属不安全。** 事件可能在 Run A 释放设备、Run B 获得设备后才到达，按当前 holder 会把迟到事件错分给 B。
2. **去掉 commandId 中递增的 exec 后，没有持久化的逻辑命令轮次。** Resume 同一动作重试与同一节点重新执行可能得到相同 ID，或因重新计算而得到不同 ID。
3. **“执行无超时”会造成永久等待。** 应避免固定短超时误判长耗时动作，但必须增加执行进展监测、业务期限和卡死处置。
4. **只改批次活跃约束不足以统一执行准入。** 核查清单列出的同步、异步、重跑、Resume 等入口并非全部经过 ExperimentScheduler；必须证明所有入口受统一约束。

此外，跨类资源锁全序、设备事件序号的重启语义、人工 override 的授权与状态语义、两实验共用设备和点位的组合验收，均须在并行度 2 前解决。

## 2. §10 十个问题逐项裁决

### Q1. §4.2 将互斥粒度从 workflow 降到 batch attempt 是否足够？

**结论：需补充证据。**

- **位置：** 设计基线 §4.2；源码核查清单 §1、§3。
- **依据：** 核查清单列出 E-01 至 E-10 共十条执行入口，其中同步单流程、异步单流程、同步跑实验、批次重跑和 Resume 等路径并非全部经过 ExperimentScheduler。批次活跃唯一约束只能防止同一 batch 的多个 active attempt，不能自动约束绕过调度器的执行入口。
- **风险：** 同一实验或批次可能通过不同入口产生双 active；队列准入、数据库约束和 Resume 之间可能发生竞态。
- **建议：**
  1. 先定义统一的 execution admission service / 调度准入边界。
  2. 所有同步、异步、重跑、Resume、自动续队入口都必须经过该边界；禁止旁路直接启动执行。
  3. 数据库唯一约束作为并发兜底，而不是唯一控制层。
  4. 明确 active 状态集合。当前示例只列 queued/running/paused，需论证 pending/planned 等状态是否也占用 active slot。
  5. 若采用 PostgreSQL 部分唯一索引，须验证状态更新、失败回滚和历史数据兼容；不要在未核实迁移约束前直接照抄生成列方案。
- **验收：**
  - 同一 batch 两个并发提交最多产生一个 active attempt。
  - pending/planned/queued 状态下重复重跑不能创建第二个 active attempt。
  - 同步入口与异步入口同时提交，最多一个进入执行。
  - Resume 与新建 attempt 并发时最多一个取得执行权。
  - 通过静态调用链检查证明所有入口都经过统一准入；旁路测试必须失败关闭。

### Q2. §4.3 设备占用者归属 E3，设备锁释放后迟到事件是否会错归属？

**结论：反对当前方案。P0。**

- **位置：** 设计基线 §4.3。
- **依据：** 当前 holder 表示“此刻谁持有设备”，不表示“事件产生时谁持有设备”。异步上报、网络延迟、断线补发和重连均可能导致事件晚于锁释放到达。
- **风险：** Run A 产生的事件在 A 释放设备、B 获得设备后才抵达；若按当前 holder 查询，会被错误归属给 B，导致错误推进、错误物料状态或错误设备状态。
- **建议：**
  1. 引入设备占用代次/租约身份，例如 `lease_id`、`lease_generation`、`holder_run_id`、`acquired_at`、`released_at`。
  2. 若设备协议允许，E3 事件应携带产生时的 lease generation 或等价上下文。
  3. 如果设备不能携带，不能用当前 holder 反推历史归属；无法证明归属的事件必须进入 `UNATTRIBUTED` / `UNKNOWN`，不得自动推进 Run。
  4. 设备释放与事件窗口应有明确协议：释放前 drain、设备事件序号水位线、或其他可验证的边界；不能只依赖应用层锁。
- **验收：**
  - Run A 持有设备时产生 E3，事件延迟到 A 释放、B 获得设备后才到达；事件不得归属 B。
  - 覆盖设备断线补发、侧车重启、设备重启、快速 A→B→C 占用者切换。
  - 无法确定归属时，事件被隔离并告警，不触发节点成功或物料状态变化。

### Q3. §4.4 去掉 exec 后，Resume 如何区分新一轮与同一轮重试？

**结论：需补充设计。P0。**

- **位置：** 设计基线 §4.4。
- **依据：** 当前建议的 key 为 run/node/step/device/loopIndex。相同节点可能因网络故障 Resume 同一逻辑动作，也可能由人工重新执行而产生新的逻辑动作；二者不能只靠当前执行序号是否变化来区分。
- **风险：** 同一物理动作重试生成新 commandId，设备可能重复执行；新逻辑动作复用旧 commandId，设备可能去重掉合法的新动作。
- **建议：** 在命令首次创建时持久化逻辑动作身份，至少区分：
  - `logical_operation_id`：一次逻辑物理动作的稳定身份；
  - `command_id`：设备幂等身份，与逻辑动作绑定；
  - `attempt_no`：传输/查询尝试次数，审计递增，不改变 commandId；
  - 如业务允许同一节点显式重执行，再增加 `operation_generation` 或由新的 logical_operation_id 表达新动作。
  Resume 必须读取已持久化身份，禁止每次恢复重新拼接 ID。
- **验收：**
  - 发送前崩溃后 Resume：同一逻辑动作、同一 commandId。
  - 设备已完成但中控未落库时崩溃：对账后采纳结果，不重新执行。
  - UNKNOWN 后人工确认：保留原命令身份和处置历史。
  - 人工明确重新执行：创建新的 logical_operation_id 和 commandId。
  - 循环体第二轮：与第一轮身份不同；同一轮 Resume 身份不变。

### Q4. 设备不支持 queryStatus 时，是否只能人工确认？

**结论：支持该产品边界，但需分级。**

- **位置：** 设计基线 §4.5、§5。
- **依据：** 物理动作在断线后可能已发生，也可能未发生；没有可靠状态查询或可证明的回执时，中控不能推断动作结果。
- **风险：** 把“没有收到结果”当成“没有执行”并自动重发，可能重复移液、搬运、开盖、离心等物理动作。
- **建议：** 将设备按协议能力分级：
  - L0：commandId 回显、真实 ACK、queryStatus、事件序号/补发均具备；
  - L1：具备部分能力，恢复路径受限；
  - L2：无可靠状态查询/回执，断线后只能人工现场核验；不进入无人值守自动恢复清单。
  对无法核实的物理状态，保持 UNKNOWN 并隔离相关设备/物料/位置，不得“忽略”后自动释放资源。
- **验收：** 对不同等级设备分别断网、重启侧车、重启设备；证明 L1/L2 不会自动重发不确定的物理动作。

### Q5. R-01 跨类锁无全序，是否必须先统一全序才能开并行度 2？

**结论：必须先解决，或以可复核证据证明不存在跨类嵌套持锁。P0。**

- **位置：** 设计基线 §3.4、§8 R-01；核查清单 §4。
- **依据：** 设备锁、点位锁、轨道分区锁各自内部排序，不代表设备→点位、点位→设备等跨类组合有统一顺序。
- **风险：** A 持设备等点位，B 持点位等设备，形成循环等待；部分锁残留会进一步阻塞其他 Run。
- **建议：**
  1. 建立统一资源键和全局排序，例如 `(resource_type_rank, resource_id)`。
  2. 所有跨类组合资源申请必须按统一顺序，或改为原子申请/失败即完整回滚。
  3. 明确等待时是否持有部分资源；优先避免持有部分资源无限等待。
  4. 逐项核查异常、超时、取消、线程中断和进程重启时的释放路径。
- **验收：** 双 Run 反向申请设备/点位/轨道资源，持续压力测试无死锁；任何申请失败都不残留部分锁；租约与持有者校验一致。

### Q6. R-02 多实例 fencing 的最小改造集是什么？

**结论：当前“epoch 一列 + 三处条件更新”描述不充分。**

- **位置：** 设计基线 §8 R-02。
- **依据：** fencing 必须阻止失去执行权的旧实例继续写状态、占资源、推进节点或发送物理命令。只保护部分数据库 UPDATE 不足以阻止旧执行体的外部副作用。
- **风险：** 旧实例网络隔离后新实例接管；旧实例恢复后仍可发出命令，造成双执行。
- **建议：** 未来多实例前至少完成：
  1. 单调递增 execution epoch / fencing token；
  2. 原子获取与续租、owner 校验；
  3. Run、Batch、资源锁、节点推进、事件消费、命令账本写入口均校验 epoch；
  4. 命令网关校验当前执行权；设备协议可行时也传递并校验 fencing token；
  5. 旧实例恢复后所有写操作和命令发送必须被拒绝；
  6. 明确租约过期、时钟偏差、接管窗口和设备侧旧命令处理。
  当前单实例范围可不实施完整多实例 fencing，但必须定义单实例执行体 owner/失效规则，并测试僵死/重启/滚动部署的重叠窗口。
- **验收：** 旧实例暂停、租约过期、新实例接管、旧实例恢复；旧实例不得更新状态、持有资源、推进节点或发送有效命令。

### Q7. 心跳 1 秒 / ACK 1–3 秒 / 执行无超时是否成立？

**结论：反对当前三层表述；应改为四类监测。P0。**

- **位置：** 设计基线 §4.5、§5。
- **依据：** 长耗时孵育/离心不能被统一 30 秒判失败；但 ACK 成功且心跳正常，也不能证明设备内部执行线程仍在推进。
- **风险：** “执行无超时”可能使卡死设备永久占用资源；同时“连续三次心跳丢失”与“1 秒内停止派发”存在时间定义不一致。
- **建议：** 拆成四类：
  1. 链路健康：心跳周期、丢失判定、停止派发时限分开定义；
  2. 命令受理：ACK 计时和重试规则按设备协议配置；
  3. 执行进展：方法级进展信号、状态变化或阶段性检查；
  4. 业务完成期限：预期时长、告警阈值、最大业务期限和人工处置策略。
  超过业务期限不等于物理动作失败，不得自动重发；但必须告警、阻止不安全的后续派发，并进入明确处置状态。设备心跳正常不等于执行进展正常。
- **验收：**
  - ACK 正常、心跳正常、执行线程卡死；
  - 心跳丢失但设备可能仍在执行；
  - 长耗时动作正常推进但超过普通方法时长；
  - 执行进展长期不变；
  - 业务期限超限但设备仍报告执行中。
  各场景均不得错误标成功/失败或自动重发；告警和资源隔离行为符合定义。

### Q8. 人工“忽略并继续”的审计要求是否足够？

**结论：需补充安全约束。**

- **位置：** 设计基线 §4.5、§9 H-08。
- **依据：** 判定人、时间、依据和不可静默是必要条件，但不足以证明操作授权、对象边界、状态变化和证据可信度。
- **风险：** 普通操作员越权处置高风险物理动作；节点被误标成功；物料/位置锁被错误释放；审计无法还原当时状态。
- **建议：** override 记录至少包含：
  - tenant、experiment、batch、run、node、command、device、material、position 等目标对象；
  - 原状态快照、处置结果、理由、证据引用、判定人、授权人、时间；
  - 操作规则版本、审批记录、是否双人复核；
  - 明确哪些状态被改变、哪些仍为 UNKNOWN；
  - 不可覆盖的追加式审计记录。
  建议使用 `MANUALLY_DISPOSITIONED` 或等价状态，不能映射为自动 `COMPLETED`。人工处置不得默认释放物料和位置占用。
- **验收：** 权限矩阵测试、双人审批测试、证据缺失测试、审计不可变测试、后续 Run 能区分自动完成与人工处置；override 不得无条件释放物理资源。

### Q9. §7 是否遗漏两实验共用设备 + 共用点位？

**结论：确认遗漏，必须补测试。**

- **位置：** 设计基线 §7。
- **依据：** 现有 P-13、P-14、P-18、P-32 分别覆盖设备竞争、机械臂竞争、交叉锁和设备/位置生命周期，但没有覆盖两个实验同时竞争同一设备与同一点位的组合资源申请。
- **风险：** 设备锁和点位锁各自正确，组合申请仍可能部分成功、死锁、物料位置被覆盖或迟到事件串 Run。
- **建议：** 在现有 P/C 矩阵后新增 P-36 至 P-41（见 §3）。
- **验收：** 每个测试都记录 run/batch/material/device/position、资源获取释放顺序、事件序号、命令 ID、状态时间线和可复现脚本。

  5. 删除或改写任何“设计后即可”“直接复用”“已正确”等没有实现证据支撑的结论。
  6. `device_event.run_id` 先标记 deprecated 并完成全仓写入/读取/API/SQL/迁移/历史数据/外部依赖核查，再决定 DROP COLUMN；不能只凭认领 SQL 未过滤就直接删列。
  7. `device_event_seq` 必须补充设备重启语义。若设备重启后序号归零，需引入 `device_boot_id` 或等价代次，并定义唯一性约束与补发水位线。
- **验收：** 对设计文档逐句检查事实/设计/未定标签；所有“已有/正确/可用/通过”均有对应源码或测试证据；未实施能力明确标记为设计目标。

## 3. 必须新增的验收用例

以下用例是本轮新增建议，编号从现有矩阵延续。不得用单资源测试替代组合资源测试。

| ID | 场景 | 期望 |
|---|---|---|
| P-36 | 两个实验同时申请同一设备、同一点位 | 只有一个 Run 获得完整资源组合；另一方等待或失败，不得部分占用 |
| P-37 | 两实验反向申请设备与点位，形成交叉等待 | 无循环等待；统一全序或完整回滚生效 |
| P-38 | Run A 完成设备操作，但物料仍占据共享点位；Run B 申请设备和点位 | A 可释放设备执行资源，但位置仍由 A 的物料占用；B 不得进入该位置 |
| P-39 | A 的 E3 事件延迟到达，期间设备已由 B 获得 | 事件不得归属 B；无可证明归属时进入 UNATTRIBUTED |
| P-40 | Run A 暂停，物料仍在共享点位；Run B 申请该点位 | B 不得绕过 A 的位置占用；暂停不等于释放物理位置 |
| P-41 | 设备资源申请成功、点位资源申请失败（及反向） | 申请整体回滚，不残留部分锁/预约/租约 |
| P-42 | 设备重启后 device_event_seq 从头计数 | boot generation 与序号组合不冲突；补发水位线正确 |
| P-43 | 同一节点 Resume 同一逻辑命令 vs 人工创建新逻辑动作 | 前者 commandId 不变；后者生成新 logical_operation_id/commandId |
| P-44 | ACK 与心跳均正常，但设备执行进展冻结 | 触发进展告警/异常处置，不永久等待，不自动重发 |
| P-45 | 人工 override 物理动作 UNKNOWN | 审批和证据完整；节点标记人工处置；物料/位置状态不被无条件释放 |
| P-46 | 所有执行入口并发竞争统一准入 | 同一约束下最多一个有效执行权；不存在同步/Resume/重跑旁路 |

每个用例必须记录：测试 commit SHA、环境、设备/模拟器版本、并发线程数、run/batch/material/device/position ID、commandId/logical_operation_id、事件顺序与序号、资源申请释放日志、状态时间线、崩溃注入点、告警与审计结果、可复现脚本。

## 5. 建议实施顺序

1. **源码事实复核：** 按十条执行入口、命令账本、事件写入/认领、资源锁、DDL/迁移逐项复核；每项 PASS/FAIL/UNKNOWN。
2. **统一准入入口：** 先保持并行度 1，改造同步、异步、重跑、Resume 和自动续队入口，验证行为不变。
3. **逻辑命令身份：** 持久化 logical_operation_id、commandId、attempt_no 的关系，先解决重试和 Resume 语义。
4. **事件归属协议：** 实现 commandId 关联、设备占用代次、事件 boot generation/sequence、断线补发和 UNATTRIBUTED 处置。
5. **资源协调：** 统一设备、点位、轨道/机械臂等资源的全局申请顺序，分离设备执行资源和物料位置占用。
6. **恢复与人工处置：** 实现运行中对账、执行进展检测、业务期限、UNKNOWN 隔离和 override 审批审计。
7. **并行度 2 灰度：** 仅在限定流程、限定设备、限定实验组合中开放；P0 全部通过后方可开始。
8. **扩容：** 根据机械臂瓶颈、设备吞吐、资源等待和故障恢复数据决定是否提高并行度，不以线程池空闲作为扩容依据。

## 6. 并行度 2 的放行门槛

以下条件必须全部满足，不能用“总体测试通过”掩盖单项 UNKNOWN：

- [ ] 所有执行入口经过统一准入，旁路被封堵。
- [ ] 同批次最多一个 active attempt 的数据库约束和并发测试通过。
- [ ] E1/E2 commandId 归属测试通过。
- [ ] E3 迟到事件、断线补发、设备重启测试通过。
- [ ] Resume、retry、manual re-execution 的逻辑命令身份测试通过。
- [ ] 跨类锁全序或无嵌套持锁证明通过。
- [ ] 设备执行资源与物料位置资源生命周期分离测试通过。
- [ ] 断线、ACK 丢失、设备卡死、执行超限和恢复对账测试通过。
- [ ] 人工 override 权限、证据、审批、状态和资源边界测试通过。
- [ ] 真实设备 HIL 测试通过；模拟器不得把 TCP send 成功冒充设备 ACK。
- [ ] P0 用例没有 FAIL 或 UNKNOWN。
- [ ] 有限定范围、监控指标、停止条件和回滚开关。

**任何 P0 FAIL 或 UNKNOWN：保持并行度 1，不开放真实并行。**

## 8. 交叉复核要求

下一轮评审者应直接对照本记录和修订后的设计基线，不要只复述原则。每个问题必须给出：

- 结论：支持 / 反对 / 需补充证据；

- 风险和修改建议；
- 可复现验收步骤与结果。

特别要求另一位评审者独立攻击以下反例：

1. A 释放设备后，A 的迟到 E3 到达，B 已经取得设备。
2. 同一节点 Resume 同一动作与人工重新执行同一节点。
3. ACK 正常、心跳正常，但设备执行线程卡死。
4. 两个实验同时争同一设备和同一点位，且其中一个只拿到部分资源。
5. 旧执行实例恢复后尝试继续发送命令。
6. 人工 override 后物料仍在原位置，但下一 Run 申请该位置。
