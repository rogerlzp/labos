## 二、我上轮的两处错误

### 2.1 ❌ 错误一：路径 B（每分支一个 `GraphRunner`）我判断"可行且更省"

**我上轮的论证**：`RunStateMachine` 是无状态的（字段全是注入依赖）⇒ 每分支一实例可行 ⇒ 且省掉 1000 行抽取。

**A/B/C 三方都指向路径 A**，且 **B 给出了我漏掉的决定性理由**。

#### 决定性代码事实（我核实）

`GraphRunner.activate:1592-1620`：

```java
tracker.markArrived(edge);
if (target.kind() == Kind.JOIN_PARALLEL) {
    // AND join：所有入边都到齐才推进
    int left = pending.merge(edge.to(), -1, Integer::sum);
    if (left <= 0) { ready.add(edge.to()); }
} else if (target.kind() == Kind.JOIN_CONDITIONAL) {
    if (tracker.joinReady(g, edge.to()) && ...) { ready.add(edge.to()); }
} else {
    // OR join：任一条到达即可（BPMN 语义），靠 done 去重。
    if (!done.contains(edge.to()) || graphHasCycle) { ready.add(edge.to()); }
}
```

⇒ **`pending` 计数只对 `JOIN_PARALLEL` 网关生效；普通 TASK 节点走 `else` 分支 = OR join（任一入边到达即执行，靠 `done` 去重）。**

⇒ 而且这类图**确实存在**——`ConditionalBranchTracker:33-35` 注释原文：

> **一个节点可能有多条入边**（被别的分叉也指向）。只要还有一条入边**可能**是活的，它就可能执行 ⇒ 不能判死。

#### 为什么这否掉了路径 B

路径 B 让**每个分支各自持有 `done`/`pending`** ⇒ ⇒ 跨分支的 OR-join 去重（`done.contains`）失效 ⇒ ⇒ 而共享节点的"只执行一次"正是靠这个去重保证的 ⇒ ⇒ 路径 B 必须**额外**引入跨分支的共享节点协调 ⇒ ⇒ **"省掉 1000 行抽取"的收益被跨分支协调吃掉** ⇒ 路径 A 更划算。

**⇒ 路径 A 是对的。我上轮 §2.1/§2.2 的主张作废。**

### 2.2 ⚠️ 但 B 对现状的描述有一处不准确 —— 这会误导 V1 约束的**理由**

**B 的"情况 B"原文**：

> 现有 `GraphRunner` 的 `pending` 机制，是按入边计数决定节点何时进入 ready 队列。因此，汇合节点可以在多个前驱都到达后**只执行一次**。

⇒ **这与代码不符**：`pending` 只对 `JOIN_PARALLEL` 生效；普通共享节点是 **OR join：任一到达即执行**，靠 `done` 去重。

⇒ ⇒ **这不是文字细节，它改变了 V1 约束的强度与理由**：

| | 若按 B 的描述（等齐） | 实际（OR join） |
|---|---|---|
| 串行下的语义 | 等所有前驱到齐才执行 | **先到先执行**，后到的被 `done` 挡掉 |
| 并行下的风险 | 变成"两个分支都到齐 ⇒ 可能都执行" | **两个分支几乎同时到达 ⇒ 双方都还没写 `done` ⇒ 双方都执行 ⇒ 物理动作重复** |

⇒ ⇒ **⇒ "V1 禁止两分支共享普通节点"的真正理由不是 `run_node` 唯一键冲突（那只是症状），而是 —— OR join 的去重原语 `done.contains` 依赖 run 级单线程，并发下失效。**

⇒ 这条比 A §4.1 写的"任何业务节点不能同时属于两条分支"**理由更硬**，建议直接写进 V1 约束说明。

### 2.3 ❌ 错误二：我上轮说"StepSink 侧基本安全"——只对了一半

**我上轮的原话**：`PersistingStepSink` 的 `seq` 已是 `AtomicInteger`、`resourceByStep` 是 CHM ⇒ "StepSink 侧基本安全"。

**B 的 5.4 指出的另一侧**（我核实成立）：

```java
// WorkflowService:3510-3524  —— StepCollector（被 PersistingStepSink 当 mirror 用）
static final class StepCollector implements StepSink {
    final List<StepRec> done = new ArrayList<>();               // ← ArrayList
    private final Map<String, Long> resourceByStep = new HashMap<>();  // ← HashMap

```

⇒ ⇒ **两套容器**：`PersistingStepSink` 自己安全（`:2965` AtomicInteger + `:2967` CHM），但它**镜像到 `StepCollector`** ⇒ 后者是普通容器 ⇒ **不安全**。

⇒ ⇒ **我的"StepSink 侧安全"结论要改成"StepSink 自身安全、其 mirror 不安全"。**

### 2.4 ❌ 错误三：我漏了第二道事件防线

B 的 5.3（我核实成立）：

## 三、B 的 5.6 是本轮最有价值的发现，我背书并推广它

**B 的 5.6 原文要点**：`RunStateMachine` 除了 `seq`，还有一处更隐蔽的竞态 —— `loopIndexSupplier` 是实例字段。

**我核实（成立）**：

| 位置 | 事实 |
|---|---|
| `RunStateMachine:66` | `private java.util.function.IntSupplier loopIndexSupplier = () -> 0;`（**实例字段**） |
| `RunStateMachine:114-117` | `withLoopIndexSupplier(supplier)` **写入**它 |
| `RunStateMachine:240` | 完成处理器里 `loopIndexSupplier.getAsInt()` **读取**它 |
| `GraphRunner:885` | 每次派发前 `stateMachine.withLoopIndexSupplier(() -> round);` |

⇒ ⇒ 并发下的交错：

```
线程 A：设置 loopIndexSupplier = round 2
线程 B：设置 loopIndexSupplier = round 5
线程 A：完成处理器读到 round 5   ← 串号
```

⇒ ⇒ **后果比 `seq` 严重**：`seq` 只影响事件序号；`loopIndexSupplier` 写进 **`Effect.source_loop_index`** ⇒ **物料归属记到错误的板/圈次** ⇒ 物料台账错 ⇒ 可能连带影响"这批物料是哪一步产生的"。

### 3.1 推广：B 的 5.6 揭示了一条通则

**通则**：**任何"每次派发前写、稍后读"的实例字段，在并发下都会串。**

⇒ ⇒ 建议对 `RunStateMachine` 的**全部实例字段**做一次分类审计（不只是 `seq` 和 `loopIndexSupplier`）：

| 字段 | 写点 | 读点 | 写-读之间是否跨 await | 并发后果 |
|---|---|---|---|---|
| `seq` | `emit` 内 `seq++` | 同一方法内立即读 | **否** | 序号重复/跳号（轻微） |
| `loopIndexSupplier` | 每次派发前 | 完成处理器 | **是**（跨整个节点执行） | **语义串号**（严重） |
| `stepPlanner` / `paramPlanner` / `noDeviceReason` / `materialGate` / `materialCompletion` / `loopIndexSupplier` 的 setter | 装配期（`GraphRunner` 构造链） | 执行期 | — | 装配期一次写、之后只读 ⇒ **安全**（但 `loopIndexSupplier` 例外，因为它每次派发都重设） |

⇒ ⇒ **⇒ 修法**：把 `loopIndexSupplier` 从"实例字段 + setter"改成"**每次调用显式传参**"（`executeNode(..., int loopIndex)`），或改成 `ThreadLocal`。**前者更好**（语义显式，且不影响其它调用方）。

## 四、三方都没覆盖、或覆盖不足的四个点

### 4.1 `RunProgress.count()` / `allSettled()` 的**两次独立遍历**（我上轮发现，三份材料均未提）

```java
// RunProgress:81-83
public int count(NodeStatus status) {
    return (int) nodes.values().stream().filter(n -> n.status() == status).count();
}
// RunProgress:85-88
public boolean allSettled() {
    return nodes.values().stream().noneMatch(n ->
            n.status() == NodeStatus.PENDING || n.status() == NodeStatus.RUNNING);
}
```

⇒ 换成 CHM 后**不会 CME**，但**两个方法各自遍历一次** ⇒ ⇒ 并发写入点之后，**`count()` 与 `allSettled()` 可能互相矛盾** ⇒ ⇒ `settleRun` 用它们决定 run 落 `completed` 还是 `paused` ⇒ ⇒ **可能把没跑完的 run 落成 completed**。

⇒ ⇒ **建议**：加一个一次性给出两个结论的聚合方法，并在**同一把锁/同一次遍历**里算：

```java
// [提案]
public record Summary(int completed, int manual, boolean allSettled) {}
public synchronized Summary summary() { ... }   // 一次遍历，两个结论
```
并把 `settleRun` 改成只用 `summary()`。

### 4.2 "纯重构等价"的验收锚点 —— A 提了三层验证（接近），B/C 未提

⇒ 补一条**可执行的锚点**：**两个 `seq` 连续性自测就是现成的回归网**：

```java
// test/.../engine/StressTest.java:177

// test/.../engine/EngineSelfTest.java:157
eq("seq 连续", (long) (i + 1), events.get(i).seq());
```

⇒ ⇒ **重构（抽 `executeNode`）后，这两个测试必须仍绿** ⇒ 它们就是"行为未变"的机器可判定锚点。

⇒ ⇒ 补充：**并行化的"行为等价"不能用端到端时间线比**（时间线本来就变），要分层比：

| 层 | 比什么 |
|---|---|
| 单分支流程（重构前后） | 节点顺序、`run_node` 状态与时间、`run_command` 条数与内容、**事件 seq 序列**、台账条数 —— **逐项 diff** |
| 并行流程（改造后） | 不比时间线；比终态、板位、产物、**台账完整性** |

## 五、C（Trade）的价值与不该采纳的部分

### 5.1 C 的独有价值：**SUSPENDED 三态 —— 这是真并发能不能真并行的前提**

C 主张节点执行结果应是三态：

| 状态 | 含义 | 例子 |
|---|---|---|
| `COMPLETED` | 执行完成 | 变量赋值、条件判断、脚本计算 |
| `SUSPENDED` | **等待外部条件，不占用 worker** | 设备命令（派发完就挂起）、等待设备事件、等待人工确认 |
| `FAILED` | 失败 | 策略耗尽 |

C 强调的关键点：**"设备命令派发完成 ≠ 设备节点执行完成；命令 ACK 也不等于物理动作完成；设备节点必须等到正确关联的最终事件才能转 COMPLETED。"**

⇒ ⇒ **这一点三方都没点破，但它是并行收益的前提**：

若 worker **同步等设备**（现状语义），则 4 个分支各等 30 分钟 ⇒ **线程池被占满 ⇒ 并行度再高也没有第二个分支能跑** ⇒ ⇒ **"真并发"只体现在日志时间戳上，墙钟收益 ≈ 0**。

⇒ ⇒ **⇒ 建议：V1 至少把"设备节点"改成"派发即挂起 + 事件恢复"**（`SUSPENDED`），否则第一次真并行的实测收益会低于预期，而这恰恰是最容易被误判为"并发没做对"的点。

⇒ 这与 B 的"超协调阈值不释放租约"、A 的"不设统一超时"**完全一致** —— 三方在"设备执行与节点完成的解耦"上是收敛的，只是 C 把它做成了架构层面的三态。

### 5.2 C 的组件清单：**采纳边界，不采纳节奏**

C 的十组件（`WorkflowCompiler` / `GraphPlan` / `RunCoordinator` / `TokenEngine` / `NodeDispatcher` / `NodeExecutor` / `NodeHandlerRegistry` / `RunExecutionContext` / `EventDispatcher` / `RunLifecycleManager`）**与 A 的方案不冲突，而是同一方向的不同粒度**：

| C 的组件 | 在 A/B 的方案里落在哪 |
|---|---|
| `WorkflowCompiler` / `GraphPlan` | A 的"第 3 步 `ParallelGroupPlan`"（更通用） |
| `RunCoordinator` | A/B 的"单线程主循环" |
| `NodeHandlerRegistry` | **A 的"第 1 步抽 `executeNode`"** —— 把 if-else 链变注册表，正是抽取的自然产物 |
| `RunExecutionContext` / `FlowVariableStore` | A §4.4 的 `FlowExecutionContext` |
| `EventDispatcher` | A §4.4 的 `ExecutionEventSink` |
| `RunLifecycleManager` | A 的"第 5 步 stopFlag + PauseCoordinator" |
| `TokenEngine` / `SplitActivation` | **超出 V1 范围**（V1 不支持嵌套/共享节点，暂不需要） |

⇒ ⇒ **裁决建议**：

> **采纳 C 的组件边界作为目标架构；不采纳 C 的重写节奏。**
> 理由：① 重写没有"改造前"可比 ⇒ "纯重构可验证"这个锚点失效；② 工作量从 1.5–2 天变成数周；③ 现场有真机与在跑的流程，风险不可控。

⇒ ⇒ **零成本可立刻采纳的三件**（不改变实施路径，只是把产物做成"以后能长成 C 的架构"）：

| 采纳项 | 成本 | 收益 |
|---|---|---|
| `NodeHandlerRegistry`（节点处理器注册表） | 中（抽 `executeNode` 时顺带） | if-else 链 ⇒ 可扩展；以后加新节点类型不用改主循环 |
| `FlowVariableStore`（变量语义收口） | 低 | 变量读写集中，禁止原子自增成为默认用法 |
| `ExecutionEventSink`（事件出口收口） | 低 | 一次性解决 `events` / `tee` / `JdbcEventStore.pending` / `RunMonitor` 四处 |

### 5.3 C 的一处需要收窄

C 说"优先支持结构化并行，嵌套结构允许"。⇒ 与 A/B 的"V1 拒绝嵌套"**冲突**。

⇒ ⇒ **裁决建议：V1 按 A/B 收窄（拒绝嵌套）**，理由：**嵌套 = 线程池自阻塞 + 多层 stop/pause 传播 + 多层圈次语义**，三者叠加会让第一次实施的失败概率显著上升。C 的 Token 模型是为嵌套准备的，V1 用不上。

## 六、需要拍板的五点（建议按此顺序定）

### 裁决点 1 · V1 是否包含 `SUSPENDED`（设备节点派发即挂起）？—— **建议：是**

- 不做 ⇒ worker 同步等设备 ⇒ 线程池被长任务占满 ⇒ **并行度 2 的实测墙钟收益可能接近 0**，且第一次上线就会得出"并发做了但没效果"的错误结论；
- 做 ⇒ 多一个"节点挂起 + 事件恢复"的机制，但**这一步同时也就把 `commandId` 归属规则真正落地了**（设备节点必须等到自己那条命令的最终事件才转 COMPLETED）⇒ 与 B/C/A 都一致；
- 代价：`__awaitEvent` 的恢复语义、事件游标的持久化、暂停时的挂起节点处理 ⇒ 工作量 +1~2 天。

### 裁决点 2 · 共享普通节点（多入边非网关节点）—— **建议：V1 编译期拒绝，但把理由改成"OR join 去重在并发下失效"**

- 理由不是 `run_node` 唯一键冲突（症状），而是 `activate` 的 `else` 分支（OR join + `done` 去重）**依赖 run 级单线程**；
- 文档 A §4.1 与 B 的论证都应改成这条。

### 裁决点 3 · 事件序号方案 —— **建议：改语义（分支内单调 + `branch_id`），不改 `AtomicLong`**

- 改 `AtomicLong` ⇒ 全局跳号 ⇒ 必须同时放宽 `StressTest:177` / `EngineSelfTest:157` 两个硬断言 ⇒ **等于放宽既有契约**；
- 改语义（每分支独立 `seq` + 落库带 `branch_id`，排序键 `(branch_id, seq)`）⇒ **单线程下两个自测仍绿** ⇒ 零兼容性成本；
- 前提：确认现场/下游**不依赖"全局连续"**（全仓 grep 未发现按 seq 去重或排序的业务逻辑，`seq` 只进 `payloadJson`）⇒ 需你确认现场侧。

### 裁决点 4 · 是否做一次"跨 await 实例字段"全审计？—— **建议：是，范围限定在 `RunStateMachine`**

- 触发点：B 的 5.6（`loopIndexSupplier`）；
- 方法：把每个实例字段按"写点 → 读点之间是否跨节点执行"分类，只处理"跨"的（目前只有 `loopIndexSupplier` 一个，`seq` 是"不跨"）；
- 成本：0.5 天（读代码 + 改一个 setter 为传参）。

### 裁决点 5 · 是否采纳 C 的五层重写？—— **建议：采纳组件边界，不采纳重写节奏**（见 §5.2）
