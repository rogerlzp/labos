## 二、内核包结构

### `api/` — HTTP 层

| 类 | 行数 | 职责 |
|---|---|---|
| `ApiServer` | ~1500 | 路由、参数解析、JSON 拼装、鉴权 |
| `QueryService` | ~900 | 各类查询（拓扑、位置、实验、执行历史、点位） |
| `AuthService` | ~100 | 登录、token |

**已知问题**：`ApiServer` 是巨类，路由用 `if (path.equals(...))` 串起来。
评审时可关注：增加了这么多接口后是否该拆成 Handler。

### `workflow/` — 流程与实验（最核心）

| 类 | 职责 | 关键方法 |
|---|---|---|
| `WorkflowService` | 流程执行主入口 | `execute()`、`withIsland()`、`withVars()` |
| `WorkflowGraphParser` | 解析 BPMN XML | `parse()` |
| `GraphRunner` | 按图执行（并行/异或网关） | `run()`、`toRecoverable()` |
| `ExperimentExecutor` | 实验执行（变量+循环） | `run(expId, vars, existingRunId)` |
| `ExperimentScheduler` | 多实验并行（岛锁+排队） | `submit()`、`status()` |
| `ExperimentFlowRunner` | 画布逐步执行 | `run(name, steps, vars)` |
| `RealWorkflowRunner` | 工艺回归测试 | `--all` 跑 993 个 |
| `WorkflowBuilder` | 从搬运序列生成流程 | `build()` |
| `PositionLock` | 位置锁（在 driver 包，但业务相关） | `tryReserve()`、`notePlateMove()` |

**两条执行路径**（评审重点）：

```
路径 A：WorkflowService.execute(workflowId)
        → GraphRunner.run() 或 RunStateMachine.executeAll()
        → DriverStepExecutor → 设备

路径 B：ExperimentFlowRunner.run(steps)
        → ShadowProbe → 设备（逐步执行）
```

**两者都落 run/run_node/run_command，但设备分配和变量替换是两套代码。**

### `engine/` — 状态机

| 类 | 职责 |
|---|---|
| `RunStateMachine` | 节点级状态机：pending→ready→running→completed/failed，重试、转人工 |
| `NodeProgress` / `RunProgress` | 进度快照 |

**关键语义**：失败重试用同一 `commandId`（幂等键），避免机械臂搬两次。

### `driver/` — 设备驱动

| 类 | 职责 |
|---|---|
| `DeviceDriver` | 接口：`describe()` / `execute()` / `abort()` / `healthy()` |
| `DriverRegistry` | 按能力找设备 |
| `DriverStepExecutor` | 执行一步（超时 30s，调 sink 落库） |
| `tcp/TcpDriverAdapter` | **短连接**：一命令一连接，读一行 |
| `tcp/TcpPersistentDriver` | **长连接**：按 `messageId` 配对，`pending` Map |
| `PositionLock` | 位置锁 |
| `ShadowProbe` | 单命令探针（影子模式，不落 run） |
| `ShadowRunner` | 整流程影子（不发命令只记日志） |

**两套 ID 问题就在这个包**：`DeviceDriver.execute(DriverCommand)` 里
`deviceInstanceId` 是 `device_instance.id`，而图里存的是 `resource_node.id`。

### `recovery/` — 崩溃恢复决策

| 类 | 职责 |
|---|---|
| `RecoveryDecider` | 判断崩溃后某节点该重试/跳过/转人工 |
| `workflow/StartupRecovery` | 启动时的崩溃收尾（扫描未完成的 run） |

**没有"租约接管"**——早期设计里有，实际未实现。
幂等键仍然有效：`run_command.command_id` 是唯一键，重发不会重复执行。

**安全网**：流程崩溃后自动恢复（**注意**：曾导致流程跑两遍，见开发日志 B6）。

### `alert/` — 告警

漏板、超时、失败、契约不符。去重靠 `fingerprint = errorCode|resourceId`。

## 三、数据模型（核心表）

```
resource_node          资源树：岛 → 设备 → 层位（kind: island/device/incubator/storage）
  ├ parent_id          自引用
  └ attr jsonb         含 pos_x/pos_y（画布坐标）

device_instance        设备实例（一台真实设备）
  ├ resource_id        → resource_node.id  ★ 两套 ID 的映射点
  └ driver_id          → driver 端点

device_state           设备级状态（has_plate ← 由 position_state 派生）
position_state         层位级状态（plate_id，reserved_until）★ 单一数据源

workflow / workflow_node / workflow_edge   BPMN 图
run / run_node / run_command               执行记录（命令级带 device_id）

experiment            实验（island_id / priority / deadline）
experiment_process    实验的步骤（workflow_id / seq / loop_count）
experiment_variable   实验变量
experiment_run / experiment_run_step       实验执行记录

island_flow           岛屿动线（画布上的设备连线）
experiment_graph      实验画布（设备+逻辑节点，jsonb）
robot_point           机械臂点位（code/x/y/z/device_resource_id）
```

## 四、关键数据流

### 流程执行

```
POST /api/workflows/{id}/run
  ↓
WorkflowService.execute()
  ├ 解析 BPMN → 有序节点
  ├ 构建候选池 capPool（按能力 → 设备实例 id 列表）
  │    └ preferEmptyDevices：空设备排前面
  ├ GraphRunner.run()
  │    └ toRecoverable：按能力轮转选设备（usageCursor）
  └ DriverStepExecutor.execute() 每步
       ├ DriverCommand（commandId=幂等键, timeoutMs=30s）
       ├ TcpDriverAdapter.execute() → TCP → 设备
       └ PersistingStepSink.writeStep()
            ├ INSERT run_command（含 device_id）
            └ PositionLock.notePlateMove()（Deposit 放 / Withdraw 取）
```

### 实验执行

```
POST /api/experiments/{id}/run?async=1
  ↓
ExperimentScheduler.submit()      创建 experiment_run（queued）
  ↓ 后台 2 秒轮询
  ├ 取岛锁（putIfAbsent）
  └ ExperimentExecutor.run(expId, vars, existingRunId)
       ├ loadVariables（默认值 ← 覆盖值）
       ├ expand（按 loop_count 展开，上限 20/500）
       ├ 替换 ${var}（启动前一次性）
       └ 顺序调 WorkflowService.execute（失败即停）
```

### 画布逐步执行

```
POST /api/experiments/flow-run?steps=id:method:output:params&vars=
  ↓
ExperimentFlowRunner.run()
  每步：
    ├ instanceIdOf(resourceId)       ★ ID 转换
    ├ enrichWithCoords（withCoords=1 时补点位坐标）
    ├ precheckTransfer（Transfer 前查源设备有没有板）
    ├ ShadowProbe.probe()            → TCP → 设备
    ├ 落 run_node / run_command
    └ 解析输出变量（从驱动原文取字段）
```

## 五、前端结构

```
webapp/src/
├── api/client.ts       apiFetch（统一 401 处理）
├── pages/
│   ├── Island.tsx            岛屿视图：拖拽布设备、搬运序列、层位可视化
│   ├── IslandFlow.tsx        岛屿编排：设备连线 = 搬板
│   ├── ExperimentCanvas.tsx  实验画布：设备+变量+分叉+循环+汇合（React Flow）
│   ├── Experiments.tsx       实验编排：变量表格、循环列、执行历史
│   ├── Workflows.tsx         流程库
│   ├── Designer.tsx          BPMN 设计器（bpmn-js）
│   ├── Monitor / Alerts / ... 监控、告警、日志
│   └── Login.tsx
└── App.tsx            路由 + 导航
```

**两个画布的区别**（容易混）：

| | `ExperimentCanvas` | `IslandFlow` |
|---|---|---|
| 节点 | 设备 + 变量/分叉/循环/汇合 | 只有设备 |
| 箭头 | 逻辑流转 | 板子搬过去 |
| 用途 | 实验怎么跑 | 岛上的物流怎么走 |

## 六、部署形态

### 现在（单机）

```
一台机器：内核 + 前端 + PostgreSQL
设备直连（TcpDriverAdapter）
```

### 目标（多实例 + 网关）

```
中控 × N  ──┐
            ├── Redis（状态中心）
网关 × M  ──┘
            │
        设备
```

**网关已完成但未切换**。切换开关：`LABOS_DRIVER_MODE=redis`（待实现）/ `persistent`（已实现）/ 空（短连接）。

## 七、模块依赖方向

```
api  →  workflow  →  engine  →  driver
         ↓            ↓          ↓
      recovery      alert     persistence
```

**禁止反向依赖**（`driver` 不依赖 `workflow`）。

`PositionLock` 放在 `driver/` 但业务性很强——**这是当前结构的一个瑕疵**，
评审时可以提：位置锁应该属于 `workflow` 还是独立成 `plate/` 包。
