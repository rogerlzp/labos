# 技术架构与模块地图

> 配套 `评审指引.md`。本文讲**代码结构**：每个包/类负责什么、谁调谁、数据往哪流。
>
> **技术栈基线（2026-11-10）**：内核跑在 **Spring Boot 3.2.5 / Java 17** 容器里。
> HTTP 层是 Spring MVC（Tomcat 接管 18080），持久化是 MyBatis XML，
> 连接池与事务由 Spring 管理，日志走 SLF4J。
> 迁移的逐批过程与实测证据见
> [`architecture/SPRING_BOOT_MIGRATION_20261109.md`](architecture/SPRING_BOOT_MIGRATION_20261109.md)。

## 一、整体架构

```
┌──────────────────────────────────────────────────────────┐
│ 浏览器（React 18 + TS + Antd + React Flow）  webapp/       │
└───────────────────┬──────────────────────────────────────┘
                    │ HTTP/JSON  :18080
┌───────────────────▼──────────────────────────────────────┐
│ labos-kernel/   Spring Boot 3.2.5 · Java 17 · Tomcat      │
│                                                          │
│  src/boot/   容器层（生命周期、线程池、配置全归 Spring）     │
│    web/controller/  12 个 @RestController（薄 HTTP 层）      │
│    web/service/     RunService · WorkflowWebService         │
│    web/             鉴权拦截器 · CORS · MVC 配置 · 审计       │
│                                                          │
│  src/main/   领域层（不依赖 Spring 注解，可脱离容器自测）     │
│    workflow/ engine/ driver/ recovery/ alert/ expr/ sim/   │
│    persistence/  MyBatis Mapper · DbConfig · Tx            │
│    api/        AuthService · QueryService（查询与鉴权）       │
└────────┬───────────────────────────────┬─────────────────┘
         │ HikariCP → JDBC                │ TCP + JSON
  ┌──────▼─────────┐              ┌───────▼────────────────┐
  │ PostgreSQL      │              │ 厂商驱动服务             │
  │ MyBatis XML     │              │（.NET Sidecar）          │
  └────────────────┘              └───────┬────────────────┘
                                          │ 厂商 DLL
                                    ┌─────▼────────────────┐
                                    │ 设备 / 机械臂           │
                                    └──────────────────────┘
```

**网关是可选路径**（`labos-gateway/`）：中控 → Redis → 网关 → 设备。
现在默认还是直连，网关已跑通但未切换。

**框架边界**：只有内核容器化。网关是**独立进程**，刻意保持裸 JDK + Lettuce
（理由见 `labos-gateway/pom.xml` 注释：网关是"管道"，引 Spring 会带来约 30MB
依赖和 2–3 秒启动时间，现场重启不方便）。

## 二、目录结构（boot / main 双层）

```
labos-kernel/src/
├── boot/          Spring Boot 容器层 —— 所有 Spring 依赖集中在这里
│   ├── java/com/labos/boot/
│   │   ├── LabosApplication.java        启动入口（唯一）
│   │   ├── BeanConfiguration.java       Service / Mapper 装配
│   │   ├── DataSourceConfiguration.java HikariCP + 事务管理器
│   │   ├── KernelRunner.java            容器就绪后拉起内核
│   │   ├── LogContext.java              MDC 作用域（traceId/runId/…）
│   │   └── web/                         Spring MVC 装配
│   │       ├── ApiAuthInterceptor.java  鉴权
│   │       ├── CorsConfig.java          跨域白名单
│   │       ├── WebMvcConfig.java        MVC 注册
│   │       ├── AuditRecorder.java       操作审计
│   │       ├── controller/              12 个 Controller
│   │       └── service/                 2 个 Web 业务服务
│   └── resources/
│       ├── application.properties       端口 / MyBatis / 日志
│       ├── logback-spring.xml           日志格式与滚动策略
│       └── mapper/*.xml                 8 个 Mapper XML（SQL 全在这里）
└── main/java/com/labos/kernel/           领域层
    ├── workflow/ 流程 · 实验 · 调度
    ├── engine/   状态机（重试/转人工/幂等）
    ├── driver/   设备驱动 · 位置锁
    ├── recovery/ 崩溃恢复
    ├── alert/    告警
    ├── expr/     表达式求值
    ├── sim/      设备模拟器
    ├── redis/    Redis 客户端
    ├── persistence/ MyBatis Mapper · DbConfig · Tx
    ├── device/   设备类型定义
    └── api/      AuthService · QueryService · RbacRules · ApiServer
```

**为什么要分两层**：`src/main/` 不引 Spring 注解 ⇒ 领域逻辑可以脱离容器单测，
也能被 `RealWorkflowRunner` 这类纯 JVM 工具直接驱动；`src/boot/` 只做装配与
HTTP 适配，不写业务。

## 三、容器层（`src/boot/`）

| 类 | 职责 |
|---|---|
| `LabosApplication` | 启动入口。`@SpringBootApplication` + `@MapperScan` + `@EnableTransactionManagement`；排除 DataSource 自动配置（避免 Spring 再建一个 Hikari 池） |
| `BeanConfiguration` | `QueryService` / `AuthService` / `WorkflowService` / `ExperimentScheduler` / `HeartbeatService` / `ApiServer` 全部由容器创建 |
| `DataSourceConfiguration` | HikariCP 连接池（最大 16 / 最小空闲 2 / 60s 泄漏探测）+ `DataSourceTransactionManager` + `TransactionTemplate` |
| `KernelRunner` | 容器就绪后启动内核（崩溃孤儿 settle、命令账本对账、queued rehydrate） |
| `LogContext` | MDC 作用域：`traceId` / `runId` / `commandId` / `workflowId`，try-with-resources，支持嵌套 |
| `web/ApiAuthInterceptor` | 鉴权，只作用于 `com.labos.boot.web.controller` 下的 HandlerMethod |
| `web/CorsConfig` | 跨域白名单，默认本机任意端口，可用 `LABOS_CORS_ORIGINS` 覆盖 |
| `web/WebMvcConfig` | MVC 装配 |
| `web/AuditRecorder` | 操作审计（Controller 拿不到 `HttpExchange`，单独抽一层） |

**装配前提**：Service 类的 `final` 已去掉（CGLIB 不能代理 final 类），
`@Transactional` 才能生效。**同类内部 `this.xxx()` 自调用不经过代理** ——
写路径集中在 4 个入口，事务在入口开启，内部调用共享同一连接。

## 四、HTTP 层（`src/boot/web/`）

### 分层约定

```
HTTP 请求
  ↓
ApiAuthInterceptor        鉴权（token → Session 放进 request attribute）
  ↓
@RestController           解析参数 / 组装响应 / 审计
  ↓
Service（RunService / WorkflowWebService）   业务编排
  ↓
Mapper（MyBatis XML）      SQL
  ↓
领域层（workflow / engine / driver …）
```

**Controller 是薄 HTTP 层**：不写业务分支，只做参数解析、响应形状与审计。
执行域的业务编排收进 `RunService`，流程域收进 `WorkflowWebService`。

### Controller 清单

| Controller | 职责 |
|---|---|
| `AuthController` | login / me / logout |
| `WorkflowController` | 流程 CRUD、执行、图存取、预检 |
| `RunQueryController` | 执行记录查询（列表 / 详情 / 进度） |
| `RunActionController` | 执行控制（启动 / 暂停 / 恢复 / 停止） |
| `ExperimentQueryController` | 实验查询（列表 / 详情 / 历史） |
| `ExperimentActionController` | 实验控制（建 / 跑 / 停止 / 编排） |
| `DeviceController` | 设备池、心跳、状态查询 |
| `SchedulerController` | 调度器状态 |
| `OpsUserController` | 用户与角色管理 |
| `OpsErrorController` | 错误事件与人工窗口 |
| `MetaController` | 状态词典、能力目录、型号库 |
| `FallbackController` | `/health`、静态 UI、404 兜底 |

### 迁移前后的差别

| | 迁移前 | 迁移后 |
|---|---|---|
| 路由 | `ApiServer.route()` 手写 `if (path.equals(...))` 串起来 | 注解式映射，端点自带路径 |
| 传输 | JDK `com.sun.net.httpserver` + 16 线程池 | Spring MVC / Tomcat |
| 业务代码 | 9 个 `*Api`（4457 行）混着 HTTP 与业务 | 拆成 Controller（薄）+ Service（业务） |
| 鉴权 | 每条分支自己判 | 拦截器统一处理 |

**遗留**：`ApiServer` 已从约 1500 行降到 614 行，只剩 `runKernel()`（启动收尾）
与若干静态工具方法（`jsonField` 等）。它内部以 `HttpExchange` 为签名的几个方法
**已无调用者**（死代码），JDK HttpServer 的**服务职责**已完全退役。

## 五、领域层包结构

### `workflow/` — 流程与实验（最核心）

| 类 | 职责 | 关键方法 |
|---|---|---|
| `WorkflowService` | 流程执行主入口 | `execute()`、`withIsland()`、`withVars()` |
| `WorkflowGraphParser` | 解析 BPMN XML | `parse()` |
| `GraphRunner` | 按图执行（并行/异或网关） | `run()`、`toRecoverable()` |
| `ExperimentExecutor` | 实验执行（变量+循环） | `run(expId, vars, existingRunId)` |
| `ExperimentScheduler` | 多实验并行（岛锁+排队） | `submit()`、`status()` |
| `ExperimentFlowRunner` | 画布逐步执行 | `run(name, steps, vars)` |
| `RealWorkflowRunner` | 工艺回归测试 | `--all` 跑全量流程 |
| `WorkflowBuilder` | 从搬运序列生成流程 | `build()` |

**两条执行路径**（评审重点）：

```
路径 A：WorkflowService.execute(workflowId)
        → GraphRunner.run() 或 RunStateMachine.executeAll()
        → DriverStepExecutor → 设备

路径 B：ExperimentFlowRunner.run(steps)
        → ShadowProbe → 设备（逐步执行）
```

**两者都落 run/run_node/run_command，但设备分配和变量替换是两套代码。**

### `engine/` — 状态机

| 类 | 职责 |
|---|---|
| `RunStateMachine` | 节点级状态机：pending→ready→running→completed/failed，重试、转人工 |
| `NodeProgress` / `RunProgress` | 进度快照 |

**关键语义**：失败重试用同一 `commandId`（幂等键），避免机械臂搬两次。

### `driver/` — 设备驱动

| 类 | 职责 |
|---|---|
| `DeviceDriver` | 接口：`describe()` / `execute()` / `abort()` / `healthy()` |
| `DriverRegistry` | 按能力找设备 |
| `DriverStepExecutor` | 执行一步（超时 30s，调 sink 落库） |
| `tcp/TcpDriverAdapter` | **短连接**：一命令一连接，读一行 |
| `tcp/TcpPersistentDriver` | **长连接**：按 `messageId` 配对，`pending` Map |
| `PositionLock` | 位置锁 |
| `ShadowProbe` | 单命令探针（影子模式，不落 run） |
| `ShadowRunner` | 整流程影子（不发命令只记日志） |

**两套 ID 问题就在这个包**：`DeviceDriver.execute(DriverCommand)` 里
`deviceInstanceId` 是 `device_instance.id`，而图里存的是 `resource_node.id`。

### `recovery/` — 崩溃恢复决策

| 类 | 职责 |
|---|---|
| `RecoveryDecider` | 判断崩溃后某节点该重试/跳过/转人工 |
| `workflow/StartupRecovery` | 启动时的崩溃收尾（扫描未完成的 run） |

**没有"租约接管"**——设计里提过，实际未实现。
幂等键仍然有效：`run_command.command_id` 是唯一键，重发不会重复执行。

**安全网**：流程崩溃后自动恢复（**注意**：曾导致流程跑两遍，见开发日志 B6）。

### `alert/` — 告警

漏板、超时、失败、契约不符。去重靠 `fingerprint = errorCode|resourceId`。

## 六、持久化：MyBatis XML 与事务边界

### 为什么是 MyBatis XML

现场决策：**SQL 与 Java 分离，一眼看得清**。JPA 与本项目的 `jsonb`、PG 枚举、
`ON CONFLICT`、`FOR UPDATE` 冲突。

| 配置 | 值 |
|---|---|
| 扫描 | `@MapperScan("com.labos.kernel.persistence")` |
| XML 位置 | `classpath:mapper/**/*.xml`（`src/boot/resources/mapper/`） |
| 字段映射 | `map-underscore-to-camel-case=true` |
| 语句超时 | 30 秒 |

现有 8 个 Mapper XML：`WorkflowMapper` / `RunMapper` / `GraphMapper` /
`QueryMapper` / `ExperimentMapper` / `MetaMapper` / `PauseMapper` /
`WorkflowWebMapper`。

**未收口**：约 100 条 SQL 仍散在 `QueryService` 的写路径大方法、
`DriverStepExecutor`、`ExperimentExecutor` 等处，收进 Mapper 是进行中的工作。

### 事务边界

全仓 `setAutoCommit` / `commit()` / `rollback()` **已归零**。事务有三个入口：

| 入口 | 用在哪 |
|---|---|
| `@Transactional(rollbackFor = Exception.class)` | Spring Bean 上的写方法（**checked 异常默认不回滚，必须显式声明**） |
| `Tx.inTransaction(db, c -> …)` | 静态工具类（`PauseCoordinator` / `BatchOrchestrator` / `PositionLock` 等），内部用 `TransactionTemplate` |
| `Tx.rollbackOnly()` | 正常控制流里的主动回滚（如重复请求时「校验不过就回滚并返回」） |

**桥接的关键**：`DbConfig.bind(ds)` 把 Spring 的 `DataSource` 注入静态字段，
全仓 `db.open()` 统一走 `DataSourceUtils.getConnection` —— 遗留裸 JDBC 代码
无需改动就进入 Spring 事务。

**Mapper 未注入时直接抛异常**（fail-fast），不做"静默回落裸 JDBC"兜底 ——
那种兜底会让漏绑的环境悄悄跑旧路径，查不出来。

|---|---|

## 九、关键数据流

### 流程执行

```
POST /api/workflows/{id}/run
  ↓
WorkflowController → WorkflowWebService
  ↓
WorkflowService.execute()
  ├ 解析 BPMN → 有序节点
  ├ 构建候选池 capPool（按能力 → 设备实例 id 列表）
  │    └ preferEmptyDevices：空设备排前面
  ├ GraphRunner.run()
  │    └ toRecoverable：按能力轮转选设备（usageCursor）
  └ DriverStepExecutor.execute() 每步
       ├ DriverCommand（commandId=幂等键, timeoutMs=30s）
       ├ TcpDriverAdapter.execute() → TCP → 设备
       └ PersistingStepSink.writeStep()
            ├ INSERT run_command（含 device_id）
            └ PositionLock.notePlateMove()（Deposit 放 / Withdraw 取）
```

### 实验执行

```
POST /api/experiments/{id}/run?async=1
  ↓
ExperimentActionController → ExperimentScheduler.submit()
  ↓ 创建 experiment_run（queued）
  ↓ 后台 2 秒轮询
  ├ 取岛锁（putIfAbsent）
  └ ExperimentExecutor.run(expId, vars, existingRunId)
       ├ loadVariables（默认值 ← 覆盖值）
       ├ expand（按 loop_count 展开，上限 20/500）
       ├ 替换 ${var}（启动前一次性）
       └ 顺序调 WorkflowService.execute（失败即停）
```

### 画布逐步执行

```
POST /api/experiments/flow-run?steps=id:method:output:params&vars=
  ↓
ExperimentActionController → ExperimentFlowRunner.run()
  每步：
    ├ instanceIdOf(resourceId)       ★ ID 转换
    ├ enrichWithCoords（withCoords=1 时补点位坐标）
    ├ precheckTransfer（Transfer 前查源设备有没有板）
    ├ ShadowProbe.probe()            → TCP → 设备
    ├ 落 run_node / run_command
    └ 解析输出变量（从驱动原文取字段）
```

## 十一、部署形态

### 现在（单机）

```
一台机器：内核（Spring Boot 容器）+ 前端 + PostgreSQL
→ 设备直连（TcpDriverAdapter）
```

### 目标（多实例 + 网关）

```
中控 × N  ──┐
            ├── Redis（状态中心）
网关 × M  ──┘
            │
        设备
```

**网关已完成但未切换**。切换开关：`LABOS_DRIVER_MODE=redis`（待实现）/ `persistent`（已实现）/ 空（短连接）。

### 构建与启动

```bash
./scripts/build-kernel.sh              # 拉 Maven 依赖 + 编译 main/boot + 拷贝资源
./scripts/build-kernel.sh --verify     # 额外跑事务与 Mapper 自测
./scripts/start-kernel.sh              # 启动：Spring Boot 容器 + 内核 18080
```

**为什么不用 `mvn package` 一把梭**：现有门禁与 e2e 全部按 `out/` 目录 +
裸 javac 的方式工作，改成 Maven 生命周期会同时改掉启动脚本、崩溃恢复段的重启
命令与所有自测的 classpath。**Maven 只负责拉依赖**，编译仍沿用 javac，产物照样落 `out/`。

依赖落在 `labos-kernel/lib/spring/`（已 gitignore，不提交二进制）。

## 十二、模块依赖方向

```
src/boot/   ──→  src/main/          （容器层依赖领域层，反向禁止）

领域层内部：
  api  →  workflow  →  engine  →  driver
         ↓            ↓          ↓
      recovery      alert     persistence
```

**禁止反向依赖**（`driver` 不依赖 `workflow`）。

`PositionLock` 放在 `driver/` 但业务性很强——**这是当前结构的一个瑕疵**，
评审时可以提：位置锁应该属于 `workflow` 还是独立成 `plate/` 包。
