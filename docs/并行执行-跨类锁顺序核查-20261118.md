# 跨类锁顺序：现状核查与最小约束方案

- 日期：2026-11-18
- 版本：**v2**（按评审记录 20261118-06 修订；v1 见 git 历史）

## 1. 现状：三类锁，各自的机制与顺序

### 1.1 三类锁

| 类 | 实现 | 落点表 | 内部是否有序 | 获取位置 |
|---|---|---|---|---|
| 设备执行锁 | `DeviceLock`（DB 条件更新 `device_state.current_run_id` + JVM 分片锁） | **`device_state`** | 单资源，无需排序 | `WorkflowService` 第 3091–3110 行（`onStepStart`） |
| 物理位置 | `PositionLock`（`tryReserve` / `tryReserveForever`） | **`position_state`** | 双锁按 `resource_id` 升序（第 246 行注释） | `TransferPlan` 第 218 / 245 行 |
| 轨道分区 | `RailZoneGuard`（**复用 `DeviceLock`**，`resource_id` 即 zone） | **`device_state`**（与设备锁同表同列） | 多分区 `Collections.sort` + 失败全释放 + 退避重试（第 89–124 行） | `DriverStepExecutor` 第 581 行 |

**关键事实（v2 补充）**：`RailZoneGuard` 第 92–98 行用 `DeviceLock.tryAcquire(z, runId)` 申请分区锁 ⇒ **轨道分区锁与设备执行锁是同一套锁机制、落在同一张表的同一列**，只是 `resource_id` 不同（设备 vs 分区）。

⇒ **真正的跨类互等只有两组表：`device_state` ↔ `position_state`**；设备锁与轨道分区锁之间是**同一张表的不同行**，由 §2.1 的"类内有序"机制保证不成环。

### 1.2 真实获取顺序（搬运分支）

`DriverStepExecutor` 第 540–614 行的实际顺序：

```
1. 目标位预留        TransferPlan.tryReserve / tryReserveForever
                     ↓ 失败 → safeReleaseTarget + throw
2. L1 转盘互锁       TurntableGuard.checkBeforeTransfer
                     ↓ 失败 → safeReleaseTarget + throw
3. L5 等待交互互锁   WaitingInteractionGuard.checkBeforeTransfer
                     ↓ 失败 → safeReleaseTarget + throw
4. L3 轨道分区锁     RailZoneGuard.acquire（内部排序 + 全释放重试）
                     ↓ 失败 → safeReleaseTarget + throw
5. 搬运事务          TransferTransaction.begin
```

外层再套一层：`WorkflowService.onStepStart` 先抢设备锁，`onStepDone` 释放。

**所以当前的实际全序是：**

```
设备锁  →  位置锁  →  轨道分区锁
（外层）    （内层）    （内层最后）
```

按 §1.1 的存储组划分，等价表述为：

```
device_state 组（设备 + 轨道分区）  →  position_state 组（物理位置）
```

### 1.3 关键观察

**每个失败点都调用了 `safeReleaseTarget(posLock, targetPos)`**（第 545 / 561 / 572 / 583 / 603 / 609 行）—— 位置锁抢到了、后续任何一步失败，位置锁都会被释放。这一层做得是对的。

**但设备锁不在这个释放链里**：设备锁由外层的 `onStepDone` 释放，内层失败只抛异常，外层再走 `onStepDone`。这个设计也能工作，因为异常会冒泡到 step 结束。

**注意 L1 转盘与 L5 等待交互是"检查"不是"持有"**（`TurntableGuard.checkBeforeTransfer` / `WaitingInteractionGuard.checkBeforeTransfer` 只读事实、不持锁）⇒ 它们**不构成死锁环的一环**，但它们依赖"读到的状态在真正动作前仍然有效"⇒ 现有代码用"锁内最终复核"（`DriverStepExecutor:616-619` `finalRecheck`）兜这个窗口。

## 2. 现在会不会死锁：分三种情况

### 2.1 类内多锁 —— 已解决

| 场景 | 机制 | 结论 |
|---|---|---|
| 一次搬运要两个位置（源位 + 目标位） | `tryReserveTransfer` 按 `resource_id` 升序申请 | 不会循环等待 |
| 一次运动经过多个轨道分区 | `RailZoneGuard` 排序 + 任一分区失败即全释放 + 重试 | 不会循环等待 |

这一类是安全的，且有代码注释说明设计意图。

### 2.2 类间交叉 —— 当前路径成立，但靠约定

死锁的必要条件是"环"。当前所有路径都是同一个方向：

```
device_state 组  →  position_state 组
```

只要**没有任何路径反向申请**（比如先抢位置再抢设备），就不会成环。

问题在于：**这个顺序没有任何代码强制，也没有测试保护。** 它是通过"大家都在 `onStepStart` 抢设备、在 `TransferPlan` 抢位置、在 `DriverStepExecutor` 抢轨道"这个事实维持的。

### 2.3 未来新增路径 —— 会破

只要有人新写一个"先抢位置再抢设备"的路径（比如在预占点位时提前锁设备），立刻就能构造：

```
Run A: 持设备 D1 → 等点位 P1
Run B: 持点位 P1 → 等设备 D1
→ 双向等待，两个都卡死
```

而 `RailZoneGuard` 和 `DeviceLock` 都不知道对方的存在，谁也不会主动释放。

**这就是"跨类锁无全序"的真实含义**——不是现在有 bug，是**没有护栏，改动一次就可能出事**。

## 3. 最小方案：把隐式顺序变成显式约束

**不做**"统一锁系统"或"一次性原子申请"的重构。只做三件事。

### 3.1 定义资源类型序（v2：由三值简化为两组）

```java
public enum ResourceType {
    /** device_state 组：设备执行锁 + 轨道分区锁（同一张表、同一列） */
    DEVICE_STATE(1),
    /** position_state 组：物理位置锁（另一张表） */
    POSITION(2);

    public final int rank;
}
```

规则：**任何一次申请，必须按 `rank` 非递减顺序进行。**

**为什么从三值简化为两组（v2 修正）**：v1 写 `DEVICE(1) / POSITION(2) / RAIL_ZONE(3)`，把轨道分区排到了位置锁之后。但 §1.1 已确认**轨道分区锁与设备锁是同一张表同一列**，把两者排成先后两个 rank 等于给"同表不同行"施加了一个并不存在的约束 —— 而且它会**误导实现者**：让人以为"设备锁和轨道锁之间也需要排序保护"，从而写出多余的断言逻辑。

真实的约束只有一条：**先 `device_state` 组，后 `position_state` 组**。

> 顺带说明：**"按持有时间从短到长"排序不适用**。持有期由不同生命周期决定（设备锁随 step 释放、位置锁可能跨 step，见 §7 R-18），排序依据是**锁的存储组**，不是时长。

### 3.2 在获取点加断言（v3：类型由锁实现类声明）

**类型来源的三个版本**：

| 版本 | 做法 | 问题 |
|---|---|---|
| v1 | 调用点传 `ResourceType` | 要求开发者记得传对——正是 §2.3 说的破窗点 |
| v2 | 按 `resource_node.kind` 推导 | **kind 表达不了"这一次申请的是哪种锁语义"**：同一个节点可能既参与设备执行互斥，又参与物理位置占用 |
| **v3** | **由锁实现类声明** | 调用点无从绕过，也不依赖"kind 与锁语义一一对应"这个假设 |

v3 形态：

```java
public final class DeviceLock {
    public static final ResourceType TYPE = ResourceType.DEVICE_STATE;
    ...
}

public final class PositionLock {
    public static final ResourceType TYPE = ResourceType.POSITION;
    ...
}

// RailZoneGuard 复用 DeviceLock ⇒ 自动继承 DEVICE_STATE，不单独声明
```

`resource_node.kind` 仍要查，但**只用于一致性校验**，不再用于推导：

```java
private static void checkKind(long resourceId, ResourceType type) {
    ResourceKind k = resourceKindOf(resourceId);
    if (!type.accepts(k)) {
        throw new IllegalStateException(
            "锁类型与资源 kind 不符：id=" + resourceId + " kind=" + k + " lock=" + type);
    }
}
```

这样三种入口都不会漏：新增的锁类必须声明 `TYPE`（编译期强制），现有锁类的业务逻辑不动，kind 作为最后一道一致性检查。

**断言状态用单变量，不用栈（v2 修正）**：

```java
// ThreadLocal<Integer> 记录本线程当前持有的最高 rank
private static void assertOrder(ResourceType want) {
    Integer last = HELD_RANK.get();
    if (last != null && want.rank < last) {
        throw new IllegalStateException(
            "锁顺序违规：本线程已持有 rank=" + last + "，又申请 " + want
            + "（必须先 device_state 组、后 position_state 组）");
    }
    HELD_RANK.set(Math.max(last == null ? 0 : last, want.rank));
}
```

**为什么不用 `Deque`**：v1 用 `ThreadLocal<Deque<ResourceType>>` + `peekLast()`，隐含"push/pop 配对"的假设。但 `RailZoneGuard.acquire` 对多个 zone 是**批量申请、批量释放**（第 97–113 行），**没有配对的 pop** ⇒ 栈式模型会误报。同理 `DeviceLock.acquireWithWait` 的**重入路径**（第 155–158 行，同线程同 run 已持有时直接返回 true）也不是新申请。

**能力边界（v3 补）**：单变量 `ThreadLocal` 只能做**开发期断言**，不能作为正确性依据：

| 场景 | ThreadLocal 能否表达 |
|---|---|
| 同线程内顺序申请 | 能 |
| 批量申请 / 批量释放 | 能（只记最高 rank，不回退） |
| 跨 step 持有（位置锁可能跨 step） | **不能**（step 结束线程可能换人） |
| 跨线程释放 | **不能**（ThreadLocal 不跨线程） |
| 异常退出未清理 | **不能**（需 try/finally 重置） |
| Resume 换线程 | **不能** |

所以跨 step / 跨线程的持有必须靠**显式 token**（锁表里记 `owner_token` 并校验），`ThreadLocal` 只负责"本线程这一串申请的 rank 单调"。

**三处必须显式覆盖的路径（v2 补充）**：

| # | 路径 | 处理 |
|---|---|---|
| 1 | `RailZoneGuard.acquire` 的**批量申请/批量释放** | 批量申请时只做一次 `assertOrder`（按最低 rank 判定），**不要逐个 push**；释放时无需回退（单变量取 max，不做栈式弹栈） |
| 2 | `DeviceLock.acquireWithWait` 的**重入路径** | 重入**不是新申请**，不触发断言；但实现必须能区分"新申请"与"重入" |
| 3 | **跨线程** | `WorkflowService` 的执行线程与 `ExperimentScheduler` 的 pool 是**两个线程池**，resume 在**新线程**上跑 ⇒ `ThreadLocal` 状态**不跨线程** ⇒ 断言在 resume 后失效（对 resume 无害，但覆盖不到"跨线程续跑"）⇒ **每次进入 step 时重置 `HELD_RANK`**，避免上一个 step 的残留影响本 step |

`ThreadLocal` 只用于**开发期断言**，不承担并发正确性——单实例多线程下，每个线程自己的顺序是独立的，断言正好覆盖。

### 3.3 加反向申请测试（v2：按存储组写）

## 4. 为什么不做"一次性原子申请"

有人会提议：把所有需要的资源收集起来，排序后在一个事务里全部拿下。这样最彻底，但代价很大：

| 维度 | 一次性申请 | 逐步抢放（现状） |
|---|---|---|
| 事务长度 | 覆盖整个 step，可能几十分钟 | 每次只覆盖一个资源 |
| 设备利用率 | 低（拿了不用也要占着） | 高（用完就放） |
| 与 `RailZoneGuard` 的等待重试 | 冲突（长事务里不能反复 sleep 重试） | 兼容 |
| 改造范围 | 大（要重写 `TransferPlan` + `DriverStepExecutor`） | 小 |

**现状的"逐步抢放 + 固定顺序"已经能避免死锁**，只是缺护栏。加断言的成本远低于重构。

## 5. 与软预约的关系（容易混淆的一层）

`ExperimentScheduler.tryHoldResources`（第 970–980 行）也有一层"资源占用"，但它和这里的硬锁是两件事：

| | 软预约 | 硬锁 |
|---|---|---|
| 存储 | 内存 `resourceHolds`（`synchronized`） | 数据库条件更新 |
| 作用 | 派发前粗筛，避免把不可能跑的任务塞进线程池 | 执行时真正的互斥 |
| 进程重启 | 丢失 | 保留 |
| 是否防死锁 | 不防（它是单次判定，不持有） | 是 |

**软预约不需要参与全序**，因为它不是"持有"，是"判定"。但它要按同样的类型序计算需求集合，否则会出现"软预约通过、硬锁拿不到"的偏差。

## 6. id 空间问题：结案（v2）

v1 §6 留了一个待确认："zone 的 id 和设备 resource id 是否在同一个空间？"——**答案是：同空间，但不冲突。**

**证据链**：

1. `RailZoneGuard:92-98`：轨道分区用 `DeviceLock.tryAcquire(z, runId)` ⇒ 轨道分区锁**与设备锁复用同一套锁机制**；
2. `DeviceLock` 的 DB 层落在 `device_state.current_run_id`（按 `resource_node.id`）⇒ 设备与分区是**同一张表的不同行**；
3. `PositionLock:206` 注释明写"位置（**resource_node.id**，kind 必须是 incubator/storage/transfer_point）"⇒ 位置也在同一 id 空间；
4. `resource_node.kind` 是枚举（`island/station/device/robot/storage/transfer_point/incubator/operator/virtual` + 后加 `workstation`）⇒ **一个 id 只有一个 kind**。

**结论**：

| 问题 | 答案 |
|---|---|
| 是否同空间？ | **是**，三类锁的 id 都是 `resource_node.id` |
| 同一个 id 会不会既是设备又是分区？ | **不会** —— 一个 id 只有一个 kind |
| 那"id 撞了"是不是问题？ | **不是**。锁落在**不同的表**（`device_state` vs `position_state`），id 相同也不互相干扰 |
| 真正的隔离边界是什么？ | **表**：同表（device_state 组）内是行级互斥 + 类内排序；跨表（→ position_state）才是需要约束顺序的那一类 |

⇒ §3.1 因此按**存储组**而不是按 id 空间来划分类型；§3.2 的类型由**锁实现类声明**（v3），`resource_node.kind` 只做一致性校验。

## 7. 风险

| ID | 风险 | 说明 |
|---|---|---|
| R-15 | 断言只在开发期生效 | 生产环境若关闭断言，护栏消失；建议用配置项控制，并在 CI 中强制开启 |
| R-16 | 现有代码可能已违反顺序 | 加断言后可能暴露出既有的反向申请路径，需要逐一确认是"真违规"还是"误报" |
| R-17 | `TransferPlan` 的 30 分钟 TTL 与轨道锁超时不匹配 | **v2 给改法**：位置锁能持 30 分钟，轨道锁默认超时只有 60 秒（`RailZoneGuard:43-53`，可用 `LABOS_RAIL_WAIT_TIMEOUT_MS` 覆盖）⇒ 顺序是"先占位置、再抢轨道" ⇒ 等不到轨道时白占位置 60 秒。**改法：轨道锁等不到时，先释放位置、再等轨道**（把等待挪到不持锁的阶段），即改 `DriverStepExecutor:583` 的失败路径。**注意这不是并行引入的问题，是现状就有的**（v2 补） |
| R-18 | 跨 run 的"位置占用"与"设备锁"生命周期不同 | 设备锁随 step 释放，位置锁可能跨 step（板留在原地）。**成因不是锁，是板归属**：run 终结后 `releaseRunOccupancy` 只解绑归属、板留原位、位置继续占用（设计基线 P-32 的既定语义）。"两个 run 抢同一空位"由 `PositionLock` 的 DB 条件更新挡住 ✓。**v2 补充：还要补位置占用的孤儿回收**（`DeviceLock` 有 `releaseOrphans`，位置锁侧的对应机制待确认）与"run 终结后位置何时解绑" |
| **R-19** | **设备锁是 step 粒度，设备卡死不动时会被长期占死** | 与"执行无超时"是同一件事的两面：命令既不超时也不判异常 ⇒ 锁不释放 ⇒ 其他 run 永远等不到。**v2 补**：靠设计基线 §4.5.2 的"设备锁占用看门狗"兜（告警 + 转人工，不自动释放） |
| **R-20** | **断言的覆盖有三处漏洞** | 批量申请 / 重入 / 跨线程（见 §3.2 表），实现时必须显式处理，否则会误报或漏报 |

## 8. 验收

| ID | 场景 | 期望 |
|---|---|---|
| K-01 | 正常搬运（设备→位置→轨道） | 全部成功，无断言触发 |
| K-02 | **反向申请（位置→设备）** | 抛 `IllegalStateException`，不静默通过（v2：用例从"轨道→设备"改为"位置→设备"） |
| K-03 | 位置双锁逆序 | 已由 `tryReserveTransfer` 排序，不触发断言 |
| K-04 | 轨道多分区部分失败 | 全释放后重试，不残留 |
| K-05 | 位置抢到、轨道超时 | 位置被释放（`safeReleaseTarget`），无泄漏 |
| K-06 | 两个 run 交叉申请设备与轨道 | 其中一个按顺序先拿满，另一个排队，不成环 |
| K-07 | 高并发压测（10 并发 × 100 次） | 无死锁、无残留锁、无断言误报 |
| **K-08** | **同一 run 的 ParallelGateway 两个分支同时进同一设备** | 分支级互斥生效（`DeviceLock` 的 256 条分片锁已覆盖），断言**不误报** |
| **K-09** | **resume 后在新线程上继续执行** | 断言状态不残留（进入 step 时重置），不误报 |
| **K-10** | **轨道锁批量申请多个 zone** | 断言只做一次判定，不因无配对 pop 而误报 |
| **K-11** | **设备锁重入（同线程同 run 再次申请同一设备）** | 视为重入而非新申请，不触发断言 |

## 9. 需要评审者回答（含 v2 答复）

1. `DEVICE → POSITION → RAIL_ZONE` 这个顺序是否合理？有没有更优的顺序？
   - **v2 答复**：方向正确，但模型应简化为**两组**（`device_state` 组 → `position_state` 组），因为轨道分区锁与设备锁同表同列。"按持有时间排序"**不适用**（持有期由生命周期决定）。
2. §6 的"zone id 与设备 resource id 是否同空间"，有人能确认吗？
   - **v2 已结案**：**同空间**（都是 `resource_node.id`），**不会撞**（一个 id 一个 kind），真正的隔离边界是**表**。详见 §6。
3. §3.2 用 `ThreadLocal` 做断言，是否覆盖了所有获取路径（异步线程、worker 线程）？
   - **v3 答复**：**不覆盖**，三处漏洞（批量申请 / 重入 / 跨线程）已列 §3.2 表；更重要的是跨 step 持有、跨线程释放、异常退出、Resume 换线程**都不能靠 ThreadLocal**，必须用显式 `owner_token`。方案：类型由锁类声明 + 单变量最高 rank + 进 step 重置 + token 校验。
4. §7 R-17：位置锁 30 分钟 vs 轨道锁更短超时，并行时会不会频繁出现"占了位置拿不到轨道"？
   - **v2 答复**：会，但**现状就有、不是并行引入**。不泄漏 ✓（K-05 正确），代价是"白占位置 60 秒"，并行时乘以并发数。改法见 §7 R-17。
5. §7 R-18：位置占用跨 step、设备锁随 step 释放，这个生命周期差异在并行下是否会造成"板占着位置但没人能搬"？
   - **v2 答复**：会，但成因是**板归属**不是锁；抢同一空位由 `PositionLock` 的 DB 条件更新挡住 ✓。要补的是位置占用的**孤儿回收**与解绑时机。
6. 本方案是否足以作为并行度 2 的前置，还是必须先做一次性原子申请？
   - **v2 答复**：**不必作为并行度 2 的阻塞项，但必须先做**。跨类死锁的触发条件是"同一 run 内的并发分支"（ParallelGateway），**今天就存在**，不是并行度 2 引入的 ⇒ ⑤ 是"**低成本护栏、可并行推进**"。而"一次性原子申请"**不该做**（§4 的四条理由成立）。
7. **（v2 新增）§3.1 把 `ResourceType` 从三值简化为两组，是否会漏掉"设备锁与轨道分区锁之间也需要顺序"的场景？**
   - **v2 答复**：不会 —— 它们是**同一把锁的不同行**，由 `RailZoneGuard` 的分区排序 + 全释放重试保证不成环；"顺序"概念对同表不同行不适用。
8. **（v3 改）类型由锁类声明后，还需不需要查 `resource_node.kind`？查的话性能与一致性如何保证？**（当前设计：只在一致性校验时查一次，可缓存）
   - **v2 答复**：需实施时评估。`resource_node` 是低频变更的字典表 ⇒ 可做进程内缓存（带 TTL 或变更失效）；`kind` 变更属于"设备类型重组"这类低频运维动作，不影响运行期。
