# 跨类锁顺序：现状核查与最小约束方案

- 日期：2026-11-18
- 性质：核查 + 最小方案，**未实施**
- 前提：单实例部署
- 结论先行：**现在不是"有死锁"，而是"顺序是隐式的、靠约定维持、没有强制"。需要把它变显式，不需要重构锁系统。**

---

## 1. 现状：三类锁，各自的机制与顺序

### 1.1 三类锁

| 类 | 实现 | 内部是否有序 | 获取位置 |
|---|---|---|---|
| 设备执行锁 | `DeviceLock`（DB 条件更新 `device_state.current_run_id` + JVM 分片锁） | 单资源，无需排序 | `WorkflowService` 第 3091–3110 行（`onStepStart`） |
| 物理位置 | `PositionLock`（`tryReserve` / `tryReserveForever`） | 双锁按 `resource_id` 升序（第 246 行注释） | `TransferPlan` 第 218 / 245 行 |
| 轨道分区 | `RailZoneGuard`（复用 `DeviceLock`，`resource_id` 即 zone） | 多分区 `Collections.sort` + 失败全释放 + 退避重试（第 89–124 行） | `DriverStepExecutor` 第 585 行 |

### 1.2 真实获取顺序（搬运分支）

`DriverStepExecutor` 第 545–600 行的实际顺序：

```
1. 目标位预留        TransferPlan.tryReserve / tryReserveForever
                     ↓ 失败 → safeReleaseTarget + throw
2. L1 转盘互锁       TurntableGuard.checkBeforeTransfer
                     ↓ 失败 → safeReleaseTarget + throw
3. L5 等待交互互锁   WaitingInteractionGuard.checkBeforeTransfer
                     ↓ 失败 → safeReleaseTarget + throw
4. L3 轨道分区锁     RailZoneGuard.acquire（内部排序 + 全释放重试）
                     ↓ 失败 → safeReleaseTarget + throw
5. 搬运事务          TransferTransaction.begin
```

外层再套一层：`WorkflowService.onStepStart` 先抢设备锁，`onStepDone` 释放。

**所以当前的实际全序是：**

```
设备锁  →  位置锁  →  轨道分区锁
（外层）    （内层）    （内层最后）
```

### 1.3 关键观察

**每个失败点都调用了 `safeReleaseTarget(posLock, targetPos)`** —— 也就是说，位置锁抢到了、后续任何一步失败，位置锁都会被释放。这一层做得是对的。

**但设备锁不在这个释放链里**：设备锁由外层的 `onStepDone` 释放，内层失败只抛异常，外层再走 `onStepDone`。这个设计也能工作，因为异常会冒泡到 step 结束。

## 2. 现在会不会死锁：分三种情况

### 2.1 类内多锁 —— 已解决

| 场景 | 机制 | 结论 |
|---|---|---|
| 一次搬运要两个位置（源位 + 目标位） | `tryReserveTransfer` 按 `resource_id` 升序申请 | 不会循环等待 |
| 一次运动经过多个轨道分区 | `RailZoneGuard` 排序 + 任一分区失败即全释放 + 重试 | 不会循环等待 |

这一类是安全的，且有代码注释说明设计意图。

### 2.2 类间交叉 —— 当前路径成立，但靠约定

死锁的必要条件是"环"。当前所有路径都是同一个方向：

```
设备 → 位置 → 轨道
```

只要**没有任何路径反向申请**（比如先抢轨道再抢设备），就不会成环。

问题在于：**这个顺序没有任何代码强制，也没有测试保护。** 它是通过"大家都在 `onStepStart` 抢设备、在 `TransferPlan` 抢位置、在 `DriverStepExecutor` 抢轨道"这个事实维持的。

### 2.3 未来新增路径 —— 会破

只要有人新写一个"先抢轨道再抢设备"的路径（比如机械臂空闲时提前占轨道），立刻就能构造：

```
Run A: 持设备 D1 → 等轨道 Z1
Run B: 持轨道 Z1 → 等设备 D1
→ 双向等待，两个都卡死
```

而 `RailZoneGuard` 和 `DeviceLock` 都不知道对方的存在，谁也不会主动释放。

**这就是"跨类锁无全序"的真实含义**——不是现在有 bug，是**没有护栏，改动一次就可能出事**。

## 3. 最小方案：把隐式顺序变成显式约束

**不做**"统一锁系统"或"一次性原子申请"的重构。只做三件事。

### 3.1 定义资源类型序

```java
public enum ResourceType {
    DEVICE(1), POSITION(2), RAIL_ZONE(3);

    public final int rank;
}
```

规则：**任何一次申请，必须按 `rank` 非递减顺序进行。**

### 3.2 在获取点加断言

在三类锁的 `acquire` / `tryReserve` 入口加一个线程内检查：

```java
// ThreadLocal<Deque<ResourceType>> 记录本线程当前持有的最高 rank
private static void assertOrder(ResourceType want) {
    ResourceType last = HELD.get().peekLast();
    if (last != null && want.rank < last.rank) {
        throw new IllegalStateException(
            "锁顺序违规：已持有 " + last + "，又申请 " + want
            + "（必须按 DEVICE → POSITION → RAIL_ZONE 的顺序）");
    }
}
```

`ThreadLocal` 只用于**开发期断言**，不承担并发正确性——单实例多线程下，每个线程自己的顺序是独立的，断言正好覆盖。

### 3.3 加反向申请测试

```java
// 预期抛 IllegalStateException
@Test
void railThenDevice_mustFail() {
    try (var lease = RailZoneGuard.acquire(db, tenant, runId, path)) {
        assertThrows(IllegalStateException.class,
            () -> deviceLock.acquireWithWait(devRes, runId, 1000));
    }
}
```

## 4. 为什么不做"一次性原子申请"

有人会提议：把所有需要的资源收集起来，排序后在一个事务里全部拿下。这样最彻底，但代价很大：

| 维度 | 一次性申请 | 逐步抢放（现状） |
|---|---|---|
| 事务长度 | 覆盖整个 step，可能几十分钟 | 每次只覆盖一个资源 |
| 设备利用率 | 低（拿了不用也要占着） | 高（用完就放） |
| 与 `RailZoneGuard` 的等待重试 | 冲突（长事务里不能反复 sleep 重试） | 兼容 |
| 改造范围 | 大（要重写 `TransferPlan` + `DriverStepExecutor`） | 小 |

**现状的"逐步抢放 + 固定顺序"已经能避免死锁**，只是缺护栏。加断言的成本远低于重构。

## 5. 与软预约的关系（容易混淆的一层）

`ExperimentScheduler.tryHoldResources`（第 970–980 行）也有一层"资源占用"，但它和这里的硬锁是两件事：

| | 软预约 | 硬锁 |
|---|---|---|
| 存储 | 内存 `resourceHolds`（`synchronized`） | 数据库条件更新 |
| 作用 | 派发前粗筛，避免把不可能跑的任务塞进线程池 | 执行时真正的互斥 |
| 进程重启 | 丢失 | 保留 |
| 是否防死锁 | 不防（它是单次判定，不持有） | 是 |

**软预约不需要参与全序**，因为它不是"持有"，是"判定"。但它要按同样的类型序计算需求集合，否则会出现"软预约通过、硬锁拿不到"的偏差。

## 6. 需要确认的一处实现细节

`RailZoneGuard` 用 `DeviceLock.tryAcquire(z, runId)`，其中 `z` 是 zone 的 `resource_id`；`DeviceLock` 的设备锁也用 `resource_node.id`。

**问题：zone 的 id 和设备 resource id 是否在同一个空间？**

- 如果是同一空间且会重叠 → 同一个 id 可能既是设备又是分区，两层锁会互相干扰
- 如果不重叠或有类型区分 → 无问题

这一点我在代码里没有找到明确证据，**标为待确认**。如果确实同空间，`ResourceType` 的断言就更有必要（因为无法从 id 本身判断类型）。

## 7. 风险

| ID | 风险 | 说明 |
|---|---|---|
| R-15 | 断言只在开发期生效 | 生产环境若关闭断言，护栏消失；建议用配置项控制，并在 CI 中强制开启 |
| R-16 | 现有代码可能已违反顺序 | 加断言后可能暴露出既有的反向申请路径，需要逐一确认是"真违规"还是"误报" |
| R-17 | `TransferPlan` 的 30 分钟 TTL 与轨道锁超时不匹配 | 位置锁能持 30 分钟，轨道锁waitTimeoutMs 更短，可能出现"位置占了但轨道等不到" |
| R-18 | 跨 run 的"位置占用"与"设备锁"生命周期不同 | 设备锁随 step 释放，位置锁可能跨 step（板留在原地），两者不是同一生命周期 |

R-17 和 R-18 是真实的语义问题，不属于"顺序"范畴，但会在并行时放大。建议单独评审。

## 8. 验收

| ID | 场景 | 期望 |
|---|---|---|
| K-01 | 正常搬运（设备→位置→轨道） | 全部成功，无断言触发 |
| K-02 | 反向申请（轨道→设备） | 抛 `IllegalStateException`，不静默通过 |
| K-03 | 位置双锁逆序 | 已由 `tryReserveTransfer` 排序，不触发断言 |
| K-04 | 轨道多分区部分失败 | 全释放后重试，不残留 |
| K-05 | 位置抢到、轨道超时 | 位置被释放（`safeReleaseTarget`），无泄漏 |
| K-06 | 两个 run 交叉申请设备与轨道 | 其中一个按顺序先拿满，另一个排队，不成环 |
| K-07 | 高并发压测（10 并发 × 100 次） | 无死锁、无残留锁、无断言误报 |
