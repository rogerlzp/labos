# 实验室画像与可配置项 — 设计

> 系统要给**很多实验室**用，每个实验室情况不同。
> **不能硬编码一套策略**，但**也不能什么都让用户配**（配不完，也没人会配）。

---

## 一、核心问题：配置到什么粒度

### 太少的后果

```
一套策略打天下：
  - 高通量筛选所（追求吞吐）→ 觉得太保守
  - 医学检验所（追求时效）→ 觉得排队太随意
  - 教学实验室（1-2 个实验）→ 被复杂的死锁检测拖慢
```

### 太多的后果

```
50 个配置项 → 实施顾问配不完 → 用户不敢改 → 最后全用默认
```

### 原则

> **只把"决定架构"的项做成配置；"调优"的项给合理默认值，允许高级用户改。**

---

## 二、决定架构的 6 项（必填）

这 6 项**改变系统的行为方式**，不是参数微调。

### ① 并行度意愿（最关键）

```json
"maxParallelExperiments": 1 | 2 | 4
```

| 值 | 系统形态 |
|---|---|
| **1** | **不需要死锁检测**——只有设备锁 |
| **2** | 需要设备锁 + 简单回程预留（`returnTo`），不需要等待图 |
| **3+** | **需要完整混合调度**（三层资源 + 等待图 + 粗筛） |

**这一项直接决定要实现多少东西**：

| 配置 | 实现工作量 |
|---|---|
| 1 | 已完成（D101-D104） |
| 2 | +2 天（`returnTo`） |
| 3+ | **+4 周（混合方案）** |

**为什么必填**：它决定 4 周的工作量要不要做。

### ② 调度目标

```json
"objective": "throughput" | "latency" | "fairness"
```

| 值 | 排序依据 | 适用 |
|---|---|---|
| **throughput** | 让设备不空转（攒批、大任务优先填满） | 高通量筛选所 |
| **latency** | 谁先来谁先跑（FCFS + 短任务优先） | 医学检验（出报告快） |
| **fairness** | 优先级 + 老化（防饿死） | 多客户共享 |

**影响**：队列排序、粗筛的保守程度。

### ③ 板位未知时的策略

```json
"unknownPlatePolicy": "stop_all" | "stop_related" | "continue_with_alert"
```

| 值 | 行为 | 适用 |
|---|---|---|
| **stop_all** | 全岛暂停 | 高价值样本（不能撞） |
| **stop_related** | 只停涉及这板的 | **默认，推荐** |
| **continue_with_alert** | 继续跑，只告警 | 低价值、可丢弃的样本 |

**为什么必填**：它决定"一次 UNKNOWN 要封多少资源"，影响很大。

### ④ 夜间是否有人

```json
"nightMode": {
  "enabled": true,
  "startHour": 20,
  "endHour": 8,
  "autoResume": true         // 夜间 UNKNOWN 自动降级
}
```

**为什么必填**：`UNKNOWN` 需要人工盘点。**夜里没人，系统会一直卡着**。

**夜间模式下的降级**：

| 白天 | 夜间 |
|---|---|
| 等人工盘点 | 自动标记 LOST，终止相关执行（保守但能继续跑别的） |

**代价**：可能误判（板其实还在设备里），但**总比整晚卡死好**。

### ⑤ 失败重试上限

```json
"retry": {
  "maxAttempts": 3,
  "backoffMs": 1000,
  "onExhausted": "waiting_human" | "abort"
}
```

**影响**：`recovery_policy` 的执行方式。

### ⑥ 是否需要审计追溯

```json
"audit": {
  "enabled": true,
  "level": "command" | "error" | "none"
}
```

| 值 | 存什么 | 存储量 |
|---|---|---|
| **command** | 每条命令的参数+原文 | 大 |
| **error** | 只存失败的 | 中 |
| **none** | 不存 | 小 |

**影响**：制药/临床必须 `command`；教学可以 `none`。

## 三、可以给默认值的项（可选）

这些**不改变架构**，只是调优。

| 项 | 默认 | 说明 |
|---|---|---|
| `scheduling.agingMinutes` | 5 | 优先级老化的速率 |
| `scheduling.preferEmptyDevices` | true | 优先用没板的设备 |
| `deadlock.guardAlwaysOn` | true | 死锁检测常开（评审 R6 已定） |
| `position.lockTtlMinutes` | 30 | 位置锁 TTL |
| `heartbeat.intervalSeconds` | 10 | 心跳间隔 |
| `heartbeat.offlineAlertSeconds` | 30 | 离线多久告警 |
| `experiment.maxDurationHours` | 8 | 超过就当异常 |

## 四、预设模板（降低实施成本）

**用户不用从头配**，选一个模板再微调：

### 模板 A：高通量筛选所

```json
{
  "maxParallelExperiments": 4,
  "objective": "throughput",
  "unknownPlatePolicy": "stop_related",
  "nightMode": {"enabled": true, "autoResume": true},
  "retry": {"maxAttempts": 3, "onExhausted": "abort"},
  "audit": {"enabled": false}
}
```

**特点**：能并行、追吞吐、夜间自动降级、不存详细审计。

### 模板 B：医学检验所

```json
{
  "maxParallelExperiments": 2,
  "objective": "latency",
  "unknownPlatePolicy": "stop_all",
  "nightMode": {"enabled": true, "autoResume": false},
  "retry": {"maxAttempts": 2, "onExhausted": "waiting_human"},
  "audit": {"enabled": true, "level": "command"}
}
```

**特点**：保守并行、追时效、板位不明就全停、存详细审计。

### 模板 C：教学实验室

```json
{
  "maxParallelExperiments": 1,
  "objective": "fairness",
  "unknownPlatePolicy": "stop_related",
  "nightMode": {"enabled": false},
  "retry": {"maxAttempts": 5, "onExhausted": "waiting_human"},
  "audit": {"enabled": true, "level": "error"}
}
```

**特点**：**单实验（不需要死锁检测）**、重试多次（学生操作不稳定）、存错误审计。

### 模板 D：制药 GxP

```json
{
  "maxParallelExperiments": 2,
  "objective": "fairness",
  "unknownPlatePolicy": "stop_all",
  "nightMode": {"enabled": false},
  "retry": {"maxAttempts": 1, "onExhausted": "waiting_human"},
  "audit": {"enabled": true, "level": "command"}
}
```

**特点**：**不自动重试**（要人确认）、全停、全审计。

## 五、配置存在哪

### 表结构

```sql
CREATE TABLE lab_profile (
  tenant_id     bigint PRIMARY KEY,
  template      varchar(32),        -- 从哪个模板来
  max_parallel  smallint NOT NULL,
  objective     varchar(16) NOT NULL,
  unknown_policy varchar(24) NOT NULL,
  night_mode    jsonb NOT NULL DEFAULT '{}',
  retry         jsonb NOT NULL DEFAULT '{}',
  audit         jsonb NOT NULL DEFAULT '{}',
  -- 调优项
  tuning        jsonb NOT NULL DEFAULT '{}',
  updated_at    timestamptz NOT NULL DEFAULT now(),
  updated_by    bigint
);
```

### 运行时怎么读

**启动时读一次，缓存在内存**（配置不会频繁改）：

```java
LabProfile profile = LabProfile.load(tenantId);
// 1 小时 TTL，或者配置变更时主动刷新
```

### 配置改变的影响

| 配置 | 改变后 |
|---|---|
| `maxParallel` | 立即生效（调度器读新值） |
| `unknownPlatePolicy` | 下次 UNKNOWN 生效 |
| `audit.level` | 下次执行生效 |
| `nightMode` | 每分钟检查时段 |

**正在执行的不受影响**——避免中途改变导致状态混乱。

## 六、这套配置怎么减少实现工作量

**关键**：`maxParallel` 决定了要实现多少。

| 实验室配置 | 需要实现 | 工作量 |
|---|---|---|
| **1** | 只设备锁（D101-D104） | **已完成** |
| **2** | +`returnTo` 保护回程 | +2 天 |
| **3+** | +三层资源 + 等待图 + 粗筛 | **+4 周** |

**这就是"渐进式能力"**：

```
第 1 周：交付能跑单实验的版本（任何实验室都能用）
第 2 周：加 returnTo（支持 2 并行）
第 5-6 周：加混合调度（支持 3+ 并行）
```

**每个阶段都能交付**，不用等 4 周全部做完。

## 七、实施建议

### 第一批（现在做）

| 任务 | 估时 |
|---|---|
| `lab_profile` 表 + 模板 | 1 天 |
| 配置读取 + 缓存 | 1 天 |
| `maxParallel` 接入调度器 | 1 天 |

**做完能干什么**：实验室可以选择"我只跑 1 个"，系统就走简单路径；
或者选"要跑 4 个"，**明确知道需要更多实现**。

### 第二批（按配置决定）

**如果有实验室要 2 并行** → 做 `returnTo`（2 天）
**如果有实验室要 3+** → 做混合调度（4 周）

## 八、回答用户的问题

> "要不要人工输入一些条件，来更好的做优化？"

**答案：要，但只限 6 项，且提供模板。**

**为什么只限 6 项**：

| 项 | 为什么必须人工 |
|---|---|
| **并行度意愿** | 决定架构（1 / 2 / 4 的工作量差 4 周） |
| **调度目标** | 业务模式（吞吐 vs 时效），系统猜不到 |
| **板位未知策略** | 样本价值（高价值不能撞，低价值可以丢） |
| **夜间是否有人** | 决定 UNKNOWN 时能不能等（夜里没人等不来） |
| **重试上限** | GxP 不自动重试，教学可以重试 5 次 |
| **审计级别** | 合规要求（制药必须全存，教学可以只存错误） |

**其余给默认值**，高级用户可改。

**模板降低实施成本**：4 个模板覆盖 80% 的场景。

---

## 九、一句话

**配置不是让用户"调系统"，是让用户"告诉系统他的实验室是什么样"。**

**6 项必填决定架构，其余给默认。**
**模板让实施从"配 50 项"变成"选一个再改 2 项"。**

**最重要的是第 1 项**：**并行度意愿决定了要实现多少东西**（1 → 已完成；4 → 还要 4 周）。
