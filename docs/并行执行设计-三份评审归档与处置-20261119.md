## 2. 08（MiniMax）与 09（Trae）的发现与处置

### 2.1 P0-1：锁 rank 模型与真实顺序矛盾

**发现**：

> rank 应编码"**申请槽位**"，不是"存储表"。

v2 的推理是"轨道锁与设备锁同表同列，所以同组"——这对"是否存在跨类互等"成立，但被错误套到了 rank 上。而 v3 改"类型来源"恰好把问题固化了：`RailZoneGuard` 复用 `DeviceLock`，按 v3 自动继承 `DEVICE_STATE` ⇒ 轨道永远拿不到自己的 rank。

真实顺序：设备(1) → 位置(2) → 轨道(1) ⇒ **每次正常搬运都会在轨道锁处触发断言**。

**它给的方案（第四方案）**：

```
槽位集合必须是全局序列的前缀
{} ⊂ {DEVICE} ⊂ {DEVICE, POSITION} ⊂ {DEVICE, POSITION, RAIL}
```

允许跳槽、允许同槽多次、兼容批量与重入，只禁止"跳回前面"。

配套 A1：`RailZoneGuard` 先 `enter(RAIL)`，`DeviceLock` 内部**不再按自己的 TYPE 断言**。

**处置**：**采纳**。B（改真实顺序）不推荐——先占最稀缺的轨道再等位置会降吞吐；C（只比跨组）不解决——倒退恰恰发生在跨组。

**状态**：已写入跨类锁文档 v3，但**调用链验证未做完**（只查了 `DriverStepExecutor` 一条路径）。

### 2.2 P0-4a：`command_id` 粒度假错配

**发现**：不是"两处矛盾"，是**粒度错配**——`command_id` 的天然粒度是"一次传输"，`logical_operation` 一行装不下。

**处置**：**采纳表述修正**。但最终方案按业务决策改为"逻辑操作级唯一，重试复用"（见 §4.1），比"每次传输唯一"更简单。

### 2.3 P0-4b：圈次游标在现有代码里没有答案

**发现**：

> 不是"key 会撞"，而是"**恢复时如何判定当前是第几圈**"在现有代码里没有答案。

依据：`GraphRunner:738` 的 visit 是内存计数，resume 从 1 重算；而 `RunMapper.xml:695-706` 的 `insertNodeRound` 是 `INSERT...SELECT ... WHERE loop_index = 0`，**无 `ON CONFLICT`** ⇒ 恢复重跑同圈要么撞唯一键只打 log，要么写出重复圈次行。

**处置**：**采纳**。补前置能力："恢复进循环体时先从 `run_node` 恢复圈次游标"。

### 2.4 N-A：`insertExperimentFlowRun` 是绕过调度器的旁路

**发现**：写 `workflow_id = NULL`、`status = 'running'`，直接插入。

**核实**（`RunMapper.xml:1012-1019`）：

```sql
INSERT INTO run (..., workflow_id, ..., status, ...)
VALUES (..., NULL, ..., 'running', ...)
```

⇒ 门禁对 `workflowId <= 0` 直接 allow ⇒ 不过准入、不进调度队列 ⇒ **已经存在第二个不受资源级互斥保护的多实验并行源**。

**处置**：**采纳**。降级为受控调试端点（环境开关 + 强制审计 + 文档标注豁免）。

**状态**：已写入文档，**代码未改**。

### 2.5 N-B：`physical_state` 默认值陷阱 ⇒ 上线即停线

**发现**：新增列后存量设备初值全是"未知" ⇒ 按"未知即阻断" ⇒ 上线当天全场不可派发。

**处置**：**采纳**，并进一步区分：

| 值 | 含义 | 行为 |
|---|---|---|
| `NOT_COLLECTED` | 从未采集（设备不支持） | 降级 P1 + 告警 + 列入不可并行清单，**不阻断** |
| `UNKNOWN` | 采集到但不确定 | 阻断 |

**这条后来被 10 号评审用真实事故（2026-11-15 全平台停摆）进一步印证**，见 §3.1。

### 2.6 N-F：`device_state.current_run_id` 是程序态不是设备态

**发现**：它是中控自己写的（`onStepStart` → `markDeviceBusy`），不是设备上报的。

**处置**：**采纳**。分清两件事：

- **资源分配**靠程序态（这台设备能不能分给 B）
- **开跑/恢复**靠物理态（B 到底能不能真的开跑）

### 2.7 N-C / N-D：物理态缺数据源、缺有效期

**发现**：

- 恢复第③项"机械臂分区物理空出"没有数据源，`§4.7.6` 又明确不用视觉/称重 ⇒ 每次恢复都要人工点检
- 物理态是某时刻观测，会漂移（板被拿走、耗材被换）⇒ 需要 `confirmed_at` + `expires_at`

**处置**：**采纳**。人工点检也是物理态证据（P2），落台账 + TTL 内免复核。

### 2.8 N-G：L5 守卫一直 SKIP —— **部分不采纳**

**它说**：提取线节点没带 `interactionId` ⇒ `WaitingInteractionGuard` 整个 L5 守卫一直 SKIP；`__awaitEvent` 参数里没有 process_id ⇒ waiter 的 `expect_*` 全 NULL ⇒ 全退化成弱匹配 ⇒ 而弱匹配又被建议禁用 ⇒ 事件归属无法实现。

**核实**：`WaitingInteractionGuard:33-39` 确实如此。

**判断**：**这一条要拆开**：

| 部分 | 判断 |
|---|---|
| L5 守卫 SKIP 是缺陷 | **不采纳**。提取线是"先等事件再搬"，事件本身就是到位信号；L5 只服务"不等事件直接搬"的场景。让搬运节点补 `interactionId` 是冗余 |
| 无过程标识导致事件归属难 | **采纳**，但解法不是 `process_id`，而是 `commandId` 回显（见 §4.2） |

### 2.9 09（Trae）：规范内部三处矛盾

这三条不是"设计不够好"，是**同一份文档里前后打架**。

#### 2.9.1 弱匹配"声明删除但仍在"

规范第 12 行写"不引入弱匹配"，但：

| 位置 | 内容 |
|---|---|
| 原则 6 | "没有 `commandId` 的事件只能弱匹配" |
| §4.3 | "事件不带 `commandId` → 只能走弱匹配" |
| §7.2 | 完整的"弱匹配"章节（含启用条件与风险说明） |
| §8 降级表 | "弱匹配（若开启）或独占串行" |

**处置**：**采纳**。四处全部改为"无弱匹配"；§7.2 重写，并给出"唯一 waiter 不可作为判据"的两条理由（迟到事件接盘、唯一 waiter ≠ 唯一来源）。

#### 2.9.2 "重试复用同一 commandId"与分档冲突

规范原则 2 写"统一复用"，但表设计 §1.7 写"按设备能力分档"，而现状代码 `DriverStepExecutor` 的 id 含 `-e{exec}`（每次执行变）。三处说法不一致。

**处置**：**采纳**。按业务决策统一为"逻辑操作级唯一，重试复用"（见 §4.1），并明确"`exec` 不进 `commandId`"。

#### 2.9.3 `method` 必填但示例没要求

字段表写"命令关联型必填"，但 §3.4 事件报文示例、§5 侧车要求、§6 模拟器要求**三处都没提** `method`。实现方按示例做，必然漏。

**处置**：**采纳**。降为"可选交叉校验"——归属只认 `commandId`，强制要求 `method` 只增加设备负担，没有收益。

#### 2.9.4 这三条的共同点

都是"改一处、忘一处"：改完 `funcName` / `processId` 后没有全文检索相关词，导致声明与残留并存。

**改进措施**：本轮的每份文档改动都做了全文 grep 自检（如 `grep -c "弱匹配"` 确认只剩否定语境）。

## 3. 10 号评审的两条硬发现

### 3.1 N-B：fail-closed 会重演 2026-11-15 全平台停摆

**依据**（`StirrerDispenserGuard:88-99` 原文）：

> **改之前**：配对缺失一律 `EC-STATE-UNKNOWN` 拒绝。而这个复核是**对每一条设备命令**调用的，且 `stirrer_dispenser_pair` 在客户现场落地前一直是 **0 行** ⇒ **平台里每一台设备的每一条命令都被拒**（实测：提取仪的 `PickTipComb` 直接转人工）。⇒ 这不是"守门更严"，是**整台平台发不出命令**。

**而设计基线 §4.7.3 原文是**：

> 物理态未知时，不进入可派发资源池。**不允许"先试试"。**

**这是同一个结构。** 而且更糟：`physical_state` 是新加列，存量设备初值全是"缺失"。

**处置**：**采纳，并改写 §4.7.3**：

| 情况 | 处置 |
|---|---|
| **事实源缺失**（无传感器 / 初值 / 配置表 0 行） | **fail-open**：落 `SKIP` 审计 + 告警 + 列入不可并行清单 |
| **采集到不确定**（传感器明确 unknown / 状态过期） | **fail-closed**：阻断 |

并明确："不允许先试试"**只适用于后者**。

**这条的意义**：不是"设计可以更严谨"，是**照做会出事**。而且它引的是我们自己的事故记录，不是外部标准。

### 3.2 N-A：E-13 在模拟器上测不出来 ⇒ 假绿

**依据**（`DeviceCore:86-92` 原文）：

> 画像的 step timing 记的是 `BindIncubate`，中控登记的是厂商动作名 `Bind` ⇒ 对不上 ⇒ 落回画像默认的 **20 秒** ⇒ 「按真实时长跑」其实没真等（PAuto 结合 480s 变成 20s）。

⇒ 模拟器是"**阻塞 N 秒后返回 ok**"的同步模型，不是"受理即返回 + 事件通知"。

⇒ `onStepDone` 触发时设备早做完了 ⇒ **E-13（锁已释放但设备还在动）永远重现不了** ⇒ 测试全绿、现场全错。

**处置**：**采纳**。新增改造点 10：模拟器"受理即返回"开关——

```
收到命令 → 立即回 ACK
        → 执行 N 秒
        → 再回 result（两条独立消息）
```

默认关闭以保持现状。

### 3.3 Q2：第四方案，比我给的 A/B/C 都好

**它指出 A 的真实代价**：

> 方案 A 要求把锁的释放点从 `onStepDone` 移到事件到达，这跨 `WorkflowService` ↔ `GraphRunner` 两层。

**并给了替代**：

> 设备锁照旧（step 粒度），**另加中控侧维护的设备物理占用标记**（受理即返回时建立、完成事件到达时清除）⇒ **不需要设备配合** ⇒ 并行收益保留。

**处置**：**采纳，替换原 A/B/C**。

| 对比项 | 方案 A | 第四方案 |
|---|---|---|
| 改锁释放点 | 要跨两层 | **不改** |
| 需要设备配合 | 需要 | **不需要** |
| 并行收益 | 该设备降级独占 | **保留** |

**同时采纳它的分档判据修正**：从"有没有 `physical_state`"（设备改造项，本轮范围外）改为"**会不会受理即返回**"（协议属性）。

### 3.4 Q4：每分支一个 `GraphRunner` 实例 —— 比我小 250 行

**它说**：状态全在实例字段上 ⇒ 一个实例只能跑一个分支 ⇒ **改造点 1（切子图）和 2（重写主循环）本来就是一件事**。

**前提**：分支子图必须**互不相交**，否则 `run_node` 撞唯一键 `(run_id, node_key, attempt, loop_index)`。

**处置**：**采纳**。改造点 1+2 合并，`1080 → 800` 行。新增验收 E-16（子图有交集则编译期报错）。

### 3.5 Q5：并发上限要拆两条

**它说**：

> 线程池按"执行体数"限（防饥饿），资源信号量按"同时占用的设备数"限（防把排队挪到锁层）。嵌套组不额外计数。

并纠正用词：**"16"是执行体数，不是并发度**。

**处置**：**采纳**。并发度改为 `min_r floor(capacity_r / demand_r)`，机械臂是硬瓶颈。

## 4. 业务决策（三条）

### 4.1 `commandId` 的语义

**决策**：**一次逻辑操作唯一，重试复用**。

```
commandId = 一次逻辑操作的唯一标识
  ├─ 重试（网络重发 / 断线重连 / resume）→ 复用同一个
  └─ 重新执行（人工重跑 / 循环下一轮 / 换批次）→ 生成新的
```

**连带修正**：`uk_logical_operation_cmd` **单列唯一即可**，不需要按设备档位放宽——因为 id 在所有重试中不变。

**不支持去重的设备**：id 仍稳定，但**禁止自动重试**（不靠换 id 规避，那会让设备当成新命令）。

**与现状差异**：`DriverStepExecutor` 现在把 `exec` 拼进 id（`-e{exec}`），resume 后 id 会变。改造：`exec` 只留在日志与追踪里。

### 4.2 设备忙时的处理

**决策**：中控**发指令前先查状态**；busy 则等待，过几分钟再查。

落实为（§4.3.5）：

```
① 抢设备锁
② 查状态
   ├─ idle  → 下发
   ├─ busy  → 释放锁，等 1 分钟，回 ①
   └─ 查不到 → 按事实源缺失 fail-open
③ 总等待超 15 分钟 → EC-DEVICE-BUSY-TIMEOUT，转人工
```

**关键设计**：**等待期间不持锁**。持锁等 15 分钟等于"名义上占着设备但没在用"。

### 4.3 模拟器"受理即返回"

**决策**：需要，见 §3.2。

## 7. 未采纳的一条

**不采纳理由**：

| 事实 | 说明 |
|---|---|
| 提取线结构是 `PickTipComb` → `__awaitEvent` | 先等事件再搬，事件本身就是"设备已到位"的信号 |

### 12.1 三个核心质疑

#### 12.1.1 `device_physical_hold` 不是物理互斥保证

**它指出两条**：

| 问题 | 说明 |
|---|---|
| **建立太晚** | 流程是"下发 → 设备 ACK → 建立 hold"。从下发到 ACK 之间，设备可能已开始执行，而 hold 还没建立 ⇒ 另一个 run 查到"空"就下发了 |
| **不能约束绕过中控的命令** | 中控侧标记只在中控内部生效。如果现场软件、厂商软件、调试工具能直接给设备发命令，hold 拦不住 |

**它的方案：派发租约 + 物理占用账本**

```
1. 原子申请设备租约        ← 从"ACK 后建立"提前到"派发前"
2. 成功后才允许派发
3. 下发命令
4. ACK 到达：RESERVED → ACCEPTED
5. 执行期间：保持占用
6. 完成证据到达：→ RELEASED
AC K超时：→ UNKNOWN（不释放，设备可能已收到）
```

**它还要求一个更强前提**：设备命令**单一入口**。

| 等级 | 约束 | 能否保证 |
|---|---|---|
| G1 | 所有命令经中控唯一派发入口 | 能保证中控内部互斥 |
| G2 | 设备自身支持 busy 拒绝 | 更强的物理保护 |
| G3 | 允许外部客户端绕过且不拒绝 | **不能保证，不得进并行清单** |

**处置：采纳。** 特别是"建立时机从 ACK 后提前到派发前"——这是设计缺陷，不是优化。

#### 12.1.2 `ConcurrentHashMap` 不足，且 `withVariables` 会复制 Map

**它指出两个层次**：

1. 容器线程安全 ≠ 业务操作原子性（读-改-写在 CHM 上仍会丢更新）
2. **`withVariables` 会复制**：

```java
public GraphRunner withVariables(Map<String, String> vars) {
    this.variables = new java.util.LinkedHashMap<>(vars);   // ← 复制
}
```

⇒ 每分支 new 一个 `GraphRunner` 再调 `withVariables(shared)`，**各自得到副本，根本没共享**。

**它的方案**：`FlowExecutionContext`（共享 `FlowVariableStore` + `AtomicBoolean stopFlag`），分支 Runner 持同一引用。

**处置：采纳。** 这一条推翻了我"每分支一个实例 + 共享变量"的可行性——**方案本身有矛盾，必须改**。

#### 12.1.3 E-16 不能仅凭 `run_node` 唯一键推导

**它区分三种图结构**：

| 情况 | 结构 | 判断 |
|---|---|---|
| A | 两分支 join 后共用下游 | **合法**，应归 join 之后的主执行流 |
| B | 两分支在 join **之前**经过同一静态节点 | 歧义：执行一次还是两次？结果归谁？ |
| C | 两分支共享尾部（`A→X`、`B→Y` 都到 `Z` 再 join） | 编译器应识别为共同下游 |

**它的修订**：

> 两个分支在 join 之前共享同一静态执行节点时，**若没有显式的共享节点执行语义和独立执行实例身份**，则编译期报错；共同下游节点应归入 join 之后，不计入交集。

**处置：采纳表述**。并且承认：**我没有做过全量流程扫描**，不能宣称"现有流程兼容"。

## 13. 我的回复（对本次评审）

### 13.1 五处口径矛盾：全部承认，是我的流程问题

这 5 处不是"评审者太细"，是我改文档时**只改当前那份**造成的。8.1 最典型——我在规范里写了"无弱匹配"，转手在表设计的 SQL 里写了 `expect_command_id IS NULL OR ...`，等于把刚拆掉的后门又装回去。

**改进措施**：本轮起，每次改完文档做一次跨文档 grep，关键词清单固定：`弱匹配`、`IS NULL`、`process_id`、`重新生成`、`独占串行`。

### 13.2 三个核心质疑的判断

| 质疑 | 我的判断 |
|---|---|
| hold 建立太晚 | **完全成立**，是设计缺陷。"派发前原子租约"必须做，不能靠 ACK 后补 |
| CHM 不够 + `withVariables` 复制 | **完全成立，且推翻了我的方案**。"每分支一个 GraphRunner 实例"必须改成"共享 `FlowExecutionContext`"，否则变量根本没共享 |

### 13.3 我不认同一处细节

它说"1 分钟/15 分钟需证据，可能把 20/30 分钟的正常等待判超时"。

**这取决于 15 分钟是"资源等待上限"还是"设备执行上限"**：

- 如果是**资源等待上限**（B 等 A 释放）：A 在执行 30 分钟孵育时，B 等 15 分钟超时是**正确**的——A 还要跑 15 分钟，让 B 继续等没有意义，不如转人工或换设备
- 如果是**设备执行上限**：那确实会把正常执行判超时

我文档里写的是前者（"总等待上限 → 转人工，不影响原占用者"），但表述不够明确。**改成"资源等待上限"并加一句"不影响在途占用的租约"即可，不需要重新取数。**

不过它的建议仍然有价值：**采集 BUSY 时长分布**能帮助定这个值，应该列为待办而不是阻断项。
