# 型号库与错误码映射

> **回答三个问题**：
> 1. 接一台新设备（比如第三台离心机）要改哪里？
> 2. 设备报 `0x8000000C`，中控怎么知道"该叫人换纸"？
> 3. 改了型号库，数据库里的策略怎么保持同步？

---

## 一、三层结构：类型 / 型号 / 错误码

```
设备类型（DeviceProfile）      离心机、封膜机……"这类设备大概有哪些方法、参数范围"
      ↓
具体型号（DeviceModel）         ASpin 2K、S100……"这台机器的真实指令名/参数/错误码/超时"
      ↓
错误码（ErrorDef）              0x8000000C 无纸 → EC-08-400C → 人工换耗材
```

| 层 | 代码 | 回答什么 | 加一台设备要改吗 |
|---|---|---|---|
| 类型 | `sim/DeviceProfile.java` | 参数边界（rpm 200–14000、量程 0.5–5000 µL） | **不用**（除非是新品类） |
| 型号 | `device/DeviceModels.java` | 真实指令名、参数、错误码、动作超时 | **是，只改这里** |
| 型号行为 | `sim/S100Behavior` / `AspinBehavior` | 时序约束（托盘原点、双门、先建模块） | 只有"有时序约束"的型号才要 |
| 恢复策略 | `pg_rebuild/schema/95_seed_data.sql` | 出事之后中控怎么反应 | **由型号库生成，不手写** |

**为什么要分"类型"和"型号"**：离心机有几十种型号，指令名一家一个样。
只按类型建模时，接第二台就得改代码；按型号建模后，**加一台 = 加一条定义**。

## 二、加一台设备：五步

以"再来一台离心机"为例，全部改动都在 `DeviceModels.java` 一个文件里：

### 第 1 步：确认有没有手册

| 情况 | 结论 | 怎么做 |
|---|---|---|
| 有通信接口说明（不是操作手册） | 可以对接真机 | 走第 2~5 步，`Evidence.MANUAL` |
| 只有公开规格（转速/容量/温控） | 只能先跑流程骨架 | 进 `PLANNED` 清单，等手册 |
| 什么都没有 | 什么都不做 | 别编协议，编了到现场全废 |

> 手册里最值钱的不是"能开机能关机"，而是**错误码表**和**参数单位**。
> 没有错误码表，接上去也只是"能发命令"，出故障照样靠人喊。

### 第 2 步：按手册抄指令

```java
TABLE.put("厂商型号-id", new DeviceModel(
        "厂商型号-id", "centrifuge", "厂商", "型号",
        "xml-dll", "CAN 卡 / 串口", "docs/设备/手册.pdf",
        Evidence.MANUAL, /*门数*/2, /*动作超时ms*/120_000, "接真机前必须确认的点"))
    .method("Init", "Home", "<参数XML>", 3_000)          // 真实名 → 我们的别名
    .method("ControlCover", "OpenDoorA", "...", 1_500)
    .method("GetStatus", "GetStatus", null, 300, false);  // 手册没有 → documented=false
```

规则：
- **`cmd` 必须是手册上印的名字**，别名才是我们流程用的（模拟器两个都认）。
- 手册没有的指令（如 `GetStatus`）要显式标 `documented=false` —— 接真机时可能根本不存在。
- 一条指令多种用法（S100 的 `0x04` 封膜/改板型/查板型）就登记三条别名，`args` 写清索引。

### 第 3 步：抄错误码

```java
// 只写手册码，中控码由"型号块 + 低字节"自动算（不用手填，手填一定会写错）
.error("0x8000000C", "无纸", Disposition.MANUAL,
       "更换耗材；新卷装上仍报错时弯折从动轮固定金属片")
```

`Disposition` 只有四个值，**别按"严重"分，按"该怎么办"分**：

| Disposition | 含义 | 自动重试 | 严重度（自动派生） |
|---|---|---|---|
| `RETRY` | 瞬时故障（信号量、通讯抖动） | ✅ 3 次 | warn |
| `FIX_PARAM` | 参数/时序不对，重试无用 | ❌ 人工改完再跑 | error |
| `MANUAL` | 必须人到现场（堵转、缺耗材、刀片脱落） | ❌ | error |
| `ABORT` | 协议/版本不匹配 | ❌ 直接终止 | fatal |

> 严重度不是手填的，是 `DeviceErrorMapper.severityOf()` 按上表**派生**的。
> 理由：能自动重试的不该是 fatal（半夜叫人起床），必须人处理的不该是 warn（被忽略）。

### 第 4 步（可选）：写型号行为

只有"有时序约束"的型号才需要（见第三节）：

```java
private static DeviceBehavior newBehavior(DeviceModel model) {
    return switch (model.id) {
        case "s100" -> new S100Behavior();
        case "aspin-2k" -> new AspinBehavior();
        case "新型号" -> new XXXBehavior();
        default -> null;          // 没有专属行为 → 走通用状态机
    };
}
```

### 第 5 步：重新生成 SQL

```bash
cd labos-kernel
javac -encoding UTF-8 -d out $(find src -name '*.java')
java -cp out com.labos.kernel.device.DeviceErrorSql --emit-sql
# 把输出整体替换 95_seed_data.sql 里"设备专属错误码"那一节
./scripts/test-all.sh --pure-only    # DeviceModelSelfTest 会检查 SQL 是否同步
```

## 三、模拟器为什么要"型号行为"

通用画像只能校验"方法名 + 参数范围"。真实设备还有**时序约束**，这些只有读了手册才知道：

| 型号 | 时序约束 | 不实现会怎样 |
|---|---|---|
| S100 | 托盘不在原点不能封膜（`0x8000001A`） | 流程漏了 `MoveTray(0)`，仿真照过，到现场每次都失败 |
| S100 | 故障是**锁存**的（换纸后要按清除故障） | 中控以为"重试就好"，现场必须有人按按钮 |
| ASpin 2K | 先 `PcCreateModules` 建模块实例 | 一条命令都发不出去 |
| ASpin 2K | 先 `Init` 回原点 | 设备状态未知，动作无效 |
| ASpin 2K | 两扇门（A/B），门没关不能离心 | 中控按"单门"写的流程到现场对不上 |

**这些约束实现之后，最大的收益不在模拟器，而在流程模板**：
流程写错了，仿真阶段就报 `0x8000001A`，不用等现场。

## 四、设备码 → 中控码 → 动作（链路）

```
设备回包 {"error_code":"0x8000000C"}
   │
   ├─ TcpDriverAdapter / TcpPersistentDriver
   │     ↓ 按"这台设备是哪个型号"查型号库
   ├─ DeviceErrorMapper.map(deviceInstanceId, "0x8000000C")
   │     → EC-08-400C / MANUAL / "无纸" / "换耗材…"
   │     （未登记 → EC-08-9001 + MANUAL，原始码保留在 message 与 device_raw_response）
   │
   ├─ DriverResult(errorCode=EC-08-400C, raw=原始帧)
   │     ↓ DriverStepExecutor 抛 StepFailure(scope=NODE)
   ├─ RecoveryDecider（按 error_code 查 recovery_policy）
   │     → MANUAL（转人工，告警里带"换耗材"）
   ↓
告警 + run_command.error_code + error_occurrence
```

### 型号怎么绑到设备上

三种来源，优先级从高到低：

| 来源 | 写法 | 用途 |
|---|---|---|
| `device.attr` | `{"device_model": "s100"}` | **生产口径**（DB 里配，`WorkflowService` 读取） |
| 环境变量 | `LABOS_DEVICE_MODELS="214=s100,215=aspin-2k"` | 现场联调（还没写库时） |
| 环境变量兜底 | `LABOS_DEFAULT_DEVICE_MODEL=s100` | 单机演示（**生产不要用**：会把所有设备当同一型号） |

**没绑定型号的后果**：设备码原样透传（2.0 行为），`recovery_policy` 查不到策略 ⇒ 全部转人工。
这不是崩溃，是静默降级，所以启动日志里会打印 `已绑定型号 {...}` / `未绑定型号`。

### 三种码的边界

| 码段 | 谁产生 | 例子 |
|---|---|---|
| `0x8000xxxx` | **设备**（厂商手册里的原始码） | `0x8000000C` 无纸 |
| `EC-08-4xxx` | **我们**（`4x` = 型号块，`xx` = 手册码低字节） | `0x8000000C` → `EC-08-400C` |
| `EC-05-20xx` | **适配层**（不是设备回的，是我们判断的时序/部署问题） | `EC-05-2002` 未建模块实例 |
| `EC-08-9001` | **兜底**（设备码没登记） | 任何未登记的码 |

> 编号规则：**`EC-08-<型号块><手册字节>`**，两位块 + 两位字节。
>
> | 块 | 型号 | 例 |
> |---|---|---|
> | `40` | s100（S100 封膜机） | `0x8000000C` → `EC-08-400C` |
> | `41` | aspin-2k（预留，手册无码表） | — |
> | `42`… | 新型号往后取，**不要复用** | — |
>
> **为什么必须带块**：两台不同型号可能都报 `0x8000000C`，含义完全可能不同
> （S100 是"无纸"，另一台可能是"门未关"）。只按字节编号会让两个型号抢同一个中控码，
> 策略自然就串了 —— 这比"编号不好看"严重得多。
>
> 运维看到 `EC-08-401A` 能拆成"块 40 = S100，字节 1A = 托盘不在原点"，不用查表。

## 五、现场怎么用这些码

### 5.1 出事时先看什么

```sql
-- 最近一次设备错误：原始码、中控码、原始回包都在一起
SELECT occurred_at, error_code_id, message, context->>'device_raw_response'
FROM error_occurrence WHERE resolved_at IS NULL ORDER BY occurred_at DESC LIMIT 20;
```

```sql
-- 这个码历史上出现多少次、最后是怎么处理的
SELECT ec.code, ec.title, count(*), o.outcome
FROM error_occurrence o JOIN error_code ec ON ec.id = o.error_code_id
WHERE o.occurred_at > now() - interval '30 days'
GROUP BY 1,2,4 ORDER BY 3 DESC;
```

### 5.2 想改处置（不重启）

策略在库里，改完下一次决策就生效：

```sql
-- 例：现场认为 CAN 通信错误重试 2 次太多次，改成 1 次
UPDATE recovery_policy p SET max_attempts = 1
FROM error_code ec
WHERE p.error_code_id = ec.id AND ec.code = 'EC-08-4004';
```

### 5.3 想加一个码（改代码，不是改库）

设备码 → 中控码的映射**故意放在代码里**（`DeviceModels`），不放进库：

- 它描述的是"设备说了什么"，是**手册的事实**，要跟手册版本一起走；
- 放在库里就变成"现场可以随便改"，改错了没人知道；
- 而"我们该怎么办"（retry/manual/abort）是**策略**，那才该放库里让现场调。

### 8.2 ⚠ 库里没有任何一台设备绑了型号

```sql
select count(*) filter (where attr ? 'device_model'), count(*) from device;   -- 0 | 74
```

**这是对的，不要急着补**：现有 74 台里**没有 S100，也没有 ASpin 2K**。
产线上是 `360R`（Hettich Rotanta 460R）和 `PlateLoc`（Agilent），
我们手上这两份手册**不是它们的**。乱绑的后果是"把 S100 的无纸码解释成别的机器的含义"，
比不绑更糟（不绑只是退化成"未登记码 → 转人工"，不会给出错误建议）。

绑定 SQL（等 S100/ASpin 真的进了产线、或补到 360R/PlateLoc 手册后再执行）：

```sql
-- 先确认是哪台实例（code 要和产线设备号一致）
select di.id, di.code, d.model from device_instance di
  join device d on d.id = di.device_id
 where di.deleted_at is null and (d.model ilike '%s100%' or d.model ilike '%aspin%');

-- 再绑型号（attr 是 jsonb，用 || 合并不覆盖其它字段）
update device set attr = attr || '{"device_model":"s100"}'::jsonb where code = '<设备code>';
```

绑完看启动日志：`[驱动] DRV-xxx → tcp://…（N 台设备，已绑定型号 {214=s100}）`。

### 8.3 线上已有的 60 个码怎么办

它们是**从原始错误帧自动建**的（`title` 里直接存了整段 JSON，如 `EC-08-3010`）。
本轮**没有动它们**：

- 新码走 `4xxx` 块，和现有编码不混；
- 库内错误码的 `title` 是脏数据，但 `error_occurrence` 里挂着已有记录（105 条），
  清理要连带处理外键，属于数据治理的活，不在本轮范围；
- 建议后续用 `DeviceErrorSql --list` 的映射表，把"能对上手册"的现有编码逐步收敛到新码。

## 九、把设备加进"设备池"（带图片）

型号库（代码里的 `DeviceModels`）回答"怎么说这台机器的话"；
**设备池**（库里的 `device` 表）回答"我们支持哪些机器"——前端「岛 → 设备池 → 部署」
就是按这个池子起实例的。两边都要有，一台设备才算"加完"。

### 9.1 一条命令

```bash
cd labos-kernel
export LABOS_DB_HOST=192.0.2.10 LABOS_DB_NAME=labdb LABOS_DB_USER=labos LABOS_DB_PASS=***

# 型号库里已有的（推荐）：名称/厂商/类型/能力/型号绑定全自动
java -cp out:lib/postgresql-42.7.3.jar com.labos.kernel.device.DeviceRegistrar \
     --model s100 --image docs/设备/images/s100.jpg

# 看现状
java -cp out:lib/postgresql-42.7.3.jar com.labos.kernel.device.DeviceRegistrar --list
```

它做的事（都幂等，重跑只更新不新增）：

| 步骤 | 说明 |
|---|---|
| 1 | 从型号库取 `model / vendor / device_type / capability`（**不手抄**） |
| 2 | 图片拷进 `webapp/public/devices/<code>.<ext>`，`icon = /devices/<code>.<ext>` |
| 3 | 写 `device` 行，`attr.device_model` = 型号库 id（**错误码翻译靠它**） |
| 4 | 按 `(tenant_id, code)` upsert，重复执行不会出现第二行 |

**没有图片也能加**：会生成一张占位 SVG（写着型号名 + "示意图"），
池子里不会出现空白格子，也不假装我们有实物照片。有照片时直接 `--image` 覆盖。

### 9.2 外部/未来用户怎么加

给一个 JSON 描述文件，不用记参数：

```json
{
  "code": "ROTANTA_460R",
  "name": "Hettich Rotanta 460R 离心机",
  "model": "Rotanta 460R",
  "vendor": "Hettich",
  "deviceType": "Centrifugation",
  "capability": "CENTRIFUGE",
  "deviceModel": "hettich-rotanta-460r",
  "image": "docs/设备/images/rotanta.jpg",
  "color": "#FFD9A0",
  "remark": "1 号离心机，2 号机另建实例"
}
```

```bash
java -cp out:lib/postgresql-42.7.3.jar com.labos.kernel.device.DeviceRegistrar \
     --from my-device.json
```

- `deviceModel` 必须**在型号库里存在**（否则拒绝），因为错误码翻译要用它；
  手册还没到就先别填，设备码会退化成"未登记码 → 转人工"。
- `deviceType` 用现有词表：`Centrifugation / Sealing / Incubators / Storage /
  Liquid Handling / Robots / …`（`--list` 里能看到别人在用什么）。
- `capability` 必须是 `capability` 表里有的（`SEAL` / `CENTRIFUGE` / `INCUBATE` …），
  写错会直接列出现有值并退出。

### 9.3 现在池子里有什么

| code | 名称 | 类型 | 能力 | 型号库绑定 |
|---|---|---|---|---|

## 十、全链路验收：设备池 → 岛 → 驱动 → 真命令

前面几节证明了"映射表对不对""模拟器像不像"。这一节证明的是**库里的配置能不能把命令真正发出去**——
中间隔着 `device / device_instance / resource_node / resource_capability / driver` 五张表，
任何一张接错，现象都是"界面上有这台设备，但点不动"。

```bash
export LABOS_DB_HOST=192.0.2.10 LABOS_DB_NAME=labdb LABOS_DB_USER=labos LABOS_DB_PASS=***
./scripts/verify-device-chain.sh
```

脚本做的事（全部幂等，可反复跑）：

| 步骤 | 动作 | 失败时的典型现象 |
|---|---|---|
| 1 | 型号入池（`DeviceRegistrar`） | 设备池里没有这台 |
| 2 | 部署到岛（等价前端拖拽） | 岛上看不到 |
| 3 | 补 `resource_capability` + 绑 `driver` | `EC-06-0001 驱动未加载` |
| 4 | 起 模拟器×2 + sidecar×2 | 端口连不上 |
| 5 | 走 `/api/shadow/probe` 发真命令 | 见下表的期望值 |
| 6 | 回查 `recovery_policy` | 错误码翻出来了但没策略 |

断言（这些都是**真命令**，不是单元测试的桩）：

| 设备 | 命令 | 期望 |
|---|---|---|
| S100 | MoveTray(0) → Seal → MoveTray(10000) → Seal | 前两条成功，最后一条 `EC-08-401A`（托盘不在原点） |
| S100 | 回原点 → Seal | 成功（证明故障不是永久锁死） |
| ASpin 2K | CreateModules → Home → RunProgram → CurrSpeed | 全部成功 |

### 10.1 这一步逮到的一个真 bug

第一次跑，10 条探测**全部** `EC-06-0001`（驱动未加载）。根因不在脚本，在产品代码：

`QueryService.deployModel()` 建了 `resource_node` + `device_instance`，
**但没写 `resource_capability`**。而驱动注册表
（`WorkflowService.registerAllDriversFromDb`）是这样过滤的：

```java
if (allCaps.isEmpty()) {
    System.err.println("[驱动] " + m[0] + " 跳过：名下设备都没有声明能力（查 resource_capability）");
    continue;   // ← 整条驱动被跳过，名下所有设备一起失效
}
```

也就是说：**从前端拖进去的设备，能力行是空的，驱动整条注册不上**。
这个 bug 单测发现不了（单测直接传 driver 描述符），只有走"部署 → 发命令"这条路才会暴露。

已修：`deployModel()` 部署时一并写 `resource_capability`
（`INSERT ... SELECT capability_id FROM device WHERE id = modelId`）。
库内数据也一并补齐：缺能力行的实例已补上。

### 10.2 为什么脚本要等 60 秒

驱动注册表有 60s 缓存（`REGISTRY_TTL_MS`），刚绑的 `driver` 不会立刻生效。
脚本里 `sleep 62` 就是等它过期——**不是脚本慢，是设计如此**。
如果嫌慢，重启 ApiServer 也能立刻生效。

### 10.3 脚踩到的 bash 3.2 坑（macOS）

```bash
v=abc; echo "值 $v），复用"      # bash 3.2 报：v?: unbound variable
```

macOS 自带 bash 3.2 会把 `$v` **后面紧跟的 UTF-8 中文字符吞进变量名**，
于是变量名变成 `v），复用` 这种鬼东西。所以凡是 `$var` 后面直接跟中文的，
必须写成 `${var}`。`verify-device-chain.sh` 和 `verify-m4.sh` 已批量修掉（共 7 处）。
