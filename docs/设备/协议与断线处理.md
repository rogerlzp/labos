# 协议与断线处理

> **这份文档回答两个问题**：
> 1. 设备收到指令后要不要回消息？
> 2. 设备断电了怎么办？会不会一直等、卡死？

---

## 一、先看清楚：真实设备的协议根本不一样

读了 `docs/设备/` 下两份真实手册，结论很直接：

| 设备 | 厂商型号 | 物理层 | 协议形态 |
|---|---|---|---|
| 全自动离心机 | 上海爱翱 **ASpin 2K** | CAN 卡 / 串口（COM） | **XML 消息**，经 `Cluster.dll` 的 `SendData()` 下发 |
| 封膜机 | **S100** | 串口 115200 | **二进制帧**（`0xAA` 报头 … `0xFF` 报尾） |

**离心机一条命令长这样**：

```xml
<DispatchCmd>
  <strNodeName>PlateCtri</strNodeName>
  <strCmdName>Start</strCmdName>
  <lpCmdArgs><.../></lpCmdArgs>
</DispatchCmd>
```

**封膜机一条命令长这样**（十六进制）：

```
aa 04 00 00 00 00 00 00 00 00 00 ff     封膜一次
aa 04 5a 00 00 00 00 00 00 00 00 ff     查询板型
```

**这意味着什么**：

> **不存在"一种协议对接所有设备"这回事。**
> 每台设备都要有协议适配层；"能否接入"取决于**有没有人写过它的适配器**，
> 而不是"我们的框架够不够通用"。

**当前代码的假设**：`TcpPersistentDriver` 假设所有设备都是
「TCP + JSON + `#!LABSEP!#` 分隔」——这只对**我们自己的模拟器**成立。
真实设备要么走 DLL（离心机）、要么走串口二进制（封膜机），
**都进不来这个通道**。

**对应的架构缺口**：

```
现在：[协议客户端] ──TCP/JSON──> [设备]
需要：[协议客户端] ─┬─ TCP/JSON ──> 模拟器 / 支持网络的设备
                    ├─ DLL/JNA ──> ASpin 2K（CAN）
                    └─ 串口二进制 ──> S100（封膜机）
```

**这不是马上要改的**，但必须记在案：**"接入一台新设备"的成本主要在写它的协议适配器**。

## 二、设备要不要回消息？

**要。而且是必须。**

### 2.1 我们的协议（模拟器 / 支持 TCP 的设备）

中控每下发一条命令带 `message_id`，设备回帧用 `method_status` 表达三态：

| `method_status` | 含义 | 中控动作 |
|---|---|---|
| `1` | 运行中（长任务，如离心 30 分钟） | 继续等，**不判超时** |
| `2` | 完成 | 成功，进入下一步 |
| `3` | 错误（`error_code` + `error_text`） | 按错误码查恢复策略 |

**不回会怎样**：中控只有等到超时，然后按策略重试或转人工。

### 2.2 真实设备的"回"形态不同

| 设备 | 成功的回应 | 失败的回应 |
|---|---|---|
| ASpin 2K 离心机 | `SendData` 返回 XML 结果 | 同上，结果里有错误信息 |
| S100 封膜机 | `ac` 报头 + 同指令码（如 `ac 04 ...`） | `ee` 报头 + 4 字节错误码 |

**S100 的错误码是有意义的**，不是"失败了"三个字：

| 错误码 | 含义 | 处置 |
|---|---|---|
| `0x80000006` | 未检测到孔板 | 检查上板 |
| `0x80000007` | 刀片脱落 | 需人工换刀片后重启 |
| `0x8000000C` | 无纸 | 换耗材（注意从动滚轮） |
| `0x8000001A` | 托盘不在原点，无法封膜 | 先回原点 |
| `0x80000005` | 电机堵转 | **人工排查，排除后关机重启** |

> **启示**：错误码要能区分"重试就好"和"必须人处理"。
> 现在我们的恢复策略表按 `error_code` 配 `retry/skip/abort/manual`，
> 方向是对的，但**设备专属错误码还没有映射进来**。

## 三、设备断电怎么办？（关键问题）

### 3.1 分两种情况，处理方式完全不同

| 场景 | 现象 | 中控怎么发现 | 现在怎么处理 |
|---|---|---|---|
| **真断电 / 拔网线** | TCP 连接断开 | `readerLoop` 读到 EOF | **立刻** `failAllPending("EC-99-0001","驱动连接断开")`，**所有等待中的命令立即失败** |
| **网络分区 / 设备卡死** | 连接还在，就是不回 | 等不到 `method_status` | **15 秒超时**（`EC-05-1007`） |

**所以：不会一直等、不会卡死。** 有两道闸。

### 3.2 完整的处理链条

```
发命令（带 message_id，进 pending map）
   │
   ├─ 设备回 2/3 ──────────────→ 立即返回结果
   │
   ├─ 连接断开 ────────────────→ failAllPending，立即失败（不等超时）
   │
   └─ 静默 15 秒 ──────────────→ 超时：从 pending 摘掉，返回 EC-05-1007
                                        │
                                        ↓
                                  按恢复策略查表
                          ┌─────────────┼─────────────┐
                       retry ×3        abort         manual
                          │             │             │
                    重发（同 id）    终止整图     转人工等确认
                          │
                    仍失败 → 转 manual
```

**`pending` 摘掉这个动作很重要**：设备后来真回了，会往一个没人等的
`future` 里塞——不摘掉就会内存泄漏，摘掉之后这条晚到的响应作为"孤儿"丢弃。

### 3.3 但重发有个致命问题（已修）

**原来的实现**：

```java
new DriverCommand(UUID.randomUUID().toString(), ...)   // 每次重试都新 id
```

**场景推演**：

```
1. 中控发 Transfer，机械臂真的抓住板了
2. 设备回包在路上丢了（网络抖动，但设备没坏）
3. 中控等 15 秒，超时
4. 策略 retry → 重发
5. 设备收到 —— 一条**全新的 message_id** —— 它不认识
6. 设备**再抓一次**（但手里已经有板了，或者板已经放好了）
```

**结果就是搬错板，或者撞机。**

**现在已经改成稳定键**：

```
r{runId}-n{nodeId}-e{第几次execute}-s{步骤号}-d{设备}
```

- 同一次执行内的重试 → **id 不变** → 设备可据此去重
- 换设备（REASSIGN）→ `d` 段变 → 新 id（确实是另一个物理动作）
- 循环里第二次执行 → `e` 段变 → 新 id（不是重试，是真要再做一遍）

**设备侧配合**：`DeviceCore` 已有成功结果缓存，收到重复 id 直接返回上次结果、
**不重复执行**，日志写「重复命令」。
实测：同 id 第二次 **1ms** 返回（不执行），新 id 正常执行。

### 3.4 真实设备怎么办？

**这份手册没写"重复命令怎么处理"** —— 意味着大概率**不支持幂等**。

所以对真实设备，正确做法是**保守**：

| 命令类型 | 超时后 |
|---|---|
| 查询类（`GetStatus`/`GetPoints`/`CurrSpeed`） | 可以安全重试（无副作用） |
| **动作类**（`Transfer`/`Grip`/`Start` 离心/封膜） | **不要自动重试**，转 `manual` 让人去现场看 |

> **宁可停下来等人，也不要重复搬一次板。**

**当前配置**：`EC-05-1007`（超时）是 `retry ×3`。
**建议**：动作类命令超时改走 `manual`；或者给 `device_instance` 加一个
`supports_idempotent_retry` 标记，默认 `false`。

## 四、还缺什么（按优先级）

| # | 缺口 | 影响 | 建议 |
|---|---|---|---|
| 1 | **动作类命令超时自动重试** | 可能重复搬板 | 改 `manual`，或按设备能力开关 |
| 2 | **无"离线"状态判定** | 设备断电后，前端仍显示"在线"直到下次调用 | 心跳探活失败 N 次 → 标 offline + 告警 |
| 3 | **重连风暴** | 设备恢复瞬间，多个线程同时 `ensureConnected` | 已有 `synchronized`，但要加退避 |
| 4 | **命令未持久化** | 进程崩在"已发未收"时，重启后不知道这条命令发没发 | `run_command` 落库要覆盖"已发"状态 |
| 5 | ~~没有设备专属错误码映射~~ | S100 的 `0x8000000C`（无纸）无法自动判"人工处理" | ✅ **已解决（2026-11-02）**：见下方"5 的处置" |

**第 5 条的处置（计划建 `device_error_map` 表，最后没建）**：

映射最终放在**代码里的型号库**（`device/DeviceModels`），策略仍在 `recovery_policy` 表。理由：

- "`0x8000000C` 是无纸"是**设备的事实**，要跟手册版本一起走版本管理；
  放进库里就变成"现场可以随手改"，改错了没人知道；
- "无纸该转人工"是**我们的策略**，本来就该在库里，现场可以调（不重启生效）；
- 表结构能表达的东西，代码里的 record 一样能表达，但代码能进 code review、能写单测
  （`DeviceModelSelfTest` 会检查 14 个码逐条对应）。

链路细节见 [`型号库与错误码映射.md`](型号库与错误码映射.md)。

**第 4 条值得单独说**：现在 `run_command` 记录的是执行结果，
但"命令已经发出去、还没收到回应"这个中间态，如果进程正好在此时崩溃，
重启后**无从判断设备到底做了没有**。
保守做法是：重启后对这类设备**强制转人工确认**，而不是猜。

---

## 五、一句话总结

> **设备必须回消息；不回就是超时；断了就立即失败 —— 不会卡死。**
> **但"重发"必须幂等，否则宁可转人工。**
> **真实设备协议千差万别，接入成本在适配器，不在框架。**
