## 3. 建议评审重点（按风险排序）

1. **调度器语义一致性**：`ExperimentScheduler`（EDD、岛级互斥、MAX_CONCURRENT=4、tick 2s）与 `scheduler/status` / `experiments/eta` 口径；新增"重启 rehydrate 队列""扣留解除自动续队"是否引入竞态或重复执行。
2. **S3.2 分批异步契约**：`POST /experiments/{id}/run?async=1` 的 CREATED/EXISTING/HELD/NO_MORE 语义、批变量继承（剥离 batchNo/batchSamples 的理由）、变量快照语义；契约与残余见 `docs/设计-实验编排统一-v0.1-实施清单.md` §11。
3. **鉴权与最后管理员保护**：`RbacRules` + `QueryService.updateUser` 的 `pg_advisory_xact_lock` 单事务方案；session 策略（只有 401 清 token）；前端只读禁用覆盖率。
4. **ABI/接口兼容**：`ApiServer` 3331→679 行拆 8 个 controller 后，路由归属/分发顺序/HTTP 行为是否与拆前等价（拆前拆后逐路由对拍 34/34，评审可复跑 e2e + 抽查 controller 内顺序）。
5. **状态词表单一权威**：后端 `StatusVocabulary`（含 run→experiment 迁移 CASE 生成）与前端 `utils/status.ts`（fallback + 接口合并）；是否还有页面绕过词表直接显示原始 code。
6. **测试充分性**：907 条连库测试的覆盖分布；e2e 24 条断言是否覆盖关键链路；门禁阈值只许涨的机制是否足够。
7. **数据/启动恢复**：BUG-14 启动 settle（只收 running、单实例口径）、rehydrate 的幂等、批 run 的 D8 回写。
8. **M10 前置正确性**：型号库元数据接口/页面（MANUAL 2 / PLANNED 6 / 产线在跑待接 3）、`device-go-live-check.py` 的检查项是否够现场用；准备清单是否覆盖手册接入必需信息。

## 4. 评审问题清单（请 AI 重点回答）

1. 调度/分批异步的**并发与恢复语义**是否有漏洞（重启、扣留、aborted、paused 边界）？
2. 最后管理员保护的**锁方案**（advisory lock + 单事务）能否满足单实例/未来多实例？
3. ApiServer 拆 controller 后的**分发顺序等价性**论证是否充分（前缀锚定 + 34/34 对拍）？
4. 状态词表**单一来源**是否仍有漏网（后端/前端/文档/DB 枚举）？
5. 测试体系：907 条连库测试 + 24 条 e2e + 6 个联调脚本，**覆盖与维护成本**是否均衡？门禁阈值策略是否合理？
6. M10 准备清单与型号库先行是否足以支撑"手册一到就能接"？遗漏了哪些资料/字段？
7. 后续规划（`02-后续规划.md`）的**优先级与依赖**是否合理？有没有该提前做的风险项？
8. 安全：RBAC 的写保护、用户管理、会话策略是否有需要加固的点？
9. 数据一致性：启动 settle 与 D8 回写/派生状态/读侧派生之间的边界是否清楚？
10. 是否还有"仿真全绿、真机必炸"的隐性假设（尤其错误码/时序/长任务）？
