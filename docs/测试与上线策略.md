> 面向问题：**这套系统怎么验证能真的给设备发指令？**
> 答案：分层验证，从"代码对不对"到"设备动不动"，每一层都有明确的通过标准。

---

## 一、五层验证模型

```
L5  生产灰度    真实实验、真实样本，逐步放量         ← 现场
L4  分段联调    单设备 → 单流程 → 多设备 → 整岛       ← 现场
L3  整流程影子  流程跑一遍，命令不发设备只记日志      ← 现场/内网
L2  单命令探针  一台设备一个方法，看契约对不对        ← 现场/内网
L1  单元+集成   代码逻辑、数据库读写、状态机          ← 本地/CI
```

**每一层失败就不要往下走**——L1 挂了跑 L2 是在浪费时间。

## 三、L2：单命令探针（最关键的验证手段）

### 它解决什么问题

**"内核到底能不能和设备说话？"**

不是跑一条流程，而是**只发一条命令**：

```bash
POST /api/shadow/probe?resourceId=200214&method=Home
```

返回：

```json
{
  "ok": true,
  "elapsedMs": 87,
  "contract": {
    "messageId": true,
    "messageType": true,
    "method": true,
    "methodStatus": true
  },
  "rawResponse": "{\"message_id\":\"...\",\"equipment_id\":\"214\",...}"
}
```

### 契约检查的四项

| 字段 | 含义 | 缺了会怎样 |
|---|---|---|
| `messageId` | 回包有唯一 id | 分不清是不是这次的响应 |
| `messageType` | 回包类型对 | 可能是心跳不是执行结果 |
| `method` | 回的是你发的方法 | 张冠李戴 |
| `methodStatus` | 有执行状态 | 不知道成功还是失败 |

**四项全 true 才算契约通**。

### 上现场的执行顺序

```
① 改 appsettings.json → 一个端点（先只改一个）
② 起 Sidecar
③ 挑这个端点下一台设备，跑 probe(Home)
   ├ 通 → 换下一个方法
   └ 不通 → 看 rawResponse，多半是字段名/分隔符不对
④ 这台设备的 3-5 个关键方法都通 → 换下一台
⑤ 13 个端点各挑 1-2 台，全通才进 L3
```

**为什么先 Home**：`Home` 是最安全的动作（归位），不会碰板、不会撞东西。

## 四、L3：整流程影子

### 它解决什么问题

**"一条流程跑下来，命令序列对不对？"**

不动设备，只记日志：

```bash
POST /api/workflows/239/shadow-run
```

返回：

```json
{
  "runId": 204900,
  "ok": true,
  "steps": [
    {"node": "N1", "method": "Deposit1", "device": "200171", "wouldSend": true},
    {"node": "N2", "method": "Withdraw1", "device": "200171", "wouldSend": true}
  ]
}
```

### 影子模式看什么

| 检查项 | 怎么看 |
|---|---|
| **设备分配对不对** | 每个节点落到哪台设备，是不是你期望的 |
| **方法名对不对** | `Deposit1` 还是 `Deposit1Ex`，差一个字都不行 |
| **参数对不对** | `${var}` 替换后的值是不是合理 |
| **顺序对不对** | 并行分支是不是真并行、异或走了哪条 |
| **板位预检过不过** | 有没有"源设备没板"的拦截 |

**影子跑不通，实跑一定不通**——因为影子复用了同一套设备分配和参数替换逻辑。

## 五、L4：分段联调

### 为什么分段

一次性跑复杂流程，出问题**不知道是哪一步**。

### 四段

| 段 | 内容 | 通过标准 |
|---|---|---|
| **① 单设备多方法** | 一台设备，跑它 3-5 个方法 | 每个都 ok=true，契约全通 |
| **② 单流程** | 最简单的 2 节点流程（239 这类） | 完成 2/2，`run_command` 有原文 |
| **③ 多设备协作** | 含机械臂搬运的 3-4 站 | `Transfer` 的 source/target 正确 |
| **④ 整岛** | 岛上所有设备都参与 | 无人工干预跑完 |

### 每段之间做什么

```sql
-- 看这一段发了什么命令
SELECT command_seq, method, payload, result
FROM run_command WHERE run_id = ? ORDER BY command_seq;

-- 看设备有没有报错
SELECT method, device_raw_response->>'error'
FROM run_command WHERE run_id = ? AND status = 'failed';
```

**每段跑完都要看这两条 SQL**——不只看"完成没完成"，要看"发了什么、回了什么"。

## 六、L5：生产灰度

### 放量节奏

```
第 1 周   1 个岛、1 条流程、每天 1-2 次，人工盯着
第 2 周   同岛 3-5 条流程
第 3 周   同岛全流程
第 4 周   第 2 个岛
```

**每级放量前必须满足**：

| 条件 | 为什么 |
|---|---|
| 上一级 0 事故 | |
| 告警全部处理完 | 带着告警放量会掩盖新问题 |
| 值班员能独立处理常见告警 | 否则出问题没人接 |

### 绝对不能做的

| 错误做法 | 后果 |
|---|---|
| **两套系统同时操作同一批设备** | 两边都以为板在自己手上，撞机 |
| 跳过影子直接实跑 | 参数错了才发现 |
| 一次改多个端点就上线 | 出问题不知道是哪个端点 |

**过渡必须**：先停掉正在控制这些设备的其他软件 → 人工清空设备 → 本系统上线。

## 七、怎么造测试数据

### 不碰真设备的场景

| 需求 | 做法 |
|---|---|
| 验证命令格式 | `sidecar-dotnet --mock`，返回固定 JSON |

| 验证机械臂点位 | `POST /robot-points/sync` 按设备生成 |

### 造一个"有板"的状态

```sql
INSERT INTO device_state (tenant_id, resource_id, status, has_plate, updated_at)
SELECT 1, id, 'idle', true, now()
FROM resource_node WHERE tenant_id = 1 AND code = 'ID1775'
ON CONFLICT (tenant_id, resource_id)
DO UPDATE SET has_plate = true, updated_at = now();
```

# 1. 点位有了（code = 设备编号）

  ?steps=200214:Transfer::source=ID1775;target=ID1183

## 八、出问题怎么定位

### 三步

```
① 看 run_command
   SELECT * FROM run_command WHERE run_id = ? ORDER BY command_seq;
   → 哪一步失败、当时传了什么、设备回了什么

② 看 run_node
   SELECT * FROM run_node WHERE run_id = ?;
   → 这一步用的哪台设备（resource_id）

③ 看设备原文
   SELECT device_raw_response FROM run_command WHERE id = ?;
   → 驱动到底回了什么
```

### 常见症状对照

| 症状 | 大概率原因 | 怎么确认 |
|---|---|---|
| `EC-06-0001` | 设备没注册到驱动端点 | 查 `device_instance.driver_id` |
| `EC-99-0002` | 驱动抛异常 | 看 Sidecar 日志 |
| 契约某项 false | 返回字段名不对 | 看 `rawResponse` 实际字段 |
| 预检失败 `EC-PLATE-PRECHECK` | 源设备没板 | 查 `device_state.has_plate` |
| 执行 0 步 | 图没连到设备 | 看 `steps` 是否为空 |
| 变量没回填 | 返回字段名不匹配 `output` 配置 | 看 `rawResponse` 有没有那个字段 |

## 十、指令时序：发一条、等一条

### 10.1 现在的模型

```
前端 POST /api/experiments/flow-run
    ↓
ExperimentFlowRunner 逐步骤循环
    ↓ 第 1 步
ShadowProbe.probe → TcpDriverAdapter.execute
    ↓ 建立 TCP 连接
    ↓ socket.setSoTimeout(30_000)      ← 读超时 30 秒
    ↓ 发一行 JSON（分隔符 #!LABSEP!#）
    ↓ 阻塞等回包（循环读到 deadline）
    ↓ 解析 DriverResult
    ↓ 关闭连接
    ↓ 拿到了才进第 2 步
```

**关键**：`ShadowProbe.probe()` 是**同步方法**，返回时结果已经拿到。
调用方 `for (const st of steps)` 天然串行——**不存在"发出去不管"**。

### 10.2 三层超时

| 层 | 超时 | 在哪设置 |
|---|---|---|
| 命令级 | 15 秒（默认，可配） | `ShadowProbe` 构造 `DriverCommand` 时 |
| 读超时 | 30 秒 | `socket.setSoTimeout(30_000)` |
| 连接级 | deadline 控制 | `long deadline = t0 + cmd.timeoutMs()` |

**为什么读超时（30s）比命令超时（15s）长**：读超时是"多久没收到任何字节就放弃"，
命令超时是"整条命令允许多久"。前者留余量，避免命令还在途就被判死。

### 10.3 超时后怎么办

```java
// TcpDriverAdapter
if (System.currentTimeMillis() > deadline) {
    return DriverResult.timeout(cmd.commandId(), ...);
}
```

`DriverResult.timeout` → `probe.ok() == false` → `ExperimentFlowRunner` 记 failed 并**中断后续步骤**。

**为什么中断而不是继续**：这一步没做完就做下一步，物理上可能撞机
（比如机械臂没到位就去取板）。

### 10.4 长连接模式（LABOS_DRIVER_MODE=persistent）

**为什么要有**：短连接适合"几秒回"的命令，但孵育/离心动辄几十分钟：

| 问题 | 短连接 | 长连接 |
|---|---|---|
| 等待期间 socket | 一直占着 | 复用同一条 |
| 中间设备掐连接 | 命令直接失败 | 有重连 |
| 进度/心跳上报 | 全丢 | 能收到（按 messageId 分发） |
| 建连开销 | 每命令一次 | 只一次 |

**开启**：

```bash
LABOS_DRIVER_MODE=persistent java -cp ... ApiServer 18080
```

启动日志会打印 `[驱动] 长连接模式：tcp://...`。

**核心结构**：

```
execute(cmd)
  ├ messageId 入 pending 表
  ├ 写一行到 socket（加写锁，多线程不能同时写）
  └ future.get(timeout)          ← 阻塞

readerLoop()（独立线程）
  ├ read() 按 #!LABSEP!# 分帧
  ├ 解析出 message_id
  └ pending.remove(id).complete(result)
```

**三个必须处理的点**：

| 点 | 不处理会怎样 |
|---|---|
| **重连** | 一次网络抖动就永久失联 |
| **写串行** | 多线程同时写会串包 |
| **清理悬空 future** | 超时后设备才回，往没人等的 future 里塞，内存泄漏 |

**注册表必须缓存**：

```java
if (persistent && cachedRegistry != null && 60秒内) return cachedRegistry;
```

**不缓存的话每次请求都新建驱动**——长连接等于没长连接。
实测不缓存时 `[驱动] 长连接模式` 每次都打印，缓存后只打印一次。

**缓存 60 秒**：让设备能力变更能生效，又不至于每次请求都重连。

**实测**：4 条连续命令 69/64/61/62ms，驱动只创建 1 次。

### 10.5 如果设备是"异步上报"模式

现在这套是**请求-响应**（TCP 短连接，一问一答）。有些厂商的设备是：

```
发命令 → 立即返回 accepted(userId)
        ↓
设备执行（几秒到几分钟）
        ↓
主动上报 completed(userId)
```

**这种模式现在不支持**，需要改造：

| 改造点 | 做法 |
|---|---|
| 长连接 | 不为每条命令建连接，改为常驻连接 + 消息分发 |
| 请求-响应配对 | 用 `messageId` 做 key，维护 `Map<messageId, CompletableFuture>` |
| 超时 | 按 `method` 配置（孵育可能要 30 分钟） |
| 进度 | 上报 `running(50%)` 时更新 `run_node.progress` |

**判断需要不需要改造**：看驱动返回的 `method_status`。
- 返回 `2`（成功）就是同步模式，现在这套够用
- 返回 `1`（运行中）就是异步，**长连接已经能收，但还缺"等它变成 2"**

**长连接已实现的部分**：能同时收多条消息、能按 messageId 配对。
**还缺的**：`method_status=1` 时应该**继续等**而不是直接失败。

现在代码里 `status == 1` 返回 `EC-99-0004`（"设备仍在运行"），
这是个**保守的占位**——真机上应该：
1. 收到 1 时 complete 一个"进度"事件，future 继续等
2. 收到 2 时 complete 最终结果
3. 超时才失败

### 10.6 怎么验证时序对不对

```sql
-- 看每步的耗时：如果都是 0ms，说明是 mock 立即返回
SELECT command_seq, method,
       (result->>'durationMs')::int AS 耗时ms,
       status::text
FROM run_command WHERE run_id = ?
ORDER BY command_seq;
```

**真实设备**：
```
序  方法        耗时ms   状态
1   Deposit1    3200     completed     ← 开门+放板，几秒
2   Transfer    5400     completed     ← 机械臂搬运
3   Deposit1    2800     completed
```

**耗时是 0 或个位数** → 走的是 mock 或虚拟驱动，没真在等设备。

### 10.7 并发场景

**同一条流程内**：严格串行（`for` 循环 + 同步调用）。

**不同流程之间**：靠岛级互斥（`ExperimentScheduler` 的岛锁），
同岛不会有两个流程同时发命令。

**例外**：手动调 `/api/shadow/probe` 不受岛锁约束——
**这是有意的**（现场调试要能随时单点验证），但也意味着
**调试时不要和生产流程同时操作同一台设备**。
