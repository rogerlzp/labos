## 二、核心设计决策（拍板的）

### 2.1 不用银行家算法，用等待图

**理由**：银行家要求"执行前声明最多需要多少资源"，但流程有分支，声明不出来。
硬按最坏情况声明，每个流程都要"整个岛"，**并发度归零**。

**曾经写错过的**：一度说"银行家假设资源可抢占所以不适用"——**这是误述**。
银行家本身就是为不可抢占资源设计的，它真正的前提是**预知最大需求**。
已修正（3 处文档）。

### 2.2 四层资源，不是三层

```
L1 位置   独立，任务全程
L2 通道   信号量（capacity 1/2/N），动作级
L3 门     动作级 —— 门没开，机械臂伸进去会撞机
L4 机械臂 动作级
```

**门是最后补的**：一开始漏了，用户指出"离心机门没开，机械臂伸进去会撞"。

### 2.3 固定全序：门 → 通道 → 位置 → 回程位 → 机械臂

**为什么门排最前**：

```
门开了没抢到机械臂  →  关门放弃，代价小
抢了机械臂才发现门打不开  →  板已在爪子上，没法放回去
```

**invariant**：**所有资源申请完成前，板不离开源位。**

### 2.4 回程承诺不可释放

**M1 设计里埋的矛盾**：

- D105 要求取板时全程预留回程位置
- D111 要求暂停时释放"已占但未用"的位置
- **回程预留位恰恰是"已占但未用"**

**照 D111 释放**：取板 → 故障暂停 → 放回程位 → 别人占了 → 恢复后死锁复现。

**解法**：`release_exempt` 区分**预留**（可释放）和**承诺**（不可释放）。

### 2.5 资源单元是"能力"不是"设备实例"

**踩坑过程**：M3 最初按 `params.equipment_instance_id` 算，结果"占用 ID1183 仍允许启动"。

**查数据才发现**：`equipment_instance_id=155` 是**历史脏数据**（`device_instance` 里不存在），
实际执行是按 `capability_id` 从池子里选，**INCUBATE 有 48 台候选**。

**教训**：这种"看代码以为按实例、实际按能力"的隐性契约，**光读代码看不出来**。

### 2.6 三种暂停态

| 类型 | 恢复条件 |
|---|---|
| `paused_fault` | **心跳恢复自动继续**，不需要人 |
| `waiting_human` | **必须人确认** |
| `paused_unknown` | **必须盘点 + 校正** |

**混成一个"暂停"会导致**：设备好了但没人知道可以继续，或者人以为处理了其实没处理。

## 四、⚠ 我主动列出的待审点（按返工代价排序）

### 🔴 1. 零真机验证 —— 这是最大的风险

**所有 45 项验收、104 个单测，全部在模拟器上跑。**

**模拟器验证不了的**：

| 项 | 为什么验证不了 |
|---|---|
| **门的实际开合时间** | 模拟器立即返回，真实可能要 3-30 秒 |
| **点位坐标是否准确** | 模拟器的坐标是编的 |
| **机械臂能不能到那些位置** | 需要真实运动和碰撞检测 |
| **`Transfer` 到底算几次动作** | 真机可能"抓-移-放"是三个独立动作，那 L4 的"动作级"定义就要改 |
| **通道 `capacity > 1` 的真实语义** | 宽传送带上真的能同时过两块吗？ |

**这一条不是"待改进"，是"未验证"**。所有设计都建立在这些假设上。

### 🔴 2. `order_in_device` 的语义依赖现场

**用户明确**："L1 现在定不了，不同位置要到现场定"。

**所以系统不假设 `L1` 是底层还是外层**，全部现场配。

**风险**：如果现场配错（或没配），**机械臂会去错的位置**，
而且系统**不会报错**（它只按配置执行）。

**缓解**：`fill_status != 'ok'` 的点位不参与调度。
但**没人检查"配的对不对"**。

### 🟠 3. 主链粗筛可能过度保守

**"资源最重"策略**：自动选用到设备最多的分支。

**问题**：**异常分支往往要更多设备**（比如失败要走重测流程），
按它算会让粗筛**过度保守**，把本来能跑的情况也拒了。

**现在的应对**：弹窗里给"仍然启动"，让用户自己判断。
**但没有统计"被拒了多少次、其中多少次其实能跑"**。

### 🟠 4. 等待图的"误拒"没有度量

**等待图拒绝成环的申请**，但某些申请**本可等待后成功**。

**现在**：只记录了 `rejectedCount`，**不知道其中多少是真死锁、多少是误判**。

**长期影响**：如果误拒率高，用户会觉得"系统总说不行"，失去信任。

### 🟠 5. `estimatedWaitSeconds` 不准

**算法**：`run_node.estimate_sec - 已跑秒数`。

**问题**：
- `estimate_sec` 是编排时填的，可能不准
- 如果有多个节点在跑，只取最后一个
- **实际测试中经常显示 0 秒**（已超过预估但没结束）

**已做的**：0 秒显示"不足 1 分钟"，界面标"预估，仅供参考"。

### 🟡 6. 板位解封依赖 `possible_locations`

**发现于测试**：`locatePlate` 靠 `plate.possible_locations` 找要解封的位置。

**如果这个字段丢了**（人为改库、导入数据），**封锁就永远解不开**。

**现在的应对**：`markPlateUnknown` 一定会写这个字段。
**但没有兜底**（比如"按 block_reason + 时间范围"反查）。

### 🟡 7. 脚本节点（L3）只设计了没实现

**设计**：`docs/自定义脚本节点-设计.md`（独立进程沙箱 + 审批 + 审计）。

**状态**：**只有设计**。3 周工作量，风险最高。

**如果客户提"要查外部系统"**，这个就得做，且必须配套 OS 级隔离。

## 八、评审建议关注的三件事

### ① 这些设计在真机上成立吗

**最需要懂设备的人回答**：

| 问题 | 影响 |
|---|---|
| `Transfer` 是一次动作还是三次（抓/移/放）？ | 决定 L4 的"动作级"定义 |
| 门的状态真的能靠"动作成功"推断吗？ | 万一机械卡住但返回成功 |
| 宽通道真的能同时过两块板吗？ | 决定 `capacity > 1` 是否有意义 |
| 点位坐标误差有多大？ | 决定要不要加容差校验 |

### ② "粗筛 + 细管"的分工是否合理

**粗筛可以错**（最多等很久或误拒），**细管不能错**（保证不死锁）。

**这个分工的价值**：用户点启动有反馈。
**成本**：多 1.5 周，且粗筛的误拒率没有度量。

**如果客户其实只跑 1-2 个实验**，这套全是白做——
**`lab_profile.max_parallel` 配置项**就是为这个准备的（填 1 就只走设备锁）。

### ③ 界面是否覆盖了真实操作流程

**现在的三个页面**：预检 → 监控 → 暂停处置。

**没覆盖的**：
- 板位盘点（现在只能从暂停队列进）
- 设备故障后的排查指引
- 批量操作（除批量继续外）

### 8.1 最小真机验证清单（R4 评审补）

> 评审 20261102-02 R4 指出：自曝"零真机验证"却不给出路，
> 等于把问题留给读者。这是消除该风险的第一步，**也是排期的前提**。

| # | 验什么 | 怎么验 | 判定标准 | 预估 |
|---|---|---|---|---|
| 1 | **门的开合时间与状态推断** | 真离心机连中控，发 `OpenDoor`，掐表；门被人手动关掉后再发 `Deposit` | 开门 ≤30s；手动关门后系统能拒绝进入而不是撞 | 0.5 天 |
| 2 | **`Transfer` 是一次还是三次动作** | 真机械臂跑一次完整搬运，抓驱动日志看命令条数 | 若是三条独立命令 → L4"动作级"定义要拆，`TransferPlan` 的申请时机要改 | 0.5 天 |
| 3 | **点位坐标与可达性** | 示教 4 个层位，机械臂逐个走到，目测偏差 | 偏差 ≤5mm（否则放板会卡/叠）；`order_in_device` 现场配完能跑通 | 1 天 |
| 4 | **宽通道 `capacity>1` 真实语义** | 找一条多工位通道，同时放两块板 | 能同时过 → 信号量模型成立；不能 → capacity 恒为 1，简化实现 | 0.5 天 |
| 5 | **`estimate_sec` 的真实偏差** | 同一动作跑 10 次，记录实际耗时分布 | 偏差 ≤±30% → 粗筛 `estimatedWait` 有意义；否则只能显示"未知" | 0.5 天 |

**合计 3 天（需设备在场 + 懂设备的人配合）**。
**任何一项不成立，对应的代码要改** —— 这就是为什么清单要真机先行。
