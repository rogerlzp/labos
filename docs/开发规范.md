## 一、分支模型

### 1.1 现实与目标

现状是**所有人直接往 `main` 提交**（人和 agent 都一样）。单人开发时这没问题，但本仓库经常同时有
3~4 个会话在改同一批文件，直接上 `main` 已经造成过两类事故：

- **混提交**：`ddf37b0`（2026-11-15）把「P1 精确点位」和「配置入口页面」两条线的 14 个文件
  合成一个 commit，事后只能靠内容猜归属，评审时说不清。
- **main 不自洽**：`40510a8`（2026-11-17）专门用来「补齐 main 上缺失的被引用文件」——
  因为有人只提交了自己改的文件，main 上缺依赖，干净检出编不过。

### 1.2 规则

| 场景 | 做法 |
|---|---|
| **单人、单会话** | 可以直接提交 `main`，但仍要一次一件事（见提交规范 §一） |
| **≥2 个会话并行**（默认按此处理） | 每人一条 `feat/<主题>-<YYYYMMDD>`，例：`feat/p1-explicit-position-20261115` |
| 修线上问题 | `fix/<问题>-<YYYYMMDD>`；允许从 `main` 拉，修完尽快合回 |
| 纯文档/规范 | 可直接 `main`（冲突面小），但一次只碰一类文档 |

**分支命名**：`<type>/<kebab-主题>-<YYYYMMDD>`，`type ∈ feat|fix|refactor|docs|test`。
主题用英文小写短横线，日期用**动手那天**（不是合并日）。

### 1.3 合并

```bash
git fetch origin
git rebase origin/main          # 先把分叉抹平，冲突在自己分支上解决
./scripts/test-all.sh --pure-only   # 或按测试总纲跑与改动相关的门禁
git checkout main && git merge --squash feat/xxx-20261115
git commit                      # message 按提交规范写，正文标分支来源
git push origin main
```

- **squash 合并**：一条分支只留一条 commit。分支内的「修编译」「再修一下」不该进 main 的历史。
- **禁止 force-push `main`**。已推送的 commit 有问题，用新 commit 修，不要改写历史
  （会打断其它会话的推送 —— 提交规范 §九已记录过一次事故）。
- **合并前必须 rebase**：main 上直接 merge 会留下大量分叉线，`git log --graph` 没法看。

### 1.4 main 的准入（最低要求）

1. **干净检出能编译**：`bash scripts/compile-kernel.sh`（或 `build-kernel.sh`）在有 `lib/` 的完整检出上 exit 0。
   > 缺文件导致的"只有作者本地能编过"是本仓库最贵的一类问题（`40510a8`）。
2. **门禁不被自己弄红**：至少跑与改动相关的门禁，命令与结果写进 commit 正文（提交规范 §4.3）。
3. **文档与代码同批**：改了行为就改文档，改了文档就核对数字（提交规范 §6.1）。

## 二、代码纪律

### 2.1 先盘点，再动手（本仓库最容易犯的错）

**加功能前先问"库里/代码里是不是已经有了"**。真实教训：给新设备建型号配置时，
准备新建 4 张表（型号/方法/错误码/画像），盘点 `information_schema` 后发现
`device` / `device_method` / `error_code` / `recovery_policy` / `duration_model` **全都在**，
其中 `device_method` 已经有 `device_id` 外键和 `UNIQUE(device_id, method)` ——
新建表纯属重复造轮子。

盘点手段：

```sql
-- 有哪些表
SELECT table_name FROM information_schema.tables WHERE table_schema='public' ORDER BY 1;
-- 某类表的结构
SELECT column_name, data_type FROM information_schema.columns
 WHERE table_name='device_point' ORDER BY ordinal_position;
-- 有没有重复的逻辑：grep 关键词
grep -rn "slot_index\|slotIndex" labos-kernel/src webapp/src | head
```

### 2.2 编译：**不要覆盖 `out/`**

`out/` 是**线上内核正在用的 classpath**（`scripts/start-kernel.sh` 直接 `-cp out`）。
验证性编译一律输出到隔离目录：

```bash
cd labos-kernel
rm -rf /tmp/labos-tc && mkdir -p /tmp/labos-tc
find src/main src/boot/java -name '*.java' | LC_ALL=C sort > /tmp/a.txt
javac -encoding UTF-8 -parameters -d /tmp/labos-tc \
      -cp "out:lib/postgresql-42.7.3.jar:lib/spring/*" @/tmp/a.txt
```

只有**确定要重启内核**时，才通过 `scripts/build-kernel.sh` 更新 `out/`。

### 2.3 注释写「为什么」，不写「做了什么」

```java
// ✗ 废话
// 设置 slotIndex
state.slotIndex = idx;

// ✓ 写清楚为什么需要它、不这么做会怎样
// 槽位号与 gridRow/gridCol（几何排布）、orderInDevice（加载顺序）**正交**：
// 槽位号是「第几个坑」这个稳定事实，搬板换板都不变，页面与搬运参数都按它寻址。
// 老点位（P1 之前建的）为 null —— 前端回退显示 code。
```

判断标准：三年后接手的人看注释，能不能知道**当时为什么排除另一种做法**。

### 2.4 边界与依赖

- **kernel 不引入框架依赖**（`CONTRIBUTING.md` 明令）：Spring 只在 `src/boot`，`src/main` 保持可裸跑。
- **协议适配器独立进程**：设备协议细节不写进 kernel，走 sidecar / 驱动进程。
- 新公共常量/枚举，先找既有位置（`RuntimeSettings`、`capability` 表、`DeviceModels`），不要再起一套。

### 2.5 门禁的「假红」陷阱

在**副本目录**跑门禁会假红：`test-sidecar*.sh` 找不到 `sidecar-dotnet/`（副本只拷了 `labos-kernel/`），
报 `No such file or directory`。这类失败**不是代码回归**，报告时必须写明"副本缺什么"，
不能笼统说"测试挂了"，也不能为了变绿去改测试。

## 三、数据库纪律

### 3.1 迁移文件

| 项 | 规则 |
|---|---|
| 位置 | `pg_rebuild/migration/YYYYMMDD_<snake_主题>.sql` |
| 幂等 | 必须可重复执行：`IF NOT EXISTS` / `DO $$ ... duplicate_object` / `ON CONFLICT DO NOTHING` |
| 事务 | apply 时用 `psql -1 -v ON_ERROR_STOP=1 -f <file>`（要么全成，要么全不动） |
| 合并 | 结构性变更同时更新 `pg_rebuild/schema/90_all_in_one.sql`（建库产物要自洽） |
| 现场数据 | seed 用 `ON CONFLICT DO NOTHING`，**不覆盖现场改过的值**；补丁式更新用 `WHERE ... IS DISTINCT FROM` |

### 3.2 不写假数据

**统计类表不许编初值**。例：`duration_model`（方法 → p50/p90/min/max/sample_count）是**实测统计**，
没有真实执行就留空，让它在跑的过程中自然累积 —— 编一个"看起来合理"的初值，
等于让后面所有容量分析都建在假数据上。

同理：`device_state.online` 这类**运行态**，只能由 sidecar/心跳写，**不许用脚本刷**。
本项目出现过 `/tmp/refresh-labos-links.sh` 手工刷 12 台设备的 `labos:link:*` key 的 workaround，
它掩盖了"sidecar 已经挂了"的事实（停掉 sidecar 设备仍显示在线），排查了半天。
⇒ **任何这类 workaround 必须登记在开发日志，并写清"何时可以删"**。

### 3.3 造数要撞约束，不要绕

造测试数据时撞到 CHECK 约束（如 `ck_device_point_deck_in_unreachable`：`deck_in` ⇒
`robot_reachable=false` 且 `role='internal'`），**说明约束表达的是业务事实**（内部操作位由设备自己搬、
机械臂只到交换位），应当按事实造数，而不是改成 `true` 绕过去。

### 3.4 生产库操作

- 只读查询随便跑；**写操作**（UPDATE/DELETE/DDL）先说明、再执行。
- 清理运行态数据（如僵尸 `paused` run）用**接口**而不是裸 SQL：
  `POST /api/runs/dismiss {"runIds":[...]}`（落 `aborted + EC-HUMAN-DISMISS`，有审计）；
  裸 `UPDATE run SET status='aborted'` 会绕开暂停事件与审计。
- 注意同名不同义的入口：`POST /runs/{id}/dismiss` 只处理"崩溃可恢复"记录，对普通 paused 返回
  `{"dismissed":false}` —— 清暂停队列要用批量那个。

## 四、本机环境纪律

### 4.1 端口分配（本机约定，冲突后果是"设备离线"）

| 段 | 用途 |
|---|---|
| 18080 | 内核（`scripts/start-kernel.sh`） |
| 5432 / 6379 | PostgreSQL / Redis |
| 19500–19512 | 旧演示岛（`ID-*`）模拟器 |
| 19612 | D9608-1（加液分液） |
| 19620–19623 | P_AUTO-1..4（提取仪） |
| 19624–19629 | DISP1..6（EL406） |
| 19630 / 19631 | ARM1（机械臂）/ STACK1（耗材栈） |
| 19700+ | sidecar 链路端口（`--port`） |

整线启停统一走 `python3 scripts/sim-all.py`（`--status` / `--restart --with-sidecar` / `--stop`）。

### 4.2 重启内核前

```bash
# ① 有没有正在跑的流程（有就先问，别打断别人的会话）
psql -tAc "select count(*) from run where status='running'"
# ② 有几个内核进程（两个内核同时连库会重复调度，是隐患）
ps aux | grep [L]abosApplication
# ③ 停 → 等端口释放 → 起
kill <pid>; lsof -nP -iTCP:18080 -sTCP:LISTEN     # 应为空
nohup bash scripts/start-kernel.sh >> /tmp/labos-kernel.log 2>&1 &
```

**演示/彩排用的开关必须显式传**（默认不传 = 走简化路径）：

```bash
LABOS_TRANSFER_PLAN=1              # 搬运走 TransferPlan：抢位置锁、写 transport_segment
LABOS_TRANSFER_AUTO_CONFIRM=1      # 全局自动确认（不开则每个搬运都停等人工）
LABOS_EXEC_GRAPH=1                 # 图执行
LABOS_AUTH=1                       # 要登录（=0 免登录，仅集成/演示环境用）
```

### 4.3 模拟器 / sidecar

- **在线状态不是 TCP 探测，是 Redis `labos:link:<id>:<ip>:<port>`**（sidecar 每 10s 刷、TTL 30s）。
  只起模拟器不起 sidecar ⇒ 端口在监听、中控也连得上，但 `device_state.online` 恒为 false。
- 模拟器与 sidecar 的启动参数尽量从**中控设备清单**推导（`scripts/sim-all.py` 就是这么做的），
  不要手抄端口/设备 ID —— 抄错的症状是"中控说离线、模拟器说我在跑"。
- 一台设备一个模拟器进程（一个 `DeviceCore` 一个端口），不支持单进程多设备。

### 4.4 不要动别人的在制品

**动手前先 `git status`**。看到不认识的文件被改（并发会话的 WIP），
选一条：① 不碰；② 只在自己文件里改；③ 必须同文件时按 hunk 拆开暂存
（`git diff -U3` → 手工挑 hunk → `git apply --cached`），**绝不整文件 `git add`**。

## 五、文档纪律

1. **开发日志按日期追加**（`docs/开发日志.md`），一篇里写：做了什么、为什么、验证结果、**没做什么**。
2. **"没做的"必须写**。例：P2 五条互锁一行没动，因为库里没有「搅拌 ↔ 分液器」的配对事实源 ——
   没有配对数据就实现等于把关系硬编码，评审无法核对。这句话比"已完成"更有价值。
3. **数字必须可核**：写"94/94 通过"就给出 run id（`1001729`）；写"25.9 分钟"就说明怎么算的。
4. **不要用"全部完成"总结部分完成**。用 🟡/⏳ 标出待验证项，并在下一轮把它变成 ✅ 或删掉。
5. 规范类文档互链，不复制内容（复制就会漂移）。

## 六、检查清单

### 动手前

- [ ] `git status` 看清谁在改什么
- [ ] 要加的表/字段/方法在库里、代码里**已经盘点过**
- [ ] 分支：并行会话 ≥2 就开 `feat/<主题>-<YYYYMMDD>`

### 提交前

- [ ] 一次提交一件事（用「和」连接两个改动 → 拆开）
- [ ] `git diff --cached --stat` 里没有别人的文件
- [ ] 编译验证输出到 `/tmp`，没覆盖 `out/`
- [ ] 验证命令与结果写进正文
- [ ] 改了行为 → 文档同批；没做的写进"已知问题"

### 合并 / 推送前

- [ ] `git fetch && git rebase origin/main`
- [ ] 干净检出能编译（缺文件的提交会卡住别人）
- [ ] 与改动相关的门禁跑过，假红要说明原因
- [ ] 不 force-push `main`

### 环境操作前

- [ ] 重启内核前查 `running` 数与内核进程数
- [ ] 演示/彩排开关（`LABOS_TRANSFER_PLAN` / `AUTO_CONFIRM`）显式传
- [ ] 模拟器 + sidecar 一起起（`sim-all.py --with-sidecar`）
- [ ] 手工 workaround（刷 Redis、改库状态）已登记到开发日志
