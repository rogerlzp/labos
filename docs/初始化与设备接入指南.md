## 1. 四层数据模型

```
resource_node（资源树，决定"在哪"）
  ├─ kind=island          岛屿      26 个
  │    └─ kind=device     设备      239 个
  │         ├─ kind=incubator      培养箱位   1,021 个
  │         ├─ kind=storage        存储位     1,122 个
  │         └─ kind=transfer_point 转运点       420 个
  │
device（型号字典，决定"是什么"）          59 种
  └─ code=X173  name=Incubator_2C-1
       └─ capability_id → 能做什么

device_instance（实例，决定"哪一台、连哪里"）  239 个
  ├─ device_id     → 型号
  ├─ resource_id   → 在资源树上的位置
  ├─ ip            → 设备 IP（176 个有值，63 个空）
  └─ driver_id     → 连哪个驱动端点（**目前全空**）

driver（驱动端点，决定"说哪种话"）        13 个
  ├─ endpoint = tcp://192.0.2.10:8501
  ├─ protocol = netdll / tcp
  └─ manifest = 能力清单 + 分隔符 + 设备数
```

**一句话**：`resource_node` 说位置，`device` 说型号，`device_instance` 说这台机器连哪个 IP，`driver` 说连到哪个服务端口。

## 2. 设备 IP 是干什么用的

### 2.1 真实通信链路

```
内核（Java）
   ↓ TCP + JSON（分隔符 #!LABSEP!#）
驱动服务（.NET，跑在 192.0.2.10:8501）
   ↓ 厂商 DLL / 串口 / 私有协议
设备（培养箱、机械臂、酶标仪…）
```

**关键**：内核**不直接连设备**，只连**驱动服务**。

所以 `device_instance.ip` 的实际用途是：

| 用途 | 说明 |
|---|---|
| **标识归属** | 这台设备接在哪个驱动服务所在网段的机器上 |
| **运维定位** | 现场排查时知道去哪个机柜 |
| **推导驱动端点** | 注释里写的 `"source": "equipment_instance.ip_address + serial_port"` |

**真正决定通信的是 `driver.endpoint`**，不是 `device_instance.ip`。

举例：

```
X173  Incubator_2C-1   ip=192.0.2.10  →  驱动 DRV-19200200196-8501
                                                endpoint=tcp://192.0.2.10:8501
```

设备 IP 和驱动 IP 在同一个网段，但不是同一个东西——一个驱动服务通常管一个岛上的十几台设备。

### 2.2 现有 13 个驱动端点

| 端点 | 设备数 | 能力数 |
|---|---:|---:|
| `tcp://192.0.2.10:8501` | 121 | 13 类 |
| `tcp://192.0.2.3:8500` | 11 | 3 类 |
| `tcp://192.0.2.10:8502` | 2 | 0 |
| …共 13 个 | 239 | |

## 3. 从零初始化：六个步骤

### 步骤 1：建岛屿

```sql
INSERT INTO resource_node (tenant_id, code, name, kind, path, sort_order)
VALUES (1, 'LAB-A', 'A 实验室', 'island', '/LAB-A', 10)
RETURNING id;
```

界面上对应「运维 → 设备与岛屿 → 新增岛屿」（**待开发**）。

### 步骤 2：建设备型号（如果库里已有就跳过）

```sql
INSERT INTO device (tenant_id, code, name, model, vendor, device_type, capability_id)
SELECT 1, 'Incubator_2C', '2℃ 培养箱', 'X173', 'LabOS', 'Incubators', c.id
FROM capability c WHERE c.code = 'INCUBATE' AND c.tenant_id = 1;
```

**如果这台机器在型号库里登记过**（`s100` / `aspin-2k`），把型号 id 写进 `attr`：

```sql
UPDATE device SET attr = attr || '{"device_model":"s100"}'::jsonb WHERE code = 'Sealer_1';
```

不写也能跑，但设备报的错误码会**原样透传**（`0x8000000C`），
`recovery_policy` 查不到策略 ⇒ 所有故障都变成"未知错误，转人工"。
原理见 [`设备/型号库与错误码映射.md`](设备/型号库与错误码映射.md) 第四节。

### 步骤 3：建设备实例（挂到岛上，填 IP）

```sql
-- 先在资源树上建"设备节点"
INSERT INTO resource_node (tenant_id, parent_id, code, name, kind, path)
VALUES (1, :island_id, 'X173', 'Incubator_2C-1', 'device', '/LAB-A/X173')
RETURNING id;   -- 记为 :resource_id

-- 再建设备实例
INSERT INTO device_instance
  (tenant_id, code, name, device_id, resource_id, ip, driver_id)
VALUES (1, 'X173', 'Incubator_2C-1', :device_id, :resource_id,
        '192.0.2.10', :driver_id);
```

### 步骤 4：建驱动端点

```sql
INSERT INTO driver (tenant_id, code, name, version, protocol, endpoint, manifest)
VALUES (1, 'DRV-19200200196-8501', '驱动服务 192.0.2.10:8501', '1.0', 'netdll',
        'tcp://192.0.2.10:8501',
        '{"tcp_delimiter":"#!LABSEP!#","driver_kind":"dotnet-dll"}'::jsonb);
```

### 步骤 5：验证连通（影子探针）

```bash
# 登录拿 token
TOKEN=$(curl -s -X POST http://localhost:18080/api/auth/login \
  -d '{"username":"admin","password":"admin123"}' | jq -r .token)

# 对一台设备发单条命令，看契约对不对
curl -X POST "http://localhost:18080/api/shadow/probe?resourceId=200173&method=OpenDoor" \
  -H "Authorization: Bearer $TOKEN"
```

返回：

```json
{
  "ok": true,
  "elapsedMs": 83,
  "contract": { "messageId": true, "messageType": true,
                "method": true, "methodStatus": true },
  "rawResponse": "{\"message_id\":\"...\",\"message_type\":5,...}"
}
```

**契约 4 个字段全 true 才算接通。** 有 false 说明驱动返回格式不符，要么改驱动，要么改适配层。

### 步骤 6：建流程

两条路：

| 方式 | 适合 | 操作 |
|---|---|---|
| **设计器拖拽** | 新流程 | 「编排 → 流程库 → 新建」→ bpmn-js 画 → 保存 |
| **导入流程 XML（初始化数据）** | 初始化 | 直接 `INSERT INTO workflow (graph)` |

流程节点建好后，**预检**会告诉你能不能跑：

```bash
curl "http://localhost:18080/api/workflows/{id}/preflight" -H "Authorization: Bearer $TOKEN"
```

## 4. 现状差距（诚实清单）

| # | 缺口 | 影响 | 优先级 |
|---|---|---|---|
| 1 | **`device_instance.driver_id` 全空** | 运行时靠"所有设备挂同一个驱动"兜底；多驱动场景会连错 | **P0** |
| 2 | **63 台设备没有 IP** | 无法定位到机柜，多驱动时无法推导端点 | P1 |
| 3 | **驱动端点只能改 `appsettings.json`** | 运维改端点要动配置文件+重启 | P1 |
| 4 | **没有"新增设备"界面** | 只能写 SQL | P1 |
| 5 | **没有"新增岛屿"界面** | 只能写 SQL | P1 |
| 6 | **驱动能力 `manifest` 是导入时算的** | 现场加设备后不更新 | P2 |

### 缺口 1 的具体影响

现在 `buildDriverRegistry()` 是这么做的：

```java
// 所有设备都挂到同一个 mock/tcp 驱动上
DriverDescriptor desc = new DriverDescriptor("DRV-LOCAL-MOCK", "tcp://127.0.0.1:" + port, ...);
reg.register(adapter);
```

**没读 `device_instance.driver_id`**。所以：

- 只有 1 个驱动端点时，能正常工作
- 有 13 个端点时，**没法把设备路由到正确的端点**

这是上现场的**第一道坎**。

## 5. 上现场的执行顺序

```
第 1 天  改 appsettings.json 的 5 个端点 → 起 Sidecar
         ↓
第 2 天  逐台影子探针，验证契约（13 个端点 × 每个端点抽 1-2 台设备）
         ↓
第 3 天  补 device_instance.driver_id 的关联（写 SQL 或做界面）
         ↓
第 4 天  跑一条真实工艺（挑节点少的，如 239 的 2 节点）
         ↓
第 5 天  跑并行流程（193 个里挑一个），确认两条分支都执行
```

---

## 6. 一句话总结

> **设备 IP 只是标识和运维定位，真正通信走 `driver.endpoint`。**
> **现在最大的缺口是设备和驱动端点没关联（`driver_id` 全空），单驱动能跑，多驱动会连错。**

## 附：常用查询

```sql
-- 某个岛上的所有设备（含 IP 和驱动端点）
SELECT i.name AS 岛屿, d.code AS 设备, d.name AS 名称,
       di.ip, dr.endpoint AS 驱动端点
FROM resource_node i
JOIN resource_node d ON d.parent_id = i.id AND d.kind = 'device'
LEFT JOIN device_instance di ON di.resource_id = d.id
LEFT JOIN driver dr ON dr.id = di.driver_id
WHERE i.kind = 'island'
ORDER BY i.code, d.code;

-- 哪些设备没配 IP
SELECT code, name FROM device_instance WHERE ip IS NULL OR ip = '' ORDER BY code;

-- 哪些设备没关联驱动
SELECT count(*) FROM device_instance WHERE driver_id IS NULL;
```
