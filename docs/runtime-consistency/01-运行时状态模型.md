# 01 · 运行时状态模型（第一版 · 供评审）

> 阶段二「运行时一致性与设备执行闭环」的第一份设计文档。
> 目标：先把「几层状态各是什么、谁写、怎么从事实推导」讲清楚，**不写代码**。
> 基线：`main` @ `8a86ce7`。上游依据：`docs/architecture/LABOS_STATE_MACHINE_MULTILAYER_20261107.md`、
> `LABOS_PAUSE_AND_INTERVENTION_STATE_MODEL_20261107.md`、`ADR-PAUSE-008`（`control_state`）。

---

## 0. 一句话

LabOS 现在的核心矛盾不是「功能不够」，而是**软件命令成功 ≠ 设备执行成功 ≠ 物料到位**。
本设计把运行态拆成五层，明确每一层的「事实来源」与「投影规则」，并规定：
**任何跨层状态推进，都必须以「设备/物理确认」为事实，软件状态只能是投影。**

---

## 1. 五层状态（事实 vs 投影）

| 层 | 事实来源 | 中控里的投影 | 谁写 |
|---|---|---|---|
| L1 实验状态 | 所有 run 的聚合（D6） | `experiment.status` | 聚合器（投影，非直写） |
| L2 run 状态 | run 内节点的聚合 | `experiment_run.status` + `run.status` | 执行器/协调器 |
| L3 节点状态 | 步骤执行结果 | `run_node.status` + `execution_phase` | StepSink |
| L4 命令状态 | **设备回包**（sent→received→executing→done） | `run_command.status`（目前只有 INSERT，无 UPDATE） | CommandLedger |
| L5 物理状态 | **设备/传感确认**（板到位、门开、臂停） | `position_state` / `plate.position_status` / `device_state` | 搬运事务 + 确认链 |

**核心原则：上一层只能是下一层的投影，不能越过下一层直接断定。**

例：`run.status='paused'` 只有在「当前命令收到设备确认已停」（L4）或「超时且无法确认（L5 UNKNOWN）」之后才能成立；
不能因为「中控发了暂停命令」就把 run 写成 paused。

---

## 2. 暂停状态机（第一版提案）

> 对应评审里那张 mermaid：Running → PauseRequested → Pausing → Paused，另有 PauseUnknown。

```
Running ──(发出暂停命令)──▶ PauseRequested
   │                          │
   │                    (设备确认已暂停)
   │                          ▼
   │                        Paused ◀──(查询确认已暂停)
   │                          ▲
   │                    (设备报告仍在运行 / 超时无法确认)
   │                          │
   └──────────────────────────┴──▶ PauseUnknown（需人工查询/对账）
```

| 状态 | 含义 | 进入条件 | 可退出到 |
|---|---|---|---|
| `Running` | 正常执行 | 启动/恢复确认 | PauseRequested |
| `PauseRequested` | 中控已发暂停命令，**设备尚未确认** | 操作员点暂停 | Paused / PauseUnknown |
| `Paused` | **设备确认已停**，run 停止 | L4 收到确认 / L5 查询确认 | Running（恢复） |
| `PauseUnknown` | 超时/通信异常，**物理状态不可知** | 确认超时 / 回包矛盾 | Paused / Running（人工对账后） |

**与现状的映射**：现有 `control_state ∈ {NONE, PAUSE_REQUESTED, PAUSING, RESUMING}`（ADR-PAUSE-008）
已具备「请求→暂停中」的中间态雏形；缺的是 **`PAUSED` 之前的「设备确认」这一环**——
当前 `RunControl.pause()` 直接写 `experiment_run.status='paused'`，把「发了命令」当成了「已暂停」。

## 3. 七个必须裁决的问题（评审提出，第一版建议）

| # | 问题 | 第一版裁决建议 |
|---|---|---|
| 1 | 命令发送成功 ≠ 设备执行成功 | 拆两层：`run_command.status`（sent/received/executing/done）+ `execution_resolution`（completed/failed/unknown）。只有 done+completed 才算成功。 |
| 2 | 暂停等待期间，当前节点是否仍占设备 | **仍占**。节点在收到「确认已停」前保持 `execution_phase='DISPATCHING'`、设备锁不释放；否则别的实验会抢进还在动的设备。 |
| 3 | 设备上一命令未结束时能否接受新命令 | **默认拒绝**。以 `device_state.current_run_id` + `run_command` 未 done 为准；只有 abort/cancel 这类控制命令例外。 |
| 4 | 超时后如何查询真实状态 | 引入「状态查询」命令（设备侧 QueryStatus / 心跳里带回当前命令状态），超时后**必须查询**，查不到才落 UNKNOWN。 |
| 5 | 重复发送命令如何幂等 | 命令账本以 `(run_id, node_key, attempt, loop)` 幂等键 + `command_id`；重发复用同一 command_id，设备侧去重。 |
| 6 | 设备报告与中控内部状态冲突，以谁为准 | **设备报告为准**（物理事实），中控状态回写为投影；冲突时落 `InterventionRecord` + 转人工，不自动覆盖。 |
| 7 | 实验/节点状态的事务与事件顺序 | 事件（append-only `run_event`）先落，状态是事件的投影；状态更新与事件落库同一事务，避免「事件有了、状态没跟上」。 |

## 4. 物料位置一致性（评审特别强调）

- **软件命令成功 ≠ 物料到位**。`position_state` 的 `occupied_by_run` 只能由「搬运事务确认」写，不能由「命令 done」写。
- 现状 `TransferTransaction` 已区分「运动报告」与「位置确认」（`confirmByDeviceReport`），这是对的；
  缺口是**没有把「未确认的位置」作为一等状态**暴露给调度/暂停判断。
- 第一版建议：`plate.position_status` 增加 `IN_TRANSIT_UNCONFIRMED`（已发命令、未确认到位），
  调度器/暂停在涉及该板时必须先确认，否则转人工。

---

## 5. 一致性的四条铁律（写进后续 02-05 的公共前提）

1. **事实单写者**：每张状态表的每个字段只有一个写入类（延续 S-03 的 `ExperimentStateProjector` 单写者约定）。
2. **命令-确认两段**：任何物理动作 = 「发命令」+「收确认」两段，中间态不可忽略。
3. **UNKNOWN 是合法终态**：确认不到就落 UNKNOWN + 转人工，禁止默认「当它成功」或「当它失败」。
4. **恢复走对账**：重启/断连后，先对账（设备查询 + 位置盘点）再推进，不靠内存残留推断。
