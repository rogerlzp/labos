# 03 · 实验与节点状态一致性（第一版 · 供评审）

> 接 `01`/`02`。本文讲 L1-L3（实验 / run / 节点）之间的投影规则、事务边界、事件顺序。
> 不改代码。

---

## 0. 现状一句话

L1/L2/L3 的投影目前是**散落的 SQL CASE + 直接 UPDATE**（`StatusVocabulary.runToExperimentCaseSql()`、
`ExperimentExecutor.syncExperimentStatus`、`BatchOrchestrator` D6 聚合各自回写）。
两套暂停模型（`run` vs `experiment_run`）并存，靠约定衔接。本文不要求立刻合并两套模型，
只先定「投影的方向与时机」，合并留给实现期。

---

## 1. 投影链（谁决定谁）

```
L5 物理状态（事实）
   │ 确认
   ▼
L4 命令状态（事实：设备回包）
   │ 确认
   ▼
L3 节点状态（投影：run_node.status + execution_phase）
   │ 聚合
   ▼
L2 run 状态（投影：experiment_run.status / run.status）
   │ 聚合（D6）
   ▼
L1 实验状态（投影：experiment.status）
```

**只允许向下依赖，不允许向上回写。** 上层状态 = 下层事实的聚合函数，不是独立的事实。

---

## 2. 节点状态（L3）的收敛规则

| run_node.status | 由什么决定 |
|---|---|
| `pending` | 已建壳，未到边界 |
| `running` | 进入 `WAITING_RESOURCE` 或 `DISPATCHING` |
| `completed` | L4 全部步骤 `DONE` 且 `resolution=completed` |
| `failed` | L4 某步 `DONE` 且 `resolution=failed` |
| `manual` | 转人工（含 L4 `UNKNOWN`、扫码不匹配、板位未知） |
| `skipped` | 断点续跑明确跳过（板位不可信时**禁止**自动 skipped） |

**铁律**：`manual` 与 `UNKNOWN` 同义优先——凡物理状态不可知，L3 一律 `manual`，不自动 `failed`/`completed`。

---

## 3. 事件顺序与事务边界

1. **事件先落，状态后投**：任何状态变化先写 append-only `run_event`（事件 = 发生了什么事实），
   状态表是事件的投影。
2. **同一事务**：事件落库与对应状态投影必须在同一事务，避免「事件有了、投影没跟上」。
3. **投影只写一次**：`ExperimentStateProjector`（S-03 单写者）是唯一写 `experiment.status` 的类；
   同理收口 L2/L3 的写入口，禁止散落 UPDATE。

---

## 4. 两套暂停模型的收口策略（不在本阶段合并）

| 现状 | 目标 |
|---|---|
| `run.status='paused'` 与 `experiment_run.status='paused'` 各自直写 | 两者都是「设备确认已停」这一事实的投影 |
| `PauseManager` 写 run，`RunControl` 写 experiment_run | 统一协调器收口（实现期） |
| 靠 `RuntimeHold.Kind.of()` 兼容两套 code | 一个 `pause_kind` 词表 |

本阶段只确认一件事：**暂停的判定统一收敛到 01 §2 的状态机**（发了命令 ≠ paused），
两套表怎么合并是实现期细节。

---

## 5. 本版不做什么

- 不合并两套模型、不新增聚合器代码。
- 不决定 `run_event` 的字段结构（那是实现期 + 05 的恢复协议）。
- 不写 `experiment.status` 的最终 CASE（沿用现有 `StatusVocabulary`，只定「投影方向」）。
