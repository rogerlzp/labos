# 02 · 设备命令生命周期（第一版 · 供评审）

> 接 `01-运行时状态模型.md`。本文只讲 L4（命令状态）——「命令从发出到确认完成」的完整状态机。
> 不改代码。

---

## 0. 要解决的问题

现状里 `run_command` **只有 INSERT、没有 UPDATE**（见 `LABOS_STATE_MACHINE_MULTILAYER_20261107.md` §1 的写入点统计）：
命令发出那一刻落一行，设备回包后才回填结果。于是「已发出」与「设备已收到/正在执行/已完成」之间
**没有任何可观测的中间态**。

后果（评审已点名）：
- 「发了暂停命令」被当成「已暂停」；
- 超时后不知道命令到底执行了没有；
- 重复发送没有幂等锚点；
- 设备断连后，中控不知道「最后一条命令」处于什么状态。

---

## 1. 命令生命周期（五态 + 一个 UNKNOWN）

```
PENDING ──(已入 Outbox，未下发)──▶ SENT
  SENT ──(设备回 ACK=收到)──▶ RECEIVED
  RECEIVED ──(设备回「执行中」)──▶ EXECUTING
  EXECUTING ──(设备回「完成/失败」)──▶ DONE
  任意态 ──(超时 / 断连 / 回包矛盾)──▶ UNKNOWN
```

| 态 | 含义 | 谁写 | 依据 |
|---|---|---|---|
| `PENDING` | 命令已生成，尚未派发 | CommandOutbox | 入队 |
| `SENT` | 已发给设备，未确认收到 | 驱动 | 发送动作 |
| `RECEIVED` | 设备确认收到 | 驱动 | 设备 ACK |
| `EXECUTING` | 设备确认开始执行 | 驱动 | 设备执行回包 |
| `DONE` | 设备确认执行完（成功或失败） | 驱动 | 最终回包 |
| `UNKNOWN` | 无法确认（超时/断连/矛盾） | 恢复器 | 对账失败 |

**关键**：`DONE` 还要再分「成功/失败」，落到已有的 `execution_resolution_status`（completed/failed/unknown）；
`UNKNOWN` 是 L4 的合法终态，不等于 failed，也不等于成功。

---

## 2. 幂等（评审问题 5）

- 幂等键：`(tenant_id, run_id, node_key, attempt, loop_index, command_id)`。
- `command_id` 由中控在命令**生成时**分配一次；重发/重试**复用同一 command_id**。
- 设备侧收到相同 `command_id` 时去重（若已 DONE 则直接重放结果，不重执行）。

---

## 3. 超时与查询（评审问题 4）

- 命令超时后**必须先查询真实状态**（设备侧 QueryStatus，或心跳回包顺带当前命令状态），
  查不到或设备无响应才落 `UNKNOWN`。
- 落 `UNKNOWN` 的同时：写 `InterventionRecord` + 转人工（人工窗口），**禁止自动重试或自动跳过**。
- 现有「故障且不可达设备不参与执行」的排除逻辑（P-18）与此一致，应作为 UNKNOWN 的一个消费方。

---

## 4. 控制命令 vs 业务命令（评审问题 3）

- 业务命令（RunProgram、Transfer…）：设备上一命令未 `DONE` 时，**默认拒绝新命令**。
- 控制命令（Abort、Cancel）：允许打断，但打断后同样要确认「设备已停」（回到 01 的暂停状态机）。

---

## 5. 与 L1-L3 的衔接

- L3（节点）的 `execution_phase` 与 L4 对齐：
  `WAITING_RESOURCE → DISPATCHING(=SENT/RECEIVED/EXECUTING) → FINALIZING(=DONE/UNKNOWN)`。
- L2（run）的「暂停」只有在 L4 到达「设备确认已停」之后才写 `paused`（见 01 §2）。
- L1（实验）永远是 L2 的投影。

---

## 6. 本版不做什么

- 不设计设备侧协议细节（那在 05 恢复协议里）。
- 不改 `run_command` 表结构（实现期再加 `command_id`/状态列或新表）。
- 不决定「UNKNOWN 后人工窗口的默认动作」——那是 05 + 人工窗口设计的范围。
