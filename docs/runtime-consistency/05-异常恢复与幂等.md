# 05 · 异常恢复与幂等（第一版 · 供评审）

> 接 `01`-`04`。本文讲「系统重启、设备断连、命令重复、执行超时」之后怎么恢复到一致状态。
> 不改代码。

---

## 0. 总原则

**恢复 = 对账，不是推断。**
重启/断连后，中控的内存态不可信，必须回到「库里的事实 + 设备查询」重新对账，
再决定推进方向。凡对账不到的都落 `UNKNOWN` + 转人工。

---

## 1. 系统重启

> **评审修正（2026-11-14）**：原顺序「rehydrate → 扫锁 → 对账」有事件顺序缺陷——
> rehydrate 跑在对账之前，重启前在途命令还没查清，队列里的 run 就可能往设备派发新命令，
> 违背「先对账再推进」总原则。改为**先对账、后 rehydrate**。

| 步骤 | 动作 | 依据 |
|---|---|---|
| 1 | 进入 reconciling 阻断态 | 重启后先不派发（新命令一律挂起） |
| 2 | 对账在途命令 | 对 `run_command` 非终态 + `run_node.running` 的行，逐条向设备查询真实状态 |
| 3 | 对账物料位置 | 对 `plate.position_status != KNOWN` 的板，走盘点（查询/扫码） |
| 4 | 清扫泄漏锁 | 过 TTL 的资源锁/设备锁回收（现状 `sweepExpiredLocks`） |
| 5 | rehydrate 队列 | 对账完成后，`queued` 的 run 重新入队（现状已有） |
| 6 | 解除 reconciling，恢复派发 | 能确认的续跑；确认不到的转人工 |

**禁止**：重启后直接按内存里的「上次跑到哪」续跑——那是在用不可信状态推断事实。

---

## 2. 设备断连

- 断连期间：该设备的命令一律不派发（现状 P-18「故障且不可达」已排除）。
- 恢复上线后：先对账「最后一条命令的状态」（设备侧查询），再决定续跑/重试/转人工。
- 心跳恢复（`paused_fault` 自动恢复）与命令对账是两件事：设备在线 ≠ 上一条命令执行成功。

---

## 3. 命令重复 / 重试

- 幂等锚点：`command_id`（中控生成一次，重试复用，见 02 §2）。
- 重试只在「命令 `UNKNOWN` 或 `SENT` 未确认」时允许；`DONE` 后禁止重试（重放结果而非重执行）。
- 物理副作用只发生一次：靠命令账本的幂等键 + 设备侧去重保证（现有 `run_command` 幂等键已有雏形）。

---

## 4. 执行超时

- 超时 → 先查询（见 02 §3）→ 查不到才 `UNKNOWN`。
- `UNKNOWN` 的处理：写 `InterventionRecord` + 转人工，**禁止自动重试或自动跳过**。
- 超时期间节点仍占设备（01 §3 问题 2），直到对账出结论才释放。

---

## 5. 状态冲突

- 设备报告 vs 中控状态冲突：**以设备报告为准**，中控回写为投影（01 §3 问题 6）。
- 冲突落 `InterventionRecord` + 转人工，不自动覆盖任何一侧。

---

## 6. 本版不做什么

- 不设计设备侧协议（QueryStatus 的具体报文）。
- 不决定 `UNKNOWN` 人工窗口的默认动作/超时策略。
- 不改任何恢复代码（实现期 + 06 验收之后）。
