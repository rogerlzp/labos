# 06 · 端到端验收方案（第一版 · 供评审）

> 接 `01`-`05`。本文定义五组端到端场景的验收判据——不再只验单个 API，而是验完整实验。
> 不改代码。

---

## 0. 验收口径

每条场景都要答三个问题：
1. **实验状态**最终是否落在正确终态？
2. **节点状态**是否与命令/物理事实一致（没有「发了命令就写 completed」）？
3. **物料位置**是否与物理事实一致（没有「命令成功就写到位」）？

---

## 1. 场景一：正常实验

启动 → 设备执行 → 物料移动 → 结束。

| 判据 | 期望 |
|---|---|
| 实验状态 | `completed` |
| 每个节点的 `run_command` | `DONE` 且 `resolution=completed` |
| 物料位置 | 搬运后 `KNOWN`（有确认），不是 `IN_TRANSIT_UNCONFIRMED` |
| 事件顺序 | 每个节点「命令 done → 节点 completed → run completed → 实验 completed」 |

---

## 2. 场景二：中途暂停

| 步骤 | 判据 |
|---|---|
| 发暂停 | `control_state=PAUSE_REQUESTED`，节点仍 `DISPATCHING`，**设备锁不释放** |
| 设备确认已停 | run→`Paused`（`01 §2`）；L3 **不转 `manual`**（物理状态已知），设备锁释放 |
| 设备未确认（超时） | 节点→`manual` + `PauseUnknown`，转人工，**不写 paused** |
| 恢复 | 对账后从断点续跑，不重复已完成的物理动作 |

**核心断言**：暂停命令发出 ≠ run 立刻 `paused`；必须等到「设备确认已停」或「UNKNOWN 转人工」。

---

## 3. 场景三：设备异常（超时/断连/UNKNOWN）

| 判据 | 期望 |
|---|---|
| 命令超时 | 先查询真实状态，查不到 → `UNKNOWN` |
| `UNKNOWN` | 节点→`manual` + `InterventionRecord` + 人工窗口，不自动 failed |
| 断连恢复 | 先对账最后一条命令，再决定续跑/重试/转人工 |
| 状态冲突 | 设备报告为准，中控回写投影，转人工不自动覆盖 |

---

## 4. 场景四：物料异常（位置不符/板型不匹配/搬运失败）

| 判据 | 期望 |
|---|---|
| 板型不匹配 | 拒搬，板留在装载口（现状 `verify-internal-transfer` 已验） |
| 搬运失败 | 板标 `UNKNOWN` + 封锁可能位置，转人工盘点 |
| 位置不符 | `position_status` 落 `UNKNOWN`，调度/暂停先确认再推进 |

---

## 5. 场景五：系统重启

| 判据（顺序与 `05 §1` 一致，评审修正） | 期望 |
|---|---|
| 进入 `reconciling` 阻断态 | 重启后**不派发**，新命令一律挂起 |
| 在途命令对账 | 非终态命令逐条查询设备，确认/转人工 |
| 物料位置对账 | 非 `KNOWN` 板（含 `IN_TRANSFER`）走盘点 |
| 泄漏锁回收 | **仅回收已确认无在途命令的**过 TTL 锁，不误删他人锁 |
| rehydrate 队列 | 对账完成后 `queued` run 才重新入队 |
| 解除 `reconciling` | 能确认的续跑；确认不到的转人工 |

⚠️ 原表把「队列恢复」放第一步与 `05 §1` 冲突：在途命令未查清就重新入队派发，违背
「先对账再推进」；且泄漏锁必须在对账确认设备已停之后才回收（见 `01 §3-2`、`05 §4`）。

**最终标准（评审原话）**：系统重启、设备断连、命令重复、执行超时，都不能让
实验状态、设备状态、物料位置出现**无法解释的分歧**。

---

## 6. 执行方式

- 每组场景先出「验收脚本骨架」（造数 + 触发 + 断言），由独立评审确认判据后再写实。
- 复用现有 verify 脚本的判别性风格（不只断言 HTTP 200，断言最终状态与中间态）。
- 真实设备闭环（机械臂真动）若当前环境不具备，先以「模拟器 + 状态注入」验证状态机，
  并在报告里明确「物理闭环未覆盖」。

---

## 7. 本版不做什么

- 不写验收脚本（这是实现期的第一步，不是设计期）。
- 不定义每组场景的具体命令序列——评审通过后再细化。
