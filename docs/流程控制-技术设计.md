## 一、问题与边界

改造前，`GraphRunner` 对网关的处理是：

| 构造 | 行为 |
|---|---|
| `parallelGateway` | 分叉激活所有出边；汇合等所有入边到齐（AND） |
| `exclusiveGateway` | **只选一条出边，但条件是"打印一句话然后走 default"** |
| 回边 | `activate()` 里 `if (!done.contains(target))` → 第二圈不入队，循环永远不会发生 |

所以真正缺的是三件事：**表达式求值**、**让 `done` 允许重入**、**变量从哪来**。

设计上刻意划了两条线：

1. **不引入脚本引擎**。表达式来自流程图的用户输入，`ScriptEngine`/`eval` 等于把工控机交出去。
2. **求值失败不阻断生产**。写错的条件 → 记日志 + 走 default，而不是让整单 failed。
   代价是"条件写错不容易发现"，用 `unevaluatedConditionCount` 计数 + 日志补上。

## 二、条件求值器（`engine.ConditionEvaluator`）

### 2.1 语法

```
expr    := or
or      := and ('||' and)*
and     := cmp ('&&' cmp)*
cmp     := unary (('=='|'!='|'>='|'<='|'>'|'<') unary)?
unary   := '!' unary | primary
primary := number | string | 'true' | 'false' | '${变量名}' | '(' expr ')'
```

递归下降实现，约 300 行，零依赖。

### 2.2 类型规则（这里最容易埋坑）

| 场景 | 规则 | 为什么 |
|---|---|---|
| 两边都像数字 | 按 `double` 比 | 否则 `'10' > '9'` 会按字典序判成 false |
| `==` / `!=` | 数字按数值、否则按字符串/布尔 | 允许 `'yes' == 'yes'` |
| 大小比较 | **两边必须都是数字**，否则抛异常 | 不猜 `'abc' > 1` 的语义 |
| 变量不存在 | 取空串 | `${missing} == ''` 成立；`${missing} > 1` 抛异常并点名 |

### 2.3 安全边界

- 词法器只接受 `数字 / 字符串 / true|false / ${...} / 运算符 / 括号`
- 任何多余字符（`;`、函数调用、`Runtime...`）→ `IllegalArgumentException`，**不会被执行**
- 自测里有一条专门的注入用例：`${a} == 'x' ; Runtime.getRuntime().exec('ls')` → 拒绝

## 三、执行引擎改动（`workflow.GraphRunner`）

### 3.1 条件分支

```java
// GraphRunner.choose(outs, gatewayKey)
for (GEdge e : outs) {
    if (e.condition() == null || e.condition().isBlank()) continue;
    try {
        if (ConditionEvaluator.eval(e.condition(), variables)) { conditionHitCount++; return e; }
    } catch (RuntimeException ex) {
        unevaluatedConditionCount++;      // 留痕，不失败
        log("网关 %s 条件求值失败（%s），按默认边处理：%s", ...);
    }
}
// 走到这里：default 边 → 稳定排序第一条（逻辑不变）
```

新增两个计数器（验收/诊断用）：`conditionHitCount()`、`unevaluatedConditionCount()`。

### 3.2 循环（回边）

关键改动：`done` 从"绝对去重"变成"**图里有环时才允许重入**"。

```java
boolean hasCycle = hasCycle(graph);        // DFS 三色标记，run() 开头算一次
...

int visit = visits.merge(key, 1, Integer::sum);
if (done.contains(key) && !hasCycle) continue;   // 无环图：维持原来的去重语义
if (visit > maxVisits) { log("[循环] 达到上限"); continue; }
if (++steps > maxSteps) { log("[循环] 总步数超限"); break; }
```

OR-join 的入队条件同步放宽：

```java
if (!done.contains(edge.to()) || graphHasCycle) ready.add(edge.to());
```

**为什么不无脑允许重入**：并行/异或的重复激活很常见（同一个汇合点被两条边打到），
无脑重入会让设备动作多跑一遍 —— 那是物理副作用。用"图里是否真的存在环"做开关，
把风险限制在"用户明确画了回边"的场景。

### 3.3 变量

```java
private Map<String, String> variables;                 // 可写（节点输出会 merge 进来）
public interface NodeOutputReader { Map<String,String> outputsOf(String nodeKey); }
private NodeOutputReader outputReader = k -> Map.of(); // 默认空实现（单测/批量验收不连库）
```

- 初始化：`WorkflowService` 从 `run.input.vars` 读（实验变量 / `?vars=k=v` 注入）
- 每次任务成功后：`variables.putAll(outputReader.outputsOf(key))`，日志 `[变量] A 输出 {...}`

`WorkflowService.loadNodeOutputs(runId, nodeKey)` 取节点输出，**两个坑**：

1. `run_command` 挂在**步骤节点**（`level=1`，`node_key=S1`）上，业务节点是它的
   `parent_node_id`。只按 `n.node_key=? AND n.level=0` 查**永远查不到** ——
   必须 `LEFT JOIN run_node p ON p.id = n.parent_node_id AND (n.node_key=? OR p.node_key=?)`。
2. `run_command.result` 只有 `{ok,durationMs}`；设备真正的业务字段在
   `device_raw_response` 的 `data` 里（存的是转义过的 JSON 字符串，要先去转义）。

优先读 `device_raw_response`，取不到再退回 `result`。用正则抽顶层标量（字符串/数字/布尔）：
**不做完整 JSON 解析**是有意的 —— 结果体格式随设备变，过度结构化会把解析失败变成执行失败。

### 3.4 分支未选中：`bypassed`

新增 `node_status` 枚举值 `bypassed`（DDL：`ALTER TYPE node_status ADD VALUE 'bypassed'`）。

| 状态 | 语义 | 运行时行为 |
|---|---|---|
| `SKIPPED` | 该做没做，**板位不可信** | `GraphRunner` 立即 `break`，转人工 |
| `BYPASSED` | 异或选了另一条路，这步不用做 | 正常继续 |

标记时机：**整单成功结束后**，把仍挂 `running` 的业务节点（`level=0`）改成 `bypassed`：

```java
// WorkflowService.markBypassedNodes
if (progress.count(MANUAL) > 0 || progress.count(ABORTED) > 0 || progress.aborted()) return;
UPDATE run_node SET status='bypassed', actual_end=now(),
       input = input || '{"reason":"分支未选中（异或网关走了另一条）"}'
 WHERE run_id=? AND level=0 AND status='running';
```

为什么只在成功结束时标：失败/暂停的单子里 `running` 表示"待续跑"，
标成 `bypassed` 会让 `resumeAsync`（按 completed 跳、其余重做）误判。

### 3.5 网关成对与嵌套的判据（2026-11-08 补充）

- **角色由入/出边数决定**：入 > 1 为汇合、出 > 1 为分叉、都 > 1 先等再分、1 进 1 出等价直通；画布上的「建议名」只是命名辅助，执行器不读名字。
- **汇合语义**：并行网关（`JOIN_PARALLEL`）是 AND join——所有入边到齐才推进；非并行汇合（含异或/普通节点）是 OR join——任一条到达即推进，靠 `done` 去重。
- **1 进 1 出网关**：解析器按直通处理、本身不报错，但“画了菱形却什么都不做”是图质量问题；测试侧 `validate_flow()` 已强制禁止，`PreflightChecker` 待补同类告警。
- **嵌套**：引擎按图拓扑执行，允许嵌套；`validate_flow()` 要求内层分叉的每条分支在本分支内收口到同类型 join（异或允许同一 end），建议深度 ≤ 2 层、单图网关对 ≤ 4 对。
- **已知风险**：并行分叉没有显式汇合时，执行队列可能提前空，`settleRun` 仍把 run 标 completed、未走到的节点标 bypassed（4.16 旧图的假绿根因）。所以页面拖图与矩阵造图都必须先过 `validate_flow()` 再执行。
- **待补**：`PreflightChecker` 增加“分叉无汇合 / 1 进 1 出 / 嵌套过深”告警；页面执行入口补 run input 参数表单（当前仅支持 `?vars=` API）。
- **保存侧兜底（2026-11-08 落地）**：`WorkflowService.saveGraph` 非 draft 时校验 start/end 数量、孤立节点、从 start 可达且可达 end；失败抛 `IllegalArgumentException` → API 返回 400（带节点清单）。API `?draft=1` 放行自动化/编辑器中间态；执行前 preflight/compile 仍是第二道闸。

## 四、数据流

```
实验变量 / ?vars=k=v
        │
        ▼
   run.input.vars ──loadRunVars──► GraphRunner.variables
                                        ▲
   run_command.result ──loadNodeOutputs─┘（每次任务成功后 merge）
                                        │
                                        ▼
                              ConditionEvaluator.eval(...)
                                        │
                        ┌───────────────┴───────────────┐
                        ▼                               ▼
                 走条件边（conditionHitCount++）   走 default（unevaluatedConditionCount++）
```

## 六、已知技术债

| # | 债务 | 影响面 | 建议 |
|---|---|---|---|
| 1 | `run_node` 唯一键是 `(run_id, node_key, attempt)`，循环重入走 `UPDATE` 同一行 | 看不到中间圈次 | 按 `(run_id, node_key, attempt, loop_index)` 落行，需要表结构迁移 |
| 2 | 圈数上限是流程级（`attr.maxIterations`），不是网关级 | 一个流程多条回边共用上限 | 从网关节点属性读（需要给 `GNode` 加属性字段） |
| 3 | `loadNodeOutputs` 每次任务一次 DB 查询 | 高频节点有额外延迟（当前 <1ms/次，可接受） | 让 `DriverStepExecutor` 把结果回传给 GraphRunner，去掉查询 |
| 4 | 正则解析 JSON 结果 | 嵌套/数组取值不到 | 引入轻量 JSON path |
| 5 | 条件写错只记日志 | 现场不易发现 | 预检（preflight）里加"条件语法检查" |
