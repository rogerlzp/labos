# LabOS 并行调度架构评审与源码核查清单

- 日期：2026-11-18
- 对象：[并行执行方案-供交叉评审-20261118.md](../并行执行方案-供交叉评审-20261118.md)
- 性质：架构评审结论 + 实施前源码核查任务书；**不是实施设计定稿，也不代表已完成全部源码核查**

## 0. 评审结论

### 0.1 总体裁决

**资源驱动并行方向通过；当前方案不具备直接进入并行度 2 实施的条件。**

主要原因不是缺少线程池，而是现有执行体系已经包含异步调度、资源锁、事件认领、扣留和重启对账能力。若不先完成现状盘点和职责收敛，直接按原方案新增调度器或修改事件消费规则，会形成两套调度状态或错误的事件归属。

| 事项 | 裁决 | 实施约束 |
|---|---|---|
| 资源驱动并行 | 通过 | 作为目标架构 |
| 批次提交改异步 | 有条件通过 | 复用现有调度入口，不另建平行调度器 |
| 统一调度单元为 Run | 有条件通过 | 先澄清 BatchRun、experiment_run、run 的身份和父子关系 |
| 逐节点申请/释放资源 | 有条件通过 | 资源类别分离；全局申请顺序；失败原子回滚 |
| 事件由设备锁持有者消费 | 不通过 | 锁持有不能证明事件业务归属 |
| 立即移除 workflow 级互斥 | 不通过 | 作为迁移保护保留，逐流程/逐设备能力放开 |
| 默认并行度 4 / 每实验 2 | 暂不批准 | 线程容量不等于物理吞吐能力 |
| 并行度 1 兼容 | 强制门槛 | 先证明行为与现状等价 |
| 并行度 2 | 暂不批准 | P0 核查项与门禁测试全部通过后另行批准 |

### 0.2 本次已核对的源码事实

以下是本次评审读取到的源码证据，不等同于完整源码审计：

1. `ExperimentScheduler` 已有固定线程池、内存队列、资源预筛占用表、运行数计数、重启 reconciling 阻断态，以及 queued run rehydrate 机制。
2. `WorkflowRunGate` 已有 workflow 级并发门禁；是否所有执行入口均经过该门禁，仍须全仓核查。
3. `GraphRunner` 的 `__awaitEvent` 已通过 `DeviceEventSource.claim(runId, nodeKey, loopIndex, ...)` 认领事件，并维护设备/事件类型维度的游标。
4. `DeviceEventMapper.xml` 的 `claimEvent` 使用消费记录、唯一约束语义和 `FOR UPDATE SKIP LOCKED` 完成数据库侧原子认领；候选筛选没有以事件记录的 `run_id` 作为消费者归属的强制条件。
5. `GraphRunner` 对事件认领失败有连续失败退出逻辑；事件命中后推进本地游标并写入变量。
6. `PositionLock`、`RailZoneGuard` 等已有资源锁机制；它们的覆盖范围、持久性、跨进程正确性及释放边界尚未由本清单逐方法证明。
7. `ExperimentScheduler` 的 `queue`、`resourceHolds`、`running` 等结构包含内存态；数据库持久状态与内存态之间的恢复一致性需要专项验证。

**重要：原并行方案中“事件等待条件只有设备码 + 事件类型”“线程池固定名为 RUN_POOL”“等事件节点不持锁”等描述，均不能直接作为已核实事实引用。必须按当前代码重新逐项核对。**

### 0.3 架构边界

| 组件 | 应负责 | 不应负责 |
|---|---|---|
| Experiment / Batch 服务 | 接收提交、建立批次及执行尝试、聚合业务状态 | 自行维护第二套资源队列 |
| ExperimentScheduler | 统一排队、优先级、并发额度、派发、重启恢复 | 判断物理事件属于哪块板 |
| Resource Coordinator（目标能力，可由现有组件演进） | 资源需求评估、原子申请、释放、租约、冲突等待 | 推进流程节点 |
| GraphRunner | 执行图解释、分支、变量、节点推进、等待节点语义 | 成为全局资源调度中心 |
| Device Command 层 | 命令创建、下发、幂等键和执行上下文 | 仅凭当前锁持有者推断事件归属 |
| Device Event 层 | 事件接收、关联、认领、去重、重放/恢复 | 将不确定事件强行分配给某个 Run |
| State / Hold / Reconciliation | 状态机、现场扣留、恢复前对账 | 被内存队列状态替代 |

## 1. 源码核查规则

### 1.1 每项核查必须交付的证据

不得只写“已检查”“逻辑没问题”。每个核查项至少记录：

- 当前分支、commit SHA、核查日期；
- 文件路径、类名、方法名、关键代码行或 SQL；
- 调用链：入口 → 服务 → 调度 → 执行器 → 持久化/设备；
- 数据库表、索引、约束、事务边界；
- 并发条件：线程内、进程内、跨进程分别说明；
- 正常路径、异常路径、超时路径、崩溃恢复路径；
- 对应测试名称、测试结果；没有测试必须明确标记；
- 结论只能使用：**PASS / FAIL / UNKNOWN / NOT APPLICABLE**；
- 未核实的推断必须标为 UNKNOWN，不得写成事实。

### 1.2 核查优先级

- **P0**：可能导致重复下发、错板/错 Run 消费事件、资源冲突、物料位置错误、状态误报或恢复后危险动作。
- **P1**：可能导致饥饿、队列失控、暂停/恢复不一致、资源泄漏、可观测性不足。
- **P2**：性能、调度公平性、UI 展示和后续优化。

### 1.3 禁止的核查方式

- 只读设计文档，不追调用链；
- 只读 Java，不核对 Mapper SQL、DDL、索引和事务；
- 只证明单进程测试，不验证数据库跨实例竞争；
- 只测 happy path，不测超时、重复事件、崩溃和恢复；
- 用 mock 资源锁测试替代真实持久化锁语义；
- 将“唯一消费”误当作“业务归属正确”；
- 将“线程池有空闲线程”误当作“物理资源可并行”。

## 2. P0：执行入口与调度体系核查

### 2.1 核查目标

确认系统只有一个权威调度与派发路径。同步入口、异步入口、批次入口、单流程入口、子 Run 入口不能绕过统一门禁或重复建立执行。

### 2.2 必查文件与符号

| 文件/区域 | 必查符号或内容 | 必须回答 |
|---|---|---|
| `labos-kernel/.../workflow/ExperimentScheduler.java` | `submit`、`dispatch`、`executeOne`、tick/loop、rehydrate、pool、running、resourceHolds | 谁入队、谁派发、何时占资源、何时计数、失败如何回滚？ |
| `labos-kernel/.../workflow/BatchOrchestrator.java` | `runAll`、`executeBatch`、批次创建和状态更新 | 是否同步阻塞？是否直接执行而绕开 Scheduler？ |
| `labos-kernel/.../workflow/WorkflowWebService.java` | run/submit/resume/stop 等入口 | HTTP 请求是否只提交请求？哪些入口同步执行？ |
| `labos-kernel/.../workflow/ExperimentExecutor.java` | run、resume、execute 等 | 是否存在第二条执行路径？门禁、Hold、审计是否完整？ |
| 全仓搜索 | `GraphRunner.run`、`ExperimentExecutor`、`BatchOrchestrator`、`submit(`、`new Thread`、Executor 提交点 | 所有执行入口是否被枚举？是否有旁路？ |
| 数据库 Mapper / DDL | `experiment_run`、`experiment_batch_run`、`run` 相关 SQL | queued、running 的唯一权威记录是什么？ |

### 2.3 必须形成的产物

1. 全部执行入口清单（HTTP、内部调用、恢复、定时器、人工操作）。
2. 每个入口的完整调用时序图。
3. 当前同步路径与异步路径的差异表。
4. 统一调度后的唯一状态写入者和唯一派发者定义。
5. 重复提交与并发提交的幂等键设计。

### 2.4 通过标准

- 所有可执行入口均纳入同一套调度门禁；
- 不存在绕开调度器直接启动 GraphRunner 的未受控路径；
- HTTP 提交不因长流程执行而长期阻塞（若产品明确要求同步入口，需单独定义同步等待协议）；
- 同一业务尝试不会被两个入口重复派发；
- 并行度 1 下，批次顺序、停止条件、结果和审计语义与改造前一致。

## 3. P0：Run、Batch 与执行身份核查

### 3.1 必须澄清的实体

当前设计中至少出现以下实体，不能仅用“Run”一词混称：

- Experiment：实验业务对象；
- ExperimentBatch：批次；
- ExperimentBatchRun：批次尝试/重试身份；
- ExperimentRun：实验执行记录；
- Run：流程执行记录，可能有 parent_run_id 和 run_type；
- Node execution / command：节点执行与设备命令身份。

### 3.2 核查问题

1. 每次用户提交是否生成新的 batch_run？
2. batch_run 与 experiment_run 是否一对一、一对多或历史兼容关系？
3. experiment_run 与 run 无外键关系时，依靠什么不可变关联键追溯？
4. 子 Run 的 parent_run_id 如何确定其所属批次和实验？
5. 重试是复用 Run、复用 batch_run，还是创建新 attempt？
6. queued / running / paused / quarantined 等活动态的定义是否与唯一索引一致？
7. 重复请求、网络重试、进程重启能否识别同一业务意图？
8. 一个 Batch 失败而其他 Batch 继续时，父 Experiment 如何聚合？

### 3.3 必须交付

- 实体关系图（ERD）；
- 主键、外键、唯一索引、活动态约束清单；
- Run 身份传播表：Experiment → Batch → BatchRun → ExperimentRun → Run → Node → Command → Event；
- 重试与恢复状态转换表。

**禁止在未证明身份链完整前，以“统一 Run”为由重写表关系或新增第二套活动态唯一约束。**

## 4. P0：设备命令与事件业务归属核查

### 4.1 核查目标

证明每个设备事件能够关联到正确的命令、Run、节点和物料。数据库保证一条事件不被重复消费，只能解决去重，不能单独证明消费者正确。

### 4.2 必查文件与符号

| 文件/区域 | 必查内容 |
|---|---|
| `labos-kernel/.../workflow/GraphRunner.java` | `waitForDeviceEvent`、`__awaitEvent`、eventBaseCursor、eventRunId、eventCursors |
| `labos-kernel/.../event/DeviceEventSource.java` | claim 契约、参数含义、返回语义 |
| `labos-kernel/.../event/MapperDeviceEventSource.java` | tenant、run、node、loopIndex 如何传递；事务边界 |
| `labos-kernel/src/boot/resources/mapper/DeviceEventMapper.xml` | `claimEvent`、候选过滤、`SKIP LOCKED`、消费记录、重入语义 |
| 设备事件接收入口 | 原始事件如何解析、去重、入库；设备身份如何校验 |
| 命令下发层 | command ID、幂等键、设备返回值、超时与重试 |
| DDL / migration | device_event、device_event_consumption 及关联索引、唯一约束 |

### 4.3 必须回答的关键问题

1. 设备是否支持回传 commandId、processId、板号/物料 ID、设备序列号？
2. 如果不支持，是否存在可靠的替代关联键？其歧义边界是什么？
3. `device_event.run_id` 表示生产事件的来源 Run，还是消费 Run？两种语义不能混用。
4. claim 的 `runId + nodeKey + loopIndex` 是等待者身份，还是事件归属依据？
5. 当前候选查询允许哪些 Run 领取哪些事件？是否按 tenant、device、eventType、command/物料上下文过滤？
6. `dispatched_at` 与 consumption 表的更新是否在同一事务/同一 SQL 原子完成？
7. claim 成功后进程崩溃，等待者重入能否取得同一事件？不同等待者是否可能错误取得？
8. 事件先于等待节点到达、乱序、重复、迟到时如何处理？
9. 一块板连续经过多个设备，事件如何保持物料身份链？
10. 设备不支持精确关联时，是否进入受限串行模式或人工隔离？

### 4.4 评审裁决

不采用“当前持有设备锁的 Run 自动拥有该设备下一条事件”作为通用归属规则。

建议目标关联链：

`Command → Run → Node → Batch/Material → DeviceEvent`

优先以不可伪造/可验证的 commandId 关联；设备不支持时，使用经过验证的物料身份、设备会话或交互步骤组合键，并明确其可靠性等级。无法唯一归属的事件不得推进自动流程。

### 4.5 通过标准

- 不同 Run 同时等待同一设备/事件类型时，事件不会串 Run、串板；
- 重复、乱序、迟到事件不会重复推进节点；
- 事件与命令关联在持久化层可审计；
- claim 与消费记录具有明确事务语义；
- 无法确定归属的事件进入隔离/人工确认，不得猜测归属。

## 5. P0：资源模型、锁顺序与租约核查

### 5.1 资源必须分类建模

| 类别 | 例子 | 生命周期 |
|---|---|---|
| 设备执行资源 | 提取仪、离心机、PCR | 执行期间占用；设备确认完成后释放 |
| 物理位置资源 | 板位、孔位、架位、设备腔体 | 物料实际占据期间持续占用 |
| 移动资源 | 机械臂、轨道、轨道分区 | 物理移动区间占用 |
| 消耗资源 | 试剂、枪头、耗材 | 预留、消耗、退回/报废；不是普通互斥锁 |
| 能力/容量资源 | 温控位、并行通道、批量槽位 | 按容量计数，不一定独占 |

设备执行完成不能自动释放物料位置；移动资源释放不能改变物料位置事实；耗材预留不能被当作设备锁。

### 5.2 必查文件与符号

| 文件/区域 | 必查内容 |
|---|---|
| `.../driver/DeviceLock.java` | acquire/release、current_run_id、租约、条件更新、超时 |
| `.../driver/PositionLock.java` | 单锁/双锁顺序、位置占用与设备执行锁关系 |
| `.../driver/RailZoneGuard.java` | 分区锁顺序、失败回滚、跨线程/跨进程语义 |
| `ExperimentScheduler.java` | resourceHolds 的预筛与真实锁之间是否有竞态 |
| `PersistingStepSink` 实现及调用方 | onStepStart/onStepDone 的实际触发范围；异常退出是否释放 |
| 物料身份/位置服务与 DDL | 位置状态由谁写入；设备状态与物料位置是否分离 |
| 所有资源锁 SQL / Mapper | 原子申请、条件释放、租约过期、owner 校验 |

### 5.3 必须回答

1. 资源锁是 JVM 内锁、数据库锁还是两者组合？
2. 两个 LabOS 实例同时申请同一资源，数据库能否保证只有一个成功？
3. owner 身份是否包含 tenant、run、node、attempt、lease token？
4. 释放是否校验 owner，避免旧 Run 释放新 Run 的锁？
5. 服务崩溃后如何区分“租约失效”与“设备仍在执行”？
6. 资源申请失败时是否释放本次已申请的全部临时资源？
7. 不同锁是否存在全局顺序？顺序覆盖设备、位置、轨道等所有类别吗？
8. 资源超时、心跳中断、设备断联、未知状态如何处理？
9. 位置占用是否跟随物料实际移动，而不是跟随某个 Run 的节点完成？
10. 内存 resourceHolds 与数据库真实占用不一致时，以谁为准？

### 5.4 通过标准

- 数据库/持久化层是跨进程资源正确性的最终裁决者；
- 多资源申请具备全局顺序或原子事务；部分申请失败可完整回滚；
- 释放具备 owner/token 校验；
- 不以简单 TTL 到期作为设备安全释放依据；
- 位置占用与设备执行锁分离；
- 任何 UNKNOWN 资源状态都阻止冲突动作派发。

## 6. P0：状态机、暂停/停止与批次聚合核查

### 6.1 必须分离的状态维度

| 维度 | 例子 | 含义 |
|---|---|---|
| Experiment 状态 | running / paused / completed / failed / quarantined | 用户可见的实验业务状态 |
| Batch 状态 | queued / running / paused / completed / failed | 批次执行状态 |
| Run 状态 | queued / running / paused / completed / failed / quarantined | 一次执行尝试的生命周期 |
| Scheduler 状态 | pending / eligible / waiting_resource / dispatched | 是否具备派发条件 |
| Resource 状态 | available / reserved / occupied / releasing / unknown | 物理/逻辑资源状态 |
| Device 状态 | idle / executing / pause_requested / paused / fault / unknown | 设备真实反馈状态 |

以上仅为维度示例，不代表要求立即新增同名枚举。必须先核对现有 StatusVocabulary、状态机和数据库约束。

### 6.2 必须回答

1. Pause 请求发出后，谁记录 pause_requested？设备确认如何关联？
2. 设备已暂停与 Run 已暂停是否有明确区分？
3. Batch 暂停后 Experiment 何时才能进入 paused？
4. 实验级暂停如何协调正在运行、等待资源、尚未派发的批次？
5. 单批暂停是否影响同实验其他批次？
6. Stop 是取消尚未派发、请求设备停止、等待安全边界，还是强制终止？必须区分。
7. 某批失败时，其他批继续的策略由谁决定？是否按实验配置？
8. 失败批重试如何避免与原 attempt 同时活跃？
9. Resume 前是否重新检查 Hold、资源、设备状态、物料位置和命令在途状态？
10. 聚合状态是否存在“所有批次已结束但实验仍 running”或“单批完成导致实验提前 completed”的窗口？

### 6.3 通过标准

- Pause requested 不等于 paused；
- 设备确认暂停不自动等于实验级暂停；
- 单批操作与实验级操作具有明确作用域；
- 未派发批次在实验暂停/停止后不会继续启动；
- Resume 必须重新经过 Hold、资源和现场状态检查；
- 实验聚合状态有确定、可测试的真值表。

## 7. P0：Hold、Island、审计与安全边界核查

### 7.1 必查范围

- Island 边界：资源是否严格限定在正确岛/租户；是否存在跨岛资源误认领。
- Hold：CLEAR / HELD / UNKNOWN 的定义、读取失败处理、缓存有效期、派发前最后一次校验。
- Reconciliation：启动时何时进入阻断、对账失败是否保持阻断、何时允许 endReconciling。
- 审计：提交、入队、派发、资源申请/释放、命令下发、事件认领、暂停/恢复/停止均可追溯。
- 权限：谁能提交并行任务、调整并行度、解除隔离、人工释放资源。
- 安全动作：急停、设备故障、门禁/安全联锁的优先级高于调度优先级。

### 7.2 通过标准

- Hold 查询异常按 UNKNOWN 处理，不得当作 CLEAR；
- Reconciliation 未完成时禁止新命令派发；
- 资源释放和人工解锁都有审计及权限；
- 并行不跨越原有 Island / tenant 安全边界；
- 安全联锁和急停不会被普通排队/恢复逻辑覆盖。

## 8. P1：队列公平性、线程与吞吐量核查

### 8.1 不得混淆的三个上限

1. 执行线程上限：JVM 能同时运行多少执行任务。
2. 调度并发上限：允许多少 Run 进入执行态。
3. 物理资源吞吐上限：设备、机械臂、位置、耗材与流程依赖共同允许的并行能力。

三者不能用一个 `MAX_CONCURRENT` 代表。

### 8.2 必查问题

- 固定线程池是否有无界等待队列？提交前是否先占资源？
- running 计数在任务提交、线程真正开始、完成、异常、取消时是否严格平衡？
- 动态降低并发上限时如何收敛？不应中断正在执行的物理动作。
- 是否存在某个实验长期占满线程导致其他流程饥饿？
- 资源等待是否采用事件驱动唤醒，还是固定轮询/指数退避？
- 优先级是否支持 aging，避免低优先级永久饥饿？
- 机械臂是否成为共享瓶颈？是否有搬运队列与安全窗口？
- 是否有每设备服务时间、队列等待时间、资源利用率的真实观测数据？

### 8.3 通过标准

- 不会因“线程池排队”提前占住物理资源；
- running 计数无泄漏、无负数、无重复扣减；
- 队列长度有界或有明确背压；
- 并行度配置与物理资源能力分开；
- 有可观测的队列等待、资源等待、执行耗时和失败原因。

## 9. P0/P1：重启恢复与多实例并发核查

### 9.1 故障注入场景

1. Run 已 queued，尚未派发时进程崩溃；
2. Run 已标记 dispatched，但线程尚未开始；
3. 命令已发送，设备未回包；
4. 设备已执行完成，事件尚未入库；
5. 事件已入库并被 claim，GraphRunner 尚未持久化节点结果；
6. 资源已申请，进程在释放前崩溃；
7. 旧实例恢复期间，新实例启动并尝试派发；
8. 数据库短暂不可用后恢复；
9. 设备断联，资源和物料状态均为 UNKNOWN；
10. 同一个 queued Run 被两个 Scheduler 实例同时读取。

### 9.2 必须回答

- queued run rehydrate 是否会重复入队？
- 派发认领是否数据库原子化？
- 执行任务是否有 lease/owner/epoch，避免旧实例继续写入？
- 命令是否有幂等键，设备端是否支持去重？
- 进程崩溃后如何恢复已 claim 的事件？
- 资源租约过期是否会错误释放仍在运行的设备？
- 多实例是否通过数据库锁/条件更新/唯一约束竞争？
- reconciling 是否为全局/租户/岛级阻断，而非单 JVM 布尔值？
- 对账失败时是否 fail closed？

### 9.3 通过标准

- 同一 Run 最多只有一个有效派发者；
- 旧实例失去租约后不能继续更新权威状态或下发命令；
- 任何命令在途未知时禁止可能冲突的新命令；
- 事件消费、节点推进、资源释放均具备崩溃恢复语义；
- 多实例测试通过，而非只通过单 JVM 测试。

## 10. 目标架构与推荐实施顺序

### 10.1 目标职责

`Submission → ExperimentScheduler → Resource Coordinator → Run/GraphRunner → Command/Event Correlation → Physical Device`

- Scheduler：决定哪个请求可以被派发。
- Resource Coordinator：决定请求能否获得需要的资源。
- GraphRunner：推进工作流节点。
- Command 层：创建和下发可追踪、幂等的命令。
- Event 层：把设备反馈关联回唯一业务上下文。
- State/Hold/Reconciliation：约束所有状态变更与恢复。

Resource Coordinator 可以逐步由现有 DeviceLock、PositionLock、RailZoneGuard 等演进，不要求另起一套锁系统。内存结构只能优化调度，不能作为跨实例正确性的唯一依据。

### 10.2 分阶段实施

| 阶段 | 工作 | 放行条件 |
|---|---|---|
| 0. 源码审计 | 执行入口、Run 身份、锁、事件、状态、Hold、恢复全链路核查 | 本文 P0 清单有证据结论 |
| 1. 统一调度入口 | 批次从同步执行改为提交统一 Scheduler；暂时并行度 1 | 行为兼容、幂等、审计、重启测试通过 |
| 2. 事件归属 | 命令/Run/Node/Batch/Material/Event 关联 | P0 事件归属测试全部通过 |
| 3. 资源协调 | 资源分类、原子申请、租约、失败回滚、位置独立占用 | P0 资源及崩溃测试通过 |
| 4. 状态聚合 | Batch/Run/Experiment 状态、暂停/停止/恢复 | 状态真值表和并发状态测试通过 |
| 5. 小流量并行 | 在明确支持的设备/流程组合中开放并行度 2 | 仿真、硬件在环、真实现场验收通过 |
| 6. 扩容 | 按资源能力逐步提高并行度 | 吞吐、故障恢复、饥饿和安全指标满足要求 |

**禁止把“并行度 1 重构完成”解释为“并行安全已证明”。** 并行度 1 只证明兼容性与统一入口；事件归属和资源竞争仍需单独验证。

## 11. 并行验收测试矩阵

原方案 P-01 至 P-12 保留，但以下用例必须补充。测试必须包含真实 SQL/事务竞争；涉及物理动作的场景先使用设备模拟器，再进入硬件在环和现场验证。

| ID | 优先级 | 场景 | 通过标准 |
|---|---|---|---|
| P-13 | P0 | 两个 Run 同时申请同一设备 | 仅一个获得资源；另一个排队；无重复命令 |
| P-14 | P0 | 两个实验用不同设备、共用一台机械臂 | 非搬运节点可并行；机械臂动作互斥 |
| P-15 | P0 | 两个 Run 争用同一物理位置 | 位置仅归属一个物料；设备锁释放不释放位置 |

| P-17 | P0 | 事件早于等待节点到达 | 合法事件不丢失；不被无关 Run 领取 |
| P-18 | P0 | 两个 Run 交叉申请资源 A/B | 无循环等待；失败申请不残留部分锁 |

| P-31 | P0 | 旧实例租约失效后仍尝试写状态/下发 | 被 fencing/owner 校验拒绝 |

| P-34 | P1 | 长等待节点与短任务并存 | 等待不长期占用执行线程；其他任务可推进 |
| P-35 | P1 | 调度队列突增 | 背压生效；队列和资源占用有界 |

### 11.1 每个测试必须记录

- 测试环境与 commit SHA；
- 初始数据库快照/fixture；
- 并发线程数和 Scheduler 实例数；
- 事件顺序、命令 ID、Run ID、Batch ID、物料 ID；
- 资源申请/释放日志；
- 状态变化时间线；
- 预期与实际差异；
- 是否覆盖崩溃点；
- 测试结果和可复现脚本。

## 13. 本次评审的明确建议

1. 先执行第 2–9 节源码核查，不先改业务代码。
2. 将核查结果按文件/方法/SQL/测试证据落入独立报告；本清单只负责定义核查标准。
3. 先统一现有 ExperimentScheduler 与 BatchOrchestrator 的关系，不新增第二个权威调度器。
4. 将事件业务归属列为并行开放的 P0 门槛；设备锁只负责资源互斥。
5. 将设备执行资源、物理位置、移动资源和消耗资源分开管理。
6. 保留 WorkflowRunGate 作为迁移保护，按经过验证的流程/设备能力逐步放开。
7. 先实现并验收并行度 1 的统一入口，再进行并行度 2 的独立安全评审。

**最终原则：并行不是“多开几个线程”，而是多个独立执行体在共享物理世界中安全地协调资源、命令、事件、物料和状态。只有这些关系可证明、可恢复、可审计，才允许增加并行度。**
