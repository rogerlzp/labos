## 2. 🔴 本轮新发现

### N1 · `verify-role-permissions.py` **第二次跑必失败**（17/3）

实测（连跑两次，均失败）：

```
✓ admin/operator/designer/viewer GET config 200      （4 条）
✗ admin POST /api/schedule-plans → 409（期望 200）（{'error': 'planNo 可能重复'}）
✗ operator POST /api/schedule-plans → 409（期望 200）
✗ designer POST /api/schedule-plans → 409（期望 200）
✓ viewer POST /api/schedule-plans → 403（期望）
… 其余 12 条全过
通过 17 / 失败 3
```

**根因链（三段）**：

1. 脚本第 93-96 行：`planNo` 按角色固定为 `VERIFY-PERM-admin` / `-operator` / `-designer`
2. 脚本第 105-109 行：**清理用 `PUT {"status":"archived"}`**，不是 DELETE
3. DB：`uk_schedule_plan UNIQUE (tenant_id, plan_no)` —— **不带状态条件** ⇒ **archived 的号仍然占位**

⇒ 第一次跑：号不存在 → 200 ✓ → 归档
　第二次跑：号已存在（archived）→ **409** ⇒ 3 条断言失败

**这与上一轮 `verify-stale-auto-dismiss` 的清理 bug 是同一类**：
> **用「业务状态」做清理，但业务状态不释放唯一键。**

上一轮修的是"dismiss 把 `pause_reason` 置 NULL 导致按 `pause_reason` 清会漏"；
这一轮是"archived 不释放 `plan_no` 唯一键" —— **同一个坑的另一个面**。

**⚠ 你的回归表里的 20/0 是首次运行的数字。** 库里现有：
`VERIFY-PERM-admin` / `-operator` / `-designer` 三条都是 **archived** 状态（14:08:57 建的），
所以任何复跑都会 409。
