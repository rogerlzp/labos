# 并行执行下的暂停与恢复：现状、缺陷与设计

- 日期：2026-11-18
- 性质：设计文档，**未实施**
- 前提：单实例部署；目标态是"多实验 + 多批次并行"
- 定位：这是并行改造里**最容易被低估**的一块。并行会把"停一半"从不可能变成常态。

---

## 0. 一句话

现在有两套暂停机制（`run.status` + `RuntimeHold`）和一条恢复链路，单体场景能工作；但**一旦多批并行，"暂停一批"和"暂停整个实验"会变成两个不同的操作**，而现有设计只支持后者的一部分。

---

## 1. 现状

### 1.1 两套暂停机制

| 机制 | 作用域 | 是否改 `run.status` | 典型场景 |
|---|---|---|---|
| `run.status='paused'` + `pause_kind` | 单个 run | **改** | 单流程暂停、设备故障 |
| `RuntimeHold` | SITE / ISLAND / EXPERIMENT 三级 | **不改** | 实验级暂停、现场扣留 |

`pause_kind` 三个值：

| 值 | 含义 | 恢复条件 |
|---|---|---|
| `paused_fault` | 设备故障 | 心跳恢复后自动继续 |
| `waiting_human` | 需人工确认（重试耗尽、板位不一致） | 人工处理后恢复 |
| `paused_unknown` | 板位置未知 | **必须提供 corrections（板号→实际位置）** |

### 1.2 暂停生效点：只在动作边界

`GraphRunner` 每到一个节点边界查一次（`WorkflowService` 第 1298 行）：

```java
.withPauseChecker(() -> isRunPaused(runId)
        || new RuntimeHold(db, tenantId).coverageForWorkflow(workflowId).blocks())
```

两个后果：

- 动作执行**中**不能暂停（机械臂不能悬停承重、离心不能中途开盖）
- 最长响应延迟 = 当前动作耗时，孵育就是 30 分钟

这是物理约束决定的，不是实现缺陷。

### 1.3 恢复链路（已核实的实际顺序）

```
RunService:274
  → PauseCoordinator.resumeWorkflowRun:255
      ├ 开事务
      ├ claimTx        幂等：重复请求回放首次结果
      ├ P-08 强门禁     位置未确认（只有运动报告）→ 只允许终止，不允许继续
      ├ PauseManager.resumeTx:509
      │    ├ pauseKindOfTx      读当前 pause_kind
      │    ├ kind==null → isCrashRecoverableTx 判是否崩溃可恢复
      │    ├ PAUSED_UNKNOWN 必须有 corrections
      │    └ 执行状态变更（resumeToQueued / resumeToAborted）
      ├ settleTx + insertPauseEvent
      └ 提交
  → 提交后 resumeAsync   （内存动作，故意放在事务外）
```

**这个设计有三处是对的**，要肯定：

1. **幂等**：`claimTx` 保证重复 resume 回放首次结果，不会重复执行
2. **强门禁**：位置未确认时只允许终止，防止"板还在半路就继续"
3. **事务边界正确**：`resumeAsync` 放在提交后，避免"内部异常把外层标 rollback-only"

### 1.4 启动恢复

| 机制 | 做什么 |
|---|---|
| `StartupRecovery` | 启动时收 `running`；`queued/pending` 超 1 小时才收（避免误杀刚入队的） |
| `CommandLedger.reconcileOnStartup` | 陈旧在途命令逐条 `queryStatus`，确认不了落 UNKNOWN |

## 2. 现有缺陷（代码级，6 条）

### D-00 `quarantined` 的 run 根本走不到恢复 SQL

服务层判定链（`PauseManager.resumeTx` 第 512–520 行）：

```java
String kind = pauseKindOfTx(c, runId);        // WHERE status='paused'      → quarantined 为 null
if (kind == null) {
    crashed = isCrashRecoverableTx(c, runId); // WHERE status='failed'...   → quarantined 为 false
    if (!crashed) return new ResumeResult(false, "该执行不在暂停状态", ...);  // ← 提前返回
}
...
mappers().resumeToQueued(tenantId, runId);     // ← quarantined 永远到不了
```

**后果**：只在 `resumeToQueued` 的 SQL 里加 `quarantined` 是**死代码**。必须让 `isCrashRecoverable` 放行 `quarantined`（语义上"隔离待确认"与"failed+recoverable"同类），否则被隔离的 run 永远醒不过来，还会永久占住批次/流程的活跃名额。

### D-01 `resumeToQueued` 的 UPDATE 没有状态守卫（TOCTOU）

```sql
-- PauseMapper.xml 第 107-111 行
UPDATE run SET status = 'queued', pause_kind = NULL, ...
 WHERE tenant_id = #{param1} AND id = #{param2}
```

**只有 tenant + id，没有任何状态条件。**

`resumeTx` 虽然在事务内先用 `pauseKindOfTx` 读了状态，但那是"先读后写"，不是原子条件更新：两个并发请求都读到 `paused`，都能 UPDATE 成功；或读完之后状态被别的路径改掉，UPDATE 仍然成功。

**定性**：这是 **TOCTOU**（check-then-act 的时间窗），不是"已完成的 run 能被重新跑"——`completed` 在服务层就被 `isCrashRecoverable` 拦住了，正常路径不可达。

修复目标是把"先读后写"变成"带状态条件的原子更新 + 检查影响行数"。

### D-02 `resumeToAborted` 同样无守卫（第 113-118 行）

### D-03 恢复不校验归属

`resumeTx` 只按 `(tenant, id)`，没有校验这个 run 是否属于当前请求的 workflow。跨流程 resume 只要 id 对得上就能执行。

### D-04 实验级暂停不改 run 状态

`RuntimeHold` 只阻止派发，run 仍是 `running`。

源码注释里已经记录过实测问题：

> 2026-11-06 实测：实验级暂停停不住 workflow 级 run（只查 run.status 的话底层流程永远看不到它）

现在的修法是"每节点边界也查 Hold"，但**状态层面仍然是 `running`**，导致：

- UI 上分不清"真在跑"和"被 Hold 住了"
- 恢复时不需要 resume（因为没 paused），只需要解除 Hold —— 两条路径语义不同

### D-05 `resumeAsync` 失败会留下僵尸 `queued`

注释写得很清楚：

> 恢复已提交，但异步续跑启动失败

此时 run 已是 `queued`，但没有 worker 在跑。需要兜底扫描，现在没有。

## 3. 多并行下的七个新问题

这些在单 run 场景下不存在，并行后必然出现。

| ID | 问题 | 为什么并行后才出现 |
|---|---|---|
| **Q-01** | 一批暂停，其他批怎么办？ | 现在只有"停整个 run"，没有"停这一批"的概念 |
| **Q-02** | 实验级暂停，如何协调 4 批？ | 有的在跑、有的排队、有的未启动，停的时机完全不同 |
| **Q-03** | 恢复时 4 批同时 resume 会抢设备吗？ | 单 run 不需要考虑，多批会瞬间冲击设备锁 |
| **Q-04** | 暂停期间资源释放不释放？ | 设备锁随 step 释放，但位置锁可能还占着（板还在设备里） |
| **Q-05** | 恢复顺序要不要按 `batch_no`？ | 严格顺序会让批 4 等批 1，可能空转 |
| **Q-06** | 暂停后改了配置，恢复用新配置还是旧快照？ | 单 run 变更少，多批时配置漂移风险大 |
| **Q-07** | 重复/并发 resume 4 批 | 现在 `claimTx` 按单次命令幂等，4 批是 4 条命令 |

### 3.1 每条的具体分析

**Q-01 批次级暂停缺失**

现在 `PauseCommand.workflow(runId, ...)` 是按 run 的。要停"第 2 批"，只能：
- 找到第 2 批对应的 runId，单独停
- 但用户界面上"停第 2 批"这个操作不存在

**Q-02 实验级暂停的协调**

理想语义：

```
实验 E 有 4 批：批1 离心中 / 批2 孵育中 / 批3 等设备 / 批4 未启动
用户点"暂停实验"
  ├ 批1：等到离心结束（安全边界）→ paused
  ├ 批2：等到孵育结束 → paused（或按配置，孵育中不动）
  ├ 批3：从等待队列移除 → paused（没启动过，直接标）
  ├ 批4：不启动
  └ 实验状态：等 4 批全部确认暂停后，才变 paused
```

现在的实现只做到"写 Hold + 各 run 在边界自己停"，**没有"全部确认后才改实验状态"这一步**。

**Q-03 恢复时的资源冲击**

4 批同时 resume，4 个线程同时抢设备锁。如果只有 2 台设备，2 个会等待。这本身没问题（设备锁会排队），但：

- 如果 `acquireWithWait` 的超时是 60 秒，另外 2 个会失败
- 失败后 run 变什么状态？现在的路径没有定义

**Q-04 暂停期间的资源**

| 资源 | 暂停时 | 恢复时 |
|---|---|---|
| 设备锁 | 随 step 释放（`onStepDone` 总会调） | 重新抢 |
| 位置锁 | **可能还占着**（30 分钟 TTL 或永久） | 重新校验 |
| 机械臂分区 | 随动作释放 | 重新抢 |

风险：暂停 30 分钟后，位置锁 TTL 到期自动释放，但板可能还在设备里 → 别的 run 以为位置空了。

**恢复时校验失败（锁已过期 / 板不在原位 / 无法确认）的处置**：不得新造错误码，直接**把该 run 转 `paused_unknown`**，复用现成的 corrections 路径（`resumeTx` 已要求 `paused_unknown` 必须提供"板号 → 实际位置"）。

这样三件事同时成立：恢复被安全阻断；用户看到的是熟悉的"板位置未知，请校正"；同实验其他批一并被阻塞（见 §4.5）。

**Q-07 并发 resume**

`claimTx` 按 `PauseCommand` 的幂等键去重。4 批是 4 条独立命令，各自幂等，但"4 批一起恢复"这个操作本身没有幂等保护。

## 4. 目标设计

### 4.1 三层语义（必须分开）

| 层 | 表示 | 何时用 |
|---|---|---|
| **实验级** | `experiment.status = paused` + Hold 记录 | 用户点"暂停实验" |
| **批次级** | `experiment_batch.status = paused` + Hold（batch 作用域） | 用户点"暂停这一批" |
| **run 级** | `run.status = paused` + `pause_kind` | 单流程暂停、设备故障 |

关键规则：**上层暂停不直接改下层状态，而是"请求"下层停，下层在安全边界自己改。**

由此推出第二条：**Hold 请求可以立即持久化，但 `run.paused` 不能提前写。** 收到请求就标 `paused`，等于伪造"物理动作已停在安全边界"。

### 4.1.1 用户可见的中间态

长动作（孵育 30 分钟）从"点了暂停"到"真的暂停"隔着几十分钟。如果 UI 一直显示 `running`，用户会认为操作没生效，然后重复点击或去现场干预。

因此需要一组**独立于 `run_status`** 的暂停协调状态：

| 状态 | 含义 | 用户看到 |
|---|---|---|
| `pause_requested` | 请求已接受，尚未生效 | 立刻显示"已提交" |
| `pausing` | 已通知各 run，等待动作边界 | "正在暂停（批 2/4 已确认）" |
| `pause_blocked` | 有 run 处于 UNKNOWN 或超时未确认 | 阻塞原因 + 需人工处理 |
| `paused` | 所有必要对象已确认 | 等同现有语义 |
| `resume_requested` / `resuming` | 恢复协调过程 | 恢复进度 |

**这组状态与 `run_status` 是两回事**：不加枚举值（沿用"用列不用枚举"原则），落在 `experiment.pause_state` 或独立的协调表上。

### 4.2 状态传播

```
实验暂停请求
  → 写 experiment 级 Hold（scope=experiment）
  → 对该实验所有活跃批次写 batch 级 Hold
  → 每个 run 在节点边界检查 Hold → 自行转 paused
  → 所有 run 确认 paused 后，批次标 paused
  → 所有批次确认 paused 后，实验标 paused
```

**为什么必须"逐层确认"**：任何一层没确认就标上层，会出现"实验显示已暂停，但批 2 还在离心"。

### 4.3 恢复协调

```
恢复实验
  → 检查：所有批次的 run 是否都是 paused/未启动
  → 解除 experiment Hold
  → 逐批恢复（不是一起）：
      1. 检查该批资源需求
      2. 通过准入（GuardedStart 的 resume 分支）
      3. 提交后唤醒 scheduler
      4. 下一批等前一批通过准入后再做
  → 全部恢复后，实验标 running
```

**逐批恢复而不是一起恢复**：避免 4 个线程同时抢设备锁导致 2 个超时失败。

### 4.4 恢复顺序

| 策略 | 说明 | 建议 |
|---|---|---|
| 严格按 `batch_no` | 批 1 恢复完才批 2 | **默认**，保证与串行语义一致 |
| 并行恢复 | 所有批同时进队列 | 可选，需配合并行度上限 |
| 按资源可用性 | 谁能跑先跑 | 复杂，暂不做 |

### 4.5 阻塞式暂停

现在的 `paused_unknown` 必须提供 corrections 才能恢复。并行后要加一条：

**如果一批是 `paused_unknown`，同实验的其他批也不能启动。** 因为板位置未知意味着现场状态不可信，其他批贸然启动可能撞板。

### 4.6 幂等与冲突

| 场景 | 处理 |
|---|---|
| 重复暂停同一批 | 幂等，返回首次结果 |
| 重复恢复同一批 | 幂等（`claimTx` 已有） |
| 暂停和恢复并发 | 按 `PauseCommand` 幂等键串行化 |
| 恢复到一半失败 | 已恢复的保持，失败的标 `paused_fault`，不整体回滚 |
| 恢复时 run 已被别人改成 running | UPDATE 影响行数 0 → 报冲突，不静默成功 |

---

### 4.7 隔离后的恢复：人工确认是一次动作

`quarantined`（隔离待确认）的恢复**不能只填板位置**，必须同时确认设备可用性（2026-11-19 业务确认）。

**页面表单**：

```
① 板 P-xxx 现在在哪？
   ○ 仍在设备内   ○ 已到交换位   ○ 找不到（丢失）

② 设备当前能否交给别人用？
   ○ 可以（腔内已清空）   ○ 不可以（还有板）

[确认并提交]   [终止流程]
```

**三条分支**：

| 选项组合 | 系统行为 | 设备占用 |
|---|---|---|
| 位置明确 + 设备可用 | `resumeToQueued` + 写 corrections | **释放** |
| 位置明确 + 设备不可用 | **不允许提交**，提示"请先清空设备" | 保持 |
| 板找不到 | `resumeToAborted` + `EC-BOARD-LOST` | **释放** |

**为什么不能只确认位置**：位置知道不等于设备干净。允许分开会让用户以为"填完位置就完事"，忽略腔内残留。

**为什么设备要单独判断**：隔离实例同时占两类资源——

| 资源 | 释放时机 |
|---|---|
| 流程名额（`workflow_id`） | 隔离结束时（恢复或终止） |
| 设备锁 / 物理占用 | **人工确认"设备可用"时** |

所以隔离的实例会卡住那台设备，其他流程用不了——这是正确的，因为中控不知道板在不在里面。

详见《并行执行-设计文档》I-05。

## 5. 代码改造清单

### 5.1 SQL 层（最小、最紧急）

| 文件 | 改动 | 优先级 |
|---|---|---|
| `PauseMapper.xml` `resumeToQueued` | 加 `AND status IN ('paused','failed','quarantined')` | **P0** |
| `PauseMapper.xml` `resumeToAborted` | 同样加状态条件 | **P0** |
| 调用方 | 检查影响行数，0 行报冲突 | **P0** |

这一条**今天就能做**，不需要任何设计决策。

### 5.2 服务层

| 文件 | 改动 |
|---|---|
| `PauseManager.resumeTx` | 加 tenant + workflow 归属校验（现在只按 id） |
| `PauseCoordinator.resumeWorkflowRun` | 加准入调用（`GuardedStart` 的 resume 分支），替代现在的裸 `resumeAsync` |
| `PauseCoordinator` | 新增批次级恢复方法：`resumeBatch(experimentId, batchNo)` |
| `RuntimeHold.Scope` | 加 `BATCH("batch")` 取值 |
| 新增 `BatchPauseCoordinator` | 实验级暂停的逐批协调逻辑（暂停确认、恢复顺序） |

### 5.3 兜底

| 文件 | 改动 |
|---|---|
| `StartupRecovery` | 增加"僵尸 queued 扫描"：`status='queued'` 超过 N 分钟且无对应 worker → 标 `paused_fault` |
| `ExperimentScheduler` | 批次恢复时检查"同实验是否有 `paused_unknown` 批" |

### 5.4 不改的

| 项 | 原因 |
|---|---|
| `run_status` 枚举 | 不加值（沿用"用列不用枚举"原则） |
| 动作边界暂停 | 物理约束，不能改 |
| `claimTx` 幂等机制 | 已经正确，复用 |

| ID | 问题 | 选项 | 建议 |
|---|---|---|---|
| H-12 | 实验级暂停时，run 的 `paused` 由谁写 | ① 只写 Hold，run 保持 `running` ② Hold 请求立即持久化，run 在**安全边界自行**转 `paused` | **②**。注意不是"Hold 与 run 状态同时改"——Hold 是请求，`paused` 必须由下层在动作边界写入，否则等于伪造暂停完成（与 §4.1 一致） |
| H-13 | 暂停期间位置锁是否强制保留 | ① 保留（可能永久占用） ② TTL 到期释放，恢复时重校验 | **②**，但恢复前必须校验 |
| H-14 | 恢复顺序 | ① 严格按 batch_no ② 并行 ③ 按资源 | **①** |
| H-15 | `paused_unknown` 是否阻塞同实验其他批 | ① 阻塞 ② 不阻塞 | **①**，安全优先 |

## 8. 风险

| ID | 风险 | 说明 |
|---|---|---|
| R-23 | 逐批恢复会让总恢复时间变长 | 4 批 × 检查耗时，可能几十秒 |
| R-24 | Hold 与 run.status 双写不一致 | 必须定义谁是权威（建议 run.status 为准，Hold 只是"请求"） |
| R-25 | 暂停时位置锁过期，恢复时板不在原位 | 必须恢复前强制校验，不能只看状态 |
| R-26 | 实验状态聚合延迟 | 全部批确认后才改实验状态，用户可能觉得"点了没反应" |
| R-27 | `paused_fault` 自动恢复与人工恢复冲突 | 需明确"自动恢复"是否也要过准入 |
