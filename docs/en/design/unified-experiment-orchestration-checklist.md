> **English edition.** The Chinese original is [`docs/设计-实验编排统一-v0.1-实施清单.md`](../../设计-实验编排统一-v0.1-实施清单.md); this is

> the Chinese source — if they ever disagree, the Chinese original wins.

> Companion design: [`docs/设计-实验编排统一-v0.1-草稿.md`](../../设计-实验编排统一-v0.1-草稿.md)
>  
> Purpose: to break the `S1/S2/S3` of `M9.5` down from a "direction" into executable tasks, so that scheduling, division of labour and a second review become possible.
>  
> Position: **do the smallest closed loop first, then extend the capability**. Every phase has to satisfy the dedicated entry gate of `M9.5` in `ROADMAP.md`.

---

## 0. The overall principles

1. **Remove the misleading bits first, then add capability**
   - The goal of `S1` is not "more features"; it is to remove the misleading "the canvas and the execution are inconsistent" first.
2. **Close the write paths first, then extend the data model**
   - Keeping the dual `graph/process` write entry point would make every later phase an unstable state.
3. **Make the execution semantics clear first, then open up the UI capability**
   - Semantics that cannot be executed should not be put into the canvas first.
4. **Define the rollback and the verification first, then start the implementation**
   - `S1/S2/S3` all have to have a failure rollback and an acceptance script; "change it first and add the tests afterwards" is not accepted.

---

## 1. Overview of the phases

| Phase | Goal | What it does not do | Deliverable |
|---|---|---|---|
| **S1 Unified write entry point** | Make the canvas save really affect the execution, and stop `graph/process` from splitting | No real concurrency inside an experiment, no batching | Single-entry save, the graph compiled into the database, a read-only table, regression tests |
| **S2 Partial-order execution** | Let several workflows inside an experiment express their order dependency | By default **no wall-clock concurrency is promised**; unless the three resource layers + the wait-for graph are brought in at the same time | `experiment_process_edge`, partial-order dispatch, join waiting, UI state updates |
| **S3 Batched execution** | Let one experiment support "logical batches + several attempts" | No automatic modelling of the complex clearing between batches | `experiment_batch` / `experiment_batch_run`, a failure only re-runs that batch, the batch view |

## 2. S1 · Unified write entry point

### 2.1 Goal

Get rid of the state where "the canvas only stores the drawing and the execution still looks at the table", and form the single trustworthy write path:

- Canvas save = update the layout + compile `process`
- The workflow table on the detail page = a read-only mirror
- Any sub-step fails = roll everything back

### 2.2 Backend tasks

| # | Task | Explanation |
|---|---|---|
| 1 | Add `saveExperimentGraphAndCompile(...)` | It is the single write entry point and replaces the scattered `saveExperimentGraph` / the direct writes to `experiment_process` |
| 2 | Graph validator | Validates the required fields, the isolated nodes, the illegal edges and the cycles (at least S1 must not save a graph that "cannot be linearised") |
| 3 | Graph compiler | `graph -> experiment_process`; to begin with it only supports the linear / linearisable scenarios |
| 4 | Single-transaction write | `experiment_graph` / `experiment_process` / `experiment.version` are completed in the same transaction |
| 5 | Close the existing write entry point | The workflow table on the detail page becomes read-only; if the existing API is called it returns a clear error instead of silently accepting it |

### 2.3 Frontend tasks

| # | Task | Explanation |
|---|---|---|
| 1 | The canvas save calls the new API | The graph and the workflow table are no longer saved separately |
| 2 | The workflow table on the detail page becomes read-only | The "generated by the canvas" note and the jump button are kept |
| 3 | Disable `fork/parallel` | Until the S2 semantics are ready, no new inexecutable topology may be drawn |
| 4 | Locate the save failure | Highlight directly "which node / edge is invalid" |

### 2.4 Regression tests

| Category | Test case |
|---|---|
| Unit test | Graph validator: an empty graph, an isolated node, an illegal back edge, a workflow with no binding |
| Unit test | Graph compiler: a 3-node linear graph -> `seq=1..N` |
| Integration | After a successful save `experiment_graph` and `experiment_process` are updated at the same time |
| Integration | When the compilation fails, neither side is written to the database |
| Integration | When a `process` write failure is simulated, `graph` is rolled back as well |
| UI/e2e | After the order is changed on the canvas, the order of the workflow table on the detail page changes in sync |

### 2.5 Risks

- **The biggest risk**: the existing entry point is not write-closed, which produces "looks unified, actually a dual write"
- **The secondary risk**: the validator is too lax and lets the S2/S3 semantics leak into S1 too early

### 2.6 Exit conditions

1. The workflow table can no longer be edited
2. The execution order after the canvas save matches the workflow table on the detail page
3. A failed save never leaves a half-finished result

## 3. S2 · Partial-order execution

### 3.1 Goal

Let the workflows inside an experiment no longer have only the linear `seq` order, but support:

- predecessor / successor dependencies
- join waiting
- priority on the same level

**The current default goal is a "partial order", not "real concurrency"**.

### 3.2 Which version to build first

| Version | Semantics | Recommendation |
|---|---|---|
| **S2-A conservative version** | Only a partial order is supported; the scheduler advances only one of the currently executable set at a time, **no wall-clock overlap is promised** | **Recommended first** |
| S2-B complete version | Real concurrent dispatch; the three resource layers + the wait-for graph come with it | Only do it if you are willing to take on the resource governance at the same time |

> The current recommendation: **do S2-A first**.  
> Reason: it can first deliver "the dependency relations are expressed correctly", without cramming "multi-resource deadlock governance" into the same batch of changes.

### 3.3 Backend tasks

| # | Task | Explanation |
|---|---|---|
| 1 | Add `experiment_process_edge` | It expresses the partial order instead of relying on `seq` alone |
| 2 | Rework the dispatcher | From "run them one by one by `seq`" to "pick the executable nodes whose in-degree is 0" |
| 3 | Join waiting | The successor is only released when all the predecessors are done |
| 4 | `priority` takes effect | When several are executable on the same level, the priority decides who runs first |
| 5 | Fix the failure policy | To begin with, keep "any failure stops the whole order" |

### 3.4 The extra tasks needed if S2-B is done

| # | Task | Explanation |
|---|---|---|
| 1 | Bring the three-layer resource model into the experiment layer | Position / port / robot arm |
| 2 | Wait-for graph + cycle rejection | It prevents the multiple branches from forming a cross-layer waiting cycle |
| 3 | Rate-limit the concurrent dispatch | It prevents all the executable branches from being pushed onto the lock-contention path at once |
| 4 | Observability | A wait-for graph snapshot, the deadlock-rejection log, the state of the concurrent branches |

### 3.5 Regression tests

| Category | Test case |
|---|---|
| Unit test | The A→B→C partial order is correct |
| Unit test | `priority` takes effect when A and B are on the same level |
| Unit test | C can only run after A/B are done (join) |
| Integration | When one of them fails, the whole order stops |
| Integration | The partial-order graph can be reconstructed in the detail page / execution history |
| Extension (S2-B only) | The three-branch A→B→C→A deadlock construction is rejected instead of hanging |

### 3.6 Risks

- **The biggest risk**: smuggling "concurrency" in under the name of "partial order" without doing the resource governance at the same time
- **The second risk**: `priority` is misunderstood as preemption of what is running, instead of "who is dispatched first on the same level"

### 3.7 Exit conditions

1. At least 1 non-linear experiment can correctly express the predecessors / the join
2. The document explicitly states whether it is currently `S2-A` or `S2-B`
3. If it is `S2-A`, neither the UI nor the document may suggest that "real concurrency is already supported"

## 4. S3 · Batched execution

### 4.1 Goal

Support "splitting one experiment into several logical batches", and:

- each batch can be executed on its own
- a failing batch can be re-run on its own
- the re-run history is traceable

### 4.2 Data model

| Table | Semantics |
|---|---|
| `experiment_batch` | The logical batch (which batch, the current state, the sample set / range) |
| `experiment_batch_run` | Every actual execution of that batch |

### 4.3 Backend tasks

| # | Task | Explanation |
|---|---|---|
| 1 | Batch splitter | Generates the logical batches from `batch_split` and the sample set |
| 2 | Batch-creation logic | Writes `experiment_batch` before the first run |
| 3 | Execution archiving | Every execution writes an `experiment_batch_run` and increments `attempt_no` |
| 4 | Aggregation state machine | Aggregates the batch state and the overall experiment state |
| 5 | Re-run entry point | Supports "re-run only the failed batches" |

### 4.4 Frontend tasks

| # | Task | Explanation |
|---|---|---|
| 1 | Add a batch view to the experiment detail page | The state, the attempt count and the corresponding run of each batch are visible |
| 2 | Re-run button for a failed batch | Only enabled for a failed batch |
| 3 | Expand the batch history | The several attempts on the same batch can be viewed |

### 4.5 Regression tests

| Category | Test case |
|---|---|
| Unit test | 96 samples / `batch_split=24` -> 4 batches |
| Integration | After the 2nd batch fails, only the 2nd batch is re-run and the attempt history is kept |
| Integration | The successful batches are not affected by the re-run of the failed batch |
| UI/e2e | The detail page shows the batch, the attempt count and the linked run |

### 4.6 Risks

- **The biggest risk**: making the "logical batch" into a "pointer to the current run", so that a single re-run overwrites the history
- **The second risk**: the mapping between the batches and the samples is unstable, so the sample set drifts on a re-run

### 4.7 Exit conditions

1. After any batch fails, only that batch can be re-run
2. At least two attempts of history are kept
3. The aggregation rules of the overall experiment state and the batch state are written down clearly and are covered by tests

---

## 5. The suggested scheduling order

| Order | What to do first | Reason |
|---|---|---|
| 1 | **S1** | Get rid of "the canvas does not take effect" first, and remove the false premise for continuing the design |
| 2 | **S2-A** | Deliver "the partial order is correct" first, without packaging the resource deadlock governance together with it |
| 3 | **S3** | Add the batches only after the execution semantics are stable, to avoid changing the state model while it runs |
| 4 | S2-B (optional) | Only when real concurrency is genuinely needed, bring the three resource layers + the wait-for graph in as well |

---

## 6. The 3 decisions still to be made before the development starts

1. **Does S2 choose A or B in the end**
   - This is the watershed between the cost of the resource governance and the speed of the delivery
2. **How the batch-to-sample mapping is stored**
   - Is it `experiment_sample.batch_no`, or a separate batch-to-sample mapping table
3. **Does a linear experiment allow a light reordering inside the table**
   - If it does, be careful not to reintroduce the second entry point "the table was changed but the graph was not"

---

## 7. The conclusion in one sentence

`M9.5` is no longer a "draft of a direction" now, it is a "**design plan that tasks can be scheduled against**".  
But when the development really starts, it is recommended to proceed in the order **S1 → S2-A → S3**, and to keep "real concurrency + the wait-for graph" as a separate upgrade instead of shipping it in the first version.

## 8. S3 · The go-ahead decisions and the interface contract (proposed by the implementer on 2026-11-03)

> Purpose: to settle the open items of §6 so that the backend / frontend can start in parallel. These are **the implementer's decisions**;
> if the reviewer disagrees, they can be overturned during the implementation (the cost: changing a column / changing a JSON field).

### 8.1 The decisions

| # | Decision | Reason |
|---|---|---|
| D1 | The batch switch: `experiment.batch_split int NULL` = the number of samples per batch; `NULL` = no batching (**the default behaviour is completely unchanged**) | One column switches it on, no migration of the data |
| D2 | The sample mapping: **on the first execution**, in ascending `experiment_sample.sample_id` order, cut off a batch every `batch_split` samples; snapshot that batch's `[{sampleId, barcode}]` into `experiment_batch.samples jsonb`; from then on a re-run only uses the snapshot | The snapshot = the sample set does not drift on a re-run (the second risk of §4.6), and no separate mapping table has to be built |
| D3 | The run semantics: one 「Execute experiment」 of a batched experiment = run **all the batches that have not succeeded yet** serially by `batch_no`; one `experiment_run` per batch + one `experiment_batch_run(attempt_no)`; when a batch fails, **continue** with the following batches; when a pause hold is encountered, stop at the **batch boundary** and do not start the next batch | It reuses the existing `ExperimentExecutor` (one run per batch) and does not build a new executor; draft §5: any failure = the experiment failed, but the remaining batches can continue |
| D4 | The re-run: `POST /api/experiments/{id}/batches/{batchNo}/run` only runs that batch, with a new `attempt_no`, and the historical attempts are kept; only batches that are not `completed` are allowed | It corresponds to §4.1 / §4.3 #5 / §4.4 #2 |
| D5 | The variable injection: the variables of each batch run get `batchNo` (a numeric string) and `batchSamples` (a comma-separated string of the sample barcodes) appended; **the variables the user passed explicitly with the same name are not overwritten** | It does not break the existing variable semantics; the workflow parameters can use ${batchNo} |
| D6 | The state aggregation: a `running/queued` batch → experiment=running; a `paused` batch and no running one → paused; all `completed` → finished; no running/paused and any `failed/aborted` → failed; when `batch_split` is NULL the default logic applies | §4.7 #3 requires the rules to be written down clearly and covered by tests |
| D7 | The batches are **serial** to each other (2.0 does not run them in parallel); the batch boundary checks `RuntimeHold` / `stop_requested` | There is only one device; S2-A only promises a partial order |

### 8.2 The data model

| Table / column | Definition |
|---|---|
| `experiment.batch_split int NULL` | The number of samples per batch; NULL = no batching |
| `experiment_batch` | id bigserial PK, tenant_id, experiment_id FK, batch_no int, sample_count int, samples jsonb, status varchar, created_at, updated_at; UNIQUE(tenant_id, experiment_id, batch_no) |
| `experiment_batch_run` | id bigserial PK, tenant_id, batch_id FK ON DELETE CASCADE, experiment_run_id FK, attempt_no int, status varchar, started_at, finished_at, error text; UNIQUE(batch_id, attempt_no) |

The `status` values reuse the existing vocabulary: `pending / queued / running / paused / completed / failed / aborted`.
The DDL has to update both the shards (`pg_rebuild/schema/20_kernel.sql` or `96_schema_fix.sql`) and the merged artefact
`pg_rebuild/schema/90_all_in_one.sql` (run `pg_rebuild/merge.sh`), and it has to pass `scripts/check-schema-sync.sh`.

### 8.3 The interface contract

**GET `/api/experiments/{id}/batches`**

~~~json
{
  "experimentId": 813,
  "batchSplit": 24,
  "items": [{
    "id": 1, "batchNo": 1, "sampleCount": 24,
    "samples": [{"sampleId": 101, "barcode": "BC001"}],
    "status": "failed",
    "attemptCount": 2,
    "currentRunId": 41,
    "runs": [
      {"batchRunId": 3, "runId": 40, "attemptNo": 1, "status": "failed",
       "startedAt": "2026-11-03 19:00:00", "finishedAt": "2026-11-03 19:02:00", "error": "..."},
      {"batchRunId": 5, "runId": 41, "attemptNo": 2, "status": "failed",
       "startedAt": "2026-11-03 19:05:00", "finishedAt": "2026-11-03 19:07:00", "error": "..."}
    ]
  }],
  "summary": {"total": 4, "pending": 1, "running": 0, "completed": 2, "failed": 1}
}
~~~

When `batchSplit` is null, `items` is an empty array (the frontend hides the batch cards accordingly).

**POST `/api/experiments/{id}/batches/{batchNo}/run`**

The request body may contain `{"vars": {"k": "v"}}` (the same as the existing experiment execution). The response:

~~~json
{"experimentId": 813, "batchNo": 2, "runId": 42, "batchRunId": 5, "attemptNo": 3,
 "status": "completed", "doneSteps": 12, "totalSteps": 12, "error": null}
~~~

An already-succeeded batch / a batch that does not exist → 400 `{"error": "..."}`.

**POST `/api/experiments/{id}/run` (the existing interface, extended for batching)**

The existing fields are kept (`status / doneSteps / totalSteps / error`); when batching, the following is appended:

~~~json
{"batchSplit": 24,
 "batches": [{"batchNo": 1, "runId": 41, "batchRunId": 2, "attemptNo": 1,
              "status": "completed", "doneSteps": 12, "totalSteps": 12}]}
~~~

`status` is the aggregated experiment state (D6).

### 8.4 Acceptance (= §4.7, every item verifiable)

1. After any batch fails, only that batch can be re-run — a DB integration test + the UI button
2. At least two attempts of history are kept — `experiment_batch_run.attempt_no` + the history API
3. The state aggregation rules are written down clearly and are covered by tests — D6 + a unit test
4. When `batch_split` is NULL the behaviour is exactly the same as today — a regression assertion

## 10. S3.1 · Resume write-back / configuration entry point / re-run concurrency (implementer, 2026-11-03)

> Corresponds to the remainder 1/2/3 of §9. The decisions are proposed by the implementer and the review can overturn them.

### 10.1 What has to be solved

1. **After a run inside a batch is recovered / stopped, the batch layer is not updated and it overwrites the aggregated state**: @@ExperimentScheduler.executeOne@@
   when a queued run is recovered it goes through @@exec.run(exp, null, runId)@@ with the default reload → @@syncExperimentStatus=true@@;
   when a batch run is recovered and finishes, the experiment table is overwritten by **the state of the single run** (e.g. a batch that was paused is recovered and finishes,
   the experiment goes straight to finished while the other batches are still pending). @@RunControl.stop/resume@@ is the same.
2. A **concurrent re-run of the same batch** can hit @@UNIQUE(batch_id, attempt_no)@@.
3. **@@batch_split@@ only has a DB entry point**, it cannot be configured on the page (the DoD "the feature can be demonstrated" is not met).

### 10.2 The decisions

| # | Decision |
|---|---|
| D8 | **The unified write-back point** @@BatchOrchestrator.onRunStatusChanged(long runId)@@: a non-batch run returns false straight away (zero change on the default path); a batch run updates the attempt row (status/error/finished_at) + the aggregated batch state + the aggregated experiment state (D6). **Idempotent**. |
| D9 | **The scheduler recovery**: @@ExperimentScheduler.executeOne@@ first probes whether the run belongs to a batch → a batch run runs with @@syncExperimentStatus=false@@ and calls D8 at the end; the exception fallback that marks it failed also calls D8. |
| D10 | **The run control**: @@RunControl.stop/resume@@ **skips** the single-run @@syncExperimentStatus@@ for a batch run and goes through D8 instead (after a resume status=queued; a stop on a non-running state lands aborted and then status=aborted). The branch in which the stop request is set (running) does not change the state and needs no write-back. |
| D11 | **The configuration entry point**: @@PUT /api/experiments/{id}/batch-split@@, body @@{"batchSplit": N}@@ or @@{"batchSplit": null}@@; N must be >0 (0 is treated as null = clear); **the modification is refused when batch rows already exist** (the snapshot of D2 is fixed), 400 explains "clear the batch data first". The frontend action row gets a 「Batch settings」 dialog. |
| D12 | **The re-run concurrency**: @@BatchOrchestrator.executeBatch@@ does a @@SELECT id FROM experiment_batch WHERE id=? FOR UPDATE@@ inside the same transaction before it computes @@attempt_no@@ and INSERTs, which serialises a same-batch re-run. |
| D13 | **The pure-logic addition**: @@BatchPlanner.normalizeSplit(Integer)@@ (null/<=0→null, otherwise the value as it is), for the validation of D11, unit-testable. |

### 10.3 The interface contract (D11)

~~~
PUT /api/experiments/{id}/batch-split
{"batchSplit": 24}    // set 24 samples per batch
{"batchSplit": null}  // switch the batching off (only allowed when no batch has been created yet)

200 → {"experimentId":818,"batchSplit":24,"updated":true}
400 → {"error":"实验已有批次（快照已固化），不能改 batch_split；要改请先清批次数据"}
~~~

### 10.4 Acceptance (every item verifiable)

1. After a batch run is recovered successfully: @@experiment_batch_run.status@@ and @@experiment_batch.status@@ are in sync,
   and the experiment state is aggregated per **D6** (it must not become the state of a single run).
2. After the run of a batch is stopped, the batch table syncs to aborted/failed.
3. **The behaviour of a non-batch run is exactly the same as before the change** (a regression assertion: it does not write the batch table, and the experiment state is still synced by the single run).
4. The configuration API is available; the change is refused when batches already exist; an invalid value gives 400.
5. A concurrent re-run of the same batch does not raise a unique-key conflict (the row lock serialises it).
6. The pure-logic / with-database self-tests + the gate threshold are synchronised (the Lead adjusts ci-gate centrally).

## 11. S3.2 · Batched asynchrony (the scheduler dispatches batch by batch, implementer, 2026-11-03)

### 11.1 The interface contract (POST /api/experiments/{id}/run?async=1)

- When `batch_split` is empty: it goes through `scheduler.submit` **as it is** (one run for the whole order), and the response is unchanged
  `{"experimentRunId", "status":"queued", "async":true}`.
- For a batched experiment: it creates / takes the queued run of "the next batch that has not succeeded" and re-queues it; there are four kinds of 200 response:
  - **CREATED / EXISTING** (can be queued): `{"experimentId","experimentRunId","batchNo","batchRunId","attemptNo","status":"queued","async":true}`
  - **HELD** (there is an on-site hold at the batch boundary): `{"experimentId","experimentRunId":null,"held":true,"status":"paused","batchNo","holdReason"}`
  - **NO_MORE** (no more batches): `{"experimentId","experimentRunId":null,"status":<the aggregated experiment state>}`
  - A repeated POST: when a batch run that has not finished already exists, EXISTING is hit (nothing new is created, the 200 returns the actual state).
- The semantics of `runAll/runBatch` of the synchronous `POST /run` are unchanged (the regression assertions are all green).

### 11.2 The re-queue semantics (aligned with D3)

After a batch run has finished (the D8 write-back is done and the island lock is released) → if the actual state is not `aborted/paused` and there is **no overlapping hold**,
the run of the next batch is created and re-queued:
- **A failure continues**: both a failed and a completed batch continue with the next batch; a failed batch is not retried in place;
- **aborted stops**: after a manual stop the remaining batches stay pending and are not re-run automatically;
- **A hold stops at the batch boundary**: the candidate batch is marked paused and no attempt is created (after the hold is released a person has to start it again, see §11.3);
- The D5 batch variables (batchNo / batchSamples) are injected by the scheduler, which looks them up from the batch snapshot.

**The new semantic boundaries confirmed at the wrap-up (recorded, not opened as a separate item)**:

- The variable inheritance of the re-queue **strips** `batchNo`/`batchSamples`: after the executor finishes it writes the merged variables back into run.variables,
  so if they were passed on as they are, the batch context of the previous batch would overwrite the next batch with the identity of the "explicit user variables"; therefore only the explicit user variables are inherited.
- When the scheduler executes a queued run it reads run.variables as the overrides (**snapshot semantics**): after a recovery / a restart it keeps the variables of the submission,
  and it does not fetch the current defaults of the experiment again (if the review thinks it should fetch them again, that has to be discussed separately).
- `loadBatches` is a read-side derivation; on the write side `derivedBatchStatus` (D8) still stores the value per "the state of the latest run",
  so a batch that is paused and has a failed attempt would have its original value in the table changed if D8 writes it back — the candidates for the automatic continuation are limited to "no attempt",
  it is not triggered normally, and it is recorded as a known boundary.
