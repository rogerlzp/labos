## 2. Core design decisions (the ones that were signed off)

### 2.1 Not the banker's algorithm, but a wait-for graph

**Reason**: the banker's algorithm requires "declaring up front how many resources are needed at most", but workflows have branches, so it cannot be declared.
If you declare for the worst case, every workflow has to take "the whole island" — **the concurrency goes to zero**.

**A claim that was wrong earlier**: at one point it said "the banker's algorithm assumes resources are preemptible, so it does not apply" — **this is a misstatement**.
The banker's algorithm is designed for non-preemptible resources in the first place; its real premise is **knowing the maximum demand in advance**.
It has been corrected (3 places in the documentation).

### 2.2 Four resource layers, not three

```
L1 position  independent, for the whole task
L2 channel   semaphore (capacity 1/2/N), action level
L3 gate      action level — with the gate not open, the robot arm reaching in will crash
L4 robot arm action level
```

**The gate was the last one added**: it was missed at first; the user pointed out that "if the centrifuge door is not open, the robot arm reaching in will crash".

### 2.3 Fixed total order: gate → channel → position → return position → robot arm

**Why the gate comes first**:

```
Gate opened but the robot arm not obtained  →  close the gate and give up, the cost is small
Robot arm obtained, only then the gate turns out not to open  →  the plate is already in the gripper, it cannot be put back
```

**invariant**: **the plate does not leave the source position until all resource requests have completed.**

### 2.4 The return-position commitment cannot be released

**The contradiction buried in the M1 design**:

- D105 requires the return position to be reserved for the whole pickup
- D111 requires the "occupied but not yet used" positions to be released on a pause
- **The reserved return position is exactly "occupied but not yet used"**

**Releasing per D111**: pickup → fault pause → put it back on the return position → someone else takes it → after the resume the deadlock reproduces.

**The solution**: `release_exempt` distinguishes **reservation** (releasable) from **commitment** (not releasable).

### 2.5 The resource unit is a "capability", not a "device instance"

**The pitfall**: M3 originally computed by `params.equipment_instance_id`, and the result was "occupying ID1183 still allowed to start".

**It only showed up when querying the data**: `equipment_instance_id=155` is **historical dirty data** (it does not exist in `device_instance`),
the actual execution picks from the pool by `capability_id` — **INCUBATE has 48 candidates**.

**Lesson**: an implicit contract of this kind — "reading the code makes you think it works per instance, while it actually works per capability" — **cannot be seen by reading the code alone**.

### 2.6 Three pause kinds

| Kind | Resume condition |
|---|---|
| `paused_fault` | **Resumes automatically once the heartbeat recovers**, no person needed |
| `waiting_human` | **A person must confirm** |
| `paused_unknown` | **An inventory + a correction are required** |

**Collapsing them into one "pause" leads to**: the device is fine again but nobody knows it can continue, or people think it was handled when it was not.

## 4. ⚠ Points I put up for review myself (ordered by the cost of rework)

### 🔴 1. Zero real-device verification — this is the biggest risk

**All 45 acceptance checks and all 104 unit tests ran on the simulator.**

**What the simulator cannot verify**:

| Item | Why it cannot be verified |
|---|---|
| **The real opening/closing time of the gate** | The simulator returns immediately; the real one may take 3-30 s |
| **Whether the position coordinates are accurate** | The simulator's coordinates are made up |
| **Whether the robot arm can reach those positions** | It needs real motion and collision detection |
| **How many actions a `Transfer` actually counts as** | On a real device "grasp - move - place" may be three separate actions, and then the "action level" definition of L4 has to change |
| **The real meaning of a channel with `capacity > 1`** | Can two plates really pass at the same time on a wide conveyor? |

**This one is not "to be improved", it is "unverified"**. Every design rests on these assumptions.

### 🔴 2. The semantics of `order_in_device` depend on the site

**The user was explicit**: "L1 cannot be settled now, the different positions have to be determined on site".

**So the system does not assume whether `L1` is the bottom or the outer layer** — everything is configured on site.

**Risk**: if the site configuration is wrong (or missing), **the robot arm will go to the wrong position**,
and the system **will not report an error** (it only executes what it was configured to do).

**Mitigation**: positions with `fill_status != 'ok'` do not take part in scheduling.
But **nobody checks "whether it was configured correctly"**.

### 🟠 3. The main-chain coarse screening may be overly conservative

**The "heaviest on resources" strategy**: it automatically picks the branch that needs the most devices.

**Problem**: **the exception branch often needs more devices** (e.g. a failure has to go through the retest flow),
computing against it makes the coarse screening **overly conservative** and rejects cases that could actually have run.

**The current answer**: the pop-up offers "Start anyway" and lets the user decide.
**But there is no statistic for "how many times was it rejected, and how many of those could actually have run"**.

### 🟠 4. The "false rejection" of the wait-for graph is not measured

**The wait-for graph rejects requests that would close a cycle**, but some requests **could have succeeded after waiting**.

**Today**: only `rejectedCount` is recorded; **we do not know how many of them were real deadlocks and how many were misjudgements**.

**Long-term effect**: if the false-rejection rate is high, users will feel that "the system keeps saying no" and will lose trust.

### 🟠 5. `estimatedWaitSeconds` is inaccurate

**Algorithm**: `run_node.estimate_sec` − the seconds already elapsed.

**Problem**:
- `estimate_sec` is filled in at authoring time, so it may be inaccurate
- if several nodes are running, only the last one is taken
- **in actual testing it often shows 0 seconds** (the estimate has been exceeded but the node has not finished)

**What has been done**: a 0-second value is shown as "Less than 1 minute", and the screen marks it as an estimate (estimate only).

### 🟡 6. Unblocking a plate position depends on `possible_locations`

**Found during testing**: `locatePlate` relies on `plate.possible_locations` to find the positions that have to be unblocked.

**If that field is lost** (someone edits the database by hand, data is imported), **the block can never be lifted**.

**The current answer**: `markPlateUnknown` always writes that field.
**But there is no fallback** (e.g. a reverse lookup "by block_reason + time range").

### 🟡 7. The script node (L3) is designed but not implemented

**Design**: `docs/自定义脚本节点-设计.md` (separate-process sandbox + approval + audit).

**Status**: **design only**. 3 weeks of work, the highest risk.

**If a customer asks for "querying an external system"**, this has to be built, and it must come with OS-level isolation.

## 8. Three things the review is asked to focus on

### ① Do these designs hold on a real device

**The person who knows the equipment best should answer**:

| Question | Impact |
|---|---|
| Is a `Transfer` one action or three (grasp / move / place)? | It decides the "action level" definition of L4 |
| Can the gate state really be inferred from "the action succeeded"? | What if it is mechanically jammed but returns success |
| Can a wide channel really take two plates at the same time? | It decides whether `capacity > 1` means anything |
| How large is the position-coordinate error? | It decides whether a tolerance check has to be added |

### ② Is the division of labour between "coarse screening + fine pipe" reasonable

**The coarse screening may be wrong** (at worst it waits a long time or rejects falsely), **the fine pipe must not be wrong** (it guarantees no deadlock).

**The value of this division of labour**: the user gets feedback when they press start.
**The cost**: 1.5 extra weeks, and the false-rejection rate of the coarse screening is not measured.

**If the customer only ever runs 1-2 experiments**, all of this is wasted work —
the **`lab_profile.max_parallel` configuration item** exists exactly for that (fill in 1 and only the device locks are used).

### ③ Do the screens cover the real operating flow

**The three pages today**: pre-flight → monitoring → pause handling.

**Not covered**:
- Plate-position inventory (today it can only be reached from the paused queue)
- Troubleshooting guidance after a device fault
- Batch operations (other than batch resume)

### 8.1 Minimum real-device verification checklist (added by the R4 review)

> Review 20261102-02 R4 pointed out that disclosing "zero real-device verification" without offering a way out amounts to leaving the problem to the reader.
> This is the first step towards removing that risk, **and it is the precondition for scheduling**.

| # | What to verify | How to verify | Pass criterion | Estimate |
|---|---|---|---|---|
| 1 | **The opening/closing time of the gate and the state inference** | Connect a real centrifuge to the console, send `OpenDoor`, time it; after a person has closed the gate by hand, send `Deposit` | Opening ≤30 s; after a manual close the system can refuse entry instead of crashing | 0.5 day |
| 2 | **Is a `Transfer` one action or three** | Run one complete transfer with a real robot arm and count the commands in the driver log | If it is three separate commands → the "action level" definition of L4 has to be split, and the moment at which `TransferPlan` requests its resources has to change | 0.5 day |
| 3 | **Position coordinates and reachability** | Teach 4 layer positions, let the robot arm walk to each of them and check the deviation by eye | Deviation ≤5 mm (otherwise placing a plate will jam or stack); `order_in_device` works once it is configured on site | 1 day |
| 4 | **The real meaning of a wide channel with `capacity>1`** | Find a multi-station channel and put two plates on it at the same time | If both can pass → the semaphore model holds; if not → capacity stays 1 and the implementation is simplified | 0.5 day |
| 5 | **The real deviation of `estimate_sec`** | Run the same action 10 times and record the distribution of the actual durations | Deviation ≤±30% → the coarse-screening `estimatedWait` is meaningful; otherwise it can only show "Unknown" | 0.5 day |

**Total: 3 days (the equipment has to be on site + someone who knows the equipment has to cooperate)**.
**If any one of them does not hold, the corresponding code has to change** — which is why the checklist has to come before the real device.
