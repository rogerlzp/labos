## Comment list

### R1 (P1 blocking) Conceptual error: the premise of the banker's algorithm is not "preemptible"

**Location**: `设计审核包.md` risk 3; the last section of `并发调度决策记录.md` D12; `暂停恢复与故障处理-设计.md` §7.

**Problem**: all three documents say "the premise of the banker's algorithm is that resources are preemptible, the physical world does not allow that, so it cannot be used / loses its meaning". **This is a misstatement of the
classic algorithm.** The banker's algorithm is the other way round — it is a deadlock-avoidance algorithm designed for **non-preemptible** resources: it avoids deadlock by refusing to enter an unsafe state, and no preemption
happens at any point. Of the four deadlock conditions, "no preemption" is precisely one of the conditions under which deadlock exists; the banker's algorithm avoids deadlock *while acknowledging* non-preemptibility.

The banker's algorithm really has only two premises:
1. **The maximum resource demand of every process is known in advance**;
2. A process releases all of its resources within a finite time once it has obtained all of them.

**Impact on this project**: the conclusion (do not use the banker's algorithm) still holds, but **the correct reason is premise 1** — workflows have branches, so the maximum demand cannot be known in advance; and the
resources of this project are not homogeneous and countable (a position has an identity, a robot arm has spatial constraints), so they do not fit the banker's "resource instance counting" model.

**Remediation requirement**: fix the reasoning in the three documents. The reason was wrong, and even though the conclusion is right, later implementers will draw inferences from the wrong premise (for example that "adding
preemption would make the banker's algorithm applicable").

### R2 (P1 blocking) Hard contradiction: the D5 return-leg reservation × the D12 pause release

**Location**: `并发调度决策记录.md` D5 vs D12; `暂停恢复与故障处理-设计.md` §5 "releasing the resource is mandatory".

**Problem**:
- D5: when picking up a plate, **reserve the return position**; it is held for the whole task. This is the root-cure for form 1 (return-leg deadlock).
- D12 / pause-and-resume §5: on a fault pause, **release the "reserved but unused" positions**, otherwise the whole island is deadlocked.

**The return-leg reserved position is precisely a "reserved but unused" position.** Workflow fault pause → per D12 the return-leg position is released → another workflow takes it → after manual recovery the workflow resumes →
the return position is gone → **form 1 deadlock recurs exactly as before**, and the D5 protection is completely ineffective on the fault path.

**Remediation requirement**: an exemption rule must be defined before any code is written. Recommendation: the return-leg reserved position (the one declared by `returnTo`) is **explicitly exempted** from the pause-release
rule, and only "look-ahead reserved positions that do not declare returnTo" may be released; and D5 and D12 must cross-reference this exemption in both places.

### R3 (P1 blocking) The multi-resource acquisition order of a Transfer has no invariant, and the "refusal" semantics do not hold in the physical world

**Location**: `资源模型与死锁避免-设计.md` §2, §3.

**Problem**: one Transfer actually has to hold **L3 robot arm + source L2 + target L2 + target L1 (+ D5's return-leg L1)** at the same time. The existing `tryReserveTransfer` orders only the two positions by ascending id; **there
is no rule at all for the acquisition order across resource types**.

Worse is the timing: if it is implemented as "the robot arm grabs the plate first (L3 held, the plate has already left the source position) → then requests the target L1/L2 → is refused by the wait-for graph", the **plate is
already on the arm** at that point, and "refuse this request, return a failure and retry" cannot physically be carried out — the plate cannot hover.

**Remediation requirement**: the design must add one hard invariant: **the plate does not leave the source position until every resource request has completed (request first, grab afterwards)**; and it must define a fixed
acquisition order for the five resource classes (recommended: L3 → source L2 → target L2 → target L1 → return-leg L1, all following the same topological order). The wait-for graph is the safety net, not a substitute for the
acquisition order.

### R4 (P1 severe) The granularity of the wait-for graph contradicts the parallel gateway; the `auto` switch introduces a race

**Location**: `资源模型与死锁避免-设计.md` §5; the "optimisation" section of `并发调度决策记录.md` D10.

**Problem**:
1. The nodes of the wait-for graph are runs, but D6 allows the multiple branches of a parallel gateway within a single run to **acquire resources concurrently**. A run-level wait-for graph cannot express branches within a run
   waiting on each other — it either misjudges a self-loop or misses the detection.
2. `LABOS_DEADLOCK_GUARD=auto` uses `running > 1` as the test, which excludes exactly the "parallel within a single run" case from detection. The review package lists `hasParallelNode` as an "optionally more precise" refinement
   — **it is not optional, it is mandatory**.
3. The COUNT test has a real race: two runs start at the same time, each of them sees `running = 1`, and each of them switches detection off.

**Remediation requirement**: the recommendation is to **delete `auto` and keep detection always on**. The author calculated the overhead as microseconds — the switch saves microseconds and introduces a race, missed detections
and one configuration item that operations has to understand. The nodes of the wait-for graph should be "execution branches" rather than runs.

---

### R5 (P1 severe) There is no answer for livelock / starvation after a refusal

**Location**: `资源模型与死锁避免-设计.md` §6, second batch, "after a refusal wait 200ms and retry, at most N times".

**Problem**: when the refused party retries, the cycle is most likely still there (the holders on the cycle have not finished), so it will **be refused repeatedly**. The design gives no answer to:
- the backoff strategy (a fixed 200ms makes the retries oscillate in step);
- the ageing mechanism (the one that has waited longest goes first, otherwise some workflow may be the one refused forever — the wait-for graph naturally favours whoever arrived first);
- what happens when the N attempts are exhausted (fail? escalate to an alert? switch to `waiting_human`?).

**Remediation requirement**: add the complete post-refusal strategy. At the minimum: exponential backoff + ageing by waiting time + switch to `waiting_human` with an alert once exhausted (to connect with the D14 state
machine).

---

### R6 (P2 normal) The terminal event of the L2 entry/exit "pass-through" is undefined

**Location**: `资源模型与死锁避免-设计.md` §2 "the entry is only occupied for the few seconds the plate is passing through".

**Problem**: when is L2 considered released? Which signal is authoritative — the device ack, the position sensor, or the return of the command? The simulator does not expose this, and on a real device it is a source of races
(release too early and the next plate rear-ends it). In addition, the challenge raised by scenario A of the review package holds: if one plate-entry action takes 30 seconds, L2 is a de-facto serialisation point, and "two
plates entering B in parallel" is parallel only in the positional sense.

**Remediation requirement**: the design must state the event that decides the release of L2, and the real-device commissioning checklist must include "measured occupancy time of L2".

---

### R7 (P2 normal) The resource propagation rule after a plate becomes UNKNOWN is missing

**Location**: `暂停恢复与故障处理-设计.md` §4; `并发调度决策记录.md` D13.

**Problem**: after a plate is marked UNKNOWN, the design only says "pause every workflow involving that plate", but **it does not say what happens to the physical space it may be occupying** — the source position, the target
position, the robot arm's working space. Other workflows may put a new plate into a position that "might have a plate on it", causing a physical collision.

**Remediation requirement**: when UNKNOWN is triggered, block all the L1/L2 resources corresponding to its "set of possible positions" until the manual inventory clears them. In addition: the author's own "unattended at
night" problem really exists, so a degraded path should be added — if an UNKNOWN is not handled within N hours, automatically abort the related workflows and isolate the area instead of waiting forever.

## An independent judgement on "is this over-engineered"

The author's self-questioning is sincere, and it is right: **"how many experiments run in parallel in a day" is the first question of this case** and should precede all technical discussion. One perspective the author did not
mention is added here:

**Even if the answer really is 1-2 parallel, D5 (returnTo) cannot be cut.** Two parallel workflows are enough to trigger form 1 (return-leg deadlock) — the document's own derivation uses two experiments. So the candidates for
cutting are D10 (the wait-for graph) and part of D11-D14; **D5 is the minimum configuration for the two-parallel scenario**, and its place on the "cut" list has to be taken out.

The proposed decision tree:
- Parallel ≤ 1: D1-D4 are enough, D10-D14 are all shelved;
- Parallel 2-3: **D5 must be done**, the D10 wait-for graph can be downgraded to "timeout + alert" (form 2 does not form a cycle at 2 parallel; cycle detection is only needed at 3);
- Parallel ≥ 4: the full set is necessary.
