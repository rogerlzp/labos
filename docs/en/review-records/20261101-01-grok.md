## 1. Review text (as written)

### 1.1 Overall assessment

> The review guidelines can serve as an entry point, but they cannot serve as the standard. I checked the source code
> they name: The direction for troubleshooting severe bugs is already out of date, and the closing sentence "993
> processes at 100 % pass" describes walking the graph on the simulation bus as if the system were already usable.

### 1.2 The documentation system (four sets of "which one is authoritative")

> The repository root now has two sets of "which one is authoritative", and reviewers will each read their own.
>
> | Document | The position it claims | Reality |
> |---|---|---|
> | `LabOS2.0_功能规格说明书.md` (2.0-draft, 10-29) | Both the README and the review guidelines say "the functionality is governed by it" | The 2.0 of that time did not do React, did not do nest plate positions, and did not do multi-experiment scheduling. That code all exists now |
> | The design draft of 11-01 under `docs/` | The review guidelines list it as optional reading | Experiment orchestration, island locks, plate-position mutual exclusion and the rolling horizon are all written here, and they do not cross-reference the specification |
> | D1–D11 in `决策记录.md` | The decisions in chapter 12 of the specification | Chapter 5 of the review guidelines has another D1–D10 with the same numbers but different content |
> | `docs/modules/README.md` | The module index | It still says "the design documents are basically blank, corresponding to the 9 layers of the specification". This index itself was never marked obsolete |
>
> The guidelines mark the old scheduling plan in the root as obsolete, and that is right. What is missing is one
> harder sentence: **The specification of 10-29 only constrains what is still not done in the "release gate";
> behaviour already landed after 11-01 is governed by the code and the design drafts under `docs/`, and when the two
> sides conflict, change the specification first — do not make the reviewer choose one of two.**
> `docs/modules/README.md` should be marked obsolete like those old scheduling plans.

### 1.3 Two places in the architecture map that lead you astray

> `recovery/` is still the wrong decision (`RecoveryDecider`); the crash cleanup is in `workflow/StartupRecovery`,
> and there is no lease takeover as the guidelines claim. The PostgreSQL address was written as `192.0.2.1:6379`,
> which is the Redis port.

### 1.4 `putPlate` does not persist: the real root cause

> **`putPlate` does not persist — the phenomenon holds, the conclusion does not.** `c.commit()` is already outside
> the `if (n > 0)`.
>
> ```java
> // PositionLock.java:256-260
>                 if (n > 0) {
>                     markPlatePosition(c, plateId, resourceId, runId);
>                 }
>                 c.commit();
>                 return n;
> ```
>
> What is written next in the same transaction is a different table. The columns inserted by
> `PositionLock.markPlatePosition` are `plate_id`, `current_pos`, `current_run`, while the table creation script
> gives `plate` only `barcode` and `location_id`.
>
> ```java
> // PositionLock.java:393-408
>     private void markPlatePosition(Connection c, String plateId, long posId, long runId) {
>         try (PreparedStatement ps = c.prepareStatement("""
>                 INSERT INTO plate (tenant_id, plate_id, current_pos, current_run, status, updated_at)
>                 ...
>         } catch (SQLException ignore) {
>             // The plate table is redundant; a write failure does not affect the position lock
>         }
>     }
> ```
>
> In PostgreSQL, once this statement fails the whole transaction is void; the later `commit()` fails and rolls back,
> and the update of `position_state` is lost with it. The exception is swallowed, so the log does not necessarily
> contain the original SQL. The " `markPlatePosition` has been changed to an empty method" in the guidelines refers
> to the empty method of the same name in `WorkflowService`, not to this path that is still writing the wrong
> columns.
>
> Two other places record a failure as a success: `notePlateMove` does not look at the row count returned by
> `putPlate` and logs `[PLATE] ... -> pos=504495` even for 0 rows; `tryReserve` still returns `OK` when the update
> affects 0 rows and no record can be found (line 132 of `PositionLock.java`). The `plate=${plate}` in the log shows
> that the variable was not substituted — the same rule as "keep the original text when it cannot be found".
>
> The development log says there is no `[PLATE-ERR]`. With the source code as it is now, a failed `commit()` should
> print that line. If the two do not match, first check whether the class actually running is built from this source
> — that is exactly the "thought it was changed but it was not" that the guidelines themselves list.

### 1.5 The scheduler gap needs different wording

> `ExperimentScheduler.dispatch` really is EDD, priority and FIFO, plus the island lock and 2-second polling, with no
> promised window and no frozen zone. But section 1 of `多实验并行调度-动态规划与滚动排程.md` writes the rolling horizon up as a
> conclusion, and the 1.0 route in section 6 is island lock plus greedy. **The code matches section 6.** The document
> status is still "pending review". The gap is that target and method are mixed together in the same document, not
> that the code is missing an already-finalised design. The class comment says "greedy + rolling", but rolling does
> not appear in the implementation.

### 1.6 The remaining items can be kept, plus one addition

> The two sets of `long` IDs, the separate allocation and variable substitution written by
> `WorkflowService`/`GraphRunner` and by `ExperimentFlowRunner`, and the long connection treating `method_status=1`
> as a failure are all consistent with the code. One addition: **the default is still a short connection** —
> `TcpDriverAdapter` treats every status other than 2 as a failure, so the problem with 30-minute incubation is not
> limited to long connections. The description of the progress semantics and the `ApiServer` god class can also be
> kept.
>
> The island lock TTL is 2 hours, and the comment states that after it expires two experiments may run on the same
> island at the same time. This is a deliberate trade-off, and it is not written in the decision table of the
> guidelines.

### 1.7 The closing sentence passes

> `RealWorkflowRunner.runAll` has already been switched to `GraphRunner` and `SimulatedBus`, and it counts how many
> default edges the parallel gateway and the exclusive gateway took. This is **walking the graph on the simulation
> bus, not 993 processes passing on real devices**. The old `BATCH_VALIDATION_REPORT.md` still says 992 and
> topological sorting. The 993 and 100 % in the guidelines have no output of that run attached. Multi-experiment
> parallelism has the island lock, but plate-position pre-emption cannot yet be said to have prevented conflicts
> until `putPlate` is fixed.

### 1.8 Recommended order of the review comments

> 1. **Plate-position transaction.** After `tryReserve` commits the reservation, `putPlate` writes the wrong `plate`
>    table in the same transaction, and the rollback takes the position reservation with it. `notePlateMove` then treats
>    the return value as a success.
> 2. **Two sets of IDs and two execution paths.** Value types are the right direction. Before that, first confirm
>    whether the candidate pools of `ExperimentFlowRunner.instanceIdOf` and `WorkflowService` use the same mapping.
> 3. **Does a failure really stop the flow?** The experiment orchestration states that a failure stops the flow
>    immediately; a step that fails to persist is caught and the flow continues (the "losing data is better than
>    stopping the flow" in `WorkflowService`). Both statements hold at once, and they must be looked at separately
>    during the review.
> 4. **Documentation hierarchy.** The specification, the design drafts, the decision numbers and the module index — four
>    sets of statements. This is worth converging before the frontend styling.

## 4. Reflection on the review method itself

### 4.1 Why I could fool myself

| Phenomenon | Psychology |
|---|---|
| `putPlate` returned a pos, so I concluded it had succeeded | **I stopped verifying as soon as the return value matched the expectation**, without checking whether the return value really meant success |
| 993/993 at 100 % and I said "the processes passed" | **I wanted to produce a good-looking conclusion** and treated the simulation as reality |
| `replace` failed silently three times | Each time I ran `s.replace()` and did not verify — **the tool would normally have raised an error** |

**What they have in common: the acceptance criterion was "it looks right", not "the data proves it".**

### 4.2 What the external review added

| What I saw | What the review saw |
|---|---|
| `putPlate` returned a pos → success | The `plate` table is written with the wrong columns in the same transaction → everything is rolled back |
| `recovery/` has a lease takeover (as the document says) | It is actually `RecoveryDecider`, there is no lease |
| 993/993 = the processes passed | 993 processes walking the graph on `SimulatedBus` |
| The PG address | 6379 is Redis |

**The value of an external review: it does not accept "it looks right", only "this is what the code does".**

### The remediation for A3 **never actually took effect** (re-check conclusion, 2026-11-02)

The A3 row in the table above records "changed to reference `决策记录.md` | ✅ Changed", but **in fact only the heading
was changed**: the chapter 5 heading of `docs/评审指引.md` once read "the numbering is aligned with `决策记录.md`, no
separate set is started", **but the table content was never replaced**, and it still differs completely from the
content of chapter 12 of `决策记录.md`.

**Re-check characterisation**: this is "**changing the declaration without changing the entity**" — the same
disease as this project's "keep the old text and add an erratum" mistake on the banker misstatement, and its "claim
that D1-D20 are continuous with no duplicates" mistake in the decision record. Three independent recurrences show
that it is a **systemic defect**, not an occasional slip of the pen.

**Final remediation, 2026-11-02**: give up on "aligning to a single numbering source" and switch to **block
allocation** (`评审规范.md` §7): `决策记录.md` D1-D11 (unchanged) / `并发调度决策记录.md` D101-D119 / `开发日志.md` D201-D227 /
