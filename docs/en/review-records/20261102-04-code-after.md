## 3. Not fixed / misjudged / not fixed thoroughly (blocking items)

### 3.1 [P0-11] the `code` of the role seed does not match —— **still exists**, and it was misjudged as "non-existent"

**The factual layer (certain)**:

- The seed defines the roles: `app_role` is written with `code = 'admin' / 'operator' / 'viewer'`
  ([95_seed_data.sql:20-24](../../../pg_rebuild/schema/95_seed_data.sql#L20-L24)).
- The user roles are assembled: the JOIN condition requires `code = 'ROLE1' / 'ROLE2' / 'ROLE4'`
  ([95_seed_data.sql:71-82](../../../pg_rebuild/schema/95_seed_data.sql#L71-L82)).
- A `grep ROLE1|ROLE2|ROLE4` over the whole repository **only hits 95_seed_data.sql:78-80 and the review documents** (there is no
  third write).
- The **only change** to `95_seed_data.sql` in this round is adding `ON CONFLICT DO NOTHING` to the `app_user` insert (proved by
  `git diff af8d5f3 HEAD -- pg_rebuild/schema/95_seed_data.sql`), **not a single JOIN line was touched**.

→ **`ROLE1/ROLE2/ROLE4` never match in `app_role`, and the `user_role` assembly is permanently 0 rows. The defective entity is still
there.**

**Why it was judged "non-existent"**: the fixing party relied on
[20261102-03-code-self.md:472-474](../../评审记录/20261102-03-code-self.md#L472-L474) where a
`grep -rn "ROLE1\|ROLE2\|ROLE4" --include=*.java` with **zero hits** was taken as the proof that "after the re-check the problem
does not exist". **But the `--include=*.java` scope is wrong** — the problem is in the `.sql` (the JOIN is in the seed script); the
literal would never appear on the Java side. This is a **self-proof trap**: using a grep with a restricted scope to disprove "it
does not exist".

**Layered attribution (the affected layer, to be confirmed by the reviewed party)**: the runtime authentication goes through the
single column `sys_user.role`
([AuthService.java:130](../../../labos-kernel/src/main/java/com/labos/kernel/api/AuthService.java#L130)), and this set of RBAC
tables `app_role/user_role` **has no reader anywhere in this repository**. Therefore the original comment "the RBAC is completely
ineffective" should be **corrected** into two more accurate statements: (a) the seed assembly is ineffective (`user_role` is
permanently empty); (b) **two role models coexist and have split** (`sys_user.role` vs `app_role/user_role`), which comes from the
same root as the project's "dual paths" disease. Whichever statement is taken, **the conclusion "it does not exist" does not hold**.

### 3.2 [A1 · new] `P0-3` only creates the table, the seed is not connected —— the "dual paths" appear again in the authentication domain

- The authentication reads the table: `sys_user`
  ([AuthService.java:73,130](../../../labos-kernel/src/main/java/com/labos/kernel/api/AuthService.java#L73-L130)).
- The seed loads the tables: `app_user` + `user_role` ([95_seed_data.sql:61-82](../../../pg_rebuild/schema/95_seed_data.sql#L61-L82)),
  and there is **not a single `INSERT INTO sys_user`** in the whole repository.
- Consequence: after initialising with `deploy.sh` (`90_all_in_one.sql` + `95_seed_data.sql`), **`sys_user` is empty** → only the 1
  admin that `ensureSeedUser()` creates automatically can log in; the `admin/operator/viewer` in the seed (password `CHANGE_ME`) **are
  completely invisible in the authentication chain**.
- Characterisation: the fix of `P0-3` **only added the table DDL and did not connect the seed to the table the authentication actually
  reads** — which is exactly the root cause the re-check package states in §2, "**written ≠ connected**", once more, in the **authentication
  domain**.

### 3.3 [A2] the fix of `P1-4` is not thorough —— the same decision exists in two implementations and only one was changed

- Changed: [PositionLock.tryReserve](../../../labos-kernel/src/main/java/com/labos/kernel/driver/PositionLock.java#L144-L154) — the
  three-state decision (`reserved_by_run IS NULL` / expired / same run).
- **Not changed**:
  [PositionLock.firstAvailablePosition:771](../../../labos-kernel/src/main/java/com/labos/kernel/driver/PositionLock.java#L771) still
  uses the two-state `AND (ps.reserved_until IS NULL OR ps.reserved_until < now())`. The caller
  [:691](../../../labos-kernel/src/main/java/com/labos/kernel/driver/PositionLock.java#L691) (Deposit choosing an empty position) → **will
  pick a "permanently committed position (`reserved_by_run` non-null + `reserved_until` NULL)" as an empty one**, which
  contradicts the decision in `tryReserve`.
- Same kind of residue: [stats():807](../../../labos-kernel/src/main/java/com/labos/kernel/driver/PositionLock.java#L807) counts with
  `reserved_until > now()`, **missing the permanently committed positions**.
- Conclusion: P1-4 is a **partial fix** and cannot be counted as "fully fixed".
