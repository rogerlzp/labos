## 2. Issue list

### ① (P1) A timeout does not settle the run as `failed` — the assertion contradicts the settled state

**Location**: `scripts/verify-flow-matrix.py:340-347` (the ③ part of `sec_waitsleep`); the wording lands at `docs/完整流程测试矩阵-设计.md:83`, `docs/设计-逻辑节点分层与编辑器分工.md:105` (and the English mirrors).

**The code facts the reviewer pointed out**:

- The production settlement goes through `WorkflowService.settleRun` (`:2392-2436`): it first early-returns on `isRunPaused(runId)` (`:2395`, so **a paused run must never be overwritten by completed / failed**) → `aborted ⇒ failed` → `manual || skipped ⇒ paused + pause_kind='waiting_human' + pause_reason + paused_at` (`:2413`), and when `manual` is true it also calls `openManualWindow` (`:2446`). **`MANUAL` ⇒ the run is `paused`.**
- The `anyManual ? "failed" : "completed"` at `api/OpsApi.java:501-503` is **a separate demo insert path** that does not go through the production settlement.

**The contradiction**: the matrix's ③ part nevertheless asserts `ok("__wait timeout: whole run failed")`, while the `run.status` read by `ctx.run` is `paused` ⇒ that assertion must fail. `ci-gate.sh` goes red whenever the failure count is non-zero, regardless of `MIN_MATRIX=55`. The design document writes the two paths as one ("whole run `failed` (the `OpsApi` mapping)").

**The reviewer's conclusion**: node row `manual` + whole run `paused` is the current resume semantics (a human fixes the variable and presses continue; this step re-runs); if the product wants a terminal failed state that must not be resumed, that needs a separate settlement on this error code and **cannot rely on the existing `MANUAL`**. Suggestion: change the assertion and the document so they admit `paused`.

### ② (P1) An external refresh clobbers the variable this graph just wrote

**Location**: the variable refresh inside the `GraphRunner.waitForVariable` poll loop; the `__setVar` / `__expr` of `executeBuiltin`.

**The code facts the reviewer pointed out**:

- `__wait` calls `loadRunVars` every round and then `variables.putAll(...)` (**whole-table overwrite**).
- `__setVar` / `__expr` change the in-memory `variables` only and **have not written back** to `run.input.vars`.

**Consequence**: when the table is empty, an empty map does not `putAll`, so the in-memory `ready=1` survives — which is why the matrix's second part passes. **But if the experiment already starts with a variable of the same name** (say `ready=0`), the first poll overwrites the `1` that `__setVar` just wrote back to `0`, and then it waits until timeout. "Waiting for an external write" is right; **"an earlier variable node assigns, a later node waits for it" is wrong when an initial variable exists**.

**The reviewer's conclusion**: the refresh should **fill only the keys the in-memory map does not yet have**, or the assignment should first write back to `run.input.vars`.

### ③ (P2) Preflight still uses `isLogicNode(display name)`, ignoring the `__` prefix

**Location**: `PreflightChecker` (preflight) + `RealWorkflowRunner.resolveCapability` (capability resolution).

**The code facts the reviewer pointed out**: `isLogicNode` recognises **English keywords only** (`delay` / `variable` / `script` …), not the `__` prefix. The display names of the dragged-out built-in nodes are "延时" (delay) and "等待变量" (wait for variable) in Chinese — not one keyword matches ⇒ on the NodeDef path the capability resolves to `UNKNOWN` with an empty candidate device set, and preflight reports `PF-01` (no capability, cannot allocate a device).

**Impact**: it does not block the API from starting, but the top of the designer goes red. (If the variable node's display name is "变量节点", it is the same seam.)

### 4.1 Item-by-item response (review guidelines §4: conclusion / reason / remediation / verification)

**① "timeout settlement status" → fixed**

- **Conclusion**: the reviewer is right; my earlier judgement was wrong. The matrix asserted `failed`, contradicting the `paused` that the production settlement `settleRun` actually lands.
- **Reason (why it was wrong)**: when characterising this I copied the `anyManual ? "failed"` from `OpsApi.java:501-503`, **mistaking the demo insert path for the production settlement**, and did not go back to `WorkflowService.settleRun` to confirm the `MANUAL` branch line by line (`:2400` checks `manual`, `:2413` lands `paused + waiting_human`). The node row `manual` and the whole run `paused` are two different things: the former is "this step stopped waiting for a human", the latter is "the whole run is suspended and can be resumed".
- **Remediation**:
  - Assertion: `scripts/verify-flow-matrix.py:340-347` changed to `ok("__wait timeout: whole run paused (to manual, waiting for a human to resume)")`, with a comment above explaining "the production settlement goes through `settleRun`, `MANUAL ⇒ paused`; `failed` is reserved for `aborted` and the `OpsApi` demo path".
  - Documents (6 places, Chinese / English 1:1): `docs/完整流程测试矩阵-设计.md:83`, `docs/设计-逻辑节点分层与编辑器分工.md:105`, `docs/en/full-flow-test-matrix-design.md` (the corresponding line), `docs/en/design/logic-nodes-by-layer.md` (the corresponding line), all changed to the `paused` wording; the stale "whole run `failed` (the `OpsApi` mapping)" wording was rewritten directly, with no old text left behind.

**② "external refresh clobbers this graph's own write" → fixed**

- **Conclusion**: the reviewer is right. The whole-table `putAll` does clobber a value this graph just wrote and has not yet persisted.
- **Reason (why it was wrong)**: `__wait` needs to read external writes (otherwise it can never be satisfied), so it calls `loadRunVars` every round; but the refresh was written as a **whole-table overwrite** with no distinction between "written by this graph" and "arrived from outside". `__setVar` / `__expr` change memory only and never persist, so as soon as this graph's write shares a name with an external one it is treated as the "old value" and written back. The empty-table case hides it because an empty map does not trigger `putAll`.
- **Remediation**: `GraphRunner` gains `private final Set<String> locallyWrittenVars` (`:115`) and `writeVar(var, value)` (`:118`, writes memory and records the key name); `__setVar` / `__expr` go through `writeVar` (`:547` / `:552`); the refresh inside `waitForVariable` (`:584`) becomes **fill only keys this graph has not written**:
  ```
  if (!locallyWrittenVars.contains(e.getKey())) variables.put(e.getKey(), e.getValue());   // :611
  ```
  Semantics: external writes (device response fields, manual DB edits) still take effect; this graph's own assignment wins for this graph.
- **Verification**: a new pure-logic case `caseWaitNotClobberedByRefresh` (`GraphRunnerTest`) constructs "the experiment already has `ready=0` → `__setVar` writes `ready=1` → `__wait ready==1`" and asserts **no fall-through to manual**, both built-in nodes `completed`, and no device command emitted. Regression:
  ```
  GraphRunnerTest              15 passed, 0 failed
  ……
  649 passed / 0 failed (10 DB-connected tests skipped)
  ```
  Command: `./scripts/test-all.sh --pure-only`.

**③ "preflight judges a logic node by display name" → fixed; the two adjacent seams (fixed this round on the user's call)**

- **Conclusion**: the reviewer is right. `isLogicNode(display name)` does not recognise a built-in node with a Chinese display name.
- **Reason (why it was wrong)**: the `__` prefix was judged **only in the parser** (to set `Kind.BUILTIN`); the preflight / capability-resolution chain had no source-aligned check — two places each rolled their own, so "the parser sees a built-in, but preflight sees a task missing its capability". This is exactly the pit the review guidelines §7 warns about ("the only truth of landed behaviour is the code"): two rule sets for one fact.
- **Remediation**: the `__`-prefix check is extracted into a **single source of truth** `WorkflowGraphParser.isBuiltinProtocol(String)` (`proto.startsWith("__")`), used by both the parser (`:174`) and capability resolution (the first level of `RealWorkflowRunner.resolveCapability`, `:447`):
  ```
  if (WorkflowGraphParser.isBuiltinProtocol(protocolName) || isLogicNode(name)) return new CapabilitySource(LOGIC, "logic");
  ```
- **Verification (real-machine probe)**: three probe workflows were created and `GET /api/workflows/{id}/preflight` was run:
  - A (`__sleep` with the display name "延时" + a real device task) → 1 `[WARN] PF-03` (the downstream task "would never be reached");
  - B (only `__wait` with the display name "等待变量") → 1 `[ERROR] PF-07` (the flow has no task node);
  - C (a device task only, the control) → 0 issues.
  - **`PF-01` no longer appears** ⇒ ③'s fix works.
- **The two adjacent seams → the user called for fixing them this round; fixed** (the next seam after ③ was fixed; neither was introduced by this delivery):
  1. **Seam A (a pure built-in graph falsely reports `PF-07`)**: `PreflightChecker`'s `tasks` collects `Kind.TASK` only, so a flow with only `__sleep` / `__wait` / `__setVar` was judged `PF-07` "the flow has no task node" (ERROR, blocks startup).
     - **Remediation**: `tasks` still collects device tasks only (the capability / device checks and the `taskCount` / `reachableCount` counts rely on it); "is there anything executable" is judged separately by `hasExecutable` (`Kind.TASK` **or** `Kind.BUILTIN`), and the message becomes "the flow has no executable node (a device task or a built-in logic node)".
  2. **Seam B (the dry run missing `builtinParams` causes a false `PF-03` downstream)**: the dry-run `GraphRunner` was not given `builtinParams` ⇒ `__sleep` throws on a missing argument and `__wait` necessarily waits until timeout; either one makes the whole graph `break`, so its **downstream real device task** was judged `PF-03` "would never be reached".
     - **Remediation**: `GraphRunner` gains a `withDryRun(boolean)` switch; under the dry run (`PreflightChecker` calls `.withDryRun(true)`) a built-in node is a **pass-through** — it only records `progress.complete(nodeId, "[干跑] " + method)` (the dry-run marker), **never runs `executeBuiltin`**, reads no value, does not sleep, and reads no external variables, so it cannot throw on a missing argument. A dry run is about structural reachability; a built-in node's value semantics simply do not hold there.
- **Verification**:
  - **Pure logic**: `GraphRunnerTest` gains `caseBuiltinDryRunNoOp` (under the dry run the built-in nodes do not turn manual / do not actually sleep / the downstream device task is reached) ⇒ `GraphRunnerTest` **16 / 0**, full pure logic **650 / 0**.
  - **DB-connected self-test**: `workflow.PreflightDbSelfTest` added (probe flows assemble XML in memory only, use negative phantom ids, and write nothing to the DB): a pure built-in graph no longer falsely reports `PF-07` / built-in nodes do not block the downstream (no more false `PF-03`) / a device-task-only graph as the control has no `PF-03` / a gateway-only graph still reports `PF-07` ⇒ **4 / 0**.
