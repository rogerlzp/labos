### 3.2 变量（6）

| 用例 | 期望 | 结果 |
|---|---|---|
| `${temp} > 37`，temp=38 | true | ✓ |
| `${temp} > 37`，temp=37 | false | ✓ |

### 3.3 逻辑与括号（6）

## 4.7 第二轮补充验证（2026-11-03 下午）

### 4.7.1 节点输出驱动条件（之前最大的缺口）

构造 `T-OUT`(1261)：`开始 → [查板型 GetPlateType] → ◇板型>=1吗 →(真)回到查板型 / (假)结束`，
流程 attr `maxIterations=2`。

| 断言 | 实际（run 205395） | 结果 |
|---|---|---|
| 设备回包字段进入变量表 | `plateType=1`（来自 `device_raw_response.data`） | ✓ |
| 条件读得到它 | `${plateType} >= 1` 为真 | ✓ |
| 循环按上限停 | 执行 **2 次** GetPlateType 后结束，整单 `completed` | ✓ |

**这一步挖出两个真 bug**：

1. `run_command` 挂在**步骤节点**（`level=1`）上，业务节点是它的 parent。
   原来按 `node_key=? AND level=0` 查，**一条都查不到**，变量永远是空的。
2. `run_command.result` 只有 `{ok,durationMs}`，设备业务字段在
   `device_raw_response.data` 里，且是转义过的 JSON 字符串。

### 4.7.2 循环 + 并行（最容易死循环的组合）

构造 `T-PLOOP`(1262)：并行分叉 →（A：单次）／（B：带回边，条件 `${go}==yes`）→ 并行汇合，
`maxIterations=2`。

| 断言 | 实际（run 205396） | 结果 |
|---|---|---|
| A 执行 1 次 | `A completed` | ✓ |
| B 按条件走 2 圈 | `B completed` | ✓ |
| 汇合点等待两路 | 模拟器共收到 **3 条 Seal**（A 1 + B 2） | ✓ |
| 不死循环、不卡死 | 整单 `completed` | ✓ |

### 4.7.3 圈数上限可配置

`workflow.attr.maxIterations = 3` 后跑 `T-LOOP`(1259)：模拟器收到 **3 条** Seal（原来默认 10 条）。
改成 2 后 `T-OUT` 正好 2 圈 —— 配置生效。

### 4.7.4 条件语法预检（PF-09）

构造 `T-BAD`(1260)：条件写成 `${ok} >`（不完整）。

```
GET /api/workflows/1260/preflight
→ WARN PF-09 XOR  边 XOR→A 的条件表达式语法有问题：表达式意外结束：${ok} >（执行时会走默认边）
→ WARN PF-03 A    节点「走A分支」永远不会被执行
```

预检**不阻断启动**（WARN），但现场在跑之前就能看见。

### 4.7.5 三分支异或（>2 条出边）

构造 `T-X3`(1263)：`X 分支` 三条出边 —— 条件 `${v}==1`、条件 `${v}==2`、default。

| 输入 | 结果 |
|---|---|
| `vars=v=1` | `A:completed  B:bypassed  C:bypassed` |
| `vars=v=2` | `A:bypassed  B:completed  C:bypassed` |
| `vars=v=9` | `A:bypassed  B:bypassed  C:completed` |

按声明顺序求值、第一条成立即选、都不成立走 default —— 与设计一致。
