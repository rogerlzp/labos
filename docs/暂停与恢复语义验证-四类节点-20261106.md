> 回答四个问题：
> ① 发生暂停时，会停在**哪一类**节点上？
> ② 恢复时，是从**下一个**节点接着跑，还是从**当前（暂停点）**节点跑？
> ③ 设备节点与逻辑（变量/表达式）节点在暂停/恢复上**有什么区别**？

## 1. 一句话结论

| 问题 | 答案 |
|---|---|
| ① 暂停会停在哪些节点？ | **只停在设备任务节点**。异或网关、并行网关、**逻辑节点（变量/表达式）都不会成为暂停点** —— 源码里 `pauseChecker` 只在 `Kind.TASK` 分支里检查（`Kind.BUILTIN` 走独立分支，不查暂停）。<br>⚠ 且暂停是「**上一个节点已执行完**」之后才生效 —— 检查点在 `executeNode` **之前**，信号到达时正在执行的那个节点**已经跑完了** |
| ② 恢复从哪继续？ | **从「还没做完的那个节点」继续**，不是从下一个、也不是从头。已 `completed` 的节点**跳过不重跑**；没做完的**重跑**。<br>实测：暂停时设备节点**已完成**（检查点在执行之前），它进 `skipKeys` → 续跑**跳过** → 设备指令只下发 1 次 |
| ③ 设备 vs 逻辑的差别？ | **暂停点选择上没差别**（两者都是任务节点）。差别在**续跑时**：逻辑节点重跑是**纯计算、零副作用**；设备节点重跑会**真的再下一次设备指令**——所以机制必须保证它不被重复下发 |

## 2. 源码依据（结论不是猜的）

### 2.1 暂停检查点只有一处，且只在任务分支

`labos-kernel/src/main/java/com/labos/kernel/workflow/GraphRunner.java`：

```java
} else if (node.kind() == Kind.TASK) {
    // P1-8：在**任务节点的动作边界**检查暂停。
    // 不停在动作中间 —— 机械臂抓着板会掉。
    // 也不停 start/gateway —— 它们不是"一步活"，停在那里没意义。
    // 把 key 放回队列，恢复时从这里继续。
    if (pauseChecker.getAsBoolean()) {
        ready.offer(key);
        done.remove(key);
        paused = true;
        log.accept("[暂停] 收到暂停请求，在节点边界停下，待执行节点：" + key);
        break;
    }
    RecoverableNode rn = toRecoverable(node);
    ...
```

三个关键点：

1. **检查点在 `Kind.TASK` 分支内** → 网关（`SPLIT_XOR` / `SPLIT_PARALLEL` / `JOIN_*`）与
   起止事件**根本不查暂停**，所以暂停点必然是任务节点。
2. **检查点在 `executeNode` 之前** → 停在**动作边界**，不会停在设备指令中间
   （「机械臂抓着板会掉」）。
3. **`ready.offer(key); done.remove(key);`** → 停下的节点被**放回队列**且从 `done` 移除，
   语义上就是「这个节点还没做，恢复时接着做」。

### 2.2 暂停是查库实现的

`WorkflowService.java:824`：

```java
// P1-8：每到一个节点边界查一次 DB —— 状态是 paused 就停。
// 只查单行主键，开销可忽略；不查的话暂停按钮等于没用。
.withPauseChecker(() -> isRunPaused(runId));
```

即：**页面点「暂停」→ `run.status='paused'` → 执行线程在下一个任务节点边界查到 → 停**。

### 2.2b 暂停生效的确切时机（实测澄清）

`pauseChecker` 在 `executeNode` **之前**调用，所以：

```
… → 节点 X（执行中）…  ← 此刻收到暂停信号，X 仍会跑完
… → 节点 X 的下一个边界  ← 这里才查到 paused，停下
```

即**暂停是「上一个节点已执行完」之后才生效**。停下时执行的代码是：

```java
ready.offer(key);   // 把这个节点放回队列
done.remove(key);   // 从已完成集合里移除
paused = true;
break;              // 本轮不再往下走
```

**「放回队列」不等于「会被重跑」**，而且那个队列**根本用不上**：
`ready` 是 `GraphRunner.run()` 内部的**局部变量**，`break` 之后方法直接返回，
队列随之丢弃。**恢复是一次全新的 `run()` 调用** —— 从 START 重新出发，
靠 `skipKeys` 把已完成的节点一个个跳过。

所以「从当前节点继续」**不是靠队列记住进度实现的，而是靠 skipKeys 反推**：
凡是上一轮 `completed` 的都跳过，剩下的第一个就是"接着该跑的那个"。

实测：设备节点在暂停时**已完成** → 进 `skipKeys` → 续跑跳过 →
**设备指令只下发 1 次**（`run_command` 实测 1 条，且有真实回包）。

> ⚠ **「设备节点在暂停时已完成」不等于「暂停总是迟到」**。
> 本轮这个结论是**在快速设备（150ms）上测出来的**：脚本等 `run_command` 出现才发暂停，
> 而 `run_command` 是**步结束后**才落库的 ⇒ 暂停发出去时设备早跑完了。
> 用长耗时设备（10–18 秒）在**执行到一半**时发暂停，结论**不变**：
> 设备方法照旧跑完（`completed`），run 变 `paused`，
> 下一个任务节点边界才真正停下 —— 因为检查点始终在 `executeNode` **之前**。
> 判据怎么写才不误判，见《设备执行中的暂停》§1.5。

### 2.3 恢复的「从哪继续」由 `skipKeys` 决定

`WorkflowService.resumeAsync(runId)`：

```java
// 断点续跑要跳过的节点 key（上一轮已经 completed 的那些）
SELECT node_key FROM run_node
 WHERE tenant_id = ? AND run_id = ? AND level = 0 AND status = 'completed'
```

拿到 `doneKeys` 后：

```java
// 先删步骤行（level=1），再删业务节点
DELETE FROM run_node s USING run_node p
 WHERE s.level = 1 AND p.id = s.parent_node_id AND p.level = 0 AND p.status <> 'completed'
DELETE FROM run_node WHERE level = 0 AND status <> 'completed'
UPDATE run SET status = 'running', pause_kind = NULL, ... WHERE id = ?
```

然后 `execute(wid, mode, rid, doneKeys)` → `GraphRunner.withSkipKeys(doneKeys)`：

```java
if ((node.kind() == Kind.TASK || node.kind() == Kind.BUILTIN)
        && skipKeys.contains(key)) {
    // 断点续跑：这个节点上一轮已经做完了，直接当完成往下走
    log.accept("[续跑] 节点 " + key + " 已完成，跳过");
}
```

**所以答案是「从还没做完的那个节点继续」**：

- 上一轮 `completed` 的节点 → 进 `skipKeys` → **跳过，不重跑**
- 上一轮没 `completed` 的节点 → 行被删掉 → **重跑**

### 2.4 设备节点与逻辑节点的**真正**差别

两者在被跳过 / 重跑的处理上**没有差别**（`skipKeys` 把 `Kind.TASK` / `Kind.BUILTIN` 并列）。
差别在**续跑时的副作用**：

| | 逻辑节点·瞬时计算（`__setVar` / `__expr`） | 设备节点（普通 task） |
|---|---|---|
| 做什么 | 引擎自己算一个值写进变量表 | 通过驱动给设备下指令 |
| 重跑代价 | **零副作用**（重算一遍，结果一样） | **物理副作用**——机械臂再搬一次板、设备再动一次 |
| 源码保护 | 无需特殊处理 | `GraphRunner` 注释明确写了：「**不能**按执行结果决定是否退回。退回意味着重跑，而在真实设备上重跑 = 开两次盖（物理副作用不可撤销）」 |
| 被跳过时 | 变量值从 `run_node` 保留 | 已完成的设备动作不再重做（靠 `skipKeys`） |

`WorkflowService.java:825-827` 的注释是这条设计的核心：

```java
// 注意：**不能**按执行结果决定是否退回。
// 退回意味着重跑，而在真实设备上重跑 = 开两次盖（物理副作用不可撤销）。
```

> ⚠ 顺带记一个**容易踩的坑**：`run_command` 挂在 **level=1 步骤行**上，
> 要经 `parent_node_id` 关联到 level=0 的业务节点才能对上设备节点。
> 第一版直接按 level=0 关联，查出来是 0 条 —— 差点误判成「设备根本没跑」。

### 3.3 三个最有说服力的证据

1. **「续跑不重复下发」** —— `run_command` 里 DEV 只有 **1 条**指令，且带真实
   `device_raw_response`。这说明「物理副作用不可撤销」这条设计**真的生效**了：

## 4. 四个待回答问题的完整回答

### Q1 · 发生暂停时会暂停到这些节点吗？

| 节点类型 | 会不会成为暂停点 | 依据 |
|---|---|---|
| **异或网关**（✕） | **不会** | `pauseChecker` 只在 `Kind.TASK` 分支；网关在 `else` 分支直接走 `choose()`/激活出边 |
| **并行网关**（＋） | **不会** | 同上 |
| **设备节点** | **会**（在它的动作边界）—— 但实际生效是「**它执行完之后**的下一个边界」，因为检查点在 `executeNode` 之前 | `Kind.TASK` 分支 |
| **变量/表达式节点**（瞬时计算） | **不会** | `Kind.BUILTIN` 走**独立的 `else if` 分支**，那个分支里**没有** `pauseChecker`；`skipKeys` 把 `TASK`/`BUILTIN` 并列只是「续跑跳过」对两者一视同仁。实测：暂停点落在设备节点，VAR 已 `completed` |
| **延时/等待节点**（`__sleep` / `__wait`） | **会** | 等待循环按 500ms 分片轮询 `pauseChecker`（`GraphRunner.waitInterruptibly`） |
| 起点/终点 | **不会** | `Kind.START` / `Kind.END`，不是「一步活」 |

> ⚠ 一个细节：`Kind.BUILTIN` 在源码里走的是**独立的 `else if` 分支**，那个分支里**没有**
> `pauseChecker` 检查 —— 所以 `__setVar` / `__expr` 这类**瞬时计算**的逻辑节点本身不会成为暂停点。
> 实测也印证了：暂停点落在设备节点上，变量节点 VAR 已经 `completed` 了。
> 源码 `skipKeys` 判断把 `TASK` 和 `BUILTIN` 并列，只是因为**续跑跳过**对两者一视同仁。
>
> **例外（2026-11-06 追加）**：`__sleep` / `__wait` 两个内置节点在**等待循环**里按 500ms 分片
> 轮询 `pauseChecker`，因此**可以**成为暂停点。等待语义本身由 `verify-flow-matrix.py` 的
> `waitsleep` 小节覆盖；「在 `__sleep` / `__wait` 上暂停」目前还没有专门的页面断言。

### Q2 · 恢复时从下一个节点开始，还是从当前节点跑？

**从「当前那个还没做完的节点」跑** —— 既不是"下一个"，也不是"从头"。

- 暂停点那个节点：上一轮**没做完** → 续跑**重跑它**（实测：DEV 续跑后 completed）
- 暂停点**之前**已 `completed` 的节点：进 `skipKeys` → **跳过，不重跑**
  （实测：VAR 续跑后仍只有 1 条记录）

一句话：**已完成的不再做，从卡住那一步接着来**（`GraphRunner` 注释原话）。

### Q3 · 设备节点和逻辑节点处理上有什么区别？

| 维度 | 逻辑节点·瞬时计算（`__setVar`/`__expr`） | 设备节点 |
|---|---|---|
| **能否成为暂停点** | ❌ **不能**（源码里 `Kind.BUILTIN` 分支不查 `pauseChecker`；实测暂停点落在设备节点）。**例外**：`__sleep` / `__wait` 见 §4 Q1 / Q3 的例外说明 | ✅ 能（动作边界，指令下发前） |
| **暂停时机** | — | 指令下发**之前**（动作边界，不停在指令中间） |
| **续跑是否重跑** | 已 completed → 跳过 | 已 completed → 跳过；**未 completed → 重跑（会再下一次指令）** |
| **重跑代价** | 零副作用 | **物理副作用**（机械臂再搬一次板） |
| **保护机制** | 无需特殊保护 | 靠 `skipKeys` + 「不按执行结果退回」的硬约束 |
| **失败/跳过时** | 求值失败 → 转 `manual` 并停下（不能带着错值往下跑） | 动作被跳过 → **板位不可信 → 转人工确认**（D9：跳过意味着板子位置未知） |

**最重要的一条**：设备节点被重跑意味着**设备会真的再动一次**。所以设计上：

- 恢复只从**未完成**的节点开始，不从头（否则整条流程的设备动作全部重做）
- 已完成的设备动作靠 `skipKeys` 跳过
- 源码明确禁止「按执行结果决定是否退回」——退回=重跑=开两次盖
