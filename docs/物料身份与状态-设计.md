### 0.1 本稿怎么来的：三份独立设计的收敛

同一件事收到了**三份互相独立的设计**（不是一份设计的三次评审）：

| # | 来源 | 文件 | 形态 |
|---|---|---|---|
| A | 本会话 v2（合并 Grok / Kimi / OpenAI 三份**评审**意见） | `docs/物料身份与状态-设计.md`（本文件的上一版） | 最小落地：`plate` 加列 + 效果表 + 审计表 |
| B | 并发会话的**独立 v2** | `docs/物料身份与状态-设计-v2.md`（保留作对照） | 四类事实分开 + 8 条不变量 + `run_node` 加两列 |
| C | 第三份独立设计草稿（外部评审方给出） | 未入库（本稿已吸收其结论） | 完整 Material / Location / Content / Event / Effect 五对象模型 |

**三方共识（12 条，本稿全部采纳）**：

| # | 共识 |
|---|---|
| C1 | **身份 ≠ 位置**：位置是物料的属性/关联，不是身份 |
| C2 | **执行声明 ≠ 物理事实**：流程声明 / 设备回报 / 系统确认，三者不能等同 |
| C3 | **当前状态与历史事件分离**：当前值可投影，历史不可覆盖 |
| C4 | **来源 / 当前归属 / 加工历史**是三件事，不能共用一个 `owner_*` |
| C5 | **循环轮次 / 重试次数 / 执行实例必须分开建模**（`loop_round` / `attempt` / `execution_id`） |
| C6 | **设备执行与数据库事务不混为一谈**：物理动作回滚不了 |
| C7 | **一对多结构必须预留**，第一期用校验规则限制，而不是把表设计成永远一对一 |
| C8 | **未声明 ≠ 无影响**：要显式分类（NONE / DECLARED / UNKNOWN） |
| C9 | **位置锁复用现有 `PositionLock`**，不另建一套占用系统 |
| C10 | **租户隔离尚未真正实现**（`TENANT = 1L` 写死），新表有 `tenant_id` 不等于隔离成立 |
| C11 | **先 S0 定模型、后 S1 建表**；不要先冻结 DDL 再补模型 |
| C12 | **耗材独立后续阶段**：第一期不建半成品库存/消耗功能 |

**分歧与裁决（7 条，本稿的取舍）**：

| # | 分歧 | A（本稿 v2） | B（独立 v2） | C（第三份） | **裁决** | 理由 |
|---|---|---|---|---|---|---|
| D1 | 幂等键锚点 | `run+node+loop+plate` | effect_key | 逻辑执行实例 + effect_index | **结构化唯一键 `(tenant, run, node, loop, effect_index)`**（v3.2 修正：不落字符串 `execution_id`，见 §5.5） | C 的锚点最稳；且它天然解决「一个节点产生多个效果」 |
| D2 | 执行事实载体 | 效果表兼作 T1 | `run_node` 加两列 | 独立 Execution Fact 对象 | **三处分工（v3.2 修正）**：**设备命令事实 = `command_ledger`（派发前落账/幂等键/UNKNOWN）+ `run_command`（回包后的结果台账）**；节点级同步状态进 `run_node`；物料效果独立表 | 不新建第二套命令台账，也不让效果表兼任执行事实；原稿「复用 `run_command`」写错了（它没有 `command_id` 列） |
| D3 | 效果状态机 | 3 态 | 3 态 | **5 态** | **6 态（v3.2 补 `CANCELLED`）** | "效果不符合规则"与"物理事实待核对"是两种完全不同的处置；run 终止后未应用的效果必须有终态（CANCELLED），否则补偿会重放失效意图 |
| D4 | 节点与效果的状态关系 | 解耦（未细化） | 解耦（未细化） | 明确"节点要等效果达确认等级才算完整完成" | **采纳 C，并给出落地** | 不改 `node_status` 枚举；由**派发闸门**（§5.2b，注入 GraphRunner/executeAll 的 predicate，读 `run_node.material_sync_status`）决定下游派不派；⚠ 不用 `runtime_hold` 扣节点：其 scope 实际是 `site\|island\|experiment`（无 run/node 粒度） |
| D5 | 事件表命名与字段 | `plate_state_audit` | `plate_material_event` | `Material Event`（含 `occurred_at`/`recorded_at`） | **`plate_material_event` + 双时间戳** | "event" 比 "audit" 更能表达不可变事件流；物理发生时间 ≠ 系统记录时间必须分开 |
| D6 | 领域模型落地范围 | 最轻（`plate` 加列） | 中 | 最重（Material/Location/Content 三关系表） | **折中**：Material=现有 `plate` 加列；Location=**复用** `position_state`；Content=**复用** `plate_well`/`sample`/`sample_aliquot` | 三份的"未来模型"一致，差别只在第一期建多少表；复用既有的能少两套真源 |
| D7 | 耗材判据 | 独立身份/生命周期追溯 | 独立实体 + 位置 + 附着历史 | 独立身份/生命周期/库存/批次/有效期/复用/追溯 | **取并集** | 三方措辞不同，实质一致 |

### 0.3 第 5 轮独立复审（20261112-05 / 06）后的关键裁决（v3.2）

> 依据：`docs/评审记录/20261112-05-mavis.md`（并行会话）与 `20261112-06-mavis.md`（本会话 3 个独立子代理复核 + 汇总）及三份 findings。
> 完整处置表见 §18.1。

| # | 裁决 | 为什么（详见） |
|---|---|---|
| R1 | **执行事实载体 = `command_ledger` + `run_command` 两表分工**；`run_command` **没有** `command_id` 列（原稿写错），`command_id` 在 `command_ledger` | 命令账本在**派发前**落账，才能表达「已下发、未回包」窗口；`run_command` 是**回包后**才写的结果台账（§5.3/§7） |
| R2 | **T1 失败 = run 级隔离（quarantined + experiment 级 runtime_hold），不是「run failed」**；隔离/人工确认前**禁止 resume 重派设备命令** | 现有 `markRunFailed` 无转人工通道，重启后人工续跑会把已完成物理动作再执行一次（§5.2b/§5.8） |
| R3 | **下游「不派发」= 派发闸门 predicate**（GraphRunner / executeAll 派发前查前置节点 `material_sync_status`），**不是**「调度器依赖检查」 | 现有节点派发在 GraphRunner 内存队列里，`ExperimentScheduler` 只到 workflow-step 粒度，不存在节点级依赖检查（§5.2b/§5.7） |
| R4 | **物理执行通路清单要写全**：2 条生产通路已进统一完成点；`/api/experiments/flow-run` 与 ShadowRunner/单命令探针是**已知缺口**，S0 内必须先处置 | 前者绕过 `RunStateMachine` 直接驱动设备，后者真实动作但不落执行事实（§16.1） |
| R5 | **效果状态机 6 态**（补 `CANCELLED`）；`NEEDS_RECONCILIATION` / `REJECTED` / `FAILED` 都要有人工闭环（权限 + 原因 + 事件 + API） | 只有「FAILED→PENDING」不够；run 终止后未应用的效果会永远悬空（§5.8/§8） |
| R6 | **O-2 的跨租户/引用约束继续保留；§7⑧ 在第 6 轮 12 条基础上新增身份绑定两外键，当前共 14 条 `ADD CONSTRAINT`**（4 唯一键 + 9 外键 + 1 空值 CHECK） | 原稿只给 3 组，O-2 未闭合；此前版本实测补 `uq_run_tenant_id` 后对应约束可建；含扫码绑定表的当前合并版仍须重跑（§7⑧） |

### 0.4 第 6 轮补充评审后的新增裁决（v3.3）

| # | 裁决 | 落地 |
|---|---|---|
| N1 | **执行确认与物料同步彻底分离**：新增 `execution_resolution_status`；`none/legacy/transition` 只要物理结果未知就禁止普通续跑 | §5.2c / §7④ / §8 |

## 4. 核心模型

### 4.1 Material 领域分层（新增：不封死在 `plate` 表）

```
Material（物料，抽象基类）
├── Container（容器：装东西的）
│   ├── PCR Plate
│   ├── Deep Well Plate
│   └── Assay Plate
├── Consumable（耗材：盖子、卡扣 —— 需独立身份或生命周期追溯的）
├── Sample（样品）
├── Reagent（试剂）
└── Waste（废弃物）
```

**本期只落地**：`Container` 这一支的板级工艺阶段 + 归属 + 审计。
其余分支**只是把命名空间留出来**，不建表。

⚠ **`plate` 不改名、不改表结构定位**。它是 `Container` 的一个实例化，
不是 Material 的全部 —— 这条边界写清楚，将来加样品/试剂/废弃物时才不用推翻第一期。

### 4.2 容器的四个维度 + 三条边界

| 维度 | 落点（v3.2 定稿） | 本期 |
|---|---|---|
| **身份**（条码 / 板型规格） | `plate.barcode` / `plate_type` / `rows` / `cols` | 已有。**`plate_type` 不动**（它是规格，不是工艺角色） |
| **板级工艺阶段** | `plate.process_state` | **新增**（v1 叫 `content_state`，v2 改名） |
| **耗材状态** | `plate.seal_state`（膜；**NULL = 未知**，`none` / `sealed`） | **新增**（独立耗材实体推迟到 S5） |
| **位置**（既有，不改） | `position_state`（唯一真源）+ `plate.location_id`（冗余投影）/ `plate.position_status`（位置可信度） | **不改**；新稿只读不双写（§17 Q2） |
| **归属**（三概念） | 当前归属 = `position_state.occupied_by_run`；生产来源/加工历史 = `plate_material_event`（§4.5） | **不加 `plate.current_run_id` / `origin_*`**（v3.2 采纳 v2.2 异议：没有 CREATE 与 handoff 闭环时这些列只会制造第二个归属真源） |

**为什么改名 `content_state` → `process_state`**：
「内容」暗示它描述板里装的东西，而那正是 `plate_well` 的职责；
「工艺阶段」准确表达它描述的是**这块板在工艺流程中的位置**。

**三条边界（本期必须写死，否则会和 `plate_well` 打架）**：

| # | 边界 |
|---|---|
| ① | 本期描述的是**整块容器的工艺阶段**（一块板一个阶段，同质） |
| ② | **不代表孔级样品内容** —— 那是 `plate_well` 的真源；两者**不得互相矛盾** |
| ③ | **不代表体积 / 浓度等物理化学属性** —— 那是 `sample` 的真源 |

**「还剩几块空板」的口径**：只有整板 well 数据已完整登记、且全部 well 的 `status='empty'` 时才判空；
**未建 well 行 = 孔级数据未知，不等于空板**。不另立一个 `empty` 板级状态（否则两个真源）。

### 4.3 板级工艺阶段字典：租户级 + 模板集

| 决策 | 取值 | 理由 |
|---|---|---|
| 字典归属 | **租户级**（带 `tenant_id`） | 阶段名是客户工艺的词汇，系统无权规定 |
| 是否内置 | **全局模板集**（`is_template=true`），新租户初始化时**复制成租户副本** | 从零建 18 个阶段体验极差；但模板只是"建议" |
| 唯一标识 | `code`（机器标识）+ `display_name`（客户看到的） | 改名不该改引用 |
| 删除 | **只停用（`enabled=false`），不物理删除** | 已被引用的阶段删了就断了历史显示 |
| 引用约束 | `plate.process_state` 与 `(tenant_id, code)` 的**复合外键**（或等效校验） | 不能出现"字典里没有的状态" |

⚠ **租户隔离现状**：`WorkflowWebService.TENANT = 1L` 是写死的 ⇒
**不能因为新表有 `tenant_id` 就认为租户隔离已成立**。新代码的字典与状态读写
必须走同一套租户上下文，且**这一条要作为已知问题单独记（§13）**。

### 4.4 耗材：判据扩大

| | 判据 | 结论 |
|---|---|---|
| v1 判据 | 是否需要**独立追踪位置** | 太窄 |
| **v2 判据** | 是否需要**独立身份或生命周期追溯**（位置、批次、库存、附着历史、可重复使用、质量追溯……） | 采纳评审意见 |

⇒ **膜**：撕下即弃、不单独追踪 ⇒ `plate.seal_state` 一个字段就够。
⇒ **盖子**：有独立条码/库存/附着历史 ⇒ 需要独立实体。
⇒ **本期不改造既有 `consumable` / `consumable_lot`**——它们需要自己的位置与附着历史模型，
**先冻结不完整结构是错的** ⇒ 整体改造推迟到 S5（§14）。

### 4.5 归属：三个概念，不能混

| 概念 | 落点 | 语义 | 会不会被覆盖 |
|---|---|---|---|
| **当前归属** | `position_state.occupied_by_run` | 当前由谁管 | **会** |
| **生产来源** | `plate_material_event` 的首条来源记录 | 最初由谁产生 | **不会** |
| **加工历史** | `plate_material_event` | 每次状态结果一行 | 只追加 |

**为什么必须拆**：一块板被 A（扩增）、B（纯化）、C（检测）三个 Run 依次加工后，
必须同时能回答"谁生产的（A）"、"谁最后加工的（C）"、"现在归谁"。
用一组 `owner_*` ⇒ 每次迁移覆盖 ⇒ **生产关系永久丢失**。本期没有 CREATE/handoff 闭环，
因此**不新增 `plate.origin_*` / `current_run_id`**；首条事件只表达已有记录中的最早来源，不伪造系统上线前历史。

⇒ **`/api/runs/{id}/material-effects` 按效果记录的 `source_run_id` 查**，
**不按任何「当前归属」字段查**（归属已有 `position_state` 唯一真源，§4.5）；
接口文案改为「**本 run 声明的物料结果 / 状态变更**」，不再称"新产出的板"。

## 5. 执行事实与物料效果（v1 重写）

### 5.1 为什么不能靠单事务

| 事实 | 后果 |
|---|---|
| 设备命令**先提交**（`insertRunCommand`），节点完成**后提交**（`updateNodeStateLive`） | 二者本来就不在一个事务里 |
| 设备动作**物理不可撤销** | 迁移失败若回滚节点完成 ⇒ 续跑时设备动作会**再做一次**（重复物理动作 = 事故） |
| `PositionLock` 的审计**刻意**在位置事务外独立写入、失败只打日志 | 照抄这条会得到设计想避免的缝 |

⇒ **「必须与节点完成同事务」这个要求在当前架构下做不到**，v1 把它当既有能力写是错的。
⇒ **目标改为**：**执行事实先形成可恢复的记录；物料状态迁移具备幂等、可重放、异常隔离**。
数据库内部能原子提交的记录尽量放同一事务。

### 5.2 三层分工（不新建执行引擎）

| 层 | 职责 | 本期改动 |
|---|---|---|
| `GraphRunner` | 流程图推进、循环、分支、暂停、恢复 | **不碰数据库**（保持现状） |
| `RunStateMachine` / `StepExecutor` | 执行节点、重试、设备命令 | 增加**不吞异常**的完成通知（§5.7） |
| `PositionLock` / `CommandLedger` | 板位锁、命令记录、物理执行追溯 | **不动**（位置 ≠ 内容） |
| **MaterialEffectService**（新增） | 物料输入输出、状态迁移、物料审计、幂等 | **新增领域服务**，消费执行事实 |

⚠ **明确禁止**：不要把物料状态更新塞进 `PositionLock` —— 位置管理和工艺内容管理会再次耦合。

### 5.2b 两级失败语义与派发闸门（v3.3 收敛）

**T1 与 T2 的失败后果完全不同**；v3.2 已按源码证据确定隔离通道，v3.3 继续沿用：

| 阶段 | 失败意味着 | 后果 | 落地通道 |
|---|---|---|---|
| **T1**（物料效果意图没落成预期状态） | 设备命令事实通常已在 `command_ledger` / `run_command`；缺的是物料账本与补偿依据 | **隔离 run（quarantined）+ experiment 级 `runtime_hold`**；不是 run failed；人工对账前禁止 resume 重派设备命令 | 复用 `StartupRecovery.quarantineUncertainRuns` 先例 |
| **T2**（应用状态投影） | 物理动作已发生且已留痕，只是投影没跟上 | 节点保持物理完成；物料同步记录具体异常；依赖后继不派发，无关分支继续 | `run_node.material_sync_status` + 派发闸门；效果按原因进入 PENDING/FAILED/REJECTED/NEEDS_RECONCILIATION |

**为什么「只落 run=failed」不够**：`markRunFailed` 不写 `pause_kind` / `recoverable`，数据库整体不可用时也写不进去；
重启后的普通 CONTINUE 可能删除未完成节点并重放已完成物理动作。因此 T1 失败必须隔离，
恢复入口先按 `command_ledger` / `run_command` 对账（§5.3/§5.8）。

**下游「不派发」的机制**：
1. 节点级物料状态为 `not_required / pending / applied / failed / rejected / needs_reconciliation / cancelled`；
   其中效果 `REJECTED` **一一映射**为节点 `rejected`，不与可重试 `failed` 合并；
2. **派发闸门 = 注入 `GraphRunner` / `RunStateMachine.executeAll` 的 predicate**：节点准备执行前检查全部直接前置，
   只有 `not_required / applied` 放行；`pending / failed / rejected / needs_reconciliation / cancelled` 一律阻断；
3. **循环节点的裁决（v3.3 关闭 §13.2-13）**：不读取 T1 时尚未创建的圈次 run_node，也不信任其默认 `not_required`。
   闸门按 run 级声明快照确定每圈预期 effect 集合，再按 `source_loop_index=1..N + effect_index` 汇总实际 effect：
   任一预期效果缺失，或任一效果不是 APPLIED，都阻断；`none/legacy` 以执行确认状态和汇总行的 `not_required` 判定。
   多效果必须全部 APPLIED，不能以汇总行或最后一圈代替；
4. 闸门命中 ⇒ 节点不启动，run 落 `paused + pause_kind=material_sync`，并记 experiment 级 `runtime_hold` 告警；
   对账完成且人工确认后通过现有 resume 入口唤醒；
5. 闸门不放在只管 workflow-step 的 `ExperimentScheduler`。`GraphRunner` 仍不直接访问数据库，
   predicate 由 boot 层 `MaterialEffectService` 注入，与现有 `withPauseChecker` 同一依赖方向。

⇒ **不新增 `node_status` 枚举值**：物理完成、物料同步与后继派发是三个不同维度，不伪造设备失败。

### 5.2c 执行确认状态：所有节点共有的重放守卫（v3.3 新增）

`physical_completed_at` 只能证明“已确认完成”，不能单独覆盖“已派发但结果未知”。新增
`run_node.execution_resolution_status`，与既有 `node_status` 和 `material_sync_status` 分开：

| 状态 | 含义 | 普通续跑语义 |
|---|---|---|
| `unresolved` | 尚未形成最终执行结论；包含未开始/执行中及老数据未知 | 只有**没有派发证据**时才允许按普通未开始节点处理 |
| `completed` | 已确认目标物理动作完成 | 只补执行/物料记录，禁止重新执行设备动作 |
| `failed_confirmed` | 已确认目标物理动作未发生 | 才可进入现有安全重试策略 |
| `reconciliation_required` | 已有派发或执行迹象，但最终物理结果未知 | **禁止删除重建、普通 resume 或自动重试**；先设备查询/人工对账 |

- 不再单设 UNKNOWN：UNKNOWN 是证据状况，统一落入 `reconciliation_required`；既有 `node_status` 继续表达未开始、运行中、完成等流程生命周期；
- 明确成功时同时写 `completed + physical_completed_at + physical_evidence_level + physical_evidence`；老 `status=completed` 只能以 `legacy` 证据兼容，不能伪造精确发生时间；
- 超时、连接中断或 `command_ledger=UNKNOWN/DISPATCH_STARTED` 时写 `reconciliation_required`，**无论声明是 `none`、`legacy_unspecified` 还是 `transition`**；无效果节点的 `material_sync_status` 仍可保持 `not_required`；
- 续跑守卫必须联合检查执行确认状态、物理完成时间、run_node 原状态、`command_ledger/run_command`、Effect/Event 引用。任何已确认完成、结果未知或已被物料记录引用的节点都不得删除重建；
- `failed_confirmed` 必须由明确证据支持，不能把超时直接映射成失败。人工确认完成后只补证据与原逻辑效果，人工确认未发生才允许进入现有重试策略。

### 5.3 T1：执行事实确认（命令事实 = `command_ledger` + `run_command`）

**先说清「执行事实」到底落在哪（第 5 轮 P0 修正，v3.3 保留）**：

| 事实 | 载体 | 时机 | 说明 |
|---|---|---|---|
| 命令**已派发、结果未知** | **`command_ledger`** | 派发**前** | `command_id varchar(160)`、`idempotency_key`、`state`（`DISPATCH_STARTED / ACKED / FAILED / UNKNOWN`）、`resolved_at/by`；已有 `CommandLedger` Java 实现。⚠ 第 6 轮 N15：生产实列 **21 列**，另有 `abort_state varchar(24)` / `abort_detail varchar(200)` / `abort_at timestamptz`（`99s_command_abort.sql:26-28`）—— 那是**部分列**清单，不是完整列 |
| 命令**回包结果** | **`run_command`** | 回包**后** | `device_raw_response` / `status` / `attempt` / `sent_at` / `finished_at`；**没有 `command_id` 列**；`ack_at` 有列无写入者，不得当证据 |
| 节点执行结论 | `run_node.execution_resolution_status` + 物理证据字段 | 执行结论形成时 | `completed / failed_confirmed / reconciliation_required` 的判定见 §5.2c；成功才写 `physical_completed_at` |
| 物料效果意图 | `plate_material_effect`（通常 `PENDING`） | 回包后、节点标 completed 前 | T1 的物料账本；同时追加 `plate_material_effect_action(DECLARE)` |

⇒ **T1 = 节点执行结论 + 物料效果意图落库**，不是从零创建命令事实。T1 失败时隔离 run（§5.2b），恢复先对账：
成功回包且满足快照中的 `acceptedEvidenceLevels`，才可按声明快照补建效果；`UNKNOWN / DISPATCH_STARTED` 或证据不足一律人工核对。
**`ACKED` 只是 `device_ack`，不自动等于独立物理确认；任何路径都禁止直接重跑设备动作。**

**声明快照（不用新表）**：
- **run 启动时把每个节点的 `materialEffect` 快照写进 `run_node.input.material_effect_snapshot`**
  （含 `mode / inputs / outputs / operations / acceptedEvidenceLevels` 与哈希），并真正写入 `run.workflow_ver`；
- 效果记录再存一份 `declaration` 快照；续跑/补偿只读快照，不读最新设计；
- 子过程每轮执行前，把 `iterationBindings` 的**原始表达式与解析后值**一并冻结到 `target_snapshot`（含调用路径、轮次、来源/目的位置、`scanRef`、实际设备参数与 `command_id/stepSeq`）；设备命令与物料效果必须消费同一份绑定结果；
- 扫码晚绑定产生的身份事实保存于 run 作用域上下文，扫码原始回包仍在命令事实中；下游效果快照记录 `scanKey`、扫码证据及受控身份绑定记录 ID，不能只保存最后解析出的条码；
- 本期只保证物料声明与上述运行绑定快照，不声称顺便解决整个 BPMN 图的版本化。

**证据等级**：声明快照回答“打算做什么”，不属于物理证据。

| 等级 | 含义 | 边界 |
|---|---|---|
| `device_ack` | 设备或驱动报告成功 | 只证明执行链拿到成功回包，不冒充独立物理确认 |
| `physical_confirmed` | 设备最终状态查询、传感器或其他可信物理反馈确认 | 真机证据 |
| `manual_confirmed` | 授权人员现场核实 | 必须记录操作者、时间、原因 |
| `legacy` | 仅用于老数据 `status=completed` 的兼容 | 不代表新证据能力，也不能伪造精确完成时间 |

普通方法默认接受 `device_ack`；高风险方法可只接受 `physical_confirmed / manual_confirmed`。证据策略随声明快照冻结；
UI、事件与验收报告必须保留实际等级，不得统一写成“物理已核实”。

**效果记录必须保存**：

| 字段 | 为什么必须 |
|---|---|
| `declaration` + `payload_hash` | 续跑按当时声明解释旧动作；同键同负载可跳过，同键不同负载必须报错 |
| **原始目标与解析证据** | 保存原始 `target`、`plateId`、`barcode`、目标位置、`occupied_by_run`、`command_id/stepSeq`、解析时间和依据；原声明与原始证据不可覆盖 |
| **实际解析出的 `plate_id`** | 能确定身份时保存；补偿按它重放，不重跑 `target.by=position`；不能确定时允许 NULL，但 `APPLIED` 前必须补齐 |
| `expected_state_version` + 期望状态快照 | T1 记录应用前基线；T2 做 CAS，防止旧效果覆盖人工修正 |
| 结构化幂等字段 | `source_run_id / source_node_key / source_loop_index / source_attempt / effect_index`；`attempt` 只留痕、不进幂等键 |
| **每次动作追加 `plate_material_effect_action`** | 声明、应用、对账、补充目标证据、重试、取消均有不可变审计 |

目标最初无法解析但已有物理执行迹象时，效果进入 `NEEDS_RECONCILIATION`，保留空 `plate_id` 和完整解析证据；
授权人员可补充 `confirmedTarget + resolutionEvidence` 后恢复，但只能追加证据与 action，不能改写原始声明或原始解析记录。

### 5.4 T2：物料状态投影与可重放事件

**单效果、单事务**：`锁效果 → 锁板 → 校验期望版本/状态 → 应用迁移 → 写恰好一条自动事件 → 追加 effect action
→ 回写节点级 material_sync_status（按 §5.9 映射表；同一事务，与效果状态一起落）→ 标记 APPLIED`。
⚠ **节点级列的写入者与时机**（第 6 轮复核员 C 指出此前缺失，第 6 轮 P1-03）：
**唯一写入者是 T2 事务本身**（`MaterialEffectService`），**与效果行、事件、action 同事务**；
取值按 §5.9 的「效果状态 → 节点物料状态」映射表逐态对应（`APPLIED→applied`、`PENDING→pending`、
`FAILED→failed`、`REJECTED→rejected`、`NEEDS_RECONCILIATION→needs_reconciliation`、`CANCELLED→cancelled`）。
⇒ **T1 失败时不写该列**（效果意图都没落库 ⇒ 无从推导节点级值）；**T1 成功即写 `pending`**。
⇒ **闸门与恢复入口都只读这一列**，不再回查 effect 表（回查只在 §5.8 的人工对账路径里发生）。
⚠ **多效果节点**：同一节点一轮内可能有多个 effect ⇒ 节点级是**单值** ⇒ 按「**全部 APPLIED 才 `applied`**，
任一非 APPLIED 取其中最严重者（`rejected` > `needs_reconciliation` > `failed` > `pending` > `cancelled`）」
折算；该折算规则与 §11.2 T23「部分成功不得整体标记 APPLIED」一致。
`APPLIED` 必须恰好对应一条由该效果产生的自动 `plate_material_event`；缺事件、重复事件或效果未应用而有自动事件都视为事务不变量破坏，由集成测试阻断交付。

**事件不是差异补丁，而是完整状态快照**：
- `from_process_state / from_seal_state` 与 `to_process_state / to_seal_state` 始终保存两个维度的完整 before/after；
- `changed_fields` 明确列出本次实际改变的维度；`from = to` 可以表示一次真实“状态确认”，此时 `changed_fields=[]`，仍可推进事件版本；
- 事件同时保存 `from_state_version / to_state_version`。NULL 表示该维度明确为未知；维度未修改由 `changed_fields` 表达，不再靠“from/to 是否相同”猜测；
- 重放必须从已知基线事件及其 `to_state_version` 开始，按 `(plate_id, to_state_version, id)` 顺序应用完整快照。基线缺失或版本断档 ⇒ 停止重放并转人工，**禁止把 NULL 当成“保持不变”**；
- 自动事件必须有关联 `effect_id`、来源节点与证据；人工事件必须有操作者、原因与证据。对账/恢复 action 本身不生成板事件，只有确认真实板状态后才生成事件。

| 失败情形 | 行为 |
|---|---|
| 声明自相矛盾、字典/契约等业务规则不符 | 效果 `REJECTED` + 错误码，节点 `rejected`，告警转人工；不写 Event、不改 Plate、不自动重试 |
| 板找不到、归属不符、设备/声明/位置身份冲突 | `NEEDS_RECONCILIATION`；不写 Event、不改 Plate、不猜测，等待补充证据 |
| 数据库失败、可恢复并发冲突 | `FAILED` + 错误码；按 §5.8 有界退避与最大次数受控重试 |
| 人工盘点与自动迁移并发 | 按 §5.6 显式 rebase / cancel；禁止最后写入者无声覆盖 |
| run 已终止 / 取消 | 未应用效果置 `CANCELLED`（追加 action），不再重放 |

### 5.5 幂等键（v3.2：结构化唯一键，不落字符串 execution_id）

```
幂等键 = UNIQUE (tenant_id, source_run_id, source_node_key, source_loop_index, effect_index)
```

- `execution_id` 只是这一组字段的**逻辑名**，**不作为字符串列落库**（v3.2 采纳 v2.2 异议：拼接键要处理分隔符/长度/大小写，
  且 `node_key` 可能包含分隔符；结构化唯一键还能被外键与查询直接利用）；
- 命令账本的 `command_ledger.idempotency_key` 是**派发级**幂等键，由 `(run, node, loop, step_seq)` 编码；
  它和效果幂等键是**两层**（一个节点可能有多个 step、多个 effect），通过 `run_id / node_key / loop` 对齐，不互相替代。

**为什么换锚点**（三方裁决 D1）：v2 用的是 `run+node+loop+plate`，它有两个洞 ——
① 一个节点**产生多个效果**时（分装、混合）没有区分位；
② 「板」不是效果的天然单位（一个效果可能涉及多块物料）。

⇒ `effect_index` 是**同一次执行内的效果序号**（一个节点声明 3 个效果就是 0/1/2），
一个效果涉及几块物料就在它自己的声明里写清 ⇒ **幂等键与「板」解耦**。

| 设计点 | 理由 |
|---|---|
| **循环工艺单元 = 子过程，不是孤立节点自转** | 常见业务是“取板 → 处理 → 放板”等多个动作组成子过程，每轮换一块板、来源位置或目的位置；`loop_index` 是防止合法效果被去重的底线，不代表推荐单节点循环建模 |
| **`source_loop_index` 进幂等键** | 同一执行节点在不同轮次产生的效果均为合法效果，不能被幂等键吃掉；普通无环执行固定为 0 |
| **子过程调用路径必须唯一** | `source_node_key` 存**执行调用路径键**（含子过程调用键及必要的祖先轮次），不是模板内局部 `node_key`；完整调用栈与轮次向量另存 `target_snapshot.loopPath`，避免同一子过程被多处/多轮调用时撞键 |
| **每轮参数先绑定、后派发** | 每轮显式解析 `iterationBindings`；来源/目的位置、板身份引用与设备参数来自同一份绑定结果，缺失或冲突必须在物理派发前阻断 |
| **`attempt` 不进幂等键** | 设备/节点**重试**是同一次逻辑执行的第 N 次尝试 ⇒ 不该产生新的物料迁移（attempt 只进 action 留痕） |
| **同键同负载可跳过 / 同键不同负载必须报错** | 静默吞掉「设计变了」是最危险的失败模式 |
| **`payload_hash` 必存** | 哈希覆盖声明及本轮已解析绑定值，作为「同键是否同负载」的依据 |

⚠ **`source_loop_index` 取执行上下文里的轮次，不取 `run_node.loop_index`** ——
这条是 2026-11-12 回源码核出来的（`docs/评审记录/20261112-04-openai.md` O-4），v3.2 再按第 5 轮复核收紧：

⚠ **两种情形的边界（v3.3 补，避免把时序论证套错地方）**：
| 情形 | 库里有什么 | 时序论证是否适用 |
|---|---|---|
| **有环图，第 N 圈（N≥2）** | 汇总行 + 第 1…N-1 圈的行（**本圈没有**） | **适用** ⇒ 读到的是上一圈 ⇒ 撞键 |

并把「无环图只有汇总行」当作不一致的例证 —— **这条例证不成立**：无环图每个节点只跑一轮，
`loop_index=0` 就是它**唯一且无歧义**的值；不一致只存在于**有环图**（同一 node_key 有 1 条汇总行 + N 条圈次行）。

很可能改成「等圈次行存在时再读」，而那在 T1 时点上**永远等不到**。

⇒ `attempt` 不入键的收益也随之明确：**设备重试不改 `visit`** ⇒ 同一逻辑执行重试 N 次仍是同一个幂等键 ⇒ 效果只应用一次 ✓

按上述语义，**该用途已不成立**。

⇒ **直接后果**：§13.2-13 的方案 (b)「圈次行执行后回写 `material_sync_status`」在现有 SQL 语义下**不安全**
（第 2 圈的回写会覆盖第 1 圈的同步状态）⇒ **(b) 被否**，O-16 只能取 (a)（从 `plate_material_effect` 汇总，§5.2b）。
⇒ **同时新增一条已知缺口**：历史圈次行数据不可信（生产库当前 `loop_index>0` 行数 = **0**，暂无存量受害数据，
但**已有的 `loop_index>0` 语义不要再被当成逐圈事实**）。
⇒ 库内**已有**正确的写法可照抄：`insertBuiltinCommand` / `updateBuiltinCommandNote` 明确带了 `AND loop_index = 0`
（`RunMapper.xml:658` / `:680`）⇒ S1/S2 的新写入**必须**显式带 `AND loop_index = 0` 或精确圈次条件。

⚠ **跨续跑（v3.2 补 · 并行 05 号评审 O-2）**：续跑时 `GraphRunner` 的内存 `visits` 从零开始，
若节点已跑过 N-1 圈，第 N 圈会重新得到 `visit=1` ⇒ **与已应用效果撞幂等键**。
⇒ S2 实现要求：续跑启动前**按 `run_node` 圈次行（或效果记录）恢复每个节点的 `visit` 起点**
（`MAX(source_loop_index) + 1`），并以该起点初始化 `visits`；**不得从 1 重新计数**。

⚠ **v3.2 补（第 5 轮 S12；第 6 轮 N06 收紧措辞并补漏）**：**下列 5 条**按节点更新/查询的 SQL（`updateNodeStateLive` / `updateNodeResult` / `markBypassed` /
`selectTopNodeKeyIds` / resume 的 `deleteIncompleteTopNodes`）**只过滤 `level=0`、不过滤 `loop_index`** ⇒ 会命中圈次行。
⚠ **不是「全库都这样」**：`insertBuiltinCommand` / `updateBuiltinCommandNote`（`RunMapper.xml:658` / `:680`）**明确带了 `AND loop_index = 0`** ⇒ 库内**已有**正确写法可照抄，S1/S2 照抄即可。
⚠ **原清单漏了一条**（第 6 轮 N06）：`selectCompletedNodeKeys`（`RunMapper.xml:466-472`，`level=0` + `status='completed'`，**无 `loop_index`**）是**续跑链路取 skipKeys 的来源**（`WorkflowService.java:710`），与 `deleteIncompleteTopNodes` 同属一条链 ⇒ 一并列入。
⇒ S1/S2 的新写入必须显式带 `AND loop_index = 0`（或按精确圈次条件），**不得沿用现有写法**；结合上文「圈次行不是不可变事实」⇒ 更严格地说，**任何按 `node_key` 的写都可能改到圈次行**。

⚠ **v1 的 `(owner_run_id, owner_node_key, plate_id)` 会让循环第三圈撞唯一索引** —— 这是硬伤（v2 已修）。

### 5.6 并发：板级串行化与冲突仲裁

唯一索引只防“同一幂等键重复”，不防两个不同节点/人工同时改同一块板；Effect 行锁也不代替 Plate 行锁。

| 场景 | 规则 |
|---|---|
| 两个自动迁移同改一块板 | T2 内 `SELECT ... FOR UPDATE` 锁板 + `state_version` CAS；版本不符 ⇒ `FAILED(MAT_STATE_CONFLICT)`，不写 Event、不覆盖 |
| 人工改状态 API | 必须带 `expectedVersion`；不符 ⇒ HTTP 409 + 当前值/版本；人工事件同样使用完整 before/after 与 `changed_fields` |
| 人工盘点 vs 自动迁移同时发生 | 自动效果进入冲突处置，不自行改基线；只有授权 `REBASE` 可在声明 hash、目标板和效果语义均未变化时更新期望版本后重试，否则必须 `CANCEL` 并新建效果 |
| 审计一致性 | `from_*` 必须等于本次事务读到的完整值；自动事件唯一键与同板 `to_state_version` 唯一键共同防止重复/交错提交 |
| 冲突可见性 | 冲突一律追加 `plate_material_effect_action(REBASE/CANCEL)` + 告警；禁止最后写入者无声覆盖 |

⚠ 现有 `PositionLock` 解决位置互斥，不等于物料状态并发已解决。声明 hash 或目标身份冲突**禁止 rebase**，必须人工对账。

### 5.7 完成处理器：唯一注入点与圈次传递

物料效果处理只有一个注入点：共享的 `RunStateMachine` 实例，不是在 GraphRunner 和 WorkflowService 各挂一次。
`NodeCompletionHandler` 是 kernel/domain 定义的端口；`MaterialEffectService` 在 boot/infrastructure 实现并注入。
`GraphRunner` 只传执行上下文，不依赖数据库、Mapper 或物料表。

| 返回 | 含义 | 调用方动作 |
|---|---|---|
| `CONTINUE` | 当前节点无效果，或效果已 `APPLIED` | 节点可完成，后继进入派发闸门检查 |
| `HOLD` | 效果 `PENDING / FAILED / REJECTED / NEEDS_RECONCILIATION / CANCELLED` | 节点保持物理完成，后继被闸门阻断，run 进 `paused(material_sync)`；REJECTED 不与 FAILED 合并 |
| 抛持久化异常 | T1：执行结论/效果意图无法持久化 | 立即中止当前 run 并隔离，不得续跑重放设备动作 |

| 决策点 | 结论 |
|---|---|
| 注入点 | `RunStateMachine.executeNode`：设备执行成功之后、`np.setStatus(COMPLETED)` / `emit(NODE_COMPLETED)` 之前调用，构造注入一次 |
| 完成上下文 | 显式携带 `runId / runNodeId / nodeKey / loopIndex / effectIndex / commandId / stepSeq / 执行证据`；不允许反查最新一圈 |
| 圈次从哪来 | 图路径传内存 `visit`（1..N）；顺序执行与无环图传 0；签名扩展点仍为 `GraphRunner.java:649`、`WorkflowService.java:1057/1065`、`RealWorkflowRunner.java:183`、`RunStateMachine.java:76`（**顺序路径 `executeAll` 内部调用 `executeNode` 的那一处**）及测试/demo。⚠ **第 6 轮 N13 补全**：`src/main/java` 下还有 **4 个 demo 的 5 处调用点**同批改，否则**主源码编译不过**（不只是测试）：`driver/EndToEndDemo.java:156`、`driver/tcp/SidecarDemo.java:131`、`persistence/PersistenceDemo.java:86`、`engine/EngineDemo.java:61` 与 `:88` |
| 覆盖范围 | 只覆盖设备 TASK 节点；BUILTIN 声明 `materialEffect` 预检 ERROR；flow-run 与影子跑是已知缺口 |
| 失败语义 | T2 类失败留在效果状态与 action；只有 T1 持久化失败上抛，由 `WorkflowService` 隔离 run |
| `effect_index` 分配 | 一次通知内按 `outputs` 数组顺序分配 `0..n-1`；重放/重试复用原序号 |
| 与 ExecutionListener 的区别 | listener 是可失败的副作用出口之外的通知机制，异常不得影响执行；完成处理器必须能反映失败，二者不合并 |
| 事件落库 | `ExecutionListener` 事件缓冲且失败路径可能丢，不承载必须补偿的意图；完成处理器写 effect/action，T2 写物料 Event |
| 节点级同步状态的写入者 | **T2 事务内的 `MaterialEffectService`**（唯一写入者），与效果行/事件/action **同事务**；取值按 §5.9 映射表逐态对应；多效果按「全部 APPLIED 才 `applied`，否则取最严重者」折算；T1 失败不写该列 |

⇒ 不新建通用 Execution Fact 平台，也不把本设计扩大成全局通用物料状态机；仅新增上述端口、实现与续跑守卫。

### 5.8 Worker、恢复状态机与人工闭环

**效果状态机（6 态）**：对账不直接写 APPLIED，而是恢复原 T2 投影路径。

| 当前 | 触发 | 下一个 | 谁 | 记什么 |
|---|---|---|---|---|
| `PENDING` | T2 成功 | `APPLIED` | AUTO | action `APPLY` + 恰好一条自动 Event |
| `PENDING` | 确定性声明/配置/业务规则错误 | `REJECTED` | AUTO | action `APPLY` + error_code；无 Event |
| `PENDING` | 物理身份或结果证据冲突 | `NEEDS_RECONCILIATION` | AUTO | action `APPLY` + 证据；无 Event |
| `PENDING` | 可恢复数据库/并发失败，或 Worker 重试超限 | `FAILED` | AUTO | action `APPLY/RETRY` + error_code |
| `PENDING / FAILED / NEEDS_RECONCILIATION` | run 终止或授权取消 | `CANCELLED` | AUTO / MANUAL | action `CANCEL` + 原因 |
| `FAILED` | 可恢复错误的人工/到期重试 | `PENDING` | **需恢复权限** | action `RETRY` + 原因 |
| `NEEDS_RECONCILIATION` | `completed`：物理已完成，目标与证据足够 | `PENDING` | **需核对权限** | action `RECONCILE` + `resolutionEvidence`；随后走 T2 |
| `NEEDS_RECONCILIATION` | `not_completed`：明确未执行/未产生该效果 | `CANCELLED` | 同上 | action `RECONCILE` + 证据；不写 Event |
| `NEEDS_RECONCILIATION` | `still_unknown`：证据仍不足 | 保持原态 | 同上 | 追加 action 与证据，不伪造状态推进 |
| `REJECTED / APPLIED / CANCELLED` | 终态 | — | — | 不自动重试；更正真实板状态须另走人工 Event 或新效果 |

**Worker 领取与重试**：
- 只扫描 `PENDING AND (next_retry_at IS NULL OR next_retry_at <= now())`；FAILED 不会无条件被自动任务反复拾起，只有可恢复错误且未超限的显式调度/授权 retry 才回到 PENDING；
- 每个效果一个短事务，使用 `SELECT ... FOR UPDATE SKIP LOCKED` 领取；事务内完成 T2，**不增加持久 `PROCESSING` 状态**。Worker 崩溃导致事务回滚，行锁自然释放，其他 Worker 可继续；
- `apply_attempt_count` 单调递增，记录 `last_error_code / last_error_message / last_attempt_at`；可恢复错误使用有界指数退避与 `next_retry_at`，达到配置上限转 `FAILED` 并告警转人工；
- 同键同负载的重复回调可跳过；同键不同负载、声明 hash 变化或目标身份变化必须报错，禁止以 retry/rebase 掩盖；
- `REBASE` 只更新版本基线，必须由授权操作、留 action；`CANCEL` 只取消未应用效果；二者均不直接生成板 Event。

**动作审计表 `plate_material_effect_action` 是效果处置历史**：声明、应用、对账、补证、重试、rebase、取消均追加一行；
`plate_material_event` 只记真实板状态快照，不用 RECONCILIATION 事件伪造迁移。

| 崩溃/失败场景 | 行为 |
|---|---|
| **T1 前崩溃**（命令已下发/已回包，但执行结论或效果意图没写成） | 先按命令账本和回包对账；证据满足快照才补 `completed` 与 PENDING 效果，UNKNOWN/DISPATCH_STARTED 则 `reconciliation_required` + run 隔离；禁止“重跑即可” |
| T1 后 / T2 前崩溃 | PENDING 效果由 Worker 按已解析 `plate_id` 重放 T2，不重跑设备或位置寻址 |
| T2 回滚 | 同事务回滚 Plate/Event/action/APPLIED；效果保持 PENDING，退避后重放 |
| 重复补偿 / 双 Worker | Effect 行锁、结构化幂等键、Effect→Event 唯一约束共同保证只应用一次 |
| 补偿时流程已续跑/已结束 | 效果可独立对账；run 终止则未应用效果取消，不能借补偿重新驱动物理执行 |
| run 被隔离 | `quarantined` + experiment 级 `runtime_hold`；执行确认、命令账本、Effect/Event 引用全部闭环前禁止 resume |
| 数据库异常 | 不得无声继续；记录错误并隔离/转人工 |

**人工恢复统一要求**：`material:reconcile / material:retry / material:cancel / material:rebase` 分权；`note` 必填；
每次操作追加 action 与 `actor_id`，目标补证保存 `confirmedTarget + resolutionEvidence`；恢复只处理记录与投影，绝不重新执行设备动作。

### 5.9 执行确认、物料效果与 Run 状态的关系

`node_status`、`execution_resolution_status`、`material_sync_status` 是三个不同维度，不能互相替代。

| 执行确认 | 物料效果 | 既有节点状态 | 节点物料状态 | 结果 |
|---|---|---|---|---|
| `completed` | 全部达成 | `completed` | `applied` | 正常继续 |
| `completed` | 待投影/可恢复失败 | `completed` | `pending / failed` | 下游阻断，run `paused(material_sync)` |
| `completed` | 物理事实待核对 | `completed` | `needs_reconciliation` | 下游阻断，人工对账 |
| `completed` | 确定性声明/规则错误 | `completed` | `rejected` | 下游阻断，不自动重试 |
| `completed` | 不再应用 | `completed` | `cancelled` | 下游阻断，只能显式处置 |
| `failed_confirmed` | 未产生效果 | `failed / manual` | `not_required` 或 `cancelled` | 明确未执行证据充分时才走既有安全重试 |
| `reconciliation_required` | 无论 `none / legacy_unspecified / transition` | 不伪造 failed/completed | 可有效果，也可 `not_required` | 禁止普通 resume、删除重建和自动重试，先对账 |
| 成功但 T1 持久化失败 | 意图未知 | 不标 completed | 不写假状态 | 隔离 run，不落假完成 |

⇒ 显式 `none` 只表示“无物料效果”，不表示“物理结果一定已知”；`legacy_unspecified` 同样受执行确认守卫约束。
⇒ 不新增 `node_status` 枚举值；`REJECTED → rejected` 是一一映射，其他效果状态也按上表映射，不合并进 FAILED。
⇒ Run 由流程依赖、执行确认与物料一致性共同决定；物料问题不一律变成 Run 失败，但异常物料的依赖后继不能继续。


## 6. 节点的物料效果契约

### 6.1 独立列，不塞进 `params`

**为什么不能放 `params`**：执行侧的**设备参数通道**只读 `workflow_node.params->'method_params'`（`params` 的其他字段各走各的通道，见 §3 的口径修正），
并用**扁平 JSON 解析器**解析后透传给驱动 ⇒ 嵌套结构放进去会被错误解析、
**甚至透传给设备**。而且 `produces` 是**中控自己的业务契约**，不是设备执行参数。

⇒ **独立列** `workflow_node.material_effect jsonb`：

```
workflow_node
├── params → method_params   ← 发给设备的参数（不动）
└── material_effect          ← 中控的物料契约（新增）
    ├── inputs
    ├── outputs
    └── operations
```

**好处**：不混进设备参数；设计器可独立编辑；可独立做 JSON Schema 校验；
可查"哪些节点声明了物料效果"；将来升级契约不影响设备驱动。

### 6.2 契约形态

```json
{
  "materialEffect": {
    "mode": "transition",
    "acceptedEvidenceLevels": ["device_ack", "physical_confirmed", "manual_confirmed"],
    "inputs":  [ { "by": "plateId", "plateId": 1001 } ],
    "outputs": [ { "by": "plateId", "plateId": 1001,
                   "processState": "amplified_product",
                   "sealState": "sealed" } ],
    "operations": []
  }
}
```

| 字段 | 含义 |
|---|---|
| `mode` | `none`（明确无物料副作用）/ `transition`（声明状态迁移）/ `legacy_unspecified`（老流程，运行等价 `none`，预检 WARN） |
| `inputs` / `outputs` | 物料身份 + 结果。**本期只支持一对一状态变化**；`outputs` 是数组（未来 1→N 预留） |
| `operations` | 预留：分装（1→N）、混合（N→1）、转板（1→1 新板）、取样检测（1→1 + 数据） |

⚠ **本期不实现分装/合并**，但**结构不封死**扩展空间（评审 O-3 的要求）；`operations` 本期仅占位，**预检拒绝未知 operation**（v3.2 收窄空承诺）。

⚠ **"本期只支持一对一"是 `_校验规则_` 的限制，不是表结构的限制**（评审 O-5 的要求）：
`inputs` / `outputs` 是**数组**，`operations` 是**数组** ⇒ 表结构天生支持多输入多输出；
本期只是**在校验层**拒绝一条声明里出现多个输入/输出。
⇒ 将来放开 SPLIT / MERGE **不需要改表**，只需要放宽校验并实现 operation 语义。

### 6.2a 子过程循环：每轮参数绑定（v3.3 新增）

循环出板、逐板处理等场景应建模为**有明确输入/输出的子过程**，而不是让一个孤立节点无上下文地自循环。
子过程可以包含取板、扫码、处理、放板等多个动作；每一轮通过显式 `iterationBindings` 改变参数：

```json
{
  "subprocess": "plate_batch_process",
  "iterationBindings": {
    "sourcePosition": "${loop.item.source}",
    "destinationPosition": "${loop.item.destination}",
    "plateTarget": { "by": "scanRef", "scanKey": "currentPlate" }
  }
}
```

| 规则 | 必须行为 |
|---|---|
| 每轮绑定先于物理派发 | 当前轮的来源位置、目的位置、板身份引用等任一必需值缺失或冲突 ⇒ 不派发设备命令；不得等动作做完后才补参数 |
| 设备与物料共用绑定结果 | `method_params` 和 `material_effect` 不得各自解析出不同位置/身份；同一个解析器输出同时用于命令、执行证据和效果快照 |
| 绑定结果不可变 | 原始表达式、解析后值、调用路径、轮次向量和 `command_id/stepSeq` 冻结进 `target_snapshot`；后续轮次不得覆盖前轮 |
| 重试复用原轮次绑定 | 设备重试/补偿不得重新读取已被后续轮次修改的共享变量；同键不同绑定值按冲突处理 |
| 调用路径可区分 | 同一子过程模板被不同节点或不同父循环调用时，以执行调用路径键区分；完整 `loopPath` 进入证据快照 |

⇒ 现有图引擎是否已有“子过程定义、每轮参数解析与调用路径传递”能力，**本稿不假设已具备**；
S2 必须把它列为独立集成点，并先通过 §11.2 T37/T38。这里定义的是物料契约对循环执行的要求，不冒充现成引擎功能。

### 6.3 目标解析：物料身份优先，位置只是辅助

| 规则 | 说明 |
|---|---|
| **物料身份优先** | `plateId` / `barcode` 是身份；位置是空间属性，不是身份 |
| 位置寻址必须校验归属 | 事务内校验 `tenant_id + resource_id + occupied_by_run`（fail-closed） |
| 条码寻址也要校验 | 校验预期位置/归属，除非将来有显式跨 run 移交操作 |
| **`AUTO-` 是系统保留编码命名空间** | 由系统生成器显式登记和解析，不靠“前缀看起来相似”猜测；该命名空间内的身份不得作为已核实条码驱动物料迁移 |
| 设备重分配 | 设计时 `resourceId` 不一定是实际目标；命令参数、设备回包、最终位置只是不同等级的运行时证据 |
| 解析失败/冲突 | 保留原始证据并转人工；不得用相似前缀、当前占用者或设备 ID 直接猜出目标 |
| 多步节点 | target 必须指明哪一步结束时的位置，并保存 `command_id + stepSeq`；不能用节点结束时另一位置反推整节点作用对象 |

⇒ T1 在能确定身份时保存 `plate_id`；不能确定时保存 NULL + 原始 target 和解析证据并进入 `NEEDS_RECONCILIATION`。
后续补证只能追加 `confirmedTarget / resolutionEvidence`，不覆盖原声明与原始证据；APPLIED 前必须得到确定的同租户 `plate_id`。

⚠ **barcode 事实（v3.2 补）**：`plate.barcode` 是 **NOT NULL** 且同租户唯一（`uk_plate_barcode`），当前代码无更新路径 ⇒ §17 Q1 按此修正。

**证据优先级（评审 O-3 的要求：不能只凭 `occupied_by_run` 就认定物理身份已确认）**：

| 序 | 证据 | 说明 |
|---|---|---|
| 1 | 声明里**显式**的 `plateId` / `barcode` | 人/设计器指名的那块板 —— 但**它只是"我们以为是谁"，不是"物理上是谁"** |
| 2 | **设备命令回包**里的物料标识 | 设备自己说的（比位置投影新）—— 这是**物理证据** |
| 3 | 命令参数里的目标位置 + 位置状态投影 | 最弱 —— **只是辅助** |
| 4 | `occupied_by_run` | **只能证明"这个 run 占了它"，不能证明"物理上就是它"** |
| 5 | **`plate.position_status` / `possible_locations`**（第 6 轮 N02 补） | 板级**位置可信度**（KNOWN/IN_TRANSFER/UNKNOWN/LOST）—— **它不是身份，但它是「能不能用第 3/4 级去解析身份」的准入条件** |

⇒ **第 5 级不是第 6 个身份来源，而是三、四级的准入闸门**（v3.3 补 · 第 6 轮 N02）：

| 硬规则 | 说明 | 依据 |
|---|---|---|
| **目标板 `position_status ∈ {UNKNOWN, LOST}` ⇒ 一律不得由第 3/4 级证据解析出身份** | 直接进 **`NEEDS_RECONCILIATION`** + 转人工；**不得**落库 `plate_id` | `93_m1_parallel.sql:188-190` 的列注释原文：「`UNKNOWN` 必须人工盘点，**系统不做任何猜测**」 |
| `position_status = 'IN_TRANSFER'` | 板正在转移 ⇒ 第 3 级（位置投影）**不可用**，只能靠第 1/2 级 | `PositionLock.java:212/271`、`DeviceStateMapper.xml:291` 会写该值 |
| `position_status = 'KNOWN'` | 第 3/4 级**可用** | 同上 |
| 该列是**活的**真源，不是历史遗留 | 人工盘点会写它（`PauseMapper.xml:27-30`，由 `PauseManager.java:422/501` 驱动）⇒ 不能当只读字段 | 生产实况：`public.plate` 6 行 = `KNOWN`×4 / `IN_TRANSFER`×2 |

⇒ **与 §3 / §4.2 / §17 Q2 的口径对齐**：这三处早已把 `plate.position_status` 列为独立真源，
**只有本节的实施规范漏了它** ⇒ 补齐后，「位置可信度 = `position_status`」这句话才真正落到代码里。
⚠ **与 §11.2 T10 的分工**：T10 覆盖的是「**找不到**」（解析不出身份）⇒ 隔离转人工；
本规则覆盖的是「**找到了，但位置状态官方标记为未知/丢失**」⇒ 同样不采信。两者是**并列**关系，不重复。

⇒ **证据冲突与规则错误分开**：

| 情形 | 处置 | 理由 |
|---|---|---|
| ① 声明与 ② 设备回包指向不同板 | `NEEDS_RECONCILIATION`；`plate_id` 不采信任一方，不写 Event、不改 Plate | 物理身份不确定，不是确定性配置错误；人工补证后才可恢复 |
| ② 设备回包与 ③ 位置投影指向不同板 | 同上 | 位置可能滞后，也可能是回包/映射错误；不能仅因设备优先就硬写 |
| ③ 与 ④ 冲突，或位置可信度为准入拒绝 | 同上 | 弱证据不能互猜；UNKNOWN/LOST 必须人工盘点 |
| ① 与 ② 一致，且位置准入与归属校验通过 | 解析为该板，保存完整证据 | 多路证据互证 |
| 声明自相矛盾、字典非法、契约不支持 | `REJECTED` | 确定性规则错误，与物理事实不确定分开 |

⇒ 对账确认目标后，仍按 `completed → PENDING → T2` 应用；T2 再次校验版本、租户、归属和声明，补证接口本身绝不直接改板。

### 6.3a 中途扫码与身份晚绑定（v3.3 新增）

真实流程可以在开始时不扫码，执行到某个子过程节点才扫描并取得板码。此时不得在 run 启动时伪造固定 `plateId`，
而应把“扫码”建模为**身份证据产生动作**，把后续使用建模为**对扫描事实的引用**：

```json
{ "target": { "by": "scanRef", "scanKey": "currentPlate" } }
```

| 时点/情形 | 规则 |
|---|---|
| 扫码节点完成 | 将原始条码、原始回包、`command_id/stepSeq`、调用路径和轮次写入 run 作用域 `materialIdentities[scanKey]`；同一 `scanKey` 同轮重复写同值可幂等，不同值必须冲突告警 |
| 下游节点尚未到扫码步骤 | 预检必须证明依赖顺序；运行期引用尚不存在的 `scanRef` ⇒ 派发前阻断并标记流程/数据错误，**不得先执行再补身份** |
| 扫码命中同租户既有板 | 绑定到稳定 `plate.id`，再校验位置可信度、归属和声明；`plate_id` 才是后续效果的内部目标 |
| 扫码命中当前物理位置的 AUTO 占位板 | 只有在扫码证据、位置、run 占用一致且新条码同租户唯一时，才允许受控一次性 `AUTO → scanned` 绑定；更新 `plate.barcode` 与追加 `plate_identity_binding` 必须同事务 |
| 扫码无匹配板，或多板/位置/声明冲突 | 不自动建板、不覆盖已有真实条码、不选择“最像”的板；进入 `NEEDS_RECONCILIATION`，由授权人员补证 |
| 扫码之后 | 下游只解析一次并冻结 `plate_id + identityBindingId + 原始证据`；补偿重放不得重新扫码，也不得随当前位置变化改认另一块板 |

- 扫码本身**不改变工艺阶段或膜状态**，因此不写 `plate_material_event`；身份绑定写独立、不可变的 `plate_identity_binding` 审计。
- 普通条码编辑仍然禁止；唯一例外是上述 AUTO 占位身份的受控绑定。已绑定真实条码的板不得再次借扫码改码。
- 身份绑定与物料效果分开：绑定接口/扫码处理器只确认“是谁”，T2 仍按原声明确认“变成什么状态”；禁止绑定成功就直接 APPLIED。
- 现有代码是否已有可复用的扫码结果上下文与 AUTO 改码事务，**尚未核实**；S2 实现前必须对源码确认，不得把本节当成现有能力描述。

### 6.4 显式声明 vs 未声明

| 情况 | 行为 |
|---|---|
| 明确无物料副作用 | 节点声明 `materialEffect.mode = "none"` ⇒ **不报警** |
| **内置逻辑节点（BUILTIN）声明物料效果** | **ERROR**（预检拦截）：内置节点不经过统一完成点，本期不承载物料效果 |
| **画布逐步执行 / 影子跑 / 单命令探针** | **不覆盖**：这些通路不产生/不经过物料效果处理（§13.2-7/8），只允许在操作规范约束下用于调试 |
| 老流程未声明 | **WARN**（不改行为）；新版本里按 WARN 处理 |
| 已知会改内容/膜的节点缺声明 | **ERROR**（发布/启动时拦截） |
| 无法分类的节点 | 要求人工确认 `none` 或补声明 |
| 声明的状态不在字典里或已停用 | **ERROR**（发布/启动时拦截）；**运行期若被停用/删除 ⇒ 迁移失败转人工，不写「未知状态」冒充成功** |

⚠ **为什么不能一律 WARN**：v1 说"系统分不清搬运和忘了声明" —— 这不准确。
**能力/方法元数据可以在设计期标出**「位置-only / 可改变内容或膜 / 未知」，
只用于校验，不用于运行期猜状态 ⇒ 有了分类，就不必对所有节点一刀切。

## 7. 数据模型汇总（v3.3 · 含第 6 轮与现场子循环/扫码补充；最终版待真跑）

> 下列 SQL 是 **S1 迁移脚本的结构基准**，不是可直接重复执行的幂等脚本：
> `CREATE TABLE / ADD COLUMN / ADD CONSTRAINT` 在 PG17 里重复执行会报错
> ⇒ S1 实施时用 `DO $$ ... EXCEPTION WHEN duplicate_object / duplicate_column ...` 包裹（v2.2 §14 / 第 5 轮 D14）。
> **不改既有表的数据语义**：只加列/加表/加约束。

```sql
-- ① 板级工艺阶段字典（租户级；模板集与租户副本分开）
CREATE TABLE plate_process_state (
  id           bigserial PRIMARY KEY,
  tenant_id    bigint      NOT NULL,          -- 模板用 0；不加 tenant FK（模板行会挡住）
  code         varchar(32) NOT NULL,
  display_name varchar(64) NOT NULL,
  sort_order   int         NOT NULL DEFAULT 0,
  is_template  boolean     NOT NULL DEFAULT false,
  enabled      boolean     NOT NULL DEFAULT true,   -- 停用而非删除
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, code)
);
-- 注：模板集用 tenant_id = 0 存；新租户初始化时复制成租户副本。

-- ② plate 加列（v3.2：不加 current_run_id / origin_*，归属见 §4.5）
ALTER TABLE plate
  ADD COLUMN process_state   varchar(32),            -- → plate_process_state.code；NULL=未知
  ADD COLUMN seal_state      varchar(16),            -- NULL=未知；none / sealed
  ADD COLUMN state_version   bigint NOT NULL DEFAULT 0;  -- CAS 用
-- 引用约束：process_state 必须存在于同租户的 plate_process_state。
-- ⚠ MATCH SIMPLE（PG 默认）：process_state 为 NULL 时不强制外键 ⇒ 老数据「未知」≠「非法」。
ALTER TABLE plate ADD CONSTRAINT fk_plate_process_state
  FOREIGN KEY (tenant_id, process_state)
  REFERENCES plate_process_state (tenant_id, code);
ALTER TABLE plate ADD CONSTRAINT ck_plate_seal_state
  CHECK (seal_state IN ('none','sealed'));   -- NULL 自动通过 ⇒ 表示未知
-- 老数据：process_state / seal_state 均为 NULL = 未知；state_version=0 无害。
-- （v3.1 的 seal_state NOT NULL DEFAULT 'none' 是一次静默回填，会把老板断言成「无膜」，v3.2 已改）

-- ③ 流程节点：物料效果声明独立列（v2.2 口径；不塞 params）
ALTER TABLE workflow_node
  ADD COLUMN material_effect jsonb;   -- 声明（mode + inputs/outputs/operations）；运行期快照另存 run_node.input

-- ④ 节点级：流程生命周期、执行确认、物料同步三者分离（共六列）
ALTER TABLE run_node
  ADD COLUMN physical_completed_at timestamptz,
  ADD COLUMN physical_evidence_level varchar(24),
  ADD COLUMN physical_evidence jsonb,
  ADD COLUMN execution_resolution_status varchar(32) NOT NULL DEFAULT 'unresolved',
  ADD COLUMN material_sync_status varchar(24) NOT NULL DEFAULT 'not_required',
  ADD COLUMN material_error_code varchar(64);
ALTER TABLE run_node ADD CONSTRAINT ck_run_node_exec_resolution
  CHECK (execution_resolution_status IN
    ('unresolved','completed','failed_confirmed','reconciliation_required'));
ALTER TABLE run_node ADD CONSTRAINT ck_run_node_physical_evidence_level
  CHECK (physical_evidence_level IN ('device_ack','physical_confirmed','manual_confirmed','legacy'));
ALTER TABLE run_node ADD CONSTRAINT ck_run_node_physical_completion
  CHECK (
    (execution_resolution_status = 'completed'
       AND physical_completed_at IS NOT NULL
       AND physical_evidence_level IS NOT NULL
       AND physical_evidence IS NOT NULL)
    OR (execution_resolution_status <> 'completed' AND physical_completed_at IS NULL)
  );
ALTER TABLE run_node ADD CONSTRAINT ck_run_node_material_sync
  CHECK (material_sync_status IN
    ('not_required','pending','applied','failed','needs_reconciliation','cancelled','rejected'));
-- 老数据默认 unresolved + not_required：不伪造物理完成；legacy 只在有人工迁移证据时显式标记。
CREATE INDEX ix_run_node_exec_resolution
  ON run_node (tenant_id, execution_resolution_status)
  WHERE execution_resolution_status IN ('unresolved','reconciliation_required');
CREATE INDEX ix_run_node_material_sync
  ON run_node (tenant_id, material_sync_status)
  WHERE material_sync_status IN ('pending','failed','needs_reconciliation','cancelled','rejected');
-- 索引 WHERE 必须覆盖 §5.2b 全阻断清单和 §5.2c 守卫查询；枚举回退先迁数据，再 NOT VALID→VALIDATE。

-- ⑤ 物料效果（迁移意图）：目标证据、版本基线、Worker 重试均有载体
CREATE TABLE plate_material_effect (
  id                bigserial PRIMARY KEY,

  source_run_id     bigint      NOT NULL,

  resolution_evidence jsonb     NOT NULL DEFAULT '{}'::jsonb, -- 原始解析证据，不覆盖
  reconciliation_evidence jsonb,                      -- 后续补证，追加进 action 历史
  payload_hash      varchar(64) NOT NULL,
  expected_state_version bigint,
  expected_process_state varchar(32),
  expected_seal_state varchar(16),
  status            varchar(24) NOT NULL,
  apply_attempt_count int NOT NULL DEFAULT 0,
  next_retry_at     timestamptz,
  last_attempt_at   timestamptz,
  applied_at        timestamptz,
  error_code        varchar(64),                      -- 最近一次错误

  CONSTRAINT ck_effect_status CHECK (status IN

  CONSTRAINT ck_effect_dimensions CHECK
    (source_loop_index >= 0 AND effect_index >= 0 AND source_attempt >= 0 AND apply_attempt_count >= 0),
  CONSTRAINT ck_effect_applicable_target CHECK

CREATE UNIQUE INDEX uk_plate_material_effect_key

-- Worker 只扫 PENDING；FAILED/NEEDS_RECONCILIATION 是人工/受控恢复队列，不被普通 Worker 无条件拾起。

CREATE UNIQUE INDEX uk_plate_material_event_effect
  ON plate_material_event (tenant_id, effect_id) WHERE effect_id IS NOT NULL;
CREATE UNIQUE INDEX uk_plate_material_event_version

CREATE INDEX ix_plate_material_event_replay
  ON plate_material_event (tenant_id, plate_id, to_state_version, id);
CREATE INDEX ix_plate_material_event_source ON plate_material_event (tenant_id, source_run_id);
-- from=to 且 changed_fields=[] 是合法状态确认事件；恢复 action 本身不写 Event。
-- 一个自动 Effect 最多一条 Event；同板同一 to_state_version 最多一条 Event。

-- ⑦a 中途扫码的身份绑定审计（不可变；不改变 process_state / seal_state，不写物料 Event）
CREATE TABLE plate_identity_binding (
  id                bigserial PRIMARY KEY,
```

**效果状态机（六态，v3.2 补 `CANCELLED`）**：

| 状态 | 含义 | 后续 |
|---|---|---|
| `PENDING` | 等待处理 | 补偿任务 / 下次重试 |
| `APPLIED` | 效果已应用 | 终态 |
| `REJECTED` | **效果不符合规则**（目标板归属不符、声明自相矛盾） | 终态，**转人工**，不自动重试 |
| `NEEDS_RECONCILIATION` | **物理事实不明确**（设备超时但可能已动作 / 身份证据冲突） | 等对账，**不得直接认定动作没发生** |

| `CANCELLED` | run 终止/取消，效果不再应用 | 终态（`plate_material_effect_action` 记 CANCEL） |

### 11.2 异常场景（38 条 · 合并至现场子循环与中途扫码补充）

| # | 场景 | 必须保证的结果 |
|---|---|---|
| T01 | 设备执行成功，数据库写入失败 | T1 隔离 run 并转人工；不得静默显示成功或重放物理动作 |
| T02 | `none / legacy_unspecified / transition` 节点超时 | 都写 `execution_resolution_status=reconciliation_required`；有效果则 NEEDS_RECONCILIATION；禁止普通 resume/自动重试 |
| T03 | 同一设备命令回调重复两次 | 效果只应用一次，自动 Event 最多一条 |
| T04 | 同一节点循环执行三次 | 三次效果可按 loop/effect_index 追溯，互不吞并 |
| T05 | 同一逻辑执行重试三次 | attempt 不入幂等键，只产生一次物料效果 |
| T06 | Run 崩溃后恢复 | 已确认效果不重复；PENDING 按已解析 plate_id 重放；未知物理结果先对账 |
| T07 | 两个 Run 同时修改一块板 | Plate 行锁 + state_version CAS，不无声覆盖 |
| T08 | 两个物料同时占用一个位置 | 复用 PositionLock 阻断 |
| T09 | 目标位置已经占用 | 失败可见并转人工，不猜测 |
| T10 | 物料找不到或位置 UNKNOWN/LOST/IN_TRANSFER | 不用位置/占用猜身份；保留证据并 NEEDS_RECONCILIATION |
| T11 | 人工盘点与自动迁移同时发生 | 只能显式 rebase/cancel；声明 hash 或目标变化禁止 rebase |
| T12 | 声明与设备/位置证据指向不同板 | NEEDS_RECONCILIATION，不采信设备 ID、不写 Event；确定性声明错误才 REJECTED |
| T13 | 节点执行成功但效果处理失败 | 节点保持物理完成，相关后继不派发，无关分支继续 |
| T14 | 状态更新成功但 Event/action 写入失败 | 单事务回滚，不允许 APPLIED 无 Event 或状态变化无历史 |
| T15 | 跨租户物料、字典、Effect、Event、action 引用 | 复合约束与租户上下文必须拒绝 |
| T16 | FAILED / NEEDS_RECONCILIATION 恢复 | 权限、原因、证据和追加 action 完整 |
| T17 | 顺序执行与图执行 | 同一 NodeCompletionHandler 端口与实现，不重复注入 |
| T18 | 多步骤节点执行 | 保存 commandId/stepSeq 与目标解析证据，不遗漏中间事实 |
| T19 | 人工修正后收到旧回调 | 版本/CAS 与唯一键阻止覆盖人工状态 |
| T20 | Run 异常终止后位置仍被占用 | 可安全核对和释放，不由物料补偿擅自改位置 |
| T21 | 运行中修改节点声明 | 旧 run 只用启动快照；同键不同 payload 必须报错 |
| T22 | 字典停用后既有板仍引用 | 历史可显示；新声明预检 ERROR；在途效果转人工 |
| T23 | 同一 execution 多 effect 部分成功 | 各 effect 独立状态，不得整体 APPLIED；全部闭环才解除闸门 |
| T24 | 对账三种结论 | completed→PENDING→T2；not_completed→CANCELLED；still_unknown 保持；全部追加证据/action |
| T25 | 人工修正后旧回调晚到 | 幂等/版本检查忽略旧写入，人工 Event 与 version 不被覆盖 |
| T26 | 循环第 N 圈失败或预期 effect 缺失 | 按声明快照汇总 1..N 的 effect；缺失或任一非 APPLIED 都阻断 |
| T27 | 隔离/暂停 run 重启 | 保持隔离/暂停；执行、命令、Effect/Event 引用未闭环不得删节点重跑 |
| T28 | `none/legacy` 节点已有派发证据后崩溃 | 即使没有物料效果也禁止删除重建和普通 resume |
| T29 | 删除 Plate 投影后从事件重放 | 从已知基线按版本顺序重放，最终两个维度与版本完全一致；断档即停止 |
| T30 | 两个 Worker 同时扫描同一 PENDING | `FOR UPDATE SKIP LOCKED` 只一个应用；Effect/Event 唯一约束兜底 |
| T31 | Worker 可恢复错误连续失败 | 有界指数退避、次数与错误留痕；超限转 FAILED 人工，不无限循环 |
| T32 | 效果 REJECTED | 节点 `rejected`、闸门阻断、无自动重试、无 Event |
| T33 | 初始目标未知，授权补证 | 原证据不可改；completed 后回 PENDING 走 T2；补证接口本身不改板 |
| T34 | 明确改为未知 vs 维度未修改 | changed_fields 与完整 from/to 区分；from=to 的状态确认事件可存在且版本+1 |
| T35 | 多 attempt × 重复/乱序/晚到回调 | 命令层和效果层分别幂等；晚到旧回调不生成新效果、不覆盖新状态 |
| T36 | Run 收尾仍有未闭环效果或执行未知 | 禁止 completed；返回未闭环清单，不能靠 CANCELLED 假装全部成功 |
| T37 | 子过程循环 × 每轮不同源/目的位置 | 设备参数与物料目标使用同一轮绑定；各轮证据不被覆盖；同一子过程多处/多轮调用不撞效果键；缺参数在派发前阻断 |
| T38 | 开始无码，中途扫码后使用 `scanRef` | 扫码前引用阻断；命中既有板解析 plate.id；AUTO 受控绑定与审计原子提交；重复/冲突/无匹配均不猜板；补偿不重新扫码 |

⚠ 任何一条没有明确处理机制，都**不能**宣称物料状态管理具备生产可用性。
