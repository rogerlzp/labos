## 1. 问题：现场会问、但系统答不上来的问题

| 问题 | 今天的答案 |
|---|---|
| 这块板现在处于工艺的哪一步？ | ❌ 答不上来。`plate` 没有板级工艺阶段字段 |
| 谁生产了这块板？谁最后加工了它？ | ❌ 答不上来。`plate` 没有生产来源字段；`plate_state_audit` 这张表还不存在 |
| 这次执行声明了哪些物料结果？ | ❌ 答不上来 |
| 这批板里还有几块是空的？ | ⚠️ **一半能答**：`plate_well.status`（`empty/filled/consumed/invalid`）模型已在，只是库里没数据 ⇒ 口径要定（§4.2） |

**为什么重要**：流程与流程之间的输入往往就是上一流程的产物（同一块板换内容）。
系统说不出"这块板现在是什么"，就等于跨流程的物料交接没有语义。

## 2. 根因：缺的是「板级工艺阶段」，不是「孔级内容」

**修正 v1 的判断**（E5）：孔级样品模型**早就存在**：

```
sample            (barcode, sample_type, batch_id, volume, concentration, ...)
sample_aliquot    (parent_id, barcode, volume, ...)
plate_well        (plate_id, well_row, well_col, sample_id, aliquot_id, volume, status)
```

⇒ 真正缺的不是"每个孔装着什么"，而是**板级工艺阶段**与**加工归属**。

⇒ **v1 的"四个维度"框架要改**（见 §4.1）：不是给 `plate` 加几个字段，
而是建立一个 **Material 领域**，`plate` 只是它的一个子类。

## 4. 核心模型

### 4.1 Material 领域分层（新增：不封死在 `plate` 表）

```
Material（物料，抽象基类）
├── Container（容器：装东西的）
│   ├── PCR Plate
│   ├── Deep Well Plate
│   └── Assay Plate
├── Consumable（耗材：盖子、卡扣 —— 需独立身份或生命周期追溯的）
├── Sample（样品）
├── Reagent（试剂）
└── Waste（废弃物）
```

**本期只落地**：`Container` 这一支的板级工艺阶段 + 归属 + 审计。
其余分支**只是把命名空间留出来**，不建表。

⚠ **`plate` 不改名、不改表结构定位**。它是 `Container` 的一个实例化，
不是 Material 的全部 —— 这条边界写清楚，将来加样品/试剂/废弃物时才不用推翻第一期。

### 4.2 容器的四个维度 + 三条边界

| 维度 | 落点 | 本期 |
|---|---|---|
| **身份**（条码 / 板型规格） | `plate.barcode` / `plate_type` / `rows` / `cols` | 已有。**`plate_type` 不动**（它是规格，不是工艺角色） |
| **板级工艺阶段** | `plate.process_state` | **新增**（v1 叫 `content_state`，v2 改名） |
| **耗材状态** | `plate.seal_state`（膜） | **新增**（独立耗材实体推迟到 S5） |
| **归属** | `plate.current_run_id` / `origin_run_id` / `origin_node_key` | **新增**（三概念见 §4.5） |

**为什么改名 `content_state` → `process_state`**：
「内容」暗示它描述板里装的东西，而那正是 `plate_well` 的职责；
「工艺阶段」准确表达它描述的是**这块板在工艺流程中的位置**。

**三条边界（本期必须写死，否则会和 `plate_well` 打架）**：

| # | 边界 |
|---|---|
| ① | 本期描述的是**整块容器的工艺阶段**（一块板一个阶段，同质） |
| ② | **不代表孔级样品内容** —— 那是 `plate_well` 的真源；两者**不得互相矛盾** |
| ③ | **不代表体积 / 浓度等物理化学属性** —— 那是 `sample` 的真源 |

**「还剩几块空板」的口径**：按 `plate_well` 判定（未建 well 行，或全部 well 的 `status='empty'`）；
**不另立一个 `empty` 板级状态**（否则两个真源）。

### 4.3 板级工艺阶段字典：租户级 + 模板集

| 决策 | 取值 | 理由 |
|---|---|---|
| 字典归属 | **租户级**（带 `tenant_id`） | 阶段名是客户工艺的词汇，系统无权规定 |
| 是否内置 | **全局模板集**（`is_template=true`），新租户初始化时**复制成租户副本** | 从零建 18 个阶段体验极差；但模板只是"建议" |
| 唯一标识 | `code`（机器标识）+ `display_name`（客户看到的） | 改名不该改引用 |
| 删除 | **只停用（`enabled=false`），不物理删除** | 已被引用的阶段删了就断了历史显示 |
| 引用约束 | `plate.process_state` 与 `(tenant_id, code)` 的**复合外键**（或等效校验） | 不能出现"字典里没有的状态" |

⚠ **租户隔离现状**：`WorkflowWebService.TENANT = 1L` 是写死的 ⇒
**不能因为新表有 `tenant_id` 就认为租户隔离已成立**。新代码的字典与状态读写
必须走同一套租户上下文，且**这一条要作为已知问题单独记（§13）**。

### 4.4 耗材：判据扩大

| | 判据 | 结论 |
|---|---|---|
| v1 判据 | 是否需要**独立追踪位置** | 太窄 |
| **v2 判据** | 是否需要**独立身份或生命周期追溯**（位置、批次、库存、附着历史、可重复使用、质量追溯……） | 采纳评审意见 |

⇒ **膜**：撕下即弃、不单独追踪 ⇒ `plate.seal_state` 一个字段就够。
⇒ **盖子**：有独立条码/库存/附着历史 ⇒ 需要独立实体。
⇒ **本期不建 `consumable` 表**（v1 建了）—— 评审一致认为它需要自己的位置与附着历史模型，
**先冻结不完整结构是错的** ⇒ 整表推迟到 S5（§14）。

### 4.5 归属：三个概念，不能混

| 概念 | 落点 | 语义 | 会不会被覆盖 |
|---|---|---|---|
| **当前归属** | `plate.current_run_id` | 当前由谁管 | **会** |
| **生产来源** | `plate.origin_run_id` / `origin_node_key` | 最初由谁产生 | **不会** |
| **加工历史** | `plate_state_audit` | 每次改变一行 | 只追加 |

**为什么必须拆**：一块板被 A（扩增）、B（纯化）、C（检测）三个 Run 依次加工后，
必须同时能回答"谁生产的（A）"、"谁最后加工的（C）"、"现在归谁"。
用一组 `owner_*` ⇒ 每次迁移覆盖 ⇒ **生产关系永久丢失**。

⇒ **`/api/runs/{id}/materials` 按审计/效果记录的 `source_run_id` 查**，
**不按 `plate.current_run_id` 查**；
接口文案改为「**本 run 声明的物料结果 / 状态变更**」，不再称"新产出的板"。

## 5. 执行事实与物料效果（v1 重写）

### 5.1 为什么不能靠单事务

| 事实 | 后果 |
|---|---|
| 设备命令**先提交**（`insertRunCommand`），节点完成**后提交**（`updateNodeStateLive`） | 二者本来就不在一个事务里 |
| 设备动作**物理不可撤销** | 迁移失败若回滚节点完成 ⇒ 续跑时设备动作会**再做一次**（重复物理动作 = 事故） |
| `PositionLock` 的审计**刻意**在位置事务外独立写入、失败只打日志 | 照抄这条会得到设计想避免的缝 |

⇒ **「必须与节点完成同事务」这个要求在当前架构下做不到**，v1 把它当既有能力写是错的。
⇒ **目标改为**：**执行事实先形成可恢复的记录；物料状态迁移具备幂等、可重放、异常隔离**。
数据库内部能原子提交的记录尽量放同一事务。

### 5.2 三层分工（不新建执行引擎）

| 层 | 职责 | 本期改动 |
|---|---|---|
| `GraphRunner` | 流程图推进、循环、分支、暂停、恢复 | **不碰数据库**（保持现状） |
| `RunStateMachine` / `StepExecutor` | 执行节点、重试、设备命令 | 增加**不吞异常**的完成通知（§5.7） |
| `PositionLock` / `CommandLedger` | 板位锁、命令记录、物理执行追溯 | **不动**（位置 ≠ 内容） |
| **MaterialEffectService**（新增） | 物料输入输出、状态迁移、物料审计、幂等 | **新增领域服务**，消费执行事实 |

⚠ **明确禁止**：不要把物料状态更新塞进 `PositionLock` —— 位置管理和工艺内容管理会再次耦合。

### 5.3 T1：执行事实确认

设备命令结果 + 节点完成 + **待处理的物料效果记录**（`PENDING`）落库。

**效果记录必须保存**（不能只留一个 `applied` 标志在审计表上）：

| 字段 | 为什么必须 |
|---|---|
| 声明快照（`declaration` JSONB） | 运行期间改了声明，续跑/补偿要按**当时**的声明解释旧物理动作 |
| **实际解析出的 `plate_id`** | 补偿按它重放，**不重跑 `target.by=position`**（板可能已经搬走） |
| 幂等键 + `payload_hash` | 同键同负载可安全跳过；**同键不同负载必须报错** |
| `source_run_id` / `source_node_key` / `source_loop_index` | 归属与轮次 |

**运行版本快照**：`run` 启动时把**生效的声明与 workflow 版本**冻结下来，
续跑只读快照，**不读最新设计**（否则旧物理动作会被新声明解释）。

### 5.4 T2：物料状态投影

**在一个事务里**：`锁板 → 应用迁移 → 写审计 → 标记 APPLIED`。

| 失败情形 | 行为 |
|---|---|
| 迁移失败 | 效果记录保留 `FAILED` + 错误码，**告警 + 转人工**；**禁止静默吞掉** |
| 板找不到 / 归属不符 | **隔离并转人工，不猜测**（§6.3） |
| 人工盘点与自动迁移并发 | 必须有明确的冲突处理（§5.6），**禁止"最后写入者无声覆盖"** |

### 5.5 幂等键

```
幂等键 = tenant_id + source_run_id + source_node_key + source_loop_index + plate_id
```

| 设计点 | 理由 |
|---|---|
| **含 `source_loop_index`** | `run_node` 唯一键已含 `loop_index`（`20_kernel.sql:328`）⇒ 同一节点循环跑三次是**三次合法效果**，不能被幂等键吃掉 |
| **`attempt` 不入键** | 设备/节点**重试**是同一次逻辑执行的第 N 次尝试 ⇒ 不该产生新的物料迁移 |
| **与 `run_node` 唯一键对齐** | `(run_id, node_key, attempt, loop_index)` ⇒ 我们取它的 `(run_id, node_key, loop_index)` + `plate_id` |
| **同键同负载可跳过 / 同键不同负载必须报错** | 静默吞掉"设计变了"是最危险的失败模式 |

⚠ **v1 的 `(owner_run_id, owner_node_key, plate_id)` 会让循环第三圈撞唯一索引** —— 这是硬伤。

### 5.6 并发：板级串行化

唯一索引只防"同一幂等键重复"，**不防两个不同节点/人工同时改同一块板**。

⇒ T2 内对 `plate` 行 **`SELECT ... FOR UPDATE`**，或用 `state_version` 做 **CAS**。
⇒ 审计记录的 `from_*` 必须与本次实际更新一致（否则"两条审计都看似成功、后提交者覆盖先提交者"）。
⇒ 自动迁移与人工修改冲突时：**明确谁失败、怎么告警**。

⚠ 现有 `PositionLock` 解决的是**位置互斥**，**不等于**物料状态的并发更新已解决。

### 5.7 完成点：两条路径都要覆盖，且异常不吞

**这是 v1 写错、v2 纠正的关键点。**

| 候选 | 覆盖 | 问题 |
|---|---|---|
| `GraphRunner.java:650`（设备 TASK 完成） | 只覆盖**图执行** | 顺序执行路径（`sm.executeAll`）**不经过**它 |
| `GraphRunner.java:604`（内置节点完成） | 只覆盖**内置节点** | 设备任务不在这里（v1 的错误 E1） |
| `ExecutionListener` 的 `NODE_COMPLETED` 事件 | **两条路径都覆盖** ✓ | ⚠ `emit()` **捕获 `RuntimeException` 后忽略**（"监听器故障不得影响执行"）⇒ 不能承载"必须留下待补偿意图"的动作 |

⇒ **v2 的方案**：在 `RunStateMachine.executeNode` 成功返回前，
触发一个**专用的、异常不吞**的完成通知 `nodeEffectListener`；
`GraphRunner` 与 `WorkflowService` 两条路径都注入它。

| 决策点 | 说明 |
|---|---|
| 异常怎么处理 | **不吞**：上抛给调用方，由调用方决定"转人工"还是"记 PENDING 后继续"。⇒ **不能复用 `ExecutionListener`** |
| 顺序执行路径的轮次 | sequential 路径无循环 ⇒ `source_loop_index = 0` |
| `ExecutionListener` 怎么办 | **保留原样**（它是"副作用出口"语义，别改）⇒ 新增的是**另一个**回调 |

### 5.8 补偿与恢复

| 场景 | 行为 |
|---|---|
| T1 前崩溃 | 什么都没发生 ⇒ 设备动作也没发生 ⇒ 重跑即可 |
| T1 后 / T2 前崩溃 | 效果记录 `PENDING` ⇒ 补偿任务按**已解析的 `plate_id`** 重放 T2（不重跑设备动作、不重跑位置寻址） |
| T2 回滚 | 效果记录回 `PENDING` ⇒ 同上重放 |
| 重复补偿 | 幂等键挡住 ⇒ 同键同负载跳过 |
| 补偿时流程已续跑 | 效果记录与 run 解耦 ⇒ 补偿不依赖 run 还活着 |
| 数据库异常 | **不得无声继续** ⇒ 记错误码 + 转人工 |

## 6. 节点的物料效果契约

### 6.1 独立列，不塞进 `params`

**为什么不能放 `params`**：执行侧只读 `workflow_node.params->'method_params'`，
并用**扁平 JSON 解析器**解析后透传给驱动 ⇒ 嵌套结构放进去会被错误解析、
**甚至透传给设备**。而且 `produces` 是**中控自己的业务契约**，不是设备执行参数。

⇒ **独立列** `workflow_node.material_effect jsonb`：

```
workflow_node
├── params → method_params   ← 发给设备的参数（不动）
└── material_effect          ← 中控的物料契约（新增）
    ├── inputs
    ├── outputs
    └── operations
```

**好处**：不混进设备参数；设计器可独立编辑；可独立做 JSON Schema 校验；
可查"哪些节点声明了物料效果"；将来升级契约不影响设备驱动。

### 6.2 契约形态

```json
{
  "materialEffect": {
    "inputs":  [ { "by": "plateId", "plateId": 1001 } ],
    "outputs": [ { "by": "plateId", "plateId": 1001,
                   "processState": "amplified_product",
                   "sealState": "sealed" } ],
    "operations": []
  }
}
```

| 字段 | 含义 |
|---|---|
| `inputs` / `outputs` | 物料身份 + 结果。**本期只支持一对一状态变化** |
| `operations` | 预留：分装（1→N）、混合（N→1）、转板（1→1 新板）、取样检测（1→1 + 数据） |

⚠ **本期不实现分装/合并**，但**结构不封死**扩展空间（评审 O-3 的要求）。

### 6.3 目标解析：物料身份优先，位置只是辅助

| 规则 | 说明 |
|---|---|
| **物料身份优先** | `plateId` / `barcode` 是身份；**位置是空间属性，不是身份** |
| 位置寻址必须校验归属 | 事务内校验 `tenant_id + resource_id + occupied_by_run`（**fail-closed**，与现有取板路径同口径） |
| 条码寻址也要校验 | 校验预期位置 / 归属，除非将来有显式的跨 run 移交操作 |
| `AUTO-*` 占位身份 | 位置登记缺条码时生成 ⇒ **不得当成已核实条码** |
| 设备重分配 | 设计时写死的 `resourceId` 不一定是实际目标 ⇒ **命令参数、设备回包、最终位置才是运行时证据** |
| 解析失败 | **隔离并转人工，不猜测** |
| 多步节点 | 必须定义 target 指**哪一步结束时的位置**；不能用节点结束时另一个位置反推整节点的作用对象 |

⇒ **T1 必须把解析出的 `plate_id` 落进效果记录**，后续一切以它为准。

### 6.4 显式声明 vs 未声明

| 情况 | 行为 |
|---|---|
| 明确无物料副作用 | 节点声明 `materialEffect: "none"`（或等价字段）⇒ **不报警** |
| 老流程未声明 | **WARN**（不改行为）；新版本里按 WARN 处理 |
| 已知会改内容/膜的节点缺声明 | **ERROR**（发布/启动时拦截） |
| 无法分类的节点 | 要求人工确认 `none` 或补声明 |
| 声明的状态不在字典里 | **ERROR**（发布/启动时拦截）；**运行期若被删 ⇒ 迁移失败转人工，不写"未知状态"冒充成功** |

⚠ **为什么不能一律 WARN**：v1 说"系统分不清搬运和忘了声明" —— 这不准确。
**能力/方法元数据可以在设计期标出**「位置-only / 可改变内容或膜 / 未知」，
只用于校验，不用于运行期猜状态 ⇒ 有了分类，就不必对所有节点一刀切。

## 7. 数据模型汇总

```sql
-- ① 板级工艺阶段字典（租户级；模板集与租户副本分开）
CREATE TABLE plate_process_state (
  id           bigserial PRIMARY KEY,
  tenant_id    bigint      NOT NULL,
  code         varchar(32) NOT NULL,
  display_name varchar(64) NOT NULL,
  sort_order   int         NOT NULL DEFAULT 0,
  is_template  boolean     NOT NULL DEFAULT false,  -- 全局模板（不属任何租户的数据）
  enabled      boolean     NOT NULL DEFAULT true,   -- 停用而非删除
  UNIQUE (tenant_id, code)
);
-- 注：模板集用 tenant_id = 0 存；新租户初始化时复制成租户副本。

-- ② plate 加列（★ 不动 plate_type —— 它是板型规格 96/384/24/tube_rack）
ALTER TABLE plate
  ADD COLUMN process_state   varchar(32),            -- → plate_process_state.code
  ADD COLUMN seal_state      varchar(16) NOT NULL DEFAULT 'none',  -- none / sealed
  ADD COLUMN current_run_id  bigint,                 -- 当前归属（可覆盖）
  ADD COLUMN origin_run_id   bigint,                 -- 生产来源（不覆盖）
  ADD COLUMN origin_node_key varchar(64),
  ADD COLUMN state_version   bigint NOT NULL DEFAULT 0;  -- CAS 用
-- 引用约束：process_state 必须存在于同租户的 plate_process_state（复合外键或等效校验）
-- CHECK (seal_state IN ('none','sealed'))

-- ③ 物料效果（T1 写 PENDING → T2 应用）
CREATE TABLE plate_material_effect (
  id                bigserial PRIMARY KEY,
  tenant_id         bigint      NOT NULL,
  effect_key        varchar(128) NOT NULL,   -- 幂等键（应用侧哈希）
  source_run_id     bigint      NOT NULL,
  source_node_key   varchar(64) NOT NULL,
  source_loop_index int         NOT NULL DEFAULT 0,
  source_attempt    int         NOT NULL DEFAULT 0,   -- 留痕，不入幂等键
  plate_id          bigint,                    -- T1 解析出的实际板（补偿按它重放）
  declaration       jsonb      NOT NULL,      -- 声明快照（运行版本冻结）
  payload_hash      varchar(64) NOT NULL,      -- 同键不同负载 → 报错
  status            varchar(16) NOT NULL,      -- PENDING / APPLIED / FAILED
  applied_at        timestamptz,
  error_code        varchar(64),
  error_message     varchar(255),
  created_at        timestamptz NOT NULL DEFAULT now(),
  updated_at        timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ux_plate_material_effect_key
  ON plate_material_effect (tenant_id, effect_key);
CREATE INDEX ix_plate_material_effect_pending
  ON plate_material_effect (tenant_id, status, created_at) WHERE status <> 'APPLIED';

-- ④ 状态迁移审计（T2 写）
CREATE TABLE plate_state_audit (
  id                 bigserial PRIMARY KEY,
  tenant_id          bigint      NOT NULL,
  plate_id           bigint      NOT NULL,
  from_process_state varchar(32),
  to_process_state   varchar(32),
  from_seal_state    varchar(16),
  to_seal_state      varchar(16),
  from_owner_run_id  bigint,
  to_owner_run_id    bigint,
  source_run_id      bigint,
  source_node_key    varchar(64),
  source_loop_index  int         NOT NULL DEFAULT 0,
  command_id         varchar(64),        -- 物理命令 ID
  effect_id          bigint,             -- 对应 plate_material_effect
  evidence           varchar(24) NOT NULL,  -- 证据来源（见下）
  operator           varchar(16) NOT NULL,  -- AUTO / MANUAL
  note               varchar(255),
  created_at         timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ix_plate_state_audit_plate  ON plate_state_audit (tenant_id, plate_id, created_at DESC);
CREATE INDEX ix_plate_state_audit_source ON plate_state_audit (tenant_id, source_run_id);
```

**证据来源枚举**（`evidence`）：

| 值 | 含义 |
|---|---|
| `DEVICE_CONFIRMED` | 设备结果确认（读到了实际状态） |
| `EXECUTION_DECLARED` | 节点完成后按声明迁移（**系统说的，不是设备说的**） |
| `MANUAL_INVENTORY` | 人工现场盘点 |
| `MANUAL_CORRECTION` | 人工纠正系统记录 |
| `RECONCILIATION` | 对账 / 恢复程序修复 |

⚠ **原则**：系统按节点声明写入状态，**不等于**设备真正检测到了物料状态。
**这两种证据不能都显示成"设备已确认"。**

⚠ **`consumable` 表本期不建**（§4.4）⇒ 独立耗材整体推迟到 S5。

## 11. 验收标准

### 11.1 功能

| 问题 | 怎么验 | 层级 |
|---|---|---|
| 节点产出后板阶段变了 | 跑带 `materialEffect` 的流程 ⇒ `plate.process_state` = 声明值 | 真环境 |
| 迁移有留痕且能看出证据来源 | `plate_state_audit` 一行，`evidence` 正确 | 真环境 |
| 能回答"谁生产的 / 谁最后加工的 / 现在归谁" | 三个字段 + 审计历史分别可查 | 真环境 |
| 能回答"本 run 声明了哪些物料结果" | `GET /api/runs/{id}/material-effects` | 真环境 |
| 字典改名不影响引用 | 改 `display_name` ⇒ 显示跟着变，`code` 不变 | 纯逻辑 |
| 老流程零行为变化 | 库里原有流程跑一遍，结果与改动前一致 | 真环境 |

### 11.2 异常场景（三份评审共同要求）

| 场景 | 必须保证的结果 |
|---|---|
| 设备执行成功，数据库写入失败 | **不允许静默显示物料状态正确** ⇒ 效果记录 `FAILED` + 转人工 |
| 设备超时，但实际动作可能已发生 | **不允许直接认定动作未发生** |
| 同一节点重试 | **不重复应用**同一次物料效果（`attempt` 不入幂等键） |
| 同一节点循环执行三次 | **三次真实效果均可追溯**（幂等键含 `loop_index`） |
| Run 崩溃后恢复 | 已确认的效果不重复；未确认的效果**可恢复**（按已解析的 `plate_id` 重放） |
| 两个 Run 同时修改一块板 | **不发生状态覆盖**（`FOR UPDATE` / CAS） |
| 人工盘点与自动迁移同时发生 | 有明确的并发冲突处理，**不无声覆盖** |
| 物料找不到 | **隔离并转人工，不能猜测** |
