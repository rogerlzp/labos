### 0.1 本稿怎么来的：三份独立设计的收敛

同一件事收到了**三份互相独立的设计**（不是一份设计的三次评审）：

| # | 来源 | 文件 | 形态 |
|---|---|---|---|
| A | 本会话 v2（合并 Grok / Kimi / OpenAI 三份**评审**意见） | `docs/物料身份与状态-设计.md`（本文件的上一版） | 最小落地：`plate` 加列 + 效果表 + 审计表 |
| B | 并发会话的**独立 v2** | `docs/物料身份与状态-设计-v2.md`（保留作对照） | 四类事实分开 + 8 条不变量 + `run_node` 加两列 |
| C | 第三份独立设计草稿（外部评审方给出） | 未入库（本稿已吸收其结论） | 完整 Material / Location / Content / Event / Effect 五对象模型 |

**三方共识（12 条，本稿全部采纳）**：

| # | 共识 |
|---|---|
| C1 | **身份 ≠ 位置**：位置是物料的属性/关联，不是身份 |
| C2 | **执行声明 ≠ 物理事实**：流程声明 / 设备回报 / 系统确认，三者不能等同 |
| C3 | **当前状态与历史事件分离**：当前值可投影，历史不可覆盖 |
| C4 | **来源 / 当前归属 / 加工历史**是三件事，不能共用一个 `owner_*` |
| C5 | **循环轮次 / 重试次数 / 执行实例必须分开建模**（`loop_round` / `attempt` / `execution_id`） |
| C6 | **设备执行与数据库事务不混为一谈**：物理动作回滚不了 |
| C7 | **一对多结构必须预留**，第一期用校验规则限制，而不是把表设计成永远一对一 |
| C8 | **未声明 ≠ 无影响**：要显式分类（NONE / DECLARED / UNKNOWN） |
| C9 | **位置锁复用现有 `PositionLock`**，不另建一套占用系统 |
| C10 | **租户隔离尚未真正实现**（`TENANT = 1L` 写死），新表有 `tenant_id` 不等于隔离成立 |
| C11 | **先 S0 定模型、后 S1 建表**；不要先冻结 DDL 再补模型 |
| C12 | **耗材独立后续阶段**：第一期不建半成品库存/消耗功能 |

**分歧与裁决（7 条，本稿的取舍）**：

| # | 分歧 | A（本稿 v2） | B（独立 v2） | C（第三份） | **裁决** | 理由 |
|---|---|---|---|---|---|---|
| D1 | 幂等键锚点 | `run+node+loop+plate` | effect_key | 逻辑执行实例 + effect_index | **结构化唯一键 `(tenant, run, node, loop, effect_index)`**（v3.2 修正：不落字符串 `execution_id`，见 §5.5） | C 的锚点最稳；且它天然解决「一个节点产生多个效果」 |
| D2 | 执行事实载体 | 效果表兼作 T1 | `run_node` 加两列 | 独立 Execution Fact 对象 | **三处分工（v3.2 修正）**：**设备命令事实 = `command_ledger`（派发前落账/幂等键/UNKNOWN）+ `run_command`（回包后的结果台账）**；节点级同步状态进 `run_node`；物料效果独立表 | 不新建第二套命令台账，也不让效果表兼任执行事实；原稿「复用 `run_command`」写错了（它没有 `command_id` 列） |
| D3 | 效果状态机 | 3 态 | 3 态 | **5 态** | **6 态（v3.2 补 `CANCELLED`）** | "效果不符合规则"与"物理事实待核对"是两种完全不同的处置；run 终止后未应用的效果必须有终态（CANCELLED），否则补偿会重放失效意图 |
| D4 | 节点与效果的状态关系 | 解耦（未细化） | 解耦（未细化） | 明确"节点要等效果达确认等级才算完整完成" | **采纳 C，并给出落地** | 不改 `node_status` 枚举；由**派发闸门**（§5.2b，注入 GraphRunner/executeAll 的 predicate，读 `run_node.material_sync_status`）决定下游派不派；⚠ 不用 `runtime_hold` 扣节点：其 scope 实际是 `site\|island\|experiment`（无 run/node 粒度） |
| D5 | 事件表命名与字段 | `plate_state_audit` | `plate_material_event` | `Material Event`（含 `occurred_at`/`recorded_at`） | **`plate_material_event` + 双时间戳** | "event" 比 "audit" 更能表达不可变事件流；物理发生时间 ≠ 系统记录时间必须分开 |
| D6 | 领域模型落地范围 | 最轻（`plate` 加列） | 中 | 最重（Material/Location/Content 三关系表） | **折中**：Material=现有 `plate` 加列；Location=**复用** `position_state`；Content=**复用** `plate_well`/`sample`/`sample_aliquot` | 三份的"未来模型"一致，差别只在第一期建多少表；复用既有的能少两套真源 |
| D7 | 耗材判据 | 独立身份/生命周期追溯 | 独立实体 + 位置 + 附着历史 | 独立身份/生命周期/库存/批次/有效期/复用/追溯 | **取并集** | 三方措辞不同，实质一致 |

### 0.3 第 5 轮独立复审（20261112-05 / 06）后的关键裁决（v3.2）

> 依据：`docs/评审记录/20261112-05-mavis.md`（并行会话）与 `20261112-06-mavis.md`（本会话 3 个独立子代理复核 + 汇总）及三份 findings。
> 完整处置表见 §18.1。

| # | 裁决 | 为什么（详见） |
|---|---|---|
| R1 | **执行事实载体 = `command_ledger` + `run_command` 两表分工**；`run_command` **没有** `command_id` 列（原稿写错），`command_id` 在 `command_ledger` | 命令账本在**派发前**落账，才能表达「已下发、未回包」窗口；`run_command` 是**回包后**才写的结果台账（§5.3/§7） |
| R2 | **T1 失败 = run 级隔离（quarantined + experiment 级 runtime_hold），不是「run failed」**；隔离/人工确认前**禁止 resume 重派设备命令** | 现有 `markRunFailed` 无转人工通道，重启后人工续跑会把已完成物理动作再执行一次（§5.2b/§5.8） |
| R3 | **下游「不派发」= 派发闸门 predicate**（GraphRunner / executeAll 派发前查前置节点 `material_sync_status`），**不是**「调度器依赖检查」 | 现有节点派发在 GraphRunner 内存队列里，`ExperimentScheduler` 只到 workflow-step 粒度，不存在节点级依赖检查（§5.2b/§5.7） |
| R4 | **物理执行通路清单要写全**：2 条生产通路已进统一完成点；`/api/experiments/flow-run` 与 ShadowRunner/单命令探针是**已知缺口**，S0 内必须先处置 | 前者绕过 `RunStateMachine` 直接驱动设备，后者真实动作但不落执行事实（§16.1） |
| R5 | **效果状态机 6 态**（补 `CANCELLED`）；`NEEDS_RECONCILIATION` / `REJECTED` / `FAILED` 都要有人工闭环（权限 + 原因 + 事件 + API） | 只有「FAILED→PENDING」不够；run 终止后未应用的效果会永远悬空（§5.8/§8） |
| R6 | **O-2 的跨租户约束补齐到 6 类 / 8 条**（`run_node↔run`、effect→run、event→run、effect→plate、event→plate、event→同租户同 Run 的三列 FK + 空值 CHECK） | 原稿只给 3 组，O-2 未闭合；实测补 `uq_run_tenant_id` 后全部可建（§7⑧） |

## 1. 问题：现场会问、但系统答不上来的问题

| 问题 | 今天的答案 |
|---|---|
| 这块板现在处于工艺的哪一步？ | ❌ 答不上来。`plate` 没有板级工艺阶段字段 |
| 谁生产了这块板？谁最后加工了它？ | ❌ 答不上来。`plate` 没有生产来源字段；`plate_material_event` 这张表还不存在 |
| 这次执行声明了哪些物料结果？ | ❌ 答不上来 |
| 这批板里还有几块是空的？ | ⚠️ **一半能答**：`plate_well.status`（`empty/filled/consumed/invalid`）模型已在，只是库里没数据 ⇒ 口径要定（§4.2） |

**为什么重要**：流程与流程之间的输入往往就是上一流程的产物（同一块板换内容）。
系统说不出"这块板现在是什么"，就等于跨流程的物料交接没有语义。

## 2. 根因：缺的是「板级工艺阶段」，不是「孔级内容」

**修正 v1 的判断**（E5）：孔级样品模型**早就存在**：

```
sample            (barcode, sample_type, batch_id, volume, concentration, ...)
sample_aliquot    (parent_id, barcode, volume, ...)
plate_well        (plate_id, well_row, well_col, sample_id, aliquot_id, volume, status)
```

⇒ 真正缺的不是"每个孔装着什么"，而是**板级工艺阶段**与**加工归属**。

⇒ **v1 的"四个维度"框架要改**（见 §4.1）：不是给 `plate` 加几个字段，
而是建立一个 **Material 领域**，`plate` 只是它的一个子类。

## 4. 核心模型

### 4.1 Material 领域分层（新增：不封死在 `plate` 表）

```
Material（物料，抽象基类）
├── Container（容器：装东西的）
│   ├── PCR Plate
│   ├── Deep Well Plate
│   └── Assay Plate
├── Consumable（耗材：盖子、卡扣 —— 需独立身份或生命周期追溯的）
├── Sample（样品）
├── Reagent（试剂）
└── Waste（废弃物）
```

**本期只落地**：`Container` 这一支的板级工艺阶段 + 归属 + 审计。
其余分支**只是把命名空间留出来**，不建表。

⚠ **`plate` 不改名、不改表结构定位**。它是 `Container` 的一个实例化，
不是 Material 的全部 —— 这条边界写清楚，将来加样品/试剂/废弃物时才不用推翻第一期。

### 4.2 容器的四个维度 + 三条边界

| 维度 | 落点（v3.2 定稿） | 本期 |
|---|---|---|
| **身份**（条码 / 板型规格） | `plate.barcode` / `plate_type` / `rows` / `cols` | 已有。**`plate_type` 不动**（它是规格，不是工艺角色） |
| **板级工艺阶段** | `plate.process_state` | **新增**（v1 叫 `content_state`，v2 改名） |
| **耗材状态** | `plate.seal_state`（膜；**NULL = 未知**，`none` / `sealed`） | **新增**（独立耗材实体推迟到 S5） |
| **位置**（既有，不改） | `position_state`（唯一真源）+ `plate.location_id`（冗余投影）/ `plate.position_status`（位置可信度） | **不改**；新稿只读不双写（§17 Q2） |
| **归属**（三概念） | 当前归属 = `position_state.occupied_by_run`；生产来源/加工历史 = `plate_material_event`（§4.5） | **不加 `plate.current_run_id` / `origin_*`**（v3.2 采纳 v2.2 异议：没有 CREATE 与 handoff 闭环时这些列只会制造第二个归属真源） |

**为什么改名 `content_state` → `process_state`**：
「内容」暗示它描述板里装的东西，而那正是 `plate_well` 的职责；
「工艺阶段」准确表达它描述的是**这块板在工艺流程中的位置**。

**三条边界（本期必须写死，否则会和 `plate_well` 打架）**：

| # | 边界 |
|---|---|
| ① | 本期描述的是**整块容器的工艺阶段**（一块板一个阶段，同质） |
| ② | **不代表孔级样品内容** —— 那是 `plate_well` 的真源；两者**不得互相矛盾** |
| ③ | **不代表体积 / 浓度等物理化学属性** —— 那是 `sample` 的真源 |

**「还剩几块空板」的口径**：按 `plate_well` 判定（未建 well 行，或全部 well 的 `status='empty'`）；
**不另立一个 `empty` 板级状态**（否则两个真源）。

### 4.3 板级工艺阶段字典：租户级 + 模板集

| 决策 | 取值 | 理由 |
|---|---|---|
| 字典归属 | **租户级**（带 `tenant_id`） | 阶段名是客户工艺的词汇，系统无权规定 |
| 是否内置 | **全局模板集**（`is_template=true`），新租户初始化时**复制成租户副本** | 从零建 18 个阶段体验极差；但模板只是"建议" |
| 唯一标识 | `code`（机器标识）+ `display_name`（客户看到的） | 改名不该改引用 |
| 删除 | **只停用（`enabled=false`），不物理删除** | 已被引用的阶段删了就断了历史显示 |
| 引用约束 | `plate.process_state` 与 `(tenant_id, code)` 的**复合外键**（或等效校验） | 不能出现"字典里没有的状态" |

⚠ **租户隔离现状**：`WorkflowWebService.TENANT = 1L` 是写死的 ⇒
**不能因为新表有 `tenant_id` 就认为租户隔离已成立**。新代码的字典与状态读写
必须走同一套租户上下文，且**这一条要作为已知问题单独记（§13）**。

### 4.4 耗材：判据扩大

| | 判据 | 结论 |
|---|---|---|
| v1 判据 | 是否需要**独立追踪位置** | 太窄 |
| **v2 判据** | 是否需要**独立身份或生命周期追溯**（位置、批次、库存、附着历史、可重复使用、质量追溯……） | 采纳评审意见 |

⇒ **膜**：撕下即弃、不单独追踪 ⇒ `plate.seal_state` 一个字段就够。
⇒ **盖子**：有独立条码/库存/附着历史 ⇒ 需要独立实体。
⇒ **本期不建 `consumable` 表**（v1 建了）—— 评审一致认为它需要自己的位置与附着历史模型，
**先冻结不完整结构是错的** ⇒ 整表推迟到 S5（§14）。

### 4.5 归属：三个概念，不能混

| 概念 | 落点 | 语义 | 会不会被覆盖 |
|---|---|---|---|
| **当前归属** | `position_state.occupied_by_run` | 当前由谁管 | **会** |
| **生产来源** | `plate.origin_run_id` / `origin_node_key` | 最初由谁产生 | **不会** |
| **加工历史** | `plate_material_event` | 每次改变一行 | 只追加 |

**为什么必须拆**：一块板被 A（扩增）、B（纯化）、C（检测）三个 Run 依次加工后，
必须同时能回答"谁生产的（A）"、"谁最后加工的（C）"、"现在归谁"。
用一组 `owner_*` ⇒ 每次迁移覆盖 ⇒ **生产关系永久丢失**。

⇒ **`/api/runs/{id}/materials` 按审计/效果记录的 `source_run_id` 查**，
**不按任何「当前归属」字段查**（归属已有 `position_state` 唯一真源，§4.5）；
接口文案改为「**本 run 声明的物料结果 / 状态变更**」，不再称"新产出的板"。

## 5. 执行事实与物料效果（v1 重写）

### 5.1 为什么不能靠单事务

| 事实 | 后果 |
|---|---|
| 设备命令**先提交**（`insertRunCommand`），节点完成**后提交**（`updateNodeStateLive`） | 二者本来就不在一个事务里 |
| 设备动作**物理不可撤销** | 迁移失败若回滚节点完成 ⇒ 续跑时设备动作会**再做一次**（重复物理动作 = 事故） |
| `PositionLock` 的审计**刻意**在位置事务外独立写入、失败只打日志 | 照抄这条会得到设计想避免的缝 |

⇒ **「必须与节点完成同事务」这个要求在当前架构下做不到**，v1 把它当既有能力写是错的。
⇒ **目标改为**：**执行事实先形成可恢复的记录；物料状态迁移具备幂等、可重放、异常隔离**。
数据库内部能原子提交的记录尽量放同一事务。

### 5.2 三层分工（不新建执行引擎）

| 层 | 职责 | 本期改动 |
|---|---|---|
| `GraphRunner` | 流程图推进、循环、分支、暂停、恢复 | **不碰数据库**（保持现状） |
| `RunStateMachine` / `StepExecutor` | 执行节点、重试、设备命令 | 增加**不吞异常**的完成通知（§5.7） |
| `PositionLock` / `CommandLedger` | 板位锁、命令记录、物理执行追溯 | **不动**（位置 ≠ 内容） |
| **MaterialEffectService**（新增） | 物料输入输出、状态迁移、物料审计、幂等 | **新增领域服务**，消费执行事实 |

⚠ **明确禁止**：不要把物料状态更新塞进 `PositionLock` —— 位置管理和工艺内容管理会再次耦合。

### 5.2b 两级失败语义（v3.2 重写 · 把「阻断」落成现有机制）

**T1 与 T2 的失败后果完全不同**；v3.2 按第 5 轮复审的源码证据重写了定义与落地通道：

| 阶段 | 失败意味着 | 后果（v3.2 修正） | 落地通道（现有机制/先例） |
|---|---|---|---|
| **T1**（物料效果意图没落成 `PENDING`） | 设备的**命令事实**通常已在 `command_ledger` / `run_command`（§5.3）；缺的是**物料账本与补偿依据**。只有数据库整体不可用的极端情形，物理动作才真的「无记录」 | **隔离 run（quarantined）+ 抬 experiment 级 `runtime_hold`**，等人工对账；**不是「run failed」**；**隔离期间禁止 resume 重派设备命令** | 复用 `StartupRecovery.quarantineUncertainRuns` 的既有先例（`StartupRecovery.java:130-166`，人工确认放行 `:171+`） |
| **T2**（应用状态投影） | 物理动作已发生且已留痕，只是**投影**没跟上 | **节点仍算完成**（设备确实做完了），但**物料标为待核对**，**依赖它的下游不派发** | `run_node.material_sync_status` + **派发闸门**（见下）；效果状态 `NEEDS_RECONCILIATION` |

**为什么「只落 run=failed」不够（第 5 轮源码结论）**：`markRunFailed` 不写 `pause_kind` / `recoverable`
⇒ `resume` 被拒绝、没有转人工窗口；而数据库整体不可用时 `markFailed` 也写不进去，
重启后 `StartupRecovery` 把 run 收成 `failed + recoverable`，人工 CONTINUE 走 `resumeAsync`
**删掉未完成节点重跑** ⇒ 把已经做完的物理动作**再做一次**。
⇒ T1 失败必须是**隔离**；恢复入口必须先按 `command_ledger` / `run_command` 对账（§5.3/§5.8）。

**下游「不派发」的机制（v3.2 修正：不是「调度器依赖检查」）**：
1. 节点级事实记在 `run_node.material_sync_status`（`not_required / pending / applied / failed / needs_reconciliation / cancelled`）；
2. **派发闸门 = 注入 `GraphRunner` / `RunStateMachine.executeAll` 的 predicate**：节点被激活、准备执行前，
   检查它**全部直接前置节点**的 `material_sync_status` —— 只有 `not_required` / `applied` 放行，
   `pending` / `failed` / `needs_reconciliation` / `cancelled` 一律阻断；**无依赖关系的分支照常继续**；
   循环节点必须汇总本节点各圈次（`loop_index=1..N`）的实际状态，任一圈未闭环即阻断（§5.5）；
   ⚠ **v3.2 补 · 本会话核出**：循环各圈的物料状态**目前没有载体** —— 圈次行是节点执行**之后**才写
   （`GraphRunner.java:657`，T1 时点还不存在），且 `insertNodeRound`（`RunMapper.xml:584-595`）**不写**
   `material_sync_status` ⇒ 新列走默认 `not_required` ⇒ 闸门会把「某圈待对账」误判成 `not_required` **放行**。
   ⇒ **S0 冻结前必须先裁决载体**，见 §13.2-13；
3. 闸门命中 ⇒ 该节点**不启动**，run 落 `paused` + `pause_kind=material_sync`（**新增枚举值**，见 §12），
   并记一条 experiment 级 `runtime_hold` 告警；**对账完成/人工确认后走 `POST /api/runs/{id}/resume`（continue）唤醒** ——
   复用现有续跑入口，不另造唤醒机制；
4. **为什么不放在 `ExperimentScheduler`**：它只到 workflow-step 粒度（`ExperimentExecutor.expand`），
   管不到 workflow_node；现有节点派发在 `GraphRunner` 内存 ready 队列里；
5. `GraphRunner` 仍然**不直接访问数据库**：闸门 predicate 由 boot 层的 `MaterialEffectService` 注入
   （与现有 `withPauseChecker` 同一种模式）。

⇒ **不新增 `node_status` 枚举值**：「设备做完了但物料没同步」由 `material_sync_status` 表达，
「后继节点不许跑」由派发闸门表达，两件事分开。
⇒ 现场看到的是「设备做完了，但这一批物料还没对账，后面的活没派下去」，**而不是**一个假的设备失败。

### 5.3 T1：执行事实确认（v3.2 重写：命令事实 = `command_ledger` + `run_command`）

**先说清「执行事实」到底落在哪（第 5 轮 P0 修正）**：

| 事实 | 载体 | 时机 | 说明 |
|---|---|---|---|
| 命令**已派发、结果未知** | **`command_ledger`** | 派发**前** | `command_id varchar(160)`、`idempotency_key`、`state`（`DISPATCH_STARTED / ACKED / FAILED / UNKNOWN`）、`resolved_at/by`；已有 `CommandLedger` Java 实现 |
| 命令**回包结果** | **`run_command`** | 回包**后** | `device_raw_response` / `status` / `attempt` / `sent_at` / `finished_at`；**没有 `command_id` 列**（原稿写错）；`ack_at` 有列无写入者 |
| 节点物理完成 | 新增 `run_node.physical_completed_at` | 节点完成时 | 只表示物理动作已完成 |
| 物料效果意图 | 新增 `plate_material_effect`（`PENDING`） | 回包后、节点标 completed 前 | T1 的「物料账本」部分；每次动作追加 `plate_material_effect_action` |

⇒ **T1 = 物料效果意图落库**（不是从零创建执行事实）：命令事实通常已在命令账本里；
T1 失败时**隔离 run**（§5.2b），恢复时**先对账**：`ACKED` ⇒ 物理已发生 ⇒ 允许按声明快照重建效果；
`UNKNOWN / DISPATCH_STARTED` ⇒ 人工核对；**禁止直接重跑设备动作**。

**声明快照（v3.2 给出载体，不用新表）**：
- **run 启动时把每个节点的 `materialEffect` 快照写进 `run_node.input.material_effect_snapshot`**
  （含 `mode / target / set / acceptedEvidenceLevels` 与哈希），并**真正写入 `run.workflow_ver`**（现有列从未写过）；
- 效果记录再存一份 `declaration` 快照；续跑/补偿**只读快照**，不读最新设计（否则旧物理动作会被新声明解释）；
- 本期只保证**物料声明快照**，不声称顺便解决整个 BPMN 图的版本化（v2.2 口径）。

**证据等级（v3.2 补 · 吸收 v2.2 §2.6）**：§6.1 的契约里用了 `acceptedEvidenceLevels`，
但此前**只出现过字段名、没有定义等级语义** ⇒ 此处补齐，四个等级：

| 等级 | 含义 | 边界 |
|---|---|---|
| `device_ack` | 设备或驱动报告成功 | 只证明执行链拿到成功回包，**不冒充独立物理确认** |
| `physical_confirmed` | 设备最终状态查询、传感器或其他可信物理反馈确认 | 真机证据 |
| `manual_confirmed` | 授权人员现场核实 | **必须**记录操作者、时间、原因 |
| `legacy` | 仅用于老数据 `status=completed` 的兼容 | **不代表新证据能力** |

- 普通方法默认接受 `device_ack`；高风险方法可在元数据里只接受 `physical_confirmed` / `manual_confirmed`；
  **证据策略随声明一起快照**（同上一段）。
- **声明快照回答「打算做什么」，不属于物理证据** —— 不得把快照当确认。
- UI、事件与验收报告必须保留**实际等级**，不得统一写成「物理已核实」，也不得把人工确认当成设备自动确认。

**效果记录必须保存**（不能只留一个 `applied` 标志在审计表上）：

| 字段 | 为什么必须 |
|---|---|
| 声明快照（`declaration` JSONB） | 运行期间改了声明，续跑/补偿要按**当时**的声明解释旧物理动作 |
| **实际解析出的 `plate_id`** | 补偿按它重放，**不重跑 `target.by=position`**（板可能已经搬走） |
| 幂等键 + `payload_hash` | 同键同负载可安全跳过；**同键不同负载必须报错** |
| `source_run_id` / `source_node_key` / `source_loop_index` / `source_attempt` / `effect_index` | 归属与轮次；`attempt` 只留痕、不进幂等键 |
| **每次动作追加 `plate_material_effect_action`** | 声明/应用/对账/重试/取消都要有不可变审计（v2.2 §4.6，v3.2 采纳） |

### 5.4 T2：物料状态投影

**在一个事务里**：`锁板 → 校验期望版本 → 应用迁移 → 写审计事件 → 追加 effect action → 标记 APPLIED`。

| 失败情形 | 行为 |
|---|---|
| 迁移失败（业务规则不符） | 效果记录 `REJECTED` + 错误码，**告警 + 转人工**；**禁止静默吞掉**、不自动重试 |
| 板找不到 / 归属不符 / 身份证据冲突 | **隔离并转人工，不猜测**（§6.3）⇒ `NEEDS_RECONCILIATION` |
| 数据库/并发失败 | 效果记录 `FAILED` + 错误码，**可受控重试**（§5.8） |
| 人工盘点与自动迁移并发 | 按 §5.6 仲裁，**禁止最后写入者无声覆盖** |
| run 已终止 / 取消 | 未应用效果置 `CANCELLED`（追加 action），不再重放 |

### 5.5 幂等键（v3.2：结构化唯一键，不落字符串 execution_id）

```
幂等键 = UNIQUE (tenant_id, source_run_id, source_node_key, source_loop_index, effect_index)
```

- `execution_id` 只是这一组字段的**逻辑名**，**不作为字符串列落库**（v3.2 采纳 v2.2 异议：拼接键要处理分隔符/长度/大小写，
  且 `node_key` 可能包含分隔符；结构化唯一键还能被外键与查询直接利用）；
- 命令账本的 `command_ledger.idempotency_key` 是**派发级**幂等键，由 `(run, node, loop, step_seq)` 编码；
  它和效果幂等键是**两层**（一个节点可能有多个 step、多个 effect），通过 `run_id / node_key / loop` 对齐，不互相替代。

**为什么换锚点**（三方裁决 D1）：v2 用的是 `run+node+loop+plate`，它有两个洞 ——
① 一个节点**产生多个效果**时（分装、混合）没有区分位；
② 「板」不是效果的天然单位（一个效果可能涉及多块物料）。

⇒ `effect_index` 是**同一次执行内的效果序号**（一个节点声明 3 个效果就是 0/1/2），
一个效果涉及几块物料就在它自己的声明里写清 ⇒ **幂等键与「板」解耦**。

| 设计点 | 理由 |
|---|---|
| **`source_loop_index` 进幂等键** | 同一节点循环跑三次是**三次合法效果**，不能被幂等键吃掉 |
| **`attempt` 不进幂等键** | 设备/节点**重试**是同一次逻辑执行的第 N 次尝试 ⇒ 不该产生新的物料迁移（attempt 只进 action 留痕） |
| **同键同负载可跳过 / 同键不同负载必须报错** | 静默吞掉「设计变了」是最危险的失败模式 |
| **`payload_hash` 必存** | 判断「同键是否同负载」的依据 |

⚠ **`source_loop_index` 取执行上下文里的轮次，不取 `run_node.loop_index`** ——
这条是 2026-11-12 回源码核出来的（`docs/评审记录/20261112-04-openai.md` O-4），v3.2 再按第 5 轮复核收紧：

| 事实 | 证据 |
|---|---|
| `visit` 从 **1** 开始 | `GraphRunner.java:536` `visits.merge(key, 1, Integer::sum)` |
| 圈次落库用的就是 `visit` | `GraphRunner.java:657` `roundRecorder.record(key, visit, …)` |
| 落库 `loop_index = round` ⇒ **1..N**；**汇总行是 0** | `WorkflowService.java:1910-1929` |
| ⇒ `visit` 与**圈次行**的 `loop_index` 一致 | 上两条合起来 |
| ⚠ **但 `roundRecorder` 只在 `graphHasCycle && visit >= 1` 时调用** | `GraphRunner.java:654` |
| ⇒ **无环图的节点只有汇总行（`loop_index=0`），永远不落 1..N 的圈次行** | 同上 |
| ⚠ **但圈次行是「节点执行之后」才写的** | `GraphRunner.java:649` `stateMachine.executeNode(...)` → `:650` 回写节点状态 → `:657` `roundRecorder.record(key, visit, …)` |
| ⇒ **T1 发生在 `executeNode` 内部 ⇒ 本圈的行此刻还没落库** | 同上（完成处理器挂点见 §5.7） |

⇒ **读库拿不到「本圈」的轮次 —— 这是**时序**问题，不是「语义不一致」**（v3.2 补 · 05 号评审 O-11 修正）：
T1 那一刻库里只有汇总行（`loop_index=0`）⇒ 若 T1 改从 `run_node.loop_index` 取轮次，
**第 2/3 圈都会读到 `0` ⇒ 与第 1 圈撞同一个幂等键 ⇒ 效果被静默吞掉**
⇒ 幂等键的轮次**只能来自执行上下文**（图路径 = 内存 `visit`；顺序/无环 = 0，§5.7 传递）。

⚠ **纠正原稿的一处错误论证**（O-11）：原稿写「读库会得到**语义不一致**的值」，
并把「无环图只有汇总行」当作不一致的例证 —— **这条例证不成立**：无环图每个节点只跑一轮，
`loop_index=0` 就是它**唯一且无歧义**的值；不一致只存在于**有环图**（同一 node_key 有 1 条汇总行 + N 条圈次行）。
而**真正让「读库」不可行的是上面的时序，不是这个不一致** —— 实施者若按「不一致」去理解，
很可能改成「等圈次行存在时再读」，而那在 T1 时点上**永远等不到**。

⇒ `attempt` 不入键的收益也随之明确：**设备重试不改 `visit`** ⇒ 同一逻辑执行重试 N 次仍是同一个幂等键 ⇒ 效果只应用一次 ✓

⚠ **跨续跑（v3.2 补 · 并行 05 号评审 O-2）**：续跑时 `GraphRunner` 的内存 `visits` 从零开始，
若节点已跑过 N-1 圈，第 N 圈会重新得到 `visit=1` ⇒ **与已应用效果撞幂等键**。
⇒ S2 实现要求：续跑启动前**按 `run_node` 圈次行（或效果记录）恢复每个节点的 `visit` 起点**
（`MAX(source_loop_index) + 1`），并以该起点初始化 `visits`；**不得从 1 重新计数**。

⚠ **v3.2 补（第 5 轮 S12）**：现有按节点更新/查询的 SQL（`updateNodeStateLive` / `updateNodeResult` / `markBypassed` /
`selectTopNodeKeyIds` / resume 的 `deleteIncompleteTopNodes`）**只过滤 `level=0`、不过滤 `loop_index`** ⇒ 会命中圈次行。
⇒ S1/S2 的新写入必须显式带 `AND loop_index = 0`（或按精确圈次条件），**不得沿用现有写法**。

⚠ **v1 的 `(owner_run_id, owner_node_key, plate_id)` 会让循环第三圈撞唯一索引** —— 这是硬伤（v2 已修）。

### 5.6 并发：板级串行化与冲突仲裁（v3.2 补规则）

唯一索引只防「同一幂等键重复」，**不防两个不同节点/人工同时改同一块板**。

| 场景 | 规则（v3.2） |
|---|---|
| 两个自动迁移同改一块板 | T2 内 `SELECT ... FOR UPDATE` 锁板 + **`state_version` CAS**（读—校验—写入同一事务；版本不符 ⇒ `FAILED` + 受控重试，不覆盖） |
| 人工改状态 API | 必须带 `expectedVersion`；版本不符 ⇒ **HTTP 409** + 当前值/版本，不静默覆盖 |
| 人工盘点 vs 自动迁移同时发生 | **人工优先**：自动迁移读到新版本 ⇒ 回 `PENDING` 等重放（不写值）；人工操作追加 `MANUAL_INVENTORY / MANUAL_CORRECTION` 事件，并把该板待处理效果置 `CANCELLED`（原因留痕） |
| 审计一致性 | `from_*` 必须等于**本次事务读到的值**（否则「两条审计都像成功、后提交覆盖先提交」） |
| 冲突可见性 | 冲突一律产生 `plate_material_effect_action`（`REBASE / CANCEL`）+ 告警；**禁止最后写入者无声覆盖** |

⚠ 现有 `PositionLock` 解决的是**位置互斥**，**不等于**物料状态的并发更新已解决。

### 5.7 完成处理器：唯一注入点与圈次传递（v3.2 重写）

**结论先说**：物料效果处理**只有一个注入点** —— 共享的 `RunStateMachine` 实例（`WorkflowService` 构造一份 `sm`，
同时供图执行与顺序执行使用），**不是**在 GraphRunner 和 WorkflowService 各挂一次（那会让图路径重复触发）。
真正的机制是**完成处理器** `NodeCompletionHandler`（不是监听器），返回值决定后续动作：

| 返回 | 含义 | 调用方动作 |
|---|---|---|
| `CONTINUE` | 当前节点无效果，或效果已 `APPLIED` | 节点可完成，后继进入派发闸门检查 |
| `HOLD` | 效果 `PENDING / FAILED / NEEDS_RECONCILIATION`（物理已完成但物料未闭环） | 节点仍标 completed（不伪造设备失败），**后继被闸门阻断**，run 进 `paused(pause_kind=material_sync)` |
| 抛持久化异常 | T1：连效果意图/物理完成事实都写不进去 | 立即中止当前 run ⇒ **隔离**（§5.2b），**不得续跑重放设备动作** |

| 决策点 | v3.2 结论 |
|---|---|
| 注入点 | `RunStateMachine.executeNode`：设备执行成功之后、`np.setStatus(COMPLETED)` / `emit(NODE_COMPLETED)` **之前**调用（构造注入，测试可替换） |
| 完成上下文 | 显式携带 `runId / runNodeId / nodeKey / loopIndex / effectIndex / 命令证据`；**不允许处理器反查最新一圈** |
| 圈次从哪来 | **图路径传内存 `visit`**（1..N）；**顺序执行与无环图传 0**；签名扩展点：`GraphRunner.java:649`、`WorkflowService.java:1057/1065`、`RealWorkflowRunner.java:183` 及测试/demo（S2 一次性改，见 §12） |
| 覆盖范围 | 只覆盖**设备 TASK 节点**；BUILTIN 节点不经过 `executeNode` ⇒ **BUILTIN 节点声明 `materialEffect` 预检即 ERROR**（§6.4）；`POST /api/experiments/flow-run` 与影子跑是已知缺口（§16.1） |
| 失败语义 | 处理器内部处理 T2 类失败（吞异常但留 `PENDING / FAILED` + 错误码）；**只有 T1 才上抛**，由 `WorkflowService` 的 catch 接住并隔离 run |
| `effect_index` 分配 | 一次通知内按 `outputs` 数组顺序分配 `0..n-1`；**重放/重试复用同一 `effect_index`**，不得重新编号 |
| 与 ExecutionListener 的区别 | listener 是副作用出口、故障不得影响执行；完成处理器**必须能反映失败** ⇒ 语义相反，**不合并**；`ExecutionListener` 保留原样 |
| 事件落库 | `ExecutionListener` 事件是缓冲落库、失败路径可能丢 ⇒ **不承载**「必须留下待补偿意图」；完成处理器自己写 action 表 |

⇒ **保留原样的东西**：`ExecutionListener` 不动（副作用出口）；`GraphRunner` 仍不碰数据库；两条生产路径（图 / 顺序）都走同一个 `sm`。

### 5.8 恢复：状态机、动作审计与人工闭环（v3.2 重写）

**效果状态机（6 态；v3.2 补 `CANCELLED`）**：

| 当前 | 触发 | 下一个 | 谁 | 记什么 |
|---|---|---|---|---|
| `PENDING` | T2 成功 | `APPLIED` | AUTO | action `APPLY` + `plate_material_event`（真实板变化） |
| `PENDING` | 业务规则不符 | `REJECTED` | AUTO | action `APPLY`（失败留痕） |
| `PENDING` | 数据库/并发失败 | `FAILED` | AUTO | action `APPLY` + error_code |
| `PENDING` | run 终止/取消 | `CANCELLED` | AUTO | action `CANCEL` |
| `FAILED` | 受控重试 | `PENDING` | **需恢复权限** | action `RETRY` + 原因 |
| `NEEDS_RECONCILIATION` | 人工对账：物理已发生且与声明一致 | `APPLIED` | **需核对权限** | action `RECONCILE` + 证据快照 |
| `NEEDS_RECONCILIATION` | 人工对账：物理未发生或与声明不符 | `REJECTED` | 同上 | action `RECONCILE` + 证据快照 |
| `REJECTED / APPLIED / CANCELLED` | 终态 | — | — | 不自动重试；确需更正 ⇒ 追加 `MANUAL_CORRECTION` 事件 + 新效果 |

**动作审计表 `plate_material_effect_action` 是唯一历史**（v2.2 §4.6 采纳）：
每次声明/应用/对账/重试/取消**追加一行**（`from_status → to_status`、`actor_type / actor_id`、原因、证据快照）；
`plate_material_event` **只记真实板状态变化**，不用 `RECONCILIATION` 事件伪造迁移。

| 崩溃/失败场景 | 行为（v3.2 修正） |
|---|---|
| **T1 前崩溃**（命令已下发/已回包，但效果意图没写成） | **先对账**：`command_ledger` `ACKED` ⇒ 物理已发生 ⇒ 按 run 级声明快照**重建 `PENDING` 效果**；`UNKNOWN / DISPATCH_STARTED` ⇒ 隔离 + 人工。**禁止**「重跑即可」 |
| T1 后 / T2 前崩溃 | 效果 `PENDING` ⇒ 补偿按**已解析的 `plate_id`** 重放 T2（不重跑设备动作、不重跑位置寻址） |
| T2 回滚 | 效果回 `PENDING` ⇒ 同上重放（幂等键挡住重复 action） |
| 重复补偿 | 幂等键 + action 追加 ⇒ 同键同负载跳过 |
| 补偿时流程已续跑/已结束 | 效果与 run 解耦 ⇒ 补偿不依赖 run 还活着；run 终止则未应用效果置 `CANCELLED` |
| run 被隔离（T1 失败） | run 落 `quarantined` + experiment 级 `runtime_hold`；**人工确认 + 对账完成前禁止 resume 重派设备命令** |
| 数据库异常 | **不得无声继续** ⇒ 记错误码 + 隔离/转人工 |

**人工恢复的权限、原因与审计**（评审 O-1 + 第 5 轮 G6）：

| 项 | 规则 |
|---|---|
| 谁可以操作 | 需独立权限（`material:reconcile` / `material:retry`；不能由自动补偿任务无脑改） |
| 是否要求写原因 | **必须**（`note` 留当时的失败原因与对账结论） |
| 每次尝试 | **追加一条 action**（不覆盖失败记录）；同时写 `operator_user_id` |
| 并发恢复 | 同一效果只允许一个恢复任务在跑（行锁 / `state_version`） |
| 恢复只做什么 | **只重新处理物料状态投影**，**绝不重新执行设备动作** |
| 接口 | `POST /api/material-effects/{id}/retry`、`POST /api/material-effects/{id}/reconcile`（§8） |

### 5.9 节点状态、效果状态、Run 状态的关系（v3.2 更新）

**三者不等价**，必须分开看：

| 设备执行 | 物料效果 | 节点状态 | 效果状态 | 结果 |
|---|---|---|---|---|
| 成功 | 达成 | `completed` | `APPLIED` | 正常继续 |
| 成功 | **待核对/失败** | `completed` | `NEEDS_RECONCILIATION` / `FAILED` | 节点算完成，**下游被派发闸门阻断**，run 进 `paused(material_sync)` |
| 成功 | 配置错误 | `completed` | `REJECTED` | 节点算完成，**下游阻断**，转人工 |
| 失败 / 人工 | 未产生效果 | `failed` / `manual` | — | 按既有恢复策略走 |
| **超时** | **结果未知** | `manual` | `NEEDS_RECONCILIATION` | **不得直接认定动作没发生**；先查命令账本 / 人工对账 |
| 设备成功但 T1 连意图都写不进 | — | 不标 completed | — | **隔离 run（quarantined）**，不落假完成、不续跑重放 |

⇒ **「节点完整完成」的判定**：显式声明 `NONE` 的节点不等效果；声明了效果的节点，
**只有效果达到相应确认等级**才算完整完成（由完成处理器返回 `CONTINUE`）。
⇒ **不新增 `node_status` 枚举值**：用 `run_node.material_sync_status` 表达，由**派发闸门**表达「下游不派发」。
⇒ **Run 能不能继续**：由流程依赖关系 + 节点执行结果 + 物料一致性共同决定 ——
既不该把物料问题一律变成整个 Run 失败，也不该允许依赖异常物料的后续节点继续跑。


## 6. 节点的物料效果契约

### 6.1 独立列，不塞进 `params`

**为什么不能放 `params`**：执行侧只读 `workflow_node.params->'method_params'`，
并用**扁平 JSON 解析器**解析后透传给驱动 ⇒ 嵌套结构放进去会被错误解析、
**甚至透传给设备**。而且 `produces` 是**中控自己的业务契约**，不是设备执行参数。

⇒ **独立列** `workflow_node.material_effect jsonb`：

```
workflow_node
├── params → method_params   ← 发给设备的参数（不动）
└── material_effect          ← 中控的物料契约（新增）
    ├── inputs
    ├── outputs
    └── operations
```

**好处**：不混进设备参数；设计器可独立编辑；可独立做 JSON Schema 校验；
可查"哪些节点声明了物料效果"；将来升级契约不影响设备驱动。

### 6.2 契约形态

```json
{
  "materialEffect": {
    "mode": "transition",
    "acceptedEvidenceLevels": ["device_ack", "physical_confirmed", "manual_confirmed"],
    "inputs":  [ { "by": "plateId", "plateId": 1001 } ],
    "outputs": [ { "by": "plateId", "plateId": 1001,
                   "processState": "amplified_product",
                   "sealState": "sealed" } ],
    "operations": []
  }
}
```

| 字段 | 含义 |
|---|---|
| `mode` | `none`（明确无物料副作用）/ `transition`（声明状态迁移）/ `legacy_unspecified`（老流程，运行等价 `none`，预检 WARN） |
| `inputs` / `outputs` | 物料身份 + 结果。**本期只支持一对一状态变化**；`outputs` 是数组（未来 1→N 预留） |
| `operations` | 预留：分装（1→N）、混合（N→1）、转板（1→1 新板）、取样检测（1→1 + 数据） |

⚠ **本期不实现分装/合并**，但**结构不封死**扩展空间（评审 O-3 的要求）；`operations` 本期仅占位，**预检拒绝未知 operation**（v3.2 收窄空承诺）。

⚠ **"本期只支持一对一"是 `_校验规则_` 的限制，不是表结构的限制**（评审 O-5 的要求）：
`inputs` / `outputs` 是**数组**，`operations` 是**数组** ⇒ 表结构天生支持多输入多输出；
本期只是**在校验层**拒绝一条声明里出现多个输入/输出。
⇒ 将来放开 SPLIT / MERGE **不需要改表**，只需要放宽校验并实现 operation 语义。

### 6.3 目标解析：物料身份优先，位置只是辅助

| 规则 | 说明 |
|---|---|
| **物料身份优先** | `plateId` / `barcode` 是身份；**位置是空间属性，不是身份** |
| 位置寻址必须校验归属 | 事务内校验 `tenant_id + resource_id + occupied_by_run`（**fail-closed**，与现有取板路径同口径） |
| 条码寻址也要校验 | 校验预期位置 / 归属，除非将来有显式的跨 run 移交操作 |
| `AUTO-*` 占位身份 | 位置登记缺条码时生成（会作为 barcode 落 `plate` 表）⇒ **不得当成已核实条码** |
| 设备重分配 | 设计时写死的 `resourceId` 不一定是实际目标 ⇒ **命令参数、设备回包、最终位置才是运行时证据** |
| 解析失败 | **隔离并转人工，不猜测** |
| 多步节点 | 必须定义 target 指**哪一步结束时的位置**；不能用节点结束时另一个位置反推整节点的作用对象 |

⇒ **T1 必须把解析出的 `plate_id` 落进效果记录**，后续一切以它为准。

⚠ **barcode 事实（v3.2 补）**：`plate.barcode` 是 **NOT NULL** 且同租户唯一（`uk_plate_barcode`），当前代码无更新路径 ⇒ §17 Q1 按此修正。

**证据优先级（评审 O-3 的要求：不能只凭 `occupied_by_run` 就认定物理身份已确认）**：

| 序 | 证据 | 说明 |
|---|---|---|
| 1 | 声明里**显式**的 `plateId` / `barcode` | 人/设计器指名的那块板 —— 但**它只是"我们以为是谁"，不是"物理上是谁"** |
| 2 | **设备命令回包**里的物料标识 | 设备自己说的（比位置投影新）—— 这是**物理证据** |
| 3 | 命令参数里的目标位置 + 位置状态投影 | 最弱 —— **只是辅助** |
| 4 | `occupied_by_run` | **只能证明"这个 run 占了它"，不能证明"物理上就是它"** |

⇒ **三类冲突，三种处置**（v3.2 补 · 评审 20261112-05 的 O-8）：

| 冲突 | 处置 | 理由 |
|---|---|---|
| **① 声明 vs ② 设备回包**（指向**不同的板**） | 效果进 **`REJECTED`** + 转人工核对**声明** | 声明是"我们以为是谁"、② 是"物理上是谁" ⇒ **不按声明硬写**（与 §11.2 的 T12 同口径）⇒ 落库的 `plate_id` 取 **②**，不取 ① |
| ① 与 ② **一致** | 取该板 | 两路证据互证 |
| **② 设备回包 vs ③ 位置状态投影** | ② 优先 | 位置投影可能滞后（板在设备执行期间被物理移动过） |
| ③ 与 ④ 冲突 | 进 `NEEDS_RECONCILIATION` | 两个都是弱证据，**不自动采信任何一方** |
⇒ **设备执行期间发生了物理移动**（位置投影更新时机与物料状态处理时机不一致）时，
上面第 2 条证据优先于第 3 条 —— 否则会解析到错误的板。

### 6.4 显式声明 vs 未声明

| 情况 | 行为 |
|---|---|
| 明确无物料副作用 | 节点声明 `materialEffect.mode = "none"` ⇒ **不报警** |
| **内置逻辑节点（BUILTIN）声明物料效果** | **ERROR**（预检拦截）：内置节点不经过统一完成点，本期不承载物料效果 |
| **画布逐步执行 / 影子跑 / 单命令探针** | **不覆盖**：这些通路不产生/不经过物料效果处理（§13.2-7/8），只允许在操作规范约束下用于调试 |
| 老流程未声明 | **WARN**（不改行为）；新版本里按 WARN 处理 |
| 已知会改内容/膜的节点缺声明 | **ERROR**（发布/启动时拦截） |
| 无法分类的节点 | 要求人工确认 `none` 或补声明 |
| 声明的状态不在字典里或已停用 | **ERROR**（发布/启动时拦截）；**运行期若被停用/删除 ⇒ 迁移失败转人工，不写「未知状态」冒充成功** |

⚠ **为什么不能一律 WARN**：v1 说"系统分不清搬运和忘了声明" —— 这不准确。
**能力/方法元数据可以在设计期标出**「位置-only / 可改变内容或膜 / 未知」，
只用于校验，不用于运行期猜状态 ⇒ 有了分类，就不必对所有节点一刀切。

## 7. 数据模型汇总（v3.2 · 已按第 5 轮复核修正）

> 下列 SQL 是 **S1 迁移脚本的结构基准**，不是可直接重复执行的幂等脚本：
> `CREATE TABLE / ADD COLUMN / ADD CONSTRAINT` 在 PG17 里重复执行会报错
> ⇒ S1 实施时用 `DO $$ ... EXCEPTION WHEN duplicate_object / duplicate_column ...` 包裹（v2.2 §14 / 第 5 轮 D14）。

--       老数据 status='completed' + material_sync_status='not_required' = 无物料声明的老流程（不是「未知」）。

**效果状态机（六态，v3.2 补 `CANCELLED`）**：

| 状态 | 含义 | 后续 |
|---|---|---|
| `PENDING` | 等待处理 | 补偿任务 / 下次重试 |
| `APPLIED` | 效果已应用 | 终态 |
| `REJECTED` | **效果不符合规则**（目标板归属不符、声明自相矛盾） | 终态，**转人工**，不自动重试 |
| `NEEDS_RECONCILIATION` | **物理事实不明确**（设备超时但可能已动作 / 身份证据冲突） | 等对账，**不得直接认定动作没发生** |
| `FAILED` | 处理失败（数据库/并发） | 保留 + 可受控重试 |
| `CANCELLED` | run 终止/取消，效果不再应用 | 终态（`plate_material_effect_action` 记 CANCEL） |

**事件证据枚举（`evidence`，v3.2 去掉 RECONCILIATION）**：

| 值 | 含义 |
|---|---|
| `DEVICE_CONFIRMED` | 设备结果确认（读到了实际状态） |
| `EXECUTION_DECLARED` | 节点完成后按声明迁移（**系统说的，不是设备说的**） |
| `MANUAL_INVENTORY` | 人工现场盘点 |
| `MANUAL_CORRECTION` | 人工纠正系统记录（**追加一条新事件，不覆盖历史**） |

**Execution Fact 落在哪（v3.2 裁决 R1）**：**不新建第二套命令台账** ——

| 事实 | 载体 | 关键列 |
|---|---|---|
| 命令已派发、结果未知 | **`command_ledger`** | `command_id varchar(160)`、`idempotency_key`、`state`、`resolved_at/by` |
| 命令回包结果 | **`run_command`** | `device_raw_response`、`status`、`attempt`、`sent_at`、`finished_at`（**无 `command_id` 列**） |

⚠ 原稿「`run_command` 已经有 `command_id`」是**事实错误**（第 5 轮 P0）：它 17 列里没有这一列，
`ack_at` 有列无写入者；真正的派发前事实在 `command_ledger`（已有 `CommandLedger` 实现，含 UNKNOWN 人工核对）。
**`command_ledger` 是命令台账、`plate_material_event` 是物料台账，两者不混。**

⚠ **`consumable` / `consumable_lot` 表已存在**（`30_business.sql:134,150`），S5 是**改造**不是新建（§4.4/§14）。

⚠ **`plate_material_event` 与 `plate_location_audit` 是两条线**：
前者记**内容/状态**变化，后者记**位置**变化；一次搬运可能只产生后者。

⚠ **原则**：系统按节点声明写入状态，**不等于**设备真正检测到了物料状态。
**这两种证据不能都显示成「设备已确认」。**

### 11.2 异常场景（27 条 · 三份评审 + 三份设计 + 统一架构 V1.0 + 第 5 轮复核的合并清单）

| # | 场景 | 必须保证的结果 |
|---|---|---|
| T01 | 设备执行成功，数据库写入失败 | **不允许静默显示物料状态正确** ⇒ T1 失败 ⇒ **阻断 run 并转人工**（重跑会把物理动作做第二次） |
| T02 | 设备超时，但实际动作可能已发生 | **不允许直接认定动作未发生** ⇒ 效果进 `NEEDS_RECONCILIATION` |
| T03 | 同一个设备命令回调重复两次 | 效果只应用一次（幂等键挡住） |
| T04 | 同一节点在一个 Run 中循环执行三次 | **三次真实效果均可追溯**（结构化幂等键含内存 `visit`） |
| T05 | 同一逻辑执行重试三次 | **只产生一次物料效果**（`attempt` 不进幂等键，只进 action 留痕） |
| T06 | Run 崩溃后恢复 | 已确认的效果不重复；未确认的**可恢复**（按已解析的 `plate_id` 重放） |
| T07 | 两个 Run 同时修改一块板 | **不发生状态覆盖**（`FOR UPDATE` / `state_version` CAS） |
| T08 | 两个物料同时占用同一个位置 | 由现有 `PositionLock` 挡住（**复用，不另建**） |
| T09 | 目标位置已经占用 | 迁移失败可见 + 转人工，不猜测 |
| T10 | 物料找不到 / 身份无法确认 | **隔离并转人工，不能猜测**（位置只作辅助，不作身份） |
| T11 | 人工盘点与自动迁移同时发生 | 有明确的冲突处理，**不无声覆盖** |
| T12 | 声明与设备执行结果不一致 | 效果进 `REJECTED` 并转人工，**不按声明硬写** |
| T13 | 节点执行成功但效果处理失败 | 节点仍算完成（不伪造设备失败），**下游不派发**（派发闸门查直接前置节点的物料同步状态） |
| T14 | 状态更新成功但事件记录失败 | 二者**同事务**，要么都成要么都回滚（不允许"状态改了但没历史"） |
| T15 | 跨租户的物料或字典引用 | **必须被拒绝**（复合外键 / 租户上下文校验） |
| T16 | `FAILED → PENDING` / `NEEDS_RECONCILIATION` 的恢复 | **权限、原因、审计完整**；每次尝试追加一条 action（RETRY / RECONCILE），不覆盖失败记录 |
| T17 | 顺序执行与图执行 | 进入**同一套**状态处理机制（不是两套） |
| T18 | 多步骤节点执行 | **不遗漏**中间执行事实与物料影响 |
| T19 | 人工修正后再次收到旧回调 | **不覆盖**人工确认后的状态 |
| T20 | Run 异常终止后位置仍被占用 | 可安全核对和释放 |
| T21 | 运行中改了节点声明 | T1/T2 只用 run 启动快照（`run_node.input.material_effect_snapshot`），**新声明不影响已开始的 run**；下一个 run 才生效 |
| T22 | 字典状态被停用后既有板仍引用 | 停用不删（`enabled=false`）⇒ 历史显示不受影响；新迁移声明停用状态 ⇒ 预检 ERROR |
| T23 | 同一 execution 的多个 effect 部分成功 | 每个 `effect_index` 独立状态；**部分成功不得整体标记 APPLIED**；run 只有在全部 effect 闭环后才解除闸门 |
| T24 | `NEEDS_RECONCILIATION` 经人工确认/否决 | `reconcile` 接口 → `APPLIED` / `REJECTED`，追加 action + 原因 + 证据快照；确认前不写板状态 |
| T25 | 人工修正后再次收到旧回调 | 旧回调命中幂等键（已处理）⇒ 忽略；人工修正已追加事件 / version 递增，不被覆盖 |
| T26 | 节点在循环第 N 圈失败/待对账 | 循环节点必须汇总 1..N 圈实际状态；任一圈未闭环 ⇒ 下游闸门阻断，不能只看汇总行 |
| T27 | 被隔离/被闸门扣住的 run 重启 | 保持 `quarantined` / `paused(material_sync)`；**禁止** resume 删节点重跑；对账闭环后按 §8 前置条件恢复 |

⚠ 任何一条没有明确处理机制，都**不能**宣称物料状态管理具备生产可用性。
