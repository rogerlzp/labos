## 1. 问题：现场会问、但系统答不上来的问题

以下四个问题来自真实工艺的现场（脱敏表述）：

| 问题 | 今天的答案 |
|---|---|
| 这块板现在装着什么？ | ❌ 答不上来。`plate` 表没有内容物字段 |
| 这块板是谁放进孵育箱的？之前在哪？ | ⚠️ **一半能答**：`plate_location_audit` 有位置流转痕迹（放板/取板各一行），但**不知道它当时装着什么** |
| 这次执行产出了哪些板？ | ❌ 答不上来。`plate` 没有"归属哪个 run / 哪一步"的字段 |
| 这批板里还有几块是空的？ | ❌ 答不上来。没有状态就没法按状态统计 |

**为什么这些问题重要**：它们不是"锦上添花的功能需求"，而是**追溯与交接的地基**。
流程与流程之间的输入往往就是上一流程的产物（同一块板换内容），
系统说不出"这块板现在是什么"，就等于跨流程的物料交接没有语义。

## 2. 根因：容器只有「在哪」，没有「是什么」

LabOS 现有的容器模型回答的是**空间问题**：

```
plate (barcode, plate_type, rows, cols, status, location_id, position_status)
  └─ position_state (resource_id, plate_id, occupied_by_run, ...)   ← 板在哪个位置
```

它**不回答内容问题**。真实工艺里，一块板的标签是这样的：

```
PCR板-3  [扩增产物]  (PCR扩增)  -膜
   │         │          │       └── 耗材状态（封过膜）
   │         │          └────────── 归属（属于哪一步）
   │         └───────────────────── 内容物状态（现在装着什么）
   └─────────────────────────────── 身份（条码）
```

⇒ **四个维度，LabOS 只实现了第一个。** 本期补上后三个（身份已有）。

## 4. 核心模型

### 4.1 容器的四个维度

| 维度 | 存哪 | 本期 |
|---|---|---|
| **身份**（条码/类型） | `plate.barcode` / `plate_type` | 已有；`plate_type` 要从 `unknown` 改成真字典 |
| **内容物状态** | `plate.content_state` | **新增** |
| **耗材状态** | `plate.seal_state`（膜）+ `consumable` 表（盖子等独立耗材） | **新增**（§4.3） |
| **归属**（哪个 run / 哪一步） | `plate.owner_run_id` / `owner_node_key` | **新增** |

### 4.2 内容物状态：租户级字典，不是系统枚举

**问题**：内容物状态本质上是**客户工艺的词汇**（`扩增产物` / `纯化后样品` / `显色` / `终止`…）。
真实工艺里出现过 18 种。系统**不应该假设**客户叫什么。

**方案**：`plate_content_state` 是**租户级字典表**，产品的责任只是给一份**推荐集**。

| 决策 | 取值 | 理由 |
|---|---|---|
| 字典归属 | **租户级**（带 `tenant_id`） | 状态名是客户词汇，系统无权规定 |
| 是否内置 | 内置**一份推荐集**（`is_builtin`），租户可复制/改名/增删 | 从零建 18 个状态体验极差；但推荐集只是"建议"，不是"规定" |
| 唯一标识 | `code`（机器标识，与语种无关）+ `display_name`（客户看到的） | 改名不该改引用 |
| 状态取值 | `plate.content_state` 存 `code` | 显示时按当前租户的字典本地化 |

⚠ **不要**把内容物状态做成 `varchar` 自由文本或 `jsonb`：
前者会出现「扩增产物 / 扩增产物 」两种写法（没法按状态查），
后者没法索引（「现在有几块板在扩增后状态」这种查询做不了）。

### 4.3 耗材：**一个判据，两种建模**

真实工艺里「耗材」有两种，它们的**建模代价差一个数量级**：

| | 图上是什么 | 建模 |
|---|---|---|
| **膜** | 封上 → 撕掉 → 撕下来的**直接进垃圾桶，不单独追踪** | `plate.seal_state`（`none` / `sealed`）—— 一个字段 |
| **盖子** | **独立实体**：有自己的位置流转（从常温载架取 → 盖到板上 → 再撕下） | `consumable` 表 —— 一类新实体 |

**判据（本文新增，建议写进评审结论）**：

> **耗材是否需要独立追踪位置？** 需要 ⇒ 独立实体；不需要 ⇒ 板上一个状态字段。

膜不需要（撕下来即弃），盖子需要（要知道自己从哪来、被盖在哪块板上）。
⇒ 不用为了"统一"把膜也塞进 `consumable` 表 —— 那只会产生噪音数据。

**未来的升级路径**：若将来要求「封的膜要回收、再利用」，把膜也变成 `consumable`，
`plate.seal_state` 降级成派生值（"当前盖着哪个 consumable"）。**表结构已为此留口**。

### 4.4 归属：为什么要单独两个字段

`owner_run_id` + `owner_node_key`（不用 `attr` JSONB）——
因为归属**要参与查询**：「这次 run 产出了哪些板」「这个节点动了哪些板」是高频查询，
JSONB 里的东西没法索引。

**归属在跨流程边界上怎么移交**：流程 A 结束、流程 B 开始时，
把 A 的 outputs（按 §6 声明）对应的板的 `owner_run_id` 交给 B 的 run。
⇒ **这是阶段 3 的内容，本期只把字段留出来，不实现移交**。

## 5. 状态迁移

### 5.1 一次迁移是什么

| 概念 | 内容 |
|---|---|
| **迁移** | 一块板的（内容物状态 / 耗材状态 / 归属）的一次改变 |
| **留痕** | `plate_state_audit` 一行：谁、什么时候、把什么从什么改成了什么 |
| **当前值** | `plate` 表上的冗余（便于查询），**由迁移同步更新** |

### 5.2 触发点：只有两个

| 触发 | 来源 | operator |
|---|---|---|
| **节点执行完成** | 节点声明了产出（§6） | `AUTO` |
| **人工盘点改状态** | 盘点页 | `MANUAL` |

⚠ **不允许隐式推导**：「板在孵育箱里 ⇒ 状态应该是孵育后」——**不做**。
状态是**声明**出来的（"我这一步产出的是 X"），不是从位置**推断**出来的。
理由：位置变化和内容变化是**两件事**（搬板不改内容，加液改内容但位置不变），
混在一起就会出现"移一下板状态就变了"的错误行为。

### 5.3 幂等：同一节点同一块板只迁移一次

- `plate_state_audit` 上加唯一索引 `(run_id, node_id, plate_id)`
- 节点重试、设备重试、run 续跑 ⇒ 不会写两行
- 幂等靠**唯一索引**（不是靠"先查再写"）⇒ 并发下也安全

### 5.4 与暂停 / 恢复 / 断点续跑的关系

| 场景 | 行为 | 是否正确 |
|---|---|---|
| 暂停 | 节点没完成 ⇒ 不迁移 | ✓ |
| 恢复后重跑 | 节点完成 ⇒ 迁移一次 | ✓ |
| 断点续跑（`skipKeys` 跳过已完成的节点） | **不迁移** | ⚠ 见 §5.5 |

### 5.5 ⚠ 事务边界（本文最需要评审的一点）

**要求**：**状态迁移必须与「节点完成」落库在同一事务里。**

否则会出现两种缝：

| 缝 | 后果 |
|---|---|
| 节点完成已提交、迁移未提交（崩在中间） | 板子"跑完了"但状态没变 ⇒ 追溯断链，且**无法自动修复**（没人知道它该变成什么） |
| 迁移已提交、节点完成未提交 | 板子状态变了但节点还在跑 ⇒ 状态超前，同样断链 |

**当前代码的事实**：节点状态走 `run_node` 表、命令走 `run_command` / `command_ledger`，
**是否在同一事务需要评审确认**（本设计不假设它已经是）。

⇒ **给评审者的问题 1**：如果节点完成与迁移无法同事务（跨库/跨服务/异步），
退路是什么？本文给的退路是：**迁移表加 `applied` 标志 + 一个幂等的补偿任务**，
但那会把"简单的一刀"变成"带补偿机制的一刀"——**这是本方案最大的不确定性**。

### 5.6 执行侧怎么挂

**沿用现成的 listener 模式**（不发明新机制）：

```
GraphRunner（纯执行器，不碰 DB）
   └── 节点完成 → 触发 NodeEffectListener.onNodeDone(nodeKey, method, params, ok)
          └── WorkflowService（boot 层，有 DB）实现它
                 ├── 读该节点的 produces 声明
                 ├── 找到目标板（按位置 / 按条码）
                 ├── 写 plate 的新状态
                 └── 写 plate_state_audit 一行
```

⚠ **失败处理**：迁移失败**不能让节点回滚**（板子已经动了，物理事实不可撤销）⇒
迁移失败**记错误码 + 转人工**，不吞。理由与 `run_node` 的既有口径一致：
物理动作已发生 ⇒ 状态对不上必须让人看见，不能静默继续。

## 6. 节点声明产出物料

### 6.1 表达方式：`workflow_node.params` 里加 `produces`

**为什么放 `params`（JSONB）而不是加新列**：方法参数本来就在那儿；
`produces` 是"这个方法的物料副作用"，与参数同源。**本期不加列**（少一次迁移）。

> 备选：`workflow_node.produces jsonb` 独立列 —— 更干净、更好查
> （"哪些节点声明了产出"可以直接 SQL 查）。
> **取舍**：本期用 `params.produces`（少一列少一次迁移）；若评审认为"可查询性"更重要，改独立列。

### 6.2 形态

```json
{
  "produces": {
    "contentState": "amplified_product",
    "sealState": "sealed",
    "target": { "by": "position", "resourceId": 1000005 },
    "consumes": { "kind": "lid", "from": "stock" }
  }
}
```

| 字段 | 含义 |
|---|---|
| `contentState` | 产出后的内容物状态 `code`（§4.2 字典） |
| `sealState` | 产出后的膜状态（`none` / `sealed`） |
| `target.by` | `position`（按位置寻址）/ `barcode`（按条码寻址） |
| `consumes` | 消耗的独立耗材（本期只登记不执行，见 §14） |

**两种寻址方式的分工**：
- `position` —— 覆盖真实工艺里绝大多数动作（机械臂搬到哪就是哪）
- `barcode` —— 分装、转板这类"必须指定某一块板"的场景

### 6.3 没有声明产出会怎样

| 情况 | 行为 |
|---|---|
| 节点**动了板**但没声明 `produces` | 板状态**不变**；设计器预检给 **WARN**（"这个节点会动板，但没声明产出"） |
| 节点声明了但 `target` 找不到板 | **不静默**：记错误码 + 转人工（板子被别的实验占了/位置不对） |
| 节点声明的 `contentState` 不在字典里 | **预检拦截**（WARN）+ 运行期按"未知状态"处理并留痕 |

⚠ **为什么"没声明"只是 WARN 而不是阻断**：现场有大量节点是纯搬运（不改内容），
系统分不清"这个节点不改内容"和"用户忘了声明"⇒ 一刀切阻断会挡住正常流程。
⇒ **设计器侧给提示，运行期不猜**。

### 6.4 与搬运节点的关系

搬运（`Transfer`）**只改位置，不改内容物状态** ⇒ 搬运节点不声明 `produces`。
位置迁移由 `PositionLock` 负责（已有）⇒ **两条线不重叠**：
位置变更写 `plate_location_audit`，内容变更写 `plate_state_audit`。

## 7. 数据模型汇总

```sql
-- ① 内容物状态字典（租户级）
CREATE TABLE plate_content_state (
  id           bigserial PRIMARY KEY,
  tenant_id    bigint      NOT NULL,
  code         varchar(32) NOT NULL,
  display_name varchar(64) NOT NULL,
  sort_order   int         NOT NULL DEFAULT 0,
  is_builtin   boolean     NOT NULL DEFAULT false,
  UNIQUE (tenant_id, code)
);

-- ② 容器：加三列 + plate_type 变真字典
ALTER TABLE plate
  ADD COLUMN content_state  varchar(32),   -- → plate_content_state.code
  ADD COLUMN seal_state     varchar(16),   -- none / sealed（膜）
  ADD COLUMN owner_run_id   bigint,        -- 归属 run
  ADD COLUMN owner_node_key varchar(64);   -- 归属步骤
-- plate_type 取值：pcr_plate / deep_well / assay_plate / reagent_reservoir /
--                  sample_deep_well / consumable / unknown

-- ③ 独立耗材（盖子等需要独立追踪位置的耗材）
CREATE TABLE consumable (
  id          bigserial PRIMARY KEY,
  tenant_id   bigint      NOT NULL,
  kind        varchar(24) NOT NULL,        -- lid / cap / foil
  barcode     varchar(64),
  status      varchar(16) NOT NULL,        -- available / attached / discarded
  plate_id    bigint,                      -- 盖在哪个板上
  resource_id bigint,                      -- 当前在哪个位置
  run_id      bigint,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  deleted_at  timestamptz
);
CREATE INDEX ix_consumable_tenant_status ON consumable (tenant_id, status);
CREATE INDEX ix_consumable_plate        ON consumable (plate_id) WHERE deleted_at IS NULL;

-- ④ 状态迁移留痕
CREATE TABLE plate_state_audit (
  id                bigserial PRIMARY KEY,
  tenant_id         bigint      NOT NULL,
  plate_id          bigint      NOT NULL,
  from_content_state varchar(32),
  to_content_state   varchar(32),
  from_seal_state    varchar(16),
  to_seal_state      varchar(16),
  owner_run_id      bigint,
  owner_node_key    varchar(64),
  operator          varchar(16) NOT NULL,  -- AUTO / MANUAL
  note              varchar(255),
  created_at        timestamptz NOT NULL DEFAULT now()
);
-- 幂等：同一节点同一块板只迁移一次
CREATE UNIQUE INDEX ux_plate_state_audit_once
  ON plate_state_audit (owner_run_id, owner_node_key, plate_id);
```

> ⚠ **索引口径待评审**：`ux_plate_state_audit_once` 含 `owner_run_id`，
> 人工盘点（`operator='MANUAL'`）的 `owner_run_id` 为空 ⇒
> PostgreSQL 的唯一索引**允许多个 NULL** ⇒ 人工记录不受约束 ✓（这是有意为之）。
> 但若将来 `owner_run_id` 可空且要约束人工记录，需另加部分索引。

## 10. 迁移与兼容

| 项 | 做法 |
|---|---|
| **老数据** | `content_state` / `seal_state` / `owner_*` 全为空 ⇒ 语义是「**未知**」，不是「空」 |
| **不做历史回填** | 不知道历史状态，回填等于编数据 ⇒ 宁可未知 |
| **UI 显示** | 空值显示「未知」，不显示「空」 |
| **老流程** | 没有 `produces` 声明 ⇒ 行为与现在完全一致（状态不变）⇒ **零风险上线** |
| **老 API** | `GET /api/plates` 的响应体**只加字段不改字段**；新增筛选参数可选 |
| **建库脚本** | 走 `pg_rebuild/` 分片 + `90_all_in_one.sql`（`check-schema-sync.sh` 校验同源） |

## 11. 验收标准

| 问题 | 怎么验 | 层级 |
|---|---|---|
| 一块板被节点产出后状态变了 | 跑一个带 `produces` 的流程 ⇒ `plate.content_state` 变成声明的值 | 真环境 |
| 迁移有留痕 | `plate_state_audit` 有一行，`operator='AUTO'`，from/to 正确 | 真环境 |
| 能回答「这块板现在装着什么」 | `GET /api/plates/{barcode}` 返回 `content_state` + 字典文案 | 真环境 |
| 能回答「这次 run 产出了哪些板」 | `GET /api/runs/{id}/materials` 返回板列表 | 真环境 |
| 同一节点重试不会写两行 | 节点重试 ⇒ 审计表仍只有一行（唯一索引） | 纯逻辑 |
| 断点续跑不重复迁移 | `skipKeys` 跳过节点 ⇒ 审计表不新增行 | 纯逻辑 |
| 没声明产出 ⇒ 状态不变且有提示 | 预检报 WARN，板状态保持原值 | 纯逻辑 |
| 老数据不受影响 | 库里原有的 6 块板 `content_state` 仍为空，接口返回「未知」 | 真环境 |
| 字典改名不影响引用 | 改 `display_name` ⇒ 板上的状态显示跟着变，`code` 不变 | 纯逻辑 |
