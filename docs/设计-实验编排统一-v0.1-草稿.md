## 1. 现状：先摆证据，不靠印象

### 1.1 两套模型，只有一套在执行

| 表 | 谁写 | 谁读（执行） | 结论 |
|---|---|---|---|
| `experiment_process`（seq / workflow_id / loop_count / params_override） | 实验详情的"流程编排表"、API | `ExperimentExecutor.expand()` **按 seq 展开执行** | **唯一被执行的结构** |
| `experiment_graph`（graph jsonb：nodes / edges） | 只有画布（`GET/PUT /api/experiments/{id}/graph`） | **没人读** | 画布目前是死路 |

代码证据：

```
ExperimentExecutor.java:112   FROM experiment_process ... ORDER BY seq
QueryService.java:2139         SELECT graph FROM experiment_graph      ← 只有画布 API
QueryService.java:2162         INSERT INTO experiment_graph ...
```

**所以现在的"画布编排"画完不影响执行**——用户如果按画布调了顺序去跑，跑的还是表里的顺序。
这是必须先修的第一个问题（不是"要不要统一"，是"现在就不一致"）。

### 1.2 两个"编排"其实是两个层级

| | 流程（workflow） | 实验（experiment） |
|---|---|---|
| 画的是什么 | 一台/几台设备上的动作序列（BPMN task + 网关） | 多条流程之间的先后、变量、分叉、循环 |
| 编辑器 | bpmn-js（`/designer/:id`） | ReactFlow（`/experiments/:id/canvas`） |
| 存储 | `workflow.graph->>'xml'` | `experiment_graph.graph`（jsonb） |
| 执行器 | `GraphRunner` | `ExperimentExecutor`（**只按 seq 线性跑**） |
| 支持的语义 | 分叉/汇合/循环/变量 | 画布上能画分叉/并行/循环，**执行器一个都不支持** |

也就是说：**画布能画的语义 > 执行器能跑的语义**。这不是"以后补"，是画了会误导。

### 1.3 已经有"画了但没执行"的先例

`experiment_process.run_after`（int, 默认 0）在表里、在 API 里都返回，
但 `ExperimentExecutor` **完全没读它**。这就是"模型先行、执行没跟上"的典型：
字段存在会让人以为"填了就会等前面那步跑完"。

> 设计上的教训：**不要为了"看起来完整"提前加字段**。每加一个不执行的字段，
> 就是给下一个人埋一个假前提。

## 2. 问题一：`experiment_graph` 与 `experiment_process` 怎么统一

### 2.1 三个选项

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. process 为准，graph 只存布局**（推荐） | 画布保存 → 解析成 process 行（seq/顺序）+ 布局写回 graph | 执行模型单一；画布回归"编辑器"本职；表可校验 | 需要写"图 → 序列"的编译器；图里 DAG 暂时表达不了 |
| B. graph 为准，process 是视图 | 执行器改成读 graph | 画布语义完整（分叉/并行都能跑） | 要重写执行器 + 调度；process 上已有的循环/参数覆盖要迁移；风险大 |
| C. 双写 | 两边都改 | 短期省事 | **必然漂移**（就是现在这个局面），否决 |

### 2.2 推荐 A 的规则

1. **画布是唯一编辑入口**（拓扑类改动：加/删/连线）
2. 保存时**编译**：按拓扑序遍历节点 → 生成 `experiment_process`（seq 从 1 开始）
   - `workflow` 节点 → 一行，`workflow_id` 取自节点
   - `loop` 节点 → 给它包住的流程行写 `loop_count`
   - `variable` 节点 → 写进实验变量表（已有 `experiment_variable`）
3. **表只读**：详情页的流程表不再提供增删改，只显示"由画布生成"的序列 + 一个「在画布中编辑」按钮
   - 理由：`seq` 是线性量，**无法表达 DAG**。只要还允许表内调序，就会出现"表里线性、图里有分叉"的冲突
4. **编译失败要拒绝保存**：图里有环、有孤立节点、workflow 节点没绑流程 → 400 + 指出哪个节点
5. **顺序的唯一来源**：编译结果；graph 里节点的 `x/y` 只是布局，不参与语义

### 2.3 这条路的边界（诚实说明）

- 现在的画布支持 `fork/parallel`，但 `experiment_process` + `ExperimentExecutor` **只会线性跑**。
  在 Q3 的 DAG 落地之前，**带分叉的图编译出来只能退化成"按画布从左到右的线性序"**。
  所以第一阶段要么：
  - (a) 画布禁用 fork/parallel（画了也跑不对，干脆不给画），或
  - (b) 允许画但保存时明确警告"当前按线性执行，分叉暂不生效"
- 我倾向 **(a)**：不能执行的语义不要摆出来（和 §1.3 的教训一致）。

## 3. 问题二：能不能共用一个画布框架

### 3.1 两个层级，其实同构

剥掉表现形式，两者的元素几乎一一对应：

| 概念 | 流程（BPMN） | 实验（ReactFlow） |
|---|---|---|
| 一个有名字的步骤 | `bpmn:task` | `workflow` 节点 |
| 顺序 | `sequenceFlow` | edge |
| 分叉 | `exclusiveGateway` | `fork` |
| 并行 | `parallelGateway` | `parallel` + `join` |
| 循环 | 回边 + `maxIterations` | `loop` 节点 |
| 变量 | `__setVar` / `__expr` 内置节点 | `variable` 节点 |

**结论：结构同构，只是粒度不同**（流程的 task = 设备动作，实验的 workflow 节点 = 一整条流程）。

### 3.2 三个选项

| 选项 | 做法 | 优点 | 代价 | 何时合适 |
|---|---|---|---|---|
| **A. 全部用 BPMN** | 实验也存 BPMN XML；流程节点用 `bpmn:callActivity`（`calledElement=workflow:{id}`）；`GraphRunner` 支持"调用子流程" | **一套解析器/执行器/状态着色/测试**；两个层级用同一个编辑器 | 实验画布要迁移（当前 5 条数据）；`callActivity` 要加进 `TYPE_MAP` 且执行器要递归调用；ReactFlow 页面退役 | 想做"一套引擎"时 |
| **B. 两套编辑器，画布编译到 process**（短期推荐） | 保留 ReactFlow 做实验编排；只加"编译落库"（Q1 的 A） | 改动小（1–2 天）；风险低；马上消除"画布不生效" | 仍是两套模型，长期维护两套语义 | 现在 |
| C. 全部用 ReactFlow | 流程也改用 ReactFlow | 前端统一 | 要重写 BPMN 解析/执行/导入导出；bpmn-js 的成熟能力全丢 | 不建议 |

### 3.3 我的判断（不确定，想请评审挑战）

**先 B 后 A**，判据写清楚：

- 现在做 A 的收益不明显：**实验级只有 5 条数据、还没有人真的依赖分叉并行**（执行器也不支持）
- 但 A 是唯一能消除"两套执行器"的路。`GraphRunner` 和 `ExperimentExecutor`
  已经出现过语义不同步的苗头（`run_after` 字段、`bypassed` 语义、循环圈次）
- **触发条件**：当 Q3 的 DAG 真正实施时，A 的边际成本最低（反正要动执行器），
  那时一起做，比现在单独做一次更划算

> 所以我的建议是：**Q1 先落地（编译落库、表只读），Q2 的 A 与 Q3 的 DAG 合并成一个里程碑做**。

## 4. 问题三：流程之间的优先级、要不要嵌套子实验

### 4.1 现在的顺序是怎么定的

`experiment_process.seq` 升序，**严格线性**。没有优先级字段参与调度
（`priority` 在 `experiment` 上，是"实验之间"的排队优先级，不是"流程之间"）。

### 4.2 三个选项

| 选项 | 表达 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **A. 纯线性**（现状） | `seq` | 依次执行 | 并行、条件跳过、失败只重跑某段 |
| **B. DAG + 优先级**（推荐） | `edges(from,to)` + 节点 `priority` | 偏序：能并行的并行、关键路径优先；失败可只重跑下游 | 需要执行器支持并发派发 + 汇聚等待 |
| C. 子实验嵌套 | `experiment` 自引用 `parent_id` | 复用"一组流程" | 锁归属、变量作用域、取消传播、报表聚合全都复杂一倍 |

### 4.3 为什么推荐 B 而不是 C

用户提的"嵌套"，我理解真实需求是两种：

1. **复用**：同一组流程，换个样品再跑一遍 → 这是**模板/批次**（Q4），不是嵌套
2. **分组**：一个实验里分几个阶段（前处理 / 上机 / 分析） → 这是**DAG 的偏序 + 分组标签**，不是嵌套

嵌套会引入的问题（都要单独设计）：
- 子实验的"资源锁"归谁？父实验锁了机械臂，子实验要不要继承？
- 变量作用域：父实验的变量子实验能不能改？
- 取消/暂停：父实验暂停，子实验跟着停还是继续？
- 报表：一次执行的成功率按父算还是子算？

**结论：不做嵌套。** 用 DAG 表达先后与并行，用"分组标签(phase)"做阶段可视化，用批次做复用。

### 4.4 DAG 落地需要什么（草案）

```sql
-- 实验内流程之间的偏序（替代/补充 seq）
ALTER TABLE experiment_process ADD COLUMN priority smallint NOT NULL DEFAULT 5;  -- 同层竞争时先跑谁
CREATE TABLE experiment_process_edge (
  tenant_id   bigint NOT NULL,
  experiment_id bigint NOT NULL,
  from_id     bigint NOT NULL REFERENCES experiment_process(id) ON DELETE CASCADE,
  to_id       bigint NOT NULL REFERENCES experiment_process(id) ON DELETE CASCADE,
  PRIMARY KEY (from_id, to_id)
);
```

执行语义：
- 入度为 0 的节点可派发；同一时刻可跑多个（但**是否允许真实 wall-clock 并发**
  取决于资源模型，不能只看 `DeviceLock`）
- 汇聚：所有前驱完成才继续（等价 BPMN 的 parallel join）
- 失败：默认**停整单**（与现在一致）；可选"跳过失败分支继续"是另一个开关，先不做

> 这里要特别收口一个前提：`DeviceLock` **只能保证单设备互斥**，并不能证明
> "实验内 DAG 并发整体安全"。如果 S2 要做**真实并发派发**（两条分支在墙钟时间上重叠），
> 必须一并纳入现有的**三层资源模型 + 等待图**方案（位置 / port / 机械臂），
> 否则仍可能出现"A 持有位置等机械臂，B 持有机械臂等目标位，C 再形成回环"这类多资源死锁。
>
> 所以 S2 有两个可选落地口径：
> 1. **保守版**：逻辑并行、物理串行——只算偏序，不让多分支真实同时抢资源；
> 2. **完整版**：真实并发 + 三层资源 + 等待图拒环。
>
> 我现在倾向：**如果 S2 不同时带死锁治理，就只能宣称“支持偏序”，不能宣称“支持并行执行”。**

## 5. 问题四：一个实验很多样品，怎么分批

### 5.1 场景拆开看

> 一个实验 96 个样品，设备一次只能处理 24 个（或一块板），所以要分 4 批。

三种可能的落点：

| 选项 | 粒度 | 表达 | 优点 | 代价 |
|---|---|---|---|---|
| A. 实验级批次表 | `experiment_batch`（batch_no, 样品集合, 状态） | 一个实验 N 个批次，每批一次 run | 可观测性好；失败只重跑一批；报表能按批看 | 多一层表；状态要汇总 |
| B. 流程级批量参数 | workflow 接受 `batchSize`，内部循环 | 一次 run 处理多批 | run 数量少 | 失败重跑粒度粗；单 run 时间过长；进度难展示 |
| **C. 展开成多次 run**（推荐，A 的简化版） | 复用 M6 的"展开"思路：编译期把 `batch_split` 展开成 N 个 run | 不新增执行器；每批一行 run | 复用现有 run/run_node/进度/失败重跑 | N 批 = N 个 run，列表变长（可用父实验分组显示） |

### 5.2 推荐做法

1. `experiment_process` 加 `batch_split`（`null` = 不分批；`24` = 每批最多 24 个样品）
2. 编译/执行时按样品集合切成 N 批 → **每批一次 run**
3. 但**批次与 run 不能做一对一覆盖**：同一批失败后重跑，必须保留历史
4. 所以数据上要分两层：
   - `experiment_batch` = 逻辑批次（第几批、样品集合、当前汇总状态）
   - `experiment_batch_run` = 这批实际跑过的每一次（`run_id / attempt_no / status`）
5. 实验状态 = 各逻辑批次的聚合（全成 = 成功；任一失败 = 失败，但**其余批可以继续**）
6. 失败重跑：新建一条 `experiment_batch_run`，只重跑失败批次，不覆盖历史 `run_id`
7. 变量作用域：实验级变量全局共享；批次变量（如当前批的样品列表）在每批 run 开始时注入

### 5.3 我没想清楚的地方

- **批次之间要不要串行？** 设备只有一套，理论上自动被设备锁串行；但如果批次间需要"换板/清场"，
  就需要显式的"批间准备"步骤——这个还没有模型
- **样品怎么挂到批次上？** 现在 `experiment_sample` 是实验级关联表，没有"属于哪一批"的字段
- **批次归属落在哪层？** 是 `experiment_run` 自带 `batch_no/batch_id`，还是单独
  `experiment_batch_run` 关联 run？我现在倾向后者，因为它天然支持"同一批多次尝试"。

## 7. 迁移路径（分三步，每步可独立上线）

| 步 | 内容 | 产出 | 估 |
|---|---|---|---|
| **S1** | 新增**单一保存入口**：画布保存时同事务写 `experiment_graph` + 编译后的 `experiment_process` + `experiment.version`；表变只读；分叉/并行在画布里禁用 | 真正消除"画布不生效"与双写分裂 | 1–2 天 |
| **S2** | DAG：`experiment_process_edge` + 执行器偏序派发 + 汇聚等待；若做真实并发，**同步纳入三层资源 + 等待图**；优先级字段生效 | 实验内可偏序；是否可真并发取决于资源治理是否一起落地 | 3–5 天 |
| **S3** | 批次：`experiment_batch` + `experiment_batch_run` + 展开成多次 run + 失败只重跑该批 | 多批样品，且重跑历史可审计 | 2–3 天 |
| 可选 | 实验也改用 BPMN（`callActivity`），两套执行器合一 | 一套引擎 | 1–2 周（与 S2 合并更划算） |

### 7.1 S1 的 DoD（补充，避免再出“双套路径”）

1. 后端只保留**一个**“保存实验编排”的写入口
2. 该入口在**同一事务**里同时完成：
   - 保存 `experiment_graph`
   - 编译并整体替换 `experiment_process`
   - 更新 `experiment.version`
3. 现有流程表直改入口在同版本**关写**（至少 UI 不再暴露，后端拒绝外部写）
4. 任一子步骤失败时整体回滚，不允许出现“graph 已更新、process 没更新”或反过来
5. 回归测试至少覆盖：
   - 线性图保存成功 → `graph/process` 同步更新
   - 非法图保存失败 → 两边都不落库
   - 模拟 `process` 写失败 → `graph` 也回滚

## 补记（2026-11-05）：设计器「拖设备/拖方法」的落点取舍

本文 §2 的 A/B/C 讨论的是**编排统一**（graph 与 process 谁为准），结论 B「短期保留两套编辑器」继续有效。本轮另有一组更局部的取舍，记在这里避免与 §2 混淆：

| 选项 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A | bpmn 设计器加自定义 palette provider，让设备出现在官方 palette | 交互最"原生" | 要注册自定义元素类型与 moddle 扩展，`BpmnExpander` 展开成 subProcess 时还需额外兼容 | 放弃 |
| B | 把实验画布 `/canvas`（React Flow）作为「拖设备」的正式落点 | 它本来就有「岛上的设备」列表，改动最小 | 用户要求交互发生在流程设计器内；两套编辑器的语义会进一步混在一起 | **被用户否决**（原方案②） |
| C | 全部改成 React Flow | 前端统一 | 重写 BPMN 解析 / 编译 / 执行 / 导入导出，丢掉 bpmn-js 成熟能力 | §2 已判不建议 |
| D | 保持 bpmn 设计器，左侧做独立「岛 → 设备 → 方法」面板 + HTML5 拖放 + `modeling.createShape` + 自定义 renderer | 不动执行链与 XML 契约，图片随 SVG 缩放导出 | `$attrs` 只读 getter、无 `getAbsoluteOrigin()`、面板挤窄画布致既有 e2e 落点越界 | **采用** |

代价的完整清单与产品口径（流程可选绑岛、跨岛设备仍允许、板子换设备自动插机械臂）见 `决策记录.md` 2026-11-05 行与 `评审包-20261103/03-设计文档.md` D16。
