## 5. 关键设计决策（审核时重点核对语义）

1. **点位是点级稳定 id**：`device_point.id` 是点位身份；`resource_node.id` 是资源身份；`/api/positions` 两者都返回。
2. **绑定固化规则**：`node_binding.position_id → device_instance.id` 命中即 **pinned**，跳过候选池；只有 `node_binding` 为空 + legacy 才回退 XML/候选池。
3. **工位口径**：工位实体是 `resource_node(kind='workstation')`，**不是** `device_point.point_kind='workstation'`。`point_kind` 只表达 deck_in/deck_out/nest/waste 的交接角色。
4. **deck_in 可达性（P0-1）**：`deck_in`（台面内工位）`robot_reachable=false`、`point_role='internal'`、非进出位（与 272 个 internal 点位同口径）；机械臂只放 `deck_out`。
5. **角色**：admin/operator/designer/viewer（viewer 保留只读）。
6. **机械臂 type**：实际 `device_type='Robots'`（不是 'arm'）。
7. **搬运可观测**：保留既有 `TransferPlan`，新增 `transport_segment` 作为可观测记录（from/to/robot/status）。
8. **加锁顺序**：全局固定 `岛→设备→端口→点位→机械臂→物料`，多锁按资源 id 升序；`WaitForGraph` 做死锁环检测（误拒优于死锁）。
9. **扫码校验**：`barcode_policy` 五值（none/read/update/validate_in/validate_both）；validate_in/both 进设备方向不匹配 ⇒ 转人工停下等人（fail-closed）。

## 7. 已知边界 / 待产品确认（审核时不要误判为缺陷）

| 项 | 说明 |
|---|---|
| **P0-1 产品口径** | `deck_in` 已按建议值 `robot_reachable=false` 落地；若产品认为某 deck_in 确需机械臂可达，应另设 point_kind，**改一行迁移即可回退**（见详细设计 §10.2 开放问题 8） |

| **P1 不碰派发核心** | `experiment-runs/{id}/start` 通过 readiness 后「实际派发走既有调度链路」，未改写派发核心 |
| **调度器仍内存态** | `ExperimentScheduler` 未消费 `schedule_plan` 参数做最优化（2.0 简化版：贪心+滚动）；resource_booking 是观测记录 |
| **transport_segment 会累积** | 无软删；`scripts/cleanup-transport-segments.sql` 按保留期物理删除（默认 30 天） |

## 8. 审核建议清单（给审核 AI）

1. **跑一遍 §6 的回归**（纯单测 + 3~5 个 verify 脚本），核对数字。
2. **抽查 P1 全链路**：建模板 → instantiate → 配位置 → verify → readiness.ready → start（见交接清单 §5.1 的 7 步 curl）。
3. **核对数据口径**：`SELECT kind FROM resource_node WHERE kind='workstation'` 应 4 行；`device_point WHERE point_kind='deck_in'` 应 `robot_reachable=f, point_role=internal`。
4. **核对迁移幂等**：任一 `2026111*.sql` 连跑两次应 exit 0。
5. **核对新装库**：scratch schema 跑 `90_all_in_one.sql`（见交接清单 §9 的验证方法）。
6. **语义核对**：`node_binding` pinned 优先于候选池（用**不同**点位绑定，见测试报告 P0-2 的判别性用例）。
7. **角色导航**：admin 见「用户/审计」，designer/operator 裁剪，viewer 只读。
