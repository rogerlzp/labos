# LabOS AI：技术路线、实现步骤与市场竞争

## 0. 一页纸

**要做的事**：让科研人员用自然语言描述实验目标，由 AI 生成候选方案，经编译、校验、仿真、人工批准后，由 LabOS 确定性执行并留下可追溯证据。AI 永远不直接控制设备。

**为什么现在能做**：LabOS 已经跑通真实实验流程，手里有四样别人难复制的东西——命令账本、物料效果事务、搬运位置三态确认、设备事件幂等。这四样是"AI 敢不敢碰真实实验"的前置条件。

**缺什么**：四块基础设施还没建——对象级权限、租户上下文、服务端流程编译、可靠审计。以及两个必须立刻修的缺陷（并发门禁 fail-open、编译器丢设备能力映射）。

**分几步**：六步，12 个月。只读助手 → 能力接口 → 编译器 → Agent 团队 → 受控执行 → 单一实验域闭环。每步有明确的通过标准，不通过就停。

**竞争位置**：市场分四层（信息层 / 执行层 / 算法层 / 具身层）。多数玩家只占一层。我们的位置是"执行层 + 向上的编排接口"，差异化是**"AI 的建议能变成真实、可追溯、可追责的实验"**，而不是"模型更聪明"。

**一句话**：这不是给中控加一个聊天框，是把"科学意图 → 可执行计划 → 物理事实 → 下一轮决策"连成闭环。

## 1. 现状：中控有什么，卡在哪

### 1.1 已经有的（真资产）

| 能力 | 具体形态 | 为什么重要 |
|---|---|---|
| 命令账本 | 派发前先落库，幂等键防重发；重启时逐条查询设备状态，确认不了就进 `UNKNOWN` 且不自动重发 | 保证"命令不会重复执行"，这是自动化的生命线 |
| 物料效果闭环 | 节点确认与效果意图同事务；物料投影独立提交；闸门读失败时 fail-closed | 保证"物料状态不会凭空消失" |
| 搬运位置三态 | 设备回包只记 `REPORTED`；位置证据确认后才写 `CONFIRMED`；否则 `UNKNOWN` 等人工盘点 | 保证"设备说搬完了"不等于"板真的在目标槽" |
| 设备事件幂等 | 事件唯一索引 + run 游标 + 单事件消费约束 | 保证"一个事件只被一个 run 消费"，不会串单 |
| 流程与设备模型 | BPMN 流程图、节点、设备方法参数、能力绑定、点位、互锁 | 这是编译器的现成输入，不需要另造一套 |

这五样加起来，构成了"执行可信"的地基。AI 层要用的每一个事实，都应该从这里取，而不是让模型自己编。

### 1.2 卡在哪（六个缺口）

| 缺口 | 现象 | 后果 |
|---|---|---|
| 并发门禁 fail-open | 参数非法、状态词表为空、数据库异常三种情况下，门禁返回"允许" | 同一流程可能起两个 run，抢同一批设备事件和唯一机械臂 |
| 编译器丢能力映射 | 批量编译时接收了设备能力表，但内部调用没用上 | 预览显示的能力与实际执行可能不一致 |
| 状态投影不是事实聚合 | 实验状态只是把 run/batch 结果投影过去，多事实聚合被标记为"延后" | AI 无法凭状态判断"实验是否真的完成" |
| 设备事件身份不足 | 全局共享令牌、租户写死、事件来源 ID 可缺省 | 回调可被伪造或跨 run 投递 |
| 审计 best-effort | 写失败只记日志，不阻断业务 | 高风险动作可能"做了但没记录" |
| 无对象级权限 | 只有四个全局角色，核心链路租户写死 | 同租户跨项目可读，不能直接接多项目客户数据 |

### 1.3 一句话判断

执行底座兑现了大约 60%；而 AI 层要求的"可信事实"，依赖的恰好是缺的那 40%。所以顺序必须是**先补底座，再谈 AI 写入**。

## 2. AI 要解决什么问题

### 2.1 不是"加个聊天框"

如果只是让模型回答"这个实验为什么停了"，那是客服机器人，不是产品。真正的问题有三个：

1. **流程设计门槛高**。今天改一个实验参数，要工程师打开流程图、找到节点、改参数、检查依赖、重新发布。科研人员无法自助。
2. **异常归因靠人**。设备报错、物料没到位、位置不确定，现场要靠有经验的人逐层排查，夜里没人就停着。
3. **结果无法闭环**。上一轮实验的数据没法自动变成下一轮的参数建议，全靠人看表、拍脑袋。

### 2.2 AI 的正确介入点

| 环节 | AI 做什么 | AI 不做什么 |
|---|---|---|
| 设计 | 把"我要做一批 qPCR 检测"变成结构化草案，标出缺失信息和风险 | 不能凭空发明设备、方法、参数 |
| 启动前 | 解释"为什么不能启动"，指出是设备离线、物料未核验还是位置未分配 | 不能替人核验物料、不能改就绪判定 |
| 执行中 | 订阅事件，解释等待、超时、异常，给候选恢复方案 | 不能自己重试、不能解除隔离、不能改物理事实 |
| 结束后 | 汇总事实、区分假设与未知、关联证据、建议下一步 | 不能把无证据的推测写成事实 |

## 3. 技术路线

### 3.1 五层结构（AI 在上面两层）

```
L4 科研智能        Research Copilot / 个人 Agent / 项目 Agent
                   文献 · 假设 · 设计 · 分析 · 优化
                        ↓ 只能调用受控工具
L3 Agent 与编排     Agent Runtime · Planner · Workflow Compiler
                    Simulation · 审批 · 知识检索 · 实验工作区
                        ↓ 只能提交已批准的计划
L2 LabOS Core       实验 · 流程/节点 · 调度 · 资源 · 设备能力
（事实权威）        命令生命周期 · 物料/样本/位置 · 状态对账
                    权限 · 审计 · 恢复
                        ↓
L1 设备与边缘       驱动 · 边车 · 协议适配 · 边缘采集
                        ↓
L0 物理实验室       仪器 · 移液 · 机械臂 · 存储 · 传感器 · 人
```

三条不可越权的边界：

- **L4 不能碰数据和设备**：不许直连数据库、不许拼设备命令、不许自己宣布"实验成功"。
- **L3 不能改事实**：Agent 失败不改变 L2 已确认的设备、物料、实验状态。
- **L2 是唯一权威**：L3/L4 不维护"事实副本"，所有状态以 L2 为准。

分层是逻辑边界，不是要求立刻拆微服务。当前应保持模块化单体，等部署和隔离需求被证实再拆。

### 3.2 三条铁律

**铁律一：AI 不直接控制设备。**
原因不是保守，是三个工程事实：
- 设备命令不可撤销。开盖、移液、离心做错了，回滚不了。
- 模型的输出不稳定。同一个提示词两次调用可能给出不同参数。
- 责任无法归属。出了事故，必须有"谁批准的、按哪个版本执行的"这条链。

**铁律二：自然语言不能直接变命令。**
自然语言有歧义、不可校验、不可复现。必须经过：
结构化的实验 DSL（有类型、有单位、有版本）→ 编译成确定性计划 → 校验能力与资源 → 仿真 → 人工批准 → 冻结快照 → 才可执行。

**铁律三：命令完成 ≠ 物理完成。**
这是实验室事故最主要的来源。设备回包"搬运完成"，不代表板在目标槽；必须由位置证据、扫码或人工确认后，才能把节点标为物理完成。

### 3.3 核心机制：从意图到事实的八步

```
1 意图     用户用自然语言描述目标与约束
2 DSL      转成有类型的步骤：输入输出、参数、单位、条件、质量要求
3 校验     Schema、变量、依赖、设备能力、参数范围、样本身份、安全策略
4 规划     设备/资源/位置/耗材/时间窗分配
5 仿真     逻辑、资源冲突、容量、位置、可模拟的物理约束
6 审批     展示差异、风险、资源占用、预计人工任务；记录批准人与版本
7 冻结     冻结 DSL、编译器版本、能力版本、设备配置、物料分配、校验结果
8 执行     由 L2 调度器创建节点与命令；执行期不解释自然语言
   +
9 对账     设备事件与物理观察对账，处理偏差
10 归档    原始数据、派生数据、质量指标、偏差、分析版本关联到实验
```

关键设计点：

- **第 7 步的冻结是整条链的锚**。计划冻结后任何变更都要生成新版本并重新校验、重新审批。这样"正在跑的实验"不会被"后来改的模板"影响。
- **第 8 步明确"执行时不解释自然语言"**。这是把 AI 的不确定性和执行的确定性隔离开的分界线。
- **第 9 步的对账器**是新增的关键组件。它按证据来源、可信度、时间顺序裁决冲突；判不了就进 `UNKNOWN / NEEDS_RECONCILIATION`，绝不乐观推进。

### 3.4 双事实流（最容易做错的地方）

系统里同时存在四类事实，它们相互约束但不是单向级联：

| 事实流 | 内容 |
|---|---|
| 命令事实 | 已创建 / 已发送 / 设备已接受 / 执行中 / 设备报完成或失败 / 超时 / 取消 |
| 物理事实 | 样本、板、耗材实际在哪个位置；是否被抓取；是否落位；是否扫码或视觉确认 |
| 流程事实 | 节点前置条件满足、运行、等待、暂停、完成、失败、人工接管 |
| 实验事实 | 实验级状态与整体运行条件 |

四条规则：

1. 设备返回"搬运完成"不能自动证明板在目标槽。
2. 位置确认失败时，节点不能被标记为物理完成。
3. 人工确认物料到位，也不能伪造设备命令成功。
4. 冲突无法判定时，必须进 `UNKNOWN`，而不是默认成功。

AI 在这里的角色只有一个：**把四类事实拼成一份人可读的证据摘要**，明确指出哪些是已确认、哪些是推断、哪些是未知。它不能改变任何一条。

### 3.5 Agent 的权限与数据边界

**授权公式**（五个条件同时成立才允许）：

```
允许 = 租户匹配 ∧ 项目成员 ∧ 主体权限 ∧ 能力策略 ∧ 资源状态
```

**四条原则**：

1. Agent 是"受委托主体"，不是超级服务账号。**权限取交集，不取并集**，永不超过发起人。
2. 每次工具调用都要重新授权，不能只在会话创建时检查一次。项目成员被撤权后，长任务的下一次调用必须被拒。
3. 主体传播链 `用户 → Agent → 运行 → 设备 → 回调` 每一段都要能回答"谁授权、何时校验、审计记谁"。设备回调不因为关联了某次运行就重新获得发起人的权限。
4. 设备身份与用户身份分离。设备用独立的机器身份，不能借用用户会话。

**数据边界**（四级）：

| 等级 | 示例 | 默认策略 |
|---|---|---|
| D0 公开 | 公开论文、公开产品文档 | 可用已批准的外部模型 |
| D1 内部 | 内部流程元数据、非敏感说明 | 仅批准模型，最小化 |
| D2 机密 | 客户实验方案、项目上下文、未公开结果、内部工艺 | **默认不出域**，需项目授权与供应商批准 |
| D3 受限 | 个人信息、样本可识别信息、受监管数据、凭据 | **禁止外发**，需专门合规评估 |

分级只能被提高，不能被 Agent 或提示词降低。供应商的训练使用、保留期、处理地区、子处理方不明时，状态是 `UNKNOWN`，禁止 D2/D3 出域。

### 3.6 为什么不用另外两条看似更快的路

**路线 A：让 LLM 直接生成设备命令或代码去执行。**
快，但不可校验、不可复现、不可追责。一次错误移液可能就是几十万的样本损失。**不采用。**

**路线 B：让多个 Agent 自由讨论、自由委派、自主决定重试。**
演示效果好看，但会出三类问题：Agent 之间互相等待、失败后不知道从哪恢复、写操作权限扩散。**不采用**。首版只做"一个协调 Agent + 若干专业子 Agent + 有限并行 DAG"，明确禁止 Agent 自己创建 Agent。

## 4. 实现步骤

### 4.0 前置：两个必修缺陷（约 2–3 周，独立于 AI）

| 缺陷 | 修什么 | 怎么算修好 |
|---|---|---|
| 并发门禁 fail-open | 改成三态：允许 / 拒绝（已存在运行）/ 拒绝（无法判断）。无法判断必须拒绝；数据库异常、词表为空、参数非法都不能放行。同时把"新建"和"恢复"两条路径都纳入同一个原子准入边界 | 29 组验收、33 个可独立判断单元全部通过；其中必须包含两个独立进程争抢同一流程、以及"提交结果未知"的处理 |
| 编译器丢能力映射 | 两处调用补齐设备能力表透传 | 14 项验收；必须证明旧代码在这些用例上会失败 |

这两个不修，"可信执行"就是空话。而且门禁修不好会让流程直接起不来，所以必须有回滚方案。

### 4.1 第一期：只读助手（1–2 个月）

**做什么**：六个只读工具——查实验状态、查运行时间线、查设备健康、查物料位置、解释为什么被阻断、检索已验证的 SOP。

**产出**：一个能回答"这个实验为什么停在这儿"的助手；每条回答都带数据来源和时间，能点回系统。

**通过标准**：关键回答 100% 有权威数据来源；越权查询被拒；构造设备离线、命令超时、位置不明、重复事件等样本，回答不能把未知说成成功。

**不通过怎么办**：如果回答经常需要人纠正，说明事实投影不完整，回到第一期补"证据摘要"接口，不往下走。

### 4.2 第二期：能力接口（2–3 个月）

**做什么**：给现有业务能力套一层受控封装——查询类、草案类、预览类、执行类（后置）。每个能力记录版本、参数模式、风险等级、权限、幂等、超时、副作用、验证等级。

**关键约束**：不提供任意 SQL、不提供通用 HTTP 代理、不直接暴露设备驱动。高风险能力必须支持"预览/试运行"再"提交"。

**通过标准**：工具不绕过领域服务；读写边界清晰；每个写操作有幂等键、调用主体、参数摘要、审计事件。

### 4.3 第三期：流程编译器（3–5 个月）

**做什么**：定义实验 DSL（版本化、带单位、引用稳定 ID、每个动作声明前置条件/副作用/完成证据/失败处理），并编译到现有 BPMN 流程模型，生成不可变执行计划。

**输出**：相同输入和版本，必须产出相同计划；未通过校验的计划不能提交；计划变更必须重新校验和审批。

**关键决定**：**复用现有 BPMN，不新建平行执行引擎**。这条决定把工作量从"6 个月+"降到"2 个月左右"，也避免了两套状态机打架。

**通过标准**：计划可复现；计划冻结后任何变更生成新版本；仿真结果必须标明级别（结构校验/资源校验/物理近似/校准模型）和未覆盖风险。

### 4.4 第四期：Agent 团队（5–7 个月）

**做什么**：一个协调 Agent + 文献、方案、资源、数据/质控、审核五个专业 Agent。共享同一套权威数据，不各自维护事实副本。

**约束**：串行或有限并行的 DAG；不开放 Agent 自由创建 Agent；项目管理员选择模板、工具权限、知识范围；个人私有记忆不自动暴露给项目成员。

**通过标准**：跨用户/跨项目隔离测试通过；Agent 失败可恢复；任务可审计。

### 4.5 第五期：受控执行辅助（7–9 个月）

**做什么**：执行监控、异常诊断、恢复建议（不是恢复动作）。恢复由确定性策略加操作员审批完成。

**关键约束**：不同风险的操作分别定义策略——机械臂、液体处理、温控、开盖、样本移动不能用统一的"重试三次"。恢复动作必须校验设备能力、当前状态和人工审批。

**通过标准**：设备故障注入、断网、重启、迟到事件、人工接管场景全部通过；Agent 不自行改变物理或执行事实。

### 4.6 第六期：单一实验域闭环（9–12 个月）

**做什么**：选一个流程稳定、输出指标明确的实验域，做"设计 → 执行 → 分析 → 下一轮"的闭环。优化方法从实验设计（DoE）、统计模型、贝叶斯优化开始，不先上强化学习。

**通过标准**：至少三轮或足够样本量的迭代，按领域标准独立评价；**不以"模型给出更优参数"作为成功**，要看重复性和质量指标。

**选域标准**：流程已稳定且重复执行；输入可控、输出明确；有历史数据或可低成本采集；样本/试剂批次/设备/方法可追溯；失败成本和生物安全风险可控。

### 4.7 六个阶段的共同纪律

1. 每项能力标 `PASS / PARTIAL / FAIL / UNKNOWN`，`PASS` 必须绑定版本、环境、测试范围和证据 ID。
2. `PARTIAL` 必须列出未覆盖场景；`UNKNOWN` 不得默认通过。
3. 证据分六层：文档 / 源码 / 自动化测试 / 模拟器 / 真实现场 / 生产数据。**不跨级替代**——模拟器通过不能证明现场。
4. 上限规则：上层（Agent/Skill）的成熟度不得高于其关键依赖的成熟度。
5. 任何安全或物理事实关键测试失败，能力不得晋级。
6. 变更（模型、提示词、模式、驱动、固件、方法、安全策略）后按影响范围重新验证。

## 5. 和现有中控怎么结合

### 5.1 直接复用，不重写

| 现有资产 | AI 层怎么用 |
|---|---|
| 命令账本 | 作为"命令事实"的唯一来源；AI 的时间线和异常解释都从这里取 |
| 物料效果事务 | 判断"物料是否真的应用成功"；AI 不重算，只读结果 |
| 搬运位置三态 | 解释"为什么停在等待确认"；区分设备报完成与物理确认 |
| 设备事件幂等 | 提供稳定时间线；AI 引用事件时带事件 ID，可回链 |
| BPMN 流程与节点 | 作为编译器的输入；DSL 编译到这套模型，不另造执行引擎 |
| 设备模型与方法参数 | 作为能力目录的底座；每个能力的参数范围、单位、前置条件从这里长出来 |
| 点位与绑定 | 提供精确执行位置；AI 不猜位置，只用绑定结果 |
| 全局角色（四类） | 作为权限的起点，**不是终点**；上面要叠对象级授权 |

### 5.2 必须补的四块（这是真正的工作量）

**第一块：对象级权限。**
现在只有四个全局角色，租户写死。要接多项目客户数据，必须有"用户 → 项目 → 实验 → 资源"的对象级授权，并且服务端从资源关系解析所属项目，**不信任客户端或模型传入的项目 ID**。覆盖范围包括任务、产物、证据引用、记忆、附件、导出、缓存、搜索索引。

**第二块：租户上下文。**
核心执行路径现在固定 `TENANT=1`。要么统一改成从请求上下文解析，要么明确"只支持单租户部署"并写进产品边界。**不能一边写死一边宣称支持多租户。**

**第三块：服务端流程编译。**
现在 AI 规划的业务校验在前端，模型输出的操作由浏览器展开应用。这条路不能上真实数据——前端可以被绕过。必须把"模式校验、能力校验、参数白名单"搬到服务端。

**第四块：可靠审计。**
现在审计写失败不阻断业务。高风险动作（启动、取消、改关键参数、解除隔离、物料报废）必须与业务事实同事务，或用发件箱（outbox）保证最终一致；审计不可写时，动作必须失败或进入可恢复待处理状态。

### 5.3 改造顺序：先加旁路，再替换

```
第 1 步  只读旁路      新增只读查询接口，不动现有链路
第 2 步  草案旁路      AI 只产出草案，人工确认后才进入现有实例化
第 3 步  服务端校验    把前端校验搬到服务端，前端只展示差异
第 4 步  原子化        把"确认 + 实例化 + 审计"收进一个事务
第 5 步  权限收紧      对象级 ACL 生效，先只对真实项目数据
第 6 步  执行接入      只有前五步全部通过，才允许 AI 触发执行
```

这个顺序的核心是：**每一步都可以独立上线、独立回滚，且不改变现有链路的正确性**。任何一步要求"大重构"，就说明顺序错了。

### 5.4 三个"不"

1. **不重写核心控制系统**。AI 是加在旁边的编排层，不是替换执行内核。
2. **不新建平行调度引擎**。复用现有调度、资源锁、互锁。
3. **不让 AI 成为安全关键链路的单点**。模型不可用时，已批准的确定性流程必须能照常跑完。

## 6. 市场竞争

> 说明：以下为结构性判断，用于确定产品定位与投入优先级；具体厂商份额、定价与客户名单需市场部门补充实证后校准。

### 6.1 市场分四层，多数玩家只占一层

| 层 | 玩家类型 | 强在哪 | 弱在哪 |
|---|---|---|---|
| 信息层 | LIMS / ELN | 样本与数据管理、合规记录、报告 | 不知道设备真实状态，无法执行 |
| 执行层 | 自动化集成商、工作站软件、调度软件 | 设备接入、流程执行、板位调度 | 流程写死，改参数要工程师改图；不理解科研意图 |
| 算法层 | AI for Science 公司 | 分子设计、结构预测、实验设计优化 | 建议做出来了，实验室跑不动；拿不到真实执行数据 |
| 具身层 | 机器人实验室 / 自驾实验室 | 全流程无人化 | 建设成本极高、场景极窄、难以复制到常规实验室 |

### 6.2 我们的位置与差异化

**位置**：执行层 + 向上的编排接口。往下接设备，往上接科研意图。

**差异化（三条）**：

1. **"能执行"的 AI，不是"会建议"的 AI**。算法层公司的建议停在 PPT 上，我们的建议能编译成计划、在真实设备上跑、留下证据。
2. **"可追责"的 AI**。每一次执行都能回答：谁提的、谁批的、按哪个版本的计划、哪台设备、实际偏差多少。这在受监管场景（医药、临床检测）是刚需，在普通科研场景是加分项。
3. **"不替换"的 AI**。客户已有的设备、流程、数据不用推倒重来。这直接决定了销售周期——替换型方案通常要 6–12 个月决策，增强型方案可以 1–2 个月试点。

### 6.3 护城河

| 护城河 | 为什么难复制 |
|---|---|
| 执行事实的完整性 | 命令账本、物理确认、物料效果是两三年踩坑攒出来的，不是读代码能抄的 |
| 设备接入广度 | 每接一台设备都是脏活：协议、错误码、超时、断线、固件差异 |
| 领域知识编码 | 点位、方法、互锁、错误码映射，是领域专家加工程师一起沉淀的 |
| 客户迁移成本 | 实验流程一旦搬上来，换平台的成本极高 |

**但要清醒**：这四条护城河都建立在"客户真的把流程搬上来"之上。如果只卖 AI 助手而不碰执行，护城河一条都不成立。

### 6.4 威胁

| 威胁方向 | 具体形态 | 我们的应对 |
|---|---|---|
| 从上面打 | AI for Science 公司向下做执行 | 他们缺设备接入和物料/位置严谨性，短期难 |
| 从下面打 | 设备厂商自己做编排 | 只支持自家设备，客户被锁定，反而给我们机会 |
| 从旁边打 | 机器人集成商 + 通用大模型做轻量编排 | 缺审计、幂等、物料闭环，进不了受监管场景 |
| 低价替代 | 通用工作流引擎 + 插件 | 不懂实验室语义，异常处理撑不住 |
| 最大威胁 | 客户选择"人工 + 通用 AI 助手" | 只能靠"可执行、可追责"的实证案例打 |

### 6.5 商业化路径

```
第 1 步  Core 打底      设备接入 + 执行稳定，卖"跑得通、不出事"
第 2 步  AI 提频        只读助手 + 草案生成，降低使用门槛，提高日活
第 3 步  模板复用      项目级 Agent + 流程模板，形成可交付的垂直应用
第 4 步  单域案例      一个实验域的完整闭环，形成可复制的标杆
第 5 步  生态          能力市场、方法市场、应用模板市场
```

关键判断：**第 1 步不能跳过**。跳过它直接卖 AI，会因为"执行不稳"而失信；而执行稳了再卖 AI，客户已经在平台上，获客成本极低。

### 6.6 定价与打包（建议方向）

- 基础层按设备数或工作站位授权（一次性 + 年维护）。
- AI 层按项目数或活跃科研人员数订阅。
- 垂直应用按场景打包（如核酸检测、样本制备、QC）。
- 能力市场成熟后再考虑分成。

不建议按 token 或按次调用收费——客户无法预估成本，会抑制使用。

## 7. 风险与不做什么

### 7.1 主要风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 底座不完整被 AI 放大 | 门禁 fail-open、状态投影不全，AI 会把"不确定"说成"确定" | 先修两个缺陷；证据不足一律输出未知 |
| 效率收益无法量化 | 5 次试用撑不起统计结论，管理层会质疑投入 | 把效率降为观察项，门槛只看安全与证据 |
| ACL 成本被低估 | 对象级权限覆盖任务、产物、证据、记忆、导出、缓存，工作量大 | 分两期：先合成数据，真实数据前必须补齐 |
| 场景选错 | 选了流程不稳、指标不清的实验域 | 六条选域标准，不满足就不进第六期 |
| 客户数据出域风险 | 模型供应商条款不明时仍可能外发 | D2 默认不出域，供应商不明即禁止 |
| 组织风险 | 文档多版本、结论互相矛盾，导致评审失效 | 单一基线、强制注明 commit、编号唯一 |

### 7.2 明确不做（至少在早期）

- 不做没有审批和安全边界的"大模型直接控制机械臂"。
- 不把任意 Python 代码当生产协议执行。
- 不以 Agent 数量、模型参数量、聊天轮数当核心指标。
- 不一上来做跨所有生命科学领域的自动优化。
- 不声称数字孪生能证明真实物理执行必然成功。
- 不让每位用户维护一套彼此隔离的重复 Agent 代码。
- 不重写核心控制系统，不新建平行执行引擎。

## 8. 结论

**技术上**：这条路走得通，因为它把最难的部分交给了确定性系统——编译、校验、冻结、对账、审计；把 AI 限制在"理解意图、生成候选、解释事实"这三个它擅长且错了也不致命的位置。

**实施上**：顺序不能颠倒。先修两个缺陷，再补四块基础设施，然后才谈 AI 写入。想跳过中间步骤直接做"AI 自动实验"，一定会回到"演示很酷、现场不敢用"的老路。

**商业上**：竞争的不是模型，是"AI 的建议能不能变成真实、可追溯、可追责的实验"。这个能力依附在执行层上，所以必须先有稳定的中控，再有 AI；而一旦客户把流程搬上来，替换成本就成了我们的护城河。

**一句话**：先让 AI 理解中控，再让 AI 使用中控，最后才允许 AI 通过中控影响真实实验。
