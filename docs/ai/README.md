# LabOS AI：公开路线、架构与实践讨论

本目录集中讨论 LabOS 的 AI 产品路线、可信执行架构、Agent 协作方式与工程实践。内容面向公开评审，适合研发团队及其他 AI 助手阅读和提出修改建议。

本目录只讨论 LabOS 自有设计与实践，不包含外部品牌、厂商产品或竞品对标内容。所有实施文档均为待评审方案，不代表已经开发、测试或验收完成。

## 核心路线

```text
先核实现状
  → 只读 AI 助手
  → 人工批准的实验流程草案
  → 服务端编译、校验、仿真与计划冻结
  → 受控执行与事实对账
  → 单一实验域的结果反馈闭环
```

核心原则：

- AI 负责推理、解释和建议；LabOS Core 负责授权、校验、执行、状态和事实。
- 自然语言不能直接变成设备命令，必须经过结构化 DSL、编译、校验、资源规划、仿真、审批和执行快照。
- Agent 不直接访问数据库、Mapper、驱动或设备网络，只能调用受控业务工具。
- 命令完成不等于物理完成；设备报告、物料位置与实验结果必须分别取证。
- 先做一个真实实验场景，不先建设通用自主科研平台。
- Tenant 隔离不等于 Project ACL；真实项目数据必须有对象级授权和数据出域策略。
- Capability/Skill/Agent 的成熟度必须由对应版本和环境的证据证明，不能以文档或模拟器结果替代现场验收。

## 其他 AI 如何参与评审

建议按以下格式提出意见，便于转成可执行修改：

```text
结论：支持 / 反对 / 需要补充证据
位置：文档名 + 章节
依据：源码、接口、数据对象、实验约束或可复现推理
风险：权限、安全、物理事实、数据谱系、交付范围或成本
建议：具体删改内容或替代方案
验收：如何证明建议有效，哪些情况必须保持 UNKNOWN
```

评审时须区分：

- **现状事实**：必须能定位到源码、API、迁移或测试。
- **目标设计**：只是提案，不描述为已具备能力。
- **实施计划**：未开发、未运行、未验收时应明确标注。
- **未知事项**：证据不足时保持 UNKNOWN，不用推测补齐。
- **成熟度**：按具体能力版本、环境和证据分级，不以平台级概括替代。

## 当前最值得讨论的问题

1. 首个真实项目应选择哪个标准化、结果机器可读且现有设备可支撑的实验场景？
2. 只读助手需要哪些最小工具集和 EvidenceSummary 字段，才能解释“为什么实验停住”？
3. Workflow DSL 如何复用现有 BPMN/节点模型，而不是另建平行执行引擎？
4. Agent 的用户、项目、实验和资源级委托权限应如何表达与审计？
5. AI Workbench 的 30 天范围是否仍然过大，哪些交付应进一步删减？
6. 哪些验收指标能同时证明配置更快、执行更稳、失败更可归因、下一轮更有依据？
