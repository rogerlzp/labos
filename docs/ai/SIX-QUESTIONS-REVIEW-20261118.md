## 二、逐题

### Q1 产品方向是否成立

**结论：成立，但是"有条件成立"——条件是两个 FAIL 必须真修。**

**三条依据**

1. **差异化选对了位置**。方案没有押"模型更强"，而是押"AI 的想法能不能安全、可靠、可追溯地变成真实实验"。后者依赖的是 LabOS 已有的命令账本、物料效果事务、位置确认——这些是同行复制不了的部分。
2. **自我约束很硬**。明确不做：LLM 直控机械臂、任意 Python 当生产协议、Agent 数量当指标、数字孪生证明物理成功、每人一套 Agent 代码。这五条"不做"比"做"更能说明方向想清楚了。
3. **第一个场景收窄了**。只做一个标准化实验域的闭环（G6），不铺通用平台。这是能落地的节奏。

**两条风险**

- 如果 30 天做不出可量化的效率提升，AI 层会被内部当成演示功能，预算会断。而目前"效率提升 50%"已被降为观察项，等于承认暂时证明不了。
- 12 个月到 G6 闭环，需要设备、科学、工程三方同时到位。这类项目普遍延期，路线图里所有日期都标了"非承诺"，实际是在提前免责。

**需要你拍板**：首个真实实验域选哪个？（qPCR/核酸检测是当前假设，但 01 和 05 都还标着"待定"）

### Q2 架构分层是否合理

**结论：分层合理；但"双事实流"和"执行快照"目前是设计，不是能力。**

**三条依据**

1. **五层边界清晰**：L0 物理 → L1 边缘 → L2 Core → L3 编排 → L4 智能。最关键的一条是"L2 是执行事实的唯一权威，L3/L4 不维护平行事实"。这条与现有代码结构一致（Core 已有命令账本），不是空中楼阁。
2. **双事实流抓住了本质**：命令完成不等于物理完成。设备回包只记 `REPORTED`，位置证据确认后才写 `CONFIRMED`，判不了就进 `UNKNOWN`。这是实验室场景最值钱的一条设计。
3. **不强行微服务化**（ADR-006）：先模块化，等部署和隔离需求证实再拆。务实。

**两处未闭合**

- **双事实流还没实现**：G0-02 明确 `ExperimentStateProjector` 的多事实聚合是 `DEFERRED`，实验状态仍只是把 Run/Batch 结果投影过去。也就是说，"四流对账"今天不存在。
- **执行快照依赖编译器**：而 G0-04 说当前 AI Plan 的业务校验在前端 `flowPlan.ts`，服务端没有 DSL 编译链。快照冻结无从谈起。

**需要你拍板**：是否接受"编译器先编译现有 BPMN、不新建平行引擎"（ADR-G0-06）？这条决定 G3 的工作量是 2 个月还是 6 个月。

### Q3 Agent 权限是否可控

**结论：设计上可控，代码上不可控。这是全部材料里落差最大的一项。**

**三条依据**

1. **授权模型是对的**：`Allow = 租户匹配 ∧ 项目成员 ∧ 主体权限 ∧ 能力策略 ∧ 资源状态`，Agent 取交集不取并集，每次工具调用重新授权，撤权后长任务的下一次调用必须被拒。这套逻辑站得住。
2. **主体传播链补上了**：`user → agent → run → device → callback` 四段，每段写明"谁授权、何时校验、审计记谁"，并明确"设备回调不因关联了 Run 就重新获得用户权限"。
3. **威胁模型覆盖 9 类**：注入、工具误用、幻觉、重复执行、陈旧上下文、模型故障、Agent 死循环、跨项目泄漏、不安全恢复。

**为什么说代码不可控**

- 现在只有 `admin/operator/designer/viewer` 四个全局角色
- 核心执行路径固定 `TENANT=1L`
- **没有** user→project→experiment→dataset 的对象级策略引擎
- 设备事件入口用全局共享 token、固定租户、`sourceEventId` 可缺省

所以"Agent 权限可控"这句话，今天只能加一个前提：**只在单项目、单租户、受信任网络内成立**。

**需要你拍板**：Project ACL 现在投，还是 30 天只做合成数据、真实数据前再补？（这是成本分水岭，见 Q4）

### Q4 30 天范围是否现实

**结论：功能范围现实，但"35–44 人日"只覆盖功能，不含安全治理。**

**三条依据**

1. **功能范围是收敛的**：2 张新表（`ai_task`/`ai_artifact`）、3 类异步任务、1 个新页面 + 2 个页面增强。1 后端 + 1 前端做 35–44 人日，紧但可行。
2. **估工已如实修正**：修订附录把四阶段改为 7–9 / 12–15 / 6–8 / 10–12，合计 35–44，并明确"不含 ACL、审计补强"，且"不作为承诺"。这个诚实度是加分项。
3. **验收门槛改了方向**：把"效率下降 50%"降为观察项，阶段门只看安全、证据、权限、审计、幂等这些确定性项。这是对的——5 次样本本来撑不起统计结论。

**风险**

- 如果按 09 的要求"真实数据前必须完成 Project ACL"，实际工期要再加 20–30 人日，30 天会变成 45–60 天。
- `RUN_REVIEW` 依赖证据链完整，但 G0-10 说数据谱系只有局部能力。这个任务可能做不实。
- 修订附录把"第 8–30 天接真实数据"改成"按门禁开放"，等于承认 30 天可能延期。

**需要你拍板**：30 天的成功标准是"功能可用（合成数据跑通）"还是"真实项目试用"？两者差一个 ACL 加一条数据谱系。

### Q5 成熟度如何判定

**结论：这是全套材料里质量最高的一份；但它是尺子，还没有量过任何东西。**

**三条依据**

1. **五级成熟度可执行**：L0 定义 → L1 实现 → L2 台架 → L3 真实验室 → L4 生产，每级绑定最低证据，**禁止跳级**。
2. **证据六层防自欺**：E0 文档 / E1 源码 / E2 测试 / E3 模拟 / E4 现场 / E5 生产，明确"E1 不证明运行、E3 不证明现场"。
3. **两条硬规则**：`PASS` 必须绑定版本+环境+范围+证据 ID；`UNKNOWN` 不得默认通过；上层成熟度不得超过关键依赖。

**缺口**

- **没有降级/退出机制**：L4 失效后怎么退回、证书有效期多久、谁判定失效、复审周期多长，全部未定义。
- **没有签核主体**：谁有权批准 L3/L4、争议怎么裁决，未定。
- **目前 0 项被评级**：09 也明确"评审处置不等于 08 的能力验收状态"。

**需要你拍板**：谁有权批 L3/L4？如果不定，这套标准会被绕开。

### Q6 现状底座到底怎样

**结论：比"0 PASS"看起来厚，比"能承载自主 Agent"薄得多。**

**好的部分（真资产）**

1. **命令账本**：派发前落库、幂等键防重发、重启时逐条 `QueryStatus` 对账、确认不了就进 `UNKNOWN` 且不自动重发。
2. **物料效果闭环**：节点确认与效果意图同事务（T1），物料投影独立提交（T2），闸门读失败 fail-closed。
3. **搬运位置三态**：设备回包只记 `REPORTED`，位置证据确认后才 `CONFIRMED`，否则 `UNKNOWN` 等人工盘点。
4. **设备事件幂等**：`source_event_id` 唯一索引 + run 游标 + 单事件消费约束。

这四件是很多团队做不到的，也是"可信执行"叙事的真实地基。

**缺的部分（正是 AI 要用的）**

| 缺口 | 编号 | 对 AI 的直接影响 |
|---|---|---|
| 并发门禁 fail-open | G0-01 | 同一流程可能双 run 抢设备事件 |
| 编译器丢能力映射 | G0-07 | 预览与执行可能不一致 |
| 状态投影不是事实聚合 | G0-02 | AI 无法凭 `experiment.status` 判断真实完成 |
| 设备事件身份不足 | G0-03 | 回调可被伪造/跨 run 投递 |
| 审计 best-effort | G0-05 | 高风险动作可能无审计 |
| 无对象级 ACL | G0-06 | 同租户跨项目可读 |

**一句话**：执行底座兑现了约 60%；AI 层要求的"可信事实"，依赖的正是缺的那 40%。

## 三、只记三件事

1. **可以批方向，不要批"已就绪"**。设计基线能冻结，代码是 0，证据是全空。任何对外表述都要带上这个前提。
2. **两个 FAIL 必须先修**。`G0-01` 让门禁在库抖动时放行，`G0-07` 让预览和执行可能不一致。这两个不修，"可信执行"就是空话，且 G0-01 修不好会让流程直接起不来。
