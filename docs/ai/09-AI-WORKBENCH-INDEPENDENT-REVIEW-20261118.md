## 4. P1 整改项

### R1 — 项目级数据授权缺口

**问题：** Agent/项目记忆设计强调项目成员范围，但 06 T3 明确“不做项目级 ACL”，只做角色 + tenant。一个租户包含多个项目时，tenant 过滤不能阻止同租户跨项目读取。

**要求：**
- 在真实项目数据试用前，实现 Project Member ACL；不能只依赖前端隐藏。
- Project、Experiment、ExperimentRun、Run、AITask、AIArtifact、EvidenceRef、Project Memory 的读取/写入均须验证对象所属 Project 和调用主体的成员权限。
- Agent 使用委托授权：主体用户权限 ∩ 项目成员权限 ∩ Capability 权限 ∩ 当前任务策略；Agent 不得扩大调用者权限。
- 暂无项目成员模型时，只允许一个明确隔离的试点项目和服务端白名单，且不得把该模式称为项目级 ACL。
- 跨项目同租户的 ID 猜测、列表过滤、证据引用、缓存和导出均纳入负向测试。

**验收：** 同租户 Project A 成员无法读取/修改 Project B 的任务、产物、运行证据、记忆或附件；直接 API 与间接证据链接均拒绝。

### R2 — G0 风险与 Workbench 试用准入不一致

G0 历史核查列出的重点风险包括：
- WorkflowRunGate 在 SQL 异常、状态词表为空、参数不完整时 fail-open；
- ExperimentStateProjector 多事实聚合仍有 DEFERRED 项；
- 设备事件入口固定 tenant、设备身份/令牌共享及 sourceEventId 可缺省；
- AI Plan 尚非完整服务端 DSL 编译、业务校验、审批和执行快照；
- 审计 best-effort、RBAC 缺少对象级权限。

**要求：** 把“可开发 AI UI/异步任务”与“可接真实项目数据/可影响业务对象”分成不同准入等级。任何 fail-open、租户/设备身份错误、事实聚合未闭环或关键审计不可追溯项，必须由对应工程整改及证据关闭后，才允许真实项目写入链路。Workbench 的 mock/synthetic 环境可先行，但不得用演示通过替代工程门禁。

### R3 — 草稿确认与实验实例化原子性

**要求：**
- 锁定 AIArtifact；验证状态、主体权限、模板版本、schema 版本及 `expectedContentHash`。
- 对 Artifact 消费映射、Experiment、ExperimentRun、Placement 和业务审计建立明确事务边界。
- 实例化和消费映射必须同事务提交；若审计采用独立存储，则必须提供可靠 outbox/可重放关联，不能仅 best-effort。
- 对同一 Artifact 重复确认返回原 Experiment/Run ID；同 key 不同 payload/hash 返回 409。
- 失败时不留下半成品业务对象；数据库唯一约束兜底，不能只靠前端防抖。
- 并发双击、HTTP 超时后重试、事务中断、提交后响应丢失均要测试。

### R4 — AI 草稿字段白名单与参数边界

首期只允许模型生成和用户编辑明确列入白名单的字段。建议：
- 可编辑：实验名称、描述、成功判据文本、模板已声明可调的参数。
- 参数补丁必须有 `path/type/unit/min/max/enum/templateVersion/mutability/approvalRequirement` 元数据；服务端按模板 schema 校验，不接受模型自行声明边界。
- 样本数、重复次数、温度、时间、体积等只能在已批准的模板参数范围内调整。
- 首期禁止 AI 修改设备绑定、设备方法、Workflow/Node 结构、物料身份/物理位置、安全策略、联锁和执行权限。
- 不认识的路径、单位不匹配、模板版本变化、超范围参数一律阻断，不自动修正后放行。

### R5 — 审计必须与风险等级匹配

将审计分级：
- 低风险查询/非持久化解释：可异步遥测，但仍需可追踪 task ID。
- Task/Artifact 创建、重试、取消、读取敏感上下文：持久化主体、时间、调用者、项目、模型/提示词/schema 版本、输入/输出哈希、结果。
- 草稿确认/实例化：业务事务内可靠关联审计，不能仅 best-effort。
- 设备控制和高风险写操作：本期 AI 不提供；未来必须审批、执行快照、可靠审计及可恢复记录。

审计内容采用白名单，避免保存 API Key、Authorization、完整敏感提示词或供应商原始响应。审计写失败时，安全关键操作必须失败关闭或进入可恢复待处理状态，不能默默继续。

### R6 — 模型数据出域和知识产权治理

在任何真实项目数据发往外部模型前，明确：
- 数据分类：公开、内部、客户机密、个人信息、受监管/敏感实验数据；
- 各模型供应商的数据保留、训练使用、处理地区、子处理方、删除机制及合同条款；
- 脱敏/最小化、字段级允许清单、日志与缓存保留期；
- 客户实验方案、原始数据、样本身份、项目记忆默认受控，不因“已脱敏”就自动允许出域；
- 每个 Project/Task 可配置模型路由与禁止出域策略，服务端强制执行；
- 数据出域决策可审计，并有禁用外部模型时的降级路径。

## 5. 对 05/06 的落地修订条款

以下条款是 05/06 的强制补充，不要求重写既有页面/API/worker 设计。研发任务必须将本节纳入 05/06 对应章节和验收清单。

### 5.1 05 — 0–30 天实施方案

1. **准入分层**：第 0–7 天可在合成数据/隔离测试租户开发；不得接真实客户项目数据。第 8–30 天是否接真实项目，取决于 §4 R1/R2/R5/R6 的逐项门禁，不按日历自动开放。
2. **对象授权**：每个 API、Mapper、EvidenceRef、导出和缓存读取都做 Project ACL；tenant 过滤只是必要条件，不是充分条件。
3. **原子实例化**：新增事务设计和数据库唯一约束；Artifact 锁、哈希校验、模板版本校验、Experiment/ExperimentRun/Placement 创建、消费映射与审计关联必须形成可恢复一致性边界。
4. **参数安全**：在 draft schema 中增加受控参数目录引用；`parameterPatches.path` 只允许服务端模板 schema 白名单路径。首期禁止修改设备/方法/流程结构/位置/安全策略。
5. **审计**：将草稿确认/实例化审计从 best-effort 提升为可靠事务关联；安全关键动作审计失败时不得静默成功。
6. **模型出域**：在 Task 创建前执行数据分类与模型策略判定；默认不把客户机密、个人信息和原始实验数据发送至未批准的外部模型。
7. **工期修正**：原 05 各阶段估工 7–9、12–15、6–8、10–12 人日，合计应为 **35–44 人日**，不是 35–42 人日。该合计仍是估算，不是承诺。
8. **任务顺序**：先异步任务骨架，再 EXPERIMENT_DRAFT，再 READINESS_EXPLAIN，再 RUN_REVIEW；任何阶段不得越过安全门禁。

### 5.2 06 — 第 1–7 天任务卡

1. T3 不再把“角色 + tenant”描述为真实项目数据隔离完成。若 Project ACL 尚未实现，验收环境只允许单一合成项目/白名单。
2. 新增 T3 权限测试：同 tenant 跨 Project 拒绝；跨项目证据引用、任务列表、artifact、memory、缓存和导出拒绝。
3. T1/T2 增加数据库约束：Artifact 单次消费、唯一消费映射、同 idempotency key + 同 input hash 返回原任务；同 key + 不同 hash 返回 `409 IDEMPOTENCY_KEY_REUSED`。
4. Worker 的 lease/attempt 必须具有 fencing：旧 Worker 在 lease 过期、任务取消或 attempt 增加后，不能提交 artifact、更新状态或覆盖新结果。
5. 增加实例化事务自测：并发双击只生成一个 Experiment/Run；中途异常完全回滚；提交成功但客户端超时后重试返回相同 ID。
6. 真实数据出域测试：拒绝未批准供应商、项目禁止出域、含受控字段的输入；日志/错误中不得出现密钥或敏感原文。
7. 第 7 天出口必须是证据清单，不是“任务卡已完成”：迁移 drift、自测原始结果、并发/迟到结果、对象授权、审计失败行为、出域策略、静态依赖扫描均需有记录。

## 6. G0 与 AI Workbench 的准入矩阵

| 能力/环境 | 允许范围 | 前置条件 |
|---|---|---|
| 本地开发、合成数据 | UI、Task、Worker、假 handler、schema 迭代 | 默认隔离；无真实设备依赖 |
| 内部演示、合成项目 | 端到端草稿与模拟 readiness/review | 明确标记 SYNTHETIC；无客户数据 |
| 内部真实数据只读 | 查询、解释、复盘 | 对象 ACL、租户边界、数据出域策略、审计通过；G0 对应读路径已复核 |
| 真实项目草稿生成 | 生成受限 Draft，不实例化 | R1/R2/R5/R6 关闭；项目授权和模型策略可验证 |
| 人工确认并实例化 | 创建 Experiment/Run/Placement | R3 原子性和审计可靠性通过；模板/参数白名单通过 |
| 任何设备执行动作 | 本期不允许 AI 调用 | 未来单独立项，重新风险评审、审批与现场验证 |

## 7. 新增能力成熟度分级

详见 [08 Capability Verification Standard](08-CAPABILITY-VERIFICATION-STANDARD.md)。成熟度必须按 Capability、Skill、Agent、设备/驱动和实验场景分别评级，不可用某个模块的成熟度代表整个平台。

## 8. 最终决策

- **保留**：产品战略、五层架构、Agent Runtime、Capability Catalog、Workflow Compiler 的总体方向。
- **保留但加门禁**：30 天 Workbench 方案。
- **允许启动**：第 1–7 天任务卡中的合成数据异步底座工作。
- **修改后启动**：任何接触真实项目数据、项目记忆、草稿实例化的工作。
- **暂缓**：多 Agent 自由自治、AI 自动启动实验、自动实验优化。
- **不批准**：仅凭角色 + tenant 就宣称项目隔离完成；仅凭 G0 历史报告就宣称当前 HEAD 全部通过；审计 best-effort 下的真实项目实例化。

原则：**先让 AI 理解中控，再让 AI 使用中控，最后才允许 AI 通过中控影响真实实验。**
