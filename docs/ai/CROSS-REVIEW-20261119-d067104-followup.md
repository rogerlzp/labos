## 2. F-01：轨道锁继承 DEVICE_STATE 后，真实申请顺序仍可能 rank 倒退

**发现类型：** 已知问题反驳 + 需补证据  
**结论：** 反对当前 rank 方案直接实施；必须先用源码调用链证明真实顺序，或修改模型。  
**位置：**《跨类锁顺序核查》§3.1–§3.3；《实施总纲》§3.4；验收 K-01。

### 依据

《跨类锁顺序核查》将资源组定义为：

- DEVICE_STATE：rank 1，包含设备执行锁与轨道分区锁；
- POSITION：rank 2，包含物理位置锁；
- RailZoneGuard 复用 DeviceLock，因此轨道锁继承 DEVICE_STATE(rank 1)。

同一文档规定申请 rank 必须非递减。

已知问题清单给出的真实搬运顺序是：

`设备(rank 1) → 位置(rank 2) → 轨道(rank 1)`

若该顺序经源码核实，则轨道申请时发生 `2 → 1`，违反非递减断言。把设备锁和轨道锁放在同一个存储组，只能说明它们共享表/存储组，不能证明它们在一次业务申请序列中永远相邻，也不能消除“位置锁已取得后再申请轨道锁”的反向依赖。

因此，文档中“设备与轨道同组，所以两者之间不存在顺序约束”的论证不充分：问题不是设备与轨道彼此谁先谁后，而是二者之间是否夹着 POSITION 组申请。

### 建议

实施前先画出真实调用路径的时序图，至少覆盖：

1. 正常搬运；
2. 位置预留后申请轨道；
3. 轨道批量申请失败并释放；
4. 失败回滚与重试；
5. 跨 step 持有位置锁；
6. resume 在新线程重新申请资源。

然后比较以下方案：

- **方案 A：拆分“存储组”与“锁语义 rank”。** 表可以继续复用，但锁语义不能因复用 DeviceLock 而自动继承同一个 rank；需要明确哪些资源申请之间存在真实顺序约束。
- **方案 B：调整真实申请顺序。** 如果物理流程允许，避免持有 POSITION 后再申请 DEVICE_STATE；也可评估先申请全部短期运动资源，再进入位置占用阶段。
- **方案 C：只对明确存在依赖的跨组申请做断言。** 仅当静态依赖图证明不会形成环时才可采用；不得用“关闭断言”掩盖真实死锁风险。

不建议只把 rank 数字改成 1/2/3。rank 必须表达真实依赖关系，而不是为了让测试通过而人为排序。

### 验收

- 给出源码文件、方法、行号和调用链，证明每种路径的实际申请顺序。
- K-01 覆盖真实正常搬运路径，不能只用人工构造的理想顺序。
- 正常路径不得误报；人为构造的真实反向依赖必须失败或被静态约束拒绝。
- 跨 step / 跨线程持有必须由显式 owner token 或等价机制证明，ThreadLocal 仅作开发期辅助断言。
- 若现场真实顺序无法确认，结论保持 **UNKNOWN**，不得批准锁护栏进入生产。

## 3. F-02：operation_key 的身份维度需要从“字符串持久化”闭环到“可恢复查找”

**发现类型：** 已知问题反驳 + 新问题  
**结论：** operation_key 的维度扩展方向支持；当前身份来源与 DDL 尚不足以证明 resume 后稳定。  
**位置：**《表设计》§1.1.1、§1.3、§1.7；总纲 §3.3；验收 L-*。

### 依据

§1.1.1 将 key 扩展为：

`r{run}|n{node}|s{step}|b{branch}|d{device}[|l{loop}][|i{invocation}]`

并规定首次生成后持久化，重放时读取。这一原则正确，但需要回答一个先于“读取已持久化 key”的问题：

**resume 后，执行器如何找到原来那条 operation，而不是先用重置后的上下文重新计算一个不同的 key？**

目前 §1.3 的 DDL：

- 注释中的 operation_key 仍是旧形态 `r|n|s|d[|l]`；
- 有 `loop_index` 列，但没有 branch_id / invocation_id 的独立来源字段；
- command_id 是 logical_operation 行上的单列；
- 唯一约束为 `(tenant_id, operation_key, generation)`。

§1.7 又规定不支持去重的设备每次传输生成新 commandId，并明确承认现有 command_id 唯一约束需要按设备档位放宽。仅在文字中写“实施时放宽”还不是可执行 DDL。

### 风险场景

1. **循环恢复：** 第 2 圈暂停，进程重启后内存 loopIndex 从 1 重新计算。若查找原 operation 前就用新 loopIndex 拼 key，可能找不到原第 2 圈记录，或错误命中第 1 圈记录。
2. **并行分支恢复：** branch 上下文重建后若分支标识不稳定，同一物理动作可能产生新 key。
3. **重复 invocation：** 同一 step 内两次独立物理调用，如果 invocation 序号只存在内存中，重启后无法证明是原调用重放还是新调用。
4. **不去重设备：** 同一逻辑操作可产生多次物理传输 ID；若 command_id 仍在 logical_operation 上单列唯一，数据模型无法自然表达一对多。

### 建议

将身份模型拆为三个实体/层次：

1. **LogicalOperation**：一次业务意图，具有稳定 operation_id、稳定 operation_key、generation。
2. **LogicalCommand**：该业务意图对应的稳定逻辑命令身份（若业务上一个 operation 可含多个命令，应明确其序号/子身份）。
3. **DeviceCommandAttempt**：每次真实传输一条记录，包含 device_command_id、attempt_no、设备能力档位、发送/确认状态和原始回包。

对设备去重能力分档：

- 支持严格幂等去重：同一逻辑命令重发复用稳定 device_command_id。
- 不支持去重：每次传输生成新的 device_command_id，但仍关联同一个 logical_operation / logical_command；不得把“每次传输新 ID”塞回一个全局唯一的 logical_operation.command_id 字段。

同时将 branch_id、loop_instance_id、invocation_id 的生成规则、持久化位置、恢复查找顺序写进 DDL 和状态迁移说明。不要把可恢复身份建立在内存计数器上。

### 验收

- 第 2 圈中断后重启并 resume，必须命中原 operation_id，不能重新生成第 1 圈身份。
- 同一 step 两次独立 invocation，operation 身份不同；同一 invocation 的重试，operation 身份不变。
- 并行分支重启后 branch_id 稳定。
- 不去重设备一次逻辑操作发生多次传输时，所有 device_command_id 唯一，且可追溯到同一个逻辑操作。
- 人工改变物理世界后是否 generation+1，必须定义明确触发条件；不能仅凭“resume”或“重试”一词推断。
- 上述任一身份来源无法持久化或恢复时，必须进入 UNKNOWN / 人工处置，不得猜测归属。

## 4. F-03：advisory lock 需要隔离级别前提，0 候选事件还存在迟到 waiter 问题

**发现类型：** 已知问题反驳 + 新问题  
**结论：** 匹配域 advisory lock 是正确方向，但“消除幻读”的结论必须附带隔离级别和迟到 waiter 处理条件。  
**位置：**《表设计》§2.4；验收 W-*。

### 4.1 事务隔离级别

§2.4 要求 waiter 创建和事件认领都先获取同一把 `pg_advisory_xact_lock`，再在锁内读取候选集。这能把两个竞争路径串行化，但不能脱离事务隔离级别讨论可见性。

- 在 PostgreSQL **READ COMMITTED** 下，每条语句取得新的快照。事务在取得 advisory lock 后，再用下一条 SQL 查询候选集，可以看到前一个持锁事务已经提交的 waiter。
- 在 **REPEATABLE READ** 下，事务快照在事务首次需要快照时建立。若事件认领事务先建立快照、随后等待 advisory lock，等锁释放后仍可能使用旧快照，看不到刚提交的 waiter。
- SERIALIZABLE 还需要明确序列化失败的重试边界，不能把 serialization failure 当作“没有 waiter”或普通歧义。

因此，advisory lock 不能被描述为在任意隔离级别下都自动消除幻读。

### 建议

1. 明确 waiter 创建与事件认领必须使用同一事务级 advisory lock，且持有至事务提交/回滚。
2. 明确相关事务隔离级别。若采用 READ COMMITTED，明确要求“获取锁后，候选集查询必须是后续独立 SQL 语句”。
3. 若使用 REPEATABLE READ / SERIALIZABLE，必须提供可复现并发测试及完整重试策略。
4. 将 advisory lock 的键编码定义为稳定、无歧义的匹配域编码。32 位 hash 碰撞通常造成额外串行而非错归，但仍应避免依赖含糊的字符串拼接。

### 4.2 0 个候选与迟到 waiter

§2.4 当前规定候选集为 0 时提交事件 `UNATTRIBUTED`。

即使 waiter 创建和事件认领共享 advisory lock，仍可能发生：

1. 事件先取得匹配域锁；
2. 候选集为 0；
3. 事件提交为 UNATTRIBUTED 并释放锁；
4. waiter 随后取得锁并提交；
5. 后续没有机制重新扫描该事件。

这不是幻读，而是**事件先到、waiter 后到**的时序问题。共享锁保证串行，不保证事件一定等到 waiter 出现。

### 建议

在以下策略中明确选择一种：

- **Grace window：** 0 候选时先保持 PENDING / WAITING_FOR_WAITER，在短暂宽限期后才提交 UNATTRIBUTED；
- **反向回扫：** waiter 创建提交后，按匹配域回扫尚未归属且仍在有效期内的事件；
- **两者结合：** 事件保留待匹配状态，waiter 创建和事件到达都触发同一幂等匹配流程。

歧义（多候选）与暂时无候选必须区分：多候选可以提交 UNATTRIBUTED 并告警；0 候选不应在没有迟到匹配策略时立即永久终结。

### 验收

- READ COMMITTED 下，两个事务交错创建 waiter / 认领事件，不能错归。
- 若支持 REPEATABLE READ，必须构造“认领事务先建立快照、后等待锁”的用例，证明不会漏看 waiter，或明确禁止该隔离级别。
- 事件先到、waiter 后到，最终仍能唯一匹配。
- 多 waiter 歧义时不得任意挑选；UNATTRIBUTED 记录必须独立持久化。
- 过期 waiter 不得参与候选集；过期事件不得被迟到 waiter 重新认领。
- 任一时序无法证明唯一归属时保持 UNKNOWN / UNATTRIBUTED，不得猜测。

## 5. F-04：恢复三项核对不等于工艺恢复条件

**发现类型：** 已知问题补方案 + 新问题  
**结论：** §4.7 三层状态划分支持；§4.7.4 三项核对只能证明部分空间/设备安全，不能作为所有节点的完整恢复许可。  
**位置：**《设计基线》§4.7.2–§4.7.6；《暂停与恢复设计》§4.3、§4.5、§4.6。

### 依据

§4.7.4 当前三项是：

1. 板位置；
2. 设备是否真停；
3. 机械臂位置与分区是否物理空出。

这三项很重要，但没有覆盖工艺准备状态。例如：

- 针是否堵塞或残留；
- 液面/剩余体积是否足够；
- 耗材是否仍在位、是否已被消耗；
- tip / reservoir / reagent 是否需要更换或重新确认；
- 上一条命令是否可能已产生部分物理效果；
- 重放该节点会不会重复加样、重复吸液或重复转移。

§4.7.3 已规定耗材未知时不扣减、不复用，说明耗材本身已被承认为物理事实；但“不扣减、不复用”不是“恢复时已确认耗材可用”。

### 建议：恢复前置条件改为节点级四组检查

| 检查组 | 例子 | 默认失败处理 |
|---|---|---|
| 空间安全 | 板位、夹爪、腔体、机械臂、轨道分区 | 阻断 |
| 设备安全 | 设备停止、故障码、门锁/盖锁、设备模式 | 阻断 |
| 工艺准备 | 针状态、液面、耗材余量、耗材有效期/批次 | 按节点要求阻断或人工确认 |
| 操作连续性 | 上一命令是否完成、是否部分执行、重放是否会重复物理动作 | UNKNOWN 时阻断 |

不要要求每个节点都检查所有耗材；应由节点声明自己的恢复前置条件。例如：

- 加样/吸液：针状态、液面、耗材、是否可能部分出液；
- 转运：板位、夹爪、目的位置、轨道状态；
- 离心：转子/载具、盖锁、设备运行状态；
- 孵育：温度、计时状态、样品位置及剩余工艺时间。

每条物理观察至少需要记录：subject、fact_type、value、source、observed_at、confidence、expires_at。证据过期后必须重新确认，不能永久复用历史结论。

### 验收

- 对每类节点定义恢复前置条件，不允许以全局三项检查替代。
- 构造“板位置正确、设备已停、机械臂空出，但针堵塞/液面不足”的恢复用例，必须阻断加样节点。
- 构造“命令可能部分执行”的用例，不得自动重放。
- 没有传感器能力的设备允许人工点检作为 P2 证据，但必须记录操作者、时间和证据；不能伪装成 P0。
- 设备只返回 done 时，必须按设备协议能力和节点语义决定可否升级证据等级；不能仅凭 done 推断所有物理事实。
- 证据过期、来源不可信或无法区分“未执行/部分执行/已执行”时保持 UNKNOWN。

## 6. F-05：待派发记录与暂停协调对象需要真正落成持久化模型

**发现类型：** 已知问题补方案  
**结论：** 方向支持，但目前是流程轮廓，尚不足以直接实现可靠性语义。  
**位置：**《实施总纲》§3.0.2(B)、§3.0.3；《暂停与恢复设计》§4.1.1、§4.3、§4.6。

### 依据与风险

总纲提出事务内写 queued 和持久化待派发记录，提交后唤醒 scheduler，这是正确方向。但目前仍需定义：

- dispatch 记录与 run 的一对一/一对多关系；
- scheduler 如何原子 claim；
- worker lease、心跳和过期回收；
- 发送成功但确认丢失时如何幂等；
- retry 与 dispatch_attempt 的关系；
- run 已终结但 dispatch 仍待处理时如何清理；
- 多次唤醒是否可能重复派发。

暂停设计的 pause_requested / pausing / pause_blocked 等状态也需要有持久化协调对象或明确的权威字段。否则服务重启后，无法可靠恢复“哪些批次已确认、哪些仍在等待、哪次暂停请求已经被更新的恢复请求取代”。

### 建议

- Dispatch：采用事务内写入的 outbox/dispatch 表，定义唯一 dispatch_id、run_id、state、attempt_count、lease_owner、lease_until、next_retry_at、last_error、created_at、updated_at；scheduler 通过原子 claim 获取任务。
- Pause：定义 pause_operation_id、scope、target_id、generation/request_version、requested_by、requested_at、deadline_at、status；逐个 target 记录确认状态和原因。
- pause/resume 竞争按 generation/request_version 做条件更新，旧请求不得覆盖新请求。
- 所有“提交成功但唤醒失败”的路径都由持久化扫描恢复，不依赖进程内回调。

### 验收

- DB commit 后、scheduler 唤醒前杀进程，重启后任务在规定 SLA 内被拾起。
- 唤醒重复执行不产生重复 worker 或重复物理命令。
- worker lease 过期后可安全重新 claim；旧 worker 恢复时不能越权继续执行。
- 暂停/恢复交错、服务重启、超时和部分批次确认后，协调状态可重建且审计链完整。

## 7. 对评审邀请的最小补充建议

建议在原八问后增加以下四项，不必重写邀请全文：

**9. 身份恢复：** operation_key 虽规定首次生成后持久化，但 branch / loop / invocation 的身份来源、恢复查找路径和 DDL 是否完整？尤其 loopIndex 重启后重算，如何保证命中原 operation？

**10. 事务隔离：** §2.4 的匹配域 advisory lock 是否明确 PostgreSQL 隔离级别？READ COMMITTED 与 REPEATABLE READ 下，拿锁后的候选集查询是否都能看到前一事务已提交 waiter？

**11. 迟到 waiter：** 事件先到、候选集为 0 时立即提交 UNATTRIBUTED，后续 waiter 才创建，如何避免事件永久无法归属？是否有 grace window 或 waiter 创建后的反向回扫？

**12. 工艺恢复：** §4.7.4 三项核对是否仅覆盖空间/设备安全？针状态、液面、耗材和上一条命令部分执行情况，是否应作为节点级恢复前置条件？

锁序问题仍保留在第 1 问，并要求评审者明确验证“设备→位置→轨道”是否为真实调用顺序。

## 8. 最终裁决建议

| 项目 | 当前裁决 |
|---|---|
| 资源驱动并行总体方向 | 支持继续设计 |
| 全局锁序 / 跨类锁护栏 | **P0 未关闭，不批准实现** |
| operation_key / command_id | **P0 未关闭，不批准建表与接入** |
| waiter / event 归属 | **P0 未关闭，不批准事件认领实现** |
| 物理态与恢复 | **P0 未关闭，不批准自动恢复扩展** |
| outbox / pause coordinator | P1，进入实现前补齐持久化规格 |
| 并行度 2 | **继续不批准** |

**总原则：** 设计文档可以定义 UNKNOWN 的处理方式，但不能把 UNKNOWN 写成可继续执行。任何不能证明身份唯一、事件唯一归属、资源锁序无环、物理动作可安全续接的场景，都必须停在可审计的阻断状态。
