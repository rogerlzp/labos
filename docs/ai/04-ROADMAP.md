# AI-native LabOS 12 个月路线图 V1.0

- 日期：2026-11-18
- 状态：建议计划；不是工期承诺
- 前提：以当前 LabOS 现有实现为基础，不重写核心控制系统

## 1. 总体策略

按“先可信执行、再 AI 生成、再实验闭环”的顺序推进。并行开展产品原型和架构盘点，但 AI 写操作的开放必须受执行可靠性门禁约束。

## 2. 阶段计划

| 阶段 | 最早开工 | 最早完成 | 交付物 | 退出门槛 |
|---|---:|---:|---|---|
| G0 现状盘点 | 第 0 周 | 第 4 周末 | 领域对象/状态机/API/设备能力/数据谱系矩阵 | 每项能力标 PASS/FAIL/UNKNOWN，附源码与测试证据 |
| G1 只读 AI 助手 | 第 1 月 | 第 2 月末 | 自然语言查询、状态解释、事件时间线 | 关键回答 100% 有权威数据来源；越权查询被拒绝 |
| G2 Capability API | 第 2 月 | 第 3 月末 | Capability Catalog、权限、幂等、审计 | 工具不绕过领域服务；读写边界清晰 |
| G3 Workflow Compiler | 第 3 月 | 第 5 月末 | DSL、Schema、静态校验、计划快照、仿真 | 相同输入/版本可复现；未校验计划不能提交 |
| G4 Agent 团队 | 第 5 月 | 第 7 月末 | 个人/项目 Agent、知识分区、Agent Runtime | 多 Agent 任务可恢复、可审计、无跨项目泄漏 |
| G5 执行辅助 | 第 7 月 | 第 9 月末 | 执行监控、异常诊断、审批恢复 | Agent 不自行改变物理/执行事实；所有写操作审批；高风险审计 Outbox 与故障注入测试通过 |
| G6 实验闭环 | 第 9 月 | 第 12 月末 | 单一实验场景 DBTL、数据质控和优化 | 多轮实验有完整谱系、独立复核和重复性证据 |

重叠区间只表示可以并行做设计、数据准备和隔离环境开发，不表示可以跳过前置门禁或提前开放真实数据/写能力。05 的 30 天 Workbench 是挂在 G1 准备阶段的场景化 P0 试点，不另占 G 编号：它复用现有模板实例化，不提前交付 G3 通用 Workflow Compiler；四批交付可并行准备，但合成数据、真实数据、实例化和试用分别受对应能力门禁约束。所有时间均为相对建议，不是承诺日期。

## 3. G0：必须先完成的源码盘点

形成矩阵：
`领域对象 | 代码入口 | API | 数据表 | 状态机 | 事件 | 权限 | 测试 | 证据等级 | 缺口`

范围：
- Experiment / Run / Workflow / Node；
- Device / Driver / Capability / Method；
- Command / Device Event / Timeout / Retry；
- Material / Sample / Position / Placement；
- Scheduler / Resource Pool / Interlock；
- Result / Dataset / Audit / Permission / Recovery。

特别核对命令完成与物料物理位置确认的双事实关系；检查重复/迟到事件、设备断线、重启和人工接管。命令事实与物理事实应独立约束节点状态，这必须在源码和测试中验证，而不是只在文档里规定。

## 4. G1：只读 AI 助手

用户自然语言示例：
- “这个实验为什么停在这里？”
- “设备返回了什么？最近一次位置确认是什么？”
- “这批样本经历了哪些节点和设备？”
- “今天有哪些资源冲突？”
- “这个流程依赖哪些设备能力和物料？”

每条回答：
- 结论；
- 数据来源与时间；
- 已确认事实；
- 推断与未知；
- 下一步建议。

验收：构造设备离线、命令超时、物料位置不明、节点等待、重复事件等测试样本，核对回答不能把 UNKNOWN 说成成功。

## 5. G2：Capability API

先为现有业务 API 做受控封装，不大规模改造：
- Query Capabilities；
- Workflow Draft/Validate；
- Resource Preview；
- Execution Submit（后置）；
- Execution Pause/Resume/Cancel（高风险、需审批）；
- Material Trace / Location Query；
- Result Query。

每个 Capability 记录版本、Schema、风险、权限、幂等、超时、副作用和验证等级。

## 6. G3：Workflow Compiler

实施顺序：
1. 盘点现有 Workflow/Node JSON 和设备方法参数；
2. 建 DSL Schema 与版本兼容策略；
3. 将 DSL 编译到现有工作流模型；
4. 先做静态校验，再做资源校验；
5. 生成不可变 ExecutionPlan Snapshot；
6. 绑定 `PLAN_APPROVAL`；计划批准不等于 `START`，启动仍检查实时 readiness 和启动权限；
7. 由现有调度和执行引擎运行；
8. 将计划与实际偏差归档。

禁止用 LLM 生成任意 Python 并直接进入生产。若某个设备确实需要脚本，脚本应由经过验证的驱动/Capability 包装，固定版本、参数 Schema 和安全策略。

## 7. G4：虚拟团队

先做一个项目级团队：
- Coordinator
- Literature
- Protocol
- Resource
- Data/QC
- Reviewer

首版采用串行/有限并行 DAG，不开放 Agent 自由创建 Agent。项目管理员可以选择模板、工具权限和知识范围。

## 8. G5：执行监控与异常助手

Agent 可解释：
- 命令处于何种生命周期；
- 设备事件是否迟到/重复；
- 节点等待什么前置条件；
- 物料位置是否确认；
- 哪些恢复路径可用、各自风险是什么。

恢复动作由确定性策略与操作员审批完成。对机械臂、液体处理、温控、开盖、样本移动等风险不同的操作分别定义策略，不使用统一“重试三次”。

## 9. G6：选择一个实验建立 DBTL

候选标准：
- 实验流程已稳定且重复执行；
- 输入参数可控、输出指标明确；
- 有足够历史数据或可低成本采集；
- 样本/试剂批次/设备/方法可追溯；
- 实验质量由领域专家定义；
- 失败成本和生物安全风险可控。

优化方法先从 DoE、统计模型、贝叶斯优化和受约束搜索开始。每轮记录候选方案、选择理由、实验计划版本、实际偏差、结果、质量评价和下一轮决策。只有在数据量、漂移监控和 OOS 证据成熟后才评估强化学习/复杂序列模型。

## 10. 关键里程碑验收

- G0：核心领域对象实现矩阵；未知项有负责人和验证计划。
- G1：只读助手回答状态不越权、不幻觉；证据可点击回到系统。
- G2：工具权限、审计、幂等和错误分类通过测试。
- G3：同一计划可复现，计划变更重新校验并重新执行 `PLAN_APPROVAL`。
- G4：跨用户/项目隔离测试通过，Agent 失败可恢复。
- G5：设备故障注入、断网、重启、迟到事件和人工接管场景通过；高风险审计 Outbox 已接入，并通过“审计不可写时业务动作无副作用”的故障注入测试。
- G6：至少三轮或足够样本量的实验迭代，按领域标准独立评价；不以“模型给出更优参数”作为成功。

## 11. 团队组织建议

小团队可按能力分工，而非按 Agent 名称分工：
- Core/Control：领域状态、命令、设备、物料、调度和恢复。
- Platform/AI：Capability API、Agent Runtime、Workflow Compiler、知识权限。
- Science/Application：实验方法、数据质量、试点设计和科学验证。
- QA/Integration：模拟器、真实设备、故障注入、端到端验收。

一个人可以兼任多个角色，但每个里程碑必须有独立验收人。

## 12. 不应提前做的事情

- 先做全能 AI Scientist；
- 先做 Agent 商店；
- 先接几十个模型；
- 先上自动无人值守实验；
- 先做跨领域自动优化；
- 在没有证据时把模拟器完成率当作真实设备可靠性；
- 以大规模重构替代对现有实现的精准补齐。
