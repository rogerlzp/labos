## 2. G0-01：WorkflowRunGate 热修任务卡

### 2.1 原子准入必须明确为数据库可见的协调机制

当前若仅写“共享事务锁、数据库约束或等价机制”，实施自由度过大，无法形成可重复验收的并发正确性保证。任务卡应要求实施者明确并记录：

1. **锁定粒度/唯一键**：例如 `tenant_id + workflow_id`；若实际领域模型还需 project 或其他隔离维度，必须由源码和业务约束证明，不能随意扩大或缩小锁范围。
2. **无 active Run 时的竞态**：说明两个请求同时查询不到 active Run 时，如何保证只有一个请求创建成功。
3. **协调机制选择**：明确采用数据库唯一约束、advisory lock、guard row、可串行化事务或其他数据库级机制，并说明选择依据。不能只依赖单 JVM 的 `synchronized` / 内存锁，因为 Web 与 Executor 可能处于不同线程、进程或实例。
4. **事务边界**：明确锁获取、active Run 检查、Run 创建、初始状态写入和事务提交的顺序及原子范围。
5. **异常路径**：事务回滚、锁等待超时、死锁、连接中断、提交结果未知时的行为；不得在状态未知时放行。
6. **并行范围**：不同 workflow 是否可并行；同一 workflow 的并发策略如何受配置控制。

### 2.2 并发策略必须与默认互斥语义一致

任务卡需消除“已知 active Run 必须拒绝”与“`LABOS_WORKFLOW_CONCURRENT_RUN=allow` 可开启并发”之间的表述冲突。建议明确：

- 默认策略：同一 tenant/workflow 同时最多一个 active Run。
- 显式并发：只有在配置被授权启用、配置状态可确定且相关审计要求满足时才允许；应说明这是有意改变默认业务语义的受控开关。
- 无论并发开关如何配置，数据库不可用、状态词表未知、状态查询结果不确定、事务协调失败等 UNKNOWN/ERROR 情况都必须拒绝。
- 已知 active Run 与未知状态/基础设施故障必须使用不同 reason code，不能混为一类。

### 2.3 续跑排除自身必须做归属校验

对用于续跑的 `excludeRunId`（或等价参数）增加负向验收：

- 当前合法续跑 Run，且 tenant/workflow 归属均匹配：允许按设计排除自身。
- 其他 workflow 的 Run ID：拒绝，不得排除。
- 其他 tenant 的 Run ID：拒绝，不得排除。
- 不存在的 Run ID：拒绝。
- Run 存在但不属于当前请求/当前续跑上下文：拒绝。
- 调用者不能通过任意构造 `excludeRunId` 绕过同 workflow 互斥。

### 2.4 三态契约与错误原因

三态对调用方保持稳定是合理的；但非法参数直接归入 `DENY_UNKNOWN` 会损失错误语义。建议保留三态决策，同时增加稳定的 `reasonCode`，例如：

- `INVALID_INPUT`
- `STATUS_CONFIGURATION_UNKNOWN`
- `DATABASE_UNAVAILABLE`
- `ACTIVE_RUN_EXISTS`
- `CONCURRENCY_POLICY_DISABLED`

也可复用项目既有非法请求错误类型。重点是：拒绝结果必须可诊断、可审计，且 UNKNOWN/ERROR 绝不映射为 ALLOW。

### 2.5 G0-01 必须补充的验收

保留原任务卡已有 15 项，不以新增项目替换或删减。另补充：

1. 两个独立进程/实例、两个独立数据库连接同时争抢同一 workflow，验证最多一个请求成功准入。
2. 不同 workflow 的请求可按设计并行，不发生无谓全局串行。
3. 续跑排除自身时验证 Run 的 tenant/workflow 归属。
4. 跨 tenant、跨 workflow、不存在及不属于当前请求的 Run ID 均不能被排除。
5. 准入成功后事务回滚，另一个请求能够在锁释放后正常取得准入。
6. 锁等待超时、死锁、连接中断和提交结果不确定时均不放行。
7. 并发配置开启时，已知 active 冲突与未知故障分别按各自语义处理。
8. 明确证明 Web `run` 与 `ExperimentExecutor` 消费的是同一准入决策/同一协调边界，而不是各自实现一套互不约束的检查。

## 3. G0-07：RecipeCompiler 能力映射修复任务卡

### 3.1 全仓清查所有编译调用点

不能只验证目前已发现的两个路径。任务卡应要求对全仓所有 `RecipeCompiler.compile` 和 `RecipeCompiler.compileAll` 调用点进行清查，并在交付记录中列出：

- 调用文件、方法及调用场景；
- 是否应透传 capability mapping；
- 采用两参数旧回退语义还是三参数显式能力映射；
- 对应测试或为何不需要额外测试。

至少覆盖：

- 批量预览：`capabilityByResource` 三参数透传；
- 执行前展开：`resourceCap` 三参数透传；
- 普通两参数调用：保持既有回退语义；
- 其他调用点：逐一判定，不能遗漏。

### 3.2 增加能识别优先级错误的判别性测试

仅验证“预览结果等于执行结果”不足以证明两条路径都正确；如果两条路径都错误地回退到 protocol capability，测试仍可能通过。

建议至少增加两组明确夹具：

**用例 A：验证 bound 优先于 protocol**

- explicit capability：不存在；
- bound capability：`BOUND_CAP`；
- protocol capability：`PROTOCOL_CAP`；
- 直接 `compile`、`compileAll`、执行前展开均必须得到 `BOUND_CAP`。

**用例 B：验证 explicit 优先级最高**

- explicit capability：`EXPLICIT_CAP`；
- bound capability：`BOUND_CAP`；
- protocol capability：`PROTOCOL_CAP`；
- 最终结果必须为 `EXPLICIT_CAP`。

测试应断言具体 capability 值，而不是只断言非空或两条路径相等。

### 3.3 预览/执行一致性必须绑定同一输入快照

只有输入版本相同，才要求预览与执行前展开结果一致。至少固定或记录：

- Workflow 版本；
- NodeDef/节点定义版本；
- 设备绑定版本；
- Recipe 模板版本；
- Capability 映射版本。

验收规则：

- 同一不可变输入快照：预览与执行前展开必须一致。
- 输入版本变化：必须重新计算，不得复用旧版本缓存或旧预览结果。
- 测试应覆盖 capability mapping 变化后的缓存失效/重新计算行为（若该路径存在缓存）。

### 3.4 G0-07 必须补充的验收

保留原任务卡已有 12 项，不以新增项目替换或删减。另补充：

1. 全仓 `compile` / `compileAll` 调用点清单与分类。
2. 上述 bound/protocol 判别性用例。
3. 上述 explicit/bound/protocol 优先级用例。
4. 同一不可变输入快照下，预览、直接编译、执行前展开的结果一致。
5. Capability 映射版本变化后，不复用旧版本结果。

## 4. 实施与验收顺序

1. **先修订任务卡**：将本评审第 2、3 节的约束和验收补入对应任务卡；保留原有验收项。
2. **G0-01 独立实施**：单独修复分支/提交；先补并发与归属测试，再实现数据库级协调机制；完成后独立验收。
3. **G0-07 独立实施**：单独修复分支/提交；先完成全仓调用点清查和判别性测试，再修改透传路径；完成后独立验收。
4. **更新 G0 增量审计**：记录实际代码 HEAD、文件/方法、测试命令与结果、证据路径、适用范围及遗留 UNKNOWN。
5. **最后复核 G1 准入门槛**：不能因为任务卡已修订或 PR 文档已合并，就宣称 G0 风险已经关闭。

两个修复单元分别验收，不互相等待，也不占用 G1/AI Workbench 的交付额度。外部/其他 AI 的交叉评审意见到达后，应逐条记录“采纳/不采纳/待验证”及理由；不必为等待意见而停止准备工作。
