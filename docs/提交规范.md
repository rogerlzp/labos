# 提交规范

> 本文件规定 commit message 怎么写、什么时候提交、什么不该提交。
> 目的：三个月后回看 `git log`，能知道**为什么改**，而不只是**改了什么**。

---

## 一、提交时机

| 应当提交 | 不应提交 |
|---|---|
| 一个功能完整可用（哪怕只有一部分） | 编译不过的中间状态 |
| 一个 bug 修好并验证过 | 只改了一半的改动 |
| 一次文档更新（成体系的） | 临时调试代码（`System.err.println` 等） |
| 一次重构完成 | 与本轮任务无关的格式化 |

**一次提交一件事**。如果 commit message 需要用 "和" 连接两个不相关的改动，就该拆成两个。

---

## 二、Commit Message 格式

```
<类型>(<范围>): <简短描述>

<正文：为什么这么改>

<影响/副作用/已知问题>
```

### 2.1 类型（必填）

| 类型 | 用于 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat(experiment): 实验执行器支持循环展开` |
| `fix` | 修 bug | `fix(plate): putPlate 事务回滚导致层位未写入` |
| `docs` | 文档 | `docs: 补评审规范与提交规范` |
| `refactor` | 重构（不改行为） | `refactor(driver): 两套 ID 改用值类型` |
| `perf` | 性能 | `perf(scheduler): 候选池查询加索引` |
| `test` | 测试 | `test(plate): 补位置抢占的并发用例` |
| `chore` | 构建/依赖/杂项 | `chore: 升级 postgresql 驱动` |

### 2.2 范围（建议填）

用模块名，和 `docs/技术架构与模块地图.md` 的包结构对应：

`api` / `workflow` / `engine` / `driver` / `recovery` / `alert` / `plate` / `gateway` / `webapp` / `docs`

### 2.3 简短描述（必填）

- **不超过 50 字**
- **写做了什么**，不是"修改了一些东西"
- 用中文（本项目团队语言）
- 不以句号结尾

**反例**：

```
fix: 修复了一些问题            ← 什么问题？
feat: 更新代码                 ← 更新了什么？
fix: bug fix                   ← 完全没信息
```

**正例**：

```
fix(plate): putPlate 事务回滚导致层位未写入
feat(experiment): 实验执行器支持循环展开
docs: 补评审规范与提交规范
```

## 三、正文（重要改动必填）

**正文回答"为什么"，不是"改了什么"**（改了什么看 diff 就行）。

### 3.1 修 bug 时的正文模板

```
<现象>：一句话描述用户/运维看到的现象
<根因>：技术层面的原因
<修法>：怎么改的，以及为什么这么改而不是别的方案
<验证>：怎么确认改对了
```

**示例**（本项目真实案例）：

```
fix(plate): putPlate 事务回滚导致层位未写入

现象：日志显示 [PLATE] Deposit1 -> pos=504495，但 position_state 里没有这行。

根因：同一事务里 markPlatePosition 写 plate 表时列名不匹配
（代码 write plate_id/current_pos/current_run，表里只有 barcode/location_id），
SQL 失败让整个事务作废，commit() 抛异常后 rollback，position_state 的更新一起没了。
异常被 catch (SQLException ignore) 吃掉，所以日志里看不到 SQL 原文。

修法：把 plate 表写入移出主事务（commit 后用独立连接），
失败只记 WARN 不影响位置锁。列名改成实际结构。

验证：执行 239 后层位写入 I4495/PL-xxx，has_plate 与层位一致。
```

### 3.2 新功能时的正文模板

```
<做什么>：一句话
<关键设计>：为什么这么设计，有没有别的选择
<已知限制>：没做什么，什么时候做
```

## 四、必须写进 commit 的内容

### 4.1 已知问题必须写

如果这次提交**引入或遗留了问题**，必须在 commit message 里写明。

**反例**：

```
feat(experiment): 实验执行器完成
```

**实际状态**：循环展开能用，但变量替换只支持顶层、分叉还没做。

**正例**：

```
feat(experiment): 实验执行器支持变量替换与循环展开

已知限制：
- 只支持顶层 ${var}，不支持表达式 ${a}+${b}
- 分叉网关未实现，多条出边只走第一条
- 循环上限 20 次（防展开爆炸）
```

**为什么**：三个月后有人说"文档说支持表达式求值啊"，
`git log` 能立刻回答"当时就写了没做"。

### 4.2 破坏性变更必须写

```
BREAKING CHANGE: /api/workflows 的 limit 上限从无限制改为 500
```

### 4.3 验证命令与结果

重要改动（尤其是修 bug）要写**怎么验证的**：

```
验证：
- 单测 51 个全绿
- 工艺 993/993（SimulatedBus 走图，非真设备）
- 执行 239，层位写入 I4495，has_plate 一致
```

## 五、不应提交的内容

| 内容 | 处理 |
|---|---|
| `System.err.println` 调试日志（临时的） | 删掉或改成正式日志 |
| 编译产物（`out/`、`*.class`） | `.gitignore` |
| 大文件（日志、图片 > 1MB） | 放独立存储 |
| 本地配置（IP、密码硬编码） | 环境变量或配置模板 |
| `TODO` 占位代码 | 要么实现，要么在 commit 里说明 |

**本项目的 `.gitignore` 应包含**：

```
out/
*.class
node_modules/
dist/
*.log
```

## 六、本项目的特殊约定

### 6.1 文档与代码同批提交

改了行为就要改文档，**同一个 commit**。

```
feat(plate): 位置锁支持搬运双锁
docs: 板位级占用设计补第 5 节（双锁与死锁避免）
```

**不要**先提交代码，文档"下次补"——大概率永远不补。

### 6.2 修 bug 要记录"踩坑过程"

本项目的 bug 记录习惯（见 `docs/开发日志.md`）：

```
### Bug（标题）

**现象**：...
**根因**：...
**修法**：...
**教训**：...
```

**为什么记录踩坑过程**：同一个坑会反复踩（本项目"以为改了其实没改"踩了 5 次），
记录了才能识别出模式。

### 6.3 评审后的提交要引用评审编号

```
fix(plate): 修 putPlate 事务回滚

评审意见：20261101-01 / C1
处置：见 docs/评审记录/20261101-01-grok.md
```

## 七、检查清单

提交前自查：

- [ ] 一次提交一件事
- [ ] 类型和范围填了
- [ ] 简短描述说清了"做了什么"
- [ ] 正文说清了"为什么"（重要改动）
- [ ] 已知问题写了
- [ ] 验证方式写了
- [ ] 文档同步更新了
- [ ] 没有调试代码和编译产物
- [ ] `git status` 里没有意外文件

---

## 八、反例集（本项目的真实教训）

| 反例 | 问题 |
|---|---|
| `feat: 板子流动` | 不知道改了什么（是动画？是设备分配？） |
| `fix: 修 bug` | 什么 bug |
| `docs: 更新文档` | 哪份、为什么 |
| 把 `putPlate` 不落库说成"已修复"却没写怎么验证的 | 无法确认是否真修好 |
| 只提交代码不提交文档 | 造成代码与文档不一致 |

**判断标准**：三个月后的你（或新同事）看这条 message，能不能知道**为什么这么改**。
