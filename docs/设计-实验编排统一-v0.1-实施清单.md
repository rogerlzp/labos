# 实验编排统一 · 实施清单 v0.1

> 配套设计：[`docs/设计-实验编排统一-v0.1-草稿.md`](docs/设计-实验编排统一-v0.1-草稿.md)
>  
> 目的：把 `M9.5` 的 `S1/S2/S3` 从“方向”拆成可执行任务，便于排期、分工与二次评审。
>  
> 口径：**先做最小闭环，再做能力扩展**。所有阶段都必须满足 `ROADMAP.md` 中 `M9.5` 的专属准入门槛。

---

## 0. 总原则

1. **先消除误导，再增加能力**
   - `S1` 的目标不是“功能更强”，而是先把“画布与执行不一致”这个误导去掉。
2. **先收口写路径，再扩展数据模型**
   - 继续保留 `graph/process` 双写入口，会把后面所有阶段都做成不稳定状态。
3. **先明确执行语义，再开放 UI 能力**
   - 不能执行的语义不要先在画布里放出来。
4. **先定义回滚与验证，再进入实现**
   - `S1/S2/S3` 都必须有失败回滚和验收脚本，不接受“先改出来再补测”。

---

## 1. 阶段总览

| 阶段 | 目标 | 不做什么 | 产出 |
|---|---|---|---|
| **S1 统一写入口** | 让画布保存真正影响执行，且 `graph/process` 不再分裂 | 不做实验内真并发，不做批次 | 单入口保存、图编译落库、表只读、回归测试 |
| **S2 偏序执行** | 让实验内多个流程可以表达先后依赖 | 默认**不承诺墙钟并发**；除非同步带三层资源 + 等待图 | `experiment_process_edge`、偏序派发、汇聚等待、UI 状态更新 |
| **S3 分批执行** | 让一个实验支持“逻辑批次 + 多次尝试” | 不做复杂的批间清场自动建模 | `experiment_batch` / `experiment_batch_run`、失败只重跑该批、批次视图 |

## 2. S1 · 统一写入口

### 2.1 目标

把“画布只存图形、执行仍看表”的状态收掉，形成唯一可信写路径：

- 画布保存 = 更新布局 + 编译 `process`
- 详情页流程表 = 只读镜像
- 任一子步骤失败 = 整体回滚

### 2.2 后端任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 新增 `saveExperimentGraphAndCompile(...)` | 作为唯一写入口，替代分散的 `saveExperimentGraph` / 直改 `experiment_process` |
| 2 | 图校验器 | 校验必填字段、孤立节点、非法边、循环（至少 S1 不能保存“不可线性化”的图） |
| 3 | 图编译器 | `graph -> experiment_process`，先只支持线性/可线性化场景 |
| 4 | 单事务写入 | 同事务完成 `experiment_graph` / `experiment_process` / `experiment.version` |
| 5 | 关闭现有写入口 | 详情页流程表改只读；现有 API 若被调，返回明确错误而非静默接受 |

### 2.3 前端任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 画布保存接新接口 | 不再分别保存图与流程表 |
| 2 | 详情页流程表改只读 | 保留“由画布生成”的说明与跳转按钮 |
| 3 | 禁用 `fork/parallel` | 直到 S2 语义准备好前，不允许新画出不可执行拓扑 |
| 4 | 保存失败定位 | 把“哪一个节点/边不合法”直接高亮出来 |

### 2.4 回归测试

| 类别 | 用例 |
|---|---|
| 单测 | 图校验器：空图、孤立节点、非法回边、未绑定流程 |
| 单测 | 图编译器：3 节点线性图 -> `seq=1..N` |
| 集成 | 保存成功后 `experiment_graph` 与 `experiment_process` 同时更新 |
| 集成 | 编译失败时，两边都不落库 |
| 集成 | 模拟 `process` 写失败时，`graph` 也回滚 |
| UI/e2e | 画布改顺序后，详情页流程表顺序同步变化 |

### 2.5 风险点

- **最大风险**：现有入口未关写，形成“看似统一、实际双写”
- **次级风险**：校验器太宽松，把 S2/S3 的语义提前漏进 S1

### 2.6 出门条件

1. 现有流程表不再允许编辑
2. 画布保存后的执行顺序与详情页流程表一致
3. 任一保存失败不会留下半成品

## 3. S2 · 偏序执行

### 3.1 目标

让实验内流程之间不再只有 `seq` 线性顺序，而是支持：

- 前驱/后继依赖
- 汇聚等待
- 同层优先级

**当前默认目标是“偏序”而不是“真并发”**。

### 3.2 先做哪个版本

| 版本 | 语义 | 推荐度 |
|---|---|---|
| **S2-A 保守版** | 只支持偏序；调度器一次只推进当前可执行集合中的一个，**不承诺墙钟重叠** | **推荐先做** |
| S2-B 完整版 | 真并发派发；同时上三层资源 + 等待图 | 只有在愿意同步承担资源治理工作时再做 |

> 当前建议：**先做 S2-A**。  
> 原因：它能先兑现“依赖关系表达正确”，而不把“多资源死锁治理”塞进同一批变更里。

### 3.3 后端任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 新增 `experiment_process_edge` | 表达偏序，而不是只靠 `seq` |
| 2 | 派发器改造 | 从“按 `seq` 逐个跑”改成“选入度为 0 的可执行节点” |
| 3 | 汇聚等待 | 所有前驱完成才放行后继 |
| 4 | `priority` 生效 | 同层可执行时，按优先级决策谁先跑 |
| 5 | 失败策略固定 | 先继续维持“任一失败停整单” |

### 3.4 若做 S2-B，需要额外加上的任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 三层资源建模接入实验层 | 位置 / port / 机械臂 |
| 2 | 等待图 + 拒环 | 防止多分支形成跨层等待环 |
| 3 | 并发派发限流 | 防止一下子把可执行分支全部推到争锁路径上 |
| 4 | 可观测性 | 等待图快照、死锁拒绝日志、并发分支状态 |

### 3.5 回归测试

| 类别 | 用例 |
|---|---|
| 单测 | A→B→C 偏序正确 |
| 单测 | A,B 同层时 `priority` 生效 |
| 单测 | A/B 完成后 C 才能运行（join） |
| 集成 | 一条失败时整单停止 |
| 集成 | 偏序图在详情页/执行历史中可还原 |
| 扩展（仅 S2-B） | 三分支 A→B→C→A 死锁构造被拒绝，而不是卡死 |

### 3.6 风险点

- **最大风险**：把“偏序”偷换成“并发”，但又没同步做资源治理
- **第二风险**：`priority` 被误解成抢占运行中，而不是“同层谁先派发”

### 3.7 出门条件

1. 至少 1 个非线性实验可正确表达前驱/汇聚
2. 文档明确写死当前是 `S2-A` 还是 `S2-B`
3. 若是 `S2-A`，UI 和文档都不得暗示“已支持真并发”

## 4. S3 · 分批执行

### 4.1 目标

支持“一个实验拆成多个逻辑批次”，并且：

- 每批可单独执行
- 每批失败可单独重跑
- 重跑历史可追踪

### 4.2 数据模型

| 表 | 语义 |
|---|---|
| `experiment_batch` | 逻辑批次（第几批、当前状态、样品集合/范围） |
| `experiment_batch_run` | 该批次的每一次实际执行 |

### 4.3 后端任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 批次切分器 | 根据 `batch_split` 和样品集合生成逻辑批次 |
| 2 | 建批逻辑 | 首次运行前写 `experiment_batch` |
| 3 | 执行归档 | 每次执行写 `experiment_batch_run`，递增 `attempt_no` |
| 4 | 汇总状态机 | 批次状态与实验总状态聚合 |
| 5 | 重跑入口 | 支持“只重跑失败批次” |

### 4.4 前端任务

| # | 任务 | 说明 |
|---|---|---|
| 1 | 实验详情页新增批次视图 | 看得到每批状态、尝试次数、对应 run |
| 2 | 失败批次重跑按钮 | 只对失败批开放 |
| 3 | 批次历史展开 | 同一批多次尝试可查看 |

### 4.5 回归测试

| 类别 | 用例 |
|---|---|
| 单测 | 96 样品 / `batch_split=24` -> 4 批 |
| 集成 | 第 2 批失败后，只重跑第 2 批，历史 attempt 保留 |
| 集成 | 成功批次不受失败批重跑影响 |
| UI/e2e | 详情页能看到批次、尝试次数、关联 run |

### 4.6 风险点

- **最大风险**：把“逻辑批次”做成“当前 run 指针”，导致一重跑就覆盖历史
- **第二风险**：批次与样品映射不稳定，重跑时样品集合漂移

### 4.7 出门条件

1. 任一批失败后，可只重跑该批
2. 至少保留两次尝试历史
3. 实验总状态与批次状态聚合规则写清并被测试覆盖

---

## 5. 建议排期顺序

| 顺序 | 先做什么 | 原因 |
|---|---|---|
| 1 | **S1** | 先把“画布不生效”收掉，消除继续设计的假前提 |
| 2 | **S2-A** | 先兑现“偏序正确”，不把资源死锁治理一起打包 |
| 3 | **S3** | 在执行语义稳定后再加批次，避免边跑边改状态模型 |
| 4 | S2-B（可选） | 只有在确实需要真并发时，再把三层资源 + 等待图并入 |

---

## 6. 进入开发前还要明确的 3 个决定

1. **S2 到底选 A 还是 B**
   - 这是资源治理成本和交付速度的分水岭
2. **批次样品映射怎么落库**
   - 是 `experiment_sample.batch_no`，还是单独批次样品映射表
3. **线性实验是否允许表内轻量调序**
   - 如果允许，要小心重新引入“表改了、图没改”的第二入口

---

## 7. 一句话结论

`M9.5` 现在已经不再是“方向草案”，而是“**可以排任务的设计方案**”。  
但真正进入开发时，建议按 **S1 → S2-A → S3** 的顺序推进，把“真并发 + 等待图”保留为单独升级，而不是第一版就一起上。

## 8. S3 · 开工决定与接口契约（2026-11-03 执行方提议）

> 目的：把 §6 的未决项拍死，让后端/前端能并行开工。这些是**执行方决定**；
> 评审方若不同意，可在实施中推翻（成本：改列/改 JSON 字段）。

### 8.1 决定

| # | 决定 | 理由 |
|---|---|---|
| D1 | 批次开关：`experiment.batch_split int NULL` = 每批样品数；`NULL` = 不分批（**默认行为完全不变**） | 加一列即可开关，零存量数据迁移 |
| D2 | 样品映射：**首次执行时**按 `experiment_sample.sample_id` 升序，每 `batch_split` 个切一批；把该批 `[{sampleId, barcode}]` 快照进 `experiment_batch.samples jsonb`；此后重跑只用快照 | 快照 = 重跑时样品集合不漂移（§4.6 第二风险），不必另建映射表 |
| D3 | 运行语义：分批实验一次「执行实验」= 按 `batch_no` 串行跑**所有未成功批次**；每批一个 `experiment_run` + 一条 `experiment_batch_run(attempt_no)`；某批失败**继续**后续批；遇暂停扣留则停在**批边界**、不启动下一批 | 复用现有 `ExperimentExecutor`（每批一次 run），不新建执行器；草稿 §5：任一失败=实验失败，但其余批可以继续 |
| D4 | 重跑：`POST /api/experiments/{id}/batches/{batchNo}/run` 只跑该批，新 `attempt_no`，历史尝试保留；只允许非 `completed` 批 | 对应 §4.1 / §4.3 #5 / §4.4 #2 |
| D5 | 变量注入：每批 run 的 variables 追加 `batchNo`（数字串）、`batchSamples`（样品条码逗号串）；**不覆盖用户显式传入的同名变量** | 不破坏现有变量语义；流程参数可用 ${batchNo} |
| D6 | 状态聚合：有 `running/queued` 批 → experiment=running；有 `paused` 批且无 running → paused；全部 `completed` → finished；无 running/paused 且任一 `failed/aborted` → failed；`batch_split` 为 NULL 走默认逻辑 | §4.7 #3 要求规则写清并被测试覆盖 |
| D7 | 批次之间**串行**（1.0 不并行）；批边界检查 `RuntimeHold` / `stop_requested` | 设备只有一套；S2-A 只承诺偏序 |

### 8.2 数据模型

| 表/列 | 定义 |
|---|---|
| `experiment.batch_split int NULL` | 每批样品数；NULL=不分批 |
| `experiment_batch` | id bigserial PK, tenant_id, experiment_id FK, batch_no int, sample_count int, samples jsonb, status varchar, created_at, updated_at；UNIQUE(tenant_id, experiment_id, batch_no) |
| `experiment_batch_run` | id bigserial PK, tenant_id, batch_id FK ON DELETE CASCADE, experiment_run_id FK, attempt_no int, status varchar, started_at, finished_at, error text；UNIQUE(batch_id, attempt_no) |

status 取值沿用现有词表：`pending / queued / running / paused / completed / failed / aborted`。
DDL 必须同时更新分片（`pg_rebuild/schema/20_kernel.sql` 或 `96_schema_fix.sql`）与合并产物
`pg_rebuild/schema/90_all_in_one.sql`（跑 `pg_rebuild/merge.sh`），并过 `scripts/check-schema-sync.sh`。

### 8.3 接口契约

**GET `/api/experiments/{id}/batches`**

~~~json
{
  "experimentId": 813,
  "batchSplit": 24,
  "items": [{
    "id": 1, "batchNo": 1, "sampleCount": 24,
    "samples": [{"sampleId": 101, "barcode": "BC001"}],
    "status": "failed",
    "attemptCount": 2,
    "currentRunId": 41,
    "runs": [
      {"batchRunId": 3, "runId": 40, "attemptNo": 1, "status": "failed",
       "startedAt": "2026-11-03 19:00:00", "finishedAt": "2026-11-03 19:02:00", "error": "..."},
      {"batchRunId": 5, "runId": 41, "attemptNo": 2, "status": "failed",
       "startedAt": "2026-11-03 19:05:00", "finishedAt": "2026-11-03 19:07:00", "error": "..."}
    ]
  }],
  "summary": {"total": 4, "pending": 1, "running": 0, "completed": 2, "failed": 1}
}
~~~

`batchSplit` 为 null 时 `items` 为空数组（前端据此隐藏批次卡片）。

**POST `/api/experiments/{id}/batches/{batchNo}/run`**

请求体可选 `{"vars": {"k": "v"}}`（与现有实验执行一致）。响应：

~~~json
{"experimentId": 813, "batchNo": 2, "runId": 42, "batchRunId": 5, "attemptNo": 3,
 "status": "completed", "doneSteps": 12, "totalSteps": 12, "error": null}
~~~

已成功的批 / 不存在的批 → 400 `{"error": "..."}`。

**POST `/api/experiments/{id}/run`（现有接口，分批时扩展）**

保留现有字段（`status / doneSteps / totalSteps / error`）；分批时追加：

~~~json
{"batchSplit": 24,
 "batches": [{"batchNo": 1, "runId": 41, "batchRunId": 2, "attemptNo": 1,
              "status": "completed", "doneSteps": 12, "totalSteps": 12}]}
~~~

`status` 为聚合后的实验状态（D6）。

### 8.4 验收（= §4.7，逐条可验）

1. 任一批失败后，可只重跑该批 —— DB 集成测试 + UI 按钮
2. 至少保留两次尝试历史 —— `experiment_batch_run.attempt_no` + 历史接口
3. 状态聚合规则写清并被测试覆盖 —— D6 + 单测
4. `batch_split` 为 NULL 时行为与今天完全一致 —— 回归断言

## 10. S3.1 · 续跑回写 / 配置入口 / 重跑并发（2026-11-03 执行方）

> 对应 §9 残余 1/2/3。决定由执行方提议，评审可推翻。

### 10.1 要解决什么

1. **批内 run 经恢复/停止后批次层不更新，且会覆盖聚合状态**：@@ExperimentScheduler.executeOne@@
   恢复 queued run 时走 @@exec.run(exp, null, runId)@@ 默认重载 → @@syncExperimentStatus=true@@；
   批次 run 恢复后跑完，实验表被**单条 run 的状态**覆盖（例：某批 paused 恢复后跑完，
   实验直接 finished，其他批还 pending）。@@RunControl.stop/resume@@ 同理。
2. **并发重跑同一批**可能撞 @@UNIQUE(batch_id, attempt_no)@@。
3. **@@batch_split@@ 只有 DB 入口**，页面上配不了（DoD「功能可演示」不满足）。

### 10.2 决定

| # | 决定 |
|---|---|
| D8 | **统一回写点** @@BatchOrchestrator.onRunStatusChanged(long runId)@@：非批次 run 直接返回 false（默认路径零变化）；批次 run 更新 attempt 行（status/error/finished_at）+ 批次汇总状态 + 实验聚合状态（D6）。**幂等**。 |
| D9 | **调度器恢复**：@@ExperimentScheduler.executeOne@@ 先探测 run 是否属于批次 → 批次 run 用 @@syncExperimentStatus=false@@ 跑，结束后调 D8；异常兜底标记 failed 后同样调 D8。 |
| D10 | **运行控制**：@@RunControl.stop/resume@@ 对批次 run **跳过**单条 run 的 @@syncExperimentStatus@@，改走 D8（resume 后 status=queued；stop 非运行态落 aborted 后 status=aborted）。停止请求置位分支（running）不改状态，不需要回写。 |
| D11 | **配置入口**：@@PUT /api/experiments/{id}/batch-split@@，body @@{"batchSplit": N}@@ 或 @@{"batchSplit": null}@@；N 必须 >0（0 视为 null=清空）；**已有批次行时拒绝修改**（D2 快照固化），400 说明"需先清批次数据"。前端操作行加「分批设置」弹窗。 |
| D12 | **重跑并发**：@@BatchOrchestrator.executeBatch@@ 在同一事务里 @@SELECT id FROM experiment_batch WHERE id=? FOR UPDATE@@ 后再算 @@attempt_no@@ 并 INSERT，串行化同批重跑。 |
| D13 | **纯逻辑补充**：@@BatchPlanner.normalizeSplit(Integer)@@（null/<=0→null，其余原值），供 D11 校验，可单测。 |

## 11. S3.2 · 分批异步（调度器按批派发，2026-11-03 执行方）

### 11.1 接口契约（POST /api/experiments/{id}/run?async=1）

- `batch_split` 为空：**原样**走 `scheduler.submit`（一次整单 run），响应不变
  `{"experimentRunId", "status":"queued", "async":true}`。
- 分批实验：建/取"下一未成功批次"的 queued run 并重新入队，四种 200 响应：
  - **CREATED / EXISTING**（可入队）：`{"experimentId","experimentRunId","batchNo","batchRunId","attemptNo","status":"queued","async":true}`
  - **HELD**（批边界有现场扣留）：`{"experimentId","experimentRunId":null,"held":true,"status":"paused","batchNo","holdReason"}`
  - **NO_MORE**（无更多批）：`{"experimentId","experimentRunId":null,"status":实验聚合状态}`
  - 重复 POST：已有未结束批次 run 时命中 EXISTING（不新建，200 返回实际状态）。
- 同步 `POST /run` 的 `runAll/runBatch` 语义未变（回归断言全绿）。

### 11.2 续队语义（与 D3 对齐）

一条批次 run 跑完（D8 回写完成、岛锁释放之后）→ 若实际状态不是 `aborted/paused` 且**无覆盖扣留**，
建下一批 run 重新入队：
- **失败继续**：本批 failed/completed 都继续下一批；失败批不原地重试；
- **aborted 停止**：人工停止后剩余批保持 pending，不自动重跑；
- **扣留停在批边界**：候选批标 paused、不建 attempt（解除后需人工再发起，见 §11.3）；
- D5 批变量（batchNo/batchSamples）由调度器按批次快照反查注入。
