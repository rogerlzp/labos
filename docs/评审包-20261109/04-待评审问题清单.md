# 04 待评审问题清单（请逐条给结论）

> 每条请给：**结论（通过 / 有风险 / 不通过）+ 严重级 P0/P1/P2 + 文件:行号 + 触发场景 + 复现/证据 + 建议**。
> P0 = 可能导致误放行物理动作/丢状态/数据不一致；P1 = 崩溃/并发/边界下不正确或不可运维；P2 = 可维护性/UX/测试缺口。

## Q1（P0）隔离解除会不会误清其它 Hold？

- `StartupRecovery.resolveQuarantine` 解 Hold 调用 `RuntimeHold.clearTx(EXPERIMENT, expId, ...)`，这是**清该实验所有 kind**。
- 背景：本批已把唯一索引改成 `(tenant,scope,scope_id,kind)`，允许同实验同时存在 manual/fault/human 多个 Hold。
- 请判断：隔离解除时是否会把人工暂停/故障 Hold 一并清掉？是否应改为只清隔离对应的 kind（如 HUMAN）？
- 相关：`StartupRecovery.java` resolveQuarantine、`RuntimeHold.java` clearTx/clearKind。

## Q2（P0）PauseCoordinator 事务内有跨连接读，是否存在竞态？

- `resumeExperimentRun` / `pauseExperimentRun` 先 `db.open()` 开事务，再 `new RunControl(...).info(...)`（**新连接读**），再回到事务连接写。
- 请判断：读到的 RunInfo（island/experiment/status）可能在读与写之间被并发改；是否需要把 info 也收进同一事务，或加 SELECT FOR UPDATE？
- 相关：`PauseCoordinator.java` pauseExperimentRun/resumeExperimentRun/stopExperimentRun。

## Q3（P0）commit 后动作失败的一致性

- E-5/E-6 的批次聚合、`scheduler.resumeRun` 是在 commit 后执行，失败只打日志。
- 请判断：若 commit 成功后进程崩溃/入队失败，experiment_run 已在 queued，是否会被启动 rehydrate 拾起？workflow 级 run 的异步续跑是否会被漏掉？
- 相关：`PauseCoordinator.java`、`ExperimentScheduler.rehydrateQueued`、`WorkflowService.resumeAsync`。

## Q4（P1）命令账本 key 与事务边界

- 稳定 key 末尾 opSeq 是执行器**内存自增**（`DriverStepExecutor.ledgerOpSeq`）；重启后计数归零。
- `CommandLedger.begin` 用单事务写 ledger+outbox；`finish` 用另一连接写 ACKED/FAILED；失败返回 fail-closed。
- 请判断：重启/重放时 key 是否可能碰撞或误判重复？ledger 与 outbox 的原子性是否足够？`finish` 失败导致 DISPATCH_STARTED 残留是否只能等 10 分钟对账？
- 相关：`CommandLedger.java`、`DriverStepExecutor.java`、`CommandOutbox.java`。

## Q5（P1）Outbox 的“派发”语义是否被高估？

- `CommandOutbox.dispatchPending` 只把 PENDING 标 DELIVERED，没有真实外部消费者；replay API 只重置状态。
- 请判断：当前是否应称为“Outbox 记录/内部派发”而不是“外部事件投递完成”？文档中是否有过度表述（`docs/architecture/COMMAND_LEDGER_P07_FIRST_SLICE_20261108.md`）？
- 相关：`CommandOutbox.java`、`RunApi.java` `/api/command-outbox`。

## Q6（P1）Handoff 门禁是否可能被绕过或误 block？

- `HandoffGate.workcellChain` 只从 workflow_node.resource_id 推导 Workcell；显式 `experiment_workcell` 绑定不参与 chain；若 workflow 无资源节点则 chain 为空 → 直接放行。
- 三条件：confirmed + intervention_record_id + manual_window_id；manual_window 是 run_id=0 的合成记录。
- 请判断：跨 Workcell 实验若资源节点为空/资源树推导失败，是否等于绕过 Handoff 门禁？是否应改为「显式绑定>1 时必须能推导或直接阻断」？
- 相关：`HandoffGate.java`、`ExperimentApi.java` confirm、`QueryService.confirmHandoff`。

## Q7（P1）逐候选派发的性能与语义

- `ExperimentScheduler.dispatch` 对每个候选调用 `RuntimeHold.coveringForExperiment`（内含递归 CTE + active hold 查询），每 2s tick。
- `autoContinueHeldBatches` 也逐候选；`BatchDbSelfTest` 语义已从“任何 Hold 全停”改为“只停被覆盖实验”。
- 请判断：队列大/库慢时是否有性能风险？UNKNOWN 的 fail-closed 是否覆盖所有候选路径？改变全局闸门语义是否符合 ADR-FAULT-SCOPE-001/002？
- 相关：`ExperimentScheduler.java`、`RuntimeHold.java`、`ExperimentWorkcellScope.java`。

## Q8（P1）多 Hold 索引迁移与 clear 语义

- 99m 先 `DROP INDEX uk_runtime_hold_active` 再按 kind 重建；若现网已有重复 (tenant,scope,scope_id) 多行，重建是否安全？迁移失败如何回滚？
- `clear()` 仍清全部 kind，调用点有哪些可能误清？`clearKind` 是否应成为默认？
- 相关：`pg_rebuild/schema/99m_runtime_hold_multi.sql`、`RuntimeHold.java`、`RunControl.resume`。

## Q9（P1）schema 迁移与 90_all_in_one 的可靠性

- 本批把 `ALTER TYPE run_status ADD VALUE ...`、`CREATE INDEX`、`ALTER TABLE ADD COLUMN` 直接拼进 `90_all_in_one.sql`。
- 请判断：在已有生产库上重复执行 90 是否幂等？`ALTER TYPE ADD VALUE` 在事务中的限制？是否有版本化迁移记录？评审是否需要求先给迁移测试？
- 相关：`pg_rebuild/schema/merge.sh`、`90_all_in_one.sql`、`99l/99m/99p/99q/99r`。

## Q10（P1）启动隔离的漏判/误判

- `quarantineUncertainRuns` 只隔离「command_ledger 有 UNKNOWN/DISPATCH_STARTED」的 run；没有账本但设备仍在动（例如非 protect 路径、旧历史 run）是否可能被普通 settle 清锁？
- `settle` 排除条件只排除有 ledger 记录的 run；`settleOrphanExperimentRuns` 是否也需要同类门禁？
- 相关：`StartupRecovery.java`、`ApiServer` 启动顺序、`CommandLedger.reconcileOnStartup`。

## Q11（P1）TransferTransaction 与物理确认的真实性

- 事务只在 `LABOS_TRANSFER_PLAN=1` 且 protect 分支创建；非 protect 路径没有事务。
- `plate` 参数取 `ctx.params().get("plate")`，缺失时 null；confirm 只落证据，不更新 `plate.position_status`/`position_state`。
- 请判断：这是否足以支撑“回包≠位置确认”的闭环？是否会让 REPORTED 永久悬挂、或者下一步在未确认位置继续？
- 相关：`DriverStepExecutor.executeWithPlan`、`TransferTransaction.java`、`PauseManager.resume` 强门禁。

## Q12（P1）新 API 的鉴权/权限

- 新增：`POST /api/runs/{id}/quarantine/release`、`POST /api/experiments/{id}/handoffs/confirm`、`POST /api/transfers/{id}/confirm`、`POST /api/command-outbox/{id}/replay`、`POST /api/plate-position-evidence`。
- 当前只取登录会话，未见角色/权限矩阵校验。请判断：viewer 是否可能调用这些写接口？是否需要 `requireWrite`/角色检查？
- 相关：`RunApi.java`、`ExperimentApi.java`、`ApiServer` 路由与 auth。

## Q13（P2）前端新页面的可靠性

- `/manual-windows`、`/quarantined`、`/handoffs` 只有 Playwright 冒烟，没有 e2e 断言集；错误处理/空态/只读保护靠 useReadOnly 与 message。
- 请判断：是否有明显 UX/一致性缺口（如确认后刷新、错误提示、网络失败、分页）？
- 相关：`webapp/src/pages/ManualWindows.tsx`、`Quarantine.tsx`、`Handoffs.tsx`。

## Q14（P2）测试与门禁可信度

- `test-all` 在 API 运行时偶发 1~3 条失败，已定位为并发写库；停 API 后 1240/0。
- e2e 都是模拟器/演示库；`verify-dispatch-isolation`/`verify-experiment-fault-closure` 不在 `ci-gate.sh` 中。
- 请判断：验收证据是否足够？是否需要把两个故障注入脚本纳入门禁（会增加运行时间）？
- 相关：`scripts/test-all.sh`、`ci-gate.sh`、`02-验证记录.md`。
