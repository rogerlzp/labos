## 8. 关键决策与踩坑

### 8.1 4.16 既有 flaky —— 根因（证据链）

- **现象**：4.16 报 `run 没变 paused（completed；…)`，节点状态混编 `bypassed`/`completed`，**未出现 paused**。
- **根因**：等待「设备步已完成」的判据 `dev_cmd_count >= 1` 是**「设备步已完成」**的信号（`run_command` 的 step 行**结束后才 INSERT**），与收尾 `WorkflowService.settleRun` 里的 `if (isRunPaused(runId)) return;` 构成**竞态**，窗口仅 ~50ms。
  ⇒ 当暂停请求恰好落在设备步**收尾之后、节点边界判定之前**的窗口里，`settleRun` 会先把它收成 completed。
- **佐证**：内核日志在失败轮 **0 条** `[暂停] 收到暂停请求，在节点边界停下，待执行节点：…`。
- **定级**：**既有 flaky**（改动前就会偶发），**与 S-03 / PauseCoordinator 无关**。
- **处置（用户裁决）**：**「重做为真边界暂停」** —— 图结构新增第二个设备任务节点 `DEV2`；触发点从 `dev_cmd_count(ids["DEV"])>=1` 改为「设备执行中」判据（`device_state.status='running'` 且 `current_run_id` 指向本次 run）；断言同步改写（`pause_node_key=DEV2`、`DEV` completed、`DEV2` pending→恢复重跑、`DEV` 不重跑），并核对内核日志出现 `[暂停] 收到暂停请求，在节点边界停下，待执行节点：<DEV2>`。**尚未实现**（见 `02` §1）。

### 8.2 段 2.7 `outvar` 环境阻塞（前序已修）

- **现象**：2.7 的 `outvar` 用例失败。
- **根因**：设备 `200214` 的模拟器以 `--profile generic --rand-delay 30000:300000` 运行，`GetPosition + Home` 耗时超过 `Ctx.run(wait=420)` 的 420 秒预算。
- **修复**：改 `--profile robot --rand-delay 30000:45000:42`（固定种子）⇒ 2.7 = 55/0。
- **登记**：`REMEDIATION_STATUS.md` G-05。

### 8.3 为什么 V1 要拆「安全子集」

- **完整 P-06/P-03 依赖**：Hold + Intent + Event/Outbox **单事务** + `PAUSING` 异步收敛 —— 这会**改变 API 时序语义**（从「立即 paused」变成「返回 accepted」），进而让既有 4.17 判据变红。
- **纪律**（`REMEDIATION_STATUS.md:146`）：**禁止同一 PR 同时改实现与验收判据**。故先切验收口径（PR-S04-A），再上行为（PR-S04-B）。
- **V1 的价值**：在**不动 API 时序**的前提下，先把「统一编排 + 幂等 + fail-closed + 运维可见」落地，可独立验收。
