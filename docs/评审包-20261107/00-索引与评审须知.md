## 4. 术语表（评审前必读）

| 术语 | 含义（本项目内） |
|---|---|
| **两套 run 模型** | ① `run`（**Workflow 级**，由 `PauseManager` 管理）；② `experiment_run`（**Experiment 级**，由 `RunControl`/`RuntimeHold` 管理）。两表 ID 空间独立，**并存且各自写库**，本项目历史遗留（S-01 登记）。 |
| **Fact / Intent / Projection / Gate** | 状态机分层：**事实**（设备/命令真实状态）、**意图**（`PAUSE_REQUESTED`/`PAUSING` 等控制意图）、**投影**（`experiment.status` 这类对外可见状态）、**门禁**（谁被允许继续派发）。L-02 只加「意图」的表达列。 |
| **UNKNOWN（fail-closed）** | 「读不到就当作最坏情况」。安全闸门查询读库失败时**必须阻断**而不是放行。改前 5 处调用点读库异常会静默放行（fail-open）。 |
| **RuntimeHold** | 现场级扣留（实验 / 岛 / 站点粒度）。存在生效 Hold 时调度器停派发所有新实验。 |
| **`control_state`** | L-02 新增列（`NONE`/`PAUSE_REQUESTED`/`PAUSING`/`RESUMING`），表达「暂停控制过程」，与表达「生命周期」的 `status` 分离（ADR-PAUSE-008）。 |
| **`pause_request`** | V1-5 新增表，按 `(tenant_id, request_id)` 唯一，作 `PauseCoordinator` 的**幂等键**（ADR-PAUSE-009）。 |
| **E-1 ~ E-6** | `PauseCoordinator` 收敛的 6 个写入入口（workflow 暂停/恢复/批量忽略/单条忽略、experiment 暂停/恢复/停止），见 V1 设计 §1。 |
| **G-1 ~ G-4** | 需要 fail-closed 的 4 个安全闸门调用点，见 V1 设计 §2。 |
| **V1 / V2** | 同一工作项的两期。**V1 = 「不加新事务模型也能独立验收的安全子集」**；**V2 = 完整项**（Hold + Intent + Event/Outbox **单事务**、`PAUSING` 异步收敛、API 返回 `request accepted`）。本轮只做 V1。 |
| **S-03 单写者不变量** | `experiment.status` 只允许 `ExperimentStateProjector` 写；用源码扫描（`ExperimentStateProjectorSelfTest`）把这条**结构约束变成会红的测试**。 |

## 5. 建议评审重点（按风险排序）

1. **V1 适配层是否真的「行为不变」**：`PauseCoordinator` 把 6 个入口统一后，外部 JSON 响应必须**逐字段等价**。
   请重点核对 `RunApi.pauseRunJson/resumeRunJson/dismiss*/`、`ExperimentApi.pause/resume/stop` 的响应结构与改前是否一致；
   特别是 `resumeExperimentRun` 在「现场扣留仍在」时返回的 `requeued=false` + UNKNOWN 语义。
2. **`pause_request` 幂等的边界**：只在带 `X-Request-Id` 时去重；无该头必须与改前**逐字段一致**（一行都不写）。
   请核对 `PauseCoordinator.claim()/settle()/abandon()`：`ON CONFLICT DO NOTHING` + 回放 + 「目标不存在 ⇒ abandon 允许真重跑」这条链是否闭合。
3. **fail-closed 的**覆盖面 **：本轮把 5 处调用点改成「UNKNOWN 视为阻断」。
   请扫一遍：**还有没有第 6 处**闸门查询漏改（尤其告警、心跳、批次编排、`autoContinueHeldBatches` 之外的路径）？
4. **S-03 单写者不变量是否够强**：`ExperimentStateProjectorSelfTest` 用正则 `UPDATE\s+experiment\b[^;]{0,300}?SET\s+status` 扫描。
   请评估：这个正则的**误伤 / 漏网**（大小写、`UPDATE  experiment` 多空格、动态拼接 SQL、`String.format` 拼接、别名写在 `SET` 之前等）；以及「5 条」这个**计数断言**是否会在合理重构时假红。
5. **`control_state` 与 `status` 的分离是否自洽**：L-02 只加表达列，但 `control_state` 暂无写入方（行为切换属 PR-S04-B）。
   请评估：现在就让 schema/词表/前端都支持 `control_state`，会不会造成「列存在但永远 `NONE`」的**误导性可观测**？词表 `control` scope 是否该先隐藏？
6. **4.16 的既有 flaky 与 S-03 无关性**：`dev_cmd_count>=1`（「设备步已完成」）与收尾 `settleRun` 的 `if (isRunPaused(runId)) return;` 存在 ~50ms 竞态窗口。
   请独立判断：这是**真竞态**还是**断言写脆了**？重写为「真边界暂停」是否真的能去掉 flaky（而不是把窗口挪走）？
7. **门禁阈值「只许涨」机制**：`ci-gate.sh` 段 0 扫 git 历史。本轮 `MIN_PURE 651→673`。
   请评估：把测试数当阈值，会不会诱导「为凑数写弱断言」？如何约束断言质量？
8. **文档自洽**：`REMEDIATION_STATUS.md` 若干 `IN_PR` 证据行仍写 `GATE_EXIT=0 / MIN_PURE=664`（旧一次运行的证据）。
   请核对：`REMEDIATION_STATUS.md` / `ADR_INDEX.md` / `LABOS_PAUSE_COORDINATOR_V1_DESIGN_20261107.md` §7.1 / 本包 `01` 的**数字是否互相对齐**。

## 6. 评审问题清单（请评审 AI 逐条回答）

1. **适配层零行为漂移**：`PauseCoordinator` 统一 6 入口后，有没有**任何**外部可观测差异（响应字段、HTTP 状态码、错误码、时序）？请给出「对齐前 vs 对齐后」的逐字段对照结论。
2. **幂等键设计**：用**独立表 + 唯一索引**（ADR-PAUSE-009）而非「在目标行上加列」，这个选择在「一次请求跨多个目标」时是否仍然正确？`request_id` 由客户端还是服务端生成更稳？
3. **fail-closed 完备性**：`RuntimeHold` 的 `activeChecked()`（抛异常）/ `active()`（吞异常，仅供展示）/ `coverageFor` / `coverageForWorkflow` / `siteState` 的**语义边界**是否清晰到「不会有人误用展示用的 `active()` 去做闸门判定」？请在代码里找出所有使用点并判定。
4. **S-03 不变量**：源码扫描正则能覆盖哪些形态？请列出**至少 3 种能绕过它**的写法（若有），并建议如何加固（AST / 编译器插件 / 运行时拦截）。
5. **`control_state` 现在是「死列」吗**：在 PR-S04-B 之前它永远是 `NONE`。这期间：schema、`StatusVocabulary` 的 `control` scope、前端词表、`GET /api/holds` 的表达，是否存在**误导**风险？应该先隐藏还是保留？
6. **`status varchar(32)` 扩容**：改前有无**依赖 `varchar(16)` 长度**的逻辑（截断、比较、索引长度、前端宽度）？扩容是否会影响任何索引/约束/物化视图？
