# 仿真与验证指南

> **仿真不是另一个运行模式，只是换一个 `StepExecutor` / `DeviceDriver` 实现。**
> 这条设计让"验证"和"生产"共用同一套执行逻辑，区别只在末端。

---

## 一、三层仿真

| 层 | 类 | 替换什么 | 验证什么 |
|---|---|---|---|
| **① 虚拟总线** | `engine/SimulatedBus` | `StepExecutor` | 流程逻辑、状态机、重试、转人工 |
| **② 虚拟驱动** | `driver/VirtualDriver` | `DeviceDriver` | 设备分配、能力匹配、命令结构 |
| **③ Mock 服务** | `driver/tcp/MockDriverServer` | 真实厂商驱动 | **协议**：分帧、字段名、超时、原文 |

**越往下越接近真实**：

```
SimulatedBus      内存里返回结果，零网络
VirtualDriver     走驱动接口，有 DriverResult 结构
MockDriverServer  真开 TCP 端口，收发 JSON，验证 #!LABSEP!# 分帧
真驱动            .NET Sidecar → 设备
```

## 二、怎么跑

### 2.1 跑全量工艺（最快看结果）

```bash
cd labos-kernel

# 全部流程在虚拟总线上走一遍
LABOS_DB_NAME=<库名> java -cp "out:lib/postgresql-42.7.3.jar" \
     com.labos.kernel.workflow.RealWorkflowRunner --all
```

**输出**：

```
流程总数 xxx，耗时 xxxx ms
全部完成     xxx 个  100.0%
结构异常       0 个（无环、无孤立节点）
节点完成   xxxxx 个  100.0%
转人工         0 个
```

**看什么**：

| 指标 | 含义 | 不正常时说明 |
|---|---|---|
| **结构异常** | 图有环、有孤立节点 | 图解析有问题 |
| **转人工** | 节点找不到能力/设备 | 设备分配或能力字典缺 |
| **完成率** | 走完的比例 | 有节点失败 |

### 2.2 单流程按图执行

```bash
LABOS_DB_NAME=<库名> java -cp "out:lib/postgresql-42.7.3.jar" \
     com.labos.kernel.workflow.RealWorkflowRunner --all --verbose
```

**加 `--verbose`** 会打印每个节点的分配结果。

### 2.3 单命令探针（验证协议）

**不落库、不走流程**，只发一条命令：

```bash
POST /api/shadow/probe?resourceId=200214&method=Home
```

返回：

```json
{
  "ok": true,
  "elapsedMs": 62,
  "contract": {
    "messageId": true,
    "messageType": true,
    "method": true,
    "methodStatus": true
  },
  "rawResponse": "{\"message_id\":\"...\",\"method_status\":2,...}"
}
```

**`contract` 四项全 true 才算协议通**：

| 字段 | 缺了会怎样 |
|---|---|
| `messageId` | 分不清是不是这次的响应 |
| `messageType` | 可能是心跳不是执行结果 |
| `method` | 可能张冠李戴 |
| `methodStatus` | 不知道成功还是失败 |

**上现场第一步就用这个**——改完 `appsettings.json` 先 probe，别急着跑流程。

### 2.4 整流程影子（看"会发什么"）

```bash
POST /api/workflows/{id}/shadow-run
```

**不发命令**，只把每一步"打算发什么"记下来。

**看什么**：
- 每个节点落到哪台设备
- 方法名对不对（`Deposit1` 还是 `Deposit1Ex`）
- 参数替换后的值
- 顺序对不对（并行、异或走了哪条）

### 2.5 画布逐步执行（落库，可在界面看）

```bash
POST /api/experiments/flow-run
  ?name=试跑
  &steps=200214:Transfer::source=ID1775;target=ID1183
  &vars=plate=PL-001
```

**这个会真发命令**（走驱动），并把每步写进 `run` / `run_node` / `run_command`。

## 三、注入故障（验证重试与恢复）

`SimulatedBus` 支持按设备注入故障：

```java
SimulatedBus bus = new SimulatedBus()
    .fail(200214, "TRANSFER", "EC-05-1007", 2)       // 前 2 次超时
    .fail(200171, "INCUBATE", "EC-05-0001", Integer.MAX_VALUE);  // 永久故障
```

**参数**：

| 参数 | 说明 |
|---|---|
| `resourceId` | 哪台设备 |
| `capability` | 哪个能力 |
| `errorCode` | 返回什么错误码 |
| `times` | 失败几次（`MAX_VALUE` = 永远坏） |
| `scope` | 恢复范围（`COMMAND` / `PLATE` / `RUN`） |

**验证什么**：

```
故障注入 → 状态机按 recovery_policy 决策 →
  重试成功     → 记录 attempt=2
  重试耗尽     → 转人工
  不可恢复     → 中止并告警
```

**这是"错误可决策"的验证方式**——不是看日志，是看状态机怎么走。

## 四、怎么看到结果

### 4.1 命令行

| 命令 | 输出 |
|---|---|
| `RealWorkflowRunner --all` | 完成率、结构异常、转人工数 |
| `RecoverySelfTest` | 崩溃恢复的 17 个断言 |
| `EngineSelfTest` | 状态机的 14 个断言 |
| `AlertSelfTest` | 告警的 12 个断言 |
| `GraphRunnerTest` | 图执行的 5 个断言 |

### 4.2 接口

| 接口 | 看什么 |
|---|---|
| `GET /api/runs` | 执行列表 |
| `GET /api/runs/{id}` | 单次执行的节点树 |
| `GET /api/experiments/{id}/runs` | 实验执行历史 |
| `GET /api/scheduler/status` | 岛锁、队列、stalled |
| `GET /api/positions?islandId=` | 哪些层位有板 |

### 4.3 数据库（最可靠）

```sql
-- 一条执行发了哪些命令
SELECT command_seq, method, device_id, status, error_code,
       payload, device_raw_response
FROM run_command WHERE run_id = ? ORDER BY command_seq;

-- 每个节点的状态
SELECT name, status, resource_id FROM run_node WHERE run_id = ? ORDER BY id;

-- 整体结论
SELECT status, error_code, output FROM run WHERE id = ?;
```

**`durationMs` 全是 0 或个位数** → 走的是虚拟总线，没真在等设备。

### 4.4 界面

| 页面 | 看什么 |
|---|---|
| **执行监控** | 节点树、每步状态 |
| **实验编排 → 执行历史** | 每次实验的状态/进度/耗时 |
| **岛屿视图 → 设备详情** | 层位占用（绿/粉/橙） |
| **告警** | 漏板、超时、失败 |

## 五、仿真的能力边界

**能验证的**：

| 项 | 能 |
|---|---|
| 图解析（并行、异或、回环） | ✅ |
| 节点排序与依赖 | ✅ |
| 设备分配（按能力、轮转、空设备优先） | ✅ |
| 变量替换 | ✅ |
| 重试与转人工 | ✅ |
| 板位占用与释放 | ✅ |
| 数据库落库 | ✅ |
| 协议字段（用 Mock 服务） | ✅ |

**不能验证的**：

| 项 | 为什么 |
|---|---|
| **真实耗时** | 虚拟总线立即返回，看 Verilog 时长是假的 |
| **物理约束** | 机械臂会不会撞、夹具能不能夹住 |
| **设备真实行为** | 驱动 DLL 的边界情况 |
| **并发争用** | 多设备同时动作时的干扰 |

**所以**：仿真通过 = **逻辑正确**，不等于**能上生产**。
上线还要走 `docs/测试与上线策略.md` 的 L2-L5。
