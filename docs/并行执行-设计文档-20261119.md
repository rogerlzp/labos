## 1. 背景与目标

### 1.1 现状

```
第 1 层  ExperimentScheduler   多实验并行（资源级互斥、队列、优先级）
第 2 层  BatchOrchestrator     批次【串行】（runAll 是同步 for 循环）
第 3 层  WorkflowRunGate       按 (租户, 流程) 互斥
第 4 层  GraphRunner           单线程 ready.poll()，并行网关只"多条路都走"
```

实际能并行的：两个不同实验、用不同设备。
不能并行的：同实验的多批次、同流程多实例、单流程内的并行分支。

### 1.2 目标

把"批次串行 + 流程级互斥"改为**资源驱动的并行**：设备/点位/机械臂不冲突就并行，冲突就排队。

同时保证三件事在任何并行度下都是确定的：

- 不串板（事件归属正确）
- 不重复执行（命令幂等）
- 不卡死（暂停、恢复、断线都有确定处置）

### 1.3 不新建调度器

现有 `ExperimentScheduler` 已有资源级互斥、优先级、并行度热加载、独立线程池。要做的是**让批次进这个队列**，不是再造一个。

## 2. 部署与范围

### D-01 单实例部署（硬前提）

**决策**：按**单实例**设计和验证。所有关于锁、状态写入、执行体的正确性论证都以此为前提。

**依据**：`device_state.current_run_id` 是 run 粒度，DB 层拦不住"同 run 的两个分支"；真正互斥的是 JVM 分片锁（`DeviceLock:81-95`）。

**推论**：上多实例时这套正确性**全部失效**，需重新设计执行体身份与锁的落点。

### D-02 不做多实例 fencing / epoch

**决策**：不评审、不列入遗留、不列为待决策。提出即视为超范围。

**但保留一个区分**（必须，否则会误删）：

| 名称 | 解决什么 | 单实例是否需要 |
|---|---|---|
| `hold_epoch`（**设备占用代次**） | 旧完成事件误清新租约 | **需要** |
| `owner_epoch`（执行体 fencing） | 旧实例写回状态 | 不需要 |

### D-03 同步入口不改成异步

**决策**：`E-01`（同步单流程）、`E-03`（同步跑实验）保持同步阻塞。

**依据**：响应里有 `totalSteps` / `doneSteps` / `batches`，改成异步这些字段就空了——**那是改契约，不是重构**。

### D-04 不做"人工拆分命令"

**决策**：不引入 `logical_command` 子表，不引入 `parent_operation_id`。

**业务模型定义**（不是从重试规则推导）：

> 一个 `logical_operation` = **一次独立的物理设备动作**，身份由 `operation_id` 持久化，对应一个 `command_id`。
> 若业务需要多个独立物理动作，应**分别建立多个 `logical_operation`**。

**触发条件**：如果某天某设备要求"一次意图两步完成"，会以**现场事故**形式出现——那时才引入子表，不预先建。

## 3. 事件与命令

### 3.1 事件只有两类

| 类型 | 例子 | 带 `commandId` | 归属 |
|---|---|---|---|
| **命令关联型** | `waiting_interaction`、`extract_done`、进度上报 | **必须** | 归到该命令所属 run / node / branch |
| **系统型** | 心跳、自检告警、人工开门 | 没有 | **不归属任何 run**，只更新设备状态 |

**不存在第三类。** "设备自发事件"中的绝大多数（到交换点、提取完成）本身就是某条命令的结果。

### B-01 归属只认 `commandId`，无弱匹配

匹配只有三种结果：

| 条件 | 结果 |
|---|---|
| `waiter.expect_command_id` 非空，且等于 `event.command_id` | 匹配 |
| 两者都有但不相等 | **不匹配** |
| 任一为空 | **不匹配** |

**强制写法**：

```sql
AND w.expect_command_id IS NOT NULL
AND e.command_id IS NOT NULL
AND w.expect_command_id = e.command_id
```

**禁止** `AND (w.expect_command_id IS NULL OR ...)` ——那是给"没声明归属的 waiter"开后门。

### B-02 匹配不上就 `UNATTRIBUTED`，不推进

**决策**：事件没有 `commandId`、或与所有 waiter 都对不上 ⇒ 进 `UNATTRIBUTED` + 告警，**不推进任何流程、不释放任何资源**。

**且歧义记录必须独立持久化**：不能随归属事务回滚一起消失，否则下次同样歧义、永远进不了人工队列。

**技术手段**：匹配域 `(tenant, device_code, event_type)` 上取事务级 advisory lock，同时覆盖"waiter 创建"与"事件认领"；歧义时只提交事件状态、不回滚。

### B-03 不回显 `commandId` 的设备：只能走同步命令型流程

**先纠正一个早期错误**：

```
❌ 旧依据：A 释放后 B 持有，A 的迟到事件会被判给 B ⇒ 推进错误流程
✅ 实际：  无 commandId 的事件匹配不到任何 waiter ⇒ 全部 UNATTRIBUTED
```

**后果不是"推错"，是"推不动"**，而且含义更硬：

> 设备不回显 `commandId` ⇒ 它的事件永远进 `UNATTRIBUTED` ⇒ **任何依赖 `__awaitEvent` 的流程在这台设备上根本跑不起来**。

**硬要求**（规范层面）：

> 侧车**必须**为自发事件回填触发它的 `commandId`。无法回填的设备，**不得进入含 `__awaitEvent` 的流程**。

**独占串行的真实作用**：只是调度降级（同一时刻一个 run 用设备），**不提供任何事件归属能力**。

### C-01 `commandId` = 一次逻辑操作的唯一标识，重试复用

| 场景 | `commandId` |
|---|---|
| 网络重发 / 断线重连 / resume | **不变** |
| 人工重跑 / 循环下一轮 / 换批次 | **变** |

**依据**：`commandId` 是设备去重键，粒度必须是"设备认为的一次执行"。重试换 id = 让设备当成新命令 = 重复动作。

**推论**：`uk_logical_operation_cmd` **单列唯一即可**，不需按设备档位放宽。

### C-02 身份来源：`operation_id` 是权威，禁止拼接

**决策**：`operation_id` 是持久化权威身份；`command_id` 与之**一一映射**。不得从 `branch`/`step`/`process` 临时拼接后当权威身份。

**依据**：多处各自拼字符串，必然出现"同一操作两种 id"或"不同操作同一 id"。

### C-03 不支持去重的设备：id 稳定，禁止自动重试

**决策**：id 不换（换 id 问题更严重）；但这类设备断线后**只能 `queryStatus` + 人工确认**，不能自动重发。

### C-04 `exec` 不进 `commandId`

**现状缺陷**：`DriverStepExecutor:1474` 的 `-e{exec}`，resume 后 `execSeq` 从 0 重来 ⇒ id 变化。

**处置**：`exec` 只保留在日志与追踪里。

### C-05 `NOT_FOUND` 一律落 `UNKNOWN`，不重发

| 状态 | 处理 |
|---|---|
| `PENDING` | 确认没发出，可首次发送 |
| `ACKED` | 不重发，只等结果 |
| `NOT_FOUND` | `UNKNOWN`，人工 |
| `UNKNOWN` | 人工 |

**依据**：`NOT_FOUND` ≠ 设备没执行过（可能重启丢账本、查询接口不覆盖历史）。

### C-06 方法名统一 `method`

| 字段 | 处置 |
|---|---|
| `method` | 保留，三边已统一（`device_method.method` / 模拟器 / 侧车） |
| `funcName` | **不引入**，就是 `method` 的别名 |
| `processId`（事件表） | **删除** |
| `interaction_step` | 保留，但**只服务 L5 交互守卫，不参与事件归属** |

## 4. 设备与物理态

### D-05 三层状态分开

| 层 | 谁拥有 | 一致性 |
|---|---|---|
| **程序态** | LabOS（`run.status` / `node.status` / `command.state`） | 强一致（同库同事务） |
| **设备态** | 设备软件（在线、心跳、回包） | 最终一致（靠推断） |
| **物理态** | 现场（板在哪、夹爪夹住没有） | **只能对账，没有事务** |

**铁律**：**程序态可以回滚，物理态不能。** 把 run 标成 `failed` 不会让移过的液回去。

### D-06 物理事实 P0–P4 分级

| 级别 | 来源 | 能否推进 |
|---|---|---|
| P0 | 设备确认 + 独立传感器交叉验证 | 能 |
| P1 | 设备主动确认 | 能，标 `DEVICE_CONFIRMED` |
| P2 | 人工确认 | 能，标 `MANUAL_VERIFIED` |
| P3 | 时序推断 | **不能** |
| P4 | 无信息 | **不能** |

**当前现实**：现场只有扫码，无第二证据 ⇒ **P0 实际为空集，最高可达 P1**。文档不得用 P0 做承诺。

### D-07 事实源缺失 fail-open，查询故障 fail-closed

| 场景 | 判定 | 处理 |
|---|---|---|
| 设备未配置状态采集能力 | 事实源缺失 | **fail-open** + SKIP 审计 + 不可并行标记 |
| 已配置，返回 `idle` | 状态明确 | 放行 |
| 已配置，返回 `busy` | 状态明确 | 释放锁，等待重查 |
| 已配置，返回 `unknown` / 数据过期 | 状态不确定 | **fail-closed** |
| 已配置，但查询超时 / 连接失败 / 接口异常 | **查询故障** | **fail-closed** |
| 配置项本身不存在 | 事实源缺失 | 按第一行处理 |

**原则**：

> **"没有配置这项能力"可以跳过；"本来应该有能力，但现在拿不到结果"不能当作没有配置。**

**依据**：`StirrerDispenserGuard:88-99` 记录了 2026-11-15 的事故——配对缺失一律拒绝 ⇒ 表 0 行 ⇒ **平台每一条设备命令都被拒 ⇒ 全平台停摆**。

### D-08 设备忙：先查状态，不直接下发

```
① 抢设备锁
② 查设备状态
   ├─ idle  → 下发
   ├─ busy  → 释放锁，等待，回 ①
   └─ 查不到 → 按 D-07 处理
③ 超过等待上限 → EC-DEVICE-BUSY-TIMEOUT，转人工
```

**依据**：设备忙时**不接受指令**（不是排队，是拒绝）。盲发会得到 busy 错误或更糟——被覆盖。

### D-09 等待上限可配置，等待期间不持锁

| 参数 | 取值 |
|---|---|
| 查询间隔 | 按设备/方法分档（秒级 / 分级 / 分钟级） |
| 总等待上限 | **可配置，默认 30 分钟**；现场有 60 分钟级工艺且设备紧张时调大 |
| 等待期间持锁 | **不持** |

**关键区分**（这是三份评审反复混的点）：

```
资源等待上限  = B 愿意为等 A 释放设备付多久  → 业务意愿
设备执行上限  = A 最多跑多久                → 方法超时（INCUBATE 30min / THERMOCYCLE 60min）
```

**B 超时只终止 B 的等待**：B 转人工或换设备，**A 的租约不受影响**。

### D-10 设备物理占用租约

**流程**：

```
1. 派发前原子申请租约（RESERVED）      ← 不是 ACK 之后
2. 记录 owner_command_id + hold_epoch
3. ACK 到达：RESERVED → ACCEPTED
4. 执行期间：EXECUTING
5. 完成事件：按 (device, command_id, hold_epoch) 条件清除
6. ACK 超时：→ UNKNOWN，不释放
7. 超过 TTL：进 QUARANTINED，不自动释放、不重新准入
8. 检查点必须放在 executeCommand 这个唯一收口
```

**表结构**：

```sql
device_physical_hold (
  tenant_id, device_id,
  state,                 -- RESERVED / ACCEPTED / EXECUTING / UNKNOWN / RELEASED
  owner_command_id,
  hold_epoch,            -- 设备占用代次，每次新建 +1，持久化且严格单调
  established_at, expires_at, released_at
)
```

**释放必须条件匹配**：

```sql
UPDATE device_physical_hold
   SET state = 'RELEASED', released_at = now()
 WHERE tenant_id = ? AND device_id = ?
   AND owner_command_id = ? AND hold_epoch = ?
   AND state IN ('ACCEPTED','EXECUTING','UNKNOWN');
```

**三条硬约束**：

| 约束 | 原因 |
|---|---|
| 重复完成事件幂等 | epoch 不匹配即无效，不能清掉新租约 |
| 迟到事件不得释放新租约 | 同上 |
| 设备账本**独立于** `device_event` 表 | 事件表不能代替租约事实源 |

**注意**：租约只保证"中控内部不再下发"，**不保证设备物理上没在执行别人的命令**。

## 5. 暂停与恢复

### E-01 实验暂停是"请求"，不是"命令"

**决策**：上层发 `Hold`，**不直接改 run 状态**；下层在动作边界自己转 `paused`。

**依据**：物理动作不能悬停——离心、孵育、机械臂承重都不能中途停。收到请求就标 `paused` 等于**伪造"已停在安全边界"**。

### E-02 暂停只在动作边界生效

**决策**：`GraphRunner` 每到一个节点边界查一次。**动作执行中不能暂停。**

**代价**：最长响应延迟 = 当前动作耗时（孵育就是 30 分钟）。急停是唯一例外。

### E-03 暂停协调状态：`experiment_run.control_state`，7 个值

**落点纠正**：不是 `run.control_state`，是 **`experiment_run.control_state`**（`99c_pause_control.sql:26`）。

**全集（7 个，两边原值域都不全）**：

| 值 | 含义 | 用户可见 |
|---|---|---|
| `NONE` | 无请求，正常运行 | — |
| `PAUSE_REQUESTED` | 已请求，未生效 | 已提交 |
| `PAUSING` | 正在停（部分确认） | 正在暂停（批 2/4 已确认） |
| `PAUSE_BLOCKED` | 有 run 无法确认 | 卡住 + **`blocking_run_id`** + 原因 |
| `PAUSED` | 全部确认，暂停完成 | 已暂停 |
| `RESUME_REQUESTED` | 已请求恢复 | 恢复已提交 |
| `RESUMING` | 正在恢复 | 恢复中 |

**状态迁移**：

```
NONE → PAUSE_REQUESTED → PAUSING → PAUSED
                              ↓
                        PAUSE_BLOCKED（需 blocking_run_id）
PAUSED → RESUME_REQUESTED → RESUMING → NONE
```

**与 `run` 的关系**：experiment 级是**聚合视图**，不独立双写——否则出现"实验 `PAUSING`、run `NONE`"。

### E-04 恢复前四项核对（节点级）

| 检查组 | 检查内容 | 失败处理 |
|---|---|---|
| 空间安全 | 板位、夹爪、机械臂、设备腔体 | 阻断 |
| 设备安全 | 设备是否真停、故障码 | 阻断 |
| **工艺准备** | 针是否堵、液面、耗材余量/有效性 | 阻断或人工确认 |
| 操作连续性 | 上一条命令是否完成、是否可能重复执行 | UNKNOWN 时阻断 |

**不是每个节点查全部**：加样查针/液面、转运查板位/夹爪、离心查转子/盖锁、孵育查温度/计时。

**证据必须带时效**：`observed_at` + `expires_at`，过期重查。

### E-05 `QUARANTINED` 恢复必须过物理安全门槛

**决策**：允许进恢复链 **≠** 允许直接恢复执行。

```
QUARANTINED
  → 人工发起恢复
RECOVERY_CHECKING
  ├─ 设备状态无法确认 → 回 QUARANTINED
  ├─ 物理位置无法确认 → 回 QUARANTINED
  ├─ 上一条命令 UNKNOWN → 人工处置
  └─ 四项核对通过（E-04）
RECOVERY_APPROVED
  → 恢复到安全执行边界
```

**硬约束**：

| 约束 | 原因 |
|---|---|
| `run.status` 可恢复 ≠ 设备物理安全 | 程序态与物理态不是一回事 |
| **不得自动释放旧租约** | 设备可能仍在执行 |
| 人工确认必须记录操作者、时间、证据、结果 | 事后可追责 |

**源码缺陷**：`resumeTx:512-520` 的判定链是 `pauseKindOfTx`（只认 `paused`）→ `isCrashRecoverable`（只认 `failed`）→ 都不满足就提前返回。**只在 SQL 加 `quarantined` 是死代码**——走不到那条 SQL。必须改服务层。

## 6. 资源与锁

### F-01 三类资源，生命周期各不相同

| 资源 | 存储 | 生命周期 |
|---|---|---|
| 设备执行锁 | `device_state` | **step 级**（`onStepStart` 到 `onStepDone`） |
| 物理位置锁 | `position_state` | **可跨 step** |
| 轨道分区锁 | 复用 `device_state` | **仅运动窗口** |

### F-02 锁类型由实现类声明

```java
public final class DeviceLock   { public static final ResourceType TYPE = DEVICE_STATE; }
public final class PositionLock { public static final ResourceType TYPE = POSITION; }
```

**依据**：调用点传类型要靠开发者记得；按 `resource_node.kind` 推导则表达不了"这次申请的是哪种锁语义"。由类声明则**编译期强制**。

### F-03 申请顺序：槽位集合必须是前缀

```
{} ⊂ {DEVICE} ⊂ {DEVICE, POSITION} ⊂ {DEVICE, POSITION, RAIL}
```

允许跳槽、允许同槽多次，只禁止"跳回前面"。

**依据**：真实顺序是 设备 → 位置 → 轨道；而轨道锁复用 `DeviceLock` 落在 `device_state`，若按"存储组"定 rank 会变成 1→2→1，**每次正常搬运都触发断言**。

**配套**：`RailZoneGuard` 先 `enter(RAIL)`，`DeviceLock` 内部不再按自己的 TYPE 断言。

### F-04 ThreadLocal 只做开发期断言

| 场景 | 能否表达 |
|---|---|
| 同线程顺序申请 | 能 |
| 批量申请/释放 | 能（只记最高 rank） |
| 跨 step 持有 | **不能** |
| 跨线程释放 | **不能** |
| Resume 换线程 | **不能** |

**决策**：跨 step / 跨线程一律靠**显式 `owner_token`**。

### F-05 多机械臂：当前模型表达不了（新增缺口）

**现状**：`RailZoneGuard:65-73` 按 **`pathKey`** 查 zones，**不区分哪台臂**。

| 场景 | 现在的行为 | 是否符合需求 |
|---|---|---|
| 1 台臂 | 正常 | ✅ |
| 2 台臂，走同一路径标识 | **查同一组 zone，互相锁住** | ❌ 本可并行 |
| 2 台臂，工作区重叠 | 路径相同时锁住 | ✅ 但靠巧合 |
| 2 台臂，工作区不重叠但路径标识相同 | 被误锁 | ❌ 损失并行 |

**两个缺口**：

1. **`pathKey` 不区分子臂** ⇒ 2 台臂走同一逻辑路径会拿同一组 zone
2. **没有"臂与臂碰撞"概念** ⇒ 两台臂工作空间重叠需要另一层互斥，现在没有

**上 2 台臂之前必须补**：

| 项 | 要做 |
|---|---|
| `pathKey` | 加入臂维度（`arm_id + path`），或在 `rail_zone` 配置里标注归属 |
| 碰撞区 | 工作空间重叠时，需 `arm_collision_zone` 或把重叠区建成共享 zone |
| 配置校验 | 启动时校验"两台臂的 zone 集合是否有交集"，有交集告警 |

**当前结论**：1 台臂时现状够用；**上第 2 台臂之前必须先补这一章**，否则要么误锁（降并行），要么漏锁（撞机）。

## 7. 并发与调度

### G-01 三个层次分开

| 层 | 现状 | 目标 |
|---|---|---|
| 批次 | 串行（`runAll` for 循环） | 资源允许则并行 |
| 流程实例 | 按 (租户, 流程) 互斥 | 互斥粒度降到批次 |
| 流程内分支 | 串行（`ready.poll()`） | **真并发** |

### G-02 并行收益从哪来（关键修正）

**早期结论"提取线并发收益≈0"是错的**——只算了臂的 112 秒，没算分支里的设备执行时间。

**正确的任务画像**：

| 任务 | 典型耗时 | 是否瓶颈 |
|---|---|---|
| 机械臂搬运 | **15 秒左右** | 短，可排队 |
| 设备执行（孵育/离心/提取） | **几分钟 ~ 30 分钟** | **长，是主时间** |

**分支结构**：

```
臂搬运(15s) → 设备执行(5min) → 臂搬运(15s)
                ↑
        这段时间臂是空闲的
```

⇒ **设备执行期间臂可以服务其他分支**，多个分支的设备执行可以**重叠**。

**这才是并行收益的来源。**

**收益取决于分支内容**：

| 分支内容 | 并发收益 |
|---|---|
| 含长设备任务（几分钟 ~ 30 分钟） | **显著**（设备执行重叠） |
| 只有臂操作（秒级），无长任务 | ≈ 0（臂串行） |

**收益上限**由"分支中可重叠的长任务时长"决定，**不是由臂速度决定**。

**多臂的影响**：

| 现场 | 收益 |
|---|---|
| 1 台臂 | 设备执行重叠的部分有收益；臂操作排队 |
| 2 台臂 | 设备执行 + 臂操作都能重叠，收益更高（前提是分支能分到不同臂，见 F-05） |

### G-03 并行度 = 瓶颈资源容量

```
并行度 = min over r ( floor(capacity_r / demand_r) )
```

当前硬瓶颈是机械臂，`WorkflowWebService:287` 记"可并行 run 数 ≈ 1.9" ⇒ **向下取整 = 1**。

但注意：这是**臂操作时段**的并发上限，不是整体并行度——设备执行期间臂空闲，可以服务别的分支。

### G-04 线程池与信号量是两条限制

| 机制 | 限制什么 | 目的 |
|---|---|---|
| 线程池 | **执行体数** | 防饥饿 |
| 资源信号量 | **同时占用的设备数** | 防"把排队从流程层挪到锁层" |

**嵌套并行组不额外计数**——内外层抢同一批设备，相乘会自我阻塞。

### G-05 并行度 2 的放行条件

不是"设计通过"，而是：

| 条件 | 状态 |
|---|---|

| 命令幂等（C-01~C-05）落地 | 待实施 |

## 8. 并行网关

### H-01 目标模型：真并发

```
SPLIT_PARALLEL
  ├── 分支 1 ──┐
  ├── 分支 2 ──┤  同时执行
  └── 分支 3 ──┘
JOIN_PARALLEL    汇合
```

**现状**：`GraphRunner:736` 单线程 `ready.poll()`，并行网关只"多条路都走"。

### H-02 实现路径：每分支一个 `GraphRunner` 实例

**决策**：外层主循环保持单线程，只加"遇到并行组就委托"的分支；每个分支一个 `GraphRunner` 实例，共享 `FlowExecutionContext`。

**前提**：分支子图**互不相交**（`split` 到 `join` 之间，除 `joinKey` 外不得被两条分支覆盖）。

### H-03 一个分支失败 → 全体停止发新指令

```
分支 A 失败
  → stopFlag = true
  → 其他分支在下一个节点边界不再进入新节点
  → 已下发的命令：不撤回、不强杀，等回包
  → 回包后不再推进
  → 全部退出后，组标记 FAILED
```

**依据**：物理动作不能撤回。

**配套**：停止等待有上限（`drain_timeout`），超限的进 `QUARANTINED`（E-05），**不自动释放、不重新准入**。

### H-04 变量流程级共享，但字段所有权要分清

```java
FlowExecutionContext {
    FlowVariableStore variables;   // 共享同一实例
    AtomicBoolean stopFlag;
}
```

**关键**：现有 `withVariables` 是 `new LinkedHashMap<>(vars)`，**会复制**——每分支一个 `GraphRunner` 再调它，**各自拿到副本，根本没共享**。必须改为注入共享引用。

**字段所有权**：

| 状态 | 所有权 | 说明 |
|---|---|---|
| `variables` | **流程级共享** | 同名写冲突编译期禁止 |
| `stopFlag` | **并行组级共享** | 任一分支失败触发 |
| `consumedValues` | **流程级**（随 variables） | 去重语义跟着变量走 |
| `eventCursors` | **流程级**，必须单调推进 | 不能被后完成的线程覆盖成较小值 |
| `visits` | **分支局部** | 循环轮次按分支独立 |
| `done` | **分支局部** | 否则 A 做过的节点让 B 跳过 |
| `progress.aborted` | **与 `stopFlag` 统一** | 避免两套停止信号 |

**禁止**"6 个字段全换 `ConcurrentHashMap`"这种笼统说法——容器换了不等于业务操作原子。

### H-05 禁止同一并行组内两分支写同一变量 key

**决策**：编译期检查，冲突即报错。

**依据**：变量是流程级共享的，同时写同一 key 没有"合并"这回事，只有"谁后写谁赢"——那是静默错误。

**分支不设超时**：用心跳（链路健康）+ 进展监测（状态是否变化）替代，两者都只告警不判失败。依据：孵育 30 分钟、离心 20 分钟都是正常业务。

### I-02 准入与插入必须同一事务

**决策**：只在 Controller 层加门禁不改事务边界，等于没修。

### I-03 全局锁序：`workflow 行 → 实验行 → run 表`

**已知反例**：`API-E05` 的 `createNextBatchAttempt` 已在事务内持实验行锁（`BatchOrchestrator:585`），若把准入内联会反序（实验行 → workflow 行）。

**处置**：**禁止 `API-E05` 同事务内联**，改事务外先准入。

**但这引出原子性问题**（见 K-01a）。

### I-04 提交与派发靠持久化待派发记录

**决策**：事务内写 `status='queued'` **并写待派发记录**，提交后唤醒；新增运行期僵尸扫描（阈值远小于 1 小时）。

**依据**：`StartupRecovery` 对 `queued` 是**超 1 小时**才收——那不叫兜底，叫挂一小时。

### K-01a 为什么是"唯一索引"而不是"四选一"

`I-03` 的处置是"事务外先准入"，时间线：

```
事务 A（准入）              事务 B（插入 run）
BEGIN
  查无 active
COMMIT   ← 行锁/advisory 全部释放
                           BEGIN
                             INSERT run(status='queued')
                           COMMIT ← 唯一索引在这里检查
        ↑
   窗口：另一个请求也能通过检查
```

| 候选 | 能否覆盖窗口 |
|---|---|
| `SELECT ... FOR UPDATE` | ❌ 随事务提交释放 |
| `pg_advisory_xact_lock` | ❌ 事务级，提交即释放 |
| `SERIALIZABLE` | ❌ 只管单事务内 |
| **唯一索引** | ✅ 插入时必然检查 |

⇒ 唯一索引不是"选项之一"，是**唯一能兜住这条处置的机制**；其余三个只是"减少冲突重试"。
