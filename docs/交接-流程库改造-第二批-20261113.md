## 1. 🔴 环境修复（接手前必看）

### 1.1 现象

| 现象 | 实测 |
|---|---|
| `GET /api/workflows/{id}` 返回 **500** | 页面点开任何一条流程都拿不到详情 |
| 流程库只有 **5 条**流程（全是 SOP-0042 / dbg-edge 这类测试数据） | 上一轮结束时 158 条真实流程"不见了" |

### 1.2 根因

上一轮为了隔离验证新写的列表 SQL，**把本地内核的 `LABOS_DB_*` 指向了本机临时库 `labdb`（5 条合成数据）**，验证完没切回来。
那个库的 schema 落后于另一会话的 S2 物料改动，后端日志里的原文是：

```
ERROR: column n.material_effect does not exist
### The error may exist in file .../out/mapper/GraphMapper.xml
```

`material_effect` 列由 S2 物料设计引入（在 `workflow_node` 上），临时库里没有 ⇒ 详情接口必然 500。
**这不是 P0 代码的 bug，是环境指错库。**

### 1.3 修法（已做完）

```bash
# 真数据在服务器库：192.0.2.2/labdb（schema 完整、159 条流程）
cd labos-kernel
export LABOS_DB_HOST=192.0.2.2 LABOS_DB_PORT=5432 LABOS_DB_USER=labos \
       LABOS_DB_NAME=labdb LABOS_DB_PASS='REDACTED_DB_PASSWORD'
java -cp "out:lib/postgresql-42.7.3.jar:lib/spring/*" com.labos.boot.LabosApplication
```

> ⚠️ **重启内核必须带这几个环境变量**。`scripts/start-kernel.sh` 不设默认值，
> 默认值在 `scripts/baseline-up.sh` 顶部（服务器库）。不设就会连到本机同名库。


## 2. 第二批做了什么（前端为主）

### 2.1 版面：从"大卡片套表格"改成四段式

| 段 | 内容 | 为什么 |
|---|---|---|
| ① 页头 | 标题 + 计数 + 「新建流程」 | 主操作不再藏在卡片的 extra 里 |
| ② **统计条** | 全部 / 已发布 / 草稿 / 未指定岛 / 空流程 | 台账健康度一眼可见；覆盖全库（独立接口），不按当前页数算 |
| ③ 工具条 | 搜索 + 岛筛选 + 只看空流程 + 重置 + 只读提示 | 筛选集中在一处 |
| ④ 表格 | 10 列紧凑行高 | 密度来自**用列承载信息**，不是留白 |

**统计条的可点性约定**：带 ▾ 的格子（未指定岛 / 空流程）可点，且对应**真实筛选**；
「已发布 / 草稿」是只读信息（后端还没有 status 过滤，且 status 语义未固化）——
**不允许出现"点了没反应"的假交互**。

### 2.2 抽屉加料（560px）

原来只有预检 + 节点表。现在依次是：预检摘要 → **问题清单** → 治理字段 → 节点构成 → **最近运行** → **版本历史**。

- **版本历史**：接上早就存在但没端到端呈现的 `workflow_graph_history` + `/history` + `/restore`（回滚会写 `workflow.restore` 审计）。
  流程是资产，资产要能回退。
- **最近运行**：接 `/workflows/{id}/runs`，用**全站统一状态词表**（`utils/status.ts` 的 `statusColor/statusLabel`）渲染结果徽章。

### 2.3 术语中文化

| 原来（内核词） | 现在（现场话） | 依据 |
|---|---|---|
| `ALIQUOT` / `SEAL` / `CENTRIFUGE` | 移液分装 / 封膜 / 离心 | 后端 `capability.name`（新增 `capabilityName` 字段透出） |
| `explicit` / `protocol` / `heuristic` | 手动指定 / 方法定义 / 自动推断 | 前端 `SOURCE_LABEL` 映射表 |

原始 code 仍然保留在数据里（接口继续返回），追溯不受影响。

## 5. 未闭环 / 需要别人接手

### 5.1 🔴 自动对齐门禁红：**不是这一批引入的**，归属在未提交的「自动对齐/折叠」重写

`scripts/verify-designer-autolayout.py` 的第 ③ 组断言失败：

```
✗ 同一条分支上的节点 x 对齐（前后端对齐）
  ({160: [350, 550, 750, 950, 1150, 1350], 560: [550, 750, 950, 1150, 1350, 1550, 1750, 1950, 2150, 2350]})
```

**已排除的因素**（都做过对照实验）：

| 假设 | 实验 | 结论 |
|---|---|---|
| 是设计器三栏塌陷修复（`wrap={false}` / `minWidth:0`）引入的 | 排版算法里唯一的 `getBoundingClientRect` 在 2735 行（画布全屏），不在排版逻辑；排版只用常量 `MAX_COLS_PER_ROW=10` | **排除** |
| 是折行容量 `MAX_COLS_PER_ROW` 引入的 | 临时改成 999 复跑，仍是同样两行、同样错位 | **排除** |
| HEAD 版本是绿的 | 把 HEAD 的 `Designer.tsx` 换进去跑 ⇒ 脚本连「适应画布」按钮都找不到（该按钮与折行逻辑都只在工作树里） | **HEAD 从未跑过这个脚本** ⇒ 这条门禁自落地起就没绿过 |

**实测根因**（`scripts/diag-align-lanes.py` 可复现）：流程 1000830 的图是
`S→…→P(XOR_SPLIT)→{0b8dpbp | 1aqhlr8}→J(XOR_JOIN)→…→E`，排版后：

```
行 y=560: 02cvemm(550) 1rwyoag(750) 0g40ih6(950) 0b8dpbp(1150) 1aqhlr8(1350) …
行 y=575: P(175) J(375)
```

两条分支节点**既不同列、也不在不同车道**，而 `placePair` 的口径明确要求
「所有分支都从分叉点右边同一列出发」（`Designer.tsx:2135-2141`）。
可疑点在 `placePair` 的 `joinCol = col + 1 + maxW`：`seqWidth(s, j)` 对
「单节点直达 join」的分支返回 **0**，于是 join 与分支节点同列；
随后折叠的块范围 `[forkCol, joinCol]` 装不下分支，分支被拆成独立块重新排 ⇒ 前后端错位。

**建议修法（未实施，属他人功能）**：`seqWidth` 对分支至少计 1
（或 `joinCol = col + 1 + max(maxW, 1)`），并让折叠的块范围覆盖分支所在列。
改完请重跑 `scripts/verify-designer-autolayout.py`。

### 5.2 🟡 列表行首信号灯仍只做了一项

现在只有「节点数 = 0 → 灰条」。**每行真实预检三态（绿/黄/红）需要批量预检接口**

### 5.3 🟡 `workflow.status` 语义仍未固化

`status` 目前**没有任何写入方**（新建固定 1），所以库里 159 条全是「草稿」，
统计条上「已发布 0 / 草稿 159」。界面照实显示，没有把 1 偷偷翻译成"已发布"。
固化取值需要业务口径拍板（草稿 / 已发布 / 已停用？发布动作由谁触发？）。

### 5.4 🟡 `category` 仍是内部枚举
