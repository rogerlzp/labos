# AI-native LabOS 产品战略 V1.0

- 日期：2026-11-18
- 状态：战略讨论稿 / 架构基线候选，非已批准需求
- 适用项目：LabOS（中控）
- 依据：中控既有项目讨论与设计背景；AutoDNA Nature 论文及公开海外资料
- 重要边界：本文不宣称已完成全仓源码审计、设备现场验证或产品能力验收。涉及现有实现的映射均标明证据等级，必须由后续代码核查补齐。

## 1. 执行摘要

**产品愿景：让每个科研人员拥有 AI 实验团队，让每个实验项目拥有自己的 AI 工作空间；LabOS 负责把 AI 的想法安全、可靠、可追溯地变成真实实验。**

LabOS 不应停留在传统实验室设备调度软件，也不应以“聊天机器人 + 一组 Agent”作为产品终点。目标是 AI-native Laboratory Operating System：由可信的实验执行底座、实验工作流编译与编排层、AI 科研协作层构成。

核心差异化不在模型数量，而在以下闭环：
1. AI 理解研究目标并提出实验意图；
2. 将意图转成有类型、有版本、可验证的实验流程；
3. 在执行前检查设备能力、资源、物料、样本、位置、权限和安全约束；
4. 由 LabOS 确定性执行并记录设备命令与物理世界事实；
5. 将实际执行、偏差、异常、原始数据、分析结果关联到样本与实验；
6. AI 根据可信数据提出下一轮方案，人类批准后再执行。

**关键架构原则：AI 负责推理与建议，LabOS 负责授权、校验、执行、状态和事实。** 任何 Agent 都不得绕过领域服务直接写数据库、拼接底层设备命令或自行宣布实验/物料状态。

## 2. 市场与对标结论

### 2.1 闭环产品形态要求

LabOS 的目标产品形态应满足以下要求：
- Agent、Workflow、Data 与 Scheduler 形成连续实验闭环，而不是彼此分散的功能菜单。
- 样本、物料、位置、协议、执行和结果之间建立全生命周期数据谱系。
- 动态调度由确定性执行层负责，统一处理设备、人员、物料、方法和权限约束。
- 第三方设备接入与多中心调度依赖标准化能力描述和可验证适配器。
- 以真实实验场景验证平台价值，不以功能清单或单次演示代替现场验收。

本评审包仅使用公开资料与 LabOS 自有设计，不收录第三方私有设计材料。

### 2.2 AutoDNA 代表的方向

AutoDNA（Nature，2026-11-04）报告了一个面向生物分子操作的 AI-native 实验室：多智能体协作，跨 20 多类仪器、超过 11,000 个硬件步骤，覆盖核酸合成、转录、扩增、测序等操作；论文报告四类应用结果，包括并发协议执行提速、DNA 数据存储端到端恢复和 KRAS 突变检测。其重要性在于模型、实验流程与仪器工程共同设计，而不是简单给既有实验室外挂一个问答模型。

AutoDNA 是研究平台与特定实验域的成果，不应直接推断为通用实验室产品已经解决任意设备、任意实验和任意实验室的自主执行。

### 2.3 海外产品与开放生态

- Synthace：实验设计、规划、仿真、执行和结构化数据串联；其公开开发文档把 Workflow、Planner、Simulation 快照、Execution 分开。这种“计划冻结后再执行”的对象模型值得借鉴。
- Emerald Cloud Lab：公开展示统一软件入口、脚本化实验方法、分析能力和实验元数据/数据完整性管理，代表云实验室将执行、数据和知识体系整合的方向。
- Opentrons：开放 API / Python Protocol API、可替换模块和实验室自动化硬件生态，说明设备可编程性与开发者生态是平台扩展的重要来源。
- SiLA 2：设备互操作接口标准，围绕 Features、Commands、Properties 统一表达设备能力；适合作为设备连接适配层参考，不等于实验业务编排标准。
- Autoprotocol：平台无关、结构化、可映射硬件的实验协议描述思想；可借鉴其明确步骤和可组合性，不必照搬其全部语法。

## 3. 产品定位与边界

### 3.1 产品定位

LabOS = 实验室执行操作系统（LabOS Core）+ AI 科研协作平台（LabOS AI）+ 垂直实验应用（LabOS Applications）。

| 产品层 | 用户价值 | 关键能力 |
|---|---|---|
| LabOS Core | 实验能安全、确定、可追溯地执行 | 设备/驱动、实验/流程、节点、命令、调度、物料/样本、位置、权限、审计、恢复 |
| LabOS AI | 科研人员用自然语言和虚拟团队完成研究工作 | Research Copilot、个人/项目 Agent、知识检索、方案生成、数据分析、异常解释 |
| LabOS Applications | 将平台能力封装成可交付实验场景 | 核酸提取/检测、样本制备、QC、细胞/蛋白实验等 |

### 3.2 不做什么（至少在早期）

- 不做没有审批和安全边界的“LLM 直接控制机械臂”。
- 不把任意 Python 代码作为生产协议直接执行。
- 不以 Agent 数量、模型参数量或聊天轮数作为产品核心指标。
- 不一开始追求跨所有生命科学领域的自动实验优化。
- 不声称数字孪生能证明真实物理执行必然成功。
- 不让每位用户维护一套彼此隔离、重复建设的 Agent 代码。

## 4. 目标用户与核心工作流

### 4.1 用户角色
- 科研人员：提出研究目标、查看方案、批准实验、解释结果。
- 实验平台主管/管理员：维护设备、方法、资源、人员权限和实验室策略。
- 实验执行人员：准备试剂耗材、处理补料/换板/清洁、接管异常。
- 项目负责人：管理项目目标、实验计划、结果和协作知识。
- 自动化/设备工程师：接入设备、定义能力、验证驱动和恢复策略。

### 4.2 主工作流
研究目标 → 文献/知识证据 → 候选实验设计 → 流程草案 → 编译与可执行性校验 → 仿真/资源计划 → 人工批准 → 实验执行 → 结果/偏差归档 → 分析与下一轮设计。

任何阶段均可进入“需人工确认/接管/中止”，并保留原因、责任人和上下文。

## 5. 产品能力优先级

### P0：AI 中控助手（先读后写）
- 自然语言查询设备、实验、节点、命令、物料和告警。
- 解释当前状态及证据来源；回答必须引用系统事实，不可凭语言模型猜测。
- 生成实验流程草案、排程建议、异常处理建议；初期只读或草案态。
- 支持用户将建议转成正式系统对象，但写操作需要权限与确认。

### P1：Workflow Compiler
- 结构化实验 DSL、Schema 版本、单位系统、设备/耗材能力约束。
- 静态校验、资源规划、冲突检测、仿真、计划快照和审批。
- 编译器输出仅能调用已注册的 Lab Capability，不允许模型生成任意设备命令。

### P2：个人与项目虚拟团队
- 一个主协调 Agent + 专业 Agent（文献、实验设计、物料、执行监控、数据分析、质量审核）。
- Agent 由模板配置实例化，不为每人复制一套代码。
- 个人、项目、实验、实验室知识与记忆严格分区授权。
- 多 Agent 共享同一套权威 LabOS 数据，不各自维护“事实副本”。

### P3：实验数据闭环与优化
- 先选择一个标准化实验场景。
- 建立实验变量、结果指标、质量门槛和可追溯数据集。
- 从统计分析/DoE/贝叶斯优化开始；达到证据门槛后再考虑更复杂的策略学习。
- 优化建议需经过实验负责人审批，不能因模型置信度高就自动执行。

## 6. 产品验收指标（建议值，需试点校准）

| 维度 | 指标 | 验收原则 |
|---|---|---|
| 事实准确性 | 状态问答引用率、事实错误率 | 关键状态回答必须可追溯到 API/事件/审计记录 |
| 流程质量 | DSL 静态校验通过率、人工修改率 | 按实验域分层统计，不以单一平均值掩盖风险 |
| 执行安全 | 未授权命令数、绕过校验次数 | 目标为 0；任何一次均需事故复盘 |
| 执行可靠性 | 计划/实际差异、命令超时与恢复率 | 以设备/方法分层，不能只报全局平均值 |
| 可追溯性 | 样本—物料—步骤—命令—数据关联完整率 | 关键对象链路完整，缺失明确标 UNKNOWN |
| 效率 | 实验准备时间、排程等待、人工干预时间 | 与基线对照，避免只统计 AI 响应时间 |
| 科学有效性 | 实验质量指标、重复性、独立验证 | 由领域专家定义，不能用流程完成率替代 |

## 7. 商业化路径

1. 先以 LabOS Core 作为基础产品，证明设备与流程执行稳定、可复用。
2. 通过 AI 助手降低使用门槛，扩大用户触达与系统使用频率。
3. 以项目 Agent 和 Workflow 模板形成可复用应用。
4. 在单一垂直实验场景建立 DBTL 案例，再拓展到相邻实验域。
5. 后续可探索设备能力市场、经过验证的实验方法/Skill 市场和应用模板市场。

能力市场必须区分：设备厂商声明、现场验证能力、实验室验证方法、AI 生成建议。未经验证的 AI 方案不得标记为已验证 Skill。

## 8. 关键决策

| 决策 | 建议 |
|---|---|
| AI 是否直接控制设备 | 否；只调用受控业务工具，经编译、校验和审批 |
| Agent 是否按人复制 | 否；模板 + 配置 + 权限上下文动态实例化 |
| 实验流程表示 | 版本化结构化 DSL，编译为确定性执行计划 |
| 设备接口 | 内部统一 Capability API，外部适配 SiLA 2 等开放接口 |
| 运行事实 | LabOS Core 是权威来源；Agent 只读/调用领域服务 |
| 首个 AI 场景 | AI 实验流程助手 + 执行状态解释，先读后写 |
| 首个优化场景 | 从已有成熟流程中选择一个变量空间有限、质量指标明确的实验 |

## 9. 风险与待验证事项

- 现有 API 是否已覆盖所有 Agent 所需操作：需源码盘点。
- 设备能力描述是否足够细化到参数范围、单位、前置条件和副作用：需能力矩阵。
- 实验 DSL 与现有 Workflow 模型如何映射：需设计评审。
- 样本、试剂、耗材、位置和实验数据谱系是否完整：需链路审计。
- 设备错误恢复是否有可验证的幂等、重试和人工接管语义：需按设备验证。
- 用户隔离、项目权限、模型数据使用和知识产权边界：需安全评审。
- 监管场景（GxP、21 CFR Part 11 等）需按目标市场单独评估，不以“支持审计日志”宣称合规。

## 10. 结论

LabOS 应从“实验室中控”演进为“AI-native 实验室执行与协作平台”。核心竞争力是把科学意图、可执行流程、物理执行事实和实验数据连成可信闭环。先把底座做可靠，再让 AI 变得聪明；先证明一个场景，再复制到更多实验室和实验域。
