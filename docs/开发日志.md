### Bug（按发现顺序）

**B1. 编译假象（最严重，浪费 4 轮）**

```bash
javac ... 2>&1 | grep error    # 中文"错误"匹配不到，一直以为编译通过
```

实际有 `NodeProgress` 类型错、`DriverRegistry` 未导入，所有新加路由都没进 class 文件，表现为 `no route`。

**教训**：过滤构建输出必须匹配真实语言的错误关键字。中文 JDK 输出是「错误」，不是 `error`。

**B2. token 过期后页面"静默变空"**

岛屿视图空白但无报错。真相：401，但裸 `fetch` 拿到 JSON 后没人处理。

修：`client.ts` 导出 `apiFetch`，401 时清 token + 派发 `labos:unauthorized` + 抛错。**批量替换 7 个页面的裸 fetch**。

**B3. `device_state` 外键失败**

`markPlatePosition` 写的是 `device_instance.id`（171），外键指向 `resource_node.id`（200171）。

修：映射后再写，映射不到就跳过（**不能写 0**，0 也撞外键）。

**B4. 拖动吞掉点击**

`onMouseDown` 直接进拖动态，`click` 不触发。修：移动不足 4px 视为点击。

**B5. 详情 Card 渲染拖垮整个布局**

`Card` 嵌在 `Space` 里，异常时右侧整块消失。修：改用 `Modal`（portal 独立渲染树）。

**B6. 安全网导致流程跑两遍（历史）**

按图执行失败后"退回顺序重跑"，但判断时动作已经执行了 → **真实设备上等于开两次盖**。

修：只在解析阶段失败才退回。这条已写进规格。

**B7. 影子检查设备分配错**

`ShadowRunner` 只按能力从池里挑，没读节点绑定的 `bound_resource_id`。修：有绑定优先用绑定。

### 设计决策

**D201. 池子是"型号"不是"设备实例"**

实验室语义是"这个岛要 3 台孵箱"，不是"把某一台具体孵箱搬过去"。

所以池子 = `device`（型号），拖拽 = `POST deploy` 建新实例。

**型号池管建新，设备与岛屿页管运维**——前者是设计，后者是现场。

**D202. 搬运序列不落 run，但能存成流程**

「走一遍」是现场调试工具：验证物流通不通，不产生生产数据。

「存为流程」才落库。两者的区别写在按钮文案上（"走一遍"vs"存为流程并打开设计器"）。

**D203. 搬运流程的节点绑死设备**

普通流程节点只标能力，执行时从池里随机挑。

搬运流程额外存 `bound_resource_id`——语义是"板子必须经过这几台具体设备"。

**D204. 影子跑分两级**

| 级别 | 做什么 | 为什么 |
|---|---|---|
| 单命令探针 | 一个方法能不能调通 | 安全，随时可停 |
| 整流程影子跑 | 全流程契约覆盖 | 失败不中断，覆盖所有节点 |

不做"整流程真跑 + 决策丢弃"——因为物理动作不可撤销，停在半路比不跑更糟。

**D205. 甘特用 SVG 不用 frappe-gantt**

frappe-gantt 要绝对日期，我们的数据是相对毫秒，转来转去引入时区问题；暗色主题还要覆盖一堆 CSS。

横道图只有几行坐标计算，SVG 更直接。图表库留给统计场景（利用率趋势、时长分布）用 ECharts。

**D206. 流程图历史必须"回滚前也备份"**

否则回滚后就找不到"回滚前"的样子，回滚变成单向操作。

### 设计决策

**D207. 实验层管数据和多轮，流程层管动作和条件**

| 能力 | 层 | 理由 |
|---|---|---|
| 设备动作、条件分支、单流程循环 | 流程（BPMN） | 已有，原生支持 |
| 变量、跨流程循环、流程间依赖 | 实验 | BPMN 表达不了 |

若两层都能表达条件，维护时必冲突。

**D208. 变量整体替换，不逐条 diff**

变量通常 <10 个。全删再插在一个事务里做，不会出现"删了一半"的中间态。

**D209. 变量类型只做标量（number/string/boolean）**

实验参数本质是标量（温度、体积、板数）。复杂结构应进流程节点参数。

**D210. 循环只做单层**

嵌套循环会让展开后步骤数爆炸（3×3×3=27），界面难表达、难调试。真需要时用流程层 BPMN 回环。

**D211. 多实验并行：岛级互斥，不做岛内并行**

物理事实：一个岛通常只有 1 台机械臂，两个实验同时跑会打架且无法区分板子归属。

岛级容量=1 是**安全下界**。代价是并行度=岛数（26），但比撞机械臂好。

**D212. 实验必须显式声明 island_id**

从流程节点反推不可靠——普通节点只绑能力，执行时才选设备，岛不确定。

显式声明后调度器能静态算清资源占用。

**D213. 调度用启发式（EDD + 优先级 + FIFO），不用最优解算法**

三个理由：
1. 结果可解释（"它截止最早"）
2. 出错能手工干预
3. 工时精度只有 10 秒级、波动比最大 13.5×，最优解和启发式的差距小于工时误差

> 在数据不准的系统里追求算法最优是自欺欺人。先管住资源冲突，再谈优化。

**D214. 消除"持有并等待"来防死锁**

实验一次性申请所有资源，全有或全无。1.0 每个实验只需 1 个岛，天然满足。

将来跨岛时按 `island_id` 升序申请（全局顺序），消除循环等待。

**D215. 岛锁带 TTL（2 小时）**

防止执行线程异常退出（OOM/kill -9）导致锁永久泄漏。

代价是"可能两个实验同时跑一个岛"，**但比永久卡死好**。

**D216. 不做纯动态规划（DP），做滚动时域动态调度**

纯 DP 状态数是 `2^N × 时间档^M`（N=50 实验、M=26 岛），天文数字。

且 DP 求最优的前提是工时准确，而我们的波动比最大 13.5×。

**关键厘清**："动态规划"（Bellman 最优）≠"动态调度"（运行时调整）。前者用不了，后者该做。

做法：滚动时域（Rolling Horizon）——
- 承诺窗口：已开始的实验绝不改
- 冻结区：未来 15 分钟排程不动（否则等于没排程）
- 事件驱动重排：新实验/完成/失败/设备离线才重排
- 局部修复：只重排受影响部分，避免排程抖动

**贪心（EDD + 最早可用岛）优于全局最优的理由**：在滚动框架下，每一步局部最优比一次性全局最优更实用——因为一次性最优的前提（未来已知）在现实中不成立。

**D217. 实验必须显式声明 island_id**（拍板）

从流程节点反推岛不可靠（普通节点只绑能力）。显式声明后调度器能静态算清资源占用。

代价：用户要选岛。缓解：默认选设备最多的岛。

**D218. 1.0 用岛级互斥，并行度=岛数（拍板）**

物理事实：一个岛通常 1 台机械臂，两实验同时跑会打架且无法区分板子归属。

岛级容量=1 是安全下界。代价是并行度受限于岛数（26），收益是绝不撞机械臂。

**D219. 1.0 不做跨流程依赖（拍板）**

原有实现 `run_mode` 统计 99.7% 是 sequential。支持 DAG 需拓扑排序+环检测+部分失败处理，1.0 用不上。

真出现并行需求，用"拆成两个实验 + 岛级并行"代替。

**D220. 位置级互斥比岛级互斥更本质（用户指出的物理约束）**

用户场景：实验 A 把板放进位置 X，实验 B 绝不能往 X 再放板，否则压碎/卡死。

**岛级互斥防不住这个**——它管的是"谁在用机械臂"，不是"哪个位置有板"：

| 情况 | 岛级互斥能否防住 |
|---|---|
| 跨岛共享同一位置 | ❌ |
| 上一个实验的板还留在位置里 | ❌ |

**根因**：机械臂是**瞬时**资源（搬一次几秒），位置是**持久**资源（板占几小时）。用一个粒度管两种资源必然失真。

**D221. 位置状态要区分"实际占用"与"预约"**

- `plate_id` 非空 = 板实际在里面（持久）
- `reserved_until` 未过期 = 有人预约搬运中（短时）

不做预约 → 两个实验同时看到"位置空"，都去放板。

**预约 = 分布式锁在数据库里的实现**。

**D222. 搬运必须一次性锁定源和目标**

```
实验 A 占源 X，等目标 Y（被 B 占）
实验 B 占源 Y，等目标 X（被 A 占）
→ 死锁
```

两条规则：
1. **全有或全无**（拿不到目标就放掉源）
2. **按 resource_id 升序申请**（消除循环等待）

**D223. 1.0 岛级互斥 + 位置锁双保险**

| 方案 | 并行度 | 安全 |
|---|---|---|
| 只岛级 | 26 | 跨岛位置冲突防不住 |
| 只位置级 | 高 | 需秒级时长 + 位置初始化 + 机械臂时间片，现在都没有 |
| **两者都做** | 26 | ✅ 双重保险 |

**岛级是安全网，位置级是正确性。** 先有正确性，再逐步放开安全网。

2.0 放开岛级的前提：秒级时长 + 位置初始化 + 机械臂时间片 + 位置锁稳定 3 个月。

**D224. 位置冷启动必须人工清空**

上线时所有位置视为"空"。但原有系统跑过的板可能还在里面。

**绝对禁止新旧系统并行操作设备**——位置锁不知道原有系统放了板。

过渡：原有系统停 → 人工清空 → 新系统上线 → 盘点 → 开始跑。

```
seq  loop  workflow  run_id  status
1    0     239       204932  completed
2    0     648       204933  completed
2    1     648       204934  completed   ← 循环展开
```

**设计要点**：

1. **失败即停**：实验室里跳过一步意味着板子位置未知，后续步骤全是错的
2. **变量在流程启动前一次性替换**：变量在一次实验内不变，每节点替换是浪费
3. **循环上限 20、总步数上限 500**：防止展开后爆炸到无法调试
4. **找不到的变量保留 `${name}` 原样**：让执行时报错更直观，比替换成空字符串好排查

### 功能（板子转运：自动插入机械臂）

**问题**：连线 `A → B` 只执行 A 或 B 自己的方法，板子永远搬不过去。

**关键发现**：机械臂有 `Transfer(source, target)` —— 正是"从 A 搬到 B"的原子操作。

**实现**：遍历设备节点时检查相邻两站，**两端都不是 TRANSFER 能力**就在中间插：

```ts
steps.push({
  resourceId: arm.resourceId,
  method: 'Transfer',
  params: { source: prevDev.code, target: d.label },
});
```

**实测**（开始→机械臂→分叉→ID1775→汇合→ID1183→结束）：

```
1. Home        resourceId=200214
2. Deposit1    resourceId=200210      ← ID1775 放板
3. Transfer    source=ID1775 target=ID1183   ← 自动插入
4. Deposit1    resourceId=200171      ← ID1183 收板
```

**局限**：
- 机械臂永远取岛上第一个 TRANSFER
- source/target 传设备编号，驱动是否认还需现场验证
- 没做"板子在不在"的预检

### 文档（指令时序）

`测试与上线策略.md` 加第十章：发一条等一条。

**核心事实**：`ShadowProbe.probe()` 是同步方法，返回时结果已拿到；
`for` 循环天然串行，不存在"发出去不管"。

**三层超时**：

| 层 | 超时 | 在哪 |
|---|---|---|
| 命令级 | 15 秒 | `DriverCommand.timeoutMs()` |
| 读超时 | 30 秒 | `socket.setSoTimeout(30_000)` |
| 连接级 | deadline | `t0 + cmd.timeoutMs()` |

**读超时比命令超时长**：留余量，避免命令还在途就被判死。

**超时后中断后续步骤**：这一步没做完就做下一步，物理上可能撞机。

**异步上报模式不支持**：现在是一问一答（TCP 短连接）。
判断依据看 `method_status`——返回 2 是同步，返回 1（运行中）就说明是异步，需要改造。

**怎么验证时序对不对**：看 `run_command.result->>'durationMs'`。
全是 0 或个位数说明走的是 mock，没真在等设备。

### 功能（长连接驱动）

`TcpPersistentDriver`：一条常驻连接，按 `message_id` 配对请求与响应。

```
execute(cmd)          → messageId 入 pending → 写 socket → future.get(timeout)
readerLoop()          → read 按分隔符分帧 → 解析 messageId → pending.remove(id).complete()
```

**开关**：`LABOS_DRIVER_MODE=persistent`

**三个必须处理的点**：
- **重连**：断了自动重连，否则一次抖动永久失联
- **写串行**：`synchronized (writeLock)`，多线程不能同时写
- **清理悬空**：超时后 `pending.remove(id)`，否则设备后来真回了会往没人等的 future 里塞

**还发现一个关键问题**：`buildDriverRegistry()` 每次调用都 new 一个驱动，
长连接等于没长连接。加 `cachedRegistry` + 60 秒 TTL 后才真正复用。

**实测**：
```
不缓存：[驱动] 长连接模式  每次都打印
缓存后：只打印 1 次，4 条命令 69/64/61/62ms
```

**还没做的**：`method_status=1`（运行中）现在直接返回失败。
真机上应该保留 future 继续等，收到 2 才 complete。

### 功能（板子流动：设备轮转）

### Bug（多进程抢 mock 驱动导致 30 秒超时）

### 修复（putPlate 不落库 — 评审给出根因）

**外部评审（Grok，2026-11-01 21:40）对照源码指出根因，我之前的判断是错的。**

**真实链路**：

```

  ↓ 同一事务
putPlate → UPDATE position_state SET plate_id（n=1）
  ↓ 同一事务，if (n > 0) 里

  ↓

  ↓

  ↓ 异常被 catch (SQLException ignore) 吃掉
```

|---|---|---|
| `notePlateMove` | 不看 `putPlate` 返回行数，0 行也 `return pos` | 返回 0 时返回 `NO_EMPTY_POSITION` |
| `tryReserve` | 更新 0 行 + 查不到记录仍返回 `OK` | 返回 `NOT_FOUND` |

### 修复（长任务被误判超时 — P0 前置）

**问题**：设备回 `method_status=1`（运行中）时，驱动直接判失败。

真机上孵育要 30 分钟，驱动会先报一次"运行中"，再报"完成"。
现在的代码**收到第一次"运行中"就返回失败**，等于所有长任务都跑不了。

**修法**：

| 驱动 | 改前 | 改后 |
|---|---|---|
| 长连接 `TcpPersistentDriver.dispatch` | `pending.remove(id)` 后无条件 complete | **先看 status**：=1 时不摘不 complete，等下一帧 |
| 短连接 `TcpDriverAdapter` 读帧循环 | 收到 FINISH 帧就返回 | status=1 时 `continue`，继续读 |

**关键点**：长连接里 `pending.remove(id)` 必须在**确认不是运行中**之后。
先摘再判，future 就没了，设备后面真报完成也没人接。

**验证方式**：给 `MockDriverServer` 加 `LABOS_MOCK_LONG_TASK=1`，
让它连发两帧（`status=1` → `status=2`），并加了独立 main 可单独启动。

```
手工测 mock：帧1 status=1，帧2 status=2  ✅
驱动探针：  ok=true, method_status=2, 13ms  ✅
```

**踩坑**：一开始以为 19301 是 Java Mock，实际是 **.NET Sidecar**（`LegacySidecar.` 进程）。
改了半天 Java Mock 的代码，完全没生效——因为连的不是它。

**教训**：改之前先 `lsof -i :端口` 看**谁在监听**，
不要假设"我在改的那个类就是跑着的那个"。
这是第八次"验证手段本身有问题"。

### 功能（每台设备一个模拟器 + 多驱动注册）

**问题**：之前一个 `MockDriverServer` 模拟所有设备，测不出真实场景：

### 功能（设备心跳 + 三态 + 结果返回）

**1. 心跳（在线/离线）**

新增 `driver/HeartbeatService`：每 10 秒按 driver 端点做 TCP 探活，
结果写 `driver_health` + `device_state.online`。

**为什么只能中控发起**：这套协议里中控是客户端、驱动是服务端，
服务端推不到没监听的客户端，只能轮询。

**为什么按端点不按设备**：同端点下共享一条通路，逐台连会放大 N 倍连接数。

**坑**：一开始用纯 UPDATE 写 `device_state.online`，
但设备可能从没有过 `device_state` 记录（从没执行过）→ 更新 0 行 →
表现为"7 个模拟器都在跑，界面只显示 2 台在线"。改成 UPSERT 后正常。

**2. 三态（idle/running/error）**

`onStepStart` 标 running + `current_method`，`onStepDone` 标回 idle/error。

**坑（第九次两套 ID）**：`onStepStart` 传的是 `device_instance.id`（171），
`device_state.resource_id` 是 `resource_node.id`（200171）。
直接比较更新 0 行**且不报错**，表现为"运行中状态查不到"。
加了子查询转换后正常（日志确认"更新 1 行"）。

**3. 结果返回**

回包的 `data` 字段原样存进 `run_command.device_raw_response`。
取结果三种方式：SQL 查 jsonb、配 output 变量自动传递、`/api/runs/{id}`。

**4. 前端**

设备卡片加状态圆点：绿=在线空闲、黄=运行中（悬停显示方法名）、
红=错误、灰=离线（无光晕）。

**5. 接口**

`GET /api/heartbeat` 返回每个端点的在线状态；
`/api/topology` 的设备对象加了 `online`/`status`/`currentMethod`/`hasPlate`。

**实测**：
```

...
执行 239 时：Deposit1 耗时 4053ms（慢了 4 秒）
```

### 修复（前端不自动刷新设备状态）

**问题**：设备在线/运行中状态写进了库，但**前端不刷新**——
只有手动 reload 页面才能看到"某台设备掉线了"或"正在执行"。

**验证过程**（三张截图）：

| 阶段 | 界面 | 数据库 |
|---|---|---|
| 执行前 | 全部绿点 | 全 idle |
| 执行中（ID1183 慢设备 15s） | **ID1183 黄点** | `ID1183 \| running \| Deposit1` |
| 执行后 | 全部绿点 | `ID1183 idle` |

**第一张"执行中"截图拍空了**——界面还是绿的，因为没刷新。
这暴露了问题：**状态数据有了，但没人去取**。

**修法**：`Island.tsx` 加 5 秒轮询：

```tsx
useEffect(() => {
  const timer = setInterval(() => setTopoReload((n) => n + 1), 5000);
  return () => clearInterval(timer);
}, []);
```

**同时改成静默刷新**：首次加载显示 loading，之后的轮询不动 loading 状态，
否则每 5 秒闪一下很难看。

```tsx
const firstLoad = useRef(true);
if (firstLoad.current) setTopoLoading(true);
```

**教训**：数据链路通了不等于用户能看到。
"写进库"和"显示在界面"之间还差一个刷新机制——
这个缺口在测试时不会暴露（测试总是先 reload）。

### 功能（设备离线告警）

**规则**：`online=false` 且 `last_heartbeat` 超 30 秒 → 开告警；恢复 → 自动关闭。
幂等键 `DEVICE-OFFLINE|<resourceId>`，同一设备只会有一条未关闭告警。

**第一次上线踩的坑：一次开了 169 条误报。**

原因：库里 169 台设备的驱动指向 5 个从来没通过的真实 IP，
而心跳的 UPSERT **无论在线与否都写 `last_heartbeat`**，

### 功能（表达式引擎 M1.1 完成）

**问题**：`substVars` 只做纯替换（`${i}` → 值），流程里写不了 `${usedSlots + 1}`。

**实现**：`com.labos.kernel.expr` 包，四个类：

| 类 | 职责 |
|---|---|
| `Expression` | tokenizer + 递归下降 parser + AST（~400 行） |
| `Evaluator` | 求值（含短路、除零检查、类型检查） |
| `Template` | 处理 `ID1183-L${i}` 这种"字符串里嵌表达式" |
| `Values` | 类型转换（字符串↔数字）、路径查找、相等判断 |

**为什么不引脚本引擎**：Nashorn 在 JDK 15+ 已移除，GraalJS 几十 MB，
都能执行任意代码。自己写 400 行，零依赖、只能算数、行为可控。

**踩的两个坑**：

1. **`ID1183-L${i}` 不是表达式，是模板**
   一开始用 `Expression.parse` 直接解析，报"无法识别的字符 '$'"。
   拆出 `Template` 类：它在字符串里找 `${}`，对每段调用 `Expression`。

2. **变量都是 String，`i + 1` 会拼成 "31"**
   流程变量存在 `Map<String,String>` 里，`+` 运算时
   "有一边是 String 就拼接" 的规则导致 `"3" + 1` → `"31"`。
   改成"**两边都能当数字就做加法**"（`Values.isNumeric`）。
   同理 `requireNum` 也从"检查是不是 String"改成"检查能不能解析"。

**实测**：

```
ExpressionSelfTest   30/30
  ID1183-L${cycles + 1}     → ID1183-L5
  ${floor(cycles / 2)}      → 2
  ${plate}-RAW              → PL-777-RAW
  ${i * 2}（i="5"）          → 10
  1 / 0                     → 异常"除数为 0（表达式 1 / 0）"
  undefinedVar              → 异常"变量未定义：undefinedVar"

端到端（跑 239，传 vars=cycles=4,plate=PL-777）：
  run_command.payload = {cycles: 4, plate_id: PL-777}   ← 替换生效
  未传的变量保留原样 ${xxx}                              ← 符合设计
```

**表达式能力边界（故意不做）**：字符串函数、函数定义、循环、对象数组、正则。
**表达式只做"算一个值"，不做"写逻辑"。**

### 功能（M2 等待图死锁检测）

**新增 `driver/WaitForGraph`**：

```java
boolean waitFor(long waiter, long holder)  // 记录"谁在等谁"，返回是否成环
void release(long runId)                   // 清边（拿到资源或结束了）
```

**核心场景（用户提的）**：

```
流程1 占 A，要 B（B 被流程2 占）→ 加边 1→2 → DFS 无环 → 允许等待
流程2 占 B，要 C（C 被流程3 占）→ 加边 2→3 → 无环 → 允许等待
流程3 占 C，要 A（A 被流程1 占）→ 加边 3→1
  DFS: 3→1→2→3 ← 成环 → **拒绝流程3**
```

**接入 `TransferPlan`**：
- 抢机械臂失败 → 查持有者 → 加边检测 → 成环立刻拒绝（不傻等 60 秒）
- 抢位置失败 → 如果是"被别人预约" → 同样检测
- 释放时 `GRAPH.release(runId)` 清边

**全局单例**：`TransferPlan.graph()`。
每个实例各持一个就失去意义——环是跨执行形成的。

**实测**：

```
WaitForGraphSelfTest  13/13
  ✓ 链 1→2 无环
  ✓ 流程3 等流程1 被拒（成环）
  ✓ 拒绝后图上没有 3→1 的边
  ✓ 流程1 释放后 3→1 可以了
  ✓ 自己等自己被拒
  ✓ 五元环：前 4 条允许，第五条拒绝
```

**关键设计点**：
- **先加边再检测**：如果加了之后有环，说明这次等待会死锁
- **成环就撤销边**，不留脏数据
- **release 要清两类边**：自己等的、别人等自己的
  忘了清会留下僵尸边，把没死锁的情况判成死锁

**误拒是接受的代价**：某些本可过的申请会被保守拒绝。
但误拒只是重试一次，死锁要人介入。

### 功能（设备型号库 + 错误码链路：离心机/封膜机按真机适配）

**起因**：只有 S100 和 ASpin 2K 两份真实手册，但设备接入是"一台一台来"的。
按类型建模时，接第二台离心机就得改代码；按型号建模后，**加一台 = 加一条定义**。

**分层**（这次才理清）：

```
DeviceProfile（类型）  离心机"大概有哪些方法、rpm 200–14000"——只管参数边界
DeviceModel（型号）    ASpin 2K / S100 的真实指令名、参数、错误码、动作超时
DeviceBehavior（行为） 时序约束：托盘原点、双门、先建模块实例
recovery_policy（库）  出事之后怎么办（现场可改）
```

**为什么把"型号"从 sim 包里挪出来**（新包 `com.labos.kernel.device`）：
同一份定义现在有**三处消费者**——模拟器（按手册回包）、适配层
（`DeviceErrorMapper` 把 `0x8000000C` 翻成 `EC-08-300C`）、SQL 生成器
（`DeviceErrorSql` 出 `error_code` + `recovery_policy`）。
放在 sim 包里会让"中控依赖模拟器"，以后写 .NET sidecar 就没法复用。

**S100 按手册补细的地方**：

- 错误码是 **14 个不是 15 个**（`0x0D`/`0x0F` 手册里没有，之前文档写错了）；
- `0x04` 一条指令码挂三种用法（封膜 / 改板型 / 查板型），靠索引 `0x00`/`0xA5`/`0x5A` 区分；
- **托盘不在原点不能封膜** → `0x8000001A`。这条实现之后，
  流程里漏写 `MoveTray(0)` 会在仿真阶段就暴露，不用等现场；
- **故障是锁存的**：报了无纸，换纸但不按清除故障，再封还是报无纸。

**ASpin 2K 按手册改掉的三处错误**：

- 原来编了个 `ControlCoverClose` 指令 —— **手册里没有**，就是 `ControlCover` + `nControType=0`；
- `nControType` 不是"开=1/关=0"两值，是 **0=关 / 1=开 A 门 / 2=开 B 门**，这机器有两扇门；
- `Start` 参数是**时间/速度/加速度**，没有 rpm 名义值；手册示例等待
  `120000 + 离心秒数*1000` —— 中控按 30 秒超时会**每次都误判超时**。

**错误码怎么用起来**（这是本轮真正解决的东西）：

```
设备 0x8000000C
  → DeviceErrorMapper（型号库查表）→ EC-08-300C / MANUAL / "换耗材"
  → DriverResult.errorCode = EC-08-300C（原始帧照样进 device_raw_response）
  → RecoveryDecider（recovery_policy, scope=node）→ MANUAL
```

- 编号规则 **`EC-08-30` + 手册码低字节**：`0x8000001A` ↔ `EC-08-301A`，运维能反推；
- 未登记的码 → `EC-08-9001` + 转人工，**不静默、不猜**；
- 严重度不是手填，按处置派生（RETRY→warn / MANUAL→error / ABORT→fatal），
  否则"能自动重试的"会被标成 fatal 半夜叫人；
- **长连接模式也要翻译**：`TcpPersistentDriver` 原来把所有失败压成 `EC-05-0001`，
  设备码在长连接路径完全丢失。

**踩的坑**：

1. **`switch` 语句里的 `case X -> expr;` 不返回值**。
   `S100Behavior` 里写了 `case "GetPlateType" -> Reply.ok(...)`，
   编译通过、运行不报错，**返回值被静默丢弃**，落到 `default` 回了通用帧。
   自检抓到的（"查板型返回 3"失败），否则会以为"模拟器支持查板型"。
   已改成 `case X -> { return ...; }`。**箭头语法只有在 switch 表达式里才 yield。**
2. **有型号时不能再按画像校验方法集**：S100 的 `MoveTray`、ASpin 的
   `CreateModules` 都不在通用画像里，按画像校验会**误拒合法指令**。
   画像是参数边界，型号才是方法集权威。
3. **真实驱动把参数序列化成字符串**（`"value":"10000"`），模拟器原来只认数字，
   e2e 自检一跑就暴露。参数解析现在两种都认。
4. **`Map.ofEntries` 不保序**，型号列表要按登记顺序打印，改用 `LinkedHashMap`。

|---|---|---|
| `device.DeviceModelSelfTest` | 192 | 型号库笔误、14 个码逐条、映射、决策、SQL 是否同步 |

#### 1. 种子进了真库（`labos_demo` @ 192.0.2.10）

#### 4. .NET sidecar（`sidecar-dotnet/`）

真机这一层原来只有模拟器，**现场没有东西去说设备的语言**。本轮补上：

```
labos-kernel ──TCP(JSON+SEP)──> sidecar ──┬── 串口 12 字节帧      (S100)
                                          ├── Cluster.dll + XML   (ASpin 2K)
                                          └── 转发给 Java 模拟器   (工位)
```

几个关键决定：

- **型号定义不写死**：`DeviceModelExport`（Java）把型号库导成 `models.json`，
  sidecar 启动时读。抄两份一定漂移，现象是"模拟器能跑、现场发不出指令"。
  `test-sidecar.sh` 会比对导出结果与仓库文件，不一致直接失败。
- **错误码不翻译**：设备说 `0x8000000C` 就回 `0x8000000C`。
  "该转人工还是重试"是业务策略，必须只有一处定义（`recovery_policy`）。
- **sim 档不是为了偷懒**：中控→sidecar→设备 这条链里，中间那跳最容易出问题
  （帧怎么拼、参数怎么转、错误码怎么回）。sim 档把它和"设备本身对不对"分开验，
  上现场只换传输，逻辑一行不改。

#### 踩的坑

1. **串口读超时不能写死**：`ReadTimeout=3000` 而封膜要 12 秒 → 每次封膜都超时 →
   中控判失败 → 重试 → **重复封膜**。改成按型号 `delayMs`/`actionTimeoutMs` 每条命令动态放宽。
2. **`Integer.parseInt("80000001", 16)` 溢出**：`0x8000000C` 超过 int 正数范围，
   取低字节要用 `Long.parseLong(...) & 0xFF`。
3. **`byteOf` 要在登记时炸，不要在运行时炸**：设备码写错格式，
   `DeviceModel.error()` 直接抛异常 —— 自检阶段发现，比现场发现"这条码没翻译"好。
4. **参数校验顺序**：`SealWithType(9)` 原来先查托盘 → 报"托盘不在原点"。
   改成先验参数：参数错是"你发错了"，跟托盘在哪无关；否则现场会去查机械。
5. **`DeviceModel` 构造器参数位置**：`errorBlock` 在 `note` 之后，
   我第一次插在 `note` 之前，编译报"int 无法转换为 String"。

### 修复（"流程跑绿了但设备没动" —— 页面上抓到的三个真 bug）

用户问"页面上能看到流程执行吗"。用浏览器真的点了一遍，**看到了，但看到的是假的**。

#### 1. 🔴 最严重：绑了设备的节点被当成"逻辑节点"，设备调用整个被跳过

流程库里点执行 → 运行详情 **1/1 节点完成、失败 0**，一片绿。
但翻模拟器日志：**一条命令都没收到**；`run_command.result = {"ok": true, "durationMs": 0}`。

根因在 `RealWorkflowRunner`：

```java
/** 合法设备实例 id 的上界。真实 id 只有三位数(162~405)，更大的都是伪值。 */
public static final long MAX_PLAUSIBLE_RESOURCE_ID = 10_000L;
...
if (equipmentInstanceId != null && (... || equipmentInstanceId > MAX_PLAUSIBLE_RESOURCE_ID))
    return new CapabilitySource(LOGIC, "logic");   // ← 判成逻辑节点
```

而 `GraphRunner` 把节点的 `bound_resource_id`（**资源 id**）传进来当这个参数 ——
现在部署出来的设备 `resource_node.id` 是 **5xxxxx**（如 504830），**全部 > 10000**。
⇒ 任何"把设备拖到节点上"的流程都会被判成逻辑节点 ⇒
`DriverStepExecutor` 第一句就是

```java
if (deviceId == 0L || "LOGIC".equalsIgnoreCase(ctx.capabilityCode())) {
    // 不调设备，直接把每一步标成功
    return;
}
```

**假绿**就是这么来的。这个 bug 单测发现不了（单测不经过"部署→资源 id 变大"这条路）。
修：上界改成 99_999_999（只拦老数据的 9 位伪 id）；并把真实原因写进注释。

#### 2. `bound_resource_id` 根本没被用来钉设备

即使能力解析对了，节点只是"按能力轮转选设备"——同能力两台时会跑到另一台机器上（编排里选的 2 号机，实际跑 1 号机）。
修：`GraphRunner.withBoundInstances(resource_node.id → device_instance.id)`，
绑了资源的节点直接钉住那台实例，不参与轮转。

#### 3. 流程库列表按"任务数"排序，新建的流程根本看不见

`ORDER BY task_count DESC` ⇒ 刚建的单步流程（task_count=1）落在 limit 60 之外，
界面上搜不到，现象是"刚建的流程不见了"。改成 `ORDER BY updated_at DESC`。

#### 4. sidecar 的 sim 转发不重连

模拟器重启后，sidecar 缓存的那条 TCP 连接是半开的（`TcpClient.Connected` 仍是 true），
后续每条命令都写进黑洞，**到 sidecar 重启为止**。修：回包超时就丢连接；
失败重试一次；错误码从 ASpin 专用的 `EC-05-2001` 换成 `EC-05-1006`（通讯失败）。

#### 验证（真机=模拟器，走页面点）

| 场景 | 结果 |
|---|---|
| 正常 | 运行详情 **节点 1/1、失败 0**，设备列显示 `S100-1`，模拟器日志有 `收到 Seal id=…-d413` |
| 注入无纸 | 节点 `manual`，原因 **`策略[EC-08-400C@NODE] 指定直接转人工`**，run 变 `paused`，进"暂停队列" |
| 设备重启后立刻跑 | 可能失败一次（`EC-05-1006`），60 秒内自愈（驱动注册表缓存过期后重建） |

#### 还没修的（记着）

- 运行详情的"节点 0/1、失败 0"：manual 的节点既不算完成也不算失败，计数读起来像"没跑"。
- 暂停队列看不到**为什么停**（哪个错误码），得点进运行详情才看得到 `EC-08-400C`。
- 心跳离线告警有并发 bug：`duplicate key ... alert_state_pkey（DEVICE-OFFLINE|200171）`，
  说明 upsert 写成 insert 了，每次心跳都报一次 ERROR。

### 功能（断点续跑：点"继续"真的接着跑）+ 修复（心跳告警 upsert / 暂停原因）

上一轮把"页面上能看到流程执行"跑通了，这一轮补的是**闭环的最后一步**。

#### 1. 🔴 点"继续"其实什么都没发生

`PauseManager.resume` 只把 run 置回 `queued`（源码注释写明：执行体早退出了，
从中间续跑"是下一轮的事"）。但**没有任何东西去拾起 queued 的 run** ——
现场换完纸点"继续"，界面显示排队，然后永远排队。

修：
- `GraphRunner.withSkipKeys(Set)`：上一轮已 completed 的节点**跳过不执行**
  （不跳的话重跑会把板再搬一次）。
- `WorkflowService.resumeAsync(runId)`：读已完成节点 → 删掉未完成节点的
  run_node（run_command 随 FK 级联）→ run 置 running → 后台用**同一个 runId** 续跑。
- `ApiServer` 的 resume 接口在 `action=continue` 成功后接这个续跑。

验证（全从页面点）：故障注入 → 暂停 → 换纸（重启模拟器）→ 点"继续"
→ **run completed，节点 completed，模拟器又收到一次 Seal**。

#### 2. 暂停队列看不出"为什么停"

行里只有"执行到需要人工确认的节点" + 停在节点 `—`（`run.pause_node_key` 是 null）。
后端改成取**第一个未完成的业务节点**（名字 + 状态 + `input.reason`），

#### 4. 心跳离线告警每次刷 ERROR（duplicate key）

### 修复（重试退避从来没生效）+ 功能（子步骤落错误码、尝试留痕）

#### 1. 🔴 "retry 3 次" 实际是 50ms 内重试三次

`WorkflowService` 里给状态机传的是：

```java
new RunStateMachine(decider, …, Sleeper.recording(new ArrayList<>()), …)
```

`Sleeper.recording` 只把退避时间**记进一个 ArrayList**，**不真睡**——那是给单测用的替身，
被留在了生产路径上。于是策略里写的 `retry 3 次 / exponential 500ms`
真实行为是：失败、立刻重试、立刻再失败，**50ms 用完三次机会**。
设备"忙两秒"这种瞬时故障必然被判失败转人工。退避计算得再准也没用。

改：生产用 `Sleeper.REAL`；只有 CI/批量验证嫌慢时设 `LABOS_FAST_RECOVERY=1` 才记录式。
`RealWorkflowRunner`（批量验收 `--all`）保持记录式，但加了注释说明**别照抄**。

实测（`EC-08-4001` 信号量溢出 → retry ×3）：

| 尝试 | 时刻 | 间隔 |
|---|---|---|
| S1 | 20:50:33.883 | — |
| S2 | 20:50:34.552 | +669ms（≈500） |
| S3 | 20:50:35.694 | +1142ms（≈1000） |
| S4 | 20:50:37.885 | +2191ms（≈2000） |

只能去 `run_command` 表里翻。

#### 3. 多次尝试本来就留痕，但没人验证过

### 重构（恢复作用域收口：从"抛出点随手写"改成错误码的属性）

**问题**：`RecoveryScope` 原来在抛出点硬编码 —— 所有设备失败都抛 `NODE`。
而库里按错误性质配了不同层级：

| 码 | 库里策略 | 原来实际 |
|---|---|---|
| `EC-05-1006` 通讯失败 | **command** / retry×5 | 通配 node/manual（一次就转人工） |
| `EC-05-1007` 回包超时 | **command** / retry×3 | 同上 |
| `EC-06-0001` 驱动未加载 | **run** / abort | `无匹配策略（层级=DEVICE）` → 转人工 |

上一轮按前缀临时补了"通讯类走 COMMAND"，但那是**第二份规则**，迟早和库里的配置再次分叉。

**做法**：

1. `error_code` 加 `scope` 列（`20_kernel.sql` / `90_all_in_one.sql` 同步）；
2. 回填**不另写一张意图表**，而是"优先取该码恢复策略的 scope"——
   写策略时定的层级就是真实意图；
3. `DriverStepExecutor.scopeOf(code)` 成为**唯一出口**：懒加载
   `error_code.scope` → 查不到再按前缀兜底（`EC-05-10*`/`EC-99-*`→command，`EC-06-*`→device）；
4. 五个抛出点（驱动未加载 / 发送失败 / 设备返回 / 资源占用 / 步骤异常）全部改用它。

**实测**：

| 场景 | 修前 | 修后 |
|---|---|---|
| 驱动没加载（把 ASPIN 实例的 driver_id 置空） | `无匹配策略（层级=DEVICE）` → **paused / manual** | `策略[EC-06-0001@RUN] 终止执行` → **failed / aborted** |
| 通讯失败（端点指到死端口） | 一次就 manual | `EC-05-1006@COMMAND` 重试 5 次、退避约 7.5s 才转人工 |

**顺带**：种子 SQL 里加了幂等回填段（`ALTER ... IF NOT EXISTS` + 只填空值），
重复执行两次确认无副作用；`test-all` 350/0，正常流程跑通（205364 completed）。

**还没做**：`scope` 目前没有 UI 编辑入口，改层级仍然要写 SQL。
错误码管理页做出来之前，这算已知缺口。

### 功能（一个码多条策略：按作用域各一条）

#### 为什么"多策略"不是"回退链"

先看运行时：`RecoveryPolicyResolver` 是 `specificity` → `priority` 排序后 **`findFirst`**。
所以同一码、同一作用域的两条策略里，只有 priority 小的会用上，另一条是**死配置**。

真正需要多条的场景是**同一码在不同作用域下处理不同**：

```
EC-05-1006（通讯失败）
  command 作用域 → retry ×5（单条重发）
  node    作用域 → manual ×1（节点层就别硬试了，叫人）
```

运行时按"谁匹配当前作用域"选。所以模型是 **一个码 × 一个作用域 = 一条策略**。

#### 实现

### 功能（分支未选中标 `bypassed`）+ 实测：并行/分支/循环/表达式/变量到底支持到哪

用户问"除了普通任务节点，并行、分支、循环、表达式、变量呢？并行中一条走了其他跳过呢？"
拿两个真流程在模拟器上跑了一遍（`T-PAR` 1257 并行、`T-XOR` 1258 分支）。

#### 1. 并行网关（AND）：**支持**

```
开始 → ◇并行分叉 → [Seal-A] ↘
                  → [Seal-B] ↗ → ◇并行汇合 → 结束
```

实测：两条都执行（模拟器收到 2 条 Seal）、`parallelJoin` 等两路都到齐才推进、整单 completed。

#### 2. 并行中一条失败：**不跳过，整单停下**

同样流程把第 2 条 Seal 注入无纸：

| 节点 | 结果 |
|---|---|
| Seal-A | completed |
| Seal-B | **manual / EC-08-400C** |
| 整单 | **paused** |

汇合点不会放行（等不齐），另一条已经做完的保持 completed。这是对的：
并行分支失败不等于"跳过"，重不重试由策略决定。

#### 3. 分支网关（XOR）：能分叉，但**条件不求值**

```
开始 → ◇分支(default=f3) → [走A分支] (condition ${ok}==true) ↘
                        → [走B分支] (default)               ↗ 结束
```

实测：走了 **B（default）**，`A` 没走。
`GraphRunner.choose()` 里对 conditionExpression 的处理是**记一条日志然后按 default 走** ——
条件表达式**从来没求值过**（存量图里 conditionExpression 使用数为 0，所以一直没暴露）。

#### 4. 🔴 没走的分支原来一直是 `running`

改之前：没走的分支节点停在 `running`（界面上靠"整单没在跑 ⇒ 显示未执行"遮过去），
分不清"这条路压根不用走"和"还没轮到"，也没法统计。

新增状态 **`bypassed`**（不是复用 `skipped`！）：

| 状态 | 含义 | 运行时行为 |
|---|---|---|
| `skipped` | 该做没做，**板位不可信** | GraphRunner **停下转人工** |
| `bypassed` | 异或网关选了另一条路，这步不用做 | 正常继续 |

- `node_status` 枚举加 `bypassed`
- 整单**成功**结束后，把仍挂 `running` 的业务节点标 `bypassed` + `input.reason`
  （失败/暂停时不标：那些 `running` 是"待续跑"，标了会让续跑逻辑误判）
- 界面：图上淡灰点线、图例「分支未选中 N」、节点表状态「未选中」+ 原因

实测（T-XOR）：`走B分支 completed`、`走A分支 bypassed / 分支未选中（异或网关走了另一条）`。

#### 5. 循环：**不支持**

回边会被 `activate()` 的 `if (!done.contains(target))` 直接忽略 —— 走第二圈时发现目标已执行过，
不再入队。加上条件不求值，"循环退出条件"也无从判断。要在图里做循环，得先支持表达式求值。

#### 6. 表达式 / 变量

| | 现状 |
|---|---|
| `conditionExpression` | **解析了、存下来了、不求值**（`unevaluatedConditionCount` 只统计，不用） |
| 流程内变量 | 无。只有**实验层**在启动前把 `${var}` 替换进参数（`ExperimentExecutor` 的 vars） |
| 网关 default | 支持（XOR 无匹配时走 default，再没有就稳定排序第一条） |

要真做条件分支，需要：表达式求值器（安全的、不用 eval）+ 运行期变量表（节点输出写进上下文）。
这是下一轮的事，不在这次范围。

### 功能（条件分支求值 / 回边循环 / 运行期变量）+ 文档三件套

#### 1. 条件表达式求值器（`engine.ConditionEvaluator`）

为什么自己写：表达式来自流程图的用户输入，用 `ScriptEngine`/`eval` 等于把工控机交出去。
自己写递归下降，只认 `比较/逻辑/括号/数字/字符串/变量`，多一个字符就报错。
自测里专门有一条注入用例 `... ; Runtime.getRuntime().exec('ls')` → 拒绝。

类型规则踩过的坑：`'10' > '9'` 如果按字符串比是 false，按数字比才是 true。
所以"两边都能当数字就按数值比"，大小比较**两边必须都是数字**，否则报错不猜。

#### 2. GraphRunner：条件真的求值 + 回边能重入

- `choose()` 里逐个求值出边的条件，成立就选它；求值失败 → 记 `unevaluatedConditionCount` 并走 default（**不阻断生产**）
- `done` 从"绝对去重"改成"**图里有环才允许重入**"：DFS 三色标记算一次 `hasCycle`，
  无环图维持原语义（防止并行汇合重复激活把设备动作多跑一遍）
- 保护：单节点 10 圈、总步数 500，超了记日志停下

#### 3. 变量：两个来源

| 来源 | 实现 |
|---|---|
| 启动时传入 | `?vars=k=v`（异步路径原来忽略变量，这次补上）→ 写 `run.input.vars` |
| 节点输出 | 每次任务成功后查 `run_command.result`，抽顶层标量 merge 进变量表 |

循环之所以在此之前"没法真的循环"，就是因为没有第二个来源 —— 条件里的变量永远不变。

### 修复（设备「详情」里方法为空）

### M6 完成（循环按圈次落库 loop_index + 建库脚本补外键）

ROADMAP 的 M6，也就是评审后清单里的两条 P0。

#### 1. 循环每圈一行：`run_node.loop_index`

原来一个业务节点只有一行（唯一键 `(run_id,node_key,attempt)`），循环跑 5 圈也只有最终状态 ——
"第 3 圈为什么失败"永远查不到。

改法（**纯增量，不动老语义**）：

| 行 | loop_index | 含义 |
|---|---|---|
| 汇总行 | **0** | 这个节点的**最终结果**（既有查询只看它，等价于改造前） |
| 圈次行 | 1..N | 第几圈的实际执行（状态/错误码/起止时间） |

唯一键改为 `(run_id,node_key,attempt,loop_index)`；`GraphRunner` 每圈回调 `RoundRecorder`，
`WorkflowService.recordNodeRound` 按圈 INSERT（从汇总行复制 name/seq/node_type，不重复拼字段）。

**只在"图里真有环"时记**：无环图每个节点只跑一次，汇总行已经代表那次，
再记一行会让"节点数"翻倍 —— 第一版就是这么把 `verify-device-chain` 的 3 步流程跑红的
（`第 1 步状态不对（completed\ncompleted）`：查出两行）。

查询侧统一收口（`loop_index = 0`）：节点数、当前节点、流程图着色、流程执行记录计数。
运行详情则**返回全部行**，前端把圈次行挂到汇总行下面展开：

```
节点（1）
  封膜一轮  已完成  —      ← 汇总
    封膜一轮 已完成  第 1 圈
    封膜一轮 已完成  第 2 圈
    封膜一轮 已完成  第 3 圈
```

### M7 完成（可运维性：错误码增删 / scope 校验 / 表达式算术 / 阈值热配）

### 功能（内置节点：变量 / 表达式）—— 引擎侧已完成

用户问"流程图里能不能加变量节点、表达式节点、程序代码节点"。

#### 定下的三条边界

| 节点 | 决定 | 理由 |
|---|---|---|
| 变量 `__setVar` | ✅ 做 | 循环/条件要靠它自增，安全 |
| 表达式 `__expr` | ✅ 做 | 复用条件求值器的算术，安全 |
| 程序代码 | ❌ 不做 | `eval`/脚本引擎等于把工控机交出去；改走"内置函数白名单" |

#### 实现方式（不加自定义 BPMN 元素）

节点仍是 `bpmn:task`，靠 **`protocolName` 以 `__` 开头**标记为内置：

- 解析：`WorkflowGraphParser` 见到 `__` 前缀 → `Kind.BUILTIN`（不找能力、不找设备）
- 执行：`GraphRunner` 内联执行，**不经过状态机、不产生设备命令**
  - `__setVar`：`{var, value}`，value 里的 `${x}` 先替换
  - `__expr`：`{var, expr}`，用 `ConditionEvaluator.value()` 算（支持 `+ - * /`）
  - 参数复用 `workflow_node.params->'method_params'`，不新增字段
- 失败：写 `MANUAL` + `EC-BUILTIN-001` 并**停下**（不能带着错值去做条件分支）
- 记账：`RunProgress.complete/manual`（内置节点没有设备/重试语义，走状态机反而绕）

上一轮我因为「body 传参、后端只读 query」把 Demo-D 的两条编排清空了。修完前端还不够 ——
**这类错误的特点是：接口返回 200，数据没了**。人工点页面基本发现不了，必须用断言钉住。

#### 后端三道防线（`replaceExperimentProcesses`）

| 情形 | 现在的行为 |
|---|---|
| `workflowIds` 参数缺失 | **400**「要清空请显式传 ?workflowIds=」 |
| id ≤ 0（前端把「＋ 新建流程…」的哨兵值 -1 混进来） | **400**「编排里有非法流程 id：[-1]」 |
| id 不存在 / 已删除 | **400**「流程不存在或已删除：[999999]」 |

**顺序很关键**：校验全部放在 `DELETE` **之前**。第一版没校验，删完才发现插不进去 →
编排已经丢了，回滚也救不回来（事务里能回滚，但错误信息是
`Batch entry 1 ... violates foreign key constraint`，看不出是哪个 id）。

#### 回归断言（`verify-device-chain.sh` 第 10 组，38 → 41 条）

```
✓ 缺 workflowIds → 400，编排未被清空（N 条）
✓ 非法流程 id（-1，哨兵值）→ 400，编排未被清空
✓ 引用不存在的流程 → 400（先校验再删），编排未被清空
```

三条都同时断言 **HTTP 码** 和 **条数不变** —— 只看 HTTP 码不够：万一接口回了 400
但先删后报错，数据照样没了。

### 验证（"多实验/多流程并行"到底测过没有）

用户问了两件事：甘特要不要做并行、并行到底测过没。我把它当验证任务做了一遍，

#### 结论

| 场景 | 结论 | 证据 |
|---|---|---|
| 流程内并行分支 | ✅ 两条都跑 | `verify-parallel-flow.py` 4/0 |
| 两条分支抢同一台设备 | ✅ 自动串行（DeviceLock） | 命令时间段重叠 = 0 |
| 同岛多实验 | ✅ 排队串行 | 峰值并行 = 1，`verify-parallel-experiments.py` 3/0 |
| 跨岛多实验 | ⚠️ 代码支持，**未实测** | 环境只有 Device_Test 接了模拟器 |
| 甘特并行建模 | ❌ 不做（有意） | 见文档 §5 |

#### 一个值得记的观察

流程内并行**看不出加速**，原因不是"没并起来"，而是**设备是瓶颈**：
两条分支的指令间隔 201ms、时间段不重叠 —— `DeviceLock` 把"抢同一台设备"排了队。
换句话说：单机场景下并行度受限于设备数，不是线程数。

#### 新增两个可复跑脚本

- `scripts/verify-parallel-flow.py`：自动建图（fork/join）→ 执行 → 断言两条分支完成 + 设备串行 → 清理
- `scripts/verify-parallel-experiments.py`：自动建 N 个实验 → 同时异步提交 → 采样 `running` 数 → 断言峰值 = 1 → 清理

脚本里的口令一律走 `LABOS_DB_*` 环境变量，不写进文件。

### 门禁（并行能力接进 ci-gate：第 2.6 道门）

把两个并行验证脚本接进门禁，以后"并行"这件事有自动化兜底，不再只靠一次手工验证。

```
./scripts/ci-gate.sh --with-db
  1. 纯逻辑单测     379 / 0
  2. 前端类型       tsc 0 错误
  2.5 建库产物      与分片同源
  2.6 并行能力      流程内 4/0、同岛并发 3/0
  3. 设备全链路     41 / 0
  门禁通过
```

#### 三个设计细节

1. **放在设备链路之前**（2.6 < 3）：链路脚本跑完会把自己的 sidecar 停掉，
   而并行脚本要靠环境里已经在跑的 sidecar + 模拟器 —— 顺序反了就会假失败。
2. **阈值也是"只许涨"**：`MIN_PFLOW=4`、`MIN_PEXP=3`，断言被删会红灯。
3. **环境不具备时优雅跳过**：没有"最近 2 小时成功执行过的设备"、或 API 不可用时，
   脚本打印 `SKIP:` 并退出 0，门禁显示"跳过（环境里没有可用设备）"而不是红。
   —— 干净 CI 里没有模拟器是常态，不能因此判门禁失败。

顺带修了 flow 脚本的设备默认值：原来取"库里第一台"，抓到过没接模拟器的那台
（Seal 连失败 4 次转人工）；现在取**最近 2 小时真的跑成功过命令**的设备。

### 功能（设备任务参数编辑 + 实验详情补「＋ 新建流程」按钮）

#### 1. 设备任务的参数现在按方法定义渲染输入框

设计器右侧「节点设置」里，选中设备任务后原来只有一个 JSON 文本框 ——
等于要求使用方知道参数名和格式。现在：

- 按 `/api/methods/{m}/params` 的 `param_schema` **逐个渲染输入框**
  （标签是参数名，`*` 标必填，占位符是方法定义里的说明）
- 值支持 `${变量}`，和条件表达式同一套替换规则
- 下面仍保留「原始 JSON」文本框：方法没定义参数、或要传额外字段时用它
- 改输入框会**同步改那份 JSON**（单一数据源，保存时不用再拼）

实测：选中 `S100 封膜验证` 的 Seal 节点 → 参数 `args` 输入框（占位符 `0x04: aa 04 00 … 00 ff`）
→ 填 `0x04 AA 04` → 保存 → 库里 `{"args": "0x04 AA 04"}` ✅

**修的坑**：这个节点的 `method_params` 在库里是数字 `0`（老数据不是对象），

#### 调查出来的现状（都是代码/表里核过的）

1. **`experiment_graph` 没人执行** —— 只有画布 API 读写它；

#### 四个问题的建议（草稿里都有选项与代价）

| # | 建议 |

| 1 | **process 为唯一事实来源**，graph 降级为布局；画布保存时编译落库；表变只读 |

关键论据：设备锁（`DeviceLock`）已经能保证"同一台设备不被两个流程同时用"，

### M9.5-S3 前置（`runtime_hold` 作用域扣留 + 实验级暂停/停止/恢复，`ce3eaf0`/`4458c88`）

**为什么先做**：执行语义（S2-A）稳定后，下一步才是批次；但批次要求"每批可单独跑/停"，
先把**实验级**的暂停/停止/恢复做出来，否则批次只能靠杀进程。

- 执行器加**动作边界检查点**：每步开始前查 stop_requested → aborted；查覆盖扣留 → paused。

- `RunControl`：停止（运行中只置 `stop_requested`，非运行态直接 aborted）、恢复（解除最内层扣留、
  run 回 queued、从 `seq:loop_index` 断点续跑；**site 级扣留不由单实验恢复解除**）。
- 接口：`GET /api/runtime/holds`、`POST /api/experiments/runs/{id}/(pause|stop|resume)`。
- 自测里发现并修掉 **BUG-20261103-10**（`9c1f65d`）：`ExperimentExecutor` 把 `experiment_run.id`
  写进 `experiment.run_id`，而后者外键指向 `run(id)` —— 两个 id 空间，迟早撞 23503。

**验证**：`RuntimeHoldSelfTest` / `RuntimeHoldDbSelfTest` / `RunControlSelfTest` /

### M9.5-S3（分批执行：两层批次表 + 按批串行 + 失败批重跑，`bbcc5bc` / 前端 `fd59d90`）

**要解决什么**：一个实验 96 个样品、设备一次只处理 24 个 → 要分 4 批；每批可单独跑、

### M9.5-S3.1（续跑回写 + 分批配置入口 + 重跑并发，`c915948` / 前端 `5f12696`）

**要解决什么（S3 残余 1/2/3）**：批内 run 走调度器恢复或人工恢复/停止后，批次层不更新，
而且会**用单条 run 的状态覆盖实验聚合状态**（例：某批 paused 恢复后跑完，实验被直接写 finished，
其他批还 pending）；同批并发重跑可能撞唯一键；`batch_split` 只能改库、页面上配不了。

**做法（实施清单 §10 决定 D8-D13）**：
- **D8 统一回写点** `BatchOrchestrator.onRunStatusChanged(runId)`：非批次 run 直接返回 false 且
  **零写**（老路径行为不变）；批次 run 在一个事务里回写 attempt 行（status/error/finished_at，
  终态时间 COALESCE 保幂等）并按读侧自愈口径重算批次状态，再按 D6 聚合实验状态。
- **D9 调度器**：`executeOne` 先探测 run 是否批次 run → 批次 run 用 `syncExperimentStatus=false` 跑、
  结束后 D8；异常兜底 markStatus(failed) 后再 D8。D8 自身失败只记日志 —— 不能冒到外层 catch
  把刚跑完的 run 假标成 failed。
- **D10 运行控制**：`RunControl.stop/resume` 改完 run 后探测批次归属，批次 run 跳过单 run 的
  `syncExperimentStatus`、改走 D8（resume→attempt/batch queued，实验按聚合显示 running；
  stop 非运行态→attempt/batch aborted，实验聚合 failed）。
- **D11 配置入口**：`PUT /api/experiments/{id}/batch-split`（>0 或 null，0 视为关闭；已有批次改值
  拒绝 —— D2 快照固化；非法值 400）+ 前端实验详情操作行「分批设置」弹窗（回填当前值、说明固化规则）。
- **D12 并发**：同批重跑在同一事务里 `SELECT … FOR UPDATE` 锁批次行后再算 attempt_no 并 INSERT，
  行锁串行化，不再撞 `UNIQUE(batch_id, attempt_no)`。
- **D13** `BatchPlanner.normalizeSplit`：null/<=0 -> null，>0 原值，供配置入口与读开关同口径。

|---|---|

### S3.2 残余收尾（重启 rehydrate / 扣留解除自动续队 / async vars / paused 批派生，`9bd83e5` / 联调脚本 `ed612f3`）

#### 1. 重启 rehydrate 待派发队列（§11.3-2）
调度器队列是内存态：进程重启后库里仍 `status='queued'` 的 run（async 整单 / 异步分批已建出的下一批）
没人入队就**永远不执行**，页面一直"排队中"。
- `ExperimentScheduler.rehydrateQueued()`：启动时查 queued run（联查 experiment 取 island/priority/deadline），
  跳过已在内存队列的，装回队列并返回条数；**幂等**（启动只调一次，运行中不调）。
- ApiServer 启动收尾打印 `[启动收尾] 待派发 rehydrate：N 条`；失败只打日志不阻断启动。
- 实测：造 1 条 queued run 重启 → `rehydrate：1 条` 且该 run 被派发到终态；二次重启 → `0 条`（幂等）。

#### 2. 扣留解除后自动续队（§11.3-1）
批边界遇扣留时候选批标 paused、不建 attempt（D7），旧口径要人解除扣留后再手动 POST async 才继续。
- 调度循环每 5 tick（约 10s）调 `autoContinueHeldBatches()`：任何扣留生效一律不动；扫
  "paused 且**无任何 attempt**、实验非终态"的批，再逐条判 coveringFor（三级作用域），
  调 `createNextBatchAttempt` → CREATED 才 `resumeRun` 入队（每 tick ≤5，单条失败只记日志）。
- 日志：`[调度] 扣留解除，自动续跑实验 X 第 N 批（run#M）`。
- 实测：造 experiment 级 hold → async 返回 `held:true` 且 0 attempt → 删 hold 后 ~10s 自动续队跑完 2 批。

#### 3. async 变量 overrides 持久化（§11.3-4）
- `ExperimentScheduler.submit(exp, vars)` / `BatchOrchestrator.createNextBatchAttempt(..., vars)` 把 vars 写进
  `experiment_run.variables`；调度器执行 queued run 时读出作为执行器用户 overrides
  （非批次保持 sync=true，批次 merge D5 批变量）；续队沿用上一 run 的用户变量。
- **剥掉 batchNo/batchSamples**：执行器跑完会把合并变量写回 run.variables，若原样传下一批，
  上一批批上下文会以"用户显式变量"身份覆盖下一批（D5 用户优先）——故续队只继承用户显式变量。
- 实测：async 提交 `{"k":"v","dose":"12"}` → `experiment_run.variables` 落 `{"dose":"12","k":"v"}`。

#### 4. paused 批派生状态口径（§11.3-5）
`loadBatches` 派生规则改为：**任一次 completed → completed**；否则最新尝试的 run 状态是
running/queued → 该状态；否则 `storedStatus='paused'` → paused；否则最新尝试状态。
缺省语义：批停在边界/等人时，不该被**上一次的 failed 尝试**盖成"失败"；D6 聚合也随之显示 paused。

### 权限收口：角色白名单 + 最后管理员保护 + 前端角色感知（`afddf5b` / `3339606` / `19bb67b`）

**背景（M11「角色权限」先行）**：系统已有最小鉴权（`sys_user.role` ∈ admin/operator/viewer、登录发内存 token、

#### 权限收尾（`4e3baec` / `ec28d02`）：事务锁 + 会话失败重试 + 只读覆盖补齐

上一轮权限收口留了三个尾巴，本日补齐：
- **最后管理员保护的事务锁**（`4e3baec`）：原来"读管理员数 → 写角色"两步无锁，极端并发下两个 admin 同时降级可能都通过。
  `QueryService.updateUser` 改为单事务：`pg_advisory_xact_lock(hashtext('labos:user-role'))` 全局串行化用户角色写入
  → 目标行 `FOR UPDATE` 读 → 目标为启用 admin 时同连接 `countEnabledAdmins()` + `lastAdminGuard` 判定
  → 拒绝即回滚不 UPDATE → 正常 UPDATE 后 commit（异常显式 rollback）。锁为 xact 级、提交/回滚自动释放，固定 key 覆盖跨用户交叉场景。
  实测：外部事务持锁时 worker 阻塞后 1536ms 完成；真实 admin 降级/停用仍 400 且 DB 未变。
- **会话失败策略**（`ec28d02`）：原来 `/api/auth/me` 任何失败（网络/500/内核重启）都会清 token 回登录页；
  现在**只有 401 才清 token**，其余失败保留 token 并显示全屏「会话恢复失败 + 重试 / 重新登录」，不白屏也不踢人。
  Playwright route mock（me 返回 500）实测：停重试页 → token 仍在 localStorage → 点重试恢复主界面。
- **只读覆盖补齐 + 角色文案同源**（`ec28d02`）：Alerts（保存/认领/关闭）、Plates（报位置/丢失）、Topology/Island
