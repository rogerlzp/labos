## A. 部署与范围

### A-01 单实例部署（硬前提）

**决策**：LabOS 按**单实例**设计和验证。所有关于锁、状态写入、执行体的正确性论证，都以此为前提。

**依据**：`device_state.current_run_id` 是 run 粒度，DB 层拦不住"同 run 的两个分支"；真正互斥的是 JVM 分片锁（`DeviceLock:81-95` 的 `LOCAL_LOCKS` + `LOCAL_HOLDS`）。

**推论**：一旦上多实例，这套正确性**全部失效**，需要重新设计，不是"补个字段"。

### A-02 不做多实例 fencing / epoch

**决策**：**不评审、不列入遗留、不列为待决策**。评审中提出即视为超范围。

**依据**：6 轮评审里被提了 4 次，每次都因为它在"遗留清单"里而被当成未闭合项。**留着"不适用"的条目 = 邀请别人再问一次。**

**但保留一个区分**（必须，否则会误删）：

| 名称 | 解决什么 | 单实例是否需要 |
|---|---|---|
| `hold_epoch`（**设备占用代次**） | 旧完成事件误清新租约 | **需要** |
| `owner_epoch`（执行体 fencing） | 旧实例写回状态 | 不需要 |

### A-03 同步入口不改成异步

**决策**：`E-01`（同步单流程）、`E-03`（同步跑实验）**保持同步阻塞**。

**依据**：响应里有 `totalSteps` / `doneSteps` / `batches`，改成异步这些字段就空了——**那是改契约，不是重构**。

### A-04 不做"人工拆分命令"

**决策**：不引入 `logical_command` 子表，不引入 `parent_operation_id`。

**依据**：三种可能场景逐个检查后，**都不需要**：

| 场景 | 实际是什么 |
|---|---|
| 设备卡住人工挪板 | 原操作已失败，新建两个操作 |
| 流程从直达改经中转 | 改流程定义，是另一个流程 |
| 一个意图多条命令 | 已被 `step` 拆分，每条命令本就是独立 operation |

且 `commandId` 在重试中不变 ⇒ 一个 operation 只有一个命令 ⇒ **一对多不存在**。

## B. 事件归属

### B-01 只认 `commandId`，无弱匹配

**决策**：事件与 waiter 的匹配只有三种结果：

| 条件 | 结果 |
|---|---|
| `waiter.expect_command_id` 非空，且等于 `event.command_id` | 匹配 |
| 两者都有但不相等 | **不匹配** |
| 任一为空 | **不匹配** |

**依据**：弱匹配在"同设备多 waiter"时不可靠，且是迟到事件的接盘者。

**写法必须严格**：

```sql
AND w.expect_command_id IS NOT NULL
AND e.command_id IS NOT NULL
AND w.expect_command_id = e.command_id
```

**禁止** `AND (w.expect_command_id IS NULL OR ...)` ——那等于给"没声明归属的 waiter"开后门。

### B-02 事件只有两类

| 类型 | 例子 | 带 `commandId` | 归属 |
|---|---|---|---|
| **命令关联型** | `waiting_interaction`、`extract_done`、进度上报 | **必须** | 归到该命令所属 run / node / branch |
| **系统型** | 心跳、自检告警、人工开门 | 没有 | **不归属任何 run**，只更新设备状态 |

**关键**：不存在第三类。"设备自发事件"中的绝大多数（到交换点、提取完成）本身就是某条命令的结果。

### B-03 匹配不上就 `UNATTRIBUTED`，不推进

**决策**：事件没有 `commandId`、或与所有 waiter 都对不上 ⇒ 进 `UNATTRIBUTED` + 告警，**不推进任何流程、不释放任何资源**。

**且歧义记录必须独立持久化**：不能随归属事务回滚一起消失，否则下次同样歧义、永远进不了人工队列。

### B-04 独占串行是调度降级，**不提供事件归属**

**决策**：设备不回显 `commandId` ⇒ 该设备降级为独占串行。但**独占串行只保证"同一时刻只有一个人在调度"，不能证明"迟到事件属于当前操作"**。

**依据**：A 释放设备后 B 持有，A 的迟到事件会被判给 B ⇒ 推进错误流程。

**推论**：这类设备的能力边界是"能跑，但事件不能自动推进流程"。

### B-05 方法名统一 `method`，不引入 `processId` / `funcName`

**决策**：

| 字段 | 处置 |
|---|---|
| `method` | 保留，三边（中控 `device_method.method` / 模拟器 / 侧车）已统一 |
| `funcName` | **不引入**，就是 `method` 的别名 |
| `processId`（事件表） | **删除**，语义从未定义，生产不填 |
| `interaction_step` | 保留，但**只服务 L5 交互守卫，不参与事件归属** |

## C. 命令身份

### C-01 `commandId` = 一次逻辑操作的唯一标识，重试复用

**决策**：

| 场景 | `commandId` |
|---|---|
| 网络重发 / 断线重连 / resume | **不变** |
| 人工重跑 / 循环下一轮 / 换批次 | **变** |

**依据**：`commandId` 是设备去重键，粒度必须是"设备认为的一次执行"。重试换 id = 让设备当成新命令 = 重复动作。

**推论**：`uk_logical_operation_cmd` **单列唯一即可**，不需要按设备档位放宽。

### C-02 不支持设备去重的设备：id 稳定，但禁止自动重试

**决策**：id 不换（换 id 问题更严重）；但这类设备断线后**只能 `queryStatus` + 人工确认**，不能自动重发。

**依据**：设备不支持去重 ⇒ 重发必然重复执行。

### C-03 `exec` 不进 `commandId`

**决策**：现状 `DriverStepExecutor:1474` 的 `-e{exec}` 是回归缺陷（resume 后 execSeq 从 0 重来，导致 id 变化）。`exec` 只保留在日志与追踪里。

### C-04 `NOT_FOUND` 一律落 `UNKNOWN`，不重发

**决策**：设备查询返回 `NOT_FOUND` ≠ 设备没执行过（可能重启丢账本、查询接口不覆盖历史）。

| 状态 | 处理 |
|---|---|
| `PENDING` | 确认没发出，可首次发送 |
| `ACKED` | 不重发，只等结果 |
| `NOT_FOUND` | `UNKNOWN`，人工 |
| `UNKNOWN` | 人工 |

## D. 设备与物理态

### D-01 三层状态分开

| 层 | 谁拥有 | 一致性 |
|---|---|---|
| **程序态** | LabOS（`run.status` / `node.status` / `command.state`） | 强一致（同库同事务） |
| **设备态** | 设备软件（在线、心跳、回包） | 最终一致（靠推断） |
| **物理态** | 现场（板在哪、夹爪夹住没有） | **只能对账，没有事务** |

**铁律**：**程序态可以回滚，物理态不能。** 把 run 标成 `failed` 不会让移过的液回去。

### D-02 物理事实 P0–P4 分级

| 级别 | 来源 | 能否推进 |
|---|---|---|
| P0 | 设备确认 + 独立传感器交叉验证 | 能 |
| P1 | 设备主动确认 | 能，标 `DEVICE_CONFIRMED` |
| P2 | 人工确认 | 能，标 `MANUAL_VERIFIED` |
| P3 | 时序推断 | **不能** |
| P4 | 无信息 | **不能** |

**注意**：当前现场**只有扫码**，没有第二证据 ⇒ **P0 实际为空集，最高可达 P1**。文档不得用 P0 做承诺。

### D-03 事实源缺失 fail-open，采集不确定 fail-closed

**决策**：

| 情况 | 处置 |
|---|---|
| **事实源缺失**（无传感器 / `physical_state IS NULL` / 配置表 0 行） | **fail-open**：跳过 + 落 `SKIP` 审计 + 告警 + 列入不可并行清单 |
| **采集到不确定**（传感器明确回 unknown / 状态过期） | **fail-closed**：阻断 |

**依据**：`StirrerDispenserGuard:88-99` 记录了 2026-11-15 的事故——配对缺失一律拒绝 ⇒ 表 0 行 ⇒ **平台每一条设备命令都被拒 ⇒ 全平台停摆**。

`physical_state` 是新增列，存量设备初值必然全是"缺失"。按 fail-closed 处理会重演事故。

### D-04 设备忙：先查状态，不直接下发

**决策**：

```
① 抢设备锁
② 查设备状态
   ├─ idle  → 下发
   ├─ busy  → 释放锁，等待一段时间，回 ①
   └─ 查不到 → 按 D-03 的 fail-open 处理
③ 超过等待上限 → EC-DEVICE-BUSY-TIMEOUT，转人工
```

**依据**：设备忙时**不接受指令**（不是排队，是拒绝）。盲发会得到 busy 错误或更糟——被覆盖。

### D-05 等待上限可配置，等待期间不持锁

| 参数 | 取值 |
|---|---|
| 查询间隔 | 按设备/方法分档（秒级 / 分级 / 分钟级） |
| 总等待上限 | **可配置，默认 30 分钟**，多并行时现场调大 |
| 等待期间持锁 | **不持** |

**依据**：持锁等待等于"名义上占着设备但没在用"，其他 run 排队却做不了事。写死一个上限等于替现场做它们做不了的判断。

### D-06 设备物理占用：派发前原子建立，带 `command_id` + `hold_epoch`

**决策**：

```
1. 派发前原子申请租约（RESERVED）      ← 不是 ACK 之后
2. 记录 owner_command_id + hold_epoch
3. ACK 到达：RESERVED → ACCEPTED
4. 完成事件：按 (device, command_id, hold_epoch) 条件清除
5. ACK 超时：→ UNKNOWN，不释放
6. 超过 TTL：复用 E-19（进 QUARANTINED，不自动释放）
7. 检查点必须放在 executeCommand 这个唯一收口
```

**依据**：三条合并——建立时机（下发→ACK 有窗口）、归属（旧事件清错新租约）、落点（不能放调度器层，否则 `ExperimentFlowRunner` 会漏）。

## E. 暂停与恢复

### E-01 实验暂停是"请求"，不是"命令"

**决策**：上层发 `Hold`，**不直接改 run 状态**；下层在动作边界自己转 `paused`。

**依据**：物理动作不能悬停——离心、孵育、机械臂承重都不能中途停。收到请求就标 `paused` 等于**伪造"已停在安全边界"**。

### E-02 暂停只在动作边界生效

**决策**：`GraphRunner` 每到一个节点边界查一次。**动作执行中不能暂停。**

**代价**：最长响应延迟 = 当前动作耗时（孵育就是 30 分钟）。急停是唯一例外。

### E-03 中间态必须可见

| 状态 | 用户看到 |
|---|---|
| `pause_requested` | 已提交 |
| `pausing` | 正在暂停（批 2/4 已确认） |
| `pause_blocked` | 卡住 + **`blocking_run_id`** + 原因 |
| `paused` | 已暂停 |

**依据**：长动作从"点了"到"真的停"隔几十分钟，UI 一直显示 `running` 会让用户重复点击或去现场干预。

**且必须与 `run.control_state` 聚合，不独立双写**——否则出现"实验 pausing、run NONE"。

### E-04 恢复前四项核对（节点级）

| 检查组 | 检查内容 | 失败处理 |
|---|---|---|
| 空间安全 | 板位、夹爪、机械臂、设备腔体 | 阻断 |
| 设备安全 | 设备是否真停、故障码 | 阻断 |
| **工艺准备** | 针是否堵、液面、耗材余量/有效性 | 阻断或人工确认 |
| 操作连续性 | 上一条命令是否完成、是否可能重复执行 | UNKNOWN 时阻断 |

**不是每个节点查全部**：加样查针/液面、转运查板位/夹爪、离心查转子/盖锁、孵育查温度/计时。

**证据必须带时效**：`observed_at` + `expires_at`，过期重查。

### E-05 `quarantined` 必须能进恢复链

**决策**：改 `isCrashRecoverable` 放行 `quarantined`。

**依据**：`resumeTx:512-520` 的判定链是 `pauseKindOfTx`（只认 `paused`）→ `isCrashRecoverable`（只认 `failed`）→ 都不满足就提前返回。**只在 SQL 加 `quarantined` 是死代码**——根本走不到那条 SQL。

## F. 资源与锁

### F-01 锁类型由实现类声明，`kind` 只做一致性校验

**决策**：

```java
public final class DeviceLock   { public static final ResourceType TYPE = DEVICE_STATE; }
public final class PositionLock { public static final ResourceType TYPE = POSITION; }
```

**依据**：调用点传类型要靠开发者记得；按 `resource_node.kind` 推导则表达不了"这次申请的是哪种锁语义"（同一节点可能既参与执行互斥又参与位置占用）。由类声明则**编译期强制**。

### F-02 申请顺序：设备 → 位置 → 轨道（前缀判定）

**决策**：

```
{} ⊂ {DEVICE} ⊂ {DEVICE, POSITION} ⊂ {DEVICE, POSITION, RAIL}
```

即**已持有的槽位集合必须是全局序列的前缀**。允许跳槽、允许同槽多次，只禁止"跳回前面"。

**依据**：真实顺序是 设备 → 位置 → 轨道；而轨道锁复用 `DeviceLock` 落在 `device_state`，若按"存储组"定 rank 会变成 1→2→1，**每次正常搬运都触发断言**。

**配套**：`RailZoneGuard` 先 `enter(RAIL)`，`DeviceLock` 内部不再按自己的 TYPE 断言。

### F-03 ThreadLocal 只做开发期断言

| 场景 | ThreadLocal 能否表达 |
|---|---|
| 同线程顺序申请 | 能 |
| 批量申请/释放 | 能（只记最高 rank） |
| 跨 step 持有 | **不能** |
| 跨线程释放 | **不能** |
| Resume 换线程 | **不能** |

**决策**：跨 step / 跨线程一律靠**显式 `owner_token`**，ThreadLocal 只负责"本线程这一串申请单调"。

### F-04 设备锁不等于设备空闲

**决策**：锁只证明"没人申请"，不证明"物理上可用"。D-04 的设备忙检查与 F-02 的锁顺序是**两件事**，不能互相替代。

## G. 并发与调度

### G-01 线程池按"执行体数"限制

防饥饿。4 批 × 4 分支 = 16 个执行体，不能无限扩。

### G-02 资源信号量按"同时占用的设备数"限制

防"把排队从流程层挪到锁层"。

**依据**：机械臂实测 9.33 秒/次，**2 个 run 已到容量边缘**。16 个执行体全在等锁，端到端时长不会变好，还多付线程与锁开销。

### G-03 并行度 = 瓶颈资源容量

```
并行度 = min over r ( floor(capacity_r / demand_r) )
```

当前硬瓶颈是机械臂，capacity≈2。**"16"是执行体数，不是并发度。**

### G-04 嵌套并行组不额外计数

内外层抢同一批设备，相乘会自我阻塞。

## H. 并行网关

### H-01 真并发：split 到 join 之间并行执行

**决策**：`SPLIT_PARALLEL` 的多个分支**同时执行**，`JOIN_PARALLEL` 汇合。

**现状**：`GraphRunner:736` 是单线程 `ready.poll()`，并行网关只是"多条路都走"。

**实现路径**：**每分支一个 `GraphRunner` 实例** + 共享 `FlowExecutionContext`，外层主循环保持单线程。

### H-02 一个分支失败 → 全体停止发新指令

```
分支 A 失败
  → stopFlag = true
  → 其他分支在下一个节点边界不再进入新节点
  → 已下发的命令：不撤回、不强杀，等回包
  → 回包后不再推进
  → 全部退出后，组标记 FAILED
```

**依据**：物理动作不能撤回。

**配套**：停止等待有上限（`drain_timeout`），超限的进 `QUARANTINED`，**不自动释放、不重新准入**。

### H-03 变量流程级共享，用 `FlowExecutionContext`

**决策**：

```java
FlowExecutionContext {
    FlowVariableStore variables;   // 共享同一实例
    AtomicBoolean stopFlag;
}
```

**关键**：现有 `withVariables` 是 `new LinkedHashMap<>(vars)`，**会复制**——每分支一个 `GraphRunner` 再调它，**各自拿到副本，根本没共享**。必须改为注入共享引用。

### H-04 禁止同一并行组内两分支写同一变量 key

**决策**：编译期检查，冲突即报错。

**依据**：变量是流程级共享的，同时写同一 key 没有"合并"这回事，只有"谁后写谁赢"——那是静默错误。

### H-05 分支不设超时

**决策**：不设执行超时。用心跳（链路健康）+ 进展监测（状态是否变化）替代，两者都只告警不判失败。

**依据**：孵育 30 分钟、离心 20 分钟都是正常业务，超时会误判。

## I. 准入

### I-01 所有入口统一走 `RunAdmission`

**决策**：`E-01` / `E-02` / `E-09` / `E-03` / `E-08` 全部接入。现状 `E-02` / `E-05` / `E-08` / `E-09` **完全不过准入**。

### I-02 准入与插入必须同一事务、同一连接

**决策**：只在 Controller 层加门禁不改事务边界，等于没修。

### I-03 全局锁序：`workflow 行 → 实验行 → run 表`

**依据**：批次路径已持实验行锁（`lockExperimentRow`），准入路径要持 workflow 行锁，反序会 ABBA 死锁。

**⚠ 已知反例**：`E-05` 的 `createNextBatchAttempt` 已在事务内持实验行锁（`BatchOrchestrator:585`），若把准入内联会反序。**处置：禁止 E-05 同事务内联**，改事务外先准入。

### I-04 提交与派发靠持久化待派发记录

**决策**：事务内写 `status='queued'` **并写待派发记录**，提交后唤醒；新增运行期僵尸扫描（阈值远小于 1 小时）。

**依据**：`StartupRecovery` 对 `queued` 是**超 1 小时**才收——那不叫兜底，叫挂一小时。
