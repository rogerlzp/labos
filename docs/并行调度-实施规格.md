# 并行调度 — 实施规格

> **这份是"照着写代码"的规格**，不是设计讨论。
> 设计讨论见各专题文档；本文件只写"要实现什么、怎么验收"。

**范围**：支持 **3 个以上实验并行**（`lab_profile.max_parallel >= 3`）。
**总工期**：**4.75 周**（5 个里程碑）。

> ⚠ **本文件的资源模型已被修正**，见 `docs/资源模型修正-出入口门与点位属性.md`。
> 主要变化：
> - **L2 出入口不是"1 个/设备"**，而是 `device_port` 表，1~N 个，有方向（in/out/both）
> - **新增 L3「门」资源**（`device_access`）——门没开，机械臂伸进去会撞机
> - **`robot_point` 补 9 个属性**（对应哪个口/哪个门/接近方向/安全高度等）
>
> 本文件第二节的"固定全序"要按修正后的顺序：
> `门 → 通道 → 位置 → 回程位 → 机械臂`，**门排在最前**（门开了但没抢到机械臂，可以关门放弃）。

## 一、资源模型

### 1.1 三层资源

| 层 | 表/字段 | 粒度 | 共享性 | 占用时长 |
|---|---|---|---|---|
| **L1 位置** | `position_state` | 一个层位 | 独立 | 任务全程 |
| **L2 出入口** | `resource_booking`（`source_type='port'`） | 一台设备一个 | 共享 | **动作级** |
| **L3 机械臂** | `resource_booking`（`source_type='robot'`） | 一个岛一个 | 共享 | **动作级** |

### 1.2 `resource_booking` 扩展

**已有表**（不用新建），复用 `period` + `ex_booking_overlap` 约束：

```sql
-- 已有的约束
EXCLUDE USING gist (resource_id WITH =, period WITH &&)
WHERE (status IN ('planned','active') AND deleted_at IS NULL)
```

**`source_type` 的取值**（新增语义，不改结构）：

| 值 | 含义 | 暂停时可释放 |
|---|---|---|
| `port` | 设备出入口 | ✅ |
| `robot` | 机械臂 | ✅（没抓板时） |
| `position-reserve` | 普通位置预留 | ✅ |
| **`position-return`** | **回程承诺** | ❌ **不可释放**（评审 R2） |

### 1.3 板位状态扩展

```sql
ALTER TABLE position_state ADD COLUMN IF NOT EXISTS
    block_reason varchar(32);
-- PLATE_UNKNOWN = 板位置未知时系统封锁，等人工盘点

ALTER TABLE plate ADD COLUMN IF NOT EXISTS
    position_status varchar(16) NOT NULL DEFAULT 'KNOWN';
-- KNOWN / UNKNOWN / LOST

ALTER TABLE plate ADD COLUMN IF NOT EXISTS
    possible_locations bigint[];
-- UNKNOWN 时的可能位置集合：{源设备, 目标设备, 机械臂}
```

## 二、资源获取协议（**最关键的 invariant**）

### 2.1 固定全序

**一次 Transfer 必须按这个顺序申请**：

```
① 源口     (L2, source 设备的 port)
② 源位     (L1, source 设备的某个位置)
③ 目标口   (L2, target 设备的 port)
④ 目标位   (L1, target 设备的某个位置)
⑤ 回程位   (L1, source_type='position-return')
⑥ 机械臂   (L3, 岛内 robot)
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   **到此为止，所有资源到手；板仍在源位，可安全放弃**
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⑦ 抓板     ← 不可逆点
⑧ 移动、放下
⑨ 释放：机械臂、源口、目标口
⑩ 回程位保持（直到板回去）
```

### 2.2 Invariant

> **所有资源申请完成前，板不离开源位。**

**任何一步失败**：

```java
// 伪代码
List<Long> acquired = new ArrayList<>();
try {
    for (Resource r : orderedRequests) {
        long id = acquire(r);   // 失败抛异常
        acquired.add(id);
    }
    // 全部到手，才抓板
    grabPlate();
} catch (AcquireFailed e) {
    releaseAll(acquired);       // 逆序释放
    // 板还在源位，状态不变，可安全重试
    return RETRY;
}
```

### 2.3 为什么顺序必须固定

| 原因 | 说明 |
|---|---|
| **消除循环等待** | 固定全序 → 不会出现"A 拿 1 等 2、B 拿 2 等 1" |
| **"拒绝"才能执行** | 只有"还没抓板"时才能安全放弃 |
| **减少持有时间** | 机械臂最后申请，持有时间最短 |

**注意**：这和"按 id 升序"不冲突——id 升序只在同类资源内有效，
跨类型必须有显式全序。

## 三、粗筛（启动前）

### 3.1 主链定义

**三种，按优先级**：

```java
String mainPath = node.attr("mainPath");           // ① 人工标记
if (mainPath == null) {
    mainPath = selectHeaviestBranch(node);          // ② 资源最重
}
if (mainPath == null) {
    mainPath = selectLongestBranch(node);           // ③ 节点最多
}
```

**`selectHeaviestBranch`**：

```java
// 算每条分支的主链设备集合大小，取最大
Branch best = null;
int maxSize = -1;
for (Branch b : node.branches()) {
    Set<Long> devices = collectDevices(b);   // 该分支用的设备
    if (devices.size() > maxSize) {
        maxSize = devices.size();
        best = b;
    }
}
```

### 3.2 粗筛算法

**资源单元 = 设备**（不是位置）。

```java
boolean canStart(long workflowId, long tenantId) {
    // ① 待启动执行的需求：主链所有设备
    Set<Long> need = mainPathDevices(workflowId);

    // ② running 执行的剩余需求
    Map<Long, Set<Long>> runningNeed = new HashMap<>();
    for (Run r : runningRuns()) {
        runningNeed.put(r.id(), remainingDevices(r));   // 从当前节点到主链结束
    }

    // ③ 已分配 = 所有 running 当前占着的设备
    Set<Long> allocated = allHeldDevices(runningRuns());

    // ④ 可用 = 总设备 - 已分配
    Set<Long> available = allDevices();
    available.removeAll(allocated);

    // ⑤ 银行家安全检测
    Map<Long, Set<Long>> work = new HashMap<>(runningNeed);
    work.put(-1L, need);                    // -1 = 待启动的
    Set<Long> W = new HashSet<>(available);
    Set<Long> done = new HashSet<>();

    boolean progress = true;
    while (progress) {
        progress = false;
        for (var e : work.entrySet()) {
            if (done.contains(e.getKey())) continue;
            if (W.containsAll(e.getValue())) {
                W.addAll(heldDevices(e.getKey()));   // 完成释放
                done.add(e.getKey());
                progress = true;
            }
        }
    }
    return done.size() == work.size();      // 全部能完成 = 安全
}
```

### 3.3 拒绝时的输出

```json
{
  "canStart": false,
  "reason": "资源不足：孵箱被 2 个执行占用",
  "estimatedWaitSeconds": 1800,
  "blocking": [
    {"runId": 123, "deviceCode": "ID1183", "nodeName": "孵育", "etaSeconds": 1800}
  ]
}
```

**`estimatedWaitSeconds` 算法**：找"最快能完成的阻塞执行"，
用 `duration_model.base` 算剩余时间（**不准，标注仅供参考**）。

## 四、细管（执行中）

### 4.1 等待图

**内存结构**：

```java
// runId → 它正在等的 run 集合
Map<Long, Set<Long>> waitFor = new ConcurrentHashMap<>();
```

### 4.2 抢资源

```java
AcquireResult acquire(Resource r, long runId) {
    // ① 直接抢
    if (tryAcquireLock(r, runId)) {
        return OK;
    }

    // ② 找到持有者
    Long holder = holderOf(r);
    if (holder == null) return RETRY;      // 瞬时竞争

    // ③ 加边
    waitFor.computeIfAbsent(runId, k -> ConcurrentHashMap.newKeySet()).add(holder);

    // ④ 环检测
    if (hasCycle(runId)) {
        waitFor.get(runId).remove(holder);   // 撤销边
        return WOULD_DEADLOCK;
    }

    return WAIT;                            // 等待，被唤醒时重试
}

boolean hasCycle(long start) {
    Set<Long> visited = new HashSet<>();
    Deque<Long> stack = new ArrayDeque<>();
    stack.push(start);
    while (!stack.isEmpty()) {
        long cur = stack.pop();
        if (!visited.add(cur)) continue;
        for (long next : waitFor.getOrDefault(cur, Set.of())) {
            if (next == start) return true;     // 回到起点 = 环
            stack.push(next);
        }
    }
    return false;
}
```

### 4.3 拒绝后的处理

```java
switch (result) {
    case WOULD_DEADLOCK:
        // 退避后重试，不让它一直转
        sleep(200 + random(300));
        retryCount++;
        if (retryCount > MAX_RETRY) {
            transitionTo(WAITING_HUMAN, "资源环检测连续拒绝");
        }
        break;
    case WAIT:
        parkUntilNotified();           // 被释放时唤醒
        break;
}
```

### 4.4 饥饿检测

```java
// 每 30 秒扫一次
for (var e : waitStartTime.entrySet()) {
    long waitedSec = now() - e.getValue();
    if (waitedSec > 600) {                     // 10 分钟
        alert("执行 " + e.getKey() + " 等待超过 10 分钟");
        // 优先级老化
        bumpPriority(e.getKey(), (int) (waitedSec / 60));
    }
}
```

## 五、暂停与恢复

### 5.1 状态机

```
pending → running → completed
            │
            ├─→ paused_fault    （设备故障，心跳恢复自动继续）
            ├─→ waiting_human   （重试耗尽/板位不一致，人工 resume）
            └─→ paused_unknown  （板位置未知，人工盘点 + 校正）
```

### 5.2 安全暂停点

```java
for (Step step : node.steps()) {
    if (shouldPause()) {
        transitionTo(pauseState());
        return;
    }
    executeStep(step);      // 一旦开始，必须跑完
}
```

### 5.3 暂停时释放资源

```java
List<Long> toRelease = bookings.stream()
    .filter(b -> b.runId() == runId)
    .filter(b -> !"position-return".equals(b.sourceType()))   // ★ 豁免（R2）
    .toList();
release(toRelease);
```

### 5.4 恢复接口

```
POST /api/runs/{runId}/resume
  ?action=continue|retry|skip|abort
  body: { "corrections": { "plate_position": {"plate": "...", "now_at": "..."} } }
```

**`corrections` 必填**（当 `paused_unknown` 时）——不校正位置，后面的板位判断全错。

## 七、实现里程碑

### M1：四层资源 + 表达式引擎（1.75 周）

| 任务 | 产出 |
|---|---|
| `resource_booking.source_type` 扩展 | `port`/`robot`/`position-reserve`/`position-return` |
| **`device_port` 表** + 三种形态配置 | 分离（in+out）/ 多进多出 / 单一（both） |
| **`device_port_usage` 信号量** | capacity=1 互斥，capacity>1 计数（用户确认物理上常见） |
| **`device_access` 门表** | 状态靠**动作结果**推断，不查询设备 |
| **`robot_point` 补 9 字段** | point_type/port_id/position_id/access_id/approach_axis/safe_z_offset/max_stack/height_mm/order_in_device |
| **`device_point_template` 模板表** | 按 device.model 自动带出属性 |
| 点位 `fill_status` | ok / pending / verified；pending 的不参与动态规划 |
| 机械臂的动作级锁 | 复用 `DeviceLock` |
| **点位 code 变量替换** | 查 `robot_point` 前先 `substVars(target)`（`ID1183-L${i}`） |
| **表达式引擎** | `${usedSlots + 1}`、`${i} % 8`、`${a > b ? 1 : 2}` |
| **`order_in_device` 必填校验** | 缺了标 `fill_status='pending'` |
| **循环展开** | 循环节点每步用不同的 `i`，展开成多个 Transfer |
| 位置自动选择（**可选**） | `firstAvailablePosition()` **默认关闭**，只在 `autoPickSlot=true` 时用 |

**验收**（5 个场景）：
```
① 分离出入口：流程1 进、流程2 出，互不阻塞
② 多进多出：4 块板同时进出（capacity 各为 1 的 4 个口）
③ 单一口：进和出互斥（同一把锁）
④ 门：门未开时拒绝进入；开门动作成功后 state='open'
⑤ 模板：新设备同步点位时，approach_axis/safe_z_offset 自动带出；
        position_id 缺失则 fill_status='pending'，不参与调度
⑥ **循环+变量**：循环 i=1..8，target='ID1183-L${i}'
        断言：展开成 8 步，每步查到的点位 code 不同
⑦ **门成对**：所有路径（成功/失败/超时/暂停）都执行关门；
        关门失败标 unknown 并告警
```

### M2：细管（1 周）

| 任务 | 产出 |
|---|---|
| 等待图 + 环检测 | `WaitForGraph` 类 |
| 固定全序申请 | `TransferResourcePlan` |
| 拒绝后退避重试 | `WOULD_DEADLOCK` + backoff |

**验收**：
```
场景：3 个流程走 A→B→C→A 环
断言：
  - 第 3 个流程被拒绝，不进入等待图
  - 前 2 个最终完成
  - 全程无死锁（2 分钟内全部结束或明确报饿）
```

### M3：主链定义（3 天，可与 M1 并行）

| 任务 | 产出 |
|---|---|
| 人工标记 `mainPath` | 流程编排页加字段 |
| 自动选"资源最重" | `selectHeaviestBranch()` |
| 自动选"节点最多" | `selectLongestBranch()` |

**验收**：
```
流程有 2 个分支（有样本/空板）
标记 mainPath=有样本
断言：粗筛按"有样本"的设备集合算
```

### M4：粗筛（1 周）

| 任务 | 产出 |
|---|---|
| 银行家安全检查 | `canStart()` |
| 启动接口返回明确信息 | `canStart` + `estimatedWait` + `blocking` |
| 队列（不能启动的排队） | `startQueue` |

**验收**：
```
场景：只有 1 个孵箱，2 个流程都要用
断言：
  - 第 1 个启动成功
  - 第 2 个返回 canStart=false，blocking 指向第 1 个
  - estimatedWait 非空
```

### M5：饥饿处理（3 天）

| 任务 | 产出 |
|---|---|
| 等待时长统计 | `waitStartTime` |
| 优先级老化 | 每 1 分钟 +1 |
| 饿死告警 | 超过 10 分钟推告警 |

**验收**：
```
场景：长任务占着设备，短任务等待
断言：短任务等 10 分钟后触发告警，优先级已提升
```

## 八、总验收（M1-M5 完成后）

### 场景 A：两块板进多板位设备

```
B 有 3 个内部位置
2 个流程各送一块板进 B
```
**期望**：并行完成，各占一个位置。

### 场景 B：三流程环

```
3 个流程走 A→B→C→A
```
**期望**：不死锁，第 3 个被拒后重试，最终全部完成。

### 场景 C：设备故障影响范围

```
流程1 用 B，流程2 不用 B
B 故障
```
**期望**：流程1 暂停，**流程2 继续**。

### 场景 D：机械臂急停

```
Transfer 中途急停
```
**期望**：板标 UNKNOWN，2 台设备全部位置封锁，告警推送，等人工。

### 场景 E：单实验降级

```
max_parallel = 1
```
**期望**：只走设备锁，不启动粗筛和等待图（性能无损耗）。

## 九、风险与前置假设

### 前置假设（**不成立就要重新评估**）

| # | 假设 | 不成立的话 |
|---|---|---|
| 1 | **实验室会配 `max_parallel >= 3`** | 4 周工作白做 |
| 2 | 岛内设备数 ≤ 20 | 等待图 DFS 可能变慢（影响小） |
| 3 | 流程分支数 ≤ 10 | 主链选择算法要优化 |
| 4 | **有人在故障时能到场** | UNKNOWN 会长期卡死，夜间模式必须开 |

### 已知风险

| 风险 | 缓解 |
|---|---|
| **主链标错** | 细管兜底（只影响体验） |
| **误拒**（保守） | 记录"被拒但本可过"的案例，定期回看 |
| **等待图误判** | 提供快照接口 `GET /api/deadlock/graph` 便于排查 |
| **粗筛的 estimatedWait 不准** | 界面标注"仅供参考" |

## 十、评审要点

**这份规格最该被挑战的地方**：

| # | 问题 |
|---|---|
| 1 | **三层资源的"动作级"边界**够明确吗？`Transfer` 算一次动作还是三次（抓/移/放）？ |
| 2 | **固定全序**（源口→源位→目标口→目标位→回程位→机械臂）在物理上合理吗？有没有"必须先抢机械臂才能开柜门"的设备？ |
| 3 | **主链粗筛的"资源最重"选择**会不会总选到异常分支（因为异常分支往往要更多设备）？ |
| 4 | **场景 C（故障影响范围）**里，"流程2 继续"会不会因为共享机械臂而实际上被阻塞？ |
| 5 | **M1 的验收**（两块板同时进 B）在真实设备上可行吗？有没有"设备同一时刻只能接受一块板"的物理限制？ |
