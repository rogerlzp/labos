## 0. 实验层要解决什么

实验层把若干流程按顺序组成一次实验，并在开跑之前把「将来要跑什么」画出来，而不是等跑起来才发现冲突。

多实验并行要自己设计。流程内部已经有 BPMN；实验层只保证顺序，以及排程可见。

---

## 1. 三层模型

```
实验（Experiment）           ← 本文件的范围
 └ 流程（Workflow）          ← BPMN，已有
     └ 节点（Node）          ← 设备动作，已有
```

### 1.1 职责边界（关键）

| 能力 | 放哪层 | 为什么 |
|---|---|---|
| 设备动作顺序 | 流程 | 已有，BPMN 原生 |
| 条件分支 | 流程（网关） | 已有，异或网关按图只走一条出边 |
| 单流程内循环 | 流程（回环） | BPMN 原生支持 |
| **实验变量** | **实验** | 跨流程共享的输入（温度、板数） |
| **跨流程循环** | **实验** | "N 个流程跑 M 轮"，BPMN 表达不了 |
| **流程间依赖** | **实验** | 流程 A 完成才跑 B |
| **资源占用声明** | **实验** | 调度器需要提前知道"这个实验要占哪些岛" |

**一句话：动作和条件归流程，数据和多轮归实验，资源冲突归调度器。**

## 2. 实验的定义

### 2.1 数据结构

```json
{
  "experimentNo": "EXP0812",
  "name": "培养箱出板",
  "priority": 50,                    // 0-100，越大越优先
  "deadline": "2026-11-01T18:00",    // 可选，用于 EDD 调度
  "variables": [
    {"name": "temp",       "type": "number", "defaultValue": "37"},
    {"name": "plateCount", "type": "number", "defaultValue": "3"}
  ],
  "steps": [
    {"seq": 1, "workflowId": 239, "params": {"temp": "${temp}"}},
    {"seq": 2, "workflowId": 648, "loopCount": "${plateCount}",
     "params": {"plateCount": "${plateCount}"}},
    {"seq": 3, "workflowId": 278}
  ]
}
```

### 2.2 变量

| 类型 | 支持 | 说明 |
|---|---|---|
| `number` | ✅ | 温度、体积、板数 |
| `string` | ✅ | 批次号、操作员 |
| `boolean` | ✅ | 开关 |
| 数组/对象 | ❌ | 复杂结构应进流程节点参数 |

**引用语法**：`${变量名}`，只在**字符串值**里替换。

```json
{"params": {"temp": "${temp}", "note": "批次-${batch}"}}
```

**替换时机**：流程启动前（一次替换，不是每节点）。理由：变量在一次实验内不变，每节点替换是浪费。

### 2.3 循环

```json
{"seq": 2, "workflowId": 648, "loopCount": "${plateCount}"}
```

| 写法 | 含义 |
|---|---|
| `null` / 缺省 | 跑 1 次 |
| `"3"` | 跑 3 次 |
| `"${plateCount}"` | 按变量值跑 |

**1.0 只做单层循环**。嵌套循环（循环里套循环）会导致：
- 展开后步骤数爆炸（3×3=9，3×3×3=27）
- 界面上难以表达和调试

真需要嵌套时，用流程层 BPMN 回环。

### 2.4 依赖（S2-A 已生效）

依赖不再用 `runAfter` 字段表达，而是落成 `experiment_process_edge` 边表（前驱 → 后继）：

```sql
-- experiment_process_edge(tenant_id, experiment_id, from_id, to_id)
```

**执行序 = Kahn 拓扑排序**（同层按 `seq` 稳定排序），有环直接拒绝。
没有边的存量数据退化为按 `seq` 升序 —— 与改动前完全一致。

**当前口径是 S2-A：只承诺偏序，物理串行推进，不承诺墙钟并发**；
要真并发必须先接三层资源 + 等待图。详见 §4.4。

## 3. 界面设计

### 3.1 编排页（编排 → 实验编排）

```
┌─ 实验 EXP0812 培养箱出板 ──────────────────────────────┐
│ 优先级 [50▾]  截止 [2026-11-01 18:00]                  │
├─ 变量 ────────────────────────────────────────────────┤
│ 名称         类型     默认值   说明                    │
│ temp         数字     37       孵育温度                │
│ plateCount   数字     3        板数                    │
│ [+ 添加变量]                                           │
├─ 流程序列 ────────────────────────────────────────────┤
│ ≡ 1. 入板流程 (2 节点)        参数: temp=${temp}   [×] │
│ ≡ 2. ⟳ 重复 ${plateCount} 次                            │
│      2.1 读板流程 (7 节点)                        [×] │
│      2.2 转板流程 (3 节点)                        [×] │
│ ≡ 3. 出板流程 (2 节点)                            [×] │
│ [+ 添加流程]  [+ 添加循环块]                           │
├───────────────────────────────────────────────────────┤
│ [保存编排]  [试算排程]  [执行]                          │
└───────────────────────────────────────────────────────┘
```

### 3.2 试算排程（关键功能）

点「试算排程」→ 不执行，只算：

```
┌─ 排程试算 · EXP0812 ──────────────────────────────────┐
│ 展开后步骤数：2 + 7×3 + 3×3 + 2 = 36 步                │
│ 预计耗时：18.5 分钟（基于 duration_model）              │
│ 占用设备：                                                │
│   Incubator_2C-1   00:00-06:00 ─────────────────      │
│   XRobot A10LR     02:00-08:00    ─────────────────   │
│   Thermo ATC       06:00-12:00       ─────────────    │
│ ⚠ 冲突：与 EXP0813 抢 XRobot（02:00-04:00 重叠）         │
│ [调整] [仍然执行]                                        │
└───────────────────────────────────────────────────────┘
```

**跑之前就能看到冲突**，而不是跑到一半卡住。

### 3.3 实验列表（带状态）

```
实验列表

编号      名称          状态       进度    优先级  预计   实际
EXP0812  培养箱出板    running    12/36   50      18.5m  4.2m
EXP0813  CMS 复核      queued     —       50      9.0m   —
EXP0814  质控           completed  8/8     30      3.0m   3.1m
EXP0815  夜班批次       failed     5/20    10      —      —
```

**状态机**：

```
draft ──┬─→ queued ──→ running ──┬─→ completed
        │      ↑         │  │     ├─→ failed ──(人工处置后恢复)──┐
        │      │         │  │     └─→ aborted（终态，不可恢复）  │
        │      │         │  └─→ paused ──(恢复)─────────────────┤
        │      │         │          ↑                          │
        │      └─────────┴──────────┘（恢复后重新排队，断点续跑）│
        └─→ cancelled                                            │
                                                                 │
        queued ◀─────────────────────────────────────────────────┘
```

- `paused`：**现场扣留**（不是单实验行为），见 §4.3。
- `failed`：**可恢复**——人工处置完成后从失败那一步续跑。
- `aborted`：**终态**——人工停止，不可恢复（要重跑请重新提交）。

## 4. 执行语义

### 4.1 一次实验的执行（节点驱动 + 动作边界检查点）

```
① 变量解析：默认值 ← 执行时传入的覆盖值
② 编译：读 experiment_process_edge → Kahn 拓扑排序得 steps；循环块按 loopCount 展开成 N 份
③ 断点续跑基线：读 experiment_run_step 中 status='completed' 的 seq:loop_index，续跑时跳过
④ 逐节点推进（物理串行）：
     每步执行前先过"动作边界闸门"：
        - 停止请求命中  → 实验 aborted（终态）
        - 现场扣留命中  → 实验 paused（不释放资源）
     替换 ${var} → 调 WorkflowService.execute(workflowId, params)
     步结果三态 → 见 §4.2
⑤ 收尾：settle() 统一把终态写进 experiment_run，并同步 experiment.status
```

**关键点：检查只发生在"动作边界"**——不打断已经下发到设备的动作。
机械臂抓着板，中途硬停只会在现场制造未知状态；所以停止/暂停最多等当前动作跑完。

### 4.2 失败处理（步结果三态）

| 步结果 | 判定 | 实验状态 | 能否恢复 |
|---|---|---|---|
| 全部节点 `COMPLETED` | OK | 继续下一步 | — |
| 有节点 `MANUAL` / `SKIPPED` | INTERRUPTED | **paused**（等人处置） | ✅ 处置后从本步续跑 |
| 其余未完成节点 | FAILED | **failed** | ✅ 人工处置后从失败那一步续跑 |

**`MANUAL`/`SKIPPED` 是"暂停"不是"失败"**：值守模式下等人干预属于正常路径，
不能被判成 failed 后无法接回（这是改动前的缺陷）。

**不做"跳过失败继续跑"**：实验室里跳过一步意味着板子位置未知，后续步骤全是错的。

### 4.3 状态变更：暂停 / 停止 / 恢复

#### 4.3.1 作用域扣留（RuntimeHold）

暂停不是"单实验行为"，而是**现场级安全事件**：同一现场（站 / 岛）里只要有实验被暂停，
其他并行实验也必须一起停下——否则机械臂还在替另一个实验搬板，人根本进不去处置。

| 作用域 | scope_id | 含义 |
|---|---|---|
| `site` | 无 | 全站扣留 |
| `island` | island_id | 整岛扣留（岛内机械臂共享，必须整岛停） |
| `experiment` | experiment_id | 单实验扣留 |

**覆盖优先级：`experiment` > `island` > `site`**。命中即停，最内层的作用域优先给出原因。

#### 4.3.2 三条不可退让的语义

1. **暂停是现场级事件**：一个实验暂停 → 同岛其他在跑/排队的实验一并落 `paused`，不是只停自己。
2. **只在动作边界生效**：不硬杀执行中的动作，等正在进行的动作跑完再停（设备动作不可中断）。
3. **扣留不释放资源**：与流程级 `PauseManager`「释放已占未用」相反——实验级暂停要求现场保持原状，
   等人工介入，擅自释放反而制造新的未知状态。

#### 4.3.3 三个动作

| 动作 | 对象 | 行为 |
|---|---|---|
| 暂停 | 运行中 / 排队中 | 按作用域 `raise` 扣留 → 受影响 run 落 `paused`（已下发的动作等它跑完） |
| 停止 | 运行中 | 置 `stop_requested`，在下一个动作边界落 `aborted`（终态，不可恢复） |
| 停止 | 非运行中 | 直接落 `aborted` + 同步 `experiment.status` |
| 恢复 | paused / failed | 解除最内层扣留（**`site` 不解除**）→ run 回 `queued` → 断点续跑 |

#### 4.3.4 断点续跑

- 步标识：`seq:loop_index`（同一 `seq` 的循环每一圈独立可续）。
- 续跑时跳过 `experiment_run_step.status='completed'` 的步。
- 被中断的步落 `status='paused'`（**不是 completed**，所以下次不会被跳过，会从该步重跑）。
- `failed` 从失败那一步重试；`aborted` / `cancelled` 是终态，只能重新提交。

#### 4.3.5 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/runtime/holds` | 当前生效的扣留列表 |
| POST | `/api/experiments/runs/{id}/pause` | 暂停（query：`scope` / `kind` / `reason`，默认 island + manual） |
| POST | `/api/experiments/runs/{id}/stop` | 停止（返回 `stopping` / `aborted`） |
| POST | `/api/experiments/runs/{id}/resume` | 恢复（解扣留 + 断点续跑） |

#### 4.3.6 界面入口（2026-11-03 补齐）

入口在「实验列表 → 点行 → 实验详情」页的「执行历史」表：

| 位置 | 内容 |
|---|---|
| 行操作列 | 排队/运行中：**暂停**、**停止**；暂停/失败：**恢复**、**停止**；终态不显示 |
| 暂停弹窗 | 选作用域 + 原因；默认 `island`（与接口默认一致，见 §4.3.5），说明"只在动作边界停、不释放板位"；未分配岛时后端自动退化为 `experiment`，**接口回实际生效作用域**（不是请求值） |
| 恢复 | 一键；被 `site` 级扣留罩住时提示"仍被现场扣留：…，先解除扣留"——不假装已恢复 |
| 停止 | 二次确认（运行中不打断、动作边界收尾、终态不可恢复） |
| 「现场扣留」卡片 | 接 `GET /api/runtime/holds`，5s 刷新；列范围/类型/原因/开始时间，当前实验的扣留打「当前实验」标；空态明确写"没有生效的扣留" |
| 「暂停原因」列 | `pause_kind`（人工暂停/设备故障/板位未知/等人工确认）+ 原因；`stop_requested` 时状态列加「停止中」 |

**为什么必须有这张卡片**：暂停是"现场闸门"，不是某条 run 的状态。只显示 run 的 `paused`
会让人以为"某个单子停了"，而实际是被覆盖的实验都停在动作边界、板位不释放。

**时间显示坑**：扣留接口给 ISO（`…T10:50:40Z`），其余接口多是 JDBC 本地时间串；
原样 `slice(0,19)` 会把 UTC 当本地显示（差 8 小时），值班员会误判"已经停了多久"。
前端 `fmtTime` 两种都归一成本地时区。

**复跑**：`scripts/verify-exp-control.py`（借空实验 → 插 2 条 queued run → 界面走
暂停→恢复→停止 → 22 条断言 → 删数据并还原状态，能反复跑）；只读冒烟由
`scripts/e2e-smoke.py` T4 覆盖（断言卡片/控制列存在，阈值 16）。

### 4.4 执行序：偏序（S2-A）

```
① 读 experiment_process（seq 只用于"同层谁先跑"的稳定排序）
② 读 experiment_process_edge 得前驱 -> 后继
③ Kahn 拓扑排序：
     - 入度为 0 的进就绪集，同层按 seq 升序取
     - 有环 → 抛错拒绝（"实验编排存在环，无法确定执行顺序"）
④ 循环块按 loopCount 复制，参数里的 ${var} 在流程启动前一次性替换
```

**S2-A 只承诺偏序，不承诺墙钟并发**：就绪集里一次取一个、物理串行推进。
所以"同层"目前只体现为**派发顺序**，不是并行执行。

**断点续跑的步标识是 `seq:loop_index`**：同一 `seq` 的循环每一圈都独立可续。

## 5. 多实验并行（本文件只给约束，算法见另一份）

### 5.1 必须解决的冲突

```
实验 A：用 Incubator_2C-1（0-6 分钟）
实验 B：也用 Incubator_2C-1（2-8 分钟）   ← 撞了
```

### 5.2 资源层级

```
岛（island）        ← 粗粒度：一个岛内的机械臂是共享的
 └ 设备（device）   ← 细粒度：单台设备同一时刻只能有一个动作
```

**为什么要有岛级锁**：岛内的机械臂负责搬板，两个实验同时在同一个岛跑，机械臂会打架——即使它们用的是不同的孵箱。

### 5.3 1.0 的并行策略（保守）

| 策略 | 1.0 | 说明 |
|---|---|---|
| 岛级互斥 | ✅ | **一个岛同一时刻只跑一个实验** |
| 设备级互斥 | ✅ | 跨岛共享设备时（少见）加锁 |
| 优先级抢占 | ❌ | 不抢占，高优先级排队 |
| 时间片轮转 | ❌ | 不做 |
| 死锁检测 | ✅ | 超时 + 全局顺序 |

**岛级互斥的代价**：并行度 = 岛数（26）。但这是**安全的下界**——不会出现机械臂打架。

**为什么不做岛内多实验并行**：需要精确的"机械臂占用时间窗"建模，而工时精度只有 10 秒级（已知问题），做不准。

> 等新系统积累 3 个月真实时长数据，再放开岛内并行。

## 6. 数据模型（新增部分）

```sql
-- 实验变量
experiment_variable (id, experiment_id, name, type, default_value, description)

-- 实验主表加列
ALTER TABLE experiment ADD COLUMN priority int DEFAULT 50;
ALTER TABLE experiment ADD COLUMN deadline timestamptz;
ALTER TABLE experiment ADD COLUMN started_at timestamptz;
ALTER TABLE experiment ADD COLUMN finished_at timestamptz;

-- 编排表加列（已建）
experiment_process (..., loop_count varchar(64), params_override jsonb)

-- 实验执行记录（新表）
experiment_run (
  id, tenant_id, experiment_id,
  status,              -- queued/running/paused/completed/failed/cancelled
  variables jsonb,     -- 本次执行的实际变量值
  expanded_steps int,  -- 展开后步骤数
  started_at, finished_at,
  current_seq int,     -- 正在跑第几步
  error text
);

-- 每步的执行记录
experiment_run_step (
  id, experiment_run_id, seq, loop_index,
  workflow_id, run_id,     -- 关联 workflow_run
  status, started_at, finished_at, error
);
```

## 9. 与现有系统的衔接

| 现有能力 | 复用方式 |
|---|---|
| `WorkflowService.execute()` | 实验执行器调它跑每个流程 |
| `run` / `run_node` / `run_command` | 每个流程一个 run，实验层只存 run_id |
| `device_state` | 调度器判断"设备是否被占" |
| 值守模式 | 实验继承（experiment_run 存 attendance） |
| 恢复策略 | 流程内部走，实验层不重复实现 |
| 告警 | 流程失败 → 告警 → 实验 paused |

## 10. 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 时长精度 10 秒级 | 排程试算不准 | 用 p90 而非 p50 |
| 岛级互斥降低并行度 | 26 个岛最多 26 个实验并行 | 1.0 可接受 |
| 变量替换在启动前 | 执行中改变量不生效 | 明确写在界面上 |
| 展开后步骤数爆炸 | 100 步 × 10 轮 = 1000 步 | 限制 `loopCount ≤ 20`，总步数 ≤ 500 |

## 十一、画布编排（v0.2 补充）

### 11.1 节点的完整类型

| 类型 | 颜色 | 作用 | 执行语义 |
|---|---|---|---|
| **开始** | 绿 | 流程入口 | 无 |
| **结束** | 灰 | 流程出口 | 无 |
| **设备** | 青 | 在某台设备上执行一个方法 | 真实调用驱动 |
| **流程** | 蓝 | 跑一条已有 workflow | 子流程 |
| **变量** | 紫 | 定义/赋值 | 写入变量表 |
| **分叉** | 橙 | 按条件走两条路 | 条件求值 |
| **并行** | 绿 | 同时跑多条 | 受岛级互斥约束 |
| **循环** | 粉 | 重复 N 次 | 展开 |

### 11.2 开始/结束节点为什么必须自动带入

**不自动带的话，执行入口靠猜**：

```java
// 这种写法在图有环、或多起点时会选错
const start = nodes.find(n => !incoming.has(n.id));
```

**带了之后**：

```
● 开始（无入边连接点，物理上不能连到它）
  ↓
... 业务节点 ...
  ↓
● 结束（无出边连接点，物理上不能从它连出去）
```

**UI 层面就杜绝了非法操作**，比执行时校验更好。

### 11.3 拖入设备自动插入

**问题**：拖 5 台设备要拉 6 次线，漏一根的表现是"后面几步不执行"，看不出原因。

**做法**：

```
拖入设备 N
  ↓ 找指向「结束」的边
  ↓ 改成指向 N
  ↓ 加一条 N → 结束
  ↓ 结束节点下移 130px
```

视觉效果就是"插进去"，用户不需要理解边的重连。

### 11.4 变量传递的三个层次（核心）

这是实验编排区别于"一串动作列表"的关键。

#### 层次 ①：静态变量

```
变量节点  plateCount = 2
                    ↓
设备节点参数 {"cycles": "${plateCount}"}
                    ↓ 执行时替换
              {"cycles": 2}
```

**何时确定**：建图时。

**适用**：用户事先知道的参数（温度、次数、板数）。

#### 层次 ②：节点输出

```
设备节点 A
  方法：BarcodeScan
  输出：plateId=plate      ← 配置"取返回 JSON 的 plateId，存进 ${plate}"
       ↓ 执行
  驱动返回 {"plateId": "PL-2026-001", "code": 0}
       ↓ 解析
  ${plate} = "PL-2026-001"
       ↓
设备节点 B 参数 {"plate_id": "${plate}"}
       ↓
  {"plate_id": "PL-2026-001"}
```

**何时确定**：执行到该节点之后。

**适用**：条码扫描结果、设备状态、上一步的产出。

#### 层次 ③：表达式计算

```
变量节点  total = ${plateCount} * 2
```

**何时确定**：执行时求值。

**状态**：未实现（需要表达式引擎，且不能是 eval）。

### 11.5 层次 ② 为什么需要"逐步执行"

**现在的执行方式**：

```
整条链 → 一次性生成 workflow → 整体执行
```

**问题**：生成 workflow 时变量还没值——**因为还没执行，哪来的返回值**。

**必须改成**：

```
解析出第 1 步
  ↓ 替换参数（用当前变量）
  ↓ 执行
  ↓ 拿返回原文
  ↓ 按 output 配置解析出变量
  ↓ 累积到变量表
解析出第 2 步
  ↓ 用更新后的变量表替换参数
  ...
```

**代价**：

| 项 | 一次性生成 | 逐步执行 |
|---|---|---|
| 执行速度 | 快（一次调度） | 慢（每步一次调度） |
| 变量回填 | ❌ 不可能 | ✅ |
| 失败重试粒度 | 整流程 | 单步 |
| 执行记录 | 一条 run | N 条 run（或一条 run 多个节点） |

**结论**：要做数据流，必须逐步执行。1.0 接受速度损失。

### 11.6 输出变量配置格式

```
plateId=plate
```

- 左边：驱动返回 JSON 的字段名（支持 `a.b` 点号取嵌套）
- 右边：变量名

**为什么不用 JSON 配置**：

```json
{"outputs": [{"from": "plateId", "to": "plate"}]}
```

单个输出用 `k=v` 更短，界面上一个输入框就够。多个输出用逗号分隔。

### 11.7 执行时的形状

```
开始
  ↓
变量 plateCount=2           ← 写变量表
  ↓
设备 ID0000 / LoadFile      ← 执行；若配了 output 则回填
  ↓
分叉 ${plateCount} > 1      ← 求值选路
  ├─ true  → 循环 ${plateCount}
  │            ↓
  │          设备 ID1731        ← 重复 2 次
  │            ↓
  └─ false → 设备 ID1775
               ↓
结束
```

**注意**：分叉的两条路最终要汇合到「结束」（或一个汇合节点），否则会有一条路走不完。

## 十二、技术实现（执行模型）

### 12.1 图的存储

```sql
experiment_graph (
  experiment_id UNIQUE,
  graph jsonb
)
```

```json
{
  "nodes": [
    {"id":"dev-1","type":"kindNode","position":{"x":240,"y":80},
     "data":{"kind":"device","label":"ID0000","resourceId":200206,
             "capability":"ALIQUOT","ip":"192.0.2.10",
             "method":"LoadFile","output":"plateId=plate"}}
  ],
  "edges": [{"id":"e1","source":"start-1","target":"dev-1"}]
}
```

**为什么用 jsonb 不拆表**：图的形状随需求变（以后可能加"汇合""等待""子流程"），
拆表要频繁改 schema；而图只在整体读写、不按节点查询，jsonb 够用。

### 12.2 执行管线

```
① 从开始节点出发，沿 source→target 遍历（seen 集合防环）
② 按类型处理
   ├ start/end   → 跳过
   ├ variable    → 写变量表（值里的 ${x} 先替换）
   ├ device      → 收集 (resourceId, method, output)
   ├ loop        → 记 loopFrom + 次数
   ├ fork        → 条件求值，选一条出边
   └ parallel    → 1.0 跳过
③ 循环展开：主链走完后，把 steps[loopFrom..] 复制 (n-1) 遍
④ 逐步执行，每步之间传递变量
```

**③ 为什么在主循环外做**：回跳要改 `cur`，而 `cur` 重复会被 `seen` 挡住，
主循环立刻退出。所以先走完单链，最后统一复制。

### 12.3 变量替换

```java
"${plate}"  →  vars.get("plate")
```

**找不到的变量保留原样**（`${plate}`），不替换成空串——
执行时看到 `${plate}` 一眼能看出"变量没定义"，看到空串只会猜"参数漏填了"。

**替换后纯数字转 Long**：驱动对类型敏感，`"7"` 和 `7` 在某些协议里不是一回事。

### 12.4 执行器状态管理

```java
workflows.withIsland(isl).withVars(vars).execute(id);
finally {
    workflows.withIsland(null);      // 忘了清会让下个请求莫名沿用
    workflows.withVars(Map.of());
}
```

**为什么用 Service 字段而不是逐层传参**：参数在 `loadMethodParams` 里就转成 Map 了，
再往回改签名要动 4 个方法；一次执行就是一个 Service 实例的生命周期。

### 12.5 逐步执行 vs 一次性生成

| 维度 | 一次性生成 | 逐步执行 |
|---|---|---|
| 变量回填 | ❌ | ✅ |
| 执行速度 | 快 | 慢（每步一次调度） |
| 失败粒度 | 整流程 | 单步 |

**结论**：要做节点间数据流，必须逐步执行，1.0 接受速度损失。

### 12.6 安全边界

**不用 `eval` / `Function()` 求值条件与表达式**：

画布内容来自用户输入（存在数据库里、可能被复制粘贴），`eval` 等于把浏览器交给别人写代码。

只支持固定形式：

```
左值 运算符 右值                （条件）
"${a} > 37"  → 解析 → a > 37
```

**循环次数上限 20**：`Math.min(20, ...)`，防止 `${n}` 传 10000 把流程撑爆。

### 12.7 待实现

| 项 | 说明 |
|---|---|
| 输出变量回填 | 每步执行后从驱动原文解析字段写入变量表 |
| 表达式求值 | `${a} + ${b}` 算术，需要表达式引擎 |
| 分叉汇合点 | 现在分叉两条路都指向结束，没有"汇合后继续" |
| 并行 | 受岛级互斥约束 |

## 十四、板子转运：机械臂如何被自动调用

### 14.1 问题

用户连线 `设备A → 设备B`，期望"板子从 A 搬到 B"。

但一个箭头**只代表一次执行**，而真实搬运是：

```
A 放板  →  机械臂抓取移动放置  →  B 收板
```

**如果每个箭头只执行 A 或 B 自己的方法，板子永远搬不过去。**

### 14.2 关键发现：机械臂有 Transfer 方法

```
ID1731 (XRobot A10LR)
  ├ Transfer            source(select,必填) target(select,必填) consumable(number)
  ├ Pick / Place        抓 / 放
  ├ Move                移动
  ├ GripAction          夹爪动作
  └ Home / ReturnToSafe 归位
```

**`Transfer(source, target)` 正是"从 A 搬到 B"的原子操作**。

### 14.3 自动展开规则

遍历路径上的设备节点时，检查**相邻两站**：

```
上一站不是机械臂 && 这一站不是机械臂
  ↓
在中间插入：机械臂.Transfer(source=上一站编号, target=这一站编号)
```

**为什么两端都不是机械臂才插**：
- 如果上一站本身就是机械臂（比如刚搬完），不用再插
- 如果这一站是机械臂，它自己会动，不需要"搬过去"

### 14.4 实测

图：`开始 → ID1731(机械臂) → 分叉 → ID1775(培养箱) → 汇合 → ID1183(培养箱) → 结束`

执行记录：

| 序 | 方法 | 参数 | 说明 |
|---|---|---|---|
| 1 | `Home` | resourceId=200214 | 机械臂归位（用户显式配的） |
| 2 | `Deposit1` | resourceId=200210 | ID1775 放板 |
| 3 | **`Transfer`** | **source=ID1775, target=ID1183** | **自动插入的搬运** |
| 4 | `Deposit1` | resourceId=200171 | ID1183 收板 |

**第 3 步是系统自动补的**，参数直接用了两端设备的编号。

### 14.5 机械臂怎么找

```ts
const arm = islandDevices.find((x) => x.capability === 'TRANSFER');
```

**取当前岛上第一个 TRANSFER 能力的设备**。

**局限**：一个岛有多台机械臂时，永远用第一台。要精确控制需要：
- 在设备节点上加"用哪台机械臂搬"的配置
- 或者画布上显式插入机械臂节点（`A → 机械臂 → B`）

### 14.6 source/target 用什么值

传的是**设备编号**（`ID1775` / `ID1183`），不是位置码。

**为什么**：`Transfer` 的参数是 `select` 类型，选项来源还没确认。
传设备编号是最直观的——机械臂知道"ID1775 这台机器在哪"。

**如果驱动要的是位置码**（如 `I4495`），需要：
1. 前端从设备的层位里取第一个空位
2. 或者驱动侧做映射

### 14.7 还没做的（诚实）

| 项 | 说明 |
|---|---|
| 自动补 A 放板 / B 收板 | 现在只插 `Transfer`，A/B 自己的动作靠用户配 |
| 机械臂选择 | 永远用岛上第一个 TRANSFER |
| source/target 值格式 | 传设备编号，驱动是否认还需现场验证 |
| 抓取防错 | 板子在空设备上时不该搬——需要 `has_plate` 预检 |

## 十五、机械臂点位与板位预检

### 15.1 为什么需要点位

机械臂的 `Transfer(source, target)` 参数是 `select`，值**不是设备编号，而是点位码**。

现场流程：

```
机械臂示教 → 拖到每个设备前 → 记下坐标 → 保存为点位（如 PT-001）
     ↓
导出点位表（Excel / XML）
     ↓
导入本系统 robot_point 表
     ↓
流程里 Transfer(source="PT-001", target="PT-002")
```

**为什么不用设备编号**：机械臂只知道"坐标"，不知道"这是哪台设备"。
点位就是"设备坐标"的命名。

### 15.2 表结构

```sql
robot_point (
  island_id, robot_resource_id, code, name,
  x, y, z,                    -- 坐标（示教得到的）
  device_resource_id,         -- 关联哪台设备
  action,                     -- Pick / Place / PickPlace
  synced_at                   -- 上次同步时间
)
UNIQUE (tenant_id, robot_resource_id, code)
```

**`device_resource_id` 的作用**：让界面能显示"PT-001 = ID1775 培养箱"，
而不是一串坐标。用户选点位时看得懂。

### 15.3 首次没有点位表怎么办

提供 `POST /api/islands/{id}/robot-points/sync?robotResourceId=`：

```sql
INSERT INTO robot_point (island_id, robot_resource_id, code, name, device_resource_id, action)
SELECT ?, ?, d.code, d.name, d.id, 'PickPlace'
FROM resource_node d
WHERE d.parent_id = ? AND d.kind = 'device' AND d.id <> ?
```

**点位 code 直接用设备编号**（`ID1775`）——这样 `Transfer` 的 source/target
传设备编号就能工作，不用等现场出点位表。

**后续**：现场示教后，把真实坐标回填到 `x/y/z`，`code` 可以改成 `PT-001` 之类。

### 15.4 板位预检

**问题**：机械臂抓空会报错，但错误信息是"抓取失败"——现场得猜是点位错了、还是板不在。

**做法**：执行 `Transfer` 前查源设备的 `device_state.has_plate`。

```java
if (method.startsWith("Transfer")) {
    Object src = params.get("source");
    // 查 has_plate，false 就拦下
    return src + " 上没有板，不能搬";
}
```

**实测**：

| 场景 | 结果 |
|---|---|
| 源设备无板 | `failed`：`ID1775 上没有板，不能搬` |
| 源设备有板 | `completed` |

**为什么只在 Transfer 前查**：`Home`/`Deposit` 不涉及"从某处抓"，
查了反而误拦（Deposit 是往设备里放板，源设备本来就没板）。

**预检失败不阻断落库**：仍然插 `run_node`（status=failed，error_code=EC-PLATE-PRECHECK），
运维能查到"是预检拦的，不是设备报错"。

### 15.5 参数格式的坑

`steps` 格式是 `id:method:output:params`，**四段**。

```
200214:Transfer::source=ID1775;target=ID1183
              ↑↑
              两个冒号：output 为空
```

**写成三段**（`200214:Transfer:source=...`）会把参数当成 `output`，
`params` 为空，预检拿不到 source 就静默放行——**表现为"预检没生效"**。

**这个坑很隐蔽**：不报错，只是预检不触发。

### 15.6 点位示教（界面）

设备节点属性面板底部：

```
机械臂点位（示教）
点位码 = 设备编号，填当前机械臂停在这台设备前的坐标
  [X: ____] [Y: ____] [Z: ____]  [记点位]
```

点「记点位」→

```bash
PUT /api/islands/{id}/robot-points/{code}
    ?action=PickPlace&deviceResourceId=200210
    body: {"x": 420}
→ {"updated": 1, "code": "ID1775"}
```

**现场用法**：

```
① 在机械臂示教器上把机械臂拖到 ID1775 前方
② 读出示教器上的坐标（或点"读取当前位置"）
③ 在画布上选中 ID1775 节点，填坐标，点「记点位」
④ 点位表里这条的 x/y/z 就更新了
```

**为什么不在画布上画坐标**：机械臂是三维的（x/y/z + 姿态），
画布是二维的，画出来会误导。**填数值更准确**。

**`updated=0` 的含义**：这个点位还不存在。要先在岛屿视图点「同步点位」，
或者直接调 `POST /robot-points/sync`。
