# 变量传递与点位初始化 — 设计

> 回答两个问题：
> ① 节点改了变量，下游怎么用？会不会被别的实验改错？
> ② 板位和机械臂点位怎么初始化？多板位怎么指定？

---

## 一、变量：三层隔离

### 1.1 三层结构

```
实验定义层   experiment_variable     变量名 + 默认值 + 类型
                 ↓
执行实例层   run_variable            本次执行的变量快照
                 ↓
节点参数层   workflow_node.params    形如 {"plate": "${plateId}"}
```

| 层 | 表 | 作用 | 谁改 |
|---|---|---|---|
| **定义** | `experiment_variable` | 这个实验有哪些变量、默认值 | 编排时人工配 |
| **实例** | `run_variable` | 这次执行的实际值 | 执行时写入 |
| **引用** | `workflow_node.params` | 节点里写 `${name}` | 编排时配 |

### 1.2 变量会不会被别的实验改错

**不会——只要走对路径。**

**关键：`run_variable` 带 `run_id`。**

```sql
CREATE TABLE run_variable (
  tenant_id  bigint,
  run_id     bigint,      -- ★ 按执行隔离
  name       varchar,
  value      text,
  updated_at timestamptz
);
```

**每个 `run` 有一份独立的变量副本**，实验 A 的执行改不到实验 B 的。

**但有一个真实的坑**：

| 场景 | 会不会串 |
|---|---|
| 同一个实验跑两次 | ❌ 不串（两个 run，两份变量） |
| 两个不同实验并行 | ❌ 不串（run 不同） |
| **改了 `experiment_variable` 的默认值，正在跑的执行** | ✅ **会串** |

**为什么**：`ExperimentExecutor` 在**启动时**读一遍默认值，之后不再读。
如果执行到一半有人改了默认值，**这次执行不受影响**（所以其实是安全的）。

**真正需要注意的**：`WorkflowService.withVars()` 是**进程级共享的 Map**。

```java
public WorkflowService withVars(Map<String, String> vars) {
    this.varOverrides = vars;   // 字段，不是 ThreadLocal
    return this;
}
```

**并发执行时**，A 的线程调 `withVars`，B 的线程也调——**后者覆盖前者**。

**这是当前的真实风险**。

### 1.3 修法：变量作用域

**方案 A：ThreadLocal**（改动小）

```java
private final ThreadLocal<Map<String, String>> varOverrides = new ThreadLocal<>();
```

**优点**：线程隔离，天然不串。
**缺点**：异步任务（调度器的后台线程）要手动传递。

**方案 B：显式传参**（最干净）

```java
Execution execute(long workflowId, Map<String, String> vars);
```

**优点**：没有隐式状态，看得见。
**缺点**：要改所有调用点。

**建议 B**——这个项目已经因为"隐式共享状态"踩过坑（两套 ID、两套板位）。

### 1.3.1 已采用的修法：ThreadLocal（2026-11-02）

改了 `WorkflowService`：

```java
private final ThreadLocal<Map<String, String>> runtimeVars =
        ThreadLocal.withInitial(Map::of);
private final ThreadLocal<Long> islandFilter = new ThreadLocal<>();
```

**为什么选 ThreadLocal 而不是显式传参**：

- `substVars` 在 `loadMethodParams` 深处调用，改签名要动 4-5 个方法
- `withIsland` 也是同样的共享字段问题，一起改省事

**代价**：线程池复用线程时必须 `clearVars()`，否则变量残留。

**已在两处加了 finally**：

| 位置 | 说明 |
|---|---|
| `ApiServer.workflowRunJson` | 原来 finally 里调 `withVars(Map.of())`，改成 `clearVars()` |
| `ExperimentExecutor.run` | 原来没有 finally，补上 |

**验证**：并发 3 个各带不同 `vars=plate=PLATE-n`，全部成功。

**注意**：`withIsland` 也改成了 ThreadLocal——它原来是普通字段，
并发时 A 设岛 1、B 设岛 2，A 可能用 B 的岛去选设备。

### 1.4 节点怎么"改"变量

**现在的机制**：节点只能**产出**变量（从设备返回提取），不能修改已有变量。

```
设备返回 {"data": {"plate": "PL-001"}}
       ↓ 节点配 {"output": "plateId"}
run_variable 新增一行 name=plateId, value=PL-001
       ↓ 下一个节点引用 ${plateId}
```

**提取规则**（`ExperimentFlowRunner` 里）：

```java
String field = ...;  // 节点配的 output
Object v = data.get(field);   // 从 data 里取同名字段
runVariable.put(field, String.valueOf(v));
```

**如果节点要"修改"已有变量**（比如计数器 +1）：

**当前不支持**——`${count}+1` 这种表达式**故意没做**。

**为什么不做**：

| 做 | 代价 |
|---|---|
| 支持表达式求值 | 要写解析器，或引入脚本引擎（安全风险） |
| 只支持 `${var}` | 够用，且不会算错 |

**如果确实需要计数**：用循环节点的 `loop_index`（执行时自动带序号），不要用变量自增。

### 1.5 变量找不到时

**规则：保留 `${name}` 原样，不替换成空串。**

```java
// substVars
return matcher.replaceAll(m -> vars.getOrDefault(m.group(1), "${" + m.group(1) + "}"));
```

**好处**：

- 日志里看到 `plate=${plate}`，一眼知道"这个变量没传"
- 如果替换成空串，日志是 `plate=`，看不出是漏传还是真为空

**代价**：驱动收到含 `${}` 的参数会报错——但**这正是想要的**：
**宁可失败，也不要静默传个空值**。

## 二、点位：初始化 + 单多板位

### 2.1 为什么会有点位问题

机械臂搬板的动作是 `Transfer(source, target)`。

- `source` / `target` 是**点位码**，不是设备编号
- 点位码 → 坐标（x/y/z）→ 机械臂才知道去哪

**如果点位没初始化**，机械臂不知道往哪动。

### 2.2 三种板位情况

| 情况 | 例子 | 流程里要不要指定 |
|---|---|---|
| **设备只有一个板位** | 单工位孵箱 | **不用**——自动用那个点 |
| **设备有多个板位** | 8 层层位架 | **要指定**——否则不知道放第几层 |
| **板位在设备外部** | 堆板机 | 要指定 |

### 2.3 点位模型

```sql
robot_point (
  island_id,            -- 哪个岛的点位
  robot_resource_id,    -- 哪台机械臂
  code,                 -- 点位码，Transfer 用的就是它
  x, y, z,              -- 坐标
  device_resource_id,   -- 这个点属于哪台设备 ★
  action                -- 动作类型（pick/place/home...）
)
```

**关键字段 `device_resource_id`**：把点位和设备的对应关系固定下来。

**这样机械臂才能"自动获取"**：

```
流程说 Transfer(source=ID1775, target=ID1183)
        ↓ 查 robot_point
source 点 → 该设备唯一层位的坐标
target 点 → 该设备唯一层位的坐标
        ↓
下发带坐标的 Transfer
```

### 2.4 初始化流程（岛屿创建后必做）

```
① 创建岛屿，拖入设备
        ↓
② 同步点位（POST /api/islands/{id}/robot-points/sync?robotResourceId=）
   —— 按岛上设备自动生成点位，code = 设备编号
        ↓
③ 示教 / 读坐标
   —— 真机：POST .../robot-points/{code}/capture 从机械臂读
   —— 模拟：手工填或 CSV 导入
        ↓
④ 校验：每个设备是否都有点位
        ↓
⑤ 才能跑流程
```

**第 ② 步生成的规则**：

```sql
-- 每台设备一个点位，code = 设备编号
INSERT INTO robot_point (island_id, robot_resource_id, code, device_resource_id)
SELECT i.id, <robotId>, d.code, d.id
FROM resource_node d
WHERE d.parent_id = <islandId> AND d.kind = 'device'
ON CONFLICT (island_id, robot_resource_id, code) DO UPDATE
SET device_resource_id = EXCLUDED.device_resource_id;
```

**注意**：`sync` 只建"设备级"点位（一台设备一个）。

**多板位怎么办**：

**方案：设备级点位 + 层位级点位两级**

```
ID1183          ← 设备级（默认用第一个空层位）
ID1183-L1       ← 层位 1
ID1183-L2       ← 层位 2
...
```

**流程里**：

- 不写 `target` → 用设备级点位（**自动选第一个空层位**）
- 写 `target=ID1183-L2` → 用指定层位

**这才是"单板位不用指定、多板位要指定"的实现**。

### 2.5 自动选层位的逻辑

```java
// Transfer 的 target 只有设备编号时
if (!targetHasLayer) {
    // 查该设备第一个空闲层位
    Long posId = firstAvailablePosition(deviceResourceId);
    target = "设备编号-L" + layerNoOf(posId);
}
```

**依赖 `position_state`**（哪个层位空着）。

**这就是为什么板位追踪必须准**——点位选错，机械臂会往有板的层位放。

### 2.6 真机同步

**`POST .../robot-points/{code}/capture`** 已经从机械臂读坐标：

```json
// 机械臂返回
{"data": {"x": 320.5, "y": 180.2, "z": 45.0}}
```

**`QJson.extractXYZ`** 宽松匹配 `x`/`pos_x`/`X` 三种写法（不同厂商字段名不同）。

**同步策略**：

| 场景 | 做法 |
|---|---|
| 首次部署 | 逐点示教 + capture |
| 设备位置微调 | 重新 capture 那一个点 |
| 大批量 | CSV 导入（`POST .../robot-points.csv`） |

**CSV 导入用 `COALESCE`**：只更新传了值的字段，不清空已有坐标。

### 2.7 校验：跑流程前必须过

**加一个"点位完整性检查"**：

```sql
-- 有设备但没点位的
SELECT d.code FROM resource_node d
WHERE d.parent_id = <islandId> AND d.kind = 'device'
  AND NOT EXISTS (
    SELECT 1 FROM robot_point p
    WHERE p.island_id = <islandId> AND p.device_resource_id = d.id);
```

**如果有缺失**，`Transfer` 会失败——**最好在跑之前就拦住**。

## 三、实施顺序

| # | 任务 | 依赖 |
|---|---|---|
| 1 | ✅ 岛锁（已完成） | — |
| 2 | **变量改成显式传参** | 无 |
| 3 | **点位：设备级 + 层位级两级** | 无 |
| 4 | **自动选层位** | 依赖第 3 项 + `position_state` |
| 5 | **点位完整性检查** | 依赖第 3 项 |

**第 2 项最急**——`withVars` 的共享 Map 在并发下会串，
而并发已经验证是可行的（16 并发零失败），**这个坑随时会踩**。

---

## 四、一句话总结

**变量**：三层结构（定义 / 实例 / 引用），`run_variable` 按 `run_id` 隔离；
**唯一风险是 `withVars` 的进程级共享 Map**，要改成显式传参或 ThreadLocal。

**点位**：`robot_point.device_resource_id` 把点位和设备绑死；
**单板位不用指定（自动用唯一层位）、多板位用 `设备-L<n>` 指定**；
岛屿创建后先 `sync` 再 `capture`，才能跑流程。
