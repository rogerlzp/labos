# 现场部署手册

> 给现场工程师用。按顺序做，每步都有明确的"通过标准"。
> **任何一步没过，不要往下走。**

---

## 零、上现场前先确认

| 项 | 怎么确认 |
|---|---|
| 实验室网络能通 | `ping <驱动服务IP>` |
| 驱动服务已启动 | `nc -z <IP> 8501` 或 `telnet <IP> 8501` |
| 数据库可连 | `psql -h <DB_IP> -U <用户> -d labdb -c "select 1"` |
| 中控机器时间准确 | `date`（时间不准会导致超时判断错） |
| 有回滚方案 | 数据已备份，并且能退回上线前的控制方式 |

## 一、部署中控

### 1.1 上传代码

```bash
# 目标机器上
mkdir -p /opt/labos && cd /opt/labos
# 用 scp / rsync 把仓库传上来
```

### 1.2 建库

```bash
cd /opt/labos/pg_rebuild

export HOST=<DB_IP> PORT=5432 DB=labos
export USER_DB=<DB用户> PASS_DB=<DB密码>

./schema/run_schema.sh          # 建 98 张表
psql ... -f schema/99_verify.sql # 校验
psql ... -f schema/95_seed_data.sql  # 可选：初始数据
```

**通过标准**：`99_verify.sql` 全绿，`select count(*) from resource_node` 有数据。

### 1.3 启动内核

```bash
cd /opt/labos/labos-kernel
javac -encoding UTF-8 -d out $(find src -name '*.java')

LABOS_DB_HOST=<DB_IP> \
LABOS_DB_NAME=labdb \
LABOS_DB_USER=<用户> \
LABOS_DB_PASS=<密码> \
nohup java -Dfile.encoding=UTF-8 \
     -cp "out:lib/postgresql-42.7.3.jar" \ >> /opt/labos/api.log 2>&1 &
```

**通过标准**：

```
[调度] 已启动（岛级互斥，最多 4 个实验并行）
```

```bash
curl -X POST http://localhost:18080/api/auth/login \
     -d '{"username":"admin","password":"admin123"}'
# 返回 token 即成功
```

### 1.4 启动前端

```bash
cd /opt/labos/webapp
npm install && npm run build
# 用 nginx 或 npm run preview 提供静态文件
```

## 二、接设备（核心）

### 2.1 改驱动端点配置

驱动服务（.NET Sidecar）的 `appsettings.json`：

```json
{
  "EquipmentDriver": {
    "Servers": [
      { "endpoint": "tcp://<设备服务IP>:8501" }
    ]
  }
}
```

**注意**：一个端点管**多台设备**。如果实验室有多个驱动服务，配多行。

### 2.2 数据库里登记端点

```sql
-- 看现有端点
SELECT id, code, endpoint FROM driver;

-- 新增/修改（一条 endpoint 对应一个驱动服务）
UPDATE driver SET endpoint = 'tcp://<IP>:8501' WHERE code = 'DRV-xxx';
```

### 2.3 确认设备归属

```sql
-- 每台设备必须挂到一个 driver 上，否则报 EC-06-0001
SELECT r.code AS 设备, d.code AS 驱动, d.endpoint
FROM device_instance di
JOIN resource_node r ON r.id = di.resource_id
LEFT JOIN driver d ON d.id = di.driver_id
WHERE di.deleted_at IS NULL;
```

**`驱动` 或 `endpoint` 为空的，必须先补上**。

## 三、验证（按顺序，不能跳）

### 第 1 步：单命令探针（最安全）

**选 `Home`（归位）**——它不碰板、不撞东西。

```bash
curl -X POST "http://localhost:18080/api/shadow/probe?resourceId=<设备resource_id>&method=Home"
```

**通过标准**：

```json
{
  "ok": true,
  "elapsedMs": 87,
  "contract": {
    "messageId": true,
    "messageType": true,
    "method": true,
    "methodStatus": true
  }
}
```

**契约四项全 true 才算通**。有一项 false，看 `rawResponse` 里实际字段名叫什么。

### 第 2 步：这台设备的关键方法

按顺序试：`Home` → `GetStatus`（如果有）→ 真正的动作（`Deposit1` 等）。

**每试一个方法，记录 `elapsedMs`**——这是真实耗时，后面配超时要用。

### 第 3 步：整流程影子

```bash
curl -X POST "http://localhost:18080/api/workflows/<流程id>/shadow-run"
```

**不发命令**，只返回"会发什么"。

**通过标准**：
- 每个节点落到**对的设备**
- 方法名**对**（`Deposit1` 不是 `Deposit1Ex`）
- 参数替换后**值合理**

### 第 4 步：单流程实跑

```bash
curl -X POST "http://localhost:18080/api/workflows/<流程id>/run?islandId=<岛id>"
```

**通过标准**：

```sql
SELECT command_seq, method, device_id, status, error_code,
       (result->>'durationMs')::int AS 耗时ms
FROM run_command WHERE run_id = <上一步返回的 runId> ORDER BY command_seq;
```

- 每步 `status = completed`
- **`耗时ms` 不是 0**（是 0 说明没真在等设备）

### 第 5 步：重复 20 次

**单次通过不代表稳定**。跑 20 次，看有没有偶发失败。

```bash
for i in $(seq 1 20); do
  curl -s -X POST ".../api/workflows/<id>/run?islandId=<id>" \
       -H "Authorization: Bearer $T" -o /dev/null -w "%{http_code} "
done
```

## 四、常见错误码对照

| 错误码 | 含义 | 怎么查 |
|---|---|---|
| `EC-06-0001` | 设备没注册到驱动端点 | 查 `device_instance.driver_id` |
| `EC-05-1006` | TCP 通讯失败 | 查网络、端口、驱动是否活着 |
| `EC-05-1007` | 命令超时 | 查 `elapsedMs`、设备是否真在跑 |
| `EC-05-0001` | 设备返回失败 | 看 `device_raw_response` 里的 `error` |
| `EC-99-0002` | 驱动抛异常 | 看 Sidecar 日志 |
| `EC-PLATE-PRECHECK` | 搬运前源设备没板 | 查 `device_state.has_plate` |
| 契约某项 false | 返回字段名不对 | 看 `rawResponse` 实际字段 |

## 五、出问题怎么定位（三步）

### 第 1 步：看命令

```sql
SELECT command_seq, method, device_id, payload,
       status, error_code, device_raw_response
FROM run_command WHERE run_id = ? ORDER BY command_seq;
```

**这一张表能回答 80% 的问题**：发了什么、给谁、设备回了什么。

### 第 2 步：看节点

```sql
SELECT name, status, resource_id FROM run_node
WHERE run_id = ? ORDER BY id;
```

**看是哪一步失败的、用的哪台设备**。

### 第 3 步：看设备状态

```sql
SELECT r.code, ds.status, ds.has_plate, ds.current_run_id
FROM device_state ds JOIN resource_node r ON r.id = ds.resource_id
WHERE ds.tenant_id = 1;
```

**板子在哪、设备在忙什么**。

## 六、回滚方案

**出问题时**：

```bash
# 1. 停中控
pkill -f ApiServer

# 2. 人工清空设备（把板子拿出来，机械臂归位）
#    这一步必须人工做——系统不知道现场实际状态

# 3. 退回上线前的控制方式（如果还留着）
# 4. 通知值班员
```

**绝不能**：两套控制软件同时操作同一批设备——两边都以为板在自己手上，会撞机。

## 七、日常运维

| 事项 | 命令 |
|---|---|
| 看服务是否活着 | `curl http://localhost:18080/health` |
| 看调度状态 | `curl .../api/scheduler/status` |
| 看日志 | `tail -100 /opt/labos/api.log` |
| 看告警 | 界面的"告警"页 |
| 重启 | `pkill -f ApiServer` 然后按 1.3 启动 |

### 日志不要用 `>` 覆盖

```bash
# 错：每次重启清空历史，出问题查不到
nohup java ... > api.log 2>&1 &

# 对：追加
nohup java ... >> api.log 2>&1 &
```

**这条是踩过坑的**：排查跨重启问题时，历史日志被清空了，看不到错误行。
