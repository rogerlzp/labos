# 暂停、恢复与故障处理 — 设计

> 三个问题：
> ① 设备故障，其他并行实验要不要停？
> ② 需要人工介入，怎么暂停、怎么通知、怎么恢复？
> ③ 机械臂抓着板子时，能停吗？

---

## 一、核心原则：动作不可中断

### 为什么

**设备动作是物理过程，不能在中间停下**：

```
机械臂从 A 抓板，移到半空 → 停在这里？
  板会掉。机械臂的结构不允许悬停承重。
```

**所以：暂停只能在"动作边界"发生，不能在动作中间。**

```
节点1 [动作1] [动作2] [动作3] → 节点2 [动作1] ...
            ↑        ↑        ↑
         可暂停   可暂停    可暂停      ← 只有这些点是安全的
```

**这叫"安全暂停点"（safe point）**。

### 实现：每个动作是原子的

```
动作开始 → 抢资源 → 下发命令 → 等完成 → 记录结果 → 释放资源
                                         ↑
                                    只有这里能检查"要不要暂停"
```

**动作执行期间，暂停请求只标记，不生效。**

## 二、问题 1：设备故障，其他实验要不要停

### 答案：**不是全停，看依赖**

```
设备 B 故障
  ↓
流程1（正在用 B）   → 暂停，等 B 修复
流程2（不用 B）     → 继续跑，不受影响
流程3（计划用 B）   → 暂停，等 B 修复或改道
```

**判断依据**：流程后续会不会用到 B。

### 但机械臂故障是例外

**机械臂是"搬运通道"，它坏了全岛的物流都断**：

```
机械臂故障
  ↓
所有需要搬板的流程 → 暂停
纯计算/纯等待的节点 → 可以继续（比如已经在孵育的，等它孵完）
```

**注意**：**已经在设备里执行的不能停**（孵育到一半停了，样本就废了）。

**所以**：

| 故障对象 | 影响范围 |
|---|---|
| **普通设备**（孵箱/离心机） | 只有用它的流程 |
| **机械臂** | 需要搬运的流程，但**正在执行的动作要跑完** |

### 故障时的动作：暂停 + 释放 + 重规划

```
① 检测到设备故障（心跳失败 / 命令返回硬件错误）
② 标记该设备 status='fault'
③ 找出所有依赖它的 running 执行
④ 这些执行：**执行完当前动作** → 暂停（status='paused_fault'）
⑤ **释放它们占着的其他资源**（位置、其他设备锁）← 关键，让别的流程能跑
⑥ 等设备恢复 → 重新调度
```

**第 ⑤ 步最重要**：暂停的执行如果还占着资源，会把整个岛拖死。

## 三、问题 2：需要人工介入

### 什么情况会触发

| 触发 | 例子 |
|---|---|
| 命令返回 `method_status=3` 且错误码标记"需人工" | 夹具卡住、传感器异常 |
| 重试耗尽 | 超时重试 3 次仍失败 |
| 板位不一致 | 系统认为有板，设备说没有 |
| 人工主动暂停 | 操作员点"暂停" |

### 状态机

```
        ┌──────────────────────────────────┐
        │                                  │
        ▼                                  │
    [running] ──触发──> [waiting_human] ──人工确认──┘
        │                    │
        │                    └──人工取消──> [aborted]
        │
        └──完成──> [completed]
```

### 暂停的时机

**必须在当前动作完成后**：

```java
// 执行每一步之前检查
if (shouldPause()) {
    transitionTo("waiting_human");
    return;   // 不再往下走
}
executeStep();   // 这一步一旦开始，必须跑完
```

### 怎么通知人

| 通道 | 内容 |
|---|---|
| **`run.status = 'waiting_human'`** | 前端列表变红 |
| **`alert_state`** | 推一条告警（含错误码、设备、哪一步） |
| **`run_node.last_error`** | 具体原因 |

### 人工怎么恢复

```
POST /api/runs/{runId}/resume
  ?action=continue     继续（人工已处理）
  &action=retry        重试当前动作
  &action=skip         跳过这一步（危险，要二次确认）
  &action=abort        终止
```

**关键：恢复必须由人触发**，系统不能自己猜"是不是处理好了"。

### 恢复后的状态修正

**人工处理完，现场状态可能和系统记录不一致**：

```
系统记录：板在 B 的 L1
实际：人工把板拿出来了
```

**所以 `resume` 要带一个"状态校正"**：

```json
{
  "action": "continue",
  "corrections": {
    "plate_position": {"plate": "PL-001", "now_at": "ID1183-L1"}
  }
}
```

**不校正就继续，后面的板位判断全错。**

## 四、问题 3：机械臂抓着板子时能停吗

### 分三种情况

#### ① 机械臂正在搬运（已抓板，未放下）

**不能停。**

```
必须让它完成这次搬运（放到目标位置）
  → 完成后再检查暂停请求
```

**为什么**：停在半空板会掉。

**实现**：`Transfer` 动作是原子的，中途不响应暂停。

#### ② 机械臂空闲，板在设备里

**可以立即停。**

板在设备里是安全状态，停了等人工处理即可。

#### ③ 人工强制停止机械臂

**这是最危险的状态**：

```
机械臂抓着板，被人工按了急停
  → 板在哪？机械臂上？半空？
  → 系统完全不知道
```

**处理流程**：

```
① 系统检测到"命令超时/连接断开" + "上一个动作是 Transfer"
② 标记该板位置为 **UNKNOWN**（不是"在机械臂上"，是"不知道"）
③ 该实验 → status='paused_unknown'
④ 推最高优先级告警："板 PL-001 位置未知，需人工盘点"
⑤ **所有涉及这块板的流程全部暂停**
⑥ 人工盘点后，调 resume + corrections 修正位置
```

**关键**：**不能假设板还在机械臂上**——可能掉地上了，可能被人拿走了。

### 状态设计：位置的三态

| 状态 | 含义 | 怎么产生 |
|---|---|---|
| **KNOWN** | 明确在某位置 | 正常动作完成 |
| **UNKNOWN** | 不知道在哪 | 搬运中异常 |
| **LOST** | 确认丢了 | 人工盘点确认 |

**`UNKNOWN` 必须人工介入**，系统不做任何猜测。

### 4.1 「可能位置集合」：一次 UNKNOWN 要封锁多少资源（评审 202604 补充）

**只知道"不知道"是不够的** —— 还得回答：**在人工盘点前，哪些资源不能被别人用？**

#### 可能位置集合怎么算

一次 `Transfer(source=S, target=T)` 的**物理路径**：

```
    时间轴 ──────────────────────────────────→
S 的设备内 ──→ 被抓出 ──→ 在机械臂上 ──→ 放下 ──→ T 的设备内
   ↑ 已知        ↑ 从这里开始就说不清了              ↑ 到这里才重新已知
```

**异常发生时刻**决定了可能的落点：

| 异常时机 | 可能位置集合 |
|---|---|
| 命令发出，还没开始搬 | `{S 的全部位置}`（基本确定还在 S） |
| 已抓出，移动中 | `{S 的出口区, 机械臂, T 的入口区}` |
| 已到 T，还没放下 | `{机械臂, T 的入口区}` |
| 放下过程中 | `{T 的入口区, T 的第一个空位}` |

**保守做法（默认）**：**取全路径的并集**

```
可能位置 = { S 的所有位置, T 的所有位置, 机械臂 }
```

**为什么取并集而不是更精确的**：

- 设备回包可能不准确（说"在移动中"，其实已经放下了）
- **宁可多封，不可漏封** —— 漏封会导致真撞机

#### 封锁规则

```sql
-- 板标 UNKNOWN，同时记录可能位置集合
UPDATE plate
SET position_status = 'UNKNOWN',
    possible_locations = ARRAY[src_resource_id, dst_resource_id, robot_resource_id]
WHERE barcode = ?;

-- 把这些位置全部标为"疑似占用"（别人不能往这放板）
UPDATE position_state
SET reserved_by_run = -1,          -- -1 = 系统封锁，不是某个执行
    reserved_until = now() + interval '24 hours',
    block_reason = 'PLATE_UNKNOWN'
WHERE resource_id = ANY(?) AND current_plate_id IS NULL;
```

**注意三点**：

| 点 | 说明 |
|---|---|
| **封的是位置，不是设备** | 设备本身还能干别的（比如读板机可以读别的板），只是**这些位置不能放新板** |
| **`reserved_by_run = -1`** | 特殊值，表示"系统封锁"而非执行占用，人工盘点后才能解 |
| **TTL 给 24 小时** | 不是 30 分钟——这是要人来的，给足时间；且 TTL 到了也**不自动解封**（见下） |

#### 解封条件：只有人工盘点

**不能靠超时自动解封** —— 板可能真掉在设备里，超时解封会让别的板放进去，**物理上叠板**。

```
① 运维到现场，找到板（在 S？在 T？在臂上？掉地上？）
② 调接口报告实际位置：
   POST /api/plates/{barcode}/locate
   { "actual_location": "ID1183-L2", "operator": "张三", "note": "卡在入口滑轨" }
③ 系统更新 position_status = 'KNOWN'，解封其余位置
④ 相关执行调 resume 恢复
```

#### 如果找不到板

```
标记 position_status = 'LOST'
  → 所有涉及这板的执行 → aborted
  → 走损耗/补样流程
  → 相关位置解封（板确定不在了）
```

#### 对并发的影响（要说清楚）

**一次 UNKNOWN 会封锁 2 台设备的全部位置**：

```
封锁前：ID1183 有 8 个空位，ID1775 有 8 个空位
封锁后：16 个位置全不能用（直到人工盘点）
```

**这是很重的代价**，但相比"叠板导致板子碎在设备里"，是划算的。

**所以设计上要尽量少产生 UNKNOWN**：

| 措施 | 效果 |
|---|---|
| **动作原子性 + 超时设足** | 减少"命令超时但实际还在跑"的误判 |
| **命令带幂等键** | 重发时设备能识别"这是同一次搬运"，不会重复搬 |
| **急停前先查状态** | 如果驱动支持 `GetStatus`，急停前先问一下板在哪 |

## 五、问题 1 追问：其他实验要不要跟着暂停

### 分情况

| 情况 | 其他实验 | 理由 |
|---|---|---|
| **普通设备故障** | **不停** | 它们不用这台设备 |
| **机械臂故障** | **暂停需要搬运的**，正在执行的动作跑完 | 物流断了 |
| **板位置 UNKNOWN** | **暂停所有涉及这块板的** | 不知道板在哪，任何搬运都可能撞 |
| **人工主动暂停** | **不停** | 只是这一个实验要停 |

### 释放资源是必须的

**被暂停的执行如果还占着资源，会把整个岛拖死**：

```
流程1 用 B 时故障，暂停
  - 它还占着 A 的位置（出板位）
  - 流程2 想用 A → 抢不到 → 也卡住
```

**所以暂停时要释放"不再需要的"资源**：

| 资源 | 暂停时 |
|---|---|
| 正在用的设备锁 | **保持**（板可能还在里面） |
| 已占但未用的位置 | **释放** |
| 机械臂 | **释放**（没抓着板的话） |
| 岛锁 | 释放 |

**但**：如果板还在设备里，**设备锁不能释放**（别的流程会往里放板）。

## 六、完整的执行状态机

```
                    ┌─────────────┐
                    │   pending   │
                    └──────┬──────┘
                           │ 调度
                    ┌──────▼──────┐
              ┌─────│   running   │─────┐
              │     └──────┬──────┘     │
        故障/人工            │ 全部完成   │ 不可恢复
              │              ▼           │
    ┌─────────▼────────┐  ┌──────────┐   │
    │  paused_fault    │  │completed │   │
    │  waiting_human   │  └──────────┘   │
    │  paused_unknown  │                 │
    └─────────┬────────┘                 ▼
              │ 人工恢复            ┌─────────┐
              └──────> running      │ aborted │
                                    └─────────┘
```

**三种暂停态的区别**：

| 状态 | 触发 | 恢复条件 |
|---|---|---|
| `paused_fault` | 设备故障 | 设备恢复健康（心跳正常） |
| `waiting_human` | 需人工处理 | 人工调 resume |
| `paused_unknown` | 板位置未知 | 人工盘点 + 校正 |

## 七、和银行家算法的关系（问题 1 的延伸）

**你问"用了银行家算法，故障时其他实验的规划要不要重算"** —— **要**。

### 故障改变可用资源

```
原来：资源 { A, B, C } 全可用，安全序列存在
故障后：B 不可用 → 资源 { A, C }
  → 原来的安全序列可能不成立了
  → **必须重算**
```

### 重算的时机

| 时机 | 动作 |
|---|---|
| 设备故障 | 重算所有 running 的安全性 |
| 设备恢复 | 重算（可以放行更多） |
| 人工恢复一个执行 | 重算 |

**不安全的执行 → 暂停**（不是终止，是暂停等资源恢复）。

### 但有个现实约束

**已经在设备里的板不能因为"重算不安全"就拿出来**：

```
孵育到一半，重算发现"不安全" → 能停吗？
  → 不能，强行停会毁掉样本
```

**所以**：

| 资源 | 能否因重算而中断 |
|---|---|
| 位置 | ✅ 可以（板可以换地方） |
| 设备（正在执行） | ❌ **不能**（样本在里面） |
| 机械臂（正在搬） | ❌ **不能**（板在半空） |

**结论：银行家算法的"安全检测"只能用于"新申请的资源"，
不能用于"已经占着且在用的资源"。**

**这就是"不可抢占资源"的现实约束** —— 已占着在用的资源不能因"重算不安全"就中断，
这是物理事实，**与银行家算法的前提无关**（银行家本就是为不可抢占资源设计的，
它的前提是"预知最大需求"，见本章末的概念修正）。

## 八、实施优先级

| # | 任务 | 依赖 | 估时 |
|---|---|---|---|
| 1 | **动作原子性**（中途不响应暂停） | 无 | 已有（同步执行） |
| 2 | **安全暂停点**（每步前检查） | 1 | 2 天 |
| 3 | **状态机扩展**（3 种暂停态） | 2 | 3 天 |
| 4 | **人工恢复接口** + 状态校正 | 3 | 2 天 |
| 5 | **板位置 UNKNOWN** | 3 | 2 天 |
| 6 | **故障影响范围分析**（依赖哪些设备） | 前瞻扫描 | 3 天 |
| 7 | **暂停时释放非必要资源** | 3 | 2 天 |
| 8 | **重算安全序列** | 银行家 + 6 | 3 天 |

**总共约 3 周**，且第 6、8 依赖前瞻扫描和银行家算法。

## 九、一句话总结

**暂停只能在动作边界发生**，动作中途不能停（板会掉）。

**故障不停其他实验**，除非是机械臂故障或板位置未知。

**人工介入必须显式恢复 + 状态校正**，系统不猜。

**银行家算法的安全检测只管"新申请"，不能中断"已占着在用的"。**

### ⚠ 概念修正（评审 R1 指出）

**之前这里写的是"物理世界不可抢占，所以银行家算法不适用"——这是误述。**

**银行家算法（Dijkstra 1965）本身就是为不可抢占资源设计的**（打印机、磁带机），
它不要求资源可抢占。

**它真正的前提是"预知最大需求"（max claim）**：

> 每个进程必须声明它最多会申请多少资源，系统才能算"分配后是否还有安全序列"。

**本项目做不到这个前提**：

- 流程有 `exclusiveGateway` / `loop`，跑哪条分支要执行时才知道
- 最大需求随分支变化，**无法在执行前声明**

**所以不采用银行家算法的理由只有一个：预知不了最大需求。**
和"能不能抢占"无关。

**这个区别很重要**：如果实现者按错误理由理解，可能会以为
"只要加上抢占机制就能用银行家"——那是白费功夫，
真正的障碍是需求不可预知。
