# 异步结果查询与动态分支 — 设计

> **场景**：结果由前面某个设备异步产生（读板要 10 分钟），
> 用到的时候去查、处理、然后决定走哪条分支。
>
> **关键判断**：**这不需要脚本沙箱**。需要的是"结果暂存 + 变量注入 + 查询节点"。

---

## 一、先分清三种"查询"

| 查什么 | 例子 | 需要什么 |
|---|---|---|
| **① 查本系统的异步结果** | "读板结果出来了吗" | **结果表 + 变量注入**（本设计） |
| **② 查本系统的实时状态** | "哪个层位空着" | 受限查询 API（已有 `ctx.freeSlots`） |
| **③ 查外部系统** | "LIMS 里这个样本的信息" | **脚本 + 白名单**（才需要沙箱） |

**用户提的场景是 ①** —— 结果**已经由本系统产生**，只是**异步的**。

**不需要上传代码，不需要沙箱。**

---

## 二、场景拆解

### 2.1 典型流程

```
节点1：送板到读板机
节点2：读板（异步，5-10 分钟出结果）
节点3：同时做别的（比如离心另一批）
节点4：← 这里要"根据读板结果决定走哪条"
        读板结果 OD > 0.5 → 走"阳性"分支（继续测序）
        OD <= 0.5 → 走"阴性"分支（归档）
```

**关键**：节点 4 执行时，节点 2 的结果**可能刚出来，也可能还没出来**。

### 2.2 三个必须解决的问题

| # | 问题 | 解法 |
|---|---|---|
| 1 | **结果存在哪** | `run_result` 表 |
| 2 | **怎么引用** | 注入变量 `${results.xxx}` |
| 3 | **还没出来怎么办** | 等待 + 超时 + 降级策略 |

---

## 三、结果存储

### 3.1 表结构

```sql
CREATE TABLE run_result (
    id          bigserial PRIMARY KEY,
    tenant_id   bigint NOT NULL,
    run_id      bigint NOT NULL REFERENCES run(id),
    node_id     bigint,                    -- 哪个节点产生的
    result_key  varchar(64) NOT NULL,      -- 'readPlate'
    payload     jsonb NOT NULL,            -- {"od": 0.65, "plate": "PL-001"}
    source      varchar(16) NOT NULL,      -- 'device' | 'manual' | 'external'
    created_at  timestamptz NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, run_id, result_key)
);

CREATE INDEX idx_run_result_lookup ON run_result (tenant_id, run_id, result_key);
```

**`result_key` 唯一** —— 同一个 run 里同一个 key 只有一份（后写覆盖，或者报错，见下）。

### 3.2 结果从哪来

| 来源 | 怎么产生 | 例子 |
|---|---|---|
| **`device`** | 设备命令的返回里有 `data` | `{"data": {"od": 0.65}}` |
| **`manual`** | 人工在界面上填 | 显微镜观察结果 |
| **`external`** | 外部系统推送（webhook） | LIMS 回传 |

**`device` 是主路径**：

```json
// 节点配 {"output": "readPlate"}
// 设备返回 {"data": {"od": 0.65, "plate": "PL-001"}}
// → 自动写 run_result(result_key='readPlate', payload={...})
```

**这已经在现实现里有雏形**（`output` 变量），只是没存到独立表。

### 3.3 重复产生怎么办

**同一个 key 出现两次**：

| 策略 | 适用 |
|---|---|
| **报错**（默认） | 正常流程不该重复 |
| **覆盖** | 重试场景（第二次结果更可信） |
| **保留首次** | 一次性结果（如"第一次读板"） |

**配置在节点上**：

```json
{ "output": "readPlate", "onDuplicate": "error" | "overwrite" | "keep_first" }
```

**默认 `error`** —— 静默覆盖会让问题藏起来。

## 四、变量注入：怎么在表达式里引用

### 4.1 注入规则

**每个节点执行前**，把本 run 的**所有已完成结果**注入变量：

```java
Map<String, Object> vars = new HashMap<>(runVars);

for (RunResult r : resultsOf(runId)) {
    // 展开成 results.<key>.<field>
    Map<String, Object> flat = new HashMap<>();
    flatten(r.resultKey(), r.payload(), flat);   // 递归展开嵌套
    flat.forEach((k, v) -> vars.put("results." + k, v));
}
```

**展开后变量长这样**：

```
results.readPlate.od       = 0.65
results.readPlate.plate    = "PL-001"
results.qc.concentration   = 12.5
```

### 4.2 表达式里怎么用

```json
{
  "nodeType": "exclusiveGateway",
  "condition": "${results.readPlate.od > 0.5}",
  "then": [...],   // 阳性分支
  "else": [...]    // 阴性分支
}
```

**或更复杂的条件**：

```json
{
  "condition": "${results.readPlate.od > 0.5 && results.readPlate.plate != null}"
}
```

### 4.3 结果还没出来时，变量长什么样

**没出来的结果，变量不存在** → 表达式求值报"变量未定义"。

**这不够好** —— 需要区分"没出来"和"值为 null"。

**方案：注入一个"存在性标记"**：

```
results.readPlate.od          = 0.65
results.readPlate.__exists    = true      ← 结果存在
results.qc.__exists           = false     ← 结果还没出来
```

**表达式可以判断**：

```json
{ "condition": "${results.readPlate.__exists && results.readPlate.od > 0.5}" }
```

**更好的是用一个函数**：

```json
{ "condition": "${has('readPlate') && results.readPlate.od > 0.5}" }
```

**`has()` 是表达式引擎的内置函数**（只读变量表，不算越权）。

## 五、结果还没出来：等待策略

### 5.1 三种策略

| 策略 | 行为 | 适用 |
|---|---|---|
| **`wait`** | 轮询直到出现或超时 | 默认，结果一定会来 |
| **`skip`** | 不等待，按"没有结果"继续 | 结果是可选的 |
| **`pause`** | 暂停，等人确认 | 结果很重要，不能猜 |

### 5.2 配置

**在判定节点上配**：

```json
{
  "nodeType": "exclusiveGateway",
  "waitFor": {
    "results": ["readPlate"],
    "timeoutMs": 600000,          // 最多等 10 分钟
    "pollMs": 2000,               // 每 2 秒查一次
    "onTimeout": "pause"          // fail | skip | pause
  },
  "condition": "${results.readPlate.od > 0.5}",
  "then": [...],
  "else": [...]
}
```

### 5.3 等待期间的资源

**关键**：**等待时释放所有占用的资源**。

```
节点4 要等读板结果
  → 释放：机械臂、通道、位置（如果有）
  → 只保留：设备锁（如果板还在设备里）
  → 状态：run.status = 'waiting_result'
```

**为什么**：等 10 分钟期间，别的流程要能用机械臂。

### 5.4 等待的可观测性

**界面显示**：

```
执行 #205123  等待结果
  等：readPlate（已等 3 分 20 秒，超时 10 分钟）
  预计：读板通常 8 分钟
```

**`预计` 从 `duration_model` 拿** —— 让值班员知道"还要等多久"。

### 5.5 超时了怎么办

| `onTimeout` | 行为 | 提醒 |
|---|---|---|
| **`fail`** | 执行失败 | 简单，但要人工重跑 |
| **`skip`** | 当作"没有结果"继续 | 可能走错分支 |
| **`pause`** ⭐ | 暂停等人 | **默认推荐**（结果重要时） |

**`pause` 的实现**：`status='waiting_human'`，告警"等结果超时"。

## 六、动态分支：结果的典型用法

### 6.1 场景：读板结果决定后续

```json
{
  "nodeType": "exclusiveGateway",
  "name": "OD 判定",
  "waitFor": { "results": ["readPlate"], "timeoutMs": 600000, "onTimeout": "pause" },
  "condition": "${results.readPlate.od > 0.5}",
  "then": [
    { "name": "阳性：继续建库" },
    { "nodeType": "script", "scriptId": "assign-barcode" }
  ],
  "else": [
    { "name": "阴性：归档存储" },
    { "method": "Transfer", "params": { "target": "ARCHIVE-S${plateCount + 1}" } }
  ]
}
```

### 6.2 场景：三个结果组合判断

```json
{
  "condition": "${results.qc.concentration > 10 && results.qc.purity > 1.8}"
}
```

**走"合格"分支；否则走"重提"分支**。

### 6.3 场景：结果驱动点位选择

**这是用户提的"动态更新流程"**：

```json
{
  "nodeType": "compute",
  "waitFor": { "results": ["readPlate"] },
  "set": {
    // 根据 OD 值选不同的存储温度区
    "storageSlot": "${results.readPlate.od > 0.5 ? 'COLD-' : 'ROOM-'}${plateId}"
  }
}
```

**结果 → 变量 → 点位**，全链路打通。

## 七、和脚本节点的关系（重要）

### 7.1 大部分场景不需要脚本

| 需求 | 用什么 |
|---|---|
| 等结果，按值分支 | **`waitFor` + 表达式** |
| 结果组合判断 | **表达式** |
| 结果驱动点位 | **`compute` + 表达式** |
| **结果在外部系统** | **脚本**（白名单代查） |
| **结果要做复杂转换**（如 JSON 嵌套几层） | 表达式不够 → 脚本 |

### 7.2 判断标准

```java
// 能写成表达式吗？
if (需求可以表达为"对已有变量的运算") {
    用表达式;   // 安全、快
} else if (需求是"查本系统的结果/状态") {
    用 waitFor + 变量注入;   // 安全、中等快
} else {
    用脚本;   // 有风险、慢
}
```

**用户这个场景落在第二类**，**不需要脚本**。

## 八、实施

### 8.1 在 M1 里做（3 天）

| # | 任务 | 估时 |
|---|---|---|
| 1 | `run_result` 表 + 写入（从 `output` 配置） | 1 天 |
| 2 | 变量注入（`results.<key>.<field>`） | 1 天 |
| 3 | `waitFor` + 轮询 + 超时 | 1 天 |
| 4 | `has()` 函数（表达式引擎加一个内置函数） | 0.5 天 |

**这 3 天要加进 M1**（1.75 → **2.1 周**）。

### 8.2 验收

| 场景 | 断言 |
|---|---|
| **结果先到** | 判定节点直接读到，不等待 |
| **结果后到** | 轮询 2 秒后读到 |
| **结果不来** | 超时后按 `onTimeout` 处理 |
| **等待期间** | 机械臂已被释放（别的流程能用） |
| **重复结果** | 按 `onDuplicate` 策略处理 |
| **变量不存在** | `has()` 返回 false，表达式不报错 |

## 九、一个容易忽略的点：结果的时效性

**结果不是永远有效的**：

```
读板结果 2 小时前出来
  → 现在还能用来判定吗？（样本可能变质）
```

**加一个"有效期"**：

```json
{ "output": "readPlate", "validForMs": 7200000 }   // 2 小时
```

**过期后**：
- `has('readPlate')` 返回 **false**
- `results.readPlate.__expired` 标 true

**为什么**：**用过期结果做判断，可能得出错误结论而不自知。**

## 十、待确认

| # | 问题 | 影响 |
|---|---|---|
| 1 | 结果**一定会有**，还是**可能永远不来**？ | 决定默认 `onTimeout` |
| 2 | 同一个 key **重复出现**正常吗？ | 决定 `onDuplicate` 默认值 |
| 3 | 结果**有有效期**吗？（样本会变质） | 决定要不要 `validForMs` |
| 4 | 结果**谁写**？（设备自动 / 人工填 / 外部推） | 决定 `source` 的默认值 |

**第 3 点容易被忽略** —— 如果读板结果是 2 小时前的，
现在用它判定"阳性/阴性"，**依据可能是错过的**。
