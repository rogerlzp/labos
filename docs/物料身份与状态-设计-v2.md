## 1. 当前实现中必须遵守的事实

1. `GraphRunner` 不直接访问数据库；TASK 在 `GraphRunner.java:649-650` 完成，`:604` 是 BUILTIN 分支。
2. `WorkflowService` 同时存在图执行与 `sm.executeAll` 顺序执行；只接图监听器会漏掉顺序路径。
3. `recordNodeState` 是独立 mapper 更新并吞异常；现有普通执行监听器也允许失败不影响物理执行。
4. `run_node` 已有 `loop_index`，同一节点可以在同一 run 中执行多圈。
5. `position_state.plate_id` 存板条码，`occupied_by_run` 是当前占用归属；取板已有 run 归属校验。
6. 缺少真实条码时，位置登记可能生成 `AUTO-<runId>`；它不是可用于物料追溯的真实身份。
7. `plate_well.sample_id/aliquot_id/volume/status` 已存在，板级工艺状态不能成为第二份孔级内容真相。
8. 执行参数当前读取 `workflow_node.params->'method_params'`，扁平解析后透传驱动；物料声明不得进入这个通道。
9. `run.workflow_ver` 字段存在但当前 `insertRun` 未写；续跑会重新读取流程定义，因此声明必须快照。
10. 物理动作与数据库不可能共享一个 ACID 事务。本方案只保证数据库内事实可恢复，**不宣称物理动作 exactly-once**。
11. `RuntimeHold.Scope` 当前只有 `site/island/experiment`，没有节点级门禁；`WorkflowWebService.java:48` 仍固定 `TENANT = 1L`。因此节点依赖门禁必须接调度边界，多租户也不能只靠新增复合外键就宣称完成。

## 2. 模型边界与不变量

### 2.1 四类事实分开

| 事实 | 唯一权威来源 | 本方案是否修改 |
|---|---|---|
| 板是谁、孔里有什么 | `plate`、`plate_well/sample_aliquot` | 只给 `plate` 增加板级工艺状态，不改孔级模型 |
| 板当前在哪里、被哪个 run 占用 | `position_state` | 不改 |
| 设备/节点物理上是否完成 | 命令证据 + `run_node.physical_completed_at` | 新增显式时间戳，恢复时禁止仅凭猜测重放 |
| 板级工艺状态如何变化 | 声明快照 → effect → event → 当前投影 | 新增 |

### 2.2 板级工艺状态的定义

`process_state_code` 表达的是**整板在工艺中的阶段或处置状态**，例如 `amplified_product`、`purified_sample`。

它满足：

- 一块板在同一版本只有一个板级工艺状态；
- 默认假设该状态适用于整板，不表达“只有部分孔处于该阶段”；
- 不表达样本身份、体积、浓度、批号、孔位谱系；
- `NULL` 表示未知，不等于空板；
- “空板”若需要统计，必须有独立字典 code，并明确它与全部 well 为空之间是否需要一致性校验，本期不自动推导。

### 2.3 膜状态

`seal_state` 只回答“当前是否封膜”：

- `none`：确认未封膜；
- `sealed`：确认已封膜；
- `NULL`：未知。

本期不记录膜批号、条码、供应商、有效期、附着历史。出现这些需求时，膜应升级为独立耗材，而不是继续往 `plate` 加字段。

### 2.4 不再使用模糊的 owner

“归属”至少有三件事，不能共用一个 `owner_run_id`：

1. **来源**：哪个 run/node/loop 产生了这次状态结果——写不可变事件；
2. **当前占用**：板当前位置由哪个 run 占用——继续查 `position_state`；
3. **跨流程持有权移交**：阶段 3 的显式业务操作，本期不实现。

因此本期不新增 `plate.owner_run_id/owner_node_key`。

### 2.5 核心不变量

- **I1**：位置变化不自动改变工艺状态，工艺状态变化不自动改位置。
- **I2**：自动迁移只能来自已完成物理节点的不可变声明快照，运行期不根据方法名或位置猜状态。
- **I3**：每个自动 effect 最多产生一条 event；同一节点不同循环圈次是不同 effect。
- **I4**：event 与 `plate` 当前投影在同一事务写入，event 的 from/to 必须等于本次实际变化。
- **I5**：同一板的所有投影通过行锁与 `state_version` 串行化，禁止最后写入者无声覆盖。
- **I6**：物理完成但迁移失败时，保留下游阻断与补偿意图；恢复不得先重做设备动作。
- **I7**：老流程没有 `material_effect` 时保持原行为，但仍可在发布预检中提示补声明。
- **I8**：非法、未核实或属于其他 run 的目标板不得被修改。
- **I9**：声明、设备回包和独立物理确认必须分级保存；超时/未知不得被当成确定失败或直接重跑。
- **I10**：effect/event/action 的 run、run_node、plate、effect 引用必须 tenant 一致，不能只在冗余字段上写一个 tenant_id；数据库引用一致也不能替代请求租户上下文。
- **I11**：声明、设备证据与位置投影发生身份冲突时不得按优先级硬写；确定性配置错误为 FAILED，物理身份无法一致确认时为 NEEDS_RECONCILIATION。
- **I12**：effect 的每次声明、应用、对账、重试、rebase 与取消都追加不可变 action；恢复历史不能只保留一份会被覆盖的最新证据。

### 2.6 执行结果、证据等级与幂等维度

**执行结果**至少分为：

| 结果 | 物料处理 |
|---|---|
| 设备明确成功，且证据满足节点策略 | 可进入 T1，但证据等级通常只是 `device_ack` |
| 设备明确成功，但节点要求独立物理/人工确认 | 先保持 NEEDS_RECONCILIATION，等待满足策略的证据 |
| 设备明确失败且确认未产生目标动作 | 不创建待迁移效果，走现有失败路径 |
| 超时、连接中断、结果未知 | `NEEDS_RECONCILIATION`，禁止直接当作失败重跑 |
| 设备查询、传感器或人工对账后确认完成 | 补物理完成证据，满足节点策略后进入 T1/T2 |
| 对账后确认未执行 | effect 标记 `CANCELLED`，不写 event；后续能否重试仍走现有安全策略 |

**证据等级**：

- `device_ack`：设备或驱动报告成功；证明执行链得到成功回包，不冒充独立物理确认；
- `physical_confirmed`：设备最终状态查询、传感器或其他可信物理反馈确认；
- `manual_confirmed`：授权人员现场核实，必须记录操作者、时间与原因；
- `legacy`：仅用于老数据 `status=completed` 的兼容，不代表新证据能力。

声明快照回答“打算做什么”，不属于物理证据。普通方法默认可采用 `device_ack`，高风险方法可在元数据中只接受 `physical_confirmed/manual_confirmed`；证据策略随声明一起快照。UI、事件和验收报告必须保留实际等级，不能统一写成“物理已核实”，也不能把人工确认当成设备自动确认。

**圈次、重试与执行实例**：

- `loop_index` 标识业务上有意发生的第几次加工，是 effect 来源键的一部分；
- `attempt` 标识同一逻辑执行的命令重试，**不进入 effect 唯一键**，重试不得变成第二次物料加工；
- `execution_id/command_id/stepSeq` 标识实际执行证据，尽量引用现有 `run_command/command_ledger` 的真实主键或 UUID，保存在完成证据和事件快照中；
- 同一来源重复回调、worker 重试和 run 恢复始终处理同一个 effect；确需再次加工时必须由新的节点、圈次或 run 表达，不能靠清空记录绕过幂等；
- 如果现有多步执行无法形成可追溯的命令证据，必须在 S0 补齐证据映射，不能编造 `execution_id`。

## 3. 总体流程

```text
流程设计
  └─ workflow_node.material_effect（独立列）
       ├─ mode=none                 明确无物料状态副作用
       └─ mode=transition           明确目标板与目标状态

run 创建节点外壳
  └─ 将生效声明、workflow 版本、declaration_hash 快照进 run_node.input

设备执行结果（图执行 / 顺序执行共同边界）
  ├─ 明确成功且证据满足策略：T1 完成登记 + 目标解析 + effect/action 原子落库
  │     ├─ PENDING 时立即尝试 T2
  │     │    ├─ 成功：event + plate 投影 + effect(APPLIED) + action，允许依赖后继
  │     │    └─ 失败：保留 PENDING/FAILED，阻断依赖后继
  │     ├─ FAILED：物理完成事实保留，物料错误单独记录
  │     └─ NEEDS_RECONCILIATION：身份证据冲突，不写 event
  ├─ 明确未执行：不迁移物料，走现有失败路径
  └─ 超时/未知或证据不满足策略：effect(NEEDS_RECONCILIATION)，对账前禁止重跑

调度依赖门禁（不是节点设备状态，也不是 runtime_hold）
  ├─ 直接前置存在未闭环物料效果：阻断依赖后继
  └─ 无关分支：允许继续

恢复
  ├─ 已有 physical_completed_at：只补 effect，不重做设备动作
  ├─ T1 未落库但命令证据完整：先对账，再补完成与 effect
  └─ 命令结果不确定：隔离/人工，不猜、不自动重放
```

普通执行事件监听仍可用于展示，但**物料完成处理器不是 best-effort listener**：它的失败必须进入明确的恢复路径。

## 4. 数据模型

以下 DDL 是评审用逻辑模型；实施时按 `pg_rebuild/schema/` 分片与 `90_all_in_one.sql` 同源生成，并通过 `check-schema-sync.sh`。

### 4.1 租户工艺状态字典

```sql
CREATE TABLE plate_process_state (
  tenant_id       bigint      NOT NULL REFERENCES tenant(id),
  code            varchar(32) NOT NULL,
  display_name    varchar(64) NOT NULL,
  enabled         boolean     NOT NULL DEFAULT true,
  is_recommended  boolean     NOT NULL DEFAULT false,
  sort_order      int         NOT NULL DEFAULT 0,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, code)
);
```

约束与生命周期：

- `code` 使用 `[a-z][a-z0-9_]{1,31}`，创建后不可修改；
- `display_name` 可改；event 另存当时名称快照，避免历史文案随字典改名而漂移；
- 不提供物理删除，只能 `enabled=false`；
- 停用只阻止新声明和新 run，不阻断已经快照的在途 effect；
- 推荐集是租户初始化模板，`is_recommended=true` 不代表不可编辑；
- 新租户由租户初始化流程复制推荐集，既有租户通过幂等 seed 补齐缺失项，不覆盖租户修改。

### 4.2 `plate` 当前投影

```sql
ALTER TABLE plate
  ADD COLUMN process_state_code varchar(32),

ALTER TABLE plate
```

`state_version` 从 0 开始，每次自动或人工投影成功都加 1；即使 from=to，也允许记录一次真实声明事件并增加版本。

### 4.3 `run_node` 物理完成与物料同步状态

```sql
ALTER TABLE run_node
  ADD COLUMN physical_completed_at   timestamptz,
  ADD COLUMN physical_evidence_level varchar(24),
  ADD COLUMN physical_evidence       jsonb NOT NULL DEFAULT '{}'::jsonb,
  ADD COLUMN material_sync_status    varchar(24) NOT NULL DEFAULT 'not_required',
  ADD COLUMN material_error_code     varchar(64);

ALTER TABLE run_node
  ADD CONSTRAINT ck_run_node_material_sync
    CHECK (material_sync_status IN
      ('not_required', 'pending', 'applied', 'failed',
       'needs_reconciliation', 'cancelled')),
  ADD CONSTRAINT ck_run_node_physical_evidence_level
    CHECK (physical_evidence_level IS NULL OR physical_evidence_level IN
      ('device_ack', 'physical_confirmed', 'manual_confirmed', 'legacy')),
  ADD CONSTRAINT ck_run_node_physical_evidence_required
    CHECK (physical_completed_at IS NULL OR physical_evidence_level IS NOT NULL);

CREATE INDEX ix_run_node_material_sync
  ON run_node (tenant_id, material_sync_status)
  WHERE material_sync_status IN ('pending', 'failed', 'needs_reconciliation');
```

语义：

- `physical_completed_at` 是**系统确认完成事实成立时的登记时间**，用于恢复守卫，不等于物料投影完成，也不必然等于设备真实动作发生时间或独立物理确认时间；
- `physical_evidence` 至少保存证据来源、设备/命令/步骤标识、attempt、设备完成时间和记录时间；多步节点保存标识列表，不能只留一个无法对应的“成功”布尔值。设备提供的真实发生时间另存 `physical_evidence.occurredAt`，并进入 event.occurred_at；
- 新执行的所有明确成功且满足证据策略的节点都写完成登记时间与证据等级；老数据中 `status=completed` 只作为 `legacy` 兼容证据；
- 超时/未知时 `physical_completed_at` 保持为空，物料状态为 `needs_reconciliation`；
- 物理执行成功后，即使 T2 失败，节点也可以保持既有 `completed` 终态；`material_sync_status` 单独表达物料异常，由 §5.2 的调度依赖门禁阻断后继。**不得再用 `status=manual` 伪造设备失败或承担物料门禁**；
- 物理完成登记时间和证据必须保留；`material_error_code` 不覆盖设备自己的 `error_code`。

### 4.4 `plate_material_effect`： durable 迁移意图

```sql
CREATE TABLE plate_material_effect (
  id                       bigserial PRIMARY KEY,
  tenant_id                bigint      NOT NULL REFERENCES tenant(id),

  expected_seal_state      varchar(16),

  CONSTRAINT uk_material_effect_source
    UNIQUE (tenant_id, run_id, node_key, loop_index, effect_index),
  CONSTRAINT fk_material_effect_run
    FOREIGN KEY (tenant_id, run_id) REFERENCES run (tenant_id, id),
  CONSTRAINT fk_material_effect_run_node

    REFERENCES run_node (tenant_id, run_id, id),
  CONSTRAINT fk_material_effect_plate
    FOREIGN KEY (tenant_id, resolved_plate_id) REFERENCES plate (tenant_id, id),
  CONSTRAINT ck_material_effect_status
    CHECK (status IN
      ('pending', 'applied', 'failed', 'needs_reconciliation', 'cancelled'))
);

CREATE INDEX ix_material_effect_retry
  ON plate_material_effect (tenant_id, status, next_retry_at)
  WHERE status = 'pending';
CREATE INDEX ix_material_effect_reconciliation
  ON plate_material_effect (tenant_id, status, updated_at)
  WHERE status = 'needs_reconciliation';
CREATE INDEX ix_material_effect_run
  ON plate_material_effect (tenant_id, run_id, node_key, loop_index);
CREATE INDEX ix_material_effect_plate
  ON plate_material_effect (tenant_id, resolved_plate_id)
  WHERE resolved_plate_id IS NOT NULL;
```

说明：

- 本期每个节点每圈最多一个 effect，固定 `effect_index=0`；多目标必须拆节点。未来扩展时用稳定的 `effect_index` 标识声明项，不能按数组顺序重排历史声明。
- 目标解析失败时 `resolved_plate_id` 可以为空：空条码、AUTO、多个目标等确定性配置错误以 `failed` 留下；设备证据、声明与位置投影冲突则以 `needs_reconciliation` 留下，防止“物理做完但系统没记录”。
- 超时/未知创建 `needs_reconciliation`；对账确认未产生目标动作后为 `cancelled`，两者都不写 event。
- `reconciliation_evidence` 只保存最新对账快照；操作者、依据、时间、结论及每次状态变化的完整历史写入 §4.6 的 append-only action。
- `apply_attempt_count` 只统计物料投影应用次数，不是设备物理重试次数；设备 attempt 在执行证据里单独记录。
- `declaration_hash` 用于识别同一来源重试时声明是否被换；同键不同 hash 必须失败，不允许覆盖。
- `expected_state_version` 将 T1 与 T2 之间的并发变化变成显式冲突，而不是覆盖。
- 上述复合外键要求被引用表存在匹配的 `UNIQUE` 键。实施时先为 `run(tenant_id,id)`、`run_node(tenant_id,run_id,id)`、`plate(tenant_id,id)` 补齐唯一约束，再建外键；不得退化成“应用里记得查租户”。

## 5. 完成、迁移与恢复

### 5.1 run 启动：先固定声明

创建 `run_node` 外壳时写入：

```json
{
  "capability": "...",
  "method": "...",
  "material_effect_snapshot": {
    "mode": "transition",
    "target": { "by": "position", "resourceId": 1000005 },
    "set": { "processState": "amplified_product" },
    "acceptedEvidenceLevels": ["device_ack", "physical_confirmed", "manual_confirmed"]
  },
  "material_effect_hash": "<sha256>",
  "workflow_version": 7
}
```

规则：

- `run.workflow_ver` 写实际版本；
- 声明中的变量在启动时解析后快照，目标与状态不再随设计器编辑改变；
- 启动时合并方法元数据中的证据策略；`acceptedEvidenceLevels` 与声明一起快照并纳入 hash，续跑不采用后来修改的策略；
- 续跑复用已有 `run_node.input.material_effect_snapshot`，禁止用最新流程定义覆盖；
- 老流程保存为 `mode=legacy_unspecified`，运行行为等价于 `none`，但预检仍能区分；
- 本方案只保证物料声明快照，不声称顺便解决整个 BPMN 图的版本化问题。

### 5.2 共同执行结果处理器与调度依赖门禁

在 `RunStateMachine` 的执行结果边界接入 `NodeCompletionHandler`，由 boot 层的 `MaterialEffectService` 实现。图执行和顺序执行都必须调用同一实现；明确成功进入 T1，超时/未知进入对账登记，不能把处理器只挂在“成功回调”上。

完成上下文必须显式携带 `runId/runNodeId/nodeKey/loopIndex/effectIndex` 与实际命令证据，不允许 DB 处理器反查“最新一圈”：

- 无环图与顺序执行的 `loopIndex=0`；
- 有环图使用本次 `visit`（1..N）作为 `loopIndex`，T1 定位或创建实际圈次行；`loop_index=0` 的汇总行只用于展示，不作为该圈物料来源；
- 所有状态写入按 `(run_id,node_key,loop_index)` 精确定位，不复用当前缺少 loop 条件、可能同时改多行的更新方式；
- 同一圈多个设备 attempt 都关联同一个逻辑 effect，证据中保留每次 attempt，不得新造圈次。

处理器不是普通通知监听器，返回：

- `CONTINUE`：当前节点无效果或 effect 已 APPLIED，其直接后继可以进入门禁检查；
- `HOLD`：目标、状态或物理事实需要恢复，阻断依赖后继并进入人工/恢复；
- 抛出持久化异常：当前 run 立即中止并进入 §5.6 的不确定性恢复。尤其 T1 连物理完成事实与迁移意图都无法写入时，不得把节点当成功静默继续，也不得直接续跑重放。

**调度依赖门禁是独立必检步骤。** 调度器每次派发节点前检查其全部直接前置节点：只有 `not_required/applied` 允许释放依赖后继；`pending/failed/needs_reconciliation/cancelled` 均阻断依赖后继，无关分支可以继续。门禁不新增 `node_status` 枚举，不修改设备终态，也不使用只有 experiment/island/site 作用域的 `runtime_hold` 代替。

- 图执行按实际依赖边检查全部直接前置；顺序执行在下一个节点开始前检查相应前序节点，两者使用同一判定函数；
- 循环节点必须汇总本次执行实际产生的 visit 1..N 圈次行，任一圈未闭环都阻断；不得只查 `loop_index=0` 的汇总行，也不得只查第一圈或最后一圈；
- 物料后处理失败不得伪造成设备执行失败。若当前 RunStateMachine 无法实现“依赖后继阻断、无关分支继续”，必须在 S0 标为未通过并在 S2B 补齐调度边界，不能用扣住整个实验冒充完成；
- `GraphRunner` 仍不访问数据库，门禁由现有执行状态边界与 boot 层服务协作完成。

### 5.3 T1：完成事实与迁移意图原子落库

仅在执行证据支持“物理动作已完成”且证据等级满足快照中的 `acceptedEvidenceLevels` 时，对 `mode=transition` 执行：

1. 开启本地 PG 事务；
2. 根据声明快照和实际执行证据解析目标，必要时锁定位置与板行；
3. 记录 `resolved_plate_id`、解析证据和 `expected_state_version/from`；
4. 插入或更新同一来源 effect：解析成功为 `pending`，确定性配置错误为 `failed`，身份证据冲突为 `needs_reconciliation`；
5. 更新 `run_node.physical_completed_at`、`physical_evidence_level`、`physical_evidence`、`material_sync_status`；
6. 配置失败或身份冲突时写对应 `material_error_code` 与证据；节点保持物理执行成功终态，返回 HOLD，由依赖门禁扣住后继，不改写为 `manual` 或设备失败；
7. 追加 DECLARE action，固化当次状态变化与证据；
8. 提交。

对 `mode=none/legacy_unspecified`：只写物理完成、证据和 `not_required`，不创建 effect/action。

若执行超时/未知，或设备虽返回成功但证据等级不满足快照策略，`mode=transition` 必须在单独短事务中持久化 `needs_reconciliation` effect、DECLARE/RECONCILE action 和 run_node 状态，`physical_completed_at` 保持为空，设备回包与其时间先存入证据；`none/legacy` 走现有未知结果路径，但同样禁止直接自动重跑。取得可接受证据后再补物理完成登记时间。若对账后确认未产生目标动作，已有 effect 改为 `cancelled` 并追加 RECONCILE action 与对账证据，不写 event。

**T1 提交后，即使进程崩溃，也知道物理动作对应什么物料意图和证据等级。**

### 5.4 T2：迁移、事件与 APPLIED 原子落库

T1 成功后，当前执行线程立即尝试 T2；后台 worker 只负责后续补偿，不是正常路径的必需延迟。

1. 开启事务，`SELECT effect ... FOR UPDATE`；
2. 先核对 declaration hash 和已解析目标，防止同键不同义；
3. hash 与目标一致时，若已 APPLIED 直接返回成功且不重复追加 action；若不是 PENDING，按当前状态返回，不强行迁移；
4. `SELECT plate ... FOR UPDATE`；
5. 检查 `state_version`、声明 from 与 T1 保存的期望 from；不一致则标记 `failed(MAT_STATE_CONFLICT)`，不写 event；
6. 插入 event，`state_version=expected+1`，保存字典显示名、来源、证据等级、证据快照与物理发生时间；
7. 更新 `plate.process_state_code/seal_state/state_version`；
8. effect 标记 APPLIED，写 `applied_at`；
9. 更新 `run_node.material_sync_status='applied'` 并清物料错误码；
10. 追加 APPLY action，保存本次证据与 `pending → applied`；
11. 提交。

步骤 4–5 的业务校验失败时，在同一短事务中**只提交失败记录**：effect 标记 `failed` 并写错误码，同时更新 `run_node.material_sync_status='failed'` 和 `material_error_code`，追加 `pending → failed` 的 APPLY action；不得写 event，也不得更新 plate。提交后立即 T2 返回 `HOLD`，阻断依赖下游。

步骤 2 发现同键不同 hash/目标是特殊情况：不得覆盖原声明、目标或 event。原 effect 尚未 APPLIED 时标记 `failed(DECLARATION_SOURCE_CONFLICT)` 并追加 APPLY action；已经 APPLIED 时保持 `applied`，追加带冲突错误的 APPLY action 与对账证据，并将本次 run_node 的**物料同步状态**标记失败、返回 HOLD，不改写设备终态。这样既能阻断配置事故，又不会把已成立的历史效果改成失败。

若临时数据库异常导致上述失败记录也无法提交，则整个 T2 回滚，effect 保持原状态；PENDING 由后台 worker 按有上限的指数退避补偿。不能把暂时无法判断结果的异常直接写成确定业务失败。

只有 T2 成功，当前执行线程才返回 `CONTINUE`。

### 5.5 失败分类与恢复策略

| 失败或不确定 | effect | 是否自动重试 | 依赖下游 |
|---|---|---|---|
| 数据库临时异常、连接冲突 | `pending`，记录 `next_retry_at` | 仅自动重试数据库投影，有上限指数退避 | 停止 |
| 目标不存在、归属不符、AUTO 条码、多个目标等确定性配置错误 | `failed` | 否，人工处理后重放 effect | 停止 |
| 设备标识、声明与位置投影互相矛盾 | `needs_reconciliation` | 否，提交确认后的身份与解析证据 | 停止 |
| `state_version` 冲突 | `failed` | 否，人工确认实际状态 | 停止 |
| 同来源不同 declaration hash/目标 | 未应用则 `failed`；已应用则保持 `applied` 并追加冲突证据 | 否，按配置事故处理，不覆盖历史 | 停止 |
| 设备超时、必要步骤结果未知 | `needs_reconciliation` | **不自动重试设备，也不运行 T2 worker** | 停止 |
| 对账确认目标动作未发生 | `cancelled` | 不自动重试；按现有安全策略决定后续 | 停止 |
| 同 hash、同目标重试发现已 APPLIED | 不变 | 直接视为成功 | 可继续 |

PENDING worker 只处理数据库投影补偿，不查询就重放设备命令。NEEDS_RECONCILIATION 由设备最终状态查询或人工对账处理：确认完成后补证据并转为 PENDING，确认未发生后转为 CANCELLED，仍无法确认则保持隔离。

后台补偿成功**不自动恢复 run**；第一期由操作员确认后点继续，避免无人值守时状态冲突被静默放行。立即 T2 成功的正常流程无需人工。

### 5.6 执行结果不确定或 T1 崩溃：先对账，禁止直接重做

T1 未提交可能意味着“设备已经成功返回，但完成与 effect 没落库”；设备超时则连物理结果本身也可能未知。恢复时：

1. 查同一逻辑节点的 `run_command/command_ledger`、步骤证据和各 attempt，区分逻辑圈次与物理重试；
2. 若所有必要物理步骤均有确定成功结果，根据 run_node 快照补写物理完成、证据与 effect，再走 T2，**不重放设备命令**；
3. 若任何必要步骤结果不确定，写入或保持 `needs_reconciliation`，进入设备最终状态查询/隔离/人工确认，不猜成功，也不自动重跑；
4. 对账确认已完成时，保留原 effect 来源键并补证据；确认未发生时标记 `cancelled`；不得通过删除 effect 或增加 attempt 制造另一条物料事件；
5. 在恢复对账完成前，该节点禁止按普通“未完成节点”续跑。

这覆盖的是可恢复性，不把数据库故障包装成物理 exactly-once。

**续跑删除守卫是上线前置条件。** 当前续跑会删除未完成 `run_node`；接入物料效果后，删除条件必须增加 `physical_completed_at IS NULL`，并排除任何已被 effect/event 引用的行。物理已完成、需要对账或已有物料记录的行不得删除重建。续跑计划必须把 `physical_completed_at` 非空的节点视为“只按原快照补物料记录，不重放设备动作”；老数据以 `status='completed'` 作为 `legacy` 兼容判据。若物理完成登记时间缺失且状态也不是已完成，则先执行上面的对账：`run_command/command_ledger` 证据充分才补写，证据不确定就隔离，禁止直接重跑。

### 5.7 人工盘点改状态

人工修改不经过自动 effect，使用一个同步事务：

1. 要求 `expectedVersion` 和修改原因；
2. 锁板并检查版本；
3. 写 `MANUAL` event；
4. 更新当前投影与 `state_version`；
5. 版本冲突返回 HTTP 409，由用户重新确认，不自动覆盖。

## 6. 节点声明契约

### 6.1 存放位置

固定放入独立列 `workflow_node.material_effect jsonb`。选择独立列是因为它是需要稳定约束、快照与查询的执行契约，不是因为“JSONB 不能索引”。`workflow_node.params->'method_params'` 保持原执行参数通道，Mapper 不得再从 params 读取物料声明。

```sql
ALTER TABLE workflow_node
  ADD COLUMN material_effect jsonb;
```

列内结构由版本化 JSON Schema 与应用启动预检约束；S1 同步 Mapper，S2A 将生效声明快照进 run_node。

`workflow_node.material_effect` 的列值示例：

```json
{
  "mode": "transition",
  "target": {
    "by": "position",
    "resourceId": 1000005
  },
  "from": {
    "processState": "pcr_input"
  },
  "set": {
    "processState": "amplified_product",
    "sealState": "sealed"
  }
}
```

`workflow_node.params` 仍只承载原参数，例如：

```json
{
  "method_params": {
    "cycles": 30
  }
}
```

明确无副作用时，独立列的列值为：

```json
{
  "mode": "none",
  "reason": "transfer_only"
}
```

约束：

- 本期 `material_effect` 只声明板级工艺/封膜状态效果，不声明位置迁移、孔级内容变化、CREATE 或 RETIRE；这些名称不得提前出现在 Schema 中形成空承诺；
- `material_effect` 永远不进入 `method_params`，不透传驱动；
- 使用正式 JSON 解析器与 JSON Schema，不复用扁平 `parseFlatJson`；
- `mode=none` 不允许出现 `target/from/set`；
- `mode=transition` 必须有且只有一个 target，`set` 至少包含一个字段；
- `from` 可选，用于要求加工前必须处于指定工艺/封膜状态；T1 解析和 T2 应用都要检查。未配置 `from` 不代表允许并发覆盖，`state_version` 仍必须匹配；
- 本期不建立字典级全局状态迁移矩阵；当业务需要限制所有节点的合法迁移时另评，不能把局部 `from` 前置条件冒充完整生命周期状态机；
- 自动声明不能把状态显式写成 `null`；未知只能来自老数据或带原因的人工修改；
- `processState` 引用租户字典 code；`sealState` 只能是 `none/sealed`；
- 本期一个节点每圈最多一个 effect，多目标拆节点。

### 6.2 target 形态

```json
{ "by": "position", "resourceId": 1000005, "stepSeq": 2 }
```

或：

```json
{ "by": "barcode", "barcode": "${plateBarcode}", "stepSeq": 1 }
```

- `stepSeq` 用于多步节点指定物料作用发生在哪一步；
- 缺省时只允许“最后一步且候选板唯一”，否则报目标歧义；
- 变量在 run 启动快照时解析，不在补偿时重新求值。

### 6.3 目标解析、身份证据与归属校验

声明中的 `plateId/barcode/position` 是**目标选择约束**，不是物理身份确认。解析必须同时保存声明约束、设备命令/回包、stepSeq、位置投影与占用证据，不能只保存最后选中的 plateId。

按位置：

1. 用 `tenant_id + resource_id` 查 `position_state`；
2. 将 `position_state.plate_id` 条码映射到未删除的 `plate`；
3. 要求 `occupied_by_run=当前 run`；它只证明当前 run 的占用授权，不证明设备实际处理了哪块板；
4. 保存实际位置、占用 run、关联命令/步骤证据；
5. 空位置、多个候选、归属为空或不符属于确定性配置/授权错误，标记 FAILED。

按条码：

1. 锁 `tenant_id + barcode` 对应的板；
2. 空条码、`AUTO-*`、多个目标属于确定性配置错误，标记 FAILED；
3. 至少满足一项目标选择证据：当前位置由本 run 占用，或本节点成功命令的参数/回包明确包含该条码；前者仍只是位置/占用证据，不得冒充设备身份确认；
4. 若声明同时带位置，条码与位置必须一致；不一致时还要结合设备证据判断是确定性配置错误还是物理身份冲突。

**身份冲突处理**：设备命令/回包中与本次 `stepSeq` 对应的明确物料标识，应先于位置投影用于核对实际作用对象，但“优先核对”不等于冲突时硬写。设备证据、声明约束、位置投影互相矛盾且无法确定性归为配置错误时，effect/run_node 进入 `needs_reconciliation(MAT_IDENTITY_CONFLICT)`，保存全部冲突证据，不写 event、不更新 plate。对账必须能提交确认后的 plateId 与目标解析证据，才能重新进入 T1/T2。

禁止为了方便而取“第一块板”“第一个空位”作为物料效果目标。

### 6.4 设计期与启动预检

给方法/能力增加设计期元数据：

| 分类 | 例子 | 新流程缺少声明 |
|---|---|---|
| `location_only` | 纯搬运 | 设计器可生成显式 `none` |
| `may_change_material` | 移液、封膜、撕膜、扩增 | ERROR，必须配置 `transition` 或由用户明确确认 `none` |
| `unknown` | 未登记方法 | ERROR，必须人工分类，不能默认无效果 |

规则：

- 方法分类元数据只用于设计/发布校验，运行期不据此猜目标状态；
- 方法元数据另含 `acceptedEvidenceLevels`：普通方法默认接受 `device_ack/physical_confirmed/manual_confirmed`，高风险方法可去掉 `device_ack`；新流程不得只接受 `legacy`。该策略用于运行期证据门禁，仍不用于猜目标或目标状态；
- 老流程缺失为 `legacy_unspecified`：运行不阻断、状态不变，发布新版时给 WARN 并要求逐步补齐；
- 不存在的字典 code：发布和启动均 ERROR；
- 已停用 code：新声明/新 run ERROR，在途快照仍允许按原声明完成；
- `target` 不完整、多个目标、set 为空均为 ERROR，不是 WARN。

## 7. 查询语义与接口

### 7.1 板查询

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/plates?processState=&sealState=&resourceId=&plateType=` | 当前投影筛选；`plateType` 仅沿用现字段，本期不改字典 |
| GET | `/api/plates/{barcode}` | 返回工艺状态、膜状态、`stateVersion`、当前位置及最近事件摘要 |
| GET | `/api/plates/{barcode}/material-events?cursor=` | 事件历史，包含来源 run/node/loop、当时显示名、证据等级、物理发生时间与系统记录时间 |
| PATCH | `/api/plates/{barcode}/material-state` | 人工修改，要求 `expectedVersion` 与 `reason` |

人工修改示例：

```json
{
  "expectedVersion": 12,
  "processStateCode": "purified_sample",
  "sealState": null,
  "reason": "现场复核后修正"
}
```

字段缺席表示不变，显式 `null` 表示人工标记未知；响应冲突使用 409。人工事件固定记录 `manual_confirmed`、操作者、原因和证据快照，不能由客户端伪造为设备物理确认。

### 7.2 run 物料结果

`GET /api/runs/{id}/materials` 同时返回：

- 已 APPLIED 的 event；
- PENDING/FAILED/NEEDS_RECONCILIATION/CANCELLED 的 effect，避免“没有 event 就仿佛没有物料动作”；
- 按板聚合本 run 的首次/最终声明状态、事件数、同步状态和实际证据等级，不把不同证据来源压成一个虚构的“最高等级”；
- 每个未完成 effect 的声明快照、执行证据、错误码、最新对账快照与完整 action 历史，不只返回一个可重试布尔值。

接口含义命名为“**本 run 的物料状态结果**”，不是“本 run 新创建的板”，也不是“当前 owner 为本 run 的板”。

### 7.3 字典

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/plate-process-states?includeDisabled=` | 字典列表 |
| POST | `/api/plate-process-states` | 新增 code |
| PATCH | `/api/plate-process-states/{code}` | 改显示名、排序、启停；禁止改 code |
| — | 不提供 DELETE | 已被历史引用的词汇不能物理消失 |

### 7.4 effect 对账与恢复

| 方法 | 路径 | 适用状态与语义 |
|---|---|---|
| GET | `/api/material-effects/{id}/actions` | 按时间返回完整 DECLARE/APPLY/RECONCILE/RETRY/REBASE/CANCEL 历史 |
| POST | `/api/material-effects/{id}/reconcile` | 仅 NEEDS_RECONCILIATION；提交 `completed/not_completed/still_unknown`、证据、操作者、可选 `occurredAt`，以及可选 `confirmedTarget:{plateId,resolutionEvidence}`；身份冲突确认完成时必须提交 confirmedTarget |
| POST | `/api/material-effects/{id}/retry` | 仅重试物料投影，不重跑设备；FAILED 必须填原因，状态冲突还须提交重新确认的 `expectedVersion` |
| POST | `/api/material-effects/{id}/cancel` | 仅 FAILED；确认放弃自动迁移或已由人工事件处理，必须填原因，不写自动 event |

恢复规则：

- 所有操作在事务内锁 effect 并检查当前状态，状态已变化返回 409；同步更新 run_node，并追加对应 action。`reconciliation_evidence` 可更新为最新快照，但不得覆盖或删除 action 中的历史证据；
- 对账 `completed` 补物理证据后进入 T1/T2；身份冲突还须由服务端重新校验 confirmedTarget 的租户、板身份和解析证据，不能盲目接受客户端 ID。`not_completed` 将 effect/run_node 标记 CANCELLED；`still_unknown` 追加 `needs_reconciliation → needs_reconciliation` 的 RECONCILE action 并保持隔离；
- retry、rebase、cancel 分别追加 RETRY、REBASE、CANCEL action；恢复动作本身不写 plate event，只有后续真实物料投影成功才写 event；
- 状态冲突后的重试属于**显式 rebase**：保留声明 hash，重新读取当前版本与实际 from 作为新的期望快照，并把操作者、原因、旧/新版本与状态写入当次 REBASE action，最新快照同步到 `reconciliation_evidence`。若声明中的 from 前置条件已不成立，禁止 rebase，只能取消后另走评审后的新操作；rebase 不能绕过工艺前置条件；
- declaration hash/目标不一致属于配置事故，不允许 retry/rebase；原 effect 尚未 APPLIED 时可取消，已 APPLIED 时必须保留原历史并走配置事故处置，不得取消或改写旧 event；
- 恢复接口需要独立的物料恢复权限，不能沿用普通“继续 run”按钮隐式放行；补偿成功后仍按本文策略由操作员确认继续。

所有接口必须从服务端认证/授权上下文取得 tenant 与操作者，不接受客户端传 tenant_id 越权查询。复合外键只保证数据库引用一致，**不等于请求租户上下文已经贯通**；源码仍存在 `WorkflowWebService.TENANT = 1L`，在该约束与全链路隔离测试完成前，本方案只能按当前单租户环境交付，不能宣称多租户生产可用。

## 9. 兼容与上线

1. 老板的新字段为 `NULL/0`，界面显示“未知”，不做历史编造回填。
2. 老流程没有 `material_effect` 时保持原执行行为，不自动改状态。
3. 新执行节点增加物理完成登记时间、证据等级与证据快照，不改变无物料声明节点的下游推进语义；老数据只标 `legacy`。
4. 只有显式 `mode=transition` 才启用物料效果；另设 `LABOS_MATERIAL_EFFECT_ENABLED` 作为上线总开关，灰度异常时关闭新效果，不影响老流程。
5. 总开关只禁止创建新 effect，不得停用已有 PENDING 的补偿、NEEDS_RECONCILIATION 的查询与对账，否则会把在途物理动作变成不可恢复记录。
6. `GET /api/plates` 只增加响应字段和可选筛选，不改旧字段。
7. 本期不改 `plate_type`、不建 `consumable`、不移交跨流程持有权、不改 `plate.status` 废料语义。
8. 建库分片与 `90_all_in_one.sql` 必须同步；seed 幂等且不覆盖租户修改。

## 11. 验收与故障矩阵

### 11.1 模型与声明

| # | 用例 | 预期 |
|---|---|---|
| M1 | 老数据查询 | NULL 显示未知，不显示空板 |
| M2 | 字典改名 | 当前显示可用新名，历史 event 保留当时名称快照 |
| M3 | 停用字典 | 新 run 拦截；已快照在途 effect 可完成 |
| M4 | `material_effect` 放进 `method_params` | Schema/预检拒绝，驱动 payload 不含物料声明 |
| M5 | 老流程无声明 | 行为与现状一致；预检能识别 legacy |
| M6 | 已知改物料的方法缺声明 | 新流程发布 ERROR |
| M7 | 纯搬运显式 none | 不创建 effect，不误报为漏配 |
| M8 | 声明 from 与当前状态不符 | T1 失败，不写 event，不自动改成目标状态 |
| M9 | 物理发生时间未知或晚于系统记录 | occurred_at 可为空或与 created_at 不同，不互相伪造 |
| M10 | 逐个插入 effect/run_node/action 的全部合法状态与动作枚举 | 包括 20 字符的 `needs_reconciliation` 在内全部成功；非法值被拒绝 |
| M11 | Mapper 读取独立列，同时 params 保留 method_params | 声明读取来源唯一，执行参数不变；params 内同名声明不得被兼容读取 |

### 11.2 执行路径、依赖门禁与幂等

| # | 用例 | 预期 |
|---|---|---|
| E1 | 同一流程分别走图执行和顺序执行 | effect/event/action/当前投影一致 |
| E2 | 同节点同 run 循环两圈处理同板 | 两条不同 loop_index 的 effect/event；门禁检查实际 visit 1..N 而非汇总行 |
| E3 | 同来源同声明重放 | 不新增 event，不重复推进版本，不重复追加 APPLY action |
| E4 | 同来源不同 declaration hash | 失败并告警，不覆盖原 effect |
| E5 | from=to 的合法声明 | 留一条真实声明事件并推进版本，语义可审计 |
| E6 | T2 后重复调用 worker | 直接返回成功，无副作用 |
| E7 | 同一逻辑执行有三个设备 attempt、重复回调和恢复 | 证据保留各 attempt，但始终只有一个 effect，最多一条 event |
| E8 | 分别用设备回包、独立物理反馈、人工核实完成 | event 准确保留 device_ack/physical_confirmed/manual_confirmed，不自动升级证据等级 |
| E9 | 前置节点 T2 失败，同时存在依赖后继与无关分支 | 依赖后继不派发，无关分支可继续；物理节点仍保持原成功终态 |
| E10 | 循环节点部分圈次 APPLIED、部分 FAILED/NEEDS_RECONCILIATION | 依赖后继仍被阻断，不因 loop_index=0 或最后一圈成功而放行 |
| E11 | 正常图、顺序、多步、循环、设备重试、人工恢复六路径 | 每条路径都能提供逻辑圈次、命令/步骤/attempt 与 effect 的可追溯映射 |

### 11.3 目标、租户与并发

| # | 用例 | 预期 |
|---|---|---|
| C1 | 位置上的板属于其他 run | 失败，两板状态均不变 |
| C2 | `AUTO-*`、空条码、多个目标 | 确定性配置错误为 FAILED，不写 event |
| C3 | 设备重分配、多步节点、目标歧义 | 按实际证据解析；不能唯一确定则失败 |
| C4 | 两个不同节点同时改同板 | 若 T1 取得相同版本，则一个 APPLIED、另一个 MAT_STATE_CONFLICT；不出现重复版本或静默覆盖，后者只能对账/rebase |
| C5 | T1 与 T2 之间人工改板 | T2 检测版本冲突，不覆盖人工值 |
| C6 | 两个人工客户端同时提交 | 一个成功，另一个 409 |
| C7 | effect/event/action 引用其他 tenant 的 run、run_node、plate 或 effect | 复合外键拒绝，应用层测试同样拒绝 |
| C8 | 两个操作员同时对账或 rebase 同一 effect | 行锁与状态检查使一个成功，另一个 409；成功动作追加历史，失败请求不覆盖证据 |
| C9 | 设备明确条码与声明/位置投影冲突 | NEEDS_RECONCILIATION，无 event；提交 confirmedTarget 与证据后才可继续，且只应用一次 |
| C10 | 客户端伪造 tenant_id 或跨租户调用恢复接口 | 服务端上下文与权限拒绝，不依赖复合外键兜底 |

### 11.4 崩溃与恢复

| # | 故障点 | 预期 |
|---|---|---|
| R1 | 物理成功、T1 前崩溃 | 先查命令证据；确定成功只补记录，不确定则隔离，禁止直接重放；不得推断设备未动作 |
| R2 | T1 提交后、T2 前崩溃 | PENDING 被 worker 找到并应用一次 |
| R3 | T2 中途异常 | event、投影、effect、run_node、action 整体回滚，不出现部分提交 |
| R4 | T2 已提交、响应前崩溃 | 重试看到 APPLIED，直接成功 |
| R5 | 临时 DB 故障 | 有界重试；超过上限转人工，不静默 |
| R6 | 物料失败后点继续 | 只补 effect；物理完成节点不重做设备动作 |
| R7 | 编辑流程声明后续跑 | 使用 run_node 原快照，不按新声明改旧物理动作 |
| R8 | 设备超时，随后最终状态确认实际已完成 | 原 effect 从对账转 PENDING，补证据后只应用一次，不重放设备 |
| R9 | 设备超时，随后确认目标动作未发生 | effect/run_node 为 CANCELLED，无 event，不自动重试，追加 RECONCILE action |
| R10 | 多次查询仍无法确定物理结果 | 保持 NEEDS_RECONCILIATION，PENDING worker 不处理，设备不重跑 |
| R11 | 状态冲突后操作员显式 rebase | 保留声明与旧证据，REBASE action 记录新旧版本和原因，按新版本只应用一次 |
| R12 | 灰度开关关闭时仍有在途 effect | 新 effect 被禁止；已有 PENDING 补偿和对账接口仍可用 |
| R13 | T1 连完成事实与意图都无法持久化 | 当前 run 中止并进入对账恢复，不静默推进，不推断物理动作未发生 |
| R14 | T2 成功、业务失败、retry/rebase/cancel 后查询历史 | 每步均有对应不可变 action；恢复动作不生成 plate event，最新快照不覆盖历史 |

### 11.5 交付验证等级

- S1：迁移脚本 + schema sync + 数据库约束与全枚举测试；
- S2：真实 PostgreSQL 故障注入、六条执行路径与依赖门禁集成测试；
- S3/S4：API、完整 action 历史与页面实操；
- 模拟驱动通过只证明逻辑链，不等于真设备验证；真机结论必须另做 HIL。
