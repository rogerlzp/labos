## 4. 🟡 F2 · `verify-role-nav.py` 断言数不稳定（3/0 vs 2/0）

### 4.1 现象

总览 §6 写"期望 **3/0**（清单旧写 2/0 为笔误）"。我实测得到 **2/0**。
脚本本身**相对 HEAD 零改动**，所以是**跨次运行不幂等**。

### 4.2 根因链

`scripts/verify-role-nav.py:91-101`：

```python
_, body = api("/api/users", "POST", {"username": "verify-designer", ...})
created = json.loads(body).get("created")
if created:
    ok("临时 designer 账号创建成功")
elif created is not None:
    ok("临时 designer 账号已存在（幂等）")
# ← created 为 None 时，两个分支都不命中，一条断言都不记，且不报错
```

而重复创建同名用户时，`POST /api/users` 返回的是：

```
HTTP 500  {"timestamp":"...","status":500,"error":"Internal Server Error","path":"/api/users"}
```

⇒ `created` 解析为 `None` ⇒ **静默少一条断言**，PASS 计数变成 2。

**500 的来源**：`OpsUserController.createUser`（`OpsUserController.java:73-90`）**没有 try/catch**，
`SQLException` 直抛 ⇒ Spring 默认错误体。
而 `app_user` 的唯一约束名是 `uk_app_user`（`UNIQUE (tenant_id, username)`）—— **按仓库约定本该映射成 409**。
参照 `StockController.writeError`（`StockController.java:574-586`）：靠异常消息里的 `uk_` 子串判 409。
`OpsUserController` 没走这条路。

### 4.3 后果

- 审核 AI 照文档"期望 3/0"核对，**看到 2/0 会误判为失败**，白花时间排查
- 更隐蔽的是：**少的那条断言恰好是"账号创建成功"** —— 它挂了不影响后续两条，看起来"只差一条"，很容易被当成"环境差异"

### 4.4 建议

1. **后端**：`OpsUserController.createUser` 加 try/catch，用 `writeError` 风格把 `uk_app_user` 冲突映射成 **409** + `{"error":"用户名已存在"}`
   （这也顺带修掉"重复创建用户返回 500"这个独立缺陷）
2. **脚本**：`elif created is not None:` 改成 `else:`（无论什么情况都记一条），或把账号创建失败改成 `bad(...)` 让它显性失败
3. **文档**：修好后再写"期望 3/0"

## 5. 🟡 F3 · `deck_in` 的可达性修好了，但**没有约束兜底**

P0-1 的修复是**纯数据 UPDATE**（`20261114_deck_in_reachable_fix.sql`）：

```sql
UPDATE device_point SET robot_reachable=false, point_role='internal',
       is_entry=false, is_exit=false, updated_at=now()
 WHERE point_kind='deck_in' AND (robot_reachable=true OR point_role<>'internal' ...);
```

`device_point` 上**没有任何约束**把 `point_kind='deck_in'` 绑定到 `robot_reachable=false`：

| 约束 | 管什么 | 管不管 deck_in |
|---|---|---|
| `ck_device_point_kind` | `point_kind ∈ {nest,deck_in,deck_out,waste}` | ❌ 只管取值 |
| `ck_device_point_role` | `point_role ∈ {entry,exit,both,internal}` | ❌ 只管取值 |
| `ck_device_point_flags` | `internal ⇒ 非进出位` | ❌ 不提 robot_reachable |

**后果（我实测过）**：
- `robot_reachable` **列默认值是 `true`**
- 新增一个 deck_in 点位时，默认组合（`point_role='both'` + 非进出）会被 `ck_device_point_flags` **拒绝插入**（报错，但不是语义提示）
- 但 `point_kind='deck_in' + point_role='internal' + robot_reachable=true` **能插进去** ⇒ **语义冲突可复现**
  （我实测这个组合确实能通过所有约束）

⇒ 以后任何一次"给新设备加台面内工位"的操作，都可能把 P0-1 重新引入，且**没有任何东西会拦**。

**建议**：加一条 CHECK 兜底

```sql
ALTER TABLE device_point ADD CONSTRAINT ck_device_point_deck_in_reach
  CHECK (point_kind <> 'deck_in' OR robot_reachable = false);
```

（并把 `20261113_device_point.sql` 的 `robot_reachable` 默认值改成 `false` —— 272 个 internal 点位都是 f，
默认值取 `true` 对多数点位是错的。）
