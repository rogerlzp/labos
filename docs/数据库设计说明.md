# 数据库设计说明

> 只讲**当前怎么用**：每张表存什么、关键字段、谁写谁读、常用查询。
> 建表脚本在 `pg_rebuild/schema/`，本文是它的说明书。

---

## 一、概览

库名默认 `labdb`（环境变量 `LABOS_DB_NAME`），共 **98 张表**，按职责分七组：

| 组 | 表 | 说明 |
|---|---|---|
| **资源模型** | `resource_node` `device_instance` `capability` `device_state` `resource_capability` | 岛→设备→层位的树，以及设备实时状态 |
| **流程** | `workflow` `workflow_node` `workflow_edge` `workflow_node_step` | BPMN 图定义 |
| **执行** | `run` `run_node` `run_command` `run_event` `run_variable` `run_artifact` | 一次执行的完整痕迹 |
| **实验** | `experiment` `experiment_process` `experiment_variable` `experiment_graph` `experiment_run` `experiment_run_step` | 多流程编排 + 变量 + 循环 |
| **板位** | `plate` `plate_well` `position_state` `robot_point` | 板子在哪、机械臂点位 |
| **驱动** | `driver` `driver_capability` `driver_health` `device_method` `device_log` | 设备方法字典与通信 |
| **告警** | `alert_state` | 告警聚合 |

**分区表**：`device_log`、`run_event` 按月分区（`device_log_202609` 等），查询时直接查父表即可。

## 二、资源模型

### `resource_node` — 资源树（核心表）

岛 → 设备 → 层位，用 `parent_id` 自引用成一棵树。

| 字段 | 说明 |
|---|---|
| `id` | **主键**。图、执行记录、位置状态都用它 ★ |
| `parent_id` | 上级节点；岛为 NULL，设备指向岛，层位指向设备 |
| `kind` | 枚举：`island` / `device` / `incubator` / `storage` / `transfer_point` |
| `code` | 业务编号，如 `ID1183`、`I4495`、`LAB-DEMO-02`，**界面上显示的就是它** |
| `name` | 中文名 |
| `attr` jsonb | 扩展属性，画布坐标在 `attr->>'pos_x'` / `pos_y` |

**层级约定**：

```
island（岛）
 └ device（设备，如 ID1183 孵箱）
    └ incubator / storage / transfer_point（层位，如 I4495）
```

**常用查询**：

```sql
-- 某个岛下的所有设备
SELECT id, code, name FROM resource_node
WHERE parent_id = (SELECT id FROM resource_node WHERE code = 'LAB-DEMO-02')
  AND kind = 'device';

-- 某台设备的层位
SELECT id, code FROM resource_node
WHERE parent_id = (SELECT id FROM resource_node WHERE code = 'ID1183')
  AND kind IN ('incubator','storage','transfer_point');
```

### `device_instance` — 设备实例

**一台真实设备**。与 `resource_node` 的区别：

| | `resource_node` | `device_instance` |
|---|---|---|
| 语义 | 资源树节点（含岛、层位） | 只有"可下发的设备" |
| 被谁用 | 图、执行记录、位置 | **驱动、探针** ★ |
| 关系 | `device_instance.resource_id → resource_node.id` | |

**⚠ 这是本项目最容易踩的坑**：两者都是 `long`，混用不报错但行为错。
上层调用统一用 `resource_node.id`，**只有调驱动前才转成 `device_instance.id`**。

```sql
-- 转换（代码里封装在 instanceIdOf()）
SELECT id FROM device_instance WHERE resource_id = ? AND deleted_at IS NULL;
```

关键字段：`driver_id`（走哪个驱动端点）、`ip`（归属标识+运维定位，**不是通信地址**）。

### `capability` — 能力字典

`INCUBATE`（孵育）、`TRANSFER`（转运）、`ALIQUOT`（分液）等。
设备通过 `resource_capability` 关联能力，流程节点按**能力**找设备，不写死编号。

### `device_state` — 设备实时状态

| 字段 | 说明 |
|---|---|
| `status` | `idle` / `running` / `error` |
| `has_plate` | **派生字段**：该设备下任一层位有板 → true |
| `current_run_id` | 当前占用它的 run |

**`has_plate` 不要手工维护**，由 `PositionLock.refreshHasPlate()` 从 `position_state` 派生。
两处各写会不一致（"显示有板但层位是空的"，取板时取不到）。

## 三、板位

### `position_state` — 层位状态（板位唯一真相）

| 字段 | 说明 |
|---|---|
| `resource_id` | 层位的 `resource_node.id` |
| `plate_id` | 板号；NULL/空 = 空闲 |
| `reserved_until` | 预约到期时间（搬运中临时占住） |
| `reserved_by_run` | 谁预约的 |
| `occupied_since` | 从什么时候开始有板 |

**三种状态**：

| 状态 | 判据 | 含义 |
|---|---|---|
| 空闲 | `plate_id` 空 且 无有效预约 | 可放板 |
| 预约中 | `reserved_until > now()` | 搬运中，几十秒 |
| 有板 | `plate_id` 非空 | 占着，要等实验取板 |

**抢占必须原子**（一条语句完成检查+占用）：

```sql
INSERT INTO position_state (tenant_id, resource_id, reserved_until, reserved_by_run, updated_at)
VALUES (?, ?, now() + ?::interval, ?, now())
ON CONFLICT (tenant_id, resource_id) DO UPDATE
SET reserved_until = now() + ?::interval, reserved_by_run = EXCLUDED.reserved_by_run
WHERE (position_state.plate_id IS NULL OR position_state.plate_id = '')
  AND (position_state.reserved_until IS NULL
       OR position_state.reserved_until < now()
       OR position_state.reserved_by_run = EXCLUDED.reserved_by_run);
```

**为什么不能先 SELECT 再 UPDATE**：中间有窗口，两个实验会同时认为位置空闲。

### `robot_point` — 机械臂点位

| 字段 | 说明 |
|---|---|
| `robot_resource_id` | 哪台机械臂（`resource_node.id`） |
| `code` | 点位码，`Transfer(source, target)` 用的就是它 |
| `x` / `y` / `z` | 示教得到的坐标 |
| `device_resource_id` | 关联哪台设备（界面显示用） |

**`code` 默认等于设备编号**（同步时按设备生成），后续示教后填坐标即可。

### `plate` / `plate_well` — 板子档案

`plate` 存板号、类型、当前位置；`plate_well` 存 96 孔板每孔的样本。

**注意** `plate` 是**冗余表**：板位的真相在 `position_state`。
写 `plate` 失败**不能影响**位置锁（所以它不在位置锁的事务里）。

## 四、流程与执行

### `workflow` / `workflow_node` / `workflow_edge`

BPMN 图定义。

| 表 | 关键字段 |
|---|---|
| `workflow` | `code`、`name`、`graph_xml`（bpmn-js 的 XML） |
| `workflow_node` | `node_key`（BPMN 元素 id）、`name`、`method`、`params` jsonb |
| `workflow_edge` | `source_key` → `target_key`、`condition` |

`workflow_node.params` 里常见：

```json
{
  "method_params": { "plate_id": "${batch}-${no}" },
  "bound_resource_id": 200171,
  "x": 320, "y": 200
}
```

### `run` / `run_node` / `run_command` — 执行痕迹（三层）

```
run（一次执行）
 └ run_node（一个节点）
    └ run_command（一次设备命令）
```

| 表 | 关键字段 | 谁写 |
|---|---|---|
| `run` | `status`(run_status)、`mode`、`workflow_id`、`output` | 执行入口 |
| `run_node` | `name`、`status`(node_status)、`resource_id`、`level` | 状态机 |
| `run_command` | `command_seq`、`method`、`payload`、`device_raw_response`、`device_id`、`attempt` | 驱动执行 |

**⚠ 两个状态枚举不是同一个类型**：

- `run.status` 是 `run_status`
- `run_node.status` / `run_command.status` 是 `node_status`

写混了 JDBC 会报 `column status is of type X but expression is of type Y`。

**排查问题必查三张表**：

```sql
-- ① 哪一步失败、传了什么、设备回了什么
SELECT command_seq, method, device_id, status, error_code,
       payload, device_raw_response
FROM run_command WHERE run_id = ? ORDER BY command_seq;

-- ② 这一步用的哪台设备
SELECT name, status, resource_id FROM run_node WHERE run_id = ? ORDER BY id;

-- ③ 整体结论
SELECT status, error_code, output FROM run WHERE id = ?;
```

`run_command` 是**最有价值的那张表**：有 `payload`（实际参数）、
`device_raw_response`（驱动原文）、`device_id`（哪台设备）。
出问题时它比日志更可靠。

## 五、实验

```
experiment（实验定义）
 ├ experiment_process（步骤：哪个流程、第几步、循环几次）
 ├ experiment_variable（变量：默认值）
 ├ experiment_graph（画布 jsonb）
 └ experiment_run（一次执行）
    └ experiment_run_step（展开后的每一步，含 loop_index）
```

### `experiment`

| 字段 | 说明 |
|---|---|
| `island_id` | 在哪个岛跑（**调度器据此做岛级互斥**） |
| `priority` | 优先级，越小越优先 |
| `deadline` | 截止时间（排序时优先于优先级） |

### `experiment_process`

| 字段 | 说明 |
|---|---|
| `workflow_id` | 用哪个流程 |
| `seq` | 第几步 |
| `loop_count` | 循环次数；空=1，支持 `${var}` |

### `experiment_run` / `experiment_run_step`

| 表 | 关键字段 |
|---|---|
| `experiment_run` | `status`、`variables` jsonb、`expanded_steps`、`current_seq` |
| `experiment_run_step` | `seq`、`loop_index`、`workflow_id`、`run_id` |

`experiment_run_step.run_id` 指向 `run.id`——**实验层只记录"跑了哪个 run"，细节去 `run` 查**。

## 六、驱动

### `driver` — 驱动端点

`endpoint` 形如 `tcp://host:8501`。**一个驱动服务管多台设备**，
所以 `device_instance.ip` 不是通信地址，`driver.endpoint` 才是。

### `device_method` — 方法字典

| 字段 | 说明 |
|---|---|
| `device_id` / `capability_id` | 哪些设备/能力能调这个方法 |
| `method` | 方法名，如 `Deposit1`、`Transfer`、`Home` |
| `params` jsonb | 参数定义（`control_type`、`required`、`options`） |
| `timeout_ms` | 超时 |

前端选完方法后拉 `GET /api/methods/{method}/params` 渲染表单，数据来自这里。

### `device_log` — 通信日志（按月分区）

原始收发字节，**排查协议问题时看**。日常不查（量大）。

## 七、常用查询

### 某个岛现在有哪些位置有板

```sql
SELECT r.code AS 位置, r2.code AS 所属设备, ps.plate_id, ps.occupied_since
FROM position_state ps
JOIN resource_node r  ON r.id = ps.resource_id
LEFT JOIN resource_node r2 ON r2.id = r.parent_id
WHERE r.parent_id IN (
        SELECT id FROM resource_node
        WHERE parent_id = (SELECT id FROM resource_node WHERE code = ?)
      )
  AND ps.plate_id IS NOT NULL;
```

### 设备实时状态

```sql
SELECT r.code AS 设备, ds.status, ds.has_plate, ds.current_run_id
FROM device_state ds JOIN resource_node r ON r.id = ds.resource_id
WHERE ds.tenant_id = 1;
```

### 某个实验最近几次执行

```sql
SELECT id, status, expanded_steps, current_seq, started_at, finished_at
FROM experiment_run WHERE experiment_id = ?
ORDER BY id DESC LIMIT 20;
```

### 一条执行发了哪些命令

```sql
SELECT command_seq, method, device_id, status, error_code,
       (result->>'durationMs')::int AS 耗时ms
FROM run_command WHERE run_id = ? ORDER BY command_seq;
```

**耗时是 0 或个位数** → 走的是 mock/虚拟驱动，没真在等设备。

## 八、设计约定

| 约定 | 说明 |
|---|---|
| **`tenant_id` 每表都有** | 多租户，查询必须带，否则会串数据 |
| **`deleted_at` 软删** | 有这列的表查询要加 `deleted_at IS NULL` |
| **两套 ID** | 上层 `resource_node.id`，调驱动前转 `device_instance.id` |
| **两个状态枚举** | `run_status` vs `node_status`，别混 |
| **`has_plate` 是派生** | 由 `position_state` 算出来，不要手工写 |
| **`plate` 是冗余** | 写失败不影响位置锁，不要放进位置锁事务 |
| **命令行要幂等** | `run_command.attempt` + 同一 `command_id`，重发不重复执行 |

## 九、建表与初始化

```bash
cd pg_rebuild

# 1) 建表（纯 DDL，不含任何数据）
psql -h <host> -U <user> -d <db> -f schema/90_all_in_one.sql

# 2) 校验
psql -h <host> -U <user> -d <db> -f schema/99_verify.sql

# 3) 可选：初始数据（租户 / 字典 / 账号）
psql -h <host> -U <user> -d <db> -f schema/95_seed_data.sql
```

**建表与数据是分开的**：

| 文件 | 内容 | 是否必需 |
|---|---|---|
| `90_all_in_one.sql` | 74 张表的 DDL | 必需 |
| `95_seed_data.sql` | 租户 / 能力字典 / 错误码 / 初始账号 | **可选**，但租户必需 |

`95_seed_data.sql` 里全部是 `ON CONFLICT DO NOTHING`，
**不删不改已有数据**，可以安全重复执行。

`schema/merge.sh` 把 `10/20/30/40` 分片合成 `90_all_in_one.sql`（不含种子）。
