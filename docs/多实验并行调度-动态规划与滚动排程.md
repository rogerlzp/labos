## 1. 先厘清概念：三种"动态规划"

这个词在不同语境下指完全不同的东西，必须先分开：

| 说法 | 学术含义 | 我们用不用 |
|---|---|---|
| **动态规划（DP）** | 状态转移方程求最优解（Bellman） | ❌ 状态爆炸，用不了 |
| **动态调度（Dynamic Scheduling）** | 运行时根据实际状态调整排程 | ✅ **这才是该做的** |
| **滚动时域（Rolling Horizon）** | 每次只排未来一个窗口，循环重排 | ✅ **具体实现方式** |

**结论：不做 DP，做滚动时域动态调度。**

理由见 §2，做法见 §3。

## 2. 为什么纯 DP 用不了

### 2.1 问题规模

标准 Job Shop 的 DP 状态：

```
f(S, t₁, t₂, ..., t_M) = 已排实验集合 S、各岛可用时间 t_i 下的最小完工时间

状态数 ≈ 2^N × (时间离散档数)^M
```

| 参数 | 我们的值 |
|---|---|
| N（实验数） | 夜班 20~50 |
| M（岛数） | 26 |
| 时间档 | 哪怕只按分钟分，一个班 8 小时 = 480 档 |

`2^50 × 480^26` —— 天文数字。

### 2.2 就算能算，输入也不准

DP 求最优解的前提是**工时准确**。而我们的现实：

```
方法               p50      p90     波动比
Transfer          10.0s    40.0s     4.0×
RunProtocol       25.0s   250.0s    10.0×
Run               18.5s   250.0s    13.5×
```

**波动比 13.5 倍**意味着：最优解和次优解的实际差距，小于工时误差本身。

> 用不准的数据算最优解，等于用精确的秤称一堆会呼吸的东西。

### 2.3 唯一能用 DP 的特例（并说明为什么还是不用）

如果满足：

- 每个实验只占 1 个岛（✅ 我们的 1.0 约束）
- 实验之间无顺序依赖（✅ 1.0 全独立）
- 目标只是最小化最大完工时间

那么退化成 **P||Cmax（并行机调度）**，有 DP 解和 PTAS 近似。

**但我们还是不用**，因为：

| 原因 | 说明 |
|---|---|
| 目标不只是 Cmax | 还有截止时间满足率、设备利用率均衡 |
| 现场会变 | 设备坏了、实验失败了，DP 的解立刻作废 |
| 不可解释 | 值班员要的是"为什么它排第 5"，不是"Pareto 最优" |

## 3. 该做的：滚动时域动态调度

### 3.1 核心思想

```
不一次性排完所有实验。
每次只排未来一个窗口（比如 2 小时），跑完再排下一段。
```

这是 MES / APS 领域的标准做法，本质就是**动态地做规划**——每一轮都是对当前状态的最优决策，而不是对全周期的一次性最优。

### 3.2 三个关键机制

#### ① 承诺窗口（Commitment Window）

```
已开始的实验 → 绝不改动
```

**为什么**：实验已经在驱动设备了，改了也没用，还可能造成板子位置错乱。

#### ② 冻结区（Frozen Zone）

```
未来 15 分钟内的排程 → 除非有紧急插单，否则不动
```

**为什么**：让现场有准备时间。总在变的排程等于没有排程。

#### ③ 事件驱动重排（Event-Triggered Rescheduling）

| 事件 | 动作 |
|---|---|
| 新实验提交 | 插入排队，下次重排时考虑 |
| 实验完成 | 释放岛，立刻尝试派发下一个 |
| 实验失败 | 释放岛 + 告警 + 重排 |
| 设备离线 | 标记该岛不可用 + 重排受影响实验 |
| 人工改优先级 | 立即重排 |

**不是定时轮询才算动态**——事件驱动的响应更快。

### 3.3 完整算法

```java
/**
 * 滚动排程主循环。
 * 每 2 秒或被事件触发时执行一次。
 */
void rollingSchedule() {

    // ── ① 收集当前状态 ──────────────────────────
    List<Island> islands = loadIslands();               // 26 个
    Map<Long, Instant> islandFree = loadIslandFreeAt(); // 各岛何时可用
    List<ExpRun> committed = loadCommitted();           // 已开始，不可动
    List<ExpRun> queue = loadQueued();                  // 待排

    // ── ② 排序：EDD → 优先级 → FIFO ──────────────
    queue.sort(EDD_THEN_PRIORITY_THEN_FIFO);

    // ── ③ 逐个尝试分配（贪心 + 最早可用岛）──────
    for (ExpRun r : queue) {
        Duration dur = estimate(r);                     // 用 p90，不用 p50

        Island best = null;
        Instant bestStart = null;

        for (Island isl : islands) {
            if (!isl.available()) continue;             // 设备离线

            Instant start = islandFree.get(isl.id());
            Instant end   = start.plus(dur);

            // 死线约束：超了就不选这个岛
            if (r.deadline != null && end.isAfter(r.deadline)) continue;

            if (bestStart == null || start.isBefore(bestStart)) {
                best = isl;
                bestStart = start;
            }
        }

        if (best == null) {
            // 没有岛能按时完成 → 标记逾期风险，但仍排队
            markAtRisk(r);
            continue;
        }

        r.assign(best, bestStart, bestStart.plus(dur));
        islandFree.put(best.id(), bestStart.plus(dur));  // 该岛往后推
    }

    // ── ④ 派发"现在就该开始"的 ─────────────────
    Instant now = Instant.now();
    for (ExpRun r : queue) {
        if (r.assignedStart().isBefore(now.plus(DISPATCH_LOOKAHEAD))) {  // 提前 10 秒派
            if (islandLock.tryAcquire(r.islandId(), r.id())) {
                dispatch(r);
            }
        }
    }
}
```

### 3.4 为什么这是"贪心"而不是"最优"

**贪心的代价**：不保证全局最优。

**贪心的好处**：

| 好处 | 说明 |
|---|---|
| **可解释** | "它截止最早，所以先给它最早的岛" |
| **可增量** | 新实验来了只影响后面的，前面的不动 |
| **可中止** | 任何时刻停下，已有排程仍然有效 |
| **O(N·M)** | 实验数 × 岛数，毫秒级 |

**关键洞察**：在**滚动**框架下，"每一步局部最优"比"一次性全局最优"更实用——因为一次性最优的前提（未来已知）在现实中不成立。

### 3.5 改进：局部修复而非全部重排

全部重排的问题：**排程抖动**（同一个实验在两次排程里位置变来变去）。

改进：

```java
// 只重排受事件影响的部分
Set<Long> affected = findAffected(event);
    // 新实验 → 只影响它之后的
    // 实验失败 → 只影响占同一岛的
    // 设备离线 → 只影响用该岛的

// 其余保持现有排程（已在 committed 里）
```

**收益**：排程稳定性大幅提升，值班员不会看到"排程一直在变"。

## 4. 实验层补什么

一个实验就是几个流程按顺序跑。流程内部用 BPMN 表达节点、连线和网关。实验层补的是：

| 补什么 | 为什么必须补 |
|---|---|
| **实验变量** | 同一个流程跑不同温度，不该复制流程 |
| **跨流程循环** | "3 个流程跑 5 轮"是夜班常态 |
| **岛级资源互斥** | 机械臂打架是物理事故，不是逻辑错误 |
| **滚动重排** | 现场一定变，排完就不动的排程等于假的 |
| **资源冲突预警** | 试算阶段就告诉你会撞，而不是跑到一半 |
| **试算排程** | 把将来要跑的事画出来 |

### 4.2 不做什么（同等重要）

| 不做 | 理由 |
|---|---|
| 甘特图拖拽调整排程 | 工时不准，拖了也是假的 |
| 自动优化算法（CPLEX/GA） | 数据不准 + 不可解释 |
| 岛内多实验并行 | 需秒级时长数据，现有工时数据只有 10 秒级 |
| 嵌套循环 | 展开后步骤数爆炸 |
| 条件块（if/else） | 用流程层 BPMN 网关，避免两处都能表达条件 |

> **克制也是设计**：不做的每一项，都是因为它会带来"看起来能做、实际做不准"的风险。

## 5. 三个必须拍板的决策

### 决策 1：实验必须显式声明 `island_id`

| 方案 | 问题 |
|---|---|
| 从流程节点反推岛 | 普通节点只绑能力，执行时才选设备 → **岛不确定** |
| 按能力池第一个算 | 会算出"这个实验用 5 个岛"，实际只用了 1 个 |
| **显式声明** | ✅ 调度器能静态算清资源占用 |

**代价**：用户必须选岛。**收益**：排程可预测。

> **建议：采用显式声明。** 界面上默认选"设备最多的岛"，减少操作成本。

### 决策 2：1.0 用岛级互斥（并行度 = 岛数）

| 方案 | 并行度 | 风险 |
|---|---|---|
| **岛级互斥** | = 岛数（26） | 无机械臂打架 |
| 岛内并行 | 更高 | 需秒级时长 + 板级跟踪，现在都做不到 |

**代价**：同时能跑的实验数不超过岛数。

**收益**：**绝不出现机械臂打架**。

> **建议：采用岛级互斥。** 这是安全下界。等积累 3 个月真实时长数据，再评估岛内并行。

### 决策 3：1.0 不做跨流程依赖（`runAfter` 字段留但不用）

| 方案 | 复杂度 | 收益 |
|---|---|---|
| 全顺序 | 低 | 库内流程实例以顺序执行为主（`run_mode` 统计） |
| 支持 `runAfter` DAG | 高（需拓扑排序 + 环检测 + 部分失败处理） | 1.0 用不上 |

**代价**：暂时不能表达"流程 A 和 B 并行，都完成才跑 C"。

**收益**：执行器简单，出错好查。

> **建议：1.0 全顺序。** 真出现并行需求，用"拆成两个实验 + 岛级并行"代替。

## 7. 验证标准

1.0 做完，必须能回答：

| 问题 | 验证方式 |
|---|---|
| 两个实验会不会抢同一个岛？ | 提交 2 个同岛实验 → 第二个进 queued，第一个完成后自动开始 |
| 机械臂会不会打架？ | 同岛永不同时跑（岛锁） |
| 实验失败会不会卡住岛？ | 杀进程 → TTL 到期释放 → 下一个能进 |
| 排程能不能解释？ | `/api/scheduler/status` 显示每个锁的持有者和到期时间 |
| 变量替换对不对？ | `temp=37` 代入流程，跑出来的 `run_command.payload` 里能看到 |
| 循环展开对不对？ | `loopCount=3` → 生成 3 个 run，`experiment_run_step.loop_index` 是 0/1/2 |
