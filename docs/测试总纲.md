## 1. 有效测试判据（红线）

来自 2026-11-08 的 `scripts/ci-gate.sh` 审查。**不满足以下判据的「通过」不算通过**，即使断言数是绿的。

### 1.1 禁止用 SQL 造/改业务状态

被测动作必须由真实入口触发：页面按钮或 HTTP API。脚本直接 `INSERT run status='running'`、`UPDATE run SET status='paused'`、`INSERT device_method ... interruptible=true`、`UPDATE runtime_hold SET released_at=...`、`UPDATE device_instance SET driver_id=...` 都绕过了 Java 业务规则，随后读回来的很可能只是自己刚写进去的值。

清理阶段删自己造的数据是允许的；**构造和改变业务状态不允许**。

### 1.2 关键动作必须三段同断言

每个会影响用户的动作，要同时断言 **页面 DOM + API JSON + DB 行**，三者不一致即红。
只查库能证明「后端算对了」，证明不了「用户看得到、点得动」。

### 1.3 门禁脚本自身必须可信

- 子脚本**退出码**必须纳入判定，不能只解析中文「通过 N / 失败 M」文本；
- 汇总行缺失要单独成一类，且打印输出尾部；
- `MIN_*` 枚举正则必须覆盖含数字的常量名；
- SKIP 的判定要与子脚本实际打印一致，同一「缺环境」条件在不同段表现必须一致；
- 有 SKIP 时不能无条件 `exit 0` 并打印「门禁通过」。

### 1.4 断言条数 ≠ 覆盖强度

`MIN_*` 只许涨，能防「删用例」，防不住「把强断言换成无条件 `ok()`」或「有数据才测的关键分支」。
因此加用例时要写清断言判据，删断言要说明；长期目标是给关键断言稳定 ID，门禁校验「必需 ID 集合」而非仅条数（见 §8）。

### 1.5 当前已知的 5 类偏差（脚本侧待修，见 §8）

| # | 偏差 | 证据 | 影响 |
|---|---|---|---|
| 1 | 默认门禁不测页面、不测 API | `ci-gate.sh` 无参只跑段 0/1/2/2.5；`test-all.sh:137` 用 `java -cp` 直调 main | 绿灯 ≠ 页面能用 |

## 3. 三类场景（不遗漏）

### 3.1 改功能时：五步决策卡

1. **定范围**：`git diff --name-only` → 匹配 §4 映射表 → 得到「本次必跑段 + 命令」。阶段 1 后由 `scripts/test-select.py` 自动输出。
2. **定轨道**（沿用 `docs/测试规范.md:44-52` 的双轨表，该表内容仍有效）：后端逻辑 → 脚本轨；界面交互 → 页面轨；接口字段 / 端到端链路 → 两轨都要。
3. **判契约变更**：动了状态词表、API 字段、`pg_rebuild/schema/` → 强制触发 §1.2 的三段同断言，并同步 `webapp/src/api/client.ts` 的类型与页面展示。
4. **判用例变更**：加/删断言 → 按 §5.3 同步；改期望值不能只改实现不改用例。
5. **留证**：把「本次触发了哪些段、实际跑了什么、结果如何」写进提交信息（`docs/提交规范.md:149-158` 已要求写验证方式，正好接上）。SKIP 的段必须写明原因。

### 3.2 不同模块：映射表一条记录即可，不写 15 份模块测试文档

模块划分依据 `docs/技术架构与模块地图.md`：Java 11 个包、React 23 个页面、3 个外围进程。
每个模块在 §4 只占一行（`paths` / `gates` / `tier`），已有的模块设计文档保留为设计说明，测试部分改成一行指向本文。

**四个已确认的覆盖空白**（优先补，都是低成本）：

| 空白 | 证据 | 处置 |
|---|---|---|
| 权限零门禁覆盖 | `verify-rbac.py` 是孤儿；唯一角色断言在 `e2e-smoke.py` 的 admin | 接 T1，加一个非 admin 角色页面冒烟 |
| 两个静态检查未接 | `README.md:144` 要求 `scan-i18n.py`，`verify-en-docs.py:8` 自称可进 CI，但 `.github/workflows/ci.yml` / `ci-gate.sh` 都没调 | 接 T0，零成本 |
| gateway / Redis 零自动化 | `scripts/` 里 `redis` 只命中文档脚本 | 标 `manual`，见 §2.3 |
| 6 个未覆盖页面 | `docs/测试用例总表.md:238`（`/gantt` `/duration` `/plates` `/island` `/topology` `/audit` 等） | 按使用频率分级，先只读冒烟 |

### 3.3 提交时：统一口径

**以本节为准，以下 5 处旧清单全部 `DEPRECATED`**：`CONTRIBUTING.md` 第 5 条、`.github/PULL_REQUEST_TEMPLATE.md` 验证勾选项、`docs/提交规范.md` §七、`docs/测试规范.md` §七、`docs/自查清单.md` §E。

| 环节 | 现行规则 |
|---|---|
| `git commit` 前 | 跑 §3.1 决策卡给出的必跑段；验证命令与结果写进提交信息 |
| `git push` 前 | `.githooks/pre-push` 调 `scripts/gate-select.py` 按 diff 选档：文档只跑 `verify-en-docs.py`，代码跑 T0；T1 建议清单打印（`LABOS_GATE_T1=1` 自动跑）；T2 全量留发布前 |

| GitHub CI | 保持 T0；阶段 3 补 `scan-i18n.py` / `verify-en-docs.py` |
| nightly | 按 T1 全模块 + 关键 T2 裁剪；4.13 独占段单独排队 |
| SKIP | 有 SKIP 必须显式列出「哪些没跑、为什么」；`SKIP_GATE=1` 必须留痕，不允许无痕绕过 |

| 名称 | 含义 | 出处 |
|---|---|---|
| **V1–V5** | 上线验证视角：单元 / 单命令探针 / 整流程影子 / 分段联调 / 生产灰度 | 原 `docs/测试与上线策略.md` 的五层模型，保留为现场上线参考 |

### 5.3 加 / 删用例的维护动作

### 7.3 讨论纪要：两个方案的取舍

**「文档和脚本一起改」还是「先文档后脚本」？**

- 一起改的好处：文档声明的红线立刻与脚本一致，不会出现「文档说不能 SQL 造状态、脚本还在造」的空窗。
- 一起改的代价：脚本侧 P0 涉及 4 个门禁 bug + 2 个暂停脚本（4.16/4.18）的入口重写（4.17 已走真实入口），外加 4.18 的 `interruptible` 夹具口径；需要 PG + API + 前端 + sidecar + 仿真机全套环境，且必须跑 `--all`（40 分钟、4.13 独占）才能验证；与十几份文档的改动放在同一个变更里，一旦回归无法归因。
- **结论（D-TEST-08）**：本次只改文档；脚本按 §8 阶段 0 → 1 → 3 分批。为控制空窗，本文 §1.5 明确列出「当前已知的 5 类偏差」并声明「改造完成前引用相关门禁结论须注明此限制」。用户可在文档评审通过后决定脚本何时开工。
