## 一、我认领：P0-1 是我上轮改 ⑤ v2 时引入的回归，v3 没有修

**位置**：⑤ §3.1 / §3.2（v3）、邀请"已知问题清单 P0-1"

### 1.1 事实确认：P0-1 属实，且 K-01 必红

⑤ v3 的 `ResourceType` **仍是两值**（§3.1 未改）：

```java
public enum ResourceType {
    DEVICE_STATE(1),
    POSITION(2);
}
```

真实申请顺序（`DriverStepExecutor:540-614` 搬运分支）：

| 序 | 申请 | 锁实现 | §3.1 的 rank |
|---|---|---|---|
| 外层 | 设备执行锁 | `DeviceLock`（`device_state`） | **1** |
| 1 | 目标位预留 | `PositionLock`（`position_state`） | **2** |
| 4 | 轨道分区锁 | `RailZoneGuard` → **复用 `DeviceLock`** | **1** |

⇒ 序列是 **1 → 2 → 1**，而 §3.2 的断言是 `want.rank < last.rank ⇒ throw` ⇒ **每次正常搬运到轨道锁处必抛 `IllegalStateException`** ⇒ **K-01（正常搬运无断言触发）必红**。

### 1.2 v3 改了什么、没改什么

v3 改的是**类型来源**（由调用点传 → 按 kind 推导 → **由锁实现类声明**），**没有改 rank 值，也没有改"轨道复用 DeviceLock"这个事实**。

⇒ 且 v3 的"类型由锁实现类声明"**恰好把问题固化了**：`RailZoneGuard` 复用 `DeviceLock`，按 v3 的写法它"自动继承 `DEVICE_STATE`" ⇒ **轨道永远拿不到自己的 rank**。

**结论：这条回归是我在上一轮（评审记录 20261118-06 的 ⑤ v2 重写）引入的 —— 我当时把 `ResourceType` 从三值"简化"成两组，理由是"轨道分区锁与设备锁同表同列"。那个理由对"是否存在跨类互等"是对的（同一张表的行之间不互等），但我把它错误地套到了"rank 序"上 —— rank 应当编码的是"申请槽位"，不是"存储表"。**

### 1.3 候选方案 A/B/C 的结论

| 方案 | 结论 | 依据 |
|---|---|---|
| **A 类型三值（DEVICE/POSITION/RAIL）与存储表解耦** | **方向正确，但必须配一条 A1** | 真实槽位序 = 设备(1) → 位置(2) → 轨道(3) ⇒ 单调 ✓。**但 A1：断言只能由"语义拥有者"发起一次** —— `RailZoneGuard` 在调 `DeviceLock.tryAcquire` 之前 `enter(RAIL)`；`DeviceLock` 内部**不得再按自己的 TYPE 断言**，否则 `RAIL(3)` 之后又断言 `DEVICE_STATE(1)` ⇒ 仍然倒退、仍然误报 |
| **B 调整真实申请顺序**（先轨道后位置） | **不推荐** | 技术上可行（轨道路径键 `sourcePos->targetPos` 由位置**码**算出，不需要持有位置锁）；但会变成"**先占最稀缺资源（轨道）再排队等位置**"⇒ 轨道持有时间变长 ⇒ 机械臂吞吐进一步下降（实测臂已是瓶颈，设计基线 R-03：单臂 ≈6.46 次/分、单 run 需求 p50 ≈3.35 次/分）⇒ 与 §4.7 的物理态视角也冲突（轨道"物理空出"更难保证） |
| **C 断言只比跨组** | **不解决** | 倒退**正是**跨组（position 组 → device_state 组）。"只比跨组"若指"只在同一组内比"，则跨组乱序完全不被拦 ⇒ 护栏失效 |

### 1.4 我建议的第四方案（比 A 更贴真实语义）

把断言从"**rank 单调**"改成"**槽位序列必须是全局固定序列的前缀**"：

```
全局槽位序列：DEVICE(1) → POSITION(2) → RAIL(3)
本线程已持有的槽位集合必须是它的前缀：
  {} ⊂ {DEVICE} ⊂ {DEVICE,POSITION} ⊂ {DEVICE,POSITION,RAIL}
```

好处：

- 允许"跳过某槽位"（非搬运节点只申请设备锁 ⇒ {DEVICE} ✓）；
- 允许"同槽位多次"（`RailZoneGuard` 批量申请多个分区 ⇒ 仍是 {DEVICE,POSITION,RAIL} ✓，不需要配对 pop ⇒ **天然规避 v1 的栈式误报**）；
- 只禁止"**跳回前面的槽位**"（设备 → 轨道 → 位置 这类），这正是会成环的模式；
- 与"重入"天然兼容（重入不新增槽位）。

⇒ **建议：采纳 A（三值）+ A1（断言只在语义拥有者发起）+ 前缀判定（而非 rank 单调），三者一起上。**

## 二、已列问题的表述修正（两条都属实，但表述可以更准）

### N-H · P0-4a：`command_id` 的问题不是"两处矛盾"，是**粒度错配**

**事实**：③ §1.3 的 DDL 里 `command_id VARCHAR(160) NOT NULL` + `uk_logical_operation_cmd UNIQUE (tenant_id, command_id)`；§1.7 说"不去重设备每次传输实例生成新 id"。

**精确表述**：矛盾确实存在，但根因不是"两处写法不一致"，而是——

> **`command_id` 的天然粒度是"一次传输"，不是"一个逻辑动作"。**
> `logical_operation` 一行只能装一个 `command_id`（`NOT NULL` + 单列）⇒ 它**结构上无法**承载"每次传输一个新 id"。

⇒ 三条出路互斥，必须选一条：

| 出路 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | **`command_id` 从 `logical_operation` 移走** —— 它属于传输明细层，`command_ledger` 已有 `command_id` 列（一行一次传输）；`logical_operation` 不再存它（或只存"当前生效的"引用） | `logical_operation` 与 `command_ledger` 的关联改为按 `operation_id` 外键 ✓（总纲 §3.3 已写"`CommandLedger.begin` 记录 `(operation_id, attempt_no)`"⇒ 方向已经对了，只需把 DDL 对齐） |
| B | 不去重设备**每传输一次就新建一行 logical_operation**（`generation` 递增） | `generation` 的语义被污染（现在定义为"人工重跑"）⇒ 又一处"两套语义" |
| C | 不去重设备也用稳定 id | **回到卡死的原问题**（设备按"已见过"忽略 ⇒ 流程卡死）⇒ 不可 |

⇒ 建议 **A**，并把 §1.7 与 §1.3 的 DDL 对齐。

### N-I · P0-4b：不是"key 会撞"，是"**恢复时的循环圈次身份在现有代码里就不唯一**"

**代码证据**：

| 事实 | 位置 |
|---|---|
| `visit` 是**本次 `run()` 调用内的内存计数** | `GraphRunner.java:738` `visits.merge(key, 1, Integer::sum)` |
| 圈次只给**真正在环上**的节点 | `GraphRunner.java:881` `cyclicNodeKeys.contains(key) ? visit : 0` |
| 透传到 StepContext（**内存**） | `GraphRunner.java:882` `executor.execute(c.withLoopIndex(round))` |
| resume 时 `GraphRunner` 重新 `run()` ⇒ **visit 从 1 重算** | `WorkflowService.java:1274` `.withMaxVisits(...)`（每次执行新建） |
| 但 `run_node.loop_index` 是**持久化**的 | `WorkflowService.java:2833` `recordNodeRound` → `RunMapper.insertNodeRound` |
| **`insertNodeRound` 是 `INSERT ... SELECT`，无冲突处理** | `RunMapper.xml:695-706`；唯一键 `uk_run_node (run_id, node_key, attempt, loop_index)` |

⇒ 恢复后重跑同一圈时：

- `attempt` 不变 ⇒ **撞唯一键，插入失败**（`n == 0`），代码只打一条 log："记循环圈次失败（找不到汇总行）"（`WorkflowService:2846-2848`）⇒ **圈次历史静默丢失**；
- `attempt` 变了 ⇒ 写出**同一逻辑圈的两行**。

⇒ 所以准确表述是：

> **P0-4b 的根不是 key 拼接，而是"恢复时如何判定当前是第几圈"这件事在现有代码里就没有答案**（内存 visit 重算 vs 持久化 loop_index 行，二者可能不一致）。
> `operation_key` 的 `|l{loop}` 维度因此**当前不可得**。

⇒ 修法建议：**`operation_key` 的 loop 维度取持久化的 `run_node.loop_index`**（而不是 `ctx.loopIndex()`），并在设计里补一条前置能力："**恢复进入循环体时，必须先从 `run_node` 恢复圈次游标**"。这本身是独立于本方案的一个小改造（把内存 visit 初始化为"已持久化的最大圈次"），但**不补这条，`|l{loop}` 就是空的**。

⇒ 另外 §1.1.1 的"**首次生成后持久化，重放时读取，不重新拼接**"这条约束是**正确且必要**的 —— 它让"第 2 圈在同一次执行内用内存 visit=2 生成新 key"这条路可行。但它**不覆盖 resume 跨执行**的情形 ⇒ 两条要分开写。

### N-A · `insertExperimentFlowRun` 是一条**绕过调度器的旁路**，总纲"必须过准入"对它不成立 ⭐

**位置**：总纲 §3.1 新增的"两条不经 `createRun` 的 run 插入路径"表

总纲写：`RunMapper.insertExperimentFlowRun`（xml:1012）"生产路径 ⇒ **必须过准入**"。

**核对（`RunMapper.xml:1012-1019`）**：

⇒ **三个致命细节**：

⇒ **这条路径与设计基线 §4.1"让批次提交进入现有 `ExperimentScheduler`、不新建调度器"的目标直接冲突** —— 它是一个已经在跑的、**不经过调度器**的实验执行器。⇒ 并行化改造若不覆盖它，它就是**第二个不受资源级互斥保护的多实验并行源**。

⇒ 建议把这条从"准入清单"移到"**调度覆盖清单**"，并回答三问：
- 它是否应该走 `ExperimentScheduler`？（它现在自己逐节点执行，是另一套执行器）

- 它的 `workflow_id=NULL` 意味着什么业务含义？（"实验流程"不是"流程定义"？）

### N-B · `physical_state` 新列的默认值陷阱：**上线即停线**（直接回答邀请第 8 问）⭐

**位置**：总纲 §3.2.1、设计基线 §4.7.2 / §4.7.3 / §4.7.5

总纲 §3.2.1 写："`device_state` 增加 `physical_state` 列（`in_motion / idle / unknown`）"、"未知时该设备不进可派发池"。

⇒ **`physical_state` 是新增列 ⇒ 所有存量设备的初值都是 `unknown`** ⇒ 若"未知即阻断派发"，**上线当天全场设备都不可派发 ⇒ 停线**。

⇒ 而且邀请的"已知问题清单"已经承认："物理态 数据来源目前只有扫码，没有第二证据 ⇒ §4.7.2 的 P0 级（交叉验证）现在实际拿不到" ⇒ **当前所有设备实际上都只能到 P1**。

⇒ **修法：必须把"未知"拆成两种**：

| 取值 | 含义 | 处置 |
|---|---|---|
| `NOT_COLLECTED`（**从未采集**） | 该设备/协议不上报物理态 | **降级到 P1**（按设备确认处理）+ 告警 + 列入"不可并行清单" |
| `UNKNOWN`（**采集到不确定**） | 设备明确报告"我不知道/卡住" | **阻断派发** + 转 `paused_unknown` |

⇒ 这条必须写进 §4.7.2 的分级表：**"未采集"不是"不确定"**。两者的处置完全相反。

⇒ **更根本的一问（这是第 8 问的真答案）**：

> **谁来写 `physical_state`？** 设备上报？侧车转换？中控根据命令回包推断？
> 若设备只回 `done`、不报物理态（邀请第 8 问的前提），那么这一列**永远是 `NOT_COLLECTED`** ⇒ §4.7 的三层模型在当前协议下**无法落地**。

⇒ ⇒ 所以 §4.7.5 建议的"把'物理态未知必须阻断派发'列入**并行度 2 的放行条件**" —— **按当前数据源，这条永远达不到 ⇒ 并行度 2 永远开不了**。⇒ 建议改写为：
- 放行条件改为"**物理态数据源已确定（谁写、怎么分级、未采集怎么降级）**"，而不是"物理态未知必须阻断"；
- §4.7 作为**目标态设计**保留，但明确标注"**依赖设备侧协议升级，本轮不作为并行度 2 的放行条件**"。

### N-C · 恢复核对第③项"机械臂分区是否物理空出"**没有数据源** ⇒ 每次恢复都变成人工流程

**位置**：设计基线 §4.7.4 ③、总纲 §3.2.1"恢复三项核对"

§4.7.4 要求三项全过才允许恢复，第③项是"机械臂在哪、分区是否物理空出 —— **没有**（现状）⇒ 需要'物理空出'确认"；总纲 §3.2.1 说"缺一项即停在 `paused_unknown`"。

⇒ 但 §4.7.6 明确"**不用视觉 / 称重做在线判定**（现场没有该设备）" ⇒ **第③项没有任何自动来源** ⇒ ⇒ **每一次恢复都要求人工点检机械臂**。

⇒ 这与"无人值守"是直接冲突，而且**成本落在每一次恢复**上（不是偶发）。

⇒ 建议（与 ③ 的 `result_trust` 体系一致）：**人工确认也是物理态证据**，只是不可自动采集：

| 手段 | 层级 | 有效期 | 说明 |
|---|---|---|---|
| 设备自报 | P1 | 短（分钟级） | 当前只有这一种 |
| **人工点检一次 + 记入分区台账** | **P2** | **TTL 内免复核** | 点检结论落库（分区 + 空出确认 + 操作人 + 时间），TTL 内恢复直接采信 |

⇒ 即：第③项从"每次都查"降为"**人工确认一次、台账 TTL 内免复核**"，否则这条路走不下去。

### N-D · §4.7 缺"物理态的有效期"

**位置**：设计基线 §4.7.1 / §4.7.4

§4.7.1 的表格把物理态标为"**只能对账，没有事务**" —— 这个判断是对的，但推论没写出来：**物理态是"某一时刻的观测"，会漂移**（板被人工拿走、耗材被换、手臂被人工移动）。

⇒ 多并行下：A 在 T 时刻确认了物理态 → 5 分钟后 B 进来 → 物理态可能已变，而 A 的确认还"有效"。

⇒ 建议补两条：
1. `physical_state` 确认带 `confirmed_at`；**超过 TTL 视为过期**；
2. 恢复核对时，"确认距今多久"要进决策（不是只问"确不确认过"）。

⇒ 这与 N-C 的"人工点检 TTL"是同一套机制，建议合并设计。

### N-E · §4.7.5 的影响面算法不准，会误导容量规划

**位置**：设计基线 §4.7.5

现表：

| 并行度 | 一个物理态未知的影响 |
|---|---|
| 4 | **最多 3 个 run 被一个未知设备拖住** |

⇒ **算法不对**。一个未知设备只拖住**想用这台设备**的 run；若 4 个 run 用 4 台不同设备、其中 1 台未知 ⇒ **只有 1 个受影响**。

⇒ 正确表述：**影响面 = min(想用该资源的 run 数, 并行度上限)**，与"并行度"**不是线性关系**。

⇒ 现在的写法会让人以为"并行度 4 ⇒ 一次未知损失 75% 产能"，从而**过度保守地压低并行度上限**，或者反过来在真实场景里低估影响。建议改成公式。

### N-F · §4.7.1 把 `device_state.current_run_id` 归到"**设备态**"是**归层错误**

**位置**：设计基线 §4.7.1 表格（设备态行）

现表把 `device_state.current_run_id` 列在"**设备态**（设备软件拥有 / 最终一致）"。

⇒ **核对**：`current_run_id` 是**中控自己写的** —— `WorkflowService.onStepStart` → `markDeviceBusy` → `DeviceStateMapper.markRunning` ⇒ 它是**程序态**（同库同事务、强一致），不是设备态。

⇒ **影响不是学术性的**：

- §4.7.3 的硬规则"设备未知 → 不进入可派发资源池"，如果读者以为"设备占用"属于设备态，就会把**程序态的资源占用**与**物理态的未知**混在一起；
- 而实际上：**"这台设备能不能分配给 B"完全由程序态保证**（`current_run_id` 强一致）；物理态未知影响的是"**分配给 B 之后 B 能不能真的开跑**"，不影响分配正确性；
- ⇒ 两件事必须分开：**资源分配靠程序态；开跑/恢复靠物理态**。

⇒ 建议 §4.7.1 的表格把 `current_run_id` 移到"程序态"，设备态只留"在线、心跳、回包 `error_code`、设备自报的物理状态"。总纲 §3.2.1 那句"不与 `current_run_id` 混用"也就有了明确所指。

### N-G · 提取线流程节点**没有带 `interactionId`** ⇒ L5 等待交互互锁在现场一直是跳过的

**位置**：设计基线 §4.7（物理态的证据来源）、③ §2.5（精匹配）、⑥ §1.2

**核对**：`WaitingInteractionGuard:33-40` —— **`interactionId` 为空 ⇒ 整个 L5 守卫 `SKIP`（放行）**，并记一条 `InterlockDecision.SKIP`。

而 `DriverStepExecutor:568-570` 从**节点参数**取 `deviceSessionId` / `workflowStepId` / `interactionId` —— 这些是**搬运节点**的参数。

⇒ **我在 `scripts/setup-extraction-flow.py` 里 grep 不到 `interactionId` / `deviceSessionId` / `workflowStepId`**（该脚本生成的就是提取线的 8 个阶段 + 8 个 `__awaitEvent`）⇒ **该流程的搬运节点没带 `interactionId`** ⇒ **L5"机械臂操作交换位前必须存在有效等待交互"这条保护在现场一直是关的**。

⇒ 两个后果，都与本轮主题直接相关：

1. **物理态侧**：§4.7.4 的"板在哪""机械臂分区是否空出"缺一个现成证据源 —— 而"有效等待交互"台账（`WaitingInteractionMapper.selectEffective`）本来就是一个"物理态证据"，只是现场没启用；
2. **事件归属侧**：③ §2.5 的精匹配需要 waiter 侧有 `expect_interaction`，而 `expect_interaction` 的**期望值来源**在现有协议里也缺 —— `__awaitEvent` 的参数只有 `device / eventType / timeout / interval / into / deviceInto`（`GraphRunner.describeBuiltin:319-327`），**没有 process_id / interaction**。⇒ **waiter 的 `expect_*` 目前全是 NULL ⇒ 全部退化成弱匹配 ⇒ 而弱匹配又被建议默认禁用 ⇒ 事件归属在现有协议下无法实现**。

⇒ 建议把"**给 `__awaitEvent` 增加 `expectProcessId` / `expectInteraction` 参数（或从节点参数继承 `interactionId`）**"作为事件归属落地的前置条件，与"节点携带 `interactionId`"一起纳入协议准入条件（设计基线 §5 的第五条之外再加一条）。
