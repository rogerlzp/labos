## 三、阻断级

### B1. 测试条数不实：全文 8 处写「373」，实测 368

**复现命令（文档原文，未改一字）**：

```bash
./scripts/test-all.sh --pure-only
# 文档期望：通过 373 / 失败 0
# 实测输出：通过 368 / 失败 0（跳过 2 个连库测试）
```

**差值归因（精确到唯一一处）**：逐类比对四份文档的用例清单后，**只有一处错**——
[04 §三](file:///path/to/labos/docs/评审包-20261103/04-测试文档.md#L59) 把
`driver.DeviceErrorChainSelfTest` 标为 **19**，实跑 **14**。其余 10 类全部吻合
（196 / 41 / 30 / 23 / 17 / 14 / 13 / 13 / 6，+ `SidecarChainTest` 7 计 1）：

```
196+41+30+23+17+14+13+13+6+1 = 354  ... 按文档口径（含 19）得 373
196+41+30+23+17+14+13+13+6+1 = 368  ... 按实测口径（含 14）得 368
```

即 **373 − 368 = 5 = 19 − 14**，一处笔误穿透到全文。

**影响（不止数字不准）**：文档在 [04 §二](file:///path/to/labos/docs/评审包-20261103/04-测试文档.md#L30)、

第三方按文档执行会看到 368，**第一反应就是"少了 5 条，疑似回归"**。
这与本项目硬约束「内部文档统计数字不一致 = 评审阻断」直接冲突。

**出现位置**：[00:36](file:///path/to/labos/docs/评审包-20261103/00-索引与评审须知.md#L36)、[00:146](file:///path/to/labos/docs/评审包-20261103/00-索引与评审须知.md#L146)、[02:96](file:///path/to/labos/docs/评审包-20261103/02-技术文档.md#L96)、[04:6](file:///path/to/labos/docs/评审包-20261103/04-测试文档.md#L6)、[04:30](file:///path/to/labos/docs/评审包-20261103/04-测试文档.md#L30)、[04:51](file:///path/to/labos/docs/评审包-20261103/04-测试文档.md#L51)、[04:69](file:///path/to/labos/docs/评审包-20261103/04-测试文档.md#L69)、[04:151](file:///path/to/labos/docs/评审包-20261103/04-测试文档.md#L151)。

## 四、高级别（命中用户点名重点 #2、#4）

### H1. D4 的「删行」范围不完整 —— 续跑后的步骤/命令审计记录会**静默丢失**

**事实链（读码 + schema）**：

1. [resumeAsync 的删除](file:///path/to/labos/labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java#L547-L554) 条件为
   `LEVEL = 0 AND status <> 'completed'` —— **只删业务节点**。
2. 但按 [03 D8](file:///path/to/labos/docs/评审包-20261103/03-设计文档.md#L158-L172)，`run_command` 挂在 **`level=1` 步骤节点**上；
   而 [96_schema_fix.sql:103](file:///path/to/labos/pg_rebuild/schema/96_schema_fix.sql#L103) 的
   `run_node.parent_node_id` 只是裸 `bigint`，**没有外键**。
3. 于是：删 `level=0` 行 **级联不到** `level=1` 行，也级联不到任何 `run_command`
   （它们的 FK 指向 `level=1` 的 id，见 [20_kernel.sql:320](file:///path/to/labos/pg_rebuild/schema/20_kernel.sql#L320)）。
   → **D4 正文「（`run_command` 随外键级联）」与实现不符。**
4. 续跑重跑时，[PersistingStepSink 的 `seq`](file:///path/to/labos/labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java#L1651-L1652)
   是**新建的 `AtomicInteger`**，步骤 key 从 `S1` 重新开始
   （[writeStep:1841](file:///path/to/labos/labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java#L1841) `"S" + seq.incrementAndGet()`），
   与**没被删掉的旧 `S1/S2`** 撞 `uk_run_node(run_id,node_key,attempt)`（[20_kernel.sql:308](file:///path/to/labos/pg_rebuild/schema/20_kernel.sql#L308)）。
   `attempt` 首次为 0（[NodeProgress](file:///path/to/labos/labos-kernel/src/main/java/com/labos/kernel/engine/NodeProgress.java) 初值 0），新旧同值 → 必撞。
5. 该 `SQLException` 在 [onStepDone 被 catch 成一条 `[WARN] 步骤落库失败`](file:///path/to/labos/labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java#L1789)，
   **不中断执行** → 续跑这一段"第几步、发了什么、回包什么"在库里就是缺的。

**为什么现有验收测不出来**：[verify-device-chain.sh 的续跑断言](file:///path/to/labos/scripts/verify-device-chain.sh#L280-L286)
只查两条 —— `level=0` 三个 `completed`、模拟器日志里 `收到 Seal` 恰为 2 条。
**它看的是"命令发出去了没"和"业务节点完成了没"，从不看 `run_command`/`level=1` 有没有落库**，
所以这个洞被绿灯盖住。这正踩在「可追溯」这条总原则（[03 §0](file:///path/to/labos/docs/评审包-20261103/03-设计文档.md#L10-L20)）上。

**证据边界**：本条系 **schema + 代码静态推得**，**未连库实跑**。
**最省的复核方式**：跑一次三步续跑后执行

```sql
SELECT node_key, level, status FROM run_node WHERE run_id = :RID ORDER BY id;
SELECT count(*) FROM run_command WHERE run_node_id IN (SELECT id FROM run_node WHERE run_id = :RID);
```

若续跑后 `level=1` 行数未增加、或 `run_command` 数 ≠ 实际发出命令数，即坐实。

### H2. D2 的「只在整单成功结束后才标 `bypassed`」与实现不符

**事实链**：

1. [markBypassedNodes 的排除条件](file:///path/to/labos/labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java#L1511-L1517) 为
   `MANUAL>0 || ABORTED>0 || aborted()`，**唯独没有排除 `SKIPPED`**。
2. 而 `SKIPPED` 会让 [settleRun](file:///path/to/labos/labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java#L2178-L2196)
   把整单落成 `paused / pause_kind='waiting_human'`（这本身是对的）。
3. 两者叠加：在"因跳过而停下来等人"的单子里，**下游还没执行的节点会被从 `running` 直接改成 `bypassed`**
   （[:1522](file:///path/to/labos/labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java#L1522) `SET status='bypassed'`）。
4. 而 [01 §4.2](file:///path/to/labos/docs/评审包-20261103/01-功能文档.md#L93-L101) 自己定义：
   淡灰点线（`bypassed`）= 分支没选中，灰虚线（`pending`）= 还没轮到。
   → 页面把"还没轮到、正等人"画成了"这条分支不用走"，**展示与真相不一致**（正是重点 #7 的反例）。

**触发条件**：库里存在 `strategy='skip'` 的策略。经查 seed 数据**没有** skip 策略，
故目前为**潜伏缺陷**，靠运营在 `/error-codes` 配一条才会现形。
D2 正文说"失败/暂停的单子里 `running` 表示待续跑，标了会让续跑逻辑误判"——**代码没照这句话实现**。

**顺带一个设计层疑问（非 bug）**：一个**名字叫 `skip` 的策略永远 skip 不掉**——
`SKIPPED` 一定 halt（[GraphRunner:308-315](file:///path/to/labos/labos-kernel/src/main/java/com/labos/kernel/workflow/GraphRunner.java#L308-L315) + `settleRun`）。
UI 里给运营这个选项，语义是否该改名或加提示，需被评审方确认。

**关于评审的设计提问（"`skip` 策略永远 skip 不掉"）——确认：这是有意为之，不改运行时。**

**已改 UI 文案**消歧：`skip · 跳过（跳过即停，等人工确认）`（webapp/src/pages/ErrorCodes.tsx:28）。
