### 意见 2（P1 严重）：`startAsync` 的失败兜底只捕获 `IllegalStateException`，会留下僵尸 Run

- **结论**：需要补充证据（要求纳入修复范围与验收）。
- **位置**：§3.4"拒绝路径不得留下新 running 流程 Run"；源码 `WorkflowService.startAsync`、`submitRunWorker`；验收 T19 / T23。
- **依据**：【现状事实，已在 `cf772fc` 核实】`startAsync` 的写法是：
  ```java
  try { submitRunWorker(runId, "run-exec-" + runId, () -> {...}); }
  catch (IllegalStateException busy) { markRunFailed(runId, ...); throw busy; }
  ```
  而 `submitRunWorker` 内部在 `RUN_POOL.submit(...)` 失败时 `catch (RuntimeException e) { releaseRunWorkerSlot(...); throw e; }` —— 抛出的是 `RuntimeException`（如 `RejectedExecutionException`），**不是** `IllegalStateException`。该异常会穿透 `startAsync`，`markRunFailed` 不执行，Run 停在 `running` 且无 worker。
- **风险**：并发 / 事实边界——僵尸 Run 会永久占用该 `(tenant, workflow)` 的 active 名额，在 G0-01 修复后直接导致该流程**再也无法启动**（因为新门禁会正确地判 `DENY_ACTIVE`）。这与"修复后更安全"的预期相反。
- **建议**：把 `submitRunWorker` 的失败收口为统一的启动失败语义（catch `RuntimeException`），或把"准入 + createRun + 初始状态 + worker 占位"的顺序调整为 worker 占位先行；并在 T19 增加"worker 池拒绝 / 线程创建失败"子场景。
- **验收**：注入 `RUN_POOL` 拒绝后，Run 不残留 `running`，且后续同流程请求可正常准入。**必须保持 UNKNOWN 的情况**：未做该注入测试前，不得宣称"拒绝路径无副作用"已覆盖全部失败模式。

### 意见 3（P2 一般）：异步入口缺稳定 `errorCode`，与 §3.2 的错误契约不一致

- **结论**：需要补充证据。
- **位置**：§3.2"同步与异步拒绝均返回非 2xx 和独立 `errorCode`"；验收 T08 / T09 / T18。
- **依据**：【现状事实】`WorkflowController` 仅有 `@ExceptionHandler(IllegalArgumentException.class) → 400`。`startAsync` 抛出的 `IllegalStateException`（"已有后台执行线程"）与 `SQLException` 无对应 handler，会落到框架默认 500，响应体无稳定 `errorCode`。而同步路径是通过判断 `json.startsWith("{\"error\"")` 显式映射 400。
- **风险**：兼容性——AI/前端按 `errorCode` 分支处理时，异步路径的失败无法被识别为"可重试/不可重试"。
- **建议**：在 §3.2 增加一行"异步入口的异常映射表"，并把 T18 扩展为覆盖 `IllegalStateException`（并发 worker）与 `SQLException`。
- **验收**：四种拒绝原因（active / invalid / status-unknown / DB unavailable）在同步与异步两条路径上返回可区分的 `errorCode`。**必须保持 UNKNOWN 的情况**：未测异步路径前，不得声称"两条路径错误语义一致"。
