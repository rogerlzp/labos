### 3.3 问题清单（按严重度）

**P1-A · P0 批次过大，含执行链改动，违背"先骨架后引擎"（§9.1）**

P0 七项里，P0-4（BindingResolver 进执行链）和 P0-5（隐式 Transport + TransportPlanner）直接改展开/调度管线。而近期执行链刚修完一串竞态（saveGraph 死锁、串行设备命令、命令账本），测试基线 882 项刚稳住。把 TransportPlanner 放进"不做完后面都是空中楼阁"的 P0，等于第一批就动最脆弱的层，且与文档自己的"每期可独立验收"原则张力明显。

**建议**：P0 收缩为数据层 + 权限层（P0-1/2/3/6/7 + BindingResolver 的**只读解析**版本），P0-5 隐式 Transport 降入 P1；P0-4 先做到"绑定解析结果写 run_event 可观测、不改变实际选设备行为"，一个批次跑稳后再切换。

**P1-B · 绑定固化（pinned）语义缺失——deepseek 评审我线设计稿的 P1-2 同样适用于本文**

deepseek 在生产库实测过：`workflow_node.resource_id` 绑定的设备会被 GraphRunner **候选池重解析**（"绑了≠用"）。《详细设计》的展开管线里有 `BindingResolver.resolve(...)`（§4.1），但全文搜索**没有任何"命中绑定即不参与候选池排序"的条款**（"候选"一词只出现在 `/api/devices/pool` 端点讨论中）。

**建议**：在 §4.1 增加显式规则：`节点存在 node_binding 行 ⇒ 解析结果 pinned，跳过候选池；无绑定行 ⇒ 回退 resource_id；两者皆空 ⇒ 候选池`。并在 P0-4 验收里加一条反例：绑定点位 A 的节点在候选池存在空闲点位 B 时，实际执行必须落在 A。

**P1-C · `node_binding` 与 BPMN XML 的真源关系需要拍板（§3.3.4 只说了一半）**

`workflow_node` 表本身是"从 XML 落到表"的投影（`20_kernel.sql:222` 注释），而 `node_binding` 是 XML 之外的旁挂表。后果：**流程导出/导入/复制会静默丢失绑定**。§3.3.4 标题写了"双轨期的唯一真源规则"但正文要回答的具体问题——绑定是否写进 XML 属性、导出契约是否含绑定——需要明确。

**建议**两个方案选一：① 绑定以 XML 扩展属性落图（`labos:pointRef` 之类），`node_binding` 降为投影缓存——图自包含，导出无损；② 维持旁挂表，但必须在 §6 API 里补导出/导入契约（导入时按 node_key 重挂，node_key 改名即断链要预警）。我倾向 ①，与"workflow_node 是投影"的既有架构一致；若担心 BPMN 校验器对扩展属性的容忍度，选 ② 也可接受，但契约不能缺。

**P2-D · `scope_kind='experiment'` 实际指向 `experiment_template.id`，命名误导（§3.2.2）**

解析链 `experiment > workflow > global` 里的 "experiment 级"绑定实际挂在模板上。建议改名 `scope_kind='template'`，否则后续读代码的人会以为能按实验实例覆盖模板绑定（那会是另一个语义）。

**P2-E · P0-7「示教坐标 100% 补齐」与"不编造坐标"红线的衔接要写清**

`robot_point` 现状 13 行全 `fill_status='pending'`（刻意不编造坐标）。P0-7 要求"robot_reachable=true 的点位 100% 有 robot_point"，完成路径只能靠调试台 capture。建议在 P0-7 验收里写明**完成手段 = teach-capture 通道**，并禁止用占位坐标凑数（呼应本线设计稿的 `coord_source` 列，可吸收）。
