## 1. 总体判断

「主循环单线程，遇到并行组后提交分支任务、等待全部完成，再继续主循环」方向成立，但方案把并发边界只描述成"分支执行"，实际必须同时定义六件事：

1. 图节点的执行所有权
2. 分支局部状态与流程级共享状态
3. join 的到达、合并和失败语义
4. Run 级状态机、进度、台账的并发写入
5. 暂停、停止、恢复与设备命令生命周期
6. 线程池容量和嵌套调度

**特别是**：`ConcurrentHashMap` 能解决部分数据结构并发访问问题，但**不能自动解决图执行语义、复合操作原子性和数据库事务边界**。

## 2. §7 八个问题逐项回答

### D1：`done`/`visits` 隔离后并集 + max —— **不够完整**

评审把情况分成三种：

| 情况 | 说明 |
|---|---|
| **A. 两分支完全独立，在显式 JOIN 汇合** | 并集 + max 在简单场景可工作，但只是特定图形约束下的结果，**不是一般规律** |
| **B. 两分支合法汇合到同一个普通节点** | 这种图在当前图模型里**可以表达**。`WorkflowGraphParser.Graph` 允许多条入边；`ConditionalBranchTracker` 注释也考虑了多分支指向共享节点。现有 `pending` 按入边计数决定何时进 ready，汇合节点可以只执行一次 |
| **C. 两分支包含循环** | `visits` 取 max 不保证正确：A 对 X 跑 2 圈、B 跑 1 圈，取 max=2 **不能表达两条路径各自的执行历史** |

**结论**：不要采用"分支隔离 + 并集 + max"。

**建议**：保留一个 **run 级图调度器**，由它独占维护 `done`/`visits`/`pending`/`ConditionalBranchTracker`；**分支 worker 只执行节点，不拥有图的推进权**。这样 D1 就不再是需要合并的状态问题。

**附带指出**：不能简单要求所有分支子图完全不相交——会错误拒绝"两分支汇合到共享普通节点"这种合法图。

### D2：禁止同组内两分支写同一变量 key —— **方向正确，但要补充读写冲突**

不只查 WAW，还要查 RAW / WAR：

| 冲突类型 | 示例 | V1 处理 |
|---|---|---|
| WAW | 两分支都写 `count` | 禁止 |
| **RAW** | A 写 `count`，B 读 `count` | 禁止或要求明确快照语义 |
| **WAR** | A 读 `count`，B 写 `count` | 同上 |
| 独立变量 | A 写 a，B 写 b | 允许 |

**业务真需要两分支累加怎么办**：用**分支独立输出 + JOIN 后显式聚合**，不要原子自增：

```
Branch A: result_A = 3
Branch B: result_B = 5
JOIN:     total = result_A + result_B
```

好处：无写冲突、可独立审计、汇总只执行一次、重试不重复累加、测试可确定性复现。

原子自增的额外问题：读到的值不确定、重试是否再累加、恢复如何避免重复提交、并发写与审计如何对应。

### D3/D4：停止/暂停等待上限 —— **概念要纠正**

评审指出三个时间概念必须分开：

| 概念 | 含义 | 是否属于"分支超时" |
|---|---|---|
| 节点执行超时 | 设备方法执行多久 | 是 |
| 分支执行超时 | 整个分支最多多久 | 是 |
| **停止/暂停协调等待** | 请求发出后多久还没全部到安全边界 | **否** |

**D3 停止**：不接受"等 30 分钟后强制取消其他分支"。正确状态：

```
RUNNING → STOP_REQUESTED → DRAINING
                              ├─ 全部完成 → FAILED / MANUAL
                              └─ 超协调阈值 → QUARANTINED
```

**关键**：超限进隔离，**不等于设备命令被取消，更不等于设备已空闲**。不能因为超过等待上限，就把正在执行的物理命令强制标为 UNKNOWN 后释放租约。

**D4 暂停**：类似协调过程，`PAUSE_REQUESTED → PAUSE_DRAINING → PAUSED`；未全部到达就仍是 `PAUSE_REQUESTED`。

特别要处理 `__awaitEvent`：收到暂停请求后等待逻辑必须能观察暂停、不能丢已观察到的事件、恢复时必须用可恢复的事件游标、不能把等待节点错误标成已完成。

**参数建议**：

| 时间 | 配置 |
|---|---|
| 节点执行 / 设备资源等待 | 按设备/方法配 |
| 分支整体执行 | 不设统一超时 |
| **停止等待 / 暂停等待** | **不设强制终止时间，只设运维告警阈值** |

超阈值只升级为异常协调状态、告警或隔离，**不自动结束物理执行**。

### D5：`nodeStateRecorder` 和 `ExecutionListener` 线程安全 —— **发现明确问题**

评审实际核了源码（`5dd22dc`）：

#### 5.1 `nodeStateRecorder` —— 本身安全

```java
.withNodeStateRecorder((key, st) -> recordNodeState(runId, key, st))
// → rm().updateNodeStateLive(tenantId, runId, nodeKey, status)
```

没有共享可变集合，也没把 Connection 存字段。不同 worker 更新不同节点，DB 层可处理并发 SQL。

**但这不等于整个 `WorkflowService` 回调链安全。**

#### 5.2 `ExecutionListener` —— 明确问题

```java
List<ExecutionEvent> events = new ArrayList<>();
RunStateMachine sm = new RunStateMachine(decider, tee(events, store, monitor), ...);

// tee:
return e -> {
    sink.add(e);                       // ← ArrayList.add 并发
    for (ExecutionListener l : next) l.onEvent(e);
};
```

#### 5.3 `JdbcEventStore` —— 明确不安全

```java
private final List<Map<String, Object>> pending = new ArrayList<>();
private int written = 0;
private int failed = 0;

onEvent() { pending.add(row); }        // ← 没有同步
flush()   { synchronized ... }         // ← 只有 flush 加锁，不够
```

可能：一个线程 `pending.add()`，另一个线程达到 batchSize 调 `flush()`，两个线程同时操作同一 ArrayList，清空与新增竞争。

#### 5.4 `StepCollector` —— 也不安全

```java
final List<StepRec> done = new ArrayList<>();
private final Map<String, Long> resourceByStep = new HashMap<>();
```

即使 `PersistingStepSink` 自己的 `resourceByStep` 已是 `ConcurrentHashMap`，整个步骤记录链仍不安全。

#### 5.5 `RunMonitor` —— 有并发计数问题

```java
l.done++;      // volatile 字段自增不原子
l.manual++;
```

且 `nodeKey`/`nodeStatus` 表示"当前节点"，多分支并行时**无法代表唯一当前节点**，监控语义要改成并行节点集合。

#### 5.6 `RunStateMachine` —— 比 seq 更隐蔽的竞态

```java
stateMachine.withLoopIndexSupplier(() -> round);   // 实例字段
NodeStatus st = stateMachine.executeNode(...);
// 完成处理器里再读 loopIndexSupplier.getAsInt()
```

并行后：

```
线程 A：设 loopIndexSupplier = round 2
线程 B：设 loopIndexSupplier = round 5
线程 A：完成处理器读到 round 5      ← 物料记录到错误圈次
```

**这不能通过把 seq 改 AtomicLong 解决。** 应把 loopIndex 改成 `executeNode()` 的调用参数，或放进每次执行专属的不可变上下文。

#### 5.7 DB 连接

`Tx` 用 `TransactionTemplate` + `DataSourceUtils`，连接绑定**当前线程**。所以：

- 主线程事务不会自动传播到 worker
- 不同 worker 不共享主线程事务连接
- worker 独立 `Tx.inTransaction` 会获得自己的事务上下文
- worker 直接调 mapper 不代表处于共同事务

**方案里"多线程各自拿不同连接，写库本身没问题"只对连接绑定这一层成立，不能推导整个写库链路安全。**

#### D5 结论：**目前不具备直接放行并发的条件**

至少 11 处要处理：

| 对象 | 问题 | 方向 |
|---|---|---|
| `events` | ArrayList 并发写 | 串行事件队列 |
| `JdbcEventStore.pending` | 同上 | 单消费者写入 |
| `StepCollector.done` | 同上 | 并发安全收集 |
| `StepCollector.resourceByStep` | HashMap 并发写 | ConcurrentHashMap |
| `RunMonitor.done/manual` | volatile 自增不原子 | AtomicInteger / LongAdder |
| `RunMonitor.nodeKey` | 无法表达多个并发节点 | 并行运行快照 |
| `RunProgress.nodes` | LinkedHashMap 并发写 | 并发存储 + 安全快照 |
| `RunProgress.aborted/materialHold` | 裸 boolean | AtomicBoolean |
| `RunStateMachine.seq` | long 自增竞争 | AtomicLong **或串行事件分发** |
| **`loopIndexSupplier`** | **实例级可变上下文** | **改成调用参数** |
| `ConditionalBranchTracker` | 普通容器 | 由单线程协调器独占 |

**补充**：`RunProgress.nodes` 换成 `ConcurrentHashMap` 也不够——`NodeProgress` 自身可变字段、`all()` 返回的集合视图，都需要定义安全读取方式。

### R1：seq 改 AtomicLong 会不会跳号 —— **可解决，但不能只改 AtomicLong**

三个概念要分开：

1. 序号唯一
2. 序号分配连续
3. **事件按序号顺序送达、落库**

`AtomicLong.incrementAndGet()` 解决前两个，**不保证第三个**：

```
线程 A：取 seq=1，被挂起
线程 B：取 seq=2，先调 listener
线程 A：恢复，后调 listener
⇒ listener 收到 2, 1
```

评审核了事件链：`JdbcEventStore` 把 seq 放进 payload；`RunMonitor` 不依赖 seq；**当前没发现下游要求 seq 连续的证据**。

建议定义为：

> seq 是 run 级唯一事件序号，用于排序与诊断，**不承诺数据库持久化记录无缺口**。

若要投递顺序与 seq 一致，必须串行化：

```
worker → 创建 ExecutionEvent → run 级事件队列 → 单消费者
                                                    ├→ JdbcEventStore
                                                    ├→ RunMonitor
                                                    └→ 其他 listener
```

队列必须按序处理，关闭时等待排空。

### 方案选择：有没有更小侵入的做法 —— **有，推荐单线程协调器**

评审**不建议**"每分支自己跑一个 GraphRunner"，也不建议"把整个分支子图交给独立 worker"。

**推荐**：**单线程图协调器 + 并发节点执行器**

```
GraphCoordinator（单线程）
  ├ ready / pending / done / visits / ConditionalBranchTracker
  ├ 分派节点到 WorkerPool
  ├ 接收节点完成结果
  └ 推进下游

WorkerPool（有界）
  ├ Node A
  ├ Node B
  └ Node C
```

运行过程：

1. Coordinator 从 ready 取节点
2. 同步控制节点（网关）由 Coordinator 直接处理
3. 可执行节点提交 WorkerPool
4. Coordinator 继续分派其他 ready 节点
5. Worker 完成后返回 `NodeOutcome`
6. Coordinator 更新状态、pending、下游 ready
7. JOIN 仍由现有 pending 语义决定

| 问题 | 分支 runner + allOf | 单线程协调器 + 并发节点 |
|---|---|---|
| `done`/`visits` | 需隔离和合并 | 单线程维护，不需要合并 |
| `pending` | 分支间需协调 | 单线程维护 |
| 条件分支 tracker | 要改线程安全 | 保持单线程 |
| 共享汇合节点 | 需图切分识别 | 原有入边计数自然处理 |
| **嵌套并行** | **容易线程池自我阻塞** | 统一调度，无递归阻塞 |
| 暂停/停止 | 多个 runner 协调 | 一个 coordinator 管理 |

**特别指出 D7 的死锁**：

> 线程池 4 线程，外层 4 个分支各在自己线程里调用内层并行组，提交内层任务后 `.join()` 等待。4 个外层线程全被占用，内层任务都排在队列里没有线程执行 ⇒ **典型线程池饥饿死锁**。

**"内层不额外申请信号量"只解决部分信号量嵌套，不能解决线程被外层任务占满。**

### D6：线程池 —— **全局固定池 + 每 Run 额度**

不建议每 Run 独立池，不建议 `commonPool`。

| 层级 | 机制 | 责任 |
|---|---|---|
| JVM/应用级 | 全局有界 `ThreadPoolExecutor` | 限制总工作线程 |
| Run 级 | 最大 in-flight 节点数 | 防单 Run 占满池 |
| 设备级 | 现有 `DeviceLock` | 同设备互斥 |
| 图级 | 单线程 Coordinator | 维护就绪/完成/JOIN |

还需要：有界队列、提交失败 backpressure、Run 间公平、**Coordinator 不得占用 worker 等待 worker**、不得内层递归提交后阻塞等待、关闭时等待或进安全隔离。

**每 Run 额度应由 Coordinator 维护 in-flight 计数**，不由 worker 递归获取 Semaphore（否则外层占满、内层拿不到）。

### R3：基准流程 E2E 够不够 —— **不够**

1551 个纯逻辑单测**没有经过真实图执行器**，不能证明重构无行为变化。建议三层：

**第一层：串行兼容性测试**（不启用并发）
对比改造前后的：节点执行顺序、执行次数、分支选择、节点状态、变量最终值、循环圈次、设备选择、重试与恢复决策、事件类型与归属、`run_node`/`run_step` 台账。
建议记录标准化 trace，排除时间字段后比较。

**第二层：真实并发行为测试**（用 Fake StepExecutor，不依赖真实设备耗时）
断言：A/B 执行时间真实重叠、都能在对方完成前进入执行、JOIN 必须等齐、失败后不再派发、已派发的完成后才收尾、同设备不并发、不同设备可并发。

**第三层：复杂图与异常路径**
覆盖：基础并发、汇聚到共享普通节点（只执行一次）、嵌套 SPLIT/JOIN（不死锁）、XOR 未选分支不阻塞、CONDITIONAL 只等激活分支、分支内循环圈次正确、循环跨越 JOIN、两分支写不同变量、写相同变量编译期拒绝、一分支失败全局停止、暂停全分支到边界、设备事件等待不丢、一分支重试不影响另一分支、台账并发写无重复无缺失。

**关于基准数据**：71.9 s / 62.5 s 两次本身已差 9.4 秒，**不应当作唯一性能基准**，需多次重复测量。

## 3. 额外边界（方案未列）

| # | 边界 | 说明 |
|---|---|---|
| 1 | **Coordinator 必须是唯一图状态写入者** | `ready`/`pending`/`done`/`visits`/tracker/边激活/`defaultEdgeCount`/`conditionHitCount`/步数上限，全部由它独占；worker 不得自行 `activate()` |
| 2 | **`RunStateMachine` 不能只改 seq** | 要从"实例级共享可变上下文"改成"共享状态机 + 每次执行独立上下文"：`executeNode(node, progress, executor, NodeExecutionContext{loopIndex, branchId, invocationId})` |
| 3 | **`RunProgress` 不能只换容器** | 拆成"并发写入（每节点只由自己的 worker 更新）"+"统一快照（Coordinator 或收尾阶段生成）"；`all()` 不直接暴露变化的底层视图；定义 aborted/materialHold 优先级、Coordinator 何时认定全部完成、收尾快照在哪个屏障后读 |
| 4 | **设备锁仍要保留** | `DeviceLock` 已处理"同 run 两分支不同时进同一设备"；但 `onStepStart`/`onStepDone` 的获取与释放必须在**同一执行线程**（本地持有计数是 ThreadLocal），不能拆到不同线程 |
| 5 | **JOIN 应使用分支激活身份** | 支持嵌套、分支内循环、同一 JOIN 被不同圈次触发、条件跳过部分入边时，`joinNodeKey + pendingCount` 可能无法区分轮次 ⇒ 引入 `splitActivationId`（图调度内部概念，与 commandId 无关） |
| 6 | **并行分支不能共享"当前节点"状态** | `RunMonitor.Live` 的 `nodeKey/nodeName/nodeStatus/resourceId` 是串行单节点视角；并行后应是 `activeNodes[]`（含 branchId/status/startedAt）+ run 级汇总 |

## 4. 评审结论表

| 评审项 | 结论 |
|---|---|
| 主循环单线程、并行组提交线程池 | **方向可行** |
| 每分支独立 `done`/`visits` | **不推荐** |
| JOIN 时并集 + max | **不推荐作为通用规则** |
| 同组变量写冲突禁止 | **V1 保留，并补读写冲突检查** |
| 分支不设超时 | 保留 |
| **停止等待超限强制 UNKNOWN** | **不接受** |
| 暂停等待 | **采用安全边界协调，不强制终止** |
| `RunStateMachine` AtomicLong | **必须，但不足以解决事件顺序** |
| `nodeStateRecorder` | 不应只看回调，需检查完整并发写链 |
| `ExecutionListener` | **当前实现有明确非线程安全容器** |
| 每分支一个 GraphRunner | **不推荐** |
| 全局固定池 | 推荐 |
| 每 Run 独立线程池 | 不推荐 |
| **嵌套并行** | **必须避免 worker 递归提交后阻塞等待** |
| 1000 行执行逻辑抽取 | 需要，但应先做串行兼容性重构 |

**最重要的三个调整**：

1. 不采用"分支 runner + done/visits 隔离合并"，改成单线程 GraphCoordinator 维护图状态
2. 不把线程安全改造局限于 `RunProgress` 和 `seq`，事件与步骤记录链也有真实缺口
3. 不采用递归 `allOf().join()` 的嵌套调度，采用统一节点任务池 + 完成队列

**目标形态**：

```
GraphCoordinator  决定谁可以执行
NodeExecutor      真正执行一个节点
RunExecutionContext  提供 run 级共享状态和生命周期协调
```
