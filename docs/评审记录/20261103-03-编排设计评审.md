## 一、TL;DR

这份草稿最有价值的部分，是把一个此前被 UI 掩盖的硬事实说透了：

1. `experiment_graph` 现在**确实不参与执行**；
2. `experiment_process.run_after` **确实是“表里/API 里有，执行器没读”**；
3. “先把画布的误导性状态亮出来”这个动作是对的。

但草稿当前**还不能直接进入 M9.5 排期**，因为有 2 个阻断级问题 + 1 个高级别问题：

- **B1**：§4.4 把 “DAG 并发是安全的” 建立在 `DeviceLock` 之上，这个前提不成立；项目现有并发设计文档已经明确说明，设备锁/双锁**不足以覆盖多资源死锁**，必须上三层资源模型 + 等待图。
- **B2**：§5 / §6 的批次模型装不下“失败只重跑该批”的历史与重试语义；`experiment_batch.run_id` 一对一会覆盖历史。
- **H1**：§7 把 S1 写成“可独立上线”，但若不把 `graph` 与 `process` 的保存**收口成单事务、单入口**，S1 仍会保留双写分裂风险。

换句话说：**问题识别是对的，迁移方向大体对，但实施切面还没有完全收口。**

## 二、阻断级发现

### B1. §4.4 关于 “DAG 并发 + `DeviceLock` 已足够安全” 的判断不成立

**位置：**
- 草稿 §4.4（`docs/设计-实验编排统一-v0.1-草稿.md:186-192`）
- 现有设备锁实现 `labos-kernel/src/main/java/com/labos/kernel/driver/DeviceLock.java:58-103`
- 执行时加/释放设备锁 `labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java:1847-1885`
- 现有位置双锁仅覆盖两点搬运 `labos-kernel/src/main/java/com/labos/kernel/driver/PositionLock.java:205-215`
- 项目现有死锁设计结论 `docs/资源模型与死锁避免-设计.md:273-307`

**问题：**

草稿写道：

> 设备锁（`DeviceLock`）已经能保证“同一台设备不会同时被两个流程用”，所以 DAG 的并发是安全的。

这句话的前半句对，后半句**推不出来**。

`DeviceLock` 只保证“单台设备同一时刻只有一个 run 占用”，实现上就是对 `device_state.current_run_id` 做单资源抢占/等待；`PositionLock.tryReserveTransfer()` 也只保证“两个位置按 `resource_id` 排序申请，避免 X/Y 互等”。这两者都**没有**建立“多资源等待图”，更没有覆盖：

- 位置（L1）
- 出入口/port（L2）
- 机械臂（L3）

之间的**跨层循环等待**。

而项目自己的并发设计文档已经给过结论：`returnTo` / 双锁只能解决单链路，**A→B→C→A 环必须靠等待图拒绝成环申请**，否则会死锁。

**具体死锁构造：**

设实验内 3 条 DAG 并行分支分别持有 A / B / C 的内部位置，且下一步都需要“机械臂 + 对方设备的出入口/目标位”：

1. 分支 P1：板在 A，等待进 B
2. 分支 P2：板在 B，等待进 C
3. 分支 P3：板在 C，等待进 A

这不是“同一台设备被两条流程同时用”的问题，而是**三条流程各自占着一部分资源、再等待下一部分资源**。  
`DeviceLock` 看不到这种环，只会让 3 条流程都继续等；等待图才会在 “P3 等 A，而 A 被 P1 链住” 的那一刻检测到环并拒绝。

**为什么这是阻断级：**

S2 一旦把“实验内并发派发”做成真实 wall-clock 并发，这个前提错误就不是文档瑕疵，而是**上线后会卡死整单**的执行级风险。

**建议修正：**

把 §4.4 / §8.4 的口径改成：

1. `DeviceLock` 只解决**单设备互斥**；
2. S2 若做真实并发，必须**复用/并入**现有的三层资源 + 等待图方案；
3. 若 S2 不准备同时带入等待图，则只能做“逻辑并行、物理串行”的保守版，不能宣称“实验内可并行执行”。

### B2. §5 / §6 的批次模型无法承载“失败只重跑该批”的历史与重试

**位置：**
- 草稿 §5.2（`docs/设计-实验编排统一-v0.1-草稿.md:212-216`）
- 草稿 §6 批次表草案（`docs/设计-实验编排统一-v0.1-草稿.md:235-244`）

**问题：**

草稿同时提出：

1. “每批一次 run，run 上记 `batch_no`”
2. “失败只重跑那一批”
3. `experiment_batch` 只有一个 `run_id`

这三件事当前**放不进同一套模型**。

如果一个批次失败后重跑：

- 要么覆盖 `experiment_batch.run_id`，那前一次失败 run 的历史就丢了；
- 要么不覆盖，那“当前这批对应哪次 run”又说不清；
- 而草稿里又没有真的给 `run` / `experiment_run` 加 `batch_no` 或 `batch_id` 字段，和“run 上记 `batch_no`”不一致。

**为什么这是阻断级：**

“失败只重跑该批”不是 UI 展示问题，而是**审计 / 追责 / 统计口径**问题。  
没有稳定的数据模型，后面的续跑、报工、成功率、批次详情页都会分叉。

**建议修正：**

二选一：

1. **稳定批次 + 多次尝试**  
   `experiment_batch` 只表示“逻辑批次”，新增 `experiment_batch_run(batch_id, run_id, attempt_no, status, started_at, finished_at)` 记录每次执行；
2. **run 自带批次归属**  
   直接在 `experiment_run`（或 `run`，按真实口径二选一）加 `batch_no` / `batch_id`，`experiment_batch` 只做汇总，不持有单个 `run_id`。

在这两个里，我更建议 **#1**，因为它天然支持“同一批多次尝试”的历史。

## 三、高级别发现

### H1. S1 不能只做“画布编译落库”，还必须同时收口保存入口；否则“双套路径”还在

**位置：**
- 草稿 §2.2 规则 1-5（`docs/设计-实验编排统一-v0.1-草稿.md:78-90`）
- 草稿 §7 S1（`docs/设计-实验编排统一-v0.1-草稿.md:252-259`）
- 现有 `experiment_process` 保存 `https://github.com/rogerlzp/labos/blob/7524a94d853076a601bb87ad6a0e8bc45c31d8d2/labos-kernel/src/main/java/com/labos/kernel/api/QueryService.java:1393-1425`
- 现有 `experiment_graph` 保存 `https://github.com/rogerlzp/labos/blob/7524a94d853076a601bb87ad6a0e8bc45c31d8d2/labos-kernel/src/main/java/com/labos/kernel/api/QueryService.java:2156-2172`

**问题：**

草稿里对“谁是唯一事实来源”的判断是对的，但 S1 写成“可独立上线”，当前还少了一个关键条件：

> **graph 保存 + process 编译结果保存，必须在同一个后端入口、同一事务里完成；并且 process 直改入口要同时关掉。**

现在实际代码里：

- `experiment_process` 有自己的整体替换事务；
- `experiment_graph` 也有自己的独立保存；
- 两者没有原子绑定。

如果 S1 只是“前端从画布触发一次编译”，但服务端仍保留两条独立写路径，那仍然会出现：

1. graph 写成功、process 写失败；
2. process 被直改入口改了、graph 没跟；
3. 事务成功但 version / 审计口径只更新了其中一边。

这就是你在草稿 §1 里刚刚抓出来的那类问题，只是从“历史偶发”变成“设计上保留”。

**建议修正：**

把 S1 的 Definition of Done 明确补成：

1. 新增单一保存入口：`saveExperimentGraphAndCompile(...)`
2. 该入口在**一个事务**里同时写 `experiment_graph` + `experiment_process` + `experiment.version`
3. 流程表直改入口（该路径）在同版本**关写或仅保留只读**
4. 回归测试要覆盖 “graph/process 任一写失败时整体回滚”

否则 S1 不能算真正“消除画布不生效”，只能算“把分裂概率降低”。

## 四、核实为真的项

以下判断经读码核实，草稿写得成立：

### 1. `experiment_graph` 目前确实只有画布读写，执行器不读

- 执行器只按 `experiment_process ORDER BY seq`（`labos-kernel/src/main/java/com/labos/kernel/workflow/ExperimentExecutor.java:108-139`） 展开
- `experiment_graph` 目前只有 `SELECT graph`（`https://github.com/rogerlzp/labos/blob/7524a94d853076a601bb87ad6a0e8bc45c31d8d2/labos-kernel/src/main/java/com/labos/kernel/api/QueryService.java:2137-2153`） / `saveExperimentGraph`（`https://github.com/rogerlzp/labos/blob/7524a94d853076a601bb87ad6a0e8bc45c31d8d2/labos-kernel/src/main/java/com/labos/kernel/api/QueryService.java:2156-2172`）

结论：**“画布不生效”是事实，不是推测。**

### 2. `run_after` 目前确实是 API 暴露了，但执行器没用

- API 返回 `p.run_after`（`https://github.com/rogerlzp/labos/blob/7524a94d853076a601bb87ad6a0e8bc45c31d8d2/labos-kernel/src/main/java/com/labos/kernel/api/QueryService.java:1236-1260`）
- `ExperimentExecutor.expand()` 查询字段只有 `seq / workflow_id / loop_count / params_override`，**没有 `run_after`**

结论：草稿把它作为“模型先行、执行没跟上”的反例，判断成立。

### 3. “先 B 后 A”作为路线判断，方向上合理

我没有发现必须立刻 All-in BPMN 的硬约束。  
按当前系统体量，**先解决“画布不生效”，再决定是否统一引擎**，这个排序是稳妥的。

### 4. §4.3 “先不做子实验嵌套” 的总体判断合理

草稿列出的 4 个额外设计面：

- 锁归属
- 变量作用域
- 取消传播
- 报表聚合

都是真问题，而且当前代码没有现成边界可复用。  
所以“先用 DAG + phase + batch 承接真实需求，不引入嵌套”这个判断，我这里**同意**。
