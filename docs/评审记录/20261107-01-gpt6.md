## 1. 结论摘要

当前项目已有实质性工程基础：主工作流路径已能看到 `WorkflowService → GraphRunner → RunStateMachine → DriverStepExecutor`；已有设备锁、板位预约、搬运资源计划、暂停队列、启动收尾、模拟器和较完整的 E2E 门禁。11 月 6 日的超时策略和暂停实验也比早期版本更成熟。

但有几个关键概念目前仍然混在一起：

1. **本地停止等待 ≠ 设备物理停止**；
2. **数据库锁释放 ≠ 设备物理空闲**；
3. **设备方法返回成功 ≠ 板位已被独立物理确认**；
4. **命令完成后写历史 ≠ 命令执行过程的可审计账本**；
5. **图解析失败可回退 ≠ 图执行中途失败可切换执行器重跑**。

最重要的结论：当前首要工作不是引入更多中间件，也不是大规模重写，而是封住上述语义边界，避免系统在不确定状态下重复物理动作或错误释放资源。

## 2. P1/P0 级发现

### F-01｜P0｜执行图运行时异常可能触发整条流程顺序重跑

**状态：CONFIRMED**

证据：`labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java:803-840`。

当前 `try` 块同时包含：

- `WorkflowGraphParser.parse(xml)`；
- GraphRunner 构造；
- `gr.run(g, executor)`；
- `viaGraph = true`。

同一个 `catch (RuntimeException)` 在捕获异常后调用 `sm.executeAll(rec, executor)`。

这与旁边注释“只在解析阶段失败时退回”不一致：**catch 的实际范围包括图执行本身**。如果图已执行若干节点、已经下发设备命令，之后发生运行时异常，顺序路径会从头执行 `rec`。对开盖、抓取、搬运、加样等非幂等物理动作，可能造成重复执行。

**整改要求：**

1. 将 XML 解析、静态校验与执行分成两个独立阶段。
2. 只有在任何设备命令派发前，解析/编译失败才允许选择旧执行路径。
3. 一旦 `ExecutionStarted` 或第一条命令进入 DISPATCHED，禁止自动切换执行引擎；只能进入失败、UNKNOWN、恢复或人工处置。
4. 对图执行增加“执行已产生副作用”的显式标记，不能只依赖异常类型。

**验收：** 注入“第 2 个节点设备命令已发送后，GraphRunner 抛 RuntimeException”，断言后续没有顺序执行路径、没有重复 commandId 以外的新物理动作，run 进入可审计失败/待恢复状态。

### F-02｜P0｜当前 abort 实现不能证明设备物理动作已经停止

**状态：CONFIRMED**

证据：

- `labos-kernel/src/main/java/com/labos/kernel/driver/DeviceDriver.java:28-29`：接口只定义“尽力而为”的 `abort(commandId)`。
- `labos-kernel/src/main/java/com/labos/kernel/driver/tcp/TcpPersistentDriver.java:120-127`：abort 只从本地 `pending` 移除 future 并完成一个 `EC-99-0005` 结果。
- `labos-kernel/src/main/java/com/labos/kernel/driver/tcp/TcpDriverAdapter.java:146-149`：明确写着协议没有 Abort 消息类型，方法为空操作。
- `DriverStepExecutor.executeCommand`：检测到暂停后调用 abort，并将本地等待结果作为中断结果返回。
- `WorkflowService.resumeAsync`：恢复时删除未完成节点及其命令记录，后续会重跑该节点。

因此当前测试证明的是“本地命令等待可快速结束并落库 aborted”，**不是“设备执行器/机械臂已停止运动”**。如果设备仍在执行，系统却将命令视为中断，之后恢复重跑，可能出现重复动作或资源争用。

尤其注意：最新 E2E `scripts/e2e-interrupt-during-device.py` 的断言是命令 10 秒内进入 aborted、run 进入 paused；它没有读取设备侧独立的停止确认，也没有证明运动机构实际停止。脚本临时把机械臂 Home 标为 interruptible=true，更不能据此批准真实机械臂搬运可中断。

**整改要求：**

1. 将“取消本地等待”与“设备停止”拆成两个不同结果。
2. `AbortResult` 至少区分 `REQUESTED`、`DEVICE_ACKNOWLEDGED`、`PHYSICALLY_STOPPED`、`UNSUPPORTED`、`UNKNOWN`。
3. 没有设备协议 Abort 指令或设备侧状态查询的驱动，只能报告“暂停请求已记录，当前动作继续到安全边界”，不得伪报 PHYSICALLY_STOPPED。
4. `interruptible=true` 只有在具体设备型号、固件、方法、负载/板型和停止后安全状态通过 HIL 验证后才能启用。
5. 中断结果为 UNKNOWN 时，不允许恢复时自动重跑；先 query/reattach/reconcile，无法确认则人工确认。

**验收：** 使用真实设备或可证明模拟物理运动状态的测试桩：发出暂停后，分别验证“设备确认停止”“设备拒绝停止”“响应丢失但设备继续执行”三种情况；只有第一种可落为 PHYSICALLY_STOPPED。

### F-03｜P1｜device_method 查询把设备实例 ID 当成设备型号 ID

**状态：CONFIRMED（Schema 语义与查询参数不一致）**

证据：

- `pg_rebuild/schema/30_business.sql:286-321`：`device_method.device_id` 外键指向 `device(id)`；`device_instance.device_id` 也指向 `device(id)`。前者是设备型号，后者是实例到型号的关联。
- `DriverStepExecutor.deviceMethodTimeoutSec`、`deviceLibraryTimeoutSec`：以 `device_instance.id` 作为参数，却直接执行 `device_method.device_id = ?`。
- `DriverStepExecutor.isInterruptible`：同样用 `device_id = instanceId` 查询 `interruptible`。

这是 ID 空间错误：正确路径应从 `device_instance` 取出 `device_id`，再与 `device_method.device_id` 关联，并同时约束 tenant、method。当前若实例 ID 与型号 ID 恰好相同，测试可能偶然通过；生产数据不应依赖这种巧合。

**影响：** 方法级超时、设备方法库上限和 interruptible 标记可能查不到或读错，进而退回默认超时/默认不可中断。当前 E2E 临时插入 `device_method` 时把 `ARM_DEVICE=214`（注释明确是 device_instance.id）写进 `device_method.device_id`，进一步掩盖了模型/实例混用。

**整改要求：** 改为 JOIN 查询，例如：

```sql
SELECT dm.timeout_sec
FROM device_instance di
JOIN device_method dm
  ON dm.device_id = di.device_id
 AND dm.tenant_id = di.tenant_id
WHERE di.tenant_id = ?
  AND di.id = ?
  AND di.deleted_at IS NULL
  AND dm.method = ?;
```

interruptible 与方法库上限查询也必须使用同一关联语义。补一条测试：device model id 与 device instance id 故意设置为不同值，确保查询仍能正确命中。

### F-04｜P1｜run_command 目前是“完成后记录”，不是执行中的命令账本

**状态：CONFIRMED**

证据：`WorkflowService.PersistingStepSink.onStepDone → writeStep`（约 1941 行起）；`writeStep` 在步骤完成回调中才 INSERT `run_node` 子步骤和 `run_command`，且 `sent_at`、`finished_at` 都写 `now()`。

项目在 11 月 6 日评审包中也已纠正测试判据：`run_command` 有行不代表设备正在执行，它是步骤结束后才插入的。

**影响：** 如果进程在命令已发送、设备正在运行、响应尚未返回时崩溃，数据库没有这条命令的完整派发记录。启动恢复看到的只是 run/node 的 running 状态，不能准确知道哪个 commandId 已经送出、设备可能执行到哪里。此时仅靠完成后记录无法完成可靠的命令级 reconciliation。

**整改要求：**

- 在设备派发前持久化 command ledger：`CREATED → DISPATCHED`。
- 设备 ack、running、completed、failed、aborted、unknown 分别以事件/状态更新记录。
- 命令创建与 Outbox 事件在同一 PostgreSQL 事务提交；派发成功不能替代设备确认。
- `command_attempts` 单独记录每次网络尝试；状态查询不算命令重发。
- 超时或断线后记为 UNKNOWN/RECONCILING，不要直接记 FAILED 并允许新动作。

### F-05｜P1｜板位状态是软件推断，不是独立物理确认

**状态：PARTIAL**

证据：

- `WorkflowService.PersistingStepSink.writeStep` 在方法成功后调用 `PositionLock.notePlateMove(...)`。
- `PositionLock` 通过 SQL 更新 `position_state.plate_id`、占用和预约信息；`device_state.has_plate` 从位置表刷新。
- 本轮检查到的板位状态主路径，是依据设备方法结果和参数推导位置；没有看到每次搬运后必须等待扫码、光电、称重或人工盘点证据的强制事务门槛。

**影响：** “驱动返回成功”与“板确实在目标位置”不是同一事实。设备回包可能丢失、传感器可能误报、人工可能移动板。若数据库直接把软件推断当成物理事实，下一步可能基于错误位置继续搬运。

**整改要求：**

1. 把位置模型拆成逻辑预约、物理观测、安全状态三部分。
2. 搬运完成必须进入 `VERIFYING`；扫码/传感器/人工证据匹配后才可 `CONFIRMED`。
3. 观测失败、ID 不匹配、证据过期或设备状态不明时进入 UNKNOWN/QUARANTINED。
4. TTL 到期只能让软件预约过期，不能自动证明物理位置空闲。

### F-06｜P1（条件性）｜StartupRecovery 的清锁策略没有物理对账

**状态：PARTIAL；需进一步确认调用路径**

证据：`labos-kernel/src/main/java/com/labos/kernel/workflow/StartupRecovery.java:97-160`。

`settle()` 将 running/queued/pending run 置 failed，并按 `current_run_id` 清空 `device_state` 锁，将设备状态置为 idle/error；对孤儿锁也直接清理。代码中没有在清锁前向设备查询 active command，也没有目标板位物理核验。

这可以解决“数据库锁永久卡死”，但不能证明设备已停止。若 API/内核崩溃时设备仍在运动，重启后直接清锁会允许新 run 争用仍在工作的设备。

**调用路径说明：** 本轮在 `ApiServer` 中确认到 `StartupRecovery.settleOrphanExperimentRuns` 的启动调用；没有在已检查的入口中确认 `StartupRecovery.settle()` 本身的完整调用链。因此本项作为代码策略风险记录，不能直接断言该清锁语句当前每次启动都会执行。

**整改要求：** 清理逻辑应改为“收敛 run 状态但保留资源隔离”：设备状态转 UNKNOWN/QUARANTINED，尝试 query/reattach/reconcile；只有设备确认 idle、活动命令已终结且位置确认后才释放资源锁。对确实不存在设备状态查询能力的驱动，转人工核验。

### F-07｜P1｜subProcess 缺少编译期拒绝，可能丢失流程语义

**状态：CONFIRMED（未支持的节点类型未 fail-fast）**

证据：

- `WorkflowGraphParser.isTaskLike`（约 192–196 行）白名单未包含 `subProcess`。
- `RecipeCompiler.compileAll`（136–139 行）对非 task 类型直接 `continue`，没有错误诊断。
- `docs/评审包-20261106/02-遗留与后续规划.md` §2 也把 subProcess 静默跳过列为未解决项。

不能据此简单断言所有子流程内部节点都被删除；解析器会遍历 XML 后代节点。但可以确认：subProcess 容器/作用域语义没有作为受支持的执行结构被显式编译，也没有在编译期明确拒绝。

**整改要求：** 先明确支持范围。未支持的节点类型必须返回结构化编译错误（节点 ID、类型、原因、替代方式），禁止静默跳过并让整单显示 completed。若实现 subProcess，需定义作用域变量、输入输出、异常传播、取消、重试、循环边界与子 run 审计。

## 3. P2 级发现与待验证项

### F-08｜P2｜方法库 MAX 超时可能把慢方法超时扩散给整台设备

**状态：CONFIRMED（策略如此实现）；合理性待业务确认**

`DriverStepExecutor.deviceLibraryTimeoutSec` 使用该实例对应设备方法库的 `MAX(timeout_sec)`。这样能解决设备库只登记部分方法名导致精确匹配落空的问题，但某个慢方法（如长工艺）的超时可能被用于该设备其他未登记方法（如 Home/扫码）。此外，`MethodTimeoutPolicy.resolve` 把设备方法库上限放在 `workflow_node.timeout_sec` 之前，流程节点显式设置的更短 deadline 可能失去约束作用。

**建议：** 分开定义设备方法的最大执行时长、响应超时、流程 deadline。方法缺失时优先用能力/方法族映射，不要无条件用整台设备所有方法的最大值。流程 deadline 应作为独立上限参与计算，不能被宽泛的设备库值覆盖。

### F-09｜P2｜实验级暂停查询只取最近一个匹配实验

**状态：CONFIRMED**

`DriverStepExecutor.pauseRequested(workflowId)` 对 `experiment_run` 与 `experiment_run_step` 联查后按 `er.id DESC LIMIT 1` 取一个 experimentId。若同一个 workflow 同时被多个实验运行，暂停判定只看最近的那个实验，可能漏掉另一个实验的 runtime_hold，或把暂停信号错误映射给共享 workflow run。

**建议：** 暂停作用域应沿明确的 run → experiment_run_step → experiment_run 关联传递，不要仅凭 workflowId 反查最近一个实验。并发实验复用同一 workflow 的测试必须覆盖“只暂停 A、不影响 B”以及“A/B 都暂停”的场景。

### F-10｜P2｜RecipeCompiler 的批量接口忽略 capabilityByResource

**状态：CONFIRMED**

`RecipeCompiler.compileAll(nodes, protocolCap, capabilityByResource)` 的循环内执行 `compile(n, protocolCap)`，没有把第三个参数传入 `compile(n, protocolCap, capabilityByResource)`；并且 `WorkflowService` 当前构造 recipe 时逐个调用的也是两参数重载。对没有显式 protocolName、依赖能力模板展开的绑定节点，可能无法使用绑定设备的真实能力来选 recipe。

**建议：** 修正参数传递，并在绑定资源能力与显式能力冲突时定义清晰优先级；加入模型 ID、实例 ID、resource_node ID 各不相同的测试数据。

### F-11｜P2｜Redis Gateway 队列没有完整的消费确认/重启恢复协议

**状态：PARTIAL；Gateway 是否为当前生产主链路仍 UNKNOWN**

`labos-gateway/GatewayMain.consumeLoop` 使用 `RPOP` 从队列删除命令，随后在 `handle` 中写入 pending hash，再调用驱动。代码有记录 pending 的动作，但当前入口没有看到启动时扫描 pending 并 query/reattach/reconcile 的处理，也没有消费确认后可安全重放的队列协议。

**建议：** 若该 Gateway 用于生产，改用 Redis Streams consumer group 或等价的持久投递/确认机制；pending 必须可恢复，但恢复时不能盲目重发。PostgreSQL command ledger 才是长期审计真相，Redis 只做传输/缓存/通知。

### F-12｜P2｜删除 run 与设备锁释放仍是两个独立动作

**状态：CONFIRMED（项目最新评审包也已登记）**

`docs/评审包-20261106/02-遗留与后续规划.md` §2 明确说明：删除 run 本身不释放 `device_state.current_run_id`，目前依赖后续启动兜底清理。应把删除入口、后台清理和手工清理统一到事务化服务；但在引入物理 reconciliation 前，不能把“删除 run”实现成无条件释放正在执行设备的锁。

## 4. 对当前架构的修正建议

### 4.1 暂时保留现有主执行链，不做大规模推倒重写

本轮在 `WorkflowService` 中确认的主要路径是：

```
WorkflowService
  ├─ WorkflowGraphParser
  ├─ GraphRunner
  ├─ RunStateMachine
  ├─ DriverStepExecutor
  ├─ DeviceDriver / TCP driver
  └─ PersistingStepSink
       ├─ run_node
       ├─ run_command
       ├─ device_state
       └─ PositionLock
```

`ExperimentFlowRunner` 类仍存在，并以 `ShadowProbe` 逐步执行，但本轮未确认它是当前主 API 的活动执行路径。因此，不能仅凭类存在就认定当前有两套同等活跃的生产执行内核。下一轮应做全仓调用图，确认所有入口、测试入口、旧 API 和 shadow path，再决定适配或下线。

### 4.2 目标内核分层

```
Workflow/BPMN/Canvas/Python DSL
          │
          ▼
Parser + Canonical IR + Static Validator
          │  未支持节点/类型/单位/设备能力 → 编译失败
          ▼
Immutable ExecutionPlan + hash + capability snapshot
          │
          ▼
ExecutionKernel
  ├─ Run state
  ├─ Node execution state
  └─ Command ledger / attempts / outbox
          │
          ▼
DeviceGateway
  ├─ dispatch / ack / progress / result
  ├─ query / reattach / abort
  └─ reconciliation
          │
          ▼
Physical Resource & Position Safety
  ├─ lease + fencing（软件并发协调）
  ├─ logical reservation
  ├─ physical observation
  └─ UNKNOWN / QUARANTINED / manual release
```

### 4.3 Redis 与 PostgreSQL 的职责

- PostgreSQL：不可变执行计划、run/node/command 状态、command attempts、Outbox、资源预约、物理观测证据、审计事件。
- Redis：短时协调、队列、Pub/Sub、遥测缓存、可重建的运行态视图。
- Redis lease 过期不能代表物理资源已释放；租约到期后的恢复必须核对 command 和设备状态。
- Fencing token 只有在命令入口或设备侧验证时才有防旧 Worker 的效果；仅生成 token 不构成保护。

### 4.4 物理位置与搬运事务

建议状态拆分：

| 维度 | 状态示例 | 语义 |
|---|---|---|
| 逻辑占用 | FREE / RESERVED / OCCUPIED | 调度器的软件账本 |
| 物理观测 | PRESENT / ABSENT / UNKNOWN | 传感器、扫码或人工证据 |
| 安全状态 | NORMAL / QUARANTINED / MAINTENANCE | 是否允许继续使用 |

搬运流程建议：

`REQUESTED → SOURCE_VERIFIED → SOURCE/TARGET_RESERVED → IN_TRANSIT → MOTION_REPORTED_DONE → TARGET_VERIFICATION → COMPLETED`

任何中断、超时、ID 不一致、传感器异常都进入 UNKNOWN/QUARANTINED，不允许 TTL 到期后自动当作空位。

## 7. 最终判断

LabOS 已经不是只有文档和原型的项目：主执行路径、资源互斥、板位账本、模拟器、恢复逻辑和测试门禁都已存在。下一阶段应从“功能覆盖”转向“故障时不做错事”。

当前最重要的工业化标准不是“异常后自动继续”，而是：

1. 系统能准确说出命令是否派发；
2. 不确定时不会把 UNKNOWN 伪装成 FAILED/IDLE；
3. 物理动作未确认停止时不会释放设备；
4. 板位未独立确认时不会当作事实；
5. 执行已经产生副作用后不会换路径重跑；
6. 不支持的流程语义会在执行前明确拒绝。

**建议先完成 F-01 至 F-07 的整改设计和回归用例，再开始代码修改。** 本轮不建议引入新的分布式锁系统作为优先工作，也不建议直接重写 Scheduler。


## 8. P0 修复跟进（同一评审分支追加）

### 8.1 F-01 执行图异常 fallback

**状态：已修复并增加回归测试。**

- `WorkflowService.executeGraphWithParseFallback` 现在只在 `WorkflowGraphParser.parse` 阶段捕获 RuntimeException。
- `GraphRunner.run` 在 catch 之外执行；执行期异常直接向上传播，不再调用 `sm.executeAll` 从头重跑。
- 新增 `WorkflowExecutionSafetySelfTest`：模拟设备动作已经产生副作用后抛 RuntimeException，断言顺序 fallback 调用次数为 0。
- 保留“解析失败且尚未执行设备命令时使用顺序兼容路径”的既有策略；该策略本身仍需后续逐步收紧，确保含网关/不支持语义的图不会被错误降级。

### 8.2 F-02 设备中止语义

**状态：已实施保守缓解；真实物理 Abort 仍未实现。**

- `DeviceDriver.supportsPhysicalAbort()` 新增安全默认 `false)。驱动必须明确声明，并且具体型号/固件/方法通过 HIL 验证后，才能开启异步中止路径。
- `DriverStepExecutor` 只有在方法配置允许且驱动声明物理中止能力时，才会调用 `abort`。
- `TcpPersistentDriver.abort` 不再移除 pending Future 并伪造失败结果；当前 TCP 协议无设备侧 Abort 消息，故继续等待设备自然完成。
- 当前 TCP 驱动没有覆盖 `supportsPhysicalAbort()`，因此执行中暂停将等待当前动作完成，再由 GraphRunner 在后续任务边界处理暂停。
- 新增 `DeviceDriverAbortContractSelfTest`，锁定物理中止能力默认关闭。
- 将原“几秒内命令必须 aborted”的 E2E 判据改为：当前动作自然完成、下一任务边界暂停、无重复命令；测试清理前必须确认设备不在运行，否则保留 run/资源锁供人工核验。

**限制：** 这不是设备急停，也不是实时中止。若设备执行时用户发出暂停，当前动作仍可能继续到完成。当前暂停入口会先把 run 状态写为 `paused`，因此动作收尾期间 UI 可能暂时显示 paused，但设备仍在运行；本次 active-worker guard 会拒绝此时的 resume，直到旧 worker 退出。下一阶段应引入独立的 `pause_requested/pausing/paused` 语义，避免 UI 把“已请求暂停”显示成“物理动作已停”。真实物理 Abort 仍需设备协议、驱动确认与 HIL。

### 8.3 同一 run 的 worker 所有权

**状态：已增加进程内保护；不等同于跨进程分布式锁。**

- `startAsync` 在提交后台任务前登记 active run。
- `resumeAsync` 只有在旧 worker 已退出后才能获取同一 run 的 worker 所有权；否则返回明确错误，要求等待设备动作到达安全边界。
- worker 结束时释放登记。
- 新增纯逻辑回归用例，验证同一 run 不能被第二个 worker 同时获取。
- 该保护只覆盖当前 JVM；进程崩溃、多个 Kernel 实例和跨主机调度仍需数据库 lease/fencing 与恢复对账。
