## 二、归档 §9 六问的答复

### Q1 · 第四方案（`device_physical_hold`）的假设破了怎么补？

**答：假设不会因为"设备不拒绝别的命令"而破，只会因为"存在不经物理占用准入的下发路径"而破。我核了一遍，路径是收口的。**

**先纠一个概念**：hold 假设的是"**中控不向该设备下发新命令**"，**不是**"设备不会收到别的命令"。设备内部排队、内部调度都不影响这个假设 —— 归属靠 `commandId` 回显，与"设备此刻在跑谁的活"无关。

⇒ "设备受理后又接收了别的命令"这件事，在中控体系内**只有一个来源：另一个 run/分支的中控下发**。

**下发路径盘点（我逐个核过）**：

| 路径 | 位置 | 是否发物理动作 |
|---|---|---|
| `DriverStepExecutor.executeCommand` | `DriverStepExecutor.java:1187` → `:1325` / `:1328` `driver.execute(cmd)` | ✅ **生产主路径，唯一收口点** |
| `ShadowProbe` | `ShadowProbe.java:78` `driver.execute(...)` | ❌ **已被只读白名单挡住**：`ShadowProbe:61-67` 原文"影子探针是诊断用途，但仍属 driver.execute 旁路。限制只能发只读命令（白名单：Get/Read/Status/Query 等），运动类/未知一律拒绝——**防止探针变成绕过互锁门禁的第二个物理下发通道**" |
| `DriverContractDemo` | `DriverContractDemo.java:52-61` | ❌ demo 类，生产不走 |

⇒ ⇒ **没有真正的旁路** ⇒ hold 假设在当前代码下**成立**。

**⇒ 补法（三条，按优先级）**：

| # | 动作 | 说明 |
|---|---|---|
| **1** | **物理占用检查放在 `DriverStepExecutor.executeCommand`（唯一收口点）**，不要放在调度器的资源粗筛层 | 这样将来新增任何执行器（哪怕走旁路）都自动被覆盖；而放在调度器层 ⇒ `ExperimentFlowRunner` 那条路径会漏 |
| **2** | hold 建立时记 `owner_command_id`；若之后收到**同设备另一个 `commandId`** 的完成事件 ⇒ 记**并发下发冲突**告警 + 该设备降级 | 把"假设破了"变成**可观测**的，而不是靠推理 |
| **3** | **hold 必须有 TTL/过期兜底** | 设备永不发完成事件 ⇒ hold 永不清 ⇒ 该设备永久不可用 ⇒ 超期降级为 `QUARANTINED` + 人工（与 R-10/E-19 同一处置） |

⇒ **建议在 §4.3.3 补一句口径定义**：

> `device_physical_hold` 的语义是"**中控在完成事件到达前不再向该设备下发新命令**"，**不是**"该设备此刻只在执行我的命令"。

⇒ 这句写清楚，Q1 里的假设就不是假设而是**可验证的不变量**，且验证点就是上面的第 2 条。

### Q2 · 设备忙轮询的 1 分钟间隔 / 15 分钟上限合理吗？现场设备忙的最长时间是多少？

**答：上限 15 分钟与既有口径一致 ✓；但 1 分钟间隔太粗，应分档。**

**可查的量级证据**（不是我的估计）：

| 忙的形态 | 典型时长 | 出处 |
|---|---|---|
| 机械臂搬运 | **均值 9.33 秒/次** | `WorkflowWebService:286-287`（已记录的实测） |
| 提取仪跑一个阶段（Bind/Wash/Elute） | 数十秒~数分钟 | `MethodTimeoutPolicy:49-64` 的能力默认（INCUBATE 1800s / CENTRIFUGE 900s / WASH 900s） |
| 孵育 | **30 分钟** | 同上 |

⇒ ⇒ **设备忙的典型量级跨了三个数量级（秒 → 分 → 半小时）**，用一个全局 1 分钟间隔必然两头不讨好：机械臂场景**平均白等 30 秒**（设备刚空出来，中控 1 分钟后才发现）；孵育场景 1 分钟又太频繁。

⇒ **建议按"预期忙时长"分档**（可复用 `device_method.timeout_sec`）：

| 预期忙时长 | 轮询间隔 |
|---|---|
| < 30 秒（机械臂搬运类） | **1~2 秒** |
| 30 秒 ~ 5 分钟（提取阶段、离心） | **10~30 秒** |
| > 5 分钟（孵育） | **1 分钟** |

⇒ **上限 15 分钟**：与既有 `DEVICE_LOCK_WAIT_MAX_MS = 900_000L`（`WorkflowService:3422`）一致 ✓ **口径统一，好**。但建议**分开命名与配置**：现在是两个不同的 15 分钟 —— 一个是"设备被**合法**占用多久"（正常竞争），一个是"busy 轮询多久放弃"（异常占用）。同名不同义会埋坑。

⇒ ⚠ 另外：**15 分钟是轮询上限，不是设备忙上限**。若设备真的在孵育（30 分钟），中控会在 15 分钟时放弃并转人工 ⇒ **但设备还在跑** ⇒ ⇒ 这正是 R-10 要用 `QUARANTINED` 兜的场景 ⇒ 两个数字必须联动配置（轮询上限 < 该设备的正常最长方法时长时，应该直接判"这是正常占用"而不是"busy 异常"）⇒ ⇒ **建议：轮询上限取 `min(15min, 该设备型号最长方法超时)`**，超过即视为"该设备不支持长占用"⇒ 降级独占。

### Q3 · commandId 逻辑操作级唯一 —— 人工"拆成两次执行"该不该变？

**答：应该变，但不能用 `generation` 表达 —— 需要第三层结构。**

**先看现状**（表设计 §1.7，`:263-291`）：`commandId = 一次逻辑操作的唯一标识`；场景表里"人工重跑同一节点 → 变（generation+1）"；`:289`"所以 `uk_logical_operation_cmd UNIQUE (tenant_id, command_id)` **单列唯一即可**，不需要按档位放宽——因为 id 在所有重试中都不变，**一个逻辑操作只有一行**"。

⇒ **"拆成两次"会打破"一个逻辑操作只有一行"这个前提** ⇒ 结构上装不下。

**判据：commandId 是设备侧的去重键 ⇒ 它的粒度必须是"设备看到的一次执行"。**

⇒ "人工把一次逻辑操作拆成两次执行" ⇒ 设备会看到**两个不同的东西** ⇒ 如果 commandId 不变，**设备会把第二次当重复而静默不执行** ⇒ 流程卡住或结果错 ⇒ ⇒ **必须变**。

⇒ 但**不该用 `generation +1`**：`generation` 的语义是"同一业务步被**重新执行**了几次"（人工重跑整个节点），而"拆成两次"是**同一个逻辑操作内部的两个物理段** ⇒ 语义不同 ⇒ 混用会让 `generation` 变成"逻辑操作内部的分段计数"，而它现在的定义是"同一业务步的执行代次"。

⇒ **建议的结构（三层）**：

```
logical_operation   （业务身份：operation_key + generation）
        │
        └── logical_command  （子表：一个逻辑操作下的多个物理命令）
                ├─ command_id   VARCHAR(160)   ← 设备幂等键，设备侧去重
                ├─ attempt_no   INT            ← 传输尝试次数
                └─ state / result_trust / dispose_*
```

| 场景 | logical_operation | logical_command | command_id |
|---|---|---|---|
| 传输重试（同一 id 再发一次） | 不变 | attempt_no +1 | **不变** |
| 人工重跑（整个节点再来一遍） | generation +1 | 新建一行 | **变** |
| **人工拆成两次执行** | **不变** | **新增一行** | **变** |
| resume（未结算） | 不变 | 复用 | 不变 |
| 循环下一轮 | operation_key 变（`\|l{n}`） | 新建 | 变 |

⇒ ⇒ **这一改同时解决我上一轮（20261119-09）提的 N-H**（"command_id 的粒度是传输、不是逻辑动作 ⇒ 放在 `logical_operation` 单列上是粒度错配"）⇒ **command_id 下移到子表** ⇒ `uk_logical_operation_cmd` 也随之迁到子表 ⇒ `logical_operation` 不再持有 `command_id`。

⇒ 建议在 §1.7 的场景表里补"人工拆成两次执行"这一行，并写明它落在 `logical_command` 子表。

### Q4 · E-16（分支子图互不相交）：现有流程有没有"两分支经过同一节点"的合法场景？

**答：没有 ⇒ E-16 的约束成立，可以保留为编译期检查。**

**核对提取线的实际结构**（`scripts/setup-extraction-flow.py`）：

```
split_a = b.parallel_gateway("并行拆分（磁套加载）")        # :442
  分支循环内（每台提取仪一条）：
    n_pick      (:449)  {code} 取磁套      protocol=PickTipComb
    n_wait      (:452)  等 {code} 等待交互  protocol=__awaitEvent
    n_scan      (:469)  机械臂 扫码
    n_move      (:473)  机械臂 放磁套板到 {code} 交互位
    n_done_scan (:498)  机械臂 扫码（放板到位确认）
    n_drop      (:502)  {code} 卸磁套
join_a = b.parallel_gateway("并行汇合（磁套加载完成）")      # :520
split_b = b.parallel_gateway("并行拆分（内部工序）")          # :539
```

⇒ **每个节点的 `b.task(...)` 都在分支循环体内调用** ⇒ 每条分支的节点是**各自新建**的（node_key 不同）⇒ **分支子图天然互不相交** ✓

⇒ 并行段 B 同构 ⇒ 也是不相交 ✓

⇒ **join 点不属于任何分支**：按入边计数定义（`GraphRunner:695` `pending.put(n.key(), graph.in(n.key()).size())`），join 的入边来自多条分支末端 ⇒ 它是汇合点，不是分支成员 ⇒ 切图时不能把 join 切进某条分支 ⇒ **这一点要在改造点 1 写明，否则"切子图"的实现会把 join 重复执行**。

⇒ **建议 E-16 的编译期检查再加两条**：

| # | 检查 | 理由 |
|---|---|---|
| a | 分支子图内**不得出现另一个 split/join** | 嵌套要显式递归处理，否则切图有歧义 |
| b | **join 点不得被切进任何分支** | 否则 join 会被执行多次（`run_node` 撞唯一键 + 流程重复推进） |

⇒ 另：**条件网关（包容）的分支可能共享下游节点**，但它不是 `SPLIT_PARALLEL` ⇒ `ParallelGroup` 不认它 ⇒ 不受影响 ✓（`ConditionalBranchTracker` 是另一套机制）。

### Q5 · 两分支同时写不同 key 真的安全？`LinkedHashMap` 换 `ConcurrentHashMap` 够不够？

**答：换 CHM **基本够**，但有三处必须配套改 —— 且 CHM 不会引入顺序问题（我核过没有代码遍历 `variables`）。**

**先排除一个担心**：**顺序语义无依赖**。我全仓搜了 `variables.entrySet/values/keySet/forEach` ⇒ **零命中**；`ConditionEvaluator.eval(expr, vars)`（`GraphRunner:1650`）走的是 `new Parser(src, vars)` ⇒ **按键 `get`，不遍历** ⇒ ⇒ **换 CHM 不会破坏任何依赖顺序的行为** ✓

**但三处必须配套**（否则 CHM 也不够）：

| # | 位置 | 问题 | 改法 |
|---|---|---|---|
| 1 | `GraphRunner:908` `variables.putAll(outs)` | CHM 的 `putAll` 是**逐个 put**，非原子 | **D3 已保证"不同分支写不同 key" ⇒ 写-写冲突不存在 ⇒ 实际不丢更新**；但要确认 `outs` 的 key 集合不重叠（D3 检查的是**流程变量 key**，不是节点输出 key）⇒ **建议 D3 的编译期检查扩展到"节点输出 key"** |
| 2 | `GraphRunner:177-188` `alreadyConsumed` | **读-改-删**（`get` → 比较 → `remove`）非原子 | 换成 CHM 的 `compute` / `remove(key, value)`（CAS 语义） |
| 3 | `GraphRunner:160-163` `writeVar` / `:196-199` `consumeVar` | `variables.put` + `externallyOwnedVars.contains` + `locallyWrittenVars.add/remove` 是**三步序列** | `externallyOwnedVars` / `locallyWrittenVars` 必须换 `ConcurrentHashMap.newKeySet()`；三步序列对**同一 key** 才需要原子（D3 已排除跨分支同 key）⇒ 同 key 时用 CHM 的原子 API 即可 |

⇒ **另外**：`done`（HashSet）、`visits`（HashMap，`:705`）⇒ `done` 换 `newKeySet()`；`visits` 用 CHM 的 `merge`（原子的）✓

⇒ ⇒ **结论：改造点 3 写"6 个字段换 CHM"是不够准确的**，应改成**分类清单**：

| 容器 | 处理 |
|---|---|
| `variables`（LinkedHashMap） | 换 CHM（无顺序依赖）+ 原子 API（`compute`/`merge`/`remove(k,v)`） |
| `consumedValues` | 换 CHM + `compute`（读-改-删） |
| `externallyOwnedVars` / `locallyWrittenVars` | 换 `newKeySet()` |
| `eventCursors`（`computeIfAbsent` + `put`） | 换 CHM（`computeIfAbsent`/`merge` 已是原子） |
| `visits`（`merge` 计数） | 换 CHM（`merge` 原子） |
| `done` | 换 `newKeySet()` |

⇒ ⚠ 并且 `progress.aborted()` 的可见性**不是"确认"就完事** ⇒ 它在主循环条件里（`:736`）⇒ 若非 volatile，**分支线程看不到停止信号** ⇒ D1 直接失效 ⇒ 必须显式改成 volatile/AtomicBoolean（上一轮已列，本轮仍只写"确认可见性"⇒ **建议直接定案**）。

### Q6 · 多实例：补 epoch 还是让设备锁走数据库？

**答：这不是二选一 —— 设备锁**已经在走数据库**了；而 R-11 的缺口**不是 epoch，是锁的粒度**。**

**先纠正选项本身**：设备锁的 DB 层就是条件更新 `device_state.current_run_id`（`DeviceLock.java:139` `tryAcquireDatabase`）⇒ **"让设备锁走数据库"这个选项不存在，它已经在走了。**

**真正的缺口是粒度**：`current_run_id` 是 **run 粒度** ⇒ **DB 层拦不住"同 run 的两个分支"** ⇒ 而真并发的定义就是"同 run 多分支同时跑" ⇒ ⇒ **多实例下，同一个 run 的两个分支若落在不同实例上，会同时持有同一台设备**（今天靠 JVM 分片锁挡住，跨实例就没了）。

⇒ ⇒ **R-11 的正解：把设备锁的持有者粒度从 `run` 细到 `(run, branch)`**（或加一个 `holder_token`）。

⇒ **成本很低**：表设计 v5 **已经引入了 `branch_id`**（`device_event_waiter.branch_id`、`operation_key` 的 `b{branch}`）⇒ ⇒ 设备锁的 owner 加一个分支维度是**顺水推舟**：

| 现在 | 建议 |
|---|---|
| `device_state.current_run_id` | 增加 `current_branch_id`（或 owner 串 `runId:branchId`） |
| 条件更新 `WHERE current_run_id IS NULL OR current_run_id = runId` | 加上 branch 比较：**同 run 不同 branch ⇒ 不算重入 ⇒ 必须拦** |

⇒ **epoch 与 R-11 正交，两件事要分开做**：

| 问题 | 解法 | 对应风险 |
|---|---|---|
| 旧实例在锁被接管后继续写状态（僵尸写） | **epoch** | 设计基线 R-02 |
| 同 run 两分支在多实例下不互斥 | **锁粒度加 branch** | R-11 |

⇒ ⇒ **不要用 epoch 代替粒度细化** —— epoch 解决不了"两个分支同时持有同一设备"，那正是 R-11 的内容。

⇒ ⚠ 而且 epoch **对设备锁仍然有用**（防旧实例在锁被新实例接管后把 `current_run_id` 清掉）⇒ ⇒ 多实例方案应是"**epoch + 锁粒度加 branch**"两件一起，不是二选一。

## 三、本轮新发现与需修正的旧结论
