## 1. 意见清单（按严重程度）

### P1-1 · 位置写入与自动确认不在同一事务（§8 Q2 坐实）

**现象**：`DriverStepExecutor.autoConfirmTransfer` 先调 `PositionLock.noteTransferMove`，
再调 `TransferTransaction.confirmByDeviceReport`，两者是**各自独立的 `Tx.inTransaction`**。
`noteTransferMove` 内部 `takePlate`（tx1）、`putPlate`（tx2）各自提交；`confirmByDeviceReport`（tx3）再提交。

**证据**：
- `PositionLock.java:309/386`：`putPlateInternal` / `takePlateInternal` 各自 `Tx.inTransaction`；
- `DriverStepExecutor.java:488-494`：`noteTransferMove` 成功后才 `confirmByDeviceReport`；
- `TransferTransaction.java:89-111`：confirm 内部 `selectConfirmableTransfer` + `markTransferConfirmedAuto` 又有一次 CAS。

**后果**：若 tx3 失败（事务已非 REPORTED/UNKNOWN、或板号不符），此时**位置已改、audit 已写**，
但 `transfer_transaction` 仍停留 REPORTED ⇒ 恢复门禁会拦、且「位置说板已到 target、事务说未确认」自相矛盾。
虽然单 run 单线程下 tx3 失败窗口极窄，但这不是「不可能」，是「没有原子性保证」。

**处置建议**（二选一，需拍板）：
- A. 接受窄窗口 + 在 `confirmByDeviceReport` 失败分支补**补偿**（把 audit 记一条 `note='自动确认失败待人工'` 并显式告警，不静默）；
- B. 把 confirm 与位置写入合并进同一外层事务（改动较大，需评估 `markPlateOutsideTx` 的独立连接设计是否还能成立）。

### P1-2 · D8 兜底形成安全缺口（§8 Q3 坐实，且比材料包描述更宽）

**现象**：选位 SQL `LEFT JOIN device_point dp ... dp.id IS NULL` 兜底，意味着**未配置的 2563 个老点位
绕过 `is_entry/is_exit/robot_reachable` 过滤**，仍按 `parent_id` 参与选位。

**证据**：`DeviceStateMapper.xml` 两个选位 SQL（`selectFirstAvailablePosition` /
`selectFirstOccupiedPosition`）+ 材料包 §5 D8、设计文档 §3.5。

**后果**：只要流程里出现一台「挂了老点位、但没配 `device_point`」的设备，选位就可能选到
机械臂不可达 / 角色不对的点位。当前 20 节点用测试岛 13 个已配置点位所以没踩到，
但**全库 250 台设备、2563 个老点位**是敞口。

**处置建议**：老点位归属对账（-03 报告 §5）做完前，把兜底从「无条件放行」收紧为
「仅测试岛或显式白名单放行」；或至少在选中兜底点位时打 WARN 并计入 `position_evidence.note`。

### P2-1 · 评审指引.md 的 🔴「putPlate 不落库」未回填

**现象**：`docs/评审指引.md` §六 把「`putPlate` 不落库」列为**未解决**的 🔴 严重问题。
本轮 `PositionLock.putPlate` 已改为 `putPlateInternal`（UPSERT）+ `markPlateOutsideTx`（独立连接），

与材料包「已闭环」冲突。违反 `评审规范.md` §六.3「修正被指出错误的文档」。

**处置**：评审指引.md §六 该条改为「已修复（2026-11-13），UPSERT + 独立连接写 plate 冗余表」。

### P2-2 · 快照膨胀无保留策略（§8 Q7）

每 run `run_position_snapshot` 全库 2576 行 append-only，累计 5152。无裁剪/保留策略，
无性能评估。`insertRunPositionSnapshot` 在 run 启动关键路径上（虽写失败只告警）。
**处置**：定保留策略（按 run 保留 / 按时间归档），并在快照表加 `taken_at` 分区或定期清理说明。

### P2-3 · 源通道方向 "out" 零验证（§8 Q9）

`TransferPlan.java:134` 源通道 `"in" → "out"`，但测试岛 13 台 `device_port=0`，
`hasPorts` 兜底直接跳过 ⇒ 这条改动**从未真正执行**。材料包 D10 诚实标注了这一点。
**处置**：补 `device_port` 数据后单独回归，否则「方向已修正」只能算「代码改了、行为未验证」。

### P2-4 · 扫码关联取「第一个有板点位」（§8 Q8）

`confirmScanAtDevice` 用 `selectPlateIdOnDevice` 取设备下**第一个**有板点位。
多点位设备（如 ID-X229 4 个层位）若同时放多块板，扫码会关联错板。
当前 20 节点流程 ReadBarcode 在第 1 节点（无板）所以没触发，属潜伏。
**处置**：多点位设备扫码需定位到具体点位，或至少在关联前校验「设备下只有一块板」。

### P2-5 · insertPlateIfAbsent 并发窗口

`insertPlateIfAbsent` 用 `WHERE NOT EXISTS`（`DeviceStateMapper.xml:393-402`），
**不是** `ON CONFLICT DO NOTHING`。两个并发 TMP- 板同 barcode 时（TMP 号含 pointId 理论上唯一，
但 `uk_plate_barcode` 仍可能被非 TMP 路径撞），会抛唯一约束异常；
被 `markPlateOutsideTx` 的 catch 吞掉后，**alias 也一并丢失**（alias 在 putPlate 里、异常在它之前已提交？需复核顺序）。
**处置**：改为 `ON CONFLICT DO NOTHING`，与 `insertPlateAlias` 一致。

### P3-1 · 文档口径漂移：2569 vs 2576

设计文档 §0/§1.1 写「2569 个点位」，§9 验收写「2576 行（2569+新建 7）」；
材料包 §3 写「全库点位 2576」；-03 报告 §0 写「2576，其中 2563 迁移」。四处分 2569/2576/2563 三个数，
虽能靠「新建 7 前后」自圆其说，但跨文档漂移易误导。
**处置**：统一为「2563 迁移 + 6 基线 = 2569（本轮前）；+ 7 新建 = 2576（本轮后）」。

### P3-2 · autoConfirmWfCache 缓存 0 的边界

`autoConfirmWfCache` 是 `volatile Long`，`workflowIdOfRun()` 异常/无 run 返回 0 后，
0 会被缓存（判断是 `wf == null` 而非 `wf == 0`），后续该 run 都判「关闭」。
因为 DriverStepExecutor 是 per-run（构造带 runId），无跨 run 串扰；且「关」是 fail-safe 方向，
所以**不是 bug**，但注释未说明这个边界。
**处置**：补一行注释或改为「只在 >0 时缓存」。

### P3-3 · 交接稿 §5 正文未回改

材料包 §2 指引「读 §5.1 而非 §5」。已核实 `-02` 交接稿确有 §5.1 追加纠正，但 §5 **正文**
仍是旧根因（归给 `resolvePlateId`），只在 §5.1 追加纠正、未回改 §5。
按 `评审规范.md` §四「修正文档，不留过时描述」，§5 正文应在开头加「⚠️ 已过时，见 §5.1」。
**处置**：§5 标题下加一行过时标注即可，不必重写。
