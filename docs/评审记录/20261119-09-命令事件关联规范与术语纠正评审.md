## 一、术语纠正：依据成立，但目标名可以再定

### 1.1 三条依据逐条核验

| 依据 | 核对 | 判定 |
|---|---|---|
| 类型对不上 | `device_event.process_id VARCHAR(128)`（schema `:4975`、migration `:13/:23`）vs `experiment_process.id` identity BIGINT（schema `:1355-1358`、`:530`） | ✅ **成立** |
| 协议契约原话 | `docs/设备事件协议契约.md:57`："`processId` / `interactionStep` \| 否 \| 后续精确工位/交互步骤匹配使用，本阶段只保存" | ✅ **原话属实**，但它说的是"**工位**/交互步骤"，不是"设备程序名" |
| 混名后果 | ✅ 成立 | |

⇒ **"现有 `process_id` 列装的不是实验编排节点"这个结论正确。改名必要。**

### 1.2 但目标名 `funcName` 与唯一权威定义对不上

**关键事实**：`device_event.process_id` **没有列级 COMMENT**（核过：schema 里只有 `source_event_id`（`:4990`）与 `dispatched_at` 有 COMMENT）⇒ **这一列在库里的语义没有任何权威定义**，唯一来源是协议契约 §57。

⇒ 而协议契约 §57 说的是"**工位**/交互步骤匹配" ⇒ **"工位" ≠ "设备程序名（P1 / Centrifuge3000）"**。

而且**当前没有任何生产者填这一列**：

- 侧车无引用（`sidecar-dotnet/` grep 无 `processId`）；
- `Protocol.cs` 只构造 `SpontaneousFrame(equipmentId, eventType, payload)`；
- 前端无引用（`webapp/` grep 无命中）；

⇒ 生产库里这一列**应当全是 NULL**（除非有外部方在发）。

**⇒ 三点结论**：

1. **改名必要** ✓（名字误导，必须去掉）；
2. **目标名证据不足**：`funcName`（设备程序名）、`stationCode`（工位码）、`programCode` 三者都说得通，**需要业务确认**（归入 H-03 那类"代码看不出"的待确认）；
3. **RENAME 保留数据的价值为零**（该列从没被写过）⇒ 更干净的做法是：旧列改名成 `legacy_process_id` 或直接 DROP，新列用明确语义的名字。**不要用 RENAME 把一个猜测固化成列名。**

### 1.3 但这场命名之争**不影响归属**，优先级可降

规范 §2.1 写"**归属只认 `commandId`**" —— **这是本轮最重要、也最正确的一个决策**。

⇒ 因为 `funcName` / `processId` 无论叫什么，都**不是归属键** ⇒ 命名定不下来，**不阻塞事件归属方案的落地**。

⇒ 建议：**命名归入待确认（P1，不阻塞），归属逻辑与 API 兼容（P0，阻塞）**。

## 二、三个阻断项

### P0-1 · §4.3 的匹配 SQL 与 §7 的规则文本互相矛盾 ⇒ "精确等待"会被"无归属迟到事件"串上 ⭐

**位置**：规范 §4.3（SQL）vs §7.1 / §7.2（规则文本）

**规范 §4.3 写的**：

```sql
AND (e.command_id IS NULL
     OR e.command_id = #{expectedCommandId})
```

**规范 §7 写的**：

- §7.1 强匹配：`事件.commandId == waiter.expect_command_id` → 强匹配
- §7.2 弱匹配：`事件无 commandId` → **仅当该设备 + 该事件类型下只有一个 WAITING waiter 时允许**
- §7.3：事件有 commandId 但无 waiter 声明该 id → UNATTRIBUTED

**⇒ SQL 与文本不是一回事。** 按 SQL 的写法：

| 场景 | 事件 | waiter | SQL 结果 | 规则文本应该是 | 判定 |
|---|---|---|---|---|---|
| 精确 waiter 被无归属事件污染 | `command_id = NULL` | `expect='cmd-1'` | **匹配**（第一分支为真） | 不该匹配（事件无 id ⇒ 属弱匹配域） | ❌ **串** |
| 弱 waiter 被带 id 的事件污染 | `command_id='cmd-2'` | `expect=NULL` | `e.command_id IS NULL`=假、`e.command_id = NULL`=NULL ⇒ 整体 NULL ⇒ **不匹配** | §7.3 说不匹配 ✓ | ✅ 一致 |
| 精确 waiter 遇到别人的事件 | `command_id='cmd-2'` | `expect='cmd-1'` | 不匹配 ✓ | 不匹配 ✓ | ✅ 一致 |

⇒ **第一行是真漏洞**：一个**声明了精确期望**的 waiter，会被一个**不带 commandId 的迟到事件**匹配上 —— 而"弱匹配是串板的主要来源"恰恰是规范 §7.2 自己承认的（"弱匹配默认关闭"）。

⇒ 后果：**弱匹配绕过"默认关闭"的开关，只因为 waiter 声明了精确期望** ⇒ 一个本该被挡住的无归属事件，把精确等待的流程推进了。

**正确 SQL（两类 waiter 互不串扰）**：

```sql
AND ( (#{expectedCommandId} IS NOT NULL AND e.command_id = #{expectedCommandId})
   OR (#{expectedCommandId} IS NULL     AND e.command_id IS NULL) )
```

即：**声明了期望 ⇒ 只认精确事件；没声明 ⇒ 只认无 id 事件（且仍受 §7.2 的"唯一 waiter"约束）**。

⇒ 验收补一条：**W-14：waiter 声明 `expect_command_id='cmd-1'`，到达一个 `command_id IS NULL` 的事件 ⇒ 不匹配，事件进 UNATTRIBUTED，waiter 保持 WAITING**。

### P0-2 · `expect_command_id` 的填充来源缺失 ⇒ 全部退化为弱匹配 ⇒ 归属不可用 ⭐

**位置**：规范 §4.4

§4.4 写："由等待节点声明：如果该事件应该由某条命令触发，就写入该命令的 `commandId`。"

**问题**：`commandId` 是**中控自己生成的动态串**（`r{run}-n{node}-e{exec}-s{step}-d{device}`，`DriverStepExecutor:1474-1478`）⇒ 含 run id 与递增的 exec ⇒ **人工在流程图里填这个字符串不可行**（也不该让用户填）。

⇒ 而 `__awaitEvent` 是**独立内置节点**（`GraphRunner:1068-1070`），它**不知道**"本 run 最近给这台设备发过哪条命令"，除非中控自己去查。

⇒ **唯一可行路径（规范必须写明）**：**中控在 `__awaitEvent` 执行时自动填** —— 从 `command_ledger` 查"本 run + 该 device + 最近一条未结算命令"的 `command_id`。

⇒ 但这条路本身有歧义：设备先执行 A 命令、再执行 B 命令，**迟到的 A 事件**到达时，"最近一条命令"是 B ⇒ 归属错 ⇒ ⇒ **只有设备回显 commandId 才能真正消歧** ⇒ ⇒ **§5 的"侧车必须回显 commandId"是归属可用的前提，不是可选增强**。

⇒ ⇒ **不补这条，`expect_command_id` 永远为 NULL ⇒ 全部落到 §7.2 的弱匹配 ⇒ 而弱匹配默认关闭 ⇒ 事件归属完全不可用。**

⇒ 这与上一轮的 N-G 是**同一类问题的换名版**：上一轮是"精匹配缺期望值来源（`expect_process_id` / `expect_interaction`）"，这一轮换成 `expect_command_id`，**来源问题原封不动**。

⇒ 建议规范补一条 §4.5："**`expect_command_id` 的三个候选来源与取舍**"：

1. 流程图显式配置（**不可行**，id 动态）⇒ 否决；
2. 中控自动取"最近一条命令"（可行，但有迟到歧义）；
3. **设备回显（唯一无歧义）⇒ 列为协议准入硬要求**。

### P0-3 · API body 字段改名是**对外契约的破坏性变更**，且失败是**静默**的 ⭐

**位置**：规范 §4.2

§4.2 的代码：

```java
String funcName  = trimmed(ApiServer.jsonField(body, "funcName"));   // 原 processId
Long   processId = ApiServer.jsonLong(body, "processId");            // 实验编排节点 id
```

**核对 `ApiServer.jsonLong`（`:331-338`）**：

```java
Pattern.compile("\"" + key + "\"\\s*:\\s*\"?(-?\\d+)\"?").matcher(body);
return m.find() ? Long.valueOf(m.group(1)) : null;
```

⇒ **只匹配数字** ⇒ 两种旧客户端行为：

| 旧客户端发 | 新代码结果 | 危害 |
|---|---|---|
| `"processId": "P1"`（设备程序名，字符串） | 正则不匹配 ⇒ **返回 null，静默丢弃** | 设备程序名丢失，外部方**无任何报错** ⇒ 难以发现 |
| `"processId": "123"`（设备程序名恰好是数字） | **被解析成实验编排节点 id = 123** | **静默错值** ⇒ 可能指向完全无关的实验节点 |

⇒ 而 `funcName` 是**新字段名** ⇒ 旧客户端根本不会发 ⇒ ⇒ **必须双读兼容**。

⇒ **必须补的三件事**：

| # | 动作 | 说明 |
|---|---|---|
| 1 | **一个版本的兼容期** | 同时接受 `funcName`（新）与 `processId`（旧）；按**内容形状**区分：纯数字 ⇒ 编排节点 id，否则 ⇒ 设备程序名（落到 `legacy_process_id`）。兼容期结束再删旧字段 |
| 2 | **对外公告 + 版本号** | 这是 `POST /api/device-events` 的字段名 + 类型双重变更 ⇒ 属于破坏性变更，需要在协议文档里标注版本与迁移期 |
| 3 | **别把"没读到"当"没有"** | 兼容期内的解析失败要有 WARN 日志（现在 `jsonLong` 静默返回 null ⇒ 外部方发错格式完全无痕） |
