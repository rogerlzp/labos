### C-01 确认（无动作）

### C-02 数据库终态不变量（P1）
- **结论**：**接受**。
- **理由**：接口层"恰好一个返回成功"不等于库内只有一条 active；尤其在"准入成功后应用层崩溃"这类场景，只有查库能发现。
- **处置**：并入 04 任务卡，建议新增：
  - 不变量语句：`SELECT COUNT(*) FROM run WHERE tenant_id=? AND workflow_id=? AND deleted_at IS NULL AND status::text IN (<StatusVocabulary 中 active=true 的集合>)`，终态必须 `≤ 1`；
  - 该断言作为 T11 / T20 / T25 / T26 的**统一收尾断言**，而不是新增独立用例（避免矩阵膨胀）；
  - 明确 active 集合必须来自 `StatusVocabulary`（当前为 `queued/running/paused/quarantined`），不得在 SQL 里手写字符串。
- **验证**：任一竞争用例结束后自动执行该计数，非 `≤1` 即整项 FAIL。
- **保持 UNKNOWN**：多实例测试环境缺失时，该断言仅在单实例范围有效，不得外推。

### C-03 resume/resume（P1）
- **结论**：**接受，并建议扩展为两类场景**。
- **理由**：原文提到"两个 recoverable Run"；核对后还有一个更硬的同类问题——`WorkflowService.resumeAsync` 的互斥依赖 `ACTIVE_RUN_WORKERS`（JVM 内 `static ConcurrentMap`），跨实例对**同一 Run** 的重复 resume 不在任何 JVM 锁保护内。
- **处置**：建议新增 **G01-T29**，拆两个子项：
  - T29a：同一 Run 在两个实例/两连接同时 resume → 最多一个 worker，DB 终态 active ≤ 1；
  - T29b：两个不同 recoverable Run（A paused、B failed/recoverable）同时 resume → 最多一个成功，另一个 `DENY_ACTIVE`，败者 Run 保持原状态。
- **验证**：两子项均需附"旧实现（或未加数据库协调前）可复现双 active"的失败证据，否则视为测试无效。
- **保持 UNKNOWN**：若领域模型决定"允许同流程多个 recoverable Run 并存"，则 T29b 的预期结果必须重写，在此之前不得判 PASS。

### C-04 commit outcome unknown（P1）
- **结论**：**接受**。
- **理由**：`DENY_UNKNOWN` 表达"我没做成决定"；`COMMIT_UNKNOWN` 表达"我做了，但不知道成没成"。后者若被当作前者，调用方会认为"库里一定没有新 Run"而重试，正是重复创建的根因。
- **处置**：建议在 §3.2 增一行：
  | 场景 | 决策 | 稳定错误语义 |
  |---|---|---|
  | 事务提交结果未知（连接在 COMMIT 阶段中断等） | `DENY_UNKNOWN` + **mutation 待对账** | `EC-WORKFLOW-GATE-COMMIT-UNKNOWN` |
  并在 §3.5 明确：该状态下**禁止自动重试**，必须先按 `(tenant, workflow, 时间窗)` 对账是否存在新 Run，再决定是否允许再次准入。
- **验证**：T24d 的预期结果改为"返回 `COMMIT-UNKNOWN`；不自动重试；对账能确定是否存在新 Run"。
- **保持 UNKNOWN**：对账无法确定时，该 `(tenant, workflow)` 应保持"拒绝新准入"直到人工确认，不得默认放行。
