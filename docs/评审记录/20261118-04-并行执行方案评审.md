## 一、总体结论

方案的**问题定义和资源驱动的判据是对的**，而且和系统既有演进方向一致（`docs/多实验并行调度-设计.md` §1.2 已写明"岛锁过粗"的结论）。文档用 `[事实]/[设计]/[未定]` 四级标注、结尾列 7 个问题给评审，方法上是对的。

但有三个问题会直接影响实施：

1. **§3 的并行模型在代码里已经存在**。`ExperimentScheduler`（`labos-kernel/src/main/java/com/labos/kernel/workflow/ExperimentScheduler.java`）的类注释就是"实验调度器：多实验并行的唯一入口"，它已经实现了队列、优先级、并行度上限、资源级准入、扣留门禁、重启对账阻断。按 §8 的五步实施，会造出**第二套调度器**。
2. **§5.1 改错了地方**。真正卡住"同实验多批并行"的既不是流程门禁也不是唯一索引，而是 `BatchOrchestrator.createNextBatchAttempt` 里"同一实验同时只允许一条批次 run"的**实验级串行化逻辑 + `SELECT ... FOR UPDATE` 锁实验行**。只加唯一索引不删这段逻辑，并行跑不起来；删了这段逻辑不加别的保护，重复提交会建出两条同批尝试。
3. **§4 的"持设备锁才能消费事件"在现有结构下不可行**。设备锁是 **step 粒度**（`onStepStart` 抢、`onStepDone`/`onStepAborted` 放），而 `__awaitEvent` 是 `GraphRunner` 内置节点、不经过 step 生命周期 —— 它根本没有锁可持。若在等待期间额外持锁，会把设备整段独占，与 §3.3 追求的利用率目标直接冲突。文档 §4.3 第一行标了 `[待确认]`，但这个"待确认"的答案是"确认就是这样"，且结论比文档设想的严重。

另有一批事实性错误（优先级字段与方向、线程池归属、岛锁表述、环境变量重复、状态码不存在等），详见第三节。

### F-01 · §3 与已上线的 `ExperimentScheduler` 高度重复，方案把存量当增量

**位置**：§3 全节（3.1/3.3/3.4/3.5）、§8 第 2 步与第 5 步

**核对**（`ExperimentScheduler.java`）：

| 文档 §3 的设计 | 代码现状 |
|---|---|
| §3.1 待执行队列 | `:168` `private final List<Queued> queue`；`:72-74` `Queued` 记录 |
| §3.4 优先级 + 同级 FIFO | `:138-141` `QUEUE_ORDER` = deadline ASC → **priority DESC** → submittedAt ASC；`:733-741` `sortByOptimization` 连续优化因子 |
| §3.5 并行度上限（全局/每实验/物理资源） | `:52` `MAX_CONCURRENT = 4`；`:211` `maxConcurrent` 可变；`:311-314` 从 `schedule_plan.max_iterations_running` 热加载 |
| §3.3 可执行 = 资源不冲突 | `:750-758` **资源级准入（2026-11-10，取代岛锁）**：`requiredResources(experimentId)` + `tryHoldResources(need, experimentRunId)`，注释原文"需要的资源没被别的实验占着 ⇒ 可以开跑（**同岛也可以并行**）；有冲突 ⇒ 留在队列里等" |
| §6 现场扣留门禁 | `:743-748` `RuntimeHold.coveringForExperiment`；UNKNOWN ⇒ `:744-746` **整轮不派发（fail-closed）** |
| §3.5 物理可用资源数 | `:159-162` 资源集由 `DeviceLock`/`PositionLock`/板子归属推导 |

**更关键的口径冲突**：文档 §7 说"并行度按 run 计，不按 experiment_run 计"，而现有调度单元**就是 `experiment_run`**（`Queued.experimentRunId`）。文档与现状在这一点上方向相反。

**建议**：§3 不应重写，应改写成"**在 `ExperimentScheduler` 现有资源级准入之上，额外放开同实验多批并行**"。即把方案缩小成两件事：
- (a) 放开实验级批次串行化（见 F-02）；
- (b) 解决同设备事件归属（见 F-03）。
§3.4/§3.5 的优先级与并行度**直接复用现有实现，不重写**，只在 §3.5 补一句"每实验上限"是新增维度。

### F-02 · §5.1 改错了层级：真正的拦路虎是实验级串行化逻辑，不是唯一索引

**位置**：§5.1、§9 P-09、§8 第 4 步

**核对**（`BatchOrchestrator.java:556-624`）：

```java
// createNextBatchAttempt()，事务内 lockExperimentRow(c, experimentId) 之后
ActiveAttempt active = activeBatchAttempt(c, experimentId);
if (active != null) {
    return new NextBatchAttempt(NextBatchOutcome.EXISTING, ...);   // :591-597
}
```

- `:688-690` `lockExperimentRow` = `SELECT experiment ... FOR UPDATE`（注释："判定'同实验是否已有批次 run 在队列/执行'是实验级不变量，只锁某一批挡不住两个请求同时给不同批建单"）
- `:695-705` `activeBatchAttempt` 查该实验下 `status IN (queued/running/paused)` 的批次 run
- 类注释 D3 明写："**批次串行**"；`experiment_batch_run` 表注释也写"批次之间串行（D7）"

**这是应用层的显式不变量 + 行锁，不是数据库约束。** 文档 §5.1 提出的唯一索引 `(tenant_id, batch_id, active_slot)` 只解决"同一批不能有两条活跃尝试"，**完全不触及"同一实验只能有一条活跃批次 run"**。结论：

- 按文档实施 ⇒ `createNextBatchAttempt` 永远返回 `EXISTING`，并行批**根本建不出来**；
- 删掉那段逻辑但不加替代 ⇒ 重复 `POST /run?async=1` 会同时建出两条同批尝试，破坏 §9 P-09 的幂等要求。

**建议**：§5.1 重写为两层，各自给出**代码级**改法：
1. **实验级**：把"同实验仅一条活跃批次 run"从"应用层判断"改为"**允许 N 条，但按 batch_no 顺序各建一条**"，或改为"允许 N 条活跃 + 保留一个建单串行点（锁实验行只用于建单，不用于限制活跃数）"。
2. **批次级**：唯一索引按文档思路加，但**状态源必须用 `experiment_run.status` 而不是 `experiment_batch_run.status`**（见 X-05）。

### F-03 · §4 的"持设备锁才能消费事件"不可行；已有更简洁的实现路径

**位置**：§4.2、§4.3 表格第一行、§10.5、§11 第 1 问

**核对（设备锁粒度）**：
- `WorkflowService.java:3091-3110`：`onStepStart` 里 `DeviceLock.acquireWithWait(resNodeId, runId, waitMs)`，抢不到就等，预算按设备登记方法超时上限（**下限 60 秒、上限 15 分钟**），等不到抛 `IllegalStateException`。
- `WorkflowService.java:3142-3154 / 3169-3181`：`onStepDone` / `onStepAborted` 里 `DeviceLock.release(...)`。
- ⇒ **设备锁的持有期 = 一个 step。**
- `GraphRunner.java:319-325 / 1068-1070 / 1215+`：`__awaitEvent` 是内置节点，由 `executeBuiltin` 直接调用 `waitForDeviceEvent`，**不经过 `DriverStepExecutor` 的 step 生命周期**。

**结论**：`__awaitEvent` 期间**没有设备锁可持**。若为了 §4.2 而在等待前后额外抢一把设备锁并跨越等待持有，则该设备在等待全程被独占（孵育场景可达 30 分钟），**设备利用率从"逐步抢放"退化成"整段独占"**，与 §3.3 的核心取舍直接矛盾。且 `device_state.current_run_id` 是 run 粒度语义，"当前持有者是谁"需要额外查询，未必比事件归属更便宜。

**已有更简洁的路径**（文档漏掉了）：
- `device_event_consumption` 表**已经记录 run_id**：`event_id BIGINT PRIMARY KEY, tenant_id, run_id, node_key, loop_index`（`pg_rebuild/schema/90_all_in_one.sql:5013-5016`）。
- `DeviceEventMapper.xml:65-100` 的 `claimEvent` CTE：候选选择条件是 `(tenant_id, device_code, event_type) + id > afterId + dispatched_at IS NULL + NOT EXISTS consumption`，**没有 run_id 过滤**；`run_id` 只用在 `existing`（崩溃重入）和 INSERT 上。
- `device_event` 表已有 `process_id` / `interaction_step` 字段（`:4975-4976`）。

⇒ **最小改法是给候选集加归属维度**（按 run/板/工位过滤），而不是让等待者持锁。这样"一个物理事件只消费一次"的语义不变，也不会把设备锁的粒度搞乱。文档 §4.3 的"payload 里记录板号/批次"其实就接近这个方向，但没有把它提升为主方案，且 §4.4 把"广播"否掉时误以为只剩"持锁"一条路。

**建议**：§4 改为两案并列 —— **A案（推荐）事件侧加归属**：`__awaitEvent` 支持可选的归属过滤（run/板/工位），`claimEvent` 候选加 `AND (e.run_id = #{runId} OR e.run_id IS NULL)` 之类的条件（具体语义随设备上报能力定）；**B案 持有者校验**：保留文档思路，但明确"持有者"是**设备锁持有者**或**板归属**，并说明它必须跨 step 持锁，从而接受设备被独占的代价。§11 第 1 问的答案应是"A 案更简洁"。

## 五、方案层面的设计问题（4 条）

**D-01 · §8 第 1 步"纯重构、行为不变"不成立。**
当前 `POST /experiments/{id}/run` 返回 `RunAllResult(batched, experimentRunId, status, totalSteps, doneSteps, error, batchSplit, batches)`，其中 `totalSteps/doneSteps/batches` 是**跑完才有值**的。改成"提交+异步"后这些字段必然为空 ⇒ **HTTP 响应体语义变化 = 行为变化**，前端要适配。文档把它归为"纯重构、行为完全不变、地基"，这个定位会让实施者低估风险。
建议：① 明确写成"新增 async 端点或 `?async=1` 分支，不改现有 sync 端点"；② 或把第 1 步的验收写成"sync 路径响应体逐字段不变 + async 路径新增字段"。另注：**async 路径其实已经存在**（`createNextBatchAttempt` + `ExperimentScheduler.continueNextBatch`，`BatchOrchestrator.java:556` / `ExperimentScheduler.java:878`），第 1 步的真实内容只是"把 sync 路径也接进调度器"。

**D-02 · §6 的"人工停止"一行把问题问偏了。**
现有语义已经回答了这个问题：`ExperimentScheduler.continueNextBatch`（`:863-871`）明确"**aborted / paused 不继续**：人工停止后剩余批保持 pending，不自动重跑"。所以 §6 应直接写清"沿用现有口径"，而不是留作待裁决。

**D-03 · §10.1 的死锁风险被高估、但死锁来源被漏掉。**
- 已有的缓解是有效的：`PositionLock.java:246` 明确"按 resource_id 升序申请——消除循环等待"（文档 §10.1 这条 `[事实]` **核对通过**）。
- 但真正的循环等待来源不是点位锁，而是**设备锁 + 点位锁 + 轨道分区锁跨层混拿**（`DeviceLock` 在 step 粒度、`PositionLock` 在搬运粒度、`RailZoneGuard` 在路径粒度）。文档把三者的申请顺序当成同一个顺序，没有给出跨层的统一排序规则 ⇒ 等待图检环即使实现了，也需要"跨层全序"这个前提才有意义。
- 建议：§10.1 的问题改成"**三类锁是否需要统一的全序申请顺序**"，这比"要不要先实现等待图"更可执行。

**D-04 · §9 缺三个场景。**
建议补：
- **P-13 并发提交同一实验两次**（两个 `POST /run` 同时打）—— 现有 `lockExperimentRow` 保护，改并行后必须重新验证（F-02 的直接后果）。
- **P-14 审计**：事件消费表里每个事件归属到哪个 run/node；并行下不能出现"事件归属错 run"。
- **P-15 重启后恢复**：进程重启时正有 N 批并行在跑，R5 对账未完成前**不得派发**，对账完成后是否恢复并行。

## 六、对 §11 七个问题的答复

| # | 问题 | 答复 |
|---|---|---|
| 1 | §4 "持锁才能消费事件"是否足够避免死等？有没有更简洁的做法？ | **不够，且不可行**（F-03）。更简洁的是**事件侧加归属维度**：`device_event_consumption` 已有 run_id，`device_event` 已有 `process_id`/`interaction_step`，`claimEvent` 加归属过滤即可，保持"全局一次消费"语义不变，也不打乱设备锁的 step 粒度 |
| 2 | §5.2 三选项选哪个？ | **C，但复用现有开关**（X-04）。理由：`WorkflowRunGate` 的 javadoc 已记录两条实测理由（事件抢消费 + 机械臂唯一资源），保留一个可运维的开关比硬删安全；开关名用现有的 `LABOS_WORKFLOW_CONCURRENT_RUN=allow` |
| 3 | 逐节点抢放 vs 一次性占全？ | **逐节点抢放**，与现状一致（`DeviceLock` 已是 step 粒度）。但代价要写清：跨层锁序（D-03）+ 设备锁等待预算 60s~15min（`WorkflowService.java:3094`），等不到会抛异常转 failed 而不是排队 |
| 4 | 是否必须先实现等待图检环才能开并行？ | **不必作为前置**，但必须先定"三类锁的统一申请顺序"。等待图检环是**观测手段**，不是开并行的前置条件；顺序规则才是。现有 `PositionLock` 升序申请只覆盖点位锁 |
| 5 | 事件归属实现在哪一层最干净？ | **不在 `GraphRunner` 也不在 `StepSink`，在事件认领层**（`DeviceEventMapper.claimEvent` + `DeviceEventSource`）。理由：归属是"事件 → run"的映射问题，在认领 SQL 里做最自然，且已有一半字段；放在 `GraphRunner` 里则要跨层查设备锁，破坏 step 粒度 |
| 6 | §9 十二个场景是否有遗漏？ | 有，补 P-13/P-14/P-15（D-04）。特别是"两个实验共用设备+点位"—— 现有 `ExperimentScheduler` 的 `requiredResources` + `tryHoldResources` 已覆盖**派发前粗筛**，但 §3.3 说"无需改"要补一句：**粗筛不替代运行时互斥**，运行时仍靠 `DeviceLock`/`PositionLock`/`RailZoneGuard` |
| 7 | 是否遗漏某条现有约束？ | 是，6 条见第四节（M-01~M-06）。最要紧的是 **M-06 机械臂吞吐实测** —— 它直接推翻 §1.2 与 §9 P-01/P-02 |
