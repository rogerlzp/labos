## 二、阻断项

### F-01 · `quarantined` 的 run 恢复不了：P0 的 SQL 守卫对它是死代码

**位置**：总纲 §3.0.1、⑥ §5.1、④ v2 §4.5

**核对链路**（`PauseMapper.xml` + `PauseManager.resumeTx`）：

```xml
<!-- PauseMapper.xml:14-17 -->
<select id="selectPauseKind" resultType="java.lang.String">
  SELECT pause_kind FROM run
   WHERE tenant_id = #{param1} AND id = #{param2} AND status = 'paused'
</select>

<!-- PauseMapper.xml:19-25 -->
<select id="isCrashRecoverable" resultType="boolean">
  SELECT EXISTS(
    SELECT 1 FROM run
     WHERE tenant_id = #{param1} AND id = #{param2}
       AND status = 'failed'
       AND (input->>'recoverable')::boolean IS TRUE)
</select>
```

```java
// PauseManager.resumeTx:512-520
String kind = pauseKindOfTx(c, runId);
if (kind == null) {
    crashed = isCrashRecoverableTx(c, runId);
    if (!crashed) {
        return new ResumeResult(false, "该执行不在暂停状态", runId, action.name(), 0);
    }
}
```

⇒ 对一个 `status='quarantined'` 的 run：

1. `selectPauseKind` 的 WHERE 含 `status='paused'` ⇒ **返回 null**；
2. `kind == null` ⇒ 走 `isCrashRecoverableTx` ⇒ 它的 WHERE 含 `status='failed'` ⇒ **false**；
3. ⇒ `resumeTx` **返回"该执行不在暂停状态"并提前退出**，**根本不会调用 `resumeToQueued`**。

⇒ 所以总纲 §3.0.1 提的 `AND status IN ('paused','failed','quarantined')`：

- 对 `paused` ✅ 有效；
- 对 `failed` ✅ 有效（`isCrashRecoverable` 已放行）；
- 对 **`quarantined` ❌ 是死代码**——`resumeToQueued` 永远不会被调用到这一行。

**这是三份文档共同的缺口**（总纲 §3.0.1、⑥ §5.1、以及我上一轮改的 ④ v2 §4.5）——我上一轮只加了 SQL 守卫的 `quarantined`，没意识到服务层判定会先拦掉，**这一条我认**。

**修法（二选一，必须同时改 SQL 与服务层判定）**：

| 方案 | 改动 | 说明 |
|---|---|---|
| **A（推荐）** | `isCrashRecoverable` 的 WHERE 改为 `status IN ('failed','quarantined') AND (input->>'recoverable')::boolean IS TRUE`；`quarantined` 的 run 在被隔离时置 `input.recoverable=true` | 语义最准：**"隔离待确认"本来就是"可人工恢复"的状态**，`quarantined` 与 `failed`+recoverable 本质同类 |
| B | `pauseKindOfTx` 的 WHERE 去掉 `status='paused'`，改为按 `status IN ('paused','quarantined')` 取 `pause_kind` | 改动面小，但会让 `pause_kind` 的语义从"暂停类型"变成"暂停或隔离类型"，与 `experiment_run.pause_kind` 的同口径约定冲突 |

⇒ 无论选哪个，**验收要补一条**：R-09 现在只验"completed 被拒"，要加"**quarantined 能被恢复**"。

**并且**：⑥ §2 D-04 说的"实验级暂停不改 run 状态"、H-12 建议"实验暂停时 run 也标 paused"——一旦 run 被标成 `paused`（而不是 `quarantined`），走的是 `selectPauseKind` 那条路，不受本条影响。**两条路径要分开看**：隔离（quarantined）是**系统判定的物理未知**，实验暂停是**人工请求的等待**。总纲把两者混在一句"状态守卫"里，容易漏。

## 三、需要修订的其他问题

### N-01 · D-01 的定性偏重：completed 的 run 在正常路径上**resume 不了**

**位置**：⑥ §2 D-01、总纲 §0 一页纸"最紧急的一行"

⑥ 写："后果：**已完成（completed）的 run 也能被改成 queued**，重新跑一遍。"

**核对**（`PauseManager.resumeTx:512-520`，同上 F-01 的链路）：completed 的 run ⇒ `pause_kind` 为 null（settle 已清空）⇒ `kind == null` ⇒ `isCrashRecoverableTx` 要求 `status='failed'` ⇒ **false** ⇒ 返回"该执行不在暂停状态"，**不会调用 `resumeToQueued`**。

⇒ **"completed 的 run 能被 resume" 在正常调用路径上不可达。** 真正的缺口是 **TOCTOU 竞态**：

- `pauseKindOfTx` 读到 `'paused'` 与 `resumeToQueued` 之间，run 可能被别的路径改成 completed（该 run 恰好跑到完成）；
- 两个并发 resume 都读到 `'paused'` → 都 UPDATE 成功（`resumeToQueued` 无状态条件）⇒ 重复唤醒。

⇒ **修复方案仍然正确且更严格**（加状态守卫同时堵住这两条），但**定性应改为**：

> 恢复的写操作**缺少原子状态条件**，存在 TOCTOU 竞态：并发 resume 可重复唤醒；恢复期间 run 状态被别的路径改写时也会被覆盖。

⇒ 影响：**定性写重会让评审者误判严重性**，也可能触发不必要的现网排查（"completed 的 run 被重跑了"听起来是已发生的事故，而它其实没发生过）。总纲把它列为"最紧急的一行 / 现网漏洞 / 今天可做"——**该做的还是要做**（加守卫），但理由应写成"消除 TOCTOU"，不是"completed 能被 resume"。

### N-03 · 决策 A（行锁）缺"全局锁序"，与批次路径有死锁风险

**位置**：总纲 §3.0.2 决策 A、§3.0.3 骨架第 130 行 `admissionLock(c, tenantId, workflowId)`

总纲建议"行锁 `SELECT ... FOR UPDATE`"（锁 workflow 行）。方向对——同 workflow 的准入串行化 ⇒ 后一个请求能看到前一个已提交的 run ⇒ 竞态消除 ✓。`RunAdmission` 骨架里 `admissionLock` 在 `checkInTx` **之前** ✓ 顺序也对。

**但总纲没写两件事**：

1. **跨路径的锁序**。批次路径 `createNextBatchAttempt` 已经持有**实验行锁**（`lockExperimentRow`，`BatchOrchestrator:688-690`）。若准入路径拿 **workflow 行锁**、批次路径拿 **实验行锁**，两条路径各持一把再等另一把 ⇒ **死锁**。
   ⇒ 必须规定全局锁序，例如：**workflow 行 → 实验行 → run 表**，且所有路径一律按此序取锁。

2. **同 workflow 准入的串行化成本**。并行批次时，4 批的准入会排队在同一把 workflow 行锁上。准入是一次短事务（判 + 写），可接受，但要在总纲写明这个预期，否则实测会以为是"卡住了"。

> 另注：总纲骨架里的 `WorkflowRunGate.checkInTx(c, …)` 是**待新建**的方法（现有 `check` 用独立连接 `db.open()`，`WorkflowRunGate:123`）⇒ 总纲 §3.0.3 的伪代码应标注"新增"，否则评审者可能以为现成有。

### N-04 · 决策 B"崩溃由 `StartupRecovery` 兜底"目前不成立

**位置**：总纲 §3.0.2 决策 B

总纲写"事务内写 `status='queued'`，提交后唤醒；崩溃由 `StartupRecovery` 兜底"。

**核对**：⑥ §1.4 对 `StartupRecovery` 的描述是"启动时收 `running`；**`queued/pending` 超 1 小时才收**（避免误杀刚入队的）"。

⇒ 崩溃后那条 `queued` 的 run **要等 1 小时才被收**。这不叫"兜底"，叫"挂一小时"。

⇒ 而且这与 ⑥ D-05 直接相关：`resumeAsync` 失败会留下僵尸 `queued`，⑥ §5.3 提的"僵尸 queued 扫描（超 N 分钟无 worker → `paused_fault`）"是**运行期**兜底，不覆盖"进程崩溃后重启"这一种。

⇒ **决策 B 需明确三件事**：
1. 崩溃恢复的**可接受延迟**（1 小时？15 分钟？）；
2. 若要求秒级 ⇒ 需要真正的 `rehydrate` 机制（`ExperimentScheduler` 已有 `rehydrate` 语义：把库里 `queued` 的 run 重新装进派发队列）；
3. 决策 B 说"提交后唤醒"——**唤醒失败时 run 就是僵尸 queued**，这条路径（提交成功 → 唤醒失败 → 进程活着）只能靠运行期扫描兜。

### N-05 · ⑥ Q-04 的位置锁 TTL 风险，缺"校验失败怎么办"

**位置**：⑥ §3.1 Q-04、§7 H-13、§8 R-25

⑥ 识别得很准："暂停 30 分钟后，位置锁 TTL 到期自动释放，但板可能还在设备里 → 别的 run 以为位置空了。"

**但只写到"恢复前强制校验"**（H-13 建议②），没写**校验失败之后怎么办**。现实里"板不在原位"有三种情况：

| 情况 | 正确处置 |
|---|---|
| 板在原位，只是锁过期 | 重新认领位置，继续 |
| 板被人工搬走但已登记 | 按 `locatePlateTx` 更正位置后继续 |
| **板位置不明** | ⇒ 转 `paused_unknown`，**强制人工盘点**，不得自动继续 |

⇒ 第三种才是 H-13 真正要防的。⑥ §4.5 已经有"`paused_unknown` 必须提供 corrections"的机制 ⇒ **恢复前校验失败 ⇒ 直接转 `paused_unknown`**，复用现成路径，而不是新造一个错误码。

### N-06 · "点了没反应"是必然的，缺 UI 中间态

**位置**：⑥ §4.2、R-26、用户问的第 5 问

⑥ 的语义（**上层暂停不直接改下层状态，而是"请求"下层停，下层在安全边界自己改**）**是可行的，而且是唯一正确的做法**——物理约束决定了动作执行中不能停（机械臂不能悬停承重、离心不能中途开盖）。

**但"用户点了没反应"是必然结果**，R-26 已经承认了，却没给解法。

⇒ 建议（沿用系统既有"用列不用枚举"原则，不新增 `run_status` 值）：

| 层 | 中间态 | UI 显示 |
|---|---|---|
| 实验 | `experiment.status` 保持 `running`，加一列 `pausing`（或 `transition_state`） | "正在暂停（2/4 批已停）" |
| 批次 | `experiment_batch.status` 同理 | "该批正在暂停" |
| run | `run.pause_kind` 加一个取值 `pausing`（字符串列，非枚举） | "正在停止" |

⇒ 没有这个中间态，用户看到的是"点了暂停，状态还是运行中，几分钟后才变" ⇒ **必然被当成故障**。而 R-26 的措辞"用户可能觉得点了没反应"低估了它。

## 五、对总纲 §7.2 七个问题的答复

1. **§3.0 的四个决策是否成立？**
   - **A（DB 准入互斥点）**：方向成立（行锁 + 索引兜底），但**必须补全局锁序**（workflow → 实验 → run），否则与批次路径的实验行锁互等（N-03）。
   - **B（提交与派发衔接）**：方向成立，但**"崩溃由 StartupRecovery 兜底"目前不成立**（queued 超 1 小时才收），需明确延迟目标或改用 rehydrate（N-04）。
   - **C（事件表最终 DDL）**：成立。合并方向对，但**必须与 F-02 第 3 条一并处理**——`run_id` 的去留不能单方面定。
   - **D（active 集合是否含 paused）**：**建议现在就定**：取 `('queued','running')` 排除 `paused`（理由见 ② v2 §4.2.2：同步 `runBatch` 允许重跑 paused 批，异步 `activeBatchAttempt` 把它当占用，两条路径本来就不一致；唯一索引会强制其中一种）。总纲"先只做行锁、索引推迟"是安全的过渡，但会把这个决策继续挂着。
2. **§3.1 的"每批开跑前准入"会不会因批间终结延迟误拒？**
   ⇒ **不会**。串行批次前一批一定已终结（`executeBatch` 返回前 `ExperimentExecutor.settle` 已落 run 终态、`finishBatchRun` 同步调用，`BatchOrchestrator:834`）。重新判定的真正理由是"防外部并发启动同 workflow"。
3. **§3.2 的"实验暂停 = 请求，不是命令"是否可行？**
   ⇒ **可行，且是唯一正确的做法**（物理约束决定）。但**必须配 UI 中间态**（N-06），否则"点了没反应"是必然结果而非风险。
4. **§3.3 的 `commandId` 去掉 `exec` 后，resume 如何区分"新一轮"与"同一轮重试"？**
   ⇒ **不需要区分**——真正目标是"同一条物理命令在设备侧只执行一次"。但**不能一刀切去掉 `exec`**：去重设备用稳定 id，不去重设备保留 `exec`（③ v3 §1.7）。总纲 §3.3 的写法会让不去重设备卡死（F-02 第 2 条）。
5. **§3.4 的锁护栏能否在阶段 1 期间并行落地？**
   ⇒ **能，且建议它最先落地**。零行为变化、不依赖其它模块、且是唯一不依赖"记得改全"的护栏。前提是按 ⑤ v2 §3.2 的形态（按 kind 推导 + 单变量），而不是总纲 §3.4 的"(type.rank, id) 字典序"（F-02 第 4 条）。
6. **§4 的验收是否遗漏"两实验共用设备 + 共用点位"？**
   ⇒ **不遗漏**：② v2 已补 P-34（两实验共用设备 + 共用点位）。但总纲 §4 的统计过时（N-02），且"并行场景"在第一阶段不可执行。
7. **本总纲是否把某处"设计"写成了"已有能力"？**
   ⇒ **有一处半**：总纲 §3.4 把 `LockOrderGuard` 写成"新增"✓ 正确；但 §3.0.3 骨架里直接调用 `WorkflowRunGate.checkInTx(c, …)`——**该方法不存在**（现有 `check` 用独立连接）⇒ 虽在伪代码里，仍应标注"新增方法"以免被读成现成能力。另一处：§1.1 的"挡住同流程多实例"用词会让人以为多实例部署，实际是单实例下的多条 run，建议改为"同流程并发 run"。
