### 1.4 `putPlate` 不落库：真实根因

> **`putPlate` 不落库，现象成立，下一步不成立。** `c.commit()` 已经在 `if (n > 0)` 外面。
>
> ```java
> // PositionLock.java:256-260
>                 if (n > 0) {
>                     markPlatePosition(c, plateId, resourceId, runId);
>                 }
>                 c.commit();
>                 return n;
> ```
>
> 同一事务里接着写的是另一张表。`PositionLock.markPlatePosition` 插入的列是
> `plate_id`、`current_pos`、`current_run`，而建表脚本里的 `plate` 只有 `barcode` 和 `location_id`。
>
> ```java
> // PositionLock.java:393-408
>     private void markPlatePosition(Connection c, String plateId, long posId, long runId) {
>         try (PreparedStatement ps = c.prepareStatement("""
>                 INSERT INTO plate (tenant_id, plate_id, current_pos, current_run, status, updated_at)
>                 ...
>         } catch (SQLException ignore) {
>             // plate 表是冗余，写失败不影响位置锁
>         }
>     }
> ```
>
> PostgreSQL 里这条语句失败后，整个事务已经作废，后面的 `commit()` 会失败并回滚，
> `position_state` 的更新一起没了。异常被吃掉，所以日志里不一定有 SQL 原文。
> 指引里「`markPlatePosition` 已改成空方法」指的是 `WorkflowService` 里同名的那个空方法，
> 不是这条还在写错列的路径。
>
> 另外两处会把失败记成成功：`notePlateMove` 不看 `putPlate` 的返回行数，0 行也打
> `[PLATE] ... -> pos=504495`；`tryReserve` 在更新 0 行且查不到记录时仍返回 `OK`
> （`PositionLock.java` 第 132 行）。日志里的 `plate=${plate}` 说明变量没被替换，
> 和「找不到就保留原文」是同一条规则。
>
> 开发日志说没有 `[PLATE-ERR]`。按现在这份源码，`commit()` 失败应该打出那行。
> 对不上的话，先确认正在跑的 class 是不是这份源码——这正是指引自己列的「以为改了其实没改」。

### 1.5 调度器差距要改说法

> `ExperimentScheduler.dispatch` 确实是 EDD、优先级、FIFO，外加岛锁和 2 秒轮询，
> 没有承诺窗口，也没有冻结区。但 `多实验并行调度-动态规划与滚动排程.md` 第 1 节把滚动时域写成结论，
> 第 6 节的 1.0 路线就是岛锁加贪心。**代码对齐的是第 6 节。**
> 文档状态仍是「待评审」。差距是同一份文档里目标和方法混在一起，不是代码漏做了一个已经定稿的设计。
> 类注释写「贪心 + 滚动」，滚动并没有出现在实现里。

### 1.6 其余几条可以保留 + 补充

> 两套 `long` ID、`WorkflowService`/`GraphRunner` 与 `ExperimentFlowRunner` 各写一套分配和变量替换、
> 长连接把 `method_status=1` 当失败，都和代码一致。
> 补充一条：**默认仍是短连接**，`TcpDriverAdapter` 把所有不是 2 的状态都当失败，
> 孵育 30 分钟的问题不限于长连接。进度语义和 `ApiServer` 巨类的描述也可以保留。
>
> 岛锁的 TTL 是 2 小时，注释写明了过期后可能两个实验同跑一个岛。
> 这是有意的取舍，指引的决策表里没有写。

### 1.7 结尾那句过了

> `RealWorkflowRunner.runAll` 已经改用 `GraphRunner` 和 `SimulatedBus`，会统计并行网关和异或网关走了几条默认边。
> 这是**仿真总线上的按图走完，不是 流程在真设备上通过**。
> `BATCH_VALIDATION_REPORT.md` 仍写 992 和拓扑排序。
> 指引里的通过率没有附这次运行的输出。
> 多实验并行有岛锁，板位抢占在 `putPlate` 修好之前还不能说已经防住冲突。

### 1.8 评审建议顺序

> 1. **板位事务。** `tryReserve` 提交预约之后，`putPlate` 在同一事务里写错 `plate` 表，回滚把层位一起撤掉。`notePlateMove` 又把返回值当成成功。
> 2. **两套 ID 和两条执行路径。** 值类型是对的方向。在那之前，先确认 `ExperimentFlowRunner.instanceIdOf` 和 `WorkflowService` 的候选池用的是不是同一个映射。
> 3. **失败是否真的停住。** 实验编排写了失败即停；步骤落库失败被 catch 后流程继续（`WorkflowService` 里「数据丢了比流程停了好」）。这两条同时成立，评审时要分开看。
> 4. **文档层次。** 规格、设计稿、决策编号、模块索引，四套说法。这比前端样式更值得先收。

## 四、对评审方法本身的反思

### 4.1 为什么我能骗过自己

| 现象 | 心理 |
|---|---|
| `putPlate` 返回了 pos，就认为成功 | **看到返回值符合预期就停止验证**，没检查返回值是否真的代表了成功 |
| 全量 100% 就说"工艺通过" | **想给出好看的结论**，把仿真当真实 |
| `replace` 静默失败 3 次 | 每次都是 `s.replace()` 后没验证，**默认工具会报错** |

**共同点：验证标准是"看起来对"，不是"数据证明对"。**

### 4.2 外部评审补了什么

| 我看到的 | 评审看到的 |
|---|---|
| `putPlate` 返回 pos → 成功 | 同一事务里 `plate` 表写错列 → 整体回滚 |
| `recovery/` 有租约接管（文档写的） | 实际是 `RecoveryDecider`，没有租约 |
| 全量走图 = 工艺通过 | 在 `SimulatedBus` 上走图 |
| PG 地址 | 6379 是 Redis |

**外部评审的价值：它不接受"看起来对"，只接受"代码是这样"。**
