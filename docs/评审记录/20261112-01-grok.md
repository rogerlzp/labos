## 二、意见清单

### ①（P1）节点完成和命令不在同一事务；同事务要求和「失败不回滚」互相否定

**位置**：设计 §5.5、§5.6；`GraphRunner.java:648-650`；`WorkflowService.java:2213-2244`（`onStepDone` → `writeStep` → `insertRunCommand`）；`RunMapper.xml:555-563`（`updateNodeStateLive`）；`WorkflowService.java:1790-1796`。

**代码事实**：

- 设备任务的顺序是：先 `executeNode`（步结束时 `insertRunCommand` 单独提交），返回之后才 `updateNodeStateLive` 把 level=0 写成 `completed`。两次都是各自的 mapper 调用。跑图的方法上没有 `@Transactional`，也没有包在 `Tx.inTransaction` 里。
- `PositionLock.auditPlateMove`（`:301`）写明审计用独立连接，失败只打日志，故意不进位置锁的事务。内容迁移如果照抄这条，就会得到设计想避免的那条缝。
- 命令已经代表物理动作发生过。若把「节点完成 UPDATE」和「状态迁移 INSERT」放进同一个事务，迁移失败会把节点完成一起滚回去。续跑时这个节点不在 `skipKeys` 里，设备动作会再做一次。这和 §5.6「物理事实不可撤销，所以不能回滚节点」相反。
- 「崩在中间就无法自动修复，因为没人知道它该变成什么」过重。`produces` 声明还在节点上。修不了的是**按当时位置重新找板**：板可能已经搬走。补偿必须沿用当时解析出来的 `plate_id`，不能重跑 `target.by=position`。

**结论**：决策 1 不接受「必须与节点完成同事务」这个字面要求。接受「不能留下无法补的断链」。

**建议改成**：

1. 命令维持现状，先提交。
2. 节点状态更新提交之后，再用 `Tx.inTransaction` 写 `plate` 当前值 + `plate_state_audit`。幂等键挡住重放。
3. 这一步失败：节点保持 `completed`，整单转人工（现有 `waiting_human` 口径），补偿任务按审计里已记下的 `plate_id` 重放。不要靠 `skipKeys` 路径再进一次 listener——跳过的节点不会再走到 `:650`。

### ②（P1）「现成挂点」和「现成 listener」都覆盖不到设备节点

**位置**：设计 §3、§5.6；`GraphRunner.java:604` 与 `:648-650`；`BuiltinListener`（`:189-204`）只在内置分支 `:577-626` 被调用，并且 `catch (RuntimeException ignore)` 后继续。

**代码事实**：

- `:604` 的 `nodeStateRecorder.accept(key, "completed")` 在 `Kind.BUILTIN` 分支里。PCR、封膜、加液都是 `Kind.TASK`，完成回调在 `:650`。
- `GraphRunner` 确实不碰数据库（没有 JDBC import）。这句话对。
- `BuiltinListener` 是给 `__sleep` / `__wait` 补命令台账的，失败被吞掉，语义是「台账写不进去不能影响执行」。内容迁移如果挂在这里，失败会被吞，而且设备节点根本不会进来。

**建议**：新的 `NodeEffectListener` 挂在 `:650` 的任务完成之后，由 `WorkflowService` 实现。不要复用 `BuiltinListener` 的吞异常。内置节点本期不产出物料，不必挂 `:604`。

### ③（P1）幂等键在 §5.3 和 §7 各写了一套

**位置**：§5.3 写唯一索引 `(run_id, node_id, plate_id)`；§7 的表没有这两列，索引是 `(owner_run_id, owner_node_key, plate_id)`。

**代码事实**：PostgreSQL 唯一索引对 NULL 的默认行为（多个 NULL 互不相等）描述是对的。人工盘点把 `owner_run_id` 留空，因此不受这把索引约束，这点成立。

**问题**：两处不是同一个键。实现时若按 §5.3 去建，表上没有 `run_id` / `node_id`。另外同一节点对同一块板只能有一行；内容物和封膜必须写在同一行的 from/to 里，不能记成两次迁移。

**建议**：以 §7 的列名为准，写进 §5.3，并加上 `tenant_id`。人工盘点继续留空 `owner_run_id`。不要依赖以后打开 `NULLS NOT DISTINCT`。

### ④（P1）不要把 `plate_type` 改成工艺角色

**位置**：设计 §4.1、§7、决策 6；`pg_rebuild/schema/30_business.sql:61-75`。

**代码事实**：`plate_type varchar(32) NOT NULL DEFAULT '96'`，注释是 `96 / 384 / 24 / tube_rack`。旁边已有 `rows` / `cols`。`status` 的默认值是 `available`，注释是 `available / in_use / consumed / discarded`，不是 `active`。

设计稿 §7 要把 `plate_type` 收成 `pcr_plate / deep_well / assay_plate / … / consumable`。一块 PCR 板可以是 96 孔也可以是 384 孔。写进现有列会丢掉板型规格。`consumable` 作为板类型还会和 §4.3 的独立耗材实体缠在一起。

**建议**：决策 6 否决「就改这 6 个取值」。`plate_type` 继续表示规格。工艺角色若确实需要，另加列（例如 `vessel_role`），本期可以不加。S1 不要写这列的数据迁移。

### ⑤（P2）不阻断是对的；理由要改

**位置**：§6.3、§6.4、决策 5。

**代码事实**：节点有方法名和能力。`Transfer` 与加液、封膜、扩增不是同一类。设计器预检已经按能力工作，不是「看见动板就分不清」。

**建议**：决策 5 接受「运行期不猜、不阻断」。WARN 的对象收成「会改内容的能力」，`Transfer` 以及只改位置的方法排除在外。不要对所有会动板的节点强制声明，那会把正常搬运全部打成漏配。

### ⑥（P2）§2 / §3 的现状词表和 schema 不一致

**位置**：§2 的 `position_status(IN_TRANSFER|KNOWN)`；§3 的 `status(active)`。

**代码事实**：`position_status` 的列注释是 `KNOWN / UNKNOWN / LOST`（`90_all_in_one.sql:2539`）。`plate.status` 见意见 ④。`plate_well` 在 schema 里有 `sample_id` / `aliquot_id` / `status`，但内核 Java 侧没有写入点，执行器今天不用它。所以「现场答不上这块板装着什么」仍然成立；只是不要把孔位表写成不存在。

**建议**：§3 改成与 schema 一致，并加一句「孔位表未接入执行」。现场库的 6 行快照可以留，但标明是当时的数据，不是词表。

### ⑦（P2）耗材判据还差一刀

**位置**：§4.3、决策 3。

「要不要单独追踪位置」能分开膜和盖子，这刀是对的。它不够普适：吸头有位置（哪一盒、哪一列），但不应每支吸头一行 `consumable`。缺的是「是否逐件保留身份」。只按盒、按批计数的，用位置上的数量，不建实体。

**建议**：判据改成「既要独立位置，又要逐件身份」才进 `consumable`。膜维持 `seal_state`。S5 继续不进第一刀（决策 7 接受）。
