## 二、§7 八问逐条答复

### 第 1 问 · D1 的合并规则（并集 + 圈次 max）是否覆盖所有形状？有没有"同一节点合法地出现在两条分支里"的图？

**答：合并规则覆盖所有形状 ✓，但校验器漏了一类图。**

**为什么覆盖**：`gateway_parallel` 的语义是"每条出边一条分支，join 等所有入边到齐"。一个节点若被两条并行分支共同指向，它就是 **join**（入边 ≥ 2），**不属于任何分支** ⇒ ⇒ 分支子图天然互斥 ⇒ "并集 + 圈次 max"够用。

**漏掉的一类：条件网关（`gateway_conditional`）**。
`GraphRunner` 里另有 `ConditionalBranchTracker`（`:702`）专门处理"哪条入边是分支被跳过的、永远不会来"⇒ **条件网关的分支可能汇到同一个下游节点**。

⇒ 条件网关是**顺序执行**的（不并发），本不该被切进并行组。但方案的"步 2 图分析"只说"找 `SPLIT_PARALLEL` → 配对 `JOIN_PARALLEL`"⇒ ⇒ **校验器必须同时把条件网关的分支排除在外**，否则会把"包容分支"误当成并行分支切进去 ⇒ 两类分支的合并语义完全不同（包容只走一条，并行全走）。

⇒ **建议校验器规则补三条**（不是一条）：
1. 分支子图互不相交；
2. 分支子图内**不得出现另一个 split/join**（嵌套要显式递归）；
3. 分支子图**不得包含条件网关的分支**（`gateway_conditional` 不参与切分）。

### 第 2 问 · D2（禁止同组内两分支写同一变量 key）是否过严？业务真需要"两分支累加"怎么办？

**答：不过严 ✓ —— "累加"需求不需要放宽这条约束。但编译期检查漏了一种模式。**

**"两分支累加"怎么落地（不需要原子操作）**：两分支各写**不同的 key**（`count_a`、`count_b`）⇒ 这是 D2 允许的 ⇒ **join 节点做 `count_a + count_b`** ⇒ ⇒ 业务要的"累加"完全能在 join 处表达，**不需要放开同 key 写入，也不需要提供原子自增 API**。

⇒ 方案 D2 的论证成立："计数器在并行流程里语义不清（谁该看到几？)"、编译期硬约束优于运行时静默错误。

⚠ **但编译期检查只覆盖了"写同一 key"，没覆盖"读-改-写同一 key"**：
分支 A 读 `count=0` → 分支 B 写 `count=1` → A 写 `count=0+1=1` ⇒ **丢更新**，且**编译期查不出来**（两边写的 key 相同 ⇒ 已被禁；但若 A 读的是 `count` 而写的是 `count_total`，就绕过了检查）。

⇒ ⇒ **检查规则应从"同 key 写冲突"扩展为"同 key 的读-改-写依赖"** —— 即某个节点的输出值依赖某 key 的旧值，且另一分支也写该 key ⇒ 冲突。

### 第 3 问 · D3/D4 的上限：按方法配、按设备配，还是固定值？

**答：都不完全是 —— 应该按"等待对象"配。两个上限的来源不同。**

| 上限 | 等的是谁 | 来源 |
|---|---|---|
| **执行超时**（业务已定"分支不设超时"） | — | 不设 |
| **停止收尾上限**（D3：分支失败后等在途命令完成） | **设备的物理收尾** | **按方法配** —— 复用 `device_method.timeout_sec` / `MethodTimeoutPolicy` 能力默认（INCUBATE 1800s / THERMOCYCLE 3600s / CENTRIFUGE 900s） |
| **暂停等待上限**（D4：分支卡在等事件时用户点了暂停） | **事件到达**，不是设备执行 | **按节点自己的 `__awaitEvent` timeout 参数**（现网是 600/900 秒），**不是方法超时** |

⇒ ⇒ **两个上限不能共用一个"按方法配"的配置** —— D4 等的是"事件多久来"，D3 等的是"设备多久做完"，量级可以差一个数量级。

⇒ ⇒ 建议文档用三个**不重名**的参数：`执行超时` / `停止收尾上限` / `暂停等待上限`，避免再次出现"一个 15 分钟被两种语义共用"（这在《确定事项总表》D-09 已经踩过一次）。

### 第 4 问 · D5：nodeStateRecorder / ExecutionListener 被多线程调用是否安全？DB 连接从哪来？

**答：DB 连接没问题（方案的判断正确 ✓），但真正的隐患有三处，方案只列了其中一处。**

#### 4.1 连接来源 —— 方案判断正确 ✓

`persistence/Tx.java:20-23` 类注释原文：

> 用 Spring 的 `TransactionTemplate` + `DataSourceTransactionManager`：在事务内 `db.open()` 会经 **`DataSourceUtils` 拿到同一条线程绑定连接**，提交/回滚/连接归还全由框架负责。

`Tx.inTransaction`（`:71-83`）= `new TransactionTemplate(manager()).execute(status -> { try (Connection c = db.open()) { ... } })` ⇒ **线程绑定连接** ⇒ ⇒ **多线程各自 `inTransaction` ⇒ 各拿各的连接 ⇒ 写库本身互不干扰 ✓**（方案 §D5 的判断正确）。

#### 4.2 隐患 ①：事件缓冲区是 `ArrayList`（方案未列）⚠

```java
// WorkflowService:1060
List<ExecutionEvent> events = new ArrayList<>();

// WorkflowService:1913-1921
private static ExecutionListener tee(List<ExecutionEvent> sink, ExecutionListener... next) {
    return e -> {
        sink.add(e);              // ← 并发 add 到 ArrayList
        for (ExecutionListener l : next) { l.onEvent(e); }
    };
}
```

⇒ **多线程并发 `add` 到 `ArrayList`** ⇒ 丢事件 / `ArrayIndexOutOfBoundsException` / 扩容期间数组错乱。**这是 D5 里最容易漏、后果最直接的一处**（台账丢失 = 现场无法复盘）。

#### 4.3 隐患 ②：`RunMonitor.Live` 是可变对象（方案未列）⚠

```java
// RunMonitor:24
public static final RunMonitor INSTANCE = new RunMonitor();
// RunMonitor:52
private final Map<Long, Live> live = new ConcurrentHashMap<>();   // ← Map 线程安全
// RunMonitor:26 注释原文
/** 单个 run 的实时快照（可变，只在执行线程写）。 */
// RunMonitor:61-67
public void onEvent(long runId, ExecutionEvent e) {
    Live l = live.get(runId);
    l.lastEvent = e.type().name();     // ← 多分支并发写同一个 Live 对象
```

⇒ `live` 这个 Map 是安全的，但**每个 run 只有一个 `Live` 实例** ⇒ 两个分支的事件**并发写同一个对象的字段** ⇒ **"当前在哪个节点"会来回跳变** ⇒ 页面"卡在哪"的诊断信息失真。**不崩，但不可信** —— 而这恰好是现场排障唯一能看的东西。

⇒ 注释自述的"只在执行线程写"这个前提，在并发下**破了**。

#### 4.4 隐患 ③：`RunProgress` 的遍历点（方案只提了容器）

方案 R2 说"`RunProgress.nodes` 是 LinkedHashMap ⇒ 改 CHM + AtomicBoolean"。但：

```java
// RunProgress:24-26
public Collection<NodeProgress> all() { return nodes.values(); }   // ← 活视图
// RunProgress:81-83
public int count(NodeStatus status) {
    return (int) nodes.values().stream().filter(...).count();       // ← 遍历
}
// RunProgress:85-88
public boolean allSettled() {
    return nodes.values().stream().noneMatch(...);                   // ← 遍历
}
```

⇒ 换成 CHM 后不会 CME，但 **`count()` 与 `allSettled()` 是两次独立遍历** ⇒ ⇒ 并发写入时**两个方法可能给出不一致的结果**（一个说全结算、一个说没全结算）⇒ ⇒ `settleRun` 用它们决定 run 落 completed 还是 paused ⇒ ⇒ **可能把未完成的 run 落成 completed**。

⇒ ⇒ 不只是"容器换掉"，**遍历也要在同一把锁或同一次遍历里算**。

#### 4.5 确认安全的两处（方案担心但实际没问题）

| 组件 | 结论 |
|---|---|
| `nodeStateRecorder`（`WorkflowService:1305` → `recordNodeState` → `rm().updateNodeStateLive`） | ✅ **安全** —— mapper 每次独立开连接；且不同 `node_key` 无唯一键冲突（D1 的不相交保证） |
| `PersistingStepSink`（`:2985-2993`） | ✅ `seq` **已经是 `AtomicInteger`**（`:2989`）、`resourceByStep` 是 `ConcurrentHashMap` ⇒ StepSink 侧基本安全 |

⇒ ⇒ **D5 的完整清单（方案需要补的）**：
1. `List<ExecutionEvent> events` ⇒ 线程安全容器（**新增，方案未列**）
2. `RunMonitor.Live` 字段 ⇒ 按分支维护或改线程安全（**新增，方案未列**）
3. `RunProgress.count()/allSettled()` 的遍历一致性（**新增，方案只提了容器**）
4. `RunProgress.nodes` / `aborted` / `materialHold`（方案 R2 已列 ✓）

### 第 5 问 · R1：seq 改 AtomicLong 后会跳号，下游依赖序号连续吗？

**答：依赖存在，但只在测试断言与 payload 记录里，没有业务去重逻辑。**

**依赖点（硬证据）**：

```java
// test/.../engine/StressTest.java:176-177
for (int i = 0; i < events.size(); i++) {
    eq("seq@" + i, (long) (i + 1), events.get(i).seq());      // ← 断言严格连续
}
// test/.../engine/EngineSelfTest.java:156-157
for (int i = 0; i < events.size(); i++) {
    eq("seq 连续", (long) (i + 1), events.get(i).seq());      // ← 同上
}
```

⇒ **两个自测硬断言 `seq == 1..N`** ⇒ 任何"跳号"改动都会让它们红 ⇒ ⇒ 它们既是**约束**，也是**现成的回归网**（见第 7 问）。

**业务侧**：全仓 grep 未发现"按 seq 去重 / 按 seq 排序落库"的逻辑；`seq` 只出现在 `JdbcEventStore:67`（写进 `payloadJson`）⇒ ⇒ **没有业务依赖连续性**。

**结论与建议**：
- 并发下"全局连续序号"**本来就不存在**（两个分支的事件没有天然全序）；
- ⇒ 建议**不改 AtomicLong**，而是把 seq 的语义改成"**分支内单调**"，并在事件/落库带上 `branch_id`；
- ⇒ 排序键用 `(branch_id, seq)` 或 `(occurred_at, node_id)`；
- ⇒ **单线程场景只有一条分支 ⇒ 两个"seq 连续"自测仍绿 ✓**（这是零成本的兼容性保障）。

### 第 6 问 · 有没有比"抽 executeNode + 并行组"更小侵入的做法？复核"每分支一个 GraphRunner 不可行"

**答：§3.3 的"不可行"论证不成立。状态机是无状态的，每分支一实例可行。而且两条路共用同一份前置工作。**

**核对 `RunStateMachine` 的实例字段**：只有 `decider / listener / sleeper / clock / seq / stepPlanner / paramPlanner / noDeviceReason / materialCompletion / materialGate / loopIndexSupplier` ⇒ **全部是注入的依赖或配置项，没有任何"执行到哪一步"的跨节点状态**。

`RunProgress` 的类注释（`:9-12`）也印证了这一点：

> 持有全部节点的可变进度，可序列化落库。**状态机本身不存状态**，所以「暂停 → 存盘 → 重启续跑」只需把这个对象还原回去。

⇒ ⇒ **每分支一个 `RunStateMachine` 实例完全可行**（前提：`seq` 每分支独立 + `listener` 线程安全 + `decider/sleeper/clock` 可共享）。

⇒ ⇒ **真正的 run 级共享是三样**：

| # | 共享物 | 3.1（主循环单线程 + 分支上池） | 每分支一实例 |
|---|---|---|---|
| 1 | `RunProgress`（进度） | 共享 ⇒ 要线程安全 | 共享 ⇒ **同样要线程安全** |
| 2 | `listener` / 事件缓冲（台账） | 共享 ⇒ 要线程安全 | 共享 ⇒ **同样要线程安全** |
| 3 | `variables`（流程变量） | 共享 ⇒ 已线程安全化 ✓ | 共享 ⇒ **同样** |

⇒ ⇒ **这三样一个都躲不掉 ⇒ 两条路的工作量差异比方案说的小得多。**

**真正的取舍点不是"状态机 run 级"，而是"主循环状态（`pending` / `ready` / `done` / `visits` / `tracker`）由谁持有"**：

| 路径 | 主循环状态 | 要不要抽 `executeNode`（1000 行控制流） |
|---|---|---|
| 方案 3.1 | 主线程持有 | **要**（`break` → `return Outcome`） |
| 每分支一实例 | **各分支各自持有** | **不要** —— 分支内部跑自己的子图循环 |

⇒ ⇒ **而"切出分支子图"这件事，两条路都要做（方案的步 2）** ⇒ ⇒ **步 2 同时产出"分支互不相交"的校验器** ⇒ ⇒ **⇒ 建议的改造顺序（也是第 6 问的答案）**：

1. **先做步 2**（图分析 + 切子图 + 校验器）—— 它是两条路共用的资产，且**独立可交付、可验证**（切图正确性可用纯逻辑单测覆盖，不需要跑图）；
2. **用步 2 的产物再决定执行路径**：若"分支子图"能被喂进一个独立 `GraphRunner`，则走每分支一实例（省掉 1000 行抽取）；若不能，则走方案 3.1；
3. **D5 的三处内存结构改造与路径选择无关** ⇒ 可以并行做。

⇒ ⇒ **⇒ "更小侵入"是存在的，而且第一步（步 2）在两条路上都是净收益。**

### 第 7 问 · R3：1000 行控制流改写怎么验证"纯重构无行为变化"？用基准流程端到端对比够吗？

**答：不够 —— 端到端对比恰好会失败，因为这次改动的核心就是时间线变了。**

端到端能验的是"最终结果一致"（板位、run 终态、产物）；**验不了"中间顺序一致"** —— 而顺序恰恰是本次要改的东西 ⇒ ⇒ 拿它当"纯重构"的锚点，必然报红 ⇒ ⇒ 锚点选错了。

**正确的锚点：P-08（单分支流程行为完全一致）**。

| 对比对象 | 锚点 | 判据 |
|---|---|---|
| **重构前后 · 无并行分支的流程** | 逐项 diff | 节点执行顺序一致；`run_node` 状态/时间一致；`run_command` 条数与内容一致；**事件 seq 序列一致（1..N 连续）**；台账条数一致 |
| **重构前后 · 有并行分支的流程** | 只比结果 | 不比时间线；比终态、板位、产物、台账完整性（条数与 node_key 集合） |
| **并发正确性** | 新增 | 见下 |

⇒ ⇒ **两个"seq 连续"自测（`StressTest:177`、`EngineSelfTest:157`）就是现成的回归网** —— 重构若偷偷改了事件发出顺序或丢事件，它们会红 ⇒ ⇒ **建议把"单分支流程的重构前后 diff"作为合并门槛，把这两个自测作为 CI 门槛**。

⇒ ⇒ **并发正确性目前缺一类验收**（方案的 P-01~P-08 没覆盖）：**"两个分支同时落 `run_node` / `run_command`"的台账完整性** ⇒ 建议加一条：N 个节点并发执行后，`run_node` 行数 = 节点数 × 圈次、**无重复行、无缺失行**（方案的 P-05 只说"每个节点一条"，没说怎么验）。

### 第 8 问 · D6：全局固定池 + 信号量，还是每 run 一个？与 run 级并发上限怎么配合？

**答：全局固定池 + 信号量 ✓ 合理。但 D6 与 D7 组合会产生一个方案里没有的线程池死锁（见 N-A）。**

信号量与 run 级上限的配合：建议**信号量的许可数 = min(run 级并发上限 × 每 run 最大分支数, 物理设备并行容量)**，且**信号量必须在"提交分支任务之前"获取**（不是在任务内部获取），否则超限的分支会占着池线程等许可。

## 三、方案未列出的发现

### N-A ⚠ D6 + D7 组合 = 经典线程池死锁（方案风险表没有）

D7 写："`inner` 在 `outer` 的分支线程里执行"。

设池大小 = N：
- 外层并行组占 N 个分支线程；
- 其中某个分支线程遇到内层 split ⇒ **提交内层分支任务到同一个池** ⇒ 然后 `allOf().join()` 等内层完成；
- ⇒ **内层任务排在池队列里，而池里所有线程都在等内层完成** ⇒ ⇒ **死锁**（N 个线程全被占 + 队列里全是它们要等的任务）。

⇒ ⇒ **D7"不额外申请信号量"是对的（信号量不解决这个），但"在同一池里提交"会死锁**。

⇒ ⇒ 两个可行方向：
- **(a)** 内层用**独立的小池**（或 `ForkJoinPool` 的 work-stealing：外层分支线程在 `join()` 时会帮跑内层任务 ⇒ 不死锁）；
- **(b)** 内层**不提交线程池**，在当前分支线程里**串行**执行内层各分支（内层并发度要求不高时最简单）。

⇒ ⇒ 建议在风险表加一条：**R8：嵌套并行组用同一线程池 ⇒ 线程池死锁**。

### N-B · 步骤顺序：步 5（修 `RunProgress` / `RunStateMachine` 线程安全）应提前

方案把"修 RunProgress 与 RunStateMachine 的线程安全"排在**步 5（最后）**，而步 3（提交线程池）已经产生并发 ⇒ ⇒ **步 3 落地时，步 5 的对象已经被多线程并发写** ⇒ ⇒ 中间态（步 3 完成、步 5 未做）是**必崩的**，不是"暂时不安全"。

⇒ ⇒ 建议改为：**步 1（抽 executeNode）→ 步 2（图分析）→ 步 5a（线程安全化 RunProgress/RunStateMachine/事件缓冲/RunMonitor）→ 步 3（提交线程池）→ 步 4（停止语义）** ⇒ ⇒ **线程安全化必须先于任何并发**。

### N-C · `RunStateMachine.seq` 若改成 AtomicLong，两个"seq 连续"自测会红

见第 5 问 ⇒ ⇒ 若坚持改 AtomicLong（全局唯一但跳号），必须同步改这两个自测的期望 —— 那等于**放宽了一条已被断言的契约** ⇒ ⇒ 而"分支内 seq + branch 维度"方案**不用改测试**（单线程仍连续）⇒ ⇒ 进一步支持第 5 问的建议。

### N-D · `GraphRunner` 局部容器 `pending` / `tracker` 的线程安全

方案 §1.2 列了五个局部容器，但注意：**分支线程若跑自己的子图循环，这五个容器是分支私有的 ⇒ 天然安全**；而方案 3.1（主循环持有 ready/done/pending，分支线程只执行单节点）⇒ `done` / `visits` 由**主线程**写（分支线程不写）⇒ 也安全。

⇒ ⇒ **⇒ 这其实是"每分支一实例"的一个额外优势**：分支子图的 `pending`/`ready`/`tracker` 不用做线程安全化 ⇒ ⇒ 方案 3.1 之所以需要 `done`/`visits` 隔离（D1），正是因为它们被主线程共享 —— 而每分支一实例下**不需要隔离设计，直接各分支私有即可** ⇒ ⇒ 又一条支持第 6 问的证据。

## 四、改造路径建议（"如何彻底改造"）

按依赖与可验证性排序，每步都能独立交付与验收：

| 步 | 内容 | 为什么这个顺序 | 可验证锚点 |
|---|---|---|---|
| **S1** | 图分析：split/join 配对、切分支子图、三条校验（互不相交 / 子图内无 split-join / 排除条件网关） | **两条执行路径的共用资产**；纯逻辑，不碰执行 | 纯逻辑单测（切图结果 + 校验器命中） |
| **S2** | 事件/台账/进度三处内存结构线程安全化：`events` 容器、`RunMonitor.Live`、`RunProgress`（容器 + `aborted`/`materialHold` + **遍历一致性**） | **必须先于任何并发**（N-B）；与执行路径无关 | 并发写单测（多线程写 → 条数/一致性断言） |
| **S3** | `RunStateMachine.seq` 方案定案：**分支内单调 + branch 维度**（不改 AtomicLong） | 单线程下两个"seq 连续"自测仍绿 | `StressTest:177`、`EngineSelfTest:157` 绿 |
| **S4** | 执行路径二选一：<br>(a) 每分支一 `GraphRunner` + 每分支一 `RunStateMachine`（**不抽 1000 行**）<br>(b) 抽 `executeNode` + 主循环委托 | **先做 S1 再评估**（第 6 问）：切图产物是共用前置；若 (a) 可行则省掉最大的一次性改动 | 无并行流程的重构前后**逐项 diff**（顺序/台账/事件序列） |
| **S5** | 并行组执行：分支提交 + 等齐 + 结果汇总；线程池与信号量（**信号量在提交前获取**） | | P-01（时间戳重叠 < 1 秒）、P-05（台账完整） |
| **S6** | 停止/暂停语义：`stopFlag` + 边界检查 + **两个独立上限**（停止收尾=方法超时；暂停等待=节点 timeout） | 第 3 问 | P-03、P-04 |
| **S7** | 嵌套并行组：**独立池或串行**（N-A） | | P-07 + 一条"不死锁"压测 |
| **S8** | D2 编译期检查扩展到"读-改-写同 key" | 第 2 问 | 编译期用例 |

**并发正确性的验收缺口**（建议补进 P 组）：
- P-09：N 节点并发后 `run_node` 行数 = 节点数 × 圈次，无重复无缺失；
- P-10：并发下事件缓冲**不丢事件**（`events.size()` == 各分支事件数之和）；
- P-11：并发下 `RunMonitor` 的 Live 状态可解释（每分支各自可见，不互相覆盖）；
- P-12：`count()` 与 `allSettled()` 在并发写入点之后给出一致结论。
