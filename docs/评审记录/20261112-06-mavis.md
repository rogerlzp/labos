### M1【P0】【事实错误】`run_command` 没有 `command_id`：执行事实载体选错表
- **来源**：S1 / D1 / G16（三份报告独立发现，多源印证）。
- **文档位置**：§7 L652-655；§15③ L853；§0.1 D2 L59；关联 §7 L604。
- **证据**：`run_command` 实列 = id/tenant_id/run_id/run_node_id/command_seq/method/payload/status/attempt/sent_at/ack_at/finished_at/ack_latency_ms/result/device_raw_response/error_code（`pg_rebuild/schema/20_kernel.sql:336-354`；`90_all_in_one.sql:2756` 另补 device_id）——**无 command_id**。`command_id` 在 `command_ledger`：`99f_command_ledger.sql:9-27`（:19 `varchar(160)`、:26 `uk_command_ledger_key (tenant_id,idempotency_key)`）；`command_outbox.command_id` 同宽（`99n_command_outbox.sql:12`）。账本在**派发前**落账、回包写结果：`labos-kernel/src/main/java/com/labos/kernel/driver/DriverStepExecutor.java:675-706/721-728`（fail-closed 拒绝重复下发）；`run_command` 是**回包后**才在 `onStepDone` 插入（`WorkflowService.java:2213/2302`、`RunMapper.xml:614-623`），"已下发未回包"窗口它还没有行。崩溃隔离现有实现即按账本筛（`RunMapper.xml:714-735` 排除 `command_ledger.state IN ('UNKNOWN','DISPATCH_STARTED')`）。`ack_at` 有列无写入（同 insert 只写 sent_at/finished_at）。`event.command_id varchar(64)`（§7 L604）装不下 160 字符。
- **影响**：S2 按文档 `SELECT command_id FROM run_command` 直接失败；更严重的是把现有命令账本（派发前落账/幂等键/UNKNOWN 人工核对）当不存在，重复造第二套执行事实与对账机制，两套账本对不上。
- **建议改法**：§7/D2 改两表分工——① 命令事实 = `command_ledger`（派发前落账/idempotency_key/command_id/UNKNOWN 对账）+ `run_command`（回包后结果台账）；② `event.command_id` 改 varchar(160) 或 `command_ledger_id bigint` + `(tenant_id, command_ledger_id)` 复合 FK；③ 写明设计与 `command_ledger.idempotency_key` 的关系；④ `ack_at` 补写入点，否则不得当证据。

### M2【P0】【事实错误 + 设计风险】T1 失败/崩溃恢复会重做物理动作；无 run 级转人工通道
- **来源**：G1 / S4 / S17（多源印证）。
- **文档位置**：§5.2b L263；§5.7 L376-377；§5.8 L385-386；§11.2 T01 L757；§17 Q5 L902。
- **证据**：文档自相矛盾——L263「T1 失败 = 物理动作已发生，但系统没留下任何记录 ⇒ 必须阻断整个 run 并转人工」；L377「物料通知在设备动作已完成之后、节点标记 completed 之前」；L385「T1 前崩溃 ⇒ 什么都没发生 ⇒ 设备动作也没发生 ⇒ 重跑即可」。按 L377 时序，T1 前窗口必然包含"设备已动、记录未落"，L385 等于把同一物理动作做第二次；且"没留下任何记录"不实（§3 L133 自述命令先提交；`command_ledger` 派发前落账，见 M1）。运行期落点：T1 抛 RuntimeException → `WorkflowService.java:1070-1084` catch → `markRunFailed` :655-667 → `RunMapper.xml:8-16` 只写 `status='failed'`+`input.error`（不写 recoverable/pause_kind）⇒ `PauseMapper.xml:19-25` 恢复判定不成立 ⇒ `PauseManager.java:246-252` 返回「该执行不在暂停状态」，人工无事可做。更糟分支：DB 不可用时 markRunFailed 也失败（:1078-1083 只记日志）⇒ run 停 running → 重启 `StartupRecovery` 收成 failed+recoverable（`RunMapper.xml:715-735`）→ 人工 CONTINUE → `resumeAsync`（`WorkflowService.java:697-738`）删未完成节点后同 runId 重跑 ⇒ 已完成物理动作再做一次。正确先例未被引用：`StartupRecovery.java:130-166` 隔离不确定 run 时标 quarantined + 抬 `RuntimeHold.Scope.EXPERIMENT`。
- **影响**：照 §5.8 写恢复预案 = 物理动作重复（开盖/移液/封膜做两次）= 安全事故；T1 运行期失败则 run 变哑巴 failed，无人工入口。
- **建议改法**：删除 L385，改恢复矩阵三行（命令证据充分成功 ⇒ 补写物理完成+effect，不重做；证据不确定 ⇒ NEEDS_RECONCILIATION + run quarantined + experiment hold + 人工确认，禁止 resume 重派；证据明确失败未执行 ⇒ 不建 effect、按既有失败策略）；T1 失败定义为 run 级隔离（quarantined + experiment 级 runtime_hold）；修正 L263 的 T1 定义措辞；§11.2 加 T21。

### M3【P1】【设计风险】完成挂点机制不可按现签名实现，且"两条路径注入"与源码不符
- **来源**：S3 / G3 / G4。
- **文档位置**：§5.7 L369-379；§5.5 L330-345；§5.3 L285；§13 L800。
- **证据**：`executeNode` 签名 `(RecoverableNode, RunProgress, StepExecutor)`（`RunStateMachine.java:87-89`），`StepContext` 只带 nodeId/key/capability/method/resource/attempt/steps/params（:107-109）——**无 loop/visit**；`visit` 是 `GraphRunner.run()` 局部 `Map`（`GraphRunner.java:504/536`），调用点 :649 不传 ⇒ §5.7"在 executeNode 挂点"与 §5.5"取内存 visit"不能同时成立（须改签名/加执行上下文，影响 GraphRunner:649、WorkflowService:1057/1065、RealWorkflowRunner:183 等调用点）。两条路径共用**同一** `RunStateMachine` 实例（`WorkflowService.java:982` 创建 → GraphRunner :997、顺序 :1057/:1065）⇒ "两条路径都注入"字面实现会重复触发（图路径两次，effect_index 生成两个序号，幂等键挡不住）。§5.3 L285 说 T1 含"节点完成"落库，§5.7 L377 要求物料通知在"节点标记 completed 之前" ⇒ 不能同时成立；`np.setStatus(COMPLETED)` 早于返回（`RunStateMachine.java:110-112`），DB 完成写是 `GraphRunner:650` 返回后做 ⇒"完成"指内存还是 DB 未写清；`physical_completed_at`/`material_sync_status` 的写入者与事务边界全文未定义。
- **影响**：S2 实现时 T1 包不包节点完成、谁写 physical 字段各写各的；下游 gate 依赖 `material_sync_status`，写入者不明 ⇒ 阻断不生效或误阻断。
- **建议改法**：单一挂点（`RunStateMachine` 构造注入一次），通知入参携带 `loop_visit`（图）/0（顺序）并列出受影响签名；给出 T1 精确写入集合与事务边界（建议 effect 插入 + run_node 三列同事务；节点 completed 仍由既有 recorder 写）；写明"内存 completed ≠ DB completed"及 hook 失败时行保持 running 的后果。

- **建议改法**：§5.5 改为"1 条汇总行 + N 条圈次行"；写明"现有 UPDATE 未过滤 loop_index ⇒ 新更新必须显式 `AND loop_index=0`，且不能用库里的 loop_index 做幂等/历史判断"；加"路径×场景→source_loop_index"映射表；把恢复后 visit 一致性列为 S0 验证项 + 集成测试。
