## 一、评审原文（要点摘录）

> 这次评审的重点是：这套设计能不能真正解决中控系统的物料追踪问题，是否符合现有执行引擎、数据库和状态管理机制，以及实施后会不会引入新的数据一致性问题。
>
> 暂不建议直接进入 S2。

**评审特别肯定的三点**（原文）：

> 1. 没有把位置变化和内容变化混为一谈。
> 2. 没有为了统一建模强行把膜、盖子都塞进一张表。
> 3. 把跨流程物料交接、事件触发、分装等复杂问题明确放到了后续阶段。

**评审指出的两处文档事实错误**（原文）：

> - §5.6 将 WorkflowService 描述为 boot 层服务。实际上，现有 WorkflowService 位于 labos-kernel/src/main 的领域层，WorkflowWebService 才在 boot 层。
> - §5.6 把 NodeEffectListener 描述为现成 listener 模式的延伸，需要明确它是新增接口，而不是现有 BuiltinListener 已经支持的功能。

**评审给出的最终建议**（原文）：

> 我认为应该把它提到整个中控系统的层面讨论。…… 不要把这项工作仅仅作为 Plate 功能升级，而应该作为 LabOS 物料领域的第一期建设。
>
> 先不要做 S1 建表。先把 S0 做好，尤其是物料生命周期、节点执行事实、循环幂等和异常恢复这四个问题。

## 三、被评审方逐条回应

> 依 `docs/评审规范.md` §四，逐条给结论 / 理由 / 处置 / 验证。

### O-1、O-6、O-9、O-23 · 事务边界与分层 —— **全部接受**

**结论**：接受，且**这是本次修订最大的一处改动**。

**理由（为什么会错）**：我原稿把"数据库事务"当成了"物理执行与状态一致"的保障。
评审指出得对 —— 设备已经动完，数据库回滚撤不回机械臂；
而且现有代码里 `run_node` 完成更新与 `run_command` 插入**本来就是各自的独立提交**
（命令先提交），"必须同事务"这个要求在当前架构下**根本满足不了**，我却在设计稿里当既有能力写。

**处置**：设计稿 v2 §5 整节重写为**两阶段模型**：

- **T1（执行事实确认）**：设备命令结果 + 节点完成 + **待处理的物料效果记录**（`PENDING`）落库。
  效果记录必须保存**声明快照 + 实际解析出的 `plate_id` + 幂等键 + 负载哈希**，
  不能只留一个 `applied` 标志。
- **T2（物料状态投影）**：在一个事务里"锁板 → 应用迁移 → 写审计 → 标记 APPLIED"。
  失败保留 `PENDING/FAILED` 并告警、转人工，**禁止静默吞掉**。

补偿按**效果记录里已解析出的 `plate_id`** 重放，**不重跑 `target.by=position`**（板可能已经搬走）。

**验证**：v2 §11 已把评审给的 8 个异常场景逐条列进验收表。

### O-2、O-13 · 归属模型 —— **全部接受**

**结论**：接受。

**理由**：我原稿用一组 `owner_*` 同时承担"当前归谁 / 谁生产的 / 谁最后改的"三件事，
评审给的例子（同���块板依次被 A/B/C 三个 Run 加工）证明它**必然丢失历史产出关系**。

**处置**：v2 §4.4 拆成三个独立概念：

| 概念 | 落点 | 语义 |
|---|---|---|
| 当前归属 | `plate.current_run_id` | 当前由谁管（可被覆盖） |
| 生产来源 | `plate.origin_run_id` / `origin_node_key` | 最初由谁产生（不覆盖） |
| 加工历史 | `plate_state_audit` | 每次改变都留一行，含 `from_owner_*` / `to_owner_*` |

`/api/runs/{id}/materials` 改为**按审计/效果记录的 `source_run_id` 查**，不按当前 `plate.owner_run_id` 查；
接口文案改为"本 run 声明的物料结果"，不再称"新产出的板"。

### O-3、O-17 · `produces` 表达能力 —— **接受**

**结论**：接受。

**理由**：评审列的五种物料关系（加液 / 转板 / 分装 / 混合 / 取样检测）说明
"一块板 → 一个状态"的二元结构**把未来封死了**。

**处置**：v2 §6 改为统一的 **`materialEffect`** 契约（`inputs` / `outputs` / `operations`），
**独立列**（不再塞进 `params`，理由见 O-24 与 Kimi R6 的同类意见）。
本期**只实现一对一状态变化**，但**结构不封死扩展空间**。
`consumes` 按评审意见**从正式契约里移除**（本期只登记不执行，不该先占正式位置）。

### O-5、O-20 · 挂点与分层事实错误 —— **接受，明确承认错误**

**结论**：接受。**这两条是我原稿的事实错误。**

**理由（为什么会错）**：
① 我把 `GraphRunner.java:604` 当成"设备任务完成挂点"，实际它在 **`Kind.BUILTIN` 分支**里，
设备 TASK 的完成回调在 `:650`。我读代码时看到了这个行号却没核对它属于哪个分支 ——
**这是典型的"看到了行号就以为对"**。
② 我把 `WorkflowService` 写成 boot 层，实际它在 `src/main/java/com/labos/kernel/workflow/`
（领域层），boot 层的是 `WorkflowWebService`。

**处置**：v2 §3 与 §5.6 改正；§0 加一条"已收到的评审与处置"小节，把这两条错误**明写出来**，
不留过时描述（`docs/评审规范.md` §四"修正文档，不留过时描述"）。

### O-7、O-9 · 目标寻址 —— **接受**

**结论**：接受。

**理由**：我原稿的 `target.by=position` 没说清是源位置还是目标位置，
而机械臂搬板后**源位置已经空了** ⇒ 按位置猜板必然找错。

**处置**：v2 §6.3 改为：
**物料身份优先**（`plate_id` / `barcode`），**位置只是解析的辅助信息**；
位置寻址必须在事务内校验 `tenant_id + resource_id + occupied_by_run`（fail-closed，
与现有取板路径的归属校验同口径）；条码寻址也要校验预期位置/归属。

### O-8 · 审计表信息不足 —— **接受**

**结论**：接受，且这条**比表面更重要**。

**理由**：评审那句"系统根据节点声明写入状态，不等于设备真正检测到了物料状态"——
我原稿把两者混为一谈了。**这是两种不同证据强度**。

**处置**：v2 §7 审计表补齐物理命令 ID、逻辑轮次、失败原因、状态确认来源、
是否人工确认、迁移前后归属；并引入**证据来源**枚举：
`DEVICE_CONFIRMED` / `EXECUTION_DECLARED` / `MANUAL_INVENTORY` / `MANUAL_CORRECTION` / `RECONCILIATION`。
**系统按声明写的 ≠ 设备确认的，UI 上必须区分显示。**

### O-10、O-11 · 领域模型与孔位级边界 —— **接受**

**结论**：接受。

**理由**：我原稿把"容器"当成了物料的全部。评审指出
**一块 96 孔板每孔装不同样品**时，`plate.content_state` 无法表达 ——
但**孔位级模型其实早就存在**（`plate_well` / `sample` / `sample_aliquot` 三张表都在，
只是没数据），所以第一期**绝不能再立一个能与孔位真源打架的板级真源**。

**处置**：v2 §4 引入 Material 领域分层（Material → Container / Consumable / Sample / Reagent / Waste），
把字段改名为 **`process_state`（板级工艺阶段）**，并写死三条边界：
① 本期描述的是**整块容器的工艺阶段**；② **不代表孔位级样品内容**（那是 `plate_well` 的事）；
③ **不代表体积/浓度等物理化学属性**。
「还剩几块空板」的验收口径按 `plate_well.status`（`empty/filled/consumed/invalid`）定义，
**不另立一个 `empty` 状态**。

### O-12 · 租户约束 —— **接受**

**结论**：接受，并**承认我原稿的现状描述不完整**。

**理由**：评审指出 `WorkflowWebService.TENANT = 1L` 是写死的 ⇒
"新表有 `tenant_id`" ≠ "租户隔离已实现"。我只查了 `plate` 表有 `tenant_id`，
没查**租户上下文是否真的贯穿**。

**处置**：v2 §4.2 / §7 / §10 写明三件事：
① 字典与 `plate` 之间加复合外键（或等效一致性校验）；② 字典项**停用而非物理删除**
（已被引用的要保留历史显示）；③ **租户隔离现状未达标**这件事明写为已知问题，
新代码不得假设多租户已成立。

### O-14 · 循环轮次 —— **接受**

**结论**：接受。**这是会直接破坏工艺语义的硬伤。**

**理由**：我原稿的幂等键 `(owner_run_id, owner_node_key, plate_id)` 漏了轮次。
`GraphRunner` 确实有 `visits.merge(key,1,...)` 与 `roundRecorder.record(key, visit, ...)`
⇒ 同一节点在同一 Run 里跑三次，**第三次会撞唯一索引** ⇒ 循环语义直接坏掉。

**处置**：v2 §5.3 幂等键改为
`tenant_id + source_run_id + source_node_key + source_loop_index + plate_id`，
**`attempt` 不入键**（设备/节点重试要能去重）；
同键同负载可安全跳过，**同键不同负载必须报错**（不能静默吞掉设计变化）。

### O-15、O-16、O-18 · 字典与耗材判据 —— **接受**

**结论**：接受。

**理由**：`plate_type` 是**板型规格**（`96/384/24/tube_rack`），我提议改成工艺角色会**丢规格**；
耗材判据只看"是否追踪位置"太窄 —— 有独立条码/批次/有效期/可重复使用/库存/使用追溯的
同样需要独立实体。

**处置**：v2 §4.1 **不动 `plate_type`**（它继续表示规格），工艺角色若需要另加列、本期不加；
§4.3 耗材判据改为「**是否需要独立身份或生命周期追溯**（位置、批次、库存、附着历史、复用等）」。

### O-19 · 「零风险上线」措辞 —— **接受**

**结论**：接受。

**理由**：这句话不严谨 —— 老流程不配置物料效果确实不改原执行行为，
但**新旧查询、租户隔离、迁移脚本、失败处理**都要独立验证。

**处置**：v2 §10 措辞收紧为"老流程的执行行为不变"，并列出仍需独立验证的四项。

### O-21、O-22 · 实施顺序与异常测试 —— **接受**

**结论**：接受。

**理由**：评审说得对 —— 模型没定就建表，等于把没想清楚的东西固化进 DDL。

**处置**：v2 §12 插入 **S0（领域模型定稿）**，把 S1 建表挪到 S0 之后；
§11 验收表补进评审给的 8 个异常场景。
