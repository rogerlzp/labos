## 一、结论与总体建议

**建议保留 v3.3 的总体架构，不推倒重来；但不能据此冻结 S0，也不能直接进入 S1 建表。**

v3.3 已经形成了正确的主干分层：

1. 物料身份、位置、内容与加工历史分离；
2. 执行声明、设备命令事实、物料效果分离；
3. `command_ledger` 与 `run_command` 分工，不让效果表兼任执行事实；
4. T1 执行事实记录与 T2 物料效果应用分阶段；
5. 效果采用六态，人工对账不伪造物理状态迁移；
6. 循环效果按声明快照与实际 Effect 对齐；
7. 扫码晚绑定使用 run 作用域 `scanRef`，不在扫码前猜身份；
8. 事件保留完整前后状态、版本与 changed_fields，支持重放。

这些是应保留的架构资产。本轮不建议新增通用 Execution Fact 平台，不建议把物料状态塞回 workflow params，也不建议让 LLM 或设备回包直接绕过规则写入物料真相。

但 v3.3 仍有几处“文档承诺强于数据模型实际保证”的问题。尤其是**执行声明快照不可变性、Effect/Event 同板约束、物理派发事实的恢复锚点**，这三项若不修，会破坏审计链或恢复正确性。

## 二、阻塞项（P0）

### P0-01：执行声明快照没有真正不可变的持久化载体

**涉及位置**：§5.3、§5.5、§7 中 `run_node.input.material_effect_snapshot` 的方案。

**问题**：

v3.3 将 run 启动时的物料效果声明快照放在 `run_node.input.material_effect_snapshot`。但文档同时列出的现有节点更新路径（如 `updateNodeStateLive`、`updateNodeResult`、整单结束 flush）会更新 `run_node.input` 或整行输入内容。只要这些更新仍可覆盖该字段，所谓“启动时冻结的声明”就不是不可变事实。

这不是字段命名或文档措辞问题，而是幂等与恢复的基础：若执行中声明快照被后写覆盖，后续 Worker、循环门禁或恢复逻辑就可能按新的声明解释旧的物理执行事实。

**建议裁决**：

- 首选：新增独立的 run 声明快照持久化载体，例如 `run_material_effect_declaration`，以 `tenant_id + run_id + node_key + loop_index + effect_index`（按实际声明粒度调整）作为稳定定位键。
- 快照内容至少包含声明版本/哈希、声明原文、生成时间、workflow/version 来源、声明解析结果；必须与具体 run 绑定。
- 快照写入后禁止 UPDATE/DELETE；更正只能产生新版本或显式撤销/替代记录，不得覆盖原记录。
- 若坚持放在 `run_node`，必须证明所有更新 SQL 都只更新指定列，永不整体覆盖 `input`；并用数据库权限或触发器保护快照子字段。仅靠“应用层约定不改”不够。

**验收条件**：

1. 对照所有节点状态更新、结果回写、重试、循环、整单 flush SQL，证明快照不会被覆盖；
2. 构造后续节点输入更新、节点重试、循环多轮回写，快照字节级保持不变；
3. 对快照 UPDATE/DELETE 的直接 SQL 操作应被数据库层拒绝；
4. 恢复时只读取持久化快照，不从当前 workflow 定义重新计算历史 run 的声明。

### P0-02：Effect/Event 关联约束未保证同一块板

**涉及位置**：§7⑥、§7⑧，Effect 与 `plate_material_event` 的外键。

**问题**：

文档说明事件是某个 Effect 应用后产生的状态变化，但当前复合外键如果只约束 tenant/run/effect，而不包含 `plate_id`，数据库只能保证“同租户、同 run 的某个 effect”，不能保证 Event 记录的 `plate_id` 就是该 Effect 的 `plate_id`。

因此可能出现：Effect 指向 A 板，Event 却记录 B 板。两行各自合法，组合语义错误，且后续按板重放、审计和版本链都会受到污染。

**建议裁决**：

- 在 Effect 侧建立包含 `tenant_id, source_run_id, plate_id, id` 的唯一键（或等价可被引用的唯一约束）。
- Event 到 Effect 的外键同时包含 `tenant_id, source_run_id, plate_id, effect_id`。
- 约束中的列顺序、类型、NULL 语义与唯一键完全一致；不要以应用层校验代替。
- 若一个 Effect 允许跨板，必须先改变领域模型并明确一对多关系；当前设计的单板 Effect 语义下，不允许跨板 Event。

**验收条件**：

1. 同租户、同 run、同 Effect、但错误 plate_id 的 Event 插入必须失败；
2. 正确 plate_id 的 Event 插入成功；
3. 跨租户、跨 run、跨 Effect 的反向测试均失败；
4. 对应外键与被引用唯一键在真实 PostgreSQL 中成功创建。

## 三、严重项（P1）

### P1-01：Append-only 目前主要是设计约定，缺少数据库层防篡改保证

**涉及位置**：§7 的 `plate_material_event`、Effect action、身份绑定审计等历史表。

**问题**：

“不可变事件流”“只追加”若没有数据库角色权限或触发器保护，仍可被 UPDATE/DELETE。应用代码不提供更新 API，不等于数据层不可修改。

**建议**：

- 对运行时应用角色撤销历史表 UPDATE/DELETE 权限，只保留必要的 SELECT/INSERT；
- 对必须由迁移/运维角色维护的场景，使用独立高权限角色，并将操作纳入审计；
- 可增加拒绝 UPDATE/DELETE 的触发器作为纵深防御；
- 明确哪些表是 append-only，哪些是可变投影（例如 reconciliation 当前处理状态），不要把两者混为一谈。

**验收**：以应用数据库角色执行 UPDATE/DELETE 必须失败；INSERT 正常；运维迁移角色权限边界有文档和审计记录。

### P1-02：Worker 的失败次数与退避更新可能随 T2 回滚一起丢失

**涉及位置**：§5.8 Worker 的单 Effect 事务、重试次数与退避设计。

**问题**：

若 Worker 在同一个 T2 事务中更新 Effect 状态、attempt_count、next_retry_at，随后 T2 失败并整体 rollback，则失败次数与退避时间也一并回滚。重试可能永远停留在同一 attempt，最大重试次数无法生效。

**建议**：

- 明确区分“业务应用事务”和“失败记录事务”；
- T2 失败后先 rollback，再由独立短事务记录失败次数、错误分类、退避时间与下一次可领取时间；
- 对“进程在 rollback 后、失败记录事务前崩溃”的窗口定义恢复策略，可由独立 attempt/worker-run 记录或可重建的领取/失败日志解决；
- 不要为了计数而引入长期 PROCESSING 状态；短事务锁定 PENDING 的总体思路可以保留。

**验收**：注入 T2 中途失败、进程崩溃、重复投递、双 Worker 并发等情况，证明 attempt 单调增长、退避生效、不会丢失或重复应用。

### P1-03：循环恢复不能只依赖 Effect/run_node 的最大 loop_index

**涉及位置**：§5.5、§5.8、§13.2 中循环恢复与物理执行事实的关系。

**问题**：

若设备命令已经派发或物理动作已经发生，但 T1 在 Effect 持久化前失败，单纯从 Effect 或 `run_node` 的 `MAX(source_loop_index)` 恢复，会看不到这次物理执行。恢复逻辑可能把该轮当成未执行，从而重复派发设备命令。

v3.3 已正确把 `command_ledger` 作为派发前命令事实载体；循环恢复必须真正以它为依据，而不是只在概念上提到它。

**建议**：

- 恢复扫描必须联合 `command_ledger`、`run_command`、Effect 与声明快照；
- 以已持久化的 command dispatch/idempotency 事实识别“已派发未回包”“已回包未落效果”“未派发”；
- 保存原始 loop_index、attempt、node_key、声明快照引用及命令参数摘要；恢复时不得根据当前循环计数推测原始执行轮次；
- 对无法确定物理结果的命令，进入 execution quarantine / reconciliation，不得自动重派。

**验收**：故障注入覆盖“派发前落账后崩溃”“设备已执行但回包丢失”“回包已收但 T1 失败”“Effect 未写入”等窗口；每种场景都能给出确定的恢复动作，未知状态不得自动重发。

### P1-04：节点级 material_sync_status 与一个节点多个 Effect 的聚合规则不够明确

**涉及位置**：§5.2b、§5.9、§7④、循环门禁。

**问题**：

一个节点可声明 1..N 个 Effect，而 Effect 状态独立。节点上的单一 `material_sync_status` 是聚合投影，不可能天然与某个 Effect 一一对应。若同一节点的多个 Effect 分别处于 APPLIED、FAILED、REJECTED、NEEDS_RECONCILIATION、CANCELLED，必须有确定的聚合规则。

否则节点投影可能与真实 Effect 集合矛盾，派发闸门就可能错误放行或永久阻塞。尤其是文档中“REJECTED 一一映射节点 rejected”的表述，只在恰好一个 Effect 或所有 Effect 同态时成立。

**建议**：

- 明确 Effect 行是门禁的唯一事实来源；节点级状态只是可重建的聚合投影。
- 给出确定性优先级/聚合真值表，至少覆盖多个 Effect 混合状态、循环中部分缺失、某轮 CANCELLED、部分 APPLIED + 部分待对账。
- 建议原则：只要存在任何必需 Effect 未达到允许下游的状态，节点不得放行；REJECTED 是确定性拒绝，FAILED 是可重试失败，NEEDS_RECONCILIATION 是人工核对，三者不能互相覆盖。
- 定义节点级 rejected 的语义为“至少一个必需 Effect 被确定性拒绝”，而不是“Effect 与节点一一映射”。
- 每次聚合更新必须可由 Effect 集合重算，避免双真源。

**验收**：为 1 个 Effect、多个 Effect、多个 loop、多种混合状态建立真值表与参数化测试；门禁直接按 Effect 集合校验，并验证节点投影可完全重建。

### P1-05：manual_confirmed 证据等级不能由节点声明隐式授权

**涉及位置**：§5.3 的 acceptedEvidenceLevels、§6.1 的声明契约与人工确认 API。

**问题**：

如果 workflow_node 的声明配置可以把 `manual_confirmed` 列为接受证据等级，节点配置本身就可能隐式允许人工确认作为物理事实依据。人工确认是权限敏感的操作，不能仅由工作流作者或节点配置决定。

**建议**：

- 将“系统/设备允许接受的证据等级”与“操作者有权执行人工确认”分离；
- manual_confirmed 必须由独立权限、明确操作者身份、确认原因、证据附件/引用、时间与审计 action 共同授权；
- 节点声明可以要求更高证据等级，但不得授予人工确认权限；
- 对高风险物料迁移可要求双人复核或二次确认，是否启用由权限策略决定。

**验收**：无人工确认权限的用户即使节点声明包含 manual_confirmed 也不能确认；有权限用户必须提交原因和审计证据；所有操作可追溯。

## 四、其他需要收口的事项（P2）

### P2-01：S0 设计阶段与“必须在 S0 关闭 flow-run”的阶段定义冲突

§12 将 S0 定义为设计阶段、不改代码；§16.1 / §16.3 又要求在 S0 内处置绕过统一完成点的 `/api/experiments/flow-run` 与 ShadowRunner/单命令探针。

建议拆成两个概念：

- **S0-design**：设计冻结前完成领域模型、DDL、接口、状态机与风险裁决；
- **S0-safety containment**：进入 S1 前必须完成的物理执行通路隔离/禁用或统一纳管措施。

如果 flow-run 可能驱动真实设备，安全隔离不应因为“尚未进入 S1”而延后；但也不能把代码变更写成纯设计阶段已经完成。

### P2-02：DDL 幂等包装不能吞掉 schema drift

对 `duplicate_object`、`duplicate_column` 等异常简单吞掉，可能把“对象已存在但定义错误”误判成“迁移已成功”。

建议迁移执行前后读取 PostgreSQL catalog，比较列类型、默认值、CHECK、FK、索引谓词和约束定义；仅当对象定义与目标完全一致才允许判定为幂等成功。定义不一致必须失败并要求人工迁移。

### P2-03：AUTO 来源与一次性绑定需要数据库级约束

AUTO 应保持为保留编码命名空间，不应通过前缀启发式推断来源。建议明确 AUTO 创建来源、绑定次数、绑定前后 barcode、操作者/系统身份、证据引用与冲突处置；用唯一约束或条件约束确保一次性绑定。身份冲突不得自动采信设备 ID 或写入物料事件。

### P2-04：历史数据可信度与当前状态投影的重建边界

文档已承认历史圈次行不可信。建议进一步明确：哪些字段可以从事件流重建、哪些必须以现有业务表为准、哪些历史数据只能标 UNKNOWN。不得把“重建成功”表述成“历史事实已恢复”。

### P2-05：ShadowRunner/单命令探针的真实设备保护边界

若这些通路可能连接真实设备，必须有环境级硬保护（配置白名单、设备模拟器/隔离网关、生产凭证不可用等），不能只靠调用者自觉或文档警告。若当前无法证明其不会触发物理动作，应在进入 S1 前禁用生产访问。

## 六、明确保留、不建议回退的架构决策

1. 保留 Material 身份与 Location 位置分离。
2. 保留声明、执行事实、物料效果三分离。
3. 保留 `command_ledger`（派发前事实）与 `run_command`（回包结果）两表分工。
4. 保留 T1/T2 两阶段机制，物理动作不因数据库 rollback 而被假定撤销。
5. 保留六态 Effect 状态机及 append-only action/event 思路。
6. 保留 `scanRef` 晚绑定；扫码前不推测板身份。
7. 保留 AUTO 保留命名空间，身份冲突先对账。
8. 保留循环子过程的每轮参数绑定；`loop_index` 是幂等防线，不是物理执行事实的唯一来源。
9. 不把 LLM 输出直接作为身份、状态或物理完成证据。
10. 不以“文档已写”替代 DDL 真跑、故障注入和真机验证。

## 七、给下一轮设计修订的明确要求

建议下一版标为 **v3.4 修订候选**，只围绕本记录修订，不重开已达成共识的领域模型：

1. 先解决 P0-01、P0-02，给出明确表结构/约束/写入时序；
2. 补齐 P1-01 至 P1-05 的数据层约束、事务边界、聚合真值表和授权规则；
3. 更新 S0 冻结条件，将设计冻结与安全隔离前置分开；
4. 在文档中为每条规则标注“设计约束 / 已有源码事实 / 待实现 / 待验证”，禁止把建议写成既有能力；
5. 修订后由另一评审方独立复审；最终 DDL 必须从提交文件原样抽取到隔离 PostgreSQL 真跑，并做反向约束测试；

**最终裁决**：v3.3 是可继续演进的设计基线，但不是可直接冻结的稳定规格。先做 v3.4 收口，再考虑 S0 冻结与 S1 建表。
