## 2. 本次改动清单（3 个文件）

### A. `scripts/s2-add-missing-sims.py`（修改，上一会话遗留未提交）

补 6 类缺失设备模拟器（撕膜/液站/洗板/常温堆栈/制冷载架/PCR/磁力架，端口 19506–19512）。
上一版 20 分钟卡死的脚本，本次修了 5 处：

1. **SQL 无超时** → `q()` 加 `PGOPTIONS`（`lock_timeout=15s` + `statement_timeout=15s`）+ `subprocess.run(timeout=20s)`。
2. **psql 17 命令标签污染**（根因）→ `-t` 只吞 SELECT 表头，不吞 `INSERT 0 1`/`UPDATE 1`；
   `q()` 用 `INSERT ... RETURNING id` 时返回值带 `\nINSERT 0 1`，拼进下一条 SQL 直接语法错误。
   → `q()` 加正则过滤命令标签行。
3. **Popen 管道泄漏**（20 分钟卡死的真正机制）→ `launch_sim` 的 `Popen(shell=True, start_new_session=True)`
   留下的 `/bin/sh -c` 包装进程继承父 stdout 管道；脚本接 `| tail` 时 tail 永远收不到 EOF。
   → Popen 加 `stdin/stdout/stderr=DEVNULL`。
4. **create_driver 先 DELETE 后 INSERT** → 上一轮已把 `device_instance.driver_id` 指到这些 driver，
   DELETE 触发 `device_instance_driver_id_fkey` 外键冲突。→ 改成「存在则 UPDATE、否则 INSERT」。
5. **重复 bind** → `launch_sim` 前 `nc -z` 检查端口，已被旧模拟器占用则跳过。
6. 建 device/resource_node/device_instance 改 `ON CONFLICT DO UPDATE ... RETURNING id` 幂等。

## 5. 未完成：板子"位置/流转"追踪（核心缺口）

> ⚠️ **本节根因已过时（2026-11-13 评审纠正）**：下面的 `resolvePlateId`/`AUTO-{runId}`
> 根因判断是错的（写入方早已存在，见下方 §5.1）。最终口径与实施见
> `docs/评审记录/20261113-02-物料追踪-评审检查清单.md` 的「区 4 定稿方案 · M」与
> `docs/architecture/点位初始化与物料身份-设计_20261113.md`。

现状证据（run 1001389）：

- `transfer_transaction`：6 条搬运 `plate_barcode` **全空**（只有 source→target 资源 id）。
- `plate_location_audit`：本 run **0 行**。
- `position_evidence`：全表 **0 行**；`position_state` 停在 11-11 旧数据。
- 内核日志每步 `[PLATE] <method> dev=<id> plate=AUTO-1001389 -> pos=null`（占位）。

根因（已定位，代码位置）：

1. `WorkflowService.writeStep` 调 `PositionLock.resolvePlateId(params, rawResponse, runId)`：
   Transfer 节点 methodParams 只有 `source/target`（资源码），无板号 → 兜底返回 `AUTO-{runId}`。
2. `PositionLock.notePlateMove` 只认 `Deposit/Input/Put/Load/Store` 与 `Withdraw/Output/Get/Unload/Retrieve`
   前缀，**不认识 `Transfer`** → 直接返回 null，不写位置。

建议两步（未实施）：

1. Transfer 节点 methodParams 增加板号字段（如 `plate="<板号>"`），`resolvePlateId` 读到真板号。
2. `notePlateMove` 增加 Transfer 分支：写 `plate_location_audit`（from=source 设备位、to=target 设备位、
   operator=AUTO、run_id）+ 更新 `position_state`。

### 5.1 评审修订（2026-11-13，⚠️ 上面两步的根因与方案需整体重写）

> 完整逐条结论见 `docs/评审记录/20261113-02-物料追踪-评审检查清单.md`（含代码位置与只读实测证据）。
> **实施前请以清单「区 4 定稿方案」为准**，照本节原文改会改错地方。

**根因纠正**

1. `transfer_transaction.plate_barcode` 的写入方**早已存在**，且不经过 `resolvePlateId`：
   `DriverStepExecutor.java:361` 读 `params.plate` → `TransferTransaction.begin():27-33`
   → `TransferMapper.xml:8-15`。全空是因为流程 `methodParams` 只有 `source/target`
   （实测全表 56 条、0 条有板号、本 run 6 条），不是 `AUTO-{runId}` 兜底造成的。
2. `plate_location_audit` 也有**自动**写入方：`PositionLock.putPlate:212 / takePlate:271`
   → `auditPlateMove:301-317` → `PauseMapper.xml:199-205`（`operator='AUTO'`）。
   本 run 0 行是因为 20 节点流程里没有 `Deposit/Withdraw` 前缀方法。
3. `position_evidence` 在 `TransferTransaction.confirm()` 时才写（`TransferMapper.xml:40-46`）；
   `REPORTED` 只是「运动报告」，按 P-08 设计位置必须另有独立证据才能 `CONFIRMED`
   （`TransferTransaction.java:8-14`）。**自动更新 `position_state` 会绕过该门禁，属设计变更**。

**方案纠正**

4. 只加 `plate` 键**不够**：`PositionLock.resolvePlateId:465` 只认
   `plate_id/plateID/plateId/barcode`，不认 `plate` ⇒ 两个消费点必须先统一键名（推荐 `barcode`）。
5. 「一行写 from=source 位、to=target 位」**按现有表结构做不到**：
   `plate_location_audit` 只有 `from_status/to_status/actual_location`，from/to 是状态不是位置。
   应写 2 行（取板 `KNOWN→IN_TRANSFER @source`、放板 `IN_TRANSFER→KNOWN @target`）。
6. `notePlateMove(deviceInstanceId, method, plateId, runId)` **拿不到 source/target**。
   ~~需改签名并改 `writeStep:2346-2349`~~ → **评审后纠正**：更严谨的做法是把位置登记放在
   `DriverStepExecutor.executeWithPlan:315-403` 的成功分支（该处已持有
   `db/tenantId/runId/srcRes/dstRes/plate/transferTxn`，且与 `TransferTransaction.report()`
   同时机），`writeStep` 继续只服务 Deposit/Withdraw，不重复解析资源码。
7. 即使加了分支，位置仍可能不动：实测 `position_state` 只有 4 个位置有板且是 11-11 旧数据，
   `takePlate(srcRes)` 会因归属校验返回 `NO_PLATE_TO_TAKE(-2L)`，`writeStep` 只打日志不阻断
   ⇒ **需先做位置状态引导**。
8. 🔴 **新发现的 P0 安全漏洞**：`markPlatePositionUnknown():422-426` 读 `params.plate`，
   当前没有该键 ⇒ 搬运失败时无法把板标 UNKNOWN，系统仍以为板在源位，下一节点会「机械臂伸进空位置」
   （代码 `:408-411` 注释）。板号打通后此漏洞自动闭合。

**定稿方向（2026-11-13 用户拍板 M）**：自动更新 `position_state` 并置 `CONFIRMED`，
按「严谨方式」实施。完整设计见检查清单「区 4 定稿方案 · M」，要点：
① 恢复门禁**代码不改**，补一条合法的自动确认路径让事务变 CONFIRMED，门禁自然放行
（短路门禁 = 丢掉 fail-closed，反而不严谨）；
② 位置登记放在 `DriverStepExecutor.executeWithPlan` 成功分支（那里已有全部上下文），
**不**改 `writeStep`/`notePlateMove` 签名；
③ `DEVICE_REPORT` 只在「真实板号 + 抢锁成功 + 回包 OK + 取板归属校验 + 放板落库 +
has_plate 刷新」全部满足时才自动确认，且由 `LABOS_TRANSFER_AUTO_CONFIRM` 开关控制
（默认关、**按 workflow 生效**，本次取值 `1000830`；全局开启会阻断另外 22 个无板号流程）；
④ 必须补 `putPlate` 后 `plate.position_status` 仍停在 `IN_TRANSFER` 的缺口。
