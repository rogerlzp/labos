### （一）P0 · 阻塞（2 条）

**V9-01【P0·完整性缺口 + 事实错误】§5.3 Q6 巡检兜底不成立：漏判孤儿/空板/跨租户三类违规。**
- **来源**：D1 / G5（多源印证；DDL 子代理临时 PG 实测）。
- **位置**：§5.2 R6:495、§5.3 Q6:523-527、§7.4 D2:627、§8.1 条件 #2:648、§11.4 第 7 项:756。
- **问题与证据**：Q6 用 JOIN plate_material_effect e ON e.id=v.effect_id AND e.tenant_id=v.tenant_id + v.plate_id <> e.plate_id 实现「event→effect 同租户/同 run/同 plate」。在 §4 建出的库上用原样 SQL 实测构造违规：①event.effect_id=999999（孤儿）可写入（无 FK），INNER JOIN 直接丢行 → Q6 返回 0 行；②effect.plate_id=NULL（NEEDS_RECONCILIATION 允许）而 event.plate_id=P1 时，<> 对 NULL 求值为 NULL → 被过滤；③event(tenant=2) 引用 effect(tenant=1) 可写入，join 的 tenant 条件直接让该行不进入结果集。对照：普通 plate/run 非空不一致 Q6 能发现（因此 §11.4 第 7 项只对部分场景成立）。⇒ 无 FK 策略依赖「业务层写入校验 + 巡检 + 测试」三件套，Q6 是 openai P0-02 一致性的唯一巡检项；漏判使 §8.1 条件 #2 可在存在跨租户/孤儿数据时判 PASS；event append-only 无删除/失效入口，坏事件写入后无法修复（只能再加事件，重放流仍污染）。
- **影响**：P0-02 的残余风险未闭环，「巡检 0 行」提供虚假安全感；S1 的 D2 验收失真。
- **建议**：Q6 改写为不依赖 INNER JOIN 的形式（NOT EXISTS + 同租户 + IS NOT DISTINCT FROM 处理 NULL），并补 Q11（event→effect 存在性/同租户）等；§8.1 条件 #2 在 Q6 修好并反向验证前标「未达成」；给事件表加「无效/被替代」机制或明确坏事件只能新增 correction 事件并人工标记；T-R6 需指定低层写入函数/直接 SQL 双路径测试。

**V9-02【P0·设计风险 + 事实错误】§3.7 闸门按「全部直接前置」读执行确认状态：结构节点与旧数据永远不是 completed，第一版第一个 TASK 就被挡。**
- **来源**：G1（设计一致性）+ S8/G10（相关）。
- **位置**：§3.7:256-261（尤其 L258）、§3.1:144-145、§3.2:170-174、§3.3:189、§11.4:758。
- **问题与证据**：图模型除 TASK 还有 START/网关/BUILTIN（GraphRunner.java:513/560/570/633 按 Kind 分支；只有 TASK 走 executeNode），START/网关不产生 run_node/不调用 handler ⇒ execution_resolution_status 保持 unresolved；按 §3.7 字面规则，第一个 TASK 的直接前置是 START（unresolved）⇒ 永远不满足 completed ⇒ 不派发；网关后的 TASK 同理。旧 run 的 status='completed' 节点被 §3.2 归入 unresolved（§11.4 #9 实测）⇒ 续跑后任一后继被挡。文中的「或 not_required 语义」只说明 material_sync_status，未说明执行确认如何豁免；全文没有「前置域」定义。
- **影响**：按字面实施第一版无法执行任何图；旧数据续跑全部卡死。这是「第一版可做性」的 P0 级阻塞。
- **建议**：①定义闸门前置域：只对「物料相关的前置 TASK 节点」求状态，结构节点按图语义穿透/跳过；②定义老数据映射：老 node_status='completed' ⇒ legacy_completed（或迁移写 execution_resolution_status='completed'+evidence_level='legacy' 并放开 physical_completed_at），闸门放行、续跑跳过、永不重派；③把「TASK 前驱链/网关/BUILTIN/老 run/顺序路径」列成 §7 验收用例。

**V9-05【P1·设计风险 + 事实错误】「单 Effect ⇒ 节点状态一一映射」在循环多圈下不成立；source_loop_index 的「visit（无环=0）」与源码 visit 从 1 开始冲突。**
- **来源**：G4（另有 08-openai P1-04 同类）。
- **位置**：§1.3 H1:80-83、§3.5:215、§3.8:265-266、§1.2 D1:67。
- **问题与证据**：①「单 Effect」限制的是一圈，不是整个节点：循环节点每圈各一个 Effect（唯一键含 source_loop_index），N 圈就有 N 个 Effect；节点只有一列 material_sync_status，后一圈 APPLIED 会覆盖前一圈 FAILED/NEEDS_RECONCILIATION，闸门读节点列会放行早圈未闭环（08-openai P1-04 的原始问题未解）。②v4 写「source_loop_index = visit（1..N；无环/顺序=0）」，但源码 GraphRunner.java:536 使图执行的无环节点 visit=1，顺序执行没有 visit（应 0）；且 roundRecorder 只在 graphHasCycle 时写（:654）⇒ 无环图只有汇总行（loop_index=0），若按 1 写则 Q3 全量误报。
