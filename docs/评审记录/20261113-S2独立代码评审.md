## 二、优先核查的五项

### 1. CR-001：命令账本幂等键增加圈次后缀

**结论：非循环 key 符合；循环续跑不符合；结构化审计存疑。**

#### 1.1 非循环路径是否逐字节不变

**符合。**

- `labos-kernel/src/main/java/com/labos/kernel/driver/DriverStepExecutor.java:680-690`：后缀仅在 `ctx.loopIndex() > 1` 时生成；原 key 主体仍为 run、node、attempt、step、device、method 的原有拼接。
- `labos-kernel/src/main/java/com/labos/kernel/engine/StepContext.java:20-38`：兼容构造路径默认 loopIndex 为 0。
- `labos-kernel/src/main/java/com/labos/kernel/workflow/GraphRunner.java:676-687`：无环图将 round 置为 0；循环图才使用 visit。

因此普通非循环路径以及循环第 1 圈均不追加后缀；第 2 圈开始才追加 `|vN`。按当前代码，非循环路径 key 的字符串拼接结果没有变化。

#### 1.2 visits 从 1 重建是否会导致第 1 圈重复派发

**不符合（续跑语义）。**

- `labos-kernel/src/main/java/com/labos/kernel/workflow/GraphRunner.java:525-550`：每次 run 建立新的 visits 计数器，没有从持久化圈次恢复。
- `labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java:1069-1078`：续跑使用 skipKeys。
- `labos-kernel/src/boot/resources/mapper/RunMapper.xml:460-466`：completed 节点恢复集合按 level=0 的节点级记录构建，不包含已完成圈次。
- `RunMapper.xml:484-505`：续跑守卫检查命令账本等记录；`DriverStepExecutor.java:695-705` 对已存在的账本 key 不会再次创建成功派发。

因此不能简单断言“续跑一定会把第 1 圈物理命令重复下发”：账本对同一 key 有防重复作用。但当前恢复模型只有节点级 skip，没有圈次级 checkpoint。已完成节点可能被整体跳过，剩余圈次也无法准确恢复；未完成节点则可能因旧 key 冲突进入失败/人工处理。**防重复派发不等于正确续跑。**

应补充持久化的圈次进度与每圈执行结果，并明确崩溃发生在“命令已派发、圈次记录未提交”等窗口时的恢复规则。

#### 1.3 command_ledger 没有 loop_index 列

**存疑。**

- `DriverStepExecutor.java:680-690`：圈次信息只编码在 idempotency_key 的文本后缀。
- 当前结构无法直接按 loop_index 过滤、聚合或关联 run_node 圈次行，审计查询需要解析 key。

不要求第一版立即增加列，但应将 key 格式视为稳定协议，并提供统一解析/审计查询。否则后续 key 格式调整会破坏历史圈次解释能力。

### 2. R13-06：Effect 使用真实圈次，执行确认仍写 loop_index=0

**结论：不符合设计基线。**

- `labos-kernel/src/main/java/com/labos/kernel/engine/NodeResolution.java:1-20`：NodeResolution 已携带 loopIndex。
- `labos-kernel/src/main/java/com/labos/kernel/material/MaterialEffectService.java:511-516`：Effect 写入使用真实 loopIndex。
- `labos-kernel/src/boot/resources/mapper/MaterialMapper.xml:61-88`：执行确认更新条件限定 `loop_index = 0`。
- `labos-kernel/src/main/java/com/labos/kernel/workflow/GraphRunner.java:693-700`：执行节点后才调用 roundRecorder。
- `labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java:2009-2016`：圈次行在 roundRecorder 路径中插入，晚于执行。
- 设计基线 §3.1、§3.2、§8.2 第 2 项要求圈次执行事实可落到对应圈次行，并要求执行前创建/挂起本圈 run_node 行。

当前结果是 Effect 能区分圈次，但圈次行 execution_resolution_status 保持 unresolved，执行确认落在 loop_index=0 汇总行。该实现无法完整回答每一圈是否完成、是否需要对账。

**Q18：直接相关。** completed 圈次行仍为 unresolved，会被“completed 且 execution_resolution_status unresolved”的巡检条件命中。

**Q15b：不是同一根因。** `MaterialMapper.xml:184-205` 的 material sync 更新/查询口径也存在汇总行与圈次行投影不一致问题；它与 R13-23 的圈次物料同步投影缺陷相关，不能把 Q15b 全部归因于执行确认字段。

**处置判断：** 若坚持执行确认只写汇总行，这是对冻结设计语义的变更，应走 CR；若继续遵循 v4.2，则是实现缺陷，应落实 §8.2 第 2 项——执行前创建圈次行，T1 更新该圈次行，节点汇总另行投影。当前不应将 R13-06 记为已修复。
