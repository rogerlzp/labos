## 2. 逐项核验

### R3 暂停收敛（`64b19a6`）——成立，带 1 个 P2

- 暂停 settle 时经 experiment_run→experiment→run→run_node 四表关联查 `execution_resolution_status='reconciliation_required'`，存在则 `pause_kind` 落 `manual` + 原因「设备物理结果不确定」。SQL 路径、排除 `paused_fault`（自动恢复断连不归并此口径）均与 03 设计一致。
- ⚠️ **P2-1（fail-open）**：`ExperimentExecutor.java:620-628` `hasReconciliationRequired` 的 catch 块查询失败返回 `false`，日志写明「按 clean paused 收敛」——这是**故意的 fail-open**，恰是设计文档自己立了铁律（UNKNOWN 合法终态、宁可不确定不可假确定）的方向。应改 fail-closed：查询异常时按存在 reconciliation_required 处理（落 manual）。改动是 catch 里 `return false` → `return true`，成本极低，建议在 R8 同批做掉。

### R5 启动在途板可见性（`1040cca`）——成立，带 1 个 P2

- ⚠️ **P2-2（可见性偏弱）**：重启后启动日志会滚走，操作员无从得知「这块板状态可疑」。日志只是开发可见性，不是操作员可见性。建议落到 operator 可见的 alerts/人工处理窗口（哪怕先是一张 `in_transit_alerts` 只读视图）。不挡 R8，但要在 R8 验收口径里补一条判据。
