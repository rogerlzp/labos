## 二、致命问题

### F-01 · §4.3 第 2 层归属键（设备占用者）在 E3 场景结构性失效

**位置**：§4.3 三层归属键表（第 2 层）、§10 问题 2

**核对（三段证据链）**：

1. **真实流程的结构必然是"设备命令节点 → `__awaitEvent` 节点"**。
   `scripts/setup-extraction-flow.py` 第 449–454 行：

   ```python
   n_pick = b.task(f"{code} 取磁套", protocol="PickTipComb",
                   resource=d["resourceId"], params={"plateIndex": 0}, ...)
   n_wait = b.task(f"等 {code} 等待交互", protocol="__awaitEvent",
                   params={"device": code, "eventType": EV_WAIT_INTERACTION,
                           "timeout": 600, "into": f"{code}_wait"})
   ```

   提取流程的每个阶段都是"**取磁套**（设备动作）→ **等等待交互**（`__awaitEvent`）"。

2. **设备锁在 step 结束时释放**。
   `WorkflowService.java:3169-3181`（`onStepDone`）与 `:3136-3160`（`onStepAborted`）都调 `DeviceLock.release(resNodeId, runId)`；`onStepStart`（`:3091-3110`）才 `acquireWithWait`。
   而 `__awaitEvent` 是 `GraphRunner` 内置节点（`:1068-1070` → `waitForDeviceEvent`），**不经过 `DriverStepExecutor` 的 step 生命周期**。

3. **结论**：`__awaitEvent` 等待期间，**该设备的 `device_state.current_run_id` 必然为空**（或属于另一个 run）。§4.3 第 2 层写的归属键 `device_lock.current_run_id` —— **在 E3（设备自发事件）的定义场景下拿不到值**。

**这不是"设备锁释放后事件才到"的窗口问题，而是常态**：E3 的定义就是"设备跑到交换点、主动上报"，而流程此时正卡在 `__awaitEvent` 节点里等它 —— 按流程结构，此刻设备锁早已在**上一个节点结束时**释放了。

⇒ §4.3 第 2 层在它**唯一适用**的事件类型上失效，E3 归属链是断的。

**建议（三选一，按落地成本排序）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | E3 归属改用**事件自带标识**：`device_event` 已有 `process_id` / `interaction_step` 两列（schema `:4975-4976`），且 `DeviceEventController:90-91` 已经在读这两个字段。侧车/设备侧只要能给出工位或交互步标识，归属就成立 | 需要设备侧配合（落在 H-03） |
| **B** | 在 `__awaitEvent` 节点**登记"等待占用"**：不等设备锁（那会独占设备），而是新增一张"设备等待者"登记（run_id + device + 等待起止），归属时查它 | 新增机制；但语义干净，且能顺便做"同设备多等待者排队" |
| **C** | `__awaitEvent` 等待期间**持有设备锁** | **不建议**：设备在等待全程被独占（timeout 600 秒），与 §3/§4.1 的利用率目标直接冲突；且这正是上一轮已否掉的"持锁"路 |

**§10 问题 2 的答复：会出错，且不是窗口而是常态。** 若采纳 A 案，H-03（设备协议能支持 §5 五条中的哪几条）就从"待确认"升级为**事件归属的关键前置**。

## 四、严重问题

### F-02 · §4.5"NOT_FOUND ⇒ 可重发"与系统既有的有意设计相反

**位置**：§4.5 断线处理顺序、§7.2 C-03、§10 问题 4

**核对**：`CommandLedger.reconcileWithQuery` `:171-220` 的四分支里：

```java
case NOT_FOUND, UNKNOWN -> {          // :211  ← 两者合并处理
    mapper().markQueriedUnknown(ledgerId, "查询后仍无法确认，需人工对账；" + queryEvidence(query), 250);
    ...
}
```

源码注释 `:169` 写得很清楚：

> **NOT_FOUND 不等于「设备没动过」，同样落 UNKNOWN。**

`CommandLedger:21-22` 的类注释也划了边界："**同 key 禁止重复下发**"；`DriverCommand:10-12`："靠 150ms 轮询 + ack 超时重发，没有幂等键，**重发就是真重做**"。

⇒ 文档把 `NOT_FOUND` 判成"设备没收到，可安全重发"，并写成验收期望 C-03（"重发前 `queryStatus=NOT_FOUND` → 允许重发"）。**这与系统现行的安全原则相反。**

**为什么不能这么判**：`NOT_FOUND` 的真实含义是"设备侧查不到这条命令"——可能是设备**执行了但状态记录丢失/设备重启**，或**查询能力超时/不支持**。在物理动作上重发 = 机械臂把同一块板搬两次。而 §4.4 自己列了"禁止自动重发的命令：物理动作（移液、搬运、开盖、离心、封膜）"，说明文档知道这个风险，但 §4.5 的决策表没有把它贯彻到 `NOT_FOUND` 分支上。

**建议**：决策表改为——

| queryStatus | 物理动作类命令 | 查询/幂等设置类命令 |
|---|---|---|
| `NOT_FOUND` | **不自动重发**（转人工；或仅当设备已通过 §5 第 1/3 条且 HIL 验证去重行为时，才允许同 commandId 重发） | 可重发（同 commandId） |
| `IN_PROGRESS` | 不重发，继续等 | 不重发 |
| `COMPLETED` / `FAILED` | 采纳结果 | 采纳结果 |
| `UNKNOWN` | 不重发，转人工 | 不重发，转人工 |

**§10 问题 4 的答复**：设备不支持 `queryStatus` 时**只能人工确认** —— 现有实现已经如此，文档不必改这一块；反过来应该**删掉**"NOT_FOUND 可重发"这条推论，改为"按 §5 准入条件分档"。

### F-03 · §4.4 的 `commandId` 稳定性方案与自己的 attempt 表格自相矛盾

**位置**：§3.3、§4.4、§7.2 C-01/C-06、§10 问题 3

**问题 1（内部矛盾）**：§4.4 的表格定义

| 概念 | 重试时 |
|---|---|
| `attempt` | **递增** |
| `commandId` | **不变** |
| `ledgerKey` | 含 attempt，**会变** |

而 §4.4 第二步的判定入口是"**`ledgerKey` 已存在** → 读账本 state → `queryStatus`"。

⇒ `attempt` 递增 ⇒ `ledgerKey` 变 ⇒ **新 attempt 的 ledgerKey 从来不存在** ⇒ `CommandLedger.begin` 返回 `created=true` ⇒ **直接下发，`queryStatus` 判定分支永远进不去**。第二步整棵判定树在新 attempt 上不可达，重发防护形同虚设。

同时：**同一 `commandId` 会对应多条账本行**（attempt 不同、commandId 相同），文档没有定义这种状态该长什么样、`resolve()` 该以谁为准。

**问题 2（事实层面）**：§3.3 说"`exec` 每次执行递增 ⇒ **重试时会变**"。源码注释（`DriverStepExecutor:140-142`）写的是另一种语义：

> 用来构造**稳定的命令幂等键**：**同一次执行内的重试复用同一个 id**，**循环里第二次执行则换新 id**。

⇒ 同一次执行内的重试**已经**复用同一个 id（`exec` 是作为参数传进 `executeWithPlan` 的，不在重试时递增）。真正会让 id 变的是另外两件事：

- **循环第二轮**（`exec` 递增）；
- **resume**（`WorkflowService:1069` 每次执行 `new DriverStepExecutor(...)` ⇒ `execSeq` 从 0 重来 ⇒ 同一节点续跑时拿到的 `exec` 与首次不同）。

⇒ 所以"去掉 `exec`"这个动作的真实语义是：**把 resume 场景的 id 从"每次都新"改成"永远复用同一个"**。这正是 §10 问题 3 的核心。

**§10 问题 3 的答复**：resume **不需要**区分"新一轮"与"同一轮重试"——真正的目标是"**同一条物理命令在设备侧只执行一次**"。而这个目标是否可达，取决于设备：

- **设备严格按 commandId 去重**（通过 §5 第 1/3 条并经 HIL 验证）⇒ 稳定 id 正确，resume 复用旧 id，设备会拒绝重做；
- **设备不去重**（老设备）⇒ 稳定 id 会让 resume 后的重发被设备当新命令执行（漏做风险），或设备直接忽略（流程卡死）。**此时保留 `exec` 递增更安全 —— 宁可重做，不可漏做。**

⇒ 建议：`commandId` 稳定性**按设备能力分档**，不要一刀切；§5 协议准入第 1/3 条应明确写成"**只有满足该条的设备才启用稳定 commandId**"。另外 C-01 的期望"设备只执行一次"应改写为"**设备只执行一次，或拒绝重复并被中控识别**"——两种都算通过。

### F-04 · §4.2 唯一索引的状态源问题未修（上一轮 X-05 遗留）

**位置**：§4.2 SQL（与上一版 §5.1 逐字相同）

```sql
ALTER TABLE experiment_batch_run ADD COLUMN active_slot smallint
  GENERATED ALWAYS AS (
    CASE WHEN status IN ('queued','running','paused') THEN 1 END
  ) STORED;
```

**问题 1：状态源选错。** `experiment_batch_run.status` 是 attempt 行的状态，而**真相源是 `experiment_run.status`** —— `BatchOrchestrator.loadBatches` 的派生口径明确"run 状态优先于 attempt 行"（人工停止/恢复直接改 run）。用 attempt 行 status 做唯一键 ⇒ 暂停/停止后 attempt 行可能仍停在 queued/running ⇒ 唯一键失效 ⇒ **P-25 幂等验收会假绿**。

**问题 2：`paused` 会永久占位。** `BatchMapper.xml:232-237`：

```xml
<update id="finishBatchRun">
    UPDATE experiment_batch_run
       SET status = #{param3}, error = #{param4},
           finished_at = CASE WHEN #{param5}::boolean THEN now() ELSE finished_at END
     WHERE tenant_id = #{param1} AND id = #{param2}
</update>
```

paused 传 `terminal=false` ⇒ **`finished_at` 不落、status 仍是 `paused`** ⇒ 该行永远满足 `active_slot=1` ⇒ **同一批一旦暂停过，就再也建不出第二个活跃尝试**。若把 paused 移出 active 集合，又会允许"暂停期间重跑"，与 D4（只允许非 completed 批重跑）冲突。

⇒ §4.2 需要给出：唯一键的表达式基于 `experiment_run.status`（或改成触发器/函数索引），以及 **paused 的占用语义**到底归谁。

**§10 问题 1 的答复**：把互斥粒度降到 batch attempt **不够**，存在**第三条**会造出双 active 的路径 —— **resume 路径**。`PauseMapper.resumeToQueued` 的 `UPDATE run SET status='queued'` **无状态守卫**，能把 `failed` 的 run 复活成 queued 并真的续跑，绕过新建路径上的任何门禁与唯一索引。⇒ §4.2 需要显式写出"resume 再激活也要纳入同一 active 判定"，否则建单侧收紧、resume 侧仍可双开。

## 五、事实性错误

### F-05 · §4.5 的前提（30 秒固定超时）已经过时

**位置**：§4.5 开头、§8 R-09

文档写："现有实现把三件不同的事混在一个 30 秒超时里（`MethodTimeoutPolicy` 注释'执行器级固定 30 秒'），这是根本问题。"

**核对**：`MethodTimeoutPolicy.java:6` 的类注释第一行就是"**方法超时策略：超时按方法取，不再由驱动层写死 30 秒**"；第 8–16 行描述的是**改动前**的历史：

> **为什么必须改**：改动前 `DriverStepExecutor` 用的是**执行器级固定 30 秒**……而 `device_method.timeout_sec` / `workflow_node.timeout_sec` 两张表里**存了超时值但驱动层从来不读**……后果是**任何耗时超过 30 秒的真机方法都被中控判超时**：离心 5 分钟、PCR 几十分钟、孵育 30 分钟全部必挂，与"暂停"无关，**是纯 bug**。

能力默认值已经配好（`:49-64`）：`INCUBATE=1800s`、`THERMOCYCLE=3600s`、`CENTRIFUGE=900s`、`TRANSFER=600s` 等；`DriverStepExecutor:945-946` 明确"取值优先级见 `MethodTimeoutPolicy`：设备方法级 → 设备能力级 → 流程节点级 → 能力默认 → 兜底 30 秒"。

⇒ 文档引用的是该文件里描述**改动前**的注释，把它当成现状。**R-09 同错。**

**影响（不小）**：§4.5 现在被描述成"拆三层"（工作量大、风险高、要动执行器），实际只需要**补一层**（等 ACK 的 1–3 秒窗口 + 断线检测）。两者的工期与风险估计完全不同。

**建议**：§4.5 改为"**当前是两层**：发出 → 等最终回包（超时按方法取，已解决长工艺误判）；**缺的是中间的 ACK 层与链路健康层**"。R-09 改为"已修复（`MethodTimeoutPolicy`），保留为回归观察项"。

### F-06 · §3.2 `DROP COLUMN device_event.run_id` 会破坏公开 API 契约

**位置**：§3.2

文档的论证（"死字段会误导后来者加 `AND e.run_id = #{runId}` 导致所有事件匹配不上"）**成立且有价值**。但删列这一步过头了：

- `DeviceEventController:31-34` 的 **javadoc 明写这就是对外契约**：

  ```
  POST /api/device-events
  {"device":"ID-EXT1","eventType":"waiting_interaction",
   "payload":{"station":"exchange"},"runId":123}
  ```

  `:88` 取 `runId`、`:101-102` 写库、`:141` 回显 —— 它是**已被公开承诺的字段**，第三方侧车/网关按这个形状实现。

⇒ 更关键的是：**F-01 成立之后，`run_id` 恰恰是最省事的 E3 归属替代路径**（侧车补填 → `claimEvent` 加 `AND e.run_id = #{runId}`），而不是一个该删的字段。

## 七、对 §10 十个问题的答复

| # | 问题 | 答复 |
|---|---|---|
| 1 | §4.2 把互斥粒度从 workflow 降到 batch attempt，是否足够？有没有第三条路径会造出双 active？ | **不够**。除应用层 `activeBatchAttempt` 必须同改（F-04）、唯一键状态源必须用 `experiment_run.status` 外，**第三条路径是 resume**：`PauseMapper.resumeToQueued` 的 `UPDATE run SET status='queued'` 无状态守卫，能把 failed 复活成 queued 并真的续跑，绕过新建路径的一切约束。§4.2 需显式纳入"再激活"这条写入路径 |
| 2 | §4.3 用"设备占用者"给 E3 归属，是否会在"设备锁释放后事件才到"的窗口出错？ | **会，且不是窗口，是常态**（F-01）。真实流程是"设备命令节点 → `__awaitEvent` 节点"，设备锁在上一节点 onStepDone 已释放 ⇒ `device_lock.current_run_id` 为空 ⇒ 第 2 层归属键在 E3 的定义场景下**必然取不到值**。建议改用事件自带标识（`process_id`/`interaction_step`）或新增"设备等待者"登记 |
| 3 | §4.4 去掉 `exec` 后，resume 如何区分"新一轮"与"同一轮重试"？ | **不需要区分** —— 真正目标是"同一条物理命令在设备侧只执行一次"。能否达成取决于设备是否严格按 commandId 去重：**去重设备**用稳定 id 正确；**不去重设备**保留 `exec` 递增更安全（宁可重做不可漏做）。⇒ 应按 §5 准入条件**分档启用**，不一刀切。另需修正 §4.4 第二步：`attempt` 递增会让 ledgerKey 变，"账本已存在"永远不成立，判定树不可达（F-03） |
| 4 | 设备不支持 `queryStatus` 时，是否只能接受"人工确认"？ | **是，且现有实现已经如此**（`CommandLedger:211` 把 NOT_FOUND 与 UNKNOWN 合并落 UNKNOWN 转人工，`:169` 注释解释 NOT_FOUND ≠ 设备没动过）。文档不必改这一块，反而应删掉"NOT_FOUND 可重发"这条推论（F-02） |
| 5 | R-01（跨类锁无全序）是否必须先统一全序，才能开并行度 2？ | **不必作为前置，但触发条件要改写**。跨类互等的真实场景不是"两个 run 并行"，而是**同一 run 内的 ParallelGateway 分支** —— 今天的提取流程就有 `b.parallel_gateway("并行拆分（磁套加载）")`，且 `DeviceLock:46-51` 已明确承认该场景并用 256 条线程级分片锁补互斥。⇒ R-01 是**既有风险**（今天就存在），不是并行度提高才有的；它决定的是并行度上限，不是开并行度 2 的前置条件 |
| 6 | 若未来上多实例，最小改造集是什么？ | 文档给的"一列 epoch + 三处条件更新 + 覆盖所有写入口"方向对，但**"三处"偏少**。写入口至少还包括：`RunMapper.settleTerminal/markFailed/markSettledPhase`、`ExperimentStateProjector`、`PauseMapper.resumeToQueued`（无状态守卫）、`ExperimentScheduler.markStatus`。更要紧的是 **epoch 只放 `run` 上不够** —— `run_node` / `run_command` / `command_ledger` 也必须带 epoch，否则旧实例写的账本行无法识别为"陈旧"，对账会误判 |
| 7 | 三层时间模型是否成立？"执行无超时"会不会掩盖"设备卡死不动"？ | **模型成立**（ACK 层确实缺，见 F-05：实际是两层→补一层），但"执行无超时"有一个**文档没写的代价**：设备既不发完成回包、心跳又正常（设备卡死不动）时，命令既不超时也不判异常，而**设备锁是 step 粒度、只在 onStepDone 才释放** ⇒ 该设备被长期占死，其他 run 永远等不到它。⇒ 需要一个**与命令超时分离的"设备锁占用时长"看门狗**（如同一 run 连续占用超过 N 分钟且无命令进展 ⇒ 告警/转人工），而不是靠执行超时兜底 |
| 8 | 人工"忽略并继续"的审计要求是否足够支撑事后追责？ | **方向对，但缺落点定义**（F-09）。现有 `CommandLedger.resolve()` 已带 by/note，但只有 done/failed 两态；"人工忽略"需要第三态，且"依据（照片/扫码）"要落到 `run_artifact`。建议 §7.2 C-10 与 §7.3 明确绑定这三处落点 |
| 9 | §7 验收矩阵是否遗漏"两实验共用设备 + 共用点位"？ | **是，且不止这一条**（F-08）：旧版的点位冲突（P-06）、串行回退（P-12）、等待超时（P-10）在新版矩阵里消失，编号也稀疏。建议补 P-34~P-37 四条 |
| 10 | 本方案是否有把"设计通过"写成"能力可用"的表述？ | **没有**。文档头"性质：设计基线 + 交叉评审稿。**未实施**"、§7.3 证据要求、§10 提问格式都明确。**唯一接近的表述**是 §6 第 1 步的"无（纯重构）"与"纯重构，行为不变" —— 这两句暗示"第 1 步不会有风险"，但它实际会改 HTTP 语义（F-07） |
