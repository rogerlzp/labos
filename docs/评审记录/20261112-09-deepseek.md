### （一）P0 · 阻塞（1 条）

**V8-01【P0·设计风险】T1 失败/崩溃窗口的续跑删除守卫不足：按现稿实施会重做物理动作。**
- **来源**：S4 / G1（多源印证；同批两项独立复核结论一致）。
- **位置**：§5.2:550、§5.3:563-576（T1 步骤 5 才写 physical_completed_at）、§5.6:619-631（L631 的「续跑删除守卫」）、§11.4 R13:943、§15 4f:1026。
- **问题与证据**：T1 在设备动作之后触发；若 T1 持久化失败/进程崩溃，run_node 只被 nodeStateRecorder 写成 running（GraphRunner.java:648-650），physical_completed_at 仍为 NULL、effect 未写。v2.2 的唯一删除守卫是「physical_completed_at IS NULL ⇒ 可删除」⇒ 恰好放行该窗口。现有续跑：doResumeAsync 在事务里先 deleteIncompleteStepRows 再 deleteIncompleteTopNodes（WorkflowService.java:697-738）；后者删所有 level=0 AND status<>'completed' 行（RunMapper.xml:484-490），run_command 通过 FK 级联一起删（20_kernel.sql:340）；selectCompletedNodeKeys 只认 status='completed'（RunMapper.xml:466-472）⇒ 该 node_key 不进 skipKeys，GraphRunner 续跑分支（:560-563）照旧执行设备动作。v2.2 的「先对账、禁止重跑」只写在人工恢复流程文字里，没有可执行载体；§15 4f 也把该守卫标 PARTIAL 且未给查询条件。
- **影响**：与 06 号 M2 同级的物理安全事故（开盖/移液/封膜做两次）；v2.2 删掉了「T1 前崩溃=重跑即可」的文字，但机制没有比 v3.1 强。
- **建议**：①run_node 增持久执行确认状态（至少 reconciliation_required，推荐 v3.3 的 execution_resolution_status 四态），在 T1 失败路径落状态；②续跑删除守卫改为联合检查（执行确认状态 + physical_completed_at + command_ledger/run_command 是否有派发或 UNKNOWN + effect/event 引用）；③deleteIncompleteTopNodes 与 selectCompletedNodeKeys 必须显式排除「已有命令证据但执行结论未落」的行，后者走「只补 T1/T2」旁路；④写进 §15 #1/4f 的 PASS 条件与 R13/R1 验收。
