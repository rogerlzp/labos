### O-2（P1）· `visit` 跨续跑不稳定 ⇒ 幂等键会变

**证据**

- `visits` 是**进程内**的 `HashMap`（`GraphRunner.java:504`），随 `run(...)` 结束而消失 ⇒ **进程重启后从零开始**。
- `GraphRunner.java:536` 的 `visits.merge(key, 1, Integer::sum)` 发生在**跳过判定之前**：
  `:537` `if (done.contains(key) && !hasCycle) continue;`、
  `:554` `if (done.contains(key))`、`:560-563` `if (… && skipKeys.contains(key)) { /* 续跑：直接当完成往下走 */ }`
  —— ⇒ **续跑时被 `skipKeys` 跳过的节点也会白 consume 一个轮次号**。
- `skipKeys` 的来源（`RunMapper.xml:466-472`）：`SELECT node_key FROM run_node WHERE … AND level = 0 AND (status='completed' OR (status='skipped' AND input->>'skip_confirmed'='true'))`
  ⇒ **按 `status='completed'` 判定，不看 `loop_index`**。

**推论**：对一个有环流程，续跑时被跳过的那一轮会占用一个 `visit`，**后续真正执行的那一轮拿到的 `visit` 与上一轮会话里的同一轮不是同一个值** ⇒ `execution_id` 变 ⇒ 幂等键变。而 §5.8（`:386`）明确依赖的场景正是 *「T1 后 / T2 前崩溃 ⇒ 补偿任务按已解析的 `plate_id` 重放 T2」*，§11 T06（`:762`）也依赖「Run 崩溃后恢复」。

⇒ **设计稿把锚点从「持久化的 `run_node.loop_index`」换成「内存 `visit`」，等于用一个更不稳定的量去换一个其实更稳定的量**，而没有交代续跑时轮次从哪来。

**建议处置**：设计稿必须给出「轮次在续跑时如何确定」的答案。可选：
(a) 把轮次**先落库再执行**（把 `insertNodeRound` 的时机从 `executeNode` 之后挪到之前），使 T1 能读到持久化的 `loop_index`；
(b) 在 `run_node` 上为「本节点本轮」建一行并回填 `visit`，T1 读该行；
(c) 明确「续跑时物料效果不重放、只按已落库的 `execution_id` 补偿」，并写死「续跑不得产生新的 `execution_id`」这条不变量。
**无论选哪条，都要写进 §13 与 §16 门槛 4。**

### O-5（P1）· `REJECTED` 在节点层没有落点

**证据**

- §7 效果表 CHECK：`status IN ('PENDING','APPLIED','REJECTED','NEEDS_RECONCILIATION','FAILED')` —— **五态，含 `REJECTED`**（实跑确认 `REJECTED` 可写入）。
- §7 效果状态机表：`REJECTED` = *「效果不符合规则（目标板归属不符、声明自相矛盾）」*，后续 = *「**终态**，转人工，**不自动重试**」*；而 `FAILED` = *「处理失败（数据库/并发）」*，后续 = *「保留 + **可重试**」*。
- §11.2 T12（`:768`）：*「声明与设备执行结果不一致 | 效果进 **`REJECTED`** 并转人工，不按声明硬写」* ⇒ **`REJECTED` 是可达状态**。

⇒ 一个 `REJECTED` 效果必须被映射到这 5 个值之一；最自然的映射是 `failed`。
⇒ 于是**「终态、不自动重试、需改声明」的 `REJECTED`** 与 **「可重试」的 `FAILED`** 在节点层**不可区分**：

- 而 §5.9 表里也没有一行告诉调度器「`REJECTED` 的下游怎么办」。

**建议处置**：在 §5.9 映射表补 `REJECTED` 一行，并明确节点层的落点 —— 或给 `material_sync_status` 增加 `rejected`（则 CHECK 与 §7 需同步改），或明确写「`REJECTED` 一律记为 `failed`，但**恢复入口必须先判效果状态**：`REJECTED` 不允许走 `FAILED → PENDING` 的重放路径」。

- 「**无环图又只有汇总行**」被列为「语义不一致」的例证 —— ❌ **不成立**：无环图的节点**只跑一轮**（`GraphRunner.java:651-653` 的注释原文：「无环图每个节点只跑一次，汇总行已经代表那一次，再记一行就是重复」），`loop_index = 0` 恰恰是**毫无歧义**的正确取值。
- **真正让「必须用内存 `visit`」成立的原因，文档没写**：圈次行是由 `roundRecorder.record(key, visit, …)`（`GraphRunner.java:657`）写的，而它发生在 `stateMachine.executeNode(...)`（`:649`）**返回之后** ⇒ **T1 触发的那一刻，库里还不存在本轮的圈次行**，`run_node.loop_index` 只能读到汇总行的 **0** ⇒ 若在 T1 里读库，第 2 圈、第 3 圈会拿到**同一个 0** ⇒ **全部撞同一个幂等键**（这正是 v1 的老 bug M3）。

**为什么这条不能只算措辞问题**：§5.3（`:294`）把 `source_loop_index` 列为效果记录**必须保存**的字段，但**没说它从哪来**；§5.5 又把理由写偏。实施者按字面读「读库语义不一致 ⇒ 用 visit」，很可能得出「那我读 `run_node.loop_index` 也行，只要能区分汇总行和圈次行」—— **正好退回 v1 的撞键 bug**。

**建议处置**：把 §5.5 的理由整段改写为**时序**论证：

> *「圈次行在 `executeNode` **返回之后**才落库（`GraphRunner.java:657`）⇒ T1 触发时库里只有 `loop_index=0` 的汇总行 ⇒ 读 `run_node.loop_index` 会让第 2/3 圈撞同一个幂等键；无环图只有汇总行是**正确语义**（只跑一轮），不是不一致。⇒ 轮次只能取内存 `visit`（或把圈次行改为先落库再执行）。」*

并与 O-1 / O-2 的管道方案一起写进 §13。

### O-12 ~ O-15（P3）· 事实与措辞

### 最可能出问题的那一条：**O-3（§5.3 / §5.7 / §5.8 的 T1 口径矛盾 + §5.8「T1 前崩溃 ⇒ 重跑即可」）**

**理由**：其余几条 P1 都要求实施者先做一个设计决策（怎么把 `visit` 传下去、续跑时轮次从哪来、`REJECTED` 映射成什么、barcode 结论怎么改），**决策时自然会撞上缺口**；
而 O-3 的错误分支**不是缺口，是一句写在表格里、看起来完全正常的断言** —— 一张要被照抄进恢复预案的表，在最危险的那一格写着「重跑即可」。

**证据（同一窗口的三处矛盾）**

| 位置 | 原文 | 说了什么 |
|---|---|---|
| §5.7 `:377` | 「必须是『设备动作已完成』之后、『**节点标记 completed**』之前」 | 设备动作 → 物料通知 → 节点完成 |
| §5.3 `:285` | 「设备命令结果 + **节点完成** + 待处理的物料效果记录（`PENDING`）落库」 | T1 **包含**节点完成 |
| §5.8 `:385` | 「**T1 前崩溃** \| 什么都没发生 ⇒ **设备动作也没发生** ⇒ 重跑即可」 | 把「设备动作已做、系统无记录」判成「什么都没发生」 |
| §5.2b `:263` | 「T1 失败 ⇒ **物理动作已发生，但系统没留下任何记录** ⇒ **必须阻断整个 run 并转人工** | 正确口径 |

⇒ 按 §5.7 的时序，「T1 前」这个窗口**必然包含**「设备动作做完、系统一条记录没留」；
而这正是 §5.2b 与 C6 要防的**「重跑 = 把物理动作做第二次 = 事故」**。
**§5.8 与 §5.2b 对同一个窗口给出了相反的处置指令**，而 §5.8 是那张会被直接抄进值班手册的表。

**建议**：把 §5.8 的「T1 前崩溃」拆成「设备动作**之前**崩溃 ⇒ 重跑即可」与「设备动作**之后、T1 之前**崩溃 ⇒ 阻断 run + 转人工，禁止重跑」两行；
同时把 §5.3 的 T1 定义与 §5.7 的时序对齐（节点完成移出 T1，或把节点完成提到物料通知之前），并把 §5.8「T1 后 / T2 前崩溃 ⇒ 不重跑设备动作」与 `skipKeys` 的判定口径（`RunMapper.xml:466-472` 按 `status='completed'`）对齐。

**回源码核实**（`labos-kernel/src/main/java/com/labos/kernel/workflow/GraphRunner.java`）：

```java
nodeStateRecorder.accept(key, "running");
NodeStatus st = stateMachine.executeNode(rn, progress, executor);  // :649  ← T1/T2 完成处理器在内部
nodeStateRecorder.accept(key, st.name().toLowerCase());            // :650
if (graphHasCycle && visit >= 1) {
    roundRecorder.record(key, visit, st, ...);                       // :657  ← 圈次行到此才落库
}
```

⇒ **圈次行是节点执行之后才写的**；T1 发生在 `executeNode` 内部 ⇒ 那一刻库里只有汇总行（`loop_index=0`）

**这才是「必须用执行上下文里的 `visit`」的真正原因。**
而「无环图只有汇总行」**不是**不一致的例证：无环图每个节点只跑一轮，`loop_index=0` 唯一且无歧义。

⇒ **本会话已在 §5.5 就地修正**：补两条时序事实、改写论证、显式纠正原例证，
并加一条实施提醒 —— 若按「不一致」去理解，很可能改成「等圈次行存在时再读」，而那在 T1 时点上**永远等不到**。
