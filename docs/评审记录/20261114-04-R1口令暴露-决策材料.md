## 二、三个选项

| | A. force-push 重写历史 | B. 仅轮换口令 | C. 维持现状 + 访问控制 |
|---|---|---|---|
| **做什么** | 隔离克隆重写历史（脚本已备好）→ force-push 所有含口令的分支 → 全员重新 clone；口令换不换另说 | 改库口令 + 更新所有客户端配置，历史不动 | 保持现状；确认仓库改为 private + collaborator 最小化 + DB 侧加来源 IP 白名单 |
| **一次性成本** | 中（脚本就绪，1 小时内；需协调所有协作者重新 clone） | 低（改口令 + 同步 N 台客户端） | 低 |
| **残留风险** | 若口令不换：重写前已 clone/fork 的人仍持旧口令 ⇒ **必须配合换口令才闭环**；fork/PR 缓存副本不可控 | **历史里的旧口令永远有效**——只要不改库口令，泄露面不变；只能"事后止血" | 公开仓历史永存；private 化影响协作；IP 白名单防外不防内 |
| **能否真正闭环** | ✅（重写 + 换口令） | ⚠️ 只对新口令负责，旧口令仍在野 | ❌ 只降速不消除 |

## 三、推荐

**A + B 组合，且 A 必须在确认仓库转 private 之前完成（顺序不可反）。**

理由一句话：**仓库是公开的，历史里的口令此刻对全世界有效；重写历史只解决"未来不再新增泄露者"，换口令才解决"已有泄露者"，两个都做才能闭环。** 只做 B 等于承认"旧口令终身有效"；只做 A 等于相信重写前没人 clone 过——对公开仓库这是赌。

若出于协作原因暂不能转 private，则更要立刻做 A+B，并接受"重写前已被克隆的副本不可回收"这一残余风险。
