## 检查区 2 · psql 命令标签过滤的通用性（P1，脚本）

**实测（本机 `psql 18.3`，非文档写的 17）**：
```
-tA -c "BEGIN; CREATE TEMP TABLE ...; INSERT ... RETURNING i; ROLLBACK;"
  → BEGIN / CREATE TABLE / 7 / INSERT 0 1 / ROLLBACK      ← 真实值被夹在标签中间
-q -tA -c 同上
  → 7                                                      ← 只剩真实值
```
⇒ **`-q`（--quiet）才是根治**：命令标签从源头不产生；事后正则永远追不全。

### 2.1 风险面盘点
- [x] `core-scenarios.py` 的 `q()` ✅ 🔧 **本次已修**（`:114-129` 加 `-q`）—
      它只有 1 处 `RETURNING`（`:986-987` 清 `runtime_hold` 的 `UPDATE ... RETURNING id`，仅打印）
- [x] `verify-s2-fault-injection.py` 的 `q()` ✅ 🔧 **本次已修**（`psql():57-69` 加 `-q`）—
      `:287-289` 原用 `.splitlines()[0]` 规避，现在返回值本身就干净
- [x] `s2-material-20node.py` 复用 `cs.q` ✅ 🔧 **随 core-scenarios 一起修**（`:61-62` 的 `INSERT ... RETURNING id`，`pid` 仅用于打印，不影响落库）
- [ ] 「上提为公共 helper」 ❌ **不采纳** — 3 个封装语义不同（`PGOPTIONS` 超时 / `ON_ERROR_STOP` /
      `stop` 参数 / 环境变量缺省各不相同），强行统一增加耦合；且 `-q` 已从源头解决，helper 无增量价值。
      ⚠️ 如实记录：另有 13 个脚本自带 `q()`（`baseline-seed.py`、`verify-plate-trace.py`、
      `designer-helpers.py` 等）**未改**，它们全仓无 `INSERT...RETURNING`，只可能把 `UPDATE 1` 之类的
      标签当 display 输出；一旦有人把返回值拼进 SQL 就会复现，属低概率定时炸弹

### 2.2 正则覆盖度
- [ ] 原 `_CMD_TAG` 正则 ❌ **不通过 → 🔧 已补全为兜底** —
      实测输出里的 `CREATE TABLE` 原正则就漏了；同样漏 `ALTER/DROP/TRUNCATE/SET/DO/CALL/...`。
      已改为标签集合 + `(?: [A-Z ]*)?`，并在注释里写明「`-q` 是主修，正则只兜底」
- [x] 多行 RETURNING `INSERT 0 N` ✅ **通过** — `\d+ \d+` 覆盖
- [x] `UPDATE N` / `DELETE N` ✅ **通过** — 正则覆盖；`SELECT \d+` 是冗余项（`-tA` 下 SELECT 不输出行数标签），无害

### 2.3 空结果 vs 命令标签
- [x] `SELECT` 空结果返回空串 ✅ **通过（实测）** — `-q -tA -c "UPDATE plate ... WHERE 1=0"` → `''`
- [x] 过滤后空串不误判「成功但有值」 ✅ **通过** — `q()` 契约为「失败抛错、空串=没有」；
      `-q` 下 `UPDATE 0` 也返回空串，与契约一致。修后实测：`q('BEGIN')=''`、`q(INSERT RETURNING)='7'`、

### 严谨的自动确认条件（全部满足才置 CONFIRMED）

`DEVICE_REPORT` 不能无条件等价于物理确认。仅在**同一事务**内全部成立才自动确认：

1. `LABOS_TRANSFER_PLAN` 开启且 protect 分支创建了 `transferTxn > 0`；
2. 解析到真实板号（非 null、非 `AUTO-`）；
3. `TransferPlan.acquireAll` 抢锁成功（门/通道/位置）；
4. 设备回包 `r.errorCode() == null`（失败走 `markPlatePositionUnknown`，保持 UNKNOWN）；
5. 源位：无板 → 允许「首次引导」并记 note；有板但 `occupied_by_run != runId` → **拒绝自动确认**；
6. `takePlate(src)` 与 `putPlate(dst)` 影响行数均 > 0，目标位 `plate_id` 落的是同一板号；
7. `refreshHasPlate` 后目标设备 `has_plate = true`；
8. 写 2 行 `plate_location_audit`（取板 / 放板，note 标 `DEVICE_REPORT`）+ 1 行
   `position_evidence(evidence_type='DEVICE_REPORT', run_id=...)` +
   `transfer_transaction.status=CONFIRMED, confirmed_by=<系统>, confirmed_at=now()`；
9. `plate.position_status` 置回 `KNOWN`（补现有缺口）。

任一条件不满足 ⇒ 保持 `REPORTED`/`UNKNOWN` + 板标 UNKNOWN，仍走人工
`POST /api/transfers/{id}/confirm`。
**开关**：`LABOS_TRANSFER_AUTO_CONFIRM`，**默认关**，且**按 workflow 生效**
（空=关 / `1`、`true`、`*`=全局 / 逗号分隔的 workflow id=仅这些流程）。
⚠️ 不能设全局：全库 **23 个** wf 含 Transfer 节点，只有 1000830 配了板号，
全局开启会让启动预检把另外 22 个流程一并阻断。本次取值 `1000830`。
关闭时行为与改造前逐字一致（回滚 = 摘掉环境变量）。
**可撤销**：`position_evidence.note` 写明条件与 raw 摘要；人工仍可 `markPlateUnknown` 推翻，
证据 append-only 不删。
