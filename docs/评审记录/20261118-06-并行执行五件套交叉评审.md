### F-02 · ③ 的 `base_event_id` 语义与 W-05 验收自相矛盾，且"deprecated 游标表"会丢掉 run 级固定基准

**位置**：③ §2.4 匹配 SQL、§2.7、§5.2 W-05

**核对现有实现**（`DeviceEventMapper.xml:49-57`）：

```xml
<select id="ensureRunCursor" resultType="long">
  INSERT INTO device_event_run_cursor (tenant_id, run_id, base_event_id)
  SELECT #{tenantId}, #{runId}, COALESCE(MAX(id), 0)
    FROM device_event WHERE tenant_id = #{tenantId}
  ON CONFLICT (tenant_id, run_id)
  DO UPDATE SET base_event_id = device_event_run_cursor.base_event_id
  RETURNING base_event_id
</select>
```

⇒ **`base_event_id` 是 run 级固定基准**：首次执行时取一次 MAX(id)，之后 resume 读回**旧值**（`DO UPDATE` 保持原值）。这正是"不丢早到事件"的机制。

**矛盾**：

- ③ §2.4 的匹配条件是 `w.base_event_id < ?`（事件 id 必须大于 waiter 的基准）；
- ③ §5.2 **W-05 期望**："事件先于 waiter 到达 → waiter 以 `base_event_id` 为准，**不丢**"；
- ③ §2.7：**"`device_event_run_cursor` 标记 deprecated。现在按 run 记游标，改为按 waiter 记 `base_event_id` 更精确"**。

⇒ 如果 waiter 的 `base_event_id` 取"**创建 waiter 时的 MAX(id)**"（按 waiter 记的自然读法），则**先于 waiter 到达的事件 id 更小 ⇒ 被 `<` 排除 ⇒ 事件丢失** ⇒ W-05 的期望**不成立**。
⇒ 而 §2.7 这一步恰恰**丢掉了"run 级固定基准"这个性质**，把一个 run 级不变量降级成了 waiter 级瞬时值 ⇒ 早到事件必丢。

**处置**（二选一，推荐前者）：

- **A（推荐）**：waiter 的 `base_event_id` **必须继承 `device_event_run_cursor` 的 run 级基准**（同一 run 的所有 waiter 用同一个值），**`device_event_run_cursor` 不得 deprecated** —— 它是"不丢早到事件"的唯一依据，只是从"消费者游标"变成"基准来源"，角色变了但不能删。
- **B**：接受早到事件丢失，把 W-05 期望改为"事件早于 waiter ⇒ 落 UNATTRIBUTED 并告警"。但这与业务上"设备可能在等待节点建立前就上报了"的事实冲突，**且会让现网的 `__awaitEvent` 行为退化**（现在是 run 级游标，不丢）。

⇒ 附：③ §2.7 说 `device_event_run_cursor` deprecated 的另一个理由是"按 waiter 记更精确" —— 精确性和"不丢"是**两个不同维度**，不能二选一。

## 三、③（表设计 v2）逐条核验

### F-03（严重）· §2.4 的 `FOR UPDATE SKIP LOCKED` 破坏唯一性判定

**位置**：③ §2.4、§5.2 W-07/W-08 —— **这是他们 §8 第 4 问的直接答案：不是过严，是不够严。**

**问题**：`SKIP LOCKED` 的语义是"跳过被其他事务锁住的行"。于是：

- 实际有 3 个 waiter 匹配同一事件，其中 2 个正被别的事务锁住；
- 本次查询拿到 **1 行** ⇒ 按 §2.4 的表格判"**恰好 1 行** → 置 MATCHED + 写 consumption + 推进节点"；
- ⇒ **推进了错误的流程**（3 个候选里挑了 1 个，且不是因为匹配更准，而是因为另外 2 个恰好被锁）。

⇒ "整体回滚"是对的方向，但 `SKIP LOCKED` 让"多行"这个状态**观测不到** —— 它在并发下被伪装成"唯一"。

**修法**：

1. 先在**不带 SKIP LOCKED** 的快照里判定唯一性（例如 `SELECT count(*) FROM device_event_waiter WHERE ...`）；
2. 确认唯一后，再对那一行 `FOR UPDATE`（可带 SKIP LOCKED，但要**确认拿到的是刚才判定的那一行**，靠 id 匹配）；
3. 或：用 `FOR UPDATE`（不带 SKIP LOCKED）串行化匹配 —— 单实例下匹配频率极低，串行完全够用。

⇒ 另：**W-07 的期望写漏了一半**。"两条事件同时到达 → 行锁保证不会同时匹配同一 waiter"是对的，但**另一条事件会匹配不到 ⇒ 落 UNATTRIBUTED + 告警**。这条要写进验收，否则现场会看到"无故告警"。

### F-04（严重）· §2.2 `uk_waiter` 缺 attempt，resume 路径会撞唯一键

**位置**：③ §2.2 DDL

```sql
CONSTRAINT uk_waiter UNIQUE (tenant_id, run_id, node_id, loop_index)
```

**核对现有约束**：`run_node` 的唯一键是 `UNIQUE (run_id, node_key, attempt, loop_index)`（schema `:594`）—— **含 attempt**。

⇒ resume 后该节点的 `run_node.attempt` +1 ⇒ 新建的 waiter 的 `(run_id, node_id, loop_index)` **与旧行完全相同** ⇒ **撞唯一键 ⇒ resume 路径直接失败**。

**修法**：UK 加 `attempt`；或改成只约束活跃 waiter 的部分唯一索引：

```sql
CREATE UNIQUE INDEX uk_waiter_active ON device_event_waiter (tenant_id, run_id, node_id, loop_index)
  WHERE state = 'WAITING';
```

（后者更好：历史 waiter 保留可审计，且不阻塞 resume。）

### F-05（严重）· §4.2 的对账 SQL ① ② 在迁移期永远匹配不上

**位置**：③ §4.2

**核对**：现有 `command_ledger.command_id` 写入的是**含 `exec`、每次都变**的 id（`DriverStepExecutor:1474-1478`）；而新的 `logical_operation.command_id` 是**稳定 id**。

§4.2 的两条 JOIN 都用 `o.command_id = l.command_id`：

```sql
-- ①
FROM command_ledger l LEFT JOIN logical_operation o
  ON o.tenant_id = l.tenant_id AND o.command_id = l.command_id
WHERE o.id IS NULL;
```

⇒ 迁移期（新表已建、`command_ledger` 仍在写含 exec 的 id）⇒ **JOIN 永不命中** ⇒ SQL ① 把**每一条 ledger 行**都报成"有传输明细、无逻辑动作" ⇒ 每日全量误报，告警直接失效。

**修法**（二选一）：

- 迁移期先让 `command_ledger.command_id` 也写稳定 id（与 ③ §4.1 步骤 2 同步做），再上对账；
- 或对账改按 `operation_key` 映射连接（`l.idempotency_key` → `o.operation_key || '|' || o.generation`），并在 §1.6 修正映射描述。

⇒ **另**：§1.6 说"`command_ledger.idempotency_key` 可平滑映射为 `operation_key + generation`" —— **不成立**。现有 ledgerKey 是 `r{run}|n{node}|a{attempt}|s{step}|d{device}|m{method}[|vN]`（`DriverStepExecutor:1209-1211`），含 `a{attempt}` 与 `m{method}`，而 operation_key 不含这两项 ⇒ 映射是**多对一**，不是平滑一一对应。

### F-06 · §1.4「PENDING 是唯一可安全重发的状态」在实现上几乎不可达

§3.1 要求"**下发前把 state 改 DISPATCHED（先落库再发）**"。⇒ 崩溃发生在"改 DISPATCHED 之后、真正发出之前" ⇒ 状态是 DISPATCHED（命令其实没发出去）⇒ 按 §3.2 去 `queryStatus` ⇒ `NOT_FOUND` ⇒ 按规则 1 落 UNKNOWN ⇒ **转人工**。

⇒ 即：**"命令确实没发出"这个最安全的场景，因为"先落库再发"的策略，落在了最保守的分支上**。这是"先落库再发"的固有代价（无法原子化地区分"已发未回"与"将发未发"）。

⇒ 建议：§1.4 明确承认这一点并**量化**（崩溃窗口 = 从"改 DISPATCHED"到"写完 socket"的毫秒级），写成"可接受的少量转人工"，而不是留给实施者自己去撞。

## 四、④（入口统一改造清单）核验

### F-08 · §3.2 伪代码的注释与代码不一致

**位置**：④ §3.2

```java
GuardedStart.Result start(StartRequest req) {
    Decision d = gate.check(tenant, workflow, req.excludeRunId());   // ← 在事务外
    if (!d.allowed()) return Result.rejected(d);
    return inTransaction(c -> {
        long runId = req.isResume() ? resumeInTx(c, req) : createRunInTx(c, req);
        return Result.accepted(runId);                                 // ← 事务内没有再检查
    });
}
```

注释写"**同一个数据库事务内：检查 + 插入**"，但代码里 `check` 在事务**外**，事务内只有写入。

⇒ 这是本清单**最容易被照抄错**的一处：实施者按代码写 ⇒ 两个请求同时 `check` 都通过（§3.2 自己也说了这个窗口"只加门禁不改事务边界，等于没修"）⇒ 修的意图落空。

**处置**：要么把 `check` 移进 `inTransaction`；要么把注释改成"事务内靠第 3 层唯一索引兜底，应用层 check 只是快速否定（会在竞态下放行，由索引拒绝）"，并同步修正 §3.3 第 2 层的描述。

### F-09 · §4.2「HTTP 200 → 非 2xx」与 §0/§2 的"不改变 HTTP 契约"矛盾

**核对现有门禁返回形状**（`WorkflowWebService.java:289-298`）：

```java
if (!gate.allowed()) {
    return Jsons.obj("error", gate.reason(),
                     "errorCode", "EC-WORKFLOW-RUNNING",
                     "activeRunId", gate.runId(),
                     "activeRunNo", gate.runNo(),
                     "activeStatus", gate.status());
}
```

⇒ 现有实现返回的是 **JSON 对象**（不是 HTTP 错误码），由 `WorkflowController` 用 `json.startsWith("{\"error\")"` 嗅探再转成错误响应。

⇒ E-02 若改成 4xx：前端要新分支，且与 E-01 的既有形状不一致 ⇒ **不满足 §0 的"不改变现有 HTTP 契约"**。

⇒ **建议**：E-02 沿用同一形状（200 + `{"error":…, "errorCode":"EC-WORKFLOW-RUNNING", activeRunId/activeRunNo/activeStatus}`），前端零改动。这才是"契约不变"的真解。

### F-10 · §6 步骤顺序：唯一索引兜底排在事务边界改造之前

第 6 步"加唯一索引兜底"、第 7 步"把事务边界从预检+执行改为预检+插入"。

⇒ 索引是**事务边界正确性**的兜底，先加索引会在中间态把**现有合法并发路径**打掉；且 §7 R-12 已承认它与 allow 开关冲突。

⇒ **建议 6/7 对调**（先改事务边界，再加索引），或把索引放到"所有入口都切到 GuardedStart 且事务边界已改"之后。

### F-11 · §4.3 / §7 R-13 的理由不成立

§4.3 写"批次之间要重新判定（**因为前一批可能还在跑**）"，R-13 写"若终结写入有延迟会误拒"。

⇒ 事实：串行批次前一批**一定已终结** —— `executeBatch` 返回前，`ExperimentExecutor.settle` 已落 run 终态、`finishBatchRun` 是同步调用（`BatchOrchestrator:834`）⇒ 批 2 开跑时批 1 的 run.status 已不在 active 词表 ⇒ 判定通过，**不会误拒，不需要重试**。

⇒ 真正的理由是"**防止外部并发启动同 workflow**"（这才是准入的意义），不是"前一批还在跑"。理由写错会导致实施者加不必要的重试与退避。

### F-12 · §4.5 resume 状态守卫漏了 `quarantined`，且唯一索引的 active 集有坑

**核对**（`StatusVocabulary.java:120-128`）：

| 状态 | terminal | active |
|---|---|---|
| queued / running / paused | false | **true** |
| **quarantined**（"隔离待确认"） | false | **true** |
| completed / failed / aborted | true | false |

⇒ 两个后果：

1. **状态守卫**：④ §4.5 的 `status IN ('paused','failed')` **不含 `quarantined`** ⇒ 被隔离的 run **永远无法 resume**（隔离态 = 等人工确认，人工确认完却没法恢复 ⇒ 死锁在隔离态）。
2. **唯一索引**：若按 active 词表建 `active_slot`，`quarantined` 会**永久占住该 workflow 的 active slot** ⇒ 该 workflow 在隔离解除前**无法启动任何新 run**。

⇒ **建议**：状态守卫放宽为 `('paused','failed','quarantined')`；唯一索引的 active 集合**显式定义为 `('queued','running','paused')`，排除 `quarantined`**，另设 `quarantine_blocking` 之类的列表达"隔离是否阻塞同 workflow 新启动"。

### F-13 · §5 等价性验证缺三项

| 缺项 | 为什么必须补 |
|---|---|
| **DB 不可用时的行为** | 现有 `WorkflowRunGate.check` 的 catch 分支是 **allow**（"查询失败也不拦：门禁是防止自己人打自己人，不该变成库抖一下就启动不了"，`WorkflowRunGate:147-150`）⇒ ④ §4.2 的验证项写"DB 断开 → EC-WORKFLOW-GATE-UNAVAILABLE" —— **这个错误码和这个行为现在都不存在** ⇒ 这是**新增语义 = 行为变化**，必须单独设计并声明，不能混在"行为等价"里 |
| **并发等价性** | 两个 `async=1` 同时打 ⇒ 一个成功一个被拒（§4.2 提到但 §5 没列为验证项） |
| **租户隔离** | 跨租户 resume 被拒（§4.5 提到但 §5 没列） |

### F-14 · §6 的"待确认"我可以定论：同空间，但不冲突

⑤ §6 问"zone 的 id 和设备 resource id 是否在同一个空间？" —— **同空间，但不会冲突**：

1. `RailZoneGuard:92-98`：轨道分区用 `DeviceLock.tryAcquire(z, runId)` ⇒ **轨道分区锁与设备锁复用同一套锁机制**；
2. `DeviceLock` 的 DB 层落在 `device_state.current_run_id`（按 `resource_node.id`）⇒ 设备与分区是**同一张表的不同行**；
3. `PositionLock:206` 注释明写"位置（**resource_node.id**，kind 必须是 incubator/storage/transfer_point）"⇒ 位置也在同一 id 空间；
4. `resource_node.kind` 是枚举（`island/station/device/robot/storage/transfer_point/incubator/operator/virtual` + 后加 `workstation`）⇒ **一个 id 只有一个 kind** ⇒ **同一个 id 不可能既是设备又是分区**。

⇒ **⑤ 担心的"id 撞了"不成立**；真正的问题不是 id 空间，而是**锁落在不同的表**：

| 锁 | 落点 | 表 |
|---|---|---|
| 设备执行锁 | `device_state.current_run_id` | `device_state` |
| 轨道分区锁 | 同上（复用 DeviceLock） | `device_state` |
| 物理位置锁 | `position_state` | `position_state` |

⇒ **真正的跨类互等只有一组：`device_state` ↔ `position_state`**。而⑤ §3.1 的三值 `ResourceType{DEVICE(1), POSITION(2), RAIL_ZONE(3)}` 里的 RAIL_ZONE 与 DEVICE **同组**（同表）⇒ 真正需要约束的顺序是 **"先 device_state 组，后 position_state 组"**。

⇒ **结论：⑤ 的顺序方向正确（device_state → position_state），枚举可以简化为两组**；"按持有时间从短到长"的替代排序**不适用** —— 持有期由不同生命周期决定（R-18 已指出），排序依据是"锁的存储组"，不是时长。

### F-15 · §6 最后一句的推理方向反了

⑤ §6 末句："如果确实同空间，`ResourceType` 的断言就更有必要（**因为无法从 id 本身判断类型**）"。

⇒ 断言的目的**不是**"从 id 判断类型"，而是**约束申请顺序**。类型来源与顺序约束是两件事。

⇒ 更好的实现（直接解决 §2.3 担心的"未来新增路径会破"）：

> **让锁自己按 `resource_node.kind` 推导类型**，而不是由调用点传 `ResourceType` 枚举。
> 这样新增路径**自动**受约束，不依赖开发者记得传对类型 —— 而"记得传对"正是 §2.3 说的破窗点。

⇒ 文档 §3.2 的 `ThreadLocal<Deque<ResourceType>>` 还有实现层问题：`RailZoneGuard.acquire` 对多个 zone **批量申请、批量释放**，没有 push/pop 配对 ⇒ 栈式模型会误报。建议改为"**本线程当前持有的最高 rank**"（单个变量，不是栈）。

### F-16 · §7 R-17 / R-18 的答复

**R-17（位置锁 30 分钟 vs 轨道锁更短超时）**：会，但**不是并行导致的，是现状就有的**。轨道锁默认超时 **60 秒**（`RailZoneGuard:43-53`，可用 `LABOS_RAIL_WAIT_TIMEOUT_MS` 覆盖），位置锁 TTL 30 分钟。顺序是"先占位置、再抢轨道" ⇒ 等不到轨道时 `safeReleaseTarget` 释放位置 ⇒ **不泄漏 ✓**（K-05 验收正确）。⇒ 真实代价是"**白占位置 60 秒**"，并行时该代价乘以并发数。**建议**：轨道锁等不到时**先释放位置、再等轨道**（把等待挪到不持锁的阶段），而不是持位置等轨道 —— 改 `DriverStepExecutor:583` 的失败路径即可。

**R-18（位置跨 step / 设备锁随 step）**：会，但成因不是锁，是**板归属**。位置被占 + 板在上面，run 终结后 `releaseRunOccupancy` 只解绑归属、**板留在原位、位置继续占用**（设计基线 P-32 验收正是这个语义）。并行下的真实风险是"两个 run 都想用同一个空位" ⇒ 由 `PositionLock` 的 DB 条件更新挡住 ✓。⇒ 真正要补的是**位置占用的孤儿回收**（`DeviceLock` 有 `releaseOrphans`，位置锁侧的对应机制需确认）与"run 终结后位置何时解绑"。建议 ⑤ 的 R-18 补上这条。

### F-17 · §3.2 的 ThreadLocal 断言覆盖不到的三处

| # | 漏点 | 说明 |
|---|---|---|
| 1 | `RailZoneGuard.acquire` 的**批量申请/批量释放** | 同一线程连续申请多个 zone，没有 push/pop 配对 ⇒ 栈式断言会误报（见 F-15） |
| 2 | `DeviceLock.acquireWithWait` 的**重入路径**（`:155-158`，同线程同 run 已持有时直接返回 true） | 重入不是新申请，不应触发断言；但实现必须区分"新申请"与"重入" |
| 3 | **跨线程** | `WorkflowService` 的执行线程与 `ExperimentScheduler` 的 pool 是两个线程池；resume 在**新线程**上跑 ⇒ ThreadLocal 状态**不跨线程** ⇒ 断言在 resume 后失效（对 resume 无害，但覆盖不到"跨线程续跑"） |

⇒ 建议：断言改为"按 kind 推导 + 单变量记录最高 rank + 每次进入 step 重置"。
