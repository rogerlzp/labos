## 一、本轮为什么做、做了什么

### 1.1 触发原因

第 5 轮留下两份独立记录（`20261112-05-mavis.md` 本会话 15 条 / `20261112-06-mavis.md` 并发会话 24 条），

- 05 号记录的 **O-11** 判「§5.5 给出的理由是错的」（真因是**时序**：圈次行在 `executeNode` 返回**之后**才写，

  该例证不成立：无环图每节点只跑一轮，`loop_index=0` 唯一且无歧义），全文检索「时序 / 返回之后 / 才写」**零命中**；
- ⇒ 该条已在 `3ce7741` 由本会话**回源码修正**（时序论证 + 显式纠正原例证），并由本轮复核员 A **独立复核为正解**。

### 3.3 O-16 / O-17 的数据模型裁决结论

**O-16（循环各圈的物料状态载体）⇒ 建议取 (a)**

| 问题 | 结论 | 证据 |
|---|---|---|
| 唯一键能否支撑「按轮次汇总」 | **能** | 前缀 `(tenant_id, source_run_id, source_node_key)` 正是闸门过滤键；EXPLAIN 实测 **Index Only Scan**，**无需新增任何索引** |
| 「同一圈次两行」风险 | **effect 表无此风险** | 键含 `effect_index` ⇒ 同圈多效果合法并存（实测 loop2/idx0+idx1 都成功）；`attempt` **故意不入键** ⇒ 重试不会造出同圈第二行 |
| 「跨圈次撞键」风险 | **无** | `source_loop_index` 在键内；实测 loop1..loop4 同 `effect_index=0` 全部并存 |
| 「汇总漏圈」风险 | **有，但只影响「漏写一行效果」** | effect 表**没有**「本圈应写几行 / 应有几圈」的载体；`declaration` jsonb 是**逐行快照**，只能靠解析 JSON 推算 |
| 在途圈次会不会被漏判 | **不会（(a) 的决定性优势）** | effect 行在 **T1** 落库 ⇒ 执行中的圈次已有 `PENDING` 行 ⇒ 闸门看得见 |

**(b) 的三处硬伤**：① `material_sync_status` 是 `NOT NULL DEFAULT 'not_required'` ⇒ 「没写」与「确实不需要」**不可区分**（实测默认落 `not_required`）⇒ (b) 必须先改可空或加哨兵值；② 圈次行在节点执行**之后**才写 ⇒ **在途圈次在 `run_node` 里不可见** ⇒ 「任一圈未闭环即阻断」在执行过程中判不出来；③ `uk_run_node` **含 attempt** ⇒ 同一圈次可有两行，汇总必须先按 attempt 去重，且与 §5.5「attempt 不进幂等键」口径相反。

**⇒ 结论：取 (a)**，**并补三条**：① 汇总 SQL 的过滤键固定为 `(tenant_id, source_run_id, source_node_key)`；
② 终态集合必须**显式含 `CANCELLED`**（`status NOT IN ('APPLIED','CANCELLED')` 才是正确的「未闭环」判据）；
③ 若要防「漏写一行效果」，须在 effect 表增列（如 `expected_effect_count`）或把「本圈效果数不校验」写成显式不变量。
