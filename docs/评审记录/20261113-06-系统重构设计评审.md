## 1. 意见清单

### P1-1 · `device_type='arm'` 取值错误（§5.2.2，会让过滤和审计 SQL 全部失效）

**证据（生产库实测）**：`device` 表 `device_type` 的全部取值里**没有 `'arm'`**；机械臂实际是
`device_type='Robots'`（3 台：ID-X231 / ID-XRobot_A10LR-1 等）。另有 4 台 `device_type` 为空、29 台 `MISC`。

**后果**：§5.2.2 的「`device_type='arm'` 过滤方法面板」和审计 SQL 一条都匹配不到，机械臂方法会照常暴露。

**处置**：改为 `device_type='Robots'`，或更稳妥用 `capability='TRANSFER'`（注意 TRANSFER 能力里混有 MISC 设备，需先确认哪些是 arm；建议 `device_type='Robots' OR (capability='TRANSFER' AND device_type<>'MISC')` 或直接新增 `is_mover` 标记列，与设计稿 §4.1 一致）。

### P1-2 · 点位绑定的解析优先级没讲清（§15 Q1/Q6 的关键）

**证据（本会话实测）**：`workflow_node.resource_id`（设备绑定）在**运行时被 GraphRunner 的候选池重新解析**——
我在内部搬运测试里把 MoveInLabware 显式绑到 ID-2011（resource_id=200387），运行时却解析到 ID-X202（候选池第一台 ALIQUOT），节点直接转 manual。即「绑了 ≠ 用」。

**后果**：文档 §5.2.1 说「运行时解析、编译只校验存在性」，若不解决「绑定 vs 候选池」的优先级，`point_resource_id` 会重蹈 resource_id 的覆辙——编排员绑的点位在运行时被换成别的。

**处置**：必须明确一条**统一解析函数**：
`point_resource_id 优先 → resource_id 回退 → 仅两者都空才进候选池`；且一旦命中绑定，**不参与候选池排序**（pinned 语义）。这正是 §15 Q1/Q6 的答案：运行时解析可行，但绑定必须「固化」，不能与候选池混跑两种口径。

### P1-3 · 物料配置与物料声明的双口径（§15 Q3）

**证据**：`run_material_effect_declaration` 是「run 启动时冻结的**节点级**快照」（append-only，我在 20261112 实现过），而本文 `experiment_material_config` 是「**实验级**」配置。两者粒度不同（节点 vs 实验）、生命周期不同（冻结快照 vs 可改配置）。

**后果**：文档 §5.3.2 假设「启动时以实验表为准**生成**流程声明」，但「一个实验物料如何映射到多个节点的声明」没有定义，且与 append-only 快照的幂等键会冲突。

**处置**：建议 v1 **不互相生成**——`experiment_material_config` 只做 C3 启动校验（物料位置核验），与 `run_material_effect_declaration`（流程内状态迁移）**并行共存**，口径各自独立。等 P4 再把「实验物料 → 节点声明」的映射规则设计清楚。

### P2-1 · RBAC 从「字符串」到「表+权限点」是一次大改，R1 工作量被低估

**证据**：现有 `RbacRules.java` 是**硬编码字符串**（`ROLES=[admin,operator,viewer]` + `canWrite/canManageUsers/canMaterial`），而 `app_role/permission/user_role/role_permission` 表**已存在但未被 RbacRules 使用**（我实测表在、代码用字符串）。

**后果**：文档 §6 的权限点方案（`workflow:edit` / `arm:debug` 等）意味着要把 RbacRules 的字符串判断整体迁移到「permission 表驱动」，这比「加三个角色种子」大得多。R1 的验收标准④「test-all 全绿」不足以覆盖这次改造。

**处置**：R1 明确 RbacRules 改造范围——是「保留 RbacRules 字符串、只加角色/导航裁剪」还是「全面迁到 permission 表」？建议 v1 前者（最小），权限点表只做前端菜单裁剪的数据源，后端仍用 RbacRules 字符串（可扩展 canOperate/canEditWorkflow）。

### P2-2 · 文档对「内部格搬运」状态过时

**证据**：§11 R4 把「内部格搬运建模（装载口→内部格）」列为「另立设计」。但本会话已实现 `DeviceInternalTransfer`（装载口↔内部格 + 板型/高度校验）并测试通过（`verify-internal-transfer.py` 3/0）。

**处置**：R4 该项删除或改为「已落地，见 DeviceInternalTransfer」；R4 保留 Campaign + 池调度策略即可。

### P2-3 · 小瑕疵

- §3.1「RBAC 四表」应为**五表**（含 `app_user`）。
- §5.2.2 审计 SQL 的 `JOIN device_method dm ON dm.id = n.protocol_id` 有误——`workflow_node.protocol_id` 不直接等于 `device_method.id`（已注明「或按实际引用链调整」，建议直接给出正确的引用链，避免实施时踩坑）。
- §6.2 操作员菜单摘掉了 `/manual-windows` `/quarantined` `/handoffs`，但这些是运行期「等待人工」的承接页；文档说「由运行页内嵌处理面板承接」——需确认现有 run 详情页是否已有内嵌人工处理，否则操作员会失去处理入口（权限点也要补 `run:handle-manual` 之类）。

## 2. 回答 §15 六个审阅问题

1. **点位解析时机**：运行时解析可行，但**绑定必须固化**（见 P1-2），否则被候选池覆写。编译时校验存在性 + 运行时「pinned 优先」。
2. **三条件状态机 vs run 状态机**：不重叠（readiness 是启动前闸门、run 是启动后），但 C1「busy 可预约」需与 `PositionLock.reserved` 语义对齐（避免「可预约」与「已预约」口径打架）。
3. **双声明口径**：见 P1-3，v1 不互相生成、并行共存。
4. **权限点遗漏**：需补运行期人工处理页（manual/quarantine/handoff）的权限落点（见 P2-3）。
5. **自测影响**：过滤在 API 层（`includeArm=false`），自测（PlateBarcodeSelfTest 等）直接调 DeviceCore/PositionLock，不经该接口，**不受影响**；但 `verify-plate-trace.py` 等脚本走 API 建流程，其流程用的是 Deposit/Withdraw/MoveInLabware（非 arm），也不受影响。
6. **回退路径**：是最大隐患（见 P1-2），必须「point 优先 → resource 回退 → 二者都空才候选池」的统一解析，且命中绑定不进候选池。
