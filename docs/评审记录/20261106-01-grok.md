## 二、意见清单

### ①（P1）超时不会把整单写成 `failed` —— 断言与落库状态矛盾

**位置**：`scripts/verify-flow-matrix.py:340-347`（`sec_waitsleep` 的第 ③ 段）；口径落点见 `docs/完整流程测试矩阵-设计.md:83`、`docs/设计-逻辑节点分层与编辑器分工.md:105`（及英文镜像）。

**评审方指出的代码事实**：

- 生产收尾走 `WorkflowService.settleRun`（`:2392-2436`）：先 `isRunPaused(runId)` 早退（`:2395`，**不能用 completed / failed 覆盖 paused**）→ `aborted ⇒ failed` → `manual || skipped ⇒ paused + pause_kind='waiting_human' + pause_reason + paused_at`（`:2413`），`manual` 为真时另调 `openManualWindow`（`:2446`）。**`MANUAL` ⇒ 整单 `paused`**。
- `api/OpsApi.java:501-503` 的 `anyManual ? "failed" : "completed"` 是**另一条演示插入路径**，不走生产收尾。

**矛盾**：矩阵第 ③ 段却断言 `ok("__wait 超时：整单 failed")`，实际 `ctx.run` 读到的 `run.status` 是 `paused` ⇒ 该断言必失败。`ci-gate.sh` 只要失败数非 0 即红，与 `MIN_MATRIX=55` 无关。设计文档把这两条路径写成了一条（「整单 `failed`（`OpsApi` 映射）」）。

**评审方结论**：节点行 `manual` + 整单 `paused` 才是当前的恢复语义（人改好变量再点继续，这一步会重跑）；若产品要的是失败终态、不许续跑，需要在这条错误码上另写收尾，**不能靠现有的 `MANUAL`**。建议改断言与文档，让它们承认 `paused`。

### ②（P1）外部刷新会盖掉本图刚写的变量

**位置**：`GraphRunner.waitForVariable` 轮询体内的变量刷新；`executeBuiltin` 的 `__setVar` / `__expr`。

**评审方指出的代码事实**：

- `__wait` 每一轮都 `loadRunVars`，再 `variables.putAll(...)`（**整表覆盖**）。
- `__setVar` / `__expr` 只改内存 `variables`，**还没有回写** `run.input.vars`。

**后果**：库为空时，空 map 不会 `putAll`，内存里的 `ready=1` 还在，所以矩阵第二节能过。**但实验启动时如果已经带了同名变量**（例如 `ready=0`），第一次轮询就会把 `__setVar` 刚写的 `1` 盖回 `0`，然后一直等到超时。「等待外部写入」这条路是对的；**「前面一个变量节点先赋值，后面再等它」在有初始变量时是错的**。

**评审方结论**：刷新应**只补内存里还没有的键**，或者本图赋值先写回 `run.input.vars`。

### ③（P2）预检仍用 `isLogicNode(显示名)`，不看 `__` 前缀

**位置**：`PreflightChecker`（预检）+ `RealWorkflowRunner.resolveCapability`（能力解析）。

**评审方指出的代码事实**：`isLogicNode` 只认**英文关键词**（`delay` / `variable` / `script` …），不看 `__` 前缀。拖出来的内置节点显示名是「延时」「等待变量」（中文），一条关键词都匹配不上 ⇒ 走 NodeDef 路径时能力被解析成 `UNKNOWN`、候选设备为空，预检报 `PF-01`（没有能力、无法分配设备）。

**影响**：不阻止 API 启动，但设计器顶部会是红的。（变量节点若显示名是「变量节点」，本来也是同一条缝。）
