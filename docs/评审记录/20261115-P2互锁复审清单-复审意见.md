## 2. 清单漏掉的三个问题（按严重度）

### 🔴 B-1　`isRecovered` 在生产代码里**没有任何调用方**——L4 恢复路径根本没接线

清单 P-3.2 写的是"`isRecovered` 只做重新取证，没有人工确认恢复的门禁"，读起来像
"门禁做了但少了人工确认这一环"。**实际情况更糟**：

```
grep -rn "isRecovered" --include=*.java labos-kernel/src/main
→ 只有 StirrerDispenserGuard.java:68 的定义本身
```

调用方**只存在于自测** `L4RecoveryAndReconnectDbSelfTest.java:37,41`。

这意味着：L4 在 `paused_fault` 之后，**没有任何运行时路径会去重新取证搅拌单元状态**。
恢复动作完全依赖 `PauseManager` 的通用 resume 路径——一旦 run 被恢复，搅拌单元是否真的
修好了，系统**不去检查**。这与方案 §3.4「涉及物理故障时还需人工确认恢复」的距离，
比清单描述的远得多：不是"少一环人工确认"，而是**"重取证这一环本身就是断的"**。

> 影响：清单 §2 把 L4-02 标为 ✅「故障清除后恢复 ✅ `isRecovered`」——**这个 ✅ 是虚的**，
> 它测的是一个生产中不存在的函数。

**建议**：P-3 的表述改为「恢复门禁完全未接线」，并把 `isRecovered` 接入 resume 路径
列为 **P0**，而不是设计选择。

### 🔴 B-2　L3 fail-closed + 真库 `transfer_rail_zone` 0 行 ⇒ **客户流程当前 100% 被拦死**

这是本次复审最重要的发现，**清单完全没有提**。

事实链：

1. `RailZoneGuard.acquire` 在分区集为空时 fail-closed 拒绝：
   `RailZoneGuard.java:71-74` → `"搬运路径未配置轨道分区集，禁止自动运行（fail-closed）"`
2. 分区查询是 `path_key` **严格等值匹配**（`RailZoneMapper.xml:9` `WHERE path_key = #{pathKey}`），
   无模糊匹配、无默认值、无兜底。
3. 真库实测（tenant 已建表）：

   | 表 | 行数 |
   |---|---|
   | `rail_zone` | **0** |
   | `transfer_rail_zone` | **0** |
   | `device_fact` | **0** |
   | `stirrer_dispenser_pair` | **0** |
   | `position_scan_evidence` | **0** |
   | `interlock_decision` | **0** |
   | `waiting_interaction` | **0** |

4. 客户流程 `EXT-WORKFLOW-01`（workflow id 1000929）含 **11 个 Transfer 节点**
   （`STACK1-S02 → P_AUTO-N-EXT`、`DISPn-PLATE → P_AUTO-1-EXT`、回程等），
   `source`/`target` 在 `resource_node` 中都能解析（kind=`transfer_point`），
   即**会完整走到 `executeWithPlan` 的 protect 分支**（`LABOS_TRANSFER_PLAN=1` 运行中已开）。
5. 走到 `DriverStepExecutor.java:478` `RailZoneGuard.acquire(...)` ⇒ 路径键查不到分区集
   ⇒ **每次搬运都返回 `EC-INTERLOCK-RAIL`，板不动。**

**结论：P2 合入后、客户流程的轨道分区配置补齐前，`EXT-WORKFLOW-01` 一块板也搬不动。**

清单 P-2 只问了"fail-closed 会不会卡死整条线"——**答案是：已经卡死了，只是没人跑过。**
这恰恰是 §5「建议复审顺序」把验收缺口排在最后一位所埋的伏笔：验收矩阵里没有一行是
"在真库上跑通一次客户流程"。

> 顺带：`device_fact` 0 行 ⇒ **L1 对 4 台提取仪全部静默跳过**（无 `turntable` 事实）；
> `stirrer_dispenser_pair` 0 行 ⇒ **L4 对 6 台分液器全部静默跳过**（未配对即放行，
> 见 `StirrerDispenserGuard.java:43-45`）。两项互锁当前**完全未生效**。
> `waiting_interaction` 0 行 + 客户流程 Transfer 节点 0 个带 `interactionId`
> ⇒ **L5 对全部 11 个搬运节点静默跳过**。

**净效果：五条互锁里，L1/L4/L5 当前全是"空转"，只有 L2/L3 在"硬拦"——而 L3 因为没配置
把线卡死了。** 换句话说，P2 当前的实际状态是「该拦的没拦，不该拦的全拦了」。

**建议**：
- P-2 升级为 **P0 可运行性阻断项**，明确回答"配置未齐时如何不卡死"：
  建议 **fail-open + 告警**（未配置分区集 → 放行 + 落 `interlock_decision` 告警 + 预检标红），
  或至少**按路径粒度** fail-closed（只拦已声明要走轨道的路径），而不是全局 fail-closed。
- 真库必须补 `rail_zone` + `transfer_rail_zone` 种子数据，否则 P2 无法进入任何真机验收。
- 清单 §2 验收矩阵应**新增一行**：D-00「在真库跑通一次客户流程 EXT-WORKFLOW-01 的
  至少一次 Transfer」——这才是 P2 的**最低可运行性判据**，目前缺失。

### 🟠 B-3　永久预留（`promoteReservationToForever`）**没有任何释放路径**——比清单说的更硬

清单 P-5.2 问："有没有恢复/清理路径？"

核验结果：**没有。**

- `promoteReservationToForever` → `reserved_until = NULL`（`DeviceStateMapper.xml:201-207`，
  `NULL` 即"永久"语义）
- `releasePosition` / `releaseAllPositions` 是**唯一**能清掉它的 SQL
  （`DeviceStateMapper.xml:237-247`）
- `releaseAllPositions` 的生产调用方：**无**（`PositionLock.releaseAll` 无调用者）
- TTL 清理 SQL `releaseExpiredPositions` 条件是 `reserved_until < now()`，
  对 `reserved_until IS NULL` 的永久预留**永远不生效**
- `HeartbeatService` 的孤儿清理只调 `DeviceLock.releaseOrphans()`（设备锁），
  **不管 `position_state`** —— 清单这条描述准确

**后果（比"孤儿锁"更具体）**：证据确认路径下，只要设备回包成功、`putPlate` 证据确认环节
没走完（人工没确认 / 扫码没扫 / 确认接口漏调），该目标位就**永久锁死**，
且没有任何定时任务/人工操作能把它解开——只能手工改库。
客户流程 11 个搬运节点 × 每节点 1 个目标位 = 跑几轮就把耗材栈和提取仪交互位全部锁死。

**建议**：
- 增加**按 run 维度的位置预留清理**（run 结束/异常终止时释放该 run 名下所有
  `reserved_until IS NULL` 的预留），接到 `releaseAllPositions` 已有 SQL 上即可（**SQL 已在，
  只缺调用方**）。
- 这条应该是 **P0**，不是"评审请判断可接受性"。

## 4. 对六个评审重点的补充建议（可直接进交叉评审）

- **P-1**：同意强制预检。但建议**先做「配置完备性预检」而不是「事实存在性预检」**——
  真库 `device_fact` 0 行说明当前连"提取仪是否会上报 turntable"都无从验证。
  预检应查"型号登记里是否声明了会报哪些事实"，而不是查"库里现在有没有事实行"。
- **P-2**：见 B-2，建议明确 fail-open/fail-closed 的**分路径策略**。
- **P-3**：见 B-1，`isRecovered` 接线是 P0，不是设计选择。
  另：多 run 共用搅拌器的反查，建议**按 `stirrer_resource_id` 反查配对的所有 run**，
  复用 `stirrer_dispenser_pair` 表（真库 0 行，需先补数据）。
- **P-4**：`scan_id` 建议绑定设备侧事件 id（`source_event_id`），本地合成的
  `scan-r{run}-n{node}-s{step}-a{attempt}` 在**重试场景下 attempt 变**，
  同一条真实扫码事件会被登记成两条证据 → 两次消费。这个洞在重试时必然踩到。
- **P-5**：见 B-3。建议 `confirmWithPosition` 的 REPORTED 白名单**写成验收测试断言**（清单已提，认可）。
- **P-6**：建议补 `EC-COMMUNICATION` 独立码。当前通讯异常被并进 `EC-STATE-UNKNOWN`，
  但 `DriverStepExecutor.scopeOf` 靠前缀（`EC-05-10` / `EC-99-`）分流恢复作用域
  （`DriverStepExecutor.java:310-316`）——`EC-STATE-UNKNOWN` 不匹配任何前缀 ⇒
  **落到 `RecoveryScope.NODE`**，而通讯异常理应是 `COMMAND` 级（设备状态不可信，
  应在设备级恢复）。**分类错误会导致恢复作用域错配**，这个建议从"可选"升级为"应补"。
