## 二、意见清单

### ①（P0）RemoteDeck 整节不成立 —— 上游材料第 4 节不可用

**上游材料说法**：`pylabrobot.resources.remote.server` 可以把 deck 跑成独立 http 服务，其他进程用 `RemoteDeck` 连接，适合中控跨语言/多机共享工位状态，并据此建议「RemoteDeck 作为跨语言桥」。

**核实结果**：不存在。

- PyPI `0.2.2` 全包检索 `RemoteDeck` / `resources.remote` / `RemoteResource` 0 命中；`pylabrobot` 下没有 `remote` 或 `server` 目录。
- GitHub main 上 `pylabrobot/resources/remote` 与 `pylabrobot/server` 均返回 HTTP 404。
- 唯一来源是论坛帖「Deck API」引用的 PR `https://github.com/PyLabRobot/pylabrobot/pull/896`（deck server/client over a remote API）。该 PR 状态为 **`state=closed`、`merged=False`、最后更新 2026-05-12**，即提出后未合入主干。
- 网上另有 fork 的 `pylabrobot[server]` HTTP server 说法，非官方发行物。

**影响**：按此设计跨语言桥会直接落空。**替代方案**：本仓 `labos-kernel/proto/driver.proto` 已定义 `DeviceDriver.Describe / Health / Execute / Abort / Subscribe`，且 `DriverDescriptor.driver_kind` 注释已列出 `python`；`DeviceDriver.java` 注释也把「gRPC 驱动：跨进程」列为四种实现形态之一。跨语言桥应走自有的 gRPC 契约，而不是等 PR。

### ②（P0）两套仿真后端的名字都已过时 —— 上游材料第 2 节需整体改名

**上游材料说法**：`SimulatorBackend`（Web 3D、websocket、localhost:2121、headless）与 `ChatterboxBackend()`（轻量 mock）；切换后端只改一行；真机用 `STARBackend(...)`。

**核实结果**：

| 材料 | 0.2.2 真实情况 | 证据 |
|---|---|---|
| `SimulatorBackend` | **已删除**；官方 rst 原文 `The simulator was removed in favor of the Visualizer` | `docs/user_guide/machine-agnostic-features/using-the-simulator.rst`（main raw） |
| Web 3D 可视化 | `Visualizer(resource, host="127.0.0.1", ws_port=2121, fs_port=1337, open_browser=True)`；**2121 是 websocket 端口，网页在 1337** | `pylabrobot/visualizer/visualizer.py:117-133` |
| `ChatterboxBackend()` | 类仍存在但构造即 `raise NotImplementedError`，明确要求改用 `LiquidHandlerChatterboxBackend` | `backends/chatterbox_backend.py:1-6`、`backends/chatterbox.py` |
| `STARBackend(...)` | 类真实存在（`STARBackend` 与子类 `STAR`）；另有 `STARChatterboxBackend` 通过 `logger.log(LOG_LEVEL_IO)` 离线吐固件命令 | `backends/hamilton/STAR_backend.py:1625,15319`、`STAR_chatterbox.py:205` |

**补充**：`LiquidHandlerChatterboxBackend` 是纯内存打印后端，不启端口、不渲染，适合 CI；`Visualizer` 即使 `open_browser=False` 也会起 ws + file server 两个本地端口，二者不能混为一谈。

### ③（P0）Tracker 默认关闭 —— 「自动跟踪 + 操作前校验」是静默放行

**上游材料说法**：`LiquidTracker / TipTracker` 自动跟踪每个孔剩余液体、吸头是否存在，操作前做校验，没吸头/液体不够/越界直接抛异常。

**核实结果**：

- 类名错：`LiquidTracker` 不存在，真名 `VolumeTracker`（`resources/volume_tracker.py:36`）与 `TipTracker`（`resources/tip_tracker.py:36`）。
- **两者默认全局关闭**：`volume_tracking_enabled = False`、`tip_tracking_enabled = False`；`LiquidHandler.aspirate` 里 `if does_volume_tracking(): ... remove_liquid(...)`（`liquid_handler.py:1032`），关着就整段跳过。必须显式 `set_volume_tracking(True)` / `set_tip_tracking(True)`。
- 实测（本机离线 PoC）：默认 A1 设 200 µL，跑完 `pick_up_tips → aspirate 50 → dispense 50` 后 **A1 仍 200、B1 仍 0**；显式开启两个开关后 **A1=150、B1=50**，且丢弃枪头后 `has_tip=False`。
- 事务语义：Tracker 是 `pending_volume` + `commit()` / `rollback()` 两阶段，由 `LiquidHandler` 在 backend 成功后提交（例：`liquid_handler.py:1040-1070`）。**后端不参与时状态不会自动推进**。

**影响**：这是最危险的静默坑 —— 「没报错」不等于「校验过」。任何接入方必须在启动/health 断言两个开关为真。

### ④（P1）序列化 API 名称错误，且快照恢复必须两步

**上游材料说法**：`resource.to_json()` / `from_json()`，整台 deck 布局 + 液体状态可保存/加载，适合任务快照、断点续跑。

**核实结果**：

- `to_json` / `from_json` 在全包 0 命中。真实 API：`serialize()` / `deserialize()`（`resources/resource.py:127,728`）、`load_from_json_file()`（`:783`）、`LiquidHandler.serialize() / deserialize() / load()`（`liquid_handler.py:2507,2515,2539`）、`serialize_state() / load_state()`（`:214,239`）。
- **布局与状态是两套**：`deck.serialize()` 是资源树（实测 142,010 字节），`deck.serialize_all_state()` 才是液位/枪头等状态，`load_all_state()` 回灌。
- 实测：`Deck.deserialize(layout)` 后 A1 液位 = **0**；再 `deck.load_all_state(state)` 后才恢复到 88。`serialize_state()` 只含 `rotation / head_state / head96_state / arm_state`，不含 deck。
- 自定义耗材「导入自己的耗材 JSON」被夸大：`load_from_json_file` 加载的是**已序列化的 PLR 资源树**；定义新 labware 通常要写 Python 工厂函数（`create_plate(...)` 等）。

**影响**：只做 `deserialize` 就宣称「断点续跑」会产出「布局对、液体全空」的错误状态，且不报错。

### ⑤（P1）异常体系、事件流、`plan_batches` 的归属均需修正

| 材料 | 核实 |
|---|---|
| `NoTipError`、`ResourceNotFoundError` | 真实（`resources/errors.py`） |
| `InsufficientVolumeError`、`CollisionError` | **不存在**；真实为 `TooLittleLiquidError`、`TooLittleVolumeError`、`HasTipError`、`CrossContaminationError`（已弃用）、`NoLocationError` |
| 「所有 backend 统一异常体系」 | 不成立：各设备包另有自己的 `errors.py`（如 `plate_reading/molecular_devices/backend.py`） |
| 「命令生成事件流，可在中控层 hook」 | 部分是：真实机制是 `Resource.register_state_update_callback` / `register_did_assign_resource_callback`（`resource.py:801-814,924`），`Visualizer` 订阅后推 ws；**backend 层没有统一事件流**。实测注册回调后收到状态序列 `[123.0, 100.0]` |
| 「LiquidHandler 内置 `plan_batches`」 | 真实存在但归属不同：`pylabrobot/liquid_handling/pipette_batch_scheduling.py:362` 的 `plan_batches()` + STAR backend 的 `execute_batched()`，用于通道 X/Y 分批，不是 `LiquidHandler` 的公开批量规划 |
| 「iSWAP 移板机械手社区还在孵育」 | 已实现：`LiquidHandler.pick_up_resource / move_resource / move_plate / move_lid`（`liquid_handler.py:2038-2439`），`STARChatterboxBackend` 还带 iSWAP 配置 |

### ⑥（P1）「没有 LLD / 工艺参数」是半错，会导致误判能力边界

仿真层确实没有压力曲线、液体粘滞、移液 CV、气泡、堵针、滴液的物理模拟（这点材料正确）。但**真机后端有工艺能力**：

- `liquid_classes/hamilton/star.py`（约 5,900 行）是完整的液体类别参数表，按 tip 体积 / CO-RE / 滤芯 / 液体 / jet / blow-out 组合给出吸分液参数。
- `STAR_backend.py` 有 cLLD / pLLD 液面探测：`probe_liquid_heights`（`:2811`）、`probe_liquid_volumes`（`:2968`）、`request_pip_height_last_lld`（`:7784`）、`head96_probe_z_using_clld`（`:8742`）等。

**正确表述**：PLR 不提供「物理过程仿真」，但提供「厂商工艺参数与液面探测命令」。做工艺验证时要自己叠加误差/故障注入层，别把「仿真不模拟物理」写成「库里没有工艺参数」。

### ⑦（P2）生态、版本与部署口径补充

- **许可证**：MIT（`0.2.2` METADATA），本仓 Apache-2.0，兼容可商用/可闭源，分发需保留 MIT 版权声明。

### ⑧（P1）架构建议需改：不要替换 `DeviceDriver`

上游材料建议把 PLR 的 `LiquidHandler` 作为中控「统一抽象层」，替换/统管下发指令。对照本仓代码，这会削掉现有保证：

- `DeviceDriver.execute(DriverCommand)` 强制「同一 `commandId` 幂等」（`DeviceDriver.java:19-57`），`CommandLedger` 做启动对账，`PositionLock` / `WaitForGraph` 保证物理动作不重、不串板，`PauseCoordinator` / `RuntimeHold` 保证只在动作边界暂停，`run_event` 是 append-only 审计与回放数据源。**PLR 没有幂等键、排队、资源抢占、暂停恢复**（这点材料第 8 节判断正确）。
- 本仓 `resource_node` 是「岛 → 设备 → 层位 → 板」的**车间拓扑**（`20_kernel.sql:26-53`），PLR deck 是**单台机器的台面 mm 坐标**；两者不是同一层，不能互相替代。
- 真机现状：`DeviceModels.java` 只有 `aspin-2k`（离心机）、`s100`（封膜机）有 `Evidence.MANUAL` 手册，`ROADMAP.md:66` 与 `docs/生产化路线图.md` 明写「没接过真机」，M10 才做真机接入。

**建议定位**：PLR = **离线移液语义编译器 + 状态预校验器**；LabOS 继续持有调度、锁、账本、暂停、PG 真源。三条边界：① 不让 PLR 直连硬件绕过 `CommandLedger`；② 不让 PLR deck 成为第二真源；③ 不把 `Visualizer` 当生产监控。

**材料没提但对中控最有用的能力**（本次新发现）：

- `SerializingBackend`（`backends/serializing_backend.py`）：把每条语义原语序列化成 JSON 交给 `send_command(command, data)`。实测一段 4 步移液产出 5 条命令（`setup / pick_up_tips / aspirate / dispense / drop_tips`），含 `resource_name / offset / tip / volume`。
- `pylabrobot/liquid_handling/standard.py` 的 frozen dataclass 指令对象（`Pickup / SingleChannelAspiration / MultiHeadDispensePlate / ResourceMove` 等），是现成的厂商无关中间指令层，比本仓 `capability_recipe` 的字符串序列（`30_business.sql:416-431`）强一个量级。

### ⑨（P2）并发产物 `pylabrobot-sim/` 的复核清单

评审时工作区已有未跟踪目录 `pylabrobot-sim/`（13 MB，含 `.venv` 与 3 份 `out/*.json`；`.gitignore` 已加入 `pylabrobot-sim/.venv/`）。只读核查 `run_simulator.py` 初步结论：**方向与本评审一致**（pin `0.2.2`、第 83-84 行显式开启两个追踪开关、使用 `LiquidHandlerChatterboxBackend` 与 `STARDeck()` 工厂函数、`Visualizer(ws_port=2121, fs_port=1337, open_browser=False)`、`command_id` 幂等命中返回历史结果、错误码 `EC-06-000x`、`selftest` 16/16 通过）。

建议在合并/进 CI 前补 5 项复核（本轮**未改动**该目录）：

| 项 | 复核点 |
|---|---|
| 1 | health/启动断言 `does_volume_tracking()` 与 `does_tip_tracking()` 均为真，避免未来重构后静默放行 |
| 2 | 状态输出是否**派生自 PLR tracker**，还是另维护一份 dict 账本；后者是双真源，需明确谁是权威 |
| 3 | 若要支持快照/断点续跑，必须 `serialize()` + `serialize_all_state()` 两步、`deserialize()` + `load_all_state()` 两步 |
| 4 | `Visualizer` 即使 headless 也占用两个本地端口；CI 与生产端口冲突要有开关（已有 `no_visualizer` 参数，需确认默认） |
| 5 | 异常映射：`TooLittleLiquidError` / `NoTipError` / `HasTipError` → 本仓 `error_code` + `recovery_policy`，禁止 Python 异常裸奔进内核 |

## 三、核实为对齐的部分

| 项 | 结论 |
|---|---|
| 资源是树形、与后端无关，仿真/真机共用定义 | 对齐：`Resource` / `Deck` / `Carrier` / `Plate` / `Well` / `TipSpot`，每个 well 有坐标、体积、容量 |
| Hamilton 台面定义 | 对齐，但 `STARDeck` / `STARLetDeck` 是工厂函数返回 `HamiltonSTARDeck`，`VantageDeck` 是类 |
| 海量预制耗材库 | 对齐：`pylabrobot/resources/` 下数十厂商目录，含吸头盒、96/384 板、深孔板、储液槽、载架 |

## 六、建议架构与契约映射

```
LabOS（BPMN 编排 / ExperimentScheduler / 锁 / 账本 / 暂停恢复 / PG 真源 / 审计）
   │  DriverCommand(method, params, commandId)
   ▼
[阶段 0] Python「工艺编译器」（离线，无硬件）
   ├─ 输入：deck 布局 JSON + 语义化移液任务
   ├─ PLR：VolumeTracker / TipTracker 预校验（必须显式开启）
   ├─ SerializingBackend → 标准命令 JSON 序列
   ├─ STARChatterboxBackend → 可选固件命令（离线核对）
   └─ 输出：ok / violations[] / commands[] / deck 快照
   ▼
[阶段 1] Java 侧把 commands[] 映射到 DriverCommand 或 gRPC Execute
   （driver.proto 的 driver_kind 已预留 python）
[阶段 2] M10 真机之后再评估 STARBackend 直连 USB 固件
```

| LabOS | PLR | 规则 |
|---|---|---|
| `DriverCommand.commandId` | 无对应 | **幂等键必须由 LabOS 生成并全程携带**，PLR 侧禁止重放 |
| `DriverCommand.method` | `pick_up_tips / aspirate / dispense / drop_tips / move_plate` | 由 `SerializingBackend` 的 `command` 字段映射 |
| `params` Map | `send_command` 的 `data` JSON | `resource_name / offset / tip / volume` 需转成 `labware / well / volume` |
| PG `position_state` / `plate_well` | PLR deck（副本） | **单向**：PG 决定板在哪，PLR 只算孔里多少液；绝不反向写 PG |
| `error_code` + `recovery_policy` | `TooLittleLiquidError` / `NoTipError` / `HasTipError` | 统一映射成 `EC-09-xxxx`（参数/资源错误，不可重试）等 |
| `run_event` 审计 | 可选 `register_state_update_callback` | 只作补充，主审计仍是 PG |
| `VirtualDriver` / `DeviceSimulator` | `LiquidHandlerChatterboxBackend` | 补充而非替换：CI 加一层语义级回归 |

最小骨架（阶段 0 PoC 起点）：

```python
from pylabrobot.resources import Deck
from pylabrobot.resources.volume_tracker import set_volume_tracking
from pylabrobot.resources.tip_tracker import set_tip_tracking
from pylabrobot.liquid_handling import LiquidHandler
from pylabrobot.liquid_handling.backends.serializing_backend import SerializingBackend

set_volume_tracking(True)   # 不写这两行，所有防错静默失效
set_tip_tracking(True)

class EmitBackend(SerializingBackend):
    def __init__(self):
        super().__init__(num_channels=8)
        self.commands = []
    async def send_command(self, command, data=None):
        self.commands.append({"command": command, "data": data})
        return None

# layout_json / tips / plate 由调用方按台面布局构造（此处省略）
lh = LiquidHandler(backend=EmitBackend(), deck=Deck.deserialize(layout_json))
await lh.setup()
await lh.pick_up_tips(tips["A1"])
await lh.aspirate(plate["A1"], vols=[50.0])
await lh.dispense(plate["B1"], vols=[50.0])
await lh.drop_tips(tips["A1"])
snapshot = {"layout": lh.deck.serialize(), "state": lh.deck.serialize_all_state()}
```

恢复时两步（漏第二步液体全空）：

```python
deck = Deck.deserialize(snapshot["layout"])
deck.load_all_state(snapshot["state"])
```

## 八、风险与红线

1. **禁止 PLR 绕过 `PositionLock` / `CommandLedger` / `PauseCoordinator` 直连硬件**。PLR 没有排队、资源抢占、暂停恢复、幂等键，绕过即丢掉「物理动作只发一次、板不串、可暂停」三条保证。
2. **追踪默认关闭是最大静默坑**：启动必须显式开启，并在 health 中断言；否则「没报错」不代表「校验过」。
3. **双真源**：PLR deck 只能是副本，PG 是唯一真源；不要把 142 KB 的 deck JSON 当审计记录写库。
4. **快照两步**：布局 `serialize()` + 状态 `serialize_all_state()`，恢复 `deserialize()` + `load_all_state()`，缺一不可。
5. **反序列化安全**：`deserialize(..., allow_marshal=True)` 会反序列化函数对象，等于执行代码；只允许读自己生成的可信文件。
6. **版本漂移**：main 正在重构，pin `0.2.2`；升级前跑 P0 的三后端一致性回归。
7. **部署负担**：本仓无 Docker、纯 shell + 裸进程（`docs/现场部署手册.md`）；阶段 0 用 CLI/文件交互最省事，阶段 1 才引入常驻 Python 进程（需补 venv + 守护 + 心跳）。
8. **Visualizer 只做离线回放**：即使 headless 也起两个本地端口 + websocket，不接生产状态，也不能替代 `run_event`。
9. **SiLA 别误读**：`io/sila` 是客户端 wire helpers，`README.md` 的「SiLA 2 adapter / Converter」承诺仍需自行实现，不构成合规声明。
10. **工艺验证**：误差模型（CV、堵针、滴液、残液）需在 PLR 之上自建 Decorator/故障注入层；仿真通过不等于 HIL 通过，符合 `docs/architecture/LABOS_PAUSE_EXTERNAL_PRACTICES_AND_ADR_20261107.md` 的证据等级约束。
