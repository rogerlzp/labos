## 一、评审原文（要点摘录）

### 1.1 总体判断

> 原始设计稿解决的是"业务需要什么"；V0.1 解决的是"长期应该建立什么领域模型"；v2 解决的是"现在怎样基于现有代码可靠地实现"。
> 三者并不真正冲突，主要是设计层次和实施范围不同。

> **不要简单地把三份文档拼在一起。** 应该以 v2 作为第一期实施架构，以 V0.1 作为长期领域模型和扩展边界参考，再把原始设计稿中的业务需求逐项映射进去。

### 1.2 建议的四层结构

```
① Material Identity    Plate Identity / Barcode / Container Type      它是谁？
② Material State       Process State / Seal State / Position / Well   它现在是什么？
③ Execution & Effect   Execution Fact → Material Effect → Event      哪次执行改变了它？
④ Traceability         History / Reconciliation / Manual Correction   出错后怎么恢复？
```

> **当前状态是历史事件的投影，不是历史本身。**

### 1.3 建议保留的 v2 设计（12 条）

`process_state_code` / `seal_state` / `plate_well` 为权威 / `position_state` 复用 /
`material_effect` 独立业务字段 / Run 启动快照 / T1-T2 分离 / `plate_material_event` 不可变 /
`state_version` 防覆盖 / 图执行与顺序执行共用完成处理器 / 失败只补偿不重做设备动作 / 精确区分 `loop_index`。

### 1.4 建议推迟的内容

完整通用 Material 主实体 / 通用 Location 层级 / 完整耗材库存 / 化学反应与复杂转化 / 自动感知所有设备物理变化。

> 特别强调：**不建议现在再建立一套与 `position_state` 并行的位置管理系统，也不建议重复建设 `plate_well` 已经承担的样本内容模型。**

### 1.5 最终设计原则（评审方原文）

> **物理执行事实优先于软件推测；身份优先于位置推断；历史事件优先于事后覆盖；恢复状态处理优先于重新执行设备动作。**

## 三、被评审方逐条回应

> 依 `docs/评审规范.md` §四，逐条给结论 / 理由 / 处置 / 验证。

### O-1 · T1/T2 的失败恢复 —— **接受**

**结论**：接受。v3 §5.2b 已先行写了「两级失败语义」（T1 失败 ⇒ 阻断 run；T2 失败 ⇒ 不阻断节点但扣下游），
但评审点出的 **`failed → pending` 是受权限控制的恢复操作、每次尝试都要留审计**，v3 确实没写。

**理由**：这是真缺口 —— v3 只写了"补偿任务按已解析的 `plate_id` 重放"，
没说清**谁能做、要不要写原因、重复补偿怎么留痕**。

**处置**：v3 §5.8 补一张「恢复操作语义」表：`FAILED → PENDING` 不是普通字段更新，
是**受权限控制的恢复操作**（需原因、记录操作人、每次尝试各留一行 `RECONCILIATION` 事件、
多任务并发用 `state_version`/行锁挡住）。

**验证**：v3 §11.2 的 T16（`FAILED → PENDING` 的权限/原因/审计完整）与 T19
（人工修正后旧回调不得覆盖人工确认）覆盖。

### O-2 · 跨租户数据库约束 —— **接受**

**结论**：接受。v3 §7 只做了 `plate ↔ 字典` 的复合外键，**没做 effect/event 与 plate/run_node 的跨租户约束**。

**理由**：评审说得对 —— 只靠 Service 层检查，跨租户引用在并发/直连 SQL 下仍能成立。

**处置**：v3 §7 补三组复合外键：
`plate_material_effect(tenant_id, plate_id) → plate(tenant_id, id)`、
`plate_material_event(tenant_id, plate_id) → plate(tenant_id, id)`、
`plate_material_event(tenant_id, effect_id) → plate_material_effect(tenant_id, id)`。

**验证**：v3 §11.2 的 T15（跨租户引用被数据库拒绝）；并在 DDL 实跑里验证外键真的拒。

### O-3 · 目标板解析的证据优先级 —— **接受**

**结论**：接受。

**理由**：v3 §6.3 说了"位置只是辅助、设备命令证据才是运行时证据"，
但**没说冲突时听谁的** —— 而这正是评审担心的。

**处置**：v3 §6.3 补**证据优先级**（显式 barcode/plate_id > 设备命令回包里的物料标识 >
命令参数里的目标位置 > 位置状态投影），并写明**位置状态与设备证据冲突 ⇒ 进 `NEEDS_RECONCILIATION`，
不自动采信任何一方**。

**验证**：v3 §11.2 的 T10（身份不明确不靠位置猜）与 T12（声明与执行结果不一致 ⇒ `REJECTED`）。

### O-4 · 执行路径覆盖 + `loop_index` 的真实规则 —— **接受，且查出了新东西**

**结论**：接受。**这一条促使我去查了 `loop_index` 的真实来源，结论比评审预期的更细。**

**评审的要求**：「必须明确 `loop_index` 的实际生成、传递和持久化规则，
不能仅在设计文档里假设 `visit` 与数据库圈次完全一致」。

**我实际查到的（2026-11-12 回源码核对）**：

| 事实 | 证据 |
|---|---|
| `visit` 从 **1** 开始 | `GraphRunner.java:536` `visits.merge(key, 1, Integer::sum)` |
| 圈次落库用 `visit` 本身 | `GraphRunner.java:657` `roundRecorder.record(key, visit, …)` |
| 落库时 `loop_index = round` ⇒ **1..N**；汇总行 `loop_index = 0` | `WorkflowService.java:1020`、`1904-1921` |
| ⇒ **`visit` 与圈次行 `loop_index` 一致**（都是 1..N） | 上面两条合起来 |
| ⚠ **但 `roundRecorder` 只在 `graphHasCycle && visit >= 1` 时调用** | `GraphRunner.java:654` |
| ⇒ **无环图的节点只有汇总行（`loop_index=0`），永远不会落 1..N 的圈次行** | 同上 |

**这条对幂等键有实质影响（v3 没写对的地方）**：

> **幂等键里的 `source_loop_index` 必须取 GraphRunner 的内存 `visit`，不能取 `run_node.loop_index`。**
> 因为 `run_node` 里同一个 node_key 有**两行**（汇总行 0 + 圈次行 1..N），
> 而无环图又只有汇总行 ⇒ 读库里的 `loop_index` 会得到语义不一致的值。

**处置**：v3 §5.5 写死这条规则，并说明 `attempt` 不入键的理由
（设备重试不改 `visit` ⇒ 同一逻辑执行重试 N 次仍是同一个 `execution_id` ⇒ 效果只应用一次 ✓）。

**验证**：v3 §11.2 的 T04（循环多轮可区分）与 T05（重试与执行实例不混淆）。

### O-5 · 领域扩展能力 —— **接受**

**结论**：接受。v3 §6.2 已用 `inputs` / `outputs` / `operations` 预留，
评审的担忧（第一期一对一会封死未来）已被覆盖。

**处置**：v3 §6.2 补一句明确口径：**本期"只支持一对一"是**校验规则**的限制，不是表结构的限制。**
