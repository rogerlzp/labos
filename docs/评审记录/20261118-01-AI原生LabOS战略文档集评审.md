# AI-native LabOS 战略文档集评审

> **用途**：本文件可直接作为该分支 PR 或 issue 的正文使用。
> **评审对象**：分支 `docs/ai-native-labos-strategy-clean-20261118` 的 `docs/ai/` 目录，共 11 份文档
> （`README.md`、`01-PRODUCT-STRATEGY.md` ~ `06-AI-WORKBENCH-DAY1-7.md`、`g0/` 下 4 份）。
> **源码核查基线**：`bef848e47131356494c3b20460fc77ce33232020`；G0 报告全文绑定该基线。
> **评审方式**：通读 11 份文档；并在核查基线上对 2 个 FAIL 项做源码交叉验证（见意见 4、5）。
> **证据分级**：本文严格区分【现状事实】（可定位源码/API/迁移/测试）、【目标设计】（提案，不代表已具备）、
> 【实施计划】（未开发/未运行/未验收）、【未知事项】（证据不足，保持 UNKNOWN）。
> **结论摘要**：**支持方向，反对当前排期**。3 处跨文档冲突须先裁决，否则按任一单篇执行都会返工。

---

## 总评（对应 README「核心原则」逐条判断）

| 文档核心原则 | 本评审结论 |
|---|---|
| AI 负责推理与建议，LabOS 负责授权、校验、执行、状态和事实 | **支持**。与源码现状一致，且 G0 已诚实标注 PARTIAL/UNKNOWN，没有把提案写成已完成。 |
| 自然语言不能直接变成设备命令 | **支持**。但 30 天方案与 G1 门槛在"项目级 ACL / 多租户"上冲突，见意见 2。 |
| Agent 不直接访问数据库、Mapper、驱动或设备网络 | **支持**。缺一张跨 user/agent/device/callback 的 principal 传播图，见意见 9。 |
| 命令完成 ≠ 物理完成 | **支持**。G0-03/G0-08 的取证分级是对的。 |
| 先做一个真实实验场景，不先建通用平台 | **支持**。但"第一阶段场景"有三套定义，见意见 1。 |

**最有价值的一点**：把证据纪律写进流程（区分现状/目标/计划/UNKNOWN、不把 PARTIAL 说成完成、
不把仿真当真机）。**最大风险**：纪律执行不均匀——每份文档都正确标注了自己的边界，
但跨文档没有人对齐，每份都"对"合起来不可执行。

## 逐条意见

### 意见 1（P0 阻塞）：第一阶段交付存在三套互不等价的定义

- **结论**：需要补充证据（要求收敛为一套说法）。
- **位置**：
  - `03-AGENT-AND-CAPABILITY-PLATFORM.md` §10 MVP-A / MVP-B / MVP-C；
  - `g0/03-G0-REMEDIATION-AND-NEXT-STEPS-20261118.md` §4 G1 首批工具表；
  - `05-AI-WORKBENCH-0-30D.md` §0.1 三类异步任务、§7 四批交付。
- **依据**：【目标设计】三处对"第一阶段交付"的定义分别为：
  ① 通用只读 Copilot + 流程草案 + 执行监控三个 MVP；
  ② 6 个具体只读工具（`get_experiment_status`、`get_run_timeline`、`get_device_health`、
  `get_material_location`、`explain_blocker`、`search_verified_protocols`）；
  ③ 三类异步任务（`EXPERIMENT_DRAFT`、`READINESS_EXPLAIN`、`RUN_REVIEW`）。
  第三套**没有实现第二套中的任何一个工具**，且 `READINESS_EXPLAIN`（启动前阻塞解释）
  不落入第一套任何 MVP。这不是措辞差异：按②做得到通用只读助手，按③做得到三份结构化报告，
  接口、工作量、验收用例几乎不重叠。
- **风险**：交付范围（开发按 05 做完，验收方按 03/g0 判不通过）；重复建设或双向返工。
- **建议**：在 `05` §0.1 明确声明"30 天方案是对 MVP-A 的范围收缩（特定场景替代通用助手），
  通用只读工具推迟到 G1 后期"，并同步改写 `03` §10 与 `g0/03` §4；
  用一张「MVP ↔ 30 天任务 ↔ G1 工具」映射表替代三份并列的清单。
- **验收**：三份文档的第一阶段交付清单逐项一一对应；若某 MVP 延后，必须写明延后到哪一期。
  **必须保持 UNKNOWN 的情况**：任何工具/任务未实际联调通过前，不得在映射表中标为"已具备"。

### 意见 2（P0 阻塞）：G1 准入门槛与 30 天 Workbench 范围直接冲突

- **结论**：反对（反对用同一套门槛约束两种范围）。
- **位置**：`g0/03` §3 G1 准入门槛、`04-ROADMAP.md` §4 G1 验收；
  `05-AI-WORKBENCH-0-30D.md` §0.4 R4 / §6 / `06-AI-WORKBENCH-DAY1-7.md` T3 §4.3。
- **依据**：【现状事实】`g0/03` §3 要求"tenant/user/project 上下文和**对象级读取 ACL 已明确**"
  才允许只读原型接入真实项目数据；`04` §4 要求"越权查询被拒绝"。
  【实施计划】`05` R4 与 `06` T3 明确"本期只声明角色 + 租户隔离，**项目级 ACL 不实现**"，
  `04` §7 风险表也承认当前大量 Controller 与 AuthService 固定 `TENANT=1`。
  按前者 30 天方案不准启动；按后者门槛被静默降级。
- **风险**：权限/安全——执行团队各按一份理解，出现"做完了但没达标"；
  或为过门槛临时补 ACL，破坏 30 天估工。
- **建议**：把门槛拆成两档——「G1 只读原型接入真实数据的最低门槛」
  （租户过滤 + 角色 + 越权返回 404 + 无写工具，30 天方案已覆盖）
  与「G1 全量开放门槛」（对象级 ACL 绑定 G4）。
- **验收**：`g0/03` §3 的 6 个复选框逐项标注"30 天可满足 / 延后至哪一期"，不留模糊项。
  **必须保持 UNKNOWN 的情况**：项目级 ACL 未实现前，不得宣称"项目隔离已通过测试"，
  只能标注"角色 + 租户隔离已测，项目级 UNKNOWN"。

### 意见 4（P1 严重）：G0-01 应独立为 P0 热修，不要绑在 AI 排期上（源码已核实）

- **结论**：反对（反对当前 P1 定级与"G1 准入前修复"的时点）。
- **位置**：`g0/01` §3 G0-01；`g0/03` §2 第 1 行；源码 `WorkflowRunGate.java` `check()`。
- **依据**：【现状事实，已交叉验证】在基线 `bef848e` 上读取 `WorkflowRunGate.java`，
  `check()` 确有三处 `return Decision.allow()`：参数不全、词表为空、`SQLException`；
  而同文件 Javadoc 宣称 `ExperimentExecutor.run(...)`"与 HandoffGate / 岛边界同口径 **fail-closed**"。
  实现与承诺相反。源码注释自带的实测数据佐证其保护对象：两 run 并行已到容量边缘、四 run 必排队、
  run 1001411 搬运等 62.7s 后 `EC-RESOURCE-BUSY`；设备事件先到先得、后到的 run 永远等不到。
- **风险**：安全 / 物理事实——这是**现网就存在的门禁失效**，与 AI 是否上线无关；
  可能导致同流程多 Run 抢消费设备事件、争用唯一机械臂。
- **建议**：拆成独立热修，不占 AI 项目工期；把"门禁无法判断"独立建模为 `UNKNOWN / ERROR`，
  绝不与 `ALLOW` 合并（ADR-G0-01 的原则必须落到代码注释）；排查是否已发生过事件串扰；
  生产配置禁止无审批的 `LABOS_WORKFLOW_CONCURRENT_RUN=allow`。
- **验收**：`WorkflowRunGateDbSelfTest` 增加 DB 断开、词表空、参数非法、并发竞态四例并实跑通过；
  两条入口（Web `run` 与 `ExperimentExecutor`）消费同一个决策结果。
  **必须保持 UNKNOWN 的情况**：未拿到现场事件日志前，不得断言"历史上从未发生串扰"。

### 意见 5（P1 严重）：G0-07 属实，且是纯代码缺陷（源码已核实）

- **结论**：支持（核查结论正确，建议立即修）。
- **位置**：`g0/01` §3 G0-07；源码 `RecipeCompiler.java` `compileAll(...)`。
- **依据**：【现状事实，已交叉验证】基线 `bef848e` 中三参数重载
  `compileAll(nodes, protocolCap, capabilityByResource)` 的循环内调用的是 `compile(n, protocolCap)`，
  后者再落到 `compile(node, protocolCap, Map.of())`——设备能力映射被 `Map.of()` 吞掉。
  G0 报告定位准确，`RecipeCompilerTest` 确实未覆盖该分支。
- **风险**：物理事实——编译预览忽略绑定设备能力，可能产生错误能力解析并进入执行。
- **建议**：作为独立小提交修复透传，并补回归测试：节点声明能力与绑定设备冲突时，
  预览须使用预期优先级且与执行解析一致。
- **验收**：新增回归用例通过；`compileAll` 与 `compile` 三参数路径产出的 `capability` 一致。
  **必须保持 UNKNOWN 的情况**：未做真实设备能力比对前，不得宣称"预览与真机一致"。

### 意见 6（P1 严重）：G0 判定表混淆"实现不完整"与"证据不足"

- **结论**：需要补充证据（要求重做判定口径）。
- **位置**：`g0/01` §1 判定汇总、§2 已有基础；`g0/02` 实现核查矩阵（M05/M09/M11/M15/M17/M18）。
- **依据**：【现状事实】20 项中 PASS=0、PARTIAL=16、FAIL=2、UNKNOWN=2；
  报告同时声明"重点抽样、非 1216 文件逐行审查"，但 M05、M09、M11、M15、M17、M18
  未在本轮重点读取、未给行号却判了 PARTIAL。按报告自身规则这些应为 UNKNOWN。
  反之命令账本、搬运位置确认等已有生产运行痕迹的能力被判 PARTIAL，主要是缺 CI/现场证据（G0-12）。

- **验收**：矩阵 20 项每项都有两个独立判定；未读取项一律 UNKNOWN 且不带行号。
  **必须保持 UNKNOWN 的情况**：测试文件存在 ≠ 测试通过；CI 无 status checks 时证据就绪度必须 UNKNOWN。

### 意见 7（P1 严重）：G0 结论缺保鲜机制，会随整改失效

- **结论**：需要补充证据（要求维护契约）。
- **位置**：`g0/README-G0-SOURCE-AUDIT-20261118.md` 边界声明；三份 G0 文档均绑定 `bef848e`。

- **验收**：任一整改 commit 都能在矩阵中找到对应更新；抽查 3 个行号与当前代码一致。

### 意见 9（P2 一般）：缺跨 user / agent / device / callback 的 principal 传播模型

- **结论**：需要补充证据（要求补一张模型图）。
- **位置**：`03-AGENT-AND-CAPABILITY-PLATFORM.md` §3.4 权限模型；
  `02-REFERENCE-ARCHITECTURE.md` §4 双事实流、§10 安全治理；`g0/01` §3 G0-03。
- **依据**：【目标设计】`03` 要求"Agent 是委托权限，不高于发起用户""每次调用按
  project/experiment/resource 重新授权"；【现状事实】`g0/03` 指出设备事件入口固定 `TENANT=1L`、
  全局共享 token、`sourceEventId` 可缺省、绕过用户 Session 校验。
  文档没有说明"Agent 发起的实验，异步回包的设备事件如何与发起人的委托权限关联"。
- **风险**：权限 / 安全——设备事件被伪造或跨 run 投递时，委托权限形同虚设，
  因为物理执行结果已被污染。
- **建议**：补一张 `user → agent → run → device → callback` 的 principal 传播图，
  标清每条写路径的授权主体、校验时点、审计记谁；把 G0-03 的设备身份方案纳回该图。
- **验收**：每条写路径都能回答"谁授权、何时校验、审计记谁"；跨租户/跨 run 事件被拒绝。
  **必须保持 UNKNOWN 的情况**：设备 ↔ 租户绑定未实现前，不得宣称"设备身份已隔离"。

### 意见 10（P2 一般）：三个"批准"同名不同义，需术语表固定

- **结论**：需要补充证据（要求术语收敛）。
- **位置**：`02-REFERENCE-ARCHITECTURE.md` §6 Approval；
  `05-AI-WORKBENCH-0-30D.md` §4.5 `confirm-instantiate`；现有"启动"按钮。
- **依据**：【目标设计】`02` 的 Approval 绑定不可变执行计划；
  `05` 明确 `confirmationScope: DRAFT_INSTANTIATION_ONLY` 且"按钮文案不得写成批准执行"；
  另有既有启动按钮。三者都叫"批准/确认"但 binding 对象与授权主体不同。
- **风险**：交付范围——G3 实现 Compiler 时混淆"到底哪个 approval 是执行批准"。
- **建议**：术语表固定 `DRAFT_CONFIRM`（草稿审阅）/ `PLAN_APPROVAL`（执行计划批准）/
  `START`（既有启动）三个词，各自写明授权主体与绑定对象。
- **验收**：三份文档中所有"批准/确认"出现处都使用固定术语，无一处指代不明。
  **必须保持 UNKNOWN 的情况**：`PLAN_APPROVAL` 未实现前，UI 不得出现"批准执行"字样。

### 意见 11（P2 一般）："5 次真实使用 + 主动耗时下降 ≥50%"作为 go/no-go 不成立

- **结论**：反对（反对用该指标做阶段门槛）。
- **位置**：`05-AI-WORKBENCH-0-30D.md` §9.2 试用设计、§10.1 立即停止扩张信号、R5；
  `01-PRODUCT-STRATEGY.md` §6 验收指标。
- **依据**：【目标设计】`05` 自述"5 次只能用于早期方向判断，不作统计显著性宣称"，
  但 §10.1 又用"配置效率没有改善"决定是否进入执行申请阶段——3/5 过线即通过，随机性极大。
  `configuration_active_seconds` 只写了定义，没写采集机制（谁计时、在哪埋点），
  "排除 AI 等待时间"容易被无意识美化。
- **风险**：成本 / 交付范围——5 次样本误杀有效方案或误放无效方案。
- **建议**：效率降为观察项（报告中位数 + 分布 + 样本量）；go/no-go 门槛全部放在确定性项
  （安全用例 100%、`ai_execution_attempts=0`、证据覆盖率 100%、真实使用次数达标）；
  明确计时埋点方案。
- **验收**：验收报告同时给出主动耗时、墙钟时间、模型排队时间、样本量；未达门槛如实判"未达"。
  **必须保持 UNKNOWN 的情况**：样本 < 5 或任务复杂度不可比时，结论写"尚不能判断"，不得选择性报喜。

### 意见 12（P3 建议）：层号笔误与 worker 续租归属

- **结论**：需要补充证据（两处小修）。
- **位置**：`04-ROADMAP.md` §3 G0 特别核对项；`06` T2 §3.4-C 租约与长任务。
- **依据**：【现状事实】`04` §3 写"L4 命令事实与 L5 物理事实"，与 `02` 的 L0–L4 编号正好相反；
  `06` 设 120s 租约但只说"长模型调用期间必须续租"，未明确由谁实现续租。
- **风险**：表述误导；若由各 handler 自行续租必漏，导致长任务被误判 `LEASE_EXPIRED`。
- **建议**：去掉层号，改写为"命令事实与物理事实"；续租由 worker 层独立守护线程实现，
  handler 完全不感知（执行与心跳使用独立线程）。
- **验收**：术语与 `02` 分层一致；长任务跑超 120s 仍能正常完成且不被重复执行。
  **必须保持 UNKNOWN 的情况**：未做长任务实测前，不得宣称"租约恢复机制已验证"。
