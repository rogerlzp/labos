# LabOS 物料身份与状态管理

## 统一架构设计 V1.0

**文档状态：** 待架构评审\
**版本：** V1.0\
**设计范围：** 物料身份、物料状态、位置与孔位、Workflow 执行影响、状态事件、追溯与故障恢复\
**设计原则：** 第一阶段立足现有系统，长期保留通用物料模型的扩展能力。

---

# 1. 设计目标

本设计旨在建立 LabOS 中统一、可追溯、可恢复的物料身份与状态管理机制。

系统需要回答三个核心问题：

1. **设备实际完成了什么操作？**
2. **系统是否有足够证据确定哪一个物料发生了什么变化？**
3. **如果物料状态更新失败，系统能否安全恢复，而不重复执行已经发生的物理操作？**

这三个问题分别对应：

- 执行事实（Execution Fact）
- 物料效果（Material Effect）
- 物料状态与事件（Material State / Material Event）

三者不能混为一谈。

## 1.1 第一阶段目标

第一阶段优先解决现有 Plate 体系中的问题：

- Plate 身份识别与唯一性。
- Plate 工艺状态管理。
- Plate 密封状态管理。
- Plate 位置状态管理。
- Plate 与 Well 的内容关系。
- Workflow 节点对物料状态的影响声明。
- Workflow 执行前状态快照。
- 节点执行成功后的状态处理。
- 状态更新失败后的安全恢复。
- 顺序执行与图执行使用统一状态处理机制。
- 完整的状态变化历史和审计记录。

## 1.2 长期目标

在不破坏第一阶段模型的前提下，逐步支持：

- 多种容器类型。
- 不同物料身份体系。
- 容器内部内容物追踪。
- 多输入、多输出物料关系。
- 拆分、合并、消耗、取样、转化等操作。
- 耗材生命周期与批次追溯。

第一阶段不需要一次性实现完整通用物料系统，但不能在数据模型和接口上永久锁死未来扩展。

---

# 2. 三份方案的整合与决策

三份方案不采用平行并存的方式，而是明确主次和适用范围。

| 来源        | 保留内容                               | 在统一方案中的定位 |
| --------- | ---------------------------------- | --------- |
| 原始设计稿     | 业务需求、身份管理、状态管理、追溯需求                | 业务需求基线    |
| 独立设计 v2   | Plate 状态、执行完成处理、状态迁移、快照、恢复         | 第一阶段主实施方案 |
| V0.1 领域模型 | 身份与位置分离、内容物、生命周期、Effect/Event、扩展边界 | 长期领域模型参考  |

## 2.1 采用 v2 作为第一阶段主方案

原因：

1. 更贴近当前 LabOS 已有的 Plate、Position、Workflow 和执行机制。
2. 能够在现有系统中逐步落地。
3. 不需要立即重建一套完整的通用 Material / Location / Content 系统。
4. 能优先解决执行成功与数据库状态不一致的问题。
5. 能降低第一阶段的实施风险。

## 2.2 吸收 V0.1 的领域设计

以下原则必须保留：

- 物料身份不等于物料位置。
- 物料来源不等于当前归属。
- 当前状态不等于历史事件。
- 执行声明不等于实际物理事实。
- 设备执行成功不等于物料状态已经正确更新。
- 状态更新必须具有幂等性。
- 物料状态必须可追溯、可恢复。
- 领域模型应预留多输入、多输出关系。

## 2.3 第一阶段暂不引入的设计

暂不建立完整的：

- 通用 Material 主实体体系。
- 通用 Location 层级体系。
- 完整耗材库存体系。
- 化学反应与复杂物料转化模型。
- 自动感知所有设备物理变化的系统。

这些能力应作为后续扩展，而不是第一阶段的前置条件。

# 3. 总体架构

采用四层结构。

```
┌─────────────────────────────────────────────┐
│              Material Identity              │
│                                             │
│  Plate Identity / Barcode / Container Type  │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│              Material State                 │
│                                             │
│ Process State / Seal State / Position      │
│ Plate-Well Relationship                     │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│          Execution & Material Effect        │
│                                             │
│ Execution Fact → Material Effect            │
│              → Material Event               │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│        Traceability & Reconciliation        │
│                                             │
│ History / Audit / Recovery / Manual Review  │
└─────────────────────────────────────────────┘
```

核心数据关系：

- Material Identity：回答“它是谁”。
- Material State：回答“它现在是什么状态”。
- Execution Fact：回答“设备实际执行了什么”。
- Material Effect：回答“这次执行应该对哪些物料产生什么影响”。
- Material Event：记录“系统最终确认了什么状态变化”。
- Reconciliation：处理“执行事实与物料状态不一致”的情况。

**当前状态是历史事件的投影，不能代替历史事件本身。**

# 4. 物料身份模型

## 4.1 第一阶段以 Plate 为核心

第一阶段继续复用现有 Plate 体系，不另建一套并行的 Plate 身份系统。

需要明确以下概念：

| 概念             | 含义           |
| -------------- | ------------ |
| Plate ID       | 系统内部稳定身份     |
| Barcode        | 外部可识别编码      |
| Container Type | 物理容器类型       |
| Purpose        | 容器用途         |
| Process State  | 工艺状态         |
| Seal State     | 密封状态         |
| Position State | 位置状态         |
| Plate-Well     | Plate 与孔位的关系 |

## 4.2 身份与位置必须分离

Plate 的身份不能依赖当前位置。

例如：

- Plate A 当前在设备 1。
- Plate A 随后移动到设备 2。
- Plate A 离开设备 2 后进入存储位置。

整个过程中，Plate A 的身份不应改变。

因此：

- Plate ID 是稳定身份。
- Position 是动态属性。
- Barcode 是身份解析依据之一。
- 位置不能被当作身份的替代品。

设备返回位置时，必须明确位置对应的物料身份，不能仅根据位置推断物料身份。

## 4.3 来源、归属和历史分离

需要区分：

1. Origin：物料最初来源。
2. Current Ownership：当前归属或管理关系。
3. Processing History：物料经历的加工过程。

不能用当前所属设备或位置覆盖物料来源，也不能通过当前状态推断完整历史。

# 5. 物料状态模型

第一阶段优先采用 v2 的状态设计。

建议明确以下状态维度：

| 状态维度               | 作用            |
| ------------------ | ------------- |
| process_state_code | 工艺过程状态        |
| seal_state         | 密封状态          |
| position_state     | 位置状态          |
| plate_well         | Plate 与内部孔位关系 |
| state_version      | 状态版本控制        |

## 5.1 状态维度相互独立

不同状态维度不能混成一个枚举。

例如：

一个 Plate 可以同时满足：

- 工艺状态：已完成某工艺步骤。
- 密封状态：已密封。
- 位置状态：位于存储设备。
- 孔位状态：部分孔位存在样本。

如果把这些信息压缩为一个整体状态，会造成状态组合爆炸，也不利于单独更新和审计。

## 5.2 状态变更规则

每次状态更新应具备：

- 原状态。
- 目标状态。
- 变更原因。
- 来源执行记录。
- 状态版本。
- 变更时间。
- 操作主体或系统主体。

更新必须执行版本检查，避免并发操作覆盖其他执行产生的状态变化。

建议采用乐观锁：

```
UPDATE material_state
SET state = new_state,
    state_version = state_version + 1
WHERE material_id = ?
  AND state_version = expected_version
```

具体表结构和字段名称以现有数据库设计及 v2 方案为准。

# 6. Workflow Node 与 Material Effect

这是整个架构的重要边界。

Workflow Node 不应仅依赖设备参数来决定物料状态变化。

应当将 `material_effect` 作为 Workflow Node 的独立业务字段。

不能将它放入 `params.method_params`。

## 6.1 物料影响分类

建议采用：

```
NONE
DECLARED
UNKNOWN
```

含义：

| 分类       | 含义             |
| -------- | -------------- |
| NONE     | 明确声明不改变物料状态    |
| DECLARED | 明确声明物料影响       |
| UNKNOWN  | 当前无法确定是否产生物料影响 |

不能把未声明的节点一律视为 NONE。

尤其是会改变物料物理状态、位置、内容或生命周期的设备方法，必须声明其物料影响。

对于 UNKNOWN，应根据节点类型和风险等级采取限制策略，不能默默跳过状态处理。

## 6.2 Material Effect 结构

逻辑上至少包含：

```
MaterialEffect
├── classification
├── operation
├── inputs
├── outputs
├── state_changes
└── evidence_requirements
```

第一阶段可以只支持一对一物料效果，但接口和领域结构应预留多输入、多输出。

## 6.3 第一阶段操作类型

建议支持：

- CREATE
- MOVE
- UPDATE_STATUS
- UPDATE_CONTENT
- RETIRE

后续预留：

- SPLIT
- MERGE
- CONSUME
- SAMPLE
- TRANSFORM

第一阶段不要求实现后续操作，但不应把 Effect 的数据结构设计成永远只能存在一个输入和一个输出。

# 7. 执行事实与状态处理

## 7.1 三阶段处理机制

执行与状态变化必须分离。

```
设备执行
   │
   ▼
Execution Fact
   │
   ▼
Material Effect Processor
   │
   ▼
Material Event
   │
   ▼
Material State Projection
```

### 第一阶段：Execution Fact

记录设备执行事实。

建议包含：

- execution_id
- command_id
- run_id
- node_key
- loop_index
- attempt
- device_id
- command_status
- device_result
- evidence_source
- created_at

具体字段需要结合现有设备命令与执行记录模型确认。

### 第二阶段：Material Effect Processor

根据 Execution Fact 和 Workflow Node 的 Material Effect 声明，判断物料状态应该如何变化。

必须满足：

- 幂等。
- 可重试。
- 可审计。
- 可处理执行重复回调。
- 不因数据库失败而重新执行设备物理动作。

幂等键建议至少包含：

```
execution_id + effect_index
```

不能只使用：

```
run_id + node_key + plate_id
```

因为同一个节点可能在循环中执行多次，也可能存在设备重试。

必须区分：

- loop_index：循环轮次。
- attempt：同一逻辑执行的尝试次数。
- execution_id：一次实际执行实例。

这三个概念不能互相替代。

### 第三阶段：Material State Projection

将已经确认的物料效果转换为物料状态和历史事件。

状态更新、事件记录、Effect 处理状态应尽可能在同一个数据库事务中完成。

如果事务失败：

- 不应丢失 Execution Fact。
- 不应重新执行物理设备动作。
- 应保留待处理 Effect。
- 应支持重新处理。
- 应支持人工核对。

---

# 8. Workflow 执行状态与物料状态分离

必须分别管理：

1. Node Execution Status
2. Material Effect Status
3. Workflow Run Status

例如：

```
Node Execution Status = SUCCESS

Material Effect Status = NEEDS_RECONCILIATION

Workflow Run Status = COMPLETED_WITH_WARNING
```

这是一种可能的业务状态组合，具体 Run 状态枚举需要结合现有状态机确认。

核心原则：

**设备执行成功，不代表物料状态更新成功；物料状态更新失败，也不代表设备执行失败。**

不能为了让数据库状态看起来一致，就重新执行已经完成的设备动作。

---

# 9. 状态快照与事件历史

## 9.1 Run 启动快照

Workflow Run 启动时，应记录本次执行所依赖的物料状态快照。

快照用于：

- 复现执行前条件。
- 判断执行前后状态变化。
- 检查并发状态修改。
- 支持故障恢复。
- 支持执行审计。

快照不能代替实时状态检查。

如果执行期间物料状态发生变化，应根据状态版本和执行约束判断是否允许继续。

## 9.2 Material Event

物料状态变化必须有事件记录。

建议事件包含：

```
MaterialEvent
├── event_id
├── tenant_id
├── material_id
├── event_type
├── before_state
├── after_state
├── execution_id
├── effect_id
├── command_id
├── run_id
├── node_key
├── loop_index
├── attempt
├── evidence_source
├── operator
├── reason
└── created_at
```

事件应作为不可覆盖的历史记录。

当前状态可以更新，但历史事件不能被后续状态覆盖。

人工修正也必须生成事件，不能直接修改数据库后不留记录。

# 10. 故障恢复与人工核对

这是 v2 方案需要重点补充的部分。

## 10.1 核心故障场景

### 场景 A：设备执行成功，数据库更新失败

处理：

1. 保留 Execution Fact。
2. Material Effect 标记为待处理。
3. 不重新执行设备动作。
4. 恢复后重新处理 Material Effect。
5. 成功后写入 Material Event 并更新当前状态。

### 场景 B：设备执行超时，但物理动作可能已经发生

处理：

1. 不直接认定设备执行失败。
2. 尝试查询设备命令最终状态。
3. 根据设备证据和系统记录判断实际结果。
4. 证据不足时进入 NEEDS_RECONCILIATION。
5. 不允许盲目重试物理动作。

### 场景 C：重复回调

处理：

1. 根据 execution_id 和 effect_index 检查幂等记录。
2. 已经处理的 Effect 不重复应用。
3. 保留必要的重复回调审计信息。

### 场景 D：人工确认物料状态

处理：

1. 记录人工确认主体。
2. 记录确认依据。
3. 记录原状态与修正状态。
4. 生成 Material Event。
5. 保留原执行事实。
6. 不删除失败记录。

## 10.2 Effect 恢复状态机

建议统一定义：

```
PENDING
   │
   ▼
PROCESSING
   │
   ├── 成功 ─────────► APPLIED
   │
   ├── 业务冲突 ─────► REJECTED
   │
   ├── 证据不足 ─────► NEEDS_RECONCILIATION
   │
   └── 系统异常 ─────► FAILED
```

恢复时需要明确：

- FAILED 是否允许重新进入 PENDING。
- 谁可以执行恢复。
- 是否需要人工确认。
- 恢复操作是否需要填写原因。
- 如何避免多个恢复任务并发处理。
- 如何审计每次恢复尝试。

`FAILED → PENDING` 不能只是普通字段修改，应作为受权限控制的恢复操作。

恢复操作只重新处理状态效果，不重新执行设备动作。

# 11. 位置管理与现有 PositionLock

第一阶段不建议新建并行位置锁系统。

应优先复用现有 PositionLock 和板位占用机制。

但必须明确区分：

- 物料身份。
- 物理位置。
- 位置占用。
- 执行过程中的临时占用。
- 最终确认的位置状态。

尤其要处理以下冲突：

1. 目标位置已被占用。
2. 同一 Plate 被两个 Run 同时使用。
3. 设备返回位置与数据库记录不一致。
4. 设备执行完成但位置更新失败。
5. Run 异常终止后占用未释放。

目标 Plate 的解析不能只依赖当前位置。

必须明确设备命令证据、位置状态、Run 占用冲突之间的优先级和处理规则。

# 12. 多租户与数据完整性

新增 tenant_id 并不代表已经实现完整多租户隔离。

需要逐项检查：

- Material 与 Tenant。
- Effect 与 Tenant。
- Event 与 Tenant。
- Run 与 Tenant。
- Run Node 与 Run。
- Effect 与 Run / Node。
- Position 与 Tenant。
- Plate 与 Tenant。

建议通过数据库复合约束，确保跨租户引用无法成立。

例如：

- Effect 不能引用其他租户的 Plate。
- Event 不能记录其他租户的物料变化。
- Run Node 不能关联其他租户的 Run。

还需要检查现有代码中是否存在硬编码租户上下文，例如 `TENANT=1L`。

必须从身份验证、请求上下文、领域服务和数据库约束完整验证，不能只增加字段就宣布多租户完成。

# 13. 容器、用途与耗材边界

## 13.1 容器类型与用途分离

不建议继续用单个 `plate_type` 混合表达物理类型和业务用途。

概念上应区分：

- container_type：物理容器类型。
- purpose：业务用途。

实际字段迁移需要兼容现有数据。

## 13.2 Plate-Well 关系

第一阶段保留 Plate 与 Well 的关系。

但必须明确：

- Well 是 Plate 内部位置还是独立物料。
- Well 是否具有独立身份。
- Well 是否需要独立生命周期。
- Well 中内容物如何追踪。

不能因为 Well 有位置编号，就直接把它当成独立 Material。

## 13.3 耗材

是否需要独立耗材实体，应根据以下条件判断：

- 是否有独立身份。
- 是否有独立生命周期。
- 是否有库存管理。
- 是否有批次追溯。
- 是否需要有效期管理。
- 是否会重复使用。
- 是否需要独立质量追溯。

第一阶段不实现完整耗材库存体系。

# 14. 分阶段实施路线

## S0：领域契约冻结

**目标：先确认规则，不急于建表。**

交付：

- 身份与位置边界。
- Plate 状态定义。
- 状态转换规则。
- Plate-Well 关系。
- Material Effect 契约。
- Material Event 契约。
- Execution Fact 契约。
- 幂等规则。
- 故障恢复状态机。
- 租户约束。
- 错误码和冲突处理规则。

验收：

- 所有核心概念有明确边界。
- 所有状态转换有明确规则。
- 所有关键异常场景有处理方式。
- 不存在依赖隐含假设才能运行的核心流程。

## S1：数据基础

交付：

- Plate 状态字段或状态表。
- state_version。
- 必要的执行快照。
- Material Event 数据结构。
- Material Effect 数据结构。
- 相关索引和约束。

验收：

- 状态与事件可以一致保存。
- 并发状态更新能够检测冲突。
- 幂等键具有数据库级唯一性保障。
- 多租户引用约束经过验证。

## S2：执行事实与效果处理

交付：

- Execution Fact 记录。
- Material Effect Processor。
- 统一状态处理器。
- 幂等处理。
- 失败隔离。
- 重试与恢复机制。

验收：

- 重复回调不会重复应用状态变化。
- 数据库失败不会触发设备动作重做。
- 设备超时不确定场景可以进入人工核对。
- 效果失败不会被伪装成设备执行失败。

## S3：追溯与人工核对

交付：

- 物料历史查询。
- 状态变化查询。
- 执行记录关联。
- Effect 处理记录。
- 人工修正记录。
- 恢复操作审计。

验收：

能够从任意当前物料状态追溯到：

- 产生该状态的事件。
- 对应的 Workflow Run。
- 对应的 Node。
- 对应的设备执行事实。
- 对应的状态处理结果。

## S4：流程设计器集成

交付：

- Node Material Effect 配置。
- NONE / DECLARED / UNKNOWN 分类。
- 输入输出物料配置。
- 效果配置校验。
- 节点配置展示和编辑。

验收：

- 物料影响配置是独立业务字段。
- 不依赖设备参数隐式表达。
- 未声明的物料影响能够被识别。
- 不兼容配置不能静默通过。

## S5：通用物料扩展

后续再考虑：

- 多容器类型。
- 多输入、多输出。
- SPLIT / MERGE。
- CONSUME / SAMPLE / TRANSFORM。
- 完整耗材追溯。
- 更广泛的物料身份体系。

# 16. 尚待源码验证的问题

以下内容不能仅凭设计文档确定，必须由源码和测试证明。

## 16.1 执行路径

需要确认：

- 正常图执行是否进入统一完成处理器。
- 顺序执行是否进入同一处理器。
- 多步骤节点如何记录执行事实。
- 循环执行中的 loop_index 实际语义。
- 设备重试是否产生新的 execution_id。
- 人工恢复是否绕过原有执行入口。

## 16.2 设备证据

需要确认：

- 设备是否提供 command_id。
- 是否能够查询命令最终状态。
- 设备超时后是否可以判断物理动作是否发生。
- 设备返回结果是否具有足够证据支持物料状态迁移。

## 16.3 数据一致性

需要确认：

- 当前事务边界。
- 节点执行状态写入时机。
- Material Effect 与 Event 的事务关系。
- Run 结束时是否可能遗漏未处理 Effect。
- 数据库提交失败后执行记录是否仍然保留。

## 16.4 现有领域模型

需要确认：

- Plate、Position、PositionLock 的真实关系。
- Plate-Well 的实际数据结构。
- 现有位置占用和释放逻辑。
- 是否存在其他隐含的物料状态字段。
- 当前 tenant 上下文的实际实现。

以上问题未验证前，不应将设计中建议的新字段、新接口或新状态描述成现有系统能力。

# 17. 架构评审结论与实施门槛

## 17.1 当前结论

**总体方向：有条件通过。**

采用：

- v2 作为第一阶段实施主方案。
- V0.1 作为长期领域模型和扩展边界。
- 原始设计稿作为业务需求基线。

不采用：

- 三份方案直接合并成一套庞大的通用物料系统。
- 仅通过增加状态字段解决执行一致性。
- 设备执行成功后直接修改物料状态而不记录执行事实。
- 通过重新执行设备动作修复数据库状态。
- 依赖当前位置猜测物料身份。

## 17.2 进入代码实施前的五项硬门槛

以下五项必须完成：

1. **恢复状态机明确**：包括 FAILED 恢复、人工核对、权限、原因和审计。
2. **租户约束明确**：完成关键实体的跨租户复合约束设计。
3. **身份解析明确**：设备命令证据、位置状态和 Run 占用冲突有明确优先级。
4. **执行路径明确**：所有执行方式进入统一处理器，循环和重试语义经过源码验证。
5. **扩展边界明确**：第一期可以一对一，但不能永久限制多输入、多输出。

只有完成这五项，才能冻结 S0 并进入 S1。

## 17.3 最终设计原则

整个系统必须坚持：

**物理执行事实优先于软件推测；身份优先于位置推断；历史事件优先于事后覆盖；恢复状态处理优先于重新执行设备动作。**

物料管理不是简单增加几张表，而是建立一套能够在真实设备执行、数据库异常、并发操作和人工干预下，仍然保持可追溯、可解释、可恢复的状态管理机制。
