## 一、结论先行

这份设计最值得保留的是：**位置变化与内容变化分离、租户词典、膜与独立耗材拆开、老流程默认不变、S5 不混进第一刀**。这些方向是对的。

但当前稿件有三类不能带入实施的问题：

1. **一致性契约未成立**：§5.5 要求节点完成与迁移原子提交，§5.6 又要求迁移失败不能回滚节点完成；当前代码实际是逐语句自动提交且异常被吞，不满足前者。
2. **身份与事件键不完整**：按位置找到的板没有 run 归属校验，幂等键漏掉循环圈次，事件来源与物料归属混在 `owner_*` 字段中。结果可能是改错板、漏掉合法迁移或查错 run 产出。
3. **落地链路与现状未对齐**：`GraphRunner.java:604` 是内置节点而非设备 TASK；顺序执行没有该回调；`produces` 的 JSON 路径、解析器和运行版本快照都没有定义。

因此，本次不是“补几句文档”即可通过。应先修订事务、事件模型、目标解析和声明契约，再冻结 S1 的表结构。

## 二、P0 阻塞意见

### R1（P0）事务要求互相矛盾，且当前实现明确不是同事务

**设计原文**：§5.5 要求“状态迁移必须与节点完成落库在同一事务里”；§5.6 又要求“迁移失败不能让节点回滚，记错误码 + 转人工”。如果“节点回滚”指数据库中的 `run_node=completed`，两者不能同时成立；如果指物理动作不可撤销，则文档需要把物理完成与数据库投影分开，而不是混用“节点完成”。

**代码事实**：

- `WorkflowService.recordNodeState()` 仅调用一次 `updateNodeStateLive`，并捕获异常只记日志（`WorkflowService.java:1790-1796`）。
- 对应 SQL 是独立 `UPDATE run_node`（`RunMapper.xml:555-563`）。`JdbcEventStore.java:25-27` 也明确说明无事务包裹时 mapper 调用逐语句自动提交。
- 设备步骤与命令落库同样捕获失败、不影响执行（`WorkflowService.java:2238-2249`）。
- 板位当前值与位置审计刻意在位置事务外独立写入，失败只记日志（`PositionLock.java:206-215,287-316`）。

**影响**：按现稿加一个 listener，既不能保证原子性，也不能保证断点续跑时补偿。已完成节点会进入 `skipKeys`，漏写的迁移不会自然重放。

**必须修改**：建议放弃“物理完成与物料投影必须同一事务”的表述，改成两个明确边界：

1. **T1：物理节点完成 + `plate_state_effect(PENDING)` 同事务**。_effect_ 记录必须保存声明快照、实际 `plate_id`、目标位置证据、`run_id/node_key/loop_index`、幂等键和负载哈希；不能只存一个 `applied` 标志在审计表上。
2. **T2：应用迁移 + 写审计 + 标记 APPLIED 同事务**。锁板后，以幂等插入结果决定是否更新当前值；失败保留 `PENDING/FAILED` 并告警、转人工，禁止静默吞掉。

这样“物理动作不回滚”与“完成事实和待补偿意图不丢失”可以同时成立。若坚持单事务强一致，则必须另行定义：迁移失败后节点/run 显示什么、如何记录物理已完成、恢复时如何确保不重做设备动作。两种方案只能选一种写清楚。

**验证**：故障注入至少覆盖 T1 前崩溃、T1 后/T2 前崩溃、T2 回滚、重复补偿、补偿时流程已续跑，以及数据库异常不得无声继续。

**处置状态**：待修，S2 前阻塞；其事件表结构也会影响 S1。

### R2（P0）目标板解析缺少实际身份与 run 归属约束，可能改到别 run 的板

§6 只定义 `target.by=position/barcode`，§6.3 只处理“找不到板”，没有规定“找到的板是否属于本 run/本节点”。当前 schema 已有 `position_state.occupied_by_run`，且取板路径已采用 fail-closed 归属校验（`DeviceStateMapper.xml:251-256`；`PositionLock.java:328-343`），新设计不能退化成只按位置读板。

另有两个现有事实必须纳入：

- 位置登记在缺少条码时会生成 `AUTO-<runId>`（`PositionLock.java:450-485`）。物料状态迁移不得把这个占位身份当成已核实条码。
- 执行资源会在候选设备间选择或重分配，设计时写死的 `resourceId` 不一定是实际目标；命令参数、设备回包和最终位置才是运行时证据。

**必须修改**：

- 迁移记录最终解析出的 `plate.id`，并保存解析证据；禁止仅凭设计期 `resourceId` 在事后猜板。
- 位置寻址必须在事务内校验 `tenant_id + resource_id + occupied_by_run`；条码寻址也要校验预期位置/归属，除非将来有显式的跨 run 移交操作。
- 对 `AUTO-*`、空条码、归属不明、位置被其他 run 占用一律失败可见并转人工，不做状态写入。
- 多步节点要定义 target 指哪一步结束时的位置；不能用节点结束时另一个位置反推整节点作用对象。

**验证**：同位置被其他 run 占用、条码与位置不匹配、无真实条码、设备重分配、多步进出板五类用例均不得改错板。

**处置状态**：待修，S2 前阻塞。

## 三、P1 严重意见

### R3（P1）幂等键漏掉 `loop_index`，且唯一索引本身不能保证投影幂等

当前系统明确支持同一节点循环执行，`run_node` 唯一键已经包含 `loop_index`（`20_kernel.sql:326-328`；`GraphRunner.java:651-660`）。设计的 `(owner_run_id, owner_node_key, plate_id)` 会把第二圈对同一块板的合法迁移误判为重复。

同时，唯一索引只约束审计行，不会自动保证 `plate` 当前值不重复更新；若实现是先更新 `plate` 再插审计，重复执行仍可能覆盖新状态。`owner_run_id` 为空时自动迁移也不受唯一约束，不能只对人工记录解释 NULL 规则。

**必须修改**：

- 将事件来源独立为 `source_run_id/source_node_key/source_loop_index`，幂等键至少包含 `tenant_id + source_run_id + source_node_key + source_loop_index + plate_id`；`attempt` 不应进入键，以便设备/节点重试去重。
- 同一执行声明保存 `payload_hash`；同键同负载可安全跳过，同键不同负载必须报错，不能静默吞掉设计变化。
- 用“审计插入成功才更新当前值”的单事务算法，或等价的状态版本/CAS 方案。

**处置状态**：待修，直接改变 S1 DDL。

### R4（P1）挂点引用错误，顺序执行路径会完全不迁移

`GraphRunner.java:604` 位于 `Kind.BUILTIN` 分支，不是设备 TASK 完成点。TASK 在 `GraphRunner.java:648-650` 通过状态机完成后回调。更重要的是，`WorkflowService` 在没有图、图解析失败或 `LABOS_EXEC_GRAPH=0` 时会走 `sm.executeAll`（`WorkflowService.java:1056-1066`），该路径没有 `nodeStateRecorder`，最终状态在整单收尾才批量回填（`WorkflowService.java:1099-1105,1828-1851`）。

**必须修改**：物料完成处理器必须位于图执行与顺序执行共享的节点完成边界，并分别做端到端 parity 测试。`RunStateMachine.java:105-112` 是共同完成点，但其普通事件监听器会吞异常（`:250-265`），不能直接把一个 best-effort listener 当作可靠事务处理器。还需明确 `ExperimentFlowRunner` 这条独立落库路径是否在本期范围内。

**处置状态**：待修，S2 前阻塞。

### R5（P1）“系统没有内容物模型”的现状描述不完整，新字段与 `plate_well` 边界缺失

现有 schema 已有 `sample`、`sample_aliquot`，以及 `plate_well.sample_id/aliquot_id/volume/status`（`30_business.sql:17-58,78-93`）。因此，“四个维度只实现第一个”和“这块板装着什么完全无处可存”不准确。真正缺的是**板级工艺阶段/物料处置状态**，不一定是孔级样本内容。

**必须修改**：二选一并写清不变量：

- 若本期只做整板工艺阶段，建议将 `content_state` 改名为 `process_state` 或 `material_state`，明确“整板同质、一个板一个阶段；不表达孔级样本、体积、浓度、部分孔为空”，并定义它与 `plate_well` 的派生/校验关系。
- 若目标真是回答“每个孔装着什么”，则应以 `plate_well/sample_aliquot` 为真相，不再建立一个可与之矛盾的板级内容真源。

“还有几块空板”的验收也须定义：是声明为 `empty`，还是所有 well 都为空；两者不能混称。

**处置状态**：待修，影响 S1 字段命名与验收口径。

### R6（P1）`produces` 的存放路径、解析方式和运行版本快照未定义

当前执行侧只读取 `workflow_node.params->'method_params'`（`WorkflowMapper.xml:70-75`），随后用只支持扁平 JSON 的 `parseFlatJson` 解析并透传驱动（`WorkflowService.java:1418-1458`）。因此：

- 把嵌套 `produces` 放进 `method_params` 会被错误解析并可能透传设备；
- 放在 `params` 外层则现有 listener 参数里拿不到，必须单独加载。

此外，当前 `insertRun` 不写 `workflow_ver`（`RunMapper.xml:508-514`），执行/续跑读取的是当时流程定义。若运行期间或续跑前改了声明，事后可能按新声明解释旧物理动作。

**必须修改**：建议明确使用 `params.produces`，与 `method_params` 为同级兄弟，禁止进入驱动 payload；使用正式 JSON 解析器与 JSON Schema 校验。run 启动时把生效声明及 workflow 版本快照到 run/effect，续跑只读快照，不读最新设计。

**处置状态**：待修，S2 前阻塞。

### R7（P1）“未声明只 WARN”过于粗糙，非法字典值又不能只 WARN

纯搬运不声明 `produces` 是正常情况，不能对所有“会动板”的节点一律报警或阻断；但系统也不能永远分不清“明确无副作用”和“遗漏声明”。现稿 §6.3 还允许字典值不存在时运行期按“未知状态”留痕，这会把非法值写入新模型，抵消字典预检的意义。

**必须修改**：

- 增加显式的 `materialEffect: none`（或等价字段），区分“确认只搬位置/无内容副作用”与“老流程未声明”。
- 由能力/方法元数据在设计期标识“位置-only / 可改变内容或膜 / 未知”，只用于校验，不用于运行期猜状态。
- 新版本中，已知会改内容/膜的节点缺少声明应为 ERROR；纯搬运无需 `produces`；无法分类的节点要求人工确认 `none` 或补声明。老流程保留 WARN 与零行为变化。
- 不存在的 `contentState` 必须在发布/启动时 ERROR；若运行时被删，迁移失败并转人工，不能写“未知状态”冒充成功。

**处置状态**：待修，影响 S2/S4 与验收。

### R8（P1）事件来源与当前归属混用，`/runs/{id}/materials` 查不到可靠历史产出

`plate.owner_run_id` 是当前值，跨流程移交后会被 B 覆盖；用它回答“A 当时产出了哪些板”必然丢失 A 的历史。即使在本期，“产生新板”“已有板被本 run 改状态”“当前最后归属本 run”也是三种不同语义。

审计表同样只有 `owner_run_id/owner_node_key`，没有归属的 from/to，无法满足 §5.1 所称“归属从什么改成什么”。

**必须修改**：

- 审计来源固定为不可变的 `source_*`，归属变化另存 `from_owner_*/to_owner_*`；当前 `plate.owner_*` 只作投影。
- `/api/runs/{id}/materials` 按审计/效果记录的 `source_run_id` 查询，不按当前 `plate.owner_run_id` 查询。
- 将接口文案改为“本 run 声明的物料结果/状态变更”，除非另有真正的物料创建事件，不要称“新产出的板”。

**处置状态**：待修，影响 S1 DDL 与 S3 接口。

### R9（P1）不同节点/人工并发迁移仍会丢更新，需要板级串行化或版本控制

唯一索引只能防同一幂等键重复，不能防两个不同节点或人工盘点同时改同一块板。当前设计没有锁、`state_version` 或期望前态校验，可能出现后提交者覆盖先提交者，而两条审计都看似成功。

**必须修改**：T2 内对 `plate` 行 `SELECT ... FOR UPDATE`，或增加 `state_version` 做 CAS；审计记录的 from/to 必须与本次实际更新一致。定义自动迁移与人工修改冲突时谁失败、如何告警，禁止“最后写入者无声覆盖”。

**处置状态**：待修，S2 前阻塞。

## 四、P2 一般意见

### R10（P2）耗材判据应从“是否追踪位置”扩大为“是否需要独立生命周期追溯”

位置只是独立实体的一种需求。即使膜撕下即弃，若需要批号、条码、有效期、供应商、质量追溯或使用次数，也仍应独立建模。建议判据改为：**是否需要独立身份或生命周期追溯（位置、批次、库存、附着历史、复用等）**；若只关心“当前是否封着”，板上字段才足够。

S5 的 `consumable` 当前 DDL 也只有当前 `plate_id/resource_id`，没有位置/附着审计，无法兑现“从哪来、怎么流转”。S5 还需位置与附着历史、状态机，以及“在板上 XOR 在某位置”的约束。本期建议连该表也延后到 S5，避免先冻结不完整结构。

**处置状态**：待修文档；S5 实施前必须补模型。

### R11（P2）`plate_type` 混合物理规格与工艺用途，且 DDL 并未真正建字典

现有 `plate_type` 注释是 `96/384/24/tube_rack`（`30_business.sql:61-75`），设计改成 `pcr_plate/deep_well/assay_plate/reagent_reservoir/sample_deep_well/consumable/unknown`，其中 `sample_deep_well` 是用途叠加物理类型，`consumable` 又与独立耗材实体重叠。所列是 6 个非 unknown 值 + unknown，不宜笼统称“6 类”而不说明口径。

建议拆成物理 `labware_type`（可含厂商/型号/规格）与工艺用途/角色；`rows/cols` 继续表达孔阵。若只改枚举注释，不构成 §4.1 所称“真字典”，需补字典表、引用约束与旧值迁移规则。

**处置状态**：待裁决，S1 前明确。

### R12（P2）租户完整性、字典生命周期与查询索引未闭合

- `plate.content_state` 只存 code，没有与 `(tenant_id, code)` 的复合外键；`seal_state` 无 CHECK；归属字段无引用策略。
- §4.2 允许租户“增删”，但接口没有删除/停用规则。已被引用的字典项应停用而非物理删除，或明确保留历史显示快照。
- `GET /runs/{id}/materials`、按归属/状态查询所需索引未给出；至少覆盖修正后的 `source_run_id` 与常用当前值筛选。
- 推荐集需区分“全局模板”与“租户副本”，说明新租户如何初始化，而不是只靠每行 `is_builtin` 猜测。

**处置状态**：待修 S1 DDL/API 契约。

### R13（P2）关联的 G11 废料语义没有交付项

设计头关联 G1/G2/G11，路线也把 G11 纳入阶段 1，但正文没有板废弃状态迁移、废板释放位置或验收标准。现有基础 schema 的 `plate.status` 已预留 `consumed/discarded`（`30_business.sql:68`），不能继续只写“无处可存”。

建议本期要么补最小 `plate.status -> discarded` 声明与位置处理，要么从本期关联和验收范围移除 G11，避免范围宣称大于设计内容。

**处置状态**：待裁决范围。

## 五、P3 建议

### R14（P3）“JSONB 没法索引”不是成立的技术理由

PostgreSQL JSONB 支持 GIN 与表达式索引。独立列仍然更适合这里的稳定查询、约束与维护，但理由应写成“字段语义清晰、便于复合外键/普通 B-tree 索引/避免每次解析”，不要写成 JSONB 不能索引。同理，`produces` 放 `params` 还是独立列是契约与查询频率的取舍，不是“能否查询”的绝对分界。

**处置状态**：待修措辞，不阻塞架构。

### 必须补进 §11 的验收用例

1. 图执行与顺序执行同一流程产生相同物料效果。
