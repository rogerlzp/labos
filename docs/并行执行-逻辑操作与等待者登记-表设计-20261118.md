## 0. 为什么需要这两张表

前几轮评审暴露的所有争议，根因是同一个：**系统缺少"这次操作是谁、这是第几次逻辑执行、谁在等这条事件"的显式记录**，只能靠拼字符串和查当前状态推断。

| 争议 | 缺的东西 |
|---|---|
| 重试时 commandId 该不该变 | 没有"逻辑动作"这个实体，只能拼 `run+node+step+device` |
| resume 后该复用还是重发 | 没有"这次逻辑执行结算了没有"的记录 |
| 循环第二轮 vs 重试 | 靠 `loopIndex` 后缀区分，语义模糊 |
| 事件该归谁 | 只能查设备锁持有者，而等待期间锁已释放 |
| 人工重跑 | 没有 generation 概念，无法表达"同一业务步的第二次执行" |
| 人工处置后结果可信吗 | 没有可信度维度，`MANUAL` 和 `COMPLETED` 被下游混用 |

## 1. `logical_operation`：逻辑动作身份

### 1.1 设计要点

| 概念 | 含义 | 何时变 |
|---|---|---|
| `operation_key` | **业务身份**：哪个 run 的哪个节点的第几步 | 不变（除非业务节点本身变） |
| `generation` | **逻辑执行代次**：同一业务步被"重新执行"了几次 | 人工重跑 +1；resume 不 +1 |
| `command_id` | **设备幂等身份**：下发给设备的 id | 首次生成后**永不变**（**按设备能力分档，见 §1.7**） |
| `attempt_no` | **传输尝试次数**：发了/查了几次 | 每次发送或查询 +1 |
| `result_trust` | **结果可信度**：这个结论是怎么来的 | 随状态迁移设置 |

关键区分：

- **重试**：generation 不变、command_id 不变、attempt_no +1
- **resume**：先看上次是否结算——未结算则复用（同 generation、同 command_id）；已结算则不再执行该步
- **人工重跑**：generation +1、生成新 command_id
- **循环第二轮**：`loop_index` 进 `operation_key`，属于不同业务步，不是 generation

#### 1.1.1 `operation_key` 的完整组合（v4 补）

v3 的 `r{run}|n{node}|s{step}|d{device}[|l{loop}]` 仍可能碰撞：

| 碰撞场景 | 为什么撞 |
|---|---|
| 同一节点内连续执行两次**类型相同但独立的**物理动作 | `node + step` 相同，只有参数不同 |
| 同一节点内多个相同 step invocation | `step` 只是序号，同一序号可能被重复调用 |
| 并行分支在同一节点/step 上产生相同身份 | 分支上下文没进 key |
| 流程定义不变但同一动作被显式重复调用 | 没有调用实例维度 |

**v4 组合**：

```
operation_key = r{run}|n{node}|s{step}|b{branch}|d{device}[|l{loop}][|i{invocation}]
```

| 维度 | 含义 | 何时拼入 |
|---|---|---|
| `s{step}` | 节点内第几步 | 总是 |
| `b{branch}` | 并行分支身份（ParallelGateway 的分支 id） | 图里有并行分支时 |
| `l{loop}` | 循环轮次 | 循环体内 |
| `i{invocation}` | 同一位置的重复调用序号 | 同一 step 被多次调用时 |

**默认值**：没有分支 / 循环 / 重复调用时，`b/l/i` 全部省略，key 与 v3 **完全一致** ⇒ 历史账本行不受影响。

**约束**：`operation_key` 首次生成后**持久化**，重放时读取，不重新拼接。

### 1.2 两套 attempt 的语义（必须先分清）

系统里有两个叫 attempt 的字段，含义不同，不能混用：

| 字段 | 位置 | 含义 | 何时变 |
|---|---|---|---|
| `run_node.attempt` | 节点 | 这个节点被执行了几次（resume 才 +1） | resume / 人工重跑 |
| `logical_operation.attempt_no` | 逻辑动作 | 这个动作被**发送/查询**了几次 | 每次传输尝试 |
| `command_ledger.attempt` | 传输明细 | 继承自 `run_node.attempt`，标识该次传输属于哪一轮节点执行 | 随节点 attempt |

**权威关系**：`logical_operation.attempt_no` 是"传输次数"的权威；`command_ledger` 是每次传输的明细，不单独计数。

### 1.3 DDL

```sql
CREATE TABLE IF NOT EXISTS logical_operation (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id           BIGINT       NOT NULL,

    -- 业务身份：r{run}|n{node}|s{step}|d{device}[|l{loopIndex}]
    -- 不含时间、不含次数、不含随机数
    operation_key       VARCHAR(200) NOT NULL,
    generation          INT          NOT NULL DEFAULT 1,

    -- 设备幂等身份：首次创建时生成并持久化，之后只读
    command_id          VARCHAR(160) NOT NULL,

    run_id              BIGINT       NOT NULL,
    node_id             BIGINT,
    step_seq            INT,
    loop_index          INT          NOT NULL DEFAULT 1,
    device_instance_id  BIGINT,
    method              VARCHAR(64),

    -- 状态见 §1.4
    state               VARCHAR(24)  NOT NULL,
    attempt_no          INT          NOT NULL DEFAULT 0,

    -- 结果可信度：DEVICE_CONFIRMED / MANUAL_VERIFIED / INFERRED / UNKNOWN
    result_trust        VARCHAR(16)  NOT NULL DEFAULT 'UNKNOWN',

    -- 结果与证据
    last_error_code     VARCHAR(32),
    last_error_message  VARCHAR(256),
    result              JSONB        NOT NULL DEFAULT '{}'::jsonb,
    device_raw_response JSONB,

    -- 人工处置留痕（见 §1.5）
    dispose_outcome     VARCHAR(24),
    disposed_by         VARCHAR(64),
    disposed_at         TIMESTAMPTZ,
    dispose_reason      VARCHAR(256),
    dispose_evidence    VARCHAR(256),

    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT uk_logical_operation UNIQUE (tenant_id, operation_key, generation),
    CONSTRAINT uk_logical_operation_cmd UNIQUE (tenant_id, command_id),
    CONSTRAINT ck_lo_dispose CHECK (
        (state = 'MANUAL' AND dispose_outcome IS NOT NULL AND disposed_by IS NOT NULL)
        OR state <> 'MANUAL'
    )
);

CREATE INDEX IF NOT EXISTS ix_lo_open
    ON logical_operation (tenant_id, state)
    WHERE state IN ('PENDING','DISPATCHED','ACKED','UNKNOWN');

CREATE INDEX IF NOT EXISTS ix_lo_run
    ON logical_operation (tenant_id, run_id, node_id);
```

**三条约束的作用**：

- `uk_logical_operation`：同一业务步的同一代次只能有一条
- `uk_logical_operation_cmd`：`command_id` 全局唯一 → 设备侧去重与库内记录一一对应
- `ck_lo_dispose`：进入 `MANUAL` 必须同时有处置结论和处置人，**不允许静默进入**

### 1.4 状态机

```
   创建并落 PENDING
        │
        │ dispatch（先落库再发）
        ▼
    DISPATCHED ──── 收到 ACK ────> ACKED ──── 完成 ────> COMPLETED
        │                          │                    result_trust=DEVICE_CONFIRMED
        │                          └──── 失败 ────> FAILED
        │
        ├── 查询 IN_PROGRESS ──> 保持 DISPATCHED（不重发）
        ├── 查询 NOT_FOUND / UNKNOWN ──> UNKNOWN（待人工）
        └── 进程崩溃（未发出）──> 仍是 PENDING（可安全重发）

   UNKNOWN ──人工处置──> MANUAL
                          结果按 dispose_outcome 分流（见 §1.5）
```

| 状态 | 含义 | 允许的动作 |
|---|---|---|
| `PENDING` | 已建记录，尚未下发 | 可下发；崩溃后可安全重发 |
| `DISPATCHED` | 已下发，未收到 ACK | 等 ACK；超时后查询，不盲重发 |
| `ACKED` | 设备已受理，执行中 | 只等完成；**绝不重发** |
| `COMPLETED` | 设备确认完成 | 终态 |
| `FAILED` | 设备确认失败 | 终态；是否重跑由业务决定 |
| `UNKNOWN` | 物理结果不可确认 | 终态；**只允许人工处置**，不自动重发 |
| `MANUAL` | 人工处置完成 | 终态；按 `dispose_outcome` 决定后续 |

**关键规则（与既有设计一致，不能破）**：

1. `NOT_FOUND` **不等于**设备没执行过 → 一律落 `UNKNOWN`，不重发。
2. `ACKED` 之后没有"执行超时"这个概念，只有"业务期限告警"。
3. `PENDING` 是唯一可以安全重发的状态（因为命令确实没发出）。

⚠ **v3 补充：规则 3 在实现上几乎不可达。** §3.1 要求"先落库再发"（改 `DISPATCHED` → 真正发出），崩溃窗口落在这个区间里 ⇒ 命令其实没发出，状态却是 `DISPATCHED` ⇒ 按规则 1 落 `UNKNOWN` ⇒ 转人工。

这是"先落库再发"的固有代价（无法原子化地区分"已发未回"与"将发未发"）。**可以接受，但必须量化并写进验收**：崩溃窗口 = 从"改 DISPATCHED"到"写完 socket"的毫秒级，转人工量级为"每次崩溃 1~N 条命令"，不是常态。§3.3 的 `PENDING` 分支保留，用于"建记录后、尚未进入下发"的短暂窗口。

### 1.5 人工处置：五种结论决定后续路径

`UNKNOWN` 只能由人工推进，且必须给出结论：

| `dispose_outcome` | 含义 | `result_trust` | 后续 |
|---|---|---|---|
| `NOT_EXECUTED` | 确认设备没动过 | `UNKNOWN` | 允许**同 generation** 重发（attempt_no +1，command_id 不变）；或由业务决定 generation +1 新命令 |
| `EXECUTED_OK` | 确认已执行且结果可接受 | `MANUAL_VERIFIED` | 进下一步，不重发 |
| `EXECUTED_BAD` | 确认已执行但结果不可接受 | `MANUAL_VERIFIED` | 转 `FAILED`，按失败处理 |
| `INDETERMINATE` | 无法确认 | `UNKNOWN` | 保持 `UNKNOWN`，隔离相关物料和位置，不得放行 |
| **`PARTIAL`（v3 新增）** | **部分执行**（多孔板移液只完成 3/8 孔、封膜中途失败） | `INFERRED` | **阻断后续**，需人工再决策（丢弃 / 补做 / 接受）；**不允许**直接进下一步 |

```sql
UPDATE logical_operation
   SET state = 'MANUAL',
       dispose_outcome = ?,     -- 五选一，必填
       disposed_by = ?,         -- 必填
       disposed_at = now(),
       dispose_reason = ?,      -- 原因码，必填
       dispose_evidence = ?,    -- 照片/扫码/现场记录编号
       result_trust = ?,        -- 与 outcome 对应
       result = ?
 WHERE id = ? AND state = 'UNKNOWN'
```

**四条约束**：

1. **`MANUAL` 不等于 `COMPLETED`**。下游必须按 `result_trust` 区分。
2. `INDETERMINATE` **不能**释放物料位置占用（位置事实另管）。
3. 高风险动作（移液、搬运、开盖、离心、封膜）的处置需按权限矩阵授权，必要时双人复核（见 §6 限制 5）。
4. **`result_trust` 四值的含义（v3 补齐）**——v2 里 `INFERRED` 从未被任何一条处置路径赋值，是悬空枚举：

| 取值 | 含义 | 下游可否直接采信 |
|---|---|---|
| `DEVICE_CONFIRMED` | 设备回执确认 | ✅ 可 |
| `MANUAL_VERIFIED` | 人工确认（判定人/时间/依据齐全） | ⚠️ 可，但报表必须注明"人工判定，非设备确认" |
| `INFERRED` | 推断 / **部分执行**得出 | ❌ **不可**，必须阻断后续 |
| `UNKNOWN` | 无法确认 | ❌ **不可**，阻断并隔离 |

### 1.6 与现有表的关系

| 现有对象 | 关系 |
|---|---|
| `command_ledger` | 保留为**传输层明细**（每次发送/查询一行）；`logical_operation` 是其**上位聚合**（1 : N） |
| `run_command` | 保留为**执行记录**；`logical_operation.id` 可作为外键补充 |
| `run_node.attempt` | 保留，表示节点执行轮次；与 `attempt_no` 语义不同（见 §1.2） |
| `run.exec_phase` | 保留（`PREPARED/DISPATCH_STARTED/SETTLED`），继续作为崩溃窗口标记 |

迁移时不改现有表，只新增。

⚠ **映射关系不是一一对应（v3 修正）**：现有 `command_ledger.idempotency_key` 形如 `r{run}|n{node}|a{attempt}|s{step}|d{device}|m{method}[|v{loop}]`（`DriverStepExecutor:1209-1211`），比 `operation_key` **多了 `a{attempt}` 与 `m{method}` 两项** ⇒ 同一个 `operation_key` 会对上**多条** ledger 明细行（每次传输一行）。

⇒ 正确表述：

- `logical_operation`（operation_key + generation）→ `command_ledger` 是 **1 : N**（上位聚合 : 传输明细）；
- 迁移期若要按 ledgerKey 回推 operation_key，需**剥掉 `a{attempt}` 与 `m{method}` 两段**，且**同一 operation_key 的多条明细无法区分归属** ⇒ 回填只能做到"候选集"级别，最终以 `command_id` 为准（见 §4.2）。

### 1.7 commandId 的稳定性：逻辑操作级唯一，重试复用（v5 修正）

**规则只有一条**：

```
commandId = 一次逻辑操作的唯一标识
  ├─ 重试（网络重发 / 断线重连 / resume）→ 复用同一个
  └─ 重新执行（人工重跑 / 循环下一轮 / 换批次）→ 生成新的
```

**"重试"与"重新执行"必须分开**：

| 场景 | commandId | 设备侧效果 |
|---|---|---|
| 网络超时重发 | **不变** | 支持去重的设备识别为同一命令，只执行一次 |
| resume 后续跑 | **不变** | 同上 |
| 人工重跑同一节点 | **变**（generation +1） | 设备当成新命令，正确执行第二次 |
| 循环第二轮 | **变**（`|l2` 进 key） | 同上 |

**不支持设备去重的设备怎么办**：

| 做法 | 是否采用 |
|---|---|
| 每次重试换新 id | **不采用**——设备会当成新命令，问题更严重 |
| **保持 id 稳定，但禁止自动重试** | **采用**。这类设备断线后只能 `queryStatus` + 人工确认，不能自动重发 |

所以 `uk_logical_operation_cmd UNIQUE (tenant_id, command_id)` **单列唯一即可**，不需要按档位放宽——因为 id 在所有重试中都不变，一个逻辑操作只有一行。

**与现状的差异**：`DriverStepExecutor` 现在把 `exec` 拼进 id（`-e{exec}`），导致 resume 后 id 变化。改造点：`exec` 只保留在日志与追踪里，**不进 commandId**。

## 2. `device_event_waiter`：等待者登记

### 2.1 为什么不能用设备锁

真实流程结构（提取线）：

```
n_pick  (PickTipComb)  → 抢设备锁 → 执行 → onStepDone 释放锁
   ↓
n_wait  (__awaitEvent) → 不走 step 生命周期 → 无锁
   ↓
设备上报"到交换点"（E3 自发事件）
```

**等待事件的时候，设备锁早就释放了。** 用 `device_lock.current_run_id` 做归属，在这种场景下必然取不到值。

即便锁没释放，仍有迟到事件问题：A 持锁产生事件 → A 释放 → B 持锁 → 事件到达 → 被误归给 B。

### 2.2 设计要点

**登记"谁在等"，而不是"谁占着"。**

```sql
CREATE TABLE IF NOT EXISTS device_event_waiter (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id           BIGINT       NOT NULL,

    run_id              BIGINT       NOT NULL,
    -- 并行网关真并发后，同一 run 的多个分支会同时等事件
    -- （见《并行网关并发执行设计》§5）。非并行流程固定为 'main'
    branch_id           VARCHAR(32)  NOT NULL DEFAULT 'main',
    node_id             BIGINT       NOT NULL,
    loop_index          INT          NOT NULL DEFAULT 1,

    -- 粗匹配条件（与现有 __awaitEvent 参数一致）
    device_code         VARCHAR(64)  NOT NULL,
    event_type          VARCHAR(48)  NOT NULL,

    -- 归属条件：只认 commandId（v4 删除 expect_process_id / expect_interaction）
    expect_command_id   VARCHAR(160),

    -- 等待区间
    base_event_id       BIGINT       NOT NULL,   -- ⚠ 继承 run 级基准（见 §2.2.1），不是"建 waiter 时的 MAX(id)"
    deadline_at         TIMESTAMPTZ  NOT NULL,   -- 必填，按类型默认值

    state               VARCHAR(16)  NOT NULL,   -- WAITING/MATCHED/CANCELLED/EXPIRED
    matched_event_id    BIGINT,

    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- ⚠ v2 的 `uk_waiter UNIQUE (tenant_id, run_id, node_id, loop_index)` 会让 **resume 撞唯一键**：
--   run_node 的唯一键是 (run_id, node_key, attempt, loop_index)（schema :594），**含 attempt**；
--   resume 后节点 attempt +1 ⇒ 新 waiter 的 (run_id, node_id, loop_index) 与旧行完全相同 ⇒ 插入失败。
-- ⇒ 改为**部分唯一索引**：只约束"仍在等"的 waiter；历史 waiter（MATCHED/CANCELLED/EXPIRED）保留可审计，
--   且不阻塞 resume。
-- v4：唯一键加 branch_id —— 否则同一 run 的两个并行分支等同一设备时会撞键。
CREATE UNIQUE INDEX IF NOT EXISTS uk_waiter_active
    ON device_event_waiter (tenant_id, run_id, branch_id, node_id, loop_index)
    WHERE state = 'WAITING';

CREATE INDEX IF NOT EXISTS ix_waiter_open
    ON device_event_waiter (tenant_id, device_code, event_type, base_event_id)
    WHERE state = 'WAITING';
```

**`branch_id` 的取值**：非并行流程固定 `'main'`；并行组内按分支序号（`b1`/`b2`/…）赋值，与 `operation_key` 里的 `b{branch}` 同源。

**`deadline_at` 为什么必须非空**：可空等于"永不超时"，会导致 waiter 永久挂起、节点永远等不到。建 waiter 时必须填，默认值：

| 事件类型 | 默认期限 |
|---|---|
| 一般交互事件 | 600 秒（与现有 `__awaitEvent` 的 timeout 一致） |
| 长工艺过程事件 | 按方法超时上限（复用 `MethodTimeoutPolicy`） |
| 未配置 | 600 秒兜底 |

#### 2.2.1 `base_event_id` 必须继承 run 级基准（v3 新增）

v2 的 §2.4 匹配条件是 `w.base_event_id < ?`（事件 id 必须大于 waiter 的基准），而 §5.2 的验收 W-05 又要求"事件先于 waiter 到达 ⇒ **不丢**"。这两条**互相矛盾**：如果 waiter 的 `base_event_id` 取"**建 waiter 时的 MAX(id)**"，那么先于 waiter 到达的事件 id 更小 ⇒ 被 `<` 排除 ⇒ **事件丢失**。

根因：v2 把"run 级固定基准"降级成了"waiter 级瞬时值"，并据此提出 deprecated 掉游标表。

**现状事实**（`DeviceEventMapper.xml:49-57`，`ensureRunCursor`）：

```sql
INSERT INTO device_event_run_cursor (tenant_id, run_id, base_event_id)
SELECT #{tenantId}, #{runId}, COALESCE(MAX(id), 0)
  FROM device_event WHERE tenant_id = #{tenantId}
ON CONFLICT (tenant_id, run_id)
DO UPDATE SET base_event_id = device_event_run_cursor.base_event_id
RETURNING base_event_id
```

⇒ `base_event_id` 是 **run 级固定基准**：首次执行时取一次 MAX(id)，之后 resume 读回**旧值**（`DO UPDATE` 保持原值）。这正是"不丢早到事件"的机制。

**修正（v3 采纳）**：

| 项 | v2 | v3 |
|---|---|---|
| waiter.base_event_id 来源 | 建 waiter 时的 MAX(id) | **继承 `device_event_run_cursor` 的 run 级基准**（同一 run 的所有 waiter 用同一个值） |
| `device_event_run_cursor` | deprecated | **保留，角色改为"基准来源"**（不是"消费者游标"） |
| 早到事件 | 丢失 | **不丢**（event.id > run 基准 ⇒ 可被匹配） |

> ⚠ "精确性"和"不丢"是**两个不同维度**，不能二选一：按 waiter 记基准更精确，但会丢早到事件；按 run 记基准可能多匹配到无关事件，但**不丢**。本方案取 run 级基准 —— **丢事件比多匹配更危险**。

**代价**：run 级基准意味着"该 run 开始前的所有事件"都在候选范围内。靠 §2.5 的 `command_id` 精匹配排除无关事件；匹配不上的一律进 `UNATTRIBUTED`。

### 2.3 归属落地：给 `device_event` 加一列

v1 只在验收里写了"事件标 UNATTRIBUTED"，但没有字段承载。v2 补上：

```sql
ALTER TABLE device_event
    ADD COLUMN IF NOT EXISTS attribution_state VARCHAR(16) NOT NULL DEFAULT 'PENDING';

COMMENT ON COLUMN device_event.attribution_state IS
    '归属判定：PENDING=未判定 / ATTRIBUTED=已被 waiter 匹配 / UNATTRIBUTED=无法判定归属，需人工';
```

与既有字段的区别（不要混用）：

| 字段 | 回答的问题 |
|---|---|
| `dispatched_at` | 这条事件**有没有被认领**（时间） |
| `device_event_consumption` | 这条事件**被谁消费**（唯一） |
| `attribution_state` | 这条事件**能不能判定归属**（结果） |

一条事件可以"被认领"（`dispatched_at` 非空）但"归属不确定"（`UNATTRIBUTED`）——这正是需要人工介入的情况。

### 2.4 匹配规则（v4 修正：匹配域互斥 + UNATTRIBUTED 独立提交）

**两个必须先修的并发问题**：

| 问题 | 说明 |
|---|---|
| **幻读窗口** | v3 的"先无锁 count、再精确 UPDATE"仍有窗口：count 到 1 之后、UPDATE 之前，另一个事务可能新增一个匹配 waiter ⇒ 判定的"唯一"已失效 |
| **UNATTRIBUTED 丢失** | v3 写"多行时整体回滚"，但回滚会把"事件标 UNATTRIBUTED"一起撤掉 ⇒ 事件留在 `PENDING`，下次仍然歧义，永远没人处理 |

另外，v2 的 `FOR UPDATE SKIP LOCKED` 也不可用：它会跳过被其他事务锁住的行，把"实际 3 行匹配、2 行被锁"伪装成"恰好 1 行"。

**修正一：按匹配域取互斥，覆盖"创建"与"认领"两个动作**

```sql
-- ① 事务级互斥（waiter 创建与事件认领都必须先取这把锁）
SELECT pg_advisory_xact_lock(
    hashtext(? || ':' || ? || ':' || ?)    -- tenant:device_code:event_type
);

-- ② 锁内读完整候选集（不加 SKIP LOCKED，允许看到全部）
SELECT w.id
  FROM device_event_waiter w
 WHERE w.tenant_id = ? AND w.state = 'WAITING'
   AND w.device_code = ? AND w.event_type = ?
   AND w.base_event_id < ?
   AND (w.expect_command_id IS NULL OR w.expect_command_id = ?)
 ORDER BY w.created_at;

-- ③ 恰好 1 行：条件更新，必须校验影响行数
UPDATE device_event_waiter
   SET state = 'MATCHED', matched_event_id = ?, updated_at = now()
 WHERE id = ? AND state = 'WAITING';
-- 影响 0 行 ⇒ 并发冲突，重新判定，不得当成功
```

**为什么用 advisory lock 而不是行锁**：waiter 创建是新插入，没有行可锁，行锁保护不了"插入"这个动作。按匹配域加 advisory lock 才能同时覆盖"创建"和"认领"。

**修正二：UNATTRIBUTED 不随归属回滚**

| 判定结果 | waiter | 事件 `attribution_state` | 事务 |
|---|---|---|---|
| 恰好 1 行 | 置 `MATCHED` + 写 `consumption` | `ATTRIBUTED` | 提交 |
| 0 行 | 不动 | `UNATTRIBUTED` | **提交**（只落事件状态） |
| 多行 | **不动** | `UNATTRIBUTED` + 告警 | **提交**（只落事件状态） |

**关键**：歧义时不是"整体回滚"，而是"不提交 waiter 变更、只提交事件状态"。回滚会让歧义记录一起消失，下次重复同样的歧义，永远进不了人工队列。

多条强匹配时**不许挑第一条**，也不许按"最早 waiter""当前设备占用者"兜底。

⚠ **另一条事件会匹配失败（v3 补进验收）**：两条事件同时到达时，行锁保证**不会同时匹配同一个 waiter**，但**其中一条会匹配不到**（waiter 已被另一条标记 `MATCHED`）⇒ 落 `UNATTRIBUTED` + 告警。这是"一条 waiter 对一条事件"的正确语义，不是 bug。

### 2.5 归属规则：只认 commandId（v4 重写）

事件与 waiter 的匹配只有三种结果：

| 条件 | 结果 |
|---|---|
| waiter 声明了 `expect_command_id`，事件 `command_id` 相同 | **匹配** |
| waiter 声明了 `expect_command_id`，事件 `command_id` 不同 | **不匹配** |
| waiter 未声明（`NULL`），或事件无 `command_id` | 不匹配（系统型事件不归属任何 run） |

**没有"弱匹配"。** v3 的弱匹配（"该设备只有一个 waiter 就认领"）已删除，原因有二：

| 风险 | 说明 |
|---|---|
| **迟到事件接盘** | A 释放设备后 B 开始等，一个属于 A 的迟到事件到达 ⇒ 被判给 B ⇒ 推进错误流程 |
| **唯一 waiter ≠ 唯一来源** | 只有一个 waiter 只说明"当前只有一个人在等"，不能说明"这条事件属于他" |

**所以**：事件没有 `command_id`、或与所有 waiter 都对不上 ⇒ 一律进 `UNATTRIBUTED` + 告警，**不推进任何流程、不释放任何资源**。

**这要求设备必须回显 commandId**（见《设备命令与事件关联规范》）。做不到的设备降级为**独占串行**——同一时刻只有一个 run 使用该设备，此时归属由"当前占用者"唯一确定，不需要任何事件字段。

### 2.6 状态机

```
   WAITING ──匹配成功──> MATCHED（终态）
      │
      ├── 超时（deadline_at 到）──> EXPIRED（终态，告警）
      ├── run 被取消/暂停 ──> CANCELLED（终态）
      └── 多条匹配/无法判定 ──> 保持 WAITING + 告警（不猜）
```

**EXPIRED 与节点状态的衔接**：不新增 `run_status` 枚举值（系统既有原则是"用列不用枚举"），改为：

```sql
-- run 层：pause_kind 加一个取值（字符串列，不涉及 ALTER TYPE）
UPDATE run SET pause_kind = 'waiting_event' WHERE id = ? AND status = 'running';
```

`pause_kind` 现有取值是 `paused_fault / waiting_human / paused_unknown`，新增 `waiting_event` 只是加列值，与"加枚举值要 ALTER TYPE"的限制无关。

⚠ **v3 补充**：新增取值必须同步 `StatusVocabulary` 的暂停类型词表（`SCOPE_CONTROL`）与前端映射，否则又是一次"库里加了词表没加"。

### 2.7 与现有表的关系

| 现有对象 | 关系 |
|---|---|
| `device_event_run_cursor` | **保留**（v3 修正：不再 deprecated）。角色从"消费者游标"改为"**基准来源**"——waiter 的 `base_event_id` 从它继承（见 §2.2.1） |
| `device_event_consumption` | 保留，作为"事件已被谁消费"的唯一事实。waiter 匹配成功后写一行，唯一键正好对应 waiter |
| `device_event.process_id` | **删除**（语义未定义，生产路径不填值）；归属改用新增的 `command_id` |

## 3. 关键流程走查

### 3.1 正常执行

```
1. 节点开始 → 建 logical_operation (PENDING)，生成 command_id 并持久化
2. 下发前把 state 改 DISPATCHED（先落库再发，保证崩溃可知）
3. 设备回 ACK → state = ACKED
4. 设备回完成 → state = COMPLETED，result_trust = DEVICE_CONFIRMED
5. 若下一步是 __awaitEvent → 建 device_event_waiter (WAITING)，必填 deadline_at，
   base_event_id 继承 run 级基准
6. 设备上报事件 → 先判唯一再上锁匹配 waiter → 写 consumption → 推进节点
```

### 3.2 断线重试

```
1. state = DISPATCHED，长时间无 ACK
2. 查询设备状态
   ├ IN_PROGRESS → 保持 DISPATCHED，继续等（不重发）
   ├ COMPLETED/FAILED → 落终态
   └ NOT_FOUND/UNKNOWN → state = UNKNOWN，转人工（不重发）
3. 只有 state 仍是 PENDING（确认没发出）才允许重发，attempt_no +1
```

### 3.3 Resume

```
1. 读该节点是否有 logical_operation
   ├ 无 → 新建（新 command_id）
   ├ 有且 state ∈ {COMPLETED, FAILED, MANUAL} → 已结算，跳过或按业务继续
   ├ 有且 state = PENDING → 直接复用（command_id 不变）
   ├ 有且 state = DISPATCHED → 先查询，再决定
   └ 有且 state = UNKNOWN → 不自动执行，转人工
2. **绝不因 resume 重新生成 command_id**（去重设备档位）
```

### 3.4 人工重跑

```
1. generation +1
2. 生成新 command_id
3. 新记录 state = PENDING
4. 旧 generation 的记录保留（审计）
```

### 3.5 循环体第二轮

```
operation_key 里带 |l{n}：
  r100|n10|s1|d5|l1  → 第一轮
  r100|n10|s1|d5|l2  → 第二轮（不同业务步，不是 generation）
```

## 4. 迁移与双写对账

### 4.1 迁移步骤

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | 建两张表 + 给 `device_event` 加 `attribution_state`（只新增） | 无 |
| 2 | 写路径改为"先建 logical_operation，再走 command_ledger"；**同时把 command_ledger.command_id 改成稳定 id**（否则 §4.2 的对账永远匹配不上，见下） | 低，双写期 |
| 3 | `__awaitEvent` 改为先建 waiter，再等 | 中，需回归 |
| 4 | 回填历史：从 `command_ledger` 反推 operation_key（**只能做到候选集级别**，见 §1.6） | 低，只读 |
| 5 | 每日跑一致性对账（见 §4.2），差异人工处理 | 中 |
| 6 | 观察两周无差异后，逐步以新表为准 | 中 |
| 7 | ~~`device_event_run_cursor` 标记 deprecated~~ | **v3 取消**：该表改为"基准来源"，保留（见 §2.2.1） |

**不做的事**：不删 `command_ledger`、不删 `run_command`、不改 `run_status` 枚举。

### 4.2 双写一致性对账

⚠ **迁移期口径（v3 修正）**：现有 `command_ledger.command_id` 写入的是**含 `exec`、每次都变**的 id（`DriverStepExecutor:1474-1478`），而 `logical_operation.command_id` 是**稳定 id** ⇒ 两条按 `command_id` 的 JOIN 在迁移期**永不命中** ⇒ SQL ① 会把**每一条 ledger 行**都报成"有传输明细、无逻辑动作" ⇒ 每日全量误报，告警直接失效。

⇒ **前置条件**：§4.1 步骤 2 必须**同步**把 `command_ledger.command_id` 改为写稳定 id；在此之前，**不启用 §4.2 的每日对账**（否则噪声淹没真信号）。

```sql
-- ① 有传输明细、无逻辑动作（说明写路径漏了）
--    迁移期前置：command_ledger.command_id 必须已改为稳定 id
SELECT l.id, l.idempotency_key, l.command_id, l.state
  FROM command_ledger l
  LEFT JOIN logical_operation o
    ON o.tenant_id = l.tenant_id AND o.command_id = l.command_id
 WHERE o.id IS NULL;

-- ② 已下发、但无任何传输明细（说明状态机与账本脱节）
SELECT o.id, o.command_id, o.state, o.attempt_no
  FROM logical_operation o
  LEFT JOIN command_ledger l
    ON l.tenant_id = o.tenant_id AND o.command_id = l.command_id
 WHERE l.id IS NULL
   AND o.state IN ('DISPATCHED','ACKED');

-- ③ 状态矛盾：动作已终结、但仍有未结算传输
SELECT o.id, o.command_id, o.state,
       count(l.id) FILTER (WHERE l.state = 'DISPATCH_STARTED') AS open_ledgers
  FROM logical_operation o
  JOIN command_ledger l ON l.tenant_id = o.tenant_id AND o.command_id = l.command_id
 WHERE o.state IN ('COMPLETED','FAILED','MANUAL')
 GROUP BY o.id, o.command_id, o.state
HAVING count(l.id) FILTER (WHERE l.state = 'DISPATCH_STARTED') > 0;

-- ④（v3 新增）传输计数不一致：attempt_no 与明细行数对不上
SELECT o.id, o.command_id, o.attempt_no,
       (SELECT count(*) FROM command_ledger x
         WHERE x.tenant_id = o.tenant_id AND x.command_id = o.command_id) AS ledger_rows
  FROM logical_operation o
 WHERE o.attempt_no <>
       (SELECT count(*) FROM command_ledger x
         WHERE x.tenant_id = o.tenant_id AND x.command_id = o.command_id);
```

**发现差异时**：以 `logical_operation` 为准（它是上位聚合），补写 `command_ledger` 明细；若 `logical_operation` 缺失，则从 `command_ledger` 重建。

**还缺的形态**（供后续补）：同一 `operation_key` 有多个 `generation` 同时活跃（人工重跑后旧的没结算）。

## 5. 验收场景

### 5.1 命令侧

| ID | 场景 | 期望 |
|---|---|---|
| L-01 | 同一逻辑动作重发（PENDING） | command_id 不变，generation 不变，attempt_no +1 |
| L-02 | 查询 NOT_FOUND | 落 UNKNOWN，**不重发** |
| L-03 | 查询 IN_PROGRESS | 保持 DISPATCHED，不重发 |
| L-04 | 崩溃后 resume（PENDING） | 复用同一 command_id |
| L-05 | 崩溃后 resume（DISPATCHED） | 先查询再决定，不新建 command_id |
| L-06 | 崩溃后 resume（COMPLETED） | 不重复执行该步 |
| L-07 | 人工重跑 | generation +1，新 command_id，旧记录保留 |
| L-08 | 循环第二轮 | operation_key 带 `\|l2`，与第一轮互不影响 |
| L-09 | 人工处置 EXECUTED_OK | state=MANUAL，result_trust=MANUAL_VERIFIED，下游可区分 |
| L-10 | 人工处置 NOT_EXECUTED 后重发 | 同 generation 重发，attempt_no +1，command_id 不变 |
| L-11 | 人工处置 INDETERMINATE | 保持 UNKNOWN，物料与位置不放行 |
| L-12 | 静默进入 MANUAL（无 disposed_by） | 被 `ck_lo_dispose` 拒绝 |
| **L-13** | **人工处置 PARTIAL** | **result_trust=INFERRED，阻断后续，不得自动进下一步**（v3 补） |
| **L-14** | **不去重设备上的 resume 重发** | **command_id 重新生成**（否则设备按"已见过"忽略 ⇒ 卡死）（v3 补，§1.7） |

### 5.2 事件侧

| ID | 场景 | 期望 |
|---|---|---|
| W-01 | 两条 waiter 等同一设备同一事件，事件带 `command_id` | 只有 `expect_command_id` 匹配的那条被推进 |
| W-02 | 事件 `command_id` 与所有 waiter 都不匹配 | `attribution_state='UNATTRIBUTED'`，告警，不推进 |
| W-03 | 多个 waiter、事件无 `command_id` | 全部不匹配，事件 UNATTRIBUTED |
| W-04 | **唯一** waiter、事件无 `command_id` | **仍然 UNATTRIBUTED**（v4：无弱匹配，不猜） |
| W-14 | 同一 run 的两个并行分支等同一设备 | waiter 按 `branch_id` 区分，不撞唯一键 |
| **W-05** | **事件先于 waiter 到达** | **不丢**（waiter 的 base_event_id 继承 run 级基准，见 §2.2.1） |
| W-06 | waiter 超时 | `EXPIRED` + 告警；`run.pause_kind='waiting_event'` |
| **W-07** | **两条事件同时到达** | **不会同时匹配同一 waiter；其中一条落 UNATTRIBUTED + 告警**（v3 补齐另一半） |
| W-08 | 匹配到多行 | 不更新 waiter，**只提交事件 `UNATTRIBUTED`**（不回滚），告警，不猜 |
| W-09 | 设备断电重启后事件序号归零 | 需 `device_boot_id` 区分（见 §7） |
| **W-10** | **3 个 waiter 匹配、其中 2 个正被其它事务锁住** | **不得判成"唯一"**（v4：锁内读全量，不用 `SKIP LOCKED`，见 §2.4） |
| W-11 | count 之后、UPDATE 之前并发新增 waiter | advisory lock 串行化，判定不会因幻读失效 |
| W-12 | 条件更新影响 0 行 | 视为并发冲突，重新判定，不得当作匹配成功 |
| W-13 | 歧义事件的事务边界 | 事件 `UNATTRIBUTED` 已落库，不被归属回滚撤销 |

### 5.3 一致性

| ID | 场景 | 期望 |
|---|---|---|
| C-12 | 双写期每日对账 | §4.2 四条 SQL 均无差异（**前置：command_ledger.command_id 已改稳定 id**） |
| C-13 | 差异出现时 | 以 `logical_operation` 为准补齐，记录处置 |
| **C-14** | **attempt_no 与 ledger 明细行数不一致** | **被 §4.2 的第 4 条 SQL 检出**（v3 补） |

## 6. 需要业务确认的三处

这几处在 v2/v3 里给了默认方案，实施前需业务确认。

## 7. 已知限制（必须写进实现前提）

1. **`device_event_seq` 需要配 `device_boot_id`**：设备断电重启后序号可能归零，单靠 `device_id + seq` 会冲突。唯一键应为 `(tenant_id, device_code, boot_id, seq)`。
2. **归属依赖设备回显 `command_id`**：不回显的设备无法做精匹配，也没有弱匹配兜底 ⇒ 必须降级为独占串行。这是产品边界，要写进设备准入清单。
3. **`logical_operation` 不解决跨实例问题**：本设计假设单实例。若上多实例，仍需 epoch 保护（见设计基线 R-02）。
4. **人工处置不能替代设备确认**：`MANUAL` 与 `COMPLETED` 必须在下游报表和证据链中区分显示；`PARTIAL` 必须阻断。
5. **人工处置的权限矩阵尚未实现**：v3 只定义了字段和默认规则，审批流程需单独设计。
6. **`PENDING` 的安全重发窗口在"先落库再发"下几乎不可达**（见 §1.4），转人工量级需在实施后用真实崩溃注入测一次。
