# 逻辑操作与等待者登记：表设计

- 日期：2026-11-18
- 性质：表结构与状态机设计，**未实施**
- 前提：**单实例部署**，不使用 fencing/epoch
- 目标：为并行执行提供两个缺失的身份层——**逻辑动作身份**（解决重试/resume/重跑的歧义）和**等待者登记**（解决事件归属不依赖设备锁）

---

## 0. 为什么需要这两张表

前几轮评审暴露的所有争议，根因是同一个：**系统缺少"这次操作是谁、这是第几次逻辑执行、谁在等这条事件"的显式记录**，只能靠拼字符串和查当前状态推断。

| 争议 | 缺的东西 |
|---|---|
| 重试时 commandId 该不该变 | 没有"逻辑动作"这个实体，只能拼 `run+node+step+device` |
| resume 后该复用还是重发 | 没有"这次逻辑执行结算了没有"的记录 |
| 循环第二轮 vs 重试 | 靠 `loopIndex` 后缀区分，语义模糊 |
| 事件该归谁 | 只能查设备锁持有者，而等待期间锁已释放 |
| 人工重跑 | 没有 generation 概念，无法表达"同一业务步的第二次执行" |

两张表分别解决：`logical_operation` 管命令侧身份，`device_event_waiter` 管事件侧归属。

---

## 1. `logical_operation`：逻辑动作身份

### 1.1 设计要点

| 概念 | 含义 | 何时变 |
|---|---|---|
| `operation_key` | **业务身份**：哪个 run 的哪个节点的第几步 | 不变（除非业务节点本身变） |
| `generation` | **逻辑执行代次**：同一业务步被"重新执行"了几次 | 人工重跑 +1；resume 不 +1 |
| `command_id` | **设备幂等身份**：下发给设备的 id | 首次生成后**永不变** |
| `attempt_no` | **传输尝试次数**：发了/查了几次 | 每次发送或查询 +1 |

关键区分：
- **重试**：generation 不变、command_id 不变、attempt_no +1
- **resume**：先看上次是否结算——未结算则复用（同 generation、同 command_id）；已结算则不再执行该步
- **人工重跑**：generation +1、生成新 command_id
- **循环第二轮**：`loop_index` 进 `operation_key`，属于不同业务步，不是 generation

### 1.2 DDL

```sql
CREATE TABLE IF NOT EXISTS logical_operation (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id           BIGINT       NOT NULL,

    -- 业务身份：r{run}|n{node}|s{step}|d{device}[|l{loopIndex}]
    -- 不含时间、不含次数、不含随机数
    operation_key       VARCHAR(200) NOT NULL,
    generation          INT          NOT NULL DEFAULT 1,

    -- 设备幂等身份：首次创建时生成并持久化，之后只读
    command_id          VARCHAR(160) NOT NULL,

    run_id              BIGINT       NOT NULL,
    node_id             BIGINT,
    step_seq            INT,
    loop_index          INT          NOT NULL DEFAULT 1,
    device_instance_id  BIGINT,
    method              VARCHAR(64),

    -- 状态见 §1.3
    state               VARCHAR(24)  NOT NULL,
    attempt_no          INT          NOT NULL DEFAULT 0,

    -- 结果与证据
    last_error_code     VARCHAR(32),
    last_error_message  VARCHAR(256),
    result              JSONB        NOT NULL DEFAULT '{}'::jsonb,
    device_raw_response JSONB,

    -- 人工处置留痕（见 §1.4）
    disposed_by         VARCHAR(64),
    disposed_at         TIMESTAMPTZ,
    dispose_reason      VARCHAR(256),
    dispose_evidence    VARCHAR(256),

    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT uk_logical_operation UNIQUE (tenant_id, operation_key, generation),
    CONSTRAINT uk_logical_operation_cmd UNIQUE (tenant_id, command_id)
);

CREATE INDEX IF NOT EXISTS ix_lo_open
    ON logical_operation (tenant_id, state)
    WHERE state IN ('PENDING','DISPATCHED','ACKED','UNKNOWN');

CREATE INDEX IF NOT EXISTS ix_lo_run
    ON logical_operation (tenant_id, run_id, node_id);
```

**两条唯一约束的作用**：

- `uk_logical_operation`：同一业务步的同一代次只能有一条
- `uk_logical_operation_cmd`：`command_id` 全局唯一 → 设备侧去重与库内记录一一对应

### 1.3 状态机

```
                    ┌──────────────────────────────────────┐
                    │                                      │
   创建并落 PENDING                                          │
        │                                                 │
        │ dispatch（落库成功后才发）                          │
        ▼                                                 │
    DISPATCHED ──── 收到 ACK ────> ACKED ──── 完成 ────> COMPLETED
        │                          │                    （终态）
        │                          └──── 失败 ────> FAILED（终态）
        │
        ├── 查询 IN_PROGRESS ──> 保持 DISPATCHED（不重发）
        ├── 查询 NOT_FOUND / UNKNOWN ──> UNKNOWN（终态，待人工）
        └── 进程崩溃（未发出）──> 仍是 PENDING（可安全重发）
```

| 状态 | 含义 | 允许的动作 |
|---|---|---|
| `PENDING` | 已建记录，尚未下发 | 可下发；崩溃后可安全重发 |
| `DISPATCHED` | 已下发，未收到 ACK | 等 ACK；超时后查询，不盲重发 |
| `ACKED` | 设备已受理，执行中 | 只等完成；**绝不重发** |
| `COMPLETED` | 设备确认完成 | 终态 |
| `FAILED` | 设备确认失败 | 终态；是否重跑由业务决定 |
| `UNKNOWN` | 物理结果不可确认 | 终态；**只允许人工处置**，不自动重发 |
| `MANUAL` | 人工处置完成 | 终态；标记可信度差异 |

**关键规则（与既有设计一致，不能破）**：

1. `NOT_FOUND` **不等于**设备没执行过 → 一律落 `UNKNOWN`，不重发。
2. `ACKED` 之后没有"执行超时"这个概念，只有"业务期限告警"。
3. `PENDING` 是唯一可以安全重发的状态（因为命令确实没发出）。

### 1.4 人工处置

`UNKNOWN` 只能由人工推进，且必须留痕：

```sql
UPDATE logical_operation
   SET state = 'MANUAL',
       disposed_by = ?, disposed_at = now(),
       dispose_reason = ?,      -- 必选原因码
       dispose_evidence = ?,    -- 照片/扫码/现场记录编号
       result = ?               -- 人工判定的结论
 WHERE id = ? AND state = 'UNKNOWN'
```

三条约束：

1. **`MANUAL` 不等于 `COMPLETED`**。下游要能识别"这一步是人工处置的，不是设备确认的"。
2. 人工处置**不能**自动释放物料位置占用（位置事实另管）。
3. 高风险动作（移液、搬运、开盖、离心、封膜）的处置需按权限矩阵授权，必要时双人复核。

### 1.5 与现有表的关系

| 现有对象 | 关系 |
|---|---|
| `command_ledger` | 保留为**传输层账本**（每次发送/查询一行）；`logical_operation` 是其**上位聚合**（一个逻辑动作 N 条传输尝试） |
| `run_command` | 保留为**执行记录**（节点内第几条命令、回包原文）；`logical_operation.id` 可作为外键补充 |
| `run.exec_phase` | 保留（`PREPARED/DISPATCH_STARTED/SETTLED`），继续作为崩溃窗口标记 |

迁移时不改现有表，只新增；`command_ledger.idempotency_key` 可平滑映射为 `operation_key + generation`。

## 2. `device_event_waiter`：等待者登记

### 2.1 为什么不能用设备锁

真实流程结构（提取线）：

```
n_pick  (PickTipComb)  → 抢设备锁 → 执行 → onStepDone 释放锁
   ↓
n_wait  (__awaitEvent) → 不走 step 生命周期 → 无锁
   ↓
设备上报"到交换点"（E3 自发事件）
```

**等待事件的时候，设备锁早就释放了。** 用 `device_lock.current_run_id` 做归属，在这种场景下必然取不到值。

而且即便锁没释放，仍会迟到事件问题（ChatGPT 指出的）：A 持锁产生事件 → A 释放 → B 持锁 → 事件到达 → 被误归给 B。

### 2.2 设计要点

**登记"谁在等"，而不是"谁占着"。**

```sql
CREATE TABLE IF NOT EXISTS device_event_waiter (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id           BIGINT       NOT NULL,

    run_id              BIGINT       NOT NULL,
    node_id             BIGINT       NOT NULL,
    loop_index          INT          NOT NULL DEFAULT 1,

    -- 粗匹配条件（与现有 __awaitEvent 参数一致）
    device_code         VARCHAR(64)  NOT NULL,
    event_type          VARCHAR(48)  NOT NULL,

    -- 精匹配条件（归属依据，可为空）
    expect_process_id   VARCHAR(128),
    expect_interaction  VARCHAR(128),

    -- 等待区间
    base_event_id       BIGINT       NOT NULL,   -- 从这条之后开始等
    deadline_at         TIMESTAMPTZ,             -- 业务上限，超时告警不判失败

    state               VARCHAR(16)  NOT NULL,   -- WAITING/MATCHED/CANCELLED/EXPIRED
    matched_event_id    BIGINT,

    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT uk_waiter UNIQUE (tenant_id, run_id, node_id, loop_index)
);

CREATE INDEX IF NOT EXISTS ix_waiter_open
    ON device_event_waiter (tenant_id, device_code, event_type, base_event_id)
    WHERE state = 'WAITING';
```

### 2.3 匹配规则

一条事件到达时：

```
1. 取出所有 state='WAITING'
     且 device_code / event_type 匹配
     且 base_event_id < event.id
   的 waiter

2. 精匹配（决定归属）：
   ┌ waiter 声明了 expect_process_id  且 事件 process_id 相同  → 强匹配
   ├ waiter 声明了 expect_interaction 且 事件 interaction_step 相同 → 强匹配
   ├ waiter 没声明，事件 process_id 也为空 → 弱匹配（沿用现状，允许）
   └ waiter 没声明，但事件带了别的 process_id → **不匹配**

3. 只有一个强匹配 → 匹配成功，写 consumption，waiter 置 MATCHED
   多个强匹配 → 全部不匹配，事件标 UNATTRIBUTED，告警
   无强匹配但有唯一弱匹配 → 仅在该设备当前只有这一个 waiter 时允许
   无任何匹配 → 事件留库，等后续 waiter 或人工
```

**核心原则：不确定就不归属。** 宁可让事件悬着、人工处理，也不能分给错误的 run——那会推进错误的流程、动错的板。

### 2.4 状态机

```
   WAITING ──匹配成功──> MATCHED（终态）
      │
      ├── 超时（deadline_at 到）──> EXPIRED（终态，告警，节点转 paused_waiting）
      ├── run 被取消/暂停 ──> CANCELLED（终态）
      └── 多条强匹配/无法判定 ──> 保持 WAITING + 告警（不猜）
```

### 2.5 与现有表的关系

| 现有对象 | 关系 |
|---|---|
| `device_event_run_cursor` | **可废弃或降级**。现在按 run 记游标，改为按 waiter 记 `base_event_id` 更精确 |
| `device_event_consumption` | 保留，作为"事件已被谁消费"的唯一事实。waiter 匹配成功后写一行，唯一键 `(tenant_id, run_id, node_key, loop_index)` 正好对应 waiter |
| `device_event.process_id` / `interaction_step` | **直接复用**，这是现成的精匹配依据，`DeviceEventController` 第 90–91 行已在读 |

## 3. 关键流程走查

### 3.1 正常执行

```
1. 节点开始 → 建 logical_operation (PENDING)，生成 command_id 并持久化
2. 下发前把 state 改 DISPATCHED（先落库再发，保证崩溃可知）
3. 设备回 ACK → state = ACKED
4. 设备回完成 → state = COMPLETED
5. 若下一步是 __awaitEvent → 建 device_event_waiter (WAITING)
6. 设备上报事件 → 匹配 waiter → 推进节点
```

### 3.2 断线重试

```
1. state = DISPATCHED，长时间无 ACK
2. 查询设备状态
   ├ IN_PROGRESS → 保持 DISPATCHED，继续等（不重发）
   ├ COMPLETED/FAILED → 落终态
   └ NOT_FOUND/UNKNOWN → state = UNKNOWN，转人工（不重发）
3. 只有 state 仍是 PENDING（确认没发出）才允许重发，attempt_no +1
```

### 3.3 Resume

```
1. 读该节点是否有 logical_operation
   ├ 无 → 新建（新 command_id）
   ├ 有且 state ∈ {COMPLETED, FAILED, MANUAL} → 该步已结算，跳过或按业务继续
   ├ 有且 state ∈ {PENDING} → 直接复用（command_id 不变）
   ├ 有且 state = DISPATCHED → 先查询，再决定
   └ 有且 state = UNKNOWN → 不自动执行，转人工
2. **绝不因 resume 重新生成 command_id**
```

### 3.4 人工重跑

```
1. generation +1
2. 生成新 command_id
3. 新记录 state = PENDING
4. 旧 generation 的记录保留（审计）
```

### 3.5 循环体第二轮

```
operation_key 里带 |l{n}：
  r100|n10|s1|d5|l1  → 第一轮
  r100|n10|s1|d5|l2  → 第二轮（不同业务步，不是 generation）
```

## 4. 迁移步骤

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | 建两张表（只新增，不改现有） | 无 |
| 2 | 写路径改为"先建 logical_operation，再走 command_ledger" | 低，双写期 |
| 3 | `__awaitEvent` 改为先建 waiter，再等 | 中，需回归 |
| 4 | 回填历史：从 `command_ledger` 反推 operation_key | 低，只读 |
| 5 | 观察双写一致性一周后，逐步以新表为准 | 中 |
| 6 | `device_event_run_cursor` 标记 deprecated | 低 |

**不做的事**：不删 `command_ledger`、不删 `run_command`、不改 `run_status` 枚举。

## 5. 验收场景

| ID | 场景 | 期望 |
|---|---|---|
| L-01 | 同一逻辑动作重发（PENDING） | command_id 不变，generation 不变，attempt_no +1 |
| L-02 | 查询 NOT_FOUND | 落 UNKNOWN，**不重发** |
| L-03 | 查询 IN_PROGRESS | 保持 DISPATCHED，不重发 |
| L-04 | 崩溃后 resume（PENDING） | 复用同一 command_id |
| L-05 | 崩溃后 resume（DISPATCHED） | 先查询再决定，不新建 command_id |
| L-06 | 崩溃后 resume（COMPLETED） | 不重复执行该步 |
| L-07 | 人工重跑 | generation +1，新 command_id，旧记录保留 |
| L-08 | 循环第二轮 | operation_key 带 `|l2`，与第一轮互不影响 |
| L-09 | 人工处置 UNKNOWN | state=MANUAL，留痕完整，下游可识别 |
| W-01 | 两条 waiter 等同一设备同一事件，事件带 process_id | 只有 process_id 匹配的那条被推进 |
| W-02 | 事件 process_id 与所有 waiter 都不匹配 | 事件标 UNATTRIBUTED，告警，不推进任何流程 |
| W-03 | waiter 未声明 process_id，事件也没带 | 唯一 waiter 时允许弱匹配；多个时不允许 |
| W-04 | 事件先于 waiter 到达 | waiter 以 `base_event_id` 为准，不丢 |
| W-05 | waiter 超时 | EXPIRED + 告警，节点 paused_waiting，不误判完成 |
| W-06 | 设备断电重启后事件序号归零 | 需 `device_boot_id` 区分（见 §6） |

## 6. 已知限制（必须写进实现前提）

1. **`device_event_seq` 需要配 `device_boot_id`**：设备断电重启后序号可能归零，单靠 `device_id + seq` 会冲突。唯一键应为 `(tenant_id, device_code, boot_id, seq)`。
2. **精匹配依赖设备上报 `process_id` / `interaction_step`**：不支持的设备只能弱匹配，而弱匹配在"同设备多 waiter"时不可靠 → 必须降级为独占串行。
3. **`logical_operation` 不解决跨实例问题**：本设计假设单实例。若上多实例，仍需 epoch 保护（见设计基线 R-02）。
4. **人工处置不能替代设备确认**：`MANUAL` 状态在下游报表和证据链中必须与 `COMPLETED` 区分显示。

## 7. 需要评审者回答

1. `operation_key` 不含 `exec` 后，是否有场景会导致"两个不同的物理动作撞到同一个 key"？
2. `generation` 只在人工重跑时递增，是否漏了某种"业务上算新逻辑执行"的情况（如换批次复用同一节点）？
3. `device_event_waiter` 的精匹配在 `process_id` 为空时的"弱匹配"规则，是否应该直接禁止（一律要求精匹配）？
4. `UNATTRIBUTED` 事件保留多久、由谁清理、是否要单独建表？
5. 双写期（`command_ledger` + `logical_operation`）如何验证一致性？
6. 人工处置的权限矩阵（谁可处置、何时需双人）应放在哪一层？
