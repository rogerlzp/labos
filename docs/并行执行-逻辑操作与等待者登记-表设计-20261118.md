# 逻辑操作与等待者登记：表设计

- 日期：2026-11-18
- 版本：v2（补齐 v1 自检发现的 8 个缺口）
- 性质：表结构与状态机设计，**未实施**
- 前提：**单实例部署**，不使用 fencing/epoch
- 目标：为并行执行提供两个缺失的身份层——**逻辑动作身份**（解决重试/resume/重跑的歧义）和**等待者登记**（解决事件归属不依赖设备锁）

### 修订记录

| 版本 | 变更 |
|---|---|
| v1 | 初版：两张表 + 状态机 + 15 个验收 |
| v2 | 补 `attribution_state`（UNATTRIBUTED 落地）；`pause_kind` 替代枚举；waiter 匹配加行锁；`deadline_at` 改 NOT NULL；新增 `dispose_outcome` 与 `result_trust`；新增双写对账 SQL；明确两套 attempt 语义；验收增至 21 项 |

---

## 0. 为什么需要这两张表

前几轮评审暴露的所有争议，根因是同一个：**系统缺少"这次操作是谁、这是第几次逻辑执行、谁在等这条事件"的显式记录**，只能靠拼字符串和查当前状态推断。

| 争议 | 缺的东西 |
|---|---|
| 重试时 commandId 该不该变 | 没有"逻辑动作"这个实体，只能拼 `run+node+step+device` |
| resume 后该复用还是重发 | 没有"这次逻辑执行结算了没有"的记录 |
| 循环第二轮 vs 重试 | 靠 `loopIndex` 后缀区分，语义模糊 |
| 事件该归谁 | 只能查设备锁持有者，而等待期间锁已释放 |
| 人工重跑 | 没有 generation 概念，无法表达"同一业务步的第二次执行" |
| 人工处置后结果可信吗 | 没有可信度维度，`MANUAL` 和 `COMPLETED` 被下游混用 |

## 1. `logical_operation`：逻辑动作身份

### 1.1 设计要点

| 概念 | 含义 | 何时变 |
|---|---|---|
| `operation_key` | **业务身份**：哪个 run 的哪个节点的第几步 | 不变（除非业务节点本身变） |
| `generation` | **逻辑执行代次**：同一业务步被"重新执行"了几次 | 人工重跑 +1；resume 不 +1 |
| `command_id` | **设备幂等身份**：下发给设备的 id | 首次生成后**永不变** |
| `attempt_no` | **传输尝试次数**：发了/查了几次 | 每次发送或查询 +1 |
| `result_trust` | **结果可信度**：这个结论是怎么来的 | 随状态迁移设置 |

关键区分：

- **重试**：generation 不变、command_id 不变、attempt_no +1
- **resume**：先看上次是否结算——未结算则复用（同 generation、同 command_id）；已结算则不再执行该步
- **人工重跑**：generation +1、生成新 command_id
- **循环第二轮**：`loop_index` 进 `operation_key`，属于不同业务步，不是 generation

### 1.2 两套 attempt 的语义（必须先分清）

系统里有两个叫 attempt 的字段，含义不同，不能混用：

| 字段 | 位置 | 含义 | 何时变 |
|---|---|---|---|
| `run_node.attempt` | 节点 | 这个节点被执行了几次（resume 才 +1） | resume / 人工重跑 |
| `logical_operation.attempt_no` | 逻辑动作 | 这个动作被**发送/查询**了几次 | 每次传输尝试 |
| `command_ledger.attempt` | 传输明细 | 继承自 `run_node.attempt`，标识该次传输属于哪一轮节点执行 | 随节点 attempt |

**权威关系**：`logical_operation.attempt_no` 是"传输次数"的权威；`command_ledger` 是每次传输的明细，不单独计数。

### 1.3 DDL

```sql
CREATE TABLE IF NOT EXISTS logical_operation (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id           BIGINT       NOT NULL,

    -- 业务身份：r{run}|n{node}|s{step}|d{device}[|l{loopIndex}]
    -- 不含时间、不含次数、不含随机数
    operation_key       VARCHAR(200) NOT NULL,
    generation          INT          NOT NULL DEFAULT 1,

    -- 设备幂等身份：首次创建时生成并持久化，之后只读
    command_id          VARCHAR(160) NOT NULL,

    run_id              BIGINT       NOT NULL,
    node_id             BIGINT,
    step_seq            INT,
    loop_index          INT          NOT NULL DEFAULT 1,
    device_instance_id  BIGINT,
    method              VARCHAR(64),

    -- 状态见 §1.4
    state               VARCHAR(24)  NOT NULL,
    attempt_no          INT          NOT NULL DEFAULT 0,

    -- 结果可信度：DEVICE_CONFIRMED / MANUAL_VERIFIED / INFERRED / UNKNOWN
    result_trust        VARCHAR(16)  NOT NULL DEFAULT 'UNKNOWN',

    -- 结果与证据
    last_error_code     VARCHAR(32),
    last_error_message  VARCHAR(256),
    result              JSONB        NOT NULL DEFAULT '{}'::jsonb,
    device_raw_response JSONB,

    -- 人工处置留痕（见 §1.5）
    dispose_outcome     VARCHAR(24),
    disposed_by         VARCHAR(64),
    disposed_at         TIMESTAMPTZ,
    dispose_reason      VARCHAR(256),
    dispose_evidence    VARCHAR(256),

    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT uk_logical_operation UNIQUE (tenant_id, operation_key, generation),
    CONSTRAINT uk_logical_operation_cmd UNIQUE (tenant_id, command_id),
    CONSTRAINT ck_lo_dispose CHECK (
        (state = 'MANUAL' AND dispose_outcome IS NOT NULL AND disposed_by IS NOT NULL)
        OR state <> 'MANUAL'
    )
);

CREATE INDEX IF NOT EXISTS ix_lo_open
    ON logical_operation (tenant_id, state)
    WHERE state IN ('PENDING','DISPATCHED','ACKED','UNKNOWN');

CREATE INDEX IF NOT EXISTS ix_lo_run
    ON logical_operation (tenant_id, run_id, node_id);
```

**三条约束的作用**：

- `uk_logical_operation`：同一业务步的同一代次只能有一条
- `uk_logical_operation_cmd`：`command_id` 全局唯一 → 设备侧去重与库内记录一一对应
- `ck_lo_dispose`：进入 `MANUAL` 必须同时有处置结论和处置人，**不允许静默进入**

### 1.4 状态机

```
   创建并落 PENDING
        │
        │ dispatch（先落库再发）
        ▼
    DISPATCHED ──── 收到 ACK ────> ACKED ──── 完成 ────> COMPLETED
        │                          │                    result_trust=DEVICE_CONFIRMED
        │                          └──── 失败 ────> FAILED
        │
        ├── 查询 IN_PROGRESS ──> 保持 DISPATCHED（不重发）
        ├── 查询 NOT_FOUND / UNKNOWN ──> UNKNOWN（待人工）
        └── 进程崩溃（未发出）──> 仍是 PENDING（可安全重发）

   UNKNOWN ──人工处置──> MANUAL
                          结果按 dispose_outcome 分流（见 §1.5）
```

| 状态 | 含义 | 允许的动作 |
|---|---|---|
| `PENDING` | 已建记录，尚未下发 | 可下发；崩溃后可安全重发 |
| `DISPATCHED` | 已下发，未收到 ACK | 等 ACK；超时后查询，不盲重发 |
| `ACKED` | 设备已受理，执行中 | 只等完成；**绝不重发** |
| `COMPLETED` | 设备确认完成 | 终态 |
| `FAILED` | 设备确认失败 | 终态；是否重跑由业务决定 |
| `UNKNOWN` | 物理结果不可确认 | 终态；**只允许人工处置**，不自动重发 |
| `MANUAL` | 人工处置完成 | 终态；按 `dispose_outcome` 决定后续 |

**关键规则（与既有设计一致，不能破）**：

1. `NOT_FOUND` **不等于**设备没执行过 → 一律落 `UNKNOWN`，不重发。
2. `ACKED` 之后没有"执行超时"这个概念，只有"业务期限告警"。
3. `PENDING` 是唯一可以安全重发的状态（因为命令确实没发出）。

### 1.5 人工处置：四种结论决定后续路径

`UNKNOWN` 只能由人工推进，且必须给出结论：

| `dispose_outcome` | 含义 | `result_trust` | 后续 |
|---|---|---|---|
| `NOT_EXECUTED` | 确认设备没动过 | `UNKNOWN` | 允许**同 generation** 重发（attempt_no +1，command_id 不变）；或由业务决定 generation +1 新命令 |
| `EXECUTED_OK` | 确认已执行且结果可接受 | `MANUAL_VERIFIED` | 进下一步，不重发 |
| `EXECUTED_BAD` | 确认已执行但结果不可接受 | `MANUAL_VERIFIED` | 转 `FAILED`，按失败处理 |
| `INDETERMINATE` | 无法确认 | `UNKNOWN` | 保持 `UNKNOWN`，隔离相关物料和位置，不得放行 |

```sql
UPDATE logical_operation
   SET state = 'MANUAL',
       dispose_outcome = ?,     -- 四选一，必填
       disposed_by = ?,         -- 必填
       disposed_at = now(),
       dispose_reason = ?,      -- 原因码，必填
       dispose_evidence = ?,    -- 照片/扫码/现场记录编号
       result_trust = ?,        -- 与 outcome 对应
       result = ?
 WHERE id = ? AND state = 'UNKNOWN'
```

三条约束：

1. **`MANUAL` 不等于 `COMPLETED`**。下游必须按 `result_trust` 区分。
2. `INDETERMINATE` **不能**释放物料位置占用（位置事实另管）。
3. 高风险动作（移液、搬运、开盖、离心、封膜）的处置需按权限矩阵授权，必要时双人复核（见 §6 限制 5）。

### 1.6 与现有表的关系

| 现有对象 | 关系 |
|---|---|
| `command_ledger` | 保留为**传输层明细**（每次发送/查询一行）；`logical_operation` 是其**上位聚合** |
| `run_command` | 保留为**执行记录**；`logical_operation.id` 可作为外键补充 |
| `run_node.attempt` | 保留，表示节点执行轮次；与 `attempt_no` 语义不同（见 §1.2） |
| `run.exec_phase` | 保留（`PREPARED/DISPATCH_STARTED/SETTLED`），继续作为崩溃窗口标记 |

迁移时不改现有表，只新增；`command_ledger.idempotency_key` 可平滑映射为 `operation_key + generation`。

## 2. `device_event_waiter`：等待者登记

### 2.1 为什么不能用设备锁

真实流程结构（提取线）：

```
n_pick  (PickTipComb)  → 抢设备锁 → 执行 → onStepDone 释放锁
   ↓
n_wait  (__awaitEvent) → 不走 step 生命周期 → 无锁
   ↓
设备上报"到交换点"（E3 自发事件）
```

**等待事件的时候，设备锁早就释放了。** 用 `device_lock.current_run_id` 做归属，在这种场景下必然取不到值。

即便锁没释放，仍有迟到事件问题：A 持锁产生事件 → A 释放 → B 持锁 → 事件到达 → 被误归给 B。

### 2.2 设计要点

**登记"谁在等"，而不是"谁占着"。**

```sql
CREATE TABLE IF NOT EXISTS device_event_waiter (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id           BIGINT       NOT NULL,

    run_id              BIGINT       NOT NULL,
    node_id             BIGINT       NOT NULL,
    loop_index          INT          NOT NULL DEFAULT 1,

    -- 粗匹配条件（与现有 __awaitEvent 参数一致）
    device_code         VARCHAR(64)  NOT NULL,
    event_type          VARCHAR(48)  NOT NULL,

    -- 精匹配条件（归属依据，可为空）
    expect_process_id   VARCHAR(128),
    expect_interaction  VARCHAR(128),

    -- 等待区间
    base_event_id       BIGINT       NOT NULL,   -- 从这条之后开始等
    deadline_at         TIMESTAMPTZ  NOT NULL,   -- 必填，按类型默认值

    state               VARCHAR(16)  NOT NULL,   -- WAITING/MATCHED/CANCELLED/EXPIRED
    matched_event_id    BIGINT,

    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT uk_waiter UNIQUE (tenant_id, run_id, node_id, loop_index)
);

CREATE INDEX IF NOT EXISTS ix_waiter_open
    ON device_event_waiter (tenant_id, device_code, event_type, base_event_id)
    WHERE state = 'WAITING';
```

**`deadline_at` 为什么必须非空**：可空等于"永不超时"，会导致 waiter 永久挂起、节点永远等不到。建 waiter 时必须填，默认值：

| 事件类型 | 默认期限 |
|---|---|
| 一般交互事件 | 600 秒（与现有 `__awaitEvent` 的 timeout 一致） |
| 长工艺过程事件 | 按方法超时上限（复用 `MethodTimeoutPolicy`） |
| 未配置 | 600 秒兜底 |

### 2.3 归属落地：给 `device_event` 加一列

v1 只在验收里写了"事件标 UNATTRIBUTED"，但没有字段承载。v2 补上：

```sql
ALTER TABLE device_event
    ADD COLUMN IF NOT EXISTS attribution_state VARCHAR(16) NOT NULL DEFAULT 'PENDING';

COMMENT ON COLUMN device_event.attribution_state IS
    '归属判定：PENDING=未判定 / ATTRIBUTED=已被 waiter 匹配 / UNATTRIBUTED=无法判定归属，需人工';
```

与既有字段的区别（不要混用）：

| 字段 | 回答的问题 |
|---|---|
| `dispatched_at` | 这条事件**有没有被认领**（时间） |
| `device_event_consumption` | 这条事件**被谁消费**（唯一） |
| `attribution_state` | 这条事件**能不能判定归属**（结果） |

一条事件可以"被认领"（`dispatched_at` 非空）但"归属不确定"（`UNATTRIBUTED`）——这正是需要人工介入的情况。

### 2.4 匹配规则（含并发控制）

单实例也是多线程，匹配必须加行锁，否则两条事件可能同时匹配同一个 waiter。

```sql
WITH candidate AS (
    SELECT w.id
      FROM device_event_waiter w
     WHERE w.tenant_id  = ?
       AND w.state      = 'WAITING'
       AND w.device_code = ?
       AND w.event_type  = ?
       AND w.base_event_id < ?
       AND (w.expect_process_id  IS NULL OR w.expect_process_id  = ?)
       AND (w.expect_interaction IS NULL OR w.expect_interaction = ?)
     ORDER BY w.created_at
     FOR UPDATE SKIP LOCKED
)
SELECT id FROM candidate;
```

拿到的行数决定后续：

| 行数 | 处理 |
|---|---|
| 恰好 1 行 | 置 `MATCHED` + `matched_event_id`；写 `device_event_consumption`；事件 `attribution_state='ATTRIBUTED'` |
| 0 行 | 事件 `attribution_state='UNATTRIBUTED'`，告警，不推进任何流程 |
| 多行 | **全部回滚**，事件 `UNATTRIBUTED`，告警；不猜 |

多条强匹配时必须整体回滚，不能"挑第一条"——那会推进错误的流程。

### 2.5 精匹配与弱匹配

```
waiter 声明了 expect_process_id 且 事件 process_id 相同   → 强匹配
waiter 声明了 expect_interaction 且 事件 interaction_step 相同 → 强匹配
waiter 未声明，事件也未带任何过程标识                    → 弱匹配
waiter 未声明，但事件带了别的 process_id                 → **不匹配**
```

**弱匹配的启用条件（严格）**：

- 仅当该设备当前**只有一个** WAITING 的 waiter 时才允许；
- 多个 waiter 同时等同一设备时，弱匹配一律不生效 → 事件进 `UNATTRIBUTED`。

**建议**：生产环境默认**禁止弱匹配**（配置项 `LABOS_EVENT_WEAK_MATCH=off`），要求设备必须上报过程标识。做不到的设备降级为独占串行。这一点需评审确认。

### 2.6 状态机

```
   WAITING ──匹配成功──> MATCHED（终态）
      │
      ├── 超时（deadline_at 到）──> EXPIRED（终态，告警）
      ├── run 被取消/暂停 ──> CANCELLED（终态）
      └── 多条匹配/无法判定 ──> 保持 WAITING + 告警（不猜）
```

**EXPIRED 与节点状态的衔接**：不新增 `run_status` 枚举值（系统既有原则是"用列不用枚举"），改为：

```sql
-- run 层：pause_kind 加一个取值（字符串列，不涉及 ALTER TYPE）
UPDATE run SET pause_kind = 'waiting_event' WHERE id = ? AND status = 'running';
```

`pause_kind` 现有取值是 `paused_fault / waiting_human / paused_unknown`，新增 `waiting_event` 只是加列值，与"加枚举值要 ALTER TYPE"的限制无关。

### 2.7 与现有表的关系

| 现有对象 | 关系 |
|---|---|
| `device_event_run_cursor` | **标记 deprecated**。现在按 run 记游标，改为按 waiter 记 `base_event_id` 更精确 |
| `device_event_consumption` | 保留，作为"事件已被谁消费"的唯一事实。waiter 匹配成功后写一行，唯一键正好对应 waiter |
| `device_event.process_id` / `interaction_step` | **直接复用**，这是现成的精匹配依据，`DeviceEventController` 第 90–91 行已在读 |

## 3. 关键流程走查

### 3.1 正常执行

```
1. 节点开始 → 建 logical_operation (PENDING)，生成 command_id 并持久化
2. 下发前把 state 改 DISPATCHED（先落库再发，保证崩溃可知）
3. 设备回 ACK → state = ACKED
4. 设备回完成 → state = COMPLETED，result_trust = DEVICE_CONFIRMED
5. 若下一步是 __awaitEvent → 建 device_event_waiter (WAITING)，必填 deadline_at
6. 设备上报事件 → 行锁匹配 waiter → 写 consumption → 推进节点
```

### 3.2 断线重试

```
1. state = DISPATCHED，长时间无 ACK
2. 查询设备状态
   ├ IN_PROGRESS → 保持 DISPATCHED，继续等（不重发）
   ├ COMPLETED/FAILED → 落终态
   └ NOT_FOUND/UNKNOWN → state = UNKNOWN，转人工（不重发）
3. 只有 state 仍是 PENDING（确认没发出）才允许重发，attempt_no +1
```

### 3.3 Resume

```
1. 读该节点是否有 logical_operation
   ├ 无 → 新建（新 command_id）
   ├ 有且 state ∈ {COMPLETED, FAILED, MANUAL} → 已结算，跳过或按业务继续
   ├ 有且 state = PENDING → 直接复用（command_id 不变）
   ├ 有且 state = DISPATCHED → 先查询，再决定
   └ 有且 state = UNKNOWN → 不自动执行，转人工
2. **绝不因 resume 重新生成 command_id**
```

### 3.4 人工重跑

```
1. generation +1
2. 生成新 command_id
3. 新记录 state = PENDING
4. 旧 generation 的记录保留（审计）
```

### 3.5 循环体第二轮

```
operation_key 里带 |l{n}：
  r100|n10|s1|d5|l1  → 第一轮
  r100|n10|s1|d5|l2  → 第二轮（不同业务步，不是 generation）
```

## 4. 迁移与双写对账

### 4.1 迁移步骤

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | 建两张表 + 给 `device_event` 加 `attribution_state`（只新增） | 无 |
| 2 | 写路径改为"先建 logical_operation，再走 command_ledger" | 低，双写期 |
| 3 | `__awaitEvent` 改为先建 waiter，再等 | 中，需回归 |
| 4 | 回填历史：从 `command_ledger` 反推 operation_key | 低，只读 |
| 5 | 每日跑一致性对账（见 §4.2），差异人工处理 | 中 |
| 6 | 观察两周无差异后，逐步以新表为准 | 中 |
| 7 | `device_event_run_cursor` 标记 deprecated | 低 |

**不做的事**：不删 `command_ledger`、不删 `run_command`、不改 `run_status` 枚举。

### 4.2 双写一致性对账

每日执行，差异进告警，人工处理：

```sql
-- ① 有传输明细、无逻辑动作（说明写路径漏了）
SELECT l.id, l.idempotency_key, l.command_id, l.state
  FROM command_ledger l
  LEFT JOIN logical_operation o
    ON o.tenant_id = l.tenant_id AND o.command_id = l.command_id
 WHERE o.id IS NULL;

-- ② 已下发、但无任何传输明细（说明状态机与账本脱节）
SELECT o.id, o.command_id, o.state, o.attempt_no
  FROM logical_operation o
  LEFT JOIN command_ledger l
    ON l.tenant_id = o.tenant_id AND l.command_id = o.command_id
 WHERE l.id IS NULL
   AND o.state IN ('DISPATCHED','ACKED');

-- ③ 状态矛盾：动作已终结、但仍有未结算传输
SELECT o.id, o.command_id, o.state,
       count(l.id) FILTER (WHERE l.state = 'DISPATCH_STARTED') AS open_ledgers
  FROM logical_operation o
  JOIN command_ledger l ON l.tenant_id = o.tenant_id AND l.command_id = o.command_id
 WHERE o.state IN ('COMPLETED','FAILED','MANUAL')
 GROUP BY o.id, o.command_id, o.state
HAVING count(l.id) FILTER (WHERE l.state = 'DISPATCH_STARTED') > 0;
```

**发现差异时**：以 `logical_operation` 为准（它是上位聚合），补写 `command_ledger` 明细；若 `logical_operation` 缺失，则从 `command_ledger` 重建。

## 5. 验收场景

### 5.1 命令侧

| ID | 场景 | 期望 |
|---|---|---|
| L-01 | 同一逻辑动作重发（PENDING） | command_id 不变，generation 不变，attempt_no +1 |
| L-02 | 查询 NOT_FOUND | 落 UNKNOWN，**不重发** |
| L-03 | 查询 IN_PROGRESS | 保持 DISPATCHED，不重发 |
| L-04 | 崩溃后 resume（PENDING） | 复用同一 command_id |
| L-05 | 崩溃后 resume（DISPATCHED） | 先查询再决定，不新建 command_id |
| L-06 | 崩溃后 resume（COMPLETED） | 不重复执行该步 |
| L-07 | 人工重跑 | generation +1，新 command_id，旧记录保留 |
| L-08 | 循环第二轮 | operation_key 带 `\|l2`，与第一轮互不影响 |
| L-09 | 人工处置 EXECUTED_OK | state=MANUAL，result_trust=MANUAL_VERIFIED，下游可区分 |
| L-10 | 人工处置 NOT_EXECUTED 后重发 | 同 generation 重发，attempt_no +1，command_id 不变 |
| L-11 | 人工处置 INDETERMINATE | 保持 UNKNOWN，物料与位置不放行 |
| L-12 | 静默进入 MANUAL（无 disposed_by） | 被 `ck_lo_dispose` 拒绝 |

### 5.2 事件侧

| ID | 场景 | 期望 |
|---|---|---|
| W-01 | 两条 waiter 等同一设备同一事件，事件带 process_id | 只有匹配的那条被推进 |
| W-02 | 事件 process_id 与所有 waiter 都不匹配 | `attribution_state='UNATTRIBUTED'`，告警，不推进 |
| W-03 | 多个 waiter、事件无过程标识 | 全部不匹配，事件 UNATTRIBUTED |
| W-04 | 唯一 waiter、事件无过程标识 | 弱匹配生效（若开启）；关闭时 UNATTRIBUTED |
| W-05 | 事件先于 waiter 到达 | waiter 以 `base_event_id` 为准，不丢 |
| W-06 | waiter 超时 | `EXPIRED` + 告警；`run.pause_kind='waiting_event'` |
| W-07 | 两条事件同时到达 | 行锁保证不会同时匹配同一 waiter |
| W-08 | 匹配到多行 | 整体回滚，事件 UNATTRIBUTED，不猜 |
| W-09 | 设备断电重启后事件序号归零 | 需 `device_boot_id` 区分（见 §7） |

### 5.3 一致性

| ID | 场景 | 期望 |
|---|---|---|
| C-12 | 双写期每日对账 | §4.2 三条 SQL 均无差异 |
| C-13 | 差异出现时 | 以 `logical_operation` 为准补齐，记录处置 |

## 6. 需要业务确认的三处

## 7. 已知限制（必须写进实现前提）

1. **`device_event_seq` 需要配 `device_boot_id`**：设备断电重启后序号可能归零，单靠 `device_id + seq` 会冲突。唯一键应为 `(tenant_id, device_code, boot_id, seq)`。
2. **精匹配依赖设备上报 `process_id` / `interaction_step`**：不支持的设备只能弱匹配，而弱匹配在"同设备多 waiter"时不可靠 → 必须降级为独占串行。
3. **`logical_operation` 不解决跨实例问题**：本设计假设单实例。若上多实例，仍需 epoch 保护（见设计基线 R-02）。
4. **人工处置不能替代设备确认**：`MANUAL` 与 `COMPLETED` 必须在下游报表和证据链中区分显示。
5. **人工处置的权限矩阵尚未实现**：v2 只定义了字段和默认规则，审批流程需单独设计。
