# 并发死锁分析与对策

> 你指出的场景是**真实的死锁**，不是理论问题。
> 本文分析所有可能的死锁形态，给出对策。

---

## 一、你指出的场景：板子回不了家

### 时序

```
实验 1：A 出板 → 机械臂搬到 B → B 执行 → 准备放回 A
实验 2：A 又出一块板 → 占了 A 的那个位置

结果：实验 1 要把板放回 A，但位置被占 → 卡住
```

### 为什么会发生

**根因：实验 1 从 A 取板时，只占了"A 的当前层位"，没占"回来要放的位置"。**

```
① 实验 1 取板：A 的 L1 位置 → 空了
② 实验 2 看到 L1 空了 → 往 L1 放板     ← 冲突在这里
③ 实验 1 回来：L1 被占，无处可放
```

**这不是"锁没生效"，是"锁的语义不对"**：
位置锁保护的是"此刻这个位置有没有板"，不保护"这块板将来要回哪"。

## 二、三种死锁形态

### 形态 1：回程位置被占（你指出的）

```
A ──取板──> 机械臂 ──> B          A 的位置被别的执行占了
                          ↓
                       要放回 A     ← 卡住
```

**特征**：单向资源依赖，卡在"回程"。

### 形态 2：循环等待（经典死锁）

```
实验 1：先抢 A 再要 B
实验 2：先抢 B 再要 A

实验 1 拿到 A 等 B，实验 2 拿到 B 等 A → 互相等
```

**特征**：两个执行各持一半资源。

**现状**：`PositionLock.tryReserveTransfer` 按 **id 升序**申请，
已经消除了这一种（死锁四条件里的"循环等待"）。

**但**：那只覆盖"一次搬两个位置"的原子操作。
如果流程是"先搬 X 再搬 Y"，**跨步骤的循环等待仍然可能**。

### 形态 3：机械臂本身被占

```
实验 1：机械臂搬到一半，等 B 完成
实验 2：要机械臂搬自己的板 → 等
```

**特征**：机械臂是串行资源，长任务占着会影响其他实验。

**这个不是死锁**（机械臂最终会释放），但会**严重拖慢**。

## 三、对策

### 对策 1：取板时预留回程位置（解决形态 1）★

**核心**：取板时，**同时锁定"这块板将来要回去的位置"**。

```java
// 现在的逻辑
tryReserve(sourceId, runId, ttl);          // 只占源位置
// 取板、搬运、执行...
putPlate(targetId, plateId, runId);        // 放到目标

// 应该改成
tryReserveTransfer(sourceId, returnSlotId, runId, ttl);
// ↑ 同时占源位置和回程位置（已有的双锁 API，按 id 升序防死锁）
```

**`returnSlotId` 怎么定**：

| 情况 | 回程位置 |
|---|---|
| 出板 → 执行 → **回原位置** | 原位置本身 |
| 出板 → 执行 → 换位置 | 目标位置 |
| 出板 → 执行 → 随便哪 | **预留一个空位**（最宽松） |

**关键**：**在流程设计时就确定"这块板最终去哪"**，不是执行时才找。

**实现方式**：节点参数里加 `returnTo`：

```json
{
  "method": "Transfer",
  "params": {
    "source": "ID1775",
    "target": "ID1183",
    "returnTo": "ID1775"        ← 明确声明回程位置
  }
}
```

**如果没配 `returnTo`**：默认等于 `source`（从哪来回哪去）。

### 对策 2：预留超时要能续命

**问题**：实验 1 占着回程位置，但 B 要跑 30 分钟，TTL 到期位置被释放。

**现状**：`PositionLock` 的 TTL 是 30 分钟（`DEFAULT_TTL`）。

**风险**：孵育 40 分钟的流程，回程位置会中途被抢。

**对策**：

```java
// 每次心跳/进度上报时续期
lock.extendTtl(positionId, runId, Duration.ofMinutes(30));
```

**或者**：TTL 按流程预估时长动态算（`duration_model` 里有 `base` 秒数）。

### 对策 3：抢不到就"申请"而不是"失败"

**现在**：`putPlate` 写不进去 → 报 `NO_EMPTY_POSITION` → 执行失败。

**更好的**：**排队等**（和对策 1 配合，正常情况下不会等）。

```java
if (putPlate(...) == NO_EMPTY_POSITION) {
    // 预留的位置被抢了（TTL 到期或数据异常）
    // 找一个同类设备的空位置，改为"换地方放"
    找替代位置 → 更新 run 的记录 → 继续
}
```

**这样至少不会卡死**，代价是板子可能不回到预期位置（要告警）。

### 对策 4：跨岛也一样

**注意**：形态 1 不限于同一台设备。

```
实验 1：A 岛取板 → 搬到 B 岛执行 → 要回 A 岛
实验 2：A 岛那个位置被占
```

**对策一样**：取板时预留回程位置。

### 对策 5：死锁检测（兜底）

**上面都是预防**。如果还是卡住了，需要**检测 + 打破**：

```sql
-- 找出"占了位置但很久没动"的执行
SELECT ps.reserved_by_run, r.status,
       EXTRACT(EPOCH FROM (now() - ps.reserved_until)) AS 超时秒
FROM position_state ps JOIN run r ON r.id = ps.reserved_by_run
WHERE ps.reserved_by_run IS NOT NULL
  AND ps.reserved_until < now()
  AND r.status = 'running';
```

**告警**：发现这种就推一条"疑似死锁"，让人处理。

**不要自动释放**——可能板子真在机械臂上，自动释放会更乱。

## 四、当前代码的实际风险

### 已防护

| 场景 | 防护 |
|---|---|
| 两块板放同一位置 | 位置锁（原子抢占） |
| 一次搬两个位置 | `tryReserveTransfer` 按 id 升序（防循环等待） |
| 两个执行命令同一台设备 | 设备锁 |
| 变量串扰 | ThreadLocal（已修） |

### 未防护（真实风险）

| 场景 | 后果 | 严重度 |
|---|---|---|
| **回程位置被占** | 执行卡在最后一步 | 🔴 高 |
| **跨步骤的循环等待** | 两个执行互相等 | 🟠 中 |
| **TTL 到期误释放** | 板子位置被抢，数据不一致 | 🟠 中 |

## 五、实施建议

| 顺序 | 任务 | 估时 | 影响 |
|---|---|---|---|
| 1 | **节点参数加 `returnTo`** | 1 天 | 让流程能声明回程位置 |
| 2 | **取板时双锁（source + returnTo）** | 1 天 | 根治形态 1 |
| 3 | **TTL 按流程时长动态算** | 0.5 天 | 防长流程中途失效 |
| 4 | **死锁检测 + 告警** | 1 天 | 兜底，不自动处理 |
| 5 | 抢不到时找替代位置 | 2 天 | 降级方案（可选） |

**第 1、2 项是核心**，做完形态 1 就没了。

## 六、一个取舍要说明

**预留回程位置会降低并发**：

```
实验 1 占着 A 的出板位 + 回程位 = 占两个位置
  → 实验 2 能用的位置少了一个
```

**这是必要的代价**——不预留就会死锁，死锁的代价更大（要人介入）。

**如果确实要极限并发**：可以让流程显式声明"不预留"（`reserveReturn: false`），
**由编排的人自己承担风险**。默认开启。

---

## 七、一句话总结

**你指出的死锁是真的**，根因不是"锁没生效"，是**"锁的语义不够"**：
位置锁只管"此刻有没有板"，不管"这块板将来回哪"。

**解法**：取板时**同时预留回程位置**（一次双锁），
TTL 按流程时长动态算，再加死锁检测兜底。

**这不是加个锁能解决的，是流程语义要补一个字段**（`returnTo`）。
