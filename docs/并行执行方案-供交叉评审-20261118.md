# LabOS 并行执行方案（交叉评审稿）

- 日期：2026-11-18
- 性质：设计稿，**未实施**。供其他 AI / 工程师交叉评审
- 评审目标：找出方案缺陷、遗漏场景、不可实施处
- 证据标注：`[事实]` 已核对源码或表结构；`[设计]` 提案；`[未定]` 需裁决

---

## 0. 一句话

把"同流程串行 + 流程级互斥"改为**资源驱动的并行调度**：只要设备、点位、机械臂不冲突，就允许并行执行；冲突则排队而不是拒绝。

---

## 1. 现状与问题

### 1.1 现在怎么跑 `[事实]`

**批次是串行的。** `BatchOrchestrator.runAll` 是一个同步 for 循环：

```
POST /experiments/{id}/run
  for (每一批) {
      检查现场扣留（不满足则 break）
      executeBatch(批)        ← 同步阻塞，跑完才回来
      若该批 paused/aborted 则 break
  }
  全部跑完才返回 HTTP
```

**流程是互斥的。** `WorkflowRunGate.check` 按 `(tenant_id, workflow_id)` 判断：若已存在 active run（queued/running/paused/quarantined）则拒绝新启动。

**事件是全局单次消费的。** `device_event.dispatched_at` 一旦置位即不可再被消费；`device_event_consumption.event_id` 是主键。

### 1.2 代价

| 场景 | 当前耗时 | 理论并行耗时 |
|---|---|---|
| 4 批，4 套设备 | 4 批之和 | 约 1 批 |
| 4 批，2 套设备 | 4 批之和 | 约 2 批 |
| 两个实验共用同一流程定义 | **串行**（被门禁挡住） | 资源允许即可并行 |

第三行是纯粹的效率损失：两个实验用同一个流程定义（比如都走"核酸提取"），业务上毫无关系，却被门禁当成冲突。

### 1.3 为什么不能简单"开并行"

三个硬约束：

1. **同步阻塞**：`runAll` 在 HTTP 线程里跑完所有批，开并行也没地方并发。
2. **事件抢不到**：`__awaitEvent` 的等待条件只有"设备码 + 事件类型"，没有板号/批次维度；两个 run 等同一设备同一事件时，只有一个能消费，另一个等到超时。
3. **线程池固定 4 个**：`RUN_POOL` 是固定 4 线程池，并行 4 批就占满，会饿死其他流程。

## 2. 目标与非目标

### 2.1 目标 `[设计]`

1. **同一实验的多个批次**可并行（受设备数量限制）。
2. **不同实验**可并行，即使它们共用同一个流程定义。
3. **并行判据是资源，不是流程 ID**：设备、点位、机械臂、耗材不冲突即可运行。
4. **资源不足时排队**，不拒绝、不报错。
5. 串行行为可通过配置回退（默认保守）。

### 2.2 非目标

- 不做跨实验室/跨岛的全局调度（岛边界仍存在）。
- 不做抢占：已开始的批不会被后来者打断。
- 不改设备的物理串行性：一台设备同一时刻只服务一个 run。
- 不做自动重排（失败批的续跑仍由人触发或既有策略决定）。

## 3. 并行模型

### 3.1 调度单元

统一为 **run**。无论来源是"批次执行""单流程启动""子实验"，都转成"待执行 run 请求 + 资源需求"。

```
待执行队列（按优先级 + 提交时间排序）
  ├─ run 请求 A：{ 能力: 提取, 点位数: 2, 需要机械臂: 是 }
  ├─ run 请求 B：{ 能力: 扩增, 点位数: 1, 需要机械臂: 否 }
  └─ ...
```

### 3.2 资源模型 `[事实 + 设计]`

现有资源分四类：

| 资源 | 现有机制 `[事实]` | 并行时要补 |
|---|---|---|
| 设备实例 | `DeviceLock`（条件更新 `current_run_id`） | 缺口：何时抢、何时放已有，但**等事件的节点不持锁** |
| 点位 | `PositionLock` + 点位绑定 | 需支持"按批次分配不同点位" |
| 机械臂 | `RailZoneGuard`（分区锁） | 无需改，串行是物理事实 |
| 岛 | 岛锁已废弃（D101） | 无需恢复 |

### 3.3 冲突判定 `[设计]`

一个 run 能否立即执行，取决于：

```
可执行 = 所需能力都有空闲设备实例
       ∧ 所需点位都未被占用
       ∧ （若需要机械臂）当前无其他 run 持有该分区
```

**关键取舍**：不做"一次性占全部资源"，而是**逐节点抢放**（沿用现有 `onStepStart` 抢、`onStepDone` 放）。理由：

- 实验室流程常有长时等待（孵育 30 分钟），一次性占全会让设备空转。
- 逐节点抢放会让利用率更高，但引入死锁风险。

**死锁风险是本方案的最大技术难点**，见 §10。

### 3.4 排队与优先级 `[设计]`

| 情形 | 处理 |
|---|---|
| 资源暂时不足 | 进入等待队列，定期重试（指数退避） |
| 资源永久不足（如需要 4 台但只有 2 台） | 提交时预检拒绝，给明确原因 |
| 等待超时 | 按策略转 `paused_waiting_resource`，不静默失败 |

优先级来源：`run.priority`（1 最高 9 最低，表里已有 `[事实]`）+ 同级 FIFO。

### 3.5 并行度上限 `[设计]`

三层取最小：

```
实际并行度 = min(
    全局上限（防线程/内存耗尽，默认 4）,
    每实验上限（可选，防一个实验吃满）,
    物理可用资源数
)
```

**默认建议：全局上限 4、每实验上限 2**，由实验配置显式放大。理由：现场设备通常 2–4 套，默认值应与物理现实匹配。

## 4. 事件归属（本方案最关键的一环）

### 4.1 问题 `[事实]`

```sql
-- 一个事件全局只能被消费一次
device_event.dispatched_at   timestamptz  -- NULL = 未消费，置位后不可再消费
device_event_consumption(event_id BIGINT PRIMARY KEY, ...)

-- 等待条件只有三个参数
__awaitEvent { device: 设备码, eventType: 事件类型, timeout: 秒 }
```

若两个 run 等同一台设备的同一个事件，只有一个能消费，另一个必死等。

### 4.2 方案 `[设计]`

**原则：一个物理事件只被消费一次，但消费权归属"当前持有该设备锁的 run"。**

```
run A 抢到 P_AUTO-3 的设备锁
  → 进入 __awaitEvent，此时持有锁
  → 事件到达，只有持锁者能消费
  → 消费后释放锁
run B 在等锁
  → 拿到锁后才开始等下一个事件
```

### 4.3 需要改的地方 `[设计]`

| 改动 | 原因 |
|---|---|
| `__awaitEvent` 执行前必须持有目标设备锁 | 现在是内置节点，不走 `StepExecutor`，**不经过 `onStepStart`，因此不持锁** `[待确认]` |
| 事件消费时校验"调用方是否为该设备当前持有者" | 防止非持有者抢消费 |
| 事件 `payload` 里记录板号/批次（若设备支持） | 用于兜底校验，非必须 |

### 4.4 为什么不改成"事件广播"

有人会提议把 `event_id` 主键改成 `(event_id, run_id)`，让多个 run 各消费一次。**不采用**，原因：

- 一个物理事件（"P_AUTO-3 提取完成"）对应的是**一块具体的板**，被另一个 run 消费会导致错误的流程推进。
- 广播会掩盖"等待条件不精确"这个真问题。

## 5. 互斥与唯一约束

### 5.1 从"流程级"降到"批次尝试级" `[设计]`

现在的 `(tenant, workflow)` 互斥是错的：它挡住的正是合法并行。

建议改为：

```sql
-- 同一批次同一时刻只能有一个活跃尝试
ALTER TABLE experiment_batch_run ADD COLUMN active_slot smallint
  GENERATED ALWAYS AS (
    CASE WHEN status IN ('queued','running','paused') THEN 1 END
  ) STORED;

CREATE UNIQUE INDEX uk_batch_run_active
  ON experiment_batch_run (tenant_id, batch_id, active_slot);
```

### 5.2 流程级互斥怎么处理 `[未定]`

三个选项，需要评审裁决：

| 选项 | 说明 | 风险 |
|---|---|---|
| A. 完全去掉 | 只靠资源锁 | 同一流程的两个 run 可能同时等同一设备（已有事件归属兜底） |
| B. 降级为"软限制" | 超过 N 个同流程并行时告警，不拒绝 | 需要定义 N |
| C. 保留但默认关闭 | `LABOS_WORKFLOW_EXCLUSIVE=0` 默认关 | 运维需理解开关 |

**我倾向 A**：资源锁 + 事件归属已经把真正的冲突管住了，再加流程级互斥是重复保护，代价是挡住合法并行。

## 6. 失败、暂停、恢复语义

| 场景 | 串行时 `[事实]` | 并行时应改为 `[设计]` |
|---|---|---|
| 某批失败 | `break`：后续批不跑 | 继续跑其他批；失败批可单独重跑 |
| 某批暂停/扣留 | `break`：后续批不启动 | 未启动的批不启动；已在跑的跑到节点边界停 |
| 实验状态 | 单批完成即同步（D6 聚合） | 严格按聚合规则，禁止"一批完成=整单完成" |
| 人工停止 | 停当前批 | 需明确：只停这一批，还是停整个实验的所有批 |
| 资源等待超时 | 不存在（串行不排队） | 转 `paused_waiting_resource`，人工介入 |

## 7. 与实验/批次/执行树的关系 `[事实]`

```
experiment（实验，含 N 个样本）
  └ experiment_batch（批次，按 batch_split 切分）
      └ experiment_batch_run（批次尝试，attempt_no 递增）
          └ experiment_run（批次的一次执行记录）
              └ run（流程执行，run_type 区分类型，parent_run_id 形成树）
```

并行发生在 **run 层**。批次只是"一次提交多个 run"的来源之一。

注意：`experiment_run` 与 `run` 是两张表，无外键关系，属于历史重复建模。本方案不要求合并，但需明确"并行度按 run 计，不按 experiment_run 计"。

## 8. 实施步骤（每步可独立上线）

| 步 | 内容 | 行为变化 | 回滚 |
|---|---|---|---|
| 1 | `runAll` 拆成"提交 + 异步执行"，并行度固定 1 | 无（纯重构） | 直接回退 |
| 2 | 引入槽位调度，打开并行度 2 | 批次可并行 | 配置改回 1 |
| 3 | `__awaitEvent` 前置设备锁 + 消费校验 | 同设备共享不再死等 | 关配置 |
| 4 | 互斥粒度降到 batch_run | 同流程多实验可并行 | 保留旧约束一段时间 |
| 5 | 失败隔离、暂停语义、优先级 | 失败不再全停 | 按步回退 |

**第 1 步必须先做**：它是纯重构，行为完全不变，是后续所有工作的地基。

## 10. 风险与未决问题

### 10.1 死锁（最大技术风险）

逐节点抢放（§3.3）意味着一个 run 可能持有 A 等 B，另一个持有 B 等 A。

现有基础 `[事实]`：

- `PositionLock` 的双锁按 id 升序申请（缓解循环等待）
- 等待图检环（D109/D114）**设计完成但未实现**

**未决**：并行度提高后，死锁概率是否显著上升？是否必须先实现等待图？

### 10.2 线程池容量

`RUN_POOL` 固定 4 线程 `[事实]`。并行度 4 就占满。

**未决**：扩大现有池，还是给批次单开一个池？扩大会影响所有流程的内存与连接占用。

### 10.3 实验状态聚合的中间态

并行时会出现"批 1 completed、批 2 running"，聚合规则能给出正确状态，但 UI 可能显示为"实验 running"让人误以为全部在跑。

**未决**：是否需要在实验层显示"已完成 1/4 批"。

### 10.4 资源饿死

多个实验长期竞争资源时，低优先级实验可能永远排不上。

**未决**：是否需要老化（等待越久优先级越高）。

### 10.5 事件归属的实现位置

`__awaitEvent` 是 `GraphRunner` 的内置节点，设备锁在 `PersistingStepSink.onStepStart` 抢。两者不在同一层。

**未决**：在 `GraphRunner` 内抢锁，还是把等待节点下沉到 `StepExecutor`？
