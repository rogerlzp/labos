# 自查清单

> **由来**：2026-11-02 连续三轮评审，我犯的错**不是若干个独立 bug，而是同一个元问题**——
>
> **把「我没找到」当成「不存在」，把「大概是这样」当成「实测」。**
>
> 写在文档里的规范（"所有断言必须可逆向验证"）没有拦住我，
> 因为它要求"自觉"。这份清单把它变成**可勾选的动作**。

---

## 怎么用

按场景勾选，**没勾完不提交**。每条都给了「动作」和「反例」——
反例都是我自己踩过的，不是假想。

---

## A. 搜索类（在说"没有/不存在"之前）

| # | 动作 | 判定标准 |
|---|---|---|
| A1 | 先列**问题可能出现的全部文件类型**：`.java` / `.sql` / `.ts` / `.tsx` / `.sh` / `.md` / `.yml` / `.xml` | 写在便签上，不是脑子里过 |
| A2 | grep **不要随手加 `--include`**；要加就加全 | 命令里能看到覆盖的类型 |
| A3 | 确认没有排除目录（`out/`、`node_modules/`、`dist/`、`.git/`） | 命令里无 `-exclude-dir` 或已知例外 |
| A4 | 结论写「**在 X/Y/Z 范围内** 0 命中」，**不写「不存在」** | 结论句里带范围 |
| A5 | **反例验证**：故意搜一个已知存在的字符串，确认命令真能搜到 | 该字符串有命中，才证明搜索有效 |

**踩过的坑**

| 时间 | 我的操作 | 实际 |
|---|---|---|
| 20261102-03 | `grep -rn "ROLE1" --include=*.java` → 0 命中 → 判"P0-11 不存在" | 问题在 `95_seed_data.sql`，**缺陷真实存在** |
| 更早 | `grep wireName` 排除 `out/` → 判"没有 wireName" | 有，只是被排除了 |

> **A5 是最关键的一条**：没有反例验证的"0 命中"，等于没搜。

## B. 数字类（在写任何数量之前）

| # | 动作 | 判定标准 |
|---|---|---|
| B1 | 每个数字**后面附命令 + 输出**（或至少把命令写进文档） | 读者能复制命令复现 |
| B2 | 同一指标在多份文档出现时，**只在一处定义，其余引用** | 不出现两个不同值 |
| B3 | 交付前重跑一遍：`git rev-list --count`、`wc -l`、`git diff --shortstat` | 与文档一致 |
| B4 | 文档里两处写同一指标时，**交叉核对** | 一处改了两处都改 |
| **B5** | **改数字时必须重新跑一次命令**，不能凭"我记得实测过"填 | 有当次输出 |
| **B6** | 数字旁标注**测量时点**（如"写本节时点 20，此后 +1"） | 避免写完又变造成的假错 |

**踩过的坑**

| 时间 | 我写的 | 实测 |
|---|---|---|
| 20261102-02 | 审核包表格行数「逐行虚报」 | 按 `wc -l` 差很多 |
| 20261102-04 | 提交 12 / 行数 527 / 文件 172 | 提交 **19** / 源码 **1052** / 文件 **185** |
| 20261102-04 | §三 单测 106、§11.4 单测 104 | **106** |

> **根因**：凭印象写。**"我记得大概二十个提交" 是幻觉的高发区。**

## C. 改代码类（改之前 / 改之后）

| # | 动作 | 判定标准 |
|---|---|---|
| C1 | 改判定逻辑前，**搜同一语义的所有实现** | `grep` 关键条件片段，列出全部命中点 |
| C2 | 改完后 `grep` **旧逻辑的特征片段**，确认无遗漏 | 旧片段 0 命中（或在注释里） |
| C3 | 改接口/构造时，搜**所有调用点**，确认没有留 `null` 装配 | 调用点逐个看过 |
| C4 | "修完" = **调用链通了 + 能验证**，不是"改了代码" | 能指出谁调用它 |
| C5 | 删死代码前先 `grep` 确认无调用者 | 只剩定义本身 |

**踩过的坑**

| 问题 | 我的处置 | 后果 |
|---|---|---|
| P1-4 位置预约 | 改了 `tryReserve`，**没改 `firstAvailablePosition`** | 同语义两套判定 → 选出来的位子永远抢不到 |
| P0-4 自动恢复 | `autoResumeFaulted()` 写好了，**没有调用者** | 设备恢复了流程也不动 |
| P1-10 板位三态 | `markPlateUnknown()` 写好了，**没有调用者** | 板丢了系统还以为在源位 |
| P1-1 资源保护 | 装配时 `db=null` | **四层资源保护全程未生效** |

> **C4 是这四条的共同教训：写完 ≠ 接上，接上 ≠ 接对，接对 ≠ 生效。**

## D. 下结论类

| # | 动作 | 判定标准 |
|---|---|---|
| D1 | 结论里的每个「不存在 / 已修 / 全部」，都要能指出**证据位置**（文件:行 或 命令输出） | 逐个点得出来 |
| D2 | 区分「**读码可得**」与「**运行验证**」，在文档里写明边界 | 有"本复核为读码级"这类声明 |
| D3 | 不把「我复核过」当证据 —— **复核过程本身要有输出** | 有命令、有输出、有对照 |

**踩过的坑**

- 复核包写「P0 18/18 全部修复」，同文件的记录里写「15 修 + 2 部分修 + 1 不存在」
  → **同一方两份文档自相矛盾**，且都用了"已修"这种模糊词。

## E. 提交前（最后一道闸）

| # | 动作 | 判定标准 |
|---|---|---|
| E1 | 全文搜「已修 / 全部 / 不存在」，逐个确认有证据 | 无空口结论 |
| E2 | 同一件事在全文是否只有**一种**说法 | 无自相矛盾 |
| E3 | 所有数字可复现 | 命令可跑 |
| E4 | commit message 里的数字与实际改动一致 | 对得上 |
| E5 | 改动范围与 commit message 描述的范围一致 | 没有夹带 |
| E6 | **不用 `git add -A`**；显式列出本次要提交的路径 | `git add <具体文件>` |
| E7 | 提交前 `git status` 逐行看过新增/删除 | 每个文件都能解释为什么在这 |

---

## 三条硬规则（如果只能记三条）

### 1. 「0 命中」不是结论，是**待验证的信号**

零命中必须先做 A5（反例验证），再写"在 X 范围内 0 命中"。
**绝不写"不存在"。**

### 2. 任何数字都要有命令输出，否则不写

凭印象写的数字，**正确率低于随机**（我三次都错）。

### 3. 「修完」的定义是**能指出调用链**

不是"我改了代码"，是"谁调用它、我怎么验证的"。
