## 2. 问题清单

### 🔴 P0-1 · `deck_in` 的 `robot_reachable` 与语义冲突

**现象**：ID-2011 的 4 个 `deck_in`（`ID-2011-WS1..4`）全部 `robot_reachable = true`、`point_role = 'both'`。

**全量分布**（`device_point` 290 行）：

```
deck_in  | role=both    | reachable=true  | n=4
deck_out | role=both    | reachable=true  | n=1
nest     | role=both    | reachable=true  | n=17
nest     | role=internal | reachable=false | n=272   ← 既有内部格惯例
```

**冲突点**：
1. 与提交说明自述的语义矛盾 —— 提交写 `deck_in=台面内工位`、`deck_out=机械臂可达交接位`；
   台面内的板应由**工作站内部机构**取放，机械臂到不了。
2. 与既有 272 个 `internal` 点位的惯例矛盾（全部 `false`）。
3. 与详细设计 §4.3.3 的表格矛盾（原文写"deck_in ⇒ `robot_reachable=false`"）。

**风险**：调度器若按 `robot_reachable=true` 派活，可能把"搬进台面内工位"派给机械臂 —— 而机械臂够不到台面内部。

**建议**：`deck_in` 的 `robot_reachable` 改 `false`。
若某 deck_in 确需机械臂可达（如台面边缘可抓取位），它就不该叫 `deck_in`，应另设 `point_kind`。
**需产品口径确认** → 已写入详细设计 §10.2 开放问题 8。

### 🔴 P0-3 · 验收清单没写"等 run 进终态再断言"

**现象**：我在 run **执行中**读 `Activity_077zr9t` 的 `resource_id` 得到 **200387**；run 完成后同一个字段变成 **200200**。

**两个坑**：
1. **中间态**：run 未进终态时，节点行的 `resource_id` 可能还是临时值 ⇒ 断言会读到假值。
2. **同一节点两行**：`run_node` 里同一节点有 **level=0 业务节点行** 和 **level=1 步骤/圈行**（本例 `S1`，`parent_node_id` 指向汇总行）。
   断言**必须指明看哪一行**，否则两条结论相反。

**建议**：验收步骤统一加前置条件 `等待 run.status ∈ {completed, failed, aborted, paused}`，并写明断言取 `level=0` 行。

### 🟡 P1-4 · resume 报错信息失真（既有行为，**非本分支引入**）

**现象**：`POST /api/runs/1001435/resume` 返回
```json
{"ok":false,"error":"Transaction rolled back because it has been marked as rollback-only"}
```
而日志里的真实原因是：
```
[暂停] 恢复后异步续跑启动失败（run 已 queued）：存在 1 个有设备派发证据的未完成节点，
禁止删除重建；请先对账（§3.6 续跑守卫）
```

**根因**（`PauseCoordinator.java:299-304`）：
```java
try { workflows.resumeAsync(cmd.targetId()); }
catch (RuntimeException ex) { log.error("[暂停] 恢复后异步续跑启动失败…", ex.getMessage()); }
```
catch 吞掉异常 ⇒ 外层事务已被标记 rollback-only ⇒ 提交时 Spring 抛 `UnexpectedRollbackException`，
**原始异常被替换**。

**影响**：操作员看到的是数据库内部措辞，完全不知道"要先对账"。
真原因只进了日志。

**归属**：`git log main..系统重构1 -- PauseCoordinator.java` 为空 ⇒ **既有行为**，不是本轮引入。

**建议**：`catch` 里把原始 message 带回响应（例如返回 409 + 原文），或对该异常用 `noRollbackFor`。
