# 动态流程能力 — 总纲

> 把最近讨论的所有能力串起来：**流程怎么"动"起来**。
> 各专题的细节见对应文档，本文件只讲**整体图景和关系**。

---

## 一、一句话图景

```
流程不只是"按顺序发命令"，它要能：
  ① 算（表达式）      —— 从变量算出新值
  ② 查（结果注入）    —— 读前面节点异步产生的结果
  ③ 等（waitFor）     —— 结果没出来就等
  ④ 分（动态分支）    —— 按结果走不同分支
  ⑤ 转（脚本，可选）  —— 复杂逻辑才用，风险最高
```

**前四项覆盖 90% 的"动态"需求，第五项是兜底。**

---

## 二、三级能力（按风险递增）

| 级别 | 能力 | 风险 | 性能 | 何时用 |
|---|---|---|---|---|
| **L1 表达式** | 算术、条件、取整、拼接 | ✅ 无 | 微秒 | 算一个值 |
| **L2 结果查询** | `waitFor` + `results.*` 注入 | ✅ 无 | 毫秒 | 等异步结果、按值分支 |
| **L3 脚本** | 上传 Java 代码，独立进程执行 | 🟠 **中** | 200-500ms | 查外部系统、复杂转换 |

### 判断标准（照着问）

```
① 能不能用已有变量算出来？
   能 → 表达式
② 是不是查本系统自己产生的结果/状态？
   是 → waitFor + 变量注入
③ 是不是查外部系统，或者做表达式做不了的转换？
   是 → 脚本（必须过审批）
```

**绝大多数情况落在 ① 和 ②。**

## 三、四层资源（并行调度的基础）

| 层 | 资源 | 粒度 | 占用时长 | 支持并发 |
|---|---|---|---|---|
| **L1 位置** | `position_state` | 一个层位 | 任务全程 | 多个位置独立 |
| **L2 通道** | `device_port` | 一个进/出口 | 动作级 | **capacity 1~N 计数** |
| **L3 门** | `device_access` | 一个可开合部件 | 动作级 | 同一门互斥 |
| **L4 机械臂** | `device_state` | 一台机器人 | 动作级 | 一次一个 |

### 为什么是四层而不是三层

**原来漏了"门"**：离心机门没开，机械臂伸进去会撞机。

**出入口也不是"1 个/设备"**：

| 形态 | 配置 | 锁 |
|---|---|---|
| 分离 | `IN-1` + `OUT-1` | 两把独立 |
| 多进多出 | `IN-1` `IN-2` `OUT-1` `OUT-2` | 四把 |
| 单一 | `BOTH` | 一把，进出互斥 |
| 宽通道 | `capacity=2` | **信号量**（同时两块） |

### 固定全序（防死锁）

```
门 → 通道 → 位置 → 回程位 → 机械臂
              ━━━━━━━━━━━━━━
              全部就绪才抓板
```

**门排最前**：门开了没抢到机械臂，可以关门放弃；
反过来板已在爪子上，没法放回去。

**"抓板"是不可逆点** —— 所有资源申请必须在它之前完成。

## 四、点位体系

### 4.1 编号是"中控与机械臂的约定"

```
{设备编号}-{类型}{序号}
ID1183-L3      多板位
ID1775-IN2     多入口
STACKER-OUT1   多出口
STACKER-S5     堆叠
```

### 4.2 编号 vs 访问顺序是两个概念

| 概念 | 字段 | 谁定 |
|---|---|---|
| **编号** | `code` | 编排/同步时生成 |
| **访问顺序** | `order_in_device` | **现场示教确定** |

**用户明确**："L1 现在定不了，不同位置要到现场去定"。

**所以系统不假设** `L1` 是底层还是外层，**全部现场配**。

### 4.3 点位属性（15 个字段）

关键几个：

| 属性 | 作用 |
|---|---|
| `port_id` | 走哪个通道 |
| `position_id` | 对应哪个层位 |
| `access_id` | **抓板前开哪个门** |
| `approach_axis` | 从哪个方向伸进去 |
| `safe_z_offset` | 横移前抬多高 |
| `order_in_device` | 机械臂访问顺序 |
| `fill_status` | `ok` 才能用于调度 |

### 4.4 流程里怎么生成点位

```json
{ "nodeType": "loop", "varName": "i", "from": 1, "to": 8,
  "body": [{ "method": "Transfer",
             "params": { "target": "ID1183-L${i}" } }] }
```

**循环 + 变量 → 动态点位**。这是用户要的核心能力。

## 五、异步结果查询

### 5.1 存

```sql
run_result (run_id, result_key, payload jsonb, source, created_at)
```

### 5.2 注入

```
results.readPlate.od        = 0.65
results.readPlate.__exists  = true
```

### 5.3 等

```json
{ "waitFor": { "results": ["readPlate"], "timeoutMs": 600000,
               "pollMs": 2000, "onTimeout": "pause" } }
```

**等待时必须释放机械臂/通道/位置**，否则卡死整个岛。

### 5.4 用

```json
{ "condition": "${results.readPlate.od > 0.5}" }
```

## 六、实验室画像（配置决定架构）

| 配置 | 决定什么 |
|---|---|
| **`max_parallel`** | **1 → 只需设备锁；2 → +returnTo；3+ → 四层资源+死锁检测** |
| `objective` | 吞吐 / 时效 / 公平 |
| `unknown_policy` | 板位未知时全停 / 只停相关 / 继续 |
| `night_mode` | 夜间无人时 UNKNOWN 自动降级 |
| `retry` | 重试上限（GxP 不自动重试） |
| `audit` | 命令级 / 只存错误 / 不存 |

**模板覆盖 80% 场景**：高通量 / 医学检验 / 教学 / GxP。

| 现状 | 要改什么 |
|---|---|
| `substVars` 纯替换 | **改成表达式求值** |
| `output` 配置（提取变量） | **改成写 `run_result` + 注入** |

| `robot_point` 6 字段 | **补 9 个 + `fill_status`** |

- 画布的循环列

## 八、实施路线（M1 拆细）

| 阶段 | 内容 | 估时 | 可独立验证 |
|---|---|---|---|
| **M1.1** | **表达式引擎** | 2.5 天 | ✅ 单测 |
| **M1.2** | 建表：`run_result` / `device_port` / `device_port_usage` / `device_access` / `robot_point` 补字段 / `device_point_template` | 1.5 天 | ✅ 建表脚本 |
| **M1.3** | **变量注入 + waitFor** | 3 天 | ✅ 造两条 run 验证 |
| **M1.4** | **资源获取协议**（门→通道→位置→回程→机械臂） | 3 天 | ✅ 门未开拒绝 |
| **M1.5** | **点位变量替换 + 循环展开** | 2 天 | ✅ `ID1183-L${i}` 展开 |
| **M1.6** | 端到端验收（5 场景） | 2 天 | ✅ |
| **合计** | | **14 天（2.1 周）** | |

### 为什么这个顺序

```
M1.1 最独立（纯计算，无依赖）→ 先做，能立刻验证
M1.2 是数据基础  → 二做
M1.3 依赖 1 和 2  → 三做
M1.4 依赖 2      → 四做
M1.5 依赖 1 和 2 → 五做
M1.6 全部依赖    → 最后
```

## 九、明确不做（避免范围蔓延）

| 不做 | 为什么 |
|---|---|
| **完整银行家算法** | 要求预知最大需求，流程有分支做不到 |
| **脚本节点（L3）** | 风险最高、3 周工程量，有明确需求再做 |
| **自动选空位** | 依赖设备实时配合，不一定可靠；流程用循环+变量更稳 |
| **抢占资源** | 板可能在机械臂上，抢占会砸板 |
| **`L1` 的物理含义** | 系统不假设，现场配 `order_in_device` |

## 十、待确认（不阻塞开工）

| # | 问题 | 影响 |
|---|---|---|
| 1 | 门的状态**靠动作推断**够不够？（还是需要查询接口） | 影响 M1.4 |

**都不阻塞 M1.1-M1.3**（表达式、建表、变量注入）。

---

## 十一、一句话

**流程要"动"起来，靠四级手段：算（表达式）、查（结果注入）、等（waitFor）、分（分支）。**

**这四级覆盖 90% 需求，且都是"零风险"的。**

**脚本是兜底，风险最高，有明确需求再说。**

**资源模型是四层（多加了"门"），点位编号是约定（顺序现场配）。**
