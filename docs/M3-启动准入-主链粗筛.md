# M3：启动准入（主链粗筛）

> 一键验收：`./scripts/verify-m3.sh`
> **结果：9 项通过 / 0 失败**

---

## 一、解决什么问题

纯等待图只能"**跑到一半才发现抢不到**"：

```
用户点启动 → 系统接受 → 跑 5 分钟 → 卡在抢设备上 → 一直等
```

用户体验是"**点了没反应**"。

**粗筛在启动时就算一遍**：

```json
GET /api/workflows/239/can-start

{
  "canStart": false,
  "strategy": "heaviest-devices",
  "reason": "资源不足：INCUBATE（空闲 0/48）",
  "estimatedWaitSeconds": 59,
  "blocking": [
    { "runId": 205172, "runNo": "M3-VERIFY-OCC",
      "deviceCode": "ID1183", "etaSeconds": 59 }
  ],
  "needDeviceCount": 1,
  "totalEstimateSec": 20
}
```

## 二、主链：为什么要"挑一条路"

**银行家算法要求"执行前声明最多需要多少资源"**，但流程有分支，声明不出来
（见 `docs/为什么不用银行家算法.md`）。

**折中**：**只按主链算**。主链是一条确定的路径，需求确定。

若实际走了非主链、资源不够 → 由**细管**（等待图）兜底 → 最多"等很久"，**不会死锁**。

### 三种选法（按优先级）

| # | 策略 | 谁定 | 适用 |
|---|---|---|---|
| 1 | **人工标记** | 编排时在网关上配 `params.mainPath` | 只有编排的人知道业务上哪条是常态 |
| 2 | **资源最重** | 自动：选用到设备最多的分支 | 偏保守，不会"筛过了但实际不够" |
| 3 | **节点最多** | 兜底 | 只为让算法有确定结果 |

实测 239 走的是 `heaviest-devices`（没有人工标记）。

## 三、⚠ 资源单元是"能力"不是"设备实例"

**这是最关键的一个修正。**

**最初按 `params.equipment_instance_id` 算**，结果：

```
占用 ID1183 → canStart 仍然是 true
```

**原因**：

| 事实 | 说明 |
|---|---|
| `equipment_instance_id=155` | **历史脏数据**，在 `device_instance` 表里根本不存在 |
| 实际执行怎么选设备 | **按能力从池子里选**（`capability_id`） |
| `INCUBATE` 有多少台 | **48 台** |

**所以按"实例"算完全错了。**

**改成按能力**：

```sql
SELECT c.code, count(di.id) AS total,
       count(*) FILTER (WHERE ds.current_run_id IS NULL) AS free_cnt
FROM capability c
LEFT JOIN resource_capability rc ON rc.capability_id = c.id
LEFT JOIN device_instance di ON di.resource_id = rc.resource_id ...
LEFT JOIN device_state ds ON ds.resource_id = di.resource_id ...
WHERE c.tenant_id = ? AND c.id = ?
GROUP BY c.code
```

**判据**：`free >= needCount` 才能启动。

### 同一能力出现多次按 1 台算

**顺序执行可以复用同一台设备**。

只有**并行网关**才真正同时需要多台 —— 那种情况由细管兜底。

## 四、验收结果

```
── ① 空闲时允许启动 ──
  ✅ canStart=true
  ✅ 主链策略可解释：heaviest-devices
  ✅ 需求设备数：1
  ✅ 预估总时长：20s

── ② 占用一台不影响（池子里还有很多） ──
  ✅ INCUBATE 共 48 台，占 1 台仍允许

── ③ 全占满则拒绝 ──
  ✅ canStart=false
  ✅ 拒绝信息完整（reason + blocking + 等待估算）
    reason: 资源不足：INCUBATE（空闲 0/48）
    blocking: 20 个
    首个占用: ID1183 runNo=M3-VERIFY-OCC eta=59s

── ⑤ 清理后恢复 ──
  ✅ 清理后回到允许启动
  ✅ 没有残留占用

通过 9 / 失败 0
```

**② 和 ③ 的对比说明了核心**：
- 48 台占 1 台 → **允许**（还有 47 台）
- 48 台全占 → **拒绝**（0 台空闲）

**这才是真实语义** —— 不是"这台设备被占了就不能跑"。

## 五、代码结构

| 类 | 职责 |
|---|---|
| `workflow/MainPathSelector` | 从图里选主链，输出**能力需求** |
| `workflow/AdmissionController` | 按能力查池子、判够不够、给拒绝理由 |
| `ApiServer.canStartJson` | `GET /api/workflows/{id}/can-start` |

### 主链选择的实现

```
从 start 节点 DFS 到 end，收集所有路径（上限 200 条，防指数爆炸）
  ↓
① 有 mainPath 标记且路径符合 → 用它
② 否则选"用到设备最多"的
③ 并列时选"节点最多"的
```

## 六、estimatedWaitSeconds 不准

**它用 `run_node.estimate_sec - 已跑秒数` 算**。

**时长预估本来就准不了** —— 界面上要标"**仅供参考**"。

**为什么还是给**：有比没有好。用户看到"约 59 秒"总比"不知道要等多久"强。

---

## 七、粗筛错了会怎样

| 情况 | 后果 |
|---|---|
| 粗筛说"能启动"，实际走了非主链、资源不够 | **等很久**（细管兜底，不死锁） |
| 粗筛说"不能启动"，实际资源够 | **误拒**，用户重试一次 |

**都不会导致死锁** —— 这是"粗筛可以错，细管不能错"的分工。

---

## 八、踩的坑

| 坑 | 根因 | 修法 |
|---|---|---|
| 按设备实例算完全失效 | `equipment_instance_id=155` 是脏数据，实际按能力选 | 改成按 capability 查池子 |
| `device_instance_state` 表不存在 | 我编的表名 | 用 `device_state.current_method` |
| `run_node.node_id` 不存在 | 实际是 `node_key` | 改用 `run_node.estimate_sec` |
| `resource_capability` 没有 `tenant_id` | 表结构如此 | 去掉这个条件 |
| 脚本 `OCC_RID` 是非法数字 | `psql -tAc` 把 `INSERT 0 1` 也输出了 | `head -1 \| tr -d '[:space:]'` |

**第 1 条最重要** —— 它说明"看代码以为按实例、实际按能力"这种**隐性契约**，
光读代码看不出来，必须对着数据验。

## 九、和 M1/M2 的关系

```
M3 粗筛（启动前）    → 判断能不能启动，给理由
M1 资源协议（执行中） → 固定全序申请，失败回滚
M2 等待图（执行中）   → 成环拒绝，保证不死锁
```

**三层配合**：
- 粗筛负责"**体验**"（点了有反馈）
- 细管负责"**正确性**"（不死锁）
