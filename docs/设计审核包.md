## 二、需要评审的核心判断（按风险排序）

### 🔴 风险 1：三层资源模型够不够

**主张**：资源分三层就够

| 层 | 资源 | 共享性 | 占用时长 |
|---|---|---|---|
| L1 | 每个层位 | 独立 | 任务全程 |
| L2 | 每设备的出入口 | 共享 | 动作级（几秒） |
| L3 | 机械臂 | 共享 | 动作级（2-5 秒） |

**理由**：用这三层能解释"两块板同时进 B 的不同位置"和"A→B→C→A 环"。

**希望挑战**：
- 还有没有第四层？（比如"机械臂的姿态空间"？两台机械臂会不会在空中打架？）
- "动作级"的边界怎么定？`Transfer` 是一次动作，还是"抓-移-放"三次？
- 如果设备有"前处理位"和"后处理位"两个入口，L2 是一把锁还是两把？

### 🔴 风险 2：等待图 vs 银行家算法

**主张**：用等待图（只检测环），不用完整银行家算法

**理由**：银行家要求"预知最大需求"，但流程有分支、时长不准，这个前提不成立。

**希望挑战**：
- 等待图的"误拒"会有多严重？会不会导致某些流程永远抢不到？
- 有没有可能"等待图无环但实际死锁"？（比如资源在动作中途被占）
- 用户明确要"完整的银行家算法"，用等待图替代是否偏离了需求？

### 🔴 风险 3：银行家算法"不可抢占"的约束

**主张**：安全检测只管"新申请"，不能中断"已占着在用的"

**理由**：孵育到一半停了会毁样本，机械臂搬一半停了板会掉。

**希望挑战**：
- 这个约束是否让"银行家算法"失去意义？（因为它假设可抢占）
- 如果保留这个约束，还有没有必要叫"银行家"？
- 有没有"半抢占"的方案？（比如只在安全点抢占）

### 🟠 风险 4：暂停只在动作边界

**主张**：动作执行期间不响应暂停

**代价**：暂停延迟 = 当前动作剩余时间，最长 30 分钟（孵育）

**希望挑战**：
- 30 分钟的暂停延迟在实际运维中可接受吗？
- 有没有办法缩短？（比如孵育拆成"放入-等待-取出"三个动作，等的时候可以暂停？）

### 🟠 风险 5：板位 UNKNOWN 必须人工盘点

**主张**：搬运异常后，板位置标记 UNKNOWN，必须人工确认，系统不猜

**理由**：板可能掉地上、可能被人拿走，任何假设都可能错。

**希望挑战**：
- 这个策略会不会让运维负担太重？（每次异常都要盘点）
- 有没有"低成本确认"的方式？（比如让机械臂回原点后拍照？）

### 🟡 风险 6：`returnTo` 默认等于 source

**主张**：不配 `returnTo` 时默认"从哪来回哪去"

**希望挑战**：
- 如果流程是"出板 → 执行 → 放到另一个位置"，默认 source 就错了
- 是否应该强制要求配置（不给默认）？

### 🟡 风险 7：单实验关闭检测的开关

**主张**：`running > 1` 才启用死锁检测

**希望挑战**：
- 一个实验内部的并行节点是否也需要检测？（原设计里 `hasParallelNode` 只是可选项）
- 用 COUNT 判断有竞态吗？（正好在边界时两个都以为自己是"唯一"）

## 五、怎么快速判断设计有没有明显漏洞

### 用三个场景自测

**场景 A：两块板同时进多板位设备**

```
B 有 3 个内部位置，1 个出入口
流程1：板1 进 B 位置1
流程2：板2 进 B 位置2
```

**设计说**：可以并行（L1 独立，L2 排队几秒）。

**要验证**：L2"动作级"到底多长？如果一次进板要 30 秒，流程2 就要等 30 秒——这还算"并行"吗？

**场景 B：3 个流程走环**

```
流程1：A→B→C→A
流程2：B→C→A→B
流程3：C→A→B→C
```

**设计说**：等待图检测到环，第三个被拒，前两个能完成。

**要验证**：被拒的那个会重试，重试时会不会**反复被拒**？（活锁）

**场景 C：机械臂搬一半被急停**

```
机械臂抓着板，被物理急停
```

**设计说**：标记 UNKNOWN，人工盘点。

**要验证**：如果运维不在现场（夜间无人值守），系统会一直卡着等？

## 六、诚实说明：设计可能过度的风险

**这份设计有 1860 行，覆盖了死锁、暂停、恢复、故障、板位三态。**

**可能过度设计的信号**：

| 信号 | 说明 |
|---|---|
| **没有任何真机验证** | 所有设计基于模拟器，真机的约束可能不一样 |
| **单岛 7 台设备** | 设计按"多流程并行"做，但实际会不会真的并行 3 个以上？ |
| **运维能力未知** | "人工盘点"假设有人能盘点，如果夜间无人？ |

**如果一个岛实际上只会跑 1-2 个实验**，那这套死锁检测可能根本用不上。

**建议评审时先问**：**"这个实验室一天会并行几个实验？"**
如果答案是 1-2 个，**D109-D113 可以砍掉，只保留 D101-D104**。

## 当前要审的：并行调度实施规格

**决策已定：采用方案 C（3+ 并行，混合调度，4 周）。**

**主审文档**：`docs/并行调度-实施规格.md`

**为什么是这份**：它把分散在多份设计文档里的结论**整合成可执行规格**——
有表结构、伪代码、5 个里程碑、每个里程碑的验收标准。

### 5 个必审点（规格第十节）

| # | 问题 | 为什么重要 |
|---|---|---|
| 1 | **"动作级"边界**够明确吗？`Transfer` 是一次动作还是三次（抓/移/放）？ | 决定资源占用的时长，影响并发 |
| 2 | **固定全序**（源口→源位→目标口→目标位→回程位→机械臂）物理上合理吗？ | 如果有"必须先抢机械臂才能开柜门"的设备，这个顺序就错了 |
| 3 | **主链的"资源最重"选择**会不会总选到异常分支？ | 异常分支往往要更多设备，按它算会让粗筛过度保守 |
| 4 | **"故障时流程2 继续"**会不会因为共享机械臂而实际被阻塞？ | 设计说"只停相关"，但机械臂是共享的 |
| 5 | **M1 验收**（两块板同时进 B）真实设备可行吗？有没有"同时只能接受一块板"的物理限制？ | 这决定三层资源模型成不成立 |

### 还要确认的前置假设（规格第九节）

| # | 假设 | 不成立的后果 |
|---|---|---|
| 1 | **实验室会配 `max_parallel >= 3`** | **4 周白做** |
| 2 | 岛内设备 ≤ 20 | 影响小 |
| 3 | 流程分支 ≤ 10 | 主链选择要优化 |
| 4 | **故障时有人能到场** | UNKNOWN 长期卡死，必须开夜间模式 |

**第 1 条最关键**——如果实际只配 1-2，整套方案不该做。
