## 0. 一句话结论

**建两个部分唯一索引（partial unique index），状态集合取自 `StatusVocabulary` 的 `active=true`，不用生成列。**

> **状态：已定稿（2026-11-19）。** 三个待拍板细节已全部确认（§7：`paused` 算、`quarantined` 算、batch `pending` 保留），可以进入实施。

```sql
-- ① workflow 级：同租户同流程只允许一个活跃 run
CREATE UNIQUE INDEX uk_run_active_workflow
  ON run (tenant_id, workflow_id)
  WHERE workflow_id IS NOT NULL
    AND deleted_at IS NULL
    AND status IN ('queued','running','paused','quarantined');

-- ② batch 级：同批次只允许一个活跃 attempt
CREATE UNIQUE INDEX uk_batch_run_active
  ON experiment_batch_run (tenant_id, batch_id)
  WHERE status IN ('pending','queued','running','paused','quarantined');
```

## 1. 为什么必须是唯一索引

`I-03` 的处置是"禁止 `API-E05` 同事务内联，改事务外先准入"，时间线：

```
事务 A（准入）                    事务 B（插入 run）
────────────────────────────────────────────────
BEGIN
  SELECT ... 查无 active
COMMIT   ← 行锁 / advisory lock 全部释放
                                  BEGIN
                                    INSERT run(status='queued')
                                  COMMIT ← 唯一索引在这里检查
        ↑
   窗口：另一个请求此刻也能通过检查
```

| 候选 | 能否覆盖这个窗口 | 原因 |
|---|---|---|
| `SELECT ... FOR UPDATE` | ❌ | 行锁随事务提交释放，窗口就在提交之后 |
| `pg_advisory_xact_lock` | ❌ | 事务级锁，`_xact_` 后缀即"事务结束释放" |
| `SERIALIZABLE` | ❌ | 只保证单事务内的可串行化 |
| **唯一索引** | ✅ | 任何时刻插入都要检查约束 |

**所以 K-01a 不是"四选一"，是"必须选唯一索引"**；另外三个只是"减少冲突重试"的优化（K-01b）。

## 2. 现有代码事实

### 2.1 `run` 表

```sql
CREATE TABLE run (
  id, tenant_id, run_no, run_type, parent_run_id,
  workflow_id   bigint REFERENCES workflow(id),   -- ★ 可空
  workflow_ver  int,
  mode, priority,
  status        run_status NOT NULL DEFAULT 'pending',
  ...
  deleted_at    timestamptz,
  CONSTRAINT uk_run_no UNIQUE (tenant_id, run_no)
)
```

- `workflow_id` **可为 NULL**：`insertExperimentFlowRun`（`RunMapper.xml:1012`）就写 NULL
- `status` 是**枚举** `run_status`，不是 varchar
- 已有索引：`ix_run_status`、`ix_run_planned`、`ix_run_deadline`

### 2.2 `experiment_batch_run` 表

```sql
CREATE TABLE experiment_batch_run (
  id, tenant_id, batch_id, experiment_run_id,
  attempt_no  int NOT NULL,
  status      varchar(24) NOT NULL DEFAULT 'pending',   -- ★ 字符串，不是枚举
  ...
  CONSTRAINT uk_experiment_batch_run UNIQUE (batch_id, attempt_no)
)
```

- 已有唯一约束是 `(batch_id, attempt_no)`，管"同批同一次尝试不重复"
- **没有**"同批只允许一个活跃 attempt"的约束，现在是应用层判定

### 2.3 活跃状态的权威来源

`StatusVocabulary.SCOPE_RUN`（`StatusVocabulary.java:120-132`）：

| 状态 | `active` | 说明 |
|---|---|---|
| `draft` | false | |
| `pending` | **false** | |
| `planned` | **false** | |
| `queued` | **true** | |
| `running` | **true** | |
| `paused` | **true** | |
| `quarantined` | **true** | |
| `completed` / `failed` / `aborted` / `cancelled` / `skipped` | false | 终态 |

**关键事实**：`pending` 和 `planned` **不是活跃**。所以"pending/planned 是否构成活跃窗口"这个问题在权威定义里有答案——不构成。

（`WorkflowRunGate` 第 102 行开始就是拿 `activeStatuses()` 去查的，与上表同源。）

### 2.4 现有门禁行为

`WorkflowRunGate.check`：

```java
if (db == null || tenantId <= 0 || workflowId <= 0) {
    return Decision.allow();     // ★ workflowId <= 0 直接放行
}
```

⇒ **`workflow_id` 为 NULL / 0 的 run 完全不受门禁约束**。唯一索引必须与这个行为一致，否则 `insertExperimentFlowRun` 会撞索引。

**这就是为什么要加 `WHERE workflow_id IS NOT NULL`。**

## 3. 建议方案

### 3.1 索引一：workflow 级

```sql
CREATE UNIQUE INDEX CONCURRENTLY uk_run_active_workflow
  ON run (tenant_id, workflow_id)
  WHERE workflow_id IS NOT NULL
    AND deleted_at IS NULL
    AND status IN ('queued','running','paused','quarantined');
```

| 设计点 | 理由 |
|---|---|
| `(tenant_id, workflow_id)` | 与 `WorkflowRunGate` 的查询条件完全对齐（它按这两个字段查活跃） |
| `workflow_id IS NOT NULL` | 与门禁 `workflowId <= 0 → allow` 对齐；`insertExperimentFlowRun` 写 NULL，不受约束 |
| `deleted_at IS NULL` | 软删的行不占名额 |
| 四个状态 | 直接对应 `StatusVocabulary` 的 `active=true` |
| `CONCURRENTLY` | 建索引不锁表（生产必须） |

### 3.2 索引二：batch 级

```sql
CREATE UNIQUE INDEX CONCURRENTLY uk_batch_run_active
  ON experiment_batch_run (tenant_id, batch_id)
  WHERE status IN ('pending','queued','running','paused','quarantined');
```

| 设计点 | 理由 |
|---|---|
| **不含 `attempt_no`** | 要约束的是"同批同时只有一个活着的尝试"，不是"同批同序号唯一"（后者已有） |
| 状态含 `pending` | 这里 `status` 是 **varchar**，取值与应用层一致；`pending` 表示"已建但未开跑"，也占名额 |
| 含 `quarantined` | 隔离的 attempt 仍占着这一批，不能同时再起一个 |

**⚠ `paused` 是否包含，是 K-02 的内容，未定。** 本方案默认包含，与现有 `activeBatchAttempt` 行为一致；如果 K-02 决定不含，去掉这一个值即可，索引形态不变。

### 3.3 为什么用部分唯一索引，而不是生成列

| 方案 | 做法 | 问题 |
|---|---|---|
| 生成列 + 唯一索引 | `active_slot AS (CASE WHEN status = 'active' THEN 1 END)` 生成列 | 生成列要跟状态变更同步，且 `ALTER TABLE ADD GENERATED` 会重写表 |
| **部分唯一索引** | `WHERE status IN (...)` | **无需新增列，状态集合改了只改索引定义** |

PostgreSQL 的部分唯一索引原生支持这个场景。

---

## 4. 两个索引缺一不可

| 索引 | 拦住什么 | 缺了会怎样 |
|---|---|---|
| `uk_run_active_workflow` | 同流程两个 run 同时活 | 同流程并发跑两份，设备互相抢 |
| `uk_batch_run_active` | 同一批两个 attempt 同时活 | 同一批被重复开跑，板被搬两次 |

两个索引覆盖**不同粒度**，不是二选一。

## 5. 上线步骤（必须按序）

### 步骤 0：脚本已写好并实测

迁移文件：`pg_rebuild/migration/20261119_k01a_active_unique.sql`

执行方式：

```bash
psql -v ON_ERROR_STOP=1 -U <user> -d <db> -f 20261119_k01a_active_unique.sql
```

**实测结果（2026-11-19，PostgreSQL 17.11 临时库）**：

| 场景 | 期望 | 实际 |
|---|---|---|
| 同 workflow 第二条活跃 run | 失败 | ✅ `duplicate key ... uk_run_active_workflow` |
| `workflow_id` 为 NULL 的两条 | 成功 | ✅ 两条都插入 |
| 不同 workflow 各一条活跃 | 成功 | ✅ |
| 同 workflow 两条 `completed` | 成功 | ✅ |
| 同 batch 两条活跃 attempt | 失败 | ✅ `duplicate key ... uk_batch_run_active` |
| 已有冲突数据时重跑 | **中止并提示** | ✅ `发现 1 组 workflow 级冲突...` |

**踩到的一个坑（写文档时想不到的）**：

```sql
-- ❌ 报错：functions in index predicate must be marked IMMUTABLE
AND status::text IN ('queued', ...)

-- ✅ 正确：直接用字符串字面量与枚举比较
AND status IN ('queued', ...)
```

`enum → text` 的 cast 是 `STABLE` 不是 `IMMUTABLE`，不能出现在索引谓词里。

### 步骤 1：查现有冲突数据（不改任何东西）

```sql
-- ① workflow 级冲突
SELECT tenant_id, workflow_id, count(*), array_agg(id) AS run_ids
  FROM run
 WHERE workflow_id IS NOT NULL AND deleted_at IS NULL
   AND status IN ('queued','running','paused','quarantined')
 GROUP BY tenant_id, workflow_id
HAVING count(*) > 1;

-- ② batch 级冲突
SELECT tenant_id, batch_id, count(*), array_agg(id) AS attempt_ids
  FROM experiment_batch_run
 WHERE status IN ('pending','queued','running','paused','quarantined')
 GROUP BY tenant_id, batch_id
HAVING count(*) > 1;
```

**如果两条都返回 0 行** ⇒ 可以直接建索引。
**如果有行** ⇒ 先人工确认哪一条是真活着的，把其余的置为 `aborted`，否则建索引会失败。

### 步骤 2：建索引（`CONCURRENTLY`，不锁表）

```sql
CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS uk_run_active_workflow
  ON run (tenant_id, workflow_id)
  WHERE workflow_id IS NOT NULL AND deleted_at IS NULL
    AND status IN ('queued','running','paused','quarantined');

CREATE UNIQUE INDEX CONCURRENTLY IF NOT EXISTS uk_batch_run_active
  ON experiment_batch_run (tenant_id, batch_id)
  WHERE status IN ('pending','queued','running','paused','quarantined');
```

### 步骤 3：观察失败率

建索引后，如果应用层仍有并发路径，会开始抛 `duplicate key value violates unique constraint`。

**这不是坏事**——它说明有路径没走准入。要统计这个错误码出现的次数和调用栈，逐个补准入。

### 步骤 4：确认无新增后，再改代码

`RunAdmission` 接准入时，把"检查"当**快速失败**（给出友好错误码），唯一索引当**最后兜底**。

| ID | 场景 | 期望 |
|---|---|---|
| K-01a-1 | 两请求同时启动同一 workflow | 一个成功，另一个拿到唯一约束冲突（或准入拒绝） |

## 7. 三个细节全部已定（2026-11-19）

| 细节 | 结论 |
|---|---|
| `paused` 算活跃 | ✅ **算**（§7.1） |
| `quarantined` 算活跃 | ✅ **算**（§7.2） |
| batch 的 `pending` 保留 | ✅ **保留**（§7.3，防御性，当前不命中） |

**K-01a 至此定稿，可以建索引。**

### 7.1 `paused` 算活跃 —— **已定（2026-11-19，业务确认）**

**决策：算。** 暂停的流程**必须先恢复或终止**，才能启动新的同流程实例。

**依据**：`StatusVocabulary.SCOPE_RUN` 中 `paused` 的 `active=true`。

**业务理由**：

> 暂停 ≠ 结束。暂停的实例还占着设备、点位、板位等物理资源，也可能有在途命令。
> 在"资源已被占用、状态又不明确"的情况下再起一个同流程实例，等于重复占用。

**用户可见行为**：

```
流程 A 已暂停
用户再点"启动流程 A"
  → 拒绝：「该流程已有运行中的实例（P-2026-11-19-001，已暂停），请先恢复或终止」
  → 不是静默创建第二个
```

**实现**：唯一索引 `WHERE status IN ('queued','running','paused','quarantined')` 必须含 `paused`。

**这条不是技术选择，是产品语义**：它决定"暂停的流程能不能被绕过"。去掉 `paused` 等于承认"同流程可以多实例并行"，与 `WorkflowRunGate` 的设计前提冲突。

### 7.2 `quarantined` 算活跃 —— **已定（2026-11-19，业务确认）**

**决策：算。** 隔离的实例必须先处理完（继续或终止），才能启动新的同流程实例。

**业务理由**：

> 隔离 = "不知道物理世界什么样"。这时候放新实例进来，等于在信息缺失时继续操作物理世界。
> 最坏情况：隔离实例的板可能还在设备里，新实例又去取板 ⇒ 取空、撞机、掉板。

**代价与出口**：

| 项 | 说明 |
|---|---|
| 代价 | 隔离期间同流程不能起新实例 |
| **出口 1** | **人工确认**（页面表单）→ 板位置 + 设备可用性**一起**确认 → 恢复继续 |
| **出口 2** | 确认板丢了 / 作废 → 终止（`resumeToAborted`） |

**两条出口都释放设备。**

#### 7.2.1 人工确认是"一次动作"，不是两次

业务确认（2026-11-19）：**必须同时确认两件事，不允许分开。**

```
页面表单：
  ① 板 P-xxx 现在在哪？
     ○ 仍在离心机 C-03 内
     ○ 已到交换位 EX-02
     ○ 找不到（板丢失）

  ② 离心机 C-03 当前能否交给别人用？
     ○ 可以（腔内已清空）
     ○ 不可以（还有板）

  [确认并提交]   [终止流程]
```

| 选项组合 | 系统行为 | 设备 |
|---|---|---|
| 位置明确 + 设备可用 | `resumeToQueued` + 写 corrections | **释放** |
| 位置明确 + 设备不可用 | **不允许提交**，提示"请先清空设备" | 保持占用 |
| 找不到 | `resumeToAborted` + `EC-BOARD-LOST` | **释放**（声明作废） |

**为什么不能只确认位置**：位置知道不等于设备干净。允许分开会让用户以为"填完位置就完事"，忽略腔内可能还有残留。

**设备占用与流程名额是两件事**：

| 资源 | 隔离时 | 释放时机 |
|---|---|---|
| 流程名额（`workflow_id`） | 占用 | 隔离结束时（恢复或终止） |
| 设备锁 / 物理占用 | **占用** | **人工确认"设备可用"时** |

所以隔离的实例会**卡住那台设备**，其他流程用不了——这是正确的，因为中控确实不知道板在不在里面。

### 7.3 batch 索引的 `pending` —— 保留（防御性）

**核实结果**：`BatchMapper.xml:190-201` 的插入只写 `'queued'` 和 `'running'`，**没有任何代码写 `'pending'`**。

表的 `DEFAULT 'pending'` 是预留，所以这个值**当前不会命中**，加不加对眼下没有影响。

**保留的理由**：成本为零，防的是"以后有人写了一条不指定 status 的插入"。真出现时不占名额就会导致两条 pending 都开跑。

如果将来确认不需要，去掉它只需改索引定义，不影响数据。

## 8. 风险与回滚

| 风险 | 说明 | 缓解 |
|---|---|---|
| 建索引失败（有冲突数据） | 必须先清数据 | 步骤 1 先查 |
| 索引导致合法路径被拒 | 如果存在"同流程多 run"的既有用法 | 步骤 3 观察失败率，逐个判断 |
| `CONCURRENTLY` 失败留下无效索引 | 需要 `DROP INDEX` 重来 | `IF NOT EXISTS` + 失败后清理 |
| 软删逻辑不一致 | 如果有些路径不写 `deleted_at` | 步骤 1 的查询要包含/排除两种口径都试 |

**回滚**：`DROP INDEX CONCURRENTLY uk_run_active_workflow;` —— 删索引即恢复原行为，不影响数据。
