> **结果：12 项通过 / 0 失败**

## 一、验收什么

M1 要解决的是"**多个实验并行时，设备之间不撞**"。

五件事：

| # | 能力 | 为什么需要 |
|---|---|---|
| 1 | **方法边界** | 机械臂不该有"开门"方法，孵箱不该有"搬板"方法 |
| 2 | **门保护** | 离心机门关着，机械臂伸进去会撞机 |
| 3 | **通道信号量** | 宽通道能同时过两块板，不能按互斥锁 |
| 4 | **点位生成** | 机械臂上报自己认识的层位 |
| 5 | **失败回滚** | 开门失败要能全身而退，不能占着通道不放 |

## 三、五个场景的细节

### ① 方法边界

**验证什么**：配错设备编号时**必须立刻报错**。

```
给机械臂发 OpenDoor  → EC-06-0004
给孵箱发 Transfer    → EC-06-0004
```

**为什么不"假装成功"**：模拟器如果照单全收，
现场配错时**演示阶段正常、上真机撞机**。

### ② 门保护

**验证什么**：门关着时，Transfer 前会先调 `OpenDoor`。

**实现**：`TransferPlan.acquireAll` 的**第一步**就是开门。

```
门开了但没抢到机械臂 → 关门放弃，代价小
抢了机械臂才发现门打不开 → 板已在爪子上，没法放回去
```

**这条顺序不是随便定的。**

### ③ 通道信号量

**验证什么**：`capacity=2` 时能同时占 2 个，第 3 个失败。

```sql
UPDATE device_port_usage SET in_use = in_use + 1
WHERE port_id = ? AND in_use < max_capacity
RETURNING in_use;
```

```
第 1 次 → in_use=1  ✅
第 2 次 → in_use=2  ✅
第 3 次 → 0 行      ✅
```

**`capacity=1` 只是 `max_capacity=1` 的特例**，不用两套代码。

### ④ 点位生成

**验证什么**：机械臂 `GetPoints` 返回它认为的点位。

```
ID1731-L1  (320, 140, 45)
ID1731-L2  (320, 180, 45)
ID1731-L3  (320, 220, 45)
ID1731-L4  (320, 260, 45)
```

**注意**：模拟器返回的是**固定 4 个**。
真机上这些坐标来自示教，`order_in_device` 现场配。

### ⑤ 失败回滚

**验证什么**：开门失败后，已申请的通道要释放。

```
开门失败 → 抛 AcquireException
         → rollback() 逆序释放
         → 通道占用归零（0 → 0）✅
         → 板还在源位，可安全重试
```

## 四、过程中修的两个真问题

### 问题 1：开门命令发给了机械臂的 driver

**原代码**：
```java
AccessOpener opener = m -> driver.execute(buildCommand(ctx, deviceId, m));
//                            ↑ 机械臂的 driver
```

**一次 Transfer 涉及两台设备**，各有独立 driver。
用机械臂的 driver 开离心机的门：

| 情况 | 后果 |
|---|---|
| 机械臂没有 OpenDoor | 报 EC-06-0004，流程走不下去 |
| **机械臂恰好有同名方法** | **开错了门，看起来还成功了** |

**第二种最危险**。

**修法**：按 `resourceId` 找对应设备的 driver。

### 问题 2：模拟器没有门方法

**现象**：门状态一直是 `unknown`。

**原因**：模拟器不认识 `OpenDoor` / `CloseDoor`。

**修法**：按设备类型给方法集（`--profile`）。

## 六、开关

**资源保护默认关闭**：

```bash
LABOS_TRANSFER_PLAN=1   # 开启
```

**为什么默认关**：改动搬运核心逻辑风险大。
先让现场验证"现有流程在开关关的情况下不受影响"，再逐步打开。
