## 0. 一句话

把"批次串行 + 流程级互斥"改为**资源驱动的并行执行**，同时保证事件归属、命令幂等、断线恢复三件事在任何并行度下都是确定性的。**不新建调度器**，只修三处。

**部署前提：单实例。** 本方案不涉及多实例/主备切换，因此执行体 fencing（epoch）不在范围内（见 R-02）。若未来上多实例，须先补该机制。

## 2. 现状：五层结构与执行链路 `[事实]`

```
experiment              实验，含 N 个样本
  └ experiment_batch    批次，按 batch_split 切分（96 样本 / 24 = 4 批）
      └ experiment_batch_run   批次尝试，attempt_no 递增
          └ experiment_run     批次的一次执行记录
              └ run            流程执行，run_type 区分类型，parent_run_id 形成树
```

**当前实际行为**：

- 批次**串行**：`BatchOrchestrator.runAll` 第 383–442 行是同步 for 循环，跑完一批才下一批。
- 异步路径**存在但也是串行续队**：`ExperimentScheduler` 第 856 行 `continueNextBatch`、第 662 行 `autoContinueHeldBatches`，一批完成才建下一批。
- 流程级互斥：`WorkflowRunGate` 按 `(tenant, workflow)` 判断，已存在 active 则拒绝。
- 事件**全局单次消费**：`device_event_consumption.event_id` 是主键，`dispatched_at` 置位后不可再消费。
- 事件等待条件**只有设备码 + 事件类型**：`__awaitEvent` 参数仅 `device / eventType / timeout`（`GraphRunner.describeBuiltin` 第 319–327 行）。

**代价**：4 批 × 2 小时 = 8 小时；有 4 套设备时理论上 2 小时。

## 3. 真正要解决的四个问题

### 3.1 批次串行：一个精确的不变量 `[事实]`

`BatchOrchestrator` 第 682–687 行的注释原文：

> 锁住实验行（异步分批"取下一批"的串行化点）。
> 为什么锁实验行而不是批次行：判定"同实验是否已有批次 run 在队列/执行"是**实验级不变量**，只锁某一批挡不住两个请求同时给不同批建单。

这是有意识的设计选择，不是疏漏。改它必须先论证"这条不变量为什么不再成立"。

### 3.2 事件归属：一个死字段和两个缺失字段 `[事实]`

`claimEvent` 的候选集（`DeviceEventMapper.xml` 第 73–90 行）过滤条件：

```
e.tenant_id / e.id > afterId / e.dispatched_at IS NULL
/ NOT EXISTS(已消费) / [可选] e.device_code / [可选] e.event_type
```

**没有 `e.run_id`**。而 `device_event.run_id` 的实际状况：

| 检查项 | 结果 |
|---|---|
| 建表时是否有注释 | **没有**（`source_event_id`、`dispatched_at` 都有，唯独它没有） |
| 生产路径是否填值 | **不填**。侧车只传 `(equipmentId, eventType, payload)`（`Protocol.cs` 第 85 行） |
| 是否有业务逻辑读它 | **没有**。全仓唯一读取点是 `DeviceEventController` 第 141 行的 JSON 回显 |
| 消费归属用的是哪个 runId | `claim(runId, ...)` 传的是**消费者自己**的 runId，与事件行无关 |

**结论：这是一个死字段，应删除。**

```sql
ALTER TABLE device_event DROP COLUMN run_id;
```

它的危害不是"没用"，而是**误导**：任何后来者看到 `run_id`，都会本能地想"加个 `AND e.run_id = #{runId}` 就能做归属"——而这个改动会让所有事件永远匹配不上（因为全是 null），直接瘫痪事件机制。本轮评审中已有人（包括本文作者）踩过这个坑。

**真正需要的是两列**：

```sql
ALTER TABLE device_event ADD COLUMN command_id VARCHAR(160);
  -- 事件对应的命令 id（E1/E2 类事件有，E3 自发事件为 null）
ALTER TABLE device_event ADD COLUMN device_event_seq BIGINT;
  -- 设备侧单调递增序号，用于断线补发和跳变检测
```

- `command_id` → 解决 E1/E2（命令回包、执行中间态）的归属
- `device_event_seq` → 解决"断线期间事件丢失"
- E3（设备自发事件）没有 command_id，靠**设备占用者**归属（`device_lock.current_run_id`）

### 3.3 命令幂等：一个隐藏的耦合 `[事实]`

- `commandId` = `r{run}-n{node}-e{exec}-s{step}-d{device}`（第 1474–1478 行），其中 `exec` 每次执行递增（第 206 行）。
- 账本幂等键是**另一个** key：`r{run}|n{node}|a{attempt}|s{step}|d{device}|m{method}[|v{loop}]`（第 1209–1211 行），不含 `exec`。
- 账本已存在时直接拒绝：`EC-99-0006 禁止重复下发（需人工确认设备位置）`（第 1216–1223 行）。

**结论**：现在"不会重复执行"是靠账本挡住的；一旦放开账本允许重试，`commandId` 就会变，设备会真的执行两次。

### 3.4 跨类锁无全序 `[事实]`

| 锁 | 内部有序 | 证据 |
|---|---|---|
| 设备锁 | 数据库条件更新 + 分片锁 | `DeviceLock` 第 113、201–222 行 |
| 点位锁 | 按 resource_id 升序 | `PositionLock` 第 246 行 |
| 轨道分区锁 | `Collections.sort` | `RailZoneGuard` 第 89–90 行 |

但**三类之间没有统一顺序**。A 持设备等点位、B 持点位等设备，仍可死锁。

## 4. 设计决策

### 4.1 调度：接入现有 `ExperimentScheduler`，不新建 `[设计]`

**已有能力（不需要重做）**：

| 能力 | 位置 |
|---|---|
| 资源级互斥 | 第 26、750–757 行 |
| 优先级 / EDD / FIFO | 第 138–141 行 |
| 并行度上限 + `schedule_plan` 热加载 | 第 52、211、306–313 行 |
| 资源软预约（按 id 升序） | 第 970–980 行 |
| 独立线程池 | 第 169 行 |

**要做的**：让批次提交进入这个队列，而不是新建 `BatchScheduler`。

注意：`tryHoldResources` 是**内存 Map**（第 979 行 `synchronized (resourceHoldLock)`），重启即丢。正确性最终靠 `DeviceLock` 的数据库条件更新。

### 4.2 互斥粒度：从 workflow 降到批次尝试 `[设计]`

```sql
-- 同一批次同一时刻只能有一个活跃尝试
ALTER TABLE experiment_batch_run ADD COLUMN active_slot smallint
  GENERATED ALWAYS AS (
    CASE WHEN status IN ('queued','running','paused') THEN 1 END
  ) STORED;

CREATE UNIQUE INDEX uk_batch_run_active
  ON experiment_batch_run (tenant_id, batch_id, active_slot);
```

配套改 `activeBatchAttempt`：从"同实验任何未结束批次"改为"同批次是否已有活跃尝试"。

**`WorkflowRunGate` 保留**，作为迁移期兜底（ChatGPT 裁决），按经过验证的流程/设备组合逐批放开，不一次性删除。

### 4.3 事件归属：三层，全部是系统标识 `[设计]`

**前提**：不使用板号、样本号、仓位号作为归属判据——它们是业务参数，可重、可改、可人工录错。

事件先分类：

| 类型 | 例子 | 天然标识 | 归属方式 |
|---|---|---|---|
| E1 命令回包 | 某条 Transfer 返回 ok | commandId | **commandId** |
| E2 命令中间态 | 开始执行、进度 | commandId | **commandId** |
| E3 设备自发事件 | 到交换点、需人工、故障告警 | 无 | **设备占用者** |
| E4 状态心跳 | 在线/离线、idle/running | 设备标识 | **不归属 run** |
| E5 人工事件 | 扫码、确认到位 | 操作者会话 | 操作者 + 目标对象 |

三层归属键：

| 层 | 键 | 生成方 | 适用 | 前提 |
|---|---|---|---|---|
| 1 | `commandId` | 中控，稳定拼接 | E1、E2 | 设备回显 |
| 2 | **设备占用者**（`device_lock.current_run_id`） | 中控 | E3 | 同一设备同一时刻只有一个 run |
| 3 | 独占串行（降级） | — | 无任何标识的设备 | 明确写进产品边界 |

**关于"会话 ID"**：**不需要**。归属用 `DeviceLock.holder(resourceId)` 即可，连接标识没有额外价值。

**但有一个真问题**：断线期间设备产生的自发事件会丢。解法不是会话，而是**设备事件序号 + 断线补发**：

- 每条事件带设备侧单调递增序号
- 中控记录"按设备已收到第 N 条"
- 重连后请求从 N+1 补发

### 4.4 命令重发：commandId 稳定 + attempt 递增 `[设计]`

**第一步：修 commandId 稳定性**

```
改前：r{run}-n{node}-e{exec}-s{step}-d{device}
改后：r{run}-n{node}-s{step}-d{device}[|v{loopIndex}]
```

`exec` 只保留在日志与追踪，不进幂等键。

**第二步：账本从"已存在就拒绝"改成"按设备状态判定"**

```
ledgerKey 已存在
  → 读账本 state
  → driver.queryStatus(commandId)
      ├─ NOT_FOUND   → 允许重发（同一 commandId）
      ├─ IN_PROGRESS → 拒绝，继续等（源码注释：绝不 UNKNOWN、绝不重发）
      ├─ COMPLETED   → 采纳结果
      ├─ FAILED      → 按方法幂等性决定
      └─ UNKNOWN     → 拒绝，转人工
```

**attempt 与 commandId 的关系**：

| 概念 | 层级 | 重试时 | 作用 |
|---|---|---|---|
| `attempt` | 账本 | **递增** | 记录第几次尝试、供审计与上限 |
| `commandId` | 设备 | **不变** | 设备据此去重 |
| `ledgerKey` | 账本 | 含 attempt，会变 | 防止重复建账本行 |

**禁止自动重发的命令**：

| 方法类型 | 能否自动重发 |
|---|---|
| 查询类（读状态/位置） | 能 |
| 幂等设置类（设温度/参数） | 能 |
| **物理动作**（移液、搬运、开盖、离心、封膜） | **不能**，除非设备按 commandId 严格去重且经 HIL 验证 |

### 4.5 断线恢复：三层时间模型 `[设计]`

现有实现把三件不同的事混在一个 30 秒超时里（`MethodTimeoutPolicy` 注释"执行器级固定 30 秒"），这是根本问题。必须拆开：

| 层 | 检测什么 | 时间尺度 | 超时后 |
|---|---|---|---|
| **链路健康** | 设备/侧车是否活着 | **1 秒**（心跳），连续 3 次丢失即判断开 | 立即转 UNKNOWN，停止向该设备派发新命令 |
| **命令受理** | 设备是否收到这条命令 | **1–3 秒**（等 ACK） | 未收到 ACK → 视为未受理，可安全重发（同一 commandId） |
| **执行完成** | 命令是否做完 | **无固定超时**，只按方法配"业务上限"做告警 | 不判失败，继续等 |

**第三层为什么不能有超时**：孵育 30 分钟、离心 20 分钟都是正常业务。用 30 秒判超时，会把正在正常执行的设备判成失败，进而触发人工干预或重发——**比不处理更糟**。只要收到 ACK，就说明命令已被设备受理，剩下的只是等它做完；流程本来就要等这个结果，等待是安全的。

现有 `run_command` 的三个时间戳正好对应这三层：

```sql
sent_at       -- 发出（本地时间）
ack_at        -- 设备确认收到（必须是真实设备回执，见 §5）
finished_at   -- 执行完成（可能几十分钟后）
```

**断线时的处理顺序**：

```
心跳断（1 秒内发现）
  → 该设备上所有在途命令标 UNKNOWN（不是失败）
  → 停止向该设备派发任何新命令
  → 重连后先 queryStatus 逐条对账
      COMPLETED   → 落完成
      FAILED      → 落失败
      IN_PROGRESS → 保持在途，继续等
      NOT_FOUND   → 设备没收到，可重发（同一 commandId）
      UNKNOWN     → 人工对账，不重发
```

`CommandLedger` 第 200–223 行的四态判定已经正确，可直接复用，**缺的是触发时机**。

**运行时定时对账**：现有只有启动时对账（`ApiServer` 启动收尾），运行中无人处理；进程不重启，那条 `DISPATCH_STARTED` 就悬着。必须补：

| 项 | 值 |
|---|---|
| 扫描周期 | 30 秒 |
| 筛选条件 | `state = DISPATCH_STARTED AND sent_at < now() - 90s` |
| 处理 | 复用 `reconcileWithQuery`，逐条 `queryStatus` |
| 禁止 | 自动重发 |
| 告警 | UNKNOWN 数量 > 0 立即告警 |

**人工忽略（override）**：对账或暂停后进入 UNKNOWN 的命令，人工确认现场实际情况后，可以选择"忽略并继续"：

```
人工判定：该命令实际未执行 / 已执行但结果可接受
  → 记录 override：谁判定、何时、依据（现场照片/扫码/口头确认记录）
  → 节点标记为"人工忽略"，不标为成功也不标为失败
  → 流程继续走下一个节点
  → 审计留痕，不可静默跳过
```

关键是**不能只是"跳过"**：必须留下"谁判定、依据是什么"，否则事后无法追责，也无法判断该节点的结果是否可信。

**设备不支持 `queryStatus` 时**（`DeviceDriver` 第 63 行默认返回 UNKNOWN）：断线后只能人工。这必须写进"该设备不支持无人值守"的产品边界，不能默认它有这个能力。

### 4.6 状态：调度态独立列，不加枚举 `[事实 + 设计]`

`run_status` 是 PG 枚举：`draft/pending/planned/queued/running/paused/completed/failed/aborted/skipped/quarantined/cancelled`，**没有** `paused_waiting_resource`。

且系统已有明确原则（迁移注释原文）：

> 为什么用列不用枚举值：加枚举值要 ALTER TYPE，且 PG 不允许在事务里加

所以调度态用独立列，不碰枚举：

| 维度 | 取值 | 落点 |
|---|---|---|
| Run 生命周期 | 现有 `run_status` | 不变 |
| 调度状态 | `pending / eligible / waiting_resource / dispatched` | 新增列 |
| 暂停原因 | 现有 `pause_kind` | 不变 |

## 5. 协议准入条件（五条硬要求）`[设计]`

协议是自己定的，写死这五条，不满足的设备不进"可并行清单"：

1. **`commandId` 原样回显**：所有回包携带中控下发的 id。
2. **收到即 ACK，且必须是设备真实回执**：ACK 与"执行完成"是两个独立消息。中控不得把"TCP 发送成功"当作 ACK；**模拟器也必须实现真实的 ACK 行为**，不允许"发出即算收到"——否则测试全绿、现场失效。
3. **支持按 `commandId` 查状态**：返回 `NOT_FOUND / ACCEPTED / EXECUTING / COMPLETED / FAILED` 五态。
4. **心跳周期 ≤ 1 秒**，连续 3 次丢失即判链路断开，并在 1 秒内停止向该设备派发。
5. **事件带单调递增序号，支持断线补发**。

对第三方老设备：侧车做适配层，能补则补；不能补的降级为独占串行。

### 7.1 并行（接续前两轮）

| P-01 | 4 批 4 设备并行度 4 | 总耗时接近 1 批（注意机械臂瓶颈） |
| P-02 | 4 批 2 设备 | 2 跑 2 排，耗时接近 2 批 |
| P-03 | 两实验共用同一流程定义 | 均可启动 |
| P-04 | 两批等同一设备同一事件 | 一方消费，另一方排队，无超时死等 |
| P-13 | 两 run 同时申请同一设备 | 仅一个获得，另一个排队 |
| P-14 | 不同设备共用机械臂 | 非搬运可并行，搬运互斥 |
| P-16 | 两块板等同设备同类型事件 | 按 commandId/占用者准确推进，不串板 |
| P-17 | 事件早于等待节点到达 | 不丢失，不被无关 run 领取 |
| P-18 | 两 run 交叉申请 A/B | 无循环等待，失败不残留部分锁 |
| P-19 | 命令发出后进程崩溃 | 先对账，不重复下发 |
| P-20 | 一批失败其他在跑 | 失败隔离 |
| P-21 | 实验级暂停多批不同阶段 | 协调完成后才确认实验暂停 |
| P-23 | 单实例部署下的重复派发 | 数据库约束兜底；多实例场景本方案不覆盖（见 R-02） |
| P-25 | 同批次并发重复提交 | 幂等，最多一个活跃 attempt |
| P-32 | 设备执行结束物料仍在位置 | 设备可释放，位置继续占用 |

### 7.2 命令幂等与重发（新增）

| ID | 场景 | 期望 |
|---|---|---|
| C-01 | 同一逻辑命令重发 | `commandId` 不变，设备只执行一次 |
| C-02 | 重发前 `queryStatus=IN_PROGRESS` | 拒绝重发，继续等 |
| C-03 | 重发前 `queryStatus=NOT_FOUND` | 允许重发 |
| C-04 | 重发前 `queryStatus=UNKNOWN` | 拒绝，转人工 |
| C-05 | 物理动作命令在 `NOT_FOUND` 下重发 | 需 HIL 验证；未验证前拒绝 |
| C-06 | 循环体第二次执行 | `loopIndex` 进 key，不被误判重复 |
| C-07 | 长耗时方法（孵育 30 分钟） | 收到 ACK 后一直等，**不因执行时长判失败**；只在超过业务上限时告警 |
| C-08 | 心跳中断（拔网线/杀侧车） | **1 秒内**被发现，该设备在途命令转 UNKNOWN，不再派发新命令 |
| C-09 | ACK 未收到（设备没回执） | 1–3 秒内判定未受理，允许同 commandId 重发；不得把"TCP 发送成功"当 ACK |
| C-10 | 人工对 UNKNOWN 命令选择"忽略并继续" | 节点标"人工忽略"，记录判定人/时间/依据，流程继续，审计可追溯 |
| C-11 | 模拟器行为 | 模拟器必须真实回 ACK、真实支持 queryStatus，不得"发出即算收到" |

### 7.3 证据要求

每个 ID 必须记录：commit SHA、环境、并发线程数、事件顺序、命令 ID、run/batch/物料 ID、资源申请释放日志、状态时间线、是否覆盖崩溃点、可复现脚本。

## 8. 风险与未决

| ID | 问题 | 现状 |
|---|---|---|
| R-01 | 跨类锁无全序 | 三类锁各自有序，跨类可能死锁 |
| R-02 | 无执行体 fencing | **单实例部署下不适用**。一旦上多实例/主备，必须先补 epoch：`run` 加一列 + 三处条件更新 + 覆盖所有写入口（漏一处等于没有） |
| R-03 | 机械臂是真实瓶颈 | 实测 Transfer 均值 9.33s，2 run 已到容量边缘 |
| R-04 | `tryHoldResources` 是内存态 | 重启丢失，正确性靠 `DeviceLock` |
| R-05 | 设备不支持 `queryStatus` | 断线后只能人工 |
| R-06 | 断线期间自发事件会丢 | 需设备事件序号 + 补发 |
| R-07 | 实验状态中间态 | 并行时 UI 可能显示"running"但只完成 1/4 批 |
| R-08 | **有误导性的死字段比没有字段更危险** | `device_event.run_id` 就是例子：生产不填、无人读、但会诱导后来者用它做归属（一加过滤全部事件失效）。同类字段必须删除或加注释禁止误用 |
| R-09 | 执行超时被当成"限制执行时间" | 现状 30 秒固定超时会把 30 分钟的孵育判成失败。超时的正确用途是"发现失联"，不是"限制时长"（见 §4.5） |
