## 2. 现状：五层结构与执行链路 `[事实]`

```
experiment              实验，含 N 个样本
  └ experiment_batch    批次，按 batch_split 切分（96 样本 / 24 = 4 批）
      └ experiment_batch_run   批次尝试，attempt_no 递增
          └ experiment_run     批次的一次执行记录
              └ run            流程执行，run_type 区分类型，parent_run_id 形成树
```

**当前实际行为**：

- 批次**串行**：`BatchOrchestrator.runAll` 第 383–442 行是同步 for 循环，跑完一批才下一批。
- 异步路径**存在但也是串行续队**：`ExperimentScheduler` 第 856 行 `continueNextBatch`、第 662 行 `autoContinueHeldBatches`，一批完成才建下一批。
- 流程级互斥：`WorkflowRunGate` 按 `(tenant, workflow)` 判断，已存在 active 则拒绝（开关 `LABOS_WORKFLOW_CONCURRENT_RUN=allow` 可放开）。
- 事件**全局单次消费**：`device_event_consumption.event_id` 是主键，`dispatched_at` 置位后不可再消费。
- 事件等待条件**只有设备码 + 事件类型**：`__awaitEvent` 参数仅 `device / eventType / timeout`。

**代价**：4 批 × 2 小时 = 8 小时；有 4 套设备时理论上 2 小时。**但机械臂吞吐是真实上限**（见 R-03），收益远小于设备数。

## 3. 真正要解决的四个问题

### 3.1 批次串行：一个精确的不变量 `[事实]`

`BatchOrchestrator` 第 682–687 行的注释原文：

> 锁住实验行（异步分批"取下一批"的串行化点）。
> 为什么锁实验行而不是批次行：判定"同实验是否已有批次 run 在队列/执行"是**实验级不变量**，只锁某一批挡不住两个请求同时给不同批建单。

这是有意识的设计选择，不是疏漏。改它必须先论证"这条不变量为什么不再成立"——**并行下它不再成立**，因为"同实验"不再是资源冲突的单位（见 §3.3）。

### 3.2 事件归属：等待期间没有锁持有者 `[事实]`

**真实流程结构**（提取线）：

```
n_pick  (PickTipComb)  → 抢设备锁 → 执行 → onStepDone 释放锁
   ↓
n_wait  (__awaitEvent) → 不走 step 生命周期 → 无锁
   ↓
设备上报"到交换点"（E3 自发事件）
```

设备锁在 `onStepStart` 抢（`WorkflowService:3091-3110`）、`onStepDone` 放（`:3169-3181`），而 `__awaitEvent` 是 `GraphRunner` 内置节点，**不经过 step 生命周期**。

⇒ **等待事件时，`device_lock.current_run_id` 必然为空**（或属于别的 run）。用设备锁持有者做归属，在 E3 场景下**结构性失效**，不是边缘窗口。

即便锁没释放，仍有迟到事件问题：A 持锁产生事件 → A 释放 → B 持锁 → 事件到达 → 被误归给 B。

**结论**：事件归属必须靠**显式的等待者登记 + 事件自带的过程标识**，方案见 ③ §2。

### 3.3 事件缺业务归属字段 `[事实]`

`claimEvent` 的候选集过滤条件（`DeviceEventMapper.xml:73-90`）：

```
e.tenant_id / e.id > afterId / e.dispatched_at IS NULL
/ NOT EXISTS(已消费) / [可选] e.device_code / [可选] e.event_type
```

**没有 `e.run_id`**，而 `device_event.run_id` 在生产路径上不填、也没有业务逻辑读它（唯一读取点是 `DeviceEventController:141` 的 JSON 回显）。

⚠ **该字段是 `POST /api/device-events` 的对外契约字段**（`DeviceEventController:31-34` 的 javadoc 明写 body 含 `"runId":123`）⇒ 处置见 §4.3.4。

### 3.4 命令幂等：一个隐藏的耦合 `[事实]`

- `commandId` = `r{run}-n{node}-e{exec}-s{step}-d{device}`（`:1474-1478`），其中 `exec` 每次 `execute()` 调用递增（`:206`）。
- 账本幂等键是**另一个** key：`r{run}|n{node}|a{attempt}|s{step}|d{device}|m{method}[|v{loop}]`（`:1209-1211`），不含 `exec`。
- 账本已存在时直接拒绝：`EC-99-0006 禁止重复下发（需人工确认设备位置）`（`:1216-1223`）。

**结论**：现在"不会重复执行"是靠账本挡住的。放开账本允许重试时，`commandId` 会变，设备可能真的执行两次。

### 3.5 跨类锁无全序 `[事实]`

真实顺序是 **设备 → 位置 → 轨道**（`DriverStepExecutor:581`），但这个顺序**没有任何代码强制，也没有测试保护**——它是靠"大家都在这个位置抢"维持的。

进一步：**设备锁与轨道分区锁共用 `device_state.current_run_id`**（`RailZoneGuard:98` 复用 `DeviceLock`）⇒ 真正的跨类互等只有 `device_state` ↔ `position_state` 一组。详见 ⑤。

## 4. 设计决策

### 4.1 调度：接入现有 `ExperimentScheduler`，不新建 `[设计]`

**已有能力（不需要重做）**：

| 能力 | 位置 |
|---|---|
| 资源级互斥 | `ExperimentScheduler:26,750-757` |
| 优先级 / EDD / FIFO | `:138-141` |
| 并行度上限 + `schedule_plan` 热加载 | `:52,211,306-313` |
| 资源软预约（按 id 升序） | `:970-980` |
| 独立线程池 | `:169` |

**要做的**：让批次提交进入这个队列，而不是新建 `BatchScheduler`。

注意：`tryHoldResources` 是**内存 Map**（`:979`），重启即丢。正确性最终靠 `DeviceLock` 的数据库条件更新。

### 4.2 互斥粒度：从 workflow 降到批次尝试 `[设计]`

**目标不变量**：**同一批次同一时刻只能有一个"在执行"的尝试。**

#### 4.2.1 应用层改动（详见 ④）

`BatchOrchestrator.activeBatchAttempt` 从"同实验任何未结束批次"改为"**同批次**是否已有活跃尝试"。

#### 4.2.2 数据库兜底（修正版）

v1 提出的写法有**状态源错误**与 **paused 语义错误**，本版修正：

```sql
-- ⚠ active_slot 不再用生成列：生成列读的是 experiment_batch_run.status，
--   而真相源是 experiment_run.status（人工停止/恢复直接改 run），
--   两者之间存在回写延迟 ⇒ 用显式维护。
ALTER TABLE experiment_batch_run ADD COLUMN active_slot smallint;

-- 唯一索引只约束"活跃"行：active_slot 为 NULL 的行互不冲突（PG 唯一索引视 NULL 互异）
CREATE UNIQUE INDEX uk_batch_run_active
  ON experiment_batch_run (tenant_id, batch_id, active_slot)
  WHERE active_slot IS NOT NULL;
```

**active 集合 = `('queued','running')`，明确排除 `'paused'`。**

为什么排除 paused：

| 事实 | 依据 |
|---|---|
| 同步重跑路径 `runBatch` 只拒绝 completed 批 | `BatchOrchestrator:467-469` |
| ⇒ **paused 批可以重跑**（会新建 attempt） | 同上 |
| 异步路径 `activeBatchAttempt` 查 `r.status IN ('queued','running','paused')` | `BatchMapper.xml:70-82`（**读的是 run 的状态**） |
| ⇒ 异步路径把 paused 视为"仍占用" | 同上 |

⚠ **两条路径对"paused 批能否再起一个 attempt"的判断本来就不一致。** 唯一索引会强制其中一种，本方案取 **`('queued','running')`**（保留同步重跑的既有语义），并同步把异步路径的 `activeBatchAttempt` 改为只查 `queued/running`。

异步路径"暂停后不自动续"的语义**不依赖唯一索引**，由另外两处保证：`activeBatchAttempt`（应用层）与 `selectPausedBatchCandidates`（要求该批**没有任何 attempt 行**，`BatchMapper.xml:49-61`）。

**active_slot 的维护**：与 `updateAttemptFromRun` 同一条 SQL 完成（该 SQL 已是 `SET status = r.status`，`BatchMapper.xml:204-218`）：

```sql
UPDATE experiment_batch_run br
   SET status = r.status,
       error = r.error,
       active_slot = CASE WHEN r.status IN ('queued','running') THEN 1 ELSE NULL END,
       ...
  FROM experiment_run r
 WHERE ...
```

插入路径同理：`insertBatchRunRunning` / `insertQueuedBatchRun` 建行时 `active_slot = 1`。

#### 4.2.3 resume 再激活也要纳入（新增，来自 ④ §4.5）

存在**第三条**会造出双 active 的写入路径：**resume**。`PauseMapper.resumeToQueued` 的 `UPDATE run SET status='queued'` **无状态守卫**，能把 failed 复活成 queued 并真的续跑，绕过新建路径的一切约束。

⇒ 唯一索引与状态守卫必须同时覆盖"新建"与"再激活"两条路径，否则收紧了一侧、另一侧仍可双开。

### 4.3 事件归属：等待者登记 + 事件自带标识 `[设计]`

**原则**：不使用板号、样本号、仓位号作为归属判据——它们是业务参数，可重、可改、可人工录错。

**归属分两类**：

| 事件类型 | 例子 | 天然标识 | 归属方式 |
|---|---|---|---|
| E1 命令回包 | 某条 Transfer 返回 ok | commandId | **commandId**（③ §1） |
| E2 命令中间态 | 开始执行、进度 | commandId | **commandId**（③ §1） |
| E3 设备自发事件 | 到交换点、需人工、故障告警 | 设备侧过程标识 | **等待者登记 + 精匹配**（③ §2） |
| E4 状态心跳 | 在线/离线、idle/running | 设备标识 | **不归属 run** |
| E5 人工事件 | 扫码、确认到位 | 操作者会话 | 操作者 + 目标对象 |

**E3 的归属（核心）**：**登记"谁在等"，而不是"谁占着"。**

- 中控在 `__awaitEvent` 节点建立时登记 waiter（run / node / loop / 设备码 / 事件类型 / 期望的过程标识 / 基准事件 id / 期限）；
- 设备事件到达时，用**行锁 + 唯一性判定**匹配 waiter；
- 匹配到唯一 waiter ⇒ 归属成立；匹配到多个 ⇒ **整体不猜，落 UNATTRIBUTED 并告警**；
- 匹配不到 ⇒ 落 UNATTRIBUTED 并告警，不推进任何流程。

**唯一的例外**：设备**既不按 commandId 去重、又不带过程标识** ⇒ 无法归属 ⇒ **降级为独占串行**，并写进产品边界（与 ③ §7 限制 2 一致）。

#### 4.3.4 `device_event.run_id` 的处置（v2 修正）

v1 建议直接 `DROP COLUMN`。**本版改为三选一，默认选①**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **①（默认）** | **侧车补填 runId + 认领过滤** | 需要侧车改造；与 §5 准入条件第 1 条同批做 |
| ② | 保留列 + 加注释禁止误用 | 零改造成本，但归属仍不可靠 |
| ③ | 确认无外部实现依赖后删除 | **破坏 `POST /api/device-events` 的公开契约**（`DeviceEventController:31-34`），须同步更新 API 文档 |

无论选哪个，都必须写明这是**对外契约变更**。

### 4.4 命令重发：按设备能力分档 `[设计]`

**目标不是"commandId 稳定"，而是"同一条物理命令在设备侧只执行一次"**——能否达成取决于设备是否严格按 commandId 去重。

#### 4.4.1 第一步：按设备能力分档决定 commandId 是否稳定

| 设备能力 | commandId 策略 | 理由 |
|---|---|---|
| 严格按 commandId 去重（通过 §5 第 1/3 条并 HIL 验证） | **稳定**：`r{run}-n{node}-s{step}-d{device}[|v{loop}]` | 设备据此拒绝重复；resume 复用旧 id 是**正确**行为 |
| 不去重（老设备） | **保留 `exec` 递增** | 宁可重做，不可漏做——resume 后重发会被设备当新命令执行才安全 |

⚠ v1 的"统一去掉 `exec`"对**不去重设备是有害的**：稳定 id 会让 resume 后的重发被设备忽略 ⇒ 流程卡死。

#### 4.4.2 第二步：账本判定以 commandId 为查询入口，不以 ledgerKey

v1 的判定树入口是"ledgerKey 已存在"，但 §4.4.3 的表格定义 `attempt` 递增 ⇒ ledgerKey 变 ⇒ **"已存在"永远不成立** ⇒ 判定树不可达。

**修正**：判定入口改为 **`commandId`**（一条逻辑命令对应一个 commandId，可能对应多条 ledger 明细）。

```
command_ledger 里该 commandId 有明细
  → 取最新一条明细的 state
  → driver.queryStatus(commandId)
      ├─ NOT_FOUND   → 落 UNKNOWN，转人工（NOT_FOUND ≠ 设备没动过，见 §4.5）
      ├─ IN_PROGRESS → 拒绝重发，继续等（绝不 UNKNOWN、绝不重发）
      ├─ COMPLETED   → 采纳结果
      ├─ FAILED      → 按方法幂等性决定
      └─ UNKNOWN     → 拒绝，转人工
```

#### 4.4.3 attempt / commandId / ledgerKey 三者关系（修正）

| 概念 | 层级 | 重试时 | 作用 |
|---|---|---|---|
| `attempt_no`（§1.2 的传输尝试） | 逻辑动作 | **递增** | 记录第几次传输尝试 |
| `commandId` | 设备 | 按 §4.4.1 分档 | 设备据此去重 |
| ledger 明细行 | 账本 | **每次传输一行** | 传输流水，不单独计数 |

⇒ **同一 commandId 对应多条 ledger 明细**是正常形态，不是异常。§4.4.2 的判定入口因此必须用 commandId。

#### 4.4.4 禁止自动重发的命令

| 方法类型 | 能否自动重发 |
|---|---|
| 查询类（读状态/位置） | 能 |
| 幂等设置类（设温度/参数） | 能 |
| **物理动作**（移液、搬运、开盖、离心、封膜） | **不能**，除非设备按 commandId 严格去重且经 HIL 验证 |

### 4.5 断线恢复：两层已具备，补一层 `[设计]`

**v1 的前提已过时**：超时**早已按方法取**（`MethodTimeoutPolicy:6,49-64`，`INCUBATE=1800s` / `THERMOCYCLE=3600s` / `CENTRIFUGE=900s`），长工艺被误判超时的问题**已修复**。

**当前实际是两层**：

| 层 | 现状 |
|---|---|
| 发出 → 等最终回包 | ✅ 已有，超时按方法取 |
| 链路健康（心跳） | ❌ 缺 |
| 命令受理（ACK） | ❌ 缺 |

⇒ **要补的是中间的 ACK 层与链路健康层**，不是"拆三层"。

#### 4.5.1 补齐后的三层

| 层 | 检测什么 | 时间尺度 | 超时后 |
|---|---|---|---|
| **链路健康** | 设备/侧车是否活着 | **1 秒**（心跳），连续 3 次丢失即判断开 | 立即转 UNKNOWN，停止向该设备派发新命令 |
| **命令受理** | 设备是否收到这条命令 | **1–3 秒**（等 ACK） | 未收到 ACK ⇒ 视为未受理，**可安全重发**（同一 commandId） |
| **执行完成** | 命令是否做完 | **无固定超时**，只按方法配"业务上限"做告警 | 不判失败，继续等 |

**第三层为什么不能有超时**：孵育 30 分钟、离心 20 分钟都是正常业务。只要收到 ACK，命令已被设备受理，剩下的只是等它做完。

#### 4.5.2 "执行无超时"的代价与配套看门狗（v2 新增）

**这是"执行无超时"真正的代价，v1 漏了**：设备既不发完成回包、心跳又正常（**设备卡死不动**）时，命令既不超时也不判异常；而**设备锁是 step 粒度、只在 `onStepDone` 才释放** ⇒ 该设备被长期占死，其他 run 永远等不到它。

⇒ 必须补一个**与命令超时分离的"设备锁占用看门狗"**：

| 项 | 值 |
|---|---|
| 触发条件 | 同一 run 连续持有某设备锁超过 N 分钟，且期间无命令进展 |
| N 的来源 | 按设备方法超时上限（复用 `MethodTimeoutPolicy`） |
| 动作 | 告警 + 转人工（**不自动释放锁**，不自动重发） |
| 为什么不做自动释放 | 设备可能正在执行长工艺，自动释放 ⇒ 别的 run 抢同一设备 ⇒ 物理冲突 |

#### 4.5.3 断线时的处理顺序

```
心跳断（1 秒内发现）
  → 该设备上所有在途命令标 UNKNOWN（不是失败）
  → 停止向该设备派发任何新命令
  → 重连后先 queryStatus 逐条对账
      COMPLETED   → 落完成
      FAILED      → 落失败
      IN_PROGRESS → 保持在途，继续等
      NOT_FOUND   → 落 UNKNOWN，转人工（**不重发**）
      UNKNOWN     → 落 UNKNOWN，转人工
```

`CommandLedger` 第 200–223 行的四态判定已经正确，可直接复用，**缺的是触发时机**（运行时定时对账）。

**运行时定时对账**：

| 项 | 值 |
|---|---|
| 扫描周期 | 30 秒 |
| 筛选条件 | `state = DISPATCH_STARTED AND sent_at < now() - 90s` |
| 处理 | 复用 `reconcileWithQuery`，逐条 `queryStatus` |
| 禁止 | 自动重发 |
| 告警 | UNKNOWN 数量 > 0 立即告警 |

#### 4.5.4 人工"忽略并继续"（override）

对 UNKNOWN 的命令，人工确认现场实际情况后可以选择"忽略并继续"：

```
人工判定：该命令实际未执行 / 已执行但结果可接受 / 已执行但不可接受 / 无法确认
  → 记录 override：谁判定、何时、依据（现场照片/扫码/口头确认记录）
  → 节点标记为"人工忽略"，不标为成功也不标为失败
  → 按处置结论决定是否继续下一步
  → 审计留痕，不可静默跳过
```

四种处置结论与可信度维度的完整定义见 **③ §1.5**；落点（账本/节点/产物）见 **③ §1.5**。

**设备不支持 `queryStatus` 时**（`DeviceDriver` 默认返回 UNKNOWN）：断线后只能人工。这必须写进"该设备不支持无人值守"的产品边界。

### 4.6 状态：调度态独立列，不加枚举 `[事实 + 设计]`

`run_status` 是 PG 枚举：`draft/pending/planned/queued/running/paused/completed/failed/aborted/skipped/quarantined/cancelled`，**没有** `paused_waiting_resource`。

且系统已有明确原则（迁移注释原文，`90_all_in_one.sql:2618-2620`）：

> 为什么用列不用枚举值：加枚举值要 ALTER TYPE，且 PG 不允许在事务里加。

所以调度态用独立列，不碰枚举：

| 维度 | 取值 | 落点 |
|---|---|---|
| Run 生命周期 | 现有 `run_status` | 不变 |
| 调度状态 | `pending / eligible / waiting_resource / dispatched` | 新增列 |
| 暂停原因 | 现有 `pause_kind` | 不变（新增取值属加列值，与 ALTER TYPE 无关） |

## 5. 协议准入条件（五条硬要求） `[设计]`

协议是自己定的，写死这五条，不满足的设备不进"可并行清单"：

1. **`commandId` 原样回显**：所有回包携带中控下发的 id。
2. **收到即 ACK，且必须是设备真实回执**：ACK 与"执行完成"是两个独立消息。中控不得把"TCP 发送成功"当作 ACK；**模拟器也必须实现真实的 ACK 行为**，不允许"发出即算收到"——否则测试全绿、现场失效。
3. **支持按 `commandId` 查状态**：返回 `NOT_FOUND / ACCEPTED / EXECUTING / COMPLETED / FAILED` 五态。
4. **心跳周期 ≤ 1 秒**，连续 3 次丢失即判链路断开，并在 1 秒内停止向该设备派发。
5. **事件带单调递增序号，支持断线补发**（需配 `device_boot_id`，见 ③ §7 限制 1）。

**准入清单还应包含"事件带过程标识（process_id / interaction_step）"**——否则 E3 事件无法归属 ⇒ 该设备只能降级为独占串行（§4.3 末段）。

对第三方老设备：侧车做适配层，能补则补；不能补的降级为独占串行。

## 7. 验收矩阵

### 7.1 并行（接续前几轮，v2 补齐缺口）

| ID | 场景 | 期望 |
|---|---|---|
| P-01 | 4 批 4 设备并行度 4 | 总耗时受**机械臂吞吐**约束（见 R-03），不是"接近 1 批" |
| P-02 | 4 批 2 设备 | 2 跑 2 排；耗时受臂吞吐约束 |
| P-03 | 两实验共用同一流程定义 | 均可启动（受资源约束） |
| P-04 | 两批等同一设备同一事件 | 一方消费，另一方排队，**无超时死等** |
| P-05 | 4 批同时需要机械臂 | 串行搬运，无冲突 |
| **P-06** | **点位不足（2 批抢同一点位）** | **一方等待，不冲突、不覆盖**（v2 补） |

| P-08 | 并行中现场扣留 | 未启动的批不启动；在跑的批在节点边界停 |
| P-09 | 同批次重复提交 | 幂等，最多一个活跃尝试 |
| **P-10** | **资源等待超时** | **转等待态并告警，不静默失败**（v2 补） |
| P-11 | 并行度 4 时其他流程启动 | 不被饿死（线程池足够或独立池） |
| **P-12** | **并行度 1（串行配置）** | **行为与改造前完全一致**（v2 补） |
| P-13 | 两 run 同时申请同一设备 | 仅一个获得，另一个排队 |
| P-14 | 不同设备共用机械臂 | 非搬运可并行，搬运互斥 |
| P-16 | 两块板等同设备同类型事件 | 按 commandId / waiter 准确推进，不串板 |
| P-17 | 事件早于等待节点到达 | 不丢失，不被无关 run 领取（依赖 run 级基准，见 ③ §2.2） |
| P-18 | 两 run 交叉申请 A/B | 无循环等待，失败不残留部分锁 |
| P-19 | 命令发出后进程崩溃 | 先对账，不重复下发 |
| P-20 | 一批失败其他在跑 | 失败隔离 |
| P-21 | 实验级暂停多批不同阶段 | 协调完成后才确认实验暂停 |
| P-23 | 单实例部署下的重复派发 | 数据库约束兜底；多实例场景本方案不覆盖（R-02） |
| P-25 | 同批次并发重复提交 | 幂等，最多一个活跃 attempt |
| P-32 | 设备执行结束物料仍在位置 | 设备可释放，位置继续占用 |
| **P-34** | **两实验共用设备 + 共用点位** | **不冲突、不覆盖；一方等待**（v2 补，对应 §11 第 9 问） |

### 7.2 命令幂等与重发

| ID | 场景 | 期望 |
|---|---|---|
| C-01 | 同一逻辑命令重发 | commandId 不变（**仅限去重设备**），设备只执行一次或明确拒绝重复 |
| C-02 | 重发前 `queryStatus=IN_PROGRESS` | 拒绝重发，继续等 |
| **C-03** | **重发前 `queryStatus=NOT_FOUND`** | **落 UNKNOWN，转人工，不重发**（v2 改口径：NOT_FOUND ≠ 设备没动过） |
| C-04 | 重发前 `queryStatus=UNKNOWN` | 拒绝，转人工 |
| C-05 | 物理动作命令在 `NOT_FOUND` 下重发 | **拒绝，转人工**（除非设备已验证去重且经 HIL 验证） |
| C-06 | 循环体第二次执行 | `loopIndex` 进 key，不被误判重复 |
| C-07 | 长耗时方法（孵育 30 分钟） | 收到 ACK 后一直等，**不因执行时长判失败**；只在超过业务上限时告警 |
| C-08 | 心跳中断（拔网线/杀侧车） | **1 秒内**被发现，该设备在途命令转 UNKNOWN，不再派发新命令 |
| C-09 | ACK 未收到（设备没回执） | 1–3 秒内判定未受理，允许同 commandId 重发；不得把"TCP 发送成功"当 ACK |
| C-10 | 人工对 UNKNOWN 命令选择"忽略并继续" | 按处置结论落库（③ §1.5），记录判定人/时间/依据，流程继续，审计可追溯 |
| C-11 | 模拟器行为 | 模拟器必须真实回 ACK、真实支持 queryStatus，不得"发出即算收到" |
| **C-12** | **设备卡死不动（有心跳、无完成回包）** | **设备锁占用看门狗告警 + 转人工，不自动释放锁**（v2 补，对应 §4.5.2） |

### 7.3 证据要求

每个 ID 必须记录：commit SHA、环境、并发线程数、事件顺序、命令 ID、run/batch/物料 ID、资源申请释放日志、状态时间线、是否覆盖崩溃点、可复现脚本。
