# 设备执行中的暂停 · 现状实测与「真停」实现方案（2026-11-06）

> 起因（用户原话）：
> **「大部分时候暂停命令发出去，但是设备正在执行的方法会继续，
> 只有机械臂收到暂停指令后会当前停止，你看看这个怎么实现」**
>
> 脚本：`scripts/e2e-pause-during-device.py`（workflow 级）
>       `scripts/e2e-pause-during-experiment.py`（实验级，门禁 4.17 用）
> 复跑：`python3 scripts/e2e-pause-during-device.py --api http://127.0.0.1:18080`
> 配套改动：模拟器新增 `--rand-delay MIN:MAX[:SEED]`（方法耗时随机）
> 环境：macOS，API `18080` + PostgreSQL `192.168.124.2:5432/labdb` + 仿真机 19500-19506

---

## 1. 结论（一句话）

**你的观察是对的，而且比"机械臂会停"还要更彻底一点：**
**现在暂停对**任何**正在执行的设备动作都不起作用 —— 机械臂也不会停。**

但要说清两件事（第一版把这两件事混在一起了，见 §1.5）：

| 维度 | 结论 |
|---|---|
| **暂停本身生效吗？** | ✅ **生效** —— 暂停发出去后 0.1 秒内 `run` 就变成 `paused` |
| **正在执行的设备方法会被打断吗？** | ❌ **不会** —— 设备方法跑完才停（`completed`），动作没被中断 |

实测（设备方法耗时随机 10–18 秒，**在它执行到一半**时发暂停，
判据见 §1.5 —— 用 `device_state` 确认设备真的在执行）：

```
══ 长耗时设备执行中发暂停 ══
  ✓ 观测到设备方法执行中（device_state status=running current_method=Home，归属 run #207775）
  ✓ 已在设备执行中发出暂停（UPDATE 影响 1 行）

  结果：
    run 最终状态      : paused           ← 暂停生效了
    设备指令最终状态  : completed        ← 但设备跑完了，没被打断
    节点状态          : ARM=completed
    暂停生效延迟      : 0.1 秒（从发暂停到 run 变 paused）

  ⇒ 设备指令**跑完了**（completed）：暂停没有中断正在执行的设备动作
```

源码给出的原因：**暂停检查点只在「动作边界」（`executeNode` 之前）**，
而设备执行期间线程**阻塞在等设备回包**，根本走不到那个检查点。

## 1.5 ⚠ 判据修正：「设备正在执行」到底怎么判（第一版判据是错的）

> 这一节是 2026-11-06 补的。**第一版脚本的判据本身有问题，
> 导致它测的不是「执行中暂停」，结论也偏了。**

### 坑 1：`run_command` 有行 ≠ 设备正在执行

第一版脚本这样判断「设备正在执行」：

```python
n = q1(f"SELECT count(*) FROM run_command WHERE run_id={rid}")
if n and int(n) >= 1:      # ← 以为这就是「指令发出去了」
```

**这是错的。** `run_command` 是**步结束之后**才 INSERT 的
（`WorkflowService.java` 的命令级落库：`status` 直接写 `completed`/`failed`，
`sent_at`/`finished_at` 都是 `now()`）——
它证明的是「**这一步已经跑完并落库了**」，不是「指令刚发出去」。

⇒ 于是第一版的暂停**发在设备早就跑完之后**：
`run` 已经进收尾流程，UPDATE 把状态改成 `paused` 又被自己的收尾覆盖成 `completed`
⇒ 第一版输出里那句「run 最终状态: completed ← 暂停根本没生效」**是误判**，
真实情况是「暂停发晚了，设备早跑完了」。

### 坑 2：`max(id) FROM run` 会抓到**别人的 run**

第一版用 `SELECT max(id) FROM run WHERE tenant_id=1` 定位自己的 run。
表里还留着**别的测试**的 run（有指令、有完成态），
一旦 `max(id)` 命中那条旧 run，整个脚本就在**别人的证据**上做断言
（实测就抓到了 `workflow_id=1255` 的旧 run，它 11:58 就跑完了）。

⇒ 一律按 `run.workflow_id = 本次新建的流程` 定位（天然唯一）。

### 正确的判据：`device_state`

| 信号 | 含义 | 谁写 |
|---|---|---|
| `device_state.status='running'` + `current_method` 非空 | **设备方法正在执行** | `markDeviceBusy`（`onStepStart`）/ `markDeviceIdle`（`onStepEnd`） |
| `device_state.current_run_id` | 占用该设备的 run（用来确认不是别人的执行） | `DeviceLock.tryAcquire` |
| `run_command` 有行 | 那一步**已经跑完并落库** | 命令级落库（步结束后） |

```sql
SELECT status, current_method, current_run_id
FROM device_state WHERE tenant_id=1 AND resource_id=200214;
-- running | Home | 207775   ← 这才是「设备正在执行」
```

改完判据后重测，**结论不变但证据链变了**：
暂停**确实生效**（0.1 秒内 `run` 变 `paused`），
而**设备方法照旧跑完**（`completed`）—— 这才是要解决的问题。

## 2. 现状的完整链路（读码 + 实测）

### 2.1 暂停是怎么实现的

`WorkflowService.java:824` 给执行器注入了一个「暂停检查器」：

```java
// P1-8：每到一个节点边界查一次 DB —— 状态是 paused 就停。
// 只查单行主键，开销可忽略；不查的话暂停按钮等于没用。
.withPauseChecker(() -> isRunPaused(runId));
```

`isRunPaused` 就是查一行 `run.status == 'paused'`。

### 2.2 检查点只有一个，且在动作边界

`GraphRunner.java:328-340`：

```java
} else if (node.kind() == Kind.TASK) {
    // P1-8：在**任务节点的动作边界**检查暂停。
    // 不停在动作中间 —— 机械臂抓着板会掉。
    // 也不停 start/gateway —— 它们不是"一步活"，停在那里没意义。
    // 把 key 放回队列，恢复时从这里继续。
    if (pauseChecker.getAsBoolean()) {
        ready.offer(key);
        done.remove(key);
        paused = true;
        log.accept("[暂停] 收到暂停请求，在节点边界停下，待执行节点：" + key);
        break;
    }
    RecoverableNode rn = toRecoverable(node);
    ...
    NodeStatus st = stateMachine.executeNode(rn, progress, executor);   // ← 这里阻塞等设备回包
```

**执行顺序是**：

```
节点边界 ──查 pause──▶ 没暂停 ──▶ executeNode ──▶ driver.execute ──▶ 阻塞等回包（几十秒~几分钟）
   ▲                                                                      │
   └──────────────── 设备回包后才回到这里 ────────────────────────────────┘
```

**暂停信号只在第一箭头的位置被检查**。设备正忙着的时候（第二个箭头），
没有任何代码去读 `run.status`。

### 2.3 「机械臂会停」是怎么来的 —— 是**资源保护**，不是暂停

源码里两处「机械臂不能停」的注释，说的其实是**不能在那里放资源**，不是"暂停会停它"：

- `PauseManager.java:29`：机械臂从 A 抓板、移到半空 —— **不能停在这里，板会掉**
- `PauseManager.releaseResources`：**释放「已占但未用」的资源**，三类豁免：
  - 回程承诺（`position-return`）—— 放了别人的板就占进去，回程时死锁
  - 活动设备锁 —— 板可能还在里面
  - **抓着板的机械臂 —— 不能松手**

即：暂停时会把「占着但没在用」的资源释放掉，但**正在搬运的机械臂占位被豁免**，
所以机械臂**继续搬完**。这与"机械臂收到暂停指令会停"是**相反**的语义。

> ⚠ 换句话说：**当前实现里，机械臂和普通设备在暂停这件事上行为一致 ——
> 都是"让当前动作跑完，停在下一个边界"。** 你印象里的"机械臂会停"
> 可能是把「机械臂占位被豁免不释放」记成了「机械臂会停」。

### 2.4 中断能力其实**有**，只是没接线

`DeviceDriver.java:29`：

```java
/** 中止正在执行的指令（尽力而为）。 */
void abort(String commandId);
```

两个实现：

| 实现 | 行为 |
|---|---|
| `TcpPersistentDriver.abort` | **把等待中的 future 摘掉**，让调用方立刻返回失败（`EC-99-0005 被中止`）—— **真能打断等待** |
| `TcpDriverAdapter.abort` | **空实现**（协议没有 Abort 消息类型，只能靠上层超时） |
| `VirtualDriver.abort` | 有实现 |

**但是全仓找不到任何调用方** —— 唯一的 `.abort(` 命中是 `RecoveryDecision.abort`（同名不同物）。

实测佐证：全库 `run_command` 里 `error_code='EC-99-0005'`（被中止）**一条都没有** ——
这条路径从未被走过。

### 2.5 顺带发现：长任务会被 30 秒超时打断

`DriverStepExecutor` 的超时是**执行器级固定 30 秒**：

```java
public DriverStepExecutor(DriverRegistry registry, StepSink sink, DbConfig db, long tenantId, long runId) {
    this(registry, 30_000L, "trace", sink, db, tenantId, runId);
}
```

而 `device_method.timeout_sec` / `workflow_node.timeout_sec` 两张表里**存了超时值，
但驱动层从来不读**（`grep timeout_sec` 在 driver/ 与 workflow/ 下零命中）。

后果：**任何耗时超过 30 秒的真机方法（离心 5 分钟、PCR 几十分钟、孵育 30 分钟）
都会被中控判超时**，与"暂停"无关。实测把模拟器耗时设成 20–40 秒时，
超过 30 秒的那次就 `failed` 了。

## 2.6 实验级实测：三层状态会一致地变「已暂停」，但设备动作照旧跑完

上面测的是 workflow 级 run。**实验级**（`/api/experiments/{id}/run`）有三层状态，
都要看：`run`（workflow 级，设备指令挂它下面）、`experiment_run`（实验级）、
`experiment`（实验本身，由 `experiment_run` 派生）。

实测（设备耗时随机 10–18 秒，**在它执行到一半**时发暂停，走真实的实验级暂停接口
`POST /api/experiments/runs/{id}/pause`；判据用 `device_state`，
见 §1.5 —— 确认设备真的在执行才发暂停）：

```
  ✓ 观测到设备方法执行中（device_state status=running current_method=Home，归属 run #207774）
  暂停前 experiment_run 状态: running
  暂停接口返回：HTTP 200 {"runId":1643,"experimentId":1458,"status":"paused","scope":"experiment","kind":"manual"}
  暂停后 experiment_run 状态: paused
  ✓ 实验在设备执行中暂停后，实验级两层都变 paused（experiment_run / experiment）
  ✓ 暂停在 5 秒内生效（0.2 秒）
  ✓ workflow 级 run 独立跑完（不受实验级暂停影响）：completed

  结果：
    run（workflow 级）      : completed
    experiment_run（实验级） : paused
    experiment（实验本身）   : paused
    设备指令最终状态        : completed      ← 设备动作照旧跑完
    节点状态                : ARM=completed
    暂停生效延迟            : 0.2 秒
```

**⇒ 答案：会进入暂停状态**（实验级两层都显示"已暂停"，0.2 秒内生效），
**但设备正在执行的方法不会被打断** —— 它跑完才停。

> 这条现在是门禁 4.17 段（`scripts/e2e-pause-during-experiment.py`），
> 断言只钉**语义要求**（两层都 paused + 5 秒内生效 + workflow 级 run 独立跑完），
> **不钉**「设备指令最终 completed」—— 那条会随「真停」实现而变，放进门禁就会假红。

> ⚠ **workflow 级的 `run` 是另一条独立执行**，不受实验级暂停影响：它跑完就是
> `completed`（这正是设计——"实验暂停" ≠ "底层 workflow run 暂停"）。
> 第一版把三层一起断言 ⇒ workflow run 先收尾就假红。门禁只断言实验级两层。

### ⚠ 测这个场景有个坑：异步派发会「测不到」

第一版用 `?async=1` 触发实验执行，结果**暂停前 `experiment_run` 状态就已经是
`completed`** —— 调度器把实验派发后**立刻**就跑完了（11:23:21 → 11:23:33），
我等到设备指令发出时，实验级 run 早收尾了，**暂停发在一条已完成的 run 上**
（接口照样返回 200 + `status:"paused"`，极具迷惑性）。

**必须用同步执行**（不带 `async=1`）：同步执行会阻塞 HTTP 响应，
正好留出"设备执行中"的时间窗发暂停（放后台线程跑，主线程发暂停）。

### ⚠ 顺带修掉两个真 bug（实测暴露的）

**bug 1 · `experiment_run` 的 paused 会被收尾覆盖**
`ExperimentExecutor.settle()` 收尾时无条件写 `status='completed'`，
**没有 workflow 级那道 `if (isRunPaused(runId)) return;` 保护**
（`WorkflowService.settleRun` 有）⇒ 用户刚点暂停，执行线程跑完就把它盖成 completed。
**已修**：实验级加同样的保护，并新增 `isRunPaused(long)`（与 workflow 级同口径）。

**bug 2 · `experiment` 表不同步**
`RunControl.markCoveredPaused()` 只把 `experiment_run` 标 paused，**没同步
`experiment` 表** ⇒ 实验列表显示「执行中」、详情显示「已暂停」，**两处自相矛盾**
（现场会以为还在跑，不会去点继续）。
**已修**：标记后按词表映射（`StatusVocabulary.runToExperimentCaseSql`，
与 `ExperimentExecutor.syncExperimentStatus` 同一口径，不另写一套）同步 experiment 表。

> 这两个 bug 在同步执行 + 设备执行中发暂停的场景下**同时暴露** ——
> 异步执行时实验早跑完，暂停落在已完成的 run 上，两个 bug 都被掩盖了。

## 3. 「让设备执行中真停」怎么实现

### 3.1 先分清两个不同的问题

| 问题 | 现状 | 该怎么改 |
|---|---|---|
| **A. 暂停时，正在跑的动作要不要停？** | 不停（设计如此：「机械臂抓着板会掉」） | 分设备类型决定：**可中断的设备**停，**不可中断的**（机械臂搬运中）不停 |
| **B. 长任务被 30 秒超时误杀** | 会（真机长方法必踩） | 超时改为**按方法/节点取**（`device_method.timeout_sec` 本来就存着） |

**A 是语义决策，B 是纯 bug。** B 必须修；A 需要你拍板。

### 3.2 方案 A1（推荐）：**按「动作可中断性」分级**

真机上，方法分两类：

- **可安全中断**（异步设备）：扫描、读数、孵育（能暂停再续）、离心（多数支持 stop 命令）
- **不可安全中断**（同步机械动作）：机械臂抓板/搬运/放板 —— 中断就是板掉地上

所以正确做法不是"全部停"或"全部不停"，而是**每个方法声明自己能不能中断**：

```
device_method 加一列 interruptible（boolean，默认 false）
  · 机械臂搬运类（Transfer/Grip/Release/Load/Unload）→ false
  · 长工艺类（RunProgram/Incubate/Centrifuge/Scan）→ true
```

然后：

```
① PauseManager.pause 记录暂停时，把「当前正在执行的 commandId + deviceId」写进 run
   （比如 run.pause_command_id / run.pause_device_id）

② 执行侧：driver.execute 等待回包时，用一个「可中断等待」替代阻塞等待
   —— 每 200ms 查一次 (a) run 是否被暂停且该方法 interruptible，
                              (b) 是否收到 stop 请求
   命中就调 driver.abort(commandId)，并把该方法标记为「已中断，可从这一步重试」

③ 中断与暂停的区别要在数据上体现：
   · 暂停（人没点继续）→ 停在原地，等恢复
   · 中断（设备自己停了）→ 节点状态记 aborted/interrupted，恢复时**重跑这一步**
   —— 这正是 resumeAsync 已经支持的语义（未 completed 的行会被删掉重跑）
```

**关键点 ②（实测得来的约束，必须写进实现）**：
`resumeAsync` 删的是 **`status <> 'completed'` 的所有行** ——
所以 **`paused` 与 `aborted` 在续跑时待遇完全一样**（都被删掉重跑）。
⇒ **「中断」这个状态不能靠 `run.status` 区分，只能落在节点状态上**。
   如果中断后仍把 run 标成 `paused`，续跑时用户按"继续"会以为在等人工，
   实际是自动重跑；如果标成 `aborted`，又会被"停止"语义混同。
   建议：节点状态记 `interrupted`（新增词表项），run 状态仍 `paused`，
   **界面明确区分「等人工继续」与「已中断·将自动重试这一步」**。

**关键点 ①（实现约束）**：现在的 `executeNode` 是**一次性阻塞**的，要改成可中断等待。
好消息是 `TcpPersistentDriver.abort` 已经实现了「摘掉 future 让等待方立刻返回」，
所以**驱动层不用改**，只需在 `DriverStepExecutor` 侧接上：
把 `driver.execute(cmd)` 换成「自己管 future + 定期查暂停 + 调 abort」。

### 3.3 方案 A2（保守）：**只停「下一个节点」，但明确告知用户**

如果你认为"动作中途停"风险太高（真机板会掉、离心停了要重新配平），
那就**保持现状**，但要在界面上说清楚：

- 暂停按钮的文案改成「暂停（当前动作会跑完）」
- 运行详情页在「已请求暂停，等当前动作结束」时显示这个状态
- 机械臂搬运中额外提示「板在机械臂上，本次一定搬完」

这是**零代码风险**的选项，但用户体验上"点了暂停没反应"依然存在。

### 3.4 方案 B：超时按方法取（**建议一定做**）

```
① DriverStepExecutor 不再用固定 30s，改为：
   timeout = device_method.timeout_sec（该设备该方法的）
              ?? workflow_node.timeout_sec
              ?? 兜底 30s
② device_method.timeout_sec 已有值，但很多行可能是 NULL/0 —— 需要补默认值
   （按能力给合理默认：离心 5 分钟、孵育 30 分钟、扫描 30 秒……）
③ 长任务（--long）本来就有"先回运行中、再回完成"的双帧机制，
   配合按方法超时才能真正支持"孵育 30 分钟"
```

### 3.5 实现顺序建议

| 步骤 | 内容 | 风险 | 收益 |
|---|---|---|---|
| 1 | **超时按方法取**（B） | 低（只是不再误杀） | 立刻见效，真机长方法不再假失败 |
| 2 | 暂停时**记录当前 commandId**（不改执行语义） | 低 | 为真停铺路 |
| 3 | 执行侧改可中断等待 + 按 `interruptible` 决定是否 abort（A1） | **中高**（涉及真机安全） | 暂停真正能停住可中断设备 |
| 4 | 界面明示「当前动作会跑完 / 已中断可重试」 | 低 | 消除误解 |

## 4. 本轮配套改动：模拟器随机耗时

为了能测「设备执行中发暂停」（固定耗时只有几百毫秒，暂停信号根本来不及在动作中间到达），
模拟器新增了 `--rand-delay`：

```bash
# 语法：--rand-delay MIN:MAX[:SEED]   单位毫秒
java -cp out com.labos.kernel.sim.DeviceSimulator \
     --port 19502 --device 214 --code ID1731 --cap TRANSFER --profile generic \
     --rand-delay 30000:300000          # 30–300 秒随机（真机时序）
```

- **不给 SEED** → 每次调用都不同（真机就是这样）
- **给 SEED** → 序列可复现（测试要这个）
- 优先级：`--rand-delay` > `--delay` > 画像/型号的固定耗时

`scripts/sim-up.sh` 也支持了（第三个参数）：

```bash
./scripts/sim-up.sh LAB-DEMO-02 0 30000:300000   # 全岛设备方法耗时随机 30–300 秒
```

**实测**（10–20 秒区间、种子 42）：四条命令分别耗时 **17.3 / 16.8 / 13.1 / 12.8 秒** ——
都在区间内，且每次不同。

## 5. 边界与未覆盖（诚实清单）

| 项 | 状态 | 说明 |
|---|---|---|
| 「设备执行中真停」 | ❌ **未实现** | 本轮只**实测确认了现状**并给出方案；A1 涉及真机安全，未动生产代码 |
| 「设备正在执行」怎么判 | ✅ 已订正 | `device_state.status='running'` + `current_method`；**不是** `run_command`（那是步结束才落库）——见 §1.5 |
| 机械臂 vs 普通设备的暂停差异 | ✅ 已查清 | **当前没有差异** —— 两者都是「让当前动作跑完」。「机械臂会停」是误解 |
| `abort` 链路 | ✅ 已查清 | 驱动层有实现（`TcpPersistentDriver` 真能摘 future），**但无人调用**；`EC-99-0005` 全库 0 条 |
| 30 秒固定超时 | ⚠ **已定位，未修** | `device_method.timeout_sec` 存了但没人读；长方法必被误杀 |
| 真机长任务（离心 5 分钟等） | ❌ 未覆盖 | 本轮全是仿真机 |
| 中断后「从这一步重试」 | ⚠ **机制已有** | `resumeAsync` 会删掉未 completed 的行并重跑；但没有「中断」这个状态源 |
| 暂停 + 扣留（`runtime_hold`）叠加 | ❌ 未覆盖 | `releaseResources` 的豁免逻辑与中断方案要一起设计 |
| 多个设备并发时暂停 | ❌ 未覆盖 | 暂停是 run 级的，多设备并行时该停哪个 |
| 多设备并行执行中暂停 | ❌ 未覆盖 | 本轮只测了**单设备**执行中暂停；并行时「停哪个」是设计问题 |

## 6. 复跑方式

```bash
export LABOS_DB_HOST=192.168.124.2 LABOS_DB_NAME=labdb \
       LABOS_DB_USER=labos LABOS_DB_PASS='***' LABOS_DB_PORT=5432 PGPASSWORD='***'

# ① 让演示岛某台设备的方法耗时变长（随机；给 SEED 可复现）
cd labos-kernel
pkill -f "DeviceSimulator.*--port 19502"
nohup java -cp out com.labos.kernel.sim.DeviceSimulator \
  --port 19502 --device 214 --code ID1731 --cap TRANSFER --profile generic \
  --rand-delay 10000:18000:7 > /tmp/sim-19502.log 2>&1 &
#   ⚠ 仿真机的 stdout 要单独落文件（sim-up.sh 写 /tmp/sim-<编号>.log，
#     手工起则自己指定）—— 那里能看到「完成 Home（13579ms）」这类真实耗时，
#     用来核对「设备到底执行了多久」。

# ② 跑「设备执行中发暂停」的实测（workflow 级）
cd ..
python3 scripts/e2e-pause-during-device.py --api http://127.0.0.1:18080

# ③ 跑「实验级设备执行中发暂停」（门禁 4.17 用的那个）
python3 scripts/e2e-pause-during-experiment.py --api http://127.0.0.1:18080
```

两个脚本都会自建流程、自造 run、清理现场，并打印「通过 N / 失败 M」汇总行。

> ⚠ **只开一台长耗时仿真机**：并发门禁实例会互相踩（抢同一套仿真机/DB），
> 表现为随机假失败。调试时务必**单实例**跑。
