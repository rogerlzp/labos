## 1. 研究范围与方法

仅研究并测试以下三处事务边界，未触碰其它模块：

1. `WorkflowRuntimeRepository` 的事务边界
   - 写：`required(...)` → `TransactionTemplate`，`ISOLATION_READ_COMMITTED`，每个 public 变更方法一个事务。
   - 读：`snapshotTx` → `ISOLATION_REPEATABLE_READ` + `setReadOnly(true)`。
   - Run 级串行：所有写路径先 `lockRun(...)`（`SELECT ... FOR UPDATE`），锁序 `workflow_run → execution_token/node_activation/node_attempt/...`。
   - 事件连续性：`appendEvents` 单条 `UPDATE workflow_run SET commit_version+1, event_seq=event_seq+N RETURNING` + 逐条 `INSERT runtime_event (first+i)`。
2. 图推进与调度/命令侧的多表写事务
   - `advanceGraphToken*`（`advanceGraphTokenInternal`）：锁 Run → 锁 READY Token → 读变量快照 → 决策 → 插 Activation(RUNNING) → Token→RUNNING → 推进后继 → `GRAPH_NODE_ADVANCED` → `maybeCompleteGraphRun`。
   - `advanceGraphTokenWithVariables`（`b54e0fc6` 引入的**条件网关原子路径**）：在同一个 Run 锁事务内完成「读变量快照 → 求值 → 推进 Token」，避免快照与推进之间的读-改-写窗口。
   - `SEQUENCE / SPLIT / JOIN / END` 后继推进：`split_activation`(OPEN) + `branch_activation`(ACTIVE) + 后继 Token；`JOIN` 汇聚释放（branch→ARRIVED、`arrived_branch_count+1`、达 `expected_branch_count` 时 release join + close split + 建后继 Token）；`END` 经 `maybeCompleteGraphRun` 终结 Run。
   - `advanceCompletedGraphActivation`：SUCCEEDED Activation + CONSUMED Token 的路由（含 REPLAYED / 冲突语义）。
   - `completeAttempt`（T05）：Attempt→SUCCEEDED / branch_output / flow_variable / Activation→SUCCEEDED / Token→CONSUMED / `EXECUTION_RIGHT_RELEASED` / `ATTEMPT_SUCCEEDED`。
   - `reserveCapacity`：`scheduler_capacity`(reserved_count) + Token(READY→RESERVED) + `node_activation`(RESERVED) + `node_attempt`(CREATED) + `dispatch_reservation`(HELD) + `DISPATCH_RESERVED`。
   - `applyCommandEvent`：`command_ledger` + `inbox_receipt` + `worker_execution_fact` + `runtime_event`。
   - `createRun`：`run_request_dedup` 幂等锚点 + definition_snapshot + workflow_run + 起始 Token + `RUN_CREATED`。
3. `GraphCoordinator.advance(...)` 的**多事务循环**：每一步推进是一个独立事务；仅对确定性图错误（`IllegalStateException | IllegalArgumentException | InvalidTransitionException`）调 `failGraphRun`，DB 级故障不得终结健康 Run。

**故障注入方式（不修改核心实现）**：新增测试专用装饰器 `FaultInjectingTransactionManager`，装饰 `PlatformTransactionManager`，在 `commit(TransactionStatus)` 边界注入一次性故障：

- `ABORT_BEFORE_COMMIT`：先物理 `rollback` 再向调用方抛异常（"提交前中断/崩溃"）→ 不允许有任何持久化。
- `LOST_RESULT_AFTER_COMMIT`：先物理 `commit` 再向调用方抛异常（"提交成功但调用方未收到结果"）→ 必须全部持久化且自洽。
- 只读（snapshotTx）事务**从不**被注入；Spring 连接绑定恰好释放一次。
- `armOneShot(mode)` 对下一次**写**提交注入；`armAtWrite(mode, ordinal)` 对第 N 次写提交注入（用于 `GraphCoordinator.advance` 这类多事务调用者在**第 2 个事务**上崩溃，而第 1 个事务保持持久）。整个待注入状态是单个不可变 `Armed` 值，持有于一个 `AtomicReference` 中，读引用与递减序号是一次原子 CAS，不存在「模式」与「剩余次数」两份状态的不一致观察窗口。

选择装饰 `commit` 边界而非包装 `Connection`，可保证 Repository 自身的模板、锁与 SQL 全部保持原样（核心代码零改动），且故障点与真实"进程在 COMMIT 位置崩溃"一一对应。

**约束遵守**：仅新增独立测试类；未修改 Repository / Schema / RuntimeHost / RuntimeDispatchLoop；未引入分布式锁 / 租约 / fencing token / 多实例；未推送 PR #5。

## 6. 发现的 P0 / P1 / P2 问题

### P0 / P1：无（1 项 P1 已在本次修复）

在被测的崩溃场景（提交前中断 / 提交后结果丢失 / 多事务中途崩溃 / 事务回滚）下，Token、Activation、Branch、Event、Run 的状态**全部保持一致**，`event_seq`/`commit_version` 连续性契约成立，幂等重放与相异重放均按设计 fail-closed。**未在被测业务代码中发现阻断级或高优先级缺陷。**

- **P1-1（首版遗留，本次已修复）——测试残留污染共享库**：首版 T10 在回滚后把 `branchB` 的 Attempt 留在 `STARTED`、并遗留 `HELD` 的 `dispatch_reservation`。由于 `WorkflowRuntimeRepository.findInterruptedAttempts(...)` 是**全局（非租户隔离）**扫描 `attempt_state IN ('CREATED','DISPATCHED','ACCEPTED','STARTED')`，`WorkflowRuntimeRepositoryTest#startupRecoveryScansBeyondOneBatch`（无租户作用域、硬断言 `scanned()==2`）在复用同一 `runtime_test` 库的第二次运行中会变为 3 而失败（`expected:<2> but was:<3>`）。
  - 修复：为 T10/T17/T18/T19 增加 `finally` 清理（`recoverInterruptedAttempt` 安全放弃 / DEVICE 且命令 SUCCEEDED 时 `completeAttempt`），使每个用例结束后不再遗留处于扫描集的 Attempt。
  - 验证：G4-B 单跑后 `node_attempt` 扫描集计数 = 0；紧接串跑 `WorkflowRuntimeRepositoryTest` 稳定 36/36 通过（见第 5 节）。

### P2 观察（契约/健壮性）

- **P2-1（既有测试套件隔离性，与 G4-B 改动无关）**：`WorkflowRuntimeRepository.recoverOutboxAfterRestart()` / `recoverAtStartup(...)` 的 outbox 恢复扫描是**全局（非租户隔离）**的。既有测试 `WorkflowRuntimeRepositoryTest.interruptedAttemptAfterSendStartedRequiresManualReconciliation` 断言绝对计数（`leftUncertain()==1`）且自身每次运行都会遗留 1 条 `SENDING` 的 `DEVICE_COMMAND` outbox（`restart-unknown-*` 租户，命令状态 `UNKNOWN`）；复用同一库的多次运行会使其累加并失败（`expected:<1> but was:<3>`，实测复现）。
  - 说明：该失败与该测试类**自身的非幂等性**有关，**与 G4-B 无关**——G4-B 用例使用独立随机 `g4b-*` 租户，且其残留已于 P1-1 修复后归零（本次实测 G4-B 结束后上述 outbox 无 `UNKNOWN` 残留来自 G4-B）。
  - 建议（后续另议）：该 IT 使用独立库，或将该断言改为**租户内计数**。CI 每次对全新 bootstrapped 库执行，故 CI 不受影响。

- **P2-2（契约观察）**：`advanceGraphToken*` / `advanceGraphTokenWithVariables` 没有调用方提供的幂等键。提交后结果丢失时，唯一安全的恢复路径是**重新发现**（`findReadyGraphTokens` / `findCompletedGraphActivations`），而**不能盲重试**（会得到 `StaleRuntimeWriteException`）。这一点已由 T12/T16 实证：丢失结果后 `GraphCoordinator.advance` 再次调用可经重新发现自动推进，而直接对同一已消费 Token 重放会 fail-closed。与 `createRun` / `completeAttempt` / `advanceCompletedGraphActivation`（均带重放语义）不同，该原语是 fail-closed + 发现式恢复，行为安全，但对上层（GraphCoordinator/RuntimeHost）的恢复逻辑是隐含约束，建议在规范中显式写明。

- **P2-3（契约观察）**：`createRun` 的幂等锚点是 `canonicalPayloadJson` 的**字节哈希**。若调用方在重试时提交语义等价但文本不同的 JSON，将得到 `IdempotencyConflictException`（而非幂等重放）。建议调用方在重试前严格复用同一份 canonical payload 字节。

- **P2-4（故障注入层的建模边界）**：`FaultInjectingTransactionManager` 在所有 SQL 均成功执行后于 Java 层主动 `rollback`/`commit`，证明了「单个 Repository 方法未把写操作拆成多事务」与「提交边界之后调用方丢结果的幂等性」，但**不等价于 PostgreSQL 服务端事务中途失败**（如 `pg_terminate_backend` 断连、死锁、中途约束违背后的连接恢复）。当前 19 例已覆盖应用层事务边界的崩溃一致性；若需进一步逼近真实后端故障，建议后续补 1–2 例真实 PG 后端中断用例。

- **P2-5（分支 CI 触发口径）**：`.github/workflows/ci.yml` 与 `workflow-runtime-db.yml` 的 `on.push.branches` 仅匹配 `feat/workflow-runtime-*`，而本分支名为 `test/workflow-runtime-g4b-tx-fault-injection-20261121`。若要远端双门禁自动执行，需推送为 `feat/workflow-runtime-g4b-*` 或通过 PR 触发（当前按要求未推送 PR #5）。
