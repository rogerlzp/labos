## 1. P0 · 两个脚本的幂等（根因：业务状态不释放唯一键）

### 1.1 根因

两个坑是**同一个模式**：

> **用「业务状态」做清理，但业务状态不释放唯一键。**

| 脚本 | 原来的清理方式 | 为什么留不住 |
|---|---|---|
| `verify-role-permissions.py` | `PUT status=archived` | `uk_schedule_plan UNIQUE (tenant_id, plan_no)` **不带状态条件** ⇒ archived 的号**仍然占位** ⇒ 第二次建同号 → 409 |
| `verify-schedule-plans-page.py` | **完全不清理** | Playwright 真实点「新建」建的 plan 留在库里 ⇒ 每跑一次多一条 |

### 1.2 修法

| 改动 | 内容 |
|---|---|
| **新增 DELETE 端点** | `DELETE /api/schedule-plans/{id}`（`ScheduleController` + `ScheduleMapper` + XML）。**物理删**（`schedule_plan` 没有 `deleted_at`）⇒ 释放 `plan_no`。生产侧也用得上：排程建多了要能删 |
| `verify-role-permissions.py` | ① planNo 加**运行期唯一后缀**（不靠清理保证不撞）② 清理改 **DELETE**（真清理）③ **自备账号**：operator/designer/viewer 自己建/重置口令（CI 新装库只有 admin）④ 顺带清掉历史残留 |
| `verify-schedule-plans-page.py` | ① 前置清理**自动生成号**的 plan（`PLAN-<数字>`，页面上「新建」产出的那种；手工排程有业务 planNo，不受影响）② 记录新建前后**列表差集**，结束时删掉 ③ 新增断言「点完新建后列表里**真的多了一条**」（原来只断言"有反馈"，没断言数据落地） |

### 1.3 实测

```
verify-role-permissions.py      第1次 31/0   第2次 31/0   终态 plan=0
verify-schedule-plans-page.py   第1次 10/0   第2次 10/0   终态 plan=0
DELETE 端点：不存在 id → 404 {"error":"排程不存在: 999999"}
              viewer 删 → 403 {"error":"当前账号（viewer）无写权限"}
              admin 删 → 200 {"deleted":1,"id":...}
```

断言数变化：role-permissions **20 → 31**（+账号自备 3、+清理 2、+DELETE 4、+"被拒后仍在" 1、
+负数/超上限夹紧 2）；schedule-plans-page **5 → 10**。

## 2. P0 · 验收门槛从「文字要求」变成「可执行门禁」

原来 §7 E 只有一句文字要求（"8 个 verify 每个都要连跑两次"）—— 靠人记。

**新增 `scripts/verify-idempotency.py`**：

| 断言 | 内容 |
|---|---|
| ① | 第一轮各脚本 0 失败 |
| ② | 第二轮各脚本 0 失败 |
| ③ | **同一个脚本两轮的「通过数 / 失败数」逐个相同** |
| ④ | 终态 `schedule_plan=0` / `resource_booking=0` / `stale_run=0` |

**入选标准（hermetic）**：不占设备、不建 run、不依赖历史数据、跑完自己干净。
需要前端/Playwright 的脚本在环境不具备时**显式 SKIP**（不静默算通过）且不参与两轮比对。

```
python3 scripts/verify-idempotency.py
  第1轮：role-permissions 31/0 · p2-scheduler 13/0 · binding-api 7/0 · schedule-plans-page 10/0
  第2轮：同上
  两轮比对：4 个脚本逐个一致
  终态：resource_booking=0 · schedule_plan=0 · stale_run=0
  通过 15 / 失败 0 / 跳过 0
```

**接入 CI**：

| 位置 | 改法 |
|---|---|
| `scripts/ci-gate.sh` | 新增 **段 2 · 幂等门禁**，`--idem` 开启（默认不开 —— 段 0 的定位是"不碰设备/库"） |
| `.github/workflows/idempotency.yml`（**新建**） | push 到 main + 每天 19:00 UTC；带 PG service、灌库、起内核、起前端、装 Playwright，跑 `ci-gate.sh --idem` |
| `ci.yml` | **不动** —— 它的定位写得很清楚："只跑**不需要数据库**的部分"，幂等门禁必须连库（要造数、要清数据） |

> 为什么不塞进 `ci.yml`：那是每次 push 都跑的作业，加 PG + 灌库 + 起内核 + 起前端会让每次提交都慢好几分钟，
> 而幂等门禁**每晚跑一次 + 每次 push 单独一个 job**已经足够防复发。

## 3. P2-1 · 两条自动卸载路径的判别性自测（挖出一个真缺陷）

### 3.1 缺口确认

`docs/交接-系统完善验收-20261114.md` §「实验结束自动卸载」记着：

> 脚本只覆盖 Controller 这条手动卸载路径；`ExperimentExecutor.settle` 与
> `BatchOrchestrator.syncExperimentStatusFromBatches` 是同一套 SQL 顺序修复，**尚无独立判别性脚本**。

核实：`BatchDbSelfTest` 有 **20 个 section**（批次编排几乎全覆盖），但 `grep unload|unloaded|placement|position_state|lifecycle` **零命中** ⇒ 缺口属实。

### 3.2 新增 `MaterialUnloadPathsDbSelfTest`

**关键设计**：两条路径的入口方法都**可直接调**，不必真跑 workflow、不碰设备、不受调度器状态影响：

| 路径 | 入口 | 可见性 |
|---|---|---|
| 非批次 | `ExperimentExecutor.settle(runId, "completed", 0, null, null, null, true)` | **package-private**（其 JavaDoc 明说"供 RunControlDbSelfTest 直接压这条异常敏感路径"） |
| 批次 | `BatchOrchestrator.syncExperimentStatusFromBatches(experimentId)` | **public** |

**判别点**：批次路径下，**只有一个批次终态时不得卸载**（聚合非终态），全部批次终态后才卸载 ——
这条断言能区分"聚合终态才卸载"与"见一个终态就卸"。

### 3.3 🔴 挖出的真缺陷（已修）

```
── 2. 批次路径：单批终态不卸载，整单聚合终态才卸载（判别点）──
  ✓ 聚合非终态（aggregate=running）
  ✓ ★ 单批终态但整单未终态 ⇒ process 物料**未卸载**（判别点）
  ✗ 整单终态后 process 物料未卸载（placement.status=loaded）
  ✗ 整单终态后 process 点位仍占用
```

**根因**：`BatchPlanner.aggregateExperimentStatus` 里"全部批次跑完"的终态值是 **`"finished"`**（不是 `"completed"`），
而 `BatchOrchestrator.syncExperimentStatusFromBatches` 的卸载触发条件只列了
`completed / failed / aborted / cancelled` ⇒ **`"finished"` 不在里面**。

⇒ **正常跑完的批次实验，process 物料永远不会自动卸载** —— 板子一直占着点位，下一批装不进去。

**修法**：把"实验终态"抽成一个共享判定（`BatchOrchestrator.isExperimentTerminal`），
覆盖 `completed / finished / failed / aborted / cancelled`：

```java
static boolean isExperimentTerminal(String status) {
    if (status == null) return false;
    switch (status) {
        case "completed": case "finished": case "failed":
        case "aborted": case "cancelled":
            return true;
        default: return false;
    }
}
```

> **为什么值得单独抽一个方法**：实验状态的"终态"有两个来源，**字面量不一样** ——
> 非批次 `ExperimentExecutor.settle` 用 `"completed"`，批次聚合用 `"finished"`。
> 两边各写一份字面量列表，早晚有一边漏（这次就漏了）。凡写终态列表的地方都该走同一个判定。

**修后实测**：

```
── 1. 非批次路径：run 终态即卸载 process 物料，inventory 原位不动 ──
  ✓ process 物料 placement → unloaded      ✓ process 物料点位已清空
  ✓ inventory 物料 placement 仍 loaded     ✓ inventory 物料点位仍占用（原位不动）
── 2. 批次路径：单批终态不卸载，整单聚合终态才卸载（判别点）──
  ✓ 聚合非终态（aggregate=running）
  ✓ ★ 单批终态但整单未终态 ⇒ process 物料**未卸载**（判别点）
  ✓ 单批终态时 process 点位仍占用
  ✓ 全部批次终态 ⇒ 聚合终态（aggregate=finished）
  ✓ process 物料跨批次被卸载      ✓ 整单终态后 process 点位已清空
  ✓ inventory 物料原位不动（批次路径同样）
通过 11, 失败 0
```

连跑两次 **11/0 / 11/0**，残留（position_state / device_point / resource_node / plate /
manifest_item / placement / experiment / run / batch / template）**全 0**。

已接进 `scripts/test-all.sh` 的连库自测组。

### 3.4 写自测踩过的库口径（留给下一个人）

| 坑 | 正确做法 |
|---|---|
| `position_state` 主键是 **(tenant_id, resource_id)** —— 一点位只有一行 | 自测**自造虚拟点位**（`resource_node` + `device_point`），别用现成点位（会跟别人的板撞车、cleanup 也不敢删） |
| `position_state.plate_id` 是 **varchar（条码）**，`content_id` 才是 `plate.id` | 插的时候别把 id 当条码塞 |
| `workflow.graph` 是 **jsonb** | 参数要 `?::jsonb` |
| `device_point` 的 `ck_device_point_flags` | `point_role='both'` ⇒ `is_entry`/`is_exit` 至少一个为真 |
| 清理**每条独立事务** | 共用大事务的话一条失败后面全 aborted ⇒ 清理等于没做（下次 seed 直接撞唯一键） |
| 清理要**按 resource_id / experiment_id** | 按 `plate_id`（卸载后被置 NULL）或固定 id 都会漏 |

## 5. 🔴 顺手挖出并修掉的失效 CI workflow

`.github/workflows/e2e-nightly.yml` 之前**根本跑不起来**：

```yaml
nohup java -cp "out:lib/postgresql-42.7.3.jar" \
  com.labos.kernel.api.ApiServer 18080 >/tmp/labos-api.log 2>&1 &
```

但 **`ApiServer.main` 已在 A 批删除**（`scripts/start-kernel.sh` 头注：「A 批：`java -cp out ... ApiServer 18080` 已删除（ApiServer.main 不再存在）」）
⇒ 内核起不来 ⇒ health 检查失败 ⇒ **这个 job 一直必红**。
而且 classpath 也少了 `lib/spring/*`（Spring Boot 依赖）。

**正确启动方式**（已同步修进 `e2e-nightly.yml` 和新建的 `idempotency.yml`）：

```bash
java -cp "out:lib/postgresql-42.7.3.jar:lib/spring/*" \
  com.labos.boot.LabosApplication
```
