# 03 · 设备命令生命周期验收（第一版 · 字段级清单）

> 接 02 §2.3。本文把命令生命周期细化到表/字段级证据 + 测试方法。
> 设计要求：`runtime-consistency/02`（五态 + UNKNOWN + 幂等 + 超时查询）。

> **二次评审修正（2026-11-14）**：命令生命周期在 `command_ledger`（P-07），
> **不在 `run_command`**。`run_command` 是 step 级台账（完成时写 rawResponse），
> 它「无状态推进 UPDATE」是设计如此，不是缺口。

## 3.1 现状证据（字段级）

| 字段/表 | 现状 | 设计要求 | 判定 |
|---|---|---|---|
| `command_ledger.state` | DISPATCH_STARTED→ACKED/FAILED/UNKNOWN + abort + reconcile + resolve | 生命周期可观测 | **PASS** |
| `command_ledger.idempotency_key` | 同 key 唯一，重复派发被拦（begin 返回 created=false） | 幂等 | PASS |
| `command_ledger.command_id` | 有 | 重发复用同一 id | PASS |
| `run_command.sent_at` / `finished_at` | 有（下发/回包时刻） | 保留 | PASS |
| `run_command.status` | step 级台账，完成时落终态（无中间态是设计如此） | —（非命令生命周期表） | 不适用 |
| 细粒度 `RECEIVED`/`EXECUTING` | 无（当前设备/模拟器不分别回报） | 可选增强 | 未来 |

## 3.2 测试方法（已覆盖 / 待补）

| 场景 | 测试方法 | 当前是否有 |
|---|---|---|
| 派发前落账 + 回包终态 | `CommandLedger.begin`→DISPATCH_STARTED、`finish`→ACKED/FAILED | ✅ `CommandLedgerDbSelfTest` |
| 重启陈旧派发标 UNKNOWN | `reconcileOnStartup` | ✅ `CommandLedgerDbSelfTest` |
| 重复命令幂等 | 同 idempotency_key 二次 begin → created=false | ✅ `CommandLedgerDbSelfTest` |
| 细粒度 RECEIVED/EXECUTING | 需设备分别回报 ACK/执行中 | ❌ 未来（设备支持后补） |

## 3.3 结论

- **命令生命周期已实现并测试**（`command_ledger`，P-07）。R4 判定从 GAP 改为**已实现**。
- 剩余的是**可选增强**（细粒度 RECEIVED/EXECUTING），不是阻塞项。
