## 0. 目标形态（一句话）

> **把 LabOS 从"能跑流程的中控"做成"能被智能体安全驱动的中控"：
> 智能体可以问现场、可以提协议、可以试跑，但每一条物理动作都必须过同一道闸门链。**

三句话说清分工：

| 谁负责 | 干什么 | 不干什么 |
|---|---|---|
| **推理模型**（可换，模型无关） | 读现场 → 设计协议 → 诊断异常 | **不直接碰设备**，不下发物理命令 |
| **中间件（LabOS）** | 回答"此刻能不能执行"→ 试跑 → 校验 → 派发 → 留痕 | **不判断科学结论**（反应本身靠仪器回填） |
| **现场设备** | 执行 | — |

这与外部方案 A 的分工一致：**"不保证实验科学上成立，只保证实验物理上没有作弊"。**

### 1.1 为什么 agent 入口是独立进程

> **修订（2026-11-16 外部核验后）**：原文写"沿用仓库既有先例（SiLA 2 适配器：独立进程，不给内核加依赖）"。
> 实测**仓库内并无 SiLA 2 适配器实现**——无独立进程、无连接器代码；SiLA 只出现在 `README.md:330`（roadmap 提及）、
> `LABOS_PAUSE_EXTERNAL_PRACTICES_AND_ADR_20261107.md:376`（列为待评估）、
> `docs/评审记录/20261111-01-hunyuan.md:126`（说明 PyLabRobot 的 `io/sila` 只是客户端 wire helper，不是 server）、
> 以及 `pg_rebuild/schema` 的 `driver_protocol` 枚举值 `'sila2'`。
> **"独立进程、不给内核加依赖"这条原则本身成立且值得坚持**，但依据应从"既有先例"改为**架构原则**。

独立进程的依据是三条架构原则，不是某个先例项目：

- 内核依赖保持干净：Spring Boot Web/AOP/JDBC + MyBatis + Lettuce + PG，**不因接了 agent 就多一个 SDK**
- agent 崩溃/升级不影响现场执行
- 工具分级、只读模式、来源标注等**策略**在 agent 侧实现，**安全**在内核侧实现——两侧都坏也拦得住

## 2. 三个必须新建的能力（不是改造）

### 2.1 孪生快照：可复制、可版本化

外部方案 A 的"时间压缩仿真"前提是**能复制一份现场**。LabOS 现在的状态是**分散在多张表里的活值**，
没有"复制"这回事——直接拿真表去跑仿真会污染生产。

**新建**：

| 项 | 内容 |
|---|---|
| 表 | `twin_snapshot(id, tenant_id, run_id, scope_type, scope_id, twin_version, payload jsonb, created_at)` |
| 服务 | `TwinStateService`：读现表 → 装配 `TwinState`（**不可变对象**） |
| 接口 | `POST /api/twin/snapshot`（落一份快照）/ `GET /api/twin/snapshots/{id}`（取回） |

**关键设计：快照不可变 + 版本号。**
`twin_version` 是单调递增的，仿真读的是某个版本号，**改一个字段不会污染历史快照**。
没有版本号，"上次那条报警是哪个状态下的"就永远答不出来。

**装配口径**（第一版只装这五类，其余不装）：

```
TwinState {
  plates:    [{plateUid, barcode, status, wells: [{well, volume, sampleId, aliquotId}]}]
  positions: [{resourceId, slotIndex, plateUid, occupiedByRun, reservedUntil}]
  devices:   [{resourceId, status, hasPlate, readyGive, readyTake, lastError}]
  consumables:[{lotId, code, remaining, location}]
  tips:      [{tipId, channel, status, lastUsedRun, lastUsedNode}]
}
```

**"液面多高"怎么办**（外部方案 A 的原话是"液面多高"）：
孔板规格已知（`plate.rows/cols/plate_type`）⇒ **液面高度可由体积与孔型推算**。
第一版只给**体积 + 推算液面（标注为推算值）**，不做流体仿真。

### 2.2 物理不变量引擎：规则即数据

外部方案 A 的安全架构第一条是**把容器容量、几何间隙、最大搅拌速度、化学兼容性矩阵编码成机器可检查的不变量，在仿真闸门处强制**。

LabOS 的既有先例非常好用：**`recovery_policy` 表**（错误码 → scope/strategy/params/max_attempts/priority/enabled）
已经把"规则即数据"这条路走通过一遍（`pg_rebuild/schema/90_all_in_one.sql`）。
**物理规则照抄这个形状**：

```sql
-- 草案：镜像 recovery_policy 的形状
CREATE TABLE IF NOT EXISTS physical_rule (
  id             bigserial PRIMARY KEY,
  tenant_id      bigint       NOT NULL REFERENCES tenant(id),
  rule_code      varchar(64)  NOT NULL,          -- EC-PHYS-*
  scope_type     varchar(32)  NOT NULL,          -- plate | device | position | consumable | transfer
  subject        jsonb        NOT NULL,          -- 规则作用对象的选择条件（能力/方法/设备类型…）
  assertion      jsonb        NOT NULL,          -- 断言：{"kind":"volume_ge","field":"source.volume","op":">=","value":50}
  severity       varchar(16)  NOT NULL DEFAULT 'block',  -- block | warn
  enabled        boolean      NOT NULL DEFAULT true,
  origin         varchar(32)  NOT NULL DEFAULT 'manual', -- manual | mined | derived
  sample_count   int          NOT NULL DEFAULT 0,
  created_at     timestamptz  NOT NULL DEFAULT now(),
  updated_at     timestamptz  NOT NULL DEFAULT now(),
  CONSTRAINT uk_physical_rule UNIQUE (tenant_id, rule_code)
);
```

**引擎是纯函数**：`PhysicalRuleEngine.check(TwinState, Command) → Verdict{allow, violatedCode, reason}`。
与 `InterlockContract` 的 fail-closed 口径一致：**规则未登记 = 不拦**（不是 fail-closed），
因为规则引擎是**新增能力**，不是既有安全语义的一部分——这一条与外部方案 A 相反，**必须写进文档说清楚**。

**为什么"未登记=不拦"是安全的**：
既有安全语义（L1–L5、扫码、账本）**一条不动**；物理规则层是**增量拦截**，
漏一条规则的后果是"没拦住"（退化为现状），不是"停摆"。
而 2026-11-15 的 L4 事故说明的是**反过来**才危险。

### 2.3 命令块执行：BPMN 子图独立过闸

**这是最大的一块新建项，也是"像不像外部方案 A"的关键。**

外部方案 A 把协议切成 **command block**，一段可以是一次梯度稀释，也可以是长协议的一节，
**每块独立过闸**。它的 agent 因此可以"提一小段 → 验 → 跑 → 看 → 再提下一段"。

LabOS 现状：
- `Graph` = `nodes: Map + edges: List`（`WorkflowGraphParser.java:87`）—— 是普通图，**可投影**
- `GraphRunner.run(Graph, StepExecutor)`（`GraphRunner.java:681`）—— **执行器本身与图无关**
- BPMN 的 `subProcess` 是**视觉分组**（`BpmnExpander.java:25-34`：多步节点折叠成 subProcess，内部节点仍要执行），**不是可调用的块**
- **没有 callActivity 语义**；`presetRunId` 只是复用已有 run（`WorkflowService.java:816-820`），**不是起点选择器**

⇒ **LabOS 现在无法"执行一段流程"**。agent 只能整条提交，或者什么都做不了。

**新建**：

| 项 | 内容 |
|---|---|
| 表 | `command_block(id, tenant_id, name, workflow_id, node_keys jsonb, params jsonb, status, created_at)` |
| 投影 | `GraphProjector.project(parentGraph, blockDef) → Graph`（取子集节点 + 内部边 + 入口/出口边） |
| 执行 | 复用 `GraphRunner` + **同一条闸门链**（`DriverStepExecutor`），**不开旁路** |
| 接口 | `POST /api/blocks/validate`（**只校验，返回 verdict，不执行**）<br>`POST /api/blocks/execute`（校验通过才执行） |

**两段式是硬要求**：外部方案 A 的"先验证再派发"在 agent 场景下更严格——
agent 需要**在不碰设备的前提下**知道这段能不能跑（否则它只能靠试错试出来）。

## 3. 数据层新增表一览

| 表 | 用途 | 替代/补充 |
|---|---|---|
| `twin_snapshot` | 孪生快照（不可变 + 版本） | 新 |
| `tip_usage` | 枪头级使用台账（run/node/channel/动作/体积/吸液高度） | 新（`consumable_lot.remaining` 只有批次余量） |
| `physical_rule` | 物理不变量（规则即数据） | 新 |
| `rule_hit` | 闸门命中记录（影子模式靠它观察） | 新 |
| `unmodeled_effect` | 未建模物理登记表（现象/假设/证据/状态） | 新 |
| `command_block` | 命令块定义 | 新 |

**写入方纪律（关键）**：

```
孪生状态的唯一写入方 = 物料投影(T2) + 设备事件
业务代码不得直接写 plate_well / tip_usage
```

多写入方必然状态漂移；状态一漂移，"可查询内省"就退化成"从日志猜"——那整套东西白做。

| 工具 | 约束 |
|---|---|
| `labos_execute_block(blockId, params, dry_run)` | **不允许旁路**：`validate → L0 → 既有 L1–L5 → 账本 → 派发` 一条都不少 |
| `labos_abort(run, reason)` | 走既有 `abort` 契约（`DeviceDriver.abort`） |

### 4.3 工具分级（照抄竞品已验证的做法，但**不写竞品名**）

| 级 | 含义 | 例子 |
|---|---|---|
| READ | 只读 | `labos_twin_state` |
| CONTROL | 改变现场但可回滚 | `labos_execute_block` |
| HAZARD | 不可回滚 / 危险设定点 | ——（本方案第一版**不开放 HAZARD**） |

**三条硬要求**：
1. **只读模式**：全局开关，只读模式下 CONTROL 工具直接拒绝
2. **来源标注**：凡是来自仿真的数据，**必须**带 `"source":"simulation"` 标记（外部方案 A 与竞品都强调这条）
3. **`trace_id` 透出**：仓库已有 `audit_log.trace_id`，MCP 层要能原样带出来

## 5. 关键设计决策（每条含"为什么不选另一种"）

| # | 决策 | 理由 | 被否掉的替代方案 |
|---|---|---|---|
| D1 | agent 入口独立进程 | 内核依赖不膨胀；agent 挂了不影响现场 | 内核内嵌 MCP SDK（污染依赖，违背 SiLA 先例） |
| D2 | 孪生快照不可变 + 版本号 | "复制一份现场"的前提；历史可回溯 | 直接读真表跑仿真（污染生产）、只存一份（无法追责） |
| D3 | 物理规则**即数据**（表驱动） | 镜像 `recovery_policy` 已验证的模式；运营可改、可回滚 | 规则写死在代码（改一条要发版） |
| D4 | 未登记规则 = **不拦** | 新增能力只做增量拦截；"没拦住"退回现状，"误拦"= 停摆 | fail-closed（会重演 L4 停摆） |
| D5 | L0 物理闸门插在**最前** | 纯计算只读 ⇒ 物理不可行时不产生任何位置预留/资源占用 | 插在账本后（已经占资源才说不行 ⇒ 泄漏） |
| D6 | 命令块 = BPMN 子图投影，复用 `GraphRunner` 与同一闸门链 | 不新开旁路 ⇒ agent 与人工流程**同一条安全路径** | 为 agent 单独写执行器（必然产生第二套安全语义） |
| D7 | 回流闭环**只到"人工确认的规则维护"**，不做学习模型 | 外部方案 A 的残差学习依赖真实湿实验数据；LabOS 的仿真不建模流体与光学，**学不出真残差** | 上残差学习（会得到"看起来很准、实际是假的"模型） |
| D8 | 新闸门默认**影子模式** | 2026-11-15 L4 事故的直接对策：`shadow → 观察 → on` 三步走 | 默认强制（重演全平台停摆） |

## 6. 实施批次

> 每批**独立可验收、可回滚**。M1/M2 **不依赖客户资料与现场标定**（本机可做）。
> 测试分档按 `docs/测试总纲.md`（T0 每次提交 / T1 按 diff / 连库档）。

### M1 · 孪生状态与血缘

> **前置（阻塞项，2026-11-17 已解锁）**：上游文档的 **Q10** 已裁决为**拆表**——
> 设计态独立成表 `plate_well_design`，`plate_well` 只保留运行态。
> 理由与代价：拆表后"唯一写入方"才是真的唯一（设计态 = `QpcrLayoutController`，运行态 = 物料投影 T2）；
> 迁移成本接近零——当前 `plate_well` 的行**全部**是设计态行（运行期写入方尚不存在），迁移即"搬到新表 + 清空原表"；
> 两表列名/类型/精度全同（`volume` 同为 `numeric(12,3)`），仿真器容差口径不变。
> **落地前仍须完成**：migration 合入 `pg_rebuild/migration/` + 挂 `merge.sh` + 重跑产物一致性检查，
> 以及 §5 列出的 19 个读写点改动。拆表方案与已实测的 migration 草案见**本地研究材料**（`private/`，不外发）。

| 交付 | 落点 |
|---|---|
| `TwinStateService` + `GET /api/twin/state` | `kernel/src/main/.../twin/` |
| `twin_snapshot` 表 + 快照存取 | 新 migration |
| 孔级体积写入（物料投影 T2） | `material/MaterialEffectService.java:346/510` |
| `tip_usage` 台账 | 同上 |
| `unmodeled_effect` 登记表 | 新 migration + 最小录入面 |

**验收**
- T0：装配纯函数单测（同输入同输出；缺字段不抛异常）
- 连库：一次分液后 `GET /api/twin/state` 的孔体积 / 枪头 / 板位三者自洽
- **孪生差分断言（新增）**：复用已有的孪生差分机制（`TwinDiffService` / `TwinDiffController` /
  `twin_diff_report` 表 / `pylabrobot-sim/run_simulator.py --diff-source ledger|db|twin-json`），
  要求 PyLabRobot 侧 `volume_tracker` 与库内 `plate_well` 的**逐孔差值在容差内**。
  ⇒ **M1 不要再另建一套一致性检查**，把差分报告升级为常态校验即可。
  （注意：现有差分机制比对的是"PyLabRobot vs `plate_well`"，而 `twin_snapshot` 表与 `TwinStateService`
  在 `pg_rebuild/` 与 `migration/` 中**均不存在**，只在本方案 §2.1 出现。）
- **`tip_usage` 写入方与孔体积同源（新增）**：仓库目前**无 tip 级台账**（`tip_box` 只是 `physical_type` 的枚举值，不是表）。
  `tip_usage` 的写入方必须与孔级体积**同一次物料投影**落库；**不得先建空表再补写入方**——
  否则会造出第二个"有结构无血缘"的死字段。
- **设计表不被写入方外溢（新增，拆表后专属）**：`plate_well_design` 在 M1 上线后**行数不再变化**，
  证明运行期写入方没有外溢到设计态表。取证方式：连库对比 M1 上线前后 `plate_well_design` 的行数与 `updated_at` 最大值。
- **不破坏**：既有 1226 单测基线保持全绿

### M2 · 物理不变量引擎 + L0 闸门（影子模式起步）

| 交付 | 落点 |

**第一批规则**（只做能确定判的）：

| 规则 | 判据 | 数据来源 | 数据源成熟度（2026-11-16 实测） |
|---|---|---|---|
| `EC-PHYS-VOLUME` | 源孔体积 ≥ 计划取量 + 底部间隙容差 | `plate_well.volume`（M1 接通后） | **运行期无写入方**（Q10 裁决后才可用）；且须只读运行态来源，不得读设计态写入方的值 |
| `EC-PHYS-CONSUMABLE` | 耗材余量 ≥ 计划通道数 | `consumable_lot.remaining` | **唯一写入方是人工 REST 录入**（`StockController.java:203/370`，`ConsumableMapper.xml:100-103/356`），运行期无自动扣减 |
| `EC-PHYS-GEOMETRY` | 通道间距 ≤ 槽长 | `device_point` + 耗材规格 | 取决于现场布局配置（当前为空） |
| `EC-PHYS-UNREACHABLE` | 目标位可达 | `device_point.robot_reachable` | 取决于现场标定 |
| `EC-PHYS-UNCALIBRATED` | 标定数据质量 | `robot_point.fill_status` | DDL 默认 `'ok'`（`93_m1_parallel.sql:161`），"全 pending"是**当前数据态**而非结构约束 |

> **影子期的验收口径（新增）**：上表五条规则里有三条的数据源**当前不成熟**（人工口径 / 空配置 / 标定口径）。
> 因此影子期验收标准应是「**不误拒**」而不是「命中」——用人工录入的余量去判物理闸门，误报是必然的。
> 命中记录必须标注数据来源为「人工口径 / 标定口径 / 空配置」，以便区分"规则不适用"与"规则不通过"。
> 另建议**按规则标注数据来源可信度**，避免后续把影子期命中当成设备真实缺陷上报。

**验收**
- T0：注入 5 类违规 → 各自命中对应规则；数据缺失 → **不拦**（记 `rule_hit`）
- 连库：影子期 **误拒 0**（连续 N 个 run 全放行且命中记录可解释）
- 切 `on` 后：违规命令被拒，错误码与作用域正确，**既有流程不被误伤**

## 7. 风险与反证（新增角度）

| # | 质疑 | 回答 |
|---|---|---|
| A1 | **agent 会不会绕过闸门直接下发？** | D6 + §4.2：命令块复用 `GraphRunner` 与同一条 `DriverStepExecutor` 链；agent 侧没有任何物理下发通道（内核只暴露 HTTP） |
| A2 | **规则会不会越加越多、越加越拦？** | 规则有 `enabled` 与 `severity`；`rule_hit` 提供命中率看板；连续无命中的规则**必须下线**（否则就是噪声） |
| A3 | **孪生状态和真实现场不一致怎么办？** | 快照是**读时装配**的，会漂。缓解：孪生状态与 `position_state`/`device_state` 的一致性巡检；不一致时**快照标记不可信**并拒绝用于试跑 |
| A4 | **时间压缩仿真会不会给人错误信心？** | 仿真结论**必须标 `source=simulation`**；真机结论只能靠影子模式（且影子模式默认关闭、只允许只读方法） |
| A5 | **命令块会不会绕过 BPMN 的图校验？** | 投影后的子图**仍走 `GraphRunner`**（异或/并行/回边/循环上限语义一致），不新写执行语义 |
| A6 | **这是不是又在堆概念？** | 每批都能独立验收；M1 结束时已有可用查询面，M2 结束时已有影子数据，M3 才有试跑，**M4 才碰 agent**。任一批可停 |
| A7 | **仓库规矩会被破坏吗？** | 新增表走 `pg_rebuild/schema/` migration 分片；新进程照 SiLA 先例；测试分档照 `docs/测试总纲.md`；**英文镜像待补**（Q7） |

## 8. 明确不做（边界）
