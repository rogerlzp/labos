# 设备 ID 空间与型号解析（三套 bigint 的收口）

> 2026-11-16。对应台账 `BUG-20261116-02`。
> 起因：提取线 4 个失败节点被判 `EC-05-1007`（超时），根因不是慢，而是**超时上限查错了行**。

---

## 0. 一句话

同一台设备在库里有**三套 bigint 主键**（实例号 / 资源号 / 型号行号），代码把它们混用 ——
SQL 不报错，只是**查错行**；再被 `COALESCE(MAX(..),0)` 吞成 0 就完全静默。
本次把「型号列」改名、把换算收成一个唯一入口、把三套 id 做成不可互换的类型，
并用**源码不变量测试**把这条约束钉成会红的用例。

---

## 1. 三套 id

以提取线的 DISP3 为例：

| id 空间 | 表 / 列 | DISP3 的值 | 谁在用 |
|---|---|---|---|
| **实例号** | `device_instance.id` | `1000039` | 运行期 `StepContext.resourceId()`、设备锁、心跳、命令账本 |
| **资源号** | `resource_node.id` | `1000524` | 拓扑树、点位（`device_point`）、能力绑定（`resource_capability`）、位置锁 |
| **型号行号** | `device.id` | — | `device_method`、错误码、型号属性。`device` 表的注释就是「**设备型号定义**」 |

三者的关系只有一条链：

```
device_instance.resource_id    → resource_node.id   （资源号）
device_instance.device_model_id→ device.id          （型号行号，2026-11-16 前叫 device_id）
device_method.device_model_id  → device.id          （方法库挂在型号上）
```

> `device_method` 另有 `device_instance_id`（P1 引入）：那是**型号级方法 + 实例级覆盖**，
> 语义明确，不参与本次改名。

## 2. 缺陷形态

### 2.1 查表落空（优先级链整条是死的）

`DriverStepExecutor.resolveTimeoutMs` 拿**实例号**去匹配**型号行号**（改名前）：

```sql
SELECT COALESCE(MAX(timeout_sec), 0) FROM device_method
 WHERE tenant_id = ? AND device_id = ?     -- ← 传进来的是 device_instance.id
```

不撞号 ⇒ 0 行 ⇒ `COALESCE` 返回 0 ⇒ **静默**退回能力默认（600s）。
后果：现场标定出来的真实耗时**永远调不出来**，而且日志上一个异常都没有。

### 2.2 撞号（白捡别人的上限）

提取线实例号 `1000037~1000045` 恰好落在旧演示岛遗留的型号行号区间上：

| 实例 | 实例号 | 实际命中 | 被套上的上限 |
|---|---|---|---|
| DISP1 | 1000037 | `CAROUSEL_EXTRACTOR_GENERIC` 转盘提取仪 | 22s |
| DISP2 | 1000038 | `DISPENSER_PLATE_GENERIC` 分液器 | 32s |
| **DISP3** | **1000039** | **`GANTRY_ROBOT_GENERIC` 轨道机械臂** | **7s** |
| DISP4 | 1000040 | `PLATE_STACK_GENERIC` 耗材栈 | 12s |

DISP3 的分液动作实际 8 秒 ⇒ 7 秒上限 ⇒ `EC-05-1007` ⇒ 重试 3 次 ⇒ 转人工。

### 2.3 第三个受害者（本次一并修掉）

同一个病根还有一处，之前没被发现：**设备锁等待上限**

```sql
-- QueryMapper.selectDeviceLockTimeoutSec（改前）
SELECT COALESCE(MAX(timeout_sec), 0) FROM device_method
 WHERE tenant_id = ? AND device_id = ?     -- ← 同样是实例号
```

⇒ 抢锁要等多久也取决于"撞上了谁的型号"。落到能力默认区间时表现为
「设备被占用超过 60 秒」这种误导性提示。

另外 `selectMethodInterruptible`（可中断判定）也是同一形态：
撞号时会**误判某方法可中断**（把不该停的动作当可停），这是安全事故级别的方向。

### 2.4 这不是边缘情况（测试库实测）

`device_instance` 与 `device` 两张表都是 `GENERATED BY DEFAULT AS IDENTITY`、**从 1 开始各自自增**
⇒ 两套 id 的数值区间**高度重叠**，撞号是常态不是巧合。测试库 `labdb`（2026-11-16，迁移前数据）：

| 指标 | 数值 |
|---|---|
| `device_instance` 未删实例 | **262** |
| 实例号恰好命中某个 `device.id`（撞号） | **63**（24%） |
| 其中撞到的是**别的型号** | **63**（100%，没有一个撞到自己型号） |
| 撞上的型号有非 0 `timeout_sec`（会真的套上去） | **56** |
| 型号未登记（`device_model_id` 为空） | 0 |

修复前后同一批设备拿到的**型号库超时上限**（`MAX(timeout_sec)`）抽样：

| 实例 | 设备编号 | 自己型号 | 修复前命中 | 修复前 | 修复后 | 后果 |
|---|---|---|---|---|---|---|
| 167 | ID-1131 | EQ145 | EQ167 | **20s** | 600s | **偏小**：超过 20 秒的动作全被误判超时 |
| 169 | ID-1171 | EQ161 | EQ169 | 900s | 600s | 偏大 |
| 171 | ID-1183 | EQ154 | EQ171 | 600s | **1800s** | **偏小**：该等 30 分钟的只等 10 分钟 |
| 164 | ID-1161 | EQ149 | EQ164 | **1800s** | 600s | **偏大**：真挂了要干等 30 分钟才转人工 |
| 172 | ID-0018 | EQ145 | EQ172 | 900s | 600s | 偏大 |
| 173 | ID-X173 | EQ143 | EQ173 | 600s | **1800s** | 偏小 |
| 174 | ID-X174 | EQ144 | EQ174 | 900s | **1800s** | 偏小 |

两个方向都在伤人：**偏小 ⇒ 正常动作被误判超时（重试、转人工）**；
**偏大 ⇒ 真失败了要干等，期间设备被锁着**。所以"这次只影响个别设备"是错的 ——
它让**四分之一的设备**在超时/可中断/设备锁三个判定上都用着别人的配置。

## 3. 为什么这么难发现

| # | 原因 |
|---|---|
| 1 | 三套 id **类型都是 bigint** ⇒ 传错编译能过、SQL 也不报错，只是查错行 |
| 2 | 落空那条被 `COALESCE(MAX(...),0)` 吞成 0，而 **0 是合法值**（= 没配）⇒ 完全静默 |
| 3 | 只有"撞号 **且** 撞上的上限 < 真实耗时"才炸，而且**间歇性** —— 取决于哪些实例号恰好落在别人的行号上 |
| 4 | 列名本身有歧义：`device` 表是"型号定义"，列却叫 `device_id`；读代码时"设备 id"和"型号 id"分不清 |

## 4. 修法（六步，按成本从低到高）

### 4.1 P0 让列名说清语义（改名）

| 位置 | 改前 | 改后 |
|---|---|---|
| `device_method.device_id` | `device_id` | `device_model_id` |
| `device_instance.device_id` | `device_id` | `device_model_id` |
| 唯一约束 | `uk_device_method (device_id, method)` | `uk_device_method (device_model_id, method)` |
| 视图 `v_equipment_instance_ro` | `di.device_id AS equipment_id` | `di.device_model_id AS equipment_id`（**对外列名不变**） |

改名之后，任何残留的 `WHERE device_id = <实例号>` 都会**直接报列不存在**，
而不是静默查错行。这是成本最低、覆盖最广的一招（比换 id 类型便宜两个数量级）。

### 4.2 P0 把换算收成唯一入口

新增 `com.labos.kernel.device.DeviceIdentityResolver`：

```java
ModelId model = new DeviceIdentityResolver(tenantId).modelIdOf(instanceId);
// 解析不到 ⇒ ModelId(0)，同时计数 + 一条 WARN（说明三种成因）
```

- 唯一的 SQL 出口是 `DeviceStateMapper.selectModelIdOfInstance`
  （`SELECT device_model_id FROM device_instance WHERE id = ?`）；
- Java 源码里**不许**再手写这条 SQL（由测试扫描）；
- 带实例级缓存 + `invalidate`，解析失败**不再静默**。

### 4.3 P0 落空要看得见（诊断计数）

新增 `com.labos.kernel.driver.TimeoutDiagnostics`：

| 指标 | 判读 |
|---|---|
| `bySource.device_method` | 长期为 0 ⇒ 现场超时配置根本没生效 |
| `bySource.capability_default` | 占压倒多数 ⇒ 设备库压根没登记超时 |
| `deviceLevelMissing` | 持续增长 ⇒ 该型号该方法没配超时（或挂错型号） |
| `modelUnresolved` | > 0 ⇒ `device_instance.device_model_id` 为空（型号登记不全） |

`resolveTimeoutMs` 在「设备方法级 + 型号级都为 0」时按 `(实例, 方法)` **只告警一次**
（避免每步刷屏），并把计数累加。

### 4.4 P1 编译期挡住混用（强类型 id）

`com.labos.kernel.device.DeviceIds`：

```java
DeviceIds.InstanceId  // device_instance.id
DeviceIds.ResourceId  // resource_node.id
DeviceIds.ModelId     // device.id
```

三个 `record` 互不兼容 ⇒ `modelIdOf(instanceId)` 这类混用**编译不过**。
Mapper 层仍收 `long`（MyBatis 不认 record），所以强类型落在**调用层**。

### 4.5 P1 复用正确口径，不另写一套

`DeviceMapper.selectDeviceMethods` 本来就是正确写法（`di.resource_id` → `JOIN device_method
ON dm.device_model_id = di.device_model_id`），已加注释标为**模板**：按实例取方法请复用。

### 4.6 P2 不做：把 bigint 换成带前缀的 varchar

评估过，**否决**。理由：

1. **前缀是约定不是约束**：`device_id varchar(32)` 塞 `'DI_1000039'` 照样合法，
   `COALESCE` 照样吞掉落空。本次故障的性质是"参数语义搞错"，不是"抄错字符串"，
   前缀防不住后者以外的任何东西。
2. **代价远大于收益**：bigint 8 字节 → varchar 12~16 字节，全库 PK/FK/JOIN/GIN 索引一起变大；
   30 张表的 FK 要重建；所有已存值、代码、外部集成（设备端/上位机/导表/报表）都要改。
3. **工业标准用的是结构化类型标签，不是字符串前缀**：
   OPC UA `NodeId` = `(namespaceIndex, identifierType, identifier)`；
   Asset Administration Shell 的 Reference 是 `{type, keys[]}` 对象。
   真要全局唯一标识，应在新系统里用 **UUIDv7** 或**雪花 ID**（在 64 位里留 2~3 位类型位），
   既保留 bigint 性能，又能一眼看出类型。

> 人类可读的"编码"本项目早已有独立字段：`resource_node.code` / `device.code` /
> `device_instance.code`（均 `UNIQUE(tenant_id, code)`）。前缀需求本质是给人看，
> 那个已经满足了 —— 把它挪到主键上是把两个关注点混在一起。

### 4.7 P1 实例级覆盖真的能用（2026-11-17 续做）

P1 就给 `device_method` 加了 `device_instance_id` / `scope` 两列，约束也写了
`ck_device_method_scope IN ('model','instance')`。但**唯一键仍是
`UNIQUE (device_model_id, method)`** ⇒ 同一型号同一方法只能有一行
⇒ 实例级覆盖行**根本插不进去**。那一层是死设计，超时解析也从未读过它。

续做三件事：

**① 唯一键按 scope 分离**（`20261117_device_method_instance_scope.sql`）

| 索引 | 定义 | 作用 |
|---|---|---|
| `uk_device_method_model` | `(tenant_id, device_model_id, method) WHERE scope='model'` | 型号级方法唯一（原来那条的等价物） |
| `uk_device_method_instance` | `(tenant_id, device_instance_id, method) WHERE scope='instance'` | 每台设备每方法最多一条覆盖 |

配套约束 `ck_device_method_scope_pair`：`scope='model'` ⇒ 无实例号；
`scope='instance'` ⇒ 必有实例号（防止写出"谁也匹配不到"的孤儿行）。

⚠ 写入侧必须跟着改：`upsertDeviceMethods` 的冲突目标变成
`ON CONFLICT (tenant_id, device_model_id, method) WHERE scope='model'`
—— 部分索引不写谓词就推断不到索引，PG 会直接报
"no unique or exclusion constraint matching the ON CONFLICT specification"。

**② 解析优先级加一层**（`MethodTimeoutPolicy.Sources`）

```
实例级方法 > 实例级库上限 > 型号级方法 > 型号级库上限 > 节点级 > 能力默认 > 兜底
```

新增来源标签 `device_instance_method` / `device_instance_library`（进
`TimeoutDiagnostics.bySource`）。为什么用 `Sources` record 而不是继续加 long 形参：
那会变成一排同类型 long，位置传错编译器不吭声 —— 正是本次事故的同一种病。

**③ 型号级查询必须带 `scope='model'`**

实例级行也填 `device_model_id`（表示"基于哪个型号覆盖"）。
型号级查询若不加过滤，就会把某台设备的专属配置**捡成全型号默认** ——
等于把 2026-11-16 的事故换个方向重演。这一点由测试反向断言钉住
（`selectInstance*` 里**不许**出现 `device_model_id`；四条型号级必须带 `scope='model'`）。

**读写入口**

| 用途 | 入口 |
|---|---|
| 读超时（自动带优先级） | `DriverStepExecutor.resolveTimeoutMs`（无需调用方关心层级） |
| 读可中断 | `isInterruptible`：实例级优先，无则回落型号级 |
| 写型号级可中断 | `PUT /devices/{id}/methods/{method}/interruptible`（`id` = 型号行号） |
| 写实例级可中断 | `PUT /device-instances/{instanceId}/methods/{method}/interruptible`（**新**） |

两条路径刻意用不同前缀（`/devices` vs `/device-instances`）：
三套 id 都是 bigint，靠路径名区分比靠注释可靠。

> 型号未登记的实例**不允许**建实例级覆盖（会写出一行 `device_model_id` 为空的孤儿配置），
> 接口直接 400 并说明原因。

## 6. 验证

### 6.1 迁移幂等（测试库 `192.168.124.2/labdb`）

```bash
psql -h 192.168.124.2 -U labos -d labdb -v ON_ERROR_STOP=1 \
  -f pg_rebuild/migration/20261116_device_model_id_rename.sql   # 跑两次，两次 exit 0
```

```bash
psql ... -f pg_rebuild/migration/20261117_device_method_instance_scope.sql  # 同样连跑两次
```

| 脚本 | 第 1 次 | 第 2 次 |
|---|---|---|
| `20261116_device_model_id_rename.sql` | 两列改名 + 约束跟随 | 全部跳过、exit 0 |
| `20261117_device_method_instance_scope.sql` | `uk_device_method` 删除，建 `uk_device_method_model` / `_instance` | 全部跳过、exit 0 |
| `20261116` 在 `20261117` 之后重跑 | —— | 打印「已由 scope 分离索引取代，跳过本段」（**幂等不能被后续迁移破坏**） |

部分索引的写入路径也实测过（事务内，`ROLLBACK`）：两次 `INSERT … ON CONFLICT
(tenant_id, device_model_id, method) WHERE scope='model' DO UPDATE` 只留 1 行且 `name`
被更新；同型号同方法再加一条 `scope='instance'` 行**成功**（改前会被唯一键挡住）。

### 6.2 纯逻辑（不连库）

```bash
./scripts/test-all.sh --pure-only
# 通过 1527 / 失败 6（其中 5 条属并发会话的型号库改动，见 §7）
```

新增 `driver.DeviceIdSpaceSelfTest`（**53 条**）钉死：

1. mapper 里 `device_method` / `device_instance` 语句不得再有裸 `device_id` 列；
2. **型号级**四条必须用 `device_model_id` 且带 `scope='model'`；
3. **实例级**三条必须用 `device_instance_id` 且带 `scope='instance'`，
   并且**不许**出现 `device_model_id`（拿型号列冒充实例号 = 事故的反向重演）；
4. Java 不得把 `instanceId` / `ctx.resourceId()` 喂给型号语义方法；
5. Java 不得手写换算 SQL（换算只许一处）；
6. `DeviceIds` 三套 record 不同 class、同值不相等、toString 带空间标签；
7. `selectModelIdOfInstance` 存在且读 `device_model_id`；

## 8. 现场排查手册

现象与查法对照（都用得上 `modelUnresolved` / `deviceLevelMissing` 两个指标）：

| 现象 | 先查什么 |
|---|---|
| 节点频繁 `EC-05-1007`，但设备实际很快 | 该实例 → 型号换算结果：`SELECT id, code, device_model_id FROM device_instance WHERE id = <实例号>`；再看 `device_method` 里该型号的 `timeout_sec` |
| 超时永远等于 600s（能力默认） | `device_method` 里该型号的 `timeout_sec` 是否全为 0（`deviceLevelMissing` 会持续增长） |
| 某方法"可中断"判定与现场不符 | 是否撞号：把实例号当型号查 `device_method` 会命中别人的行 |
| 抢锁报"设备被占用超过 60 秒"但设备空闲 | `selectDeviceLockTimeoutSec` 拿到的时长是否来自别的型号 |
