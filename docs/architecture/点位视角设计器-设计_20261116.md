## 1. 角色分工（谁在哪一层动手）

| 角色 | 页面 | 关心什么 | 明确不碰 |
|---|---|---|---|
| **Administrator** | `/island` `/positions` `/topology` `/models` `/event-types` `/durations` | 建岛/设备/点位/池；点位允许哪方法（`position_method`）；物料角色；机械臂示教坐标；事件类型字典；时长 | 不编排工艺 |
| **Designer（应用者/工艺）** | `/designer/:id`（**点位视角**）+ 模板编辑 | 「这一步在哪个点位做什么、板从哪来到哪去、等哪个设备的什么事件」 | 不碰设备型号/实例、不碰机械臂节点、不改点位属性、不改示教坐标 |
| **Operator** | `/material-config` `/live` `/plate-focus` | 选模板 → 实例化 → 配位置（哪个坑放哪块板）→ 扫码核验 → 启动 | 不改图、不改绑定 |

> 边界一句话：**点位与方法是管理员给的（能力边界），点位之间的工艺顺序是 designer 给的，板放哪儿是 operator 给的。**

## 2. 核心主张

> **图里只有点位，没有机械臂。**

应用者在画布上表达的是两件事：
1. 「在**某点位**执行**某方法**，处理**某物料角色**」（= 一个节点 + 一条 `node_binding`）
2. 「然后板要出现在**另一个点位**」（= 两条节点之间的连线，**不带搬运节点**）

「板怎么过去」是**执行期的一次图变换**（§4），不是应用者要画的节点。

**三条理由**

| 理由 | 说明 |
|---|---|
| 客户文档 §1.2 的语义就是设备与点位的交互 | 搬运是"上位机调度机械臂"的结果，工艺说明书里没有让用户画搬运 |
| 搬运节点是**最容易错**的一类节点 | 现状踩过：`Transfer` 的 `source/target` 写点位码还是设备码、装载口/内部格谁搬、机械臂选哪台 —— 每个坑都让流程卡死且日志不指向真凶 |
| 多臂/换臂/重试/可观测都归系统 | 应用者一旦画了机械臂，换一台臂就要改图；不画则只改调度 |

## 3. 点位视角设计器（`/designer/:id`）

### 3.1 左栏 palette：从「设备列表」换成「点位列表」

数据源全部是**现成端点**，不需要新接口：

| 用途 | 端点 | 用到的字段 |
|---|---|---|
| 点位清单 | `GET /api/positions?islandId=` | `pointId` `code` `pointRole` `robotReachable` `isEntry/isExit` `positionLabel` `slotIndex` `plateTypes` `maxHeightMm` `available` `parentDeviceCode` |
| 该点位允许的方法 | `GET /api/positions/{pointId}/methods?scopeKind=&scopeId=` | `methodId` `methodName` `allocation` `purpose` |
| 全岛矩阵（管理员用） | `GET /api/positions/method-matrix?islandId=` | 点位 × 方法 |

**分组方式**（按应用者的心智，不按数据库结构）：

```
LAB-EXT-01
├─ 提取仪（4 台）
│   ├─ P_AUTO-1 · 操作位 (INT)      [内部·机械臂不可达]  方法：PickTipComb/Incubate/Wash/Elute…
│   └─ P_AUTO-1 · 交互位 (EXT)      [可达·进出板]        方法：PickTipComb/DropTipComb…
├─ 分液器（6 台）
│   ├─ DISP1 · 板位 (PLATE)         [可达]                方法：Run
│   └─ DISP1 · 搅拌工位 (STIR)      [磁力搅拌]
├─ 耗材栈（60 槽，按 8 类分区）
│   ├─ 磁套板区 S01..S08            [8 槽·当前空 5]
│   ├─ 裂解板区 S09..S16
│   └─ …
└─ 机械臂 —— **不在 palette 里**
```

**过滤与标注规则**

| 规则 | 依据 |
|---|---|
| 只列 `position_method` 有绑定（且 `enabled`）的点位×方法组合 | 没有绑定的点位拖出来运行期必转人工 |
| 标注 `robotReachable=false` 的点位：可拖，但提示「板只能由该设备自己搬进去」 | 272 个 `point_role='internal'` 的点位都是这种 |
| 标注耗材槽的 `positionLabel`（SAMPLE/MAGNET/LYSIS/W1/W2/W3/ELUTE/WASTE）与剩余数 | 现状 60 槽已按 8 类分区 |
| 标注当前占用（`available=false` ⇒ 显示被哪块板占） | 建图时不拦，但让应用者知道他画的坑位上正放着东西 |
| **不出现设备型号、设备实例 id** | 应用者不按型号思考；型号只在"高级/管理员视图"里 |

### 3.2 拖出一个节点 = 一条 `node_binding`

这是本设计最关键的一条：**点位视角的节点与 `node_binding` 是 1:1 的**，不存在"拖完还要再去绑一次"。

| 字段 | 谁来 | 默认 | 说明 |
|---|---|---|---|
| `positionId` | 拖拽 | — | `device_point.id`（**不是** `resource_node.id`） |
| `methodId` | 下拉（该点位允许的） | 唯一时自动选中 | 双向约束：先选点位→方法只列允许的；先选方法→点位只列支持的 |
| `materialRole` | **必填**（点位视角下） | 上一次同设备的 | 搬运靠它找"搬哪块板"；空 ⇒ Planner 无法解析 |
| `loadingPattern` | 默认 `load_single` | `load_single` | 四值：不装/装一块/装选中的/装满剩余 |
| `barcodePolicy` | 设备节点默认 `validate_in`；搬运由系统定 | `validate_in` | 机械臂抓板扫码 = `validate_both`，由 Planner 用 |
| `leaveAtStation` | 复选框 | false | 干完留在工位（下一节点可能就在原地） |
| `params` | JSON（可选） | `{}` | 方法参数覆盖（如 `volume`） |

保存仍走 `PUT /api/workflows/{id}/nodes/{nodeKey}/bindings`（**整体替换**）；`{"bindings":[]}` 会把该节点打回 `legacy`。

### 3.3 四类特殊节点 / 入口

| 类型 | 长什么样 | 为什么必须有 |
|---|---|---|
| **等设备事件** | 「等 **P_AUTO-1** 上报 **等待交互**」 | 客户 §1.2 的"上位机被动响应"是整条线的技术心脏。设备由点位反推，事件类型从 `device_event_type` 下拉选（已配置化）。**这一拍不是机械臂，应用者可以也必须要能表达** |
| **从耗材栈取板** | 「取一块 **磁套板**」 | 现状 `Transfer` 只会 `ORDER BY order_in_device LIMIT 1` 取第一个空位 ⇒ "去拿一块磁套板"表达不了。改为选**耗材类型**，运行期在该类型的空槽里 `auto_first_free` 分配 |
| **阶段分组** | 8 个可折叠的阶段框（S1..S8） | 客户按 §3 数阶段（§5） |
| **搬运** | **不提供入口** | 见 §2；连线上隐含 |

### 3.4 右栏：选中节点后看到什么

- 点位属性（只读）：码 / 角色 / 可达性 / 板型 / 高度上限 / 用途标签 / 槽位号
- 方法（可改，限该点位允许的）
- 物料角色、装载方式、扫码策略、留在原位、额外参数
- **本节点将产生的搬运**（只读预览）：「进入时：DISP1-板位 ← 耗材栈-裂解板区」「离开时：DISP1-板位 → P_AUTO-1-交互位」

最后一行很重要：**不给编辑权，但要让他看见系统打算怎么搬** —— 这是"应用者不关心搬运"与"应用者要能验收"之间的平衡。

### 3.5 保存与一致性（应用者开放后最容易出事的点）

| 规则 | 内容 |
|---|---|
| 一次提交 | 图的保存与绑定的保存**必须在同一个保存动作里完成**（前端一次点「保存」⇒ 先存图再 PUT 绑定；失败要能整体回退提示） |
| `node_key` 稳定性 | 人在 bpmn-js 里拖出来的元素 id 是随机串（`Activity_1yrts0s`），**只要元素不被删除就一直稳定**；实测事故（2026-11-15 "Elute 发给 P_AUTO-1"）是**脚本按位置生成 id**（`Activity_0004`）造成的 ⇒ **纪律：点位模式下图只能由人在设计器里改；脚本重建图必须同时重建绑定** |
| 删节点 | `node_binding.node_id` 是 `ON DELETE CASCADE` ⇒ 删节点绑定自动清，无需额外处理 |
| 移动布局 | 只改 DI 坐标、不改元素 id ⇒ 绑定不受影响（这是安全的） |
| 守卫 | 编排绑定（XML `resource`）与节点绑定指向不同设备 ⇒ **拒绝执行**（已有）。点位模式下应用者不设 `resource`，所以这条不会误伤 |
| 一致性校验按钮 | 保存后跑一次「绑定自检」（回读每个节点的绑定，比对点位/方法/角色），不一致直接报错 —— 沿用 `setup-extraction-flow.py` 的回读自检做法 |

### 3.6 双视角与双轨

| 项 | 规则 |
|---|---|
| 视图由 `workflow_node.binding_mode` 决定 | `point` ⇒ 点位视角；`legacy` ⇒ 设备视角（现状）；`mixed` ⇒ 提示并禁止保存，要求先收敛 |
| 同一流程不允许混编 | 编辑器**只暴露一处**（沿用详细设计 R1 的裁定） |
| 存量 136 流程 | 全是 `legacy`，行为不变 |
| 新流程默认 | `point`（应用者建的走点位视角） |

## 4. 自动搬运：`PositionFlowPlanner`（执行期图变换）

### 4.1 插在哪一层

```
XML ──BpmnGraphParser──► Graph
                            │
                            ├─[新] PositionFlowPlanner.rewrite(Graph)  ← 只在 binding_mode=point 时执行
                            │        在需要搬运的边上插入 __transport 节点
                            ▼
                        GraphRunner（Kahn 拓扑，结构不变）
```

`__transport` 走**内置节点**通道（`protocolName` 以 `__` 开头 ⇒ `Kind.BUILTIN`，不找设备、不走驱动），与 `__sleep` / `__wait` / `__awaitEvent` 同一机制。**不需要新的 Kind，也不需要改解析器白名单。**

### 4.2 判定规则（相邻两节点 A → B）

| 条件 | 动作 |
|---|---|
| A 或 B 不是点位节点（无 `node_binding.position_id`） | 不插（可能是变量节点、事件节点、网关） |
| A、B 属于**同一设备实例** | 不插机械臂段；若需要内部搬运，由设备方法/`DeviceInternalTransfer` 负责 |
| A、B 跨设备，且 B 的 `loadingPattern ∈ {load_single, load_all_remaining, load_selected}` 且该物料还是"新板" | 插「取板 + 搬运」：从耗材栈对应 **`positionLabel` 类型**的空槽取 |
| A、B 跨设备，物料角色已有位置 | 插「搬运」：`from = A 的出口位`，`to = B 的入口位` |
| A、B 之间已有显式 `__transport`（手工兜底） | 不重复插（幂等） |
| `binding_mode = legacy` | **整条不插**（存量路径逐字不变） |

### 4.3 段链（一次跨设备搬运 = 最多 4 段）

```
A.internal ──(设备自己搬)──► A.deck_out/exit ──(机械臂)──► B.deck_in/entry ──(设备自己搬)──► B.internal
       段①（设备内部）              段②（robot）            段③（设备内部）
```

- 机械臂只到**装载口/交接位**（`robot_reachable=true`）；内部格由设备自己搬（`DeviceInternalTransfer`）。
- 段的 `from/to` 用**点位**（`device_point.id` + 点位码），不用设备编号 —— 与 `transport_segment` 的 `from_position_id/to_position_id` 一致。
- ⚠ 现状 `Transfer` 的 `source/target` 传的是**设备码**，精确点位靠 `method_params.sourcePosition/targetPosition`；两套口径并存，Planner 必须统一到点位（§7 缺口 2）。

### 4.4 执行语义

| 项 | 规则 |
|---|---|
| 锁 | 全局升序：岛 → 设备实例 → 端口 → 点位 → 机械臂 → 物料。两端点位用 `PositionLock` **原子预约**（`INSERT … ON CONFLICT DO NOTHING` 试占），抢不到换下一个槽 |
| 机械臂排他 | 同一 `robot_resource_id` 同时只允许 1 段 `running`（现状单臂 ⇒ 全岛搬运串行） |
| 机械臂选择 | 岛内 `TRANSFER` 能力设备；多臂时按"点位所属区域/示教覆盖"选，选不出则报错（**不静默用第一台**） |
| 幂等 | `idempotency_key = sha256(run_id | seq | from | to | carrier)`，命中账本不重复下发 |
| 观测 | 执行完写一条 `transport_segment`（`status=done|failed`），甘特/岛进程视图显示为灰带「搬运」 |
| 失败 | 重试按 `MethodTimeoutPolicy`；仍失败 ⇒ 节点 `MANUAL` ⇒ run 转 `paused`（人工窗口），**不静默跳过** |
| 断点续跑 | 已 `done` 的段跳过（复用既有的"已完成节点跳过"） |
| 预校验 | 源位必须有板（`position_state`）、目标位必须空、板型/高度匹配 |

### 4.5 为什么放执行期，而不是设计期插节点

| 设计期插（现状） | 执行期插（本设计） |
|---|---|
| 图上出现机械臂节点 ⇒ 与"应用者不关心搬运"直接冲突 | 图干净，只有工艺 |
| 一个岛多臂时永远用第一台（`Designer.tsx:949` 的既有局限） | 可按时段/区域选臂，换臂不改图 |
| 绑定要跟着搬运节点一起维护（多一类绑定要人配） | 搬运参数由 Planner 算，人不用配 |
| 搬运失败在图上没有独立节点可重试 | 段级可重试、可观测、可追溯 |

> 结论：**设计期那份"连续拖两台不同设备就插一个 Transfer 节点"的逻辑，在 `point` 模式下必须下线**（`legacy` 模式保留）。

### 4.6 可直接复用的现状

| 已有 | 位置 |
|---|---|
| `transport_segment` 表（`from_position_id`/`to_position_id`/`robot_resource_id`/`status`/索引） | `pg_rebuild/schema/90_all_in_one.sql:4134` |
| 执行 Transfer 时落搬运段（P2-3，失败只告警不阻断） | `DriverStepExecutor.writeTransportSegment` |
| 点位原子预约 + 双锁按 id 升序 | `PositionLock` |
| 设备端口信号量 | `DevicePortLock` |
| 命令幂等账本 | `CommandLedger` |
| 内置节点通道（`__` 前缀） | `WorkflowGraphParser.isBuiltinProtocol` |
| 节点绑定 pin 设备 + 陈旧绑定守卫 | `GraphRunner.toRecoverable:1739-1779` |

缺的只有**一个 Planner**（判定 + 插节点 + 算段链）。

## 5. 8 阶段与阶段契约

### 5.1 阶段编码（客户文档 §3 原编号）

| `S5` | W2 洗涤 | `DISP4-PLATE` | 串行 |

| `S8` | 批次收尾 | 产物板 / 废弃板分拣 → 回栈 | 4 台并行 |
| `S0` | 启动校验（客户 §2，非 §3 阶段） | 无点位（预检 + 就绪判定） | — |
| `S9` | 连续循环 / 耗材预警（客户 §3 阶段 9） | STACK1 余量 | — |

### 5.2 落点

| 用途 | 载体 | 说明 |
|---|---|---|
| 图上分组（视觉） | BPMN `bpmn:group`（不进 `flowElements`，解析器不认也不会当节点） | 应用者拖一个框把节点圈进去 |
| 数据侧聚合（甘特/看板/模板） | **新增列 `workflow_node.stage_code`**（`text`，可空） | 只加列不改语义；空 = 未分阶段 |
| 阶段顺序 | 节点在阶段内的拓扑顺序（不引入新概念） | 8 阶段内部天然由连线表达 |

> 为什么要有 `stage_code` 而不是只靠 `group`：**甘特图、运行看板、模板层、验收统计都要按阶段聚合**，而 `group` 只在 BPMN XML 里，每读一次都要解析图。

### 5.3 阶段契约（决策 3：板位 + 变量，够）

| 契约项 | 载体（现成） | 例子 |

## 6. 管理员预配清单（决定 designer 能看到什么）

## 9. 这条流程的验收用例（P2 结束时应全绿）

1. `S1`：`取磁套板`（耗材栈磁套区，类型选板）→ `P_AUTO-1-EXT`；执行后板在 `P_AUTO-1-EXT`，`transport_segment` 1 段。

**过程中又修掉 1 个真 bug**：搬运的 `sourcePosition/targetPosition` 原来取 `position_label`（现场标签），而两台设备的板位都可能标 `"PLATE"` ⇒ 驱动按 label 解析串位，报 `EC-POSITION-OCCUPIED` 且**指向机械臂自己的资源**。已改为用**点位编码**（唯一）。

**这条链上还有两道物理门（都是设计如此，不是 bug）**：
1. **抓板闸门**：`Transfer` 前必须有 `position_scan_evidence`（run + 源位 + 未消费 + 未过期）。没有扫码节点 ⇒ `EC-SCAN-EVIDENCE-MISSING`。真实流程靠 `BarcodeScan` 节点写证据。
2. **搬运确认**：设备回包只是 `REPORTED`；要么满足九项条件且 `LABOS_TRANSFER_AUTO_CONFIRM` 覆盖该流程（本项目**故意不覆盖**，见 `PositionLock` 注释），要么人工/扫码 `POST /api/transfers/{id}/confirm`。

**可复现步骤（测试环境，人工播种）**：
```
① 造板并占源位：INSERT plate + UPDATE position_state SET plate_id
② 建流程两点位直连 + 绑定（barcodePolicy 随意）
③ 起 run → 立刻 UPDATE position_state SET occupied_by_run=<runId>
   （真实场景由"设备方法放板"写；测试里抢在 A 的 ~8s 完成前种）
④ 种扫码证据：INSERT position_scan_evidence(run_id, source_position_id,
   expected/scanned=barcode, observed_at=now())
⑤ 等 run 到 __move__ → POST /api/transfers/{id}/confirm
⑥ 断言：transfer=CONFIRMED、源位空、目标位有板、run=completed
```

**顺带补齐（原遗留）**：`transport_segment` 原先只在**自动确认**路径写，人工 `confirmWithPosition` 不写 ⇒ 人工确认的搬运在甘特/岛进程视图里没有灰带。已在确认事务内补写（去重键 `(run_id, from_position_id, to_position_id)`）。

⚠ **又踩到一个 id 空间坑**：`transport_segment.from/to_position_id` 的外键指向 **`device_point(id)`**，而 `transfer_transaction.source/target_position_id` 存的是 **点位实体 id（`resource_node`）**。直接塞实体 id ⇒ FK 失败；而 PostgreSQL **一条语句报错就把整个事务作废** ⇒ 现象是"接口返回 `CONFIRMED`，但事务状态/位置账本/搬运段一条都没变"（假成功）。修法：写段前先 `selectDevicePointIdByResource` 转换。

**最终实测（同一轮）**：确认后 → 事务 `CONFIRMED`、搬运段 `470→474|done|PLT-…`、源位清空、目标位有板、run `completed`。

⚠ **两个语义坑（都实测踩过）**：
1. **裁剪状态不能用 `SKIPPED`**：`SKIPPED` 的既定语义是"该做但没做，板位不可信"，`settleRun` 会因此把整单转人工 —— 实测裁剪后 run 直接 `paused` + 人工窗口 `EC-UNKNOWN`。改用 **`BYPASSED`**（与"异或网关另一条分支没选中"同类）后 run 正常 `completed`。
2. **`mergeRunInputVars` 只合并 `vars` 子键**：往里塞 `stages` 会被静默丢掉（run.input 里根本看不到），必须用通用的 `mergeRunInputJson`。

⚠ **PF-33 的第一版做错了（已改）**：最初把它实现成**流程预检规则**（预检读"引用了这条流程的模板白名单并集"）。后果是——给一个模板配了只含 `DISP1` 的白名单，被它复用的 43 节点工艺图立刻报 **18 条阻塞**，`/workflows` 里那条共享流程整体变红。同一张图会被多个模板复用，**白名单是"这个模板允许用哪些点位"，不是"这条流程只能在这些点位跑"** ⇒ 已移到模板层判定，共享流程恢复 `blocking=false`。

**模板自检（`GET /api/experiment-templates/{id}/check`）检查项**：
`TEMPLATE-NO-PROCESS` / `WORKFLOW-MISSING` / `WORKFLOW-DELETED` / `EMPTY-GRAPH` / `ISLAND-MISMATCH` / `PREFLIGHT-BLOCKING` / `NO-MANIFEST` / `MANIFEST-ROLE` / `NO-WHITELIST` / `WHITELIST-FOREIGN` / `WHITELIST-BINDING` / `DRAFT`，返回 `{ok, errors, warnings, issues[], stats}`，编辑页以卡片直接展示。
