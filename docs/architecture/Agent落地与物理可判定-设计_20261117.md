## 0. 一句话结论

**AI 的第一版已经在设计器里跑起来了；真正的缺口不是"再加一个智能体"，而是三件事：**

1. **AI 的产出没有留痕**——`AiPlanService` 从收到 LLM 返回到解析完，全链路未写任何审计（`grep audit` 命中 0）。而本仓库最强的能力恰恰是审计，AI 是唯一绕过它的一条路径；
2. **AI 的产出没有被物理可行性拦住**——`compile` / `preflight` 判的是"结构对不对、能力有没有"，**判不了"体积够不够、几何会不会撞"**（L0 缺位，见 `物理可判定层…_20261116.md` §3 G1）；
3. **AI 只覆盖"设计期"，不覆盖"跑起来之后"**——现场最费人的是"这个 run 为什么停在这、这条告警该怎么办"，而这正是只读问答成本最低、风险最小、ROI 最高的地方。

> 一句话定位：**不是给中控加一个大脑，是给"已有的 AI 草案"补上留痕、物理闸门和运行期入口。**

先承认已有的，避免重复建造。**以下四条是当前仓库事实**：

| # | 能力 | 落点 | 证据 | 已知边界 |

| 2 | 流程规格 → **真图 → 落库 → 编译/预检** | `scripts/ai-build-flow.py` + `webapp/src/pages/Designer.tsx` 的 `window.__labosFlowSpec.import` | 脚本头写明"走页面而不是直接写库"，复用前端同一套建图规则 | 依赖页面钩子（`window.__bpmnModeler` / `window.__labosFlowSpec`），**headless 不可用** |

| 4 | 应用前**人工确认**，只落 draft，并刷新 compile/preflight | `Designer.tsx` 的 `applyAiOps` | `saveGraph(..., { draft: true })` + 并行 invalidate `compile` / `preflight`；`dataset.graphSaved` 打点供自动化断言"真的存上了" | 无 diff 视图，无"这一条为什么被拒"的解释 |

**已实现的部分里，第 3 条是最有价值的设计决策**，值得写进对外材料：

> **模型只负责"想清楚长什么样"，连线由代码做。**
> 这不是工程妥协，是把 LLM 的输出**降级成中间表示**（IR），再交给确定性编译器。
> 与"让模型写仪器控制代码"相比，它把不可验证的自然语言输出压缩成了**可静态校验的图**——
> 而 `GraphRunner` 已有 17 条网关断言、`compile`/`preflight` 已有结构校验，正好接得住。

**四条必须写下来的落差**（本文要补的就是它们）：

| 落差 | 事实 | 后果 |
|---|---|---|
| 无审计 | `AiPlanService` 无任何 `audit` / 日志埋点 | 事后无法回答"这条流程是谁让 AI 改的、AI 当时给了什么、采纳了哪几条" |
| 无物理判据 | `compile` / `preflight` 只看结构与能力；`capability_recipe.criteria` 全仓无读取方（引自 `物理可判定层…` §3 G5） | AI 能产出"语法正确、物理不可执行"的草案，而这正是外部学术方案 A 定义的第三类故障 |
| 只有设计期 | 无任何"读取 `run_event` / `device_state` 回答问题"的入口 | 现场问题仍靠人翻日志 |
| 无评测集 | AI 链路的正确性只有人工试（类注释提到的 2026-11-13 实测） | 改一次提示词，无法判断是变好还是变坏 |

## 2. 三个必须先摆正的认识

### 2.1 "代码智能体"在中控里应当退化成"图编译器"

外部学术方案 B 让模型**写仪器控制代码**，是因为它的设备接口本来就没有统一抽象，只能现生成。
本仓库的处境相反：`workflow_node.capability_id` 已经做到"工艺绑能力不绑设备"，`driver_capability` 已经声明能力。
所以**不需要生成代码**——需要的是把"意图"编译成 `workflow + workflow_node` 这张图，再由 `GraphRunner` 确定性执行。

这不是保守，而是三个可验证的好处：

- **可静态校验**：图能过 `compile` + 17 条网关断言；代码不能。
- **可复现**：同一张图跑 100 次行为一致；LLM 生成的代码每次可能不同。
- **可追责**：出问题时能指到 `run_node` 与 `command_ledger` 的某一行；生成式代码只能指到"模型"。

> 🔴 **红线**：任何"让 Agent 直接写 Java / 直接发设备命令"的方案，本文**一律不建议立项**。
> 理由不是不信任模型，而是它会绕过 `DriverStepExecutor` 那条 11 道闸门的链（顺序见 `物理可判定层…` §2.1）。

### 2.2 外部方案 B 的"数字孪生"在中控的真缺口是**持久化与时间轴**，不是渲染

外部学术方案 B 的数字孪生之所以能"在真跑之前抓到容器没放进去就读荧光"，靠的是**状态持久 + 可快进**。
本仓库的对应物是 `sim/`（18 类设备画像）与 `pylabrobot-sim`（体积/枪头跟踪），但：

- `sim/` 状态**全在内存**（`sim/DeviceBehavior.java` 注释明写"进程退出即丢弃"）；
- 全仓**无 time-scale**（只有 `--delay/--rand-delay` 真实等待）；
- `plate_well.volume` **运行期无写入方**（设计期写入方存在，见 `物理可判定层…` §3 G2 的修订说明）。

⇒ **AI 侧的"预演"能力，天花板由 P-A/P-C 决定，不由提示词决定。** 这也是本文把 AI-4 排在 P-B 之后的原因。

### 2.3 "给每个人建一个 Agent、搭虚拟团队"是组织隐喻，不是交付物

这个说法在内部沟通很好用，落到工程上会撞三堵墙：

1. **归因断链**：多个 Agent 互相调用后，"这一步是谁决定的"无法映射到 `run_id` / `node_id` / `command_id` 三元组；
2. **权限失控**：人格化的 Agent 天然想要"更多上下文"，而本仓库的 RBAC 是按角色与资源划分的；
3. **验收失焦**：无法回答"这个 Agent 做好了没有"。

**替代方案：角色 × 工具 × 权限 × 审计 四元组**（§5）。内部仍可叫"岗位助手"，对外不说"虚拟团队"。

### 2.4 反过来：中控的确定性执行，正好补上 LLM 不可重复这块短板（最有价值的对外论点）

外部学术方案 B 的同期评论明确指出：LLM 有随机性，**实验方案的可重复性会受影响**。
而本仓库恰好有：`workflow` 版本化、`workflow_node` 参数落库、`run_event` append-only、`command_ledger` 幂等键。

> 对外可以这样讲：**"AI 想一次，中控复现 N 次。"**
> 这句话把"AI 原生"从"模型多、工具多"拉回到**可复现**——是本仓库相对外部商业平台 C 的差异点，也是唯一能用现有代码证明的差异点。

## 3. 外部方案 B 的七个智能体 → 本仓库的落点对照

只做能落到既有对象上的，其余明确不做。

| 外部方案 B 的角色 | 它解决的问题 | 本仓库对应物 | 本期态度 |
|---|---|---|---|
| Planner（拆任务派活） | 需求 → 任务树 | `workflow` + `experiment` + 双画布（岛编排 / 实验画布） | **已由"图"承担**，不再造 Planner |
| 文献智能体 | 查协议、找方法 | 无（无文献库） | **不做**（没有可信数据源，做了就是幻觉） |
| 试剂智能体 | 先确认家底够不够 | `consumable_lot.remaining` + `plate_well` | **做只读版**（AI-2），写入版依赖 P-A |
| 方案智能体 | 出实验流程 | `AiPlanService` + `ai-flow-spec.py` | **已有第一版**，本文只补留痕与判据 |
| 假设智能体 | 结果不达标时提改进 | `capability_recipe.criteria`（字段在、无读取方）+ `recovery_policy` | **降级为"归因建议"**（AI-3），不承诺自动改方案 |
| 代码智能体 | 写仪器控制代码 | **无对应物，也不需要**（§2.1） | **不做** |
| 硬件智能体 | 调度与资源 | 资源级互斥 + 按序取锁 + `AdmissionController` | **已有**，不接 AI（排程本身尚未实现，见 ROADMAP M9） |

**结论：七个里只做三个半**（方案 = 已有、试剂 = 只读、假设 = 归因建议 + 留痕这条横向能力）。
少做不是保守——**七个全做，等于把"能不能跑"的验证成本乘七**，而现在连"7 张 P2 配置表 0 行"都还没解决。

## 4. 五条 AI 主线（AI-1 ~ AI-5）

编号与 `物理可判定层…` 的 P-A~P-E **并列不重叠**：那边管"物理能不能做"，这边管"AI 怎么用、怎么留痕、怎么评"。

### AI-1 · 建议留痕（**先做，1 天**）

| 项 | 内容 |
|---|---|
| 落点 | 新表 `ai_plan_log`（`id` / `workflow_id` / `user` / `instruction` / `mode` / `request_hash` / `response_raw` / `ops_count` / `errors` / `applied_count` / `model` / `latency_ms` / `created_at` / `trace_id`） |
| 写入点 | `AiPlanService.plan` 出口（服务端，唯一写入方）；**采纳结果由前端回填** `POST /workflows/{id}/ai/plan/{logId}/applied` |
| 为什么服务端写 | 前端可被绕过；AI 调用是服务端发起的，只有服务端知道"真的调了" |
| 验收 | 一次 AI 改图后：库里有一行、`applied_count` 与页面提示的数字一致、能按 `workflow_id` 查出历史 |
| 隐私 | `instruction` 与 `response_raw` 属业务内容，**不进日志文件**（只入库），符合既有"密钥不进日志"的同一条纪律 |
| 回滚 | 表可 drop，无外部依赖 |

> 这条是**所有后续 AI 能力的前置**：没有它，后面每一条都无法回答"上线之后到底变好没有"。

### AI-2 · 只读问答（**1 周，风险最低、ROI 最高**）

| 项 | 内容 |
|---|---|
| 形态 | **不做聊天框**，做两处就地入口：①告警详情「为什么 / 该怎么办」②执行详情「这一步在干什么、在等什么」 |
| 工具集 | 全部 READ：`run_event`（按 run 取窗口）、`command_ledger`、`device_state`、`position_state`、`recovery_policy`、`error code` 字典、`plate_location_audit` |
| 硬约束 | ①**只读**，无 CONTROL 工具；②每条结论必须带**证据引用**（表名 + 主键区间 + 时间窗）；③查不到就说查不到，**不许猜**；④仿真数据必须标注"仿真" |
| 落点 | 新 `ai/AskService`（服务端）+ 两个页面组件；不改既有 API 语义 |
| 验收 | 用 20 条**已结案的真实告警**做回放：答案里的证据引用能对上库；答错的必须能归因到"数据不足"而非"编造" |
| 不做 | 不改流程、不重试、不点"恢复"按钮 |

> 为什么先做这个：它把 AI 放在**纯读**侧，出错的代价是"答案不好"，而不是"板子撞了"。
> 同时它立刻消耗掉本仓库最厚的资产——`run_event` / `command_ledger` / 审计。

### AI-3 · 告警归因建议（**1 周，依赖 AI-2 的工具集**）

| 项 | 内容 |
|---|---|
| 输入 | 错误码 + `device_raw_response` + 闸门拒绝记录（`EC-*`）+ 近 N 次同类告警的处置结果 |
| 输出 | 候选恢复动作（**限定在 `recovery_policy` 已有的动作枚举内**）+ 每条的依据 + 相似历史 run 列表 |
| 关键设计 | **不给自由文本动作**。动作必须是 `recovery_policy` 里登记过的枚举值，模型只能"选"和"排序"，不能"发明" |
| 验收 | 20 条历史告警：Top1 建议命中实际处置的比率；**误推荐率（推荐了会导致二次故障的动作）必须为 0** |
| 不做 | 不自动执行（人工点）；不修改 `recovery_policy` |

### AI-4 · 草案进闸门（**依赖 P-B1 的 L0 影子模式**）

| 项 | 内容 |
|---|---|
| 变化 | `applyAiOps` 之后，除 `compile` / `preflight` 外**再跑一次 L0 物理可行性影子判定**，把"物理上做不了"的节点在应用前列出来（只提示不拒绝） |
| 为什么必须等 P-B1 | L0 未就绪时，这一条只能做成"提示词里叮嘱模型注意体积"——那是幻觉的温床 |
| 验收 | 构造 10 条"参数合法但物理不可行"的草案（源孔体积不足 / 耗材余量不够 / 点位未标定），拦截率与误拒率同时给出 |
| 回滚 | 开关 `LABOS_PHYS_GATE=off` 与既有 L0 共用，不新增开关 |

### AI-5 · 用历史执行做离线评测（**持续，不碰设备**）

这是本仓库相对外部方案 B 的**唯一数据优势**：它有 4 场考试，我们有上万次执行记录。

| 项 | 内容 |
|---|---|
| 评测集 | 取"有执行记录"的流程（快照 2026-11-04：流程 1009 / 节点 14033 / 执行 10710 / 命令 116724，**未连库核实**）作为语料 |
| 三个任务 | ①**反向重画**：把已跑通的流程转成 Flow Spec，再让 AI 从"业务描述"重建，比对结构等价率与参数差异数；②**归因命中**：AI-3 在历史告警上的 Top1 命中率；③**草案通过率**：AI 草案一次过 `compile`+`preflight` 的比例 |
| 关键纪律 | 全程**离线回放**，不连设备、不写生产流程；评测集与提示词版本一起打 tag，否则改一次提示词就不可比 |
| 落点 | `scripts/ai-eval.py`（新），产出 JSON + 一行结论，供门禁可选调用 |

## 5. 角色 × 工具 × 权限 × 审计（"虚拟团队"的落地形态）

| 角色 | 工具（分级） | 数据边界 | 审计字段 | 谁审批 |
|---|---|---|---|---|
| 工艺/方法 | READ + 生成草案（**不落库**） | 流程、模板、设备能力目录 | `ai_plan_log` | 工艺负责人点"应用到画布" |
| 现场运维 | READ + 归因建议 | 告警、`run_event`、`device_state` | 同上 + `run_id` | 值班人点"执行恢复"（既有路径） |
| 物料/耗材 | READ + 补货建议 | `consumable_lot`、`plate_well` | 同上 | 库管 |
| 排程（**最后做**） | READ | 队列、甘特 | 待定 | — |

**三条硬约束（写进代码注释，不只写在文档里）**：

1. 工具必须分级：`READ` / `CONTROL` / `HAZARD`；**只读工具集里不得出现任何写库或发命令的方法**（用测试断言，不靠自觉）；
2. `CONTROL` 类**必须**经 `DriverStepExecutor` 同一条闸门链，**禁止新增旁路**；
3. 每条 AI 输出必须能溯源到 `trace_id`（仓库已有 `audit_log.trace_id`，需要透出到 AI 层）。

**为什么是四个角色而不是"每人一个"**：角色对应的是**权限与数据边界**，人对应的是"谁能用"。
一个实验室有 3 个工艺工程师，不需要 3 个 Agent，需要的是同一个"工艺助手"下的 3 条审计记录。

## 8. 三道墙（与既有文档一致，不得放宽）

沿用 `物理可判定层与中间件对齐-设计_20261116.md` §5 的三道墙，AI 侧再加一条：

1. **动作类型墙**：AI 只产出设备动作序列，不产出化学操作；
2. **生物学复杂度墙**：不承诺自愈，不上学习模型替规则；
3. **记账边界墙**：只追踪"板去了哪、耗材用了多少"，追踪不了反应；
4. **（新增）解释力墙**：AI 的每一条结论必须带**可核对的证据引用**；给不出证据的答案，宁可说"查不到"。

**对外话术（建议采用）**：

> **LabOS 保证过程物理上没有作弊，不保证科学上成立。**
> 在此基础上补一句：**AI 负责想，中控负责不让它把板子撞了；AI 想一次，中控复现 N 次。**
