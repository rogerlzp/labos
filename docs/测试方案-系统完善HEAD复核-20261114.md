## 3. A · `POST /api/scheduler/reload-config`

后端：`SchedulerController.reloadConfig()` → `ExperimentScheduler.reloadConfig()`，无参数，返回
`{reloaded, maxConcurrent, optimizationFactor, tickMs}`。

### A1 判别性：手动重载绕过自动重载（最重要）

```bash
echo "T0 基线: $(cfg)"
# 用一组与当前值明显不同的参数建 plan
auth -X POST -H 'Content-Type: application/json' \
  -d '{"planNo":"T-A1","optimizationFactor":10,"maxIterationsRunning":3,"iterationDelaySec":1}' \
  http://127.0.0.1:18080/api/schedule-plans
echo "T1 建后(未重载): $(cfg)"            # 期望：仍为 T0 的值（自动重载需 30~90s）
auth -X POST http://127.0.0.1:18080/api/scheduler/reload-config
echo "T2 手动重载后: $(cfg)"             # 期望：{"maxConcurrent":3,"optimizationFactor":10,"tickMs":3000}
```

**期望**：T1 == T0；T2 立刻变成 `3/10/3000`，无需等待。
三项映射公式（源码 `reloadConfig()`）：

- `maxConcurrent = Math.min(maxIterationsRunning, 4)`（线程池硬上限）
- `optimizationFactor` 夹到 `[0,100]`
- `tickMs = 2000 + iterationDelaySec × 1000`（**不是**固定 7000，取决于 delay）

### A2 映射边界

分别建 `maxIterationsRunning=9`（期望 `maxConcurrent=4`）、`optimizationFactor=200`（期望 `100`）、
`iterationDelaySec=5`（期望 `tickMs=7000`），每次建完调 `reload-config` 并核对。注意
`selectSchedulePlans` 按 `id DESC` 取第一条非 `archived/done` 的 plan，**旧 plan 会一直排在新 plan 后面**，
所以每轮要先删掉上一轮的 `T-A*`，否则测到的是旧值。

### A3 幂等

```bash
auth -X POST http://127.0.0.1:18080/api/scheduler/reload-config; echo
cfg; echo            # 与上一次完全一致
```

### A4 状态过滤

把 plan 置为 `archived` 或 `done` 后调 `reload-config`，源码会 `continue` 跳过。
⚠️ 与 A5 叠加时行为见已知缺陷。

```bash
psqlq "UPDATE schedule_plan SET status='archived' WHERE plan_no='T-A1';"
auth -X POST http://127.0.0.1:18080/api/scheduler/reload-config
```

### A5 🔴 已知缺陷回归（**预期失败**，需 owner 裁决）

```bash
psqlq "DELETE FROM schedule_plan WHERE plan_no LIKE 'T-A%';"
psqlq "SELECT count(*) FROM schedule_plan;"                 # 0
auth -X POST http://127.0.0.1:18080/api/scheduler/reload-config
cfg                                                       # 期望回落 4/50/2000
```

上一轮独立验证发现 `reloadConfig()` 只在 `for (plan : selectSchedulePlans(...))` 循环体内赋值，
**无「无 active plan ⇒ 回落默认」分支**：清空表后 `reloaded:true` 但 config 保持最后一次值，直到进程重启。
截至 `6ee01b6` 该代码未改动，**本用例预期不通过**。审核结论应记录为「已知缺陷，待修」，不要误判成新回归。
建议修法：循环前先赋默认值，或循环未命中任何有效 plan 时显式回落。

### A6 权限

`ApiAuthInterceptor` 用的是 `AuthService.Session.canWrite()`：`admin || operator`；
`RbacRules.canWrite()` 多一个 `designer`，但**拦截器没用它**。
用 viewer / designer 账号 `POST /api/scheduler/reload-config` 期望 **403**；admin / operator 期望 200。
⚠️ 这与 D4「`/schedule-plans` 对 designer 可见」冲突，见 §10 第 8 条，是本次重点核对项。

## 4. B · `GET/PUT /api/settings/stale-pause`

后端：`OpsUserController.stalePauseSetting()/updateStalePauseSetting()`；
`RuntimeSettings.saveStalePauseAutoDismiss()` 里 `eff = Math.max(0, days)`，写 `sys_setting`
（`stale_pause.auto_dismiss_days`），改 `volatile` 内存值，审计 `settings.stalePauseAutoDismiss`。

| 编号 | 用例 | 命令 | 期望 |
|---|---|---|---|
| B1 | 默认读 | `auth .../api/settings/stale-pause` | `{"autoDismissDays":0}`（除非设了环境变量/库里有旧值；先记录实际值） |
| B2 | 正常写+回读 | `auth -X PUT -H 'Content-Type: application/json' -d '{"autoDismissDays":14}' .../api/settings/stale-pause` 然后 GET | 两次都是 `{"autoDismissDays":14}` |
| B3 | 落库核对 | `psqlq "SELECT value FROM sys_setting WHERE scope='global' AND setting_key='stale_pause.auto_dismiss_days'"` | `14`（键列是 `setting_key`，**不是** `key`） |
| B4 | 缺字段 | `PUT -d '{}'` | HTTP 400，`必填 autoDismissDays（0=关）` |
| B5 | 负数夹紧 | `PUT -d '{"autoDismissDays":-5}'` 然后 GET | `0`（后端 `Math.max(0,·)`） |
| B6 | 超前端上限 | `PUT -d '{"autoDismissDays":99999}'` | 后端**接受** 99999（前端 `InputNumber max=365`，后端无上限）→ 记录为前后端校验不一致 |
| B7 | 审计 | `auth ".../api/audit?action=settings.stalePauseAutoDismiss"` | 至少 1 条，`detail` 含 `autoDismissDays=` |
| B8 | 权限 | viewer `PUT` | 403 |

**B9 生效性（可选，需造数，成本高）**：设 `days=1`，构造暂停 >1 天的 `waiting_human` run，
等 30 tick 后查是否被 `dismissBatch(null,"waiting_human",24)` 清掉；同时确认 `paused_fault` /
`paused_unknown` 不受影响。源码 `warnStalePauses()` 只在 `autoDismissDays>0` 时动作，否则只 `log.warn`。
⚠️ 前端 `SchedulePlans.tsx` 注释写「保存后约 60s 生效」，但 `saveStalePauseAutoDismiss` 是**立即**改内存值；
真正有延迟的是每 30 tick 才扫一次的自动处置动作。审核时按「设置即时生效、处置有延迟」判定。

**清理（必做）**：`PUT` 回 `0`，并确认 `sys_setting` 里为 0。

## 8. F · 权限矩阵

`ApiAuthInterceptor` 规则：`!GET && !canWrite()` → 403；`path.startsWith("/api/users") && !isAdmin()` → 403。

`ApiAuthInterceptor.check()` 的写权限判断是 `AuthService.Session#canWrite()`（`admin || operator`），
**不是** `RbacRules.canWrite(role)`（`admin || operator || designer`）。

| 角色 | GET 各端点 | POST reload-config / PUT stale-pause / POST plan / POST booking |
|---|---|---|
| admin | 200 | 200 |
| operator | 200 | 200 |
| **designer** | 200 | **403**（`Session.canWrite()` 不含 designer） |
| viewer | 200 | 403 |

用例：为每个角色登录取 TOKEN，逐一打上述写端点，记录 HTTP 码。
注意 `/api/settings/stale-pause` **不是 admin 专属**（只有 `/api/users` 是），operator 也能改系统设置；
若产品期望「仅管理员可改」，这是需要报告的口径差异，而非通过项。

🔴 **重点核对**：`nav.tsx` 把 `/schedule-plans` 开放给 `designer`，但该页三个动作
（新建/编辑 plan、「立即生效」、改 `stale-pause` 天数）都是非 GET，designer 会全部 403。
若实测确为 403，应判定为**页面可见性与权限不一致**（修法二选一：拦截器改用 `RbacRules.canWrite`，
或把该页收回 admin）。

## 10. 已知风险 / 预期失败项（勿误判为回归）

1. 🔴 **A5 预期不通过**：`reloadConfig()` 无「无 plan ⇒ 回落默认」分支，截至 `6ee01b6` 未修。
2. 🟡 **自动重载周期不固定**：`ticks % 30` + `Thread.sleep(tickMs)`，无 plan 时 60s，
   `delay=1` 时 90s，`delay=5` 时 210s。交接文档「约 60s」只在默认配置成立。
3. 🟡 **前端注释与实现不符**：「暂停堆积治理」`onChange` 即时落库，注释写「点保存才落库」。
4. 🟡 **前后端校验不一致**：前端 `max=365`，后端只做 `Math.max(0,·)`，无上限。
5. 🟡 **TOKEN ~60s 过期**：跨等待必须重新登录。
6. ⚪ **并发会话**：验证期间曾出现内核重启（12:43）与多个未提交文件；每个用例前后都记 `git rev-parse HEAD` 与工作区状态。
7. ⚪ 交接文档 §5.5「生产口令轮换」按 owner 2026-11-14 口径不再作为待办。
8. 🔴 **designer 权限冲突（待实测确认）**：`/schedule-plans` 对 designer 可见，但拦截器
   `Session.canWrite()` 只认 admin/operator，页面上所有写动作预期 403。若确认，属功能不可用而非边界。
