## 0. 目标与修订原则

本清单用于驱动三份设计文档的联合修订。三份文档是同一套并行执行协议的不同视角，不得各自定义相同概念。

修订原则：

1. 同一概念只有一个权威定义；其他文档引用并展开，不另行定义。
2. 表结构、SQL、状态机、协议字段和流程示例必须遵循同一语义。
3. 不允许通过实现细节绕过设计约束，例如用设备独占租约恢复隐式事件弱匹配。
4. UNKNOWN 不等于物理停止，不等于 IDLE，也不等于资源可释放。
5. 设备能力未经协议或现场证据验证时，必须标记为未知/不支持，不得默认假设成立。
6. 业务已确定的语义不在本轮重新讨论：分支失败后全体停止发新指令、已发指令等待收尾；变量流程级共享；禁止 join 同名变量冲突；分支不设业务超时。

## 1. P0-01：统一命令身份模型

### 1.1 当前冲突

现有文档对 `commandId` 同时承担逻辑操作身份、设备幂等身份和事件关联身份的边界不清；表设计使用 `operation_key`，而并行设计中的身份生成规则没有完整覆盖 branch、loop、invocation 等并行维度。对于不支持设备去重的设备，重试时是否复用 commandId 也没有统一定义。

### 1.2 统一设计决议

必须区分以下三个业务身份：

| 标识 | 语义 | 生命周期 |
|---|---|---|
| `operation_id` | 一次逻辑操作的唯一身份 | 逻辑操作生命周期内稳定 |
| `idempotency_key` | 设备侧识别重复提交的幂等身份 | 按设备去重能力定义 |
| `command_id` | 一次实际下发命令 attempt 的唯一身份 | 每次实际下发唯一 |

规则：

**operation_id**
- 标识一次逻辑操作，不因网络重试或物理命令重发而改变。
- 必须区分不同 Run、节点、branch、loop iteration 和同一节点内的多次 invocation。
- `operation_key` 如保留，应明确它是可读业务键还是唯一身份的编码；不得与数据库主键混用。

**idempotency_key**
- 只有设备协议明确支持去重时才有效。
- 同一逻辑操作的重试可复用同一个 key，但必须遵守设备侧去重语义和有效期。
- 不支持设备去重的设备不得宣称具备设备侧幂等保证。

**command_id**
- 每次实际下发 attempt 分配独立且唯一的 ID。
- 设备回包/事件若支持精确关联，回显对应 attempt 的 command_id。
- 迟到事件必须关联原 attempt，不得关联“当前最新命令”。
- 不同 branch、invocation、loop iteration 和 attempt 不得发生身份碰撞。

### 1.3 表结构修订要求

检查并统一 `operation_id`、`operation_key`、`command_id`、`idempotency_key`、`attempt_id` 的关系。无需为了凑齐术语机械增加字段，但必须明确：

1. 数据库主键与业务身份的区别。
2. `operation_key` 是否为 `operation_id` 的可读表达。
3. `command_id` 是否一条实际下发记录对应一个。
4. 同一逻辑操作多个 attempt 的父子关系。
5. 迟到回包/事件如何定位原 attempt。
6. 唯一约束基于什么业务范围，是否包含 tenant/device 等隔离维度。

### 1.4 文档责任

- **并行网关设计：** 定义逻辑操作身份的组成维度，补充 branch、loop、invocation。
- **命令事件规范：** 定义 command attempt、重试、设备幂等和回显规则。
- **表设计 v4：** 定义字段、唯一索引、关联关系及 attempt 持久化。

### 1.5 验收条件

- [ ] 同一 Run、同一节点、两个 branch 执行相同设备操作，身份不冲突。
- [ ] 同一逻辑操作重试时 operation_id 不变。
- [ ] 每次实际下发 attempt 有唯一 command_id。
- [ ] 仅在设备确实支持去重时使用 idempotency_key。
- [ ] 不支持设备去重时，不宣称设备侧 exactly-once。
- [ ] 第一次 attempt 的迟到事件不能误归属第二次 attempt。
- [ ] 并行创建操作时不发生唯一键冲突或错误复用。

**完成标准：** 三份文档对身份定义、生命周期、生成规则、存储关系和关联规则完全一致。

## 2. P0-02：统一严格 commandId 事件归属

### 2.1 当前冲突

现有文档一方面声明“事件归属只认 commandId”，另一方面仍残留允许 NULL 参与的 SQL、弱匹配文字，以及通过设备独占推导事件归属的潜在解释。

### 2.2 统一设计决议

命令关联型事件只能通过精确 commandId 匹配：

1. event.command_id 必须非 NULL。
2. waiter.expect_command_id 必须非 NULL。
3. 两者必须完全相等。
4. 不允许通过最近命令、时间窗口、当前设备占用者、Run ID 或设备独占状态推断归属。
5. 不允许 NULL 与 NULL 匹配。
6. 不允许 NULL 作为弱匹配候选。
7. 同一事件最多被一个有效 waiter 成功认领。
8. 重复事件不得重复推进节点。
9. 不匹配事件必须保留为未归属/待审计事件，不得伪装成已消费。

匹配条件的核心约束：

```sql
WHERE w.expect_command_id IS NOT NULL
  AND e.command_id IS NOT NULL
  AND w.expect_command_id = e.command_id
```

这只是身份匹配条件，不代替 tenant、device、event_type、waiter 状态、有效期和原子认领约束。

### 2.3 系统型事件与命令关联型事件

**命令关联型事件**
- 可以推进具体逻辑操作。
- 必须精确匹配 commandId。
- 不匹配时进入未归属或异常处理。

**系统型事件**
- 如设备上线、离线、告警、状态广播。
- 不属于某个命令 waiter。
- 可更新设备状态或触发系统级处理。
- 不得因事件发生在某个 Run 执行期间而归属该 Run。

### 2.4 无 commandId 设备边界

设备独占租约只解决物理互斥，不构成事件归属证明。

- **类型 A：命令返回可可靠证明动作完成。** 可按明确的命令完成结果推进；无 commandId 自发事件仍不得认领 waiter。
- **类型 B：可通过可靠状态查询证明动作完成。** 可在设备租约内查询状态；必须定义状态来源、新鲜度和完成判据。查询结果不是伪造的 commandId 事件。
- **类型 C：只能依赖无 commandId 自发事件判断完成。** 不得弱匹配，不得仅凭设备独占推断归属；没有可靠关联机制前，不允许此类事件自动推进并行流程。

### 2.5 表与 SQL 修订要求

检查 waiter 注册、事件匹配、advisory lock 锁域、事件唯一认领、重复事件、消费状态、NULL 处理和不匹配事件持久化。创建 waiter 与认领事件必须使用一致的锁域和事务协议，防止注册/到达竞态。

### 2.6 文档责任

- **并行网关设计：** 统一事件推进规则，删除按当前 Run/设备占用者/时间推断归属的描述。
- **命令事件规范：** 删除弱匹配原则和 SQL，定义事件分类及无 commandId 设备边界。
- **表设计 v4：** 修正 SQL、NULL 处理、原子认领和未归属事件状态。

### 2.7 验收条件

- [ ] command_id 为 NULL 的事件不能匹配任何命令 waiter。
- [ ] expect_command_id 为 NULL 的 waiter 不参与命令事件匹配。
- [ ] commandId 不同的事件不能互相认领。
- [ ] 重复事件不能重复推进节点。
- [ ] 两个 waiter 竞争一个事件时最多一个成功认领。
- [ ] 无 commandId 设备不能通过独占租约恢复隐式弱匹配。
- [ ] 系统型事件不能误推进 Run 的命令等待节点。
- [ ] 三份文档不再存在与严格匹配矛盾的 SQL、示例或文字。

**完成标准：** 全文不存在通过 NULL、最近命令、时间窗口或当前设备占用者推断命令事件归属的规则。

## 3. P0-03：统一设备物理占用与失败收尾状态机

### 3.1 当前问题

以下事实不能混为一谈：命令已发送、设备已接受、命令结果已返回、物理动作已完成、设备恢复空闲、中控释放设备资源。失败后停止发新命令并等待已发动作，若没有收尾上限，可能永久等待；若超限后直接释放锁，则可能在设备仍运行时被另一个 Run 使用。

### 3.2 统一设计决议

逻辑命令生命周期、设备物理状态、设备调度占用必须分开建模。

**命令生命周期（示意，最终状态名可与现有模型统一）：**

```text
CREATED → DISPATCHED → ACCEPTED → COMPLETED / FAILED / UNKNOWN
```

**设备物理状态：**

```text
IDLE / BUSY / UNKNOWN
```

**设备调度占用：**

```text
AVAILABLE / LEASED / QUARANTINED
```

命令完成不自动意味着设备 IDLE。只有可靠的物理状态证据，才允许释放设备调度许可。

### 3.3 设备准入分档

| 设备能力 | 策略 | 约束 |
|---|---|---|
| 有可靠物理状态反馈 | B：派发前检查状态 | 检查状态新鲜度，并保护检查与派发之间的竞态 |
| 无可靠物理状态，但有可靠完成信号 | A：租约持有到完成 | 同一设备单占用，完成后还需满足安全释放条件 |
| 没有可靠状态和完成信号 | 禁止自动并行 | 人工确认或补齐设备能力 |
| 设备协议保证忙时拒绝新命令 | 可增加 C 作为设备侧保护 | C 不能替代中控准入 |

B 方案必须满足：
1. 状态来自真实设备反馈。
2. 状态有时间戳或可验证的新鲜度。
3. UNKNOWN 不得当作 IDLE。
4. 状态检查与调度许可获取/命令派发之间不存在未保护竞态。

A 方案的独占范围是单次设备占用期，不是整个 Run：

```text
获取设备租约
  → 验证设备可用
  → 下发命令
  → 等待可靠完成
  → 确认设备满足释放条件（通常为 IDLE）
  → 释放租约
```

### 3.4 失败收尾与等待上限

业务语义固定：任一分支失败后，全体停止发新指令，已发指令等待收尾。

建议组级状态：

```text
RUNNING → STOPPING
STOPPING --所有已发动作可靠收尾--> FAILED
STOPPING --等待上限触发且仍有未确认动作--> FAILED_NEEDS_MANUAL
```

等待上限采用双层约束：

- 方法级 `drain_timeout`：该方法停止发新命令后，已发动作允许继续完成的时间。
- 设备级 `max_drain_timeout`：设备允许的最大自动等待边界。

实际等待边界由方法配置与设备硬上限共同约束。具体值必须依据方法执行特征、设备安全要求和真实运行数据确定，不得凭空统一指定。

等待上限到达只表示自动等待结束，不表示设备停止：

- 未确认命令进入 UNKNOWN。
- 设备进入 QUARANTINED。
- 不得自动释放物理设备占用。
- 不得自动准入新的 Run。
- 必须有明确的人工确认和恢复流程。

同时区分三种时间语义：
1. 业务分支超时（本业务已确定不设置）。
2. 失败后的 drain 等待上限。
3. 设备物理状态确认/隔离恢复期限。

不得用一个 waiter deadline 代替这三种语义，也不得因分支不设超时而让故障收尾永久等待。

### 3.5 无 commandId 设备与租约

- 设备租约负责物理互斥，不负责事件归属。
- 可以使用可靠命令完成结果或可靠状态查询推进流程。
- 无法可靠确认完成的设备必须隔离或人工处理。
- 设备锁、设备租约、命令 waiter、事件归属是不同概念，不能用一个字段或一个锁替代。

### 3.6 文档责任

- **并行网关设计：** 定义失败停止/drain/人工收尾状态机；区分分支超时与故障收尾上限。
- **命令事件规范：** 定义 ACK、命令完成、物理动作完成和 IDLE 的区别；定义设备能力分档。
- **表设计 v4：** 明确 waiter 完成不等于设备释放；检查是否需要持久化租约、隔离和人工恢复状态。

### 3.7 验收条件

- [ ] ACK 不会直接释放物理设备占用。
- [ ] 命令完成与设备 IDLE 可以独立表达。
- [ ] 分支失败后所有分支停止发新命令。
- [ ] 已发命令等待可靠完成或等待上限触发。
- [ ] 超限 UNKNOWN 进入隔离，不自动释放并重新准入。
- [ ] 不同设备可独立完成收尾。
- [ ] 单设备隔离不会无条件阻塞无关设备。
- [ ] 人工恢复有明确的物理状态确认依据。
- [ ] 分支不设超时不会被实现为故障收尾永久等待。

**完成标准：** 逻辑失败、命令完成、设备物理空闲和资源释放形成独立、闭合的状态迁移。

## 4. P0-04：重新定义 DeviceLock 重入与逻辑所有权

### 4.1 当前问题

ThreadLocal 表达的是线程上下文，不能天然表达跨线程异步执行的逻辑所有权。并行分支、异步命令、回调和 continuation 恢复可能导致线程身份与逻辑操作身份不一致。

### 4.2 统一设计决议

保留物理设备互斥，但分离：

1. 物理设备是否被占用。
2. 当前逻辑执行是否有权重入。
3. 当前线程是否持有底层线程锁。

建议使用显式逻辑租约身份：

| 标识 | 含义 |
|---|---|
| `lease_id` | 一次设备占用期的唯一身份 |
| `owner_operation_id` | 逻辑操作所有者 |
| `owner_run_id` | Run 归属，用于审计和隔离 |
| `owner_branch_id` | 可选诊断维度；不得因此把不同分支视为同一物理锁 |

重入规则：

- 只有持有同一有效 lease_id 的逻辑执行才允许重入。
- 同 Run 不同 branch 不因 Run ID 相同而自动重入。
- 不同 Run 不能重入同一个单容量物理设备租约。
- continuation 跨线程恢复时，逻辑租约身份保持不变。
- 释放必须验证 lease_id、所有者和当前状态。
- 过期、重复释放和错误所有者释放必须安全失败。

ThreadLocal 可保留为线程内优化或诊断信息，但不能作为唯一逻辑所有权依据。

### 4.3 必须覆盖的反例

**A. 同线程、同 Run、不同 branch：** A 分支持有租约后，B 分支在同一线程运行；B 不能仅因线程和 Run 相同而重入。

**B. 跨线程释放：** 线程 A 获取租约，线程 B 收到完成回调；逻辑释放必须基于显式租约身份，不能假设 ThreadLocal 跨线程传递。

**C. 异步 continuation：** 分支下发命令后让出控制权，恢复时线程变化；逻辑租约身份不变。

**D. 同设备不同 Run：** 两个 Run 同时申请单容量设备，最多一个获得有效租约。

**E. 重复完成回调：** 同一命令完成回调重复到达，重复释放不能破坏其他占用者的租约。

### 4.4 文档责任

- **并行网关设计：** 定义 BranchState 与设备租约所有权关系；异步 continuation 不改变逻辑所有权。
- **命令事件规范：** 定义完成回调如何定位 lease；释放必须幂等并校验所有权。
- **表设计 v4：** 检查租约是否需要独立持久化，以及 lease 与 operation/attempt 的关系、释放、隔离和恢复状态。

### 4.5 验收条件

- [ ] 同线程不同 branch 不能错误重入。
- [ ] 同一 Run 的不同逻辑操作不能仅凭 Run ID 重入。
- [ ] 跨线程 continuation 保持正确的逻辑租约身份。
- [ ] 非所有者不能释放租约。
- [ ] 重复释放不会破坏锁状态。
- [ ] 两个 Run 不能同时获得同一单容量设备的有效租约。
- [ ] ThreadLocal 不再是逻辑所有权的唯一判断依据。

**完成标准：** 物理互斥与逻辑重入权限有明确边界，所有权不依赖线程身份。

## 6. 文档权威定义与责任矩阵

每项只设一个权威定义来源：

| 修订项 | 并行网关设计 | 命令事件规范 | 表设计 v4 |
|---|---|---|---|
| P0-01 命令身份 | 逻辑操作与分支身份 | 命令、attempt 与设备幂等协议 | 字段、索引、关联关系 |
| P0-02 严格事件归属 | 事件推进规则 | 协议归属规则 | SQL、认领和唯一性 |
| P0-03 设备占用与失败收尾 | 分支/组状态机 | 设备能力、完成证据 | 租约、隔离状态持久化 |
| P0-04 DeviceLock 重入 | 分支与租约所有权 | 回调释放和校验 | 租约持久化及关联 |

建议权威来源：
- 命令身份的跨文档术语和原则：本清单；具体命令协议细节由命令事件规范定义。
- 严格事件归属原则：命令事件规范；SQL/事务实现约束由表设计定义。
- 失败收尾与并行组状态机：并行网关设计；设备物理状态细节由命令事件规范定义。
- 租约持久化结构：表设计；逻辑所有权语义由并行网关设计定义。

## 7. 修订顺序

1. **P0-01 命令身份模型：** 先统一 operation、idempotency、command attempt 的关系。
2. **P0-02 严格事件归属：** 基于新的 command_id 定义修正 SQL、事件协议和 waiter 行为，清除弱匹配残留。
3. **P0-03 设备物理占用与失败收尾：** 确定设备状态、租约、隔离、人工恢复状态机。
4. **P0-04 DeviceLock 重入：** 基于 lease 和 operation 的身份关系修订重入规则。
5. **三文档联合检查：** 检查术语、SQL、状态机、字段、示例和边界条件的一致性。
