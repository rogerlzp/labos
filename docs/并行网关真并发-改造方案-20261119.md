# 并行网关真并发 —— 改造方案（待评审）

- 日期：2026-11-19
- 性质：**改造方案 + 待评审问题清单**，不是最终设计
- 前置：《并行网关并发执行设计》（2026-11-19）已定四条业务语义
- 状态：**未实施**（容器线程安全化已完成，执行模型未动）

---

## 0. 一句话

**把 `GraphRunner` 主循环里"一次执行一个节点"改成"并行组提交线程池、等齐再继续"，前提是 8 处共享状态全部线程安全。**

---

## 1. 现状（代码事实）

### 1.1 主循环是单线程

`GraphRunner:736`：

```java
while (!ready.isEmpty() && !progress.aborted()) {
    String key = ready.poll();      // ← 一次取一个
    ...
}
```

`ready` 是 `ArrayDeque`（`GraphRunner:698`），`gateway_parallel` 只是把多条出边的目标**依次**压进同一个队列。

**实测证据**（基准流程 `BASELINE-SERPAR-01`，run 1001810）：

| 节点 | 开始时间 | 设备执行 |
|---|---|---|
| Activity_0002 回零 | 14:40:06 | 11.7 s |
| Activity_0004 查料栈 | 14:40:18 | 11.5 s |
| **Activity_0008 分液** | **14:40:31** | 12.2 s |
| **Activity_0009 机械臂移动** | **14:40:45** | 11.6 s |
| Activity_0015 回安全位 | 14:40:59 | 10.9 s |

两条并行分支**间隔 14 秒，完全不重叠**。

### 1.2 主循环的状态全是方法局部变量

`GraphRunner:693-703`：

```java
Map<String, Integer> pending = new HashMap<>();     // 未完成入边计数（join 用）
Deque<String> ready = new ArrayDeque<>();           // 待执行队列
Set<String> done = new HashSet<>();                 // 已完成
ConditionalBranchTracker tracker = ...;             // 条件分支存活性
Map<String, Integer> visits = new HashMap<>();      // 圈次
```

**这五个都是普通容器**，并发分支会同时读写。

### 1.3 执行段上千行，用 `break`/`continue` 控制主循环

`GraphRunner:760-1000+` 是一个 if-else 链：

```java
if (裁剪) { ... }
else if (续跑) { ... }
else if (干跑) { ... }
else if (BUILTIN) { ... break; }        // ← break 退出主循环
else if (TASK) {
    if (物料闸门) { ready.offer(key); break; }
    if (暂停检查) { ready.offer(key); break; }
    ... 500 行 ...
}
```

**要并发执行分支，必须先把这段抽成"返回结果"的方法**（`break` → `return STOP`）。这是本方案最大的一次性改动。

### 1.4 已是线程安全的（2026-11-19 已改）

`GraphRunner` 的 6 个字段容器：

| 容器 | 现状 |
|---|---|
| `variables` | `ConcurrentHashMap` |
| `locallyWrittenVars` | `ConcurrentHashMap.newKeySet()` |
| `consumedValues` | `ConcurrentHashMap`（`alreadyConsumed` 已改 `compute`） |
| `externallyOwnedVars` | `ConcurrentHashMap.newKeySet()` |
| `eventCursors` | `ConcurrentHashMap`（已改 `merge(max)` 单调） |
| `activatedKeys` | `ConcurrentHashMap.newKeySet()` |

### 1.5 还有 2 处未处理的共享状态

**① `RunProgress`（`engine/RunProgress.java`）**

```java
private final Map<Long, NodeProgress> nodes = new LinkedHashMap<>();   // :15
private boolean aborted;                                               // :16
private boolean materialHold;                                          // :19

public NodeProgress node(long nodeId) {
    return nodes.computeIfAbsent(nodeId, NodeProgress::new);           // :21
}
```

- `LinkedHashMap` + `computeIfAbsent` 并发下会抛 `ConcurrentModificationException` 或丢写
- `aborted` / `materialHold` 是裸 boolean，跨线程不可见

**② `RunStateMachine`（`engine/RunStateMachine.java`）**

这个类的注释**自己就写着**（`:23`）：

> **线程安全**：本类**非**线程安全（`seq` 为实例字段且非原子）。

```java
private long seq = 0;      // :40
seq++;                     // :340，用于 ExecutionEvent 序号
```

**这是硬伤**：并行分支同时调状态机会产生重复序号或丢号，而 `seq` 很可能被用作事件去重/排序依据。

## 2. 目标

| 项 | 现在 | 目标 |
|---|---|---|
| `SPLIT_PARALLEL` 的多条出边 | 依次执行 | **同时执行** |
| `JOIN_PARALLEL` | 等所有入边到齐（已有） | 不变 |
| 空跑耗时（基准流程） | 62.5 s | ~50 s（省一段设备时长） |
| 台账 | 完整 | 完整（不能因为并发丢记录） |

**不在本次范围**：多批次并行、事件归属、run 级并发上限。

## 3. 方案

### 3.1 总体结构

```
主循环（仍单线程）
  ├─ 普通节点 → executeNode(key, visit) → Outcome
  └─ 并行组入口 → runParallelGroup(group)     ← 阻塞到全部完成
        ├─ 提交分支 1 到线程池
        ├─ 提交分支 2 到线程池
        └─ allOf().join() → 汇总结果 → 继续主循环
```

**关键：主循环本身不并发**，只在"遇到并行组"时交出控制权。这样 `ready`/`done`/`pending`/`visits` 的语义完全不变。

### 3.2 五个步骤

| 步 | 内容 | 工作量 | 风险 |
|---|---|---|---|
| **1** | 把 `760-1000+` 的执行段抽成 `executeNode(key, visit, LoopState) → Outcome` | 半天 | 中（纯重构，行为不变） |
| **2** | 图分析：`split → join` 配对、切分支子图、校验分支互不相交 | 2 小时 | 低 |
| **3** | `runParallelGroup`：分支提交线程池、`allOf` 等齐、结果汇总 | 半天 | 中 |
| **4** | 停止语义：`stopFlag` + 分支在节点边界退出 + 暂停聚合 | 2 小时 | 中 |
| **5** | 修 `RunProgress` 与 `RunStateMachine` 的线程安全 | 2 小时 | 低 |

**总计 1.5–2 天。**

### 3.3 为什么不做"每分支一个 GraphRunner 实例"

看起来最干净，但不可行：

```java
public GraphRunner(RunStateMachine stateMachine, ...)   // :676
```

它的第一个参数是 **run 级**状态机。分支不能各自 new 一个（会重复初始化、重复写事件）。要共享就必须把状态机改成线程安全——那和方案 3.1 的工作量一样，还多了一层对象管理。

## 4. 七个设计决策（**评审重点**）

### D1：`done` / `visits` 在分支间共享还是隔离？

| 选项 | 后果 |
|---|---|
| **共享** | 分支 A 做过的节点，分支 B 会被 `done` 挡住 ⇒ **漏执行** |
| **隔离**（每分支一个 Set/Map，join 时合并） | 正确，但要处理"同一节点在不同分支"的圈次 |

**我的建议**：隔离。分支内用独立的 `done`/`visits`，join 时合并回主集合（取并集，圈次取 max）。

**反例风险**：如果一个节点被两条分支同时覆盖（子图相交），隔离后会各跑一次 ⇒ `run_node` 唯一键 `(run_id, node_key, attempt, loop_index)` 冲突。**所以第 2 步必须校验"分支子图互不相交"，并在编译期报错。**

### D2：变量"读-改-写"要不要原子？

`variables` 已是 `ConcurrentHashMap`，但：

```java
int n = Integer.parseInt(variables.get("count"));
variables.put("count", String.valueOf(n + 1));    // 两步，并发下丢更新
```

**我的建议**：**不提供原子自增**，改为**编译期禁止同一并行组内两分支写同一个 key**。理由：

- 提供原子 API（`computeAndGet`）会让"变量当计数器"变成鼓励用法，而计数器在并行流程里几乎总是语义不清（谁该看到几？）
- 编译期禁止是硬约束，运行时不会出静默错误

**代价**：如果真有"两分支都要累加"的需求，需要改成 join 后统一算。

### D3：一个分支失败，其他分支怎么办？

业务已定：**停止发新指令，已发出的等设备完成**。

实现：

```java
AtomicBoolean stopFlag;
// 分支在**节点边界**检查：
if (stopFlag.get()) return Outcome.STOP;
// 任一分支失败：
stopFlag.set(true);
```

**待评审**：如果分支正卡在 `__awaitEvent` 等事件（可能几十分钟），`stopFlag` 设了它也不会立刻退出——要等事件超时或到达。**这个等待没有上限**（用户已定"分支不设超时"）。

**建议**：加一个"停止等待上限"（与设备收尾窗口同源，按方法配置），超限的标 `UNKNOWN` 强制退出。**这条要评审确认。**

### D4：暂停怎么聚合？

现在"在任务节点边界检查 `pauseChecker`"是单点的。并发后：

```
分支 A 到边界，停了
分支 B 还在跑
```

**我的建议**：用 `CountDownLatch(分支数)`，每个分支到边界后 `countDown()`，主循环 `await(上限)`。全部到达才算"已暂停"；部分到达则记录"哪几个分支还在跑"。

**待评审**：如果分支 B 长期不到边界（比如在等事件），暂停会一直"未完成"——同样需要上限。

### D5：台账并发写安全吗？

| 组件 | 现状 | 风险 |
|---|---|---|
| `nodeStateRecorder`（`Consumer<String,String>`） | 未核实 | 可能走 DB，多线程并发写 |
| `ExecutionListener`（状态机注入） | 未核实 | 同上 |
| `run_node` / `run_step` 表 | 有唯一键 | 并发插入可能冲突 |

**这是本方案最大的未核实项。** 需要评审者帮忙确认：`WorkflowService.onStepStart/onStepDone` 被多线程调用时，DB 连接从哪来？是否线程安全？

**我的判断**：`Tx.inTransaction` 用 `DataSourceUtils` 拿**线程绑定连接**，所以多线程各自拿不同连接，写库本身没问题；但**同一节点的记录**若被两个分支同时写，会冲突（靠 D1 的子图不相交避免）。

### D6：线程池模型

| 选项 | 说明 |
|---|---|
| **全局固定池**（大小 = 最大分支数，默认 4） | 简单；但多 run 并发时会争抢 |
| 每 run 一个池 | 隔离好；但线程数 = run 数 × 分支数，可能爆炸 |
| 复用 `ForkJoinPool.commonPool` | 零配置；但会被其他任务影响 |

**我的建议**：全局固定池 + 信号量限流（同时运行的并行组数 ≤ N）。**这条要与"run 级并发上限"一起定。**

### D7：嵌套并行组

```java
// 外层分支里又有 split
runParallelGroup(outer) → runBranch() → 又遇到 split → runParallelGroup(inner)
```

**建议**：`inner` 在 `outer` 的分支线程里执行，**不额外申请信号量**（否则嵌套会自我阻塞，和之前"执行体数"那条结论一致）。

**待评审**：内层失败如何传播到外层——直接 `stopFlag` 全局置位？

## 5. 风险清单

| ID | 风险 | 等级 | 缓解 |
|---|---|---|---|
| **R1** | `RunStateMachine.seq` 非原子（代码自述非线程安全） | **高** | 改 `AtomicLong`；改造前必须先改 |
| **R2** | `RunProgress.nodes` 是 `LinkedHashMap` | **高** | 改 `ConcurrentHashMap` + `AtomicBoolean` |
| **R3** | 1000 行控制流改写，现有测试覆盖不到 | **高** | 分两步：先纯重构（行为不变）验证，再加并发 |
| **R4** | 台账并发写（`nodeStateRecorder` / `ExecutionListener`）未核实 | 中 | 需要评审确认 |
| **R5** | 分支子图相交导致 `run_node` 唯一键冲突 | 中 | 编译期校验 + 报错 |
| **R6** | 停止/暂停等待无上限（与"分支不设超时"冲突） | 中 | 加收尾上限 |
| **R7** | 线程池争抢导致多 run 时性能反降 | 中 | 信号量限流，与 run 并发上限一起定 |

## 6. 验收

| ID | 场景 | 期望 |
|---|---|---|
| P-01 | 基准流程（2 分支各 1 节点） | 两分支 `actual_start` 相差 **< 1 秒** |
| P-02 | 同上 | 总耗时比串行少约一个分支时长 |
| P-03 | 分支 A 失败 | 分支 B 停止发新指令，已发出的等回包 |
| P-04 | 暂停 | 全部分支到边界才标 `paused(control)` |
| P-05 | 台账 | `run_node` 每个节点一条，无重复、无缺失 |
| P-06 | 分支子图相交 | 编译期报错，不允许保存 |
| P-07 | 嵌套并行 | 内层不额外申请信号量，不死锁 |
| P-08 | 单分支流程（无并行） | 行为与改造前**完全一致** |

## 7. 请评审回答的问题

1. **D1 的取舍**：`done`/`visits` 分支隔离后，join 合并规则（并集 + 圈次取 max）是否覆盖所有形状？有没有"同一节点合法地出现在两条分支里"的图？
2. **D2**：编译期禁止同组内两分支写同一变量 key，是否过严？如果业务真需要"两分支累加"，正确做法是 join 后算还是提供原子操作？
3. **D3/D4 的上限**：停止等待和暂停等待都要上限，但业务说"分支不设超时"。这个上限应该按**方法**配、按**设备**配，还是固定值？
4. **D5**：`nodeStateRecorder` 和 `ExecutionListener` 在 `WorkflowService` 里的实现，被多线程调用是否安全？DB 连接从哪来？
5. **R1**：`RunStateMachine.seq` 改成 `AtomicLong` 后，事件序号就不再连续（并发下会跳号）。有没有下游依赖"序号连续"？
6. **方案选择**：有没有比"抽 `executeNode` + 并行组"更小侵入的做法？（我评估过"每分支一个 GraphRunner"，因状态机是 run 级而不可行）
7. **R3**：1000 行控制流改写，怎么验证"纯重构无行为变化"？现有 1551 个纯逻辑单测不跑真实图，我打算用基准流程做端到端对比——够吗？
8. **D6**：线程池用全局固定池 + 信号量，还是每 run 一个？与"run 级并发上限"怎么配合？

## 8. 边界

- 实测基线：基准流程 run 1001810（71.9 s）/ 1001811（62.5 s），节点执行时间见 §1.1。
- 未核实项已在 §5 R4 标出，不做假设。
