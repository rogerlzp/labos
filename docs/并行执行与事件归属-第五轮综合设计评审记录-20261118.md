## 3. P0 评审意见

### R5-01：GuardedStart 的准入检查与 Run 写入尚未形成原子操作

**结论：FAIL（设计伪代码不具备并发准入原子性）。**

**位置**：④ §3.2、§3.3、§6。

**依据**：当前伪代码先调用 `gate.check(...)`，再进入 `inTransaction(...)`。两个并发请求可能都在事务外检查到“没有 active run”，随后分别创建 Run。即使将普通 SELECT 移入事务，如果没有锁定稳定的互斥对象或等价数据库约束，也不能仅凭事务包裹证明串行化。

**风险**：两个入口同时通过准入，产生重复 active Run；后续 scheduler 可能同时派发，破坏批次串行阶段的行为契约。

**建议**：

1. 选定数据库准入互斥点，优先考虑对稳定 workflow/admission 记录加行锁（例如 `SELECT ... FOR UPDATE`），或使用经过数据库与部署验证的等价机制。
2. 在同一事务中完成：获取准入锁、读取并判断状态、创建 Run 或更新 Resume 状态、写入待派发记录。
3. 唯一约束作为最终兜底，而不是用事务外预检代替。
4. 事务提交前不得启动异步 worker。
5. 若提交后通过唤醒 scheduler 派发，必须有持久化待派发记录、outbox 或可恢复扫描，覆盖“事务提交成功、进程在唤醒前崩溃”的窗口。

**建议流程**：

```text
事务内：
  获取 workflow/admission 互斥
  检查准入条件
  创建 Run / 更新 Resume 状态
  写入持久化待派发记录
提交事务

事务提交后：
  唤醒 scheduler
  scheduler 从持久化记录派发
```

**验收**：

- 两个独立请求同时创建同一 workflow 的 Run，只允许一个通过。
- 两个不同入口并发创建，仍只能有一个通过。
- 事务回滚后 worker 不得执行。
- 提交后、唤醒前进程崩溃，任务仍能恢复派发。
- 并发测试覆盖实际数据库隔离级别和生产使用的数据库类型。

### R5-02：唯一索引的约束范围与活跃状态集合不完整

**结论：FAIL（当前索引不能证明 workflow 准入，也可能漏掉待启动状态）。**

**位置**：④ §3.3、§6；② §4.2。

**依据**：文档提出的 batch 唯一索引只能保护同一个 batch 的 active attempt，不能替代 workflow 级互斥。当前活跃状态示例只列出 `queued/running/paused`，但核查清单中还出现 `pending/planned` 等状态。若这些状态代表已取得执行资格、等待派发或已进入调度生命周期，则它们是否属于互斥集合必须明确。

**风险**：

- 不同 batch 的 Run 可能绕过 workflow 级串行约束。
- 两个相同 batch 的创建可能在 pending/planned 窗口重复成功。
- `LABOS_WORKFLOW_CONCURRENT_RUN=allow` 与唯一索引发生语义冲突。

**建议**：

将两类约束分开设计：

| 约束 | 目的 |
|---|---|
| Workflow admission | 当前串行阶段控制 workflow 的 active 执行资格 |
| Batch active attempt | 同一个 batch 不产生多个 active attempt |

对所有 Run 状态定义是否占用准入资格，不能只给 SQL CASE 片段。对 `allow` 开关，建议让配置只能在经过显式迁移/约束策略后生效；不应静默绕过数据库唯一性保证。

**验收**：

- 覆盖 `pending → planned → queued → running → paused → terminal` 的并发重复提交。
- 覆盖同批、不同批、不同入口的并发创建。
- 明确每个状态是否占用 workflow admission 和 batch slot。
- 验证 `allow` 开关与索引的冲突行为，不允许配置与数据库约束产生相反语义。

### R5-03：事件水位必须在事件可能产生前确定；单 waiter 不代表事件归属可信

**结论：FAIL（当前 waiter 水位和弱匹配规则不足以防止串板）。**

**位置**：③ §2.2、§2.4、§2.5、§3.1；② §4.3。

**依据**：表设计使用 `base_event_id` 并要求只匹配其后的事件，但又要求事件先于 waiter 到达时不丢失。如果设备动作在 waiter 创建前已经产生事件，事后创建的水位可能将该事件排除。反过来，如果水位在动作完成后才读取，早到事件又可能被错误纳入或漏掉。

此外，“只有一个 WAITING waiter 时允许弱匹配”仍然不能证明事件来源。A 的迟到事件可能在 B 成为唯一 waiter 后到达。

**风险**：A 的物理动作完成事件推进 B 的流程，造成错误节点推进、物料串板、资源错误释放。

**建议**：

1. 在设备命令可能产生事件之前，先确定并持久化事件接收水位。
2. 持久化逻辑操作、waiter/事件关联，再下发命令。
3. 对支持设备侧 command/process/operation correlation ID 的设备，优先使用强关联。
4. 对不支持关联标识的设备，必须有经过协议验证的事件序号、水位、boot generation 和动作边界协议。
5. “当前只有一个 waiter”不得单独作为物理事件归属可信的充分条件。
6. 无法证明来源的事件进入 `UNATTRIBUTED` / `UNKNOWN`，不得推进任一 Run，不得据此释放物料或位置。
7. 同一节点重新等待时定义 waiter generation，避免旧 waiter 与新等待周期混淆。

**建议流程**：

```text
准备逻辑动作
  ↓
读取并持久化设备事件水位 / boot generation
  ↓
持久化 operation 与 waiter 关联
  ↓
下发设备命令
  ↓
接收事件并按强关联或经验证的弱关联规则匹配
  ↓
无法证明归属 → UNATTRIBUTED / UNKNOWN
```

**验收**：

- 事件先于 waiter 到达。
- A 的迟到事件在 B 开始等待后到达。
- 同设备两个 Run 等待同类事件。
- 同一 Run、同一节点重新等待，旧事件不能命中新 waiter。
- 事件归属不确定时不推进、不释放物料、不释放位置。
- 设备重启导致序号归零时，不与重启前事件冲突。

### R5-04：NOT_FOUND 在总体设计和表设计之间直接矛盾

**结论：FAIL（必须统一状态语义）。**

**位置**：② §4.4、§4.5；③ §1.4、§3.2、§5.1。

**依据**：② 的状态描述存在 `NOT_FOUND → 允许重发` 或“未收到 ACK 即可安全重发”的表达；③ 则规定 `NOT_FOUND → UNKNOWN`，并且只有 PENDING 可以安全首次发送。两者不能同时成立。

**风险**：设备已执行但账本/查询接口暂不可见时，系统重复发送相同物理动作。

**建议**：本轮采用更保守的③规则，统一状态语义：

| 状态 | 处理 |
|---|---|
| PENDING | 尚未发送，可首次发送 |
| DISPATCHED | 已尝试发送，等待 ACK；超时后查询，不盲目重发 |
| ACKED | 已受理，不重发，等待执行结果 |
| IN_PROGRESS | 不重发 |
| COMPLETED | 采纳完成结果 |
| FAILED | 按设备协议和业务策略处理 |
| NOT_FOUND | UNKNOWN；不自动重发 |
| UNKNOWN | 人工核实或按设备专用恢复协议处置 |

只有在设备协议经过验证，能够严格证明 NOT_FOUND 的可见性与语义，并且设备端支持 commandId 幂等去重时，才可以为特定设备定义例外。例外必须有设备型号/固件版本范围和 HIL 证据，不能成为全局默认。

**验收**：对命令已发送、设备已接收、物理动作已开始、动作已完成但账本未写入、设备重启、查询延迟等窗口进行断电/断网故障注入，证明不会产生重复物理动作。

### R5-05：ACK 后不能无限等待；必须监测执行进展

**结论：FAIL（时间模型缺少执行卡死检测）。**

**位置**：② §4.5、§5。

**依据**：心跳与 ACK 只能说明链路健康和命令被受理，不能证明物理动作仍在正常进展。设备可能持续发送心跳、已经 ACK，但电机/机械机构/内部流程已经卡死。

**风险**：Run 长时间停留在 ACKED/IN_PROGRESS；系统无法区分正常长任务、设备卡死和反馈丢失，可能长期占用设备、位置和物料资源。

**建议**：保留三层时间模型，但将执行层拆分为：

- **业务期限**：不同动作类型允许的合理完成窗口。
- **执行进展**：设备状态变化、进度计数、阶段事件或其他可信进展信号。
- **链路健康**：心跳、连接和 ACK 延迟。

超出业务期限不应自动判定物理失败，但必须触发告警和处置。长时间无进展应进入操作级 `STALLED` / `UNKNOWN` 处置，不需要新增 `run_status` 枚举。定义隔离、停止派发、人工确认和资源保持/释放规则。

心跳周期 1 秒、连续丢失 3 次的规则还应明确实际检测上限、网络抖动容忍、恢复策略和停止派发时限。

**验收**：

- 设备持续心跳但不再产生执行进展。
- ACK 正常但设备执行线程冻结。
- 长耗时但持续有进展的动作不会被统一短超时误杀。
- 业务期限超出后能告警、隔离并进入可审计处置。
- 未确认物理状态前不自动释放关键资源。

## 4. P1 评审意见

### R5-06：四字段身份模型正确，但传输 attempt 的权威语义需统一

**结论：需补充（模型方向支持，字段定义尚不闭合）。**

**位置**：③ §1.1、§1.2、§1.6、§4.2。

**依据**：四字段 `operation_key/generation/command_id/attempt_no` 有助于区分逻辑动作身份、重新执行代次、设备命令身份和传输尝试。但文档同时把 `logical_operation.attempt_no` 描述为传输次数权威、把 `command_ledger` 描述为每次发送/查询一行，又称 `command_ledger.attempt` 继承 `run_node.attempt`。这会混淆节点执行轮次与传输轮次。

**建议**：

| 字段 | 统一语义 |
|---|---|
| `operation_key` | 同一业务逻辑动作的稳定身份 |
| `generation` | 该逻辑动作被明确重新执行的代次 |
| `command_id` | 一次逻辑动作代次对应的设备命令身份 |
| `logical_operation.attempt_no` | 传输操作序号，需定义发送、查询是否都计入 |
| `run_node.attempt` | 流程节点执行轮次，不等同传输次数 |
| `command_ledger` | 传输/查询/响应的不可混淆明细时间线 |

如果查询也产生 ledger 明细，必须定义查询序号或 ledger event type，不能把查询误算成新的物理发送 attempt。

**验收**：完整模拟发送、ACK、查询、重连、设备重启、人工处置，能够从持久化记录还原唯一且完整的命令时间线；逻辑动作终态后不得出现未授权的新发送。

### R5-07：跨类锁顺序不能只用 ThreadLocal 类型栈保护

**结论：需补充（资源类型顺序支持，当前断言方案不足）。**

**位置**：⑤ §3.2、§4、§5。

**依据**：当前伪代码只比较 `ResourceType.rank`，未完整说明 push/pop、获取失败、异常退出、重入、线程切换和 ThreadLocal 清理。若锁跨线程释放或跨 step 持有，ThreadLocal 不能代表真实持有关系。只检查类型也无法检测同一类型资源 ID 逆序，例如先持有 POSITION 20 再申请 POSITION 10。

**建议**：

1. 定义完整 `LockOrderGuard`，至少记录资源类型、资源 ID、获取 token、获取线程/执行上下文和释放状态。
2. 以 `(ResourceType.rank, ResourceId)` 的字典序约束同时持有的锁。
3. 明确重入锁的处理规则。
4. 所有成功获取、失败回滚、异常退出和释放路径必须成对维护 guard 状态。
5. 对异步跨线程边界，不得假设 ThreadLocal 自动传递；要么禁止跨线程转移普通锁所有权，要么使用明确的 lease/token 机制。
6. 区分线程锁与跨 step 的持久化 reservation，后者不能伪装成线程持锁状态。

**验收**：

- DEVICE → POSITION → RAIL_ZONE 合法路径通过。
- RAIL_ZONE → DEVICE、POSITION → DEVICE 等反向路径被拒绝。
- 同类型 POSITION 资源逆序申请被拒绝。
- 获取失败、异常、重入、线程切换、释放后重新申请等场景无误报、漏报和 ThreadLocal 泄漏。
- 测试覆盖所有真实申请入口，而不是只测单个手写反向例子。

### R5-08：三类资源生命周期不同，必须分别建模

**结论：需补充（不能把三类锁都视为同一种锁）。**

**位置**：⑤ §3、§5、§7。

**依据**：设备锁、位置锁、轨道分区锁的生命周期可能不同。设备锁偏向执行互斥；位置占用可能表达物料仍处于某个物理点位的事实，可能跨 step 保留；轨道分区锁可能只是一次运动过程中的临时互斥。仅列出统一顺序不能说明等待、持有、释放的正确性。

**建议**：在文档中明确每种资源的：
- 语义：物理占用、设备执行互斥或临时通行互斥；
- 获取时机；
- 持有范围；
- 释放条件；
- 故障/UNKNOWN 时的保留策略；
- 是否允许跨 step、跨线程或跨 Run 保留。

继续采用逐步申请和失败回滚，不要求一次性原子申请所有资源。但必须证明在任何同时持有的资源集合中不存在逆序等待。

**验收**：覆盖两实验共享设备、共享点位、共享轨道分区，以及设备执行完成但物料仍在点位、轨道动作中断、资源部分申请失败等组合。

### R5-09：Resume 状态守卫与幂等规则不完整

**结论：需补充（当前 SQL 条件不足以定义恢复语义）。**

**位置**：④ §4.5、§7 R-11。

**依据**：示例 SQL 只允许 `paused/failed`，但风险说明又列出 `paused_fault`、`waiting_human`、`paused_unknown` 等可恢复/待处置状态。并且同一个 Run 重复 Resume 的幂等语义没有与 SQL 状态守卫完全对应。

**建议**：先建立 Resume 状态转移表，不要仅依赖一条 SQL 的 IN 列表。

至少区分：

- 普通 paused：满足恢复条件后可恢复。
- paused_fault：故障已清除且设备/物理状态确认后恢复。
- waiting_human：必须完成相应人工决策后恢复。
- paused_unknown：物理状态未确认前禁止直接恢复执行。
- manual_hold：解除 hold 后才能进入恢复判定。
- queued/running：重复 Resume 应返回既有结果或明确冲突，不得创建第二次执行。
- completed/cancelled：不得重新激活；若要重做，必须创建新的逻辑动作/Run。

恢复必须核对 tenant、workflow、run 归属，并对 UPDATE 影响行数为 0 的情况返回冲突，不能静默成功。

**验收**：逐一覆盖各状态的 Resume、重复 Resume、并发 Resume、跨 tenant/workflow 请求、设备 UNKNOWN 时 Resume，以及终态 Run 的恢复请求。

### R5-10：事件表字段与最终 DDL 必须跨文档统一

**结论：需补充（字段分散在总体设计和表设计，尚未形成唯一规范）。**

**位置**：② §3.2；③ §2、§7。

**依据**：总体设计提出 `command_id`、`device_event_seq`；表设计另外讨论 `attribution_state`、`device_boot_id` 等字段。最终字段、索引、兼容迁移和旧字段退役顺序没有统一到一个规范 DDL。

**建议**：形成唯一的事件表字段定义，至少逐项决定：

- `command_id`
- `device_event_seq`
- `device_boot_id` 或等价设备启动代次
- `attribution_state`
- `source_event_id`
- 事件发生时间与服务端接收时间
- 事件原始载荷/摘要与解析版本
- 归属证据和归属失败原因

唯一键应在设备身份、boot generation、sequence 的真实语义明确后再定，例如 tenant/device/boot/seq 的组合。不得在尚未证明设备序号跨重启行为前直接假设 sequence 全局单调。

旧 `device_event.run_id` 应先停止新写入并完成全仓读取、写入、API、SQL、历史数据和外部依赖核查，再决定 DROP；不能仅凭新的归属模型就立即删除。

**验收**：一份规范 DDL 同时被②和③引用；迁移可重复执行；旧数据可解释；设备重启和重复事件可去重；归属状态可审计。

## 5. 入口统一改造清单的实施顺序调整

**结论：当前七步顺序应调整。**

**位置**：④ §5、§6。

当前方案先新增 GuardedStart 并沿用现状事务边界，之后迁移入口，最后才把事务边界改成“预检+插入”。这会使中间提交看起来已经统一入口，但仍未解决并发准入竞态。

建议改成：

| 阶段 | 内容 | 阶段门 |
|---|---|---|
| 0 | 盘点所有创建、激活、恢复 Run 的路径 | 入口清单闭合，含定时任务、内部 API、脚本和测试工具 |
| 1 | 定义 workflow admission 锁、batch attempt 约束和活跃状态集合 | 数据库并发语义评审通过 |
| 2 | 实现事务内准入 + Run 创建/恢复 + 持久化待派发记录 | 原子性与故障窗口测试通过 |
| 3 | 接入 E-01、E-02、E-09 | 原 HTTP 契约和状态语义回归通过 |
| 4 | 接入 E-03、E-08 | 批次串行和重跑语义回归通过 |
| 5 | 接入 E-04 至 E-07、E-10 | 全入口无旁路 |
| 6 | 并行度 1 行为等价验收 | 全部 PASS 后才允许进入下一阶段 |

第一阶段不要顺便改变批次调度语义，不要把同步入口改为异步，也不要在统一准入尚未证明原子性前宣称“入口统一完成”。

## 6. 对跨类锁方案的专项裁决

本轮新增的跨类锁核查有明显进步：它把实际路径归纳为 DEVICE → POSITION → RAIL_ZONE，并指出问题是“顺序隐式、没有护栏”，而不是已证明存在死锁。对“不做一次性原子申请”的决定，本轮支持。

但目前能确认的范围应严格表述为：

> 已核查路径观察到 DEVICE → POSITION → RAIL_ZONE 的顺序；尚未证明全仓所有获取路径都遵循该顺序，也尚未证明 ThreadLocal 断言覆盖真实锁持有生命周期。

还需要补充以下核查：

1. `TurntableGuard`、`WaitingInteractionGuard`、`TransferTransaction` 等辅助路径是否隐式获取其他资源。
2. 非搬运路径是否可能先获取轨道再申请设备或位置。
3. zone ID 与 device resource ID 是否属于同一 ID 命名空间；若不是，比较顺序必须使用各自稳定的资源类型和资源 ID。
4. 位置锁是否表达物料物理占用；设备锁是否只表达设备执行互斥；轨道锁是否仅在运动窗口内有效。
5. 失败回滚和 `safeReleaseTarget` 是否覆盖所有异常路径，而非仅正常返回失败路径。

反向申请测试必须以真实获取入口构造，而不是只对 LockOrderGuard 的独立单元方法做测试。
