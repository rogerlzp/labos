## 3. 被测生产代码事实（供复审核对，均未改动）

**事务边界（`WorkflowRuntimeRepository`）**

- 写路径：`required(...)` → `TransactionTemplate`，`ISOLATION_READ_COMMITTED`。
- 读路径：`snapshotTx` → `TransactionTemplate`，`ISOLATION_REPEATABLE_READ` + `readOnly`。
- 每个 public 写方法各自成**一个**事务；不跨方法复用事务。
- 写方法起始 `lockRun(tenantId, runId)`（`SELECT ... FOR UPDATE`）；锁序约定 `Run → Token → Activation → Attempt`。
- `appendEvents` 契约：**单条** `UPDATE workflow_run SET commit_version=commit_version+1, event_seq=event_seq+N RETURNING ...` + 逐条 `INSERT runtime_event`，`event_seq` 由 `MIN..MAX` 连续覆盖（无空洞）。

**被 G4-B 直接测到的写原语**

- `createRun`（`run_request_dedup` 幂等锚点 + definition_snapshot + workflow_run + 起始 Token + `RUN_CREATED`；`CreatedRun(runId, replayed)`）。
- `startRun`。
- `advanceGraphToken` → `advanceGraphTokenInternal`（`SEQUENCE / SPLIT / JOIN / END`；`SPLIT` 插 `split_activation(OPEN)` + 每分支 `branch_activation(ACTIVE)` + 后继 Token；`JOIN` 汇聚 `arrived_branch_count+1`，达 `expected_branch_count` 时 release join + close split + 建后继 Token；`END` 经 `maybeCompleteGraphRun` 终结 Run）。
- `advanceGraphTokenWithVariables`（`b54e0fc6` 引入的**条件网关原子路径**：同一 Run 锁事务内完成「读变量快照 → 求值 → 推进 Token」）。
- `advanceCompletedGraphActivation`（SUCCEEDED Activation + CONSUMED Token 的路由，含 REPLAYED）。
- `completeAttempt`（Attempt→SUCCEEDED / `branch_output` / `flow_variable` / Activation→SUCCEEDED / Token→CONSUMED / `EXECUTION_RIGHT_RELEASED` / `ATTEMPT_SUCCEEDED`；并行分支写同一 `flow_variable` key 时抛 `InvalidTransitionException`）。
- `reserveCapacity`（`scheduler_capacity(reserved_count)` + Token `READY→RESERVED` + `node_activation(RESERVED)` + `node_attempt(CREATED, side_effect_class)` + `dispatch_reservation(HELD)` + `DISPATCH_RESERVED`）。
- `dispatchAttempt` / `beginOutboxSend` / `markOutboxDelivered` / `acceptAttempt` / `startAttempt`。
- `createCommand`（DEVICE_COMMAND Outbox）/ `markCommandSendStarted`（写 `SIDE_EFFECT_STARTED` fact，key=`command:<commandId>`）/ `receiveInbox` / `applyCommandEvent`（`command_ledger` + `inbox_receipt` + `worker_execution_fact`(写 `SIDE_EFFECT_COMPLETED`，同 key) + `runtime_event`）。
- `findReadyGraphTokens` / `findInterruptedAttempts(limit)`（**全局、无 tenant 过滤**：`attempt_state IN ('CREATED','DISPATCHED','ACCEPTED','STARTED')`）/ `recoverInterruptedAttempt`。

**`GraphCoordinator.advance(...)` 的异常处理契约（关键）**

- 仅捕获 `IllegalStateException | IllegalArgumentException | InvalidTransitionException` 时调 `failGraphRun`；
- 其它 `RuntimeException`（含注入的 `InjectedCommitAbort` / `InjectedLostResult`）**不**终结 Run；
- 内部是**多事务循环**（每一步一次独立事务），这也是 T15/T16 用 `armAtWrite(mode, 2)` 在第 2 个事务上注入的原因。

## 4. 故障注入模型（`FaultInjectingTransactionManager`）

- 装饰 Spring `PlatformTransactionManager.commit(TransactionStatus)`；两种故障模式：
  - `ABORT_BEFORE_COMMIT`：先 `delegate.rollback(status)`，再抛 `InjectedCommitAbort`（对应「提交前中断/崩溃」→ 不允许任何持久化）。
  - `LOST_RESULT_AFTER_COMMIT`：先 `delegate.commit(status)`，再抛 `InjectedLostResult`（对应「提交成功但调用方未收到结果」→ 必须已持久化且自洽，重放安全）。
- **只读事务不注入、也不消耗序号**：`TransactionSynchronizationManager.isCurrentTransactionReadOnly()` 为真时直接透传 `commit`；避免 `snapshotTx` 误吃注入。
- 触发接口：`armOneShot(mode)`（下一次**写**提交）与 `armAtWrite(mode, ordinal)`（第 N 次**写**提交），`disarm()` 清空。
- 实现状态：单个不可变 `Armed(mode, writeOrdinal)` 值持有在**一个** `AtomicReference` 中，`commit` 用一次 `updateAndGet` 原子消费序号，仅归零时触发。
- **建模边界（诚实声明）**：该注入是在**所有 SQL 均成功执行之后**、于 Java 层在事务边界主动回滚/提交。它证明的是「单个 Repository 方法没有把写拆成多事务」以及「提交边界之后调用方丢结果的幂等性」，**不等价于 PostgreSQL 服务端事务中途失败**（如 `pg_terminate_backend` 断连、死锁、中途约束违背后的连接恢复）。详见第 9/10 节。

## 9. 请复审的问题清单（重点）

1. **覆盖是否已足够**：T11–T19 是否真正闭合了第一轮指出的 P1-2 缺口？是否仍有高风险事务（如 `advanceCompletedGraphActivation` 的更多分支、`failGraphRun`/`maybeCompleteGraphRun` 的崩溃路径、Outbox 派发/重投路径）未被覆盖？

3. **清理 helper 的正确性**：`abandonIfInterrupted` 以「是否存在 `SIDE_EFFECT_COMPLETED`」作为分派依据（有 → `completeAttempt`，无 → `recoverInterruptedAttempt`）是否稳健？是否存在边界（如 `SIDE_EFFECT_STARTED` 无对应 COMPLETED、或存在模糊命令）会误走 `MANUAL_REQUIRED` 分支并制造另一种污染？是否应改为「优先 `completeAttempt`，失败再 `recoverInterruptedAttempt`」？
4. **故障注入层的建模充分性**：Java 层 `commit` 装饰是否足以代表「数据库事务崩溃」？是否必须补 1–2 例**真实 PG 后端中断**（`pg_terminate_backend` / 死锁 / 中途约束违反）才算闭合？两者证明的命题差异请给出判断。
5. **装饰器的残余并发竞态**：`commit` 中先 `armed.get()` 读 `current`、再 `updateAndGet` 消费序号；当前**单线程测试**安全，但在并发下两个线程可能同时观察到序号归零而**重复触发**同一故障。作为测试工具是否需要修（改成单次 `getAndSet(null)` 式判定）？是否应补并发用例？
6. **P2-1 归因是否正确**：`WorkflowRuntimeRepositoryTest#interruptedAttemptAfterSendStartedRequiresManualReconciliation` 的 `expected:<1> but was:<3>` 被判为**该测试类自身非幂等**（每次运行遗留 1 条 `restart-unknown-*` 的 `SENDING/UNKNOWN` outbox）+ 共享库多次运行累加，**与 G4-B 无关**。请独立复核此归因。
7. **残留口径是否还有漏网**：当前只保证不遗留「处于恢复扫描集的 Attempt」。T19 仍会留下 1 条 `outbox_state='SENDING'` 且 `command_state='SUCCEEDED'` 的 `DEVICE_COMMAND` outbox 行（`SUCCEEDED` 不在 `leftUncertain` 的模糊集合内，故不影响既有断言）。是否需要一并清理？
8. **是否存在「空测/弱测」**：请核对 T9/T10/T13 等「内层异常回滚」用例是否确实在**写入之后**才抛异常（而非参数前置校验），以及各断言是否可能因测试自身 setup 产生的行而被误判（例如 `GRAPH_NODE_ADVANCED` 基线）。
