## 2. 数据模型（本轮新增/改动的表）

### 2.1 统一「点位内容」模型（真源）

`position_state`（每个点位一行）新增两列，是「点位上放着什么」的**唯一真源**：

| 列 | 含义 |
|---|---|
| `content_kind` | `plate` / `consumable` / `reagent` / NULL（空） |
| `content_id` | 内容 id：板=plate.id、耗材=consumable_lot.id、试剂=reagent_lot.id |
| `plate_id`（已有） | 板的 barcode，保留兼容 |

一个点位同一时刻只放一件物理物。`GET /api/positions` 按 content_kind/content_id 关联出
`contentCode/contentName`。

### 2.2 点位配置层 `device_point`（新增 4 列，幂等迁移已执行）

| 列 | 含义 |
|---|---|
| `grid_row` / `grid_col` | 排/列（培养箱的层、堆栈的层、同层第几列） |
| `max_height_mm` | 该点位最高板高（mm） |
| `plate_types` | 能放板型集合（`varchar[]`，空=不限制） |

### 2.3 板 `plate`（新增 1 列）

`height_mm` numeric —— 放板时与点位 `max_height_mm` 校验。

### 2.4 耗材/试剂（复用已有表，无结构改动）

`consumable`(目录) + `consumable_lot`(批次: quantity/remaining/location_id/device_id)；
`reagent` + `reagent_lot`(volume/remaining/location_id/device_id)。批次挂到点位时**同时**写
`position_state.content_kind/content_id`（写穿），删/挪批次时同步清旧点位内容。

## 6. 关键设计决策与边界（接手务必先读）

1. **一个点位一个物理内容**：板 / 耗材 / 试剂三选一；后挂覆盖先挂（`upsertPositionContent` 里
   `plate_id=NULL` 且 content 整体覆盖）。
2. **耗材/试剂不挂板子**：它们和板子平级，都是「点位内容」；「试剂进板孔」是 plate_well 深层模型，未做。
3. **装载口 vs 内部格**：培养箱/堆栈 = 一个装载口（`{设备}-IN`，both+可达，机械臂只在这放/取）+
   内部格（internal+不可达，设备内部机构搬）。机械臂（TRANSFER）无点位。
4. **板型/高度校验是 OPT-IN**：`checkPlateFits` 只在点位显式配了 `plate_types`/`max_height_mm` 时拦；
   校验异常只告警不阻断主链。集成在 `noteTransferMove` 放板前，不匹配 → 保持 REPORTED 转人工。

### 🔴 最重要的未闭合边界（下一轮核心）

**「机械臂放装载口 → 设备内部机构搬进指定内部格」这一步未建模**，因此：
- 内部格的 `plate_types`/`max_height_mm` 约束在当前执行链里**不会真正触发**（机械臂只到装载口，
  装载口通常不设板型限制）。
- 要做的是「设备内部搬运动作」：放板到装载口后，由设备内部机构搬入某内部格（写该格的
  `position_state`），搬入时才做该格的板型/高度校验。这是让校验真正生效 + 正确表达「放的位置」的前提。

## 9. 常用 SQL（只读复现）

```sql
-- 13 台设备点位数
SELECT d.code, count(r.id) AS points,
       count(*) FILTER (WHERE dp.point_role='internal') AS internal格,
       count(*) FILTER (WHERE dp.note LIKE '%装载口%') AS 装载口
FROM resource_node d
LEFT JOIN resource_node r ON r.parent_id=d.id AND r.tenant_id=d.tenant_id

FROM resource_node r LEFT JOIN position_state ps ON ps.resource_id=r.id
WHERE r.tenant_id=1 AND r.parent_id=200229 ORDER BY r.code LIMIT 5;
```

## 10. 接手后实施记录（2026-11-13 续，本文件 §6 🔴 已部分闭合）

> 承接用户指出的**生产级安全场景**：机械臂收到指令后，若 target 位置在指令前未被原子预留，
> 搬运期间其它设备往同一位置放板就会相撞。这不是 P-08 的 `CONFIRMED` 状态机语义问题，
> 而是**位置锁**问题；上一轮把它问成「确认时机」是问偏了。

### 10.1 核实到的真实缺口

| 证据 | 结论 |
|---|---|
| `DriverStepExecutor.java` 的 `plan.acquireAll(srcRes, null, dstRes, null, null, null, factory)` | 源/目标位置参数全为 null |
| `TransferPlan.acquirePosition` 首行 `if (positionId == null) return;` | 位置预留**从未执行** |
| `driver.execute` 在前、`noteTransferMove` 的 `firstAvailablePosition` 在后 | 选位是事后的，物理动作已结束 |
| `putPlateOnPosition` 的 `WHERE plate_id IS NULL` | 只防 DB 双写，防不住物理相撞 |
| `device_access` 全库仅 2 行（读板/离心） | 培养箱/堆栈连设备级锁也没有 |

好消息：`reservePosition` 本身是原子的（`INSERT … ON CONFLICT DO UPDATE … WHERE`，TTL + 归属），
`TransferPlan.acquirePosition` 也已有死锁检测——机制齐全，只是没被调用。

### 10.2 已实施 · 阶段 0「先预留、后动作、再登记」

- `PositionLock.reserveTargetPosition(deviceRes, runId, timeoutMs)`：动作前选一个可达装载口并**原子预留**；
  抢不到时按用户口径「等待 + `log.warn` 提醒」，**60s 超时才拒绝**（`StepFailure EC-RESOURCE-BUSY` 转人工）。
- `DriverStepExecutor.executeWithPlan`：在 `acquireAll` 之前预留，把位置 id 传给
  `autoConfirmTransfer`；成功/失败/异常/开关关闭四个分支都会正确释放或消费预留。
- `PositionLock.noteTransferMove` 新增重载，接收 `reservedDstPos`，**不再事后重选位**。
- `putPlateOnPosition` 写占用时自动清 `reserved_by_run/reserved_until` ⇒
  「预留 → 占用」无窗口；装载口有板期间别的 run 的 `firstAvailablePosition` 会排除它。
- `CONFIRMED` 时机**保持现状不改**（机械臂放装载口 + 回包 OK 即确认），
  设备内部移动是另一条位置变更，各自留 audit/证据；P-08 与恢复门禁零改动。

## 13. 第六轮：设备锁泄漏 + 续跑守卫误判修复（闭合 §11.3 遗留，2026-11-13）

承接「继续做吧」，攻 §11.3 明确遗留的「点击继续被设备锁 231 卡住」。**根因是两层，
只修第一层会把第二层暴露出来**。

### 13.1 根因

**① 设备锁泄漏（`DriverStepExecutor.execute`）**

`executeWithPlan` 在**下发前**失败时抛 `StepFailure`（`EC-RESOURCE-BUSY` 装载口等待超时、
`EC-99-0002` 预留 DB 错误），而 `execute()` 只 `catch (RuntimeException)`，**没有对应
`StepFailure` 的 catch** ⇒ 直接冒泡，**`sink.onStepDone` 从未被调用** ⇒
`DeviceLock` 的两层锁都没释放：

- DB：`device_state.current_run_id` 仍指向该 run；
- JVM：`DeviceLock` 的静态 `ReentrantLock`（按 tenant/resource/run 分条带）仍被旧执行线程持有。

现场表现因此很迷惑：`device_state` 可能显示 `idle/在线`（DB 行被别的路径清了 / 查到的是
`device_instance.id` 而非 `resource_node.id`），但续跑新线程拿不到本地锁 ⇒ 空等 60s
⇒「设备被占用超过 60 秒：231」。

**② 续跑守卫误判（修完 ① 才暴露）**

如果在失败时补写 `run_command`，`RunMapper.countResumeGuardHits` 会看到未完成节点下有
命令行 ⇒ 判「设备已动」⇒ `resumeAsync` 抛「禁止删除重建」⇒ 异常在
`PauseCoordinator.resumeWorkflowRun` 的事务里被 catch，但 Spring 事务已被标记
rollback-only ⇒ 接口返回
`Transaction rolled back because it has been marked as rollback-only`，run 永远停在 paused。
（实测 run 1001411 就是这个状态；`pause_request` 里 0 行，因为事务整体回滚了。）

### 13.2 改动（3 个文件，均在 `labos-kernel/src/main/java/com/labos/kernel/`）

| 文件 | 改动 |
|---|---|
| `engine/StepSink.java` | 新增 `default onStepAborted(...)`，默认退化为 `onStepDone`，既有实现零改动 |
| `workflow/WorkflowService.java`（`PersistingStepSink`） | override：只做 `FINALIZING` 阶段 + `markDeviceIdle` + `DeviceLock.release` + 清 `resourceByStep/sentAtByStep`，**不写 `run_command` / `command_ledger`** |
| `driver/DriverStepExecutor.java` | `catch (StepFailure f)` → `sink.onStepAborted(...)` 后再 rethrow；恢复决策（MANUAL）保持不变 |

关键语义：**「下发前失败」与「设备已动作后失败」必须分开记**。前者没有物理证据，写命令行
只会让续跑守卫自己挡住自己；后者（`RuntimeException` / 设备回包失败）仍走原路径，保留证据。
