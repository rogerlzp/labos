# 为什么不用银行家算法

> 用一个具体例子讲清楚，不用术语。

---

## 一、银行家算法要求什么

**一句话**：**每个流程在开始跑之前，必须先声明"我最多需要多少资源"。**

就像你去银行借钱，**必须先说清楚"我最多要借多少"**，银行才能判断
"借给你之后，其他客户还能不能取到钱"。这就是名字的由来。

**教科书例子**：

```
系统有 3 台打印机
进程 A 声明：我最多要 2 台
进程 B 声明：我最多要 1 台

现在 A 要 1 台、B 要 1 台：
  分配后剩 1 台
  检查：A 还差 1 台（有）→ A 能完成 → 释放 2 台
       B 还差 0 台（够）→ B 能完成
  → 安全，可以分配 ✅
```

**如果 A 要 2 台、B 要 1 台**：

```
  分配后剩 0 台
  检查：A 还差 0 台 → 能完成；B 还差 0 台 → 能完成
  → 也安全
```

**如果 A 要 2 台、B 要 2 台**（总共 3 台）：

```
  A 拿 2 台，剩 1 台
  B 要 2 台，但只剩 1 台 → B 永远等不到
  → 不安全，**拒绝这次分配**
```

**关键**：银行能算，是因为**A 和 B 都提前说了"最多要几台"**。

## 二、我们的场景：说不出来

### 一个真实的流程

```
开始
  ↓
判定：板上有样本吗？
  ├─ 有 → 孵箱（30 分钟）→ 离心机 → 读板机 → 结束
  └─ 没有 → 直接出板 → 结束
```

**现在问：这个流程"最多需要几台设备"？**

| 分支 | 需要 |
|---|---|
| 有样本 | 孵箱 + 离心机 + 读板机 = **3 台** |
| 没样本 | **0 台**（只是搬出去） |

**执行到判定节点之前，不知道走哪条。**

**所以声明不出来。**

### 如果硬要声明（按最坏情况）

**声明"我最多要 3 台"**。看起来可行？**看后果**：

```
总共 4 台设备（孵箱、离心机、读板机、备用孵箱）

流程 A 声明：最多 3 台
流程 B 声明：最多 3 台

B 要启动：
  已给 A 3 台，剩 1 台
  B 要 3 台，只剩 1 台 → **拒绝**
```

**结果：B 永远启动不了，即使 A 实际上只用了 1 台。**

### 更糟的情况：分支多

**一个流程有 5 个判定节点**：

```
判定1 → 分支A/B
判定2 → 分支C/D
...
最坏情况 = 所有分支用到的设备的**并集**
```

**并集可能等于"整个岛的所有设备"。**

**然后每个流程都声明"我要整个岛"** → **任何两个流程都不能并行**。

**这就是"按最坏情况声明"的代价：并发度归零。**

## 三、那"分支确定后再声明"行不行

**想法**：等执行到判定节点，知道分支了，再声明。

**问题有三个**：

### 问题 1：声明之前已经占了资源

```
流程 A：开始 → 抢了源位置 → 搬板 → 到判定节点
                                  ↑ 此时才声明"我要3台"
```

**银行家算法的前提是"分配前声明"**，已经占着的位置怎么算？

**解法**：把"已占 + 未来需求"合起来算。**可以做，但复杂度上去了。**

### 问题 2：分支后面还有分支

```
判定1 → 分支A → 判定2 → 分支C/D
```

**每次判定都要重算**，而且**越往后，剩余的不确定性越小，但已经占的资源越多**。

**重算的意义越来越小**。

### 问题 3：声明了也可能变

**流程跑到一半，人工改了参数**（比如把"孵育 30 分钟"改成"60 分钟"），
**资源需求变了，声明要重做**。

**银行家算法假设"声明不变"**，这个假设在我们的场景不成立。

---

## 四、等待图怎么绕过这个问题

**等待图不问"你最多要多少"，只问"你现在要什么、谁占着"**。

```
流程 A 现在要孵箱
  → 孵箱被 B 占着
  → 记一条边 A → B（A 在等 B）
  → 检查：从 A 顺着边走，能不能回到 A？
      - 不能 → 等待
      - 能 → **拒绝**（这就是环，会死锁）
```

**它不预测未来，只处理当下的申请。**

### 三个流程走环的例子

```
流程1 占 A，要 B
流程2 占 B，要 C
流程3 占 C，要 A

① 流程1 要 B（被流程2 占）→ 加边 1→2 → 无环 → 等待
② 流程2 要 C（被流程3 占）→ 加边 2→3 → 无环 → 等待
③ 流程3 要 A（被流程1 占）→ 加边 3→1
   DFS：3→1→2→3 ← **成环**
   → **拒绝流程3**，它必须退出去重试

结果：流程1、2 继续等，流程3 重试
     流程1 拿到 B 完成后释放 A → 流程3 才能要 A
     **不死锁** ✅
```

**注意**：等待图**不需要知道**流程3 后面还要什么。
它只知道"流程3 现在要 A，A 被流程1 占，加了这条边会成环"。

## 五、两者的本质区别

| | 银行家算法 | 等待图 |
|---|---|---|
| **策略** | **避免**（不让进入不安全状态） | **检测**（成环才拒） |
| **需要预知** | ✅ 必须（max claim） | ❌ 不需要 |
| **拒绝时机** | 分配**前** | 成环**时** |
| **保守程度** | **高**（按最坏情况） | **中**（只拒成环） |
| **能否保证不死锁** | ✅ | ✅ |
| **适用场景** | 需求**可预知**（内存分配、银行放贷） | 需求**动态**（流程分支、数据库事务） |

**关键**：**两者都能保证不死锁**，但：

- 银行家用"**保守**"换"**确定性**"
- 等待图用"**动态检测**"换"**宽松**"

**我们的场景需求不可预知，所以只能用后者。**

## 六、工业界的实际情况

**银行家算法在实际系统里几乎不用**：

| 系统 | 用什么 | 为什么不用银行家 |
|---|---|---|
| **PostgreSQL** | 死锁检测（等待图） | 事务的资源需求不可预知 |
| **MySQL InnoDB** | 死锁检测（等待图） | 同上 |
| **Linux 内核** | 锁顺序 + 检测 | 同上 |
| **JVM** | 锁顺序 | 同上 |
| **Kubernetes 调度** | 优先级 + 抢占 | 同上 |

**银行家算法主要在教科书里**——因为它的前提太强（预知最大需求）。

**只有"资源需求确定"的场景才用**：

- 操作系统内存分配（进程启动时知道要多少）
- 实时系统的周期性任务（周期和资源需求固定）

**流程编排不是这类场景。**

## 七、如果一定要用银行家，需要做什么

**让你看到代价**：

| 步骤 | 做什么 | 代价 |
|---|---|---|
| 1 | **静态分析流程**：遍历所有分支，算资源并集 | 流程越复杂越慢；有环的话要特殊处理 |
| 2 | **声明并集**（max claim） | 每个流程声明"我可能要整个岛" |
| 3 | **接受并发度下降** | 2 个流程可能都启动不了 |
| 4 | 分支确定后**重算** | 复杂度；且已占资源要纳入 |
| 5 | 人工改参数时**重新声明** | 要重新走一遍安全检测 |

**第 3 步是致命的**：

```
一个流程声明"我要 3 台设备"，但它 90% 的情况只用 1 台
→ 系统按 3 台给它留位置
→ 别的流程只能等
→ **实际并发 1，理论并发 3**
```

**为了"理论上更严谨"，把并发降到 1 —— 这个交换不划算。**

---

## 八、一句话回答

> **银行家算法要求"执行前声明最多要多少资源"，
> 但流程有分支，声明不出来。
> 硬要声明就得按最坏情况（所有分支的并集），
> 那每个流程都要"整个岛"，并发度归零。**

**不是"银行家算法不好"，是"它的前提在本场景不成立"。**

**等待图不需要这个前提** —— 它只看当下谁在等谁，成环就拒，
同样能保证不死锁，而且不牺牲并发。

---

## 九、如果你还是不放心，可以这样做

**折中方案：混合**。

```
① 流程开始前：用银行家做一次"粗筛"
   - 只算"主链"的资源（不算分支），声明一个保守但不过分的 max claim
   - 如果连主链都排不下 → 拒绝启动（提前告诉用户"资源不够"）

② 执行过程中：用等待图做"细管"
   - 每个实际申请都要过环检测
   - 成环就拒
```

**好处**：
- 启动前有"能不能跑"的判断（银行家的价值）
- 执行中有"不死锁"的保证（等待图的价值）

**代价**：
- 两套机制都要实现
- "主链"的定义要有规则（比如：取最长的分支）

**这个方案可以做，但复杂度是纯等待图的 2 倍。**
**建议先做纯等待图，真遇到"启动前就该拒绝"的场景再补。**
