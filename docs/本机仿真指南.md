# 本机仿真指南

> **每台设备一个模拟器进程**，中控像对接真实设备一样对接它们。
> 不是"一个 mock 应付所有设备"，而是"N 个独立设备在同时运行"。

---

## 一、为什么要一台设备一个模拟器

| 一个 mock 管所有设备 | 每台设备一个模拟器 |
|---|---|
| 所有设备响应速度一样 | **可以单独把某台设成慢/故障** |
| 测不出并发 | 多台真并发（各自 socket 互不阻塞） |
| 杀掉 mock 全线停 | **可以单独杀一台，验证设备离线** |
| 设备 A 的命令可能发到 B 的端点 | 端点隔离，路由错了立刻暴露 |

**最后一条最重要**：如果所有设备共用一个端点，中控把 A 的命令发到 B 也不会报错。
每台设备一个端点后，**路由错了直接连不上**。

## 二、跨平台方案

**用 Java 写**，一个 class 在三个平台都能跑：

```bash
# macOS / Linux
java -cp out com.labos.kernel.sim.DeviceSimulator --port 19501 --device 171 --code ID1183

# Windows
java -cp out com.labos.kernel.sim.DeviceSimulator --port 19501 --device 171 --code ID1183
```

**不需要分别为 mac/windows 打包**。JVM 解决跨平台问题。

**如果要做成"双击运行"**：

```bash
# 打成可执行 jar
jar --create --file device-sim.jar --main-class com.labos.kernel.sim.DeviceSimulator -C out .

# 然后
java -jar device-sim.jar --port 19501 --device 171
```

Windows 上再套一个 `.bat`：

```bat
@echo off
java -jar device-sim.jar --port 19501 --device 171 --code ID1183
pause
```

## 三、快速开始

### 3.1 一键起全岛

```bash
cd labos-kernel

export LABOS_DB_HOST=<数据库地址>
export LABOS_DB_NAME=<库名>
export LABOS_DB_USER=<用户>
export LABOS_DB_PASS=<密码>

./scripts/sim-up.sh LAB-DEMO-02 150
```

**`150` 是每台设备的模拟耗时（毫秒）**。设成 3000 可以模拟慢设备。

**输出**：

```
=== 岛 LAB-DEMO-02：查设备 ===
=== 为每台设备分配端口并登记 driver ===
  ID0000           设备实例=206    端口=19500  能力=ALIQUOT
  ID1183           设备实例=171    端口=19501  能力=INCUBATE
  ID1731           设备实例=214    端口=19502  能力=TRANSFER
  ID1775           设备实例=210    端口=19504  能力=INCUBATE
  ...

=== 已启动 7 个模拟器 ===
```

**脚本做了四件事**：

1. 查岛上的设备（`resource_node` + `device_instance`）
2. 每台分配一个端口（19500 起）
3. **在 `driver` 表建一条记录**（`tcp://127.0.0.1:<port>`）
4. **把 `device_instance.driver_id` 指过去**
5. 起模拟器进程

### 3.2 启动中控

```bash
LABOS_DB_HOST=... LABOS_DB_NAME=... LABOS_DB_USER=... LABOS_DB_PASS=... \
java -cp "out:lib/postgresql-42.7.3.jar" com.labos.kernel.api.ApiServer 18080
```

**启动日志会列出注册的驱动**：

```
[驱动] DRV-SIM-ID1183 → tcp://127.0.0.1:19501（1 台设备）
[驱动] DRV-SIM-ID1775 → tcp://127.0.0.1:19504（1 台设备）
```

### 3.3 验证

```bash
# 单命令探针
curl -X POST "http://localhost:18080/api/shadow/probe?resourceId=200171&method=Home"

# 跑一条流程
curl -X POST "http://localhost:18080/api/workflows/239/run?islandId=504821"
```

**看每个模拟器收到了什么**：

```bash
tail -f /tmp/sim-ID1183.log
# [ID1183] #1 Deposit1（模拟耗时 150ms）
```

### 3.4 停止

```bash
./scripts/sim-down.sh
```

会把模拟器全停，并把设备从模拟驱动上摘下来。

## 四、单台模拟器的参数

```bash
java -cp out com.labos.kernel.sim.DeviceSimulator \
     --port 19501 \
     --device 171 \
     --code ID1183 \
     --cap INCUBATE \
     --delay 150
```

| 参数 | 说明 |
|---|---|
| `--port` | 监听端口（**必填**） |
| `--device` | 设备实例 id，回包里的 `equipment_id` |
| `--code` | 设备编号，只用于日志 |
| `--cap` | 能力，只用于日志 |
| `--delay` | 每个动作耗时（毫秒），默认 0 |
| `--long` | **长任务模式**：先回运行中，等一半时间再回完成 |
| `--fail N` | 每 N 条**动作类**命令失败一次（0=不失败；查询类不计） |
| `--fail-code` | 失败时返回的错误码，默认 `EC-05-0001`；型号库登记过的码会带中文含义与处置建议 |
| `--fail-method` | 只在指定方法上失败（如 `Seal`） |
| `--fail-from N` | 第 N 条动作类命令起才开始失败（前 N-1 条正常，测"跑一半坏了"） |
| `--model` | 按**具体型号**模拟（`--list-models` 看有哪些），会启用真实指令名、错误码与时序约束 |
| `--offline` | **直接不监听端口**，模拟设备没上电 |

## 五、用模拟器验证什么

### 5.1 设备慢（`--delay`）

```bash
# 让 ID1183 每步花 5 秒
java -cp out com.labos.kernel.sim.DeviceSimulator \
     --port 19501 --device 171 --code ID1183 --delay 5000
```

**验证**：中控的超时设置够不够、流程会不会因此卡住。

### 5.2 长任务（`--long`）

```bash
java -cp out com.labos.kernel.sim.DeviceSimulator \
     --port 19501 --device 171 --code ID1183 --delay 4000 --long
```

**行为**：先回 `method_status=1`（运行中），2 秒后回 `2`（完成）。

**验证**：驱动会不会把"运行中"误判成失败。**这是上真机前必须过的一关**。

### 5.3 间歇故障（`--fail`）

```bash
# 每 3 条动作类命令失败一次
java -cp out com.labos.kernel.sim.DeviceSimulator \
     --port 19501 --device 171 --code ID1183 --fail 3

# 按真机的错误码失败：S100 无纸（中控会翻成 EC-08-300C → 转人工）
java -cp out com.labos.kernel.sim.DeviceSimulator \
     --port 19501 --device 171 --code ID1183 --model s100 \
     --fail 1 --fail-method Seal --fail-code 0x8000000C --fail-from 6
```

**验证**：状态机的重试逻辑、`recovery_policy` 是否按预期生效。

> **`--fail N` 的 N 只算动作类命令**（`Transfer`/`Seal`/`Start`…），
> 查询类（`GetStatus`/`GetPoints`）不计数。原因是中控会频繁插查询，
> 按"收到的第 N 条"算会让故障落在查询上被跳过，`--fail 3` 变得不可预测。

### 5.4 设备离线（`--offline` 或直接杀掉）

```bash
# 方式一：启动时就是离线的
java ... --offline

# 方式二：运行中杀掉
pkill -f "code ID1183"
```

**验证**：`EC-05-1006`（TCP 通讯失败）是否正确报出、告警是否触发。

### 5.5 路由正确性（最关键）

```bash
# 跑一条涉及两台设备的流程
curl -X POST ".../api/workflows/239/run?islandId=..."

# 看两台设备的模拟器各自收到什么
tail -3 /tmp/sim-ID1183.log
tail -3 /tmp/sim-ID1775.log
```

**通过标准**：

```
sim-ID1183.log: [ID1183] #1 Deposit1
sim-ID1775.log: [ID1775] #1 Withdraw1
```

**各收到一条，且都是自己的命令** —— 说明路由正确。

如果发现 `ID1183` 的日志里出现了本该发给 `ID1775` 的命令，说明**设备归属配错了**。

## 六、常见问题

### Q: 启动报"名下设备都没有声明能力"

```
[驱动] DRV-SIM-ID1731-2 跳过：名下设备都没有声明能力
```

**原因**：这台设备在 `resource_capability` 里没有记录。

**修**：

```sql
INSERT INTO resource_capability (tenant_id, resource_id, capability_id)
SELECT 1, r.id, c.id
FROM resource_node r, capability c
WHERE r.tenant_id = 1 AND r.code = 'ID1731-2' AND c.code = 'TRANSFER'
ON CONFLICT DO NOTHING;
```

### Q: 执行报 `EC-06-0001`（设备没注册到驱动）

**查**：

```sql
SELECT r.code, d.code AS driver, d.endpoint
FROM device_instance di
JOIN resource_node r ON r.id = di.resource_id
LEFT JOIN driver d ON d.id = di.driver_id
WHERE r.code = '<设备编号>';
```

**`driver` 为空** → 跑一次 `sim-up.sh` 重新登记。

### Q: 模拟器起来了但中控连不上

**查端口**：

```bash
lsof -i :19501
```

**没有输出** → 模拟器没起来，看 `/tmp/sim-<编号>.log`。

**有输出但不是你的进程** → 端口被占了，换一个（改 `BASE_PORT`）。

### Q: 想同时在两个岛仿真

```bash
# 岛 A 用 19500 段
./scripts/sim-up.sh LAB-DEMO-02 150

# 岛 B 需要改 BASE_PORT，或者手工起
```

**当前脚本一次只处理一个岛**。多岛时改 `BASE_PORT` 或者手工起第二组。

## 七、和真实环境的差异

**模拟器能验证的**：

- 路由（命令发给对的设备）
- 超时（`--delay`）
- 长任务（`--long`）
- 重试（`--fail`）
- 离线处理（`--offline`）

**验证不了的**：

- 真实耗时（模拟器的 delay 是固定的，真设备有波动）
- 物理约束（会不会撞、夹不夹得住）
- 厂商 DLL 的边界情况
- 并发时的机械干扰

**所以**：模拟器通过 = **逻辑和协议对了**，不等于能上生产。

## 八、设计要点（给改代码的人看）

### 8.1 为什么模拟器是独立进程而不是线程

- **端口隔离**：每台设备一个端口，路由错了立刻暴露
- **可以单独杀**：验证设备离线
- **资源隔离**：一台模拟器崩了不影响其他

### 8.2 为什么在数据库里建 driver 记录

中控的 `buildDriverRegistry()` 读 `driver` 表：

```sql
SELECT d.id, d.code, d.endpoint, di.id AS instance_id, c.code AS cap
FROM driver d
JOIN device_instance di ON di.driver_id = d.id
LEFT JOIN resource_capability rc ON rc.resource_id = di.resource_id
LEFT JOIN capability c ON c.id = rc.capability_id
WHERE d.tenant_id = 1 AND d.status = 1 AND d.endpoint IS NOT NULL
```

**每个 driver 只认自己名下的设备**——这是"命令不会发错设备"的保证。

### 8.3 为什么不共用一个端点

如果所有设备共用一个端点，中控把 A 的命令发给 B 的模拟器，模拟器可能照单全收（因为协议里 `equipment_id` 只是个字段）。
**等到真机上才发现"机械臂去搬了不存在的板"**——代价太大。

`DeviceSimulator` 里做了校验：

```java
if (!deviceId.equals(equip)) {
    // 收到别的设备的命令，明确返回错误而不是假装成功
    return error("EC-06-0001", "设备不属于本模拟器");
}
```

## 九、按设备类型定制（--profile）

**不同设备有不同方法集**，模拟器按类型决定"哪些方法该有"。

| 类型 | 方法 | 用在哪 |
|---|---|---|
| **robot** | `Home` `Transfer` `GetPosition` `GetPoints` `Grip` `Release` | 机械臂 |
| **centrifuge** | `OpenDoor` `CloseDoor` `Load` `Unload` `RunProgram` | 离心机 |
| **incubator** | `OpenDoor` `CloseDoor` `Deposit1` `Withdraw1` `SetTemp` | 孵箱 |
| **reader** | `OpenDoor` `CloseDoor` `Read` `GetResult` | 读板机 |
| **generic** | 不限（老行为） | 兜底 |

**打错方法会明确报错**：

```
robot     OpenDoor   → 拒绝 EC-06-0004（机械臂没有开门方法）
incubator Transfer   → 拒绝 EC-06-0004（孵箱不能搬板）
```

**为什么这样设计**：现场配错设备编号时，**要立刻报错**，
而不是让模拟器"假装成功"——真机上会撞机。

### 用法

```bash
# 机械臂
java -cp out com.labos.kernel.sim.DeviceSimulator \
     --port 19601 --device 214 --code ID1731 --profile robot

# 离心机（带参数回显）
java -cp out com.labos.kernel.sim.DeviceSimulator \
     --port 19603 --device 999 --code CENT-01 --profile centrifuge
```

**`sim-up.sh` 会自动按能力选**：

```
TRANSFER   → robot
INCUBATE   → incubator
CENTRIFUGE → centrifuge
READ_PLATE → reader
其他       → generic
```

### 特殊方法的模拟行为

| 方法 | 模拟器做什么 |
|---|---|
| `Open*` / `Close*` | 直接回成功，返回 `{"door":"open"/"closed"}` |
| `GetPoints` / `SyncPoints` | 返回 4 个层位点位（`<code>-L1..L4`） |
| `RunProgram` / `Centrifuge` | **回显传入的 rpm/minutes**，便于验证参数是否传到 |
