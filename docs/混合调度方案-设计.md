# 混合调度方案 — 设计

> **启动前：主链粗筛（简化银行家）**
> **执行中：等待图细管（环检测）**
>
> 粗筛负责"提前告诉用户能不能跑"，细管负责"保证不死锁"。
> 粗筛算错不影响正确性，只是体验差一点。

---

## 一、为什么是两个机制

### 纯等待图的问题

**只能"跑到一半才发现抢不到"**：

```
用户点了"启动" → 系统接受了 → 跑 5 分钟 → 卡在抢设备上 → 一直等
```

**用户感受**：**"点了没反应"**。

### 纯银行家的问题

**要求预知最大需求**，流程有分支做不到（见 `为什么不用银行家算法.md`）。

### 混合的定位

| 机制 | 解决什么 | 算错了会怎样 |
|---|---|---|
| **主链粗筛** | "启动时就知道资源够不够" | **只是体验差**（下次排队），不影响正确性 |
| **等待图细管** | "保证不死锁" | **必须正确**（这是安全底线） |

**关键**：**粗筛可以错，细管不能错。**

---

## 二、主链的定义

### 三种定义方式（按优先级）

| 方式 | 谁定 | 适用 |
|---|---|---|
| **① 编排时人工标记** | 用户 | 最准，推荐 |
| **② 资源最重的分支** | 系统自动 | 无人工标记时 |
| **③ 节点最多的分支** | 系统兜底 | 分支复杂度接近时 |

### ① 人工标记（推荐）

编排时在判定节点上标"主链走哪条"：

```json
{
  "nodeType": "exclusiveGateway",
  "mainPath": "branch-sample",     // 指定主链
  "branches": [
    {"id": "branch-sample", "label": "有样本"},
    {"id": "branch-empty", "label": "空板"}
  ]
}
```

**为什么推荐人工标**：

- **系统不知道业务上哪条是常态**
- 比如"有样本"是 95% 的情况，"空板"是异常分支
- 只有编排的人知道

### ② 自动选"资源最重"

**没标时按算法选**：

```
对每条分支，算它需要的设备集合大小
选最大的那条作为主链
```

**理由**：按最重的算，粗筛**偏保守**——不会出现"筛过了但实际不够"。

**代价**：保守 → 并发度低一点。

### ③ 节点数最多（兜底）

**分支资源需求相同时**，选路径最长的。

**只是为了让算法有个确定结果**，不代表更准。

### 主链上的"资源需求"怎么算

**主链 = 一条确定的路径**，所以资源需求是**确定的**：

```
主链：开始 → 孵箱 → 离心机 → 读板机 → 结束
资源需求：
  位置：{孵箱的某个空位, 离心机的某个空位, 读板机的某个空位}
  设备：{孵箱, 离心机, 读板机}
  机械臂：{岛内机械臂}
```

**注意**：位置是"某类设备的空位"，不是具体哪个（启动时还不知道）。

## 三、粗筛算法（简化银行家）

### 输入

```
running 执行集合：每个执行的
  - 当前节点
  - 主链剩余节点的资源需求
  - 已占资源

待启动执行：
  - 主链全部节点的资源需求
  - 已占资源（通常为空）
```

### 算法

```
① 把"设备"当作资源单元（不细到位置）
   —— 位置数量太多，算起来复杂，且位置通常够用

② 算每个执行的"剩余需求" R_i

③ 算可用资源 A = 总资源 - 已分配

④ 银行家安全检查：
   工作向量 W = A
   完成标记 done[] = false
   循环：
     找 i 使得 done[i]=false 且 R_i ≤ W
     如果找到：
       W += 该执行已占的资源
       done[i] = true
     如果找不到且还有未完成的 → **不安全**，拒绝
     全部 done → **安全**，允许
```

**这就是标准银行家算法**，只是资源单元是"设备"而不是"位置"。

### 为什么资源单元用"设备"不用"位置"

| 用设备 | 用位置 |
|---|---|
| 数量少（10 台） | 数量多（80 个位置） |
| 算法快 | 算法慢 |
| 够用（设备是主要瓶颈） | 过度精细 |

**位置冲突由细管（位置锁）处理**，粗筛不管。

### 粗筛的输出

```json
{
  "canStart": true,
  "reason": null,
  "estimatedWait": null
}
```

或

```json
{
  "canStart": false,
  "reason": "资源不足：孵箱被 2 个执行占用",
  "estimatedWait": "约 30 分钟（等一个孵育完成）",
  "blocking": [{"runId": 123, "device": "ID1183", "until": "..."}]
}
```

**`estimatedWait` 怎么算**：粗筛时可以顺带算出来——
找"最快能完成的执行"，它的剩余时间就是乐观估计。

**这个值不准**（时长预估本来就不准），但**有比没有好**。

## 四、细管（等待图）

### 按已有设计

`docs/资源模型与死锁避免-设计.md` 第三节。

**要点**：

```
抢不到 → 加边 P → Q
       → DFS 检测从 P 出发能否回到 P
       → 有环：拒绝，撤销边
       → 无环：等待
```

### 细管的三层资源

| 层 | 用途 |
|---|---|
| **位置**（L1） | 位置冲突 |
| **出入口**（L2） | 动作级独占 |
| **机械臂**（L3） | 动作级独占 |

**粗筛只看"设备"（≈ L2+L3 的并集），细管看三层全部。**

---

## 五、两者的协同

### 启动时

```
用户点启动
  → 粗筛：算安全序列
     - 安全 → 允许启动，进入队列
     - 不安全 → **拒绝启动**，返回"资源不足 + 预计等待"
```

### 执行中

```
每一步申请资源
  → 细管：等待图检测
     - 无环 → 等待或拿到
     - 成环 → 拒绝，退避重试
```

### 粗筛算错了怎么办

**这是设计的核心保障**。

**场景**：粗筛按主链算"要 2 台"，实际走了分支要 3 台。

```
粗筛：通过（按主链 2 台算的）
执行：走到分支，要第 3 台
  → 细管：等待图检测
     - 无环 → 等（可能等很久，但不会死锁）
     - 成环 → 拒绝，退避
  → 如果一直等不到 → 超时（比如 10 分钟）→ 告警"资源饥饿"
```

**结论**：**粗筛错了最多是"等很久"或"报资源饥饿"，绝不会死锁。**

**这就是"粗筛可以错，细管不能错"的含义。**

## 六、资源饥饿的处理

**细管保证不死锁，但不保证"公平"** —— 某个执行可能一直抢不到。

### 检测

```sql
-- 某个执行等待超过阈值
SELECT run_id, resource_id, now() - wait_started_at AS 等待时长
FROM resource_wait
WHERE now() - wait_started_at > interval '10 minutes';
```

### 处理

| 策略 | 说明 |
|---|---|
| **告警** | "执行 X 等待设备 Y 超过 10 分钟" |
| **提升优先级** | 等得越久优先级越高（防饿死） |
| **人工介入** | 实在不行，人工决定让谁先 |

**不建议"强制抢占"** —— 板可能真在设备里。

### 优先级等待补偿（推荐）

```java
// 每等 1 分钟，有效优先级 +1
int effectivePriority = basePriority + (int) waitMinutes;
```

**这样等得久的最终会赢**，不会永远饿死。

## 七、实现顺序

| 批次 | 任务 | 估时 | 依赖 |
|---|---|---|---|
| **1** | 三层资源模型（位置/出入口/机械臂） | 1 周 | 无 |
| **2** | 等待图细管 + 环检测 | 1 周 | 1 |
| **3** | **主链定义**（人工标记 + 自动选） | 3 天 | 无（可并行） |
| **4** | **粗筛算法 + 启动接口** | 1 周 | 1, 3 |
| **5** | 资源饥饿告警 + 优先级等待补偿 | 3 天 | 2 |

**总计约 4 周**（比纯等待图多 1.5 周）。

**顺序不能换**：1 是基础，2 是安全底线，3-4 是体验优化。

**如果只做 1+2**：能保证不死锁，但用户点启动后可能等很久才知道抢不到。
**加上 3+4**：启动时就能给出明确反馈。

## 八、风险与取舍

### 明确接受的风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **粗筛的 `estimatedWait` 不准** | 用户看到"约 30 分钟"实际 2 小时 | 标注"预估，仅供参考" |
| **主链标记错了** | 粗筛基于错误假设 | 细管兜底（只影响体验） |
| **资源饥饿** | 某执行一直等 | 优先级等待补偿 + 告警 |
| **复杂度** | 两套机制 | 粗筛是纯计算（无状态），细管是有状态 |

### 明确不做

| 不做 | 为什么 |
|---|---|
| 粗筛算到位置粒度 | 位置太多，且位置通常够用 |
| 强制抢占 | 板可能在设备里 |
| 自动终止饥饿的执行 | 可能正在做别的事（比如孵育中） |
