## 4. 四个真问题（本轮实证 / 一处已修）

### 4.1 Q18 巡检误报（R13-22，P1，待 CR）

复杂主流程产生 5 行 `status='completed' AND execution_resolution_status='unresolved'`：
`S1/S2/S3/S4`（level=1 步骤行）与 `V0`（`__setVar` BUILTIN 节点）。
它们走 `executeBuiltin` / 不是 `executeNode`，完成处理器不触发；而设计 §3.7:419 明确
「结构节点跳过——它们没有执行确认语义」，Q18 却按 `status='completed'` 全表扫。
加上内核重载时的 run `1001333`，当前巡检共命中 8 行，**全部来自这一口径冲突**。
其余 19 组引用完整性巡检 0 行。

### 4.2 循环流程被命令账本 fail-closed 拦住 —— 本轮已修（CR-001-b）

**修复前**：run `1001338` `paused / waiting_human`，4 个圈次行全 `manual`，
错误码 **EC-99-0006**：

```
策略[*@COMMAND]已耗尽：attempt=1 >= maxAttempts=1，原意图=RETRY
命令账本已有 ... 记录，禁止重复下发（需人工确认设备位置）
```

根因：`idempotency_key` 是 `r|n|a|s|d|m`（run/node/attempt/step/device/method），
**不含圈次**；第 2 圈撞键 ⇒ `created=false` ⇒ 拒绝派发。
这是设计 §8.2#6 选定的 fail-closed 取舍，但代价首次被量化：**循环流程跑不完**。

**修复后**：`StepContext` 加 `loopIndex` + `withLoopIndex`，`GraphRunner` 派发前注入 `visit`，
`DriverStepExecutor` 只在 `loopIndex>1` 时给 key 拼 `|vN`。
无环图 / 顺序路径 / 第 1 圈 key 逐字节不变，历史账本与既有幂等行为不受影响；
同一 attempt 重发仍命中同 key、照常拒绝。

验证：loop run `1001343` **completed、0 个 EC-99-0006**，4 个圈次行状态全 `completed`。
规格变更已登记 `docs/CR-001-物料声明写入入口与循环幂等键-20261112.md`，**独立复审待做**。

### 4.3 多圈 Effect 静默丢弃（R13-06）—— 本轮已修（机制层）

**修复前**：4 个 `C1` 圈次行只有 **1** 个 `plate_material_effect`（`source_loop_index=0`）。
`MaterialEffectService` 把 `loopIndex` 写死 0 + `ON CONFLICT ... DO NOTHING`
⇒ 第 2 圈起静默丢弃（11 圈时也是 1 个）。

**修复后**：`NodeResolution` 增加 `loopIndex`；`RunStateMachine` 加 `withLoopIndexSupplier`，
`GraphRunner` 每次派发前注入本圈 `visit`；`recordEffectIntent` → `insertEffect` 用真实圈次。
**执行确认仍写 `loop_index=0` 的汇总行**（圈次行在 `executeNode` 之后才建，提前写圈级确认会落到不存在的行），
所以不需要同时改 §8.2#2 的圈次行时序 —— 这是把 R13-06 独立修掉的关键取舍。

**验证**：
- 纯逻辑单测：`withLoopIndexSupplier(() -> 3)` 时完成处理器收到 `loopIndex=3`；未注入时顺序路径为 0（`EngineSelfTest` 新增 2 例，总 **822/822**）。
- 唯一键机制（事务内真跑）：同节点插 `source_loop_index=1/2/3` 三条 → `ROUNDS=3` 全部保留；
  再插一条 `loop_index=1` → `INSERT 0 0`、`AFTER_DUP=1`（`DO NOTHING` 只对同圈去重）。
- **端到端复跑（环境恢复后通过）**：
  - 途中曾连续失败，现象是节点 `manual`、原因「无可执行资源：节点未给出初始设备，且候选集为空」。
    逐层定位到**三层环境问题叠加**：① `redis-server` 未运行 ⇒ 心跳读不到链路状态；
    ② `HeartbeatService.redisClient()` 的 catch 只打 `e.getMessage()`，把
    `failed to create a child event loop`（Netty `Multiloop` 创建失败的包装消息，真因在 cause 里）
    打成了无堆栈的一行；③ `RedisClient` 构造失败时不 `client.shutdown()`，Lettuce 持有的
    Netty EventLoopGroup 反复泄漏；④ sidecar 未写 `labos:link:*`（需重跑一次 `start-all`）。
  - 修复：catch 改打完整堆栈 + 构造失败时 `shutdown()` 释放资源；起 Redis、重跑 sidecar
    `stop-all/start-all`（写入 5 条 `labos:link:*`）⇒ 心跳恢复「5 台设备在线」。
  - 恢复后实测：loop run `1001348` `completed`，`plate_material_effect` 三条
    `C1|loop_index=1/2/3` 全 `APPLIED` ⇒ **R13-06 端到端验证通过**；
    main run `1001347` 的 3 条 Effect 仍为 `loop_index=0`（无环图口径未变）。

### 4.4 循环变量跨圈不持久（本轮新发现，P1）

首轮修完幂等键后循环**跑满了 10 圈上限**而非 3 圈。查 `run.input->'vars'`：
`{"n":"1"}` 始终不变；`__expr` 在日志里算出了 `n=2`，但下一圈变量被刷新回初值，
回边条件 `${n} >= 3` 恒不成立。

⇒ 循环退出条件依赖变量递增时**不可靠**，只能靠流程级 `maxIterations` 兜底。
脚本已改为给 loop 流程设 `maxIterations=3` 得到可复现的 3 圈；**根因未修，已列入待开发**。
这属于流程变量/内置节点层的问题，与 S2 物料链路无关，但会阻碍「循环 + 物料」的组合验收。

### 4.5 Q15b 未排除圈次行（R13-23，本轮新发现，待 CR）

Q15b 按 `(run_id, node_key, loop_index)` **逐行**比对 `run_node.material_sync_status`
与「从 Effect 集合重建的聚合值」，但：

- `updateNodeMaterialSync` 的 SQL 硬编码 `AND loop_index = 0`，只重算汇总行；
- `selectNodeMaterialSync` 的聚合是**跨所有圈**的（不带 loop_index 条件）。

⇒ 圈次行（`loop_index=1..N`）的 `material_sync_status` 永远是默认 `not_required`，
而 Q15b 拿「节点级聚合」去比它，必然不一致。当前库命中 27 行，全部是循环流程的 `C1` 圈次行。

判定：**巡检 SQL 的口径没排除圈次行**，与 R13-22（Q18 没排除 BUILTIN/步骤行）同类。
设计只定义了「节点级投影」，没定义圈次行的投影语义。处置需 CR：
要么 Q15b 收窄为 `loop_index=0`，要么把圈次行也纳入投影重算并明确语义。
本轮**未擅自改巡检 SQL**，验证脚本把 Q15b 与 Q18 一起单列为「已知口径」、明细每次照常打印。
