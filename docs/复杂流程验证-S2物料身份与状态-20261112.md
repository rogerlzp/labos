## 2. 两张图

### 2.1 `main` · 复杂主流程（11 节点 / 13 连线）

```
S → V0(__setVar stage=1) → P1(并行分叉)
                            ├─ A1 机器人 Home   [声明: PL-TRACE-2183 → ready]
                            ├─ A2 离心机 Home   [声明: PL-TRACE-2214 → in_progress]
                            └─ A3 封膜机 Home   (无声明)
                          → J1(并行汇合) → X1(异或, ${mode}=='fast')
                            ├─ T5 机器人 Home   [声明: PL-TRACE-2183 → completed]
                            └─ T6 离心机 Home   (default, 无声明)
                          → E
```

关键设计：**同一块板 `PL-TRACE-2183` 被 A1 与 T5 先后改两次**，用来验证
`state_version` 乐观锁与事件版本链是否连续；`V0` 是 BUILTIN 变量节点，用来观察 Q18。

### 2.2 `loop` · 循环探针（5 节点 / 5 连线，含回边）

```
S → C1(机器人 Home, 声明 PL-TRACE-2214 → ready) → X(异或)
      ├─ ${n} >= 3 → E
      └─ default → V(__expr: n = ${n} + 1) → 回 C1
```

流程变量 `n` 初值 1，回边上限 10 圈 / 总步数 500。

### 2.3 声明怎么挂上去的（暴露一个开发缺口）

`material_effect` **没有写入 API、设计器页面也没有录入入口**；BPMN XML 解析器同样不认这个属性
（`WorkflowGraphParser.java:184-199` 只读 id/name/protocolName/resource）。
本脚本只能在 `PUT /api/workflows/{id}/graph` 之后**直接写列**：

```sql
UPDATE workflow_node SET material_effect = '{
  "mode":"transition","target":{"barcode":"PL-TRACE-2183"},
  "set":{"processState":"ready"},
  "acceptedEvidenceLevels":["device_ack"]}'::jsonb
WHERE workflow_id=<wf> AND node_key='A1';
```

⇒ **这是头号待开发项**：声明只能靠 DBA 手改，业务上不可用。详见 §5。

## 4. 三个真问题（本轮实证）

### 4.1 Q18 巡检误报（R13-22，P1，待 CR）

复杂主流程产生 5 行 `status='completed' AND execution_resolution_status='unresolved'`：
`S1/S2/S3/S4`（level=1 步骤行）与 `V0`（`__setVar` BUILTIN 节点）。
它们走 `executeBuiltin` / 不是 `executeNode`，完成处理器不触发；而设计 §3.7:419 明确
「结构节点跳过——它们没有执行确认语义」，Q18 却按 `status='completed'` 全表扫。
加上内核重载时的 run `1001333`，当前巡检共命中 8 行，**全部来自这一口径冲突**。
其余 19 组引用完整性巡检 0 行。

### 4.2 循环流程被命令账本 fail-closed 拦住（新发现，P0/P1）

`loop` 流程 run `1001338` 最终 `paused / waiting_human`，4 个圈次行全 `manual`，
错误码 **EC-99-0006**。内核日志原文：

```
策略[*@COMMAND]已耗尽：attempt=1 >= maxAttempts=1，原意图=RETRY
命令账本已有 ... 记录，禁止重复下发（需人工确认设备位置）
```

根因：`DriverStepExecutor` 的 `idempotency_key` 是
`r|n|a|s|d|m`（run / node / attempt / step / device / method），**不含 `loop_index`**；
循环第 2 圈生成同一个 key ⇒ `CommandLedger.begin` 返回 `created=false` ⇒ 拒绝派发。

这是设计 §8.2#6 明确选定的「循环多轮重复派发一律拒绝并转人工对账」，**不是实现 bug**，
但代价在真实流程里第一次被量化：**任何带设备动作的循环流程，第 2 圈起就转人工，跑不完**。
⇒ 循环能力当前实际上不可用，需要把 `loop_index` 纳入幂等键（会动到冻结规格，需 CR）。

### 4.3 多圈 Effect 静默丢弃（R13-06，实证复现）

4 个 `C1` 圈次行，只有 **1** 个 `plate_material_effect`（`source_loop_index=0`）。
`MaterialEffectService.java` 把 `loopIndex` 写死 0 + `ON CONFLICT ... DO NOTHING`
⇒ 第 2 圈起静默丢弃。与评审记录 R13-06 判断一致，现有真实数据佐证。
**不能单独修**：圈次行目前在 `executeNode` 返回之后才建，单独传真实 visit 会让
执行确认写到不存在的行；必须与 §8.2#2「圈次行先建后执行」一起做。
