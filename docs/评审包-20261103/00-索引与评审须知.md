## 一、这是什么

这是一套**实验室自动化中控系统**（LabOS）的完整评审材料。系统负责：把实验室的仪器（封膜机、离心机、孵箱、机械臂……）接进来，用"流程图"编排工艺，按图驱动设备，设备出错时按策略重试/换机/转人工，出问题能停下来等人处理、处理完接着跑。

**它现在能干什么、怎么实现的、为什么这么设计、测到什么程度**，分别对应四份文档：

| # | 文档 | 回答什么问题 | 建议阅读顺序 |
|---|---|---|---|
| 01 | [功能文档](01-功能文档.md) | 系统能给用户什么？页面上怎么用？ | 先读，建立整体印象 |
| 02 | [技术文档](02-技术文档.md) | 代码怎么组织？一次执行走哪条链路？ | 再读，对照代码 |
| 03 | [设计文档](03-设计文档.md) | 为什么这么设计？放弃了什么？ | 重点看，这里最容易有分歧 |
| 04 | [测试文档](04-测试文档.md) | 测了什么？怎么复现？哪里没测？ | 最后看，用于判断可信度 |

历史设计与专题（52 份）仍在 `docs/` 下，本包不重复它们，只在需要时链接。

## 三、怎么把系统跑起来

### 3.1 依赖

- JDK 17+、Node 20+、.NET 10（sidecar）、PostgreSQL 14+（远程库，见环境变量）
- 可选：Redis（本仓库未强依赖，`redis` 包只有 1 个类）

### 3.2 环境变量（后端连库）

```bash
export LABOS_DB_HOST=<测试库地址>
export LABOS_DB_NAME=<库名>
export LABOS_DB_USER=<账号>
export LABOS_DB_PASS='<口令，内部渠道单独提供>'
# 注：本仓库**不存**任何数据库口令（历史上手册原文也因保密要求不入库）。
# 需要连接测试库时向项目负责人索取，不要写进代码或文档。
```

其他可调项：`LABOS_HEARTBEAT_INTERVAL_MS`（默认 10000）、`LABOS_OFFLINE_ALERT_MS`（默认 max(3×间隔, 30s)）、`LABOS_FAST_RECOVERY=1`（关闭真实退避，仅 CI 用）。

### 3.3 启动顺序（四件套）

```bash
# ① 编译内核
cd labos-kernel && javac -encoding UTF-8 -d out -cp "out:lib/postgresql-42.7.3.jar" $(find src -name '*.java')

# ② 设备模拟器（模拟真机 TCP 协议，端口 19601/19602）
java -cp out com.labos.kernel.sim.DeviceSimulator --model s100 --device 413 --code S100UI --port 19601 --delay 1
java -cp out com.labos.kernel.sim.DeviceSimulator --model aspin-2k --device 414 --code ASPINUI --port 19602 --delay 1

# ③ sidecar（.NET，把 HTTP 翻译成设备厂商协议；18501/18502）
cd sidecar-dotnet/Labos.Sidecar
dotnet run -- --model s100 --transport sim --sim-port 19601 --port 18501 --device 413

# ④ 后端 API（18080）
cd labos-kernel && java -cp "out:lib/postgresql-42.7.3.jar" com.labos.kernel.api.ApiServer 18080

# ⑤ 前端（5173）
cd webapp && npm run dev
```

首次登录：`admin / admin123`（数据库里的测试账号，**生产必须改**）。

> 没有 sidecar 时，设备链路的测试会跳过；没有模拟器时，执行会失败但不影响阅读代码。

## 四、建议评审重点（9 个）

按"最容易出问题 + 影响最大"排序。每条都给了入口，不用满仓库找。

| # | 重点 | 为什么值得看 | 入口 |
|---|---|---|---|
| 1 | **恢复作用域匹配** | 库里配 `command` 级重试，代码抛 `node` 级 → 配置永远不生效。这类"配了等于没配"最难发现 | `DriverStepExecutor.scopeOf()`、`RecoveryPolicyResolver` |
| 2 | **图执行的并行语义** | 是"逻辑并行"（一条一条跑、都能推进）不是线程并行。设备动作有物理副作用，这里错一次就是撞机 | `GraphRunner.run()` |
| 3 | **断点续跑的正确性** | 续跑时"已完成的节点必须跳过"，否则**机械臂会把板再搬一次** | `WorkflowService.resumeAsync()` + `GraphRunner.withSkipKeys` |
| 4 | **`skipped` vs `bypassed`** | 两个词看着像，行为完全不同：前者停下转人工（板位不可信），后者正常继续（分支没选中） | `NodeStatus`、`WorkflowService.markBypassedNodes` |
| 5 | **条件表达式求值器的安全边界** | 自己写的解析器，不用 `eval`。要确认真的没法注入 | `ConditionEvaluator` + `ConditionEvaluatorSelfTest` 的注入用例 |
| 6 | **循环的防死循环** | 回边写错就是无限循环；保护是"单节点默认 10 圈（可按流程配 `attr.maxIterations`）+ 总步数 500" | `GraphRunner.run()` 里的 `visits` / `maxSteps` |
| 7 | **状态与真相是否一致** | 页面显示的绿/橙/灰，是否真的对应库里的 `run_node.status`（历史上出现过"图显示未执行、实际已完成"） | `RunGraph.tsx`、`QueryService.runGraphJson` |
| 8 | **数据库写放大与幂等** | `createNodeShells` 重复插入会撞唯一键（已修）；同类问题是否还有 | 全库搜 `INSERT INTO run_node` / `ON CONFLICT` |
| 9 | **内置节点的判定边界** | `protocolName` 以 `__` 开头 = 变量/表达式节点，**不能进设备路径**。判错的后果是"无可执行资源"直接转人工（我们第一次就是这么挂的） | `WorkflowGraphParser`（`Kind.BUILTIN`）、`GraphRunner.executeBuiltin` |

## 五、已知问题与风险（诚实清单）

> 评审时请把下面这些当作"已知"，不必重复报告；但**如果你认为其中某条的严重性被低估了，请直接指出**。

### 5.1 功能性缺口

| # | 问题 | 影响 | 位置 |
|---|---|---|---|
| 1 | 错误码只能改、不能新增/删除 | 非手册来源的自定义码必须改代码 | `/error-codes` 页 |
| 2 | ~~循环重入时 `run_node` 只有一行~~ **已修（M6）**：`loop_index` 每圈一行 | 可按圈次复盘第 N 圈（汇总行仍 `loop_index=0`） | `run_node` 唯一键 `(run_id, node_key, attempt, loop_index)` |
| 3 | 变量只支持顶层标量 | 设备返回嵌套结构时取不到内层 | `WorkflowService.loadNodeOutputs` |
| 4 | 条件表达式不支持算术 | `${a}+1 > 3` 写不了 | `ConditionEvaluator` |
| 5 | 圈数上限是流程级不是网关级 | 一个流程多条回边共用一个上限 | `workflow.attr.maxIterations` |
| 6 | 回边跨越并行分叉未验证 | 组合场景可能死锁 | 测试文档 §6 |
| 7 | 实验状态/进度没有实时推送 | 页面靠 2 秒轮询 | `Experiments.tsx` |

### 5.2 工程性风险

| # | 风险 | 说明 |
|---|---|---|
| 1 | 测试库口令只在内部渠道流转 | 本包正文**只用占位符**，仓库里不含口令；脚本通过 `LABOS_DB_*` 环境变量注入 |
| 2 | 后端无鉴权分级 | 所有接口只要登录就能调，没有按角色细分（`app_role` 表存在但没用起来） |
| 3 | 单进程内存态 | 暂停/恢复、岛锁、设备锁都在进程内；多实例部署会失效 |
| 4 | 事件表按月分区，但归档/清理策略没有 | `run_event` 已 10 万+ 行 |
| 5 | 前端 19 个页面无 e2e 测试 | 全靠手工点（本项目历史上靠"真点一遍"发现过 5 个真 bug） |

### 5.3 不要相信的地方

- **模拟器不是真机**。协议帧格式对得上，但时序、并发、异常行为都比真机温和。
- **"跑绿了"不等于设备动了**。历史上出现过"页面全绿、设备一条命令没收到"（根因：设备 id 被判成伪 id）。评审时请以 `run_command` 表为准，而不是页面。
- **压测数据是单机模拟器**，不能外推到真实现场吞吐。

## 六、复审时最省事的三个动作

```bash
# ① 跑一遍纯逻辑测试（不需要数据库，1 分钟内）
cd /path/to/labos && ./scripts/test-all.sh --pure-only
# 期望：通过 379 / 失败 0

# ② 跑一遍设备全链路（需要模拟器 + sidecar，约 3 分钟）
export LABOS_DB_HOST=... LABOS_DB_NAME=... LABOS_DB_USER=... LABOS_DB_PASS=...
./scripts/verify-device-chain.sh
# 期望：41 条断言全过（脚本会打印 ✓/✗）

# ③ 抽查一个真实执行
curl -s "$API/api/runs/<id>" -H "Authorization: Bearer $TOKEN" | jq '.run.status, [.nodes[]|{nodeKey,status,errorCode}]'
# 对照页面 /runs/<id> 的流程图颜色
```
