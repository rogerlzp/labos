## 一、总体架构

```
┌────────────────────────────────────────────────────────────────┐
│ 前端  webapp (React 18 + antd 5.29 + react-query + bpmn-js)     │
│  19 个页面：流程库/设计器/实验编排/实验画布/运行详情/暂停队列/…    │
│  8,393 行 TS/TSX                                                 │
└───────────────┬────────────────────────────────────────────────┘
                │ HTTP + Bearer token（18080）
┌───────────────▼────────────────────────────────────────────────┐
│ API 层  api.ApiServer（路由/鉴权/审计） · QueryService（读）      │
│        AuthService（登录/token）                                 │
└───────────────┬────────────────────────────────────────────────┘
                │ 直接调用（同进程）
┌───────────────▼────────────────────────────────────────────────┐
│ 业务层  workflow.*                                              │
│  WorkflowService（一次执行的编排与收尾）                          │
│  GraphRunner（按 BPMN 图推进：并行/分支/循环）                    │
│  PreflightChecker（跑之前先体检） · PauseManager（暂停恢复）      │
│  ExperimentExecutor / ExperimentScheduler（实验调度）            │
│  StartupRecovery（崩溃后的孤儿单） · RunMonitor（实时状态）       │
└───────────────┬────────────────────────────────────────────────┘
                │
┌───────────────▼────────────────────────────────────────────────┐
│ 执行层  engine.*                                                │
│  RunStateMachine（重试/退避/判定的状态机）                        │
│  ConditionEvaluator（条件表达式，自研解析器）                     │
│  NodeStatus / RunProgress / 事件流                               │
└───────────────┬────────────────────────────────────────────────┘
                │ DriverStepExecutor
┌───────────────▼────────────────────────────────────────────────┐
│ 驱动层  driver.*                                                │
│  DriverRegistry（谁有驱动） · DeviceLock/PositionLock（并发）     │
│  WaitForGraph（等待图判死锁） · HeartbeatService（心跳）          │
│  TcpDriverAdapter（TCP 协议） · ShadowProbe/ShadowRunner（影子）  │
└───────────────┬────────────────────────────────────────────────┘
                │ TCP 18501/18502（自定义帧协议）
┌───────────────▼────────────────────────────────────────────────┐
│ sidecar  sidecar-dotnet/Labos.Sidecar（.NET 10）                 │
│  把中控的 JSON 帧翻译成设备厂商协议；本仓库用 sim 传输            │
└───────────────┬────────────────────────────────────────────────┘
                │ TCP 19601/19602
┌───────────────▼────────────────────────────────────────────────┐
│ 模拟器  sim.DeviceSimulator（S100 / ASpin 2K 行为）              │
└─────────────────────────────────────────────────────────────────┘
```

**为什么中间夹一层 sidecar**：设备厂商协议是 C/C++/C# SDK 形态，直接塞进 JVM 要么 JNI 要么重写。sidecar 用 .NET 复用厂商 SDK，中控只认一条稳定的 JSON 帧协议。代价是多一跳（延迟约 1–3ms，可接受）。

## 三、数据模型（核心表）

```
workflow (流程图)                       device (型号/设备池)
  ├─ workflow_node (节点)                  ├─ device_method (方法，界面读这张)
  │    resource_id / seq：设备绑定与图内顺序（从 XML 落表，读侧不解析图；
  │       在 M9 前置里补齐，存量用 BindingBackfill 回填）
  │    └─ workflow_node_step               └─ device_instance (实例，挂到岛)
  └─ workflow_graph_history (版本)

experiment (实验)
  ├─ experiment_process (seq → workflow, loop_count)
  └─ experiment_run (一次实验执行)
       └─ experiment_run_step (第 seq 步 × 第 loop 次 → run_id)

run (一次执行, run_type = workflow|experiment)
  ├─ run_node (level=0 业务节点 / level=1 步骤)
  ├─ run_command (一条命令 + 原始回包 device_raw_response)
  └─ run_event (事件流, 按月分区)

error_code (错误码) ── recovery_policy (恢复策略, 按 scope 一条)
device_state (在线/心跳) ── alert_state (告警, 按 fingerprint 唯一)
plate / plate_location_audit / position_state  (板位级互斥)
audit_log (谁改了什么)
```

**关键约束（评审时请重点看）**

| 表 | 约束 | 为什么重要 |
|---|---|---|
| `run_node` | 唯一键 `(run_id, node_key, attempt, loop_index)` | 续跑时重复插入会撞键 → 整单 failed（已修，见设计文档 D4）；`loop_index` 让循环每圈一行（M6） |
| `error_code` | 唯一键 `(tenant_id, code)`；`scope` 决定恢复层级 | 作用域配错 = 策略不生效 |
| `recovery_policy` | `(error_code_id, scope)` 一条 | 同码同作用域两条里只有一条会用（`findFirst`） |
| `alert_state` | 唯一键 `(tenant_id, fingerprint)` | upsert 写成 insert 就会每次心跳报 duplicate key（已修） |
| `device_method` | 唯一键 `(device_id, method)` | 入池时按此 upsert（已修：原来根本不写） |

**枚举**：`node_status = {pending, ready, running, completed, failed, skipped, aborted, manual, bypassed}`；`run_status`、`recovery_strategy = {retry, reassign, skip, abort, manual}`、`recovery_scope = {command, node, run, device}`。

## 四、一次执行发生了什么（主干链路）

以「流程库 → 执行」为例（实验发起的路径多一层 `ExperimentExecutor`，第 5 步之后相同）：

```
1. POST /api/workflows/{id}/run?async=1[&vars=k=v]
   ApiServer → WorkflowService.startAsync()
   → createRun()  写 run 行（status=running），写 input.vars

2. 后台线程 execute(workflowId, mode, runId)
   → 载入 workflow + workflow_node
   → createNodeShells()  给**所有**业务节点建 run_node（status=running）
        ⚠️ 这里必须幂等：续跑会再进来一次（D4）

3. 若 workflow.graph->>'xml' 有内容 → GraphRunner.run(graph, executor)
   否则退化为顺序执行（老数据）

4. GraphRunner 主循环：
   - 就绪队列取节点 → 判断类型
   - 任务节点：RunStateMachine.executeNode(...)
        → DriverStepExecutor：取设备（绑定的实例优先，否则按能力轮转）
        → DriverRegistry 找驱动 → TCP 发给 sidecar → 设备回包
        → 失败则按 scope 查 recovery_policy 决定 retry / reassign / manual / abort
   - 网关：SPLIT_PARALLEL 激活所有出边；SPLIT_XOR 用 ConditionEvaluator 选一条
   - 每个节点成功后：把设备回包的字段 merge 进变量表（循环靠它退出）
   - 边界检查：暂停请求、圈数上限、总步数上限

5. 收尾（WorkflowService）
   - updateNodeResults()  回填最终状态 + error_code
   - markBypassedNodes()  整单成功时，把仍 running 的节点标 bypassed
   - settleRun()  run 状态定稿
   - markPlatePosition()  记录板最后停在哪台设备
```

**状态回写与展示的对应关系**（评审重点 #7）：

| 库里 | 图上颜色 | 说明 |
|---|---|---|
| `completed` | 绿 | |
| `failed` / `aborted` | 红 | |
| `manual` | 橙 | 转人工 |
| `skipped` | 黄 | 策略跳过，板位不可信 |
| `bypassed` | 淡灰点线 | 分支没选中 |
| `running`（单子已停） | 灰虚线（折算 pending） | **不能直接显示"执行中"** |

## 五、关键机制

### 5.1 重试与退避

`RunStateMachine` 在失败时调 `RecoveryDecider`：

1. 用 `errorCode + scope + 上下文` 查策略（`RecoveryPolicyResolver`，`specificity → priority` 排序，`findFirst`）
2. 按策略决定 `retry / reassign / skip / abort / manual`
3. `retry` 用 `BackoffCalculator` 算延迟（线性/指数 + jitter），`Sleeper` 真的睡

> ⚠️ 历史坑：生产路径曾误用 `Sleeper.recording()`（只记录不睡）→ "retry 3 次" 实际 50ms 用完。现在生产用 `Sleeper.REAL`，只有 `LABOS_FAST_RECOVERY=1` 才记录式。

### 5.2 暂停与断点续跑

- **暂停**：`pauseChecker` 在**节点边界**检查（不在动作中间停 —— 机械臂抓着板会掉）
- **续跑**：`resumeAsync()` 读已 `completed` 的 node_key → 删掉未完成节点的 `run_node`（命令级联）→ run 置 running → 同 runId 再跑，`GraphRunner.withSkipKeys` 跳过已完成的
- **崩溃恢复**：`StartupRecovery` 在进程启动时把遗留 `running` 收成 `failed` + `input.recoverable=true` + `interruptedAt`；界面只列近 7 天，可 `dismiss`

### 5.3 并发与死锁

| 锁 | 粒度 | 解决什么 |
|---|---|---|
| `DeviceLock` | 单台设备 | 两台流程抢同一台设备 |
| `PositionLock` | 单个板位 | 机械臂把板放回正在被占的位置 |
| `IslandLock` | 整岛（可选 `exclusive=1`） | 检修时独占 |
| `WaitForGraph` | 全局 | 资源环形等待检测，发现环就拒绝申请 |

### 5.4 心跳与在线状态

`HeartbeatService` 每 `LABOS_HEARTBEAT_INTERVAL_MS`（默认 10s）探一次，超过 `max(3×间隔, 30s)` 判离线，写 `device_state.online` + 开/关 `alert_state`（`ON CONFLICT DO UPDATE`，幂等）。

### 5.5 审计

写操作（`run.start`、`error_code.update`、`run.dismiss`…）都走 `audited(...)`，落 `audit_log`。**读接口不审计**。

## 七、部署与运维

| 项 | 值 / 做法 |
|---|---|
| 端口 | API 18080、前端 5173（dev）、sidecar 18501/18502、模拟器 19601/19602 |
| 配置 | 全部走环境变量（`LABOS_DB_*`、`LABOS_HEARTBEAT_INTERVAL_MS`、`LABOS_OFFLINE_ALERT_MS`、`LABOS_FAST_RECOVERY`） |
| 日志 | stdout（重定向到 `/tmp/labos-api.log`），驱动/心跳日志量大，建议按级别过滤 |
| 备份 | 走 PostgreSQL 常规备份；`run_event` 按月分区，可整分区归档 |
| 健康检查 | `GET /api/process-status`（能返回即有活）；数据库连通性由启动日志判断 |

**已知运维陷阱**

1. 重启 API 会让所有 token 失效（token 存内存），页面需重新登录。
2. 验收脚本 `verify-device-chain.sh` 用随机端口，**收尾会自动把驱动端点还原**到 18501/18502；若手工改过端点，脚本跑完会覆盖。
3. `run_event` 与 `run_command` 增长快（已 11 万+），长期要归档策略。
