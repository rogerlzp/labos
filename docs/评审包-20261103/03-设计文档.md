> 面向：评审（重点看这份）、后续维护者

## 0. 三条总原则

这套系统是**驱动物理设备**的，所以优先级和普通后台系统不一样：

| 优先级 | 原则 | 具体表现 |
|---|---|---|
| 1 | **不伤害** | 宁可停下转人工，也不猜着往下跑（`skipped` 一律停、未登记错误码一律转人工、表达式写错走 default 而不是乱选） |
| 2 | **可追溯** | 每个动作、每个命令、每个原始回包都落库；改配置写审计 |
| 3 | **可恢复** | 暂停能续、崩溃能续、续跑不重复执行已完成动作 |

第 1 条经常和第 3 条冲突（比如"续跑要跳过已完成节点"和"跳过意味着板位不可信"），冲突时的裁决写在 D2/D4。

## D1. 恢复作用域是**错误码的属性**，不是抛出点随手写的

**背景**：原来 `DriverStepExecutor` 里所有失败都抛 `RecoveryScope.NODE`。而库里按错误性质配了不同层级：

| 码 | 库里配的 | 代码抛的 | 结果 |
|---|---|---|---|
| `EC-05-1006` 通讯失败 | `command` / retry ×5 | `node` | **匹配不上**，落到通配 → 一次网络抖动就转人工 |
| `EC-06-0001` 驱动未加载 | `run` / abort | `device` | 同样匹配不上 |

**选择**：`error_code` 加 `scope` 列；`DriverStepExecutor.scopeOf(code)` 成为唯一出口（懒加载 + 前缀兜底），五个抛出点全部改用它。

**回填数据不另写一张"意图表"**：直接取该码 `recovery_policy.scope` —— 写策略时定的层级就是真实意图。

**放弃的方案**

- 在代码里按前缀判断（`EC-05-*` → command）：短期够用，但时间一长必定和库里配置分叉（这已经是第二次了）。
- 给每个抛出点加参数：调用方容易传错，且新增错误码时容易忘。

**代价**：多一次懒加载查询（进程内缓存）；`error_code.scope` 与 `recovery_policy.scope` 可能不一致（以 policy 为准回填，之后手工改 code 的 scope 不会反过来影响已有策略）。

## D2. `skipped` 与 `bypassed` 必须分开

**背景**：异或网关选了一条路，另一条路上的节点该是什么状态？

**选择**：新增 `bypassed`（分支未选中），**不复用** `skipped`。

**为什么**：两者语义相反。

| 状态 | 语义 | 系统该做什么 |
|---|---|---|
| `skipped` | 这步**该做但没做**，板的位置已不可信 | **立即停下转人工**（继续跑会让后面的"取板"伸进空位置） |
| `bypassed` | 这条路**压根不用走** | 正常继续，不影响板位 |

如果为了省事把没走的分支标成 `skipped`，整单会被判成"板位不可信"然后停下等人 —— 完全错误的行为。

**实现要点**：只在**整单成功结束后**把仍挂 `running` 的业务节点标 `bypassed`。
排除条件必须覆盖 `MANUAL / ABORTED / SKIPPED / aborted()` ——
`SKIPPED` 会让整单落成 `paused/waiting_human`，那种单子的下游节点是"还没轮到"，
不是"分支没选中"（第一版漏了 `SKIPPED`，2026-11-03 评审 H2 指出，已补齐）。

**代价**：`node_status` 枚举多一个值，所有 switch/映射要跟着加（已加：前端两处颜色映射、后端两处状态映射）。

## D3. 图执行是**逻辑并行**，不是线程并行

**背景**：BPMN 并行网关的语义是"两条分支同时走"。

**选择**：所有就绪节点排队，**一条一条执行**；并行只体现在"都能被推进"，不要求墙钟重叠。

**为什么**：

1. 设备是共享资源。真并行要抢锁，抢锁就会死锁，而机械臂互斥是物理的（同一时间只能抓一块板）。
2. 调试时"一次一条"能复现；真并行的问题（A 卡住等 B、B 卡住等 A）在真机上就是撞机。
3. 现场瓶颈在机械行程（秒级），不在中控调度（毫秒级）。

**放弃**：线程池并行执行节点 —— 收益小、风险大。

**代价**：两条本该重叠的分支（比如两台离心机同时转）实际串行，整体时长 = 之和。这个代价在设计文档 `docs/多实验并行调度-设计.md` 里用"跨实验并行"补，不在这里补。

## D4. 断点续跑 = 删未完成节点行 + skipKeys

**背景**：点「继续」原先把 run 置回 `queued`，然后没人拾起 → 永远排队（现场表现为"换完纸点继续没反应"）。

**选择**：

1. 读本 run 已 `completed` 的 `node_key` 作为 `skipKeys`
2. **删掉"未完成业务节点"及其步骤行**：先删 `level=1`（`parent_node_id` 指向那些业务节点的），
   再删 `level=0`。`run_command` 挂步骤行上（FK `ON DELETE CASCADE`），随步骤行一起消失
3. 步骤序号从库里 `max(S<数字>)` **续编**（不能从头编，否则撞 `uk_run_node`）
4. run 置 `running`，用**同一个 runId** 后台再跑，`GraphRunner.withSkipKeys` 跳过已完成

**为什么删行**：不删的话，节点会被重新执行并再次 `INSERT`，撞唯一键 `(run_id, node_key, attempt)` → 整单 failed。这个坑真实发生过（多节点续跑必现）。

**顺带修的**：`createNodeShells` 变成幂等（已存在就复用 id），使 `execute()` 对同一 run 可重入 —— `StartupRecovery` 的重放也走这条路。

**放弃**：新建一条新 run 去"接着跑" —— 会丢掉"这次执行"的完整性，且报表里一次实验会变成两条不相干的记录。

**代价**：删行意味着丢失"失败那次"的**未完成节点**及其命令记录（已完成节点的记录保留）。若将来要保留现场，需要在删之前归档。

> 2026-11-03 评审 H1 指出：第一版只删了 `level=0`，而步骤行只靠裸字段 `parent_node_id` 指向业务节点、
> **没有外键**，删不掉；续跑时步骤序号又从 `S1` 重来，撞唯一键后被 catch 成一条 WARN ——
> 结果是"续跑的命令发了、库里没记录"，而所有断言依然全绿。已按上面 2/3 修好，
> 并在 `verify-device-chain.sh` 补 3 条断言钉住（步骤行数 / 命令行数 / 无冲突）。

## D5. 崩溃恢复只列近 7 天，且必须能"忽略"

**背景**：`/api/runs/recoverable` 挂出 41 条，多数是调试时反复重启留下的。更危险的是：**十几天前的单子点"继续"会真的重跑**，而设备状态、板位、配方早变了 —— 那不是恢复，是制造事故。

**选择**：

- 只列 `interruptedAt`（或 `actual_end`）在**近 7 天**内的
- 加 `POST /api/runs/{id}/dismiss`：人判断"这条不该续跑"时显式忽略
- 清理是**改字段**（`input.recoverable=false`），不删记录

**放弃**：一律不许续跑（丢能力）；或一律允许（危险）。7 天是"够用且不至于酿事故"的经验值，可配。

**代价**：7 天窗口内的"设备已拆除"仍需人工 dismiss；这个动作不可撤销（但可以 SQL 改回来）。

## D6. 条件表达式自己写解析器，**不用 eval**

**背景**：BPMN 的 `conditionExpression` 是用户输入。

**选择**：手写递归下降解析器，只认 `比较 / 逻辑 / 括号 / 数字 / 字符串 / ${变量}`。多一个字符就抛异常。

**为什么**：

1. `ScriptEngine` / `eval` 等于把工控机交出去 —— 一条 `Runtime.getRuntime().exec()` 就能打穿整台机器。
2. 需要的表达力很低（温度到了没、板数够没），用不着完整语言。

**失败时的行为**：**不阻断生产** —— 记 `unevaluatedConditionCount` + 日志，然后走 default 边。理由：表达式写错是配置错误，不该让整条产线停；但必须留痕（预检 `PF-09` 也会提前报）。

**放弃**：用现成表达式库（GraalJS/SpEL）—— 依赖重、且默认就带文件/网络访问能力，收窄比自写更难。

**代价**：不支持函数、正则；类型规则要自己定（例如 `'10' > '9'` 按数值比，避免字典序陷阱）。

> 2026-11-03（M7）已补算术：`+ - * /`、括号优先级、一元负号。
> 仍然是纯手写解析器，**没有引入 eval**；字符串参与算术、除以 0 一律抛错（不猜语义）。

## D7. 循环：**图里真有环**才允许重入，且有两道保险

**背景**：`GraphRunner` 用 `done` 集合去重，回边永远不会第二次执行 —— 循环写不出来。

**选择**：

1. 启动时 DFS 判断图里是否有环（`hasCycle`）
2. **只有有环的图**才允许节点重入；无环图维持原去重语义
3. 两道保险：单节点最多 10 圈（`workflow.attr.maxIterations` 可配）、总步数 500

**为什么不无脑允许重入**：并行汇合点会被多条边打到，同一个节点可能被"重复激活"。无脑重入会让设备动作多跑一遍 —— 那是物理副作用（封两次膜、搬两次板）。

**放弃**：用 BPMN 标准的 `standardLoopCharacteristics` —— 存量图里没有，且它表达不了"按条件回退到任意前置节点"。

**代价**：总步数上限是全局猜测值。

> 2026-11-03（M6）已补上"每圈一行"：`run_node.loop_index` 0=汇总行（最终状态）、1..N=每圈实际执行，
> 唯一键改为 `(run_id, node_key, attempt, loop_index)`。既有查询统一加 `loop_index = 0`，
> 等价于改造前；运行详情把圈次行挂在汇总行下面展开。
> **汇总行不是"第 0 圈"**，是"这个节点的最终结果"——这点在文档和代码注释里都写明了。

## D8. 节点输出 → 变量的取值来源

**背景**：循环要"走够次数才退出"，就需要一个会变的变量；静态变量做不到。

**选择**：每次任务成功后，把**设备原始回包**里的字段 merge 进变量表。

两个坑（都是踩出来的）：

1. `run_command` 挂在**步骤节点**（`level=1`，`node_key=S1`）上，业务节点是它的 `parent_node_id`。只按 `node_key=? AND level=0` 查**永远查不到**。
2. `run_command.result` 只有 `{ok,durationMs}`；设备真正的业务字段在 `device_raw_response` 里，且是转义过的 JSON 字符串。

**放弃**：让 `DriverStepExecutor` 把结果回传给 GraphRunner（架构上更干净，但要改执行器签名，风险更大）。当前做法是"多一次小查询"，实测 <1ms/节点。

**代价**：正则抽顶层标量，嵌套/数组取不到；高频节点有额外查询开销。

---

## D9. 循环上限放**流程级**，不放网关级

**选择**：`workflow.attr.maxIterations`（默认 10）。

**为什么**：一个流程里的回边通常不止一条，按网关配会让运维记不清"这条到底受谁管"。放在流程上，一句话能说清。

**代价**：同一流程多条回边共用一个上限。已在技术债里记着（要按网关配，得先给 `GNode` 加属性字段）。

---

## D10. 实验编排（列表）与实验画布（图）是**同一份数据**的两种视图

**背景**：老库 `run_mode` 统计 99.7% 是 `sequential`（记录在 `ExperimentCanvas.tsx` 注释里）。注意当前环境 `experiment_process` 只有 13 行 —— 659 个历史实验只填了 `experiment.workflow_id`，没走新表。

**选择**：两种编辑形态，读写的都是 `experiment_process`（列表）和 `experiment_graph`（画布）。

**为什么**：顺序场景下列表更快、不容易连错；需要分支/并行时才用图。强制所有人都用画布，反而降低效率。

**放弃**：只做画布（重）；只做列表（表达不了并行）。

**代价**：两种视图的一致性要维护（当前列表是"权威"，画布保存时会把节点图写到 `experiment_graph`，两边不自动同步）。

---

## D11. 运行记录的流程图用 **Viewer**（只读），不是 Modeler

**选择**：`bpmn-js/lib/Viewer`。

**为什么**：运行详情是"历史记录"。允许在上面编辑会造成"我改了图，为什么这次执行没变"的误解；更糟的是有人会以为改图能修正在跑的单子。

**代价**：想在运行详情里"基于这次失败改流程"，要多点一次（跳设计器）。

---

## D12. 设备方法落库（`device_method`），且**不删旧方法**

**背景**：界面「详情」读的是 `device_method`，而 `DeviceRegistrar` 原来只写 `device` 行 → 方法列表永远空。

**选择**：入池时把型号库方法 upsert 进 `device_method`；**不删除**型号库里已经没有的方法。

**为什么**：老方法可能被历史流程引用，删掉会让那些流程点开就报"方法不存在"。只增改更安全。

**代价**：型号库删方法后，数据库里会留"孤儿方法"（需要定期人工比对，或加一个"标注 deprecated"字段）。

---

## D13. 心跳阈值可配，且离线阈值跟着间隔走；现在还能**页面改、立即生效**

**背景**：原来是 `10_000L` 常量 + 写死 `30_000L`。问题不只是不能配 —— **改了间隔阈值不跟着变**：
设 60 秒探测一次、30 秒判离线，每台设备每次探测前都先被判一次离线。
后来又发现第二个问题：只能改环境变量再重启 API。现场调"多久没响应算掉线"是日常动作，
重启会打断正在跑的实验。

**选择（两步走）**：

1. 先做可配：`LABOS_HEARTBEAT_INTERVAL_MS`（默认 10s）、`LABOS_OFFLINE_ALERT_MS`（默认 `max(3×间隔, 30s)`），非法值回退默认。
2. 再升级为**运行时配置**：`sys_setting` 持久化 + 进程内静态字段（`RuntimeSettings`），
   心跳线程每个周期读内存，页面保存即生效；离线阈值强制 `≥ 2×间隔`（后端夹紧，不只靠前端提示）。

**放弃**：

- 每次探测都查库 —— 多一次往返，库抖动会拖累心跳；
- 只留环境变量 —— 要重启才生效。

**代价**：

- 配置有两份（库 + 内存），进程内改与库不一致时**以内存为准**，重启后回落到库值（代码注释已写明）；
- 环境变量仍作兜底，两套来源需要在技术文档 §7 集中说明。

## D14. 一个错误码 × 一个作用域 = 一条策略

**背景**：一开始想把"多策略"做成**回退链**（先试 retry，再 reassign…）。

**否决理由**：运行时 `RecoveryPolicyResolver` 是 `specificity → priority` 排序后 **`findFirst`**。同码同作用域的两条策略里，只有 priority 小的会用上，另一条是**死配置**。做成回退链需要改运行时语义，风险大。

**真正的多策略需求**是"同一个码在不同作用域处理不同"：

```
EC-05-1006（通讯失败）
  command → retry ×5     单条重发
  node    → manual ×1    节点层别硬试，叫人
```

**选择**：按 `(error_code_id, scope)` 唯一；界面里按作用域列出，**当前作用域那条加蓝框**。

**代价**：想做"同一作用域多级策略"（retry 3 次后仍失败再换设备）目前做不到 —— 那需要 `reassign` 策略把 scope 匹配写对，属于下一阶段。

## D15. 内置节点用 `protocolName` 的 `__` 前缀，不新增 BPMN 元素

**背景**：流程里要能"算东西"——循环自增、把上游结果整理成条件要用的值。BPMN 没有现成的
"变量节点"，bpmn-js 也不认自定义元素类型（自定义 palette 还要额外维护）。

**选择**：节点仍是 `bpmn:task`，用 `protocolName="__setVar" / "__expr"` 标记为内置；
参数复用 `workflow_node.params->'method_params'`。

**为什么这样最省**：

- 解析器只需加一条判断（`__` 前缀 → `Kind.BUILTIN`），不用改 BPMN 元素模型；
- 设计器能正常打开/保存（属性是普通 XML 属性），不需要自定义 palette；
- 执行器在 `GraphRunner` 里内联算，**不进状态机、不产生设备命令** —— 内置节点没有重试语义。

**失败语义**：表达式算不出来（写错、变量缺失）→ 记 `MANUAL` + `EC-BUILTIN-001` 并**停下**。
不能带着错值继续，否则后面的条件分支会按错值走。

**界面**：设计器右侧「节点设置」卡（设备任务 / 变量节点 / 表达式节点 + 参数），
保存走 `PUT /api/workflows/{id}/nodes/{key}`，服务端**同时**改 `workflow_node.params` 与
XML 里那一个 `protocolName` 属性，然后前端重新导入 XML —— 不碰 bpmn-js 的 modeling。

**代价**：`workflow_node` 没有 `protocol_name` 列（方法原本从 XML 来），所以"这个方法叫什么"
只能看 XML；`builtin=true` 写进 params 便于列表和排查。

## 三、边界：明确不做什么

| 不做 | 理由 |
|---|---|
| 不做线程级并行执行 | 见 D3 |
| 不做 BPMN 全元素（定时器/消息/子流程） | 只做能"把活干完"的子集；解析时忽略，预检里提示 |
| 不在中控做跨实验排程优化 | 见 `docs/多实验并行调度-设计.md` |
| 不做配方/试剂/样本管理 | 表是占位，未接入 |
| 不做多租户强隔离 | `tenant_id` 存在于所有表，但只跑过单租户；不能承诺隔离安全 |
| 不自研前端框架/状态库 | 用 antd + react-query，够用 |

## 四、风险与权衡汇总

| 风险 | 触发条件 | 现在怎么兜 | 残留 |
|---|---|---|---|
