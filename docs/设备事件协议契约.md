# 设备事件协议契约（设备主动上报）

> **状态**：内核与侧车的契约**已立并可跑通**；**真机协议仍缺厂商手册**。
> 本文的作用：把"手册没到之前能做的事"全部做完，把"手册到了要做的事"收敛成
> **一个可插拔的翻译器**，而不是重做一条链。
>
> **适用范围**：所有会**自己主动说话**的设备 —— 例如分盘式核酸提取仪跑到交换点，
> 主动报【等待交互】等上位机换板（客户文档 §1.2 的分段自驱模式）。
>
> **代码落点**：内核 `labos-kernel/src/main/java/com/labos/kernel/event/`、
> `.../boot/web/controller/DeviceEventController.java`；
> 侧车 `sidecar-dotnet/Labos.Sidecar/`（`Protocol` / `ITransport` /
> `ISpontaneousTranslator` / `DeviceEventForwarder` / `SimBridgeTransport`）。

---

## 一、判据（**两侧必须一致，别改单边**）

> **没有 `message_id` 的帧 = 设备主动上报（自发帧）。**
> 有 `message_id` 的帧 = 对某条命令的回包。

| 侧 | 落点 |
|---|---|
| 内核 | `TcpPersistentDriver.dispatch()` —— 没有 id 的帧**不丢**，按自发帧处理 |
| 侧车 | `Protocol.ParseSpontaneous()` / `Protocol.HasMessageId()` |

**为什么必须一致**：判据漂移一次，后果只有两种 ——

- 自发帧被当成回包 ⇒ **丢掉**（现场只看到"流程卡住等不到事件"）；
- 回包被当成自发帧 ⇒ **发到中控**（现场看到流程莫名往前走一步）。

两种现象都极难定位，而且**不会报错**。所以这条规则写进了两侧的注释。

> ⚠ 另一条铁律：**侧车的读侧必须是后台线程**。
> 内核此刻可能正卡在"等这个事件"上，**不会再发命令** ⇒
> 若还按「发命令 → 读一帧回包」的老路走，这条事件永远读不到（**死等**）。
> sim 档已经是这个形态（`SimBridgeTransport` 的读线程 + 两个队列）。

## 二、统一形状（内核只认这一种）

```
POST /api/device-events
{"device":"ID-EXT1","eventType":"waiting_interaction","payload":{"station":"exchange"},"runId":null}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `device` | 否 | 设备码。**解析不出实例号也照样落库** —— 事件比实例号重要，丢了就再也等不到 |
| `eventType` | **是** | 事件类型码（例 `waiting_interaction`） |
| `payload` | 否 | 事件载荷（JSON 对象）。带上下文才有意义："哪块板、哪个工位" |
| `runId` | 否 | 能关联到哪条 run 就填 |

**鉴权**：sidecar 没有中控账号 ⇒ 该端点与 `/api/devices/registry` 同档**免鉴权**（内网口径）。
装了 `LABOS_DEVICE_EVENT_TOKEN` 时，校验 `X-Labos-Device-Token`，对不上直接 401。

> 为什么要"翻译"这一层：设备协议千差万别，**中控不该在 HTTP 层猜设备的协议**。
> 谁把设备的原始报文翻译成这个形状，是**适配层**的活 —— 也就是侧车。

## 三、按型号翻译（**接真机时唯一要改的地方**）

判据是通用的，但**「怎么把这一帧读成 设备码/事件类型/载荷」是型号专属的**。
所以侧车留了一个扩展点：

```csharp
public interface ISpontaneousTranslator
{
    string ModelId { get; }                              // 型号库 id，如 aspin-2k / s100
    Protocol.SpontaneousFrame? Translate(string raw);   // 不认识 ⇒ 返回 null（不是错误）
}
```

登记（`SpontaneousTranslators.Register`）后自动生效；**没登记的型号回退通用 JSON 翻译器**
（模拟器走的就是它）。

### 手册到了怎么接（照这个单子做）

1. **读手册**，找出三件事：
   - 自发帧长什么样（XML？定长二进制？JSON？头尾字节是什么？）
   - 里面哪几个字段对应「设备码 / 事件类型 / 载荷」
   - 事件类型码的**取值表**（`waiting_interaction` 在这台设备上叫什么）
2. **写一个 `ISpontaneousTranslator`**：`Translate(raw)` 里把这三样抽出来，返回
   `new SpontaneousFrame(equipmentId, eventType, payloadJson)`。
   - 抽不出设备码 ⇒ 返回 null（**不认领**：发出去也没人认）
   - 未知事件码 ⇒ 返回 null（**不猜**）
   - **不得抛异常**（翻译失败只是"不认识这一帧"，不能把命令下发也带崩）
3. **注册**：`SpontaneousTranslators.Register(new XxxTranslator())`。
4. **如果这台设备的自发帧是"凭空冒出来"的**（不是对命令的回应），
   还要给它的传输档加一个**后台读线程**（照 `SimBridgeTransport` 的形态）：
   `ITransport.TryDequeueSpontaneous` 现在是接口默认实现（返回 false），
   串口/dll 档都还没做这一步。
5. **验收**：照 `scripts/test-sidecar-device-event.sh` 的样子写一条该型号的用例
   （桩服务顶替中控，落盘断言形状）。

> 第 4 步是**唯一可能动到命令路径**的一步 ⇒ 改完必须跑
> `scripts/test-sidecar.sh`（全链路 7/0）确认命令下发没被改坏。

## 四、**模拟的**厂商风格帧（手册没到时的样子）

> ⚠ **下面两种帧形状都是"编的"，不对应任何真机。**
> 它们的作用是：**证明按型号翻译这个扩展点真的能用**，
> 以及给拿到手册的人一个"要抽哪三样"的对照。
> 真机来了，按 §三 的单子重写即可。

### 4.1 XML 风格（照"XML 型设备"编 —— ASpin 2K 经 Cluster.dll 走的正是 XML）

```xml
<DeviceFrame>
  <EquipmentId>ID-ASPIN</EquipmentId>
  <EventType>plate_detected</EventType>
  <Payload><Slot>2</Slot><Plate>PL001</Plate></Payload>
</DeviceFrame>
```

⇒ 统一形状：

```json
{"device":"ID-ASPIN","eventType":"plate_detected",
 "payload":{"Slot":"2","Plate":"PL001"}}
```

参考实现：`SampleXmlSpontaneousTranslator`（**仅自测用，不注册进生产**）。

### 4.2 定长二进制风格（照"二进制定长帧设备"编 —— S100 串口就是 0xAA 起 0xFF 尾）

```
AA F0 <eventCode> <len> <payload…> FF
```

其中 payload = `设备码|自由文本`，事件码表（模拟）：`01=idle` / `02=plate_detected` / `03=process_done`。

⇒ 统一形状：

```json
{"device":"ID-CELL1","eventType":"plate_detected","payload":{"detail":"slot=3"}}
```

参考实现：`SampleBinarySpontaneousTranslator`（**仅自测用，不注册进生产**）。

### 4.3 通用 JSON 风格（模拟器走的就是这条，真实设备若也是 JSON 可直接用）

```json
{"message_type":6,"equipment_id":"ID-EXT1","event_type":"waiting_interaction",
 "data":{"station":"exchange"},"timestamp":"...","checksum":"","connected":1}
```
