# 设备事件协议契约（设备主动上报）

> **状态**：P0 可靠投递、幂等入库、原子消费和等待恢复已进入代码；真机帧格式仍以厂商手册为准。
> 本文约定设备、侧车与内核之间的边界，避免“命令已经出队，但事件其实丢了”的静默故障。
>
> 代码落点：内核 `labos-kernel/src/main/java/com/labos/kernel/event/`、
> `.../boot/web/controller/DeviceEventController.java`；侧车
> `sidecar-dotnet/Labos.Sidecar/DeviceEventOutbox.cs`、`DeviceEventForwarder.cs` 及翻译器。

---

## 一、帧判据与责任边界

侧车采用：**没有 `message_id` 的帧 = 设备主动上报；有 `message_id` = 命令回包。**

| 侧 | 当前责任 |
|---|---|
| 侧车 | 后台读自发帧，按型号翻译，先写磁盘 outbox，再转发 HTTP |
| 内核 HTTP 入站 | 校验设备令牌，按 `sourceEventId` 幂等写入 `device_event` |
| 内核等待节点 | 使用 run 持久游标，在数据库内原子认领一条事件 |

> **当前限制**：`TcpPersistentDriver` 的内核直连路径仍会丢弃无 `message_id` 帧。
> 本轮没有把 TCP 命令路径改成另一套分发机制；可靠主动事件走侧车通道。
> 若未来启用内核直连自发帧，必须另改该路径并补命令回包/自发帧混流测试。

侧车读侧必须是后台线程：内核可能正等这个事件、不会再发命令；若只在命令响应时读设备，就会形成死等。

## 二、统一 HTTP 形状与鉴权

```http
POST /api/device-events
X-Labos-Device-Token: <LABOS_DEVICE_EVENT_TOKEN>
Content-Type: application/json
```

```json
{
  "sourceEventId": "5a1a0fa6-baa0-4f2d-9d65-0f2e72106c21",
  "device": "ID-EXT1",
  "eventType": "waiting_interaction",
  "payload": {"station": "exchange"},
  "runId": null,
  "processId": "optional-process-id",
  "interactionStep": "optional-step-id"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `sourceEventId` | 侧车必发 | 首次接帧生成 GUID；落盘、重试、重启恢复均不改变 |
| `device` | 否 | 设备码；解析不出实例号也保留事件 |
| `eventType` | **是** | 如 `waiting_interaction` / `process_done` / `fault` |
| `payload` | 否 | JSON 载荷；空或非法时数据库兜底为 `{}` |
| `runId` | 否 | 上报时能确定才填；消费不依赖它预先绑定 run |
| `processId` / `interactionStep` | 否 | 后续精确工位/交互步骤匹配使用，本阶段只保存 |

鉴权规则：

- 生产必须配置 `LABOS_DEVICE_EVENT_TOKEN`，侧车通过 `X-Labos-Device-Token` 携带。
- 未配置令牌时默认返回 503，不开放匿名写入。
- 仅本机联调可显式设置 `LABOS_DEVICE_EVENT_ALLOW_ANONYMOUS=1`。
- 只有 POST 走独立设备令牌；`GET /api/device-events` 是观测接口，在启用账号鉴权时必须登录。
- 重复 `sourceEventId` 返回首次落库的事件 id，不新增第二条；HTTP 2xx 表示“已持久化或此前已持久化”。

## 三、侧车磁盘 outbox：失败不丢、重启可补发

处理顺序固定为：

1. 从传输自发帧队列取出一帧并翻译。
2. 生成 `sourceEventId`，把完整 HTTP 请求体写到同目录临时文件。
3. 文件写完并 flush 后原子改名为 `<sourceEventId>.json`，接帧线程此时才继续。
4. 唯一后台泵按落盘顺序串行发送；复用同一个静态 `HttpClient`。
5. **只有收到 2xx 才删除文件**。网络异常、超时、401/500 等非 2xx 都保留文件并在一秒后重试。
6. 进程启动后后台泵自动加载现有 `*.json`，继续使用文件内原 `sourceEventId` 补发。

因此，中控已提交但响应丢失、或侧车在删除文件前退出，都可能导致一次**重复投递**；数据库幂等键负责把它收敛为一条事件。语义是“至少一次投递 + 幂等入库”，不是依赖运气的“只发一次”。

目录配置（优先级从高到低）：

- `--device-event-outbox <目录>`
- `LABOS_DEVICE_EVENT_OUTBOX`
- 默认：用户本地应用数据目录下 `Labos/sidecar/device-event-outbox/<设备>-<监听端口>`

默认路径按设备与端口隔离。显式指定目录时，部署方必须保证不同 sidecar 实例不共用目录。

## 四、数据库幂等与原子认领

迁移：`pg_rebuild/migration/20261115_device_event.sql`，可重复执行；全量建库产物由 `pg_rebuild/schema/merge.sh` 拼入同一迁移。

三张表分别承担不同职责：

- `device_event`：原始事件与载荷；部分唯一索引
  `(tenant_id, device_code, source_event_id) WHERE source_event_id IS NOT NULL` 防重复。
- `device_event_run_cursor`：`(tenant_id, run_id)` 保存 `base_event_id`。
- `device_event_consumption`：`event_id` 主键保证事件全局只能被一个等待者消费；
  `(tenant_id, run_id, node_key, loop_index)` 唯一键标识等待者。

`MapperDeviceEventSource.claim()` 使用一条 PostgreSQL CTE：

1. 先查当前等待者是否已有消费记录；有则返回同一事件，支持崩溃/暂停后的重入。
2. 否则从该 run 基准之后选择最早、匹配设备与类型、尚未消费的事件。
3. 候选行使用 `FOR UPDATE SKIP LOCKED`，插入消费关系并更新 `dispatched_at/attempts`。
4. 并发唯一键冲突时本次返回空，下一轮再读，不返回重复事件。

历史上已设置 `dispatched_at`、但没有新消费关系的事件也不会被重新认领。

### run 游标与重启语义

- 含 `__awaitEvent` 的 run 第一次执行时，把当时 `MAX(device_event.id)` 持久化。
- 续跑不重新取最大值；进程停机期间到达的事件仍位于旧基准之后，恢复后能看到。
- 基准之前的历史存量不自动变成新事件。
- 无环节点 `loop_index=0`；真正回环上的节点使用当前 `visit`，同一节点不同圈不会误读上一圈的认领记录。
- 数据库读取/认领连续失败 3 次会明确失败并转人工；不再无限忽略到等待超时。

## 五、按型号翻译（厂商手册到达后的扩展点）

```csharp
public interface ISpontaneousTranslator
{
    string ModelId { get; }
    Protocol.SpontaneousFrame? Translate(string raw);
}
```

登记 `SpontaneousTranslators.Register(...)` 后按型号生效；未登记型号回退通用 JSON 翻译器。

接真机时需要：

1. 从手册确认自发帧格式、设备码字段、事件码表和载荷字段。
2. 实现型号翻译器；抽不出设备码或遇到未知事件码时返回 null，不猜、不抛异常。
3. 注册翻译器。
4. 若设备会凭空推帧，为该传输档实现后台读线程和 `ITransport.TryDequeueSpontaneous`。
5. 增加该型号的模拟帧端到端用例；若改了命令路径，必须同时回归 `scripts/test-sidecar.sh`。

### 通用 JSON 示例

```json
{"message_type":6,"equipment_id":"ID-EXT1","event_type":"waiting_interaction",
 "data":{"station":"exchange"},"timestamp":"...","checksum":"","connected":1}
```

XML 和定长二进制样例仍在 `DeviceEventSelfTest.cs`，仅用于证明扩展点可用，**不代表任何真机协议**。
