## 0. 结论摘要

本轮设计已明确并行执行、逻辑操作身份、设备事件归属和失败收尾的主要方向，但当前文档仍有几处会直接影响安全性的语义缺口或跨文档矛盾。

**阻断实现的 P0：**

1. `device_physical_hold` 在 ACK 后才建立，存在命令已被设备受理但中控尚未登记占用的竞态窗口；中控标记本身也不能阻止绕过中控的外部命令。
2. 设备事件 SQL 仍允许 NULL 与 NULL/预期值走匹配路径，与“事件归属只认 commandId、无弱匹配”冲突。
3. `commandId` 的生成示例没有覆盖 branch、invocation、generation，无法证明同一 Run 中并发操作及人工重新执行时唯一。
4. 表设计 L-14 对非去重设备 resume 重新生成 `command_id`，与“逻辑操作身份稳定、重试复用、非去重设备禁止自动重试”冲突。
5. “不回显 commandId 的设备独占串行”被写成降级方案，但独占串行不能证明迟到事件属于当前命令。
6. GraphRunner 分支共享流程变量不能仅靠把 `LinkedHashMap` 换成 `ConcurrentHashMap`；当前复制式初始化 API 可能使各分支实际持有不同 Map。

**需要补证据的 P1：**

- 全量已发布流程定义扫描，验证 E-16 是否会拒绝现有合法流程。
- 现场设备 BUSY 持续时长分布，验证 15 分钟资源等待期限的运维影响。
- 设备是否存在绕过中控的第二命令入口。
- 设备租约重启恢复、ACK 丢失、迟到完成事件、重复释放等场景的验收设计。

**未来架构约束 P2：**

- 当前单实例边界可以保留；未来多实例应采用数据库设备级租约作为原子仲裁，并结合 epoch/fencing 防止旧持有者继续派发。当前不要求实施。

## 1. 对已确定业务决策的遵循

以下决策视为已定，本评审不重新讨论其业务选择，只检查文档是否一致落实：

1. `commandId` 是一次逻辑操作的唯一标识；重试复用，重新执行换新。
2. 设备忙：先查状态；busy 时释放锁，等待 1 分钟后重查；总等待上限 15 分钟。
3. 模拟器增加“受理即返回”开关：立即 ACK，经过 N 秒再返回 result。
4. 事件归属只认 `commandId`，不允许弱匹配；不回显的设备独占串行。
5. 事实源缺失 fail-open；已采集但状态不确定 fail-closed。

本文提出的修订均以保持这些决策为前提，不将它们重新开放为产品决策。

## 2. P0-1：设备物理占用必须在派发前取得，不能在 ACK 后才建立

### 现有问题

并行网关设计中的第四方案以中控侧 `device_physical_hold` 记录设备在命令执行期间的占用。当前叙述顺序是设备锁（step 粒度）→ 命令下发 → 设备 ACK → 建立 hold → 完成事件 → 清除 hold。

这存在一个真实竞态：

1. Run A 发出命令；
2. 设备已经受理命令，但 ACK 尚未到达中控；
3. 中控尚未建立 hold；
4. Run B 查询不到 hold，可能再次向同一设备派发命令。

因此，“ACK 到达后建立 hold”不能覆盖命令受理到 ACK 入站之间的窗口。

另一个边界是：中控侧 hold 只记录中控已知的占用事实，不能阻止厂商工具、人工客户端或其他服务绕过中控直接向设备下命令。若设备自身不支持 busy 拒绝或命令互斥，中控无法单方面保证物理设备绝不会同时执行两条命令。

### 建议修订

将第四方案拆成两个概念，避免把程序态记录误称为物理互斥：

- **设备派发租约（dispatch lease）**：派发前原子取得，是中控唯一命令入口的准入凭据。
- **设备占用账本（physical occupancy record）**：记录命令已派发/已受理/执行中/结果未知等生命周期事实；不代表设备真实物理状态已被传感器证明。

建议状态至少包括：

`RESERVED → ACCEPTED → EXECUTING → RELEASED`

异常路径需要：

- 派发前已取得租约但尚未发命令：可按明确的取消证据释放；
- 命令可能已发出但 ACK 丢失：进入 `UNKNOWN`，不得因超时自动释放；
- 完成事件或可靠查询证明该操作完成：才允许释放；
- 迟到的旧命令事件不得释放后来取得的新租约。

建议最小字段：

- `device_id`
- `lease_id`
- `owner_command_id`
- `owner_run_id`
- `owner_branch_id`
- `owner_operation_id`
- `state`
- `acquired_at` / `accepted_at` / `released_at`
- `release_evidence`

唯一命令入口必须在实际派发前校验并持有该租约。若存在其他可绕过入口，应明确列为不具备自动并行资格的设备/部署条件。

### 设备能力边界

| 等级 | 条件 | 可承诺的保证 |
|---|---|---|
| G1 | 所有命令都经过中控唯一入口，入口强制校验设备租约 | 可保证中控内部单设备单命令准入 |
| G2 | 设备另有 busy 拒绝、队列互斥或等效原生保护 | 可进一步获得设备侧互斥保障 |
| G3 | 外部入口可绕过中控，且设备不拒绝并发命令 | 不能保证物理互斥；不得纳入自动并行 |

### 必须补充的验收场景

1. 租约已取得、命令尚未派发时，其他 Run 不得派发。
2. 设备已受理但 ACK 未到时，其他 Run 不得派发。
3. ACK 丢失但命令可能已执行时，租约进入 UNKNOWN，不自动释放。
4. 服务重启后可恢复未释放租约，不能把“内存状态丢失”当作设备空闲。
5. 旧 commandId 的迟到完成事件不能释放新 commandId 的租约。
6. 外部命令入口被发现时，设备并行资格应被撤销或降级，并产生审计记录。

**评审结论：当前 ACK 后建立 hold 的定义不通过。保留第四方案方向，但改为派发前原子租约 + 生命周期占用账本，并明确唯一命令入口及 G1/G2/G3 能力边界。**

## 3. P0-2：SQL 必须落实严格 commandId 匹配，NULL 不能成为匹配条件

### 发现位置

设备命令与事件关联规范 §4.3 存在如下条件：

```sql
AND (e.command_id IS NULL OR e.command_id = #{expectedCommandId})
```

表设计 §2.4 存在同类条件：

```sql
AND (w.expect_command_id IS NULL OR w.expect_command_id = ?)
```

这两处都允许缺少 commandId 的事件或 waiter 进入候选匹配路径，与“事件归属只认 commandId，无弱匹配”不一致。特别是 NULL 分支可能使无标识事件被当前 waiter 接收，重新引入已明确删除的弱匹配。

### 建议修订

所有命令关联型事件的匹配必须显式要求双方 commandId 非空且相等：

```sql
AND w.expect_command_id IS NOT NULL
AND e.command_id IS NOT NULL
AND w.expect_command_id = e.command_id
```

同时保留设备、租户、事件类型、waiter 有效状态、未认领/唯一认领等必要约束。不能用“当前只有一个 waiter”“设备当前只有一个占用者”替代 commandId 等值匹配。

应对整个仓库和所有四份设计全文检索以下模式并逐项审查：

- `command_id IS NULL OR`
- `expect_command_id IS NULL OR`
- “唯一 waiter 即可匹配”
- “无 commandId 时按当前占用者匹配”
- “弱匹配（若开启）”

**评审结论：P0。必须清除所有允许 NULL 参与事件归属的 SQL 和文字口径。**

## 4. P0-3：commandId 应直接绑定持久化逻辑操作身份

### 发现

表设计的 `operation_key` 已包含 branch、loop、invocation 等维度；但设备命令规范 §2.2 的 commandId 示例生成公式未体现 branch、invocation、generation 等维度。

这会产生至少两类风险：

1. 同一 Run 的两个 branch 若执行相同 node/step/device 组合，可能生成相同 commandId。
2. 人工重新执行时 generation 增加，但若生成公式不包含 generation，无法保证新执行获得新 commandId。

不能依赖随机拼接字符串或各文档分别定义一套公式来解决身份一致性。

### 建议修订

优先采用单一权威映射：

- 每次逻辑操作创建持久化唯一的 `operation_id`；
- `commandId` 与该 `operation_id` 一一对应（可直接使用其稳定编码）；
- retry/resume 继续引用原 `operation_id` 和 commandId；
- 新的独立物理操作创建新 `operation_id` 和 commandId；
- branch、loop、invocation、generation 用于 operation 的唯一创建键/审计维度，不由多个模块各自拼 commandId。

如果决定不直接映射 operation_id，则生成规则必须显式覆盖 run、branch、node、step、loop、invocation、generation，并通过唯一约束兜底。但不建议采用多处各自拼接的方式。

### 人工拆分语义

一次逻辑操作被人工拆成两次独立物理执行时，应视为创建两个新的逻辑操作，而不是同一操作的重试：

- 原 operation 保留拆分/取消/替代关系；
- 两个子操作分别创建新的 operation_id 和 commandId；
- 建议记录 `parent_operation_id`、`split_reason`、`split_by`、`split_at`；
- 两个子操作分别完成后，再按显式聚合规则决定父操作状态。

例如 `Transfer(A→D)` 被拆成 `Transfer(A→B)` 与 `Transfer(B→D)`，两个子动作都可能产生独立物理副作用，不能共用 commandId，否则设备幂等去重可能把第二条误认为第一条重发。

规则边界：

| 场景 | commandId |
|---|---|
| 网络重发、断线重连、resume 原动作 | 复用 |
| 原动作暂停后继续，设备确认仍是同一动作 | 复用 |
| 人工重跑/重新执行 | 新建 |
| 一次操作拆成两个独立物理动作 | 两个子操作分别新建 |
| 循环下一轮/换批次形成新动作 | 新建 |

**评审结论：P0。建议 commandId 直接映射持久化 operation_id；补齐人工拆分规则。**

## 5. P0-4：非去重设备 resume 不得通过换 commandId 自动重发

### 发现

表设计 L-14 对非去重设备的 resume 重发提出重新生成 `command_id`。这与以下既定规则冲突：

- commandId 是逻辑操作级唯一标识，重试复用；
- 不支持去重的设备禁止自动重试；
- 设备命令规范已明确非去重设备不允许自动重试，commandId 保持稳定。

重新生成 commandId 并不能让不确定的旧命令变得安全，反而可能让设备把重复物理动作当成一条新命令执行。

### 建议修订

非去重设备在命令结果不确定时：

1. resume 不自动重发；
2. 保留原 commandId 和原 operation 身份；
3. 先通过可靠状态查询/设备侧查询确认原动作是否完成；
4. 若无法确认，转人工处置，保持资源占用或 UNKNOWN 状态；
5. 只有人工明确决定创建一个新的物理动作时，才创建新 operation_id 和新 commandId，并记录其与旧操作的关系。

**评审结论：P0。删除 L-14 中“非去重设备 resume 重新生成 command_id”的规则。**

## 6. P0-5：不回显 commandId 的独占串行不等于事件归属

### 发现

设备命令规范 §7.2 明确无 commandId 的事件不匹配任何 waiter；但表设计 §2.5 又将“不回显 commandId 的设备降级为独占串行”，并描述由当前占用者唯一确定。

独占串行只能减少中控主动并发派发，不能证明某条无 commandId 事件属于当前操作。例如：

- 上一条命令的迟到事件可能在下一条命令已成为唯一占用者后到达；
- 外部入口可能产生未被中控登记的事件；
- 设备内部缓存/重放可能导致旧事件延迟上报。

因此，“当前只有一个占用者”不构成事件来源证明。

### 建议修订

明确区分：

- **调度互斥**：不回显 commandId 的设备在中控侧独占串行，不允许并行派发。
- **事件归属**：无 commandId 的自发事件不能自动推进任何 commandId waiter。

这类设备只有在以下条件之一满足时才能安全推进：

1. 设备提供与当前命令严格关联的同步返回结果，且协议能证明结果对应本次请求；
2. 设备提供可靠状态查询，查询结果能确认该逻辑操作已完成；
3. 设备协议增加 commandId 回显。

仅有“唯一 waiter/唯一占用者”不满足条件。无法获得可靠同步结果或状态查询时，必须转人工确认，不得自动将无标识事件归属到当前命令。

**评审结论：P0。保留独占串行作为调度降级，但明确它不是事件归属机制。**

## 7. P0-6：GraphRunner 必须共享同一个 FlowExecutionContext，而非只替换 Map 类型

### 发现

改造点 1+2 采用每个分支一个 GraphRunner 实例。流程变量又要求流程级共享。当前文档给出的 `withVariables(Map)` 实现示例使用类似：

```java
this.variables = new LinkedHashMap<>(vars);
```

这属于复制式初始化。即使调用方传入同一个 ConcurrentHashMap，每个分支 runner 仍可能各自复制成独立 Map，实际没有共享。

即使真的共享同一个 ConcurrentHashMap，它也只提供容器层面的并发安全，不自动提供业务层复合操作原子性、写冲突语义或确定的执行顺序。

### 建议修订

引入明确的流程执行上下文，例如：

```java
final class FlowExecutionContext {
    final FlowVariableStore variables;
    final ConsumedValueStore consumedValues;
    final EventCursorStore eventCursors;
    final AbortSignal abortSignal;
}
```

每个分支 GraphRunner 接收并持有同一个 FlowExecutionContext 引用。需要明确区分：

- `withVariablesCopy(...)`：复制式初始化，仅用于建立初始值；
- `withExecutionContext(context)`：共享同一上下文引用，不得复制其内部 store。

变量并发契约建议：

| 操作 | 规则 |
|---|---|
| 多分支并发读取 | 允许 |
| 不同分支写不同 key | 允许，必须保证可见性 |
| 多分支写同一 key | 编译期拒绝（沿用既定决策） |
| 读-改-写同一 key | 必须有明确原子操作语义，否则禁止 |
| join 后聚合写入 | 由 join 后主执行流执行，或使用显式聚合规则 |

不要把 GraphRunner 的所有实例字段一律换成 ConcurrentHashMap。应逐项确定共享范围和所有权：

- variables：流程级共享 Store；
- consumedValues：明确跨分支去重范围；
- eventCursors：单调推进，不允许较小游标覆盖较大游标；
- visits/done：分支局部状态；
- progress.aborted：原子停止信号/明确同步协议。

### 必须补充的测试

1. 两个 Runner 确认持有同一个 FlowExecutionContext 和同一个 VariableStore 实例。
2. 两分支并发写不同 key，写入均完整可见。
3. 同名 key 写入在编译期被拒绝。
4. 读改写不会静默丢更新，或编译/运行契约明确禁止该用法。
5. 循环、嵌套并行、resume 后共享上下文语义稳定。

**评审结论：P0。不能只把 LinkedHashMap 替换为 ConcurrentHashMap；必须定义并实现共享上下文及变量访问契约。**

## 8. P1：E-16 必须先用现有流程定义做兼容性扫描

### 问题

E-16 要求并行分支子图互不相交，理由是多个 Runner 对同一个静态节点可能产生 `run_node` 唯一键冲突。但归档 §9 问的是“现有流程是否有两个分支经过同一节点的合法场景”。

当前评审材料没有提供完整的已发布流程定义清单及其拓扑，因此不能据此断言现有流程不存在该情况。

需要区分三种图形：

1. **分支在 join 后共享下游节点**：这是常见合法结构。共享下游节点应属于 join 后主执行流，只执行一次，不应计入两个分支的子图交集。
2. **两个分支在 join 前可达同一个静态节点**：执行一次还是每个分支各执行一次，语义不明确；若各执行一次，当前 run_node 唯一键缺少 branch/invocation 维度，可能冲突。
3. **显式共享节点**：若产品确实需要，应定义节点实例身份、执行次数、状态归属和恢复语义，不能仅放宽 E-16。

### 建议处置

将 E-16 改为更精确的规则：

> 两个并行分支在 join 前共享同一个静态执行节点时，若流程定义没有显式声明共享节点的执行语义及独立执行实例身份，则编译期报错。join 后共同下游节点归属 join 后主执行流，不计入分支子图交集。

### 兼容性扫描要求

对所有已发布流程定义：

1. 枚举每个 `SPLIT_PARALLEL` 与对应 join；
2. 计算每个 branch 在 join 前的可达节点集合；
3. 求两两交集；
4. 将交集分类为 join 后共同下游、join 前共享静态节点、拓扑/配对异常；
5. 输出流程 ID、版本、split/join ID、交集节点和处置结论。

在扫描结果出来前，不得宣称 E-16 已证明兼容现有流程。

**评审结论：E-16 可保留为保守约束，但现有流程兼容性为 UNKNOWN，必须扫描后才能关闭该风险。**

## 9. P1：1 分钟 / 15 分钟策略是资源等待期限，不是设备执行时长上限

### 判断

当前材料没有提供现场 BUSY 持续时长分布，无法证明 15 分钟覆盖现场设备的最长忙时。文档中提到的孵育 30 分钟、离心 20 分钟方法，若设备 BUSY 状态覆盖整个执行周期，则 15 分钟可能短于正常执行时间。

不因此重开已确定的 1 分钟轮询和 15 分钟上限，但必须把语义写清楚：

- 15 分钟是**请求方等待获取设备资源的期限**；
- 不是当前设备执行动作的最长允许时长；
- Run B 等待设备 A 时，B 可在 15 分钟后进入资源等待超时/人工处置；
- A 的执行和设备租约不因 B 超时而释放或取消；
- B 的等待超时不得误操作 A 的设备占用状态。

### 建议采集的数据

按设备型号、设备实例、方法/命令类型至少采集两周：

- `busy_duration_p50`
- `busy_duration_p95`
- `busy_duration_p99`
- `busy_duration_max`
- `resource_wait_duration`
- `busy_reject_count`
- `poll_count_per_acquisition`

将“设备执行 BUSY 时长”和“请求方资源等待时长”分开统计。现场数据不足时，15 分钟只能标记为初始运维参数，不能写成经验证的现场上限。

**评审结论：策略可暂时保留；参数合理性尚无现场证据。**

## 10. P2：未来多实例采用 DB 设备级租约 + epoch fencing

当前单实例部署边界可以接受，但 R-11 应避免给人以“未来只要把锁移到数据库就够了”的印象。

未来多实例时：

- 数据库设备级租约负责跨实例原子仲裁；
- 租约按 `(tenant_id, device_id)` 维度唯一；
- 记录 `lease_id`、`owner_run_id`、`owner_branch_id`、`owner_operation_id`、`lease_epoch`、状态和过期时间；
- renew/release 必须校验 `lease_id + lease_epoch`；
- 唯一派发网关必须校验当前 epoch。

DB fencing 只能阻止旧实例更新数据库，不能自动阻止旧实例向物理设备发送命令。若设备或设备侧代理不校验 epoch，仍需确保命令派发只能经过能校验当前租约的唯一网关。

因此 DB 租约与 epoch 不是二选一：前者负责仲裁，后者负责拒绝过期持有者。当前阶段不要求实现，但应列为多实例化的前置架构条件。

## 12. 验收门槛与评审状态

- [ ] 设备租约在命令派发前原子取得，ACK 丢失进入 UNKNOWN，不自动释放。

P1 项可以在实现准备阶段并行补证据，但 E-16 的现有流程兼容性扫描应在确定编译期拒绝规则前完成。

### 最终结论

**有条件通过设计方向，暂不批准进入实现。**

这里的“暂不批准”不是否定并行执行方案，而是要求先消除上述身份、派发互斥、事件归属和共享状态的 P0 歧义。否则实现即使通过普通模拟器测试，也可能在 ACK 延迟、设备忙、迟到事件、resume 或分支并发写入时产生错误的物理动作或状态归属。
