## 0. 一句话

现有 10 条执行入口，只有 4 条经过调度器。但**"统一调度"和"统一准入"是两件事**：前者会改变响应语义，后者不会。第一步只做后者——在唯一收口点加一道门禁，让任何入口都绕不过去，但 HTTP 行为保持完全不变。

## 2. 关键区分：统一准入 vs 统一调度

这是本清单最重要的设计判断，必须先说清，否则改造会失控。

| 维度 | 统一准入 | 统一调度 |
|---|---|---|
| 做什么 | 所有入口在创建/激活 run 前，过同一道三态判定 | 所有入口都改成"建 queued run + 交给 scheduler" |
| 改变 HTTP 响应吗 | **不改变**（阻断时沿用现有 JSON 形状，见 §4.2） | **改变**（同步入口会从"返回结果"变成"返回 runId"） |
| 能否算纯重构 | 能 | **不能** |
| 覆盖"双 active"吗 | 能 | 能 |
| 需要的工期 | 小 | 大 |

**E-01 / E-03 是同步阻塞接口**，响应体里有 `totalSteps` / `doneSteps` / `batches`（`ExperimentActionController:505-512`）。改成异步提交，这些字段会变空。**这不是重构，是破坏契约。**

所以：

- **第一步（本文档）**：只做统一准入，HTTP 行为零变化
- **第二步（另开）**：再讨论要不要把同步入口改成异步，那需要产品确认

## 3. 收口点选择

### 3.1 三个候选

| 候选 | 位置 | 覆盖面 | 问题 |
|---|---|---|---|
| A | `WorkflowService.execute` | 所有执行（同步 / 异步 worker / runAll / runBatch） | `startAsync` 先 `createRun` 再提交 worker，门禁若在 execute 内，判定时 run 已存在 → 只能判"续跑"，判不到"另一个请求正在创建" |
| B | `WorkflowService.createRun` | 所有新建 run | resume 不经过 createRun → 漏掉 E-09 |
| C | **新增 `GuardedStart` 服务** | 全部 | 要改 5 个调用点，但每处改动小、语义清晰 |

### 3.2 推荐 C，理由

把"准入 + 创建 + 状态写入 + 提交"收进一个方法，任何入口都必须调它。

**v2 修正（重要）**：v1 的伪代码把 `gate.check` 放在事务**外**，但注释写"同一个数据库事务内：检查 + 插入" —— **注释与代码不符**，照抄即错（两个请求同时 `check` 都通过，然后都插入，等于没修）。**v2 把判定移进事务**：

```java
// 伪代码（v2）
GuardedStart.Result start(StartRequest req) {
    return inTransaction(c -> {
        // ① 三态准入（含 excludeSelf 语义）—— 必须在事务内，与写入原子
        Decision d = gate.checkInTx(c, tenant, workflow, req.excludeRunId());
        if (!d.allowed()) {
            rollbackOnly();
            return Result.rejected(d);
        }

        // ② 同一事务内写入
        long runId = req.isResume()
            ? resumeInTx(c, req)      // UPDATE 带原状态守卫
            : createRunInTx(c, req);  // INSERT
        return Result.accepted(runId);
    });
}
```

**为什么必须"准入 + 插入"同一事务**：现在的 `WorkflowWebService` 预检在 `execute` 之前，中间有窗口——两个请求同时查不到 active，都会放行，然后都插入。只加门禁不改事务边界，等于没修。

> 若 `gate.check` 因实现原因无法进事务（例如它用独立连接），则必须**由 §3.3 第 3 层的唯一索引兜底**，并把 §3.3 第 2 层的描述改为"事务内不再复查，靠索引拒绝"——**注释必须与代码一致**。

### 3.3 三层防护（都不依赖内存锁）

| 层 | 机制 | 作用 |
|---|---|---|
| 1 | 应用层三态准入 | 快速否定、给出明确错误码 |
| 2 | 数据库事务（同连接） | 检查与写入原子 |
| 3 | **唯一索引兜底** | 任何漏改的入口也会被数据库拒绝 |

第 3 层是"就算有人写新入口忘了调 GuardedStart，也炸不出来"的保证。没有它，所有论证都依赖"我们记得改全"。

**第 3 层的 active 集合必须显式定义（v2 修正）**：

```sql
-- active 集合 = ('queued','running','paused')，**排除 'quarantined'**
ALTER TABLE run ADD COLUMN active_slot smallint;
CREATE UNIQUE INDEX uk_run_active
  ON run (tenant_id, workflow_id, active_slot)
  WHERE active_slot IS NOT NULL;
```

为什么排除 `quarantined`：`quarantined`（"隔离待确认"）在 `StatusVocabulary:127` 是 `terminal=false` **且** `active=true` ⇒ 若计入 active 集合，**一个被隔离的 run 会永久占住该 workflow 的唯一名额**，导致该流程在隔离解除前无法启动任何新 run。

另注：若要支持"同 workflow 最多 N 个并发"，把 `active_slot` 改为"该 workflow 当前第几个 active run"（取值 1..N）即可天然支持，无需 allow 开关。

## 4. 逐条改造

### 4.1 E-01 同步单流程

| 项 | 内容 |
|---|---|
| 现状 | `WorkflowController:257` → `WorkflowWebService.run` → 消费 `Decision.allowed()` → `execute` |
| 改成 | `WorkflowWebService.run` 内改调 `GuardedStart.start(...)`，预检与插入合并进同一事务 |
| HTTP 行为 | **不变**（仍同步返回结果；阻断时沿用现有 JSON 形状） |
| 风险 | 低。`run` 的响应形状不变 |
| 验证 | 现有 workflow 回归集全绿；`EC-WORKFLOW-RUNNING` 兼容性测试 |

### 4.2 E-02 异步单流程（最需要改的一条）

| 项 | 内容 |
|---|---|
| 现状 | `WorkflowController:222-223` 直接 `workflows.startAsync`，无任何门禁 |
| 改成 | `startAsync` 内部改调 `GuardedStart.start(...)`，准入失败抛带错误码的异常 |
| HTTP 行为 | **不变**：200 + 现有 JSON 形状（见下） |
| 风险 | 低（前端零改动） |
| 验证 | 两个 `async=1` 并发 → 一个成功一个 `EC-WORKFLOW-RUNNING` |
| 附注 | 顺带修 `qs.contains("async=1")` 的宽匹配（`?notasync=1` 会误进异步分支） |

**被拒时的响应形状（v2 修正）**：v1 写"200 → 非 2xx"，这与 §0 的"不改变现有 HTTP 契约"矛盾，且与 E-01 的既有形状不一致。

现有实现（`WorkflowWebService.java:289-298`）返回的是**一个 JSON 对象**，不是 HTTP 错误码：

```java
if (!gate.allowed()) {
    return Jsons.obj("error", gate.reason(),
                     "errorCode", "EC-WORKFLOW-RUNNING",
                     "activeRunId", gate.runId(),
                     "activeRunNo", gate.runNo(),
                     "activeStatus", gate.status());
}
```

⇒ **E-02 沿用同一形状**（200 + `{"error":…, "errorCode":"EC-WORKFLOW-RUNNING", activeRunId/activeRunNo/activeStatus}`），由 `WorkflowController` 现有的 `json.startsWith("{\"error\"")` 嗅探逻辑统一转成错误响应 ⇒ **前端零改动**。

⚠ 附注：`WorkflowController` 的判错是**字符串嗅探**（`json.startsWith("{\"error\"")`）⇒ 若新错误码把 `errorCode` 放在第一个字段，嗅探会**失效** ⇒ 返回体必须保持 `error` 在首位。

### 4.3 E-03 同步跑实验

| 项 | 内容 |
|---|---|
| 现状 | `ExperimentActionController:500` → `BatchOrchestrator.runAll` → 逐批 `execute` |
| 改成 | `runAll` 内每批开跑前调 `GuardedStart`（复用同一套判定），不是整单一次判定 |
| HTTP 行为 | **不变**（仍同步返回 `totalSteps/doneSteps/batches`） |
| 风险 | 中。批次之间要重新判定 |
| 验证 | 串行 4 批仍按顺序跑；第 2 批开跑时若已有 active，行为与现在一致 |

**v2 修正理由**：v1 写"批次之间要重新判定（**因为前一批可能还在跑**）"，这个理由**不成立**——串行批次的前一批**一定已终结**（`executeBatch` 返回前 `ExperimentExecutor.settle` 已落 run 终态、`finishBatchRun` 是同步调用，`BatchOrchestrator:834`）⇒ 批 2 开跑时批 1 的 run.status 已不在 active 词表 ⇒ 判定通过，**不会误拒，不需要重试**。

重新判定的真正理由是"**防止外部并发启动同一 workflow**"——这才是准入的意义。

### 4.4 E-08 批次重跑

| 项 | 内容 |
|---|---|
| 现状 | `ExperimentActionController:401` → `BatchOrchestrator.runBatch`，无门禁 |
| 改成 | 进入 `runBatch` 前调 `GuardedStart`（`excludeRunId` 传该批上一次的 run） |
| HTTP 行为 | 不变（仍返回该批结果） |
| 风险 | 低 |
| 验证 | 同一批重复 POST → 第二次被拒或幂等返回原 run |

### 4.5 E-09 resume（最容易漏的一条）

| 项 | 内容 |
|---|---|
| 现状 | `RunService:274` → `PauseCoordinator.resumeWorkflowRun:255` → `:306` `resumeAsync`；**整条链路无门禁** |
| 改成 | `resumeAsync` 入口调 `GuardedStart.start(isResume=true)`，内部做"UPDATE 带原状态守卫 + 同事务" |
| HTTP 行为 | 不变（仍返回 resume 结果） |
| 风险 | **中高**。resume 会激活一个已存在的 run，判定逻辑与新建不同：要排除自身、校验归属、校验原状态 |
| 验证 | ① 同 run 重复 resume 幂等；② 另一 run active 时 resume 被拒；③ 跨租户/跨流程 resume 被拒 |

**resume 的三条额外要求**（与新建不同）：

```sql
-- ① 状态守卫：不能把已经 completed 的 run 再激活
--    v2 修正：补 'quarantined'（它 terminal=false/active=true，隔离态也需要能恢复）
UPDATE run SET status = 'queued'
 WHERE id = ? AND tenant_id = ? AND workflow_id = ?
   AND status IN ('paused', 'failed', 'quarantined')
   AND (pause_kind IS NULL OR pause_kind <> 'manual_hold')
```

```sql
-- ② 核对影响行数：0 行说明状态已被别人改了，必须报冲突而不是静默成功
```

```
③ 归属校验：run 必须属于当前 tenant + workflow，不能靠客户端传的 id
```

⚠ **为什么必须补 `quarantined`**：`quarantined`（"隔离待确认"）是"等人工确认"的状态。人工确认完却因不在 `paused/failed` 里而**永远无法 resume** ⇒ run 死锁在隔离态。

⚠ **与 §3.3 的呼应**：唯一索引的 active 集合**排除** `quarantined`，但 resume 守卫**包含** `quarantined` —— 两者方向相反是**故意的**：索引管"能不能再起一个新 run"，守卫管"这个 run 自己能不能被唤醒"。一个被隔离的 run 不应阻塞别人启动新 run，但自己必须能醒过来。

### 4.6 E-04 / E-05 / E-06 / E-07 / E-10

这五条已经过调度器，但**仍需确认它们最终都走 `GuardedStart`**，不能有第二条创建路径。

| ID | 需要确认 |
|---|---|
| E-04 | `scheduler.submit` 最终是否调 `createRun`；若是，改走 `GuardedStart` |
| E-05 | `createNextBatchAttempt` 建 queued run 时是否过门禁 |
| E-06/E-07 | 续队时是否重复判定（批之间可能已有 active） |
| E-10 | `existingRunId>0` 跳过预检的分支，流程 run 创建时是否补判 |

## 5. 行为等价性验证（并行度 1）

改造后必须证明"和改造前一模一样"。逐项对照：

| ID | 验证项 | 方法 |
|---|---|---|
| V-01 | 同步单流程响应字段不变 | 对比改造前后 JSON（`experimentRunId/status/totalSteps/doneSteps/error`） |
| V-02 | 异步单流程响应不变 | runId + status |
| V-03 | 同步跑实验串行顺序不变 | 4 批按 `batch_no` 升序执行 |
| V-04 | 批次失败继续语义不变 | 批 1 失败、批 2 仍启动（现有 D3） |
| V-05 | 扣留停在批边界不变 | 扣留时后续批 `paused`，不启动 |
| V-06 | resume 幂等 | 同 run 重复 resume 返回同一结果 |
| V-07 | 既有回归集 | `BatchDbSelfTest`、`WorkflowRunGateDbSelfTest` 全绿 |
| V-08 | 错误码兼容 | 原 `EC-WORKFLOW-RUNNING` 语义不变；**`error` 字段仍排首位**（§4.2 附注） |
| **V-09** | **并发等价性** | **两个 `async=1` 同时打 ⇒ 一个成功一个 `EC-WORKFLOW-RUNNING`；DB 状态不变**（v2 补） |
| **V-10** | **租户隔离** | **跨租户 resume 被拒；跨 workflow resume 被拒**（v2 补） |
| **V-11** | **DB 不可用时的行为** | **见下方说明——这是新增语义，不是等价**（v2 补） |

**"行为不变"的严格定义**：同样的输入序列，HTTP 状态码、响应字段、数据库最终状态三者都一致。

⚠ **V-11 必须单独声明（v2 新增）**：现有 `WorkflowRunGate.check` 的 catch 分支是 **allow**（"查询失败也不拦：门禁是防止自己人打自己人，不该变成库抖一下就启动不了"，`WorkflowRunGate:147-150`）。若要改成"DB 断开 ⇒ `EC-WORKFLOW-GATE-UNAVAILABLE`"，那是**新增语义 = 行为变化**，必须：

1. 单独设计（错误码、是否 fail-closed、是否重试）；
2. 在 §7 风险表里单列；
3. **不能混进"行为等价性"这一节**。

## 6. 分步实施与回滚

| 步 | 内容 | 可独立上线 | 回滚 |
|---|---|---|---|
| 1 | 新增 `GuardedStart`（内部先只做三态准入，事务边界沿用现状） | 是 | 删除类 |
| 2 | 把 E-01 切到 `GuardedStart` | 是 | 切回原调用 |
| 3 | 把 E-02 切过来 + 修 `async` 宽匹配 | 是 | 切回 |
| 4 | 把 E-09 resume 切过来 + 加状态守卫（含 `quarantined`） | 是 | 切回 |
| 5 | 把 E-03 / E-08 切过来 | 是 | 切回 |
| **6** | **把事务边界从"预检+执行"改为"预检+插入"**（v2：原第 7 步，提前） | 是 | 改回 |
| **7** | **加唯一索引兜底**（v2：原第 6 步，后移；active 集排除 `quarantined`） | 是（需迁移） | 删索引 |

**v2 调整了 6/7 的顺序**：唯一索引是**事务边界正确性**的兜底，先加索引会在中间态把现有合法并发路径打掉；且 §7 R-12 已承认它与 allow 开关冲突 ⇒ **先修事务边界，再加索引**。

**第 7 步（唯一索引）建议单独提交**，因为它涉及迁移，且是唯一不依赖"记得改全"的保证。

## 7. 风险

| ID | 风险 | 说明 |
|---|---|---|
| R-10 | 同步入口改异步会破坏契约 | 本清单明确不做；若将来要做，需产品确认并改前端 |
| R-11 | resume 的状态守卫可能挡住合法恢复 | 现有 `paused_fault / waiting_human / paused_unknown` 三种暂停态都要能恢复，守卫不能过严（v2 已补 `quarantined`） |
| R-12 | 唯一索引与显式 allow 开关冲突 | `LABOS_WORKFLOW_CONCURRENT_RUN=allow` 时唯一索引会拒绝，需要定义"放开时怎么处理约束"——建议改为"`active_slot` 取序号 ⇒ 天然支持最多 N 个并发"，从而不需要 allow 开关 |
| R-13 | 批内多次判定导致误拒 | **v2 修正理由**：串行批次前一批**已终结**，判定应通过 ⇒ 不会误拒。真正的风险是"外部并发启动同 workflow"，不是"前一批还在跑" |
| R-14 | 漏改新入口 | 只能靠唯一索引兜底 + 全仓搜索 `createRun` 的测试 |
| **R-21** | **唯一索引的 active 集合若含 `quarantined`**，被隔离的 run 会永久占住该 workflow 的唯一名额 | 已通过 §3.3 显式排除 `quarantined` 处置（v2 补） |
| **R-22** | **DB 不可用时门禁 fail-open**（现状），被当成"行为不变"写进验收 | 已在 §5 V-11 单独声明为新增语义（v2 补） |

## 9. 与其他文档的关系

| 文档 | 关系 |
|---|---|
| 并行执行与事件归属-设计基线（v2） | 本清单是其 §4.2「准入统一」缺项的展开 |
| 逻辑操作与等待者登记·表设计（v3） | 解决"提交之后"的命令与事件身份；本清单解决"提交之前"的准入 |

| 并行执行-跨类锁顺序核查（v2） | R-01 的展开；**不再"未做"** |

**三者合起来才够开并行度 2**：入口统一（本文）+ 命令/事件身份（表设计）+ 跨类锁护栏（⑤）。

> 跨类锁护栏（⑤）的定位：**不必作为并行度 2 的阻塞项，但必须先做** —— 跨类死锁的触发条件是"同一 run 内的并发分支"（ParallelGateway），今天就存在，不是并行度 2 引入的。
