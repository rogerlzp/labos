## 四、接手者要注意的坑（本轮踩过）

1. **不要先写结论后补证据。** §12.4 的冻结结论故意留空；评审记录 10 的「09:30 复跑记录」就是反例（本轮把它整块作废了）。
2. **DDL 一改，上一轮全部 DDL 证据立即失效。** 结论必须绑定 §4 的 **sha256**（现值 `ef54e51d…`）；§4 变了就要重跑并重新绑定。
3. **逐条处置表必须先列意见原文摘要再填处置**，不得从「改了哪些地方」反向生成（评审记录 10 的 §九 和我自己那版 §9.2 都栽在这）。
4. **写完表格用脚本校验编号集合**，不要靠眼力。本轮两次错配都是脚本比对发现的。
5. **catalog 签名的字节级比对对 `ALTER TYPE` 往返敏感** ⇒ 跨轮次比对要记 token 级归一化签名，否则会产生假阳性 drift。
6. **子代理会话可能没有 `write` 工具**（本轮 B 组复跑与闭环核对都遇到过）⇒ 报告要用 bash heredoc 落盘。
7. **共享仓库里并发会话会改同一份文档** ⇒ 每次提交前先 `git log` + `git status` 复核；`private/` 已在 `.gitignore:45` 忽略，复核材料落那里。
8. **`docs/物料身份与状态-设计-v2.md`、`.gitignore`、`.material-v21-review.txt`、`pylabrobot-sim/`、`docs/评审记录/20261111-01-hunyuan.md` 是其它会话的未提交文件** ⇒ **不要动、不要提交**。
