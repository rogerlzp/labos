## 2. 核心机制（实施后的运行时行为）

```
run 启动
  → 声明契约预检（§3.3b 规则 1-10，ERROR 阻断）+ 写声明快照（run_material_effect_declaration，幂等）
节点成功（执行结果边界 = 完成处理器注入点）
  → 写执行确认（run_node.execution_resolution_status='completed' + 物理证据三件套）
  → 有 transition 声明 → 目标解析（plateId/barcode/位置）→ 写 effect(PENDING/NEEDS_RECONCILIATION) + DECLARE action
  → T2 立即应用：单事务锁 effect/plate → 校验 state_version → 写 plate_material_event → 更新 plate → effect APPLIED
节点失败/超时/逃逸
  → 写 failed_confirmed / reconciliation_required（第 7 出口：非 StepFailure 的 RuntimeException 也先写确认再抛）
物料未闭环（PENDING/FAILED/REJECTED/NEEDS_RECONCILIATION 或 reconciliation_required 节点）
  → 派发前闸门停后继；收尾不标 completed；resume 有派发证据的未完成节点拒绝删除
```

**关键不变量**（可据此检查实现）：
- 物理完成的结论**必须**落在 `execution_resolution_status` + 物理证据三件套，不能只靠 `run_node.status`。
- 三张历史表 `plate_material_event` / `plate_material_effect_action` / `run_material_effect_declaration` **只 INSERT**（无 UPDATE/DELETE 业务路径）。
- 物料未闭环时，run **不得**标 completed、后继**不得**派发、续跑**不得**删证据。

## 7. 最值得质疑/核对的地方（给评审的检查清单）

1. **第 7 出口是否正确**：`RunStateMachine.executeNode` 的 `catch(RuntimeException)` 是否真能覆盖「非 StepFailure 的异常逃逸」，且先写 reconciliation_required 再 rethrow？会不会吞掉或重复写？
2. **T2 单事务的锁序**：`applyEffect` 先锁 effect 再锁 plate（FOR UPDATE），对账/rebase/人工改状态是否用了**同一锁序**（避免死锁）？`Tx.inTransaction` 嵌套（reconcile 内调 applyEffect）是否真的 JOIN 同一事务？
3. **续跑守卫的覆盖**：`countResumeGuardHits` 的 WHERE 与 `deleteIncompleteTopNodes` 是否**完全同构**（否则会漏删或漏守）？
4. **命令账本 key 去 opSeq 的副作用**：同一节点同一 step 在**非循环**场景下（如多圈 visit 但 graphHasCycle=false）是否仍会误撞？重试（attempt 递增）是否仍能正常换 key？
5. **闸门是 run 级不是节点级**：当前 `hasGateBlocker` 是「整个 run 任意未闭环就停」，不是 §3.7 的「只查前置域」。这是有意简化的保守近似，但请确认它是否**过度阻断**了无关分支（第一版整 run 暂停是 D4 明确接受的代价，但请复核是否与设计一致）。
6. **人工改状态的仲裁**：`manualStateChange` 把板上过期的 PENDING effect 转 NEEDS_RECONCILIATION，但**没有**把 run 也停下来—— 这个 effect 转 NEEDS_RECONCILIATION 后，闸门会在下一节点派发前拦住吗？
7. **无 FK 的兜底**：所有引用一致性靠 §5.3 巡检 Q1-Q18。S1 迁移后巡检 22/22=0，但**运行时新增数据**的巡检还没接入定时任务——这是否需要 S2 收尾补？
8. **Worker 接线**：`MaterialWorker` 类已写，但**内核容器启动时还没有启动该后台线程**——目前 T2 失败后 effect 保持 PENDING，靠下一次 `processNextDue` 兜底，但没人调用它。这是已知缺口（见 §8）。
9. **per-round 执行确认**：循环多圈时 `updateNodeExecution` 只更新 loop_index=0 汇总行，圈级（loop_index=1..N）的执行确认未写。这与 §3.5「权威仍是 Effect 行」是否自洽？
10. **规则5（声明 vs 设备回包冲突）未实现**：目标解析只用声明里的 target，没有比对「设备回包指向的板」。这依赖真机回包证据（U6），请确认是否可接受为「待真机验证」而非「设计欠账」。
