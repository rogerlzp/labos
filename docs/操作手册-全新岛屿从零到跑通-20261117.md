#### 搬运静默降级（`LABOS_TRANSFER_PLAN` 没开）

判据在 `DriverStepExecutor.transferProtectionEnabled()`（**唯一判据**，2026-11-18 收敛）：

| `LABOS_TRANSFER_PLAN` 的值 | 搬运保护 |
|---|---|
| 未设置 | **关** |
| `off` / `none` / `false` / `no`（大小写不敏感、去前后空格） | **关** |
| 其余任何值（含 `0` 与空串） | **开** |

没开时搬运**不报错、不失败**，只是把整套保护整个跳过——**但「静默」不总成立**：
降级期间若叠加别的故障（如搅拌状态 TTL 过期 `EC-STATE-STALE`），
节点照样会 failed，只是**搬运本身**不报错：

| 被跳过的 | 后果 |
|---|---|
| 位置锁（`PositionLock`） | 两个 run 会选到同一格 → 物理相撞 |
| `transfer_transaction` 搬运事务 | 搬运节点全 completed，但 `transfer_transaction` **零行** |
| 轨道分区互锁（`RailZoneGuard`） | 不同分区的臂会同时进同一段轨道 |
| 扫码证据确认 | 设备回包即当落位，板位账本不落账 |

**识别特征**：run 终态 `completed`，所有搬运节点 `completed`，
但 `select count(*) from transfer_transaction where run_id=?` 为 0，
且 `plate.location_id` 与 `position_state.plate_id` 对不上。

**排查（两条路都行）**：

```bash
# ① 内核自己的启动回显（权威，在日志里）
grep -a '启动开关' <内核日志> | tail -3
# ② 进程环境
ps eww <内核PID> | tr ' ' '\n' | grep LABOS_TRANSFER_PLAN
```

回显里 `搬运保护=关` 就是降级。② 的读法：**没有输出** = 未设置 = 关；
`=off`/`=none`/`=false`/`=no` = 关；`=0` 与空串 = **开**。

实测对照（同一岛 `LAB-PLASMID-01`，2026-11-18）：
降级内核下 run `1001777`/`1001779`/`1001781` 三次 `completed`、0 条事务
（其中 `1001777`/`1001779` 各有 1 个 failed 节点，是叠加的 `EC-STATE-STALE`，不是搬运本身报错）；
开启后 run `1001790`/`1001791`/`1001792` 三段分别 3/4/4 条事务且全部 `CONFIRMED`。

**要真的关掉搬运保护**：`LABOS_TRANSFER_PLAN=off ./scripts/start-kernel.sh`
（`off`/`none`/`false`/`no` 由**内核**识别，大小写不敏感、去前后空格；
用 `java -cp ...` 直接起内核也认同一个 token —— 判据只有一处）。
注意 `env -u LABOS_TRANSFER_PLAN` **没用**——脚本的默认值会立刻把它设回 `1`。

> ⚠ **`off` 约定只适用于 `LABOS_TRANSFER_PLAN`**。
> `LABOS_AUTH=off` / `LABOS_EXEC_GRAPH=off` 判读的是 `!"0".equals(getenv())`
> ⇒ 拿到 `"off"` 仍然算**开**，要关只能用 `=0`。

> 三个开关的「怎么关」语义**不一样**，别想当然：
> `LABOS_AUTH`（`ApiServer.java:102`）和 `LABOS_EXEC_GRAPH`（`WorkflowService.java:1207`）
> 是 `!"0".equals(getenv())` ⇒ **`=0` 才算关**；
> `LABOS_TRANSFER_PLAN`（`DriverStepExecutor.transferProtectionEnabled`）
> 是「未设置 / off 族 = 关，其余 = 开」。

**启动即回显**（2026-11-18 起，**内核自己**打，权威）：

```bash
[启动开关] 搬运保护=开（raw=1）｜ 执行图=开（raw=<未设置>）｜ API鉴权=开（raw=<未设置>）
[启动开关] ⚠ 搬运保护处于【关闭】：位置锁、搬运事务(transfer_transaction)、
           轨道分区互锁、扫码证据确认 全部不生效；搬运仍会执行、run 仍会 completed。
```

**降级不再静默**（2026-11-18）：降级期间每次搬运都会在 `interlock_decision` 留 **4 条**记录
（L1/L3/L4/L5 各一条），`fact_type='guard'`、`fact_value='LABOS_TRANSFER_PLAN'`，
理由写明「搬运保护未开启」：

```sql
-- 判别降级：fact_type='guard' 的就是「这次搬运没受保护」
SELECT interlock_code, decision, reason FROM interlock_decision
WHERE run_id = ? AND fact_type = 'guard';
```

⚠ **不要拿 `decision='SKIP'` 当判别依据** —— 平台**正常运行**时也会写 SKIP：
L1（无 turntable 事实）、L5（未携带 interactionId）本来就记 SKIP
（实测正常跑的 run `1001797` 里就有 9 条这样的 SKIP）。
真正区分「判过」与「没判」的是 `fact_type`：
`guard` ⇒ 没保护；`rail_zone` / `stirrer_status` / `turntable` / `waiting_interaction` ⇒ 判过了。

## 第 4 章 · 把设备装进这个岛

### 4.0 为什么顺序是「驱动 → 设备 → 点位」

| 顺序 | 步骤 | 跳过的后果 |
|---|---|---|
| 1 | **登记驱动** `driver` | 设备**界面有但点不动**，运行报 `EC-06-0001`（驱动注册表按能力匹配，能力缺失整条驱动被跳过）—— `DeviceService.java:139-141` |
| 2 | **部署设备实例**（资源树节点 + 型号 + 实例三件套） | 没有设备就没地方挂点位 |
| 3 | **改设备编号** | deploy 生成的编号是「型号code-序号」，不可控；不改号后面点位码全是乱的 |
| 4 | **造点位** | 绑定无处指向 |

> ⚠ **改编号必须在造点位之前**。`PUT /api/devices/{id}/code` 只同步
> `resource_node.code`、`resource_node.path`、`device_instance.code` 三处（`DeviceMapper.xml:90-99`），
> **已建的点位编码不会跟着变**（`DeviceController.java:294-297`）。

### 4.1 登记驱动

页面：**`/topology` → 驱动面板**（`Topology.tsx:221`）。

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"code":"DRV-SIM-ARM1","name":"轨道式四轴机械臂 ARM1 模拟驱动",
       "protocol":"mock","endpoint":"tcp://127.0.0.1:19630","vendor":"simulator"}' \
  http://127.0.0.1:18080/api/drivers
```

| 字段 | 必填 | 取值 | 证据 |
|---|---|---|---|
| `code` | ✅ | 驱动编号 | `DeviceService.java:878-879` |
| `name` | ✅ | 显示名 | `DeviceService.java:880-881` |
| `protocol` | ✅ | `grpc/http/tcp/sila2/modbus/opcua/netdll/mock` | `DeviceService.java:882-883`；`pg_rebuild/schema/10_base_platform.sql:52` |
| `endpoint` | ✅ | `tcp://<IP>:<端口>` | `DeviceService.java:884-885` |
| `vendor` | ✖ | 厂商 | `DeviceController.java:462` |
| `resident` | ✖ | `true` = 常驻进程 | `DeviceController.java:463` |

`version` **不可传**，后端固定写 `'1.0'`（`DeviceMapper.xml:387-395`）。

### 4.2 部署设备实例（**新岛推荐用这条：编号可控**）

```bash

curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"islandId":'"$ISLAND"',
       "code":"ARM1","name":"轨道式四轴机械臂 ARM1",
       "deviceType":"ROBOT","capability":"TRANSFER",
       "ip":"127.0.0.1","driverId":12}' \
  http://127.0.0.1:18080/api/devices
# 期望：{"resourceId":1000610}
```

一条调用完成**三件套**（`DeviceService.java:156-211`）：

| 写入 | 内容 |
|---|---|
| `resource_node` | `kind='device'`，`parent_id=岛`，`path='/LAB-NEW-01/ARM1'` |
| `device` | 型号字典（按 `code` 复用，没有就建；`deviceType` 默认 `MISC`） |
| `device_instance` | 实例（连哪台、哪个 IP、哪个驱动） |

字段：`islandId`（必填，缺失报「必须指定所属岛屿」）、`code`、`name`、`deviceType`、
`capability`（对应 `capability.capability_code`，决定它能接哪些流程节点）、`ip`、`driverId`。

> **另一条路**：`POST /api/device-models/{modelId}/deploy?islandId=&ip=&driverId=`

> 「型号code-序号」（`DeviceService.java:125-131`，中文名还会被替换成下划线），
> 所以用这条路**必须**再调一次 `PUT /api/devices/{id}/code` 改号。

### 4.3 造点位（三种方式）

| 方式 | 适用 | 端点 |
|---|---|---|
| 单点 | 设备只有 1~2 个位置 | 页面 `/positions`「新增点位」 |
| 批量网格 | 耗材栈这类（`STACK1-S01..S12`） | `POST /api/devices/{id}/points/grid` |
| 按规格 | 96 孔板、双工位提取仪这类规整布局 | `POST /api/devices/{id}/points/spec` |
| 独立进出口 | 网格外单独一个进出口 | `POST /api/device-points/standalone` |

**网格示例**：

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"deviceCode":"STACK1","cols":4,"rows":3,
       "pointKind":"storage","slotKind":"nest",
       "slotIndexBase":1,"maxStack":1,"maxHeightMm":45,
       "plateTypes":"deep96","robotReachable":true}' \
  http://127.0.0.1:18080/api/devices/$RESOURCE_ID/points/grid
# 期望：{"created":12,"deviceId":...}
```

| 字段 | 默认 | 取值 | 证据 |
|---|---|---|---|
| `cols` / `rows` | — | 1–200 | `DeviceService.java:957-960` |
| `pointKind` | `storage` | **只能** `incubator/storage/transfer_point`（机械臂选位 SQL 只认这三个） | `DeviceService.java:961-966` |
| `slotKind` | `nest` | `nest/waste/deck_in/deck_out` | `DeviceService.java:972-977` |
| `slotIndexBase` | 1 | 槽位号起点 | `DeviceController.java:522-523` |
| `maxStack` / `maxHeightMm` | 0 / null | 堆叠数 / 最大板高 | `DeviceController.java:524-525` |
| `plateTypes` | null | 逗号分隔板型 | `DeviceController.java:527` |
| `isEntry` / `isExit` / `robotReachable` | true | 进出口 / 机械臂可达 | `DeviceController.java:528-531` |

**语义自动推导，别硬传**：`deck_in` ⇒ 强制 `point_role=internal` + `robot_reachable=false` + 非进出口；
`deck_out` ⇒ 强制 `both` + 可达 + 进出口（`DeviceService.java:983-996`）。

点位码规则：`设备编号-R{行}C{列}`，`slotIndex = slotIndexBase + (r-1)*cols + (c-1)`（`DeviceService.java:1010-1014`）。

**按规格造点**：

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"deviceCode":"ID-EXT1","points":[
        {"code":"ID-EXT1-EXT2","label":"EXT2","slotKind":"deck_out","slotIndex":1,"pointKind":"transfer_point"},
        {"code":"ID-EXT1-INT1","label":"INT1","slotKind":"deck_in","slotIndex":2,"pointKind":"transfer_point"}]}' \
  http://127.0.0.1:18080/api/devices/$RESOURCE_ID/points/spec
```

**改点位配置**（含可达性）：`PUT /api/device-points/{pointResourceId}`，
可改 `pointRole`（`entry/exit/both/internal`）、`robotReachable`、`isEntry`、`isExit`、
`orderInDevice`、`gridRow`、`gridCol`、`maxHeightMm`、`plateTypes`、`standalone`、
`positionLabel`、`note`（`StockController.java:402`）。

> **校验**：非 `internal` 点位必须至少一个进出口为 true，否则 400（`StockController.java:414-417`）。

### 4.4 点位字段速查（**错了会一路错到运行期**）

| 列 | 取值 | 影响 |
|---|---|---|
| `code` | 全局唯一，如 `DISP1-PLATE` | **Planner 与驱动都用它解析**（不能用 label 代替） |
| `position_label` | 现场叫法，如 `PLATE`/`A1` | 仅显示；两个设备可能重名 |
| `point_role` | `entry/exit/both/internal` | 语义与筛选 |
| `slot_index` | 槽位号 | 分液器/孵箱这类多槽设备 |
| `robot_reachable` | `true` 机械臂可达 / `false` 设备内部位 | **`false` 的点位不能让机械臂搬**（预检 PF-27 会拦） |

> ⚠ **最常见误配**：把"台面内工位"标成 `robot_reachable=true`。
> Planner 会把"搬进台面"派给机械臂，运行期超时。

### 4.5 设备上线验收（**心跳为准，不是 TCP 探测**）

在线状态的唯一权威是 **Redis 心跳**（`HeartbeatService.java:332-336`，key `labos:link:<设备ID>:<IP>:<端口>`）：

```bash
./scripts/start-sim-station.sh --status
# 期望：设备在线数 = 你部署的设备数

curl -s -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:18080/api/devices/pool?islandId=$ISLAND" | head -c 400
# 期望 items 里有你刚建的设备
```

**设备不在线 ⇒ 能力池里没有它 ⇒ 流程会报"无可用设备"**。

## 第 6 章 · 画流程（designer 的活）

### 6.1 入口

1. `/workflows` → 「新建流程」（只填名称 + 所属岛）→ 打开编辑器
2. 编辑器路由：`/designer/{流程id}?islandId={岛id}`
   —— **`islandId` 决定左侧 palette 能看到哪些点位**；不带也能用，但要先选岛

### 6.2 点位视角操作五步

1. 左侧切到 **「点位视角」** tab
2. 顶部先选三样（拖之前定，拖完还能在右栏改）：
   - **物料角色**：`mainPlate` / `magPlate` / …（第 5.3 步的字典）
   - **装板方式**：装一块 / 装选中 / 全装 / 不装
   - **扫码策略**：不扫码 / 读码 / 校验进 / 校验进出 …
3. 展开某个点位（如 `DISP1-PLATE`）→ 把它的 `Run` **拖到画布**
   - 节点自动创建，**同时写入一条 `node_binding`**（不用再去右栏绑）
   - 图上**不会**出现机械臂节点
4. 依次拖下一个点位 → 两个节点自动连线
5. 选中节点，在右栏「节点设置」里设 **所属阶段**（S1..S8 / S0 / S9）
   - 阶段只用于分组与甘特聚合，**不改变执行顺序**

### 6.3 脚本化替代（画图 + 绑定必须同源）

```bash
# 图：BPMN 2.0 XML 原文；?draft=1 存草稿
curl -s -X PUT -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/xml' \
  --data-binary @flow.bpmn \
  "http://127.0.0.1:18080/api/workflows/$WFID/graph"

# 节点绑定
curl -s -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"seq":1,"positionId":$POINT_ID,"methodId":417,"materialRole":"mainPlate",
       "loadingPattern":"load_single","barcodePolicy":"none","enabled":true}' \
  http://127.0.0.1:18080/api/workflows/$WFID/nodes/$NODE_KEY/bindings
```

`node_binding` 的目标三选一（至少填一个）：`position_id`（`device_point.id`）、
`device_instance_id`、`pool_id`（约束 `ck_node_binding_target`）。

> ⚠ **图与绑定必须同源生成**。`node_key` 按位置分配：图一改，旧的 `node_binding`
> 会原地存活并指向别的节点 ⇒ 运行期"绑定优先级最高"⇒ **静默用错设备**
> （仓库实测过把 P_AUTO-3 的洗脱发给 P_AUTO-1）。
> 参照 `scripts/setup-extraction-flow.py`（图与绑定同源生成，幂等可重跑）。

### 6.4 预检（保存后必看）

页面右侧直接给 `blocking / errors / warnings` 和每条 issue 的节点位置；
接口：`GET /api/workflows/{id}/preflight`。

| 码 | 级别 | 含义 | 怎么修 |
|---|---|---|---|
| PF-21 | ERROR | 点位没授权这个方法 | 回 `/positions` 授权（§5.1） |
| PF-22 | ERROR | 声明点位模式但没绑定 | 重新拖，或右栏补绑定 |
| PF-23 | WARN | 点位绑定没有物料角色 | palette 顶部选角色后重拖 |
| PF-27 | ERROR | 跨设备但目标位机械臂可达性不成立 | 换可达点位，或确认那步该由设备自己做 |
| PF-30 | WARN | 标了可达但没有示教坐标 | 去 `/arm-console` 抓点（§5.2） |

### 6.5 只跑部分阶段（客户场景："这次只做 W1/W2"）

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:18080/api/workflows/$WFID/run?async=1&stages=S1,S2"
```

规则（实测）：

- 未分阶段的节点（变量/网关/公共步骤）**照常执行**（它们是阶段间传参的胶水）
- 被裁剪的节点状态是 **`bypassed`**（不是 `skipped`，后者会被当成"板位不可信"转人工）
- 所选阶段会记进 `run.input.stages`，事后能解释"为什么有些节点没跑"
- **只支持异步**：同步路径显式 400，不静默忽略

页面上等价入口：`/workflows` → 选中流程 → 执行面板里的**阶段多选**。

### 8.6 常见卡点与根因

| 现象 | 根因 | 处置 |
|---|---|---|
| 启动按钮点不动 | 未齐套 | 看上方原因：必填未核验 / 设备离线 |
| 一直"等交互" | 设备事件入站被拒（503） | 仿真要有 `LABOS_DEVICE_EVENT_ALLOW_ANONYMOUS=1`；真机要有 `LABOS_DEVICE_EVENT_TOKEN` |
| 搬运节点转到人工 `EC-POSITION-OCCUPIED` | 源位没板 / 板不是本 run 放的 | 配物料并核验（§8.2） |
| 搬运失败 `EC-SCAN-EVIDENCE-MISSING` | 抓板闸门要求扫码证据 | 流程里要有扫码节点，或仿真态开自动确认 |
| 预检 PF-21 | 点位没授权方法 | 授权方法（§5.1） |
| 预检 PF-23 一直提示 | 物料角色为空 | 跑 `seed-material-roles.py` |
| 点位视角 palette 是空的 | 没选岛 / 该岛没点位 | 地址带 `?islandId=`，或先在 `/positions` 造点位 |
| 拖完绑定是 0 条 | 图保存失败或绑定接口报错 | 看 toast「节点已入图，但绑定写入失败」；重拖或右栏补 |
| 图上两点位相邻，跑完没搬运 | 机械臂不在能力池 / 点位同设备 / 被 stage 裁剪 | 查 `/api/devices/pool` 有 ARM1；查 `run.input.stages` |
| 403「不能修改工艺配置」 | 当前是 operator | 换 admin/designer，或只做运行操作 |
| 403「不能执行/启动实验」 | 当前是 designer | 换 admin/operator，或让操作员起跑 |
| 阶段裁剪 400 | 用了同步执行 | 加 `async=1` |

## 结语

**把一个空岛变成能跑的实验室，顺序只有一句话：**

> **岛 → 驱动 → 设备 → 点位 → 方法授权 → 流程 → 模板 → 实例化 → 齐套 → 启动。**

每一步都有"做完怎么验"（本文每节末尾都给了命令），
每一步都有"跳过了会怎样"（§4.0 / §5.1 / §6.3 / 第 11 章）。

**别信"界面里能拖出来"就是配好了**——权限靠后端 403 兜底，
能力边界靠点位×方法授权兜底，运行真相靠 `run_command` 表里的耗时与原文兜底。
