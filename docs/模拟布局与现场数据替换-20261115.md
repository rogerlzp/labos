## 1. 模拟布局生成了什么

`python3 scripts/gen-sim-layout.py`（幂等，可重复跑）：

| 产物 | 数量 | 说明 |
|---|---|---|
| `resource_node`（kind=virtual） | 13 | 7 个轨道分区 + 6 个虚拟搅拌单元，码一律 `SIM-` 前缀 |
| `rail_zone` | 7 | 轨道分区：按 **x 坐标分带**（SIM-Z0..Z5）+ 换排道岔（SIM-ZCROSS） |
| `transfer_rail_zone` | 1680 | 搬运路径 → 分区集，**按流程里真实出现的设备对**推导（STACK1 ↔ P_AUTO-1..4，双向） |
| `robot_point` | 78 | 机械臂 ARM1 的标定：x/y/z 来自合成平面模型，`fill_status=ok` |
| `stirrer_dispenser_pair` | 6 | DISP1..6 ↔ 各自的虚拟搅拌单元 |
| `device_state` | 6 | 虚拟搅拌单元的 `idle` 状态（L4 闸门要求 10s 内新鲜） |
| `plate` + `workflow_variable` | 1 + 1 | 模拟主物料板 `SIM-PLATE-EXT-001` + 流程变量 `mainPlate` |

**设计原则（改脚本前先读）**

1. **一切从库里真实资源推导**，不手编设备/点位：岛 → 设备 → `device_point` → 点位的 `point_resource_id`。
2. **路径键口径必须与运行期一致**：`DriverStepExecutor` 用 `sourcePos->targetPos`，
   两个都是**点位的 `resource_node.id`**（`selectPositionResourceBySpec` 取 `point_resource_id`）
   ⇒ 配置必须覆盖"运行时可能选出的所有点位对"，否则 L3 fail-closed 照样拦。
3. **分区由几何推导**：路径的分区集 = 源→目标经过的所有 x 轨道段（完整运动包络）；
   跨排再加换排道岔互斥点。
4. **模拟数据必须可识别、可撤销**：资源码 `SIM-` 前缀；`robot_point.name` 以 `SIM ` 开头。

**撤销**：`python3 scripts/clean-sim-layout.py`（默认预览，`--apply` 真删；只删带 SIM 标记的，真实数据不动）。

**工位复位**：`python3 scripts/reset-sim-station.py --apply`
（把卡住的 run 留下的**板位归属**释放掉，让下一轮能接管板；板留在原位不动 —— 这正是
`a93e4a7` 起点板位引导设计的场景。**每次重跑线前先跑这个**。）

## 2. 现场来了真实数据，怎么替换

| 现场给什么 | 替换掉模拟的什么 | 怎么落 |
|---|---|---|
| 轨道分区映射（分区 ↔ 资源） | `rail_zone`（7 行） | `scripts/seed-p2-interlock.py`（已有，填 JSON）→ 删掉 `SIM-Z*` |
| 每条搬运路径经过哪些分区 | `transfer_rail_zone`（1680 行） | 同上（`transfer_rail_zones` 段） |
| 人工验证过无冲突的路径 | `rail_zone_exemption`（模拟环境 0 行） | 同上（`rail_zone_exemptions` 段） |
| 搅拌单元 ↔ 分液器配对 | `stirrer_dispenser_pair`（6 行） | 同上（`stirrer_dispenser_pairs` 段） |
| 机械臂点位 x/y/z + 示教顺序 | `robot_point`（78 行） | 现场示教后回填 `x/y/z/order_in_device`；`fill_status` 改 `verified` |
| 真实板号（操作员扫码） | `plate` + `workflow_variable.mainPlate` | 删 `SIM-PLATE-*`，改 `mainPlate` 的值 |

**替换步骤**：

```bash
# ① 先删模拟数据（真实数据不受影响）
python3 scripts/clean-sim-layout.py --apply

# ② 落现场真实配置
source /tmp/labos-env.txt
python3 scripts/seed-p2-interlock.py <你的真实配置.json>

# ③ 预检必须全绿（L3 不再全拦、L1/L4/L5 不再空转）
python3 scripts/verify-p2-interlock-config.py
```

> ⚠ **模拟数据与真实数据绝不能混用**：模拟分区是按合成几何推的，
> 与现场轨道不一致 ⇒ L3 会放行不该放行的路径。**现场部署前必须清掉模拟布局。**

## 3. 整线仿真：改造前 vs 改造后

### 3.1 改造前（run 1001660，2026-11-15 22:22）

```
节点状态：12 completed / 26 pending / 1 manual
manual 节点：Activity_0006「机械臂 放磁套板到 P_AUTO-1 交互位」
错误码：EC-RESOURCE-BUSY
日志： [搬运] 目标设备 1000611 暂无可用装载口（或已被别的 run 预留），等待中…
      [搬运] 等待装载口超时 60000ms，拒绝搬运并转人工
```

**根因（数据缺陷）**：`DriverStepExecutor.resourceOfParam` 用 `selectResourceIdByCode`
解析搬运的 `source`/`target`，而该查询对 `resource_node.code` 生效 ——
**点位码（`STACK1-S02` / `P_AUTO-1-EXT`）也是 resource_node 的 code**
⇒ 被解析成**点位资源 id** ⇒ "目标设备"成了点位本身 ⇒ 目标设备没有装载口 ⇒ 60s 超时。

⇒ **能跑通的基座岛流程用的是设备码**（`ID-1021` → `ID-ASPIN_2K-1`），
提取流程却写点位码 —— 这就是差异。已修（`scripts/setup-extraction-flow.py`）。

### 3.2 第一层修复后（run 1001662）

错误码变成 `EC-POSITION-OCCUPIED`：源位解析不到"归属本 run 的板"。
**根因**：搬运节点没有 `barcode` 参数、流程没有 `mainPlate` 变量 ⇒ 板号解析不出来
⇒ `seedStartPlatePosition` 无板可预置 ⇒ 源位归属校验必然失败。
已修（流程脚本加 `barcode: ${mainPlate}` + 生成器建模拟板与流程变量）。

### 3.3 第二层修复后（run 1001662 → 1001663）

错误码变成 `EC-SCAN-EVIDENCE-MISSING`：**抓板前强制扫码闸门**没有证据。
**根因（平台缺口，见 §4.1）**。

### 3.4 仿真态放开自动确认 + 工位复位后（run 1001664）

```
节点状态：14 completed / 25 pending / 1 manual
manual 节点：Activity_0014「机械臂 放磁套板到 P_AUTO-2 交互位」
错误码：EC-POSITION-OCCUPIED
```

⇒ **第一段搬运（STACK1 → P_AUTO-1）真的跑通了**：
板从栈位搬到了 P_AUTO-1 的交换位，L3 轨道分区、L1/L4/L5 守卫全部放行。
现在卡的是 **4 台提取仪要 4 块磁套板，而库里只有 1 块**（§4.2）。

## 4. 剩下的两个缺口（都是平台/流程语义，不是布局）

### 4.1 缺口①：抓板扫码证据的接线 —— ✅ 已闭环（2026-11-15 23:30）

**当时的现象**：搬运被 `EC-SCAN-EVIDENCE-MISSING` 拒绝（run 1001662）。

**根因**：`recordScanEvidence` 的源位取 `firstOccupiedPosition(扫描设备, runId)`
—— 扫码设备是**机械臂**，ARM1 没有 `device_point`（它手上没有板位）⇒ 源位 null
⇒ **证据根本落不下来**。

**修法（三层）**

| 层 | 改动 | 为什么 |
|---|---|---|
| 内核 | `WorkflowService` 落证据时，被扫位置取**扫码节点参数里的 `sourcePosition`**（点位码） | 扫码设备是机械臂 ⇒ 源位只能由扫码节点自己声明 |
| 内核 | 新增 `DeviceStateMapper.selectPositionResourceByPointCode`（按点位码**全局**解析） | 原有 `selectPositionResourceBySpec` 是**设备内**解析（带 `device_resource_id` 约束），而机械臂扫的是**别的设备**上的板 ⇒ 必须全局解析 |
| 内核 | `seedStartPlatePosition` 尊重流程声明的 `sourcePosition` | 板必须放到**流程声明的那个槽位**（否则扫码证据的源位与搬运的源位对不上） |

> ⚠ **试过但行不通的方案**：把"被扫点位"写在 `node_binding.position_id`。
> **平台的绑定模型要求「节点绑的点位属于该节点自己的设备」** —— 陈旧绑定守卫
> （`GraphRunner.toRecoverable`）会按点位反查设备实例，扫码节点绑了耗材栈的槽位
> 就会被判成"编排里绑的设备实例与节点绑定里绑的不是同一台"而**拒绝执行**
> （实测 run 1001665）。⇒ 跨设备点位只能走**节点参数**，不能走绑定。

**端到端证据（run 1001671）**

```
扫码证据：id=95  source_position_id=1000558（= STACK1-S09，流程声明的源位）
          expected_barcode=SIM-PLATE-EXT-001   scanned_barcode=SIM-PLATE-EXT-001
          consumed=t   ← 被抓板闸门原子消费
节点进度：22 completed（第一段搬运「STACK1-S09 → P_AUTO-1-EXT」真跑通）
```

**连库自测**：`driver.ScanEvidencePositionDbSelfTest`（13/0，已登记进 `scripts/test-all.sh`）
—— 锁住两个不变量：
① 按点位码全局解析的位置 **==** 设备内解析的位置（接线的前提）；
② 证据落在该点位 ⇒ 闸门放行并消费；源位是别的点位 ⇒ 拒绝（`EC-SCAN-EVIDENCE-MISSING`）。

**流程侧配套**（`scripts/setup-extraction-flow.py`）：
每个搬运前加一个扫码节点（`BarcodeScan`，ARM1 真实登记的方法），参数带
`barcode: ${mainPlate}`（模拟器会**原样回显**请求里的 barcode）与 `sourcePosition`；
搬运节点写显式 `sourcePosition` / `targetPosition`（点位码）。

### 4.2 缺口②：4 块磁套板（多板起点引导）

**现象**：第一条链搬完板后，第二条链找不到"归属本 run 的板"。

**机制**：`WorkflowService.seedStartPlatePosition` **只处理一块板**
（取**第一个** Transfer 节点的 source/barcode，预置到起点设备）。
而客户的工艺是"每个分液阶段给 4 台提取仪各送一块板" ⇒ 起点需要 4 块磁套板，
各自的 barcode 也要逐节点区分（现在 4 条链都写 `${mainPlate}`）。

**建议修法**

1. 流程层：4 条链各用各的板变量（`${magPlate1..4}`），生成脚本按链序号写入。
2. 内核层：`seedStartPlatePosition` 改为**按 Transfer 节点逐个预置**
   （同一 source 设备的多块板 → 依次落到不同的空位，归属同一 run）。
3. 仿真层：生成器建 4 块模拟板 + 4 个流程变量（本次只做了 1 块，因为只为了打通第一段）。

## 7. 仿真环境的标准启动方式（本轮踩到的三个环境级坑都收在这）

```bash
./scripts/start-sim-station.sh --restart   # 内核 + 13 台模拟器 + sidecar 一次拉起
./scripts/start-sim-station.sh --status    # 只看现状
```

### 坑①：模拟器启动时读中控清单会超时 ⇒ **设备 id = 0** ⇒ 一台命令都发不出去

13 个模拟器同时读 `/api/devices/registry` 会打爆内核 ⇒ 超时 ⇒ 模拟器回退到命令行参数
⇒ 没设备号 ⇒ 收到中控的命令时 `equipment_id` 对不上 ⇒ `EC-06-0001`。

⇒ 修法：`scripts/sim-all.py` 把清单里已有的 `deviceId` / `code` / `modelId`
**直接传给模拟器**（`--device` / `--code` / `--model`），不让每个模拟器再读一遍。

### 坑②：设备事件入站默认关着 ⇒ 侧车上报全部 503 ⇒ 流程卡在「等交互」

内核的 `POST /api/device-events` 在没配 `LABOS_DEVICE_EVENT_TOKEN` 时返回 503
（"设备事件入站未启用"），侧车会把事件留在 outbox 里反复重试。

⇒ 仿真态用本机联调开关：`LABOS_DEVICE_EVENT_ALLOW_ANONYMOUS=1`
（`start-sim-station.sh` 已设）。⚠ **真机必须换成真令牌，不能开匿名。**

### 坑③：卡住的 run 会一直占着板位归属 ⇒ 下一轮永远撞 EC-POSITION-OCCUPIED

`position_state.occupied_by_run` 归一个**已失败**的 run 时（不是 paused），
`seedStartPlatePosition` 会按 fail-closed 拒绝接管 ⇒ 每轮新跑都撞同一堵墙。

⇒ 修法：`scripts/reset-sim-station.py` 按「**谁持有板位归属**」找 run（不按状态筛），
把归属释放 + 板从点位取下 + run 收尾；范围只限本流程与 `SIM-PLATE-*` 模拟板，不动别的线。

### 扫码方法名必须是设备方法表里**真实登记**的名字

ARM1 的型号 `GANTRY_ROBOT_GENERIC` 登记的方法里有 `Scan`；但**模拟器**按自己
型号/画像的方法集校验指令 ⇒ 画像里没有的名字会被拒（`EC-06-0004`）。
⇒ 模拟器启动要带 `--methods`（`sim-all.py` 已带），且流程里写的方法名要与
`GET /api/devices/{resourceId}/methods` 一致（ARM1 有 `BarcodeScan` / `BarcodeScanEx`）。
