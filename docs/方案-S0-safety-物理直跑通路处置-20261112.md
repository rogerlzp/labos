
# S0-safety 物理直跑通路处置方案（第一版 · 2026-11-12）

> **状态**：**部分实施**（2026-11-12 `3d83eeb`：4 条 HTTP 通路 + sidecar bind 已收口）；剩余 sidecar 鉴权 / gateway Redis 收口 / 前端 / 负向测试 / 手册未实施。实施进度见 §10。
> **【第 10 轮修正 · S10-02 / P0】**：v4.2 复核发现原盘点**只覆盖 HTTP 通路，漏了两条非 HTTP 的物理执行入口**（sidecar TCP、gateway Redis）——它们**能驱动真机、绕过统一完成点、且零鉴权/零写权限**。本方案已补入 P6/P7 并给出处置；**S0-safety 的完成判定随之收紧**。
> **对应**：[v4 第一版收敛稿](物料身份与状态-设计-v4.md) §8.4「S0-safety」、第 7 轮 openai 评审 P2-05、以及第 7 轮 08-deepseek 复审指出的「执行通路缺口」。
> **目的**：在进入 S1 前，把所有能真实驱动设备、但不产生物料执行事实的通路收口，避免物料状态与物理现实脱节。

---

## 1. 背景

v4 已把物料效果处理统一到 RunStateMachine 的完成处理器上；但只要以下通路仍可被调用，就可能出现：

- 设备动作真实发生，但 run/run_node/run_command 与物料效果没有任何记录；
- 物料状态看起来没变，实际板已经被搬走/封膜/处理；
- 后续对账与审计无法回答「这次动作是谁、哪次执行、什么时间做的」。

因此 S0-safety 的目标不是「把功能做完」，而是先把物理动作的可审计性关住。

补充事实：

- 全局鉴权由 ApiAuthInterceptor 承担，开关是 ApiServer.AUTH_ENABLED = !"0".equals(env LABOS_AUTH)（默认开启）；没有 per-endpoint 功能开关或调试权限角色（RbacRules 只有 admin/operator/viewer + canWrite/canManageUsers）。
- ExperimentFlowRunner 目前只被 ExperimentActionController 引用（grep new ExperimentFlowRunner 仅 1 处）⇒ 下线端点不需要删除该类的其他调用方。
- 一次现场动作即使不落 run，也可能改变 position_state/plate 等既有投影（取决于动作），所以「不落执行事实」不等于「没有副作用」。

## 3. S0-safety 完成判定（进入 S1 的硬条件）

1. flow-run 端点不可用：返回 404（移除路由），且 webapp/scripts 无调用；
2. shadow-run / shadow/probe 在生产配置下默认拒绝：未显式开启时返回 403/410，不得静默执行；
3. 调试通路若被允许：必须 admin + 显式环境开关 + 审计日志 三件套；
4. 所有上述通路在开启时必须在 UI/日志明确标注「调试通路：不产生执行事实」；
5. 自动化负向测试覆盖「默认拒绝」；核心场景回归（scripts/ci-gate.sh 等）不因处置而失败；
6. 操作手册明确：调试通路不得用于生产加工；
7. **sidecar TCP**：默认只绑 `127.0.0.1`（不绑全网卡）；如确需现场直连，必须启用**共享密钥鉴权 + 来源 IP 白名单**，且密钥不得进代码库；
8. **gateway Redis**：Redis 启用 ACL/强口令，**只允许中控服务账号写入命令队列**；命令消息带签名（HMAC，中控密钥），网关侧验签失败即丢弃并告警；生产 Redis 不暴露到办公网/设备网。

## 4. 推荐方案（A：下线 + 默认拒绝 + 审计）

### 4.1 flow-run：直接下线（推荐）

- 移除 ExperimentActionController 中 @PostMapping("/experiments/flow-run")（移除路由映射，返回 404）；
- ExperimentFlowRunner 类保留不删：未来若要接入统一执行器，需要它的逐步执行能力，但第一版不提供 HTTP 入口；
- 前端无调用，无需兼容；脚本若引用需同步更新；
- 验收：curl -X POST /api/experiments/flow-run 返回 404；grep 无路由注册。

### 4.2 shadow-run / shadow/probe：默认拒绝 + 显式开关 + admin

- 新增配置项（建议 labos.safety.shadow-run-enabled、labos.safety.device-probe-enabled，默认 false）；
- 未开启：返回 403，响应体说明「调试通路已关闭（S0-safety）」；
- 开启条件：LABOS_ALLOW_SHADOW_RUN=1（或对应 env）+ 会话角色 = admin（新增 RbacRules.canDebug(role) 或直接 admin）+ audit.record；
- 生产部署检查清单强制这两个开关为 false；
- 前端：开关关闭时隐藏/禁用调试按钮，或显示「调试模式」标识 + 二次确认。

### 4.3 robot-points capture：并入 probe 开关

- 归入 labos.safety.device-probe-enabled（或单独 labos.safety.read-probe-enabled）；
- admin + audit；未开启返回 403；
- 说明：这是读动作，风险低于整流程下发，但仍属于真实设备通路，第一版按统一口径收口。

### 4.4 CLI/demo

- 不加开关（非 HTTP 入口），但在操作手册与 README 注明「仅测试/演示，不产生执行事实」。

### 4.5 sidecar TCP：默认绑本机 + 鉴权 + 白名单（第 10 轮新增）

- **默认绑 `127.0.0.1`**：`Program.cs:138` 的 `bind` 默认值从 `0.0.0.0` 改为 `127.0.0.1`；确需现场直连时用 `--bind` 显式指定，并在部署清单里记录理由；
- **加鉴权**：`TcpServer.Serve/Handle` 增加共享密钥校验（HMAC 或预共享 token），密钥由环境变量/密钥文件注入，**不得进代码库**；
- **来源白名单**：允许直连的 IP 段按现场网络配置，配置变更需审计；
- **不改变设备侧行为**：`S100SerialTransport` / `AspinClusterTransport` 的真机协议不动——sidecar 是**设备侧适配器**，收口的是「谁能命令它」；
- **文档**：`sidecar-dotnet/README.md` 与现场部署手册同步写明「中控之外直连 sidecar 属调试通路，不产生执行事实」；
- **验收**：非白名单来源连接被拒；未带密钥的请求被拒；默认 bind 不再是全网卡。

### 4.6 gateway Redis：队列写入权收口 + 命令签名（第 10 轮新增）

- **写入权隔离**：Redis 启用 ACL + 强口令，**只有中控服务账号**可写命令队列；设备/办公网账号只读或无权限；
- **命令签名**：中控写入的命令消息带 HMAC 签名（密钥与 Redis 口令分离）；网关验签失败 ⇒ 丢弃 + 告警 + 审计；
- **网络隔离**：生产 Redis 不暴露到办公网/设备网（与 §4.5 的 bind 收口同属纵深防御）；
- **注意口径**：网关「不做权限」是**它的职责边界**（README 已声明），因此**权限必须在队列入口侧收口**，不能指望网关代做；
- **文档**：`labos-gateway/README.md` 的「redis-cli 塞一条命令就能试」必须改为**仅本地 profile 适用**，生产环境操作手册写明禁止手工写队列。

## 7. 与 v4 / 评审的对应

- v4 §8.4 的 **6 条通路**（第 1/2/5/6 项 = 四条处置对象，第 3/4 项 = 配置文档/回归）对应本方案 §2 的 P1-P4 + P6/P7 与 §3 的完成判定 1-8；
- **P5「CLI/demo」不计入 6 条**：测试/演示入口、非 HTTP、不产生新的越权面，按 §4.4「仅文档声明」处理（见 §9 裁决 6）；
- 第 7 轮 openai P2-05「ShadowRunner/单命令探针真实设备保护边界」= §4.2/§4.3；
- 第 7 轮 08-deepseek 的「执行通路缺口」= P1/P2/P3/P4 清单与 §3 完成判定；
- 本方案不代替 v4 §3 的统一执行器改造：flow-run 未来若恢复，必须走与 execute 相同边界（另一轮评审）。

## 8. 明确不做

- 不删除 ShadowRunner / ShadowProbe / ExperimentFlowRunner 代码（保留能力，第一版只关入口）；
- 不新建物料处理逻辑、不改执行引擎；
- 不因关闭调试通路而修改现场已有的只读监控/点位读取需求（按 §4.3 单独开关）；
- **不改造 sidecar 的设备协议层、不改造 gateway 的设备长连接逻辑**——本次只收口「谁能命令它们」（bind/鉴权/队列写权限），设备侧行为保持不变；
- **不把 P6/P7 纳入 S0-design 冻结范围**：它们属于 S0-safety 的**实施**项（改部署与鉴权），设计稿只负责把「通路盘点完整」这件事做对。

## 9. 待评审决策点裁决（2026-11-12 · 第 11 轮 E7，逐条裁决，无未决项）

1. **非生产环境是否默认放开 shadow 通路** → **裁决：local/sim profile 放开，production 默认拒绝**（`labos.safety.shadow-run-enabled` / `labos.safety.device-probe-enabled` 默认 `false`；仅 local/sim profile 显式置 `true`；生产部署检查清单强制 `false`）。
2. **调试权限用 admin 还是新增 debug 角色** → **裁决：第一版用 admin**（不新增 `debug` 角色；复用现有 `RbacRules` 的 admin 判定，避免扩 RBAC 面；后续如需细粒度调试角色走 CR）。
3. **flow-run 用 404 还是 410** → **裁决：404（移除路由）**（前端无调用，移除 `@PostMapping("/experiments/flow-run")` 最干净；`ExperimentFlowRunner` 类保留不删，未来恢复走统一执行器）。
4. **robot-points capture 是否保留为可选只读通路** → **裁决：保留，但并入 `device-probe` 开关**（默认拒绝、admin + env 才可用；属真实设备读取动作，按统一口径收口）。
5. **前端调试入口隐藏还是禁用+提示** → **裁决：开关关闭时隐藏调试入口；开启时显示「调试模式」标识 + 二次确认**（隐藏降噪 + 提示保审计，一并做）。
6. **P5「CLI/demo」是否属 6 条通路之一** → **裁决：不计入 6 条**（非 HTTP 入口、不产生新的越权面、只服务测试/演示；按 §4.4 仅文档声明）。**口径消歧**：§8.4 的「6 条」= 4 条 HTTP（P1-P4）+ 2 条非 HTTP（P6/P7）；§2 现状清单 P1-P7 共 7 行（多出 P5）；§3 完成判定 8 条（第 7/8 条对应 P6/P7，第 1-6 条对应 P1-P4 的收口）。三者互不矛盾。
