## 2. 逐条核实与裁决

### 2.1 三份共识（4 条）

#### 第 1 条：D-06 的 hold 生命周期不完整

**三份都说**：只写了"派发前建租约、按 `command_id + hold_epoch` 清除"，没写 epoch 何时递增、怎么持久化、重复完成事件怎么办、ACK 丢失重启后怎么恢复。

**核实**：总表 D-06 只有 7 行步骤，确实没有生命周期定义。

**裁决：采纳。** 补完整语义：

| 项 | 定义 |
|---|---|
| **申请** | 派发前原子申请；记录 `tenant_id / device_id / owner_command_id / hold_epoch / state` |
| **epoch 递增** | 每次成功建立新租约 +1；**持久化**，不能只在内存；同一设备严格单调 |
| **释放** | 条件匹配：`(tenant, device, command_id, hold_epoch)` 全中，且当前 `state IN ('ACCEPTED','EXECUTING','UNKNOWN')` |
| **重复完成事件** | 幂等：不影响新租约（epoch 不匹配即无效） |
| **ACK 丢失** | → `UNKNOWN`，**不释放** |
| **重启恢复** | `RESERVED`/`UNKNOWN` 状态的租约保留，靠 `queryStatus` 对账，不靠内存 |

**它给的最小 DDL 我采纳**：

```sql
device_physical_hold (
  tenant_id, device_id,
  state,                 -- RESERVED / ACCEPTED / EXECUTING / UNKNOWN / RELEASED
  owner_command_id,
  hold_epoch,            -- 设备占用代次，每次新建 +1
  established_at, expires_at, released_at
)
```

**并明确**：设备占用账本**独立于** `device_event` 表，不能用事件表代替租约事实源。

#### 第 2 条：D-05 的 30 分钟会截断长动作

**三份都说**：`MethodTimeoutPolicy` 有 `INCUBATE=1800s`（30 分钟）、`THERMOCYCLE=3600s`（60 分钟）、`CENTRIFUGE=900s`（15 分钟），默认 30 分钟会截断 60 分钟级的合法 busy。

**核实**（`MethodTimeoutPolicy:49-51`）：**全部成立**。30 分钟恰好等于 `INCUBATE`，但 `THERMOCYCLE` 是 60 分钟。

**裁决：部分采纳。**

**不采纳"默认取 `max(method_timeout, ...)`"**，理由：

| 概念 | 含义 | 该取什么 |
|---|---|---|
| **资源等待上限** | B 愿意为等 A 释放设备付多久 | **业务意愿**，不是设备能力 |
| 设备执行上限 | A 最多跑多久 | 方法超时 |

如果取 `max`，B 要为 A 的 60 分钟 PCR 等满 60 分钟——**在多并行下这是浪费**，B 完全可以转人工或换设备。

**但三份的提醒是对的：我表述不清。** 采纳它们的写法：

```
D-05：资源等待上限（可配置，默认 30 分钟）
  ≠ 设备执行上限（按方法，INCUBATE 30min / THERMOCYCLE 60min / CENTRIFUGE 15min）

B 超时只终止 B 的等待：
  → B 转人工 / 换设备
  → A 的租约不受影响，继续执行
  → 不释放、不改写 A 的任何状态
```

**默认值 30 分钟保留**，但补一句"若现场存在 60 分钟级工艺且设备紧张，按并行度调大到 90 分钟以上"。

**并记入变更记录**：15 分钟 → 30 分钟，**是正式参数变更**，不是笔误。

#### 第 3 条：H-03 只共享 `variables` + `stopFlag` 不够

**三份都说**：`GraphRunner` 还有 `locallyWrittenVars:126`、`consumedValues:142`、`externallyOwnedVars:156`，如果只共享 `variables`，刷新/消费语义会跑偏。

**核实**：三个字段确实存在，且 `writeVar`（`:162-163`）先查 `externallyOwnedVars` 再改 `locallyWrittenVars`，`refreshVariables`（`:1411`）读三个容器。

**裁决：采纳。** 补完整所有权表：

| 状态 | 所有权 | 说明 |
|---|---|---|
| `variables` | **流程级共享** | 同名写冲突编译期禁止 |
| `stopFlag` | **并行组级共享** | 任一分支失败触发 |
| `consumedValues` | **流程级**（随 variables 一起） | 去重语义跟着变量走 |
| `eventCursors` | **流程级**，但需单调推进 | 不能被后完成的线程覆盖成较小值 |
| `visits` | **分支局部** | 循环轮次按分支独立 |
| `done` | **分支局部** | 否则 A 做过的节点让 B 跳过 |
| `progress.aborted` | **与 `stopFlag` 统一** | 避免两套停止信号 |

**并删除**并行网关文档里"6 个字段换 `ConcurrentHashMap`"的旧描述——那是笼统说法，会误导实施。

#### 第 4 条：A-04 的论证不严谨

**三份都说**：我写"`commandId` 在重试中不变 ⇒ 一个 operation 只有一个命令 ⇒ 一对多不存在"，这是逻辑跳跃——重试复用只能证明"重试用同一身份"，不能证明"一个操作只产生一条命令"。

**裁决：采纳。** 改为模型约束而非推论：

> 本设计规定：**一个 `logical_operation` 表示一次独立的物理设备动作**，其身份由 `operation_id` 持久化，一个 operation 对应一个 `command_id`。
>
> 若业务需要多个独立物理动作，应**分别建立多个 `logical_operation`**，而不是一个 operation 产生多个 commandId。
>
> 这是**业务模型的定义**，不是从重试规则推导的结论。

**并写明触发条件**（ChatGPT 建议）：如果某天某设备要求"一次意图两步完成"，会以**现场事故**形式出现——那时才需要引入子表，不是现在预先建。

#### 第 6 条：QUARANTINED 恢复缺物理安全门槛

**Trae + ChatGPT**：H-02 说超 `drain_timeout` 进 `QUARANTINED` 不自动释放，E-05 又说允许进恢复链——**允许进恢复链 ≠ 允许直接恢复执行**。

**裁决：采纳。** 补恢复状态机：

```
QUARANTINED
  → 人工发起恢复
RECOVERY_CHECKING
  ├─ 设备状态无法确认 → 回 QUARANTINED
  ├─ 物理位置无法确认 → 回 QUARANTINED
  ├─ 上一条命令 UNKNOWN → 人工处置
  └─ 四项核对通过（E-04）
RECOVERY_APPROVED
  → 恢复到安全执行边界
```

**硬约束**：
- 数据库 `run.status` 可恢复 ≠ 设备物理安全
- **不得自动释放旧租约**
- 人工确认必须记录操作者、时间、证据、处置结果

#### 第 7 条：I-02 与 I-03 的原子性矛盾

**Trae + ChatGPT**：I-02 要求"准入与插入同事务"，I-03 又说"E-05 禁同事务内联，改事务外先准入"——**两步不在同一临界区，就会重开 TOCTOU**。

**核实：成立，而且这是我自己的矛盾。**

**裁决：采纳，取 ChatGPT 的方案 A 优先。**

| 方案 | 做法 | 评价 |
|---|---|---|
| **A 统一锁序** | 重构 `E-05` 事务，按 `workflow → experiment → run` 取锁，准入与创建保持原子 | **优先评估** |
| B 准入预留 | 独立事务建 `admission_reservation`，后续事务消费 | A 做不到时用，需定义唯一性/状态机/失败回收 |
| C 重构互斥模型 | 其他机制 | 必须重新证明并发正确性 |

**明确禁止**："事务外检查准入、事务内稍后创建"的无保护模式。

#### 第 8 条：D-03/D-04 对"查不到"定义不清

**Trae + ChatGPT**：`D-04` 写"查不到 → 按 D-03 的 fail-open"，但"查不到"有三种完全不同的情况。

**裁决：采纳。** 补判定表：

| 场景 | 判定 | 处理 |
|---|---|---|
| 设备未配置状态采集能力 | 事实源缺失 | **fail-open** + SKIP 审计 + 不可并行标记 |
| 已配置，返回 `idle` | 状态明确 | 放行 |
| 已配置，返回 `busy` | 状态明确 | 释放锁，等待重查 |
| 已配置，返回 `unknown` / 数据过期 | 状态不确定 | **fail-closed** |
| 已配置，但查询超时 / 连接失败 / 接口异常 | **查询故障** | **fail-closed** |
| 配置项本身不存在 | 事实源缺失 | 按第一行处理 |

**一句话原则（采纳它的原话）**：

> **"没有配置这项能力"可以跳过；"本来应该有能力，但现在拿不到结果"不能当作没有配置。**

#### 第 9 条：K-01 的闸门范围

**Trae + ChatGPT**：说"K-01 是唯一开工闸门"容易被理解为"其他都能启动"。

**裁决：采纳。** 改为：

> K-01 是 **`RunAdmission` 模块**的唯一直接开工闸门。其他待定项分别阻塞各自模块：K-02 阻塞唯一索引、K-03 阻塞事件表、K-04 阻塞物理态、D-06 阻塞设备租约、E-05 阻塞恢复模块。

#### 第 10 条：C-01 的 commandId 生成规则

**Trae + ChatGPT**：总表说"`commandId` = 逻辑操作唯一标识"，但规范里还有旧公式（缺 `branch` / `invocation` / `generation`），实施会照抄。

**裁决：采纳。** 明确：

> **`operation_id` 是持久化权威身份；`command_id` 与之**一一映射**。**
>
> 不得从 `branch` / `step` / `process` 等字段临时拼接后作为权威身份。

**推论**：`commandId = operation_id`（或由它确定性派生），各模块不再各自拼字符串。

### 2.3 ChatGPT 独有（5 条，其中 3 条最狠）

#### 第 11 条 ⭐ B-04 的依据句与 B-01 直接冲突

**它说**：

> B-04 写"依据：A 释放后 B 持有，A 的迟到事件会被判给 B ⇒ 推进错误流程"。**但那是 B-01 之前的行为。**
>
> 按 B-01 推：设备不回显 commandId ⇒ 所有事件 `e.command_id IS NULL` ⇒ B-01 要求 `IS NOT NULL` ⇒ **匹配不到任何 waiter** ⇒ B-03 落 `UNATTRIBUTED` ⇒ **不会推进错误流程**。

**核实：完全成立。这是我引错了行为。**

正确的因果链是：

```
设备不回显 commandId
  → 该设备所有事件 command_id = NULL
  → B-01：IS NOT NULL 条件不满足
  → 匹配不到任何 waiter
  → B-03：落 UNATTRIBUTED
  → 流程无法自动推进（不是"推进错"）
```

**裁决：采纳，且推论要升级得更硬**：

> **不回显 `commandId` 的设备只能走"同步命令型"流程**（命令返回即结果）。
> **流程里若含 `__awaitEvent`，该流程在这台设备上不适用**——不是"降级运行"，是"不能运行"。

**这条推论很重**：提取线是 `n_pick`（命令）→ `n_wait`（`__awaitEvent`）→ 所以**提取线对不回显 commandId 的设备完全不适用**。

**连带结论**：规范 §5.3 现在写"若能确定…回填"是**条件式措辞**，应改为**硬要求**：

> 侧车必须为自发事件回填触发它的 `commandId`；无法回填的设备不得进入依赖 `__awaitEvent` 的流程。

#### 第 12 条 ⭐ K-01 应拆条，唯一索引不是"四选一"

**它说**：

> I-03 的处置是"改事务外先准入"⇒ 事务外准入 + 事务内插入 ⇒ **两步不在同一临界区** ⇒ 行锁 / advisory / SERIALIZABLE 都覆盖不了 ⇒ **只有唯一索引能兜住**。

**核实：完全成立，这是我的逻辑漏洞。**

我原来把"行锁 / advisory / 唯一索引 / SERIALIZABLE"并列成四选一，但它们**适用的场景不同**：

| 候选 | 覆盖"事务外检查 + 事务内插入"的窗口 |
|---|---|
| 行锁 | ❌ 两次取锁不同事务，中间可插入 |
| advisory lock | ❌ 同上 |
| SERIALIZABLE | ❌ 跨事务无法保证 |
| **唯一索引** | ✅ **只有它** |

**裁决：采纳，拆成两条**：

| 编号 | 内容 | 性质 |
|---|---|---|
| **K-01a** | 唯一约束的**形态**（`(tenant, workflow, active_slot)` 还是别的） | **真·开工闸门** |
| **K-01b** | 锁策略（行锁 / advisory 等，用于减少冲突重试） | 可后定，不急 |

**这样"唯一真正的开工闸门"这句话才准确。**

#### 第 13 条 ⭐ G-05：提取线 4 条分支共用同一台臂，真并发收益≈0

**它说**：`n_scan`(`:470`)、`n_move`(`:490`)、`n_done_scan`(`:499`) 全是 `resource=arm`，而 `arm` 是分支循环外的单一变量 ⇒ 4 条分支的 12 次臂操作排在**同一台机械臂**上 ⇒ 按 9.33 秒/次 ≈ **112 秒串行下限**。

**核实**：脚本里 `resource=arm` 出现 **5 次**（470/490/499/553/558），全部指向同一变量。

**裁决：采纳，且这是最该早看到的一条。**

**结论**：

> **真并发在提取线上收益≈0**——省下的只是"臂排队"，而臂本来就是串行的。设备是"受理即返回"本来就不占时间。

**新增 G-05**：

> 并行收益的前提是"**分支用不同设备**"。同一台瓶颈设备上的多分支只是把排队从流程层挪到锁层。

**连带**：G-03 的 capacity 向下取整要定死。`WorkflowWebService:287` 记"可并行 run 数 ≈ 1.9" ⇒ **向下取整 = 1** ⇒ 机械臂实际串行，与 G-05 同一结论。

**并建议**：先确认现场**有几台臂**，再决定要不要做真并发。如果只有一台，run 内并发的工程投入没有回报。

#### 第 14 条：E-03 的 `control_state` 挂错表

**它说**：`control_state` 在 `experiment_run`（`:3249`），`run` 表只有 `pause_kind`。且总表的取值集（`pause_requested/pausing/pause_blocked/paused`）与 ADR 的（`NONE/PAUSE_REQUESTED/PAUSING/RESUMING`）**多一个少一个**。

**核实**：`control_state` 在 `99c_pause_control.sql:26` 的 **`experiment_run`** 表，值域 `NONE/PAUSE_REQUESTED/PAUSING/RESUMING`。总表写 `run.control_state` **是错的**。

**裁决：完全采纳。**

| 项 | 改动 |
|---|---|
| 落点 | `run.control_state` → **`experiment_run.control_state`** |
| 取值集 | 统一为 ADR 的四个 + 新增 `PAUSE_BLOCKED`，并**一次性定死** |
| 聚合 | experiment 级中间态 = 各 run 状态聚合的**视图**，不独立双写 |

**取值集最终定义**（一次性）：

```
NONE              -- 无暂停请求
PAUSE_REQUESTED   -- 已请求，未生效
PAUSING           -- 部分确认
PAUSE_BLOCKED     -- 有 run 无法确认（需 blocking_run_id）
PAUSED            -- 全部确认
RESUME_REQUESTED  -- 恢复请求
RESUMING          -- 恢复中
```

#### 第 15 条：E-05 编号歧义

**它说**：总表的 `E-05` 是"QUARANTINED 恢复决策"，而 I-03 里的 `E-05` 是"`createNextBatchAttempt` 入口编号"——两个不同概念用了同一编号。

## 3. 我不同意的部分

### 3.1 不同意"D-05 默认取 `max(method_timeout, ...)`"

MiniMax 建议：

> 改成"默认取 `max(method_timeout, capability_default)`，30 分钟只作为无模型时临时兜底"。

**不同意的理由**：

这是把**资源等待**和**执行时长**两个概念又混在一起了。

```
A 在执行 60 分钟的 THERMOCYCLE
B 申请同一设备
```

- 按 `max`：B 要等 60 分钟
- **但 B 完全可以转人工或换设备**

**资源等待上限是"愿意等多久"，不是"设备最长跑多久"。** 取 max 等于说"B 必须等满 A 的全部执行时间"，那在多并行下是纯浪费。

**但保留它们的提醒**：默认值要写明"若现场有 60 分钟级工艺且设备紧张，按并行度调大"，并且**明确 B 超时不影响 A**。

### 3.2 部分同意"G-05 收益≈0"

ChatGPT 的核算对**提取线**成立（5 处 `resource=arm`）。

但结论应该限定为：

> **提取线**的 run 内并发收益≈0，因为 4 条分支共用一台臂。

**不能推广成"所有流程的 run 内并发都没收益"**——如果某个流程的分支用的是**不同设备**（比如 4 台提取仪并行），收益是真实的。

所以 G-05 的表述应该是：**并行收益的前提是"分支用不同设备"**，而不是"并行没意义"。

## 6. 我的回复

### 6.1 三份里最该被记住的两句

**ChatGPT 的**：

> 这两条不是文档洁癖，是**会被照做的错误实现指令**。

这句话解释了为什么"总表说以我为准"没有用——**实施者不会去查总表，他会打开离他最近的那份文档照抄**。所以源文档的旧口径必须改掉，不是标注"已被取代"就行。

**MiniMax 的**：

> 把中控数据库租约等同于设备物理互斥。

这是对我 D-06 的提醒：租约只保证"中控内部不再下发"，不保证"设备物理上没在执行别人的命令"。

### 6.2 我自己犯的两个逻辑错误

**错误一：B-04 的依据引错了行为。**

我写"迟到事件会被判给 B ⇒ 推进错误流程"，但那是在 B-01 之前的模型。按 B-01，无 commandId 的事件**根本匹配不到**任何 waiter，所以是"不推进"，不是"推进错"。

**两个后果不同**：前者是"做错事"，后者是"做不了事"。后者更保守、更安全，但**更致命**——它意味着含 `__awaitEvent` 的流程在这类设备上**完全不能跑**。

**错误二：把"唯一索引"当成四选一之一。**

我在 I-03 里写"禁止 E-05 同事务内联，改事务外先准入"，然后在 K-01 里把"唯一索引"和"行锁/advisory/SERIALIZABLE"并列。但事务外准入 + 事务内插入这个结构，**只有唯一索引能兜**。其余三个在两次取锁之间都有窗口。

**这两个错误的共同点**：我写结论时没有把新结论代回旧前提验算一遍。

### 6.3 我不同意的一点，以及为什么

见 §3.1：**不同意"资源等待上限取 `max(method_timeout)`"**。

理由是把"愿意等多久"和"设备最长跑多久"又混在一起了。B 等 A 的 60 分钟 PCR 时，B 转人工是**正确**的——资源等待上限本来就是业务意愿，不是设备能力。

但我承认表述不清，已按它们的写法补"**B 超时不影响 A**"。
