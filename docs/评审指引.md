## 一、这是什么

**LabOS实验室中控系统**——面向生物医药实验室的自动化控制内核。
控制对象：孵箱、机械臂、离心机、酶标仪、挪板机等，通过 TCP/JSON 与厂商驱动通信。

**核心能力**：

```
实验定义（多流程 + 变量 + 循环）
    ↓
调度（多实验并行，岛级互斥）
    ↓
流程执行（BPMN 图 → 节点 → 设备动作）
    ↓
板位跟踪（哪个位置有哪块板 + 抢占防冲突）
```

**规模**：

|---|---|---|

| 设备网关 `labos-gateway/` | 3 | 794 |
| 前端 `webapp/` | — | 5,747 |

## 三、怎么跑起来

### 依赖

- PostgreSQL `192.0.2.1:5432`（库 `labos`，用户 `labos`）
- Redis `192.0.2.1:6379`（网关状态中心）
- JDK 17（无第三方依赖，只有 `postgresql-42.7.3.jar`）
- Node 18+（前端）

### 启动

```bash
# 1. 内核（端口 18080）
cd labos-kernel
javac -encoding UTF-8 -d out $(find src -name '*.java')
java -Dfile.encoding=UTF-8 -cp "out:lib/postgresql-42.7.3.jar" \
     com.labos.kernel.api.ApiServer 18080

# 2. 前端（端口 5173）
cd webapp
npm install && npm run dev

# 3. 设备网关（可选，长连接模式）
cd labos-gateway
LABOS_REDIS_HOST=192.0.2.1 \
LABOS_GATEWAY_DRIVERS="DRV-A=tcp://192.0.2.10:8501" \
java -cp out com.labos.gateway.GatewayMain
```

### 验证

```bash
# 回归（应全绿）
cd labos-kernel
for t in recovery.RecoverySelfTest engine.EngineSelfTest alert.AlertSelfTest \
         workflow.WorkflowAlertTest workflow.GraphRunnerTest; do
  java -cp out com.labos.kernel.$t
done

# 工艺全量（流程在仿真总线上按图走）
# 注意：这是 SimulatedBus 走图，不是真设备验证
java -cp "out:lib/postgresql-42.7.3.jar" \
     com.labos.kernel.workflow.RealWorkflowRunner --all
```

### 登录

`admin` / `admin123`

## 四、代码地图

```
labos-kernel/src/main/java/com/labos/kernel/
├── api/             HTTP 接口（ApiServer 巨类 ~1500 行，QueryService 查询）
├── workflow/        流程：解析 BPMN、编译、执行、实验编排、调度
│   ├── WorkflowService      核心（执行、变量替换、候选池）
│   ├── ExperimentExecutor   实验执行（变量 + 循环展开 + 顺序跑）
│   ├── ExperimentScheduler  多实验并行（岛锁 + 排队）
│   ├── GraphRunner          按 BPMN 图执行
│   └── ExperimentFlowRunner 画布逐步执行（落 run/run_node/run_command）
├── engine/          状态机（RunStateMachine：重试、转人工、幂等）
├── driver/          设备驱动
│   ├── DeviceDriver         接口
│   ├── tcp/TcpDriverAdapter 短连接
│   ├── tcp/TcpPersistentDriver 长连接（按 messageId 配对）
│   ├── PositionLock         位置锁（原子抢占、搬运双锁）
│   └── ShadowProbe          单命令探针（影子模式）
├── recovery/        崩溃恢复决策（RecoveryDecider）；崩溃收尾在 workflow/StartupRecovery
│                    注意：没有"租约接管"机制（设计里提过，实际未实现）
├── alert/           告警（生成、去重、合并）
└── redis/           手写 RESP2 客户端

├── GatewayMain             入口（每驱动一消费线程）
├── driver/DriverConnection 长连接 + 写 Redis
└── redis/RedisClient       手写 RESP2

webapp/src/pages/
├── Island.tsx          岛屿视图（拖拽布设备、搬运序列、板位可视化）
├── Experiments.tsx     实验编排（变量表格、循环、执行历史）
├── ExperimentCanvas    实验画布（React Flow，跨流程编排：开始/结束/流程）
├── IslandFlow.tsx      岛屿编排（设备连线 = 搬板）
└── ...                 流程库、设计器、执行监控、告警等
```

## 六、已知问题（**评审重点**）

### 🔴 严重：`putPlate` 不落库（未解决）

```
现象：日志显示 [PLATE] Deposit1 dev=171 -> pos=504495
      但 position_state 表里没有这行
```

**已排除**：
- UPSERT 语句本身正确（手动执行 `INSERT 0 1` 成功）
- 参数序号正确
- 无异常日志

**下一步**：查 `putPlateInternal` 的 `c.commit()` 是否在 `if (n > 0)` 分支外。

**影响**：板位跟踪整条链路（可视化、预检、真实板号）都建立在不可靠数据上。

### 🟡 两套 ID 混用（反复出错 5 次）

```
device_instance.id (214)   ← 驱动/探针认这个
resource_node.id (200214)  ← 图/执行记录/位置认这个
```

**踩过的地方**：候选池、驱动注册表、板子动画、`ExperimentFlowRunner`、点位读坐标。

**现状**：各调用点用 `instanceIdOf()` 转换，但**没有类型层面的隔离**（都是 `long`）。

**建议**：引入 `DeviceInstanceId` / `ResourceId` 值类型，从编译期杜绝。

### 🟡 执行路径有两条，行为可能不一致

| 路径 | 入口 | 用途 |
|---|---|---|
| `WorkflowService.execute` → `GraphRunner` | 流程执行 | BPMN 图 |
| `ExperimentFlowRunner.run` | `/api/experiments/flow-run` | 画布逐步执行 |

**两者都落 `run`/`run_node`/`run_command`，但设备分配、变量替换逻辑是两套代码**。

**风险**：改了一处忘了另一处。

### 🟡 调度器是 2.0 简化版

- 岛级互斥（并行度 = 岛数）
- 贪心排序（EDD → 优先级 → FIFO）
- **没有实现设计文档里的滚动时域**

**文档写了 DP 不可行的论证，但代码没实现替代方案**——这是最大的"文档与代码差距"。

### 🟡 长连接不支持"运行中"状态

```java
if (method_status == 1) {
    return failed("设备仍在运行，需要更长超时或异步上报");
}
```

**真机上孵育可能要 30 分钟**，现在会直接判失败。

**补充**：默认仍是短连接，`TcpDriverAdapter` 把所有 `method_status != 2` 当失败，
**这个问题不限于长连接**。

### 🟡 进度语义有瑕疵

`current_seq` 是"正在跑第几步"（1-3），不是"完成了几步"。
前端显示 `3/5` 实际意思是"在跑第 3 步"，不是"完成 3 步"。

### 🟢 `markPlatePosition` 已废弃但可能还有引用

已改成空方法（注释说明原因），如果别处还在调会静默无效。

### 🟢 `ApiServer` 是 ~1500 行的巨类

路由、参数解析、JSON 拼装全在一起。评审时可以看它有多少个 `if (path.equals(...))`。

## 七、工程实践问题（也是评审点）

### 反复出现的"以为改了其实没改"（4 次）

| 现象 | 根因 |
|---|---|
| 编译假象 | `grep error` 匹配不到中文"错误"，多轮假通过 |
| 参数序号错 | `ps.setLong(13, ...)` 实际是第 12 个，静默写 NULL |
| `replace` 锚点不匹配 | `s.replace(old, new)` 静默返回原串（3 次） |
| 多进程抢驱动 | `pkill -f` 没杀干净，残留进程占着连接 |

**现在的硬性检查**：

```bash
# replace 后必须确认
python3 -c "print(s.count('新代码'))"   # 非 0
# 编译后必须用中文
javac ... 2>&1 | grep "错误"
# 清理进程后必须看连接
lsof -i :19301
```

### 测试策略存在但执行不完整

`docs/测试与上线策略.md` 定义了五层验证（单元→探针→影子→分段→灰度）。

**实际只有 L1（单元）和 L2（探针）在跑**，L3 影子有接口但没形成例行检查。

## 八、评审建议

### 高价值的评审角度

| 角度 | 看什么 |
|---|---|
| **正确性** | `PositionLock` 的原子性、搬运双锁的死锁论证、`GraphRunner` 的设备轮转 |
| **数据一致性** | 两套板位状态（已部分统一）、两套 ID、双路径执行 |
| **失败处理** | 超时后是否中断、预检失败是否阻断、幂等键是否贯穿 |
| **可观测性** | `run_command` 是否够查问题、日志是否够定位 |
| **文档与代码一致性** | 尤其调度器（文档写了滚动时域，代码是贪心） |
| **安全边界** | 不用 eval、参数校验、权限 |

### 不用太在意的

- 前端样式细节（演示级）
- `ApiServer` 的代码风格（已知是巨类）
- 测试覆盖率数字（重点看关键路径有没有测）
