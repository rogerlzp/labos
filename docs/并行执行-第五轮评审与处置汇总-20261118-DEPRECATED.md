## 4. 逐项处置说明

### 4.1 原子准入（P-01 / P-02 / P-12 / P-14）

**P-01 已改，但改法仍需评审确认。**

v1 的伪代码是：

```java
Decision d = gate.check(...);        // 事务外
if (!d.allowed()) return rejected;
return inTransaction(c -> { ... });  // 事务内只有插入
```

v2 改成：

```java
GuardedStart.Result start(StartRequest req) {
    return inTransaction(c -> {
        Decision d = gate.checkInTx(c, tenant, workflow, req.excludeRunId());
        if (!d.allowed()) { rollbackOnly(); return Result.rejected(d); }
        ...
    });
}
```

**但"移进事务"不等于"有并发正确性"**。ChatGPT 的要求是对的：必须指定数据库互斥点（行锁 / advisory lock / 唯一索引 / SERIALIZABLE 之一），否则两个事务仍可能同时读到"无 active"。

**这一条目前只改到"形式正确"，没改到"证明正确"。** 我在 §8 列为未闭合。

**P-02 部分处置，待 H-09。**

② §4.2 的 active 集合取了 `('queued','running')`，**排除 `paused`**。理由：代码里两条路径本来就打架——

| 路径 | 现在怎么对待 paused 批 |
|---|---|
| 同步 `runBatch` | 只拒 `completed`，**paused 批可以重跑** |
| 异步 `activeBatchAttempt` | 把 paused 当占用，不许新建 |

唯一索引会强制其中一种。选"排除 paused"是保同步路径。**这是产品语义取舍，不是技术判断**，标为 H-09 待业务确认。

**P-12 已改**：步骤 6/7 对调，先做事务边界，再加唯一索引。理由是"先加索引会打掉现有的合法路径"（paused 重跑）。

**P-14 已改**：② 出 v2，563 行，修订记录在文档头部列出 7 项改动，并新增 §0 冲突优先级表（§4.3/§4.4/§4.5 以 ③ 为准）。

### 4.2 事件归属（P-03 / P-07 / P-10）

**P-03 已改，且改对了。**

MiniMax 的核对最关键：现有 `ensureRunCursor`（`DeviceEventMapper.xml:49-57`）是 **run 级固定基准**——首次取 `MAX(id)`，resume 时 `DO UPDATE SET base_event_id = 原值`，这正是"不丢早到事件"的机制。

如果按 v2 的"建 waiter 时取 MAX(id)"，早到事件 id 更小，会被 `w.base_event_id < ?` 排除 → 必丢，而 W-05 恰恰要求"不丢"。

v3 改为：waiter 继承 run 级基准，`device_event_run_cursor` **保留**（不再 deprecated）。

这个修正是对"精确性"和"不丢"两个维度冲突的正确处理——**不能为了精确而牺牲不丢**。

**P-07 已改**：`FOR UPDATE SKIP LOCKED` 的问题在于它会把"3 行匹配、2 行被锁跳过"伪装成"恰好 1 行"，从而推进错误的流程。v3 改为**先无锁判唯一、再上锁更新**。

这个改法是必要的：`SKIP LOCKED` 适合"抢任务"，不适合"判唯一"。

**P-10 部分处置**：字段定义仍分散。③ 有 `attribution_state`、`device_boot_id`，② 有 `command_id`、`device_event_seq`。**尚未形成一份唯一 DDL**，这是下一版必须合并的。

### 4.3 命令语义（P-04 / P-06）

**P-04 已改，方向统一到保守侧。**

② 三处旧表述（第 223、276、381 行）全部改为"落 UNKNOWN，转人工，不重发"，C-03 改口径，C-05 改为"拒绝，转人工（除非设备已验证去重且经 HIL）"。

两份评审的判断一致：`NOT_FOUND` 可能意味着"设备执行了但查询不可见"（重启丢账本、查询接口只查当前队列、可见性延迟），**不能当作"可以安全重发"**。

**P-06 部分处置。**

③ §1.2 澄清了 `run_node.attempt`（节点轮次）与 `logical_operation.attempt_no`（传输次数）不同。**但 `command_ledger.attempt` 继承 `run_node.attempt` 这一行仍在**（③ 第 61 行），而 ChatGPT 指出：如果一次节点执行里有多次传输，`command_ledger.attempt` 全是同一个值，无法区分。

§4.2 对账 SQL 加了"迁移期口径前置条件"和第四条检查，但**迁移期的全量误报问题只被"声明"、未被"消除"**——因为现有 `command_ledger.command_id` 含 `exec`（每次都变），与新的稳定 `command_id` 永远 JOIN 不上。

### 4.4 时间模型（P-05）

**已改，但只改了一半。**

v2 删掉了"只要收到 ACK，等待是安全的"这个绝对表述，补了 §4.5.2 设备锁占用看门狗。

**但"执行进展监测"这个维度没有独立落地。** ChatGPT 的原文很关键：

> 收到 ACK 只能证明设备接受了命令，不能证明设备仍在执行，更不能证明物理过程正常。

当前只有"业务期限告警 + 设备锁看门狗"，**没有"设备是否还在产生进展"的判断**。设备 ACK 后卡死、心跳正常、锁被占着——这三种情况叠加时，系统只能靠看门狗超时释放锁，但无法区分"还在跑"和"已经死了"。

这一条我在 §8 列为未闭合。

### 4.5 锁顺序（P-08）

**部分处置，但 MiniMax 给了一个重要结案。**

它核实的实现事实：

| 事实 | 证据 |
|---|---|
| 轨道分区锁复用 `DeviceLock.tryAcquire(z)` | `RailZoneGuard:92-98` |
| 位置也是 `resource_node.id` | `PositionLock:206` |
| 一个 id 只有一个 kind | `resource_node.kind` |

⇒ **同空间、不冲突**，真正跨类互等的只有 `device_state` ↔ `position_state` 一组。

所以 v2 把 `ResourceType` 从三值**简化为两组**，并改成**按 `resource_node.kind` 推导类型**，不再依赖开发者传对枚举——这恰好解决了"未来新增路径会破"的根因。

另一处修正也很关键：**`ThreadLocal<Deque>` 栈式模型会误报**，因为 `RailZoneGuard` 是批量申请/批量释放，没有 push/pop 配对。改成"单变量记录最高 rank"。

**仍未闭合**：三类资源的生命周期（设备锁随 step、位置可跨 step、轨道仅运动窗口）没有形成完整表格。这是 R5-08 的核心，也是"板占着位置但没人能搬"这类问题的根源。

### 4.6 其他（P-09 / P-11 / P-13）

**P-09 已改**：④ §4.5 加上 `quarantined`。不改的话，被隔离的 run 永远无法恢复，且会永久占住唯一索引的 active slot。

但 ChatGPT 要求的"Resume 状态转移表"（逐个状态列允许/禁止）**尚未形成**，只有 SQL 的 `IN` 列表。

**P-11 不动，且是有意的**：① 是事实基线，改它会污染后续所有判断。两份评审都标 UNKNOWN，接受。

但两条建议已采纳：
- 删除"约 70% 的能力已经存在"这类无权重模型的百分比
- 把"三类锁已有"拆成六行细分能力

**P-13 已改**：④ §4.2 沿用现有 `200 + {error, errorCode}` 形状，不改 4xx。理由：`WorkflowWebService:289-298` 现在就是 200 + JSON，前端按 `error` 字段判，改成 4xx 会破坏契约——这恰好和 ④ §0 的"不改变 HTTP 契约"对齐。
