# 设备状态与心跳 — 设计

> 三件事：**设备在不在线**（心跳）、**设备在干什么**（三态）、**执行完返回了什么**（结果）。

---

## 一、两个维度的状态

一台设备有**两个独立**的状态，不能混：

| 维度 | 字段 | 取值 | 含义 |
|---|---|---|---|
| **通不通** | `device_state.online` | `true` / `false` | 心跳能不能探到 |
| **在干什么** | `device_state.status` | `idle` / `running` / `error` | 当前任务状态 |

**四种组合都有意义**：

| online | status | 含义 | 怎么办 |
|---|---|---|---|
| ✅ | idle | 在线空闲 | 正常，可以分配任务 |
| ✅ | running | 在线执行中 | 正常，等它完成 |
| ❌ | idle | 离线空闲 | 检查网络/电源/驱动 |
| ❌ | **running** | **执行中掉线** | **要人工看**——不知道板到哪了 |

**最后一行最关键**：如果设备在 `running` 时掉线，说明**动作做到一半失联**，这是需要人工介入的危险状态。

---

## 二、心跳：谁能发起

**这套协议里中控是客户端、驱动是服务端**。

服务端没法主动"推"给一个没监听端口的客户端，所以：

> **心跳只能由中控发起（轮询）。**

### 探活方式分两级

| 级别 | 方式 | 能发现什么 | 成本 |
|---|---|---|---|
| **① TCP 连通** | 连一下端口 | 进程死了、网络断了、端口不通 | 极低 |
| **② 方法探测** | 发一个方法看回包 | 端口通但设备卡死 | 一次往返 |

**默认用 ①**——所有驱动都支持，零成本。
如果某台设备经常"端口通但不干活"，再给它配 ②。

### 为什么按 driver 探测而不是按设备

同一个端点下的设备共享一条 TCP 通路。**端点通就是全都通**。

逐台连会放大到 N 倍连接数——7 台设备每 10 秒连 7 次，20 台就是 20 次，
对现场的驱动服务是负担。

**代价**：如果一台驱动管 20 台设备、其中 1 台真掉线，探活发现不了（端点还通）。
**这种情况要靠"方法探测"补**。

## 三、实现

### 3.1 心跳服务

`driver/HeartbeatService`：

```java
start()                    // 启动后台线程，默认 10 秒一轮
probeOnce()                // 探测一轮
markRunning(instId, method, runId)   // 标记运行中
markIdle(instId, lastError)          // 标记空闲
```

**每轮做三件事**：

1. 从 `driver` 表读所有 active 端点
2. 逐个 TCP 探测
3. 写 `driver_health`（健康记录）+ `device_state.online`（设备状态）

### 3.2 关键：UPSERT 而不是 UPDATE

```sql
INSERT INTO device_state (tenant_id, resource_id, status, online, last_heartbeat, updated_at)
SELECT ?, di.resource_id, 'idle', ?, to_timestamp(? / 1000.0), now()
FROM device_instance di
WHERE di.driver_id = ? AND di.deleted_at IS NULL
ON CONFLICT (tenant_id, resource_id) DO UPDATE
SET online = EXCLUDED.online, ...
```

**为什么必须 UPSERT**：设备可能**从来没有** `device_state` 记录（从没执行过）。
纯 `UPDATE` 会静默影响 0 行，表现为"模拟器明明在跑，界面显示离线"。

**这个坑真实踩过**：7 个模拟器都在线，但只有 2 台显示在线——
因为只有那 2 台执行过、有记录。

### 3.3 状态上报的位置

| 时机 | 动作 | 在哪 |
|---|---|---|
| 分配完设备、即将下发 | `status='running'`, `current_method=方法名` | `onStepStart` |
| 命令返回（成功/失败） | `status='idle'` 或 `'error'` | `onStepDone` |

**注意 ID 转换**：`onStepStart` 传的是 `device_instance.id`（如 171），
而 `device_state.resource_id` 是 `resource_node.id`（如 200171）。

```sql
UPDATE device_state SET status = 'running', current_method = ?
WHERE tenant_id = ? AND resource_id =
      (SELECT resource_id FROM device_instance WHERE id = ?)
```

**不转换会更新 0 行且不报错**——这个坑在这个项目里踩了九次。

## 四、三态流转

```
        ┌──────────────────────────────────┐
        │                                  │
        ▼                                  │
     [idle] ──分配设备──> [running] ──成功──┘
        │                    │
        │                    └──失败──> [error] ──重试成功──> [idle]
        │
        └──心跳失败──> online=false（status 不变）
```

**注意**：心跳失败**不改 status**。
一台设备可能"离线且 idle"，也可能"离线且 running"（后者危险）。

## 五、结果怎么返回

### 5.1 三段式回包

```json
{
  "message_id": "cmd-123",        // 幂等键，必须原样回来
  "message_type": 5,               // 5 = 完成消息
  "method": "Deposit1",
  "equipment_id": "171",
  "method_status": 2,              // 1=运行中  2=成功  其他=失败
  "error": {},                     // 失败时填
  "data": {                        // ★ 结果在这里
    "position": "A1",
    "plate": "PL-20261029"
  }
}
```

### 5.2 中控怎么存

| 存哪 | 字段 | 内容 |
|---|---|---|
| `run_command.result` | jsonb | `{"ok":true,"durationMs":4053}` |
| `run_command.device_raw_response` | text | **完整原文**（含 `data`） |
| `run_command.payload` | jsonb | 实际下发的参数 |

**`device_raw_response` 是结果追溯的唯一来源**——`data` 原样存着。

### 5.3 怎么取结果

**方式一：SQL 直接查**

```sql
SELECT method,
       device_raw_response::jsonb -> 'data' AS 结果
FROM run_command
WHERE run_id = ? ORDER BY command_seq;
```

**方式二：配置输出变量（流程里自动传递）**

在节点参数里配：

```json
{ "output": "plateId" }
```

执行时 `ExperimentFlowRunner` 会从 `data` 里取同名字段，存进变量，
下一步可以用 `${plateId}` 引用。

**方式三：接口**

```
GET /api/runs/{runId}      # 节点树 + 每步结果
```

## 六、界面表现

### 岛屿视图的设备卡片

一个**小圆点 + 颜色**：

| 颜色 | 条件 | 悬停提示 |
|---|---|---|
| 🟢 绿（带光晕） | `online=true` 且 `status=idle` | 在线空闲 |
| 🟡 黄（带光晕） | `online=true` 且 `status=running` | 运行中：Deposit1 |
| 🔴 红 | `online=true` 且 `status=error` | — |
| ⚫ 灰（无光晕） | `online=false` | 离线（心跳无响应） |

**为什么用圆点不用文字**：设备卡片本来就小，文字会挤；
圆点 + 悬停提示足够，且一眼能扫出"哪台掉线了"。

### 心跳接口

```
GET /api/heartbeat
```

```json
{
  "lastRunAt": "2026-11-02T00:56:05Z",
  "drivers": [
    {"driver": "DRV-SIM-ID1183", "online": true},
    {"driver": "DRV-19200200196-8501", "online": false}
  ]
}
```

**用途**：一眼看出"哪个端点连不上"——比逐台设备查快。

## 七、模拟器怎么配合

`DeviceSimulator` 不需要主动发心跳（协议上做不到），但要：

| 行为 | 参数 | 效果 |
|---|---|---|
| 正常响应 | 默认 | 心跳探测连得上 → 在线 |
| 不监听端口 | `--offline` | 连不上 → **离线** |
| 运行中 | 默认 | 收到命令立即回 |

**验证在线/离线**：

```bash
# 在线
java -cp "out:lib/postgresql-42.7.3.jar:lib/spring/*" com.labos.kernel.sim.DeviceSimulator --port 19501 --device 171 --code ID1183

# 离线（不监听）
java -cp "out:lib/postgresql-42.7.3.jar:lib/spring/*" com.labos.kernel.sim.DeviceSimulator --port 19501 --offline

# 运行中杀掉
pkill -f "code ID1183"
```

**10 秒内界面圆点会从绿变灰**（等下一轮心跳）。

## 八、已知限制

| 限制 | 影响 | 缓解 |
|---|---|---|
| **按端点探测，不是按设备** | 一台驱动管多台时，1 台掉线发现不了 | 给它配方法探测 |
| **10 秒间隔** | 掉线最多 10 秒后才显示 | 可配 `intervalMs` 调小 |
| **不做协议层握手** | "端口通但设备卡死"发现不了 | 同上 |
| **没有自动重连** | 离线后需要人处理 | 驱动的重连是另一层的事 |

## 九、给运维的排查顺序

设备显示离线时：

```
① journalctl / 进程在不在
② lsof -i :<端口>     端口有没有监听
③ nc -z <IP> <端口>   网络通不通
④ 看 /api/heartbeat   是哪个端点不通
⑤ 看 /tmp/sim-*.log   模拟器有没有报错
```

**别一上来就重启中控**——先确认是设备侧还是中控侧。

## 十、离线告警

### 10.1 规则

| 条件 | 动作 |
|---|---|
| `online=false` 且 `last_heartbeat` 超过 **30 秒** | 开一条 `alert_state` |
| 恢复 `online=true` 且有未关闭的告警 | 自动关闭 |

**为什么用 `last_heartbeat` 判断时长**：这个字段只在探测成功时更新，
离线后它停在最后一次成功的时间点，所以 `now() - last_heartbeat` 天然就是"离线了多久"。

### 10.2 幂等：不会刷屏

`fingerprint = 'DEVICE-OFFLINE|<resourceId>'` 是唯一键，
同一台设备**只会有一条未关闭的告警**，不会每 10 秒推一次。

```sql
-- 开告警：加 NOT EXISTS 判断
AND NOT EXISTS (
      SELECT 1 FROM alert_state a
      WHERE a.fingerprint = 'DEVICE-OFFLINE|' || r.id AND a.status = 'open')
```

### 10.3 落地时踩的坑：169 条误报

第一次上线，**一次开了 169 条离线告警**。

**原因**：库里 多台设备的 `driver_id` 指向 5 个真实 IP 驱动（`192.0.2.x`），
这些驱动**从来就没通过**。而心跳的 UPSERT **无论在线与否都写了 `last_heartbeat`**，
所以它们全被判成"离线超过 30 秒"。

**两个修正**：

| 问题 | 修法 |
|---|---|
| 离线也写 `last_heartbeat` | `CASE WHEN ? THEN now() ELSE NULL END`——**只有在线才更新** |
| 从没连上过的设备也告警 | 加了 `last_heartbeat IS NOT NULL` 条件——**只对"曾经在线过"的设备告警** |

**清理**：把那 169 条误报批量关闭并标注原因。

### 10.4 实测闭环

```
① 杀掉 ID1183 模拟器
② 等 40 秒
   ID1183 | online=f | 离线59秒 | 告警=open     ← 只有这一台
   ID1731 | online=t | 离线20秒 | 无告警        ← 正常设备不报
③ 重启模拟器
④ 等 25 秒
   [心跳] 关闭 1 条离线告警（设备已恢复）
   ID1183 | online=t | 告警状态=closed
```

### 10.5 接口

```
GET /api/device-alerts?limit=60
```

```json
{
  "total": 5,
  "items": [{
    "fingerprint": "DEVICE-OFFLINE|200171",
    "status": "open",
    "deviceCode": "ID1183",
    "deviceName": "Inheco_Shaking_Incubation-CMS",
    "online": false,
    "offlineSec": 59,
    "lastHeartbeat": "2026-11-02T01:09:50Z"
  }]
}
```

**和 `/api/alerts` 的区别**：

| 接口 | 内容 | 处置方式 |
|---|---|---|
| `/api/alerts` | **执行错误**（命令失败/超时） | 看 `run_command` |
| `/api/device-alerts` | **设备状态**（连不上） | 先查网络和电源 |

**分开是故意的**——两者的排查路径完全不同，混在一起会误导运维。
