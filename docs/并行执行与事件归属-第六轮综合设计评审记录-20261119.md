## 0. 评审结论摘要

本轮评审对象为基线 commit `fde13fb9e43793d91b3e4fe4ee14d0e995975de3` 下的七份设计文档。七份文档已形成较完整的架构骨架，覆盖统一准入、逻辑操作与事件身份、暂停恢复、跨类锁顺序和实施路径，但仍存在跨文档规则不一致，以及若干并发正确性条件没有被完整定义的问题。

本轮核心裁决：

1. **第一阶段统一准入方向正确，但必须先确定数据库互斥点、事务边界和提交后可靠派发机制。**不能先迁移入口，再补原子性。
2. **Workflow admission、batch active attempt、resume 必须是三套明确区分的规则。**不能使用一个未定义的 active 集合覆盖不同语义。
3. **四字段身份模型方向正确，但 operation identity 需要补充动作实例维度。**同一节点/step/device 下多个独立物理动作可能发生 key 碰撞。
4. **事件 waiter 唯一匹配仍需数据库级并发保护。**无锁候选集查询不能单独证明唯一性；歧义事件应持久化为 UNATTRIBUTED，而不是在整体事务回滚时一并丢失。
5. **暂停应采用请求—协调—确认模型。**必须向用户暴露 pause_requested/pausing 等中间进度，不得在物理动作尚未到安全边界时提前把 Run 标记为 paused。
6. **锁类型应由锁实现/锁 API 明确声明。**不应仅依赖 resource_node.kind 推导锁存储组；ThreadLocal 单变量 rank 不能独立覆盖跨 step、跨线程和 lease 生命周期。
7. **七份文档必须统一关键术语、状态集合、HTTP 契约和 DDL。**尤其是 E-02 的 HTTP 行为、paused/quarantined 的不同准入语义、command_id 生命周期规则。

放行边界：

- 并行度 1 的统一准入重构：在关闭本记录中的 P0 项后，可以进入实现准备。
- 第一阶段必须保持既有 HTTP 行为、同步/异步契约、批次顺序和失败语义零变化。
- 并行度 2：**不批准**。设计评审通过不等于能力可用；仍须完成源码复核、数据库并发测试、事件归属故障测试、锁生命周期测试及 HIL 验收。

## 2. 六个核心问题的逐项裁决

### R6-01：总纲 §3.0 的四个决策

**结论：需要补充证据并修改。风险级别：P0。**

**位置：**《实施总纲》§3.0；《入口统一》§3.2、§3.3、§6；《设计基线》§4.2。

#### A. 数据库准入互斥点

**裁决：支持数据库事务内准入；必须先确定实际互斥点。**

优先考虑稳定存在的 workflow 行 `SELECT ... FOR UPDATE`；若该行不适合作为互斥对象，可使用专用 admission guard 行。所有竞争入口必须锁定同一互斥对象，并在同一事务、同一连接内完成：

1. 获取 admission 互斥；
2. 查询并判定当前有效执行；
3. 创建新 Run 或执行带原状态守卫的 Resume 更新；
4. 写入持久化待派发记录；
5. 提交事务。

唯一索引是最终防线，不替代上述事务互斥和准入逻辑。Advisory lock 只有在所有入口都遵守同一协议时才有效；SERIALIZABLE 可行但需要定义序列化失败重试，不作为首选。

**风险：**只把 gate.check 移入事务、却没有锁定共同互斥对象，仍可能发生两个事务同时读到“无 active run”并双双插入。

**建议：**在实施规格中明确数据库类型、隔离级别、锁定 SQL、锁定顺序、事务边界、冲突错误映射和所有写入口的强制协议。

**验收：**两个独立连接并发启动同一 tenant/workflow，重复执行压力测试；必须至多一个事务成功，数据库最终状态符合准入约束。所有入口都必须经过相同互斥点；无法证明的写入路径保持 UNKNOWN。

#### B. 事务提交与 scheduler 派发衔接

**裁决：反对仅依赖启动恢复作为可靠派发保证。**

**位置：**《实施总纲》§3.0 决策 B；《入口统一》§3.2、§6。

“事务提交后唤醒 scheduler”存在提交成功但唤醒动作丢失的窗口。仅靠 StartupRecovery 不能证明运行期间每个已提交 queued Run 都最终被派发。

**建议：**采用最小化的事务性派发机制（Transactional Outbox 或数据库队列扫描）：

- 同一事务创建/更新 Run，并写入持久化待派发记录；
- 提交后可立即 best-effort 唤醒 scheduler；
- 后台扫描未完成记录，执行幂等认领、派发和结果记录；
- 启动恢复与运行期扫描使用同一套认领规则；
- 派发重试不得重复创建 Run，也不得因重复唤醒重复执行物理动作。

**风险：**丢任务、重复派发、Run 长期 queued、Run 状态与 scheduler 内存队列不一致。

**验收：**注入“事务提交后、唤醒前进程退出”“唤醒成功但确认记录前退出”“重复扫描/重复唤醒”等故障，证明最终可恢复且物理动作不重复。未实现持久化派发与幂等认领前，不得声称派发可靠。

#### C. 事件表 DDL 统一

**裁决：支持统一；必须从字段清单提升为唯一迁移规格。**

**位置：**《实施总纲》§3.0 决策 C；《表设计》§1、§2；《设计基线》事件归属相关章节。

**建议：**形成唯一规范，包含完整 DDL、字段类型/长度/NULL 语义、主键、唯一约束、索引、外键、状态枚举、时间字段、原始载荷、解析版本、归属证据、历史回填、双写兼容、迁移失败回滚和数据对账。按设备幂等能力分档的约束应在规范中显式表达，不要将一种 command_id 唯一约束无差别套用于所有设备。

**验收：**空库建表与既有库迁移后结构一致；迁移可重复验证；历史数据回填可审计；索引和唯一约束通过并发冲突测试。

#### D. active 集合与 paused/quarantined

**裁决：需要拆分语义；当前文档表述不一致。风险级别：P0。**

**位置：**《入口统一》§3.3、§4.5；《设计基线》§4.2；《暂停与恢复设计》状态定义。

《入口统一》将 workflow active 定义为 `queued/running/paused`，而《设计基线》对 batch active attempt 的集合采用不同规则。不同集合可以存在，但必须有不同名称、不同用途和独立状态转移表。

必须区分：

| 规则 | 要回答的问题 | 需要明确的状态语义 |
|---|---|---|
| Workflow admission | 是否允许该 workflow 创建/激活另一个 Run | paused 是否继续占用 workflow 名额 |
| Batch active attempt | 同一批次是否允许创建新的 attempt | 旧 paused attempt 是否仍占用批次尝试槽位 |
| Resume eligibility | 既有 Run 是否允许重新激活 | 允许状态、归属校验、影响行数和并发冲突 |
| Resource safety/quarantine | 隔离资源是否允许其他执行使用 | 隔离作用域是 workflow、device、position 还是更广 |

不能仅凭 `terminal`、`active` 字段推导物理安全含义。尤其 `quarantined` 即使不占 workflow 唯一名额，也可能因设备/位置状态不可信而必须阻止相关资源的新动作。

**建议：**删除含混的“active 集合”单一表述，分别命名并定义状态集合；明确 paused 与 quarantined 对 admission、batch attempt、resume、resource admission 的影响矩阵。

**验收：**对 queued/running/paused/paused_fault/waiting_human/paused_unknown/manual_hold/quarantined/failed/completed 等状态逐一验证新建、重跑、Resume 和资源认领结果。任何未纳入矩阵的状态必须保持 UNKNOWN，不得默认放行。

### R6-02：四字段 operation identity 模型

**结论：有条件支持，需补充动作实例身份。风险级别：P1。**

**位置：**《表设计》§1.1–§1.7。

`operation_key / generation / command_id / attempt_no` 的职责分离方向正确，但现有 operation_key 组合未充分覆盖同一节点内部的多个独立动作实例。

可能碰撞的场景：

- 同一 run、node、step、device、loopIndex 下连续执行两次相同类型但独立的物理动作；
- 同一节点内多个相同 step invocation；
- 并行分支在相同节点/step 上产生相同身份；
- 流程定义不变但同一 action 被显式重复调用。

**建议：**

将业务动作身份扩展为：

```text
operation_identity
  = run
  + node
  + action_slot
  + branch_identity
  + loop_identity
  + invocation_identity（必要时）
```

其中：

- `action_slot`：流程定义中稳定、可复现的动作位置；
- `branch_identity`：并行分支或调用上下文的稳定身份；
- `loop_identity`：循环轮次身份；
- `invocation_identity`：同一动作位置发生多个独立调用时区分实际调用。

`generation` 表示同一业务动作的逻辑执行代次；`command_id` 按设备幂等能力策略生成；传输发送和查询次数应分别计数，避免一个 `attempt_no` 混合不同类型的尝试。

还需统一文档中“command_id 首次生成后不变”与“不支持设备去重时每次发送生成新 ID”的冲突。应定义设备能力档位及其 command identity 规则。

**风险：**不同物理动作复用同一 key，造成错误去重、错误 Resume、错误事件归属或错误命令状态覆盖。

**验收：**至少覆盖同一节点两次相同物理动作、循环两轮、并行分支、人工重跑、Resume、断线后重试六组场景；验证唯一约束不冲突、重放语义确定、事件不会跨动作归属。若某设备协议无法证明幂等语义，相关场景必须 UNKNOWN，不得自动重发。

### R6-03：waiter 唯一性匹配与 §2.4 并发安全

**结论：方向正确，但现有“先无锁判唯一、再加锁更新”不足以证明并发唯一性。风险级别：P0。**

**位置：**《表设计》§2.4。

无锁读取候选 waiter 后再更新，仍可能存在候选集幻读/并发新增窗口。例如事务 A 读取到一个 waiter，事务 B 在 A 更新前新增另一个匹配 waiter，A 的原查询结果并不能证明全局唯一。

此外，多 waiter 竞争同一事件时，条件更新影响 0 行必须被视为并发冲突并重新判定，不能当作匹配成功。

**建议：**

1. 对同一事件匹配域建立数据库级互斥点，例如 `(tenant_id, device_code, event_type)` 对应的稳定 guard 行或其他可证明的数据库锁。
2. waiter 创建与事件认领遵守同一互斥协议。
3. 在互斥保护下读取完整候选集，再进行唯一性判定。
4. 唯一匹配时，在同一事务中更新 waiter、事件归属和消费记录。
5. 为同一事件的最终匹配关系建立唯一约束，防止重复消费。
6. 条件更新影响行数为 0 时重新读取并判定；不得推进业务状态。
7. 无法唯一归属时，禁止选择“最早 waiter”“当前设备占用者”或任意单个 waiter。

**关于整体回滚：**保守地不提交任何 waiter 归属变更是正确的；但不能让歧义事件本身随事务 rollback 一并消失。应将“归属动作整体不提交”和“UNATTRIBUTED 事件持久化”拆开设计。可在独立事务中持久化歧义事件/审计，也可在同一事务中只提交 UNATTRIBUTED 结果而不提交任何 waiter 消费。

**风险：**错误推进 Run、释放资源、把迟到事件分配给新 waiter、重复消费同一事件。

**验收：**构造并发 waiter 创建、并发事件认领、同一事件重复投递、迟到事件、多个候选 waiter、更新影响行数为 0 等测试。任何无法证明唯一归属的事件必须保持 UNATTRIBUTED/UNKNOWN，不得推进 Run 或释放资源。

### R6-04：GuardedStart 与入口统一

**结论：支持统一入口，但数据库互斥点必须先定，实施步骤需调整。风险级别：P0。**

**位置：**《入口统一》§3.2、§3.3、§4、§6；《实施总纲》实施顺序。

GuardedStart 作为统一应用入口是合理的，但“所有入口都调用 GuardedStart”不是原子准入的证明。必须先确定同一 workflow 的数据库互斥点，再实施事务内检查与写入。

**建议实施顺序：**

1. 盘点所有创建、激活、Resume、重跑入口及 mapper insert 路径。
2. 定义 workflow admission guard、batch attempt 约束和各自状态集合。
3. 实现同事务的互斥、检查、Run 创建/Resume 更新和持久化待派发记录。
4. 验证并发事务无法双重准入。
5. 迁移 E-01、E-02、E-09，再迁移 E-03、E-08、E-04 至 E-07、E-10。
6. 增加唯一索引兜底并验证迁移。
7. 完成并行度 1 行为等价验收。

**入口完整性：**必须核查定时任务、内部 API、脚本直调、演示路径、所有 mapper insert（包括 `insertRun`、`insertDemoRun`、`insertExperimentFlowRun`）和现有 `existingRunId>0` 等旁路。演示路径是否进入生产 admission 规则需明确，不能默认遗漏或默认纳入。

**WorkflowRunGate.check：**若现有方法使用独立连接或无法参与同一事务，应保留其快速预检用途，但新增明确的事务内准入方法；不能继续把独立连接查询当作原子准入。最终应只有一套权威的事务内规则。

**HTTP 行为：**《实施总纲》与《入口统一》对 E-02 被拒时的 HTTP 状态码存在矛盾。第一阶段要求 HTTP 行为零变化，因此应以已核对的现有契约为准；若现状确为 200 + JSON 错误对象，则必须保持 status、字段、字段顺序敏感逻辑（如字符串嗅探依赖 `error` 首字段）及前端可观察语义。任何改为 4xx/非 2xx 的变化必须另立变更，不得混入本阶段。

**DB 不可用语义：**现有 gate fail-open 若属实，改变为 fail-closed 属于行为变化，需单独决策、定义错误码/重试/告警，并单独验收，不能声称零变化。

**验收：**并行度 1 下，对同样输入序列比较改造前后的 HTTP 状态码、响应字段、数据库最终状态、批次顺序、失败继续语义、扣留边界、Resume 结果；并发启动测试必须只有一个成功。无法从源码和既有测试确定的旧行为先标 UNKNOWN，不得用新设计反推旧行为。

### R6-05：暂停与恢复模型

**结论：支持“暂停是协调请求，不是立即物理命令”的方向；必须增加用户可观察的中间状态。风险级别：P1。**

**位置：**《暂停与恢复设计》§4.1–§4.3、§5、§7 H-12、§8。

实验级暂停采用请求—协调—确认模型是合理的：

1. 接受暂停请求；
2. 禁止派发新的危险动作；
3. 正在执行的动作在定义好的安全边界完成或进入可证明的安全状态；
4. 各 Run/节点分别确认；
5. 汇总批次/实验暂停结果；
6. 全部必要对象确认后，才将上层状态确认为 paused。

但若用户点击后 UI 仍只显示 running，长动作可能持续数十分钟，用户会认为操作没有生效。

**建议：**增加独立于 Run terminal/status 的暂停协调状态或记录，例如：

- `pause_requested`：请求已接受；
- `pausing`：正在等待动作边界；
- `paused`：所有必要对象已确认暂停；
- `pause_blocked`：存在阻塞或 UNKNOWN；
- `resume_requested` / `resuming`：恢复协调过程。

用户界面应显示请求已接受、当前阻塞动作、各批次确认进度、阻塞原因和可选的预计等待时间（明确标记为估算）。不能因收到 Hold 请求就提前把仍在执行物理动作的 Run 标记为 paused。

需解决 §4.1“下层到安全边界才改状态”与 H-12“Hold 同时改 Run 状态”之间的矛盾：Hold 请求可以立即持久化，但 Run 的真实执行状态不能提前伪造为暂停完成。

**验收：**使用长时间孵育/离心/机械臂动作验证：点击后立即得到明确反馈；暂停中不再派发新的危险动作；动作未到安全边界时 UI 不显示暂停完成；全部必要对象确认后才显示 paused；暂停中断/设备失联/超时转为明确阻塞或 UNKNOWN；重复 Pause/Resume 幂等。

### R6-06：跨类锁类型、rank 与生命周期

**结论：需要修改。风险级别：P1。**

**位置：**《跨类锁顺序核查》§1.1、§3.1–§3.3、§6。

两类存储组（设备状态与位置状态）的简化方向可以保留，但不应由 `resource_node.kind` 单独推导当前锁类型。同一种资源节点可能参与设备执行互斥，也可能参与物理位置占用；资源 kind 并不能唯一表达调用者正在申请哪一种锁语义。

**建议：**

- `DeviceLock` 明确声明其锁类型为 `DEVICE_STATE`；
- `RailZoneGuard` 若复用 DeviceLock，则继承同一锁类型和顺序规则；
- `PositionLock` 明确声明为 `POSITION_STATE`；
- 锁类型由锁 API/实现确定，不由业务调用点猜测，也不通过 kind 映射推导；
- 锁顺序按明确的 `(type_rank, resource_id)` 全序定义；
- 批量申请必须先排序，再按统一顺序申请；部分失败的释放顺序和失败补偿要定义；
- 重入、重复资源、异常退出、跨线程交接和释放 token 必须定义；
- 物理位置占用事实与当前线程持有的执行互斥锁分开建模。

单变量 ThreadLocal 最高 rank 可作为开发期的局部断言，但不能独立覆盖跨 step 持有、跨线程释放、Resume 换线程、lease 过期和异常清理。若引入 LockOrderGuard，应记录资源类型、资源 ID、token、执行上下文、重入和异常边界；跨线程生命周期应使用显式上下文/token，而不是依赖 ThreadLocal 自动传播。

**验收：**覆盖 DEVICE→POSITION、POSITION→DEVICE 反向申请、批量锁排序、部分失败释放、重入、跨 step 持有、跨线程释放、异常退出、Resume 换线程、lease 过期和 UNKNOWN 资源处置。无法证明锁持有者或释放 token 正确时，不得自动释放可能仍保护物理资源的锁。

## 3. 跨文档一致性问题

### R6-07：E-02 HTTP 契约冲突

**结论：必须修正。风险级别：P0（第一阶段兼容性门槛）。**

**位置：**《实施总纲》§3.1；《入口统一》§4.2、§5 V-08。

总纲对 E-02 阻断响应的描述与入口统一文档“沿用既有 200 + JSON 错误对象”的描述不一致。

**建议：**以源码实际行为和既有前端契约为唯一事实来源。若当前实现确为 200 + JSON 错误对象，则总纲必须同步；并保留前端字符串嗅探所依赖的字段顺序或尽快将其改为结构化解析，但后者属于独立兼容性变更，不能在本阶段偷偷改变。

**验收：**用改造前后同一请求比对 HTTP status、headers（如有契约）、JSON 字段、字段值和前端识别结果。未重新读取源码确认当前行为前，具体旧契约标为 UNKNOWN。

### R6-08：command_id 生命周期矛盾

**结论：必须统一。风险级别：P1。**

**位置：**《表设计》§1.1、§1.7。

一处定义 command_id 首次生成后不变，另一处允许不支持设备去重时每次传输生成新 ID。

**建议：**将逻辑操作身份、设备命令身份、发送尝试身份分开。按设备能力明确：
- 支持幂等去重：重试是否复用同一 command_id；
- 不支持幂等去重：超时/断线后何种情况下禁止重发，何种情况下必须转 UNKNOWN；
- 查询命令与执行命令是否共享身份；
- 设备重启/boot identity 对 command identity 的影响。

**验收：**每个设备能力档位都要有发送、超时、断线、查询、Resume 和重放测试；无法证明设备去重语义时不得自动重发。

### R6-09：源码盘点与证据基线不统一

**结论：需要补充证据。风险级别：P1。**

**位置：**《并行调度-源码核查清单》全篇及其余文档引用的源码位置。

39/4/10 盘点数字不能仅凭本轮文档读取视为已独立核实。七份文档对源码基线的引用也不完全一致。

**建议：**下一版建立统一源码审计基线，逐项记录：
- 完整 commit SHA；
- 文件路径、类、方法和行范围；
- SQL/Mapper 与事务边界；
- 真实调用入口和旁路；
- 异常、恢复、锁释放路径；
- 对应测试名称、执行命令和结果；
- PASS/FAIL/UNKNOWN 及证据缺口。

对“已有”项至少证明生产调用链实际使用，而不只是存在类、方法或 SQL；对“部分”项明确缺少的条件；对“没有”项给出全仓搜索范围和排除理由。

**验收：**另一位评审者在同一 SHA 上能够按路径和测试独立复现每一条判定。文档存在但源码/测试不能证明的能力不得计为 PASS。

## 5. 建议实施顺序

本轮建议调整为以下顺序，避免先迁移入口、后补事务正确性：

### 阶段 0：冻结准入规格

- 盘点全部 Run 创建、激活、Resume、重跑入口和 mapper insert；
- 定义 workflow admission guard；
- 明确 workflow admission、batch active attempt、resume eligibility、resource quarantine 四套状态规则；
- 选定数据库互斥点、事务隔离级别和唯一索引设计；
- 明确 DB 不可用时 fail-open/fail-closed 的现状与目标，作为独立语义决策。

### 阶段 1：实现准入原子性与持久化派发

- 同事务完成互斥、检查、Run 创建/Resume 更新；
- 同事务写入持久化待派发记录；
- 实现提交后唤醒与后台扫描/幂等认领；
- 先完成双连接并发测试和提交后崩溃测试。

### 阶段 2：迁移入口，保持并行度 1

- 按 E-01、E-02、E-09，再 E-03、E-08、E-04 至 E-07、E-10 的顺序迁移；
- 全仓确认无绕过 admission 的生产入口；
- 增加唯一索引兜底；
- 严格保持 HTTP 和业务行为零变化。

### 阶段 3：暂停恢复协调
