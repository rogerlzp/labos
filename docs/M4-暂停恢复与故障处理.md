> 一键验收：`./scripts/verify-m4.sh` → **14 项通过 / 0 失败**
> 单测：`PauseManagerSelfTest` → **10 项通过 / 0 失败**

---

## 一、三种暂停态（不是一种）

| 类型 | 触发 | 恢复条件 | 为什么单独分 |
|---|---|---|---|
| `paused_fault` | 设备故障 | **心跳恢复就自动继续**，不需要人 | 设备好了却没人知道可以继续，是最常见的"假卡死" |
| `waiting_human` | 重试耗尽、板位不一致 | **必须人确认** | 系统不知道人处理了没有 |
| `paused_unknown` | 板位置未知 | **必须盘点 + 校正** | 位置完全未知，比前两种严重 |

**混成一个"暂停"会导致**：设备恢复了但没人点继续，或者人以为处理了其实没处理。

**实现**：不动 `run_status` 枚举，加 `run.pause_kind` 列。
加枚举值要 `ALTER TYPE`，且 PG 不允许在事务里加；而暂停类型以后可能还会增加。

## 二、暂停只能在动作边界

**机械臂从 A 抓板、移到半空 —— 不能停在这里，板会掉。**

所以暂停请求只**标记**，由执行循环在**下一步开始前**检查：

```java
for (Step step : node.steps()) {
    if (shouldPause()) {
        transitionTo(pauseState());
        return;
    }
    executeStep(step);   // 一旦开始，必须跑完
}
```

**代价**：暂停延迟 = 当前动作剩余时间。

**但孵育不该是一个"30 分钟的动作"**：

| 阶段 | 类型 | 能否暂停 |
|---|---|---|
| 放入（机械臂送板进孵箱） | 动作 | 动作边界可停 |
| **保温（等 30 分钟）** | **状态** | ✅ **随时可暂停** |
| 取出 | 动作 | 动作边界可停 |

**所以真实暂停延迟是分钟级，不是 30 分钟。**

## 三、暂停时释放资源（有豁免）

**被暂停的执行如果还占着资源，会把整个岛拖死**：

```
流程1 用 B 时故障暂停，还占着 A 的出板位
  → 流程2 想用 A，抢不到，也卡住
```

### 释放规则

| 资源 | 暂停时 | 为什么 |
|---|---|---|
| 普通"已占但未用"的位置 | **释放** | 让别的流程能跑 |
| **回程承诺（`position-return`）** | **⚠ 保持** | 放了别人的板就占进去，回程时死锁 |
| 通道占用 | **释放**（归零） | 暂停说明不在搬运中 |
| 设备锁 | **只放 `status != running` 的** | running 说明板还在里面 |
| 抓着板的机械臂 | **保持** | 不能松手 |

### 回程承诺为什么必须豁免

**这是 M1 设计里就埋下的矛盾**：

- D105 要求取板时**全程预留回程位置**
- D111 要求故障暂停时**释放"已占但未用"的位置**
- **回程预留位恰恰是"已占但未用"**

**照 D111 释放的后果**：

```
① 取板，预留回程位 L1
② 设备故障 → 暂停 → 释放 L1
③ 故障修复 → 恢复 → 要放回 L1，但 L1 已被别人占了
④ 死锁原样复现
```

**解法**：区分**预留**（可释放）和**承诺**（不可释放）。

```sql
resource_booking.release_exempt = true   -- 回程承诺默认豁免
```

## 四、板位三态

| 状态 | 含义 | 处理 |
|---|---|---|
| **KNOWN** | 明确在某位置 | 正常调度 |
| **UNKNOWN** | 不知道在哪 | **人工盘点**，涉及这板的流程全暂停 |
| **LOST** | 确认丢了 | 终止相关流程，走损耗 |

### 每次 UNKNOWN 封多少资源

**一次 Transfer 的物理路径**：

```
S 设备内 ──→ 被抓出 ──→ 在机械臂上 ──→ 放下 ──→ T 设备内
   ↑ 已知      ↑ 从这里开始说不清              ↑ 到这里才重新已知
```

**保守做法**：取全路径并集

```
可能位置 = { S 的所有位置, T 的所有位置, 机械臂 }
```

**宁可多封，不可漏封** —— 漏封会撞机。

### 封锁粒度：位置不是设备

```sql
UPDATE position_state
SET reserved_by_run = -1,          -- -1 = 系统封锁，不是某个执行
    block_reason = 'PLATE_UNKNOWN',
    reserved_until = now() + interval '24 hours'
WHERE resource_id IN (...) AND plate_id IS NULL;
```

**设备本身还能干别的**，只是这些位置不能放新板。

### 超时也不自动解封

**板可能真在设备里**。超时解封会让别的板放进去 → **物理上叠板**。

**只能人工盘点**：

```
POST /api/plates/{barcode}/locate
{"actualLocation": "ID1183-L2"}     ← 或 "LOST"
```

**每次盘点都留痕**（`plate_location_audit`）—— 板在哪是人去现场看的，
系统只记录结论，出问题要能追。

## 五、恢复必须带校正

```
POST /api/runs/{id}/resume?action=continue
{"corrections": {"PL-001": "ID1183-L2"}}
```

**`paused_unknown` 没有 corrections 直接拒绝恢复**：

```json
{
  "ok": false,
  "error": "板位置未知，必须提供 corrections（板号 → 实际位置）才能恢复"
}
```

**为什么强制**：现场和系统记录大概率不一致。**不校正就继续，后面的板位判断全错。**

### 四种恢复动作

| action | 行为 |
|---|---|
| `continue` | 继续（人工已处理） |
| `retry` | 重试当前动作 |
| `skip` | 跳过这一步（危险，要二次确认） |
| `abort` | 终止 |

## 八、踩的坑

| 坑 | 根因 | 修法 |
|---|---|---|
| 释放资源报 `current_plate_id does not exist` | 实际列名是 `plate_id` | 改名 |
| 释放资源报 `reserved_by_run does not exist` | `resource_booking` 没有这个列，要经 `run_node_id` 关联 | 改成子查询 |
| 恢复报 `status is of type run_status` | 枚举列不能直接 `setString` | SQL 加 `?::run_status` |
| 盘点后位置没解封 | 测试只设了 `block_reason`，没设 `possible_locations` | 测试补齐（真实流程会写） |

**第 4 条值得说**：代码依赖 `plate.possible_locations` 来找要解封的位置。
测试手工造数据时漏了这个字段，就解不了封。

**这暴露一个设计依赖**：`possible_locations` 是解封的唯一线索，
如果它丢了（比如人为改库），封锁就永远解不开。**以后要考虑冗余**。

## 九、和 M1/M2/M3 的关系

```
M3 粗筛（启动前）    → 判断能不能启动
M1 资源协议（执行中） → 固定全序申请，失败回滚
M2 等待图（执行中）   → 成环拒绝，保证不死锁
M4 暂停恢复（异常时） → 停下来不乱，恢复时不错
```

**M4 补的是"出事了怎么办"** —— 前面三个假设一切正常，
M4 处理设备坏、板丢了、要人介入。
