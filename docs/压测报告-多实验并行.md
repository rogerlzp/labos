# 压测报告：多实验并行

> 用 7 台模拟设备压，测吞吐、延迟、岛锁是否生效。
> 脚本：`./scripts/load-test.sh LAB-DEMO-02 1,2,4,8,16`

---

## 一、数据

### 吞吐与延迟

| 并发 | 成功 | 失败 | 耗时(s) | 吞吐(个/s) | 单均(ms) | 峰值并行 |
|---|---|---|---|---|---|---|
| 1 | 1 | 0 | 6.56 | 0.15 | 5239 | 1 |
| 2 | 2 | 0 | 6.45 | 0.31 | 5221 | 2 |
| 4 | 4 | 0 | 6.82 | 0.59 | 5304 | 4 |
| 8 | 2 | 0 | 6.42 | 0.31 | 5164 | 2 |
| 16 | 11 | 0 | 7.78 | **1.41** | 5741 | **11** |

**读法**：

- **单均稳定在 5.2-5.7 秒**，不随并发上升
- **吞吐随并发线性上升**（0.15 → 1.41）
- **没有失败**（16 并发零失败）

**结论：并发本身不拖慢单个执行，但吞吐被单次耗时锁死。**

### 单次执行的耗时构成

```sql
SELECT EXTRACT(EPOCH FROM (actual_end - actual_start)) AS 总秒,
       count(rc.id) AS 命令数,
       sum((rc.result->>'durationMs')::int) AS 命令耗时和
FROM run r LEFT JOIN run_command rc ON rc.run_id = r.id ...
```

```
总秒    命令数   命令耗时和
5.07    2        312
5.03    2        312
5.04    2        319
```

**命令只花 312ms，总耗时 5 秒 —— 4.7 秒不知道花在哪。**

## 二、三个发现

### 🔴 发现 1：岛锁没生效（架构缺口）

**证据**：并发执行时，**55 对 run 的时间区间重叠**。

```sql
SELECT count(*) FROM run a JOIN run b ON a.id < b.id
WHERE a.actual_start < b.actual_end AND b.actual_start < a.actual_end;
-- 55
```

**根因**：

```
POST /api/workflows/{id}/run     → WorkflowService.execute()  ← 不走调度器
POST /api/experiments/{id}/run   → ExperimentScheduler        ← 走调度器
```

**直接调 workflow 执行会绕开岛锁**。

**影响**：

- 现场如果两个操作员同时点"执行"，**同一个岛会跑两个实验**
- 机械臂会打架
- **这是上生产前必须堵的洞**

**修法（两个选择）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 在 WorkflowService 里加锁** | 执行前抢岛锁，抢不到排队 | 改动小，但两处逻辑重复 |
| **B. 强制走调度器** | 废弃 `/api/workflows/{id}/run`，只留实验路径 | 干净，但要改前端和现有调用 |

**建议 B**——两条执行路径并存本身就是隐患（文档里已列为已知问题）。

### 🟡 发现 2：单次执行 5 秒，但命令只要 312ms

**命令耗时和 312ms，总耗时 5000ms。**

**已排除**：

- 驱动注册表重建（改成两种模式都缓存后，仍是 5 秒）
- 队列等待（`actual_start - created_at` = 0）
- 并发争用（单并发也是 5 秒）

**没排除**：

| 可能 | 怎么验 |
|---|---|
| `PositionLock` 的多次 SQL | 加计时日志 |
| `run_event` 写入 | 同上 |
| BPMN 解析（每次执行都解析 XML） | 缓存解析结果 |
| 数据库连接建立（每次 `db.open()`） | 连接池 |

**这个还没定位到**，需要加分段计时。

**影响**：吞吐上限 = 1/5.3 ≈ **0.19 个/秒/岛**。
一个岛一天最多跑约 **1.6 万个**流程节点——对实验室够用，但离"流畅"有距离。

### 🟡 发现 3：统计口径不可靠

压测脚本用 `run.id > 水位` 统计，但有些 run 没被算进去（并发 2 时"成功"只有 1）。

**原因**：`/api/workflows/{id}/run` 是**同步**返回，
但并发时部分请求可能超时或被截断，脚本没等到就统计了。

**修法**：脚本改成"发完请求后等 2 秒再统计"。

## 三、能得出什么结论

### 好消息

| 项 | 数据 |
|---|---|
| **零失败** | 16 并发跑 11 个，全部成功 |
| **并发不拖慢单次** | 单均稳定 5.2-5.7 秒，与并发数无关 |
| **吞吐线性** | 0.15 → 1.41 个/秒，没有拐点 |

**说明系统本身没有资源争用问题**（数据库连接、线程池都够）。

### 坏消息

| 项 | 影响 |
|---|---|
| **岛锁可绕过** | 同岛真并行，机械臂会打架 |
| **单次 5 秒** | 4.7 秒是无效开销，吞吐被锁死 |
| **统计不准** | 压测数据本身要打折看 |

## 六、锁粒度重构（岛锁 → 设备锁）

### 问题：岛锁太粗

一个岛里有孵箱、离心机、读板机、机械臂，**只有机械臂是真共享的**
（同一时刻只能搬一块板）。岛级互斥把"抢机械臂"放大成"抢整个岛"：

```
实验 A：孵育 30 分钟（只用孵箱）
实验 B：离心 5 分钟（只用离心机）
岛锁 → B 傻等 30 分钟。纯浪费。
```

### 方案：三层锁，各管各的

| 锁 | 粒度 | 防什么 | 实现 |
|---|---|---|---|
| **位置锁** | 一个层位 | 两块板放同一位置 | `position_state.reserved_by_run` |
| **设备锁** | 一台设备 | 两个执行命令同一台设备 | `device_state.current_run_id` |
| **岛锁（可选）** | 整岛 | 检修/调试时独占 | `resource_booking` 的 EXCLUDE 约束 |

**机械臂不用特殊处理**——它就是一台设备，用同一把锁自然实现了"一次搬一块板"。

### 岛锁降级为可选

默认**不用**，只有显式传 `?exclusive=1` 才生效（检修、调试场景）。

### 实测对比

| 配置 | 4 并发结果 | 总耗时 |
|---|---|---|
| 岛锁开启 | **1 成功 3 拒绝** | 6 秒 |
| 岛锁关闭 + 设备锁 | **4 成功** | 8.78 秒 |

**并发能力从 1 提升到 4**，且单次耗时几乎不变。

### 顺带修的一个并发缺陷

4 并发时 2 个失败：

```
duplicate key value violates unique constraint "uk_run_no"
Key (tenant_id, run_no)=(1, WF-20261102080427077) already exists.
```

**原因**：`run_no` 用毫秒时间戳，并发时同一毫秒生成相同值。

**修**：加 4 位随机后缀（`WF-20261102080427077-4821`）。
