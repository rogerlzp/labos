## 1. 现在的问题

### 1.1 现象层：并行网关不是真并发

`GraphRunner:736-738` 是单线程 `ready.poll()`，`gateway_parallel` 只是把多条出边的目标**依次**压进同一个队列。

实测（基准流程 `BASELINE-SERPAR-01`，run 1001810）：两条并行分支**间隔 14 秒、完全不重叠**，节点执行各约 11–12 秒。

⇒ 流程图上画成并行的两条链，实际是串行跑的。

### 1.2 根因层：主循环与执行体耦合，无法分叉

`GraphRunner:693-703` 的主循环状态全是**方法局部变量**：

```java
Map<String, Integer> pending = new HashMap<>();     // 未完成入边计数（join 用）
Deque<String> ready = new ArrayDeque<>();           // 待执行队列
Set<String> done = new HashSet<>();                 // 已完成
ConditionalBranchTracker tracker = ...;             // 条件分支存活性
Map<String, Integer> visits = new HashMap<>();      // 圈次
```

`GraphRunner:760-1000+` 是一段上千行的 if-else 链，用 `break` / `continue` 直接操纵主循环：

```java
else if (BUILTIN) { ... break; }                 // 退出主循环
else if (TASK) {
    if (物料闸门) { ready.offer(key); break; }    // 重新入队并退出
    if (暂停检查) { ready.offer(key); break; }
    ... 500 行 ...
}
```

⇒ **要把一条分支"抽出来并行跑"，必须先把这段控制流变成"返回结果"的方法**（`break` → `return Outcome`）。这是整个改造里最大的一次性改动。

### 1.4 D5 核实结果：DB 连接没问题，真隐患在三处内存结构

**先澄清原方案的一处判断（它是对的）**：`persistence/Tx.java:20-23` 类注释原文——

> 用 Spring 的 `TransactionTemplate` + `DataSourceTransactionManager`：在事务内 `db.open()` 会经 **`DataSourceUtils` 拿到同一条线程绑定连接**，提交/回滚/连接归还全由框架负责。

⇒ **多线程各自 `inTransaction` ⇒ 各拿各的连接 ⇒ 写库本身互不干扰 ✓**

**真正的隐患（三处，原方案列了一处）**：

#### 隐患 A · 事件缓冲区是 `ArrayList`（原方案未列）

```java
// WorkflowService:1060
List<ExecutionEvent> events = new ArrayList<>();

// WorkflowService:1913-1921
private static ExecutionListener tee(List<ExecutionEvent> sink, ExecutionListener... next) {
    return e -> {
        sink.add(e);                       // ← 并发 add 到 ArrayList
        for (ExecutionListener l : next) { l.onEvent(e); }
    };
}
```

⇒ 多线程并发 `add` 到 `ArrayList` ⇒ **丢事件 / 数组扩容错乱 / AIOOBE**。
⇒ **后果最直接**：台账丢了，现场就没法复盘"当时到底发了什么"。

#### 隐患 B · `RunMonitor.Live` 的计数器是非原子读-改-写（原方案未列）

```java
// RunMonitor:26-41 —— 字段全是 volatile（不会撕裂）
public volatile int done;
public volatile int manual;
public volatile String nodeKey = "";
// RunMonitor:79 / :90
case NODE_COMPLETED -> { l.done++;      ... }     // ← 读-改-写，非原子
case NODE_MANUAL    -> { l.manual++;    ... }     // ← 读-改-写，非原子
```

⇒ 两个分支同时完成 ⇒ **`done` 只 +1**（丢计数）。
⇒ 且 `nodeKey` / `nodeStatus` 被**后到的分支覆盖** ⇒ **"当前卡在哪"只反映最后一个事件，不反映全部**。
⇒ 类注释自述的前提"**只在执行线程写**"在并发下破了。

#### 隐患 C · `RunProgress` 的遍历点（原方案只提了容器）

```java
// RunProgress:24-26
public Collection<NodeProgress> all() { return nodes.values(); }    // 活视图
// RunProgress:81-83
public int count(NodeStatus s) { return (int) nodes.values().stream()... }
// RunProgress:85-88
public boolean allSettled() { return nodes.values().stream().noneMatch(...); }
```

⇒ 换成 CHM 后**不会 CME**，但 `count()` 与 `allSettled()` 是**两次独立遍历** ⇒ 并发写入点之后**两个方法可能给出不一致的结论** ⇒ `settleRun` 用它们决定 run 落 `completed` 还是 `paused` ⇒ **可能把没跑完的 run 落成 completed**。

#### 确认安全的两处（原方案担心但实际没问题）

| 组件 | 结论 |
|---|---|
| `nodeStateRecorder`（`WorkflowService:1305` → `recordNodeState` → `rm().updateNodeStateLive`） | ✅ 安全 —— mapper 每次独立开连接；不同 `node_key` 无唯一键冲突 |
| `PersistingStepSink`（`:2985-2993`） | ✅ `seq` 已是 `AtomicInteger`（`:2989`）、`resourceByStep` 是 CHM |

### 1.5 语义层：三个"业务已定"与工程现实冲突

| 业务语义 | 冲突点 |
|---|---|
| "分支不设超时" | 分支卡在 `__awaitEvent` 等事件时，**失败方设了 stopFlag 它也不会立刻退出** ⇒ 无上限等待 |
| "不设超时" | 暂停时分支 B 长期不到边界，暂停永远"未完成" ⇒ 同样需要上限 |
| "同流程互斥放开" | 上层约束与"分支子图互不相交"是两件事，前者管 run 之间，后者管 run 内部 |

⇒ **"执行超时"与"收尾等待上限"必须分开命名、分开配置**（这不是新增约束，是把已有语义拆干净）。

### 1.6 方案未列的两个风险

#### 风险 A · 嵌套并行组 + 同一线程池 = 经典死锁

原方案 D6 选"全局固定池 + 信号量"，D7 说"`inner` 在 `outer` 的分支线程里执行"。

设池大小 = N：

1. 外层并行组占满 N 个分支线程；
2. 某个分支线程遇到内层 split ⇒ 提交内层任务到**同一个池**；
3. 该线程 `allOf().join()` 等内层完成；
4. ⇒ **内层任务排在池队列里，而池里所有线程都在等内层** ⇒ **死锁**。

⇒ D7"不额外申请信号量"是对的（信号量不解决这个），但**同一池提交**会死锁。

#### 风险 B · 步骤顺序：并发上线在前、线程安全化在后 ⇒ 中间态必崩

原方案把"修 `RunProgress` / `RunStateMachine` 线程安全"排在**步 5（最后）**，而步 3（提交线程池）已经产生并发 ⇒ **步 3 落地、步 5 未做时，是必崩状态**，不是"暂时不安全"。

## 2. 我的思路

### 2.1 核心判断一：`RunStateMachine` 是无状态的，"每分支一个实例"可行

原方案 §3.3 判定"每分支一个 `GraphRunner` 不可行"，理由是"第一个参数是 run 级状态机"。

**核对后这个论证不成立。** `RunStateMachine` 的全部实例字段是：

```java
private final RecoveryDecider decider;
private final ExecutionListener listener;
private final Sleeper sleeper;
private final Clock clock;
private long seq;                                   // 唯一的状态
private Function<Long, List<String>> stepPlanner;    // 配置
private Function<Long, Map<String,Object>> paramPlanner;
private Function<String,String> noDeviceReason;
private MaterialCompletion materialCompletion;
private BooleanSupplier materialGate;
private IntSupplier loopIndexSupplier;
```

⇒ **除 `seq` 外全是注入的依赖与配置项，没有任何"执行到哪一步"的跨节点状态。**

`RunProgress` 的类注释也印证了这一点：

> 持有全部节点的可变进度，可序列化落库。**状态机本身不存状态**，所以「暂停 → 存盘 → 重启续跑」只需把这个对象还原回去。

⇒ ⇒ **每分支一个 `RunStateMachine` 实例完全可行**（前提：`seq` 每分支独立、`listener` 线程安全）。

### 2.2 核心判断二：真正的取舍点不是"状态机 run 级"

两条执行路径都要面对的**三样 run 级共享**：

| # | 共享物 | 影响 |
|---|---|---|
| 1 | `RunProgress`（进度） | 必须线程安全 —— **两条路都一样** |
| 2 | `listener` / 事件缓冲（台账） | 必须线程安全 —— **两条路都一样** |
| 3 | `variables`（流程变量） | 已线程安全化 ✓ |

⇒ **两条路的工作量差异，远小于原方案描述的"不可行 vs 多抽 1000 行"。**

**真正的取舍是：主循环状态（`pending` / `ready` / `done` / `visits` / `tracker`）由谁持有。**

| 路径 | 主循环状态 | 要不要抽 `executeNode` | 分支子图的 `pending/ready/tracker` |
|---|---|---|---|
| **A. 抽 `executeNode` + 主循环委托** | 主线程持有 | **要**（1000 行控制流） | 不存在（分支只执行单节点） |
| **B. 每分支一个 `GraphRunner` 实例** | **各分支私有** | **不要** | **天然线程安全**（分支私有） |

⇒ ⇒ 路径 B 连原方案 D1 的"`done`/`visits` 分支隔离"都不需要设计（各分支私有，join 时并集 + 圈次 max 即可）。

### 2.3 核心判断三：**"切分支子图"是两条路的共用前置**

⇒ **先做切图，再定执行路径。**

理由：
- 切图是纯逻辑，不碰执行 ⇒ 可用纯单测覆盖（不需要跑真图）；
- 切图同时产出**"分支互不相交"的校验器**（两条路都需要）；
- 切图产物（分支子图）**正是路径 B 需要的输入** ⇒ 若路径 B 可行，就省掉 1000 行抽取。

⇒ **这是本文最重要的一条建议。**

### 2.4 核心判断四：条件网关**不需要额外规则**

核对 `WorkflowGraphParser.Kind:43-48`：

```java
public enum Kind {
    TASK, START, END, SPLIT_PARALLEL, JOIN_PARALLEL, SPLIT_XOR, JOIN_XOR,
    SPLIT_CONDITIONAL, JOIN_CONDITIONAL,   // 包容网关，独立 Kind
    BUILTIN
}
```

⇒ **切分只要严格认 `Kind.SPLIT_PARALLEL`**，条件网关（`SPLIT_CONDITIONAL`）天然被排除 ⇒ 不需要额外的"排除条件网关"规则，只需要**禁止分支子图内出现任何 `SPLIT_*`/`JOIN_*`**（嵌套要么显式递归、要么报错）。

### 2.5 核心判断五：`seq` 不必改 `AtomicLong`，改语义更省

**硬证据**（两个自测硬断言连续性）：

```java
// test/.../engine/StressTest.java:176-177
for (int i = 0; i < events.size(); i++) {
    eq("seq@" + i, (long) (i + 1), events.get(i).seq());
}
// test/.../engine/EngineSelfTest.java:156-157
for (int i = 0; i < events.size(); i++) {
    eq("seq 连续", (long) (i + 1), events.get(i).seq());
}
```

⇒ 全仓未发现"按 seq 去重 / 按 seq 排序"的业务逻辑；`seq` 只出现在 `JdbcEventStore:67`（写进 `payloadJson`）。

⇒ ⇒ **依赖只在测试断言里，不是业务依赖**。
⇒ ⇒ 并发下"全局连续序号"本来就不存在（两个分支的事件没有天然全序）。
⇒ ⇒ **建议：seq 改为"分支内单调"，事件/落库带 `branch_id`，排序键用 `(branch_id, seq)`** ⇒ **单线程场景只有一条分支 ⇒ 两个自测仍绿 ✓（零兼容性成本）**。

### 2.6 核心判断六：两个收尾上限的来源不同

| 上限 | 等的是谁 | 来源 |
|---|---|---|
| **执行超时**（业务已定不设） | — | 不设 |
| **停止收尾上限**（分支失败后等在途命令完成） | **设备的物理收尾** | **按方法配** —— 复用 `device_method.timeout_sec` / `MethodTimeoutPolicy` 能力默认（INCUBATE 1800s / THERMOCYCLE 3600s / CENTRIFUGE 900s） |
| **暂停等待上限**（分支卡在等事件时用户点了暂停） | **事件到达**，不是设备执行 | **按节点自己的 `__awaitEvent` timeout**（现网 600/900 秒），**不是方法超时** |

⇒ ⇒ 两者量级可差一个数量级，**不能共用一个"按方法配"的配置**。

### 2.7 核心判断七："纯重构"的锚点不是端到端对比

端到端能验"最终结果一致"，**验不了"中间顺序一致"** —— 而顺序恰是本次要改的东西 ⇒ **拿它当纯重构锚点必然报红**。

⇒ ⇒ 正确锚点 = **无并行分支的流程，重构前后逐项 diff**：
节点执行顺序 / `run_node` 状态与时间 / `run_command` 条数与内容 / **事件 seq 序列（1..N）** / 台账条数。

⇒ ⇒ 而 §2.5 那两个"seq 连续"自测**就是现成的回归网**（重构若偷改事件顺序或丢事件，它们会红）。

## 4. 我的实现提案

> 以下全部是**提案代码**，未提交。标注 `// [提案]` 的行为新增；其余为参照的现状代码。

### 4.1 S1 · 图分析器（新增文件）

```java
// [提案] kernel/workflow/ParallelGroupAnalyzer.java
package com.labos.kernel.workflow;

import com.labos.kernel.workflow.WorkflowGraphParser.GEdge;
import com.labos.kernel.workflow.WorkflowGraphParser.GNode;
import com.labos.kernel.workflow.WorkflowGraphParser.Graph;
import com.labos.kernel.workflow.WorkflowGraphParser.Kind;

import java.util.*;

/**
 * 并行组分析：SPLIT_PARALLEL → JOIN_PARALLEL 配对 + 切分支子图 + 三条校验。
 *
 * <p>纯逻辑，不碰执行 ⇒ 可用纯单测覆盖。
 */
public final class ParallelGroupAnalyzer {

    /** 一条并行分支：分支号 + 它独占的节点集合。 */
    public record Branch(String branchId, List<String> nodeKeys) {}

    /** 一个并行组：split → join，中间每条出边一条分支。 */
    public record Group(String splitKey, String joinKey, List<Branch> branches) {}

    /** 分析结果：组 + 校验错误（错误非空 ⇒ 编译期拒绝保存）。 */
    public record Analysis(List<Group> groups, List<String> errors) {
        public boolean ok() { return errors.isEmpty(); }
    }

    private ParallelGroupAnalyzer() {}

    public static Analysis analyze(Graph g) {
        List<Group> groups = new ArrayList<>();
        List<String> errors = new ArrayList<>();

        // ① 只认 SPLIT_PARALLEL —— 条件网关(SPLIT_CONDITIONAL) / 异或(SPLIT_XOR) 天然被排除
        for (GNode split : g.nodes().values()) {
            if (split.kind() != Kind.SPLIT_PARALLEL) {
                continue;
            }
            List<GEdge> outs = g.out(split.key());
            if (outs.size() < 2) {
                continue;                       // 单出边 = 直通，不是并行组
            }

            String joinKey = findJoin(g, split);   // ② 找配对 join
            if (joinKey == null) {
                errors.add("并行组 " + split.key() + " 找不到配对的 JOIN_PARALLEL");
                continue;
            }

            // ③ 切分支子图：从每条出边出发做 BFS，遇到任何网关停
            List<Branch> branches = new ArrayList<>();
            Set<String> claimed = new HashSet<>();
            int idx = 1;
            for (GEdge e : outs) {
                List<String> nodes = collectBranch(g, e.to(), joinKey);
                // 校验 A：分支子图互不相交
                for (String k : nodes) {
                    if (!claimed.add(k)) {
                        errors.add("并行组 " + split.key() + " 的分支在节点 " + k + " 上相交");
                    }
                }
                branches.add(new Branch("b" + (idx++), nodes));
            }
            groups.add(new Group(split.key(), joinKey, branches));
        }
        return new Analysis(groups, errors);
    }

    /** 配对 join：入边全部来自本 split 支配域的最小 JOIN_PARALLEL。 */
    private static String findJoin(Graph g, GNode split) {
        // [提案] 简化实现：从 split 可达、且 kind==JOIN_PARALLEL 的节点里取最近的
        //        （按图上距离）；若图上存在多个候选 ⇒ 报错而非猜。
        String best = null;
        int bestDist = Integer.MAX_VALUE;
        Deque<String> q = new ArrayDeque<>();
        Map<String, Integer> dist = new HashMap<>();
        q.add(split.key());
        dist.put(split.key(), 0);
        while (!q.isEmpty()) {
            String k = q.poll();
            int d = dist.get(k);
            for (GEdge e : g.out(k)) {
                GNode n = g.nodes().get(e.to());
                if (n == null) continue;
                if (n.kind() == Kind.JOIN_PARALLEL) {
                    if (d < bestDist) { bestDist = d; best = n.key(); }
                    continue;                    // 不穿过 join 继续找
                }
                if (dist.putIfAbsent(e.to(), d + 1) == null) {
                    q.add(e.to());
                }
            }
        }
        return best;
    }

    /** 从分支起点收集节点，遇到 join 或任何网关就停。 */
    private static List<String> collectBranch(Graph g, String start, String joinKey) {
        List<String> out = new ArrayList<>();
        Deque<String> q = new ArrayDeque<>();
        Set<String> seen = new HashSet<>();
        q.add(start);
        seen.add(start);
        while (!q.isEmpty()) {
            String k = q.poll();
            if (k.equals(joinKey)) {
                continue;                        // join 不属于任何分支
            }
            GNode n = g.nodes().get(k);
            if (n == null) continue;
            if (n.kind() == Kind.SPLIT_PARALLEL || n.kind() == Kind.SPLIT_XOR
                    || n.kind() == Kind.SPLIT_CONDITIONAL
                    || n.kind() == Kind.JOIN_PARALLEL || n.kind() == Kind.JOIN_XOR
                    || n.kind() == Kind.JOIN_CONDITIONAL) {
                // 校验 B：分支子图内不得出现任何网关（嵌套要显式递归，不能隐式吞掉）
                out.add(k);
                continue;
            }
            out.add(k);
            for (GEdge e : g.out(k)) {
                if (seen.add(e.to())) {
                    q.add(e.to());
                }
            }
        }
        return out;
    }
}
```

### 4.4 S4 · 执行路径

#### 路径 B（每分支一实例）的关键改动点

#### 路径 A（抽 `executeNode`）的控制流改写锚点

原方案的 `break` 语义必须**逐个替换成返回值**，这是"纯重构可验证"的关键：

| 现状 | 改写后 |
|---|---|
| `break;`（BUILTIN 结束本节点） | `return Outcome.DONE;` |
| `ready.offer(key); break;`（物料闸门/暂停 ⇒ 重新入队） | `return Outcome.REQUEUE(key);` |
| `continue;`（跳过） | `return Outcome.SKIP;` |
| 隐式落到循环尾 | `return Outcome.DONE;` |

⇒ **`Outcome` 是可枚举的 4 个值**，每个原 `break` 点都能一一映射 ⇒ 逐点比对即可验证等价。

### 4.5 S5 · 线程池与信号量

```java
// [提案] 提交分支之前取许可，任务内部不再取 ⇒ 否则超限分支会占着池线程等许可
private static final java.util.concurrent.Semaphore GROUP_SLOTS =
        new java.util.concurrent.Semaphore(4);   // 与 run 级并发上限一起定

void runParallelGroup(Group g) {
    if (!GROUP_SLOTS.tryAcquire()) {
        // 排队：挂到主循环的等待队列，轮询重试
        return;                                  // [提案] 具体排队机制待定
    }
    try {
        List<CompletableFuture<BranchResult>> fs = new ArrayList<>();
        for (Branch b : g.branches()) {
            fs.add(CompletableFuture.supplyAsync(
                    () -> runBranch(b), BRANCH_POOL));
        }
        CompletableFuture.allOf(fs.toArray(new CompletableFuture[0])).join();
        // 汇总：任一失败 ⇒ 整组 FAILED
    } finally {
        GROUP_SLOTS.release();
    }
}
```
