### 0.4 一句话设计主张

> **流程节点绑「点位 + 方法 + 物料角色」，不绑设备。**
> 设备实例回答"谁在那儿"，点位回答"哪个坑"，方法回答"做什么"，物料回答"拿什么"。
> 四件事原本挤在一个 `resource` 属性里，所以流程永远只是"设备动作清单"，
> 一旦工序需要"同一台设备的第 2 个坑装另一块板"或"这个坑在另一个流程里干别的事"，就表达不了。

## 2. 现状事实基线

> 本节全部是可复现的事实，不是判断。**评审时请逐条核对。**

### 2.1 点位：实为三层，不是两层

这是本次调研**最重要的一处修正**，上一版文档把它说成"两层"，实际是三层：

```
resource_node（资源树，3104 行）
 ├─ kind='device'                    250   ← 物理设备
 └─ kind='storage'/'incubator'/
    'transfer_point'                2853   ← 点位的「实体」（有 code，无配置）
        │
        │ device_point (290)  ← 配置层：设备↔点位的归属与约束
        │   device_resource_id → resource_node(kind='device')
        │   point_resource_id  → resource_node(kind='storage'/'incubator')
        │   point_role(both/internal/entry/exit) / robot_reachable
        │   plate_types[] / max_height_mm / grid_row / grid_col / position_label
        │
        │ robot_point (9)    ← 坐标层：机械臂怎么到这个点（x/y/z）
        │   robot_resource_id=200231 / device_resource_id / action=PickPlace
        │   code == 点位实体的 code（如 'ID-1021-P1'）
        │
        └─ position_state (290)  ← 运行时：哪个点位现在放着什么
```

**关键事实与设计含义**：

| 事实 | 含义 |
|---|---|
| `device_point` 290 行，`point_role` 分布 = `internal` 272 / `both` 18 | **只有 18 个点位机械臂可达**，其余 272 个是设备内部格（由设备内部机构搬） |
| `robot_point` 只有 **9 行**，而可达点位有 18 个 | **9 个可达点位没有示教坐标** ⇒ 机械臂到不了。这是 P0 的隐性阻塞项 |
| `robot_point.code` == 点位实体 `resource_node.code` | 点位码是**跨三层的稳定标识**，`Transfer(source, target)` 用的就是它 |
| `resource_node.kind='transfer_point'` 有 **420 行**，但交接文档 §6.3 写"机械臂（TRANSFER）无点位" | 两处口径不一致，本设计 §4.2 收敛 |

**证据**：
```sql
select pr.kind, dp.point_role, count(*) from device_point dp
  join resource_node pr on pr.id=dp.point_resource_id group by 1,2;
-- storage|internal|242, incubator|internal|30, storage|both|18
select id, code, robot_resource_id, device_resource_id from robot_point order by id;  -- 9 行
```

### 2.2 绑定的真实形态：BPMN XML + 投影 + 两个 ID 空间

上一版文档说"节点只绑设备"，**方向对但机制说错了**。真实机制：

**① 真源在 BPMN XML 里**

```xml
<bpmn:task id="Activity_1yrts0s" name="Run" protocolName="Run"
           resource="200183" methodParams="{}" icon="/devices/WASH.svg"/>
```

| 属性 | 含义 | 类型 |
|---|---|---|
| `resource` | **resource_node.id**（设备资源） | Long |
| `protocolName` | 设备方法名（**字符串**，不是 `device_method.id`） | String |
| `methodParams` | 方法参数 JSON | String |

解析位置：`kernel/workflow/BpmnGraphParser.java:122,129,131`。

**② `workflow_node` 是投影，不是真源**

`workflow_node.resource_id` / `.seq` 由 `BindingBackfill` 从 XML **回填**（`kernel/workflow/BindingBackfill.java`）。投影存在的原因：ETA、时间条、节点绑定面板要读列，不能每次解析 XML。

**③ 两个 ID 空间混用（已记录的坑）**

`resource_node.id`（资源空间）与 `device_instance.id`（实例空间）是两套号。`PF-11` 专门警告"绑定的 id 是设备实例号 ⇒ 与执行器口径不一致，绑定当前不生效"。

**④ 派发前会重校验**

`kernel/workflow/IslandBindingGate.java` 在实验派发时用**当前**资源树重跑绑定校验，与预检共用同一套判定与文案（PF-10/11/12/13）。

**证据**：`BpmnGraphParser.java:122-131`、`BindingBackfill.java:9-13`、`IslandBindingGate.java:27-40`。

### 3.1 三条绑定链

```
┌ 静态配置层（管理员） ─────────────────────────────────────────────┐
│  island                                                            │
│   └─ device_instance ── device_pool（可选，多对一）               │

└───────────────────────────────────────────────────────────────────┘
┌ 工艺资产层（编排人员） ───────────────────────────────────────────┐
│  workflow ── node ── node_binding ★ 点位+方法+物料角色  ← 新建     │
│  experiment_template ── manifest_item ── manifest_placement ★      │
└───────────────────────────────────────────────────────────────────┘
┌ 运行层（调度器） ─────────────────────────────────────────────────┐
│  experiment_run ── run ── run_node ── run_command                  │
│  transport_segment ★ 接力搬运段（机械臂，隐式）  ← 新建             │
└───────────────────────────────────────────────────────────────────┘
```

**三条链的正交关系**：

| 链 | 键 | 归属 | 生命周期 |
|---|---|---|---|
| 方法链 | `position × method × scope` | 管理员配，编排人员用 | 与设备同寿命 |
| 物料链 | `manifest_item × placement` | 编排人员声明，操作员填 | 与实验实例同寿命 |
| 搬运链 | `transport_segment` | 调度器生成 | 与 run 同寿命 |

#### 3.3.4 `workflow_node` 与 XML 的关系（**双轨期的唯一真源规则**）

**规则（本设计最容易被实现错的地方，评审请重点看）**：

| 项 | 规则 |
|---|---|
| 点位级绑定 | **只在 `node_binding` 里**。XML 的 `resource` 属性**不扩展** |
| 设备级绑定 | 保持现状：XML `resource` 仍是 `resource_node.id`（设备） |
| `workflow_node.resource_id` | 继续是 XML 的**投影**，由 `BindingBackfill` 维护，**不新增写入路径** |
| `workflow_node.binding_mode` | 新增列，取值 `legacy`（只有 XML 绑定）/ `point`（有 `node_binding`）/ `mixed` |

```sql
ALTER TABLE workflow_node ADD COLUMN IF NOT EXISTS binding_mode text NOT NULL DEFAULT 'legacy';
DO $$ BEGIN
  ALTER TABLE workflow_node ADD CONSTRAINT ck_workflow_node_binding_mode
    CHECK (binding_mode IN ('legacy','point','mixed'));
EXCEPTION WHEN duplicate_object THEN NULL; END $$;
```

**为什么不让 XML 也存点位**：
1. `resource` 属性已经是"设备"语义，改语义会破坏 `BindingBackfill` 与 PF-10..13
2. 点位绑定是**一对多**（一个节点可绑多个点位 = Loading Pattern），XML 的单值属性表达不了
3. 点位绑定是**动态的**（同一点位在不同流程不同用），XML 里的东西是静态的

```sql
ALTER TABLE reagent    ADD COLUMN IF NOT EXISTS role_code text;

DO $$ BEGIN
  ALTER TABLE plate ADD CONSTRAINT ck_plate_lifecycle
    CHECK (lifecycle IN ('inventory','process'));
EXCEPTION WHEN duplicate_object THEN NULL; END $$;
DO $$ BEGIN
  ALTER TABLE consumable ADD CONSTRAINT ck_consumable_lifecycle
    CHECK (lifecycle IN ('inventory','process'));
EXCEPTION WHEN duplicate_object THEN NULL; END $$;
DO $$ BEGIN
  ALTER TABLE reagent ADD CONSTRAINT ck_reagent_lifecycle
    CHECK (lifecycle IN ('inventory','process'));
EXCEPTION WHEN duplicate_object THEN NULL; END $$;
```

**语义**：

| lifecycle | 含义 | 装载 | 卸载 | 跨 run 复用 |
|---|---|---|---|---|
| `inventory` | 系统托管的永久库存 | 任何时候 | 任何时候 | ✅ |
| `process` | 本次实验专属 | 实验开始前 | 实验结束时 | ❌ |

> **口径风险**：`lifecycle` 建在**物料实例**上（如 `plate` 一行 = 一块具体板），意味着同一块板在 A 实验是 process、在 B 实验是 inventory 需要改字段。更稳的做法是建在 **manifest_item 的分配**上（一次分配一个 lifecycle）。本设计取**实例级**（简单、可查询），并在 §10 开放问题 1 标出这个取舍。

## 4. 执行语义

### 4.1 节点展开管线

**现状**：XML → `BpmnGraphParser` → `GraphRunner` → `RecipeCompiler`（能力展开）→ `DriverStepExecutor`（命令）。

**目标**：在"能力展开"之前插入**绑定解析**，产出"具体点位 + 具体物料"。

```
① XML 解析
   ↓  BpmnGraphParser.parse(xml)  → ParsedNode{key, protocolName, resourceId, methodParams}
② 绑定解析（新）
   ↓  BindingResolver.resolve(nodeKey, workflowId, experimentTemplateId)
   │   · 查 node_binding（node_id, enabled）
   │   · 校验 position_method 允许该 method（scope: experiment > workflow > global）
   │   · 若 node_binding 为空 → 回落 XML 的 resourceId（legacy）
   ↓  ResolvedBinding[]  每项含 {positionId, deviceInstanceId, poolId, methodId, materialRole, loadingPattern}
③ 物料解析（新）
   ↓  ManifestResolver.resolve(runId, materialRole)
   │   · 查 manifest_placement（run_id, manifest_item.role_code）
   │   · 校验 role 白名单（point_whitelist）
   ↓  ResolvedMaterial[] 每项含 {materialKind, materialRef, barcode, positionId}
④ 能力展开（既有）
   ↓  RecipeCompiler.compile(capabilityId, methodId, params)
   ↓  命令序列 Command[]
⑤ 搬运插入（新）
   ↓  TransportPlanner.plan(ResolvedBinding[], ResolvedMaterial[], previousEndPositions)
   ↓  TransportSegment[]
⑥ 执行（既有）
   ↓  DriverStepExecutor.execute(command)
```

**绑定解析的失败策略**：**不静默降级**。

| 情形 | 行为 |
|---|---|
| `node_binding` 存在但 `position_method` 不允许 | **报错**（不回落 XML）—— 因为用户显式绑过了，静默忽略比报错更坏 |
| `node_binding` 为空且 `binding_mode='legacy'` | 回落 XML（存量路径） |
| `node_binding` 为空且 `binding_mode='point'` | **报错**（流程声明了点位模式却没绑） |

> 依据：用户在《系统修改.txt》第 3 条说"在点位上配置设备的方法"——一旦配了，**配错必须报出来**，不能悄悄按设备跑。

### 4.2 隐式 Transport 与接力链（G3 / B3 / X1）

#### 4.2.1 何时插入搬运段

```
对每条物料流（material_role 相同的一组绑定）：
  当前位置 = 该 role 的起始位置（manifest_placement.position_id，或上一个 binding 的 position_id）
  对每个 binding b in 顺序：
     若 b.position_id ≠ 当前位置:
         插入 transport_segment{from=当前位置, to=b.position_id}
     若 b.device_instance_id ≠ 当前位置所属设备:
         插入 transport_segment{from=b.position_id, to=该设备的目标点位}
     当前位置 = b.position_id
```

**产出示例**（细胞培养岛那种 4 段接力）：

```
transport_segment#1  机械臂B → 中转位1
transport_segment#2  中转位1 → 机械臂A 的板架位
transport_segment#3  板架位 → 导轨B
transport_segment#4  导轨B → 液体工作站台面
```

#### 4.2.2 机械臂是岛级可排他资源

| 规则 | 说明 |
|---|---|
| 排他粒度 | 同一 `robot_resource_id` 同时只允许 **1 个** `transport_segment` 在 `running` |
| 实现 | 复用 `kernel/driver/DevicePortLock.java` 的信号量模式（已有 `DeviceLock` / `PositionLock` / `DevicePortLock` 三种锁） |
| 岛级互斥 | 若一岛只有一台机械臂（现状 `robot_resource_id=200231`），则**全岛搬运串行** |
| 未来多臂 | `robot_resource_id` 区分即可，但跨臂接力（臂A 放下→臂B 取走）需要**中转位**，`transport_segment` 的 `from`/`to` 天然支持 |

**当前只有一个机械臂**（`robot_point.robot_resource_id` 全是 200231），所以现状下搬运是全岛串行 —— 这是**吞吐瓶颈**，评审时需确认这是可接受的现状还是必须解决。

#### 4.2.3 幂等

复用 `kernel/driver/CommandLedger.java` 的命令账本。搬运段的幂等键：

```
idempotency_key = sha256(run_id | seq | from_position_id | to_position_id | carrier)
```

同一个 `run` 重放时命中账本 ⇒ 不重复下发。

#### 4.2.4 与 `DeviceInternalTransfer` 的分工

| 搬运类型 | 谁执行 | 表征 |
|---|---|---|
| 机械臂从装载口取放板 | 机械臂 | `transport_segment`（`robot_resource_id` 非空） |
| 设备内部机构把板从装载口搬进内部格 | **设备自己** | 既有 `DeviceInternalTransfer`（复用现有 `MoveInLabware`/`MoveOutLabware` 方法名） |

两者**不重叠**：机械臂只到装载口；内部格由设备通知中控（既有 `DeviceInternalTransfer` 已在做）。

#### 4.2.5 用户流程里看不到机械臂

| 层 | 表现 |
|---|---|
| 编排画布 | 节点上**不出现**"搬运"节点；只有"在点位的设备方法"节点 |
| 节点树（运行详情） | 显示 `Transport` 段，但标注为系统生成（灰色） |
| 事件流 | 有 `TRANSPORT_START` / `TRANSPORT_END` 事件（新增 `EventType`） |
| 管理员页 | 有独立的「机械臂调试」页（示教、路径、试走） |

**这与 外部厂商A 的口径一致**：手册 P107 "There is no need to add a load operation to obtain mover activity" —— Get/Put 由调度器自动插入。

### 4.3 工位分配（B2 / X3）

#### 4.3.1 工位层建模

`resource_node` 新增 kind：

```sql
-- 不改枚举，改用 DO $$ 包裹的 ALTER TYPE
-- ⚠ PG 限制：ALTER TYPE ... ADD VALUE 不能在事务块内「使用」，
--   本脚本必须单独执行（不在 BEGIN/COMMIT 里），且需 PG 12+
DO $$ BEGIN
  ALTER TYPE resource_kind ADD VALUE IF NOT EXISTS 'workstation';
EXCEPTION WHEN duplicate_object THEN NULL; END $$;
```

工位是**资源的子节点**，挂在设备下（台面）或岛下（独立台面）：

```
resource_node(kind='device')  ID-1183 液体工作站
 └─ resource_node(kind='workstation')  P1 / P2 / P3 ...   ← 台面工位
```

#### 4.3.2 空闲工位分配

`position_method.allocation` 三值：

| 值 | 语义 | 举例 |
|---|---|---|
| `explicit` | 必须显式指定位置 | "把板放到 incubator 的 3 号格" |
| `auto_first_free` | 自动取该设备第一个空位 | "从空闲工位里分配一个" |
| `auto_next_free` | 自动取下一个（轮转），配合 `device_pool` | "从堆栈取下一块" |

**分配算法**（`auto_first_free`）—— MyBatis Mapper 片段（占位符用仓库既有的 `#{param}` 约定）：

```xml
<!-- ConsumableMapper.xml / 新的 PositionMapper.xml -->
<select id="selectFirstFreeWorkstation" resultType="map">
  SELECT dp.id
    FROM device_point dp
    JOIN resource_node rn ON rn.id = dp.point_resource_id
   WHERE dp.device_resource_id = #{deviceResourceId}
     AND dp.enabled
     AND dp.point_kind = 'workstation'
     AND NOT EXISTS (
           SELECT 1 FROM position_state ps
            WHERE ps.position_resource_id = dp.point_resource_id
              AND ps.occupied)
   ORDER BY dp.workstation_slot NULLS LAST, dp.id
   LIMIT 1
</select>
```

> ⚠ **必须配原子预约**：上面这个 SELECT 本身不是原子的 —— 两个实验并发时可能同时查到同一个空位。
> 正确做法是复用既有 `kernel/driver/PositionLock.java` 的**原子预约**（INSERT … ON CONFLICT DO NOTHING 试占），
> 抢不到就换下一个。**只读 SELECT + 后续写入 = 有竞态**，这是本设计里最容易写错的一处。
> 这正是文库制备岛文档自己写的"P8 位置？？目前冲突！"（X3 的原始证据）。

#### 4.3.3 双交接位（X4）

液体工作站的"台面内 / 台面外"两套交接位，用 `device_point.point_kind` 区分：

| point_kind | 含义 | 机械臂可达 |
|---|---|---|
| `deck_in` | 台面内（板已在工作站里） | 否（`robot_reachable=false`） |
| `deck_out` | 台面外（等交接） | 是 |

**校验**：同一设备的 `deck_in` 与 `deck_out` 必须成对存在且 `point_kind` 不同 ⇒ PF-28 预检。

### 4.4 资源锁与排程

#### 4.4.1 锁层级（自上而下）

| 层 | 锁键 | 实现 | 备注 |
|---|---|---|---|
| L0 岛 | `island_id` | 类 `ExperimentWorkcellScope` + 类 `IslandBindingGate` | 现状：调度是岛级互斥（README 旧说法已过时，2026-11-10 改资源级） |
| L1 设备实例 | `device_instance_id` | `DeviceLock` | 已有 |
| L2 设备端口 | `port_id` | `DevicePortLock` | 已有，但**信号量只覆盖 Transfer**（`LABOS_TRANSFER_PLAN` 默认关闭） |
| L3 点位 | `position_id` | `PositionLock`（原子预约 + 双锁按 id 升序） | 已有 |
| L4 机械臂 | `robot_resource_id` | 需新增（信号量模式同 `DevicePortLock`） | §4.2.2 |
| L5 物料 | `barcode` / `material_ref` | `PlateIdentity` + `CommandLedger` | 已有 |

#### 4.4.2 加锁顺序（防死锁）

**全局固定顺序**：`岛 → 设备实例 → 端口 → 点位 → 机械臂 → 物料`

> 既有 `PositionLock` 已实现"双锁按 id 升序"，本设计沿用同一手法：**所有多锁场景按资源 id 升序获取**。

**关键点**：搬运段的锁顺序必须与设备操作**相反**吗？**不是** —— 统一升序即可，跨层不构成循环等待。

#### 4.4.3 排程持久化（激活 `schedule_plan` / `schedule_item` / `resource_booking`）

```sql
ALTER TABLE schedule_plan ADD COLUMN IF NOT EXISTS optimization_factor integer NOT NULL DEFAULT 50;
ALTER TABLE schedule_plan ADD COLUMN IF NOT EXISTS max_iterations_running integer NOT NULL DEFAULT 0;
ALTER TABLE schedule_plan ADD COLUMN IF NOT EXISTS iteration_delay_sec integer NOT NULL DEFAULT 0;
ALTER TABLE schedule_plan ADD COLUMN IF NOT EXISTS external_id text;
ALTER TABLE schedule_plan ADD COLUMN IF NOT EXISTS scheduled_start timestamptz;

```

对应 外部厂商B §5.6 的四个字段（`Schedule` / `Optimization Factor` / `Max Number of Iterations Running at Once` / `External Id`）。

**`resource_booking` 激活**：每次调度决策写一行预约（谁占了哪个资源、从什么时候到什么时候），供甘特图与事后审计。

### 4.5 物料 manifest 与生命周期（G4）

#### 4.5.1 操作员的四步链路

```
① 选实验模板
     GET /api/experiment-templates?islandId=…
② 实例化 → 生成实验 + manifest
     POST /api/experiment-templates/{id}/instantiate
     ⇒ 创建 experiment_run + manifest_item 副本 + manifest_placement（unassigned）
③ config 位置
     PUT /api/experiment-runs/{runId}/placements/{itemId}  {positionId}
     ⇒ 实时校验：板型 / 高度 / 可达性 / 是否被占 / 白名单
④ 一键启动
     POST /api/experiment-runs/{runId}/start
     ⇒ 前置校验：全部 required item 状态 ≥ verified；齐套才放行
```

**"齐套"判定**（对应 外部厂商A 的 Load Dialogue）：

```
所有 manifest_item where required = true
  → 必须有 manifest_placement
  → placement.status ∈ {verified, loaded}
  → 板型匹配 device_point.plate_types（若配了）
  → 高度 ≤ device_point.max_height_mm（若配了）
  → 点位未被其他 run 占用（position_state）
  → 点位在 point_whitelist 内
```

任一不满足 ⇒ **启动按钮禁用**并给出**具体原因清单**（不是一句"校验失败"）。

#### 4.5.2 生命周期切换

| 时机 | 动作 |
|---|---|
| manifest 生成 | `manifest_item` 复制到 run，`plate`/`consumable`/`reagent` 的 `lifecycle` 置 `process` |
| 实验结束 | `lifecycle='process'` 的物料自动卸载：清 `position_state`、置 `status='unloaded'` |
| `lifecycle='inventory'` 的物料 | 保持原位，`status` 保持 `loaded`（下次实验可复用） |

**对应 外部厂商A**："Unlike process containers, inventory containers can be unloaded at any time."

#### 4.5.3 扫码校验（B6）

`node_binding.barcode_policy` 五值（外部厂商B P30）在搬运段执行：

| 值 | 行为 |
|---|---|
| `none` | 不扫码 |
| `read` | 读码写日志 |
| `update` | 读码后修正库存里的条码 |
| `validate_in` | 进设备时校验条码与库存一致，不一致 ⇒ 开人工窗口（`manual_window`） |
| `validate_both` | 进、出都校验 |

### 4.6 点位与设备方法绑定校验（`position_method` 的运行时校验）

**每次节点执行前**（不是只在预检）：

```
1. 绑定存在？            否 ⇒ 转人工（MANUAL）
2. position_method 允许？ 否 ⇒ 转人工
3. 点位可被该设备实例使用？ 否 ⇒ 转人工
4. 点位当前是否空闲？    否 ⇒ 等待或转人工（取决于是否同 run 占用）
5. 板型/高度匹配？       否 ⇒ 拒绝（这是硬约束，不该转人工）
```

**校验必须在执行期做**，因为点位占用是运行时事实。预检只能查静态配置。

## 5. 预检规则扩展

**编号接续 `PF-19`**（`PreflightChecker.java` 现有到 PF-19）。新规则落在 `PreflightChecker` 的同一 `Issue(code, level, nodeKey, message)` 结构里。

| 码 | Level | 含义 | 触发的检查 |
|---|---|---|---|

| **PF-21** | ERROR | 点位不允许该设备方法 | `position_method` 无匹配（scope 三级都查不到） |
| **PF-22** | ERROR | 绑定目标缺失 | `node_binding` 的 `position_id`/`pool_id`/`device_instance_id` 全空（DB 约束已挡，这里是 XML 旧路径） |
| **PF-23** | ERROR | 物料角色无绑定 | `material_role` 声明了但 `manifest_item` 里没有对应 role |
| **PF-24** | WARN | 物料角色未 config 位置 | manifest 有 role 但 `manifest_placement` 缺失或 `unassigned` |
| **PF-25** | ERROR | 板型不符 | placement 点位的 `plate_types` 不含物料板型 |
| **PF-26** | ERROR | 高度超限 | `max_height_mm` < 物料高度 |
| **PF-27** | ERROR | 点位不可达 | 需要机械臂搬运但 `robot_reachable=false` |
| **PF-28** | WARN | 双交接位不成对 | 有 `deck_in` 无 `deck_out`（或反之） |
| **PF-29** | ERROR | 同一实验内点位冲突 | 两个 binding 指同一 `position_id` 且物料不同 |
| **PF-30** | WARN | 点位缺示教坐标 | `robot_reachable=true` 但无 `robot_point` 行 |
| **PF-31** | WARN | 池成员不同型号 | `operation` 池内成员 `device_id` 不一致 |
| **PF-32** | WARN | 池成员跨岛 | 池成员不属于池的 `island_id` |
| **PF-33** | ERROR | 白名单不覆盖 | binding 的点位不在 `point_whitelist` 内 |
| **PF-34** | WARN | 方法作用域冲突 | 同一点位同一方法在 global 与 workflow 两个 scope 都绑了，优先级不明确 |

**与既有规则的衔接**：

| 既有 | 关系 |
|---|---|
| PF-10 绑定 id 失效 | **互补**：PF-10 查设备绑定，PF-21 查点位绑定 |
| PF-11 id 空间不一致 | 扩展：新增检查 `node_binding.position_id` 是否误填了 `resource_node.id`（应为 `device_point.id`）⇒ 并入 PF-22 的检查项 |
| PF-12 设备不在岛内 | 扩展：检查 `node_binding.device_instance_id` 所属岛 |
| PF-13 岛内无能力设备 | 扩展：池绑定时检查池内是否有能力匹配设备 |

**预检的调用时机**（现状已固定，不改）：保存时 / `GET /api/workflows/{id}/preflight` / 派发前（`IslandBindingGate`）。

> **PF 编号是既有资产，新增只能往后排。** 若评审认为某个新规则应复用旧码，需说明为什么旧码语义不匹配。

### 6.2 设备池

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/pools?islandId=&kind=` | 池列表（含成员数） |
| POST | `/api/pools` | 建池。**校验**：`operation` 池成员必须同型号（否则 409） |
| GET | `/api/pools/{id}` | 池详情 + 成员 |
| PUT | `/api/pools/{id}` | 改配置（策略、skip、启用） |
| DELETE | `/api/pools/{id}` | 软删（`deleted_at`）。有 `node_binding` 引用时 409 |
| POST | `/api/pools/{id}/members` | 加成员 `{deviceInstanceId, subGroup?, priority?}` |
| DELETE | `/api/pools/{id}/members/{deviceInstanceId}` | 移成员 |
| PUT | `/api/pools/{id}/members/order` | 调整顺序（`priority` 批量） |

**样例**

```jsonc
// POST /api/pools
{
  "code": "POOL-DISP-01",
  "name": "分液池",
  "islandId": 1000005,
  "poolKind": "operation",
  "strategy": "least_recently_used",
  "members": [
    {"deviceInstanceId": 162, "priority": 10},    // ID-1121，型号 device_id=146
    {"deviceInstanceId": 179, "priority": 20}     // ID-1321，同型号 device_id=146
  ]
}
// → 200 {"id": 9001, "code": "POOL-DISP-01", "memberCount": 2}
// → 409 {"error": "operation 池的成员必须同型号：设备实例 164（ID-1161）的型号与其他成员不同"}
```

> 样例用真实 id：`device_instance.id=162/179/164`，三者中 162 与 179 同型号（`device_id=146`），
> 164 是另一型号（`device_id=149`）⇒ 把它加进这个 operation 池应返回 409。
> 现状 250 个实例分布在 64 个型号上（最多的 `device_id=146` 有 30 个）⇒ operation 池有足够素材。

```tsx
const navItems = useMemo(() => {
```
