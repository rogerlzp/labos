## 一、总评与结论

**v2.0 是四份材料（A/B/C/D）以来质量最高的一版**。它不是"主设计"的扩写，而是把 C（Trade）的引擎分层提案经过本轮三方裁决修正后，升级成了一份**带规范性状态机、事务边界和验收矩阵的架构基线**。特别是第二个 commit（§23–30）直接回应了"概念描述与实现必须唯一解释"的痛点：五状态机分离、T01–T17 逐操作事务边界、异常路径唯一决策表、不变量→数据库约束映射、状态机验收矩阵——这些内容超出了我前轮评审要求的水位。

**结论：建议采纳 v2.0 为目标架构基线（Architecture Approved 方向），但有三个先决条件：**

1. **先修 §四 列出的 3 处规范内部矛盾**（都是同一文档内前后章节打架，修复成本低，但不修会在 Stage B 编码时产生两种实现）；
2. **拍板与现有 GraphRunner 的关系**（双轨还是转向，见 §六）——v2.0 §19 明确写了"不采用先照旧代码做串行版本的路线"，这**推翻了我前轮"采纳组件边界、不采纳重写节奏"的裁决建议**，这个决策权在用户，必须显式拍板而不是默认；
3. **补一节"现有系统 → v2.0 持久化模型映射"**（§五.1），否则台账/物料语义在搬迁中会静默丢失。

## 三、v2.0 的核心优点（相对 v1.0 与主设计的提升）

1. **五个状态机分离 + "禁止用一个 status 字段表达多维"**（§23 开篇，1845 行）。这直接回应了现有系统最大的维护病根：`NodeActivation=SUSPENDED ≠ Token 完成 ≠ Command 完成 ≠ Run=PAUSE_DRAINING` 的四层语义在旧代码里是揉在一起的。
2. **身份体系完整**（§23.1）：objectVersion / attemptId / coordinatorEpoch / lease fencingToken / commandId 五种身份"不能互相替代"，且明确"单实例也必须校验 objectVersion 和 attemptId"（1877 行）——避免单实例阶段养成坏习惯、多实例阶段翻车。
3. **T01–T17 事务边界精确到操作**（§25），且 §25.1 明确"设备网络调用、Worker 执行、外部 API、文件 IO、人工操作均不放在数据库事务内"——这是把现有 GraphRunner 里"事务内等设备"这类隐患在协议层禁掉了。
4. **异常路径唯一决策表**（§26）：30+ 个异常每个都有唯一处理和明确禁止行为，包括最容易被忽略的"DB commit 结果未知"（§26.1）和"Outbox at-least-once 不能直接套在非幂等设备命令上"（§26.2）。后者是我四份输入材料里都没人写到的真问题。
5. **治理设计成熟**：ADR 表（§20）、WRT2-01~12 开放问题带"关闭时点+必须提供的证据"（§21）、交付状态七级定义（§22）、冻结规则（§30.3"不能只改枚举不改协议文档"）。这套治理框架本身值得保留进工程规范。
6. **UNKNOWN/QUARANTINED 纪律贯穿始终**：从 Command 状态机（§10.2）到 Branch 状态（§23.5.2 "FAILED/UNKNOWN/QUARANTINED 不得伪装成 ARRIVED"）到 Stop 收敛（T16 "任何设备命令 UNKNOWN 或资源物理状态不明，不允许进入普通 PAUSED/STOPPED 并释放租约"），一致性很好。

## 四、必须修复的规范内部矛盾（P0，进 Stage B 前必须关闭）

### 4.1 🔴 Token 状态机两版冲突（§4.2 vs §23.3）

- §4.2（335–364 行）：Token 有 `DISPATCHED / RUNNING / SUSPENDED / COMPLETED / FAILED`，且 `SUSPENDED → READY → DISPATCHED` 循环。
- §23.3（1949–1998 行）：Token 只有 `READY / RESERVED / IN_FLIGHT / WAITING / CONSUMED / TERMINAL / INVALIDATED`，并**明确声明**"NodeStarted 不改变 Token 状态"（1982 行）、"禁止 NodeActivation=SUSPENDED 与 Token 状态混同"。

两版**状态集合和语义都不同**。§23 开篇写了"若存在不一致以本章为准"，但 §4 标题是"控制流形式化语义"，读者（和编码者）不会认为第 4 章已被作废。**修法**：§4.2 整节改写为指向 §23.3 的摘要，或删除 §4.2 状态图只保留文字定义；§4.3/4.5 与 §23.3/§23.4 的衔接语句同步核对。

### 4.2 🔴 STOP_DRAINING 的 FAILED 出边缺失（§13.1/§13.4/T16 vs §23.2.1）

- §13.1 状态图（1224–1229 行）：`STOP_DRAINING → STOPPED / FAILED / MANUAL_REQUIRED / QUARANTINED`。
- §13.4（1267 行）："所有在途动作状态确定后进入 FAILED"。
- T16（2620 行）：Drain 完成可写 `Run=PAUSED / STOPPED / FAILED / MANUAL_REQUIRED / QUARANTINED`。
- **但 §23.2.1 转移表（1914–1917 行）STOP_DRAINING 只列了 STOPPED / QUARANTINED / MANUAL_REQUIRED 三条，没有 FAILED。**

而 §23 是"规范性、以此为准"的章节——按字面实现，Stop 收敛后**无法**合法进入 FAILED。**修法**：§23.2.1 补一行 `STOP_DRAINING | DrainComplete(业务失败确认) | 所有副作用已确定且含不可恢复业务失败 | FAILED | RunFailed Event`，或者明确"STOP_DRAINING 的业务失败统一落 STOPPED + failureReason，FAILED 仅由 FatalFailure 路径进入"，二选一，但必须唯一。

### 4.3 🟡 §8.1 的异步持久化暗示 vs §28 的同步事务模型

- §8.1（689 行）："持久化操作可通过异步命令完成，但状态提交的线性化顺序必须由 Run mailbox 明确维护"。
- §28 参考算法（2721–2773 行）：mailbox 处理函数**内部同步 begin transaction → commit**，"事务内不做 IO"指设备/Worker，DB 事务是同步的。
- 且 WRT2-05（1732 行）把"同步事务还是持久化命令队列"列为开放问题。

三处并存会让 Stage B/C 的读者各取所需。**修法**：§8.1 改为"本版采用 §28 的同步事务模型；持久化命令队列仅作为 WRT2-05 关闭时的备选"，并注明与 §28 的关系。

## 五、设计缺口（P1，进对应 Stage 前补）

### 5.1 缺"现有系统 → v2.0 持久化模型映射表"

v2.0 声明"不承担旧接口兼容"（§1 前言、ADR-015），这作为架构立场成立；但**业务上台账不可丢**：现有 `run_node` / `run_command` / 事件流 / `StepSink·StepCollector` / 物料台账（`source_loop_index`）/ 板位，必须有一张映射表说明每一样对应到 v2.0 的哪个实体（或"由 Handler + Domain Service 承载，不再由 Runtime 表存储"）。没有这张表，Stage D 的 Handler 搬迁会静默漏掉台账语义——而物料归属恰恰是本轮 loopIndexSupplier 竞态里最严重的后果面。**建议**：在 Stage A 退出条件里加一条"存量数据与业务语义映射表完成评审"。

### 5.2 Handler 搬迁成本未评估——这是 v2.0 最大的隐藏工作量

v2.0 把现有引擎的全部业务逻辑（步骤规划、物料门控、设备派发细节、break/continue 控制流）都抽象成 `NodeHandler` 契约（§9.2），但**没有盘点存量逻辑如何装进这个契约**。我前轮 A 材料的"第 1 步抽 executeNode：break/continue ⇒ Outcome 枚举，逐点映射"正是这件事的前置——即使走 v2.0 全重写路线，这一步的"逐点映射清单"依然是 Handler 实现的规格书。**建议**：Stage A 增加交付物"存量节点行为 → Handler Descriptor + NodeResult 映射清单"，并把"纯重构可验证"的分层比对（单分支流程：节点顺序、run_node、run_command、事件序列、台账条数逐项 diff）作为 Handler 等价性的验收锚点。

### 5.3 变量 CAS 失败 × 设备节点完成的交互未定义

T05 把"变量写入（CAS）"放进节点完成事务（2437 行），异常表规定"整个完成事务回滚；按冲突策略重算或失败"（2649 行）。对纯计算节点这是对的；但对**设备节点**，完成消息来自设备最终事件（command 已 SUCCEEDED），若此时变量 CAS 失败导致事务回滚，逻辑完成丢失而物理动作已发生——重试路径会落到 §23.4.4 的"同 commandId 幂等重发"上，绕了一圈且依赖设备支持幂等。**修法**（二选一，写进 §25.6/§26）：
- 完成事务内的变量写入**在 Coordinator 串行事务内重读重放**（Coordinator 是单写者，串行处理使 CAS 冲突在事务内可解），DB 层 CAS 仅作最后防线；或
- 规定"设备节点的完成事务不允许因变量冲突回滚"，变量写入降级为完成后的补偿步骤（需说明其与 §7.5 提交边界的关系）。

### 5.4 重试门控的状态机衔接缺口

§23.3.1 规定 `IN_FLIGHT | NodeFailed | 按 retry policy 转 READY（新 attempt）`（1974 行），即重试等待期 Token 回到 READY；而 Activation 处于 `RETRY_WAIT`、受 `retryAfter` 门控（§23.4.2）。**但 T03 Reservation 事务（2384–2393 行）的前置校验里没有"Activation=RETRY_WAIT 且 RetryDue"**——按 23.3.1 字面实现，Scheduler 可在 retryAfter 未到时把 READY Token 预约派发。**修法**：T03 前置条件补"若 Activation 存在，须为 READY 且无未到期 retryAfter"，或在 Token 增加 RETRY_WAIT 衍生态（不推荐，会加重 Token 语义负担）。

### 5.5 前端实时推送链路未指定

现有系统的事件链（`WorkflowService.events` → tee → JdbcEventStore → 前端时间线）承载 UI 实时刷新。v2.0 的 `runtime_event` 是运行时事实日志，§14.4 只定义了查询视角，**没有定义 UI 订阅/推送通道**（以及旧事件流在切换期的双写或停写）。不阻塞架构批准，但 Stage E 前要补。

### 5.6 停机切换方案缺失

Stage A–F 没有一节讲"切换"：存量在跑 run 如何收尾、新旧 Runtime 并行期怎么隔离（feature flag？新 run 走新 Runtime、旧 run 跑完旧引擎？）、回滚预案。§22 有交付状态定义但没有切换定义。**建议**：Stage F 后补"Stage G：切换与并行期"。

## 六、与现有 GraphRunner 的关系——需要用户拍板的核心决策

### 6.1 v2.0 推翻了我前轮"双轨"建议，这个推翻本身是有理由的

我前轮反对重写的三条理由（无"改造前"可比、工作量数周、现场真机风险）里，第一条被 v2.0 部分解掉了：§23–30 的状态机验收矩阵 + §29.3 事务故障注入，提供了**不依赖"与旧引擎行为等价"的正确性判据**（新的判据是状态机性质 + 故障注入，不是行为 diff）。第三条则被 Stage F（设备白名单、非危险动作、隔离环境、安全负责人签署）制度化了。真正剩下的只有第二条——**工作量与周期**，v2.0 对此完全没有估算。

### 6.2 已落地工作的去留要明确

- `5d32606`（6 个共享容器线程安全）：对新 Runtime 无用，但对**切换期内继续生产的旧 GraphRunner** 仍然必要——只要旧引擎还在线上跑一天，这些修复就有效一天。**建议保留**。
- `066b9f5`/`517b415`（RunAdmission 准入与建 run 同事务）：与 v2.0 T01/T02（CreateRun/StartRun）语义同构，可平移为新 Runtime 的 Run Creation Service。**建议明确声明其为 v2.0 的第一块已实现件**，避免重复设计。
- `16bbe8c`/`3fbd356`（BPMN 基准流程脚本 + 主设计文档）：主设计文档应标记为"被 v2.0 取代"或转为 v2.0 的输入存档，避免三份"现行设计"并存（主设计 / v1.0 / v2.0）。

### 6.3 我的建议（供拍板参考）

**采纳 v2.0 为唯一目标架构 + 旧引擎冻结特性只做安全修复的双轨制：**

1. v2.0 按 §四 修完三处矛盾后，标记 `Architecture Approved`，后续设计只此一份（主设计/v1.0 归档）；
2. 旧 GraphRunner **冻结新功能**，只接受安全/数据正确性修复（容器线程安全类），理由是切换期内它还在生产；
3. Stage A/B 的产出（状态机核心 + 内存 Repository）可以独立验证，**不等 Stage C 的持久化**就能得到第一次"新内核对旧图形跑出一致结果"的证据——这是判断重写可行性最早的闸口，建议给 Stage B 设一个显式时间盒，超期即回到增量路线重新决策；
4. 现场在跑流程先做一次全量图扫描（我前轮未闭合项 #2）：统计有多少图包含共享普通节点/回边/嵌套——**这个数字同时决定旧引擎的冻结范围和新 Runtime 编译器的拒绝清单**，是两条路线共用的前置，建议本周就做。
