## 1. 这份文档要回答什么

这份文档不重复讨论"要不要做真并发"。目标是把下面三件事讲清楚：

1. 现在的方案还缺什么，哪些点如果不先补，第一次上真并发就会先坏掉。
2. 我建议采用什么实现路径，为什么这条路径比"直接把 GraphRunner 并发化"更稳。
3. 如何把实现范围收敛成一个能落地、能验证、能逐步扩展的 V1。

一句话结论：

> 不建议做"并发版 GraphRunner"；建议做"单线程主循环 + 编译后的并发 BranchExecutor"，并把 V1 的图形范围严格收窄。

## 2. 当前问题

## 2.1 现状不是"不能并发"，而是"推进模型天生串行"

当前 `GraphRunner` 的主循环是单线程 `ready.poll()` 模型：

- 一个时刻只取一个节点
- `gateway_parallel` 只是把多条出边依次压进同一个 `ready`
- 因此并行分支在代码层只是"都会走到"，不是"同时执行"

这点在现有方案文档中已经有实测证据：两条分支开始时间相差约 14 秒，完全不重叠。

## 2.2 方案里低估了真正的共享状态范围

当前方案把主要剩余问题写成两处：

1. `RunProgress.nodes` / `aborted` / `materialHold`
2. `RunStateMachine.seq`

这两处确实要改，但它们不是最后两处。只要把分支真正并发跑起来，至少还会碰到下面这些共享对象：

### A. WorkflowService 内存事件列表

`WorkflowService` 在创建状态机时，使用：

- `List<ExecutionEvent> events = new ArrayList<>()`
- `tee(events, store, monitor)`

而 `tee(...)` 内部直接 `sink.add(e)`。

这意味着并发分支只要同时发事件，就会并发写一个普通 `ArrayList`。

### B. StepCollector

`StepCollector` 现在有两处普通容器：

- `done = new ArrayList<>()`
- `resourceByStep = new HashMap<>()`

如果多个分支并发调用 `onStepStart/onStepDone`，这里会出现：

- step 记录丢失
- 设备映射丢失
- 记录顺序不可预期

### C. RunMonitor

`RunMonitor` 虽然用 `ConcurrentHashMap` 存 run，但 `Live.done++ / manual++` 仍是普通整型自增。

并发下这会造成计数丢失。

### D. GraphRunner 本地推进语义不止 `done/visits`

方案里把 D1 的主要矛盾写成 `done/visits`，但当前推进逻辑实际还依赖：

- `pending`
- `ConditionalBranchTracker tracker`
- `done`
- `ready`

尤其 `activate(...)` 和 `recheckConditionalJoins(...)` 会共同决定 join 何时入队。

也就是说，只做"done 并集 + visits 取 max"并不能覆盖含条件汇合、嵌套网关、局部回边的图形。

## 2.3 现方案默认接受"任意并行图形"，这是复杂度真正失控的来源

如果 V1 一上来就允许下面这些形状：

- 并行组里再套并行组
- 分支里出现条件汇合
- 分支里出现回边循环
- 两个分支共享业务节点

那实现难点就不再是"并发执行节点"，而变成：

- 图切分
- 多组局部状态 merge
- 多层 stop/pause 传播
- join 激活语义保持与串行版本完全一致

这会把第一次实施的失败概率拉得很高。

## 2.4 嵌套并行不只是信号量问题，还有线程池自阻塞问题

方案文档里对 D7 的建议是：

> inner 在 outer 的分支线程里执行，不额外申请信号量

这个方向只解决了"信号量自锁"的一半问题，没有解决线程池自阻塞。

典型死锁路径：

1. 外层并行组占满固定线程池
2. 每个 worker 线程跑到内层并行组
3. worker 在线程里提交内层任务，再 `allOf().join()`
4. 但线程池已经没有空闲 worker 去执行 inner task

结果是：

- 没有额外申请信号量
- 仍然会因为线程池耗尽卡死

## 3. 我建议的总体思路

## 3.1 不做"并发版 GraphRunner"，做"单线程主循环 + 并发 BranchExecutor"

核心判断：

> GraphRunner 继续保持"唯一推进器"；并发只发生在一个已经编译好的并行组内部。

目标结构如下：

```mermaid
flowchart LR
    A[主循环仍单线程] --> B[遇到 split_parallel]
    B --> C[编译 ParallelGroupPlan]
    C --> D[每个分支形成 BranchPlan]
    D --> E[提交线程池并发执行]
    E --> F[allOf 等齐]
    F --> G[主线程汇总结果并继续]
    style A fill:#bbdefb,color:#0d47a1
    style D fill:#c8e6c9,color:#1a5e20
    style F fill:#fff3e0,color:#e65100
```

这个模型的关键价值是：

1. 主循环仍然是单线程，`ready/pending/tracker` 的全局语义不被全面改写。
2. 分支线程不是"各自维护一个小 GraphRunner"，而是顺序执行一段已编译好的节点列表。
3. join 仍然由主线程统一汇总，不把 run 级状态机拆成多份。

## 3.2 V1 先严格收范围

为了把第一次实施做稳，我建议 V1 只支持：

- `split_parallel -> 多条线性分支 -> join_parallel`

并且显式禁止：

- 并行组内再次出现 `split_parallel`
- 并行组内出现 `JOIN_CONDITIONAL`
- 并行组内出现回边循环
- 两条分支共享业务节点（`join` 节点本身除外）

也就是说，V1 的并行组是一个**编译期可证明的 DAG 片段**，每条分支都是单入口、单出口、无再分叉的线性路径。

这有两个直接好处：

1. `D1` 从"合并任意形状局部状态"收缩成"每个分支顺序跑完一段 plan"。
2. `done/visits/pending/tracker` 基本不需要做复杂 merge。

## 3.3 为什么不做"每分支一个 GraphRunner 实例"

表面上看，每分支一个实例好像更干净，但实际问题没有减少：

1. `RunStateMachine` 仍然是 run 级共享对象
2. `ExecutionListener` / `StepSink` / `RunMonitor` 仍然是 run 级共享副作用出口
3. 分支间变量、停止信号、事件游标仍要共享
4. 最后还是要解决"多个 GraphRunner 的状态怎么汇总回主 run"

换句话说：

> "每分支一个 GraphRunner"没有绕开共享状态，只是把共享状态藏到了对象边界后面。

所以我不建议走这条路。

## 4. 具体实现方案

## 4.1 编译期：先把并行组编译成计划

新增一个编译结果对象：

```text
ParallelGroupPlan
  - splitKey
  - joinKey
  - branches: List<BranchPlan>

BranchPlan
  - branchId
  - nodeKeys: List<String>
  - nodeExecPlans: List<NodeExecPlan>
```

编译期要做的校验：

1. `split` 与 `join` 配对
2. 每条分支从 `split` 出边到 `join` 前路径唯一
3. 除 `join` 外，任何业务节点不能同时属于两条分支
4. 分支内部不得再出现并行组 / 条件汇合 / 回边

如果不满足，直接在保存或发布阶段报错，不进入运行态。

## 4.2 运行期：主循环委托并行组，而不是自己并发化

主循环逻辑：

1. 读到普通节点：仍调用 `executeNode(...)`
2. 读到 `split_parallel`：不继续走原 `activate` 路径
3. 直接查到 `ParallelGroupPlan`
4. 调 `runParallelGroup(plan, ctx)`
5. `runParallelGroup` 阻塞返回后，由主线程把 `join` 视为已完成前驱，再继续推进

这个模型意味着：

- 运行期的图推进仍由主线程负责
- worker 线程只执行 node plan，不再参与全图拓扑推进

## 4.3 分支执行器：顺序执行，不再做局部拓扑计算

每个分支线程做的事情应该很简单：

1. 遍历 `BranchPlan.nodeExecPlans`
2. 每个节点开始前检查：
   - `stopFlag`
   - `pauseToken`
3. 调统一的 `executeNode(plan, ctx)`
4. 把结果写到 `BranchResult`

这样分支线程不需要维护：

- `pending`
- `ready`
- `ConditionalBranchTracker`

局部复杂度会明显下降。

## 4.4 共享上下文：显式建模，不靠零散字段拼出来

建议把共享执行态收口成一个对象：

```text
FlowExecutionContext
  - FlowVariableStore variables
  - AtomicBoolean stopFlag
  - PauseCoordinator pause
  - ConcurrentMap<String, Long> eventCursors
  - RunProgress progress
  - RunStateMachine stateMachine
  - ExecutionEventSink eventSink
  - StepSink stepSink
```

其中最重要的是：

### FlowVariableStore

不要让多个分支直接拿 `ConcurrentHashMap<String,String>` 做业务变量。

应该封成一个带语义的方法集：

- `get`
- `put`
- `putAll`
- `markConsumed`
- `alreadyConsumed`
- `refreshExternalVariables`

同时规定：

- 同一并行组内，两分支禁止写同一 key
- 不提供原子自增/原子累加语义
- 真有多分支合并计算，一律 `join` 后单节点做 reduce

### PauseCoordinator

不要让每个分支自己猜"暂停是否完成"。

需要一个并行组级协调器，记录：

- 分支总数
- 已到安全边界的分支数
- 未到达分支列表
- 暂停等待起点时间
- 最大暂停等待上限

### ExecutionEventSink

把现在零散的：

- `events`
- `tee(...)`
- `RunMonitor`

收口成一个线程安全 sink，统一做：

- 事件收集
- 事件广播
- 运行态监控更新

## 5. 必须先补的线程安全项

## 5.1 状态机与进度

### RunProgress

- `nodes` 改 `ConcurrentHashMap`
- `aborted` 改 `AtomicBoolean`
- `materialHold` 改 `AtomicBoolean`

### RunStateMachine

- `seq` 改 `AtomicLong`

这里我判断：

> 事件序号允许跳号，但必须单调递增。

现有代码和注释都强调的是"顺序可重建"，我没看到下游依赖"连续无缺口"。

## 5.2 WorkflowService 侧的共享容器

### ExecutionEvent 列表

把：

- `List<ExecutionEvent> events = new ArrayList<>()`

改成：

- `Queue<ExecutionEvent> events = new ConcurrentLinkedQueue<>()`

或者自定义 `ExecutionEventSink` 封装。

### StepCollector

把：

- `done = new ArrayList<>()`
- `resourceByStep = new HashMap<>()`

改成：

- `done = new ConcurrentLinkedQueue<>()`
- `resourceByStep = new ConcurrentHashMap<>()`

### RunMonitor

把：

- `done++`
- `manual++`

改成：

- `AtomicInteger`
或
- `LongAdder`

## 5.3 文档里遗漏但实现上必须明确的对象

我建议在方案文档里新增一张表，列出"并发后所有共享写对象"：

| 对象 | 当前类型 | 是否共享 | 处理 |
|---|---|---|---|
| `RunProgress.nodes` | `LinkedHashMap` | 是 | 改并发容器 |
| `RunProgress.aborted` | `boolean` | 是 | 改原子布尔 |
| `RunStateMachine.seq` | `long` | 是 | 改原子长整型 |
| `WorkflowService.events` | `ArrayList` | 是 | 改并发队列 |
| `StepCollector.done` | `ArrayList` | 是 | 改并发队列 |
| `StepCollector.resourceByStep` | `HashMap` | 是 | 改并发映射 |
| `RunMonitor.done/manual` | `int` | 是 | 改原子计数 |

## 6. 停止、暂停、等待三件事怎么统一

## 6.1 "分支不设超时"不等于"控制平面可以无限等"

这里必须拆成两层：

### 业务耗时

- 孵育 30 分钟是正常
- 离心 20 分钟是正常
- `__awaitEvent` 等设备上报可能也要很久

这类不应该因为"长"就被判失败。

### 控制等待

但下面这些等待，必须有控制上限：

- 分支失败后 drain 已发命令
- 暂停请求后等所有分支到边界
- stopFlag 已设后，等待某个分支从 `__awaitEvent` 或长步骤里收尾

这类上限不是业务 SLA，而是**控制平面的收尾预算**。

## 6.2 配置策略：按方法为主，设备可覆盖

我建议统一口径：

- 以方法配置为主
- 设备可覆盖
- 没有配置时再走默认值

原因：

1. 收尾窗口更接近动作语义，不是设备型号语义
2. 同一设备不同方法，等待特征可能完全不同
3. 设备侧若确实有特殊行为，再做覆盖更合理

## 6.3 超上限后的处置

超上限不等于"业务失败"，建议统一进入：

- `UNKNOWN`
- 或 `QUARANTINED`
- 或 `PAUSE_BLOCKED`

重点是：

- 不自动释放
- 不自动继续
- 必须留下状态证据和阻塞原因

## 7. V1 明确不做什么

为了保证第一次实施可收敛，我建议在文档里明确写出 V1 不做：

1. 不支持嵌套并行组
2. 不支持并行组内条件汇合
3. 不支持并行组内回边循环
4. 不支持同组内两分支写同一变量 key
5. 不提供并行变量原子累加 API

这不是永久不做，而是：

> 第一版先把"两个独立线性长任务真的并起来"做稳，再扩图形能力。

## 8. 分阶段实施建议

## 第 0 步：把范围锁死

先补文档，把 V1 支持/不支持的图形形状写死。

没有这一步，后面的实现很容易边做边膨胀。

## 第 1 步：纯重构，抽出 `executeNode(...)`

目标：

- 不改行为
- 把当前 `760-1000+` 的执行段抽成可复用方法

产物：

- `NodeExecutionOutcome`
- `executeNode(...)`

验收：

- 单分支流程与改造前行为完全一致

## 第 2 步：先补所有共享状态并发安全

目标：

- 不是先开并发
- 是先把未来会被并发访问的对象全改安全

验收：

- 并发压测下不出现 `ConcurrentModificationException`
- 事件/step/monitor 不丢写

## 第 3 步：加 `ParallelGroupPlan`

目标：

- 完成 `split->join` 配对
- 输出线性 `BranchPlan`
- 编译期拒绝非法图形

验收：

- 非法图形在保存/发布时报错
- 合法图形能稳定得到 branch plan

## 第 4 步：实现 `runParallelGroup`

目标：

- worker 线程并发执行 `BranchPlan`
- 主线程 `allOf` 等齐后统一汇总

验收：

- 两分支实际起始时间差 < 1 秒
- 总耗时明显小于串行

## 第 5 步：加停止/暂停协调

目标：

- `stopFlag`
- `PauseCoordinator`
- drain / pause 上限

验收：

- 一分支失败后，其余分支不再进入新节点
- 暂停只在所有分支到安全边界后完成

## 9. 验证策略

我不建议只拿一个基准流程做端到端对比。

至少要分三层：

## 9.1 纯重构等价验证

验证 `executeNode(...)` 抽取前后：

- 单分支流程
- 无并行图
- 同输入同输出
- 同 step 台账
- 同事件流

## 9.2 并行功能验证

重点验证：

- 两分支真正并发
- 失败 stopFlag
- 暂停等待边界
- step/事件/monitor 不丢

## 9.3 非法图形验证

验证编译期拒绝：

- 嵌套并行
- 条件汇合
- 回边循环
- 分支重叠节点
- 同组同 key 写变量

---

## 10. 最终建议

如果目的是"这次就把真并发做出来，而且做稳"，我建议最后定成下面这句话：

> V1 不做任意图形并发，只支持 `split_parallel -> 线性独立分支 -> join_parallel`；运行时采用"单线程主循环 + 编译后的并发 BranchExecutor"，并在开并发前先补齐所有共享状态的线程安全。

这条路径的优点是：

1. 正确性边界清楚
2. 共享状态收口明确
3. 图形限制可验证
4. 回归成本可控
5. 后续扩展到嵌套并行时，仍有稳定的骨架可以沿用

如果一句话说得更直白一点：

> 第一版先把"两条独立长分支真的重叠起来"做成，不要第一版就试图并发化整张图。
