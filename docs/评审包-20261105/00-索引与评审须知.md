## 4. 建议评审重点（按风险排序）

1. **崩溃恢复端到端是否真堵上缺口**：既有 L2 自测（`workflow.StartupSettleSelfTest` / `workflow.SchedulerRehydrateSelfTest`）在进程内 `new` 实例、包内重载造数，只证明方法对，证明不了 `ApiServer` 启动入口真调了 settle/rehydrate。本轮改为真 `kill -9` 真重启，断言点见 `01` §3。
2. **逻辑节点分层口径**：画布收敛（移除存不下/跑不了的节点）与设计器补齐（并行/条件/循环上限）之间是否存在**能力空洞**；两套条件语法是否真的统一到后端 `ConditionEvaluator`（画布自研 `evalCondition` 是否已下线）；`maxIterations` 的驼峰键前后端是否一致。
3. **调度派发顺序同源**：`ExperimentScheduler.dispatch()` 是否真的复用 `QUEUE_ORDER` 比较器，与页面快照排序逻辑同源（此前存在「测试过、实际乱」的隐患）。
4. **门禁机制可靠性**：「阈值只涨」+ `pre-push` 全量门禁是否会因环境变量缺失产生假红灯/假绿灯；跳过（SKIP）分支是否会掩盖真失败。
5. **测试台账自洽**：`docs/测试用例总表.md` 的常量表 / 脚本清单 / 诚实清单是否与 `scripts/ci-gate.sh` 的实际阈值 100% 对得上。
6. **中英文档 1:1**：`scripts/verify-en-docs.py` 硬错误 0（结构对齐 / 链接全通 / 中文残留归类）；是否仍有「留旧文 + 加勘误」式的非自洽修补。
7. **`subProcess` 静默跳过的风险敞口**：设计器 palette 仍保留 `create.subprocess-expanded`；`subProcess` 不在解析器白名单，连进链路会静默跳过后继（整单仍报 `completed`）。本轮按裁定「仅登记、暂不动代码」。
8. **崩溃恢复脚本自身的环境鲁棒性**：日志路径改为 `pgrep` + `lsof` 反查（避免写死路径假红）；二次重启的幂等断言是否避开了「全局计数」这类脆弱口径。

## 5. 评审问题清单（请 AI 重点回答）

1. 崩溃恢复端到端用例，**是否足以证明**「生产启动入口真的调了 settle/rehydrate」，还是仍存在「测的是脚本而非生产路径」的缺口？
2. 崩溃恢复脚本中「孤儿 `run` / `experiment_run` 被 settle」「合法 `completed` run 不被触碰」「二次重启幂等」三条断言，**是否覆盖了真实崩溃语义**？还漏了哪些边界（如 paused / 扣留态 / 半写批次）？
3. 逻辑节点分层：把逻辑节点从实验画布移出、收敛到流程设计器，**是否与用户口径（绝大多数逻辑在流程内、极少数跨流程）一致**？有没有被误删的合法用法？
4. 条件表达式语法统一到后端求值器后，**是否还有第二套求值逻辑残留在前端**（会导致「页面看着通过、执行走错分支」）？
5. 调度派发复用 `QUEUE_ORDER` 的改动，**是否在所有出队路径**上生效（正常派发 / rehydrate / 扣留解除续队）？
6. 「阈值只涨」的门禁策略，**是否足够**？有没有「用例数不降但覆盖面下降」的空子？
7. `subProcess` 静默跳过只登记不修，**风险是否可接受**？三条候选修法（预检拦截 / palette 移除 / 解析器透明化）你倾向哪条？
8. 测试台账的诚实清单（12 条）是否**如实**反映了缺口？有没有被美化的项？
9. 中英文档 1:1 的机器核对（结构对齐）能否替代人工审阅？**哪些内容是机器核对看不见的**？
10. 还有哪些「仿真全绿、真机必炸」的隐性假设（尤其崩溃/重启、时序、长任务）？
