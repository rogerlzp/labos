## 四、⚠ 重点复核的 6 条（改了语义，最可能引入新问题）

### 4.1 P1-1 生产装配 `db=null`（改装配）

**改了什么**：`DriverStepExecutor` 新增构造 `(registry, sink, db, tenantId, runId)`；
`WorkflowService` 装配改用它。

**为什么危险**：这是**四层资源保护的总开关**。改之前 `protect` 恒 false，
所有 Transfer 直接裸调 `driver.execute`；改之后**所有 Transfer 都会走抢资源流程**。

**要复核**：
```bash
# ① 确认装配点真的传了 db
grep -n "new DriverStepExecutor(registry, persistSink, db" \
  labos-kernel/src/main/java/com/labos/kernel/workflow/WorkflowService.java

# ② 跑一次真实 Transfer，看是否出现抢资源的日志
LABOS_TRANSFER_PLAN=1 ... 跑一个含 Transfer 的流程
grep "通道\|门\|位置" /tmp/xxx.log
```

**判断标准**：日志里应能看到抢门/抢通道/抢位置的记录；
若仍是裸执行，说明装配没生效。

### 4.2 P1-4 位置预约三态语义（改判定条件）

**改了什么**：

```sql
-- 原：reserved_until IS NULL → 认为空闲
-- 新：reserved_by_run IS NULL → 才认为空闲
AND (position_state.reserved_by_run IS NULL
     OR (position_state.reserved_until IS NOT NULL AND position_state.reserved_until < now())
     OR position_state.reserved_by_run = EXCLUDED.reserved_by_run)
```

**为什么危险**：这条 WHERE 决定**所有位置预约**能否成功。

**要复核**：
1. 永久承诺（`reserved_by_run` 非空 + `reserved_until` NULL）**真的抢不走**吗？
2. 过期预约（`until < now()`）**真的能抢**吗？
3. 已有数据里有没有 `reserved_by_run` 非空但 `reserved_until` 为 NULL 的**历史脏数据**？
   如果有，那些位置会变成**永久锁死**。

```sql
-- 第 3 点必查
SELECT count(*) FROM position_state
WHERE reserved_by_run IS NOT NULL AND reserved_until IS NULL;
```

**已自查**（2026-11-02）：

```
永久锁死数：0
状态分布：空闲 9 条（无历史脏数据）
```

当前库干净。**但生产库导入迁移时仍需查这一条。**

### 4.3 P1-15 最短间隔补等（行为变化）

**改了什么**：原来 `sleep(min(needMs, 60_000))`，现在**等够 `needMs`**（上限 2 小时）。

**为什么危险**：**真机上会出现“看着卡住”**。
工艺要求间隔 30 分钟，现在真的等 30 分钟，而界面只是“正在执行”。

**已自查**（2026-11-02）：

```
现有流程 min_sec：max=3 秒 / avg=3.0 秒 / 仅 1 条配了约束
```

**影响可忽略** —— 库里几乎没有时间约束，改动不会让现有流程变慢。
但**新流程如果配大间隔，行为会与以前不同**（以前等 60 秒放行，现在等够）。

**要复核**：
- 未来配置 `min_sec > 60` 的流程，是否需要 UI 提示"这里会真等 N 分钟"？
```sql
SELECT max(min_sec), avg(min_sec), count(*) FROM (
  SELECT (params->'time_constraint'->>'min_sec')::int AS min_sec
  FROM workflow_node WHERE params->'time_constraint' IS NOT NULL
) t;
```

### 4.4 P1-8 暂停检查点（新增机制）

**改了什么**：`GraphRunner` 在**任务节点边界**检查 `run.status`，暂停就 `break` 并把节点放回队列。

**为什么危险**：每个任务节点**多一次数据库查询**；且 `break` 后的收尾逻辑要保证不覆盖 `paused`。

**要复核**：
1. 高频短节点流程的性能影响（每节点一次 `SELECT status`）
2. `settleRun` 的 `isRunPaused` 保护是否覆盖所有退出路径

**已有单测**：`GraphRunnerTest` 新增用例（3 节点链，第 2 个边界暂停 → 只跑 1 个）。

### 4.5 P1-23 `apiFetch` 非 2xx 抛错（前端全局）

**改了什么**：`apiFetch` 对非 2xx 一律抛 `ApiError`。

**为什么危险**：**71 处引用全受影响**，其中 27 处自己有 `if (!r.ok)` —— 现在变成死代码。

**要复核**：
- 有没有哪处**依赖“拿到非 2xx 自己处理”**（比如把 404 当“不存在”而不是错误）？

```bash
# 找所有依赖非 2xx 语义的地方
grep -rn "r.status ===\|res.status ===" webapp/src/pages/ | head -20
```

**已知**：`Island.tsx:165` 原来写 `r.ok ? r.json() : r.text()`，
改后 `r.ok` 永真，逻辑等价（失败已在 apiFetch 抛）。**其余 26 处需要评审确认。**

### 4.6 P0-1 鉴权前移（安全边界）

**改了什么**：鉴权块从路由链中段移到**所有路由之前**；`isPublic` 补 `/api/auth/login`。

**为什么危险**：白名单漏一个就**误拦正常接口**；多一个就**留后门**。

**要复核**：
```bash
# 逐个检查白名单
sed -n '/private static boolean isPublic/,/^    }/p' \
  labos-kernel/src/main/java/com/labos/kernel/api/ApiServer.java

# 实测：所有非白名单路由应 401
for p in /api/workflows /api/runs /api/topology /api/process-status \
         /api/devices /api/alerts /api/users /api/heartbeat; do
  printf "%-24s " "$p"
  curl -s -o /dev/null -w "%{http_code}\n" "http://localhost:18080$p"
done
```

**已自查**（2026-11-02）：

```
/api/workflows     401    /api/alerts          401
/api/runs          401    /api/users           401
/api/topology      401    /api/heartbeat       401
/api/process-status 401   /health              200
/api/devices       401    /api/auth/login      405（只允许 POST，正确）
```

**判断标准**：除 `/health`、`/api/auth/login`、静态资源外，**全部 401**。
