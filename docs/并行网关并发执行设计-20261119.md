# 并行网关并发执行设计

- 日期：2026-11-19
- 性质：设计文档，**未实施**
- 前置：单实例部署；不含多实例 fencing
- 目的：把「并行网关」从**逻辑并行（顺序执行）**改为**真并发（同时执行）**

---

## 0. 一页纸

| 项 | 内容 |
|---|---|
| 现状 | `GraphRunner:736` 单线程 `ready.poll()`，并行网关只把多分支**依次压入同一队列**，逐个执行 |
| 目标 | `SPLIT_PARALLEL` 的多个分支**同时执行**，`JOIN_PARALLEL` 汇合 |
| 核心模型 | 并行组（ParallelGroup）：split 到 join 之间的子图，每条出边一个分支 |
| 四条执行语义 | 失败即停发（已发等完成）/ 变量流程级共享 / 禁止同名冲突 / 分支无超时 |
| 改造点 | **8 项**，约 990 行 |
| 最大风险 | 「无超时 + 失败等已发命令完成」可能无限等待 |
| 对前序文档的影响 | 4 处结论要改（waiters 唯一键、事件分层、暂停语义、锁重入） |

## 1. 四条执行语义（已定）

| ID | 决策 | 具体含义 |
|---|---|---|
| **D1** | 一个分支失败 → **所有分支立即停止发新指令**；已发出的指令**等设备完成后**再触发 | 是"软停止"，不是强杀。物理动作不能撤回 |
| **D2** | 变量是**流程级**的，在流程内共享 | 不是分支隔离。变量本身就是流程状态控制的一部分 |
| **D3** | `join` 时**不存在**同名变量冲突 | 冲突是流程设计错误，应当禁止，不是运行时合并 |
| **D4** | 分支**不设超时** | 不同设备执行时间差异极大（孵育 30 分钟），超时会误判失败 |

### 1.1 由 D1 推出的细节

```
分支 A 失败
  → stopFlag = true
  → 分支 B/C/D 在「下一个节点边界」检查 stopFlag → 不再进入新节点
  → 分支 B 正在等设备回包：不中断，等回包到达
  → 回包到达后检查 stopFlag → 不再推进下一个节点
  → 所有分支退出后，并行组标记为 FAILED
```

**关键**：已下发的命令**不撤回、不强杀**。设备侧是否真的停下来，由设备自己按安全边界处理。

### 1.2 由 D2 推出的事实

**变量共享已经是现状**，不需要新建机制：

```java
// GraphRunner:113
private Map<String, String> variables = new java.util.LinkedHashMap<>();
// GraphRunner:433-434
public GraphRunner withVariables(Map<String, String> vars) {
    this.variables = new java.util.LinkedHashMap<>(...);
}
```

整个 `GraphRunner` 实例共用一个 `variables`，所有节点读写同一份。所以 D2 不是"改成共享"，而是**保持共享 + 让它线程安全**。

### 1.3 由 D3 推出的检查

变量是流程级共享的，同一时刻两个分支写同一个 key 没有"合并"这回事，只有"谁后写谁赢"——那是静默错误。

所以要在**编译期**禁止：

```
同一并行组内，两个不同分支写同一个变量 key
  → 编译失败，报错指出：变量 X 被 分支1/节点A 和 分支2/节点B 同时写入
```

允许的模式：
- 分支内只写自己的 key
- 所有分支只读同一个 key（可以）
- join 之后的下游节点写（可以）

### 1.4 由 D4 推出的边界

**分支不设超时**。但"不设超时"不等于"永远不管"，需要两个替代机制：

| 机制 | 作用 | 数据来源 |
|---|---|---|
| 心跳 | 判断设备/侧车是否活着 | 已有（1 秒周期） |
| 进展监测 | 判断设备是否还在动 | 需新增（状态是否变化） |

两者都不能判"失败"，只能判"异常"，进而告警或转人工。

**⚠ 这里有一个必须解决的矛盾**（见 §6 R-01）：

D1 说"失败后等已发命令完成"，D4 说"不设超时"。如果设备卡死、永不回包，那个分支就永远退不出去，并行组永远不结束。

必须补一条：**停止时有"停止等待上限"**（不是执行超时，是"已经决定停止后，最多再等多久"）。超过则把该命令标 UNKNOWN 并强制退出。

## 2. 现状：为什么不是真并发

### 2.1 执行循环

```java
// GraphRunner:736-739
while (!ready.isEmpty() && !progress.aborted()) {
    String key = ready.poll();                    // ← 一次取一个
    int visit = visits.merge(key, 1, Integer::sum);
    if (done.contains(key) && !hasCycle) { ... }
    // ...执行这一个节点...
}
```

`ready` 是 `ArrayDeque<String>`。`SPLIT_PARALLEL` 执行完后，多条分支的目标节点被**依次** `add` 进同一个队列，然后循环一个一个 `poll`。

**所以"并行网关"在当前实现里只是"多条路都要走"，不是"同时走"。**

### 2.2 并发改造涉及的共享状态

| 字段 | 类型 | 线程安全 | 并发后的风险 |
|---|---|---|---|
| `variables`（113） | `Map<String,String>` = `LinkedHashMap` | **否** | 并发写丢更新 |
| `consumedValues`（142） | `Map<String,String>` = `LinkedHashMap` | **否** | 同上 |
| `eventCursors`（417） | `Map<String,Long>` = `LinkedHashMap` | **否** | 事件水位错乱 |
| `visits`（738 使用） | `Map<String,Integer>`，用 `merge` | **否** | 计数丢失，循环轮次错 |
| `done` | `Set<String>` | **否** | 分支 A 做过的节点让分支 B 跳过 |
| `progress.aborted()`（736） | 外部对象 | **待确认** | 若字段非 volatile，停止信号可能不被其他线程看见 |

**这 6 项是并发改造的主要工作量，不是图分析。**

### 2.3 `__awaitEvent` 的特殊性

`__awaitEvent` 是 `GraphRunner` 内置节点，不走 step 生命周期，所以不持设备锁。并发后多个分支同时进入 `__awaitEvent` 是常态，waiters 唯一键必须能区分分支。

## 3. 目标模型

### 3.1 并行组的定义

```
SPLIT_PARALLEL（分叉点）
   ├── 分支 1（出边 1 及其可达子图）
   ├── 分支 2（出边 2 及其可达子图）
   └── 分支 3（出边 3 及其可达子图）
JOIN_PARALLEL（汇合点）
```

一个 `ParallelGroup` = `{ splitKey, joinKey, branches[] }`。

嵌套并行网关：内层组作为外层某个分支的子图，递归处理。

### 3.2 执行流程

```
执行到 splitKey：
  1. 创建 stopFlag（AtomicBoolean，本组共享）
  2. 为每条分支提交一个任务到线程池
  3. 等待所有分支结束（allOf）
  4. 聚合：任一失败 → 整组 FAILED；全部停 → 整组 PAUSED；否则 SUCCESS
  5. 组结束后，继续执行 joinKey 之后

单个分支内：
  while (子图未走完) {
      if (stopFlag.get()) break;          // 节点边界检查
      执行当前节点
      if (失败) { stopFlag.set(true); break; }
      推进到下一个节点
  }
```

### 3.3 三个隔离边界

| 对象 | 是否跨分支共享 | 说明 |
|---|---|---|
| **变量**（`variables`） | **共享**（D2） | 流程级状态 |
| `done` 集合 | **隔离** | 否则分支 A 做过的节点会让分支 B 跳过 |
| `visits` 计数 | **隔离** | 循环轮次按分支独立 |

**注意**：`done` 和 `visits` 隔离，变量共享——这两者不冲突，因为它们表达不同东西：`done` 是"本分支走到哪了"，变量是"流程整体状态"。

## 4. 八个改造点

| # | 改造 | 具体 | 工作量 |
|---|---|---|---|
| **1** | 并行组识别 | 编译期找 `SPLIT_PARALLEL` → 配对 `JOIN_PARALLEL`，切出分支子图 | ~150 行 |
| **2** | 执行模型 | `GraphRunner` 主循环改为"组内提交 + 汇合等待" | ~400 行 |
| **3** | 共享容器线程安全 | 6 个字段换 `ConcurrentHashMap` / `ConcurrentHashMap.newKeySet()`；`progress.aborted()` 确认可见性 | ~80 行 |
| **4** | `done` / `visits` 按分支隔离 | 分支任务持有自己的 Set / Map | ~80 行 |
| **5** | `DeviceLock` 重入语义 | 现在"同 run 算重入"，改为"同 run **同分支** 才算" | ~60 行 |
| **6** | waiter 加 branch 维度 | 唯一键 `(run, node, loop)` → `(run, branch, node, loop)` | ~60 行（含迁移） |
| **7** | 停止/暂停聚合 | `stopFlag` + 边界检查 + 全部退出后聚合状态 | ~100 行 |
| **8** | 全局并发上限 | 组内分支数 × 并行批次数 必须限流，否则执行体爆炸 | ~60 行 |

**合计约 990 行**（不含测试）。测试另需约 300 行。

### 4.1 改造点 5 的细节（最容易漏）

现在 `DeviceLock` 的注释写的是：

> `device_state.current_run_id` 只有 run 粒度，允许同 run 重入

并发后，同一 run 的两个分支会**同时**申请同一台设备。按现有语义，第二个分支会被判为"重入"直接放行 —— **两个分支同时用一台设备**。

必须改：持有者标识从 `runId` 改为 `(runId, branchId)` 或独立的 `ownerToken`。同 run 不同分支 = 不同持有者，要排队。

### 4.2 改造点 8 的细节

```
并行度 = 批次数 × 每批分支数
例：4 批 × 4 分支 = 16 个执行体

机械臂实测 9.33 秒/次，2 个 run 已到容量边缘
⇒ 16 个执行体全在等锁，端到端时长不会变好
```

所以必须设**全局信号量**，上限按设备数计算，而不是按批次数×分支数。

**否则改完后只是把"排队"从流程层挪到了锁层，还多付了线程和锁开销。**

## 5. 对前序文档的冲击

| 文档 | 原结论 | 需要改成 |
|---|---|---|
| 表设计 §2.2 | waiter 唯一键 `(tenant, run, node, loop)` | **加 `branch_id`** |
| 表设计 §1.1.1 | `operation_key` 含 `b{branch}` | **已够，不用改** |
| 设计基线 §4.3 | 事件归属三层（commandId / 设备占用者 / 独占） | **改为两层**：命令关联型（commandId）/ 系统型（不归属） |
| 设计基线 §4.5 | 暂停在节点边界生效 | **改为"全体停止发指令 + 已发等完成 + 聚合"** |
| 跨类锁 §3.2 | 同 run 重入 | **改为同 run 同分支才算重入** |
| 入口统一 | 无影响 | — |

### 5.1 事件归属的两层简化

原三层设计里"设备占用者"这一层已经证明在生产路径上取不到值（`__awaitEvent` 等待期间设备锁已释放）。而"命令关联型事件"只要设备回显 `commandId` 就能归属，不需要额外机制。

所以最终只剩：

```
事件带 commandId  → 归属到该命令所属的 run/node/branch
事件无 commandId  → 系统型（心跳/告警/人工），不归属任何 run
无法匹配          → UNATTRIBUTED + 告警，不推进
```

`process_id` / `funcName` / 弱匹配 / 设备占用者归属，全部删除。

## 6. 风险与待评审

| ID | 风险 | 说明 |
|---|---|---|
| **R-01** | **无超时 + 等已发命令完成 = 可能无限等待** | D1 与 D4 的冲突。必须补"停止等待上限"，超过则标 UNKNOWN 强退 |
| R-02 | 变量共享的并发写 | 虽然编译期禁止同名冲突，但运行时仍需 `ConcurrentHashMap`；且"读-改-写"序列仍需原子 |
| R-03 | `done` 隔离后，join 之后的状态判定 | 并行组结束时 `done` 怎么合并到主集合 |
| R-04 | 嵌套并行组的递归 | 内层组失败如何传播到外层 |
| R-05 | 线程池饥饿 | 组内 4 分支 × 4 批次占满池，其他流程排队 |
| R-06 | 暂停在组内的一致性 | 用户点暂停时，4 个分支各自在哪个边界停 |
| R-07 | 设备锁重入语义变更的影响面 | 是否有依赖"同 run 重入"的现有路径 |

### 6.1 请评审者回答

1. **R-01 怎么解**：停止等待上限设多少？按方法配还是按设备配？超时后标 UNKNOWN 是否会让现场无法收尾？
2. **D2 变量共享**：编译期"禁止同组内两分支写同一 key"是否过严？有没有合法的写法（如计数器）需要放开？
3. **R-03**：并行组结束后，`done` 是并入主集合还是保持分支独立、只标记 join 已到达？
4. **R-05/R-04**：全局并发上限按设备数算，公式是什么？嵌套组怎么算？
5. **R-07**：`DeviceLock` 重入语义从 `runId` 改成 `(runId, branchId)`，会不会破坏现有的"同 run 跨 step 重入"场景？（位置锁是跨 step 的）
6. **改造点 2**：`GraphRunner` 主循环重构，有没有更小侵入的做法（比如保留单线程、只把"分支"提升为并行任务）？

## 7. 验收

| ID | 场景 | 期望 |
|---|---|---|
| E-01 | 4 分支并行网关 | 4 条链同时开始执行（日志时间戳重叠） |
| E-02 | 分支 A 失败 | 分支 B/C/D 不再发新指令；已发出的等回包；整组 FAILED |
| E-03 | 分支 A 失败时 B 正在等设备回包 | B 不中断，回包到达后不推进下一节点 |
| E-04 | 4 分支写不同变量 | 全部成功，变量表包含 4 个 key |
| E-05 | 两个分支写同一变量 | **编译期**报错，指出冲突位置 |
| E-06 | 4 分支同时抢同一台设备 | 串行排队，不出现两个分支同时持有 |
| E-07 | 4 分支同时 `__awaitEvent` 等同一设备 | waiter 按 branch 区分，不撞唯一键 |
| E-08 | 一个分支设备卡死（心跳正常、无回包） | 停止等待上限到达后标 UNKNOWN，整组可退出 |
| E-09 | 用户暂停 | 4 分支各自在节点边界停；全部停止后才报"已暂停" |
| E-10 | 嵌套并行网关 | 内层失败传播到外层 |
| E-11 | 16 个执行体（4 批 × 4 分支） | 全局信号量生效，不出现线程池饥饿 |
| E-12 | 并行组结束后继续串行 | `done` 状态正确，不重复执行 |
