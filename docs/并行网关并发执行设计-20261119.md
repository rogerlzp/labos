# 并行网关并发执行设计

- 日期：2026-11-19
- 性质：设计文档，**未实施**
- 前置：单实例部署；不含多实例 fencing
- 目的：把「并行网关」从**逻辑并行（顺序执行）**改为**真并发（同时执行）**

---

## 0. 一页纸

| 项 | 内容 |
|---|---|
| 现状 | `GraphRunner:736` 单线程 `ready.poll()`，并行网关只把多分支**依次压入同一队列**，逐个执行 |
| 目标 | `SPLIT_PARALLEL` 的多个分支**同时执行**，`JOIN_PARALLEL` 汇合 |
| 核心模型 | 并行组（ParallelGroup）：split 到 join 之间的子图，每条出边一个分支 |
| 四条执行语义 | 失败即停发（已发等完成）/ 变量流程级共享 / 禁止同名冲突 / 分支无超时 |
| 改造点 | **10 项**（第 1+2、4 已合并，第 5 项核实为「已具备」），约 800 行 |
| 最大风险 | ①「无超时 + 失败等已发命令完成」可能无限等待；②「命令返回 ≠ 设备空闲」；③ **事实源缺失按 fail-closed 处理会重演 2026-11-15 的全平台停摆** |
| 对前序文档的影响 | 4 处结论要改（waiters 唯一键、事件分层、暂停语义、锁重入） |

## 1. 四条执行语义（已定）

| ID | 决策 | 具体含义 |
|---|---|---|
| **D1** | 一个分支失败 → **所有分支立即停止发新指令**；已发出的指令**等设备完成后**再触发 | 是"软停止"，不是强杀。物理动作不能撤回 |
| **D2** | 变量是**流程级**的，在流程内共享 | 不是分支隔离。变量本身就是流程状态控制的一部分 |
| **D3** | `join` 时**不存在**同名变量冲突 | 冲突是流程设计错误，应当禁止，不是运行时合并 |
| **D4** | 分支**不设超时** | 不同设备执行时间差异极大（孵育 30 分钟），超时会误判失败 |

### 1.1 由 D1 推出的细节

```
分支 A 失败
  → stopFlag = true
  → 分支 B/C/D 在「下一个节点边界」检查 stopFlag → 不再进入新节点
  → 分支 B 正在等设备回包：不中断，等回包到达
  → 回包到达后检查 stopFlag → 不再推进下一个节点
  → 所有分支退出后，并行组标记为 FAILED
```

**关键**：已下发的命令**不撤回、不强杀**。设备侧是否真的停下来，由设备自己按安全边界处理。

### 1.2 由 D2 推出的事实

**变量共享已经是现状**，不需要新建机制：

```java
// GraphRunner:113
private Map<String, String> variables = new java.util.LinkedHashMap<>();
// GraphRunner:433-434
public GraphRunner withVariables(Map<String, String> vars) {
    this.variables = new java.util.LinkedHashMap<>(...);
}
```

整个 `GraphRunner` 实例共用一个 `variables`，所有节点读写同一份。所以 D2 不是"改成共享"，而是**保持共享 + 让它线程安全**。

### 1.3 由 D3 推出的检查

变量是流程级共享的，同一时刻两个分支写同一个 key 没有"合并"这回事，只有"谁后写谁赢"——那是静默错误。

所以要在**编译期**禁止：

```
同一并行组内，两个不同分支写同一个变量 key
  → 编译失败，报错指出：变量 X 被 分支1/节点A 和 分支2/节点B 同时写入
```

允许的模式：
- 分支内只写自己的 key
- 所有分支只读同一个 key（可以）
- join 之后的下游节点写（可以）

### 1.4 由 D4 推出的边界

**分支不设超时**。但"不设超时"不等于"永远不管"，需要两个替代机制：

| 机制 | 作用 | 数据来源 |
|---|---|---|
| 心跳 | 判断设备/侧车是否活着 | 已有（1 秒周期） |
| 进展监测 | 判断设备是否还在动 | 需新增（状态是否变化） |

两者都不能判"失败"，只能判"异常"，进而告警或转人工。

**⚠ 这里有一个必须解决的矛盾**（见 §6 R-01）：

D1 说"失败后等已发命令完成"，D4 说"不设超时"。如果设备卡死、永不回包，那个分支就永远退不出去，并行组永远不结束。

必须补一条：**停止时有"停止等待上限"**（不是执行超时，是"已经决定停止后，最多再等多久"）。超过则把该命令标 UNKNOWN 并强制退出。

## 2. 现状：为什么不是真并发

### 2.1 执行循环

```java
// GraphRunner:736-739
while (!ready.isEmpty() && !progress.aborted()) {
    String key = ready.poll();                    // ← 一次取一个
    int visit = visits.merge(key, 1, Integer::sum);
    if (done.contains(key) && !hasCycle) { ... }
    // ...执行这一个节点...
}
```

`ready` 是 `ArrayDeque<String>`。`SPLIT_PARALLEL` 执行完后，多条分支的目标节点被**依次** `add` 进同一个队列，然后循环一个一个 `poll`。

**所以"并行网关"在当前实现里只是"多条路都要走"，不是"同时走"。**

### 2.2 并发改造涉及的共享状态

| 字段 | 类型 | 线程安全 | 并发后的风险 |
|---|---|---|---|
| `variables`（113） | `Map<String,String>` = `LinkedHashMap` | **否** | 并发写丢更新 |
| `consumedValues`（142） | `Map<String,String>` = `LinkedHashMap` | **否** | 同上 |
| `eventCursors`（417） | `Map<String,Long>` = `LinkedHashMap` | **否** | 事件水位错乱 |
| `visits`（738 使用） | `Map<String,Integer>`，用 `merge` | **否** | 计数丢失，循环轮次错 |
| `done` | `Set<String>` | **否** | 分支 A 做过的节点让分支 B 跳过 |
| `progress.aborted()`（736） | 外部对象 | **待确认** | 若字段非 volatile，停止信号可能不被其他线程看见 |

**这 6 项是并发改造的主要工作量，不是图分析。**

### 2.3 `__awaitEvent` 的特殊性

`__awaitEvent` 是 `GraphRunner` 内置节点，不走 step 生命周期，所以不持设备锁。并发后多个分支同时进入 `__awaitEvent` 是常态，waiters 唯一键必须能区分分支。

## 3. 目标模型

### 3.1 并行组的定义

```
SPLIT_PARALLEL（分叉点）
   ├── 分支 1（出边 1 及其可达子图）
   ├── 分支 2（出边 2 及其可达子图）
   └── 分支 3（出边 3 及其可达子图）
JOIN_PARALLEL（汇合点）
```

一个 `ParallelGroup` = `{ splitKey, joinKey, branches[] }`。

嵌套并行网关：内层组作为外层某个分支的子图，递归处理。

### 3.2 执行流程

```
执行到 splitKey：
  1. 创建 stopFlag（AtomicBoolean，本组共享）
  2. 为每条分支提交一个任务到线程池
  3. 等待所有分支结束（allOf）
  4. 聚合：任一失败 → 整组 FAILED；全部停 → 整组 PAUSED；否则 SUCCESS
  5. 组结束后，继续执行 joinKey 之后

单个分支内：
  while (子图未走完) {
      if (stopFlag.get()) break;          // 节点边界检查
      执行当前节点
      if (失败) { stopFlag.set(true); break; }
      推进到下一个节点
  }
```

### 3.3 三个隔离边界

| 对象 | 是否跨分支共享 | 说明 |
|---|---|---|
| **变量**（`variables`） | **共享**（D2） | 流程级状态 |
| `done` 集合 | **隔离** | 否则分支 A 做过的节点会让分支 B 跳过 |
| `visits` 计数 | **隔离** | 循环轮次按分支独立 |

**注意**：`done` 和 `visits` 隔离，变量共享——这两者不冲突，因为它们表达不同东西：`done` 是"本分支走到哪了"，变量是"流程整体状态"。

### 4.1 改造点 5 的核实结果：不需要改

**先说结论：`DeviceLock` 的重入语义不用改。**（初稿认为要改，核实后推翻）

代码依据（`DeviceLock:81-93`）：

```java
private ReentrantLock localLock(long resourceId, long runId) {
    long h = tenantId * 31L + resourceId * 17L + runId;
    return LOCAL_LOCKS[(int) ((h ^ (h >>> 32)) & Integer.MAX_VALUE) % LOCAL_STRIPES];
}
private int holdCount(LocalKey key) {
    return LOCAL_HOLDS.get().getOrDefault(key, 0);   // ← ThreadLocal
}
```

`holdCount` 是 **ThreadLocal**，所以：

| 情况 | 实际行为 |
|---|---|
| 同 run **同线程**重入 | `holdCount > 0` → 放行 |
| 同 run **不同线程**（并行分支） | ThreadLocal 为空 → `local.tryLock()` 抢不到 → 等待（`acquireWithWait`，60 秒）或失败 |
| 不同 run | 数据库层 `tryAcquireDevice` 拦住 |

**并行分支已经被正确互斥。** 原计划"把 `runId` 改成 `(runId, branchId)`"是多余的，不做。

### 4.2 真正的缺口：命令返回 ≠ 设备空闲

`onStepDone` 在**收到最终回包**时释放锁（`WorkflowService:3170-3178`）：

```java
// 已收到最终回包；释放设备和落结果属于 FINALIZING，不再计成设备执行。
markDeviceIdle(rid, ok ? null : errorCode);
new DeviceLock(db, tenantId).release(resNodeId, runIdOf());
```

但提取线是"**受理即返回 + 事件通知完成**"：

```python
n_pick = b.task("取磁套", protocol="PickTipComb", ...)   # 命令返回 = 已受理
n_wait = b.task("等交互", protocol="__awaitEvent", ...)  # 真正的完成信号
```

于是：

```
T0  run A 下发 PickTipComb
T1  设备回"已受理"
T2  onStepDone → 释放设备锁、markDeviceIdle
T3  设备实际还在搬运
T4  run B 抢到锁（A 已释放）
T5  run B 下发 PickTipComb → 设备正在忙
```

T5 的结果取决于设备实现：

| 设备行为 | 结果 |
|---|---|
| 返回 busy | 安全，B 收到错误 |
| 排队 | 可能乱序执行 |
| 覆盖当前任务 | **事故** |

**现有防护的真实覆盖面**（比"三种设备"更准确）：

| 防护 | 覆盖 | 性质 |
|---|---|---|
| `TurntableGuard`（L1） | 转盘类 | 读 `turntable` fact；**事实缺失即 SKIP（放行）** |
| `StirrerDispenserGuard`（L4） | 分液方法的配对搅拌单元 | **未配对即 SKIP**（2026-11-15 事故后改的） |
| `LhcRunnerTransport` `eBusy(3)` | Biotek LHC | 设备侧忙判定 |
| `Gen5OleTransport` `ReadInProgress` | Gen5 读板机 | 同上 |

**但它们都不是通用的"设备物理空闲"检查**：

- 前三项各自只覆盖**特定方法或特定设备**；
- 且**事实源缺失时一律 SKIP（放行）**，不是阻断；
- 提取仪有 L1 转盘与 L4 搅拌，但都**不检查"命令返回后设备是否还在动"**。

所以 §4.2 的场景（受理即返回、锁已释放、设备仍在动）**在现有防护下确实无覆盖**。

**这是并行化后最现实的串行化缺口**：不是"两个 run 同时抢锁"，而是"锁已释放，但设备还没空"。

### 4.3 设备物理忙准入（第四方案）

#### 4.3.1 失败方向必须先定：事实源缺失 ≠ 采集到不确定

**这不是设计偏好，是有事故记录的。**

`StirrerDispenserGuard:88-99` 原文：

> **改之前**：配对缺失一律 `EC-STATE-UNKNOWN` 拒绝。而这个复核是**对每一条设备命令**调用的，且 `stirrer_dispenser_pair` 在客户现场落地前一直是 **0 行** ⇒ **平台里每一台设备的每一条命令都被拒**（实测：提取仪的 `PickTipComb` 直接转人工）。⇒ 这不是"守门更严"，是**整台平台发不出命令**。

所以规则必须是：

| 情况 | 处置 | 审计 |
|---|---|---|
| **事实源缺失**（没传感器 / 没配 `physical_state` / 表里 0 行） | **fail-open**：跳过检查，允许派发 | 落 `SKIP` + 告警 + 列入"不可并行清单" |
| **采集到不确定**（传感器明确说不确定 / 状态过期） | **fail-closed**：阻断 | 落 `REJECT` + 原因 |

**"没有数据"和"数据说不知道"是两件事。** 前者表示"这项检查不适用"，后者表示"确实无法判断"。

对本文档而言：**`physical_state` 是新加列，存量设备初值必然全是"缺失"**——如果按 fail-closed 处理，上线当天全场不可派发，重演 2026-11-15。

#### 4.3.2 方案对比

| 方案 | 做法 | 问题 |
|---|---|---|
| A 锁持有到事件到达 | `onStepDone` 不释放，等完成事件 | **要把锁释放点从 `onStepDone` 移到事件到达，跨 `WorkflowService` ↔ `GraphRunner` 两层**——正是最初否掉的"持锁等待"结构 |
| B 查 `physical_state` | 派发前检查状态 | 依赖设备改造；且缺事实源时会踩 fail-closed |
| C 靠设备返回 busy | 不做事 | 把风险推给设备 |
| **D 中控侧物理占用标记** | 见下 | **推荐** |

#### 4.3.3 第四方案：中控侧维护"设备物理占用"

```
设备锁（step 粒度，照旧，不改释放点）
  ＋
device_physical_hold（中控维护）
    建立：命令下发且设备回「已受理」时
    清除：收到完成事件 / 完成回包时
    作用：持有期间该设备不进可派发池
```

**为什么这个方案更好**：

| 对比项 | 方案 A | 方案 D |
|---|---|---|
| 改锁释放点 | 要跨两层改 | **不改** |
| 需要设备配合 | 需要（要能报完成） | **不需要** |
| 并行收益 | 该设备降级独占 | **保留**（只对"受理即返回"的设备生效） |
| 正确性来源 | 锁 | 中控自己的标记，**不依赖设备诚实** |

#### 4.3.4 分档判据换成"会不会受理即返回"

原判据是"有没有 `physical_state`"，但那是**设备改造项**，在本轮范围外。改用协议属性：

| 设备类型 | 判据 | 处置 |
|---|---|---|
| **同步阻塞**：命令返回 = 已完成 | 不会受理即返回 | 不建标记，锁释放即视为空闲 |
| **受理即返回 + 事件通知完成** | 会，且有完成信号 | **建物理占用标记**，事件到达才清除 |
| **受理即返回 + 无完成信号** | 会，且无法确认完成 | 独占串行 + 人工确认 |
| **不确定** | 无法判断 | 按"会受理即返回"处理（保守） |

第四类很重要：**判据不确定时按最保守处理**，但不能因此拒绝派发（那是 fail-closed 的坑）。

### 4.4 并发上限：两条独立限制，不能混为一条

```
线程池上限   = 执行体数限制（防饥饿）
资源信号量   = 同时占用的设备数限制（防把排队从流程层挪到锁层）
嵌套并行组  不额外计数（内外层抢同一批设备，相乘会自我阻塞）
```

**并行度公式**（按瓶颈资源算，不按执行体数算）：

```
并行度 = min over r ( floor(capacity_r / demand_r) )
例：机械臂 capacity=2（实测 2 run 已到边缘），demand=1 ⇒ 机械臂限制并行度=2
```

**用词纠正**：「4 批 × 4 分支 = 16」是**执行体数**，不是并发度。并发度由瓶颈资源决定，可能只有 2。

**否则改完后只是把"排队"从流程层挪到了锁层，还多付了线程和锁开销。**

## 5. 对前序文档的冲击

| 文档 | 原结论 | 需要改成 |
|---|---|---|
| 表设计 §2.2 | waiter 唯一键 `(tenant, run, node, loop)` | **加 `branch_id`** |
| 表设计 §1.1.1 | `operation_key` 含 `b{branch}` | **已够，不用改** |
| 设计基线 §4.3 | 事件归属三层（commandId / 设备占用者 / 独占） | **改为两层**：命令关联型（commandId）/ 系统型（不归属） |
| 设计基线 §4.5 | 暂停在节点边界生效 | **改为"全体停止发指令 + 已发等完成 + 聚合"** |
| 跨类锁 §3.2 | 同 run 重入 | **改为同 run 同分支才算重入** |
| 入口统一 | 无影响 | — |

### 5.1 事件归属的两层简化

原三层设计里"设备占用者"这一层已经证明在生产路径上取不到值（`__awaitEvent` 等待期间设备锁已释放）。而"命令关联型事件"只要设备回显 `commandId` 就能归属，不需要额外机制。

所以最终只剩：

```
事件带 commandId  → 归属到该命令所属的 run/node/branch
事件无 commandId  → 系统型（心跳/告警/人工），不归属任何 run
无法匹配          → UNATTRIBUTED + 告警，不推进
```

`process_id` / `funcName` / 弱匹配 / 设备占用者归属，全部删除。

| ID | 风险 | 说明 |
|---|---|---|
| **R-01** | **无超时 + 等已发命令完成 = 可能无限等待** | D1 与 D4 的冲突。必须补"停止等待上限"，超过则标 UNKNOWN 强退 |
| R-02 | 变量共享的并发写 | 虽然编译期禁止同名冲突，但运行时仍需 `ConcurrentHashMap`；且"读-改-写"序列仍需原子 |
| R-03 | `done` 隔离后，join 之后的状态判定 | 并行组结束时 `done` 怎么合并到主集合 |
| R-04 | 嵌套并行组的递归 | 内层组失败如何传播到外层 |
| R-05 | 线程池饥饿 | 组内 4 分支 × 4 批次占满池，其他流程排队 |
| R-06 | 暂停在组内的一致性 | 用户点暂停时，4 个分支各自在哪个边界停 |
| R-07 | ~~设备锁重入语义变更~~ | **不适用**：已核实 ThreadLocal 判定正确，无需改（§4.1） |
| **R-08** | **命令返回 ≠ 设备空闲** | 锁按"收到最终回包"释放，但"受理即返回"的设备此时可能仍在动。现有互锁只覆盖转盘/Biotek/Gen5，其余设备无保护（§4.2） |
| **R-09** | 物理忙若改用"锁持有到事件"会降低并行度 | **已用第四方案规避**（§4.3.3）：不改锁释放点，另加中控侧标记 |
| **R-10** | **R-01 与 R-08 耦合** | 「停止等待上限到达」时设备可能仍在动 ⇒ 强退等于把一台还在动的设备放回池子。必须：超限后设备进 `QUARANTINED`，**不得自动释放、不得重新准入** |
| **R-11** | **设备锁的正确性依赖单实例** | `current_run_id` 是 run 粒度，DB 层拦不住同 run 的两个分支；真正互斥的是 JVM 分片锁。**多实例部署时这条前提不成立**，必须显式声明 |

### 6.1 请评审者回答

1. **R-01 怎么解**：停止等待上限设多少？按方法配还是按设备配？超时后标 UNKNOWN 是否会让现场无法收尾？
2. **D2 变量共享**：编译期"禁止同组内两分支写同一 key"是否过严？有没有合法的写法（如计数器）需要放开？
3. **R-03**：并行组结束后，`done` 是并入主集合还是保持分支独立、只标记 join 已到达？
4. **R-05/R-04**：全局并发上限按设备数算，公式是什么？嵌套组怎么算？
5. **R-08**：设备物理忙怎么补——方案 A（锁持有到事件到达，该设备降级独占）还是 B（新增物理态检查）？按设备能力分档是否可行？
6. **改造点 2**：`GraphRunner` 主循环重构，有没有更小侵入的做法（比如保留单线程、只把"分支"提升为并行任务）？

## 7. 验收

| ID | 场景 | 期望 |
|---|---|---|
| E-01 | 4 分支并行网关 | 4 条链同时开始执行（日志时间戳重叠） |
| E-02 | 分支 A 失败 | 分支 B/C/D 不再发新指令；已发出的等回包；整组 FAILED |
| E-03 | 分支 A 失败时 B 正在等设备回包 | B 不中断，回包到达后不推进下一节点 |
| E-04 | 4 分支写不同变量 | 全部成功，变量表包含 4 个 key |
| E-05 | 两个分支写同一变量 | **编译期**报错，指出冲突位置 |
| E-06 | 4 分支同时抢同一台设备 | 串行排队，不出现两个分支同时持有 |
| E-07 | 4 分支同时 `__awaitEvent` 等同一设备 | waiter 按 branch 区分，不撞唯一键 |
| E-08 | 一个分支设备卡死（心跳正常、无回包） | 停止等待上限到达后标 UNKNOWN，整组可退出 |
| E-09 | 用户暂停 | 4 分支各自在节点边界停；全部停止后才报"已暂停" |
| E-10 | 嵌套并行网关 | 内层失败传播到外层 |
| E-11 | 16 个执行体（4 批 × 4 分支） | 全局信号量生效，不出现线程池饥饿 |
| E-12 | 并行组结束后继续串行 | `done` 状态正确，不重复执行 |
| **E-13** | 设备"受理即返回"、命令结束后仍在执行 | 另一个 run **不能**下发（物理忙准入生效，或锁持有到事件到达） |
| **E-14** | 设备返回 busy | 中控不重试、不自动排队；命令落失败并告警 |
| E-15 | 同 run 两分支抢同一设备 | ThreadLocal 判定生效，第二个分支等待或失败，不出现同时持有 |
| **E-16** | 两个分支的子图有交集（同节点被覆盖） | **编译期报错**——否则 `run_node` 撞唯一键 `(run_id, node_key, attempt, loop_index)` |
| **E-17** | 模拟器开启"受理即返回"开关 | 锁释放后设备仍在动（20 秒默认值下的阻塞模型测不出此场景） |
| **E-18** | 设备无 `physical_state` / 事实源缺失 | **不阻断**：落 SKIP + 告警 + 列入不可并行清单；只有**显式** `unknown` 才阻断 |
| **E-19** | 停止等待上限到达、设备仍在动 | 设备进 `QUARANTINED`，不释放占用、不重新准入 |

## 8. 边界

- 本文档是设计，**代码 0 行、测试 0 次**。
- 不含多实例 fencing。
- 不含设备协议改造（沿用 commandId 回显规范）。
- 四条执行语义（D1–D4）由业务方确定，本文档按此设计，不再讨论是否要这样做。

**两条必须显式声明的前提**：

1. **设备锁的正确性依赖单实例。** `device_state.current_run_id` 是 run 粒度，数据库层拦不住"同 run 的两个分支"；真正互斥的是 JVM 分片锁（`LOCAL_LOCKS` + `LOCAL_HOLDS`）。**多实例部署时这条前提不成立**，一个 run 的两个分支落在不同实例上会同时持有同一设备。见 R-11。
2. **模拟器当前是"阻塞 N 秒后返回 ok"的同步模型**（`DeviceCore:86-92` 记录了画像 step timing 与厂商方法名对不上、落回 20 秒默认值的实测）。**E-13 / E-17 在该模型下测不出来**，必须先给模拟器加"受理即返回 + 延迟完成 + 完成后发事件"的开关（改造点 10），否则测试会假绿。
