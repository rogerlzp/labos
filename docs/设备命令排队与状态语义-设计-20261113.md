# 设备命令排队与状态语义设计

> 日期：2026-11-13
>
> 问题：并行分支同时调用同一台设备时，第二条命令应该算“已发出、等待执行”，还是“尚未发出、等待设备”？从发出到设备收到、执行、返回，状态应该怎样划分？
>
> 结论：**当前协议下，第二条命令应在中控排队，尚未下发；不能显示成设备已接收或设备内排队。**

---

## 一、先给结论

两个并行分支调用同一台设备时，推荐时序是：

```text
分支 A：等待设备 → 获得设备锁 → 派发命令 A → 设备执行 A → 收到 A 最终回包 → 释放设备锁
分支 B：等待设备（尚未下发）──────────────────────→ 获得设备锁 → 派发命令 B → ...
```

在 A 执行期间：

- 设备状态是 `online=true、status=running`；
- 设备当前方法和当前命令只指向 A；
- B 的节点已经可被调度，但执行阶段是 **等待资源**；
- B **还没有写入 `DISPATCH_STARTED`，更没有发到设备 TCP 连接**；
- B 在界面上显示“等待设备空闲，尚未下发”，而不是“设备排队中”。

只有未来设备协议明确支持“接收确认”和“设备内队列”，才可以把 B 显示为：

```text
已下发 → 设备已接收 → 设备内排队 → 开始执行 → 完成
```

当前同步请求—响应协议没有这个能力，所以不能提前这样表达。

### 为什么不能把“已经发给模拟器，等它慢慢执行”当默认方案

这样看似省事，实际会把排队、取消、超时、重试、恢复和设备真实状态都变模糊：

1. TCP 写入成功不代表设备已接收，更不代表设备接受执行；
2. 同一连接里后一帧等待前一帧，只是模拟器实现细节，不是可依赖的设备队列契约；
3. 多条连接同时写入会造成并发动作，必须由设备级互斥拒绝；
4. 如果设备默默排队，调用方无法区分“没收到”“已排队”“已开始”和“执行完但回包丢失”；
5. 等待期间如何取消、如何计算超时、重启后队列是否仍在，都没有协议答案；
6. 正常调度会绕过内核设备锁，锁队列和设备队列形成两套互相不知道的顺序。

因此：**正常路径在中控排队；设备忙拒绝只作最后防线。**

## 二、必须拆成三套状态

“节点正在运行”“命令已经发出”“设备正在执行”不是同一件事。混用一个 `running` 会产生误判。

| 状态平面 | 回答的问题 | 典型状态 | 主要记录位置 |
|---|---|---|---|
| **节点／调度状态** | 流程走到哪一步，是否具备执行条件 | 未就绪、等待资源、执行中、完成、转人工 | `run_node` |
| **命令／传输状态** | 是否登记、是否开始派发、是否收到最终回包、物理结果是否确定 | 未派发、派发中、已确认、失败、结果未知 | `command_ledger`、`run_command` |
| **设备／物理状态** | 设备是否在线、此刻是否空闲、正在执行哪条命令 | 离线、空闲、运行中、故障 | `device_state`、设备 `GetStatus` |

### 同一个时刻的合理组合

以 A 正在设备上执行、B 等待同一设备为例：

| 对象 | 状态 |
|---|---|
| 节点 A | `RUNNING + DISPATCHING/WAITING_FINAL` |
| 命令 A | `DISPATCH_STARTED`，已收到最终回包后变 `ACKED` |
| 设备 | `running`，`current_method=A.method`，`current_command_id=A.commandId` |
| 节点 B | `RUNNING + WAITING_RESOURCE`，界面显示“等待设备” |
| 命令 B | **尚未创建派发账本，未下发** |
| 设备上的 B | 不存在；设备不应显示 B 为当前命令或设备内排队 |

这里节点 B 使用 `RUNNING` 表示“执行 worker 已接管这个已就绪节点”，使用 `phase=WAITING_RESOURCE` 表示并没有在动设备。若不想新增节点阶段字段，也可以暂时保留现有 `status`，但界面必须另给出等待原因，不能只显示“运行中”。

## 三、当前实现到底能证明什么

### 3.1 设备锁发生在真正下发之前

当前 `WorkflowService.onStepStart` 的顺序是：

```text
节点汇总行标 running
→ DeviceLock.acquireWithWait
→ 记录 sentAtByStep
→ markDeviceBusy
→ DriverStepExecutor.executeWithPlan
→ executeCommand
→ CommandLedger.begin(DISPATCH_STARTED)
→ driver.execute
```

所以同设备两条正常流程命令不会仅因为图上有并行分叉，就必须同时发到设备。

但当前界面只能看到 `running`，看不到“正在等锁”和“已经派发”的区别。

### 3.2 `DISPATCH_STARTED` 不是设备接收确认

`CommandLedger.begin` 在 `driver.execute` 之前落库，目的是覆盖崩溃窗口：

```text
先记账 → 再下发 → 收到回包后 ACKED / FAILED
```

这个设计是正确的安全方向，但名称容易被过度解读：

- 它证明：**中控已经决定派发，并建立防重账本**；
- 它不证明：TCP 已发送完成；
- 它不证明：驱动已收到；
- 它不证明：设备已经开始物理动作。

在当前协议没有独立接收确认帧的情况下，界面应写成：

> **派发中，物理结果尚未确认**

而不是“设备已接收”。

### 3.3 `sent_at` 也不是设备收到时间

`sentAtByStep` 在拿到设备锁之后、调用驱动之前记录。它比“等待锁之前记录”准确，但仍只是 **中控派发开始时间**。

建议后续将内部命名逐步改为 `dispatch_started_at`，避免把它解释成设备接收时间。只有设备回包中带接收时间，才有 `device_received_at`。

### 3.4 当前同步回包只给出最终结果

当前模拟器动作完成后返回 `method_status=2`，明确拒绝返回 `method_status=3`。`GetStatus` 是另一条独立查询，不是原命令的接收确认。

所以当前能可靠确认的是：

| 事实 | 依据 |
|---|---|
| 设备正在执行哪条动作 | `GetStatus.data.device_state.current_method/current_command_id` |
| 动作成功完成 | 原命令最终成功回包 |
| 动作被明确拒绝 | 原命令失败回包及错误码 |
| 设备可达 | 心跳／查询成功 |
| 命令是否曾到达但在回包前失联 | **不能确定，必须按结果未知处理** |

## 四、实测暴露出的两个问题

### 4.1 模拟器原来会把跨连接并发动作都执行

修复前，固定动作延迟 2500 ms，两个 TCP 连接同时发 `Home` 或 `RunProgram`：

- 两条都在约 2500 ms 后返回成功；
- 同一连接连续发两条才表现为串行排队；
- 说明原来只有“连接内串行”，没有“整台设备互斥”。

现已增加设备级动作占用：

- 第一条动作正常执行；
- 第二条跨连接动作立即返回 `method_status=3` 和 `EC-06-0006`；
- `GetStatus` 不等待动作结束，可立即返回 `running`、当前方法、当前命令 ID；
- 完成后恢复 `idle`，后续动作可继续执行。

常驻机器人实测：第一条 `Home` 约 3403 ms 成功；执行中查询约 10 ms 返回；第二条 `Home` 约 3 ms 被拒绝。

**这个拒绝行为是合理的最后防线，但不是正常排队体验。** 正常流程应先由内核排队，避免频繁把可等待的资源竞争变成人工错误。

### 4.2 仅锁机械臂和门记录，不足以保护搬运全过程

并行流程回归中：

- `1001368`：两个并行分支分别使用 `200231`、`504829`，均完成；
- `1001369`：读码 → 搬运 → 离心 → 搬运 → 封膜，全部完成；
- `1001370`：新模拟器下并行分支仍全部完成。

另一个并发场景中，运行 `1001371` 和 `1001372` 同时操作离心机：

```text
1001371 Transfer：离心机 OpenDoor
1001372 RunProgram：开始执行
1001372 RunProgram：因“门未关闭”返回 EC-06-0006，转人工
1001371 Transfer：随后 CloseDoor，自身继续完成
```

根因不是 ParallelGateway，也不是设备忙互斥误拒，而是搬运计划原来没有独占源／目标设备本身。门记录、通道和机械臂有锁，并不阻止另一条 run 同时向离心机发 `RunProgram`。

因此，**一次复合动作的资源锁范围必须覆盖整个物理安全区间**：

```text
申请源设备锁
→ 开源门
→ 申请目标设备锁
→ 开目标门
→ 搬运
→ 关目标门、源门
→ 最后释放源／目标设备锁
```

设备锁应在 `closeAccesses` 之后释放，而不是开门成功后或机械臂回包后立即释放。相反方向搬运继续使用等待图检测循环等待。

修复后已用两个真实并发 run 验证：

- `1001375` 和 `1001376` 同时启动，最终均为 `completed`；
- `1001375 RunProgram` 的实际命令区间为 `07:51:22.255911—07:51:28.534452`；
- `1001376 RunProgram` 的实际命令区间为 `07:51:54.008903—07:51:59.377639`；
- 两条离心命令均成功、无错误码，时间区间不重叠；第二条没有再插入第一次搬运的开门—搬动—关门安全区间；
- 回归结束后没有 `current_run_id` 非空的遗留设备锁。

这次验证证明的是设备互斥与搬运安全区间；`WAITING_RESOURCE` 等节点阶段字段仍属于后续可观测性改造，尚未上线。

## 五、推荐的状态模型

### 5.1 节点增加“执行阶段”，不要把所有语义塞进节点状态枚举

推荐新增可空字段：

```text
run_node.execution_phase
run_node.phase_since
run_node.blocked_by_run_id       可空；仅用于可观测性，不作为锁真源
run_node.blocked_reason          可空
run_node.queue_seq               可空；实现持久队列后使用
```

第一阶段推荐取值：

| `execution_phase` | 含义 | 是否已向设备派发 |
|---|---|---|
| `WAITING_RESOURCE` | 节点已就绪，正在等设备／门／位置／机械臂 | 否 |
| `DISPATCHING` | 已建立命令账本，正在调用驱动 | 可能已发出，尚无最终回包 |
| `WAITING_FINAL` | 可选；已有接收确认、等待最终结果时才使用 | 是，且设备已确认接收 |
| `RETRY_WAIT` | 本次尝试已结束，按策略等待重试 | 本次不再派发 |
| `FINALIZING` | 已收到最终回包，正在落结果、释放资源 | 是 |
| `null` | 未进入执行、已结束，或旧数据无阶段信息 | 不确定，要看终态 |

节点主状态继续使用现有 `PENDING / RUNNING / COMPLETED / MANUAL / ...`：

```text
PENDING + null                 = 图依赖未完成，尚未轮到
RUNNING + WAITING_RESOURCE     = 已轮到，但还没拿到设备，未下发
RUNNING + DISPATCHING          = 已进入命令派发，最终物理结果未确认
COMPLETED + null               = 节点完成
MANUAL + null                  = 需要人工处理
```

### 5.2 等待资源时，不要提前创建 `DISPATCH_STARTED`

这是非常重要的一致性约束：

- `WAITING_RESOURCE` 没有物理副作用，等待超时或取消后可以安全离开队列；
- `DISPATCH_STARTED` 表示已经进入“可能已派发”的崩溃敏感区；
- 如果把等待资源也记成 `DISPATCH_STARTED`，重启对账会把大量从未下发的命令误标成 `UNKNOWN`，制造不必要的人工核对。

因此，短期不必为了展示排队而伪造一条命令账本。界面可以从节点的 `WAITING_RESOURCE` 直接展示“待下发命令”。

### 5.3 命令状态短期沿用现有账本，但修正文案

| 当前账本状态 | 准确解释 | 推荐界面文案 |
|---|---|---|
| 无账本 + 节点等资源 | 尚未派发 | 等待设备，未下发 |
| `DISPATCH_STARTED` | 派发前已记账，尚无最终回包 | 派发中，结果待确认 |
| `ACKED` | 已收到成功最终回包 | 已完成 |
| `FAILED` | 已收到明确失败，或驱动明确失败 | 已失败，显示错误码 |
| `UNKNOWN` | 派发中断，物理结果无法确定 | 结果未知，禁止自动重发 |

### 5.4 设备状态只描述当前物理动作

设备侧建议保持：

```json
{
  "status": "running",
  "online": 1,
  "current_method": "Home",
  "current_command_id": "r1001370-..."
}
```

规则：

1. 设备接受动作后，才设置 `current_method/current_command_id`；
2. 执行完成后清当前方法和命令，恢复 `idle`；
3. 查询命令可以穿透执行态，不抢动作锁；
4. 等待内核锁的 B 不出现在设备当前命令里；
5. 若设备不支持队列，就不要虚构 `queued_commands`；
6. `online` 与 `status` 继续分开，执行中离线仍是危险状态。

## 六、正常、异常与恢复时序

### 6.1 同设备并行分支：正常完成

```text
时间   节点 A                  节点 B                  命令账本             设备
----   ---------------------  ---------------------  ------------------  ----------------
t0     RUNNING/WAIT_RESOURCE  RUNNING/WAIT_RESOURCE  无                  idle
t1     获得锁                 继续等待，未下发         无                  idle
t2     DISPATCHING            WAITING_RESOURCE       A:DISPATCH_STARTED  running/A
t3     等待最终回包            WAITING_RESOURCE       A:DISPATCH_STARTED  running/A
t4     收到成功回包            WAITING_RESOURCE       A:ACKED             idle
t5     FINALIZING → COMPLETED 获得锁                   A:ACKED             idle
t6     COMPLETED              DISPATCHING             A:ACKED/B:STARTED   running/B
t7     COMPLETED              COMPLETED               A:ACKED/B:ACKED     idle
```

`t5 → t6` 之间设备短暂 `idle` 是正常实现现象，不要求为了界面好看而隐藏。若未来做连续派发优化，也必须等 A 的最终回包和资源释放条件满足。

### 6.2 等资源超时

```text
B: WAITING_RESOURCE → 等待超时 / 取消 / 继续等待
```

因为 B 从未下发：

- 不需要设备侧取消；
- 不存在“设备也许已经执行”的未知窗口；
- 不应写 `UNKNOWN`；
- 可以安全地保持等待、按策略重试获取锁，或转人工；
- 绝不能为了“唤醒流程”直接绕锁发一次。

### 6.3 已派发后超时或连接断开

```text
A: DISPATCH_STARTED → 超时 / 断线 → 物理结果未知
```

此时不能直接另生成命令 ID 重发。必须区分：

- 设备仍在执行：等最终回包或用同一命令 ID 查询／恢复；
- 设备明确拒绝且未执行：可按该错误码的恢复策略处理；
- 设备可能已完成但回包丢失：同命令 ID 幂等恢复；
- 进程崩溃、无法确认：进入 `UNKNOWN`，人工核对设备与板位。

核心原则：**本地等待超时不等于设备停止，本地线程取消也不等于物理动作取消。**

### 6.4 第二条命令真的绕过锁到达忙设备

当前协议下返回明确忙错误是正确的：

```text
B 已到达设备
→ 设备检查到 activeMethod=A
→ 立即拒绝 B，不排队、不执行
→ 返回 A 的 device_state，B 的 commandId 保留在响应 message_id
```

这里 B 是“已发送但被拒绝”，不是“设备排队中”。中控若要把这种冲突自动转回队列，必须先给该忙错误定义清晰、稳定的“未执行、可重试”语义；不能把门未关闭、运行中禁止开门等安全错误一概当成可重试忙。

## 七、为什么不建议现在给模拟器加隐式动作队列

| 方案 | 优点 | 问题 | 结论 |
|---|---|---|---|
| **内核设备锁前排队** | 状态真实；取消简单；锁顺序统一；无需改设备协议 | 需要补等待阶段和队列可观测性 | **当前推荐** |
| 模拟器连接内自然串行 | 代码少 | 只对同连接有效；跨连接仍并发；不是显式队列 | 不能作为调度设计 |
| 模拟器跨连接静默排队 | 表面不报错 | 无接收确认；超时／取消／恢复复杂；与内核锁重复排队 | 不推荐 |
| 设备显式接受并入队，返回队列确认 | 可支持真实异步设备 | 需要协议、状态查询、幂等、取消和恢复全套契约 | 有真机需求时再设计 |
| 忙即拒绝 | 简单、安全、能快速暴露绕锁 | 正常竞争也可能转人工 | **只作最后防线** |

如果未来真机本身支持长任务异步执行，应新增明确的“两阶段协议”，而不是利用 TCP 阻塞模拟：

```text
请求 commandId
→ 接收确认：accepted / queued / rejected，携带 commandId
→ 执行状态查询或事件：running / succeeded / failed
→ 最终结果：同一 commandId
```

只有收到 `accepted/queued` 后，命令才能进入 `ACCEPTED` 或 `DEVICE_QUEUED`。仅 `send()` 返回不能进入这些状态。

## 八、并行语义和排队顺序

### 8.1 并行只表示允许同时调度，不承诺同设备同时执行

```text
ParallelGateway
├─ 分支 A：设备 X.Home
└─ 分支 B：设备 X.Transfer
```

合理语义是：

- A、B 可以同时进入就绪状态；
- 因 X 是独占设备，实际物理动作串行；
- 哪个先执行不应由 ParallelGateway 保证；
- 如果工艺要求 A 必须先于 B，就必须增加顺序依赖，不应依赖线程调度或队列偶然顺序。

### 8.2 当前轮询锁不保证公平 FIFO

`DeviceLock.acquireWithWait` 当前每 200 ms 尝试一次，抢到即可执行。它能实现互斥，但不保证：

- 先进入等待的先执行；
- 同 run 的分支按图顺序执行；
- 多 run 之间严格公平；
- 等待者不会被后来者插队。

第一阶段可以接受，但必须把“互斥”和“公平排队”分开描述。若需要稳定顺序，再实现持久化队列：

```text
device_command_queue
- queue_seq
- run_id / node_id / command_id
- resource_id
- state: WAITING / ACQUIRED / DISPATCHED / DONE / CANCELLED
- requested_at / acquired_at / dispatch_started_at / finished_at
- lease_owner / lease_until
```

队列只负责分配设备使用权；物理命令是否已下发仍以命令账本和设备回包为准。

## 九、界面和 API 建议

### 9.1 节点文案

| 场景 | 主文案 | 辅助信息 |
|---|---|---|
| 等锁 | **等待设备** | `设备 ID-X231 正被 run #... 使用；已等待 12.4 s；尚未下发` |
| 已派发无回包 | **命令执行中，等待回包** | 方法、命令 ID、已派发时长 |
| 有接收确认、设备排队（未来） | **设备已接收，排队中** | 设备队列位置（仅设备真实返回时） |
| 成功 | **已完成** | 执行耗时；等待资源耗时分开展示 |
| 超时且未下发 | **等待设备超时** | 可继续等待或取消，不提示物理结果未知 |
| 超时且已派发 | **命令结果待确认** | 禁止直接重发，进入恢复流程 |
| 忙拒绝 | **设备拒绝并发命令** | 当前方法、当前命令、明确错误码 |

### 9.2 耗时必须拆开

不要只给节点一个总时长：

```text
节点总耗时       48.2 s
├─ 等待设备      31.0 s
├─ 派发及设备执行 16.9 s
└─ 结果落库        0.3 s
```

否则“设备执行慢”和“前面排队久”无法区分，也无法评估并发是否真正提高吞吐。

### 9.3 API 返回建议

```json
{
  "nodeKey": "Activity_B",
  "status": "running",
  "executionPhase": "WAITING_RESOURCE",
  "phaseSince": "2026-11-13T07:33:52.000+08:00",
  "resourceId": 504831,
  "blockedByRunId": 1001371,
  "dispatchStarted": false,
  "commandState": null
}
```

`blockedByRunId` 只是查询时的快照，可能很快变化；不能作为恢复或调度判断的唯一依据。

## 十、建议实施顺序

### P0：先统一语义和文案

1. 明确 `DISPATCH_STARTED` 不等于设备已接收；
2. 将等待锁显示为“等待设备，未下发”；
3. 将 `sent_at` 的展示名改成“派发开始时间”；
4. 设备忙拒绝保留，不用隐式队列替代内核锁。

### P1：补节点执行阶段和时间戳

1. 在 `DeviceLock.acquireWithWait` 前后增加阶段回调；
2. 等锁前写 `RUNNING/WAITING_RESOURCE`；
3. 获得锁、`CommandLedger.begin` 成功后写 `DISPATCHING`；
4. 收到最终回包后写 `FINALIZING`，完成落库和释放后清阶段；
5. 记录 `wait_started_at / lock_acquired_at / dispatch_started_at / response_at`；
6. 对查询命令保持只读穿透，不与动作互斥。

### P1.1：补齐复合动作资源范围

1. TransferPlan 对自动门设备的源／目标资源申请设备锁；
2. 锁保持到搬运结束并完成关门；
3. 回滚路径同样释放设备锁并关门；
4. 用两个并发 run 验证 RunProgram 不再插入 OpenDoor—Transfer—CloseDoor 之间；
5. 保留不同设备并行能力，不能用岛级大锁解决。

### P2：确有公平性需求时做持久队列

1. 先定义 FIFO 或优先级规则；
2. 处理等待取消、租约过期、孤儿队列项；
3. 等待阶段与派发阶段分表或分状态；
4. 用压力测试验证无饥饿、无重复派发、无锁泄漏。

### P3：真机支持时再增加异步接收确认

1. 定义接收确认帧与最终结果帧；
2. 同命令 ID 全链路关联；
3. 明确设备队列是否持久化、重启后是否保留；
4. 定义排队取消、执行中止和查询恢复；
5. 完成故障注入后才在界面展示“设备已接收／设备排队中”。

## 十一、验收矩阵

| 场景 | 必须观察到 |
|---|---|
| 同一设备两个并行分支 | 两者均可就绪；只有一条派发；另一条明确显示等待设备且未下发 |
| 不同设备两个并行分支 | 两条可以真正并发，不被岛级锁串行化 |
| 第一条执行中查询状态 | `GetStatus` 立即返回当前方法和命令，不被动作耗时阻塞 |
| 绕过内核直接并发发动作 | 第一条执行，第二条明确忙拒绝；不发生并发物理动作 |
| 第一条完成后 | 第二条才获得锁、建立账本并派发；顺序可从时间戳证明 |
| 等待资源时取消 | 无设备命令、无 `UNKNOWN`、无板位副作用 |
| 派发后断线 | 不直接换新命令 ID 重发；进入幂等恢复或 `UNKNOWN` |
| 搬运中另一 run 发 RunProgram | RunProgram 等待整个搬运和关门结束，不在开门中途执行 |
| 开门失败 | 已申请设备锁和通道完整回滚；门进入明确状态；不遗留锁 |
| 两条相反方向搬运 | 固定资源顺序或等待图避免死锁；失败方可回滚 |
| 同命令 ID 成功重放 | 返回上次成功结果，不重复物理动作 |
| 查询命令重复 | 每次读取最新状态，不使用旧缓存 |

数据库断言至少包括：

```sql
-- 等资源期间不应提前出现第二条命令的 DISPATCH_STARTED。
SELECT command_id, method, state, created_at
FROM command_ledger
WHERE run_id = ? ORDER BY created_at;

-- 设备锁持有者、当前方法和当前命令必须能对应到同一活跃动作。
SELECT resource_id, current_run_id, status, current_method
FROM device_state
WHERE resource_id = ?;

-- 实际命令区间不得重叠；等待时间不能伪装成设备执行时间。
SELECT run_id, method, sent_at, finished_at, status, error_code
FROM run_command
WHERE device_id = ? ORDER BY sent_at;
```

## 十二、最终决策

1. **第二条同设备命令默认在中控等待，不下发。** 这是当前实现与协议下最真实、最安全、最容易恢复的方案。
2. **等待资源与命令派发是两个不同阶段。** 等资源没有物理副作用；一旦进入派发，就必须考虑结果未知和幂等恢复。
3. **设备 `running` 只描述当前已接受动作。** 等待内核锁的命令不应显示成设备内排队。
4. **设备忙立即拒绝是最后防线。** 它防止模拟器或异常调用并发执行，但不替代内核排队。
5. **“已发送”“已接收”“已开始”“已完成”必须有不同证据。** 当前同步协议不能提供独立接收确认时，不虚构这些状态。
6. **并行不等于同设备同时动作。** 同设备串行、不同设备并行；工艺有顺序要求时必须显式建依赖。
7. **复合动作的锁必须覆盖完整安全区间。** 对搬运而言，要覆盖源／目标设备、开门、搬动、关门，而不是只锁机械臂或门记录。
8. **先补可观测阶段，再考虑公平队列和设备异步协议。** 不建议一开始用一个更大的隐式队列掩盖状态不清的问题。
