## 7. 独立验证发现（2026-11-14）

### 7.1 🔴 P1 真缺陷：`reloadConfig()` 无「无 active plan ⇒ 回落默认」分支

`ExperimentScheduler.reloadConfig()` 只在 `for (plan : selectSchedulePlans(...))` 循环体内赋值并 `break`；当表中无 active plan 时循环不执行，三个 `volatile` 字段保持上次的值。

复现：清空 `schedule_plan`（0 行）→ 调用 `POST /api/scheduler/reload-config` → 返回 `{"reloaded":true,...}` 但 config 仍是最后一次生效的 `{"maxConcurrent":3,"optimizationFactor":10,"tickMs":3000}`，**不会回到默认 `4/50/2000`**，直到进程重启。

影响：管理员删除/归档最后一个排程参数后，调度器仍按旧参数运行，页面显示的「当前生效」与库中已无 plan 的事实不一致；且 `reloaded:true` 会让调用方误以为已重载。建议在循环前先重置为默认，或在循环未命中任何 active plan 时显式赋默认值。

### 7.2 🟡 §2.1 文档命令不可直接复现

- 单个 `TOKEN` 跨 `sleep 65` 会过期：实测第 ④ 步返回 `{"error":"未登录或会话已过期"}`。等待后须重新登录再取 config。
- 期望值 `tickMs:7000` 未说明来源，它是 `TICK_MS(2000) + iterationDelaySec(5)×1000`；无 plan 时是 `2000`。
- 受 7.1 影响，文档里的「建 plan → 等 65s → 看到 `2/80/7000`」可能被**上一次残留配置**污染（实测删空表后 config 仍是 `2/80/7000`，此时不建 plan 也能得到期望值）。判别性验证应使用与当前值不同的参数，且记录建前基线。

### 7.3 🟡 §5.4 边界需补充：重载周期随 plan 变化

`if (ticks % 30 == 0) reloadConfig()` 中 `Thread.sleep(tickMs)` 的 `tickMs` 会被 plan 的 `iterationDelaySec` 拉长：无 plan 时 30×2s=60s，`delay=1` 时 30×3s=90s，`delay=5` 时 30×7s=210s。本次实测 `delay=1` 时 48s 生效（取决于起始 tick 相位）。「约 60s」只在默认配置下成立。

### 7.4 🟡 基线后新增能力未纳入本清单

`f5ef43c` 新增 `POST /api/scheduler/reload-config`（实测 200，返回 `reloaded/maxConcurrent/optimizationFactor/tickMs`），前端 `SchedulePlans.tsx` 已接线；工作区另有 `/api/settings/stale-pause` 相关改动。§4 端点清单与 §5.4「不是实时」边界未覆盖这些。手动重载使参数可即时生效，是 §5.4 的例外。
