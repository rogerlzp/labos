## 0. 问题定义

**场景**：夜班要跑一批实验，实验室有多座岛、多台设备。怎么排？

这不是新问题，是经典的 **Job Shop Scheduling**：

| 元素 | 我们的对应物 |
|---|---|
| Job | 实验（EXP0812） |
| Operation | 流程（workflow） |
| Machine | 岛（island） |
| Processing time | 流程预计耗时（`duration_model`） |
| Precedence | 流程顺序 |

**和教科书 Job Shop 的区别**：

1. 我们的工时**不准**（精度 10 秒级，且波动比最大 13.5×）
2. 我们的资源**有物理约束**（机械臂打架 = 真撞）
3. 我们的失败**不可撤销**（开盖了就是开了）

所以**不能照搬最优解算法**（IBM CPLEX 那套），要用**保守可行的启发式**。

## 1. 资源模型

### 1.1 两级资源

```
岛（island）  容量 = 1     ← 岛内的机械臂是共享的，两个实验同时跑会打架
 └ 设备（device）容量 = 1  ← 单台设备同一时刻只能执行一个动作
```

### 1.2 为什么岛级容量是 1

**物理事实**：一个岛通常只有 1 台机械臂（`TRANSFER` 能力），它负责岛内所有板子的搬运。

两个实验同时在同一个岛跑：

```
实验 A：Incubator_2C-1 → XRobot 取板 → 放入 Thermo ATC
实验 B：Incubator_2C-2 → XRobot 取板 → 放入 Rotanta
```

XRobot 在两个实验里都被调用，**它不知道板子是谁的**——最后可能把 A 的板子送到 B 的目的地。

**结论：岛级容量必须是 1**，除非能做到"机械臂时间片分配"（需要秒级准确的时长，现在做不到）。

### 1.3 实验 → 岛的映射

**关键约束**：实验必须**显式声明在哪个岛跑**。

```sql
ALTER TABLE experiment ADD COLUMN island_id bigint REFERENCES resource_node(id);
```

**为什么必须显式**：

| 方式 | 问题 |
|---|---|
| 从流程节点反推 | 普通流程节点只绑能力，执行时才选设备 → **岛不确定** |
| 按能力池第一个算 | 会算出"这个实验同时用 5 个岛"，实际执行只用了 1 个 |

显式声明后：

```java
Set<Long> required = Set.of(experiment.islandId());
```

**一个实验只占一个岛**（2.0）。跨岛实验如果真出现，拆成多个实验 + 依赖关系。

## 2. 调度算法（2.0）

### 2.1 总体结构

```
                    ┌──────────────┐
  提交实验 ────────→ │  pending 队列 │
                    └──────┬───────┘
                           │  按优先级 + 截止时间排序
                           ↓
                    ┌──────────────┐
                    │  调度循环     │ 每 2 秒一次
                    │  (单线程)     │
                    └──────┬───────┘
                           │  找"岛空闲"的最高优先级实验
                           ↓
                    ┌──────────────┐
                    │  岛锁表       │  island_id → experiment_run_id
                    └──────┬───────┘
                           │  占用成功
                           ↓
                    ┌──────────────┐
                    │  执行线程池   │ 大小 = min(岛数, 8)
                    └──────────────┘
```

### 2.2 排序规则

```java
Comparator<ExperimentRun> order =
    // ① 有截止时间的优先（EDD: Earliest Due Date）
    comparing(r -> r.deadline == null ? LocalDateTime.MAX : r.deadline)
    // ② 同截止时间，按优先级降序
    .thenComparing(Comparator.comparingInt(ExperimentRun::priority).reversed())
    // ③ 同优先级，先提交先跑（FIFO）
    .thenComparing(ExperimentRun::submittedAt);
```

**为什么 EDD 优先于优先级**：

有截止时间的实验通常有外部约束（比如"这批样本今天必须出结果"），错过就废了。优先级可以协商，截止时间不能。

**为什么不做 SPT（最短作业优先）**：

SPT 能降低平均等待时间，但会让长实验**饿死**——夜班批次可能永远排不上。

### 2.3 调度循环伪代码

```java
while (running) {
    // ① 从队列取可执行的实验（按排序规则）
    List<ExperimentRun> candidates = pending.sorted(order);

    for (ExperimentRun r : candidates) {
        long island = r.islandId();

        // ② 尝试占岛（CAS，原子）
        if (!islandLock.tryAcquire(island, r.id())) {
            continue;   // 这个岛被占，试下一个实验
        }

        // ③ 检查岛内设备是否真的空闲（防止上一个实验没释放干净）
        if (!allDevicesIdle(island)) {
            islandLock.release(island, r.id());
            continue;
        }

        // ④ 派发
        pending.remove(r);
        r.status(RUNNING);
        executor.submit(() -> executeExperiment(r));

        // ⑤ 一次只派一个？还是一轮派满？
        // 2.0 一轮派满（不同岛可以同时开工）
    }

    sleep(2_000);   // 2 秒一轮
}
```

**一轮派满 vs 一次一个**：

一轮派满（不同岛并行开工）能提高吞吐。但会让"同一时刻启动 26 个实验"，日志和监控压力大。

**2.0 取折中**：一轮最多派 `min(空闲岛数, 4)` 个，避免瞬间压力。

### 2.4 释放

```java
finally {
    islandLock.release(island, r.id());
    r.status(COMPLETED / FAILED);
}
```

**必须在 finally 里释放**——否则一个实验崩了，岛永远被占。

## 3. 死锁避免

### 3.1 死锁的四个条件

| 条件 | 我们是否满足 | 处理 |
|---|---|---|
| 互斥 | ✅ 岛锁是互斥的 | 不可避免（物理资源） |
| 持有并等待 | ⚠️ **可能** | **消除它** |
| 不可抢占 | ✅ 不抢占 | 可接受 |
| 循环等待 | ⚠️ **可能** | 消除 |

### 3.2 消除"持有并等待"

**规则：实验一次性申请所有需要的资源，全有或全无。**

```java
// 2.0 每个实验只需要 1 个岛 → 天然满足
if (!islandLock.tryAcquire(island, r.id())) {
    continue;   // 拿不到就完全不占，不持有部分
}
```

**如果将来出现跨岛实验**（需要 2 个岛）：

```java
// 按 island_id 升序申请（全局顺序，消除循环等待）
long[] islands = required.stream().mapToLong(Long::longValue).sorted().toArray();
if (!lockAllOrNone(islands, r.id())) {
    continue;   // 一个都拿不到就全放掉
}
```

### 3.3 超时兜底

```java
// 岛锁带 TTL：占锁超过 maxDuration（默认 2 小时）自动释放
islandLock = new IslandLock(ttl = Duration.ofHours(2));
```

**为什么要有 TTL**：如果执行线程异常退出而 `finally` 没跑到（OOM、kill -9），锁会永久泄漏。

TTL 到期强制释放，代价是"可能两个实验同时跑一个岛"——**比永久卡死好**。

### 3.4 死锁检测（可选）

```java
// 每 30 秒检查：所有 pending 实验都因为锁被占而无法执行，且持锁实验无进展 → 告警
if (allPendingBlocked() && noActiveProgress(Duration.ofMinutes(10))) {
    alert("调度停滞：所有实验都在等锁，但持锁实验无进展");
}
```

## 4. 失败隔离

### 4.1 一个实验失败不能影响其他

```
实验 A 失败 → 释放岛 → 实验 C（排队中）可以进来
```

**实现**：`executeExperiment` 整体 try-catch-finally，任何异常都：
1. 标记 `experiment_run.status = FAILED`
2. 释放岛锁
3. 记 `audit_log`
4. **不抛出**（不能污染调度循环）

### 4.2 执行线程池

```java
ExecutorService executor = Executors.newFixedThreadPool(4);
```

**大小 4 而不是 26**：

- 同时跑 26 个实验，每个实验内部还有 workflow 的线程池（`RUN_POOL` 也是 4）
- 会变成 26 × 4 = 104 个线程抢 CPU
- 4 个够用（夜班 20 个实验，5 轮跑完）

**用有界队列 + CallerRuns**：队列满时让调度线程自己跑，形成背压。

### 4.3 与 workflow 的线程关系

```
调度线程池（4）  每个跑一个实验
   └ workflow 的 RUN_POOL（4）  每个跑一个流程
       └ 节点执行（顺序）
```

**总并发 = 4 实验 × 4 流程 = 16 个 run 并行**。

这个数字要监控——如果 CPU 打满，降到 2×2。

## 5. 状态机

### 5.1 实验运行状态

```
                   ┌──────────── cancelled ←── 用户取消
                   │
draft → queued ────┼──→ running ──┬──→ completed
        │          │      │       └──→ failed
        │          │      └──→ paused ──→ running（人处置后）
        │          │
        └──────────┴──→ (锁被占，留在 queued)
```

### 5.2 状态转换的原子性

```sql
-- 用条件更新保证只有一个调度线程能抢到
UPDATE experiment_run
SET status = 'running', started_at = now()
WHERE id = ? AND status = 'queued'
RETURNING id;
-- 返回 0 行 = 别人先抢到了，跳过
```

**不要用 `SELECT ... FOR UPDATE`**：会在高并发下大量等待，条件更新更轻。

## 7. 可观测性

调度器必须**能看懂它在想什么**：

```bash
GET /api/scheduler/status

{
  "running": 3,
  "queued": 12,
  "islandLocks": [
    {"islandId": 100033, "islandCode": "Pre-NGS", "runId": 204930, "since": "...", "expiresAt": "..."}
  ],
  "workers": {"pool": 4, "active": 3, "queue": 0},
  "lastDispatchAt": "...",
  "stalled": false
}
```

**`stalled` 是最重要的字段**：所有 worker 空闲、队列非空、但没有派发 → 说明有锁没释放或资源全被占。

### 7.1 调度状态接口（2026-11-03 补队列明细）

现有接口只有计数，值班看不出"谁在占岛、我在队里第几个"。补齐为：

~~~json
GET /api/scheduler/status
{
  "running": 1, "queued": 3, "maxConcurrent": 4, "stalled": false,
  "started": 41, "loopStarted": true,
  "lastDispatchAt": "2026-11-03T19:50:00",
  "islandLocks": [
    {"islandId": 100033, "islandCode": "Pre-NGS", "runId": 91, "experimentRunId": 91,
     "experimentId": 812, "experimentNo": "EXP0812", "since": "...", "expiresAt": "..."}
  ],
  "queue": [
    {"position": 1, "experimentId": 813, "experimentNo": "EXP0813",
     "experimentRunId": 92, "islandId": 100033, "islandCode": "Pre-NGS",
     "priority": 50, "deadline": null, "submittedAt": "..."}
  ],
  "workers": {"pool": 4, "active": 1, "queue": 0}
}
~~~

**字段语义**：`started` = **累计派发次数**（number；改动前的实现同名字段是 boolean
"调度循环是否已启动"，2026-11-03 起按本契约改成计数，该 boolean 语义挪到 `loopStarted` 兼容保留）。

**排序口径**：`queue` 按**实际派发顺序**（`deadline` ASC（无截止最后，EDD 优先）→ `priority` DESC → `submittedAt` ASC），与 `dispatch()` 同口径 —— 位次必须能回答"我还要等几个才轮到"，排序规则不一致位次就是假的。
`position` 从 1 开始；`running` = 正在占岛执行的实验数；`workers.queue` = 线程池里还没被
worker 取走的任务数（现在池子是直接 submit，取 0，保留字段给未来改动）。

### 7.2 实验列表「预计等待时间」（2026-11-03）

~~~json
GET /api/experiments/eta?limit=100
{"items": [
  {"experimentId": 813, "experimentNo": "EXP0813", "status": "queued",
   "islandId": 100033, "islandCode": "Pre-NGS",
   "queued": true, "queuePosition": 2, "estimateSec": 900, "estimatedWaitSec": 1830,
   "reason": "岛被 EXP0812 占用，前面还有 1 个实验"}
]}
~~~

**算法**（纯函数 `SchedulerEta.estimateWait` 可单测）：

1. 实验在**调度器岛锁持有者**集合里（内存态"谁真的在跑"），或实验表 `status=running` → `estimatedWaitSec=0`，`queued=false`；**不看 `experiment_run.status`** —— 既有的 running 行会把已结束实验误判成"运行中"；
2. 不在调度队列且不在运行 → `estimatedWaitSec=null`（不适用，前端显示" —"）；
3. 在队列中：`estimatedWaitSec = max(0, 岛当前持有者剩余估算) + Σ(同岛排在它前面的队列实验的 estimateSec)`；
   - 持有者剩余估算 = 该 run 的 `run_node` 里未完成节点的 `COALESCE(estimate_sec, 60)` 之和；
   - `estimateSec` = 该实验各流程任务节点的 `COALESCE(estimate_sec, 60)` 之和（与甘特/时间条同一估算链）；
4. `reason` 写人话（"运行中" / "岛被 EXP0812 占用，前面还有 1 个实验"），前端 tooltip 直接显示。

**局限（写进页面说明，别当承诺）**：不含换型/清洗/人工处置时间；跨岛不互斥，但受
`MAX_CONCURRENT` 池上限影响，本估算只看岛锁；暂停中的占用者按"继续跑完"估算。

## 8. 边界与限制

| 限制 | 值 | 理由 |
|---|---|---|
| 每实验最大步骤 | 500 | 展开后超过就不可能调试 |
| 单流程 `loopCount` | ≤ 20 | 同上 |
| 岛锁 TTL | 2 小时 | 兜底异常退出 |
| 调度循环间隔 | 2 秒 | 太频繁浪费 CPU，太慢响应差 |
| 实验线程池 | 4 | 避免线程爆炸 |
| 同时 running 实验 | ≤ 8 | 超过会 CPU 打满 |

## 10. 为什么不用"最优解"算法

| 算法 | 为什么不用 |
|---|---|
| CPLEX / Gurobi | 需商业授权；且输入数据（工时）本身不准，算得再优也没意义 |
| 遗传算法 | 效果好但**不可解释**——值班员问"为什么这个实验排在第 5"，答不上来 |
| 强化学习 | 需要大量训练数据，我们没有 |

**用启发式（EDD + 优先级 + FIFO）的理由**：

1. 结果**可解释**："它截止时间最早，所以先跑"
2. 出错时**能手工干预**（改优先级、改截止时间）
3. 工时不准的情况下，最优解和启发式的实际差距小于工时误差

> **在数据不准的系统里，追求算法最优是自欺欺人。**
> 先把资源冲突管住（不撞机械臂），再谈优化。
