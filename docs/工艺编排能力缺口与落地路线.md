## 一、这份文档是什么

一份**能力缺口分析 + 落地路线**。

分析对象是一张真实的实验室自动化工艺流程图（物料视角）。
它不是"画得好看"的图 —— 它是**现场在用**的编排，14 个子流程、上百个图元、
11 次扫码交接、3 条被事件驱动的控制链。

分析的结论一句话：

> **LabOS 编排的是「动作」，而这张图编排的是「物料」。**
> 板子从一个位置到另一个位置、装着什么、什么时候该停一下制冷。
> 这是两个不同的抽象层，不是在现有流程图上加几个节点能补上的。

### 2.2 容器的三个维度

节点标签有两个槽位，这是理解全图的关键：

- 容器写成 `PCR 板 [扩增产物] (所属步骤)`
  - `[扩增产物]` = **这块板现在装着什么**（内容物状态）
  - `(所属步骤)` = **这块板属于哪一步**（物料来源归属）
- 加上 `-膜` / `-盖` / `-样品` 后缀 = **耗材状态**（封过膜 / 加过盖 / 已加样）。
  ⚠ **膜与盖子不是一回事**：膜是板自己的状态（撕下来直接进垃圾桶，**不单独追踪**）；
  **盖子是独立实体** —— 它有自己的位置与流转（从常温载架取、盖到板上、再撕下）

⇒ **一块板在图上有三个维度：身份、内容、耗材。**
⚠ **口径修正（2026-11-12 评审）**：孔级样品模型（`plate_well`/`sample`/`sample_aliquot`）**早已存在**（空表），
所以真正缺的是**板级工艺阶段**（`process_state`），不是"每个孔装什么" ——
后者有家底了。详见设计稿 §4.2 的三条边界。

## 三、工艺主线

工艺类别（通用分子生物学术语，非客户机密）串成一条横穿全图的物料主线：

```
扩增板(母液) → 稀释板 → 扩增板(扩增→纯化) → 酶切板 → 体外转录板 → 转录后纯化
   → 深孔板 → 纯化板 → 检测板 → [浓度数据]
   → 检测板 / 分装板 ×N → 免疫检测板 样品-检抗-酶标-显色-终止 → [读板结果]
```

**形状上的一个重要事实**：这张图**没有任何分支 / 合流符号**。物料主线是**线性**的，
"同一高度上并列的多列板"是**不同物料各自的位置**，不是流程分支。

⇒ **真实物料视角的工艺编排里，用不到网关。**
并行 / 异或 / 条件网关在 LabOS 里是齐的，但在这类流程里**用不上**；
真正的难点全在别处（§五）。

## 四、控制与事件语义

图上有**三条不在物料主链上的旁路控制链**，全部由**事件**驱动。这是全图最有信息量的部分。

### 4.1 位置联动：停制冷 / 恢复制冷

```
低温位 / 检测板 ──→ 停制冷 ──→ …… ──→ 恢复制冷 ──→ 继续主链
        ↑ 触发：开始搬运时
```

含义：**板子进了低温位就停制冷（免得试剂在低温下变质），板子被搬走了就恢复制冷。**
这是**基于位置的状态联动**，不是定时。

### 4.2 定时联动：孵育计时

```
孵育箱 ──(虚线: 孵育计时到期)──→ 停制冷 ──→ …… ──→ 恢复制冷
```

出现 **3 次**，对应免疫检测段的**样品孵育 / 检抗孵育 / 显色孵育**三次进箱。

### 4.3 位置事件：到达孵育位时

```
孵育位 ←──(虚线: 到达孵育位时)── 停制冷
```

含义：**板子一到孵育位就触发一个动作**（不是"等了多久"）。

### 4.4 带设备读数的循环

```
酶标仪「孵育 读数」 → 「直到读数达到设定值」 → (不达标) 回到 读数
                                                (达标) → 终止显色 → 读板结果
```

### 4.5 数据产物

| 产物 | 位置 | 作用 |
|---|---|---|
| **浓度数据** | 浓度检测末尾 | 驱动「浓度调整与分装」的浓度计算 |
| **读板结果** | 终止显色末尾 | 终点产物 |
| **扫码记录** ×11 | 每一次物料交接 | 每一步都要扫到对应的板码 |

## 五、LabOS 现状对照：13 项缺口

> 现状取自真实表结构（`resource_node` / `plate` / `position_state` /
> `workflow_variable` / `experiment_variable` / `run_node` / `command_ledger`）。

### P0 · 挡住"照图编排"的四件事

| # | 缺口 | 图上的证据 | LabOS 现状 | 后果 |
|---|---|---|---|---|
| G1 | **板级工艺阶段**没建模 | 每块板带内容（扩增产物 / 纯化后样品 / 检测体系 / 显色 / 终止 …）共 18 种状态 | `plate` 只有 `status(available/in_use/consumed/discarded)` 与 `position_status(IN_TRANSFER\|KNOWN)`，**没有工艺阶段字段**；`attr` 全部为空。⚠ 孔级样品模型（`plate_well`/`sample`/`sample_aliquot`）**早已存在**（空表）⇒ 缺的是板级阶段，不是孔级内容 | "这块板现在到哪一步了"无处可查；追溯断链 |
| G2 | 耗材没建模 | `-膜`（封过）、`-盖`（加过）、`-样品`；撕膜机会把它撕掉。⚠ **膜与盖子要分开看**：膜是板的状态（撕下即弃，不单独追踪）；**盖子是独立实体**（有独立条码/库存/附着历史） | 无处可存 | 膜加个字段就够；盖子需要**一类新实体**，量级完全不同。**判据（评审后修正）**：*是否需要独立身份或生命周期追溯*（位置/批次/库存/附着历史/可重复使用/质量追溯）？ |
| G3 | 跨流程物料传递没语义 | 容器名一路串下去，前一个子流程的产物 = 下一个的输入（灰色虚线箭头） | 规格书 §7.2：「2.0 只交付顺序」；`experiment_run` 只有单值 `workflow_id` + `variables` JSONB；`plate` **没有"归属于哪个 run / 哪一步"的字段** | 照图编排 ⇒ **子流程之间的板子身份断链**：上一流程结束时板子去哪了、下一流程从哪拿，系统答不上来 |
| G4 | 设备上的「工位」层没有 | 多工位平台工位 ×47、平台内部 ×19、磁分离工位、中转位、仪器内板位 | `resource_node.kind ∈ {device, incubator, island, storage, transfer_point}`，**没有工位这一层**；`position_state.port_id` 最接近"通道"，但表达不了"一台设备几十个工位" | 机械臂的"从 3 号工位取板放到 7 号工位"**没有落点** |

### P1 · 编排时绕不过去的五件事

| # | 缺口 | 图上的证据 | LabOS 现状 | 后果 |
|---|---|---|---|---|
| G5 | 事件 / 触发器整类没有 | 三种触发：孵育计时到期 / 到达孵育位时 / 开始搬运时 | `__sleep` 是**阻塞等待**（睡 N 秒再往下走），不是"到点触发"；无定时器、无事件总线、无位置事件 | **这是范式差异，不是缺个节点**：LabOS 是"沿图一步步走"，而图上有 3 条旁路控制链不在主链上、被事件驱动 ⇒ 画不出来 |
| G6 | 设备参数（setpoint）读写没有 | 停制冷 / 恢复制冷 = **改设备的开关**，不是"跑一个动作" | 设备方法都是「`method` + `payload`，跑一个动作」；无通用读/写参数接口 | 只能表达成"调用一个叫 StopCooling 的方法"，要求设备真暴露它 |
| G7 | 带设备读数的循环只做了一半 | 酶标仪读数 → 判定 → 不达标回读数 | `__wait` 等的是「**变量**变成某值」（靠外部刷新源灌进来），**不是**「**设备读数**达标」 | 需要「设备输出 → 条件判定 → 循环」三件套打通 |
| G8 | 分装（一对多）不是一等操作 | 一份样品分到多块板，每块按不同体积取 | 板位模型是"一块板 N 个层位"，但没有"把一个容器的内容按体积/浓度分配到多个容器" | 只能拆成 N 个手写节点，或用 `__expr` 硬算 |
| G9 | 同规格多板没有动态展开 | PCR 板多块、深孔板多块 —— 同一段动作重复 N 遍，每遍一块新板 | 并行网关 ✓ 有，但**没有"按 N 动态展开 N 个实例"**（N 由实验规模决定，不能画死在图上） | 只能把 N 块板手画成 N 条并列分支 |

| # | 缺口 | 图上的证据 | LabOS 现状 | 后果 |
|---|---|---|---|---|

## 六、LabOS 已经做得不错的地方

这张图反证了下面这些是对的：

| LabOS 能力 | 在这张图上对应的东西 |
|---|---|

## 七、落地路线：从哪些方面入手

> **排序依据**：先让"一块板从哪来、到哪去、中间装着什么"在系统里成立，
> 再谈事件和触发器 —— **没有物料身份，事件模型也没地方落**。

### 阶段 0 · 先把抽象层换掉（地基）

现在 LabOS 的核心实体是**动作**（`workflow_node` = 一个设备方法）。
这张图的核心实体是**物料**。

- ⇒ 先确立「物料」是一等公民：容器有身份、有内容状态、有耗材状态、有归属
- ⇒ 再确立「工位」是一等公民：设备下的一个可放板的位置
- ⇒ 然后流程才从「动作序列」升级成「**带着物料走的动作序列**」

**这一步不动一行代码，但决定后面每一步的表结构。**

### 阶段 1 · 物料身份与状态（对应 G1 / G2 / G11 / G12）

> **详细设计**：见 [物料身份与状态 · 设计](物料身份与状态-设计.md)（待评审，含数据模型 / 状态迁移语义 / 事务边界 / 实施切片 / 决策点清单；英文镜像 `docs/en/material-identity-and-state-design.md`）。

| 动作 | 落点 |
|---|---|
| `plate` 加**板级工艺阶段**（`process_state`）、**膜**状态、归属（当前归属 / 生产来源 / 加工历史三分） | G1、G2 的膜这半边 |
| **盖子等独立耗材**作为一类新实体（自己的库存与取放），不是板的属性 —— **整表推迟到 S5**，不冻结不完整结构 | G2 的盖子这半边 |
| 板型规格继续用 `plate_type`（`96/384/24/tube_rack`），**不改**；工艺角色若需要另加列 | G12（评审修正） |
| 新增状态迁移留痕（仿 `plate_location_audit`） | G1 的"可追溯"半边 |
| **节点声明产出物料**：设备方法执行完把容器变成什么状态 | G1 的另一半 —— 没有这个，状态永远不会自己变 |
| 「废弃」状态与废料动作 | G11 |

### 阶段 2 · 工位层（对应 G4）

| 动作 | 落点 |
|---|---|
| `resource_node` 增加工位这一层（挂在设备下，`parent_id` 现成） | G4 |
| `position_state.port_id` 改成真正的工位引用 | G4 |
| 机械臂搬运的 from / to 指向工位而不是设备 | G4 |

### 阶段 3 · 跨流程物料传递（对应 G3 / G13）

| 动作 | 落点 |
|---|---|

## 八、第一个该动的刀

**建议从阶段 1 的一个最小闭环开始**，而不是一次铺开五个阶段：

> 一块板有身份（条码）、有内容物状态；
> 它被机械臂从 A 工位搬到 B 工位；
> 搬完之后，**板的内容物状态自动从 A 态变成 B 态**（因为节点声明了产出）；
> 全程留痕，能回答"这块板现在装着什么、上一步是谁把它变成这样的"。

这条闭环通了，G1 / G2 / G3 / G11 的地基就都立住了；
后面每一项（工位、跨流程传递、事件）都是在**已经能说清物料身份**的基础上加东西。

**如果只能做一件事**：做「**节点声明产出物料 + 板状态自动流转 + 状态迁移留痕**」。
它同时解决 G1、G2、G11，是其余 12 项的共同前提。

## 九、结论

1. **这张图编排的是物料，不是动作。** LabOS 编排动作。
   这是抽象层差异，不是功能数量差异。
2. **网关不是重点。** 这张图一个网关都用不上 —— 物料主线是线性的，
   并列的多列板是不同物料各自的位置。我们已经把网关做齐了（并行 / 异或 / 条件），
   但它在这类真实工艺里用不上。
3. **难点集中在三处**：物料身份与状态（G1/G2）、工位层（G4）、
   跨流程物料传递（G3）—— 这三项是**建模**问题。
4. **事件模型（G5）是范式差异**，不是加节点：
   LabOS 是「沿图一步步走」，真实工艺里有 3 条**不在主链上、被事件驱动**的控制链。
5. **先立物料身份**。没有它，事件、工位、跨流程传递全都无处落地。
