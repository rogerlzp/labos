## 4. 建议评审重点（按风险排序）

1. **超时按方法取的取值链是否合理**（`MethodTimeoutPolicy`）：设备方法级 → 设备方法库上限 → 流程节点级 → 能力默认 → 兜底 30 秒。
   重点看：**显式的设备库值（3s/5s/20s）为什么不被能力默认抬高**，以及「设备方法库上限」这一级用 `MAX(timeout_sec)` 是否会把某个慢方法的上限扩散到该设备的所有方法。
2. **A1 真停的默认是否真的安全**：`device_method.interruptible` 默认 `false` ⇒ 没有现场清单时**所有方法走老路径**（阻塞等待，行为一字不变）。
   请重点看：这条「默认不生效」是否真的没有旁路（`executeCommand` 之外还有没有别处调 `driver.execute`）。
3. **中断后的数据语义**：命令/步骤行记 `aborted`（按 `EC-99-0005` 与真失败分开），业务节点行保持 `running`，run 落 `paused`；
   恢复时 `resumeAsync` 删掉非 completed 的行 ⇒ **这一步会重跑**。
   请看：`aborted` 与 `manual` 的选择是否会影响既有 UI/统计口径。
4. **设备锁的三个语义**：`device_state.current_run_id` 的正常释放 / 幽灵锁（run 死了锁没释放）/ 孤儿锁（run 被删了锁还在）。
   本轮修了后两种，但**根因是「删 run」这个动作没有配套释放锁** —— 请评估是否该在删除 run 的入口（API/后台清理）统一处理。
5. **能力解析的「绑定设备优先」**：`loadProtocolCapability` 无 `DISTINCT/ORDER BY` ⇒ 同名方法跨能力时结果取决于物理行顺序。
   本轮改为「绑定了哪台设备就用那台设备的能力」，并把协议映射改成确定性。
   请看：`resolveCapability` 的六级顺序里，`bound` 插在 `explicit` 之后、`protocol` 之前，**这个位置对不对**（会不会让「节点上显式写错能力标注」被设备能力覆盖）。
6. **三个写死的固定超时**是否还有第四个：已知并修掉的是驱动等待 30s、设备锁等待 60s、测试脚本等待 90s。
   请扫一遍代码里还有没有「假设设备秒回」的硬编码等待。
7. **门禁机制**：新增 `parse_summary`（区分「汇总行缺失」与「有失败用例」）；门禁 22 段；`pre-push` 仍跑全量门禁。
8. **测试台账自洽**：`docs/测试用例总表.md` 的常量表 / 脚本清单 / 诚实清单是否与 `scripts/ci-gate.sh` 的实际阈值 100% 对得上。
9. **中英文档 1:1**：`scripts/verify-en-docs.py` 硬错误 0；本轮新增/修改的 8 篇是否逐段对齐（尤其新增的 `99a/99b` 分片说明与 `aborted` 状态段落）。

## 5. 评审问题清单（请 AI 重点回答）

1. **超时取值链**：`device_method → 设备库上限 → workflow_node → 能力默认 → 30s` 这条链，**顺序与兜底**是否合理？
   特别是：设备库上限用 `MAX` 会不会让一台设备上「某个慢方法」的上限扩散到它所有方法？
   `workflow_node.timeout_sec` 放在设备两级**之后**，会不会让流程侧更紧的约束失效？
2. **补默认超时**：本轮给 16 个能力补了保底（孵育 1800s / 扩增 3600s / 离心 900s / 洗板 900s / 其余 600s）。
   这些**默认值本身合不合理**？哪个能力该更长/更短？要不要按 `estimate_sec` 动态算而不是写死？
3. **A1 的默认安全**：`interruptible` 默认 false 是不是足够？还需要「可中断方法必须同时具备某个能力」这类二次保护吗？
4. **中断的状态语义**：为什么选 `aborted` 而不是新增词表项 / 复用 `manual`？
   「节点行保持 running」会不会让页面显示成「还在跑」？是否应改成显式的 `interrupted`？
5. **实验级暂停怎么传到 workflow 级**：本轮执行侧有**两条**停住的路 ——
   ① **节点边界**：`WorkflowService.withPauseChecker` 每到一个任务节点边界查一次，
      判据是「`run.status='paused'` **或** 本流程正被某个生效中的现场扣留覆盖」
      （`RunControl.pause` 落的是扣留、**不改** workflow 级 run 状态，所以只能反查
      `RuntimeHold.coveringForWorkflow`）→ 命中就 `pauseRunAtBoundary` 把底层 run 也落成 `paused`，
      后续节点保持 `pending`；这条与 `interruptible` 无关，默认生效。
   ② **动作中途**：`DriverStepExecutor.pauseRequested` 在方法执行中对**可中断**方法调 `driver.abort`
      （要 `device_method.interruptible=true`，见问题 3）。
   这条反查的**映射**（workflow run → 正在跑的实验步骤 → 实验 → 岛/现场）是否可靠？
   特别：**同一流程被多个实验并发使用**时，
   `RuntimeHold.coveringForWorkflow` 只按 `experiment_run_step.status='running'` + `workflow_id` 反查，
   若并发下同一 `workflow_id` 有多条 running 步骤，覆盖判定是否仍然可靠？
6. **设备锁**：幽灵锁与孤儿锁都靠「启动兜底」清理，但**根因是删 run 不释放锁**。
   是否应在删除 run 的入口就释放？启动兜底清理是否够（设备可能连续几小时没人重启）？
7. **能力解析**：`bound` 优先级插在 `explicit` 之后 —— 若节点显式写了错误的能力标注，
   现在会被设备能力**覆盖**（原来是显式优先）。这是想要的语义吗？
8. **固定超时的第四个**：还有哪些地方假设「设备秒回」？（尤其：告警、调度器轮询、心跳、批次编排）
9. **门禁耗时**：慢设备让门禁从 17 分钟涨到 32 分钟。
   你建议的平衡是「测试用窄区间 + 演示用全区间」，还是「按设备能力分档超时」？
10. **诚实清单**：本轮 `docs/设备执行中暂停-现状实测与实现方案-20261106.md` §5 的诚实清单，
    是否**如实**反映了缺口？有没有被美化的项（尤其「真机未验证」「现场清单未到」这两条）？
11. 还有哪些「仿真全绿、真机必炸」的隐性假设（尤其：真机的 abort 能否真的打断、
    机械臂中断会不会掉板、真机的超时配置与仿真不一致）？
