## B. 模拟器随机耗时 + 「设备执行中暂停」的实测与真停方案

### B1. 模拟器随机耗时（`1faa087`）

```
java -cp out com.labos.kernel.sim.DeviceSimulator \
     --port 19502 --device 214 --code ID1731 --cap TRANSFER --profile generic \
     --rand-delay 30000:300000          # 30–300 秒随机（真机时序）
```

- 语法 `--rand-delay MIN:MAX[:SEED]`；**不给 SEED** 每次都不同（真机就是这样），**给 SEED** 序列可复现（测试要这个）。
- 优先级：`--rand-delay` > `--delay` > 画像/型号的固定耗时。
- `scripts/sim-up.sh` 第三个参数：`./labos-kernel/scripts/sim-up.sh LAB-DEMO-02 0 30000:300000`。
- 落点：`DeviceCore`（随机值覆盖 `methodDelayMs`）、`DeviceSimulator`（参数解析）、`sim-up.sh`（脚本）。

### B2. 实测结论（用户原话：「设备正在执行的方法会继续，只有机械臂收到暂停指令后会当前停止」）

| 问 | 答 | 证据 |
|---|---|---|
| 设备执行中发暂停，**实验会进入暂停状态吗？** | **会**（0.2 秒内 `experiment_run` / `experiment` 两层都变 paused） | `e2e-pause-during-experiment.py` |
| **正在执行的设备方法会被打断吗？** | **不会** —— 它跑完才停（`completed`） | 同上，`设备指令最终状态: completed` |

## C. 判据订正 + 门禁机制加固（`a0ec575`）

### C1. 「设备正在执行」到底怎么判 —— 两个坑

| 坑 | 事实 | 后果 |
|---|---|---|
| `run_command` 有行 ≠ 设备正在执行 | `run_command` 是**步结束后**才 INSERT 的（`status` 直接写 `completed`/`failed`，`sent_at`/`finished_at` 都是 `now()`） | 第一版脚本把「这一步跑完了」当成「指令刚发出去」⇒ 暂停发出去时设备早跑完了 ⇒ **测的根本不是「执行中暂停」** |
| `max(id) FROM run` 会抓到别人的 run | 表里留着别的测试的 run（有指令、有完成态） | 实测抓到 `workflow_id=1255` 的旧 run（它 11:58 就跑完了）⇒ 整段断言**在别人的证据上做的** |

**正解**：`device_state.status='running'` + `current_method` 非空（`markDeviceBusy` 在 `onStepStart` 置、`markDeviceIdle` 在 `onStepEnd` 复位）+ `current_run_id` 确认归属；自己的 run 一律按 `run.workflow_id = 本次新建的流程` 定位。

**结论也随之订正**：第一版输出里那句「暂停根本没生效」是**误判**（暂停发晚了）；真实情况是「暂停生效，设备动作照旧跑完」。

### C2. 门禁解析子脚本输出时区分「挂掉」与「红了」

新增 `parse_summary`（`scripts/ci-gate.sh`）：汇总行缺失（脚本异常退出 / 没跑到最后一行）与「有失败用例」是**两种不同的原因**，
前者以前被兜底成「失败 1 条」但一条 `✗` 明细都打不出来 —— 表现就是「门禁红了却看不出为什么」。
现在汇总行缺失单独判一类并打出输出尾部；`e2e-pause-resume-nodes.py` 的**每条退出路径**都补打汇总行。

**验证**：门禁 4.17 由红转绿（4/0）。

## D. 超时按方法取 + A1 真停机制 + 4 个真 bug

### D1. 超时按方法取（纯 bug 修复）

**改动前**：驱动层用**执行器级固定 30 秒**；而 `device_method.timeout_sec` / `workflow_node.timeout_sec`
**存了值没人读**（`grep timeout_sec` 在 driver/ 下零命中）⇒ **任何超过 30 秒的真机方法都被中控判超时**
（离心 5 分钟、PCR 几十分钟、孵育 30 分钟必挂）—— 与暂停无关，是纯 bug。

**取值链**（`labos-kernel/src/main/java/com/labos/kernel/driver/MethodTimeoutPolicy.java`，纯逻辑，可单测）：

```
device_method.timeout_sec（设备 + 方法精确匹配）
  → 该设备方法库上限（device_method 的 MAX(timeout_sec)）
    → workflow_node.timeout_sec（流程节点级）
      → 能力默认（按设备的真实能力查表）
        → 兜底 30 秒
```

**补齐各能力默认超时**（分片 `pg_rebuild/schema/99a_method_timeout.sql`，幂等，UPDATE 260 行）：
孵育 1800s / 扩增-PCR 3600s / 离心 900s / 洗板 900s / 其余 600s（通用保底）。
**设备库里已有的 3s/5s/20s/302s 原样保留** —— 那是真机契约（预计耗时 × 2），
抬高等于把「扫码机死了」从 3 秒才发现变成 10 分钟才发现。

**实测**：`[超时] ARM Home → 600 秒（来源 device_library）` ⇒ 设备方法跑 **48 秒**正常回包，
**不再被 30 秒误杀**（改之前这一次必然 `failed`）。

**实现中踩到的四个坑**（都会**静默**退回 30 秒，所以必须打日志）：

1. `ctx.resourceId()` 其实是 **device_instance.id**（证据：`DriverRegistry.driverFor(long deviceInstanceId)`、`candidates()` 都用实例 id）—— 用 resource_node.id 查 ⇒ 全部落空。
2. 能力默认必须用**设备的真实能力**（`resource_capability`）—— 节点上的能力码是按名字**启发式猜**的（`resolveCapability` 第 6 级：节点名「机械臂搬运」被猜成 WASH）。
3. `resource_capability` 表**没有 `tenant_id` 列** —— 带上它抛 SQLException，被吞掉 ⇒ 静默回落。
4. 解析结果必须打日志（`[超时] …`），否则上面三个坑只能靠猜。

### D2. A1 真停机制（默认全 false）

- **新列**：`device_method.interruptible`（分片 `pg_rebuild/schema/99b_interruptible.sql`，默认 `false`），接口已透出（`QueryService.deviceMethodsJson`）。
- **执行侧**（`DriverStepExecutor.executeCommand`）：
  **没声明可中断 ⇒ 老路径**（调用线程直接阻塞等回包，**行为一字不变**）；
  声明了可中断 ⇒ 放到工作线程里等，主线程每 200ms 查「是否该停」
  （workflow 级 `run.status='paused'` ／ 实验级 `runtime_hold` 覆盖），命中就 `driver.abort(commandId)`。
- **中断后的数据**：命令/步骤行记 **`aborted`**（按 `EC-99-0005` 与真失败分开），run 落 `paused`；
  恢复时 `resumeAsync` 删掉非 completed 的行 ⇒ **这一步会重跑**。
- **实测**：命令 **0.3 秒**落终态（设备本身要跑 30–300 秒）——`aborted|EC-99-0005`。
- **为什么默认全 false 是安全的**：没有现场清单之前所有方法走老路径，
  **绝不会因为这个开关把正在搬板的机械臂停掉**；清单到位后置 true 即生效，不必改代码。

### D3. 顺带修掉的 4 个真 bug

| # | bug | 症状 | 修法 |
|---|---|---|---|
| 1 | **能力解析被同名方法带偏** | `loadProtocolCapability` 是 `SELECT dm.method, c.code FROM device_method ...`（**无 DISTINCT、无 ORDER BY**），而 `Home` 同时挂在离心机(221)/转运机器人(145)/洗板机(183)上 ⇒ 结果**取决于物理行顺序** ⇒ 一次 `device_method` 批量 UPDATE 就让它翻面 ⇒ **绑定了机械臂的节点改绑离心机，BPMN 里绑的资源被忽略** | ① `resolveCapability` 新增 **bound 优先级**（绑了哪台设备就用哪台设备的能力，排在协议反查之前）；② 协议映射改 `DISTINCT + ORDER BY`（结果可复现） |
| 2 | **设备锁泄漏（幽灵占用）** | 进程崩溃/API 重启时在飞的设备方法不会走 `onStepDone` ⇒ `markDeviceIdle` 不执行 ⇒ `device_state` 永远停在 `current_run_id=<已死的 run>`；而 `DeviceLock.tryAcquire` 要求 `current_run_id IS NULL OR = 自己` ⇒ **那台设备从此再也不会被任何 run 拿到**（现场：一台设备凭空永远忙） | 启动兜底 `settle` 释放被中断 run 占着的设备锁 |
| 3 | **孤儿锁**（run 被直接删除） | run 没了，锁还在 ⇒ 没人能通过 settle 找到它 ⇒ 同上 | 启动兜底额外释放**指向已删 run 的锁**；且这段清理一度被 `if (found.isEmpty()) return orphans;` **跳过**（自测补了这条出口路径） |
| 4 | **设备锁等待写死 60 秒** | 慢设备（30–300 秒/次）时，前一条流程还占着设备，下一条流程等 60 秒就放弃 ⇒ 「设备被占用超过 60 秒」⇒ 节点转人工 | 改为**按该设备自己登记的方法超时上限**取（下限 60 秒、上限 15 分钟） |

### D4. 三个写死的固定超时（同一类病根）

| 位置 | 改前 | 改后 |
|---|---|---|
| 驱动等设备回包 | 固定 30 秒 | 按方法取（§D1） |
| 抢设备锁 | 固定 60 秒 | 按设备方法超时上限取（§D3-4） |
| 测试脚本等执行 | 固定 90 秒 | 420 秒（慢设备下「设备没跑完」≠「流程没跑完」） |

**共同病根**：它们都假设「设备秒回」，而产品定位恰恰是「设备可能跑几分钟」。

### D5. 配套的测试侧修正（慢设备暴露出来的）

- **等待预算**：流程矩阵 `run(wait=90→420)`、页面矩阵 `run_workflow(wait=90→420)`、
  暂停/恢复脚本三处 `30/40/90 → 420`、仿真机联调 `120 → 420`。
- **清理时机**：测试脚本在**设备还在执行时**删 run ⇒ 在飞的步骤落库时父节点已被删
  ⇒ `run_node_parent_node_id_fkey` 违反 ⇒ 门禁「步骤落库失败」断言变红。
  修法：**清理前等设备 idle（420 秒）+ 删 run 前释放该 run 占着的设备锁**。

## 关键决策与理由

| 决策 | 理由 |
|---|---|
| 能力默认**不抬高**设备库的显式小值 | 那些是真机契约；抬高会让「设备死了」从 3 秒才发现变成 10 分钟才发现 |
| `interruptible` 默认 `false` | 没有现场清单就没有任何方法会被停掉 —— 机械臂掉板是不可逆事故 |
| 中断记 `aborted` 而不是新增词表项 | `node_status` 枚举本来就有 `aborted`；不动词表 = 不动前端 |
| 设备锁等待按设备超时上限取 | 设备最多可能被**合法**占用多久（离心 900s / 孵育 1800s），就等多久 |
| 孤儿锁在**启动兜底**清，而不是删 run 时清 | 删 run 的入口有多个（脚本、后台清理、手工 SQL），兜底一处最不容易漏 |
| 门禁用 `parse_summary` 区分「挂掉/红了」 | 「解析不到」与「解析到非零」是两种原因，处理方式完全不同 |

## 已知缺口（本轮**没有**做的）

1. **真机验证**：全部是仿真机；真机的 `abort` 能否真的打断、机械臂中断会不会掉板，都没验。
2. **现场可中断方法清单未到**：机制齐了，但**没有任何方法被打开**（`interruptible=true` 0 条）。
3. **界面未区分**「等人工继续」与「已中断·将自动重试」。
4. **设备锁的根因未治**：本轮在启动兜底清锁，但「删 run 不释放锁」的入口级问题仍在（见 `02` §2）。
5. **多设备并行执行中暂停**未覆盖（暂停是 run 级的，并行时「停哪个」是设计问题）。
6. **`subProcess` 静默跳过**沿用上一轮裁定（只登记不修）。
