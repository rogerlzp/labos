# 评审规范

> 本文件规定**如何对本项目做评审、如何记录评审、被评审方如何回应**。
> 目的是让评审可追溯：谁在什么时候、用什么模型、看了哪些代码、指出了什么、怎么处置的。

---

## 一、为什么需要规范

之前的评审是零散的对话——评审意见散在聊天记录里，
被评审方的回应也一样，事后无法回答：

- 这条意见当时是谁提的？
- 是在哪份代码版本上提的？
- 被评审方改了吗？改成了什么？
- 如果没改，为什么？

**没有记录 = 无法追责 + 会重复踩同一个坑。**

---

## 二、评审记录必须包含的字段

每条评审记录（一份评审一个文件）必须有以下字段：

| 字段 | 说明 | 示例 |
|---|---|---|
| **评审编号** | `YYYYMMDD-NN`，同一天多次评审递增 | `20261101-01` |
| **评审时间** | 精确到分钟，带时区 | `2026-11-01 21:40 (UTC+8)` |
| **评审模型** | 模型名称与版本（如已知） | `Grok 4.1 Fast` / `Claude Sonnet 4.5` |
| **评审范围** | 看了哪些文件、什么版本（git commit） | `docs/评审指引.md` + `PositionLock.java`，commit `119271a` |
| **评审方式** | 对照源码逐条验证 / 只读文档 / 跑测试 | 对照源码逐条验证 |
| **结论摘要** | 通过 / 有条件通过 / 不通过 | 有条件通过 |
| **意见清单** | 逐条编号，含严重程度 | 见下 |
| **被评审方回应** | 逐条回应：接受/不接受、理由、处置 | 见下 |
| **处置状态** | 已修 / 待修 / 不修（附理由） | |

---

## 三、意见的严重程度分级

| 级别 | 含义 | 处置要求 |
|---|---|---|
| **P0 阻塞** | 数据错误、安全事故、核心功能不可用 | 必须当轮修，或明确降级说明 |
| **P1 严重** | 功能不符预期、文档严重误导 | 本轮或下轮修 |
| **P2 一般** | 描述过时、表述不当、边界不清 | 可排期 |
| **P3 建议** | 结构优化、命名、可读性 | 可记录不修 |

---

## 四、被评审方的回应规则

### 必须逐条回应，不能笼统说"已修"

每条意见的回应必须包含：

1. **结论**：接受 / 部分接受 / 不接受
2. **理由**：为什么不接受（如果是"不接受"）
3. **处置**：改了什么（附 commit 或文件行号）/ 排期到哪 / 为什么不修
4. **验证**：怎么确认改对了

### 不允许的回应方式

| 反模式 | 为什么不行 |
|---|---|
| "已修复"（不说改了哪） | 无法验证 |
| "评审意见已全部采纳"（不逐条） | 大概率有遗漏 |
| 沉默跳过某条 | 等于没评审 |
| 改文档不改代码（或反之） | 造成新的不一致 |

### 特别要求：评审指出的错误必须承认

评审如果指出**被评审方的具体错误**（例如"你说的下一步不成立，代码是这样的"），
被评审方必须：

1. **明确承认**（"评审正确，我之前的判断是错的"）
2. **说明为什么会错**（不是找借口，是防止再犯）
3. **修正文档**（过时的描述要改，不能留着误导下一个人）

---

## 五、评审前的准备（被评审方职责）

评审者不应该花时间在"找入口"上。评审前被评审方必须准备好：

| 项 | 要求 |
|---|---|
| **入口文档** | 一份 `评审指引`，30 分钟内能理解项目、代码、已知问题 |
| **可复现** | 依赖、启动、验证命令能直接跑 |
| **已知问题清单** | **必须诚实**，包括未解决的问题 |
| **版本信息** | 评审针对哪个 commit |
| **不要藏问题** | 藏了问题的评审材料没有价值 |

### 评审材料的常见问题（本项目踩过）

| 问题 | 教训 |
|---|---|
| 只说"已完成"，不说"哪里没做" | 评审者无法判断成熟度 |
| 用仿真结果当真实通过率 | "993 个工艺 100%" 实际是 `SimulatedBus` 走图，不是真设备 |
| 已知问题的"下一步"是猜的 | 评审对照源码后发现方向完全错 |
| 多套文档各说各的 | 评审者不知道该信哪份 |

---

## 六、评审后必须做的事

| 序 | 动作 | 谁 |
|---|---|---|
| 1 | 逐条回应写入评审记录 | 被评审方 |
| 2 | P0/P1 意见修复并附验证 | 被评审方 |
| 3 | 修正被指出错误的文档（不留过时描述） | 被评审方 |
| 4 | 如果评审发现文档体系冲突，**收敛成一套说法** | 被评审方 |
| 5 | 下次评审时检查上轮意见的处置状态 | 双方 |

---

## 七、文档层次规则（本项目专用）

本项目曾出现**四套"以谁为准"**，评审者无法判断。现规定：

```
① 代码 + 数据库 schema        ← 已落地行为的唯一真相
② docs/ 里的设计文档（日期新于规格的）  ← 已设计但部分未落地的
③ LabOS2.0_功能规格说明书   ← 只约束"发布门槛里还没做的事"
④ 根目录旧排期文档 / docs/modules/README.md  ← 已过时，只看历史背景
```

**冲突时的处理**：

- ①②冲突 → **代码为准**，但要在设计文档里标注"代码未实现"或"代码与设计不符"
- ②③冲突 → **先改规格**，不要留两套说法
- 决策编号按**分段分配**，全局不允许重号（2026-11-02 起，原"各文档自建一套 D1-Dn"作废）：

  | 编号段 | 归属 | 条数 |
  |---|---|---|
  | **D1-D11** | `LabOS功能规格说明书.md` 第 12 章（= `决策记录.md`） | 11 |
  | **D101-D119** | `docs/并发调度决策记录.md` | 19 |
  | **D201-D227** | `docs/开发日志.md` | 27 |
  | **D301-D311** | `docs/评审指引.md` 第五章 | 11 |

  **跨文件引用必须带文件名**（如"并发调度 D105"）。新增决策只能在自己的段内
  续号；段位不够时向本表追加新段，**不得挤占他段号段**。

**已标记过时的文档**（开头必须写"已被 XX 取代"）：

- `前后端实施方案_编译甘特就绪调度.md`
- `目标功能文档_三方合并版.md`
- `LabOS_新一代中控实现总纲_20261029.md`
- `docs/modules/README.md`

## 八、评审记录文件命名

```
docs/评审记录/20261101-01-grok.md
                 │     │  └── 评审方标识
                 │     └───── 当天第几次
                 └─────────── 日期
```

一个评审一个文件，**只追加不修改**（后续处置写在文件末尾的"处置更新"小节）。
