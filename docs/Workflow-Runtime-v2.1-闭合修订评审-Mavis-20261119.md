## 四、本轮新发现（独立核查 §31–38 后的问题）

### F1 🔴 Command 状态集合与谓词/异常表术语不一致（进入技术拆解前必须闭合）

§31.5.1 的新 Command 集合（3121 行）里**没有"执行结果 UNKNOWN"态**：投递不确定叫 `DELIVERY_UNKNOWN`，ACK 后执行结果无法核验只能走 `QUARANTINED`（3133 行）。但：
- §31.4.3（3091 行）写"Command/Resource UNKNOWN：不满足谓词"；
- StopSafePredicate #3（3107 行）"不得存在 DELIVERY_UNKNOWN、**UNKNOWN**、ACKNOWLEDGED…"；
- §26 异常表（2658 行）"设备 ACK 丢失 → Command UNKNOWN"；
- §31.2.4 UNKNOWN 核验三类是 Attempt 级，与 Command 级如何对应未写明。

**后果**：实现者在 T14（设备事件消费）遇到"ACK 后最终事件丢失"时，没有唯一归属态。**修法**：二选一并全文统一——(a) Command 集合补 `EXECUTION_UNKNOWN`（ACK 后结果未知），QUARANTINED 只留给资源；或 (b) 全文把"Command UNKNOWN"改写为 DELIVERY_UNKNOWN（投递期）/ QUARANTINED（执行后不可核验），同步修 §26/§31.4.3/§31.4.4。倾向 (b)（更贴近 §31.5.1 现有设计）。

### F2 🔴 "原 T01–T14 保持不变"与 §32 的实质修订矛盾（措辞级，但会误导）

§31.9（3224 行）声明"原 T01–T14 保持不变"，但：
- §32.1 把 T04 的一次性"Accept+Start"拆成两条消息两个事务（语义重构，非补充约束）；
- §32.2 把 T08 的"创建后续 Attempt"**反转为**"不得在 T08 内创建，下一次 T03 创建新 Attempt"；
- §32.3 给 T10 加了消费全部分支 Token、关闭 Branch 的原子步骤。

表行虽有"并受 §31.2–§31.7 的补充约束"兜底，但引用范围不含 §32，且"保持不变"与"语义反转"（T08）直接冲突。**修法**：§31.9 改为"原 T01–T14 的事务主题保留，凡被 §32 修订处以 §32 为准"，并给出 T03/T04/T07/T08/T10/T13 六个被修订事务的显式清单。

### F3 🟡 §23.4.2 与 §31.2.1 的 Activation 转移点冲突（覆盖条款可解，建议就地修）

§23.4.2：`READY | AttemptCreated → ACTIVE`；§31.2.1（2985 行）：只有 Dispatch Commit 才置 ACTIVE。两处给出不同答案，覆盖条款虽然生效，但这正是编码时最容易各取所需的一类。建议 v2.2 就地改 §23.4.2 该行。

### F4 🟡 §31 前言引用不存在的 "§32–§39"

文档止于 §38（2909 行）。规范性覆盖范围声明引用了一个不存在的章节号——恰好出现在定义"以谁为准"的句子里。应改为 §32–§38。

### F5 🟡 Token 数据结构缺 waitKind / waitOwnerRef 字段

§31.2（2933 行）与不变量 §34.1 要求 Token=WAITING 必须关联唯一 wait owner（RetryRegistration/WaitRegistration/Join），但 §4.1 的 Token 记录结构没有这两个字段。不变量没有数据承载点，T07/T08/T10 的事务写集合也就无法落在具体列上。建议补进 §4.1 或 §31.2。

### F6 🟡 消息/事件目录已过期

§14.1 事件目录与附录 A RuntimeMessage 清单未随 §31 更新：`RetryRegistration` 生命周期事件、`DrainStarted/DrainCompleted`、`RecoveryCompleted`（§31.7.4 新引入）、`ProtocolViolation`（§31.7.1）、`WorkerAccepted` 与 `NodeStarted` 的拆分、`DELIVERY_UNKNOWN` 迁移，均不在目录中。T01–T23 是消息驱动的，目录是消息的唯一清单——建议 v2.2 同步补齐。

### F7 🟡 T17 Reservation Reconcile 对已 ACQUIRED 租约的处置未定义

§31.4.3 说撤销 RESERVED 时"仅当 ResourceLease 尚未取得物理资源所有权时才可释放该软件预留"——言下之意租约可能已 ACQUIRED，但**已 ACQUIRED 时是保留（暂停后继续用）还是走释放协议，没有规则**；若保留，Pause 期间持有物理租约与 PauseSafePredicate #6 的"租约保持有效"如何衔接也没写。建议 T17 增加一条：ACQUIRED 租约按 owner 意图分类（Pause 保留 / Stop 走 RELEASE_PENDING 或核验释放）。

### F8 🔴 变量 CAS × 设备节点完成（我第二轮 P1-5.3）仍未修，且被"保持不变"固化

T05（§25.6）仍把变量 CAS 写进完成事务，冲突→整体回滚。对设备节点：物理动作已发生而逻辑完成丢失，重试路径落到"同 commandId 幂等重发"，依赖设备能力（UNKNOWN-02）。建议在技术拆解 T05 时裁决：完成事务内重读重放（Coordinator 单写者使其可行），或设备节点完成与变量写解耦。**这条应进入 T05 的事务设计评审清单，而不是留到实现期发现。**

### F9 🟢 提醒（不阻塞）：workflow_run 单行锁成为全系统热点

§31.4.1 要求 Dispatch Commit 与 Pause/Stop Request 都锁同一 Run 行，T19 Drain Complete、runCommitVersion 递增同样如此。单实例下正确且够用；但这是把吞吐上限锚在"每 Run 每事务一次行锁竞争"上，与 WRT2-11（WorkerPool 容量/配额压测）应合并验证，避免 Stage E 才发现锁热点。

### F10 🟢 提醒：Checkpointer 的"暂停 Run 提交"机制未定义

§31.7.3 说数据库不支持跨表一致快照时"通过 Run 锁定并暂停该 Run 的状态提交"——暂停的机制（mailbox quiesce？version CAS 失败重试？）未定义，且与"Coordinator 不阻塞等待"原则（§8.5）存在张力。建议标注为实现期设计项，并优先选支持快照隔离的数据库（UNKNOWN-01 直接决定这条路是否需要）。

## 五、对 §37 自评的两点说明

1. **"文档内部 PASS"的可信度**：我独立抽查了 §37.1 的 14 项判定，落点均真实存在，无虚报。但要强调：这是**同一作者的自评**（§37.1 也如实声明了范围），PASS 的含义是"作者未再发现阻断项"，不是外部验证。本轮我仍找到 F1/F2/F3 等 10 项，说明覆盖式修订的边际收益在下降——**第三方的"找不到"比作者自己的 PASS 值钱，建议下一轮关闭项仍走独立评审**。
2. **UNKNOWN-01~05 的诚实划分是本轮最大进步**：把"文档能证明的"与"只能靠实现验证的"分开，避免了文档越来越厚、验证欠账越滚越大的老路。

## 六、下一步建议（作者方向正确，建议加三条排序约束）

作者的判断"下一步不是继续扩写架构文档，而是把 T01–T23 转化为数据库事务设计、状态转移自动化测试和故障注入测试"——**同意，并建议按以下顺序**：

1. **v2.2 就地修订（小，1 次 commit）**：修 F1–F6（F7/F8 可作为待决问题登记），顺手做"覆盖索引表"（旧条款 → 新条款映射），终止"覆盖式修订"——覆盖条款机制在两轮内有效，第三轮开始会让读者需要脑内 diff 两份规范。
2. **DDL-first 关闭 UNKNOWN-05**：先写 T01–T23 的物理 DDL（唯一约束、CAS 条件列、索引），用约束反向验证事务读写集合——这是 UNKNOWN 项里唯一不依赖外部环境、纯本地可做的。
3. **UNKNOWN-01 用选定 DB 的能力清单直接验证**（MVCC 快照隔离、`SELECT FOR UPDATE`、`UPDATE ... WHERE version=` CAS、事务内序号分配）：这些是 Postgres 系的标准能力，验证成本低，应最先关闭。
4. UNKNOWN-02/03/04 依赖设备/Worker 实现，放进 Stage D 的 Adapter 能力表验收，不要提前假设。
5. 与实现并行的三条用户级决策不变：双轨 vs 转向、存量流程图全量扫描、存量台账/物料映射表（Stage D 前置）。
